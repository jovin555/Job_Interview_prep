# high-speed-digital-fpga — Day 58

## Q1: How would you approach designing the configuration and reconfiguration path for an FPGA that must support both a factory fallback image and a field-updatable application image stored in external flash, where a failed update must never leave the board unbootable?
**Answer:** The core principle is that the device must always have a known-good image it can fall back to, independent of whatever happens to the updateable image. I'd structure the flash into at least two regions: a small, rarely-touched factory/fallback bitstream, and one or more application image slots. The FPGA's configuration controller is set up so that on power-up it attempts the application image first, and if configuration fails — CRC error, watchdog timeout, or the device simply never asserts its init-done handshake — the controller automatically falls back to the factory image. The factory image's only job is to bring up a minimal system: enough to talk to the host over whatever management interface exists, report that the application image is bad, and accept a new one. That keeps the recovery path small and easy to validate.

For the update itself, I'd never overwrite the currently-running image in place. The new image is written to the inactive slot, its integrity is verified (checksum or signature over the whole image, checked before it's ever selected for boot), and only then is a boot-select flag updated — ideally with a redundant copy of that flag so a power loss mid-write can't corrupt the selection logic. A common refinement is a "trial boot" counter: the new image is marked as pending, and the factory image or a small boot supervisor increments a counter each time the new image is attempted; if it fails to reach a "commit" point within N attempts, the system reverts. This handles the nasty case where the new image configures fine but hangs before it can do anything useful.

I'd also think about the flash access characteristics — access latency, page/sector erase granularity, and whether the flash is shared with other consumers. If the FPGA loads directly from flash via its own configuration engine, the timing requirements are dictated by that engine, not by me. If a separate microcontroller or processor stages the image, I need to make sure the staging path can't be interrupted in a way that leaves a half-written slot marked as valid. The verification step before committing is what buys that safety.

**Possible follow-ups:**
- How would you decide how many application slots to provide, and what trade-offs does that introduce in flash capacity and update complexity?
- If the board has no separate management processor and the FPGA must self-recover, how does the fallback image know the application image failed rather than just being slow to start?

## Q2: How would you approach debugging an FPGA design where the device configures successfully and runs correctly for a while, but then appears to lose its configuration — it stops responding and only recovers after a full reconfiguration?
**Answer:** The symptom — runs fine, then stops, and a reconfiguration fixes it — points at something that either corrupts the configuration memory or resets the device out of its configured state, rather than a design logic bug. I'd start by separating those two possibilities.

First, is the device actually losing configuration, or is it still configured but hung? The INIT/DONE pins and any configuration-status signals tell me which. If DONE drops, the device genuinely lost configuration — that's a configuration-memory integrity or power event. If DONE stays high but the design is unresponsive, it's more likely a logic lockup, a clock loss, or a reset that the design didn't handle.

If configuration is genuinely being lost, the usual suspects are: a power glitch on the configuration-related rails (a transient that dips below the device's brownout threshold), a single-event upset in a radiation environment, or a configuration memory corruption from an external source. I'd instrument the power rails with a scope set to trigger on a droop, and check whether the failure correlates with some other activity on the board — a motor, a relay, a high-current load switching. On the logic side, I'd check whether the design has a watchdog that can detect a hung state and trigger a reconfiguration itself, which is good practice regardless.

If it's a logic lockup rather than true configuration loss, I'd look at clock loss (a PLL losing lock and the design stalling), an unhandled illegal state in an FSM, or a reset that's asserted but never released. The fact that a full reconfiguration recovers it is consistent with any of these, so the diagnostic is to catch the failure in the act — a logic analyzer on the status pins, or an internal debug core that captures the state just before the hang.

The fix depends on the cause: if it's power, it's a decoupling or sequencing problem; if it's SEU, it's a scrubbing or redundancy strategy; if it's a lockup, it's a watchdog plus a reconfiguration trigger. The important thing is not to jump to "the FPGA is flaky" — the device is telling you something specific, and the status pins are where to start reading it.

**Possible follow-ups:**
- How would you distinguish a configuration-memory upset from a power-rail brownout if both produce the same "device stops responding" symptom?
- What would you put in place so the board can recover on its own without a human power-cycling it?

## Q3: How would you approach designing the interface between an FPGA and an external ADC that uses a source-synchronous, double-data-rate (DDR) output bus, where the data and a forwarded clock arrive at the FPGA with an unknown but bounded skew between them?
**Answer:** The key insight is that with a forwarded clock, the FPGA doesn't need to know the absolute skew — it needs to capture the data with enough timing margin that the skew, whatever it is within its bound, doesn't push the capture point outside the valid window. The forwarded clock travels alongside the data, so the skew between them is dominated by PCB trace matching and the output characteristics of the ADC, not by the FPGA's internal clock distribution.

The standard approach is to use the FPGA's input delay elements (IDELAY) or a similar per-input programmable delay to shift the capture point. I'd bring the forwarded clock into a dedicated clock-capable input, route it through the FPGA's clock management (a PLL/MMCM or a BUFG/BUFR network as appropriate), and use that to clock the input capture registers. The data lines go through IDELAY so I can individually adjust where each bit is sampled relative to the clock edge. Because it's DDR, I need to capture on both edges — typically by using an IDDR primitive or by capturing on a clock that's phase-shifted 90° and then doing the edge separation in logic.

The calibration strategy is where the real work is. I'd implement a training pattern — the ADC or the system drives a known sequence (a PRBS or a walking-1 pattern) during bring-up, and the FPGA sweeps the IDELAY taps to find the window where the pattern is captured correctly. The center of that window is the optimal tap. This is essentially the same idea as read-leveling in a DDR memory interface, applied to the ADC link. The window width tells me the timing margin; if it's too narrow, the board layout or the ADC's output timing is the problem, not the FPGA settings.

I'd also make sure the forwarded clock is treated as a clock, not as data — it needs to go to a clock-capable pin and be handled with proper clock-domain constraints. And I'd constrain the input path in the timing constraints so the tools know the relationship between the forwarded clock and the data, even though the actual skew is unknown — the constraint expresses the bound, and the IDELAY calibration handles the rest.

**Possible follow-ups:**
- How would you handle the case where the calibration window is so narrow that no single IDELAY tap gives reliable capture across all boards?
- What changes if the ADC's forwarded clock is not continuous — for example, it stops when the ADC is idle?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?
**Answer:** The uncomfortable truth is that timing analysis only tells you about the paths you've constrained. An unconstrained path is silently ignored — the tool reports "timing met" because it never checked the path that matters. So the verification effort has to focus on finding what's *not* constrained, not just on confirming that the constraints you wrote are satisfied.

I'd start by auditing the clock definitions. Every clock in the design — every PLL output, every forwarded clock, every external clock input — needs a create_clock or create_generated_clock. If a clock is defined but its relationship to another clock isn't, the paths between them are either falsely analyzed as related or not analyzed at all. I'd cross-check the clock list against the design's actual clock sources, including any clocks that come in through I/O and any that are generated internally.

Next, the I/O constraints. Every input and output needs set_input_delay/set_output_delay relative to its clock, with values that reflect the actual external device's timing. This is where a lot of designs get it wrong — the constraints are written from the FPGA's perspective without accounting for the board-level skew and the external device's setup/hold requirements. I'd verify these against the datasheets of the external components and the board's trace matching.

Then the exceptions: false paths and multicycle paths. These are the most dangerous constraints because they tell the tool to *stop* analyzing a path. Every false path should be justified — usually a CDC that's handled by a synchronizer, or a path that's genuinely don't-care. A false path applied to a path that actually needs to meet timing is a silent failure. I'd review each exception and confirm it's correct, and I'd be especially suspicious of any exception that was added to make timing close rather than because the path is genuinely exempt.

Finally, I'd use the tool's own reporting to find gaps: unconstrained paths, unconstrained endpoints, clocks with no relationship defined. Many tools have a "check_timing" or equivalent report that lists these. I'd also run the design through a CDC analysis tool to catch any crossing that isn't properly synchronized, since those often show up as unconstrained or falsely-constrained paths. The goal is to have zero unconstrained paths and every exception justified before sign-off.

**Possible follow-ups:**
- How would you catch a path that's constrained but with the wrong clock relationship — for example, a CDC that's been given a false path when it should have been synchronized?
- What's your process for reviewing constraints written by someone else on the team?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?
**Answer:** This is a situation where the engineer's reasoning is superficially plausible but misses the actual failure mode, so the goal is to correct the understanding, not just the code. The signal being "stable long enough" addresses the wrong problem — the issue with an unsynchronized CDC isn't that the signal changes too fast, it's that the receiving flop can go metastable if it samples the signal while it's transitioning, and metastability can propagate unpredictably through downstream logic. A signal that changes rarely is actually *more* likely to be sampled during a transition relative to its change rate, not less, because the transition is the only time it's not stable.

I'd start by asking the engineer to walk me through what happens at the receiving flop when the source signal transitions. If they can articulate the metastability concern, we can discuss why a two-flop synchronizer (or the appropriate synchronizer for the signal type) addresses it. If they can't, that's the teaching moment — I'd explain the physics: the receiving flop has a setup/hold window, and if the input changes within that window, the output can hover between logic levels for an indeterminate time. The synchronizer gives that metastable state a full clock cycle to resolve before the signal is used, which reduces the probability of propagation to an acceptable level.

I'd also make sure the fix matches the signal type. A single-bit level signal needs a two-flop synchronizer. A single-bit pulse needs a pulse synchronizer or a toggle-based handshake, because a two-flop synchronizer can miss a pulse that's shorter than the destination clock period. A multi-bit bus needs either a handshake, a FIFO, or a gray-coded counter — you can't just synchronize each bit independently, because the bits can arrive skewed relative to each other. If the engineer's signal is a multi-bit value, the fix is more involved than a two-flop synchronizer, and I'd want to make sure they understand why.

Throughout, I'd keep the tone collaborative — the engineer isn't wrong because they're careless, they're wrong because CDC is genuinely subtle and it's a common gap. I'd use it as a chance to establish a team norm: any signal crossing a clock domain gets reviewed specifically for synchronization, and the CDC analysis tool's warnings are treated as real. I'd also offer to pair with them on the fix so they see the pattern applied, rather than just handing them a correction.

**Possible follow-ups:**
- How would you handle it if the engineer pushed back and said the design has been running in the lab for weeks without a problem?
- What would you put in place on the team to catch this kind of issue before design review, rather than during it?
