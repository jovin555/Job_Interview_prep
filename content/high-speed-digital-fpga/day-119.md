# high-speed-digital-fpga — Day 119

## Q1: How would you approach designing the power-up and configuration sequence for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?

**Answer:** I'd treat this as a state-machine problem with explicit dependencies rather than letting each block self-start. The first step is to enumerate the ordering constraints from the device documentation: which rails must be stable before the configuration engine is released, whether the configuration engine must complete before the PLLs are allowed to lock, and whether the transceiver quads require their reference clocks and analog rails to be valid before their reset is deasserted. From that I'd build a supervisor — either a small CPLD/power-management IC or a state machine in the FPGA fabric itself — that sequences rail enables, waits for each power-good with a timeout, releases configuration, waits for the init/done handshake, then releases the PLL resets, waits for lock, and only then releases the transceiver resets and starts link training.

The key discipline is that every wait has a bounded timeout and a defined failure action, so a stuck PLL or a slow flash doesn't hang the board silently — it either retries or flags an error to the host. I'd also make the sequence observable: status registers or test points for each stage so bring-up and field diagnosis don't require guesswork. Where the FPGA supports it, I'd use the dedicated configuration-status pins rather than inferring state from behavior. Finally, I'd verify the sequence against the datasheet's power sequencing and ramp-time requirements, and test it under fast power-cycling and slow-ramp conditions, since those are where out-of-order release problems usually surface.

**Possible follow-ups:** How would you handle a PLL that occasionally fails to lock on a cold start — would you retry, and how many times before declaring failure? How do you keep the supervisor itself from being the single point of failure?

## Q2: How would you approach debugging an FPGA design where the transceiver link passes its built-in PRBS checker at the physical layer, but application-level data is occasionally corrupted, and the corruption only appears at full line rate?

**Answer:** The PRBS checker passing tells me the SerDes analog front end, CDR, and equalization are healthy — the eye is open at the sampling point. So the corruption is almost certainly above the PMA: in the PCS, the framing, the clock domain crossing between the recovered clock and the fabric, or the datapath logic. The fact that it only appears at full line rate points at timing margin or flow-control rather than a hard logic bug.

My approach would be to bisect the path. First, I'd confirm whether the errors are bit errors, word errors, or packet/frame errors — that distinguishes a serialization/deskew problem from a FIFO overflow or a framing counter wrap. I'd instrument the receive path with error counters at each stage: after the PCS deserializer, after the elastic buffer, and after the CDC into the fabric. If errors appear only after the elastic buffer, I'd look at the buffer's overflow/underflow flags and whether the recovered clock and the fabric clock are drifting relative to each other — at full rate the buffer has the least headroom. If errors appear at the deserializer, I'd check comma/alignment-word detection and lane deskew.

I'd also check the transmit side: at full rate, a FIFO feeding the transmitter can underflow if the fabric can't sustain the rate, producing idle or corrupted words that the PRBS checker never sees because it's injected downstream. Running a PRBS through the full application datapath rather than just the PMA loopback is the way to localize that. Throughout, I'd use the transceiver's eye monitor and error counters as a health check to prove the analog layer stays clean while I chase the digital cause.

**Possible follow-ups:** How would you distinguish an elastic-buffer overflow from a genuine bit error using only the transceiver's status registers? What would you change in the design if the root cause turned out to be fabric-side throughput rather than the link itself?

## Q3: How would you approach designing the decoupling and bulk capacitance network for an FPGA's transceiver power rails, where the rails see both high-frequency switching noise from the SerDes and slower, larger current transients from the fabric, and you need to verify the network is adequate before committing to the layout?

**Answer:** I'd start from the impedance profile the rail needs to present across frequency, not from a capacitor count. The transceiver rails have a tight ripple spec and are sensitive to high-frequency noise, so the target is a low, flat impedance from the low hundreds of kilohertz up to the point where the on-die capacitance and package take over — typically a few hundred megahertz. The bulk capacitors handle the low-frequency, large-transient end (fabric current steps), the mid-range ceramics handle the hundreds-of-kilohertz-to-tens-of-megahertz band, and the small high-frequency ceramics plus package and die capacitance cover the top.

The practical method is to model it: build the PDN in a simulation tool with the VRM output impedance, the capacitor models including ESR and ESL, and the plane spreading inductance, then sweep the impedance. I'd check for anti-resonance peaks where a bulk cap's inductance resonates with the ceramics — those peaks are where a transient can push the rail out of spec even though the average impedance looks fine. I'd also account for the mounting inductance of each capacitor, since a via and trace can dominate a small cap's ESL and make it useless at the frequency it was chosen for.

Before committing to layout, I'd verify with the vendor's PDN recommendation as a sanity baseline, then confirm the simulated worst-case transient droop against the rail's tolerance. After layout, I'd re-extract with real parasitics and, if possible, measure with a network analyzer or a scope on a test point during a known load step. The point of the pre-layout model is to catch the anti-resonance and mounting-inductance mistakes while they're still cheap to fix.

**Possible follow-ups:** How would you decide where to place the bulk capacitors relative to the transceiver quads versus the fabric? What measurement would you make on the first prototype to confirm the model was right?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?

**Answer:** I treat "timing analysis passes" as a claim that needs independent evidence, because the tool only checks what it was told to check. My process has three layers. First, constraint completeness: I'd review the constraint file against the design's actual clock domains, I/O interfaces, and generated clocks, and cross-check that every clock the design uses is either defined or derived, every I/O has an input/output delay relative to a real reference, and every asynchronous crossing is either synchronized in RTL or explicitly excepted with a documented reason. A constraint-coverage or CDC report from the tool is a good starting point, but I'd read the exceptions myself — a false path on a real crossing is the classic silent failure.

Second, I'd sanity-check the constraints against the interfaces: for a source-synchronous ADC or a DDR interface, the input/output delays should be derived from the datasheet's setup/hold and board skew, not guessed. I'd verify the numbers trace back to a calculation. Third, I'd look for the failure modes the tool won't catch: unconstrained paths that get optimized away, multicycle paths that are actually single-cycle, and clock-domain crossings that pass static analysis but have no synchronizer.

Before sign-off I'd also run the design at multiple corners and confirm the slack margins are believable rather than razor-thin everywhere, and I'd compare post-synthesis versus post-route timing to catch constraint interpretation differences. Where the budget allows, gate-level simulation with back-annotated delays on the critical interfaces is the strongest confirmation that the constraints match reality.

**Possible follow-ups:** How would you audit a constraint file you inherited from another engineer? What's your rule for when a false-path exception is legitimate versus a red flag?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?

**Answer:** I'd start by separating the technical question from the interpersonal one. Technically, the exceptions might be entirely correct — multicycle paths are legitimate when the logic genuinely has multiple cycles to settle, and false paths are legitimate when a path is structurally never sensitized. But "it closes with the exceptions" is not evidence that the exceptions are right, so the review needs to establish that each one is justified by the design's actual behavior, not by the closure result.

In the review, I'd ask the engineer to walk through each exception and explain, for that specific path, why the multi-cycle or false-path assumption holds — what the source and destination registers are, what the enable or handshake is that guarantees the timing, and how that's enforced in RTL. If the justification is solid and documented, the exception stays. If it's "the path doesn't matter," that's a red flag and we treat it as an unconstrained path until proven otherwise. I'd frame this as a shared standard rather than a challenge to the engineer: every exception gets a comment in the constraint file explaining why, so the next person to touch the design can audit it.

I'd also make sure the engineer understands the risk — an incorrect exception produces a design that passes analysis and fails in the field, which is the worst kind of bug because it's invisible until hardware. If we can't justify an exception, we either fix the RTL to meet single-cycle timing or add a proper synchronizer/handshake. The goal is a constraint set we can defend, and I'd want the engineer to own that defense rather than feel overruled.

**Possible follow-ups:** How would you handle it if the engineer's justification turned out to be wrong but the design still worked in the lab? What would you change in the team's review process so this gets caught earlier next time?
