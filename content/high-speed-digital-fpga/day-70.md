# high-speed-digital-fpga — Day 70

## Q1: How would you approach designing the clock domain crossing for a multi-bit Gray-coded counter value that increments continuously in a fast domain (e.g., 250 MHz) and must be sampled by a slower domain (e.g., 50 MHz) for logging, where the sampled value must always be a coherent snapshot and never a corrupted mix of bits?

**Answer:** The key insight is that a Gray code guarantees only one bit changes per increment, so a single-bit metastability event can corrupt at most one bit — and even then, the sampled value is either the old or new count, never a wildly wrong value. The standard approach is: register the Gray-coded counter in the source domain, pass each bit through a two-flop synchronizer in the destination domain, then convert the synchronized Gray value back to binary in the destination domain. The two-flop synchronizer resolves metastability on the single transitioning bit; because only one bit transitions per source clock, the destination either captures the pre-transition or post-transition value — both are valid snapshots. Important caveats: the counter must be Gray-coded at the source (not converted after synchronization), the destination clock must be slower than or comparable to the source clock (otherwise multiple transitions can occur between destination samples, breaking the single-bit-change guarantee), and the Gray-to-binary conversion must happen entirely in the destination domain. I'd also add a small amount of hysteresis or a "value stable" flag if the consumer needs to know the sample is settled. For very wide counters, I'd verify the synchronizer timing with static timing analysis and confirm the synchronizer flops are placed close together physically.

**Possible follow-ups:**
- What happens if the destination clock is faster than the source clock — does the Gray-code approach still work?
- How would you verify in simulation that the CDC is actually safe, given that metastability is a physical phenomenon?

## Q2: How would you approach designing the return-current path for a high-speed digital board where a signal transitions between two reference planes (e.g., from a ground plane to a power plane) on its way through a via?

**Answer:** The fundamental principle is that every high-speed signal has a return current that follows the path of least impedance — at high frequency, that means directly underneath the trace in the adjacent reference plane. When a signal via transitions from a layer referenced to ground to a layer referenced to a power plane, the return current must also transition between those two planes. If there's no low-impedance path for that transition, the return current is forced to take a long detour, creating a large loop area that radiates and causes signal integrity problems. The standard mitigation is to place a stitching capacitor (or a set of them) close to the signal via, connecting the two reference planes. The capacitor provides a low-impedance path for the return current at the frequencies of interest. The value and placement matter: the capacitor must be close enough that its inductance doesn't dominate, and its self-resonant frequency should be above the signal's highest significant frequency component. For very high-speed signals, I'd also consider whether the stack-up can be arranged so the signal stays referenced to the same plane throughout its route, avoiding the transition entirely. If the transition is unavoidable, I'd simulate the via transition with a 3D field solver to confirm the impedance discontinuity is acceptable, and I'd verify the stitching capacitor placement in the layout review.

**Possible follow-ups:**
- How would you decide how many stitching capacitors to place and where exactly to place them?
- What's the difference in return-path behavior between a signal transitioning between two ground planes versus between a ground plane and a power plane?

## Q3: How would you approach debugging an FPGA design where the DDR3 memory interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** This is a classic temperature-dependent timing margin issue. The fact that calibration passes at power-up but fails after warm-up suggests the timing margins are marginal and shift with temperature. My approach would be: first, confirm the correlation with temperature by monitoring the board temperature and the exact time-to-failure — does it fail at a consistent temperature, or is it random? Second, check whether the failure is in the read path, write path, or both, by running targeted memory tests that isolate read vs. write. Third, look at the calibration data — many DDR controllers log the calibrated delay values (write leveling, read gate training, read/write DQS-to-DQ skew). If those values are near the edge of their valid window at power-up, temperature drift can push them out of range. Fourth, consider the physical causes: temperature affects trace propagation delay (FR4 dielectric constant changes with temperature), driver/receiver output impedance, and the DLL/PLL in the memory controller. I'd also check whether the memory device's own timing parameters (tRCD, tRP, etc.) are being derated for temperature — some DDR devices have temperature-dependent refresh requirements. The fix might be to re-run calibration periodically, add temperature compensation to the delay values, or increase timing margins by reducing the clock frequency or adjusting the board layout. I'd also verify the power supply rails are stable across temperature — a marginal VDDQ can cause timing failures.

**Possible follow-ups:**
- How would you determine whether the issue is in the FPGA's memory controller or the DDR device itself?
- What changes would you make to the calibration routine to make it more robust across temperature?

## Q4: How would you approach designing the decoupling and bulk capacitance network for an FPGA's transceiver power rails, where the rails see both high-frequency switching noise from the SerDes and slower, larger current transients from the fabric, and you need to verify the network is adequate before committing to the layout?

**Answer:** The transceiver rails are challenging because they have two distinct noise profiles: high-frequency switching noise from the SerDes (hundreds of MHz to GHz) and slower, larger current transients from the fabric (kHz to low MHz). The decoupling network must address both. My approach would be: first, determine the target impedance across the frequency range of interest using the FPGA vendor's power delivery network (PDN) guidelines — typically the transceiver rails have a tighter ripple specification than the core rail. Second, build a capacitor bank that provides low impedance across the full frequency range: bulk capacitors (hundreds of µF) for the low-frequency transients, mid-frequency capacitors (1–10 µF) for the mid-range, and small ceramic capacitors (0.1 µF, 0.01 µF) for the high-frequency SerDes noise. The key is to minimize the parasitic inductance of the mounting and via structure — use multiple vias per capacitor, place capacitors on the same side as the FPGA if possible, and keep the loop area small. Third, verify the design before layout using a PDN simulation tool: model the VRM, the PCB planes, the capacitors (with their ESR and ESL), and the FPGA's current profile, then simulate the impedance vs. frequency and the transient response. I'd also check the anti-resonances between capacitor values — sometimes adding more capacitors of different values creates a high-impedance peak between their self-resonant frequencies. Finally, after layout, I'd measure the actual rail noise with a high-bandwidth probe and compare to the specification.

**Possible follow-ups:**
- How would you measure the transceiver rail noise accurately, given that the noise is in the hundreds of MHz range?
- What's the trade-off between using more capacitors of smaller value versus fewer capacitors of larger value?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?

**Answer:** This is a teaching moment, not a confrontation. The engineer's reasoning is a common misconception — "stable long enough" is not a valid synchronization argument because it doesn't account for metastability, which is a probabilistic phenomenon that depends on the relationship between the signal transition and the destination clock edge. My approach would be: first, acknowledge that the signal may indeed work correctly in most cases — that's what makes these bugs so insidious. Then explain the actual risk: when the signal transitions close to the destination clock edge, the destination flop can enter a metastable state, and the output is unpredictable — it may resolve to the correct value, the wrong value, or oscillate before settling. The probability is low per event, but over millions of clock cycles and across many boards, it will eventually cause a failure. I'd walk through the standard solution: a two-flop synchronizer for a single-bit signal, or a handshake or FIFO for multi-bit data. I'd also point out that the fix is cheap — two flops and a timing constraint — compared to the cost of debugging an intermittent field failure. If the engineer is still unconvinced, I'd suggest we add the synchronizer and run a formal CDC check to confirm there are no other unsynchronized crossings. The goal is to make the engineer understand the principle, not just fix this one instance, so they apply it in future designs.

**Possible follow-ups:**
- How would you verify that all CDC paths in the design are properly synchronized before sign-off?
- What would you do if the engineer argued that adding a synchronizer would add latency that the design can't tolerate?
