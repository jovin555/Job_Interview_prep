# high-speed-digital-fpga — Day 109

## Q1: How would you approach debugging an FPGA design that passes timing analysis at the nominal corner but produces occasional corrupted samples only when the board is cold (below the specified operating range), and the corruption disappears once the board warms up?

**Answer:** Cold-only failures point to a parameter that shifts monotonically with temperature, so the first step is to figure out which one. The usual suspects are oscillator startup/frequency drift, PLL lock behavior at cold, and the delay of on-chip or on-board timing paths that were characterized at 25 °C. I'd start by instrumenting the design to distinguish "data is wrong" from "data is being captured at the wrong time." A useful trick is to add a slow, known test pattern generator (e.g., a counter or PRBS) into the same capture path and log the first divergence — if the pattern is corrupted in a way consistent with a one-bit slip, it's a capture-timing problem, not a data-path logic problem.

Next I'd separate the clocking from the data path. Check whether the PLL/MMCM is actually locked at cold and whether the reference oscillator is within spec — some oscillators have a cold frequency offset or slow startup that violates the PLL's input range or lock time. If the design uses a forwarded clock from an external ADC, the clock-to-data skew at the FPGA pins will shift with temperature because the ADC's output delay and the PCB's propagation both change; a capture window that was centered at 25 °C can drift to the edge at cold. That's a classic setup/hold margin issue that timing analysis won't catch because the constraint was written for nominal.

Concretely, I'd (1) verify the clock is clean and locked at cold with a scope or on-chip clock monitor, (2) sweep the capture clock phase (IDELAY/MMCM phase shift) at cold and see whether there's a phase setting that works across the whole temperature range, (3) check whether the timing constraints actually model the min/max delay of the external interface across temperature, and (4) if the margin is genuinely thin, add margin by re-centering the sampling point or adding a small FIFO/elastic buffer with a training pattern at startup. The fix should be validated by running the full temperature sweep, not just a cold spot check.

**Possible follow-ups:** How would you decide whether the root cause is the external device's output timing versus the FPGA's internal capture path? What would you change in the constraints or the bring-up sequence to catch this class of issue before it reaches the temperature chamber?

## Q2: How would you approach designing the clock domain crossing for a multi-bit control word that is written by a slow serial interface (e.g., 10 MHz SPI) and consumed by a fast logic domain (e.g., 250 MHz), where the word changes infrequently but must never be observed in a partially updated state?

**Answer:** The key insight is that "changes infrequently" is not a synchronization guarantee — the consumer can sample at exactly the wrong moment, so the design must make the transfer atomic by construction. For a multi-bit word crossing from slow to fast, the standard robust approach is a handshake or a toggle-based scheme rather than per-bit synchronizers.

The cleanest pattern: the writer holds the data stable in a register, then asserts a request (or toggles a single-bit flag) that is synchronized into the fast domain with a two-flop synchronizer. The fast domain detects the edge, captures the whole word in one clock, and asserts an acknowledge that is synchronized back. The writer must not change the data until it sees the acknowledge. This guarantees the consumer always sees a coherent snapshot, at the cost of a few cycles of latency — which is fine for a control word that changes rarely.

An alternative is a toggle-plus-mux structure: the writer toggles a bit, the fast domain synchronizes the toggle, and on detecting the change it loads the data bus. This is essentially the same idea with less handshake overhead but requires care that the data is stable before the toggle is seen. For a truly infrequent word, I'd also consider a small asynchronous FIFO if the writer might update faster than the consumer can absorb, but for a single control word the handshake is simpler and easier to verify.

The verification matters as much as the structure: I'd run a CDC lint tool to confirm no unsynchronized multi-bit paths exist, and I'd add a formal or simulation check that the consumer never observes a value that wasn't a complete written word. I'd also make sure the reset state of the handshake is defined so the first transfer after reset is clean.

**Possible follow-ups:** What's the failure mode if the writer ignores the acknowledge and updates the data early? How would you handle a control word that must be updated faster than the handshake round-trip allows?

## Q3: How would you approach designing the decoupling and bulk capacitance network for an FPGA's transceiver power rails, where the rails see both high-frequency switching noise from the SerDes and slower, larger current transients from the fabric, and you need to verify the network is adequate before committing to the layout?

**Answer:** The transceiver rails are a two-timescale problem, so I'd design and verify the network in the frequency domain first, then confirm with time-domain simulation. The high-frequency content (SerDes switching, on the order of hundreds of MHz to GHz) is handled by the smallest capacitors placed as close to the package pins as physically possible — typically the vendor recommends a specific set of 0.1 µF and smaller values per rail per bank, and the loop inductance from the cap to the pin is what actually matters, not the capacitance value alone. The slower, larger transients (fabric current steps) are handled by bulk capacitance and the regulator's loop bandwidth.

The design process: start from the vendor's recommended decoupling and PDN target impedance for the rail, then build a model of the plane pair, the via inductance, and the capacitor ESL/ESR. I'd use a PDN impedance simulation (plane resonance plus cap network) to check that the impedance stays below the target across the frequency band of interest — roughly from the regulator's crossover frequency up to where the on-package capacitance takes over. The target impedance is derived from the allowable ripple divided by the worst-case transient current, so the ripple spec drives everything.

Before committing to layout, I'd verify with (1) the PDN impedance plot against the target, (2) a check that the cap placement keeps loop inductance low (short, wide connections, multiple vias per pad), and (3) a time-domain simulation of the worst-case current step to confirm the voltage stays within the transceiver's ripple spec. After layout, I'd re-extract the parasitics and re-run the impedance check, because the layout always adds inductance that the pre-layout model didn't capture. On the bench, a VNA measurement of the rail impedance and a scope measurement of the ripple under load are the final confirmation.

**Possible follow-ups:** How would you decide how much of the decoupling to put on-package versus on-board? What would you do if the post-layout impedance showed a resonance peak above the target in a band you can't fix with more capacitance?

## Q4: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?

**Answer:** A via stub is the unused portion of a plated through-hole below the layer where the signal enters or exits, and at multi-gigabit rates it behaves as a resonant stub that causes a notch in the channel's insertion loss and a reflection that degrades the eye. The severity scales with stub length relative to the signal's wavelength, so on a thick backplane the stub can easily be long enough to matter.

The first-line mitigation is backdrilling: after plating, the unused barrel is drilled out from the opposite side to within a controlled distance of the signal layer, which shortens the stub dramatically. The trade-off is cost and process control — backdrilling adds a manufacturing step and the remaining stub length has to be specified and inspected. The second approach is blind or buried vias, which avoid the stub entirely by construction, but they add layer-count and fabrication cost and constrain the stack-up.

Where backdrilling isn't practical, I'd consider (1) a via structure with the signal entering and leaving on adjacent layers to minimize the stub, (2) "via-in-pad" or laser-drilled microvias for the high-speed layers, and (3) compensating the channel elsewhere — pre-emphasis/equalization in the SerDes can partially recover the loss, but it can't fix a deep notch, so this is a last resort. I'd also check whether the connector and the backplane material are contributing more loss than the stub, so I don't over-engineer the via fix.

Verification: I'd model the via with a 3D field solver (including the stub, the antipads, and the return vias) and run the channel simulation to see the notch and the eye. The return path matters too — the stub's return current has to flow somewhere, so I'd ensure ground vias are placed close to the signal via to keep the loop small. On the bench, TDR would show the stub reflection directly.

**Possible follow-ups:** How would you decide the maximum allowable stub length for a given line rate? What's the interaction between backdrilling and the connector footprint, and how would you sequence the fabrication steps?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?

**Answer:** I'd treat this as a review-quality issue first and a teaching moment second, and I'd avoid framing it as "you cheated." The engineer may genuinely believe the exceptions are correct — the problem is that exceptions are the single easiest way to make a design "close" while hiding a real failure, so they need to be justified path by path, not accepted as a batch.

My approach in the review: ask the engineer to walk through each exception and explain, for that specific path, why the destination doesn't need the data on the next clock edge — what the actual latency requirement is, and what the source and destination clocks are. A legitimate multicycle path has a documented relationship (e.g., a register that's only read every N cycles, or a path between two clocks with a known ratio). A legitimate false path is one that's structurally never sensitizable (e.g., a test-only path, or a path between mutually exclusive modes). If the engineer can't articulate the justification for a given exception, it comes out.

I'd also ask for the evidence: has the design been verified with the exceptions in place, and does the verification actually exercise the paths that were excepted? A common failure is that the exceptions are correct for the intended operating mode but the design has a mode where the path does matter. I'd want to see that the modes are covered.

Then I'd set the process expectation: exceptions get reviewed and documented with a rationale, ideally in the constraint file itself, and any new exception added during closure gets flagged. If the exceptions turn out to be legitimate, I'd say so and move on — the goal is a defensible sign-off, not catching someone. If they're not, we fix the design or the constraint and re-close. The tone matters: I want the engineer to bring me the next questionable exception early, not hide it.

**Possible follow-ups:** How would you verify that a multicycle path exception is actually safe, beyond the engineer's explanation? What process would you put in place so timing exceptions get reviewed before they're used to declare closure?
