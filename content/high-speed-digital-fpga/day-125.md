# high-speed-digital-fpga — Day 125

## Q1: How would you approach debugging an FPGA design where the transceiver link passes its built-in PRBS checker at the physical layer, but application-level data is occasionally corrupted, and the corruption only appears at full line rate?

**Answer:** The fact that PRBS passes but application data fails is the key clue: PRBS is a fixed, self-synchronizing pattern generated and checked inside the transceiver's physical coding sublayer, so it exercises the SerDes, the CDR, and the analog channel — but it does not exercise the user logic between the transceiver's parallel interface and the application, nor does it stress the FIFO/gearbox boundary the way real traffic does. So I'd treat this as a problem above the PMA/PCS, not in the channel itself.

My first step is to localize where the corruption is introduced. I'd instrument the design with a pattern generator and checker placed at several observation points: at the transceiver's parallel output (before the RX FIFO), after the RX FIFO/gearbox, and at the application boundary. If the pattern is clean at the transceiver output but corrupt after the FIFO, the problem is in the clock domain crossing or the FIFO's read/write pointer logic. If it's already corrupt at the transceiver output, then the issue is in how the parallel data is framed — for example, a word-alignment or comma-detection problem that only manifests when the link is saturated.

At full line rate specifically, I'd suspect three things. First, backpressure and overflow: if the application can't drain the receive path at line rate, a FIFO overflows and silently drops or overwrites words — this often shows up as occasional corruption rather than a clean error. I'd check FIFO status flags and add an overflow counter. Second, clock domain crossing: if the transceiver's recovered clock and the application clock are asynchronous and the CDC is not a proper handshake or dual-clock FIFO, occasional metastability-induced bit errors appear only when the data rate is high enough to make the timing window tight. Third, the gearbox or width-conversion logic: at full rate the gearbox is continuously busy, and a subtle bug in the boundary handling (e.g., a word-count off-by-one) only shows up under sustained traffic.

I'd also verify the transceiver's error counters and the PCS status registers — some transceivers report disparity or sync-header errors that PRBS bypasses. And I'd run a long-duration soak at full rate with a known pseudo-random application payload, comparing transmitted and received data at the application layer, to get a bit-error-rate estimate and a repeatable failure signature.

**Possible follow-ups:** How would you distinguish a FIFO overflow from a CDC metastability problem using only on-chip instrumentation? If the corruption turns out to be in the gearbox boundary logic, what would you change in the RTL to make it robust at full rate?

## Q2: How would you approach designing the power-up and reset release sequence for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?

**Answer:** The core principle is that each block has a documented dependency on the one before it, and the reset release must be a state machine that enforces those dependencies rather than a simple RC delay or a single global reset. I'd start by extracting the vendor's power-up and reset requirements from the datasheet and the transceiver/PLL user guides — specifically the order in which the configuration engine, the clock management tiles, and the transceiver quads must be released, and any minimum delays between them.

The sequence typically looks like this: all supply rails come up and stabilize within their specified ramp and monotonicity requirements; the configuration engine is held in reset until the rails are valid and the configuration clock is stable; configuration completes and the device asserts its init/done handshake; only then are the PLLs and MMCMs released, because they need a stable reference clock and a configured fabric to lock against; and only after the PLLs are locked are the transceiver quads released, because the transceiver reference clock and the quad's internal PLL depend on the clock network being up. Each stage should be gated by a real status signal — PLL lock, configuration done, transceiver calibration done — not by a fixed timer, though I'd add timeout counters so a stuck stage doesn't hang the board silently.

I'd implement this as a dedicated power-up sequencer, either in a small CPLD/supervisor or in the FPGA fabric itself using a state machine that runs off an always-on clock. The sequencer should also handle the reverse: on a fault or a commanded reconfiguration, it should assert resets in the reverse order to avoid driving signals into an unpowered or unconfigured block. I'd also make sure the reset tree itself is properly synchronized — asynchronous assert, synchronous de-assert — into each clock domain, so that releasing reset doesn't itself create a metastability event.

Finally, I'd verify the sequence on the bench with a scope on the rail and reset lines, and I'd deliberately test out-of-order and slow-ramp scenarios (e.g., a rail that comes up late, a reference clock that starts after configuration) to confirm the sequencer holds rather than releasing early.

**Possible follow-ups:** How would you handle a hot-swap or rapid power-cycle event where the rails don't fully discharge before the next power-up? What status signals would you trust versus which would you treat as advisory only?

## Q3: How would you approach choosing between a global clock network and a regional/banked clock resource for a logic block that only needs to run at a modest rate, when the device's global clock resources are nearly exhausted?

**Answer:** The decision comes down to what the block actually needs from its clock: skew, fan-out, jitter, and whether the clock must reach logic spread across the die. A global clock network gives low skew and high fan-out across the whole device, but it consumes a scarce global resource and often has higher power. A regional or banked clock resource reaches only a portion of the die, has somewhat higher skew and lower fan-out, but frees up a global resource for a block that genuinely needs it.

For a modest-rate block, I'd first ask whether the block's logic is physically confined to one clock region. If it is — say, a control/status block that lives in one corner of the fabric — a regional clock is usually the right choice: it meets the timing at a modest rate, and it doesn't tie up a global buffer. If the block's logic is spread across the die, a regional clock may not reach all of it, and I'd either restructure the placement to confine the logic or accept that it needs a global resource.

I'd also consider whether the block's clock is related to a faster clock elsewhere. If it's a divided version of a global clock, I can often generate it from the same MMCM/PLL output and route it on a regional resource, keeping the two domains phase-related and simplifying any CDC between them. If it's fully asynchronous, the CDC strategy matters more than the clock resource choice, and I'd make sure the synchronizers are placed and constrained correctly regardless.

The other lever is to audit whether the global resources are truly all needed. Often a design has a global buffer assigned to a clock that only feeds a small block, or a clock that could be gated or merged. I'd review the clocking report, identify global buffers that are over-provisioned, and reclaim them before forcing a modest block onto a regional resource. The goal is to match each clock's reach and quality to its actual fan-out and timing requirement, not to default everything to global.

**Possible follow-ups:** What timing constraints would you apply to a regional clock to make sure the tools don't over- or under-constrain it? How would you verify that a regional clock actually reaches all the loads you intended?

## Q4: How would you approach designing the termination and coupling scheme for a multi-gigabit serial link that must traverse a backplane connector, and how would you decide between AC and DC coupling?

**Answer:** I'd start from the link's electrical requirements and the protocol's expectations, because the coupling choice is driven by both. AC coupling is the default for most multi-gigabit serial standards: it blocks DC and low-frequency common-mode differences between the two boards, which is important when the transmitter and receiver sit on separate ground references or have different common-mode voltages. It also protects against a DC fault. The cost is that the coupling capacitor forms a high-pass corner with the termination and the line, so its value must be chosen so the corner is well below the lowest frequency content of the encoded data — otherwise baseline wander and ISI appear. I'd size the capacitor from the protocol's run-length and low-frequency content, and place it close to the transmitter or receiver per the standard's guidance.

DC coupling is appropriate when the protocol requires it (some standards specify DC coupling, or the receiver needs to see the DC level), or when both ends share a well-controlled common-mode and the link is short enough that AC coupling's corner isn't needed. DC coupling avoids the capacitor's parasitics and the baseline-wander issue, but it requires the two ends' common-mode ranges to overlap and removes the fault-isolation benefit.

For termination, the key is to match the line's differential impedance at both ends and to handle the connector's impedance discontinuity. I'd use the receiver's on-die termination where available, set to the line's differential impedance, and add external termination only if the receiver's ODT isn't adequate or the standard requires it. For a backplane traversal, I'd pay close attention to the connector's impedance and to any stub or via discontinuity at the connector footprint, and I'd simulate the channel — including the connector model — to check insertion loss, return loss, and crosstalk against the link's budget. If the channel is marginal, I'd consider pre-emphasis/equalization settings at the transmitter and receiver rather than trying to fix it with termination.

I'd also verify the scheme against the standard's compliance points and run a BER test over the actual backplane, at temperature, before committing.

**Possible follow-ups:** How would you choose the AC coupling capacitor value given a specific run-length limit and line impedance? What would you do if the connector's impedance is significantly different from the line and you can't change the connector?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?

**Answer:** I'd treat this as a teaching moment first, but I'd be firm that the design cannot ship as-is. The engineer's reasoning — "it's stable long enough" — is the classic metastability fallacy: stability of the source signal says nothing about the relationship between the source signal's transition and the destination clock's sampling edge. If the transition lands inside the destination flop's setup/hold window, the flop can go metastable, and no amount of source stability prevents that; it only changes how often it happens. At a high enough data rate or over enough units and temperature corners, "rare" becomes "observed."

In the review, I'd walk through the timing: show the destination clock period, the source signal's transition, and the window in which a transition causes a violation. I'd explain that the fix depends on what the signal is. If it's a single-bit level that changes slowly relative to the destination clock, a two-flop synchronizer is the standard fix, with the synchronizer flops placed close together and marked with the appropriate synchronizer attribute so the tools don't optimize them away or retime them. If it's a pulse, a two-flop synchronizer alone can miss it, so I'd use a pulse-stretching or toggle-handshake scheme. If it's a multi-bit bus, a per-bit synchronizer is wrong — I'd use a handshake, a dual-clock FIFO, or a Gray-coded encoding depending on the data's behavior.

I'd also make sure the fix is captured in the design guidelines and the review checklist, so the same issue doesn't recur on the next block. And I'd follow up with the engineer after the fix to confirm they understand not just the fix but the reasoning, because the goal is for them to catch this themselves next time. I'd keep the tone collegial — the review is exactly where this should be caught — but I wouldn't let "it works in simulation" or "it's been fine so far" override a known correctness issue on a board that may go into a regulated or safety-relevant product.

**Possible follow-ups:** How would you verify after the fix that the CDC is actually correct — what would you look for in the CDC report or the static analysis? How would you handle it if the engineer pushed back and said the synchronizer adds latency the design can't afford?
