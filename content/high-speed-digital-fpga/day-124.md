# high-speed-digital-fpga — Day 124

## Q1: How would you approach designing the power-up and reset release sequence for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?

**Answer:** I'd treat this as a dependency-ordered state machine rather than a set of independent timers, because the failure mode you're describing — configured but non-functional — almost always comes from releasing something before its prerequisites are actually valid, not merely before a fixed delay has elapsed.

The ordering I'd establish is roughly: all supply rails within tolerance and stable (with the last rail's power-good gating everything downstream), then the configuration engine released once the configuration-mode pins and the reference clock are valid, then configuration completion confirmed by the DONE/init handshake rather than by a timeout, then the MMCM/PLLs released and their LOCK signals individually qualified, and finally the transceiver quads brought up after their reference clocks are stable and the PLL lock is confirmed. The key discipline is that each stage's release condition is a *measured* signal from the previous stage — power-good, DONE, LOCK, calibration-done — not a counter. Timers are only a backstop to catch a hung stage, never the primary trigger.

Two subtleties matter here. First, the transceiver reference clock often needs to be stable *before* the quad PLL is released, and that clock may itself come from an external oscillator with its own startup time — so the reference-clock validity has to be part of the chain, not assumed. Second, resets should be released asynchronously and de-asserted synchronously to each domain's clock, so that a domain coming out of reset doesn't see a metastable or glitchy release. I'd also make the whole sequence observable — a status register or a set of debug pins that show which stage is currently active — because when a board fails to come up, the first question is always "which stage did it stop at," and a sequence with no visibility is very hard to debug in the field.

**Possible follow-ups:**
- How would you handle a PLL that occasionally takes much longer than expected to lock — would you extend the timeout, or is a slow lock a symptom you'd investigate rather than accommodate?
- If the board can be power-cycled rapidly, how do you guarantee the sequence restarts cleanly rather than resuming mid-way through a stale state?

## Q2: How would you approach debugging an FPGA design where the transceiver link passes its built-in PRBS checker at the physical layer, but application-level data is occasionally corrupted, and the corruption only appears at full line rate?

**Answer:** The fact that PRBS passes tells me the analog channel, CDR, and equalization are healthy — the eye is open and the serializers are working. So I'd stop looking at the physical layer and start looking at everything *between* the deserializer and the application: the word alignment, the channel bonding, the elastic buffer, and the clock domain crossing out of the transceiver's recovered-clock domain into the fabric.

The "only at full line rate" clue is the most useful one. At reduced rate, the elastic buffer has slack and the CDC has idle cycles; at full rate, the buffer sits near its limits and any rate mismatch between the recovered clock and the fabric clock shows up as periodic overflow/underflow — which corrupts a word occasionally rather than continuously. So my first checks would be: is the elastic buffer's occupancy being monitored, and does it drift toward a rail over time? Is the CDC out of the transceiver domain a proper handshake or FIFO, or is it a naive multi-bit transfer that happens to work when there's slack? Second, word alignment and channel bonding: if comma alignment is being re-established or if lanes are skewing relative to each other at full rate, you get occasional misaligned words that look like corruption.

I'd also distinguish *corruption* from *loss*. If the application sees a word that's wrong but the count is right, that points at alignment or CDC. If words are being dropped or duplicated, that points at the elastic buffer or the FIFO. Instrumenting the design to count errors, buffer occupancy, and alignment events — rather than just observing the symptom — is what turns this from guesswork into a bisection. And I'd verify the test itself: is the PRBS checker actually checking the full datapath, or does it tap off before the CDC? A PRBS checker that sits inside the transceiver hard block proves less than people assume.

**Possible follow-ups:**
- How would you design the elastic buffer monitoring so that a slow drift is visible before it becomes a corruption event?
- If the corruption turns out to be in the CDC, what would you change about the crossing to make it robust at full rate?

## Q3: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?

**Answer:** The core problem is that timing analysis only proves what you told it to prove — an unconstrained path is silently "passing" because nothing is checking it. So the verification has to be about *coverage of the constraint set*, not just about the slack numbers.

My approach has a few layers. First, I'd drive the analysis tools to report unconstrained and partially-constrained paths explicitly — most vendors' tools can list paths with no timing requirement, and that list should be empty or fully explained before sign-off. Second, I'd cross-check the constraint file against the design's actual clock and I/O inventory: every clock that exists in the design should have a create_clock (or be derived from one), every I/O should have an input/output delay, and every clock domain crossing should be either properly synchronized or explicitly excepted with a written justification. Third, I'd review every timing exception — false paths and multicycle paths — as a separate artifact, because exceptions are where real bugs hide: a false path on a path that actually needs to meet timing is exactly the "passes analysis, fails hardware" scenario. Each exception should have an owner and a reason, and I'd be skeptical of any that were added late to close timing.

I'd also use CDC linting as an independent check — a structural CDC checker will flag crossings that the timing constraints don't cover, and the two views together catch more than either alone. Finally, I'd sanity-check the constraint set against the *intended* operating conditions: are the clock periods the real ones, are the I/O delays derived from the actual external device's datasheet, and are the operating conditions (voltage, temperature) the ones the part will actually see? A constraint set that's internally consistent but built on the wrong clock period is just as dangerous as a missing constraint.

**Possible follow-ups:**
- How would you handle a design where the tools report a large number of unconstrained paths that are genuinely don't-care — how do you document that without drowning in exceptions?
- What's your process for reviewing a timing exception that a colleague added, to decide whether it's legitimate?

## Q4: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?

**Answer:** The stub is the unused portion of the via barrel — the part below the layer where the signal enters, or above the layer where it exits — and at multi-gigabit rates it behaves as an open-circuited transmission-line stub that resonates and causes a notch in the channel's insertion loss, plus reflections that close the eye. On a thick backplane the stub can be long enough that the resonance falls right in the signal's bandwidth, so it's a real problem, not a theoretical one.

The first-line mitigation is to use *blind* or *buried* vias so the barrel only extends between the layers actually used, eliminating the unused stub entirely. That's the cleanest fix but it costs backplane fabrication complexity and money, so it's a design-time decision, not a respin fix. If the stack-up and fab can't support blind vias, the next option is *backdrilling*: after plating, the unused barrel portion is drilled out from the far side, leaving a short residual stub. Backdrilling is the standard production answer for thick backplanes and is usually specified as a controlled-depth operation with a tolerance on the residual stub length. The residual stub still resonates, but at a much higher frequency, ideally above the signal's bandwidth.

Beyond those two, I'd consider the via geometry itself: larger antipads on the layers the via passes through (to control via impedance and reduce parasitic capacitance), and where the channel allows, routing the transition so the stub is as short as possible. I'd also verify the result by extracting the via structure — a 3D field solver on the actual stack-up — and simulating the full channel with the stub included, rather than assuming a rule-of-thumb length is fine. The rule of thumb ("stub shorter than a tenth of a wavelength") is a starting filter, not a sign-off criterion.

**Possible follow-ups:**
- How would you decide between blind vias and backdrilling for a given backplane, given the cost and fab-capability trade-offs?
- If backdrilling leaves a residual stub that still resonates within the channel bandwidth, what else can you do at the board level to recover margin?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented the data path that captures samples from a high-speed ADC and writes them to DDR memory. During the review, you notice they've sized the capture FIFO from the average throughput rather than the worst-case burst, arguing that "the average rate is well below the memory bandwidth, so it can't overflow." How do you handle this situation?

**Answer:** I'd treat this as a teaching moment rather than a correction, because the reasoning is a very common and very understandable mistake — and the goal is for the engineer to see *why* average-rate sizing is unsafe, not just to change the number.

First, I'd make sure I understand their model. The claim is that average write rate is below memory bandwidth, so the FIFO can't overflow. The gap in that reasoning is that a FIFO absorbs *instantaneous* rate mismatch, not average mismatch — and the memory controller doesn't accept writes at a constant rate. It has arbitration latency, refresh cycles, bank conflicts, and read/write turnaround penalties, so its *instantaneous* write acceptance rate can drop well below its average bandwidth for extended periods. Meanwhile the ADC produces data in bursts at full rate. So the FIFO has to cover the worst-case *deficit* — the longest period during which the ADC produces faster than the memory controller accepts — not the average.

Second, I'd walk through how to actually size it: identify the worst-case burst length from the ADC, the worst-case memory-controller stall (refresh plus arbitration plus turnaround), and size the FIFO to cover the product of the deficit rate and the stall duration, with margin. And I'd point out that the FIFO also needs overflow *detection* and a defined behavior on overflow — silently dropping samples in a data acquisition system is often worse than a visible error.

The tone matters. I'd frame it as "let's pressure-test the assumption together" rather than "you got this wrong," and I'd ask them to walk me through the worst case so they arrive at the answer themselves. If they push back, I'd ask them to show me the analysis that bounds the memory controller's worst-case stall — if they can't produce it, that's the gap. And I'd follow up after the review to make sure the fix lands and that the lesson generalizes to the other FIFOs on the board.

**Possible follow-ups:**
- How would you handle it if the engineer had already built and tested the design and the FIFO had never overflowed in the lab — how do you make the case that it's still a problem?
- What would you add to the design review checklist so this class of issue gets caught earlier next time?
