# high-speed-digital-fpga — Day 69

## Q1: How would you approach designing the clock domain crossing for a multi-bit Gray-coded counter value that increments continuously in a fast domain (e.g., 250 MHz) and must be sampled by a slower domain (e.g., 50 MHz) for logging, where the sampled value must always be a coherent snapshot and never a corrupted mix of bits?

**Answer:** The key insight is that a binary counter cannot be safely sampled asynchronously because multiple bits can change simultaneously on a carry boundary — a two-flop synchronizer on each bit would capture a mix of old and new values. The standard solution is to convert the binary count to Gray code in the source domain, where only one bit changes per increment. Then each Gray-coded bit can be passed through an independent two-flop synchronizer into the destination domain. Because only one bit transitions per count, the worst case is that the destination captures either the old or the new value — never a corrupted intermediate. After synchronization, the Gray code is converted back to binary in the destination domain. The trade-off is the extra logic for the binary-to-Gray and Gray-to-binary conversions, plus the fact that the sampled value may lag the true count by one or two destination clock cycles, which is acceptable for logging or display. I would also add a small handshake or a "data valid" pulse if the consumer needs to know when a new coherent value is available, and I would constrain the synchronizer registers with appropriate false-path or max-delay constraints in the timing constraints so the tool does not try to time the asynchronous crossing. For very wide counters, I would consider whether the full width needs to cross, or whether a narrower snapshot (e.g., a latched value with a toggle handshake) would suffice.

- What happens if the Gray-coded counter wraps around, and does that affect the synchronization scheme?
- How would you verify in simulation that the CDC is correct, given that metastability is not modeled in RTL simulation?

## Q2: How would you approach debugging an FPGA design where the DDR3 memory interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** This is a classic temperature-dependent timing margin issue, and I would approach it systematically. First, I would confirm the correlation with temperature by monitoring the board temperature and the FPGA junction temperature while running a memory stress test, and see whether the failure rate increases monotonically with temperature. Then I would look at the timing margins reported by the memory controller's calibration — many controllers report per-bit or per-byte read/write margin values, and if those margins are shrinking with temperature, that points to a timing closure problem rather than a functional bug. The likely culprits are: (1) the read/write leveling or per-bit deskew values were calibrated at cold temperature and are not being re-calibrated as the device warms, so the optimal sampling point drifts; (2) the ODT or drive strength settings are not temperature-compensated, causing signal integrity to degrade; (3) the reference voltage or the VREF training was done at one temperature and is now off; or (4) the memory controller's timing constraints were closed with insufficient margin at the slow corner. I would also check whether the failure is data-pattern-dependent, which would point to crosstalk or ISI rather than a pure timing drift. On the board side, I would verify that the DDR power rails are stable and that the decoupling is adequate across temperature, since capacitor ESR and capacitance can change with temperature. The fix could be as simple as re-running calibration periodically, or as involved as tightening the PCB layout or adjusting the termination scheme. I would also add temperature-corner testing to the bring-up plan so this class of issue is caught earlier.

**Possible follow-ups:**
- How would you determine whether the issue is in the FPGA's memory controller or in the DRAM device itself?
- What changes would you make to the calibration routine to make it robust across temperature?

## Q3: How would you approach designing the return-current path for a high-speed digital board where a signal transitions between two reference planes (e.g., from a ground plane to a power plane) on its way through a via?

**Answer:** The fundamental principle is that every signal current must return to its source, and at high frequency the return current follows the path of least impedance — which means it flows on the reference plane directly beneath (or above) the signal trace. When a signal transitions from referencing one plane to referencing another through a via, the return current must also transition between those planes. If there is no low-impedance path for the return current to move between the planes near the via, the return current is forced to take a long detour, creating a large loop area that radiates and picks up noise, and causing a discontinuity that degrades signal integrity. The standard solution is to place a stitching capacitor (or a set of them) close to the signal via, connecting the two reference planes. The capacitor provides a low-impedance path for the return current at the frequencies of interest. The capacitor value and placement are critical: it must be close enough that the inductance of the connection does not dominate, and its self-resonant frequency must be above the signal's relevant frequency content. For very high-speed signals, a small-value capacitor (e.g., 100 nF or smaller) placed within a few millimeters of the via is typical. If the two planes are both ground planes at the same potential, a direct stitching via is even better. I would also consider whether the plane transition can be avoided altogether by routing the signal on a single reference plane, or by using a different layer stack-up. In layout review, I would flag any signal via that transitions between different reference planes and verify that a stitching capacitor or via is present nearby.

**Possible follow-ups:**
- How would you decide on the capacitor value and how many to place for a given via transition?
- What is the impact of the plane transition on the signal's characteristic impedance, and how would you quantify it?

## Q4: How would you approach designing the power-up and configuration sequence for an FPGA that loads its bitstream from external flash, when the flash device itself has a non-trivial access latency and the board may be power-cycled rapidly?

**Answer:** The first consideration is the power sequencing of the FPGA itself — the core, auxiliary, and I/O rails must come up in the order and with the timing specified by the FPGA vendor, and the configuration logic must be held in reset until all rails are stable and within tolerance. I would use a power-good signal from each regulator, combined with a sequencer or a supervisor IC, to gate the FPGA's reset and the start of configuration. The second consideration is the flash device: it has a power-up time and a minimum access latency, and if the FPGA starts trying to read the bitstream before the flash is ready, the configuration will fail. I would check the flash datasheet for its power-up timing and ensure the FPGA's configuration start is delayed until after that time, either by a fixed delay or by monitoring a ready signal from the flash if available. For rapid power-cycling, the concern is that the flash or the FPGA may not have fully discharged before power is reapplied, leading to undefined behavior. I would add a brown-out detector or a supervisor with a minimum reset timeout to ensure the system is fully reset before a new power-up sequence begins. I would also consider whether the FPGA's configuration memory needs to be cleared — some FPGAs require a full power cycle to clear, while others can be re-triggered. In the bring-up plan, I would test rapid power-cycling explicitly, with varying off-times, to characterize the minimum off-time required for reliable configuration. If the flash is slow, I might also consider a parallel configuration mode or a pre-load scheme to reduce configuration time.

- How would you debug a configuration failure that only occurs on rapid power-cycling?
- What are the trade-offs between using a serial flash versus a parallel flash for FPGA configuration?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer on your team has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?

**Answer:** I would treat this as a teaching moment rather than a confrontation, because the engineer's reasoning reflects a common misunderstanding about metastability and asynchronous crossings. I would start by acknowledging that in many cases the signal may indeed appear to work — that's what makes these bugs so insidious — but explain that "works in practice" is not the same as "works reliably across all devices, temperatures, and process corners." I would walk through the physics: when a signal crosses from one clock domain to another, the setup and hold times of the destination flip-flop can be violated, causing the output to go metastable — an indeterminate state that can persist for an unpredictable time and propagate inconsistently. I would explain that the fix is a standard two-flop synchronizer for a single-bit control signal, or a handshake or FIFO for multi-bit data, and that this is a well-established best practice, not a matter of opinion. I would also point out that the timing constraints need to reflect this — the synchronizer registers should be constrained appropriately, and the crossing should be flagged for review. If the engineer is still unconvinced, I would suggest we simulate the crossing with a metastability model or run it on hardware across multiple boards and temperatures to demonstrate the risk, but I would not sign off on the design without the synchronization. The goal is to make the engineer a better designer, not to win the argument. I would also use this as an opportunity to review the team's design review checklist to ensure CDC checks are explicitly included for future reviews.

**Possible follow-ups:**
- How would you structure a design review checklist to catch CDC issues systematically?
- How would you handle a situation where the engineer pushes back and insists their approach is fine?
