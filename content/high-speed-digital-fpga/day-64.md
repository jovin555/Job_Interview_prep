# high-speed-digital-fpga — Day 64

## Q1: How would you approach designing the clock domain crossing for a free-running multi-bit counter that increments continuously in a fast domain (e.g., 250 MHz) and must be sampled by a slower domain (e.g., 50 MHz) for logging, where the sampled value must always be a coherent snapshot and never a corrupted mix of bits?
**Answer:** A continuously incrementing multi-bit value is the classic case where a per-bit two-flop synchronizer is wrong: each bit can resolve on a different destination clock edge, so the sampled word can be a mix of old and new bits — a value that may never have existed. The standard robust approach is a Gray-coded counter. Because only one bit changes per increment, a two-flop synchronizer on the Gray-coded value can only ever capture the old value or the new value, never an incoherent intermediate. The destination domain then converts the synchronized Gray code back to binary for display or logging. The trade-off is a small amount of conversion logic and the fact that the sampled value lags the source by a couple of destination clock cycles — acceptable for logging, but not for a control loop that needs the exact instantaneous count. If the counter is wide, Gray coding still works because the single-bit-change property holds regardless of width. An alternative is a handshake or a request/acknowledge scheme, but that adds latency and complexity and is usually overkill for a monotonic counter. A third option is to capture the value into a register in the source domain, then pass a synchronized "valid" pulse to the destination and read the captured register — this works when updates are infrequent, but for a free-running counter the Gray-code approach is simpler and has bounded, deterministic latency. I would also add a constraint to keep the Gray counter on a single clock region and verify the synchronizers are recognized by the CDC checker in the tool flow.
**Possible follow-ups:** How would you verify the Gray-code CDC in simulation, given that metastability itself can't be simulated? What would change if the destination domain needed the exact count with no more than one source-clock-cycle latency?

## Q2: How would you approach debugging an FPGA design where the DDR3 interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?
**Answer:** A failure that appears only after warm-up points to a timing margin problem that is being consumed by temperature-dependent effects, not a hard logic bug. I would structure the investigation around separating the physical layer from the controller. First, I would confirm the failure is really in the memory path and not in the logic that consumes the data — a checksum or pattern test that runs continuously in the background helps localize it. Then I would look at the calibration data itself: many controllers expose the per-bit read/write delay values found during calibration. If those values are near the edge of their valid window at power-up, there is little margin left for temperature drift, and the fix is to re-run calibration or to widen the sampling window. I would also check whether the failure correlates with a specific traffic pattern or address region, which would point to a particular byte lane or DQ group rather than a global timing issue. On the board side, I would review the VREF and VTT supplies for drift over temperature, since the memory reference voltage and termination voltage directly affect the input threshold and the eye opening. I would also check the ODT settings and whether the drive strength and slew rate are appropriate for the trace length. If the design has a temperature sensor near the memory, correlating the failure with measured temperature is valuable. The systematic approach is: reproduce with a controlled thermal chamber, log the calibration values and error counters over temperature, and identify whether the margin is being lost on the read or write side. The fix is usually a combination of re-calibration at temperature, adjusting the sampling point to the center of the eye, and confirming the power integrity of the memory rails.
**Possible follow-ups:** How would you decide whether to re-calibrate periodically at runtime versus fixing the margin at design time? What board-level measurements would you take to confirm the memory rails are not drifting?

## Q3: How would you approach designing the decoupling and bulk capacitance network for an FPGA's transceiver power rails, where the rails see both high-frequency switching noise from the SerDes and slower, larger current transients from the fabric, and you need to verify the network before committing to layout?
**Answer:** The transceiver rails are the hardest power integrity problem on a typical FPGA board because they combine a very tight ripple specification with a wide frequency range of disturbance. I would approach it as an impedance-versus-frequency problem rather than a "sprinkle capacitors" problem. The target is to keep the power distribution network impedance below a calculated limit across the frequency band where the transceiver draws current — from the low-frequency envelope of the fabric load up to the high-frequency content of the SerDes switching. That means a deliberate stack of capacitors: bulk electrolytic or polymer capacitors for the low-frequency, high-energy transients; a bank of mid-frequency ceramics to bridge the gap; and small, low-inductance ceramics placed as close as possible to the transceiver power pins for the high-frequency content. The critical detail is loop inductance: the capacitor's own ESL and the via and trace inductance to the pin dominate at high frequency, so placement and via geometry matter more than the nominal capacitance value. I would use the vendor's power integrity guidance and the recommended decoupling table as a starting point, then simulate the network with the board's stack-up parasitics to confirm the impedance profile. Before committing to layout, I would verify the plane geometry — a solid, low-inductance plane pair for the transceiver rail, with the return path directly underneath — and check that the capacitor placement does not force long, thin traces that add inductance. After layout, I would re-extract and re-simulate, and if possible measure the rail with a high-bandwidth probe to confirm the ripple is within the transceiver specification under realistic traffic.
**Possible follow-ups:** How would you measure the rail impedance or ripple on a live board without disturbing the circuit? What is the risk of using a single large capacitor instead of a distributed bank?

## Q4: How would you approach designing the interface between an FPGA and an external ADC that uses a source-synchronous, double-data-rate output bus, where the data and a forwarded clock arrive at the FPGA with an unknown but bounded skew?
**Answer:** A source-synchronous DDR interface means the clock travels with the data, so the FPGA must capture the data using the forwarded clock rather than a system clock. The first decision is how to use the FPGA's input resources: the forwarded clock should drive a dedicated clock-capable input, and the data should be captured by input registers or IDELAY/ISERDES resources in the same I/O bank, so the clock and data share a controlled relationship. The unknown skew between clock and data is the central problem. The standard solution is to use per-bit or per-group delay elements (IDELAY) to shift the sampling point to the center of the data eye, and to calibrate that delay at startup using a known training pattern from the ADC. Because the skew is bounded but not known, the calibration must find the valid window and place the sample point in the middle, with margin on both sides. I would also consider whether the forwarded clock should be used directly or routed through a PLL/MMCM to clean it up and to generate the internal capture clock — but that adds jitter and must be accounted for in the timing budget. The timing analysis must include the ADC's output valid window, the board skew, the FPGA input setup/hold, and the clock path jitter. On the board side, I would match the trace lengths within the data group and keep the clock trace length matched to the data group, and control the impedance. I would verify the design with a training pattern at startup and, if the ADC supports it, a test mode that outputs a known sequence so the capture logic can be validated in hardware.
**Possible follow-ups:** How would you handle the case where the ADC's forwarded clock is not continuous, such as during power-up or idle periods? What is the difference in approach between using IDELAY calibration and using a PLL to phase-shift the capture clock?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?
**Answer:** I would treat this as a teaching moment rather than a confrontation, because the engineer's reasoning is a common and understandable misconception. The first thing I would do is separate the two issues: the technical correctness of the design, and the way the concern is raised in the review. On the technical side, I would explain why "stable long enough" is not a valid argument — the problem is not the signal's stability in the source domain, but the relationship between the signal's transition and the destination clock edge. If the transition occurs near the setup or hold window of the destination register, the register can go metastable, and the resulting value is unpredictable and can propagate inconsistently through the downstream logic. The fact that the signal is stable for many source clock cycles does not eliminate this, because the destination clock is asynchronous and the phase relationship drifts. I would then walk through the correct solution: a two-flop synchronizer for a single-bit level signal, or a proper handshake or FIFO for a multi-bit bus, and explain the latency and resource cost of each. I would also point out that the design tools have CDC checks and that an unsynchronized crossing will typically be flagged, so it is worth running those checks as part of the review. On the process side, I would make sure the engineer understands that raising this in review is exactly the right thing to do, and that the goal is to catch it before it becomes an intermittent field failure that is very hard to debug. I would ask them to update the design and to add a comment or constraint documenting the synchronization scheme so the next reviewer can see the intent. If the engineer pushed back, I would suggest we build a small test case or look at the vendor's CDC guidelines together, so the conclusion comes from evidence rather than from my assertion.
**Possible follow-ups:** How would you handle it if the signal were multi-bit and the engineer argued that the bits always change together? What would you do if the same issue appeared in a design that had already been released to production?
