## Q1: How would you approach designing a clock domain crossing (CDC) scheme for a multi-bit data bus where the source and destination clocks are asynchronous, the data changes frequently, and you need to minimize latency while ensuring data integrity?

**Answer:** This is a classic asynchronous CDC problem where you can't use simple two-flop synchronization because multiple bits could change simultaneously, leading to a corrupted word being captured. The fundamental trade-off is between latency and safety. My first step would be to characterize the actual requirements: what's the data rate, how frequently does data change, and what's the acceptable latency budget? If the data changes frequently and latency is critical, I'd look at asynchronous FIFO-based approaches. An asynchronous FIFO uses gray-coded pointers to safely transfer write/read pointers between domains, with the data itself being stored in dual-port RAM. The key design elements are: gray-code encoding for the pointers (so only one bit changes per increment), proper synchronization of the gray-coded pointers using multi-flop synchronizers, and careful generation of the full/empty flags to avoid metastability-induced errors. The FIFO depth needs to be sized based on the worst-case burst size and the frequency ratio between domains. If the data doesn't change continuously but rather in discrete "valid" windows, I might use a handshake-based approach with a valid/ack protocol, but that adds latency. For truly continuous, high-throughput transfers, the asynchronous FIFO is the standard solution. I'd also verify the design using formal CDC verification tools or at minimum, careful simulation with clock jitter and phase offset variations to ensure the gray-code pointer synchronization is robust across all timing corners.

**Possible follow-ups:**
- How would you determine the required FIFO depth for a given frequency ratio and burst pattern?
- What happens if the read side is slower than the write side on average — how does that change your approach?

## Q2: How would you approach debugging an FPGA design where the configuration bitstream loads successfully (DONE pin goes high) but the device does not enter the expected functional state — for example, all outputs remain tri-stated or in a default state?

**Answer:** When the DONE pin asserts but the design doesn't behave as expected, I'd work through this systematically. First, I'd verify the configuration was actually successful and complete — check that the DONE pin is truly asserted and stable, and verify the configuration clock and data lines were clean during loading. A partial or corrupted configuration can sometimes assert DONE prematurely. Next, I'd check the device's initialization sequence: many FPGAs have a "startup" phase after configuration where the device releases the global reset, enables I/O, and begins operation. If the startup sequence is misconfigured (e.g., wrong startup clock, incorrect timing for releasing the internal reset), the design might never actually start. I'd also verify that the global reset signal is properly de-asserted — if the reset is held active by an external source or by an internal condition, the design would remain in reset. Another common issue is that the design's clock isn't running: check if the PLL/MMCM locked, if the clock source is actually toggling, and if the clock enable signals are correct. I'd also examine the I/O standards and drive strength settings — if the I/O standard is misconfigured, outputs might appear tri-stated even though the logic is running. Finally, I'd use the FPGA vendor's debug tools: a logic analyzer integrated into the fabric, or a chipscope/signal-tap-style debug core, to observe internal signals and see where the design is stuck. If the design has a status register or heartbeat counter, I'd check if that's advancing. The key is to isolate whether this is a configuration issue, a startup/initialization issue, a clock/reset issue, or a logic issue.

**Possible follow-ups:**
- How would you distinguish between a configuration failure and a design logic failure in this scenario?
- What specific signals would you probe or monitor to narrow down the problem?

## Q3: How would you approach implementing a high-speed data path in an FPGA that must process a continuous stream of 16-bit samples at 500 MSPS, perform a 64-tap FIR filter, and output the filtered result without any dropped samples, while also meeting timing at the target clock frequency?

**Answer:** The first challenge is that 500 MSPS is typically faster than the FPGA fabric clock — most FPGAs won't run general logic at 500 MHz. So I'd need to use a parallel processing approach. The standard technique is to use multiple parallel filter banks, each operating at a lower clock rate. For example, if the fabric clock is 250 MHz, I'd need two parallel paths, each processing every other sample. For a 64-tap FIR filter, this means decomposing the filter into polyphase sub-filters. With a decimation factor of 2, the 64-tap filter splits into two 32-tap sub-filters, each operating on even and odd samples respectively. Each sub-filter runs at 250 MHz, and the results are interleaved to produce the 500 MSPS output stream. The key considerations are: ensuring the polyphase decomposition is mathematically correct (the sum of the sub-filter outputs must exactly match the original filter output), managing the data routing so each sample goes to the correct sub-filter, and handling the output interleaving without gaps. I'd also need to consider whether to use DSP slices or logic-based multipliers — for 64 taps at this rate, DSP slices are usually necessary. The DSP slices can be cascaded to implement the filter efficiently. I'd also pipeline the adder tree to meet timing, and use register retiming if needed. For verification, I'd simulate the polyphase implementation against the original filter in MATLAB or Python to confirm bit-exact equivalence, then verify timing closure in the FPGA tools. If the fabric clock can't reach 250 MHz, I might need four parallel paths at 125 MHz, which would give more timing margin but require more resources.

**Possible follow-ups:**
- How would you handle the case where the filter coefficients are programmable and change at runtime?
- What are the trade-offs between using DSP slices versus fabric logic for the multipliers?

## Q4: How would you approach designing a power distribution network (PDN) for an FPGA with multiple voltage rails, where the core rail (0.85V) has a transient current demand of up to 20A with a slew rate of 1A/ns, and you need to ensure the voltage stays within ±3% of nominal?

**Answer:** This is a demanding PDN requirement — 20A with 1A/ns slew rate means the voltage must stay within about 25 mV of 0.85V, which requires careful attention to both the DC and AC performance of the PDN. I'd start with a target impedance calculation: for a 20A transient with 25 mV allowed deviation, the maximum impedance is about 1.25 mΩ across the frequency range of interest. The frequency range extends from the transient repetition rate up to the frequency where the on-die decoupling takes over — this could be several hundred MHz. My approach would be multi-layered. First, the voltage regulator module (VRM) needs to have sufficient bandwidth and slew rate capability — a multi-phase buck converter with fast transient response is essential. The VRM's output capacitance handles the low-frequency portion of the transient. Next, bulk capacitors on the board (electrolytic or high-value ceramic) handle the mid-frequency range, typically 1 kHz to 1 MHz. Then, high-frequency ceramic capacitors (small values like 100 nF, 10 nF, 1 nF) placed close to the FPGA's power pins handle the 1 MHz to 100 MHz range. Finally, the FPGA's on-die decoupling and the package capacitance handle frequencies above that. The PCB layout is critical: I'd use a dedicated power plane for the core rail, with the plane placed close to the FPGA to minimize loop inductance. The vias connecting the capacitors to the power plane need to be short and numerous to minimize inductance. I'd also consider using interdigitated capacitor placements and possibly embedded capacitance in the PCB stack-up (thin dielectric between power and ground planes) for very high-frequency decoupling. For verification, I'd perform a frequency-domain analysis of the PDN impedance using simulation tools, then validate with time-domain transient simulations. On the bench, I'd use a high-bandwidth oscilloscope with a low-inductance probe to measure the core voltage during worst-case transient events, and possibly use a network analyzer to measure the PDN impedance.

**Possible follow-ups:**
- How would you determine the number and value of decoupling capacitors needed at each frequency range?
- What are the trade-offs between using more PCB layers for power integrity versus cost and manufacturability?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer on your team has implemented the data path that captures samples from a 500 MSPS ADC and writes them to DDR3 memory. During the review, you notice that the engineer has used a single FIFO to cross from the ADC clock domain to the memory controller clock domain, but the FIFO depth is only 64 words. When you ask about the depth, the engineer explains that the average write rate is well below the read rate, so the FIFO should never overflow. However, you're concerned about burst behavior — the ADC can produce bursts of data that could temporarily exceed the memory controller's sustainable write rate. The engineer argues that the memory controller's write buffer will absorb the bursts. How do you handle this situation?

**Answer:** This is a situation where I need to address both the technical concern and the engineer's understanding of the system behavior. I'd start by acknowledging the engineer's reasoning — they're correct that average rates matter, and it's good that they're thinking about the memory controller's buffering. However, I'd explain that in high-speed data acquisition, burst behavior is often the dominant factor in FIFO sizing, not average rates. I'd walk through a concrete scenario: if the ADC produces a burst of data at its full rate for even a few microseconds, and the memory controller is simultaneously handling refresh cycles or read/write turnaround overhead, the write buffer may not be sufficient. The key question is: what's the worst-case burst duration and what's the memory controller's sustainable write rate during that burst? I'd suggest we work together to calculate the worst-case scenario — considering the ADC's maximum burst length, the memory controller's write efficiency (which is never 100% due to refresh, read/write turnaround, and bank conflicts), and the FIFO depth needed to absorb the difference. I'd frame this as a collaborative analysis rather than a criticism. I'd also suggest we add a watermark or almost-full flag to the FIFO that could trigger backpressure to the ADC or flag an overflow condition for debugging. If the analysis shows the FIFO is indeed too small, we'd need to increase the depth — 64 words at 500 MSPS is only 128 ns of buffering, which is likely insufficient for any meaningful burst. I'd use this as a teaching moment about the importance of worst-case analysis in high-speed systems, and I'd document the analysis in the design review notes so the reasoning is captured for future reference.

**Possible follow-ups:**
- How would you calculate the worst-case burst duration and the memory controller's sustainable write rate?
- What other mechanisms could you use to handle the burst scenario besides increasing FIFO depth?
