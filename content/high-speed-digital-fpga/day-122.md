# high-speed-digital-fpga — Day 122

## Q1: How would you approach debugging an FPGA design where the device configures successfully and runs correctly for a while, but then appears to lose its configuration — it stops responding and only recovers after a full reconfiguration?

**Answer:** First I'd separate "lost configuration" from "logic wedged." A true configuration loss usually means the DONE signal dropped or the device re-entered its initialization state, so I'd instrument the board to capture DONE, INIT_B, and the configuration-mode pins on a scope with a long time base, or use a supervisor/MCU to log them continuously. If DONE genuinely deasserts, the causes are narrow: a power-rail glitch that dips below the configuration-retention threshold, a brownout on a rail the configuration memory depends on, a spurious re-trigger of the PROGRAM_B pin (noise, a floating pin, or a slow ramp on a reset supervisor), or a watchdog/supervisor that is itself resetting the device. I'd check the power sequencing and the transient response of the rails under the load conditions present at the time of failure — often the failure correlates with a load step elsewhere on the board. If DONE stays high but the logic is unresponsive, it's not configuration loss at all: it's a wedged state machine, a clock that stopped (PLL lost lock, reference dropped), or a bus hang, and I'd look at clock presence and PLL lock status instead. The key discipline is to instrument before theorizing — capture the actual state of the configuration and clock pins at the moment of failure rather than guessing.

**Possible follow-ups:** How would you distinguish a genuine reconfiguration from a soft error in configuration memory on a device that doesn't report it? What board-level changes would you make to harden the configuration path against a marginal rail?

## Q2: How would you approach designing the clock domain crossing for a multi-bit control word that is written by a slow serial interface (e.g., 10 MHz SPI) and consumed by a fast logic domain (e.g., 250 MHz), where the word changes infrequently but must never be observed in a partially updated state?

**Answer:** The requirement is atomicity, not low latency, so I'd use a handshake-based scheme rather than trying to synchronize the bus bits directly. The cleanest approach is a bundled-data handshake: the slow domain drives the multi-bit word onto a stable bus, waits for it to settle, then asserts a single request toggle; the fast domain passes that toggle through a two-flop synchronizer, and on detecting the edge, captures the whole bus in one clocked register. Because the data is held stable well before the request is seen and held until the acknowledge returns, the fast domain always samples a coherent word. The reverse acknowledge toggle tells the slow domain it can change the data. The alternative is a dual-clock asynchronous FIFO, which is overkill for an infrequently changing control word but is the right call if updates are frequent or bursty. I would explicitly avoid per-bit two-flop synchronizers on a multi-bit bus — that's the classic mistake, because bits can resolve on different cycles and produce a transiently invalid combination. I'd also add a CDC lint/formal check to prove the crossing is structurally correct, and constrain the paths as asynchronous in the timing tool so the tool doesn't try to time them as if they were synchronous.

**Possible follow-ups:** How would you handle the case where the fast domain might be reset while the slow domain is mid-handshake? What changes if the control word must be updated every few microseconds rather than infrequently?

## Q3: How would you approach designing the decoupling and bulk capacitance network for an FPGA's transceiver power rails, where the rails see both high-frequency switching noise from the SerDes and slower, larger current transients from the fabric, and you need to verify the network is adequate before committing to the layout?

**Answer:** I'd treat it as a target-impedance problem across frequency rather than a capacitor-count exercise. The transceiver rails have a tight ripple spec and noise that extends to very high frequency, so the network needs low impedance from the low-kilohertz range (bulk/regulator loop) up through the hundreds-of-megahertz range (small ceramic decoupling close to the pins). I'd start from the vendor's recommended decoupling and then verify with a PDN impedance simulation: model the regulator output impedance, the plane capacitance, the mounting inductance of each capacitor, and the via/lead inductance, and plot |Z| versus frequency against the target impedance derived from the allowed ripple and the transient current. The critical insight is that above a few tens of megahertz the capacitor values stop mattering and the mounting inductance dominates — so placement and via count matter more than the BOM. I'd also check the anti-resonance peaks between the bulk and ceramic banks, because a naive spread of values can create a high-impedance peak right where the SerDes draws current. Before layout commit, I'd confirm the plane pair provides adequate buried capacitance, that each decoupling cap has a short, low-inductance path to the pin and to the ground plane, and that the regulator's transient response covers the low-frequency end. Verification is simulation plus, once hardware exists, a measured impedance or ripple check under realistic load.

**Possible follow-ups:** How would you decide whether a plane-pair buried capacitance is worth the layer cost versus relying on discrete caps? What would you do if the measured ripple exceeded spec only at a specific frequency band?

## Q4: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?

**Answer:** A via that passes through a thick board but is only used for a layer transition leaves an unused stub below the signal layer, and that stub behaves as a resonant transmission-line branch that causes a notch in the channel response at a frequency set by the stub length and the board's effective dielectric constant. On a thick backplane the stub can easily be long enough that the notch lands inside the signal's bandwidth, so I'd address it at three levels. First, layout: use blind or buried vias so the via only spans the layers actually needed, or back-drill the unused portion after plating to shorten the stub to a controlled residual. Second, if back-drilling isn't available, I'd consider whether the transition can be routed to avoid the long stub entirely — for example, choosing layer pairs that minimize the via span. Third, verify: extract the via with a 3D field solver, include it in the channel model, and run the channel simulation to see whether the notch and the resulting insertion-loss/return-loss degradation still leave adequate margin at the target data rate. I'd also watch the reference-plane continuity through the via — a layer transition that also changes reference planes needs stitching vias to keep the return current path continuous, or the discontinuity compounds the stub problem. The decision between back-drilling cost and accepting the stub is a margin question answered by the channel simulation, not by rule of thumb.

**Possible follow-ups:** How would you decide how much residual stub is acceptable for a given data rate? What role does the connector's own via/launch structure play in the overall channel budget?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented the data path that captures samples from a high-speed ADC and writes them to DDR memory. During the review, you notice they've sized the capture FIFO from the average throughput rather than the worst-case burst, arguing that "the average rate is well below the memory bandwidth, so it can't overflow." How do you handle this situation?

**Answer:** I'd treat it as a teaching moment rather than a correction, because the reasoning error is a common and instructive one. First I'd make sure I understand their model — ask them to walk me through the burst behavior they assumed and where the average figure came from. Then I'd reframe the problem: a FIFO's depth is set by the worst-case *accumulation* of data during the longest interval the downstream can't drain, not by the long-term average. If the ADC can emit a burst faster than the memory controller can absorb it — because of refresh, arbitration with other masters, or write-buffer limits — the FIFO fills at the burst rate minus the drain rate, and the average is irrelevant during that window. I'd ask them to compute the worst-case fill for the longest plausible stall and compare it to the depth. If the depth is genuinely insufficient, the fix is either a deeper FIFO, backpressure to the ADC (if it supports it), or a scheduling change on the memory side — and I'd let them drive that analysis so the lesson sticks. Throughout I'd keep the tone collaborative: the goal is that they internalize "size for worst case, verify with the average," not that they feel caught out. I'd also note that this is exactly the kind of thing a design review exists to catch, which reinforces why we do them.

**Possible follow-ups:** How would you verify the worst-case fill assumption once hardware exists? If backpressure to the ADC isn't possible, what are the trade-offs of a deeper FIFO versus changing the memory access schedule?
