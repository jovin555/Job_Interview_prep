# high-speed-digital-fpga — Day 50

## Q1: How would you approach designing a clock domain crossing (CDC) scheme for a multi-bit data bus where the source and destination clocks are asynchronous, the data changes frequently, and you need to minimize latency while ensuring data integrity?
**Answer:** For asynchronous multi-bit data transfer with frequent changes and low-latency requirements, I'd start by analyzing the actual data flow characteristics. If the data is continuous and must not be dropped, an asynchronous FIFO is the standard approach — it handles the full rate mismatch and provides buffering. The key design decisions are FIFO depth (based on worst-case burst analysis, not just average rates) and the synchronization of the read/write pointers across domains. For pointer crossing, I'd use Gray-coded pointers with multi-stage synchronizers to avoid multi-bit metastability issues. If the data is more sporadic — where the source can hold data stable until acknowledged — a handshake-based approach (request/acknowledge with full synchronization on both sides) could work with lower latency than a FIFO, though it adds back-pressure. For truly minimal latency with frequent changes, I'd consider whether the data can tolerate occasional dropping of stale values; if so, a "toggle + data hold" scheme where the source asserts a toggle signal alongside stable data, and the destination synchronizes the toggle and samples the data once stable, can work — but this requires the data to remain stable long enough for synchronization (at least two destination clock cycles plus setup/hold margins). The critical analysis is always: what's the worst-case timing relationship, what failure modes are acceptable, and what does the system-level protocol require? I'd also verify the design with formal CDC analysis tools and constrained-random simulation with realistic clock jitter and phase relationships.

**Possible follow-ups:** How would you determine the required FIFO depth for an asynchronous transfer where the write rate can burst at 2x the read rate for up to 100 cycles? What happens if your Gray-coded pointers are not perfectly aligned due to routing delays in the FPGA fabric?

## Q2: How would you approach debugging an FPGA design where the configuration bitstream loads successfully (DONE pin goes high), but the design's internal state machine appears to be stuck in an illegal state only when a specific external input sequence occurs, and the issue is not reproducible in RTL simulation?
**Answer:** This is a classic "works in simulation, fails in hardware" scenario that requires systematic isolation. First, I'd verify that the state machine actually is in an illegal state — I'd use an integrated logic analyzer (ILA) or expose the state register to debug pins to capture the actual state sequence during the failure. If it's truly in an illegal state, I'd check whether the RTL has a default/others clause that handles all possible state encodings — synthesis tools can optimize away unreachable states unless you explicitly preserve them or use safe-state recovery. A common root cause is that the synthesis tool re-encodes the state machine (e.g., one-hot to binary) and the reset condition doesn't cover all possible flip-flop combinations, especially if the reset is asynchronous and not held long enough. Another possibility is that the input sequence in hardware differs from simulation — perhaps due to input glitches, metastability on an un-synchronized input, or a race condition between multiple inputs changing simultaneously. I'd add input synchronization registers and check the actual captured input timing against the RTL assumptions. I'd also verify that the state machine's reset is properly connected and that the device's global reset (GSR) is actually released after configuration. If the issue is timing-related — the state machine transitions based on combinational logic that doesn't meet timing under specific input skew conditions — I'd run static timing analysis on the state machine paths and check for any unconstrained paths. Finally, I'd review the synthesis logs for any warnings about the state machine encoding or unreachable states, and consider adding a watchdog or safe-state recovery mechanism that forces the FSM back to a known state if it detects an illegal encoding.

**Possible follow-ups:** How would you implement a safe-state recovery mechanism without adding excessive logic? What synthesis attributes or coding styles would you use to ensure the state machine is not optimized in a way that removes illegal-state detection?

## Q3: How would you approach designing a power distribution network (PDN) for an FPGA with multiple voltage rails, where the core rail (0.85V) has a transient current demand of up to 20A with a slew rate of 1A/ns, and you need to ensure the voltage stays within ±3% of nominal?
**Answer:** The core rail is the most challenging because of the combination of low voltage, high current, and fast transient response. The ±3% budget on 0.85V means the voltage must stay between roughly 0.8245V and 0.8755V — that's only about ±25mV of total tolerance, which includes DC drop, AC ripple, and transient excursions. I'd approach this in layers. First, the voltage regulator module (VRM) must have sufficient bandwidth to respond to the transient — a multi-phase buck converter with a high switching frequency and fast transient response is essential. The VRM's control loop bandwidth determines how much of the transient the bulk capacitance must handle before the regulator can respond. Second, the decoupling network must be designed to handle the initial di/dt before the VRM reacts. I'd use a combination of bulk capacitors (electrolytic or polymer) near the VRM output, ceramic capacitors in the mid-frequency range (22µF to 100µF in 0402/0603 packages) distributed across the board, and high-frequency decoupling (100nF and smaller) placed as close to the FPGA power pins as possible. The key is to create a flat impedance profile across the frequency range of interest — typically from a few kHz (VRM crossover) up to several hundred MHz (where the on-die capacitance and package inductance take over). I'd target a maximum PDN impedance of around 1-2 mΩ across this range. Third, the PCB stack-up and layout are critical: I'd use dedicated power and ground planes with minimal separation (e.g., 2-4 mil dielectric) to maximize plane capacitance, place vias strategically to minimize inductance between the FPGA and the decoupling capacitors, and use multiple vias in parallel to reduce via inductance. I'd also consider the FPGA package — the number and location of power/ground pins affects the effective inductance. For verification, I'd perform a PDN simulation using SPICE or specialized tools that model the VRM, capacitor networks, plane impedance, and package model together. I'd also do time-domain transient simulations with a current profile that matches the FPGA's worst-case switching pattern. On the bench, I'd measure the actual PDN impedance with a network analyzer and verify transient response with a high-bandwidth oscilloscope probing directly at the FPGA power pins using a coaxial probe technique to avoid ground bounce artifacts.

**Possible follow-ups:** How would you determine the worst-case transient current profile for the FPGA? What is the role of the FPGA's on-die capacitance and how does it affect your external decoupling strategy?

## Q4: How would you approach implementing a high-speed data path in an FPGA that must process a continuous stream of 16-bit samples at 500 MSPS, perform a 64-tap FIR filter, and output the filtered result without any dropped samples, while also meeting timing at the target clock frequency?
**Answer:** The fundamental challenge here is that 500 MSPS exceeds what most FPGA fabrics can handle directly — typical fabric clocks are 200-400 MHz. So the first decision is the parallelization strategy. I'd use a time-division multiplexed approach where the input is deserialized into multiple parallel samples per clock cycle. For example, at a 250 MHz fabric clock, I'd process two samples per cycle; at 125 MHz, four samples per cycle. The FIR filter then needs to be restructured into a polyphase or parallel form. For a 64-tap FIR with 2x parallelism, I'd split the filter into two polyphase sub-filters, each handling every other input sample. Each sub-filter would have 32 taps (since every other tap contributes to each output phase). The key insight is that the filter coefficients are shared, but the data path is interleaved. I'd use DSP slices for the multiply-accumulate operations — modern FPGAs have dedicated DSP blocks that can operate at high clock rates. The challenge is efficiently mapping the polyphase structure onto the DSP resources. For a 64-tap filter at 2x parallelism, I need 64 MAC operations per two output samples, which at 250 MHz gives me 4 ns per two outputs — so I need 64 DSP slices operating in parallel, or I can time-share fewer DSP slices if the clock rate allows. I'd also need to carefully manage the data flow: the input samples need to be buffered and aligned so that each polyphase branch receives the correct samples. Block RAMs can be used for the delay line, with careful addressing to provide the right samples to each branch. The output must be re-serialized to match the output data rate. For timing closure, I'd pipeline the multiplier inputs and accumulate chains appropriately — the DSP slices have built-in pipeline registers that can be used to break long combinational paths. I'd also consider using the FPGA's dedicated FIR compiler IP if available, which handles the polyphase decomposition and DSP mapping automatically, though I'd verify its throughput and latency characteristics. The critical verification step is to simulate the parallel implementation against a bit-exact reference model of the original filter to confirm the output matches sample-for-sample.

**Possible follow-ups:** How would you handle the filter's group delay when operating in parallel mode? What if the filter coefficients are programmable and need to be updated on-the-fly without interrupting the data stream?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer on your team has implemented the data path that captures samples from a 500 MSPS ADC and writes them to DDR3 memory. During the review, you notice that the engineer has used a single FIFO to cross from the ADC clock domain to the memory controller clock domain, but the FIFO depth is only 64 words. When you ask about the depth, the engineer explains that the average write rate is well below the read rate, so the FIFO should never overflow. However, you're concerned about burst behavior — the ADC can produce bursts of data that could temporarily exceed the memory controller's sustainable write rate. The engineer argues that the memory controller's write buffer will absorb the bursts. How do you handle this situation?
**Answer:** I'd approach this as a coaching opportunity combined with rigorous engineering analysis. First, I'd acknowledge the engineer's reasoning — the average-rate analysis is a valid starting point, and it's good that they're thinking about the memory controller's buffering. However, I'd guide them through a more complete worst-case analysis. I'd ask them to walk me through the specific burst characteristics: what's the maximum burst duration from the ADC, what's the memory controller's sustainable write rate (not peak, but sustainable — accounting for refresh cycles, read/write turnaround, and bank conflicts), and what's the worst-case latency for the memory controller to accept data once the FIFO asserts its almost-full flag? I'd encourage them to calculate the required FIFO depth using the formula: FIFO depth = (burst_rate - sustainable_rate) × burst_duration + round-trip_latency × sustainable_rate. I'd also point out that the memory controller's write buffer is not a substitute for the FIFO — it has its own constraints and can fill up under certain access patterns. Rather than just telling them the answer, I'd ask them to model the worst-case scenario in simulation — create a testbench that generates the maximum ADC burst pattern and the worst-case memory controller behavior (e.g., periodic refresh colliding with the burst) and observe whether the FIFO overflows. If the analysis shows the FIFO is insufficient, I'd discuss the options: increasing FIFO depth (what's the cost in block RAM resources?), adding flow control to throttle the ADC (is that possible with this ADC?), or using a larger elastic buffer with a watermark-based interrupt to the memory controller. I'd also emphasize that this kind of analysis should be documented in the design specification so future reviewers understand the reasoning. The goal is to help the engineer develop the habit of questioning average-case assumptions and always validating against worst-case scenarios, especially in real-time data acquisition systems where dropped samples are unacceptable.

**Possible follow-ups:** How would you help the engineer develop a simulation testbench that accurately models the memory controller's worst-case latency? What documentation or design review process would you put in place to catch similar issues earlier in future designs?
