# high-speed-digital-fpga — Day 104

## Q1: How would you approach designing the power-up and configuration sequence for an FPGA that loads its bitstream from external flash, when the flash device itself has a non-trivial access latency and the board may be power-cycled rapidly?

**Answer:** The core problem is that the FPGA's configuration engine starts driving its configuration interface as soon as its configuration I/O rails are valid, but the flash may not be ready to respond yet — and on a rapid power cycle, the flash may still be in the middle of its own internal recovery or wake-up sequence. I'd approach it in layers.

First, define the power sequencing so that the FPGA's configuration-related rails (typically the I/O bank supplying the configuration pins, plus the auxiliary rail) come up in the order the device requires, and hold the FPGA in reset until all rails are within tolerance and stable. The reset should be driven by a supervisor that monitors all rails, not just one, so a slow-ramping rail doesn't release the FPGA early.

Second, treat the flash's wake-up latency as a first-class timing requirement. I'd pull the flash datasheet's worst-case power-up-to-ready time and add margin, then either (a) delay the FPGA's configuration start by that amount using a supervisor with a programmable delay, or (b) have the FPGA's configuration controller poll a flash status/ready signal before issuing the first read. Option (b) is more robust because it adapts to the actual device rather than a fixed timer, but it requires the flash to expose a ready indication the FPGA can sample.

Third, handle the rapid power-cycle case explicitly. On a fast off-on transition, the flash may not have fully discharged, and some flash devices require a minimum reset pulse width or a minimum time between power cycles before they'll respond correctly. I'd add a power-fail detector that holds the FPGA in reset until the supply has fallen below a threshold and then risen again cleanly, and I'd verify the flash's minimum power-cycle timing against the supervisor's behavior. If the flash has an internal power-on reset that's slower than the board's ramp, the supervisor delay must cover that.

Finally, I'd verify the whole sequence on the bench with a scope: capture the rails, the FPGA reset release, the configuration start, and the flash's first response, and deliberately test rapid power cycling (short off times, repeated cycles) to confirm the FPGA either configures correctly or stays in reset — never starts configuring against a flash that isn't ready. A configuration retry mechanism in the FPGA (or a system controller that re-triggers configuration on failure) is a good backstop, but it shouldn't be the primary defense.

**Possible follow-ups:** How would you decide between a fixed supervisor delay and polling a flash ready signal, and what would push you toward one or the other? What would you check first if the board configured reliably on a slow bench supply but failed intermittently on a fast-ramping production supply?

## Q2: How would you approach debugging an FPGA design where the transceiver link passes its built-in PRBS checker at the physical layer, but application-level data is occasionally corrupted, and the corruption only appears at full line rate?

**Answer:** The PRBS checker passing tells me the SerDes analog front end, the CDR, and the serial/parallel conversion are basically healthy — the eye is open enough and the link is bit-locked. So the corruption is almost certainly above the PMA, in the PCS or the user logic, and the fact that it only appears at full line rate points at something that has no timing margin to spare: FIFO behavior, clock domain crossing, or backpressure handling.

My first move is to localize where the corruption is introduced. I'd instrument the datapath with a known pattern generator and checker placed at successive points — after the transceiver's parallel output, after the RX FIFO, after the CDC into the application clock domain, and at the application interface — and see which stage first shows errors. If the pattern is clean at the transceiver output but corrupted after the FIFO, the problem is in the FIFO/CDC; if it's clean all the way to the application interface but the application still sees bad data, the problem is in how the application consumes it (e.g., a handshake or backpressure bug).

At full line rate, the usual suspects are: an RX elastic FIFO that overflows or underflows because the recovered clock and the local clock drift slightly and the FIFO depth or the clock-correction scheme isn't adequate; a CDC that works at low rate because the synchronizer has time to settle but fails when the data changes every cycle; or a flow-control path where the application occasionally can't accept a word and the backpressure isn't propagated correctly, so a word is dropped or duplicated. I'd also check whether the error rate scales with line rate — if it does, it's a margin/timing issue; if it's constant per unit time, it's more likely an event-driven bug like a FIFO overflow on a burst.

I'd also look at the transceiver's error counters and status flags (FIFO overflow/underflow, disparity errors, clock-correction events) — many transceiver IPs expose these, and they'll often point directly at the mechanism. And I'd confirm the reference clock quality and the local clock the RX FIFO is referenced to, because a noisy or drifting reference can cause slow FIFO creep that only manifests at high sustained rates.

**Possible follow-ups:** If the RX elastic FIFO is underflowing at full rate, what are the possible root causes and how would you distinguish them? How would you design the test pattern and checker to distinguish a dropped word from a bit error from a duplicated word?

## Q3: How would you approach designing the clock domain crossing for a multi-bit control word that is written by a slow serial interface (e.g., 10 MHz SPI) and consumed by a fast logic domain (e.g., 250 MHz), where the word changes infrequently but must never be observed in a partially updated state?

**Answer:** The key insight is that the word changes infrequently, so I don't need a high-throughput CDC — I need a coherent-snapshot CDC with a handshake, not a per-bit synchronizer. Synchronizing each bit with a two-flop synchronizer would be wrong here: even though the word changes rarely, when it does change, multiple bits can change on the same source clock edge, and the destination could sample a mix of old and new bits during the transition.

The standard robust approach is a handshake-based transfer. The SPI domain writes the new word into a holding register, then toggles a request signal (a single bit) that is synchronized into the 250 MHz domain with a two-flop synchronizer. The fast domain detects the toggle (by comparing against a registered copy), captures the multi-bit word into its own register, and asserts an acknowledge that is synchronized back to the SPI domain. The SPI domain doesn't start the next write until it sees the acknowledge. Because the word is stable in the holding register for the entire time the request is in flight and until the acknowledge returns, the fast domain always captures a coherent value.

A few design details matter. The request toggle must be a single bit and must not be re-asserted until the previous transfer is acknowledged — otherwise you can lose a transfer. The fast domain should register the captured word and use that registered copy, so the capture is a single clean clock edge. And I'd add a constraint (a false path or a max-delay/`set_max_skew`-style constraint, depending on the tool) on the multi-bit bus between the two domains so the timing tool doesn't try to time it as a normal synchronous path — the handshake, not the bus timing, guarantees correctness. I'd also run a CDC lint/formal check to confirm the tool sees the synchronizers and the handshake correctly and doesn't flag the bus as an unsynchronized crossing.

If the SPI domain could ever be reset independently of the fast domain, I'd make sure the handshake protocol handles that — e.g., the fast domain treats a stuck request as a timeout, or the reset architecture guarantees both domains come out of reset in a known state before the first transfer.

**Possible follow-ups:** Why is a two-flop synchronizer per bit insufficient here even though the word changes infrequently? How would you constrain the multi-bit bus in the timing tool, and what would go wrong if you constrained it as a normal synchronous path?

## Q4: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?

**Answer:** A via through a thick backplane has a stub — the unused portion of the barrel below the layer where the signal enters or exits — and that stub behaves as a resonant transmission-line stub. At multi-gigabit rates, the stub's resonance can cause a deep notch in the channel's insertion loss and significant reflections, which shows up as eye closure and elevated jitter. The mitigation strategy depends on how much stub length I'm stuck with.

The first lever is layout: route the signal so the via is used as close to the far end of the barrel as possible, minimizing the stub length. On a thick backplane, that often means entering the board on the top layer and exiting on the bottom layer, or vice versa, so the stub is nearly zero — but that constrains the layer assignment and may not be possible for every net. Where it isn't, I'd consider whether the channel can be routed on layers that minimize the stub for the critical high-speed lanes, even if slower signals take the longer via.

The second lever is backdrilling: drill out the unused portion of the via barrel after plating, which removes most of the stub. This is the standard fix for thick backplanes and is very effective, but it adds cost and manufacturing steps, and it has its own tolerances (drill depth accuracy, remaining stub). I'd specify backdrill depth with margin and confirm the fabricator's capability.

The third lever is via design itself: use a smaller via barrel and pad (higher impedance, less capacitance), and consider whether a blind/buried via stack-up is feasible — though on a backplane that's often not practical. I'd also look at whether the connector and the via can be co-designed so the via stub resonance is pushed above the signal's bandwidth, or whether the channel can tolerate it with equalization.

Finally, I'd verify with simulation before committing: extract the via with a 3D field solver, include the stub, and look at the channel's insertion loss and TDR. If the notch falls inside the signal's spectrum, I'd iterate on backdrill depth or layer assignment. On the bench, TDR and VNA measurements of the assembled backplane confirm the model.

**Possible follow-ups:** How would you decide whether backdrilling is necessary versus relying on equalization at the receiver? What does a via stub resonance look like in a TDR trace, and how would you distinguish it from a connector discontinuity?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?

**Answer:** My first reaction is not to accept or reject the exceptions, but to make the review about the evidence for each one. Timing exceptions are legitimate design intent when they're correct and documented — a multicycle path on a slow control signal that's genuinely stable for multiple cycles is a real thing, and a false path on a test or asynchronous path is real too. But an exception added to make a failing design close is a red flag, because it can hide a real timing violation behind a constraint that says "don't check this." The distinction is whether the exception reflects how the logic actually behaves, or whether it reflects what the engineer needed to get a clean report.

So I'd walk through the exceptions one at a time with the engineer, and for each one ask: what is the logic on this path, why does it not need to meet single-cycle timing, and what in the design guarantees that? For a multicycle path, I'd want to see the enable or the protocol that makes the data stable for N cycles, and I'd want the multicycle value to match that. For a false path, I'd want to confirm the path is genuinely asynchronous or functionally don't-care, not just "slow." If the engineer can't articulate the justification in terms of the design's behavior, the exception isn't ready.

I'd also check the process around the exceptions: are they documented with a comment explaining the intent, are they reviewed by someone other than the author, and does the CDC/timing lint tool agree with them? A common failure mode is a false path applied to a path that's actually a CDC that needs a synchronizer — the exception silences the tool but doesn't make the crossing safe. I'd cross-check the exceptions against the CDC report.

Then I'd frame the conversation constructively: the goal isn't to catch the engineer out, it's to make sure the sign-off means something. If an exception is legitimate, we document it and move on. If it isn't, we fix the design or the constraint, and if that means the design doesn't close, that's the real answer and we deal with it — retiming, pipelining, or revisiting the architecture. I'd also use it as a coaching moment about why "the report is clean" is only meaningful if the constraints are trustworthy, and I'd suggest a review checklist for timing exceptions going forward so this is caught earlier.

**Possible follow-ups:** How would you distinguish a legitimate multicycle path from a false path that's masking a real violation? What process would you put in place so timing exceptions get reviewed before sign-off rather than discovered in a design review?
