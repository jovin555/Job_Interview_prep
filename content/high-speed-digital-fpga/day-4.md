# high-speed-digital-fpga — Day 4

## Q1: How would you approach designing a power-on reset (POR) circuit for an FPGA that must guarantee reliable configuration across a wide temperature range and with multiple power rails that ramp at different rates?

**Answer:** A robust POR strategy for an FPGA needs to address three things: the FPGA's own configuration requirements, the sequencing of multiple power rails, and the reset state of any external peripherals. First, I'd review the FPGA vendor's power-up sequence specification—some FPGAs require core voltage to stabilize before I/O banks, others are more tolerant. I'd use a dedicated voltage supervisor IC with programmable thresholds and a delay timer rather than a simple RC circuit, because the RC time constant drifts significantly with temperature and capacitor aging. The supervisor should monitor the slowest-ramping rail and hold the FPGA's PROGRAM_B or INIT_B pin low until all rails are within tolerance plus a safety margin (typically 50-100ms). For the external reset signal going to the FPGA fabric and any peripherals, I'd generate a separate, synchronized reset using the FPGA's own configuration-done signal—this ensures the fabric is operational before releasing resets to external devices. I'd also add a manual reset input debounced by the supervisor IC for debugging. For temperature extremes (e.g., -40°C to +85°C), I'd select a supervisor with a specified temperature coefficient and verify the delay timer's accuracy across the range in simulation.

**Possible follow-ups:** How would you handle the case where the FPGA must wake from a low-power state where some rails are turned off? What if the system has a battery-backed RTC that must retain time during power-down?

## Q2: How would you approach debugging an FPGA design where the DSP slices are producing incorrect results only when processing data at the maximum throughput rate, but work correctly at lower clock frequencies?

**Answer:** This pattern—correct at low speed, incorrect at high speed—strongly suggests a timing or pipelining issue rather than a logic error. I'd start by checking the timing report for the DSP slice paths, specifically looking at the setup and hold slack on the input registers and the pipeline registers inside the DSP block. Many FPGA DSP slices have dedicated internal pipeline registers that must be explicitly enabled; if they're bypassed, the combinatorial path through the multiplier and adder can exceed the clock period at high frequency. I'd verify the synthesis constraints correctly define the clock period and that the DSP slice is not being inferred with insufficient pipelining. Next, I'd examine the input data and coefficient alignment—if data arrives from different clock domains or through different amounts of logic, the DSP inputs might not be synchronized at the full rate. I'd add input registers immediately before the DSP slice, clocked by the same clock, to ensure deterministic timing. I'd also check whether the DSP output is being read on the correct clock edge—a common mistake is using the wrong edge or failing to account for the DSP's output register latency. Finally, I'd simulate the DSP block in isolation at the target frequency using post-place-and-route simulation, which accounts for actual routing delays, to confirm the issue is timing rather than a logic bug.

**Possible follow-ups:** How would you determine whether the issue is in the DSP slice itself versus the data path feeding it? What if the timing report shows positive slack but the problem persists?

## Q3: How would you approach selecting and configuring I/O standards for an FPGA bank that must interface with both a high-speed LVDS serial link (1.5 Gbps) and several single-ended 3.3V control signals?

**Answer:** This is a common challenge because mixing high-speed differential and single-ended signals in the same I/O bank can cause signal integrity problems. The LVDS signals are sensitive to noise from the 3.3V single-ended signals switching simultaneously, and the single-ended signals can couple into the differential pair. My approach would be to first check the FPGA's I/O bank architecture—some banks support mixed standards, but the LVDS pairs typically require specific pin pairs and VREF voltages. If the bank supports it, I'd assign the LVDS pairs to pins that are physically separated from the 3.3V signals, ideally at opposite ends of the bank. I'd also check whether the LVDS requires an external termination resistor (100 ohms differential) or if the FPGA has internal termination—if internal, I'd enable it to save board space. For the 3.3V signals, I'd use slow-slew-rate settings and lower drive strength where timing allows, to reduce switching noise. If the bank doesn't support mixing these standards, I'd need to either use a separate I/O bank for the LVDS or add level translators. I'd also verify the VCCO voltage for the bank—LVDS typically uses 2.5V VCCO, while 3.3V signals need 3.3V VCCO, so they cannot share a bank unless the FPGA supports dual-VCCO banks (rare). In practice, I'd likely assign the LVDS to a dedicated bank and the 3.3V signals to another bank, using a series resistor or level shifter if necessary.

**Possible follow-ups:** What if board space constraints force you to use a single bank? How would you handle the VCCO voltage conflict?

## Q4: How would you approach implementing a FIFO buffer in an FPGA that crosses from a 200 MHz write clock domain to a 150 MHz read clock domain, where the write side produces 32-bit data bursts of up to 64 words, and the read side consumes data at a variable rate?

**Description:** This is a classic clock domain crossing (CDC) problem requiring a dual-clock FIFO. The key parameters are the burst size (64 words), the write clock (200 MHz), and the read clock (150 MHz). The worst-case fill occurs when a full burst arrives while the read side is idle—the FIFO must hold at least 64 words plus margin for the read clock to catch up. I'd calculate the required depth: at 200 MHz, 64 words take 320 ns to write; during that time, the read side at 150 MHz can read at most 48 words (320 ns × 150 MHz), so the FIFO needs at least 64 + margin (say 16) = 80 words. I'd choose a depth of 128 words for safety. For the implementation, I'd use the FPGA vendor's dual-clock FIFO primitive or IP core rather than building one from LUTs, because the vendor version includes properly synchronized gray-code pointers and empty/full flag generation that handles metastability. I'd configure it with independent clocks, standard synchronous read/write enables, and almost-empty/almost-full flags for flow control. The write side would assert a "write enable" signal only when data is valid, and the read side would assert "read enable" when it can consume data. I'd also add a programmable almost-full threshold to throttle the write side before the FIFO overflows—for example, asserting backpressure when the fill level exceeds 96 words. For verification, I'd simulate the FIFO with worst-case burst patterns and clock jitter to ensure no data loss or corruption.

**Possible follow-ups:** How would you handle the case where the read clock is derived from a recovered clock (e.g., from a serial link) and has significant jitter? What if the write and read clock domains are asynchronous but nominally the same frequency?

## Q5: Behavioral question — You're the lead engineer on a high-speed FPGA design project. During a design review, a junior engineer presents a simulation showing the design meets timing at the slow-slow process corner but fails at the fast-fast corner. The engineer suggests ignoring the fast-fast corner because "the chip will never actually run that fast." How do you handle this situation?

**Answer:** I'd first acknowledge the engineer's observation—it's true that fast-fast corners represent a best-case process, and many designs do pass at slow-slow and typical corners. However, I'd explain that fast-fast corner failures are still important because they indicate hold-time violations, which can cause data corruption even at nominal operating conditions. A hold violation means data arrives too early relative to the clock, and this can happen at any voltage/temperature combination, not just at the fast-fast corner. I'd walk through the timing report together to identify which paths are failing—are they short paths through minimal logic, or are they clock skew issues? Often, fast-fast failures are easier to fix than slow-slow failures because they typically require adding delay rather than restructuring logic. I'd suggest we prioritize fixing the hold violations by adding delay elements, adjusting output delays, or balancing clock skew. If the engineer is still concerned about the effort, I'd propose we run a statistical timing analysis to see the probability of failure across the full operating range, and use that data to make an informed decision. Ultimately, for a high-speed design that must work reliably across temperature and voltage, I'd insist on closing timing at all three corners (slow-slow, typical, fast-fast) unless we have strong evidence from the specific application that the fast-fast corner is physically impossible—for example, if the FPGA is in a system with a voltage regulator that cannot supply the higher voltage needed for the fast-fast condition. I'd frame this as a learning opportunity: timing closure at all corners is standard practice for high-speed digital design, and understanding why each corner matters builds good engineering judgment.

**Possible follow-ups:** What if the project schedule is tight and fixing the fast-fast violations would delay tape-out by two weeks? How would you prioritize between fixing hold violations versus adding more functionality?
