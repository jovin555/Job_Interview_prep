# high-speed-digital-fpga — Day 101

## Q1: How would you approach designing the I/O planning for an FPGA that must interface with a DDR3 memory controller, a high-speed differential ADC, and a bank of slow GPIO, given that I/O bank voltage and standard choices are constrained by each bank's VCCO?
**Answer:** I'd start by grouping interfaces by their electrical requirements rather than by logical function, because the VCCO of a bank is shared across every pin in it and can't be mixed arbitrarily. DDR3 needs SSTL-class I/O at 1.5V (or the appropriate VDDQ for the memory generation), the differential ADC interface needs a high-speed differential standard — LVDS or a dedicated SerDes-capable bank — and the slow GPIO likely wants 3.3V CMOS. Those three voltage domains are mutually incompatible within a single bank, so the first task is to confirm the device has enough banks at each required VCCO and that the DDR3 byte groups and their associated DQS/strobe pins land in banks that can be set to the memory's VDDQ. I'd also check whether the differential ADC interface needs true transceiver pins or can be handled by LVDS-capable fabric I/O, since that changes which banks are even candidates. Beyond voltage, I'd respect the physical constraints: DDR3 byte lanes and their strobes must stay within the correct byte-group pins, differential pairs must use true differential pin pairs, and I'd leave margin for the reference clock and any configuration pins that are fixed by the device. Finally I'd verify the plan against the pinout early — before RTL is far along — because I/O planning mistakes are expensive to unwind once the board is laid out, and I'd document the bank/voltage assignment as part of the interface control documentation so the PCB and FPGA teams work from the same map.
**Possible follow-ups:** What would you do if the device simply doesn't have enough banks at one of the required voltages — how would you trade off between changing the memory interface width and moving GPIO to an external expander? How do you handle a differential pair that must cross from one bank to another because of pinout constraints?

## Q2: How would you approach debugging an FPGA design where the timing analysis reports that all constraints are met, but the design fails in hardware only when the device is operated at the maximum specified junction temperature?
**Answer:** Static timing analysis signs off against the corner models you give it, so "all constraints met" at the nominal or slow corner doesn't guarantee margin at the hot corner — and a failure that appears only at maximum junction temperature points at either insufficient timing margin under the hot (typically slower for many process nodes, but with different interconnect behavior) corner, or a non-timing effect that temperature exposes. My first step is to re-run timing with the hot corner explicitly selected and with the same constraints, and to look at the actual slack distribution rather than the pass/fail summary — paths that were barely positive at nominal are the suspects. I'd also check whether the design was signed off with any timing exceptions that might be masking a real path, and whether the clock uncertainty and derating assumptions match the device's datasheet at temperature. If timing looks genuinely clean at the hot corner, I'd widen the investigation to non-timing causes that correlate with heat: PLL or MMCM lock behavior and jitter over temperature, reference clock drift, power supply margin and ripple as the regulators' behavior changes with temperature, and any analog front-end or interface whose timing shifts. On the bench I'd use the device's internal logic analyzer or a debug core to see whether the failure is a setup/hold-style data corruption or a control-path failure, and I'd try to reproduce it in a temperature chamber with the design instrumented so I can see which signal breaks first. The fix depends on the root cause — adding pipeline margin, tightening constraints and re-closing, adjusting clocking, or correcting a power/analog issue — but the discipline is to separate "timing margin" from "everything else that temperature touches" before changing anything.
**Possible follow-ups:** How would you decide whether to add a pipeline stage versus re-constrain and re-close when a hot-corner path is marginal? What role does the device's on-chip temperature sensor and voltage monitoring play in your debug strategy?

## Q3: How would you approach designing the clock domain crossing for a multi-bit control word that is written by a slow serial interface (e.g., 10 MHz SPI) and consumed by a fast logic domain (e.g., 250 MHz), where the word changes infrequently but must never be observed in a partially updated state?
**Answer:** The key insight is that the word changes infrequently, so latency is cheap and correctness is the priority — this is a classic case for a handshake or a toggle-based scheme rather than trying to synchronize the bits directly. A two-flop synchronizer per bit would be wrong here because the bits can arrive skewed relative to each other and the fast domain could sample a mix of old and new bits. Instead I'd register the full word in the slow domain, then pass a single control bit — a toggle or a request — through a two-flop synchronizer into the fast domain. The fast domain detects the edge of the synchronized toggle, captures the entire word in one clock, and optionally sends an acknowledge back through its own synchronizer so the slow side knows the transfer completed before it updates the word again. Because the word is held stable in the slow domain until the acknowledge returns, the fast domain always sees a coherent value. I'd also make sure the slow-domain register is updated atomically — load the whole word on one SPI transaction boundary, not byte by byte — and I'd add a formal or simulation check that the fast domain never captures while the source is changing. If the interface needed to be simpler and the update rate truly negligible, a gray-coded or double-buffered approach could work, but the toggle-handshake is the most robust and easiest to reason about.
**Possible follow-ups:** How would you handle the case where the fast domain might be reset independently of the slow domain — what happens to an in-flight handshake? Would you use the same structure for a status word flowing the other direction, and what changes?

## Q4: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?
**Answer:** A via through a thick backplane leaves an unused portion — the stub — that behaves as an open-circuited transmission-line branch, producing a resonance that causes insertion-loss dips and return-loss peaks at frequencies related to the stub length and the board's effective dielectric constant. The first lever is to eliminate or shorten the stub: use blind or buried vias, or back-drill the via after plating to remove the unused barrel, which is the standard fix on thick backplanes. If back-drilling isn't available, I'd consider a via-in-pad or laser-drilled structure, or routing the channel so the layer transition happens where the stub is inherently short. Where the stub can't be removed, I'd model it — extract the via with a 3D field solver and include it in the channel simulation with the connector and package models — and then compensate at the link level: the SerDes equalization (pre-emphasis/FFE on transmit, CTLE/DFE on receive) can often recover a modest stub resonance, and I'd verify the eye at the target line rate with the actual channel model rather than assuming. I'd also check that the stub resonance doesn't land on a harmonic that matters for the specific data rate, and I'd keep the via antipads and return-path stitching vias well-designed so the transition doesn't add a return-path discontinuity on top of the stub. The decision between back-drilling cost and equalization margin is a trade-off I'd make explicitly with the channel simulation in hand.
**Possible follow-ups:** How would you decide the maximum acceptable stub length for a given line rate before equalization can no longer compensate? What return-path considerations apply at the same via transition, and how do stitching vias change the picture?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?
**Answer:** I'd treat this as a review-quality issue rather than an accusation, because timing exceptions are legitimate tools when they're justified — the problem is that an unjustified exception silently removes a real constraint and produces a design that passes analysis but can fail in hardware. My approach in the review is to ask the engineer to walk through each exception and explain the physical or architectural reason it's valid: a false path should correspond to a path that genuinely can't be exercised (for example, a configuration-only path or a path between mutually exclusive modes), and a multicycle path should correspond to logic that provably has multiple cycles to settle, with the setup/hold relationship documented. I'd ask for that justification to be captured in the constraints file as comments or in a constraints review document, so the reasoning is auditable later. If an exception can't be justified, we remove it and re-close timing honestly — even if that means adding pipeline stages or restructuring logic — because shipping a design that only closes because of a bad exception is a latent field failure. I'd frame the conversation around the shared goal of a design that works in hardware, not around who's right, and I'd use it as a coaching moment: the skill of justifying exceptions is exactly what separates a timing report that means something from one that doesn't. I'd also make exception review a standing item in future design reviews so it doesn't depend on someone catching it ad hoc.
**Possible follow-ups:** How would you verify after the fact that a multicycle path exception is actually safe — what analysis or simulation would you require? What would you do if the engineer pushed back and insisted the exceptions were fine and the schedule couldn't absorb a re-close?
