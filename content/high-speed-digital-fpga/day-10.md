# high-speed-digital-fpga — Day 10

## Q1: How would you approach debugging an FPGA design where the configuration bitstream loads successfully, but the design behaves differently on some boards compared to others, even though all boards pass manufacturing test?

**Answer:** This is a classic "works on my bench" problem that points to something not captured by the manufacturing test. I'd start by systematically narrowing down what "behaves differently" means—is it a timing failure, an I/O level issue, or a functional logic difference? First, I'd verify that all boards are actually loading the same bitstream and that the configuration CRC check passes consistently. Then I'd check the power rails during operation, not just at static test—particularly transient droop on the core voltage under load, which can cause marginal timing failures on some boards but not others. I'd also examine the clock inputs: if the design uses an external oscillator or clock source, board-to-board variation in clock quality (jitter, rise time, or amplitude) could push some boards past timing margins. Next, I'd look at I/O standards and termination—if the design relies on internal termination or weak pull-ups, process variation in the FPGA silicon combined with slight differences in board trace impedance could cause marginal signal integrity. I'd use a logic analyzer or chipscope-type debugger to compare internal signal behavior between a "good" and "bad" board, focusing on the specific functional paths that differ. If the difference is intermittent, I'd run extended stress testing with temperature cycling and voltage margining to try to reproduce it deterministically. Finally, I'd review the manufacturing test coverage—if it only tests continuity and basic power, it won't catch marginal timing or signal integrity issues. The key is to treat this as a statistical variation problem, not a binary pass/fail issue, and to identify which parameter is marginal.

**Possible follow-ups:** How would you determine whether the issue is in the FPGA fabric versus the external interfaces? What specific measurements would you take on the "bad" boards to compare against the "good" ones?

## Q2: How would you approach designing a high-speed data path in an FPGA that must handle a continuous stream of data with variable burst sizes, where the input rate can momentarily exceed the output rate, but the average input rate is lower than the output capacity?

**Answer:** This is fundamentally a buffering and flow-control problem. The first step is to characterize the burst profile—maximum burst size, peak rate, and the recovery time between bursts—because that determines the minimum buffer depth needed to absorb the difference between peak input and sustained output. I'd design the data path with a FIFO at the rate transition point, sized to handle the worst-case burst without overflow while accounting for the output's ability to drain the FIFO during idle periods. The FIFO depth calculation must include the round-trip latency of any backpressure mechanism—if the output can stall, the FIFO must hold enough data to cover the time between the output asserting backpressure and the input actually stopping. I'd also consider using a watermark-based flow control rather than a full/empty flag, so the output can start draining before the FIFO is completely full, reducing the chance of overflow during a burst. For the FIFO implementation itself, I'd use block RAM with a proper asynchronous or synchronous clock domain crossing depending on whether the input and output clocks are related. If the clocks are unrelated, I'd use a gray-code pointer design or a vendor-provided FIFO primitive that handles CDC safely. I'd also think about whether the system can tolerate dropping data—in most medical or industrial applications it cannot, so the design should include an overflow flag that triggers an error condition rather than silently corrupting data. Finally, I'd simulate the design with realistic burst patterns, not just continuous traffic, to verify the FIFO depth and flow control work under worst-case conditions.

**Possible follow-ups:** How would you calculate the minimum FIFO depth for a specific burst profile? What happens if the output rate drops below the average input rate for an extended period—how would you handle that?

## Q3: How would you approach implementing a digital signal processing chain in an FPGA that must maintain bit-exact compatibility with an existing fixed-point C reference model, while also meeting timing at the target clock frequency?

**Answer:** Bit-exact compatibility between an FPGA implementation and a fixed-point C model is challenging but achievable with a disciplined approach. I'd start by establishing a verification methodology that compares the FPGA output against the C model on a cycle-by-cycle or sample-by-sample basis, using a testbench that feeds identical stimulus to both. The key is to define the exact fixed-point format at every internal node—word width, fractional bits, and rounding/truncation behavior—and document this in a specification that both the C model and RTL follow. I'd pay particular attention to operation ordering: in a filter or FFT, the order of additions and multiplications affects rounding, so the RTL must match the C model's operation order exactly. For multiplication, I'd specify whether the product is truncated or rounded, and whether rounding is round-to-nearest, round-half-up, or round-toward-zero. For additions, I'd specify whether intermediate results are widened or truncated at each stage. When it comes to timing closure, the main challenge is that bit-exactness often forces a specific computation order that may not be the most timing-friendly. I'd use pipelining to break long combinational paths, but I'd insert pipeline registers only at points where they don't change the arithmetic result—for example, after a multiplication or at a point where the value is already registered. If pipelining changes the latency, I'd compensate by adding matching delay in the C model or by adjusting the output alignment in the testbench. I'd also consider using DSP slices for multiply-accumulate operations, since they have built-in registers that can be used for pipelining without changing the arithmetic. The verification process would involve running a large corpus of test vectors—including edge cases like overflow, underflow, and saturation—through both the C model and the RTL, and comparing outputs bit-for-bit. If mismatches occur, I'd use a binary search approach to isolate the first mismatching sample and trace it back to the specific operation that differs.

**Possible follow-ups:** How would you handle a situation where the C model uses floating-point arithmetic but the FPGA must use fixed-point—what conversion process would you use? How would you verify that saturation and overflow behavior matches between the C model and RTL?

## Q4: How would you approach designing a finite state machine (FSM) in an FPGA that must be robust against single-event upsets (SEUs) for a radiation-tolerant application, where the FSM controls a critical safety function?

**Answer:** For a radiation-tolerant FSM controlling a safety-critical function, the design must detect and recover from SEUs that could corrupt the state. The first decision is whether the FSM needs to be triple-modular redundant (TMR) or whether a simpler detection-and-recovery approach is sufficient. TMR with voting is the most robust approach—three copies of the FSM run in parallel, and a voter selects the majority output. However, TMR has significant overhead in area and power, and it requires careful design to ensure the three copies don't have correlated failures. If TMR is too costly, I'd consider a single FSM with state-encoding techniques that make corruption detectable. One approach is to use a Hamming-distance-based state encoding where any single-bit upset produces an invalid state that can be detected—for example, using a one-hot encoding with a check that exactly one bit is set, or using a state code with an embedded parity or CRC. When an invalid state is detected, the FSM transitions to a safe state or a recovery sequence. I'd also consider using a "shadow register" approach where the state is duplicated and compared—if the copies disagree, the FSM enters a safe state. For the state registers themselves, I'd use TMR flip-flops or at least ensure the synthesis tool doesn't optimize away any redundancy. I'd also add a watchdog mechanism: if the FSM doesn't reach an expected state within a timeout period, it resets to a known-good state. The recovery behavior depends on the application—for a safety function, the FSM should transition to a safe state (e.g., shut down or hold the last valid output) rather than attempting to resume normal operation. I'd also consider whether the FSM needs to be "self-healing"—able to recover and resume normal operation after an SEU—or whether a safe shutdown is acceptable. Finally, I'd verify the design through fault injection testing, where I simulate bit flips in the state registers and confirm the FSM responds correctly.

**Possible follow-ups:** How would you decide between TMR and a single FSM with error detection? What are the failure modes of TMR that you'd need to consider? How would you handle SEUs in the voter circuit itself?

## Q5: Behavioral question — You're the lead engineer on a high-speed FPGA design project. During a design review, a junior engineer presents a simulation showing that their design meets timing at the target clock frequency, but you notice they've set an incorrect constraint on a critical clock path—they've applied a false path constraint to a path that actually needs to meet timing. The engineer argues that the design works in simulation and that the constraint is correct because "the path doesn't matter for the current functionality." How do you handle this situation?

**Answer:** This is a situation where I need to address both the technical issue and the engineer's understanding of timing constraints. First, I'd acknowledge that the simulation passing is a good sign, but I'd explain that timing constraints are not just about making the current simulation pass—they define the contract between the design and the physical reality of the FPGA. A false path constraint tells the tools to ignore timing on that path, which means the tools won't optimize it, and if the path actually matters, the design could fail in hardware under real operating conditions. I'd ask the engineer to walk me through the path in question and explain why they believe it's a false path—this helps me understand their reasoning and gives them a chance to demonstrate their thinking. If their reasoning is based on a misunderstanding of the design's functionality, I'd explain the actual data flow and why the path does need to meet timing. I'd also point out that simulation at the RTL level doesn't catch all timing issues—gate-level simulation with back-annotated delays would be needed, and even that doesn't fully replicate the timing behavior of the actual silicon. I'd suggest we work together to correct the constraint and re-run timing analysis to see if the design still meets timing. If it doesn't, we'd need to discuss what changes are required—either in the logic, the placement, or the clocking scheme. I'd frame this as a learning opportunity: timing constraints are a critical part of the design, and getting them wrong can lead to failures that are very difficult to debug in the field. I'd also suggest we add a review checklist item for timing constraints so this type of issue is caught earlier in the design flow. The goal is not to embarrass the engineer but to ensure the design is correct and to help them develop better judgment about timing analysis.

**Possible follow-ups:** How would you verify that the corrected constraint is now accurate? What would you do if the design no longer meets timing after removing the false path constraint? How would you help the junior engineer develop better understanding of timing constraints without micromanaging their work?
