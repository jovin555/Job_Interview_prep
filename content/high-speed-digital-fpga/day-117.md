# high-speed-digital-fpga — Day 117

## Q1: How would you approach designing the clock domain crossing for a multi-bit data bus where the source and destination clocks are asynchronous, the data changes frequently, and you need to minimize latency while ensuring data integrity?
**Answer:** The key decision is which CDC structure fits the data's semantics, because "frequent changes" rules out a simple multi-bit two-flop synchronizer — that only works for a single bit, or for a bus that is guaranteed stable across the capture window (which a frequently-changing bus is not). For a wide, continuously changing bus I would reach for an asynchronous FIFO built from dual-port block RAM: the write pointer and read pointer are each Gray-coded and synchronized into the opposite domain with two-flop synchronizers, so only one bit changes per increment and the synchronized pointer is always a valid (if slightly stale) value. The full/empty flags are generated from the pointer comparison, and the BRAM handles the wide data path natively, so latency is just the FIFO occupancy plus a couple of pointer-sync stages. If the bus were infrequent and I needed a coherent snapshot rather than streaming, I'd instead use a handshake (data held stable, toggle-flag synchronized across, acknowledge back) or a multi-cycle-path constraint with a "data stable" qualifier. The trade-off is latency vs. resource cost: the FIFO gives the lowest latency for streaming data but costs BRAM and pointer logic; the handshake is cheaper but adds round-trip latency per transfer. I would also make sure the synchronizers are properly constrained (set_false_path or set_max_delay on the CDC paths) and run a CDC lint/structural check so no unsynchronized crossing slips through.
**Possible follow-ups:** How would you size the FIFO depth, and what would drive that decision? What would change if the two clocks had a known, fixed frequency ratio instead of being fully asynchronous?

## Q2: How would you approach debugging an FPGA design where the timing analysis reports all constraints are met, but the design fails in hardware only at the maximum specified junction temperature?
**Answer:** A clean timing report at the nominal corner but failure at max junction temperature points at either an incomplete constraint set or a margin problem that only the slow/hot corner exposes. First I'd confirm the report was actually run at the worst-case corner — slow process, high temperature, low voltage — because a nominal-corner report can hide paths that only fail when delays stretch. Then I'd look for constraints that don't reflect reality: missing clock definitions, false paths or multicycle paths that were added to force closure, generated clocks not derived correctly, or I/O timing that wasn't constrained at all. A common culprit is a path that was never constrained (so the tool didn't analyze it) rather than one that genuinely passes. I'd also check for asynchronous crossings that were "working" at room temperature because the metastability window was narrow and only bite when delays shift. On the hardware side, I'd use the on-chip debug facilities — internal logic analyzer, temperature readback, and if available a ring-oscillator or delay-line monitor — to see whether the failure correlates with a specific block. I'd also re-run with derated timing or add margin to see if the design is simply marginal. The fix is usually to correct the constraint, add pipeline stages to the failing path, or tighten the CDC handling, then re-verify across the full PVT envelope rather than just nominal.
**Possible follow-ups:** How would you distinguish a genuine timing-margin problem from a power-integrity problem that also worsens with temperature? What role does the on-chip temperature sensor play in your debug flow?

## Q3: How would you approach designing the decoupling and bulk capacitance network for an FPGA's transceiver power rails, where the rails see both high-frequency switching noise from the SerDes and slower, larger current transients from the fabric, and you need to verify the network is adequate before committing to the layout?
**Answer:** The transceiver rails have two very different noise sources, so I'd design the network in layers matched to frequency. For the high-frequency SerDes switching content, the decoupling has to be close to the pins — small-value, low-ESL capacitors (and where the package provides them, the on-package/on-die capacitance) placed with minimal loop inductance, because at hundreds of MHz to GHz the trace inductance dominates and a cap a few millimeters away is nearly useless. For the slower, larger fabric transients, bulk capacitance with low ESR handles the charge delivery and keeps the rail from drooping during a current step. I'd build a target impedance profile: Z_target = allowed ripple / transient current, and check that the parallel combination of bulk, mid-frequency, and high-frequency caps stays below that target across the band of interest. Before layout I'd verify with a PDN simulation — a simple impedance-vs-frequency plot of the network including plane capacitance and via inductance — and confirm there are no anti-resonance peaks where the impedance spikes above target. I'd also check the transceiver's ripple spec specifically, since it's usually tighter than the fabric rail. The layout rules that follow: minimize via count and loop area on the high-frequency caps, keep the return path continuous under the rail, and place bulk caps where the current actually flows.
**Possible follow-ups:** How would you handle an anti-resonance peak between two capacitor values in the impedance plot? What measurements would you take on the first prototype to confirm the PDN behaves as simulated?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?
**Answer:** The core risk is that timing analysis only checks what's constrained — an unconstrained path is silently ignored, so "all constraints met" can be meaningless if the constraint set is incomplete. My sign-off flow starts with constraint coverage: every clock must be defined (including generated clocks from PLLs/MMCMs, with correct source and divide/multiply relationships), every I/O must have input/output delay constraints derived from the external device's datasheet, and every CDC must be either properly synchronized or explicitly excepted with justification. I'd run the tool's unconstrained-path and clock-domain-crossing reports and drive them to zero unexplained entries. I'd also review every false path and multicycle path individually — these are the most common way a design "closes" while hiding a real violation — and require a written rationale for each. Beyond static checks, I'd cross-verify with gate-level simulation using back-annotated timing (SDF) at the worst-case corner, and run the timing report at multiple PVT corners rather than just one. A CDC structural lint tool catches synchronizer mistakes that timing analysis won't. Finally, I'd treat the constraint file as a reviewed artifact, not a build byproduct, so changes to it get the same scrutiny as RTL.
**Possible follow-ups:** How would you decide whether a given path legitimately deserves a multicycle exception versus needing a real fix? What's the danger of relying on gate-level simulation alone as your timing sign-off?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?
**Answer:** I'd treat this as a coaching moment rather than a confrontation, because the engineer's instinct — that some paths genuinely don't need single-cycle timing — is correct in principle; the question is whether each exception is justified and documented. In the review I'd ask them to walk me through each exception one at a time: what is the path, why does it not need single-cycle timing, and what is the evidence? A legitimate multicycle path has a clear functional reason (data is captured on a later cycle by design, with the logic and the capture register both aware of it) and a matching multicycle constraint on both setup and hold. A legitimate false path is one that is structurally never sensitizable or is a true asynchronous crossing that's properly synchronized elsewhere. If the engineer can articulate that for each path, great — I'd ask them to add a comment and a reference so the next reviewer can follow the reasoning. If they can't, that's the gap: the exception is masking a real violation, and we fix the design or the constraint. I'd frame it as "the exception is a claim about the design, and we need to be able to defend every claim," which keeps it about rigor rather than about the engineer being wrong. I'd also make documented exception review a standing part of the sign-off checklist so it isn't personal to this one review.
**Possible follow-ups:** How would you handle it if the engineer pushed back and insisted the exceptions were fine? What process change would you make so timing exceptions get reviewed consistently across the team?
