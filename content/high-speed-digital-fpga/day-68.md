# high-speed-digital-fpga — Day 68

## Q1: How would you approach designing the configuration memory interface for an FPGA that loads its bitstream from a parallel NOR flash, where the flash's access latency is significant relative to the FPGA's configuration clock, and the board may be power-cycled rapidly?
**Answer:** The core issue is that configuration is a synchronous handshake between two devices with very different timing characteristics, and a rapid power cycle can leave the flash in an indeterminate state while the FPGA is already trying to read from it. I'd start by characterizing the flash's worst-case access time across its full temperature and voltage range, then confirm the FPGA's configuration clock can be set slow enough that the read setup and hold windows are met with margin — configuration doesn't need to be fast, it needs to be reliable. I'd also look at the flash's own power-on requirements: many flash devices need a minimum time after VCC stabilizes before they'll respond correctly, so the FPGA's configuration start must be gated on a power-good signal from the flash rail, not just the FPGA's own POR. For rapid power cycling, the concern is that the flash may still be in the middle of an internal operation when power drops, and on the next power-up it may need a recovery period or may come up in an unexpected state. I'd add a supervisor or reset controller that holds the FPGA in reset until both rails are stable and a minimum delay has elapsed, and I'd verify the flash's datasheet for any "power-down during operation" caveats. On the FPGA side, I'd make sure the configuration mode pins are strapped correctly and that the init/busy handshake is respected rather than assumed. Finally, I'd test the design across the full power-cycle envelope — cold start, warm restart, and rapid cycling — because this is exactly the kind of thing that passes on the bench and fails in the field.
**Possible follow-ups:** How would you decide whether to add a dedicated configuration supervisor IC versus implementing the sequencing in the FPGA's power management logic? What would you check first if the board configures reliably on a bench supply but fails on a noisy production rail?

## Q2: How would you approach debugging an FPGA design where the device configures successfully and runs correctly for a period of time, but then the configuration appears to be lost — the device stops responding and requires a reconfiguration to recover?
**Answer:** The first thing I'd do is separate "the configuration was actually lost" from "the device stopped responding for some other reason." Those look identical from the outside but have very different root causes. I'd check whether the DONE pin actually de-asserts, or whether the device is still configured but the logic has locked up — that single observation splits the problem in half. If DONE is still high, the issue is in the design, not the configuration memory: a state machine stuck in an illegal state, a clock that stopped, a PLL that lost lock, or a watchdog that fired and didn't recover. If DONE actually drops, then something is disturbing the configuration memory or the device's power. On the configuration-loss side, I'd look at power integrity first — a transient droop on the core rail below the device's minimum can cause a reconfiguration or a partial loss of configuration. I'd also check for single-event upsets if the environment has radiation, and for any external signal that could be pulling the program pin or init pin. Thermal is another angle: a device that runs fine cold and loses configuration when warm points at a marginal timing or power margin that only closes at temperature. I'd instrument the board to capture the state of DONE, INIT, and the power rails at the moment of failure, ideally with a scope triggered on the event, because the failure is intermittent and you need to catch it in the act rather than reason about it after the fact. Once I know which half of the problem it is, the debug path narrows considerably.
**Possible follow-ups:** If DONE stays high but the logic is locked up, how would you determine whether it's a clock issue versus a state machine issue? What role would a watchdog play in your recovery strategy, and what are the risks of relying on one?

## Q3: How would you approach designing the decoupling and bulk capacitance network for an FPGA's transceiver power rails, where the rails see both high-frequency switching noise from the SerDes and slower, larger current transients from the fabric, and you need to verify the network before committing to layout?
**Answer:** The transceiver rails are a good example of a PDN that has to work across a very wide frequency range, because the noise sources span from the SerDes switching at the line rate down to much slower fabric current transients. I'd start by defining the target impedance across frequency — the transceiver supply has a tight ripple spec, so the impedance target is set by that spec divided by the worst-case transient current, and it has to be met from DC up to the frequencies where the on-die capacitance takes over. Then I'd build the network in layers: bulk electrolytic or polymer capacitors for the low-frequency, high-energy transients; a bank of mid-frequency ceramics for the range where the bulk caps' ESL makes them ineffective; and small, low-ESL ceramics placed as close to the pins as physically possible for the high-frequency content. The key insight is that capacitor placement and via inductance matter more than raw capacitance value at high frequency — a 100 nF cap with a long via loop can be worse than a 10 nF cap placed right at the pin. I'd model the network in a PDN simulation tool, including the plane spreading inductance and the via inductance, and sweep the impedance to confirm it stays below target across the band. I'd also check for anti-resonances between capacitor banks, because paralleling different values can create a peak in the impedance at the crossover frequency. Before committing to layout, I'd verify the model against the capacitor vendors' measured impedance curves rather than nominal values, and I'd plan a test point or two on the rail so the network can be measured on the first article. If the simulation shows a marginal band, I'd add a small series ferrite or a damping resistor rather than just piling on more capacitance.
**Possible follow-ups:** How would you measure the actual PDN impedance on a assembled board, and what would you do if the measurement showed a resonance you didn't predict? When would you consider an on-package or on-die capacitance solution versus adding more board-level capacitance?

## Q4: How would you approach designing the return-current path for a high-speed digital board where a signal transitions between two reference planes (e.g., from a ground plane to a power plane) on its way through a via?
**Answer:** The fundamental principle is that every signal current has a return current, and at high frequency the return current follows the path of least impedance — which means it flows on the reference plane directly beneath the trace, not through the ground grid. When a signal transitions from referencing one plane to referencing another, the return current has to jump between those planes, and if there's no low-inductance path for it to do so, it will find one anyway — through the plane capacitance, through the power distribution network, or by radiating. That's where EMI and signal integrity problems come from. The standard fix is to place a stitching capacitor or a via between the two reference planes close to the signal via, so the return current has a short, low-inductance path to follow. The capacitor needs to be placed within a fraction of a wavelength of the via — at multi-gigabit rates that's a very small distance, so "close" means right next to it, not somewhere on the board. I'd also consider whether the plane transition is necessary at all: if the signal can stay referenced to the same plane for its entire route, that's the cleanest solution. If a transition is unavoidable, I'd make sure the two planes are adjacent in the stack-up so the stitching via is short, and I'd avoid transitions where the reference plane changes from ground to a power plane that isn't well-decoupled to ground at the frequencies of interest. In layout review, I'd specifically look for signal vias that cross a plane split or change reference planes, and I'd flag any that don't have an adjacent stitching via or capacitor. This is one of those things that's invisible in a schematic and only shows up as a marginal eye diagram or an EMC failure, so it has to be caught in layout review.
**Possible follow-ups:** How would you decide between a stitching capacitor and a stitching via for a given plane transition? What would you look for in a post-layout simulation to confirm the return path is adequate?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?
**Answer:** This is a situation where the technical issue and the interpersonal issue need to be handled together, because the engineer's reasoning is a common and understandable mistake, and how I respond will affect whether they learn from it or just feel corrected. I'd start by acknowledging that their observation — the signal is stable for a long time relative to the clock — is often true, and that's exactly why this bug is so insidious: it works in simulation and often works on the bench, so it passes review and testing and then fails in the field at temperature or after a component change. Then I'd walk through the actual failure mechanism: the destination flop's setup and hold window is a tiny fraction of the clock period, and if the source signal transitions during that window, the flop can go metastable — its output can be an intermediate voltage, and it can resolve to either value, and the resolution time is unbounded. A single flop doesn't eliminate the problem, it just makes it less likely; a two-flop synchronizer gives the metastable output a full clock cycle to resolve before it's used, which reduces the probability of failure to an acceptable level. I'd frame it not as "you're wrong" but as "here's the standard pattern and why it exists." If the signal is a single bit, a two-flop synchronizer is the fix. If it's a multi-bit bus, the fix is different — a handshake, a FIFO, or a gray-coded counter — and I'd make sure the engineer understands that the right solution depends on what the signal represents. I'd also use it as a teaching moment for the whole team, because if one engineer made this mistake, others may have too, and a short review of CDC patterns in the next team meeting is worth more than a one-on-one correction. Finally, I'd add a CDC check to the design review checklist and, if the tooling supports it, a lint rule or a formal CDC verification step, so the next instance gets caught automatically rather than depending on someone noticing it in review.
**Possible follow-ups:** How would you handle it if the engineer pushed back and pointed out that the design has been running in the lab for weeks without a failure? What would you do if you discovered this same pattern in several other places in the design after the review?
