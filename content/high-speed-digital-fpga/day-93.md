# high-speed-digital-fpga — Day 93

## Q1: How would you approach designing the clock domain crossing for a multi-bit control word that is written by a slow serial interface (e.g., 10 MHz SPI) and consumed by a fast logic domain (e.g., 250 MHz), where the word changes infrequently but must never be observed in a partially updated state?

**Answer:** The key insight is that "infrequent" does not mean "safe" — a multi-bit word crossing domains still needs a proper handshake, because individual bits can be captured on different destination clock edges and produce a coherent-looking but wrong value. The cleanest approach is a bundled-data handshake: the source domain holds the data stable, then asserts a single-bit request signal that is synchronized into the destination domain through a two-flop synchronizer. The destination domain, on seeing the request, captures the entire multi-bit word in one clock edge and returns an acknowledge, which is itself synchronized back to the source. The source must not change the data until it sees the acknowledge. This guarantees the destination always samples a fully settled word, and it costs only a few cycles of latency — irrelevant for a control register that changes rarely. Alternatives worth mentioning: a dual-clock FIFO if the word is part of a stream, or a Gray-coded encoding if the value is a counter rather than an arbitrary word. What I would avoid is a per-bit two-flop synchronizer on a multi-bit bus — that is the classic mistake, because it gives no guarantee that all bits arrive on the same cycle. I would also add a formal or CDC-lint check to prove the crossing is recognized by the tool, and constrain the paths appropriately so the static timing tool does not try to time an inherently asynchronous path.

**Possible follow-ups:** How would you handle the case where the destination domain might be held in reset while the source is still writing? What would change if the control word were updated every few microseconds rather than rarely?

## Q2: How would you approach debugging an FPGA design where the DDR3 interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** A failure that appears only after warm-up strongly suggests a timing margin problem that is being consumed by temperature-dependent effects — either on the memory side (refresh behavior, output driver strength, ODT resistance drifting with temperature) or on the FPGA/board side (clock tree delay, trace impedance, power rail droop as leakage rises). My first step is to characterize rather than guess: reproduce the failure with a controlled thermal ramp and log exactly which temperature it starts at, whether it is read or write errors, and whether the error rate is a trickle or a cliff. A cliff suggests a hard timing violation; a trickle suggests marginal margin. Then I would instrument the design — use the memory controller's built-in error reporting and, if available, its per-bit deskew and read-capture calibration status, and check whether the calibration that was valid at power-up is still valid when hot. On the board side I would scope the rails and the memory clock at temperature, looking for droop or jitter growth. A common root cause is that write leveling or read leveling was calibrated once at cold and the delay taps no longer center the window when the delay chains shift with temperature, so the fix is often to re-run calibration periodically or to widen the timing margin by adjusting the tap settings to the center of the window rather than the edge. I would also verify the refresh rate is adequate at the elevated temperature, since DRAM retention time degrades when hot.

**Possible follow-ups:** How would you distinguish a DRAM-internal timing problem from an FPGA-side capture problem? What board-level changes would you consider if the margin cannot be recovered in the FPGA?

## Q3: How would you approach designing the termination and coupling scheme for a multi-gigabit serial link that must traverse a backplane connector, and how would you decide between AC and DC coupling?

**Answer:** I would start from the link budget and the protocol requirements rather than from a default. AC coupling is the usual choice for multi-gigabit serial links because it removes the DC common-mode difference between the two boards, which is essential when the transmitter and receiver sit on separate supplies or separate ground references — the backplane connector will not preserve a common DC level reliably. The series capacitors are placed close to the transmitter, sized so their impedance is negligible at the signal's frequency content (large enough that the low-frequency droop from baseline wander is acceptable for the chosen line code), and chosen with a dielectric and package that do not degrade the channel. DC coupling is only appropriate when both ends share a well-defined common mode and the protocol requires DC content — for example, some low-speed or control-oriented links. For termination, the decision is driven by where the termination lives: many high-speed transceivers have on-die termination, in which case the board provides the AC coupling caps and the connector, and the receiver's internal termination handles the reflection control. If on-die termination is not available or not sufficient, I would place termination at the receiver as close to the pin as possible, matched to the differential impedance of the pair. I would also confirm the connector's impedance and pin assignment, keep intra-pair skew tight, and check that the connector's ground pins provide a continuous return path for each differential pair. Finally, I would validate the whole channel with an eye-diagram simulation or measurement at the worst-case data rate before committing to the layout.

**Possible follow-ups:** How would you decide the AC coupling capacitor value, and what failure mode appears if it is too small? What would you check in the connector pinout to preserve return-path continuity?

## Q4: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?

**Answer:** A via that passes through a thick backplane but is only used on the top and bottom layers leaves an unused portion — the stub — that acts as an open-circuited transmission line and creates a resonance that shows up as a notch in the channel's insertion loss and as reflections in the time domain. The first-line mitigation is back-drilling: mechanically removing the unused barrel below the last used layer so the stub is reduced to a short, controlled length. That is the standard fix for thick backplanes and is usually specified in the fabrication notes with a maximum remaining stub length. Where back-drilling is not possible or not economical, I would consider blind or buried vias so the via only spans the layers it needs, or a via-in-pad with filled and capped construction. On the design side, I would keep the via as close to the connector or the transition point as possible, minimize the antipad size to control impedance, and add ground vias around the signal via to provide a return path. I would quantify the effect before and after with a 3D electromagnetic extraction of the via structure and fold it into the channel simulation, because whether a given stub length matters depends entirely on the data rate and the rest of the channel's margin. The decision should be driven by the simulated eye at the worst-case rate, not by a rule of thumb about stub length.

**Possible follow-ups:** How would you decide the maximum allowable stub length for a given data rate? What is the trade-off between back-drilling cost and channel margin, and how would you present that to a program team?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?

**Answer:** I would treat this as a teaching moment rather than a confrontation, because the engineer may well be right about some of the exceptions — but the burden of proof is on the exception, not on the timing report. My approach is to walk through each exception one at a time and ask a simple question: what is the actual timing requirement on this path, and where is that requirement documented? A false path is only legitimate if the path is genuinely asynchronous or logically unreachable, and that claim needs to be justified — ideally by the CDC analysis tool recognizing the crossing, or by a clear statement of why the path can never be sensitized. A multicycle path is only legitimate if the downstream logic genuinely has that many cycles to settle, which means the capture logic must be designed to tolerate the delay. I would ask the engineer to show me, for each exception, the reasoning and the evidence, and I would want the exceptions reviewed by a second pair of eyes and recorded in the design's constraint documentation so they are not silently inherited by the next engineer. If any exception turns out to be masking a real requirement, we remove it and fix the design — even if that means adding a pipeline stage or restructuring the logic. The tone I want to set is that timing exceptions are a design decision with consequences, not a knob to turn until the tool goes green.

**Possible follow-ups:** How would you verify after the fact that a false-path exception is actually safe? What process would you put in place so timing exceptions are reviewed and documented consistently across the team?
