# high-speed-digital-fpga — Day 108

## Q1: How would you approach designing the power-up and configuration sequence for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?

**Answer:** I'd treat this as a state-machine problem with explicit dependencies rather than a set of independent "wait for power good" timers. The first step is to extract the sequencing requirements from the device datasheet and the transceiver/PLL user guides: which rails must be stable before configuration starts, which rails the transceiver quads need, and what the minimum reset pulse widths and release orderings are. I'd then build a supervisor — either a small CPLD/power-management IC or a state machine in a always-on domain — that holds everything in reset until each prerequisite is satisfied, and only then releases the next stage.

The key discipline is that the FPGA's own configuration engine must not begin until its core and I/O rails are within tolerance and stable, and the PLLs and transceiver quads must not be released until their reference clocks are present and their supply rails are good. I'd sequence: rails up in the required order → reference clocks stable → release FPGA configuration → wait for the configuration-done handshake → release PLLs → release transceiver quads → release the rest of the system. Each transition should be gated on a real status signal (power-good comparators, clock-present detectors, the device's init-done output), not just a fixed delay, because delays that work at room temperature can be marginal at temperature extremes or on a fast power cycle.

I'd also design for the re-power-cycle case: if the board can be cycled rapidly, the supervisor must ensure all rails have discharged below their reset thresholds before re-sequencing, otherwise the FPGA can come up in an indeterminate state. And I'd make the whole sequence observable — status bits or a debug header — so that a board that comes up "configured but dead" can be diagnosed as a sequencing problem rather than a configuration problem.

**Possible follow-ups:**
- How would you verify the sequencing across the full temperature and ramp-rate range without instrumenting every board?
- What would you do if the FPGA's init-done signal asserts but the transceiver quad still reports not-ready?

## Q2: How would you approach debugging an FPGA design where the DDR3 interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** The "passes cold, fails warm" signature points strongly at a timing or analog margin issue that calibration happened to absorb at one temperature but not another. I'd start by separating the problem into three buckets: the memory device, the FPGA's memory controller/PHY, and the board-level channel between them.

First, I'd characterize the failure more precisely — is it a specific data pattern, a specific address region, a specific byte lane, or random? That narrows whether it's a timing margin problem on one lane or something more systemic. I'd then re-run the built-in calibration and memory test at the failing temperature and compare the calibration results (read/write leveling delays, per-bit deskew values) against the cold results. If the calibration codes have drifted toward the edge of their window when warm, that's a strong indicator that the initial calibration was marginal and temperature pushed it over.

On the board side, I'd look at the things that shift with temperature: the reference voltage and termination, the memory device's own timing (tRCD, tWR, etc. typically worsen when hot), and the power integrity of the memory rails — a rail that sags slightly when warm can degrade the input timing margin. I'd also check whether the failure correlates with sustained traffic (self-heating of the FPGA and memory) versus ambient temperature alone, which distinguishes a thermal-margin problem from a workload-dependent one.

The fix usually involves either re-running calibration periodically or on temperature change, tightening the timing margins in the controller configuration (adding margin rather than running at the edge of the calibration window), or improving the board-level signal integrity and power delivery so the margins don't collapse when warm. I'd verify the fix by running the memory test across the full specified temperature range, not just at the two endpoints.

**Possible follow-ups:**
- How would you decide whether to add periodic recalibration versus simply increasing the timing margins?
- What board-level measurements would you take to confirm the memory rail is not the culprit?

## Q3: How would you approach designing the interface between an FPGA and an external ADC that uses a source-synchronous, double-data-rate output bus, where the data and a forwarded clock arrive at the FPGA with an unknown but bounded skew?

**Answer:** The core challenge is that the forwarded clock and the data have a bounded but non-zero skew, and that skew varies with process, voltage, and temperature, so I can't just assume the clock edge lands in the middle of the data eye. I'd approach it in layers.

First, the physical layer: I'd constrain the PCB layout so the data and clock traces are matched in length within the skew budget the ADC specifies, and I'd treat the bus as a source-synchronous interface with the clock routed as a proper transmission line, terminated appropriately, and referenced to a continuous return plane. The layout matching is what keeps the skew bounded in the first place.

Second, the FPGA capture architecture: I'd use the device's input delay elements or IDELAY primitives on the data and/or clock paths to shift the sampling point into the center of the data eye, and I'd use the device's built-in per-bit deskew or a training pattern from the ADC (if it provides one) to calibrate that delay at startup. For a DDR bus, I'd capture on both edges and use the FPGA's ISERDES or DDR input registers so the timing is handled in hardware rather than in fabric logic.

Third, the timing constraints: I'd write the input timing constraints to reflect the ADC's actual output timing (clock-to-data skew, setup/hold windows) and the board skew, and I'd analyze the interface across all PVT corners rather than just nominal. The goal is to prove that the sampling point stays inside the data valid window at every corner, not just that it works on the bench.

Finally, I'd verify with a PRBS or known pattern from the ADC at the full data rate, and I'd check the eye at the FPGA pins with a scope if the margin is tight. If the skew budget is too large for a fixed delay, I'd consider a training-based approach where the FPGA sweeps the delay and picks the center of the passing window.

**Possible follow-ups:**
- How would you handle the case where the ADC provides no training pattern and the data is arbitrary?
- What would you do if the skew budget exceeds what the FPGA's input delay range can cover?

## Q4: How would you approach designing the decoupling and bulk capacitance network for an FPGA's transceiver power rails, where the rails see both high-frequency switching noise from the SerDes and slower, larger current transients from the fabric, and you need to verify the network is adequate before committing to the layout?

**Answer:** I'd treat this as a PDN impedance problem across the full frequency range the rail must support, not as a "sprinkle capacitors" exercise. The transceiver rails have two distinct noise mechanisms: the SerDes switching produces high-frequency content (hundreds of MHz into the GHz range) that the on-die and package capacitance must handle, and the fabric and transceiver block turn-on/turn-off produce slower, larger current steps that the bulk capacitance and the regulator must absorb.

I'd start by defining the target impedance: from the rail's ripple specification and the worst-case transient current, compute the impedance the network must present across the frequency band of interest. Then I'd build the network in layers — the on-die and package capacitance handles the highest frequencies, the PCB's small high-frequency capacitors (placed as close to the pins as possible, with minimal loop inductance) handle the mid-band, and the bulk capacitors plus the regulator handle the low-frequency, large-transient content. The key is that each layer covers a band and the layers overlap so there's no frequency where the impedance peaks above target.

Before committing to layout, I'd verify with a PDN simulation: model the regulator, the bulk and high-frequency capacitors with their ESR/ESL, the plane pair, and the via/package parasitics, and plot the impedance versus frequency against the target. I'd also check the anti-resonance peaks between capacitor values — mixing values without checking can create a peak that's worse than a single value. If the simulation shows a peak above target, I'd adjust values, add a capacitor, or change the plane spacing before the board is built.

After layout, I'd verify on the bench with a scope and a current probe or a network analyzer on the rail, looking at the transient response and the ripple under realistic SerDes traffic, and compare against the simulation.

**Possible follow-ups:**
- How would you handle an anti-resonance peak that appears between two capacitor values in the simulation?
- What would you measure on the bench to confirm the network meets the transceiver's ripple spec under real traffic?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?

**Answer:** I'd treat this as a review-discipline issue rather than an accusation, because the engineer may genuinely believe the exceptions are correct — and some of them may be. The problem is that timing exceptions are exactly where designs silently break, so every exception needs to be justified individually and documented, not accepted as a batch because the report is green.

My approach would be to walk through each exception with the engineer and ask three questions: what is the actual timing requirement on this path, what is the evidence that the requirement is what they claim, and what happens if the path is faster or slower than assumed? A false path is only legitimate if the path truly can never be sensitized or its result is truly don't-care; a multicycle path is only legitimate if the downstream logic genuinely has that many cycles to settle and the constraint matches the RTL's actual behavior. If the engineer can't articulate the requirement and point to the RTL or the interface spec that establishes it, the exception is suspect.

I'd also check whether the exceptions were added to fix a real timing failure or to paper over one — if a path failed and the response was to declare it a false path, that's a red flag regardless of the argument. And I'd want the exceptions reviewed by someone other than the person who wrote them, because the person who added them has an incentive to believe they're correct.

The outcome I'd aim for is a documented exception list with a justification per entry, reviewed and signed off, and a re-run of timing analysis with the exceptions in place to confirm the design still closes on the paths that genuinely matter. If any exception can't be justified, it comes out and the design gets fixed properly. I'd frame the whole thing as protecting the engineer and the project — an unjustified exception that ships is a field failure waiting to happen, and the review is where we catch it cheaply.

**Possible follow-ups:**
- How would you handle it if the engineer's exceptions turn out to be correct but undocumented?
- What process would you put in place to prevent unjustified exceptions from accumulating on future reviews?
