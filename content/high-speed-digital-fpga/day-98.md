# high-speed-digital-fpga — Day 98

## Q1: How would you approach designing the I/O planning for an FPGA that must interface with a DDR3 memory controller, a high-speed differential ADC, and a bank of slow GPIO, given that I/O bank voltage and standard choices are constrained by each bank's VCCO?
**Answer:** I'd start by treating I/O planning as a constraint-satisfaction problem driven by the physical bank architecture, not by schematic convenience. The first step is to enumerate every interface and its electrical requirements: DDR3 needs SSTL-class signaling referenced to a specific VCCO (typically 1.5V for DDR3), the differential ADC interface needs a high-speed differential standard (LVDS or a dedicated SerDes standard) with its own VCCO and possibly a dedicated reference clock pin, and the slow GPIO needs whatever logic-level standard the external devices use (often 3.3V CMOS). The key insight is that VCCO is per-bank, so signals that require different VCCO values cannot share a bank. I'd group interfaces by required VCCO first, then within each group check that the bank supports the needed I/O standards and that the pin count fits. For the DDR3 interface, I'd also respect the dedicated byte-lane structure — data pins, DQS strobes, and DM must map to the correct byte groups, and address/command/control pins have their own placement rules relative to the memory controller hard block. For the differential ADC, I'd prefer a bank that supports the required differential standard and, if the interface is source-synchronous, ensure the clock-capable pins are used for the forwarded clock. Slow GPIO is the most flexible and should be placed last, in whatever banks remain, since it has the loosest timing and standard requirements. I'd also account for reference voltage pins (VREF) where single-ended standards need them, and avoid mixing noisy high-speed interfaces with sensitive analog-adjacent signals in the same bank where possible. Finally, I'd verify the plan against the device's pinout document and the board's physical layout early — a bank assignment that's electrically valid but forces a terrible escape route on the PCB is still a bad plan, so I'd iterate with the layout engineer before freezing the pinout.
**Possible follow-ups:** What would you do if the DDR3 controller's byte-lane requirements conflicted with the bank VCCO needed by an adjacent high-speed interface? How would you handle a late requirement change that needs a new 3.3V signal when all 3.3V-capable banks are full?

## Q2: How would you approach debugging an FPGA design where the device configures successfully and runs correctly for a period of time, but then the configuration appears to be lost — the device stops responding and requires a reconfiguration to recover?
**Answer:** I'd treat this as a "configuration integrity" investigation and separate the possible causes into a few categories before touching anything. First, is the device actually losing its configuration, or is it still configured but hung? Those look similar from the outside but have very different root causes. I'd check the configuration status pins and any error flags the device exposes — many FPGAs have a CRC error or configuration error output that latches if the configuration memory is corrupted, and reading that tells me whether the bitstream itself was disturbed. If there's a CRC error flag, the likely causes are single-event upsets (if the environment has radiation), power supply glitches on the configuration-related rails, or a marginal configuration flash read. If there's no error flag but the device is unresponsive, I'd suspect the design itself — a state machine that walked into an illegal state, a PLL that lost lock, or a watchdog-type condition — rather than configuration loss. On the power side, I'd scope the core and auxiliary rails during the failure window, looking for droops or transient dips that could cause an internal reset or brownout; a slow, thermal-related drift in a regulator could produce exactly this "works for a while, then dies" signature. I'd also check whether the failure correlates with temperature (thermal soak test), with a particular activity pattern (heavy traffic on an interface), or with time alone (suggesting a leakage or drift mechanism). If the design has a soft error mitigation or scrubbing feature available, I'd check whether it's enabled and whether it's reporting corrections. And I'd add a heartbeat or status register that the host can poll so I can distinguish "configured but hung" from "reconfiguring" in the field. The fix depends entirely on which category it lands in — a power droop needs bulk capacitance or a regulator change, a soft error needs scrubbing or mitigation, and a hung state machine needs a recovery path or a design fix.
**Possible follow-ups:** How would you distinguish a genuine configuration memory corruption from a design that simply locked up, using only the pins and registers available on the board? What design practices would you build in to make the system self-recovering from this class of failure?

## Q3: How would you approach designing the clock domain crossing for a multi-bit control word that is written by a slow serial interface (e.g., 10 MHz SPI) and consumed by a fast logic domain (e.g., 250 MHz), where the word changes infrequently but must never be observed in a partially updated state?
**Answer:** The core requirement here is atomicity, not throughput — the word changes rarely, so I can afford a handshake-based scheme rather than a low-latency streaming one. The cleanest approach is a bundled-data handshake: the slow domain writes the multi-bit word into a register, then asserts a single-bit "valid" or "toggle" signal that is synchronized into the fast domain through a two-flop synchronizer. The fast domain, on detecting the synchronized toggle, captures the entire multi-bit word in one clock edge. Because the word is stable well before the toggle is asserted and held stable until the fast domain has acknowledged (or until the next update), there's no risk of sampling a partially updated value — the multi-bit bus itself is never synchronized bit-by-bit, which is the classic mistake that causes incoherent captures. I'd use a toggle (or a request/acknowledge pair) rather than a level signal so that back-to-back updates are handled correctly and the fast domain can detect each new value exactly once. The critical constraints are: the word must be held stable from before the toggle assertion until after the fast domain has captured it (enforced by the handshake protocol, not by timing luck), and the synchronizer must be a proper two-flop (or three-flop) synchronizer with the appropriate ASYNC_REG attributes so the tool doesn't optimize it away or retime it. I'd also add a CDC constraint in the timing constraints to tell the tool these paths are asynchronous and should not be timed as if they were synchronous. For verification, I'd run a CDC lint tool to confirm the only crossings are the intended single-bit synchronizers, and I'd simulate with randomized clock phase relationships to confirm the captured word is always one of the valid written values, never a mix.
**Possible follow-ups:** Why is a toggle-based handshake preferable to a simple level-based "data valid" signal here? What would change if the control word had to be updated at a rate approaching the fast clock frequency?

## Q4: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?
**Answer:** A via through a thick backplane creates a stub — the unused portion of the barrel below (or above) the layer where the signal enters — and that stub behaves as an open-circuited transmission line that resonates at a frequency determined by its length and the board's effective dielectric constant. At multi-gigabit rates, that resonance produces a notch in the channel's insertion loss and a peak in return loss that can close the eye or cause jitter. The first-line mitigation is to minimize the stub length itself: route the signal on layers as close as possible to the entry/exit layer so the unused barrel is short, or use blind/buried vias if the fabrication process supports them, which eliminates the stub entirely. If the stack-up and cost budget don't allow blind vias, back-drilling is the standard industrial answer — the fabricator drills out the unused portion of the barrel after plating, leaving a short controlled stub. The back-drill depth tolerance matters, so I'd specify it and confirm the fabricator can hold it. Where back-drilling isn't feasible, I'd consider whether the channel budget can absorb the stub — running a channel simulation with the actual stack-up and stub length to see whether the eye still closes — and if not, I'd look at active mitigation: a stub-tuning technique where a small intentional capacitance or a tuned stub is added to move the resonance out of the signal band, or equalization at the receiver (CTLE/DFE) to compensate for the loss notch. I'd also check that the via's antipads and the return-path vias are designed properly — a via with a poor return path creates its own discontinuity that compounds the stub effect. The decision between these options is driven by the data rate, the channel loss budget, and the manufacturing cost/lead-time trade-off, so I'd bring the fabricator and the SI simulation together early rather than discovering the problem at bring-up.
**Possible follow-ups:** How would you decide whether back-drilling is worth the cost versus relying on receiver equalization for a given channel? What simulation setup would you use to quantify the stub's impact before committing to a fabrication approach?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?
**Answer:** I'd treat this as a review-quality and mentorship moment rather than a confrontation, because the engineer may well be right about some of the exceptions — the problem is that the report doesn't let us tell which ones are justified. My first move is to ask the engineer to walk me through each exception and the reasoning behind it, one at a time. For each, I'd want to see the specific path, why it's genuinely a false path or a multicycle path, and what analysis or documentation supports that claim. A legitimate false path is one where the logic truly never needs to be timed — for example, a path that only exists in a test mode that's never active in operation, or a path between two domains that are genuinely asynchronous and handled by a proper CDC structure. A legitimate multicycle path is one where the destination register is only enabled every N cycles by design, and that intent is visible in the RTL and documented. What I'm listening for is whether the exception reflects a real design intent or whether it was added because the path failed and the engineer needed the report to go green. If it's the latter, that's a real problem — an unjustified exception hides a timing violation that will show up as an intermittent hardware failure. I'd frame the conversation around that risk: the goal isn't to make the report pass, it's to make the hardware work, and an exception that isn't backed by design intent is a latent bug. I'd ask the engineer to add a comment or a constraint-file annotation for each exception explaining the justification, and I'd want the exceptions reviewed by a second set of eyes — either me or a senior engineer — before sign-off. If some exceptions turn out to be unjustified, we'd remove them and fix the underlying timing, which might mean pipelining, retiming, or restructuring the logic. I'd also use this as a coaching opportunity: explain the difference between "the tool says it's fine" and "I can prove it's fine," and set the expectation that timing exceptions are design decisions that need documentation, not tool settings to be tuned until the report is clean. The tone matters — I want the engineer to leave the review understanding why this discipline exists, not feeling attacked, because the next time they'll be the one catching it.
**Possible follow-ups:** How would you structure a review process so that timing exceptions get the same scrutiny as the rest of the design? What would you do if the engineer pushed back and insisted the exceptions were fine without providing the justification you asked for?
