# high-speed-digital-fpga — Day 110

## Q1: How would you approach designing the power-up and configuration sequence for an FPGA that loads its bitstream from external flash, when the flash device itself has a non-trivial access latency and the board may be power-cycled rapidly?

**Answer:** The core problem is that the FPGA's configuration engine starts issuing commands as soon as its configuration rail is valid, but the flash may not be ready yet — and on a fast power cycle the flash may still be in the tail of its previous internal operation. I'd treat this as a sequencing and handshaking problem rather than a timing-margin problem.

First, define the rail order and the "configuration-valid" threshold explicitly from the FPGA's datasheet, and make sure the flash's own supply and reset are released in an order that guarantees the flash is out of reset and its internal state machine is idle before the FPGA begins to clock it. If the flash has a documented wake-up or reset-recovery time, that number goes into the power sequencing budget, not into "it'll probably be fine."

Second, don't rely on the FPGA's default configuration timing alone. Use the FPGA's configuration-controller status signals — init-done, and where available a configuration-error or timeout flag — to gate the start of the flash read, or use an external supervisor or CPLD to hold the FPGA's program pin until the flash is confirmed ready. A small RC or supervisor delay on the program release is often the cheapest fix, but it has to be sized against the worst-case flash wake-up plus the worst-case rail ramp, not the typical.

Third, handle the rapid-power-cycle case specifically. If the board can be cycled faster than the flash's recovery time, the flash may return garbage or NAK the first read. I'd add a bounded retry in the configuration path — either the FPGA re-attempts configuration, or a supervisor forces a full re-power of the flash — and I'd verify it by deliberately cycling power at intervals shorter than the flash spec and confirming the board either configures correctly or fails safe into a known recovery state, never into a half-configured hang.

Finally, I'd validate across the full rail-ramp spread: slow ramp, fast ramp, brownout-then-recover, and hot-plug. The failure mode to design out is the board that configures on the bench and hangs in the field because the flash was a few milliseconds slower than the bench unit.

**Possible follow-ups:** How would you decide between a supervisor-based hold-off and an FPGA-side retry loop — what are the trade-offs? What would you check first if a small fraction of boards fail to configure only on a cold start?

## Q2: How would you approach debugging an FPGA design where the transceiver link passes its built-in PRBS checker at the physical layer, but application-level data is occasionally corrupted, and the corruption only appears at full line rate?

**Answer:** A clean PRBS pass at the physical layer tells me the SerDes, the channel, and the CDR are healthy — so I'd stop looking at the analog front end and start looking at everything between the PMA and the application: the PCS, the framing, the clock domain crossing out of the transceiver's recovered-clock domain, and the buffer/flow-control logic.

My first move is to localize where the corruption is introduced. I'd bring the link up at full rate and use the transceiver's own error counters and, if available, its internal pattern generators at the PCS level rather than only the PMA level — that distinguishes "bits arriving wrong" from "bits arriving right but being mishandled." If the PCS-level checker is clean but the application sees bad data, the fault is downstream of the SerDes.

Next I'd look hard at the receive path's clock domain crossing. At full line rate the recovered clock and the fabric clock are both running flat out, and a CDC that was marginal at reduced rate — a shallow FIFO, a synchronizer with insufficient settling, a status flag sampled without proper handshaking — will start to slip. I'd check FIFO occupancy margins under sustained full-rate traffic, not bursts, and look for any place where a multi-bit value crosses domains without a proper handshake or Gray coding.

Then I'd examine framing and flow control: idle insertion, comma alignment, and whether the receiver's buffer can absorb the full-rate burst behavior. Corruption that only appears at full rate often turns out to be an overflow or an underrun that the reduced-rate test never exercised, and the "corruption" is actually dropped or duplicated words rather than flipped bits.

Finally, I'd instrument with a logic analyzer or embedded trace on the receive-side data path, timestamped against the error event, so I can see whether the bad word is a bit error, a shifted word, or a stale word — each points at a different block.

**Possible follow-ups:** How would you distinguish a receive FIFO overflow from a genuine bit error using only in-fabric instrumentation? What changes if the corruption is bursty rather than single-word?

## Q3: How would you approach designing the clock domain crossing for a multi-bit Gray-coded counter value that increments continuously in a fast domain (e.g., 250 MHz) and must be sampled by a slower domain (e.g., 50 MHz) for logging, where the sampled value must always be a coherent snapshot and never a corrupted mix of bits?

**Answer:** Gray coding is the right instinct here, but it's only sufficient under specific conditions, and I'd want to be explicit about them rather than assume them.

The property that makes Gray coding work for a CDC is that only one bit changes per increment, so a sampling edge that lands during a transition can only capture either the old or the new value — never a mix. That holds only if the counter increments by exactly one per source clock and the destination samples asynchronously. If the counter can jump by more than one (a preset, a clear, a wrap that isn't Gray-safe), the single-bit-change guarantee is broken and the scheme silently fails. So the first design decision is to guarantee the source only ever increments by one, and to handle wrap explicitly — a standard binary wrap is not Gray-safe at the boundary, so either size the counter so wrap never occurs in practice, or convert to Gray in a way that preserves the one-bit property across the rollover.

Second, the destination must sample the Gray bus through a proper synchronizer — one or two flops per bit in the destination domain — and then convert back to binary. The synchronizer resolves metastability per bit; the Gray property ensures that even if different bits resolve on different cycles, the resolved combination is still a valid adjacent code. I'd also add a settling delay or a second sample-and-compare in the destination if the destination logic is sensitive to a single stale sample, though for logging that's usually unnecessary.

Third, I'd verify it. A CDC like this is exactly what formal CDC checking and a targeted simulation with injected skew are for: I'd run a CDC lint/formal tool to confirm the tool recognizes the Gray bus as a proper synchronized structure and doesn't flag it as an unsafe multi-bit crossing, and I'd simulate with the destination sampling deliberately offset across the source transition to confirm the decoded value is always either N or N+1, never garbage.

The failure mode I'd be most careful about is a well-meaning later change — someone adds a "reset to zero" or a "load preset" to the counter and quietly destroys the one-bit-change invariant. I'd document the invariant at the module boundary and, if the tooling supports it, add an assertion that flags any increment other than +1.

**Possible follow-ups:** What would you do if the counter genuinely needs to be preset, breaking the single-increment assumption? How would you verify the Gray CDC in formal rather than simulation?

## Q4: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?

**Answer:** On a thick backplane, a via that passes through the full board thickness but is only used for a layer transition leaves an unused barrel — the stub — hanging off the signal path. At multi-gigabit rates that stub is a resonant transmission-line discontinuity: it produces a notch in the channel's insertion loss at a frequency set by the stub's electrical length, and it degrades return loss and eye height. The thicker the backplane, the longer the stub and the lower the notch frequency, so this is a real design constraint, not a rounding error.

I'd attack it in order of preference. The cleanest fix is to eliminate the stub: use blind or buried vias so the via only spans the layers it needs to connect, or use backdrilling to remove the unused barrel below the last connected layer. Backdrilling is the standard backplane answer and is well understood by fabricators, but it adds cost and drill-depth tolerance matters — you have to specify the backdrill depth and the remaining stub length budget, and confirm the fabricator can hold it.

If backdrilling isn't available, I'd reduce the stub's electrical impact: choose layer transitions that minimize the stub length (transition between adjacent layers near the surface rather than spanning the full stack), and where the channel allows, route the transition so the stub is as short as the stack-up permits. I'd also consider whether the transition can be avoided entirely by keeping the high-speed pairs on layers that don't require a full-thickness via.

Then I'd verify rather than assume. I'd extract the channel — including the via model, not just the traces — and run it through a channel simulator with the actual stack-up and connector models, and check the insertion loss and return loss against the link budget at the target rate. If the notch lands inside the signal's occupied bandwidth, I'd revisit the via design before layout is released, because fixing it after fabrication means a board spin.

The judgment call is cost versus margin: backdrilling every high-speed via on a thick backplane is expensive, so I'd backdrill the vias that actually matter — the ones whose stub resonance falls in-band for the rates in use — and leave the rest, documenting the reasoning so the decision is reviewable.

**Possible follow-ups:** How would you set a stub-length budget from the target data rate and the channel's loss tolerance? What would you check in the fabricated board to confirm the backdrill achieved the intended stub length?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?

**Answer:** I'd treat this as a review-quality issue first and a people issue second, and I'd be careful not to frame it as "you cheated" — the engineer may genuinely believe the exceptions are correct, and some of them may be. The problem is that a timing report is only meaningful relative to its exceptions, and exceptions are exactly where designs pass analysis and fail in hardware.

My approach in the review would be to walk each exception and ask one question: what is the physical justification, and where is it documented? A legitimate multicycle path has a reason — a data path that is genuinely allowed multiple cycles because the receiving logic only samples it on a slower enable, or a path between two registers that are functionally never both active. A legitimate false path has a reason — a test or debug path that is statically tied off in the configured design, or a path between asynchronous domains that is handled by a proper CDC structure. If the engineer can point to the RTL structure and the design intent that justifies the exception, and it's written down, that's a real exception. If the justification is "it works in simulation" or "it doesn't matter for current functionality," that's not a justification — that's a constraint being used to hide a real path, and I'd say so plainly.

I'd also check the exceptions for the classic failure modes: a false path applied to a whole clock domain rather than a specific path, a multicycle path whose setup and hold relationships weren't both specified, and exceptions that were added late in closure without being re-reviewed. And I'd want the exceptions under version control with a comment per exception, so the next engineer inheriting the design can see why each one exists.

Then I'd close the loop constructively: for each exception that doesn't hold up, the path either gets fixed or gets a proper constraint, and the engineer owns that work with my support. I'd also use it as a teaching moment for the whole team about why exceptions are the highest-risk part of a timing sign-off, and I'd add an exceptions review to the sign-off checklist so this is caught by process next time, not by luck.

The tone matters: the goal is a correct design and an engineer who understands why the exception discipline exists, not a public correction. But I would not sign off on a timing report whose exceptions I can't defend, and I'd make that boundary clear.

**Possible follow-ups:** How would you distinguish a genuinely safe false path from one that hides a real timing path? What would you add to the sign-off process so timing exceptions get reviewed before closure, not after?
