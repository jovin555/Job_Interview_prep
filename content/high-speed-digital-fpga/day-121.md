# high-speed-digital-fpga — Day 121

## Q1: How would you approach designing the power-up and reset release sequence for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?

**Answer:** The core principle is that each subsystem has its own prerequisites, and the reset controller must encode those dependencies explicitly rather than relying on a single global reset. I would start by writing down the dependency graph: the configuration engine needs all its supply rails within tolerance and the configuration clock stable; the PLLs need their reference clocks present and their supply rails settled; the transceiver quads need their reference clock, their analog and digital rails, and — critically — the calibration/initialization handshake to complete before the fabric is allowed to use them. Then I'd implement a small sequencing state machine (in fabric, or in a supervisor/CPLD if the FPGA isn't configured yet) that walks this graph, holding each block in reset until its prerequisites report ready via status signals rather than fixed delays. Fixed delays are the classic failure mode: they work on the bench and fail on the board that ramps slower or faster. Where the device provides "PLL locked," "transceiver ready," or "calibration done" outputs, I'd gate on those; where it doesn't, I'd add a conservative timeout with an error flag so a stuck block is reported rather than silently hanging. I'd also make sure resets are released synchronously to each domain's clock, and that the reset for a domain is asserted asynchronously but de-asserted synchronously, to avoid the classic problem of a reset release landing on a clock edge and putting different flops into different states. Finally, I'd verify the sequence in simulation with deliberately skewed rail ramp models, and on hardware by probing the status lines during bring-up.

**Possible follow-ups:** How would you handle a transceiver quad that occasionally reports ready but then drops out during the first few milliseconds of operation? What would you do if the device's configuration engine has no ready output you can observe?

## Q2: How would you approach debugging an FPGA design where the DDR3 interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** The "passes cold, fails warm" signature points strongly at a timing margin that is being consumed by temperature-dependent effects — driver impedance shift, propagation delay drift, or a reference voltage that moves — rather than a logic bug. My first move is to characterize rather than guess: run the same memory test in a loop while logging the device junction temperature and the error rate, and see whether the failures correlate with a temperature threshold or with time-since-power-on independent of temperature. If it's temperature, I'd suspect the read capture window first, because read path margin is usually the tightest. I'd re-run the controller's per-bit deskew or read-leveling calibration at the elevated temperature and compare the tap settings against the cold values — if the eye has shifted by several taps, that tells me the margin was marginal to begin with. On the board side, I'd look at the reference voltage (VREF) generation and the termination: if VREF is derived from a resistor divider off a rail that drifts, or if ODT is enabled when the topology calls for external termination (or vice versa), the eye will move with temperature. I'd also check the write path — write leveling and ODT timing — and confirm the controller isn't running with a fixed timing that was only valid at one corner. The fix is usually to re-center the calibration at the worst-case temperature, add margin by tightening the timing, or correct the termination/VREF scheme, then re-verify across the full temperature range rather than at a single point.

**Possible follow-ups:** How would you distinguish a read-path margin problem from a write-path margin problem using only the controller's built-in facilities? What would you do if the calibration taps don't shift with temperature but the errors still appear?

## Q3: How would you approach designing the clock domain crossing for a multi-bit control word that is written by a slow serial interface (e.g., 10 MHz SPI) and consumed by a fast logic domain (e.g., 250 MHz), where the word changes infrequently but must never be observed in a partially updated state?

**Answer:** The key insight is that "changes infrequently" is not a synchronization guarantee — the consumer can sample at exactly the wrong moment, so the design must make the transfer atomic by construction. The standard robust approach is a handshake or a toggle-based scheme: the writer assembles the full word in its own domain, then asserts a request (or toggles a single bit) that is synchronized into the reader domain through a two-flop synchronizer; the reader, on detecting the request/toggle edge, captures the entire word in one clock and asserts an acknowledge that is synchronized back. Because the word is stable for many writer cycles before the request is raised and held stable until the acknowledge returns, the multi-bit data is never sampled mid-update. An alternative for a register that is read rather than pushed is a double-buffered or "shadow register" scheme: the writer updates a shadow copy, then a single synchronized enable transfers the whole shadow into the live register in one reader clock. What I would avoid is putting a two-flop synchronizer on each bit of the bus — that's the classic mistake, because each bit can resolve on a different cycle and the consumer sees a mix of old and new bits. I'd also add a CDC lint/formal check to the flow so that any unsynchronized crossing is flagged automatically, and I'd constrain the crossing properly in the timing constraints (false path or max-delay as appropriate) so the tool doesn't try to time a path that isn't a real single-cycle path.

**Possible follow-ups:** When would you choose a handshake over a toggle-based scheme, and what's the latency cost of each? How would you handle the case where the writer can issue a new word before the reader has acknowledged the previous one?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?

**Answer:** I treat constraint completeness as a verification problem in its own right, not something you eyeball at the end. The first line of defense is tooling: run the vendor's timing-constraint checker and any CDC/clock-domain analysis, and treat every unconstrained or partially constrained path as a finding to be resolved, not ignored. The second is a structured review of the constraint file against the design's clock and I/O inventory — every clock source, every generated clock, every I/O interface, and every asynchronous crossing should have an explicit, justified constraint. I'd specifically hunt for the dangerous categories: false paths and multicycle paths that were added to make a design close rather than because the path genuinely doesn't need single-cycle timing; clocks that are defined but not propagated to their generated descendants; I/O delays that were guessed rather than derived from the external device's datasheet; and asynchronous crossings that are constrained as if they were synchronous. The third line is correlation with hardware: if the design has on-chip debug or a way to sweep timing, I'd confirm that the reported slack actually corresponds to real margin — a design that reports positive slack but fails at temperature or voltage extremes usually has a constraint that doesn't reflect reality. Finally, I'd make the constraint review a gate in the sign-off checklist, with a second pair of eyes, because the person who wrote the constraints is the least likely to spot their own optimistic assumptions.

**Possible follow-ups:** How would you audit a set of multicycle path constraints to confirm each one is legitimate? What's your approach when a design only closes timing after adding exceptions you're not fully comfortable with?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented the data path that captures samples from a high-speed ADC and writes them to DDR memory. During the review, you notice they've sized the capture FIFO from the average throughput rather than the worst-case burst, arguing that "the average rate is well below the memory bandwidth, so it can't overflow." How do you handle this situation?

**Answer:** I'd treat this as a teaching moment rather than a correction, because the underlying reasoning — average rate below capacity — is intuitively appealing and the engineer isn't being careless, just missing the burst behavior. In the review, I'd walk through the arithmetic with them: the FIFO must absorb the difference between the instantaneous input rate and the instantaneous drain rate over the worst-case burst, not the average. If the ADC can deliver a burst at full rate while the memory controller is momentarily busy with refresh, arbitration, or a read turnaround, the FIFO has to cover that interval, and the depth follows from (burst rate − drain rate) × burst duration, plus margin for the controller's own latency. I'd ask them to show me the worst-case burst envelope from the ADC datasheet and the memory controller's worst-case service latency, and let the numbers make the case — that's more persuasive than me asserting it. Then I'd agree on a concrete action: either resize the FIFO to cover the computed worst case, or add an overflow-detection and back-pressure/throttle mechanism so that if the assumption is ever violated, the system degrades gracefully instead of silently corrupting data. I'd also make sure the review checklist for future data-path reviews includes "FIFO depth justified from worst-case burst, not average rate," so the lesson generalizes beyond this one design. The tone throughout is collaborative — the goal is a correct design and an engineer who understands why, not a gotcha.

**Possible follow-ups:** How would you handle it if the worst-case burst analysis shows the required FIFO depth is impractically large for the available block RAM? What would you do if the engineer pushed back and argued the average-rate assumption is validated by their simulation?
