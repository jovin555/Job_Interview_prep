# high-speed-digital-fpga — Day 120

## Q1: How would you approach designing the clock domain crossing for a multi-bit data bus where the source and destination clocks are asynchronous, the data changes frequently, and you need to minimize latency while ensuring data integrity?
**Answer:** The core problem is that a multi-bit bus cannot be synchronized bit-by-bit with two-flop synchronizers, because each bit can resolve on a different clock edge and the destination can capture a mix of old and new values — a "word tear." The right approach depends on the latency budget. If latency must be minimal, the standard technique is a handshake-based muxed register: the source holds the data stable, asserts a request through a two-flop synchronizer into the destination domain, the destination captures the whole word on the synchronized request and returns an acknowledge, and the source only updates the data after the acknowledge returns. This guarantees coherent transfer at the cost of a few destination-clock cycles of round-trip latency. If the data is a continuously incrementing counter or pointer, Gray coding is preferable — only one bit changes per increment, so a two-flop synchronizer per bit is safe and the destination always sees either the old or new value, never a corrupted mix. For genuinely high-throughput streaming data, an asynchronous FIFO is the right structure: dual-port memory with Gray-coded read and write pointers synchronized across domains, and full/empty flags generated from the pointer comparison. The FIFO gives bounded latency and no data loss, at the cost of depth and the need to size it for the worst-case pointer synchronization delay. I would also add a CDC lint check and, where possible, a formal CDC verification pass, because these bugs are notoriously hard to catch in simulation. The key discipline is: never let a multi-bit value cross domains without one of these structures, and document the chosen mechanism so reviewers can check it.
**Possible follow-ups:** How would you size the asynchronous FIFO depth given the pointer synchronization latency and the burst behavior of the source? What would change if the two clocks had a known, fixed frequency ratio rather than being fully asynchronous?

## Q2: How would you approach debugging an FPGA design where the DDR3 interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?
**Answer:** A failure that appears only after warm-up points strongly to a timing or analog margin issue rather than a logic bug, so I would treat it as a margin problem and try to characterize it before changing anything. First, I would confirm the correlation with temperature — log junction or board temperature alongside the error rate, and see whether the failures begin at a repeatable threshold. Then I would look at what changes with temperature: DRAM refresh behavior, the memory controller's internal timing, and the analog characteristics of the board. A common culprit is that the write/read leveling or per-bit deskew values were calibrated once at power-up at room temperature and are now stale — as the board warms, the delay through the FPGA I/O and the DRAM changes, and the calibrated tap settings no longer sit in the center of the eye. I would check whether re-running calibration after warm-up eliminates the errors; if it does, the fix is either to re-calibrate periodically or on temperature change, or to widen the margin by improving the board-level signal integrity. I would also look at the power delivery: as the device heats up, the core and I/O rails may droop or ripple more, and the DDR I/O timing budget shrinks. I would probe the rails under load and check the decoupling. Finally, I would check whether the failure correlates with a particular data pattern or access pattern, which would point at crosstalk or a specific timing relationship rather than a global margin issue. The discipline is to isolate whether it is a calibration-staleness problem, a power integrity problem, or a signal integrity problem before committing to a fix.
**Possible follow-ups:** How would you decide whether to re-calibrate on temperature change versus simply adding more timing margin? What board-level changes would you consider if the root cause turned out to be crosstalk that only manifests at elevated temperature?

## Q3: How would you approach designing the power distribution network for an FPGA transceiver bank, where the rails see both high-frequency switching noise from the SerDes and slower, larger current transients from the fabric, and you need to verify the network is adequate before committing to the layout?
**Answer:** The transceiver rails have a tighter ripple specification than the core rail and a noise spectrum that spans a very wide range, so the PDN has to be designed as a broadband impedance problem rather than a single-capacitor problem. I would start from the transceiver's datasheet requirements — the allowed ripple, the current profile, and the recommended decoupling — and then build a target impedance curve across frequency. The low-frequency end (up to a few hundred kHz) is handled by the regulator's loop bandwidth and bulk capacitance; the mid-band (hundreds of kHz to tens of MHz) by a spread of ceramic capacitors of decreasing value; and the high-frequency end (tens of MHz to GHz) by the on-die capacitance and the package, which the board can only support by keeping the via and plane inductance low. The critical insight is that above a few tens of MHz, the board's job is to minimize the loop inductance between the capacitor and the die, so capacitor placement and via count matter more than capacitor value. I would model the PDN in a simulation tool — a 2D or 3D electromagnetic extraction of the planes and vias combined with the capacitor models and the regulator's output impedance — and check that the impedance stays below target across the band. I would also run a transient simulation with a realistic current step to confirm the voltage stays within the ripple spec. Before committing to layout, I would review the plane shapes, the capacitor placement, and the via stitching, and I would plan to measure the actual ripple on the first prototypes with a low-inductance probe. The verification is iterative: simulate, lay out, measure, and adjust.
**Possible follow-ups:** How would you decide how many vias to assign to each decoupling capacitor, and what is the trade-off? What would you do if the measured ripple on the first prototype exceeded the transceiver spec despite the simulation passing?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?
**Answer:** The danger with timing sign-off is that the tool only checks what you tell it to check, so an incomplete constraint set produces a clean report that means nothing. I would treat constraint verification as a review process, not a tool run. First, I would confirm that every clock in the design is created and that the clock definitions match the actual board — frequency, source, and whether it is generated internally or comes from an external oscillator. Second, I would check that every clock domain crossing is either properly constrained with a synchronizer and a false-path or max-delay exception, or flagged as a real timed path; the CDC report from the tool is the starting point, but I would cross-check it against the RTL. Third, I would audit every timing exception — every false path and multicycle path — and require a written justification for each one, because these are exactly where a design can "pass" while being wrong. Fourth, I would confirm the I/O timing constraints match the external device datasheets: input and output delays, board skew, and the reference clock relationships. Fifth, I would run the design at all specified PVT corners, not just the nominal one, and check that the reports are generated from the same netlist that will be programmed. Finally, I would use the tool's unconstrained-path and unconstrained-endpoint reports to catch anything the constraints missed, and I would review the constraint file itself as a design artifact in the review. The mindset is that a timing report is only as trustworthy as the constraints behind it, so the constraints get the same scrutiny as the RTL.
**Possible follow-ups:** How would you catch a clock that was accidentally left unconstrained, given that the tool may not flag it as an error? What is your process for reviewing a multicycle path exception to confirm it is genuinely safe?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?
**Answer:** I would treat this as a teaching moment rather than a confrontation, because the engineer's reasoning is a very common and understandable misconception, and the goal is to get the design fixed and the engineer to internalize why. First, I would acknowledge the intuition — it is true that the signal is stable for a long time relative to the clock — and then explain why that does not save it: the destination flop samples on its own clock edge, and if that edge lands within the setup/hold window of the transition, the flop can go metastable, and metastability can propagate and resolve differently on different cycles or different boards. The fact that it "works" in the lab is exactly the trap, because the failure is probabilistic and may only show up at temperature, at a different voltage, or on a different unit. I would then walk through the correct structure for that signal — a two-flop synchronizer for a single-bit level signal, a pulse synchronizer or toggle handshake for a pulse, and a proper handshake or FIFO for multi-bit data — and ask the engineer to propose which one fits their signal. I would also point them at the CDC lint report and the formal CDC check so they can see the tool flag it themselves. Then I would have them update the design and re-present the fix at the next review, so the learning is reinforced. The tone matters: I want the engineer to leave understanding the mechanism, not feeling embarrassed, because the same class of bug will come up again and I want them to catch it themselves next time.
**Possible follow-ups:** How would you handle it if the engineer pushed back and argued that the design had passed simulation and lab testing? What process change would you propose to catch this class of issue earlier in future reviews?
