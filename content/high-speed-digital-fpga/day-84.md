# high-speed-digital-fpga — Day 84

## Q1: How would you approach designing the power-up and configuration sequence for an FPGA that loads its bitstream from external flash, when the flash device itself has a non-trivial access latency and the board may be power-cycled rapidly?
**Answer:** The core problem is that configuration is a multi-party handshake between the power rails, the FPGA's internal configuration controller, and an external memory device that has its own wake-up and access timing — and rapid power cycling can catch any of those parties mid-initialization. I'd start by mapping the sequence explicitly: all FPGA supplies reach their minimum operating thresholds and stabilize, the FPGA releases its internal power-on reset, the configuration controller begins driving the flash interface, and the flash must be ready to respond before the controller times out waiting for the first data. The flash's wake-up latency matters because some devices need a defined delay after power is valid before they'll accept a read command, and if the FPGA starts clocking the configuration interface before that window has elapsed, the first read returns garbage or nothing, and depending on the controller's error handling the device may either retry or latch a failed configuration.

To make this robust I'd treat the flash's ready condition as a real input to the sequence rather than assuming it. If the flash has a ready/busy or reset pin, I'd drive it from a supervisor or from the FPGA itself with a deliberate hold-off, so the configuration controller doesn't begin until the flash is genuinely ready. I'd also make sure the FPGA's configuration controller is configured for the correct clock rate for that flash part — running the configuration clock faster than the flash's access time allows is a classic source of intermittent configuration failure that only shows up on some boards or at temperature extremes.

For rapid power cycling specifically, the risk is that the rails don't fully discharge between cycles, so the FPGA or flash may come up in a partially-reset state. I'd add a proper supply supervisor with a defined reset threshold and hysteresis, and I'd verify that the discharge path on each rail brings it below the device's reset threshold within the required time. On the bench I'd characterize this by cycling power at varying intervals — short off-times, long off-times, and ramping the supply slowly — and confirm configuration completes reliably across all of them. I'd also check that the configuration done signal is actually being monitored by the rest of the system, so a failed configuration is detected and retried rather than silently leaving the device idle.

**Possible follow-ups:** How would you decide whether to add a dedicated configuration supervisor versus relying on the FPGA's internal POR? What changes if the flash is shared with the application for data storage?

## Q2: How would you approach debugging an FPGA design where the device configures successfully and runs correctly for a period of time, but then the configuration appears to be lost — the device stops responding and requires a reconfiguration to recover?
**Answer:** The first thing I'd do is separate "the configuration was actually lost" from "the device stopped responding for some other reason." Those look identical from the outside but have very different root causes. If the device has a configuration status or CRC error output, I'd monitor it continuously rather than only at boot — some devices can report a configuration memory error after startup, which would point to a single-event upset or a marginal configuration memory cell rather than a logic problem. If there's no such signal, I'd try to read back the configuration or use the device's internal error detection if available.

Assuming the configuration really is being lost, I'd think about what could cause that. The most common categories are: a power supply transient that dips below the configuration memory's retention threshold, a configuration memory error from radiation or a marginal cell, a watchdog or external reset that's being asserted unexpectedly, or a thermal issue that pushes a marginal timing path or memory cell out of spec. I'd instrument the board to log the supply rails continuously with a scope or a fast logger, because a brief dip that doesn't reset the whole device can still corrupt configuration memory. I'd also check whether the failure correlates with a specific activity — a particular data pattern, a temperature threshold, or a time interval — because that narrows the cause considerably.

If it correlates with temperature, I'd suspect a marginal timing path or a memory retention issue and would look at the device's temperature derating. If it correlates with a specific operation, I'd suspect a power transient from that operation — for example, a high-current burst on an I/O bank or a transceiver. If it's random and rare, I'd consider radiation or a latent defect and would look at whether the failure rate changes with altitude or with a different batch of devices. Throughout, I'd be careful not to assume the FPGA is at fault — a marginal external component, a bad solder joint that opens when warm, or a noisy supply can all present as "the FPGA lost its configuration."

**Possible follow-ups:** How would you distinguish a configuration memory upset from a logic error that just looks like a hang? What design practices would you put in place to make the system recover automatically from this kind of failure?

## Q3: How would you approach designing the clock domain crossing for a multi-bit Gray-coded counter value that increments continuously in a fast domain (e.g., 250 MHz) and must be sampled by a slower domain (e.g., 50 MHz) for logging, where the sampled value must always be a coherent snapshot and never a corrupted mix of bits?
**Answer:** Gray coding is the key enabler here, and it's worth being explicit about why. In a binary counter, multiple bits can change on the same clock edge — for example, going from 0111 to 1000 flips four bits. If the destination domain samples during that transition, it can capture a mix of old and new bits that corresponds to a value the counter never actually held. Gray coding guarantees that only one bit changes per increment, so even if the destination samples exactly during the transition, it captures either the old value or the new value — both of which are valid states the counter actually passed through. That's the property that makes a simple multi-flop synchronizer on each bit safe for a Gray-coded value, which would not be true for a binary value.

The design itself is straightforward: the fast domain maintains the Gray-coded counter, and the slow domain passes each bit through a two-flop synchronizer clocked by the slow domain. Because only one bit changes at a time, there's no risk of an incoherent multi-bit capture. The slow domain then optionally converts the Gray code back to binary for logging or display. The one subtlety is that the synchronizer adds latency, so the value the slow domain sees is a snapshot from a few slow-domain cycles ago — that's usually fine for logging, but if the application needs the value to be current within a tight bound, that latency has to be accounted for.

I'd also think about the counter width. A wider counter means more synchronizer flops, but the Gray-coding property holds regardless of width, so there's no fundamental limit. If the counter is very wide and the slow domain only needs a coarse view, I might synchronize only the upper bits and accept that the lower bits are stale — but that changes the coherence guarantee, so I'd only do it if the application genuinely doesn't need the full value. Finally, I'd verify the design with a formal CDC check or a targeted simulation that injects a transition during the synchronizer's setup/hold window, to confirm the destination never captures an invalid state.

**Possible follow-ups:** What would change if the counter had to be binary rather than Gray-coded — how would you transfer it safely? How would you handle the case where the fast domain can increment faster than the slow domain can sample, so multiple increments occur between samples?

## Q4: How would you approach choosing between a global clock network and a regional/banked clock resource for a logic block that only needs to run at a modest rate, when the device's global clock resources are nearly exhausted?
**Answer:** The decision comes down to what the logic block actually needs from its clock, weighed against the cost of consuming a scarce global resource. Global clock networks are designed for low skew and low jitter across the entire device, which is exactly what you need when a clock drives logic spread across many regions or when the clock's timing relationship to other clocks matters. Regional or banked clock resources are typically local to a clock region or a set of I/O banks, have somewhat higher skew to distant logic, and can't reach the whole device — but they free up the global network for clocks that genuinely need it.

For a logic block running at a modest rate, the first question is whether the block is confined to a single clock region. If it is, a regional clock is usually the right choice — it meets the timing needs, keeps skew manageable within the region, and doesn't consume a global resource. If the block spans multiple regions, a regional clock may not reach all of it with acceptable skew, and I'd either restructure the logic to fit within a region or accept that it needs a global clock. The second question is whether the clock needs to have a defined phase relationship with other clocks in the design. If it does — for example, if it's used in a CDC with a related clock — the skew and jitter characteristics of the network matter more, and a global clock is usually safer.

I'd also consider whether the "modest rate" block could share a clock with another block rather than having its own. Often the cleanest answer to global clock exhaustion is to consolidate clocks: if two blocks can run from the same clock without violating their timing requirements, that frees a global resource without any downside. If consolidation isn't possible, I'd use the regional resource and verify with static timing analysis that the skew to all endpoints is within budget. The tool's clock resource report is the place to confirm what's actually being used, because the synthesis tool may promote a regional clock to a global one if it detects a need, which would defeat the purpose.

**Possible follow-ups:** What are the timing implications of driving logic in two different clock regions from the same regional clock? How would you verify that a regional clock's skew is acceptable before committing to it?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?
**Answer:** This is a case where the engineer's reasoning is intuitively appealing but misses the actual failure mode, so my first move is to make the failure mode concrete rather than just asserting that the design is wrong. The issue isn't whether the signal is stable for a long time in the steady state — it's what happens during the transition. When the source signal changes near the destination clock's setup/hold window, the destination flop can go metastable, and the resulting output is unpredictable: it may resolve to the old value, the new value, or oscillate briefly before settling. That metastability can propagate into downstream logic and cause anything from a single-cycle glitch to a persistent wrong state, and it's exactly the kind of bug that passes simulation and fails in the field at a rate that's hard to reproduce.

I'd walk through this with the engineer using a timing diagram, showing the setup/hold window and where the transition can land. I'd also point out that "stable long enough" is not a specification — the question is whether the signal is guaranteed to be stable across the destination clock's setup/hold window on every cycle, and without synchronization there's no such guarantee. I'd then show the standard fix: a two-flop synchronizer for a single-bit level signal, or a proper handshake or FIFO for a multi-bit bus. For a single-bit control signal, the two-flop synchronizer is cheap and adds only a couple of cycles of latency, which is almost always acceptable for a control signal.

The tone matters here. The engineer isn't being careless — they're reasoning from a mental model that's common and understandable, and the goal is to correct the model, not to embarrass them. I'd frame it as "this is a subtle one that trips up a lot of people" and use it as a teaching moment for the whole review, since CDC issues are exactly the kind of thing that's easy to miss. I'd also make sure the review process catches this class of issue systematically — a CDC checklist or a lint tool that flags unsynchronized crossings — so it doesn't depend on someone spotting it in review. After the review, I'd follow up to confirm the fix is in and that the design passes a CDC check.

**Possible follow-ups:** How would you handle it if the engineer pushed back and said the signal is only used as a status indicator, so a glitch wouldn't matter? What would you do if you found this same pattern in several places in the design rather than just one?
