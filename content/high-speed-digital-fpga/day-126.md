# high-speed-digital-fpga — Day 126

## Q1: How would you approach designing the power-up and reset release sequence for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?

**Answer:** I'd treat this as a dependency-ordered state machine rather than a set of independent resets. The first principle is that every block has a precondition that must be *observed*, not assumed — so the sequence is driven by status signals (configuration DONE, PLL lock, transceiver calibration done, reference clock stable) rather than by fixed delays. Fixed delays are a trap because they're only valid at one temperature/voltage corner and one board build; a delay that works on the bench can be marginal in the field.

The order I'd design toward: power rails up and within tolerance (supervisor asserts), then the configuration engine loads the bitstream and asserts DONE, then the MMCM/PLLs are released and allowed to lock, then the transceiver quads are released and their calibration completes, and only then is the user logic held in reset released. Each stage has a timeout so a stuck precondition produces a diagnosable fault rather than a silent hang. The reset itself should be asynchronous-assert / synchronous-deassert per clock domain, so de-assertion doesn't create recovery/removal violations at the flop inputs.

A subtle point: the transceiver reference clock and the fabric clock often come from different sources, and the quad needs its reference clock stable *before* release. I'd also make sure the global reset is stretchable — a short reset pulse that's shorter than a slow clock period can be missed entirely, so the reset is synchronized into each domain and held for at least a couple of cycles of the slowest clock.

**Possible follow-ups:** How would you detect and recover if a PLL never locks — do you retry, fall back to a slower clock, or flag a fault? / How would you verify this sequencing in simulation when the PLL and transceiver models don't behave like silicon?

## Q2: How would you approach debugging an FPGA design where the DDR3 interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** The "passes cold, fails warm" signature points at a timing margin that's being consumed by temperature-dependent effects, so I'd resist the urge to blame the DRAM and instead characterize *where* the margin is going. The candidates are: the FPGA's own I/O timing shifting with junction temperature, the DRAM's output timing shifting with its case temperature, the reference voltage (VREF) drifting, or the board's impedance/termination behaving differently as things heat.

My first move is to instrument rather than guess. If the controller exposes per-bit read/write leveling results or margin (e.g., a read eye scan or per-bit deskew values), I'd log those at cold and at temperature and compare — a shrinking eye on specific bits tells me whether it's a data-group skew issue, a VREF issue, or a specific lane. I'd also check whether the failures correlate with a particular address range or bank, which would point at a specific byte lane or a fly-by topology stub rather than a global timing problem.

Then I'd separate the FPGA from the DRAM: run the same pattern with the DRAM held at a controlled temperature while the FPGA heats, and vice versa. That isolates which side is drifting. If it's the FPGA side, I'd look at whether the design is running close to the timing closure limit and whether the I/O timing constraints actually model the temperature derating. If it's the DRAM side, I'd revisit the refresh rate and the ODT settings, since ODT that's fine at room temperature can be marginal when the DRAM's own termination drifts.

The fix is usually to buy back margin — retune the leveling at temperature, adjust ODT/VREF, or add margin in the constraints — but the important thing is to prove *which* margin was being eaten before changing anything.

**Possible follow-ups:** How would you build a temperature sweep into your bring-up test so this is caught before it reaches the field? / If the leveling values look fine but errors still appear, where would you look next?

## Q3: How would you approach designing the termination and coupling scheme for a multi-gigabit serial link that must traverse a backplane connector, and how would you decide between AC and DC coupling?

**Answer:** I'd start from the link's electrical requirements rather than from habit. The decision between AC and DC coupling comes down to whether the two ends share a common-mode reference and whether the protocol can tolerate the DC blocking. AC coupling is the default for most multi-gigabit serial standards because it lets each end set its own common-mode, breaks ground loops across a backplane, and protects against a DC offset between boards — the cost is that the coupling capacitor forms a high-pass corner, so its value has to be chosen so the corner sits well below the lowest frequency content of the encoded data, otherwise you get baseline wander and pattern-dependent jitter. DC coupling is only appropriate when both ends are on the same ground reference and the standard calls for it, and even then you have to be sure there's no DC offset that would eat into the receiver's common-mode range.

For termination, the key is that the termination should match the transmission line impedance at the receiver to absorb the wave and kill reflections, and it should be placed as close to the receiver pin as the layout allows. On a backplane with a connector in the path, the connector is an impedance discontinuity, so I'd pick a connector whose differential impedance is specified and close to the trace impedance, and I'd keep the pinout such that each differential pair has a nearby ground return. I'd also check whether the receiver has internal termination that can be enabled, which is usually preferable to external resistors because it's closer to the die and better controlled.

The thing I'd verify before committing: run the channel through an IBIS-AMI or similar model with the actual connector and backplane length, and look at the eye at the receiver across the specified data rate and across corners. If the eye is marginal, the levers are pre-emphasis/equalization settings, coupling capacitor value, and connector choice — in that order of cost.

**Possible follow-ups:** How would you choose the AC coupling capacitor value, and what failure mode appears if it's too small? / What would you check in the layout review to make sure the connector transition doesn't create a stub?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?

**Answer:** The core problem is that timing analysis only proves what you told it to prove — an unconstrained or falsely-excepted path is silently "passing." So my verification is really about proving the constraint set is *complete* and *honest*, not just that the tool reports no violations.

I'd start with completeness: every clock in the design must have a created clock with the correct period, every generated clock must be derived correctly, every I/O must have input/output delay constraints that reflect the actual external device timing (including board skew), and every clock domain crossing must be either properly constrained or explicitly excepted with a documented reason. The tool's unconstrained-path and clock-crossing reports are the first thing I'd read — any unconstrained endpoint is a red flag, and any CDC that isn't handled by a synchronizer or a proper handshake needs justification.

Then honesty: I'd audit every false path and multicycle path individually. A false path is only legitimate if the two endpoints genuinely can never be related in a way that matters — and "it works in simulation" is not a justification. A multicycle path is only legitimate if the logic actually has that many cycles to settle, which means the enable or the data-valid structure has to enforce it. I'd also check that the exceptions aren't accidentally masking a real path (e.g., a wildcard that catches more than intended).

Finally, I'd cross-check against the physical implementation: run the design at the actual target corner, look at the worst negative slack and whether it's concentrated on paths that the constraints claim are fine, and confirm that the constraint file is under version control and reviewed like RTL. The sign-off criterion is that a second engineer can read the constraint file and explain every exception.

**Possible follow-ups:** How would you catch a CDC that's been "fixed" by a false path rather than a synchronizer? / What's your process for keeping constraints in sync when the RTL changes?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented the data path that captures samples from a high-speed ADC and writes them to DDR memory. During the review, you notice they've sized the capture FIFO from the average throughput rather than the worst-case burst, arguing that "the average rate is well below the memory bandwidth, so it can't overflow." How do you handle this situation?

**Answer:** I'd treat this as a teaching moment rather than a "you're wrong" moment, because the underlying reasoning — average rate below capacity — is a real engineering instinct, it's just applied at the wrong level. The gap is that a FIFO doesn't care about averages; it cares about the instantaneous difference between write and read rate over the window where the reader is stalled.

In the review, I'd walk through it concretely: the ADC produces bursts, the memory controller has arbitration latency and refresh pauses, and during any window where the write rate exceeds the drain rate, the FIFO fills at the *difference* rate. So the sizing question is "what's the longest window where writes outpace reads, and how much data accumulates in that window?" — plus margin for the fact that the controller's latency isn't constant. I'd ask them to bound that window from the ADC's burst behavior and the controller's worst-case latency, and show the arithmetic. That usually makes the point without me having to assert it.

I'd also make clear that this isn't about blame — it's exactly the kind of thing design review exists to catch, and the fix (resize the FIFO, or add backpressure/flow control so the ADC can be throttled) is straightforward once the worst case is bounded. I'd want the engineer to own the rework and present the corrected sizing at the follow-up, so the lesson sticks. And I'd note the general principle for the team: size buffers from worst-case burst and stall behavior, never from averages.

**Possible follow-ups:** What would you do if the worst-case burst analysis shows the required FIFO is larger than the available block RAM? / How would you add flow control without dropping samples?
