# high-speed-digital-fpga — Day 78

## Q1: How would you approach designing the power-up and configuration sequence for an FPGA that loads its bitstream from external flash, when the flash device itself has a non-trivial access latency and the board may be power-cycled rapidly?
**Answer:** The core problem is that configuration is a multi-party handshake between the power rails, the FPGA's internal configuration controller, and an external memory device that has its own timing requirements — and rapid power cycling can violate any of them. I'd start by defining the sequence as a state machine with explicit dependencies rather than relying on default behavior. First, all FPGA supplies must reach their minimum specified levels and the internal power-on reset must release before configuration begins; the FPGA's configuration controller typically won't start until that happens, but the flash may power up on a different rail with a different ramp, so I'd verify the flash is actually ready (its own POR complete, and if it has a wake-up or deep-power-down exit time, that delay must be accounted for) before the FPGA issues its first read. If the FPGA's configuration controller assumes the flash responds within a fixed number of cycles, and the flash's first-access latency exceeds that, configuration will fail intermittently — so I'd either choose a flash whose latency fits the controller's window, or insert a controlled delay or a "wait for flash ready" gate before releasing the FPGA's configuration start. For rapid power cycling, the key risk is that a rail hasn't fully discharged before the next power-up, so the FPGA or flash sees a brown-out rather than a clean reset; I'd add a supervisor with a proper reset threshold and a hold time, and make sure the discharge path (bleed resistors or the regulator's own discharge) brings rails down predictably. I'd also make the configuration scheme robust to a failed or partial load — for example, a fallback image or a retry mechanism — so a corrupted load doesn't leave the board dead. Verification would include repeated fast power cycles at temperature extremes, monitoring the configuration done signal and the flash's ready/busy line, and scoping the rails to confirm no rail is still high when the next cycle starts.
**Possible follow-ups:** How would you decide whether the flash's latency is compatible with the FPGA's configuration controller without just reading datasheets — what would you measure? What changes if the board must support in-field bitstream updates, and how does that interact with the power-cycle robustness you described?

## Q2: How would you approach choosing between a global clock network and a regional/banked clock resource for a logic block that only needs to run at a modest rate, when the device's global clock resources are nearly exhausted?
**Answer:** The decision is really about resource allocation and the actual requirements of that clock, not about the clock's frequency alone. Global clock networks offer low skew across the whole device and are the default for anything that needs to reach many scattered destinations, but they're a scarce resource, and if they're nearly exhausted, using one for a modest-rate block may starve a block that genuinely needs it. A regional or banked clock resource can drive a localized set of logic at lower skew within its region, which is usually fine for a block whose fanout is confined to one area. So my first step is to characterize the block: how many destinations does the clock actually reach, are they physically clustered, and does the block have any timing relationship with logic outside that region? If the fanout is local and there's no cross-region timing requirement, a regional resource is the natural fit. If the block does need to communicate with logic elsewhere, I'd check whether the crossing can be handled by a CDC synchronizer rather than by forcing a global clock — often the "need" for a global clock is really a need for a clean domain crossing, which is a different problem. I'd also consider whether the block can share an existing clock (same frequency and phase relationship) rather than introducing a new one at all, since every additional clock network consumes resources and complicates timing constraints. The trade-off to watch is that regional clocks may have different jitter or insertion delay characteristics, and if the block's timing is tight, that matters. I'd confirm the choice by running timing analysis with the actual placement and checking that the regional clock's skew and the resulting setup/hold margins are acceptable, rather than assuming from the resource type alone.
**Possible follow-ups:** What symptoms in timing analysis would tell you that a regional clock choice was a mistake, and how would you recover? How would you handle a case where two blocks each want a global clock but only one global resource remains?

## Q3: How would you approach debugging an FPGA design where the device configures successfully and runs correctly for a period of time, but then the configuration appears to be lost — the device stops responding and requires a reconfiguration to recover?
**Answer:** The first thing I'd do is separate "the configuration was actually lost" from "the device stopped responding for another reason." A true loss of configuration usually means the device's internal configuration memory was disturbed or the device was reset — so I'd check whether any reset source (external supervisor, brown-out, watchdog, or a glitch on the program pin) asserted, and whether the configuration done signal actually dropped or the device merely became unresponsive. If the configuration is genuinely being lost, the likely causes are a power supply transient that dips below the device's retention threshold, a thermal or radiation event (less likely in a lab, but relevant in some environments), or an external signal that's being misinterpreted as a reconfiguration request. I'd instrument the board to log the state of the done/init signals, the reset lines, and the rail voltages over time, ideally with a scope or a logic analyzer triggered on the failure, because the event may be brief. If the rails show a dip, I'd look at the power distribution network — a transient load step from the fabric or transceivers can cause a droop that the regulator can't recover from quickly enough, and the fix is more bulk or better transient response, not a firmware change. If no rail dip is visible, I'd check for a spurious reset from a supervisor with too-tight a threshold, or a signal integrity issue on the configuration or reset lines. I'd also consider whether the device is in a state where it's still configured but the application logic has hung — in which case the "recovery by reconfiguration" is really a workaround, and the real bug is in the logic or its watchdog. The key is to not assume the configuration is lost until the done signal and rails prove it.
**Possible follow-ups:** If the failure only appears after the board has been running for hours, what would that timing suggest about the root cause? How would you distinguish a configuration loss from a logic hang without adding permanent instrumentation to every board?

## Q4: How would you approach designing the termination and coupling scheme for a multi-gigabit serial link that must traverse a backplane connector, and how would you decide between AC and DC coupling?
**Answer:** The starting point is the link's signaling standard and what the receiver expects, because that often dictates coupling before any board-level trade-off. Many high-speed serial standards are AC-coupled by definition — the receiver's common-mode is set internally, and the link relies on a DC-balanced encoding (like 8b/10b or 64b/66b) so that AC coupling doesn't cause baseline wander. If the standard requires AC coupling, the decision is made for you, and the design question becomes where to place the coupling capacitors and how to keep the transition clean. If the standard allows DC coupling, then AC coupling is a choice you make to break ground loops or level-shift between two devices with different common-mode requirements, at the cost of needing DC-balanced data and adding a component in the signal path. For a backplane traversal, the connector itself is a significant impedance discontinuity and a source of skew and loss, so I'd focus on maintaining a consistent differential impedance through the connector footprint, minimizing stub length, and ensuring the reference plane is continuous across the connector boundary. Termination is usually internal to the transceiver (on-die termination), so the board-level concern is more about not adding unnecessary series or shunt elements that would disturb the channel's impedance. I'd verify the channel with a simulation that includes the connector model and the package, and then confirm on hardware with eye-diagram or bit-error-rate measurements at the receiver. The coupling decision, if I have a choice, comes down to whether the two ends share a common ground reference and compatible common-mode ranges — if they do, DC coupling is simpler and avoids the DC-balance constraint; if not, AC coupling with a defined DC-balanced protocol is the safer path.
**Possible follow-ups:** What would you check in the channel simulation to decide whether the connector's discontinuity is acceptable? If the link works at low line rate but fails at full rate, what would that tell you about the coupling or termination choices?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?
**Answer:** I'd treat this as a teaching moment rather than a confrontation, because the engineer's reasoning isn't unreasonable on its face — it's just incomplete. The issue with an unsynchronized signal crossing domains isn't whether it's "stable long enough" in the typical case; it's that the receiving flop's setup and hold window can be violated when the signal transitions near the clock edge, and the result is a metastable output that can resolve to either value, or propagate an inconsistent value into downstream logic. "Stable long enough" describes the intended behavior, not the worst-case timing relationship, and metastability is a probabilistic failure that may not show up in simulation or even in a short lab run. I'd explain this concretely, ideally with a simple diagram of the setup/hold window and what happens when the transition lands inside it, and then walk through the standard fix: a two-flop synchronizer for a single-bit level signal, or a handshake or FIFO for a multi-bit bus, depending on what the signal actually is. I'd ask the engineer to think about what the signal's purpose is — if it's a level that's sampled, a synchronizer is enough; if it's a pulse or a multi-bit value, the approach differs. The goal is for them to arrive at the correct solution themselves, so it sticks. I'd also make sure the review process catches this class of issue systematically, for example by requiring CDC checks in the tool flow or a checklist item, so it's not dependent on someone noticing it in review. If the engineer pushed back, I'd offer to look at it together on the bench or in a CDC analysis tool, because seeing the tool flag the path is often more convincing than an argument.
**Possible follow-ups:** How would you handle it if the engineer's manager felt you were being too harsh in the review? What would you do if the same class of issue appeared in another engineer's design a few weeks later?
