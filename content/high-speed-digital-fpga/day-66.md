# high-speed-digital-fpga — Day 66

## Q1: How would you approach designing the power-up and configuration sequence for an FPGA that loads its bitstream from external flash, when the flash device itself has a non-trivial access latency and the board may be power-cycled rapidly?
**Answer:** The core issue is that configuration is a multi-stage handshake, not a single event, and each stage has its own timing dependency. I'd start by mapping the sequence explicitly: power rails come up and stabilize, the FPGA releases its internal power-on reset, the configuration controller begins reading from flash, and only then does the device assert its done/ready signal. The flash access latency matters because the configuration controller has a bounded window in which it expects valid data — if the flash needs a long wake-up or read latency after power-up, the controller can time out or read garbage. So I'd verify the flash's power-up-to-ready time against the FPGA's configuration timing budget, and if there's a mismatch, either add a deliberate delay before configuration starts or use a flash with a faster ready time. For rapid power-cycling, the real risk is that the rails don't fully discharge between cycles, so the FPGA or flash may come up in an indeterminate state — I'd check the discharge time constants of the bulk capacitance and consider a supervisor/reset IC that holds the FPGA in reset until all rails are valid and stable, rather than relying on each device's internal POR. I'd also make sure the configuration mode pins are strapped correctly and not floating, since a marginal strap can cause the device to enter the wrong configuration mode intermittently. Finally, I'd validate the whole sequence on the bench with a programmable supply that can ramp and cycle the rails at the extremes of the specified rate, and capture the configuration pins with a scope to confirm the handshake completes cleanly every time.
**Possible follow-ups:** How would you decide between a supervisor IC and relying on the FPGA's internal POR? What would you check first if configuration succeeds on a slow power ramp but fails on a fast one?

## Q2: How would you approach debugging an FPGA design where the timing analysis reports all constraints are met, but the design fails in hardware only at the maximum specified junction temperature?
**Answer:** When static timing analysis passes but hardware fails hot, the first thing I'd question is whether the analysis is actually modeling the same conditions the silicon sees. Timing analysis uses characterized delay models at specific corners, and if the design was only signed off at a nominal or room-temperature corner, the hot corner may not have been covered — delay increases with temperature for most process nodes, so a path that just barely meets timing at nominal can fail hot. I'd re-run timing analysis explicitly at the worst-case hot corner and look for paths with small positive slack, especially ones that cross clock domains or go through long combinational logic. Beyond that, I'd consider effects that static analysis doesn't capture well: on-die variation, clock tree skew that shifts with temperature, and I/O timing that depends on the external device's behavior at temperature. I'd also check whether the failure is actually a timing issue at all — thermal failures can come from a marginal power supply (regulator drift, increased IR drop), a solder joint or connector that opens when the board expands, or a reference clock that drifts out of the PLL's lock range. My approach would be to instrument the design with a way to observe internal state — either a logic analyzer core or spare debug pins — and reproduce the failure in a thermal chamber while monitoring the clock, the rails, and the failing signal simultaneously. That usually separates a genuine timing margin problem from a power or mechanical one.
**Possible follow-ups:** How would you distinguish a setup violation from a hold violation when the failure only appears hot? What role does the clock tree play in temperature-dependent timing failures?

## Q3: How would you approach designing the return-current path for a high-speed digital board where a signal transitions between two reference planes (e.g., from a ground plane to a power plane) on its way through a via?
**Answer:** The governing principle is that every signal current returns to its source through the path of least impedance, and at high frequency that return current flows in the reference plane directly beneath the trace. When a signal via passes through a plane transition — say the trace references ground on one layer and a power plane on another — the return current has to jump between those two planes, and if there's no low-impedance path for it to do so, it will find a long, inductive detour that radiates and creates ground bounce. The standard fix is to place a stitching capacitor (or a cluster of them) close to the signal via, connecting the two reference planes so the return current has a short, low-inductance path across the transition. The capacitor value isn't the critical parameter — the loop inductance of the capacitor's mounting is, so I'd use small-body, low-ESL capacitors placed as close to the via as physically possible, often on both sides of the board. For a ground-to-ground transition there's no problem, since the planes are already connected. For ground-to-power, I'd also consider whether the plane pair can be swapped in the stack-up so the signal references the same net throughout, which eliminates the transition entirely. I'd verify the design by identifying every signal via that changes reference planes and confirming each has an adjacent stitching capacitor, then checking the plane pair spacing and the capacitor placement in the layout review before the board is fabricated.
**Possible follow-ups:** How would you decide how many stitching capacitors are needed for a given via transition? What happens to the return current if the two planes are at different DC potentials?

## Q4: How would you approach designing the clock domain crossing for a multi-bit counter value that is continuously incrementing in a fast domain (e.g., 250 MHz) and must be sampled by a slower domain (e.g., 50 MHz) for display or logging, where the sampled value must always be a coherent snapshot and never a corrupted mix of bits?
**Answer:** The key insight is that a free-running multi-bit counter can't be crossed with a simple two-flop synchronizer per bit, because the bits don't all change at the same instant — a synchronizer on each bit can capture a mix of old and new values, producing a value that never actually existed. The clean solution is a handshake or a gray-code scheme. For a continuously incrementing counter, gray coding is elegant: if the counter is converted to gray code before crossing, only one bit changes per increment, so a synchronizer on each bit can only ever capture either the old or the new value, never a corrupted intermediate. The receiving domain synchronizes the gray-coded value, then converts back to binary. The trade-off is that gray coding only works cleanly for counters that increment by one; if the counter jumps or decrements, the single-bit-change property is lost. For a general multi-bit value that changes arbitrarily, I'd use a handshake: the source domain asserts a "data valid" signal, the destination synchronizes that signal, captures the data, and asserts an acknowledge that the source synchronizes back before updating the value again. This guarantees the destination always sees a stable, coherent word. For a display or logging application where latency isn't critical, the handshake is the safer, more general choice; gray coding is preferable when the value is a simple counter and you want minimal latency and logic.
**Possible follow-ups:** What's the maximum safe counter width for a gray-code crossing before the synchronizer latency becomes a problem? How would you handle a counter that must both increment and be reset from the slow domain?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?
**Answer:** I'd treat this as a teaching moment rather than a confrontation, because the engineer's reasoning isn't unreasonable on its face — it's just missing the failure mode. My first move would be to ask them to walk me through the timing: how long is the signal stable relative to the destination clock period, and what happens if the signal changes during the setup/hold window of the destination flop? The goal is to get them to see that "stable long enough" is a probabilistic argument, not a guarantee, and that metastability is a real physical phenomenon that can propagate unpredictably. I'd explain that even a signal that changes rarely can violate setup/hold at the moment it does change, and the resulting metastable output can resolve to either value or oscillate, corrupting downstream logic in ways that are hard to reproduce. Then I'd move to the fix: for a single-bit control signal, a two-flop synchronizer is the standard, low-cost solution, and for a multi-bit bus, a handshake or gray coding is needed. I'd frame it as "the synchronizer costs two flops and removes an entire class of intermittent bugs" — making the cost-benefit concrete. If the engineer pushed back, I'd suggest we add the synchronizer and then run the design through a CDC lint tool to catch any other unsynchronized crossings, turning the review into a broader improvement rather than a single correction. The tone matters: I want them to leave the review understanding *why*, not just complying.
**Possible follow-ups:** How would you verify that a CDC fix actually resolves the issue if the original failure was intermittent? What would you do if the engineer's design had already been fabricated and the fix required a respin?
