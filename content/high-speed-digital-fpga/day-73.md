# high-speed-digital-fpga — Day 73

## Q1: How would you approach designing the clock domain crossing for a multi-bit Gray-coded counter value that increments continuously in a fast domain (e.g., 250 MHz) and must be sampled by a slower domain (e.g., 50 MHz) for logging, where the sampled value must always be a coherent snapshot and never a corrupted mix of bits?

**Answer:** The key insight is that a Gray code guarantees only one bit changes per increment, so a multi-bit value can be safely sampled across an asynchronous boundary without a handshake — but only if the receiving domain samples a value that is stable for at least one full destination clock period plus synchronizer latency. The standard approach is: (1) generate the counter in binary in the source domain, (2) convert to Gray code combinationally, (3) register the Gray value in the source domain so it is stable for a full source clock cycle, (4) pass each Gray bit through a two-flop synchronizer in the destination domain, and (5) convert back to binary in the destination domain. The critical constraint is that the source clock must be slow enough relative to the destination that the Gray value is stable for at least one destination clock period — otherwise even a single-bit change can be captured mid-transition and produce a value that never existed. If the source is faster than the destination, you must either divide the source clock down before the Gray conversion, or add a "data valid" handshake. I would also verify the design with a formal CDC checker and constrain the synchronizer flops with the appropriate `set_false_path` or `set_max_delay -datapath_only` so the tool does not try to time the crossing. A common mistake is to Gray-code the counter but forget to register it in the source domain first, which reintroduces the multi-bit transition problem.

**Possible follow-ups:**
- What happens if the source and destination clocks are very close in frequency, so the Gray value is only stable for a fraction of a destination clock period?
- How would you verify this CDC in simulation, given that RTL simulation cannot model metastability?

## Q2: How would you approach debugging an FPGA design where the DDR3 memory interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** A failure that appears only after thermal soak points to a timing margin issue that is being consumed by temperature-dependent delay shifts, not a functional bug. My first step is to characterize the failure: is it a specific address range, a specific data pattern, or random? Does it correlate with a particular bank or a particular byte lane? That narrows whether it is a data-path timing issue or an address/command issue. Next, I would instrument the design to log the failing transactions and the temperature at failure, and if the device supports it, read back the calibration codes (write leveling, read gate training, read/write DQS-to-DQ delays) at cold and at the failure temperature. If the calibration codes drift significantly with temperature, the issue is likely that the calibration was performed once at power-up and the optimum sampling point has moved. The fix is usually to re-run calibration periodically or to add temperature-compensated delay adjustments. I would also check the board-level factors: is the VREF stable over temperature, is the termination (ODT) correct, and is the power rail within spec at temperature? A common root cause is that the calibration was done at a benign corner and the design has no margin at the hot corner. The right long-term fix is to add margin by design — either by tightening the PCB layout (length matching, reference plane integrity) or by adding a periodic recalibration routine.

**Possible follow-ups:**
- How would you determine whether the drift is in the FPGA's I/O delays or in the DRAM's internal timing?
- What would you change in the calibration algorithm to make it robust across temperature without a full recalibration?

## Q3: How would you approach designing the return-current path for a high-speed digital board where a signal transitions between two reference planes (e.g., from a ground plane to a power plane) on its way through a via?

**Answer:** The return current for a high-speed signal follows the path of least impedance, which at high frequency means it flows on the reference plane directly beneath the trace. When the signal via transitions from a layer referenced to ground to a layer referenced to a power plane, the return current must also transition — and if there is no low-impedance path between those two planes near the via, the return current is forced to take a long detour, creating a large loop area that radiates and causes signal integrity problems. The standard mitigation is to place a stitching capacitor (or a set of them) close to the signal via, connecting the two reference planes. The capacitor provides a low-impedance path for the return current at the frequencies of interest. The value and placement matter: the capacitor must be close enough that the loop area is small relative to the signal's rise time, and its self-resonant frequency must be above the signal's highest significant frequency component. For very high-speed signals, a single 100 nF capacitor may not be enough — a small-value, low-inductance capacitor (e.g., 10 nF in an 0402 or 0201 package) placed within a few millimeters of the via is often more effective. I would also consider whether the plane transition can be avoided entirely by routing the signal on layers referenced to the same plane, or by using a ground-referenced via transition. In the stack-up design phase, I would try to keep high-speed signals referenced to ground and only transition between ground-referenced layers.

**Possible follow-ups:**
- How would you decide how many stitching capacitors to place and where?
- What is the impact of a return path discontinuity on EMI, and how would you measure it?

## Q4: How would you approach choosing between a global clock network and a regional/banked clock resource for a logic block that only needs to run at a modest rate, when the device's global clock resources are nearly exhausted?

**Answer:** Global clock networks are a scarce resource, and using one for a slow logic block that does not need low skew across the whole die is wasteful. The decision should be driven by the clock's fanout and skew requirements, not by convenience. If the logic block is confined to a single clock region or a small number of regions, a regional or banked clock resource can drive it with adequate skew and much lower power, freeing the global resource for a clock that genuinely needs to reach the entire device (e.g., a system clock or a DDR controller clock). The trade-offs are: regional clocks have limited reach, so if the logic is spread across the die, you may need multiple regional clocks or a global one; regional clocks may have different jitter or phase-noise characteristics; and some device families restrict which pins or MMCM outputs can drive which clock networks. I would start by mapping the clock's fanout — if it stays within one or two clock regions, a regional clock is the right choice. I would also check whether the clock can be generated locally (e.g., from a regional MMCM) rather than routed from a global source, which further reduces global resource usage. The design should be constrained so the tool does not silently promote a regional clock to a global one, and I would verify the clock's skew and latency in the post-implementation timing report.

**Possible follow-ups:**
- What are the risks of using a regional clock for a block that later needs to be expanded across the die?
- How would you verify that the regional clock's skew is acceptable for the logic it drives?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer on your team has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?

**Answer:** This is a classic CDC violation, and the engineer's reasoning — that the signal is stable long enough — is exactly the kind of assumption that works in simulation and fails in hardware, because it ignores metastability and the fact that "long enough" is not a guarantee across process, voltage, and temperature. My approach in the review is to first make sure I understand the signal: is it a single-bit level, a pulse, a multi-bit bus, or a control word? The correct synchronization structure depends on the answer, and the engineer may not have realized that different signal types need different treatments. I would explain the failure mode concretely — a flip-flop sampling an asynchronous input can go metastable, and the resulting value is not guaranteed to resolve to a valid logic level within the setup/hold window, which can propagate as an incorrect value or, worse, as an inconsistent value to downstream logic. I would then walk through the correct approach for their specific signal: a two-flop synchronizer for a single-bit level, a pulse synchronizer or toggle-based handshake for a pulse, a Gray code or handshake for a multi-bit value, and an asynchronous FIFO for a data bus. I would ask them to add the appropriate synchronizer, add the correct timing constraints (e.g., `set_false_path` or `set_max_delay -datapath_only` on the crossing), and run a CDC lint tool to confirm no other unsynchronized crossings exist. The tone matters: this is a teaching moment, not a blame moment, and the goal is to make the engineer internalize the principle so they catch it themselves next time. I would also use it as a trigger to check whether the team's design review checklist includes a CDC check, and if not, add one.

**Possible follow-ups:**
- How would you verify that the synchronizer is actually working, given that RTL simulation cannot model metastability?
- What would you do if the engineer pushed back and said the signal is only used for a non-critical status indication?
