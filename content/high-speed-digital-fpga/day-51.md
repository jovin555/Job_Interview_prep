# high-speed-digital-fpga — Day 51

## Q1: How would you approach debugging an FPGA design where the transceiver link comes up and passes its built-in PRBS checker, but the application-level data occasionally arrives corrupted — and the corruption only appears when the link is running at full line rate?
**Answer:** A PRBS checker passing at full rate tells you the physical layer and the serializer/deserializer are healthy — the pattern is being recovered with adequate margin. So the corruption is almost certainly happening above the SerDes, in the fabric-side logic or in the clocking between the transceiver's recovered clock domain and the application clock domain. I'd structure the debug in layers. First, I'd confirm whether the corruption is in the data path or in the framing/alignment logic: if the link uses a comma or sync-word alignment, a mis-aligned word boundary would corrupt every word after a certain point, which is a very different signature from random bit flips. Second, I'd look at the clock domain crossing between the transceiver's RX user clock and the application logic — if the design assumes a fixed phase relationship that doesn't hold at full rate, or if the FIFO between the two domains is being read before it has enough depth, you'd see intermittent corruption that scales with throughput. Third, I'd check whether the transceiver's internal FIFO or elastic buffer is being overrun or underrun — at full line rate, small clock frequency offsets between the local reference and the recovered clock accumulate faster, and a shallow buffer can slip. I'd instrument with the transceiver's built-in eye scan and error counters, and I'd also add a fabric-side checker that compares a known pattern at the application interface, not just at the SerDes, so I can localize whether the corruption is introduced before or after the CDC. The key discipline is to bisect the path: PRBS at the SerDes passes, so move the checker one stage up at a time until it fails.
**Possible follow-ups:** How would you distinguish an elastic buffer slip from a genuine bit error using the transceiver's status registers? What would you change in the CDC if you found the corruption was a phase-related issue that only manifests at full rate?

## Q2: How would you approach designing the reset architecture for a high-speed FPGA design that has multiple clock domains, a DDR memory controller, and transceiver links, where an incomplete or improperly sequenced reset can leave the design in a non-functional state?
**Answer:** Reset architecture in a multi-domain design is really a synchronization and sequencing problem, and getting it wrong produces exactly the kind of "works sometimes, hangs other times" behavior that's painful to debug. My approach starts with a clear reset taxonomy: I'd separate power-on reset, which is asynchronous and must be held until all power rails and the PLL/MMCM are locked, from soft resets that individual blocks may need during operation. The power-on reset needs to be synchronized into each clock domain before it's released — an asynchronous de-assertion is the classic metastability hazard, so I'd use a reset synchronizer per domain that asserts asynchronously but de-asserts synchronously to that domain's clock. Second, I'd define a sequencing order: the MMCM/PLL must be locked before any logic that depends on its output clock is released from reset, and the DDR controller's reset must complete its calibration before the fabric logic that accesses memory is allowed to issue transactions. I'd implement this as a small reset controller — often a state machine clocked by a stable always-on clock — that asserts resets in a defined order and releases them only when the relevant "ready" signals (PLL lock, calibration done, transceiver reset done) are asserted. Third, I'd make sure each domain's reset is stretched to at least a few cycles of its own clock so that all flops in that domain see a clean, wide reset pulse. Finally, I'd document the reset tree and verify it in simulation with the reset released at different times relative to each clock, because the failure modes are timing-dependent and won't show up in a single simulation run.
**Possible follow-ups:** How would you handle a block that needs to be reset during operation without disturbing the rest of the design? What's the risk of using an MMCM's locked signal directly as a reset release without synchronization?

## Q3: How would you approach selecting and configuring the I/O standards and pin assignments for an FPGA bank that must simultaneously support a high-speed differential interface and several single-ended signals at different voltages, given that I/O bank voltage and standard choices are constrained by the bank's VCCO?
**Answer:** The core constraint is that all I/O in a given bank share a common VCCO, so the first thing I'd do is group signals by their required I/O standard and voltage and see whether they can coexist in one bank or need to be split across banks. A high-speed differential interface — say LVDS or a similar standard — typically requires a specific VCCO and may have restrictions on which pins within the bank can be used as differential pairs, because the differential pairs are tied to specific pin pairs and their associated I/O buffers. Single-ended signals at 3.3V cannot share a bank with a differential standard that requires a lower VCCO, so those would have to go to a separate bank. I'd also check the bank's current and simultaneous-switching-output (SSO) limits: even if the voltages are compatible, too many outputs switching at once in one bank can cause ground bounce and violate the bank's SSO budget, so I'd spread high-speed outputs across banks where possible. For the differential pair, I'd confirm the pin pair is a true differential pair in the device's pinout, set the correct I/O standard and any on-die termination or external termination the standard requires, and verify the differential pair's routing on the PCB matches the pin assignment. I'd also check whether any of the single-ended signals are inputs that need to tolerate a voltage higher than VCCO — that requires either a different bank or level shifting, because most FPGA I/O buffers are not 5V-tolerant across all standards. The output of this exercise is a pinout and bank plan that I'd review against the device's I/O banking rules before committing to the PCB layout, because changing banks after layout is expensive.
**Possible follow-ups:** How would you handle a situation where the differential interface and the single-ended signals must be in the same bank due to pinout constraints? What role does the device's I/O bank SSO calculator play in your decision?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?
**Answer:** Timing analysis is only as good as the constraints you feed it, and the most dangerous failures are the ones where the tool reports "timing met" because a path was never constrained or was constrained incorrectly. My approach is to treat constraint completeness as a reviewable artifact, not just a tool input. First, I'd make sure every clock in the design is explicitly created — including generated clocks from MMCMs/PLLs and any clocks coming in from transceivers or external sources — because an unconstrained clock means the paths it drives are not analyzed. Second, I'd review all clock domain crossings and confirm each is either properly constrained with the correct relationship (synchronous, asynchronous, or false path) or handled by a CDC structure that the tool can verify. The trap is using false path or multicycle constraints to silence warnings on paths that actually need to meet timing — that's a constraint bug that hides a real problem. Third, I'd check the I/O timing constraints: input and output delays relative to the clock, based on the external device's timing requirements, because a design can be internally clean but fail at the interface. Fourth, I'd run the tool's unconstrained-path and timing-exception reports and treat any unconstrained path as a defect to be resolved, not ignored. Finally, I'd cross-check the constraints against the design's clocking architecture documentation — if the documentation says there are three clock domains and the constraints only define two, that's a red flag. The goal is to be able to explain, for every path in the design, why it is either timed or intentionally excluded.
**Possible follow-ups:** How would you catch a constraint that is technically present but semantically wrong — for example, a multicycle path that doesn't match the actual data behavior? What's your process for reviewing constraints when inheriting a design from another engineer?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a design where a critical status signal is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?
**Answer:** This is a teaching moment, and how I handle it matters as much as the technical fix, because the engineer needs to understand why the reasoning is unsafe rather than just being told to add a synchronizer. I'd start by acknowledging the observation — the signal may indeed be stable for many cycles in the nominal case, which is probably why it appears to work in simulation and on the bench. Then I'd walk through the actual failure mode: when a signal crosses from one clock domain to another without synchronization, the receiving flop's setup and hold window can be violated, driving it metastable. Metastability doesn't mean the flop outputs a wrong value forever — it means the output is indeterminate for a short time and can resolve to either state, and worse, different destination flops can resolve differently, so a multi-bit signal can be captured in an inconsistent state. The fact that the signal is "stable long enough" in the nominal case doesn't protect against the case where the source signal changes close to the destination clock edge — that's a statistical event that will eventually occur, and in a medical or safety-related context, "eventually" is not acceptable. I'd then work with the engineer to choose the right structure: a two-flop synchronizer for a single-bit level signal, a handshake or FIFO for multi-bit data, or a pulse synchronizer if it's an event. I'd ask them to add the synchronizer, re-run the CDC lint check, and come back to explain the fix in the next review — turning it into a learning loop rather than a correction. Throughout, I'd keep the tone collaborative: the goal is a correct design and an engineer who won't make the same mistake again, not to win the argument.
**Possible follow-ups:** How would you handle it if the engineer pushed back and said the synchronizer adds latency the design can't afford? How would you make sure this class of issue is caught earlier in future reviews — for example, through a CDC lint step in the build flow?
