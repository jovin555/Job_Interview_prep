# high-speed-digital-fpga — Day 71

## Q1: How would you approach designing the clock domain crossing for a multi-bit Gray-coded counter value that increments continuously in a fast domain (e.g., 250 MHz) and must be sampled by a slower domain (e.g., 50 MHz) for logging, where the sampled value must always be a coherent snapshot and never a corrupted mix of bits?

**Answer:** The key insight is that Gray coding exists precisely to make this problem tractable: because only one bit changes per increment, a value captured mid-transition can be off by at most one count, never a scrambled mix of old and new bits. The standard approach is to register the Gray-coded value in the source domain, pass it through a two-flop synchronizer in the destination domain, and then convert back to binary (or leave it Gray if the consumer only needs monotonic ordering). The synchronizer resolves metastability on the single transitioning bit; since the other bits are stable, the worst case is that the destination samples either the pre- or post-increment value — both are valid snapshots. A few practical points matter: the Gray counter must be the *only* thing crossing — never synchronize a binary counter bit-by-bit, because multiple bits can change simultaneously and you can capture an illegal intermediate value. Also, the Gray-to-binary conversion should happen entirely in the destination domain after synchronization, not before. For very wide counters, the synchronizer latency (two destination clock cycles) sets a floor on how "fresh" the snapshot can be, which is usually fine for logging. If the consumer needs a handshake or a "data valid" indication, a toggle-based flag synchronized alongside works well. Finally, I'd constrain the CDC path in the timing tool (set_false_path or set_max_delay with a proper synchronizer attribute) so the tool doesn't try to meet an impossible setup/hold across asynchronous clocks, and I'd run a CDC lint check to confirm the synchronizer is recognized.

**Possible follow-ups:**
- What happens if the Gray counter increments faster than the destination domain can sample it — can you ever miss counts, and does that matter for logging?
- How would you verify in simulation that the synchronizer behaves correctly, given that metastability itself isn't modeled in RTL?

## Q2: How would you approach debugging an FPGA design where the DDR3 memory interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** A failure that appears only after warm-up points strongly toward a temperature-dependent timing or analog margin issue rather than a logic bug, so I'd structure the investigation around that hypothesis. First, I'd confirm the correlation is real and reproducible — run the same traffic pattern cold and hot, log the exact failing address/pattern and the time-to-failure, and check whether it tracks junction temperature or just elapsed time (which would implicate something else, like a slow drift in a power rail). Then I'd separate the physical layer from the controller: re-run the memory's built-in calibration and eye-margin measurement at temperature. If the read/write eye has shrunk, the problem is analog — likely a marginal termination, a reference voltage that drifts, or a clock/data skew that was only just inside the window at room temperature. On the digital side, I'd check whether the failure correlates with a particular traffic pattern (e.g., long bursts, bank interleaving) which would suggest a controller timing parameter rather than the DRAM itself. Practical tools: on-die eye monitoring if the controller supports it, a thermal chamber to sweep temperature while running a memory stress test, and scope/probe access on the clock and DQS lines if the board allows. Common root causes in this scenario are insufficient timing margin in the write-leveling or read-gate training (trained at one temperature, not re-trained), a decoupling network that's marginal at elevated temperature, or a VREF that isn't temperature-compensated. The fix usually involves either re-training periodically, widening the margin by adjusting drive strength/ODT, or improving the power delivery — but I'd confirm the mechanism before changing anything.

**Possible follow-ups:**
- How would you decide whether to re-run calibration periodically at runtime versus fixing the root cause in hardware?
- If the eye margin looks fine at temperature but the failure persists, where would you look next?

## Q3: How would you approach designing the return-current path for a high-speed digital board where a signal transitions between two reference planes (e.g., from a ground plane to a power plane) on its way through a via?

**Answer:** The core principle is that every high-speed signal's return current follows the path of least impedance, which at high frequency means it flows on the reference plane directly beneath (or above) the trace — so when a signal via passes through a plane boundary, the return current has to find a way to get from one reference plane to the other, and if there's no low-inductance path, it will take a long detour that creates a loop, radiates, and degrades signal integrity. The standard mitigation is to place a stitching capacitor (or a cluster of them) close to the signal via, connecting the two reference planes. The capacitor provides a local, low-inductance path for the return current at the frequencies of interest. Placement matters more than value: the cap must be within a fraction of a wavelength of the via, and its own mounting inductance (via length, pad geometry) dominates its impedance at high frequency, so a small-body, low-inductance cap placed right next to the signal via is far better than a large one placed far away. For a ground-to-power transition, the stitching cap also serves as a local decoupling element, which is a bonus. I'd also consider whether the stack-up can be arranged so that high-speed signals reference a single continuous plane for their entire route — that's the cleanest solution and avoids the problem entirely. If a plane transition is unavoidable, I'd keep the number of transitions per net to a minimum, place the stitching caps symmetrically, and verify with a 3D field solver or at least a careful review of the return path for each critical net. On a board with many such transitions, a pattern of stitching caps along the plane boundary is common practice.

**Possible follow-ups:**
- How would you choose the capacitor value and type for the stitching cap, and how does its mounting inductance affect the choice?
- What's the difference in return-path behavior between a signal transitioning ground-to-ground (same net) versus ground-to-power?

## Q4: How would you approach designing the decoupling and bulk capacitance network for an FPGA's transceiver power rails, where the rails see both high-frequency switching noise from the SerDes and slower, larger current transients from the fabric, and you need to verify the network is adequate before committing to the layout?

**Answer:** The transceiver rails are a good example of a power delivery problem that spans a very wide frequency range, so I'd design the network in layers and verify it with an impedance-versus-frequency target rather than picking caps by habit. The starting point is the regulator's specified ripple and transient tolerance, plus the transceiver's own supply-noise spec — that sets the target impedance across frequency. At the highest frequencies (hundreds of MHz and up), the on-die and package capacitance does most of the work, and the board's job is to not make things worse: small, low-inductance caps placed as close to the balls as possible, with short via stubs and minimal loop area. In the mid-band (roughly a few MHz to a few tens of MHz), the bulk and mid-frequency ceramics dominate, and this is where the SerDes switching noise and fabric transients overlap — I'd size these to cover the expected transient current with acceptable voltage droop. At low frequencies, the regulator's control loop and bulk electrolytics or polymer caps handle the slower, larger transients. The verification step is where a lot of designs go wrong: I'd model the network (including the regulator's output impedance, the plane spreading inductance, and the cap mounting inductances) and plot the impedance versus frequency, checking it stays below the target across the band. A 2D or 3D field solver for the plane and via structures gives a much more realistic answer than a simple lumped model. If the impedance peaks above target at some frequency, that's where I'd add or reposition caps. I'd also plan to measure the actual rail noise on the first prototype with a wideband probe, because simulation of PDNs is approximate and the measurement closes the loop.

**Possible follow-ups:**
- How would you measure the rail noise on a prototype without the probe's own loop inductance corrupting the measurement?
- What's the trade-off between adding more bulk capacitance and improving the regulator's transient response?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer on your team has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?

**Answer:** I'd treat this as a teaching moment rather than a confrontation, because the engineer's reasoning isn't unreasonable on its face — it's just incomplete, and the goal is to get them to see why. First, I'd acknowledge the observation: yes, the signal is stable for a long time relative to the clock period, and in simulation it will almost always work. Then I'd walk through the actual failure mode: the receiving flop's setup and hold window is a small fraction of the clock period, and if the signal transitions during that window, the flop can go metastable — its output can be an intermediate voltage, oscillate, or settle to either value, and the settling time is unbounded in theory. The fact that the signal is "stable long enough" doesn't help if the transition happens to land in the aperture; it just makes the failure rare and hard to reproduce, which is worse, not better. I'd explain that the standard fix — a two-flop synchronizer — costs almost nothing in area or latency and reduces the probability of metastability propagating to an acceptably low level. I'd also point out that the timing tool won't catch this for them: without a proper CDC constraint and synchronizer attribute, the tool may report the path as met or ignore it, so passing timing analysis is not evidence of correctness. To make it concrete, I'd ask them to think about what happens at the receiving flop over millions of power-on cycles and temperature variations — the rare event will eventually happen in the field. Then I'd work with them to add the synchronizer, add the appropriate CDC constraint, and run a CDC lint check to confirm the tool recognizes it. The tone throughout is collaborative: the goal is for them to internalize the principle, not just fix this one instance, because they'll encounter the same pattern in many forms.

**Possible follow-ups:**
- How would you handle it if the engineer pushed back and said the synchronizer adds latency that the design can't afford?
- What would you do if you later found other unsynchronized CDC paths in the same design that the review didn't catch?
