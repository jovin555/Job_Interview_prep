# high-speed-digital-fpga — Day 79

## Q1: How would you approach debugging an FPGA design where the transceiver link passes its built-in PRBS checker at the physical layer, but application-level data is occasionally corrupted — and the corruption only appears at full line rate?
**Answer:** The key insight is that a passing PRBS check proves the *physical layer* is healthy — CDR lock, equalization, and bit error rate at the serial level are all fine. So the corruption is almost certainly happening *above* the SerDes, in the fabric-side logic that moves data between the transceiver's parallel interface and the application. I'd work through it in layers. First, confirm the boundary: is the error detectable at the transceiver's user interface (the 32/64-bit parallel word going into the fabric), or only after the application logic has processed it? If the transceiver's own error flags and its internal PRBS are clean but the application sees bad data, the problem is in the fabric path. The "only at full line rate" clue is the strongest signal — it points to a timing or flow-control margin issue that only manifests when the pipeline is saturated. Common culprits: a FIFO or elastic buffer that's being overrun or underrun because the read/write rate relationship wasn't correctly accounted for at line rate; a CDC between the transceiver's recovered clock domain and the fabric clock domain where the synchronizer depth or the FIFO's almost-full/almost-empty thresholds are marginal; or a backpressure/credit scheme that works when there's slack but drops or duplicates a word when the link is saturated. I'd instrument with a fabric-side checker that compares a known pattern end-to-end (not just at the SerDes), capture the first corrupted word, and look at what's happening in the surrounding cycles — FIFO flags, valid/ready handshakes, and the CDC pointers. I'd also check whether the corruption is a single bit, a whole word, or a shifted word, because each points to a different mechanism: single-bit suggests a timing violation on a parallel bus, whole-word suggests a FIFO or handshake issue, shifted suggests a word-alignment or clock-domain issue. Finally, I'd verify the transceiver's parallel interface timing against the fabric clock — at full rate there's no idle time to absorb a marginal setup/hold, so a path that's fine at low rate can fail when the pipeline never drains.
**Possible follow-ups:** How would you distinguish between a FIFO overflow and a CDC synchronization failure as the root cause? What would you change in the design to give yourself more margin at full line rate?

## Q2: How would you approach designing the reset architecture for a high-speed FPGA design that contains multiple clock domains, a DDR memory controller, and high-speed transceiver links, where an improperly sequenced reset can leave the device in a non-functional state?
**Answer:** Reset architecture in a multi-domain design is really a sequencing and synchronization problem, and the failure mode is usually a domain that comes out of reset while its clock or its upstream data source is still unstable. I'd start by classifying every reset by *what it protects*: power-on reset for the whole device, per-domain resets for each clock domain, and functional resets for specific blocks like the DDR controller or a transceiver channel. Then I'd define the dependency order explicitly. The general principle is that a domain should only be released from reset after (a) its clock is stable and locked, (b) any PLL/MMCM it depends on has asserted lock, and (c) any upstream domain that feeds it is already out of reset and producing valid data. For the DDR controller, that means the memory clock and the controller's own PLL must be locked, and the controller's calibration must complete before the rest of the design is allowed to issue transactions — otherwise you get a design that "runs" but reads garbage. For transceivers, the channel reset and the CDR lock must complete before the fabric-side logic starts expecting data. The mechanism I'd use is a reset controller that takes the lock signals and produces a synchronized, sequenced reset release per domain, with each release synchronized into the destination clock domain using a proper reset synchronizer (async assert, sync de-assert). I'd also make sure resets are asserted asynchronously so a domain can be held in reset even if its clock has stopped, but de-asserted synchronously to avoid recovery/removal violations. Finally, I'd make the whole thing observable — status bits that tell you which domains are out of reset and which locks are asserted — because when it fails in the field, the first question is always "which domain didn't come up."
**Possible follow-ups:** How would you handle a domain whose clock is generated by a PLL that itself needs a reset — where does that reset come from? What's the risk of using a single global reset for all domains, and when might that be acceptable?

## Q3: How would you approach designing the clock domain crossing for a multi-bit Gray-coded counter value that increments continuously in a fast domain (e.g., 250 MHz) and must be sampled by a slower domain (e.g., 50 MHz) for logging, where the sampled value must always be a coherent snapshot and never a corrupted mix of bits?
**Answer:** The reason Gray coding is the right tool here is that only one bit changes between consecutive values, so even if the sampling edge lands exactly on a transition, the worst case is that you capture either the old value or the new value — never a value that never existed. That's the property that makes a multi-bit counter safe to cross without a full handshake. The design is: the counter in the fast domain is maintained in Gray code (not binary), and the slow domain samples it through a two-flop synchronizer per bit. Because only one bit is in flight at a time, the synchronizer's metastability resolution can only affect that one bit, and the result is still a valid Gray code. Then the slow domain converts the synchronized Gray value back to binary for logging. The important details: the counter must actually be Gray-coded at the source, not binary-then-converted, because a binary-to-Gray conversion in the fast domain followed by a synchronizer would still be safe, but a binary counter sampled directly would not be. The synchronizer must be a proper two-flop (or three-flop for higher MTBF) synchronizer per bit, with the synchronizer flops placed close together so their clock skew is minimal. I'd also add a small amount of logic to detect if the sampled value is "stale" — for logging, it's often useful to know the sample is coherent but may be one count old. One subtlety: if the counter can wrap, the Gray code must be designed so the wrap is also a single-bit transition, which a standard reflected Gray code handles. Finally, I'd verify the design with a formal CDC check or a CDC lint tool, because this is exactly the kind of structure that looks fine in simulation but fails in hardware if someone later "optimizes" the Gray coding away.
**Possible follow-ups:** What's the MTBF calculation for a two-flop synchronizer, and when would you need a third flop? How would this change if the counter were binary and you couldn't change the source?

## Q4: How would you approach designing the return-current path for a high-speed digital board where a signal transitions between two reference planes (e.g., from a ground plane to a power plane) on its way through a via?
**Answer:** The core principle is that every high-speed signal has a return current that follows the path of least impedance — at high frequency, that's the path of least *inductance*, which means it flows on the reference plane directly beneath (or above) the trace, and it must be able to get from the source's reference plane to the destination's reference plane without a discontinuity. When a signal via transitions from a layer referenced to ground to a layer referenced to a power plane, the return current has to jump from the ground plane to the power plane, and if there's no low-inductance path for it to do that, the return current is forced to take a long, inductive detour — which shows up as increased loop inductance, radiated emissions, and signal integrity degradation (ringing, ground bounce, crosstalk). The standard fix is to place a stitching capacitor (or a set of them) between the two reference planes, located as close as possible to the signal via — ideally within a few millimeters, because the capacitor's job is to provide a local, low-inductance path for the return current to transfer between planes. The capacitor value isn't critical for the high-frequency return path (the capacitor's own ESL dominates), so I'd use a small, low-ESL capacitor (e.g., 0402 or 0201, X7R or better) and place it right next to the via. For a differential pair, the same principle applies but the return current is the complement signal, so the pair's reference plane transition still needs a stitching cap if the pair changes reference planes. I'd also consider whether the transition can be avoided entirely — sometimes a layer change can be routed to keep the same reference plane, which is always better than adding a stitching cap. In the stack-up, I'd try to keep high-speed signals referenced to a single ground plane as much as possible, and if a power plane reference is unavoidable, ensure the power plane is adjacent to a ground plane with good inter-plane capacitance or add the stitching caps. Finally, I'd verify with a 3D field solver or a return-path analysis tool, because the "few millimeters" rule is a guideline and the actual inductance depends on the geometry.
**Possible follow-ups:** How would you decide how many stitching capacitors to place, and where exactly? What's the difference in return-path behavior between a single-ended signal and a differential pair making the same transition?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer on your team has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?
**Answer:** The first thing I'd do is separate the technical issue from the interpersonal one. Technically, this is a classic CDC violation, and the engineer's reasoning — "the signal is stable long enough" — is a common and understandable misconception, because it's true in simulation and often true in the lab, which is exactly what makes it dangerous. The failure mode is metastability: if the signal transitions near the destination clock's setup/hold window, the receiving flop can go metastable, and the probability of that happening is low but non-zero, and it gets worse with temperature, voltage, and process variation. So the design is not "wrong" in the sense of always failing — it's wrong in the sense of having a latent, intermittent failure that will eventually show up in the field. In the review, I'd make this concrete rather than abstract: I'd ask the engineer to walk through what happens if the signal changes exactly at the destination clock edge, and I'd use that to show why "stable long enough" isn't a guarantee — it's a probability argument, and the probability isn't zero. I'd also point out that the fix is cheap: a two-flop synchronizer for a single-bit control signal, or a proper handshake or FIFO for multi-bit data, and that the cost of the fix is far less than the cost of a field failure. The tone matters here — the goal is to teach the principle, not to win the argument, because a junior engineer who understands *why* the rule exists will apply it correctly in the future, whereas one who just follows the rule will make the same mistake in a different form. I'd also make sure the review process catches this systematically — a CDC lint check or a formal CDC verification step in the design flow — so it's not dependent on a senior engineer happening to notice it in a review. And I'd follow up after the review to make sure the fix is implemented and verified, not just agreed to.
**Possible follow-ups:** How would you handle it if the engineer pushed back and said the synchronizer adds latency that the design can't afford? What would you change in the design review process to catch this kind of issue earlier?
