# high-speed-digital-fpga — Day 123

## Q1: How would you approach designing the power-up and reset sequencing for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?

**Answer:** I'd treat this as a dependency-graph problem rather than a single reset line. The first step is to enumerate every domain that has a defined bring-up order — the configuration engine, the PLL/MMCM lock signals, the transceiver quad PLLs and channel PLLs, and the fabric clock domains that depend on them — and write down the "must be true before" relationship for each. From that graph I'd build a small sequencer, either in a CPLD/power-management device or in the FPGA fabric itself once configuration completes, that releases each domain only when its prerequisites are actually satisfied, not just after a fixed delay.

The key discipline is to use *status* signals rather than timers wherever the hardware provides them: configuration done, PLL lock, transceiver calibration done, and any power-good signals from the rails. Timers are a fallback for blocks that don't expose status, and when I do use them I size them from the datasheet worst case with margin, not from typical. I'd also make the reset architecture hierarchical — a global reset that fans out to per-domain reset synchronizers, so each domain's reset is released synchronously to its own clock and the asynchronous-assert/synchronous-deassert rule is respected. That prevents the classic failure where a reset is released asynchronously and a flop comes out of reset in an indeterminate state.

For the transceivers specifically, I'd follow the vendor's recommended sequence for reference clock, quad PLL, and channel bring-up, and I'd gate the fabric-side logic that consumes transceiver data until the link is actually trained, not just until the quad reports ready. Finally, I'd make the whole sequence observable — a status register or a set of debug LEDs that show which stage the sequencer reached — because "configured but non-functional" is exactly the symptom you get when one prerequisite silently never asserts, and you need to see where it stalled.

**Possible follow-ups:**
- How would you handle a PLL that occasionally fails to lock on the first attempt — would you retry, and how would you avoid a retry loop that masks a real hardware problem?
- Where would you put the sequencer if the FPGA fabric itself isn't available until configuration completes?

## Q2: How would you approach debugging an FPGA design where the DDR3 interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** A failure that only appears after warm-up points at something temperature-dependent, and I'd resist the urge to immediately blame the DRAM. The candidates are: timing margin that was always marginal and only crosses the threshold as delays shift with temperature; a power rail whose impedance or regulator behavior degrades as it heats; a reference clock or PLL whose jitter increases with temperature; or a mechanical/thermal issue like a connector or solder joint.

I'd start by making the failure observable. If the design has a built-in memory test, I'd run it continuously in a loop and log which addresses and which data patterns fail — a checkerboard-only failure versus a random failure versus an address-dependent failure each point somewhere different. I'd also add margin measurements rather than pass/fail: if the controller exposes per-bit read/write leveling delays or eye-margin readback, capturing those at cold and at hot tells me whether the margin is shrinking with temperature, which is the signature of a timing problem rather than a hard fault.

In parallel I'd instrument the rails — core, DDR I/O, and the DRAM's own supply — with a scope on a thermal soak, looking for droop or increased ripple as the board heats. I'd also check the reference clock's phase noise or at least its stability at temperature. If the margin readback shows the window closing, the fix is usually to re-run leveling periodically or at temperature, tighten the board's skew matching, or improve the power delivery; if the rails are moving, it's a power problem and no amount of controller tuning will fix it. The important thing is to separate "the DRAM is bad" from "the margin was never there and temperature just exposed it."

**Possible follow-ups:**
- Would you consider re-running write leveling periodically at runtime, and what are the risks of doing that while the system is live?
- How would you distinguish a DRAM die that's genuinely marginal at temperature from a board-level timing margin issue?

## Q3: How would you approach designing the clock domain crossing for a multi-bit control word that is written by a slow serial interface (e.g., 10 MHz SPI) and consumed by a fast logic domain (e.g., 250 MHz), where the word changes infrequently but must never be observed in a partially updated state?

**Answer:** The requirement "never observed partially updated" is the whole problem, and it rules out naively synchronizing each bit with a two-flop synchronizer — that guarantees metastability is contained per bit but says nothing about coherence across bits, so the fast domain could sample a mix of old and new bits during the update.

Because the word changes infrequently and the source is slow, the cleanest approach is a handshake-based transfer. The SPI domain writes the new word into a holding register, then asserts a request toggle. That toggle is synchronized into the fast domain with a two-flop synchronizer, which detects the edge and captures the entire word in one clock — since the word is stable in the source domain well before the toggle arrives, the capture is coherent. The fast domain then asserts an acknowledge toggle, synchronized back, and only then does the SPI domain consider the transfer complete and allowed to write the next value. The cost is a few cycles of latency, which is irrelevant for a control word that changes rarely.

An alternative, if the consumer can tolerate a small latency and I want to avoid the round-trip, is a ping-pong double buffer with a synchronized select signal: the source writes into buffer A, then flips a select bit that is synchronized into the destination, which reads from the newly selected buffer. The destination always reads a complete buffer, never a half-written one. I'd choose between these based on whether the source needs to know the transfer landed (handshake) or can fire-and-forget (ping-pong).

What I would *not* do is rely on "the word changes infrequently, so the odds of catching it mid-update are low" — that's exactly the reasoning that produces a field failure once in ten million cycles. I'd also add a CDC lint/formal check to the flow so the tool flags any unsynchronized multi-bit crossing I might have missed.

**Possible follow-ups:**
- How would you verify this CDC in simulation, given that metastability itself isn't modeled in RTL?
- What changes if the control word is written by a fast domain and consumed by a slow one instead?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?

**Answer:** The core risk is that timing analysis only proves what you told it to prove — an unconstrained or falsely excepted path is simply not checked, and the tool will happily report "all constraints met" for a design that has a hole in it. So my sign-off process is built around proving the *constraint set* is complete, not just that the report is clean.

First, I'd drive constraint coverage from the design itself: every clock must have a create_clock or create_generated_clock, every I/O must have input/output delay, and every asynchronous crossing must be explicitly handled. I'd run the tool's unconstrained-path and unconstrained-endpoint reports and treat any non-empty result as a blocker — those reports are the single best detector of missing constraints. Second, I'd review every timing exception (false path, multicycle, max/min delay) as a design decision with a written justification, because exceptions are where real bugs hide: a false path on a path that actually needs to meet timing is a silent failure. I'd want each exception traceable to a specific reason, ideally with a comment in the constraint file and a reviewer's sign-off.

Third, I'd cross-check with CDC analysis and with formal or structural checks that the clock relationships the constraints assume match the RTL's actual clock structure. Fourth, I'd run the analysis across all PVT corners the device is specified for, not just the nominal one, and confirm the I/O timing is checked against the external device's datasheet numbers rather than assumed. Finally, I'd do a gate-level simulation with back-annotated timing on the critical interfaces as a sanity check — it won't catch everything, but it catches constraint mistakes that let a real violation through. The mindset is: the timing report is only as trustworthy as the constraint file, so the constraint file gets reviewed as carefully as the RTL.

**Possible follow-ups:**
- How would you catch a false-path exception that was added to make a design close but is actually wrong?
- What's your approach when the I/O timing budget doesn't close and you have to negotiate with the external device's timing?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented the data path that captures samples from a high-speed ADC and writes them to DDR memory. During the review, you notice they've sized the capture FIFO from the average throughput rather than the worst-case burst, arguing that "the average rate is well below the memory bandwidth, so it can't overflow." How do you handle this situation?

**Answer:** I'd treat this as a teaching moment rather than a "you're wrong" moment, because the underlying reasoning — average rate is below capacity — is intuitively appealing and the engineer isn't being careless, they're just missing the burst behavior. My goal is to get them to see the failure mode themselves.

I'd start by asking a question rather than making a statement: "Walk me through what happens if the ADC delivers a burst that's faster than the memory controller can absorb for a short window — where does that data go?" That usually surfaces the gap. Then I'd frame the principle: a FIFO's depth is set by the *worst-case* difference between producer and consumer over the longest interval where the producer outruns the consumer, not by the average. The average being below capacity only guarantees the FIFO drains *eventually*; it says nothing about whether it overflows *during* a burst. I'd point out that the memory controller's write buffer is not a substitute — it's sized for its own scheduling needs, not as an extension of the capture FIFO, and relying on it couples two blocks that should be independently correct.

Then I'd move from principle to action: we need to characterize the actual worst-case burst — the ADC's maximum sustained output over the longest backpressure window the memory controller can impose — and size the FIFO (or add flow control back to the ADC, if it supports it) from that number with margin. If the ADC can't be throttled, the FIFO has to absorb the worst case or the design needs a different buffering strategy. I'd ask the engineer to bring the burst analysis to the next review so they own the fix and the reasoning. The tone throughout is collaborative — the review's job is to catch this before it's a field failure, and the engineer should leave understanding *why*, not just *what* to change.

**Possible follow-ups:**
- How would you handle it if the engineer pushed back and said the burst analysis is too conservative and would cost too much BRAM?
- What would you do if this same average-versus-worst-case mistake showed up again in a later review from the same engineer?
