# high-speed-digital-fpga — Day 53

## Q1: How would you approach designing an FPGA configuration and boot scheme for a device that must load its bitstream from external flash, where the board may be power-cycled rapidly and the flash device itself has a non-trivial access latency?
**Answer:** The core issue is that configuration is a state machine with its own timing dependencies, and rapid power cycling can catch the device mid-configuration or leave the flash in an indeterminate state. I'd start by separating the problem into three concerns: power-rail stability, flash readiness, and the FPGA's own configuration controller behavior.

First, power-rail stability. The FPGA's configuration logic has a minimum voltage threshold below which it will not reliably read the bitstream. If the rails have not fully discharged between power cycles — which is common when the bulk capacitance is large and the off-time is short — the device may see a brownout condition rather than a clean power-on reset. I'd verify that the POR circuit actually asserts reset until all rails are above their thresholds and stable, and that the reset is held long enough for the internal configuration state machine to initialize. A common mistake is relying on a simple RC delay that doesn't account for the slowest-ramping rail.

Second, flash readiness. Many serial flash devices require a power-on delay before they will respond to commands, and some have internal initialization that takes milliseconds. If the FPGA's configuration controller starts clocking the flash before it is ready, the first few bits will be garbage or the flash will not respond at all. I'd check the flash datasheet for the minimum power-on-to-first-command time and ensure the FPGA's configuration start is gated on either a fixed delay that exceeds that, or a flash-ready signal if the device provides one. For rapid power cycling, I'd also consider whether the flash itself needs a full discharge — some devices latch up or enter an undefined state if power is cycled too quickly.

Third, the FPGA configuration controller. Most modern FPGAs have a configuration state machine that can be configured for different modes (master serial, slave serial, master SPI, etc.). In master SPI mode, the FPGA drives the clock and chip select, so it controls the timing. The key parameters are the configuration clock frequency and the initial delay before the first clock edge. If the clock is too fast for the flash's access time at the current voltage and temperature, the bitstream will be corrupted. I'd set the configuration clock conservatively — well within the flash's specified access time — and verify that the FPGA's internal configuration logic meets its own setup/hold requirements relative to that clock.

For rapid power cycling specifically, I'd add a supervisor circuit that holds the FPGA in reset until the rails have been stable for a minimum period, and I'd ensure the flash's chip select is deasserted during power-down so it doesn't see partial commands. If the application requires very fast power cycling, I'd consider a configuration scheme that can detect a failed configuration and retry, rather than assuming the first attempt will always succeed.

## Q2: How would you approach debugging an FPGA design where the device configures successfully and runs correctly for a period of time, but then the configuration appears to be lost — the device stops responding and requires a reconfiguration to recover?
**Answer:** This is a classic "configuration memory corruption" or "configuration loss" scenario, and the first step is to determine whether the device actually lost its configuration or whether it entered a state where it stopped responding for another reason. The distinction matters because the debug approach is completely different.

I'd start by checking the device's configuration status pins. Most FPGAs have a DONE pin and an INIT pin, and some have a dedicated configuration error pin. If DONE deasserts, the device has genuinely lost its configuration — either due to a configuration memory upset, a power glitch, or an internal error. If DONE stays asserted but the device stops responding, the issue is more likely in the user logic or the clocking, not the configuration itself.

If DONE deasserts, I'd look at three main causes. First, power integrity. A transient droop on the core voltage — even a few tens of millivolts below the minimum — can cause the configuration memory to lose state or the device to reset. I'd scope the core rail with a high-bandwidth probe and look for droops that correlate with the failure. The trigger should be set on the failure event, not on a periodic timebase, because the droop may be very narrow. I'd also check the auxiliary and I/O rails, since some devices monitor those as part of their internal power-good logic.

Second, single-event upsets. If the device is in a radiation environment — or even at high altitude — configuration memory bits can flip. Most FPGAs have built-in error detection and correction for configuration memory, but the correction may be limited or may not cover all memory. I'd check whether the device's error correction status register shows any corrected or uncorrected errors. If the device supports partial reconfiguration or scrubbing, I'd consider whether a scrubber is needed to periodically refresh the configuration memory.

Third, thermal effects. If the failure correlates with temperature — for example, it only happens after the device has been running for a while and the board has heated up — the issue may be a marginal timing path that fails at high temperature, or a power supply that drifts out of regulation as it heats. I'd monitor the device temperature and the rail voltages over time and look for correlation with the failure.

If DONE stays asserted but the device stops responding, I'd look at the clocking first. A PLL that loses lock — due to a reference clock glitch, a power supply droop on the PLL rail, or a temperature-related drift — can cause the entire design to stop. I'd check the PLL lock signal and the reference clock integrity. I'd also check for any external component that could be causing the issue — for example, a reset signal that is being asserted by an external supervisor, or an interrupt that is being held low.

In all cases, I'd try to reproduce the failure in a controlled way — for example, by cycling the power, varying the temperature, or injecting a known disturbance — so that I can correlate the failure with a specific event. Without a reproducible trigger, the debug becomes guesswork.

**Possible follow-ups:**
- How would you distinguish between a configuration memory upset and a power supply droop if both could cause DONE to deassert?
- What design techniques would you use to make the configuration more robust against transient power glitches?

## Q3: How would you approach designing a high-speed data path in an FPGA that must perform a real-time channelizer — splitting a wideband input into multiple narrowband channels — where the input sample rate is 1 GSPS and the FPGA fabric clock is limited to 250 MHz?
**Answer:** The core challenge is that the input sample rate exceeds the fabric clock by a factor of four, so the first step is always some form of serial-to-parallel conversion or polyphase decomposition to bring the data rate down to something the fabric can process. For a channelizer, the natural approach is a polyphase filter bank, which is essentially a DFT-based channelizer implemented as a bank of filters followed by a DFT.

The first decision is the channelization scheme. If the channels are evenly spaced and the input is a single wideband signal, a polyphase filter bank is the standard approach. The input is split into P phases, where P is the number of parallel samples per fabric clock cycle. At 1 GSPS with a 250 MHz fabric clock, P = 4. Each phase feeds a subfilter, and the outputs are combined in a DFT to produce the channel outputs. The DFT can be implemented as an FFT if the number of channels is a power of two, which is usually the case.

The second decision is the filter design. The prototype lowpass filter determines the channel shape and the stopband attenuation. The filter length must be long enough to meet the stopband requirement, but every additional tap adds latency and resource usage. I'd start with a windowed-sinc design and then optimize for the specific channel spacing and attenuation requirements. The polyphase decomposition means that each subfilter operates at the lower fabric clock rate, so the filter can be implemented with DSP slices running at 250 MHz, which is well within their capability.

The third decision is the FFT architecture. For a real-time channelizer, a pipelined streaming FFT is usually the right choice — it accepts one sample per clock and produces one output per clock after a fixed latency. The FFT size determines the number of channels. If the FFT is too large to fit in a single FPGA, or if the latency is too high, a partial FFT or a two-stage approach may be needed. I'd also consider whether the application needs all channels simultaneously or only a subset — if only a subset, a channelizer that extracts only the needed channels can be much more efficient.

The fourth decision is the data path width and buffering. At 1 GSPS input, the data rate is high, and the channelizer output may be at a much lower rate per channel but with many channels. I'd carefully size the FIFOs between stages to absorb burstiness without adding excessive latency. I'd also consider whether the output needs to be packetized or streamed, and whether any backpressure is needed.

Finally, I'd verify the design with a combination of simulation and hardware testing. Simulation would use a known input signal — for example, a sum of sinusoids at known frequencies — and verify that the channelizer correctly separates them. Hardware testing would use a signal generator and a spectrum analyzer to verify the channel isolation and dynamic range.

- What trade-offs would you consider between a polyphase filter bank and a direct DFT-based channelizer?

## Q4: How would you approach debugging an FPGA design where the timing analysis reports that all constraints are met, but the design fails in hardware only when the device is operated at the maximum specified junction temperature?
**Answer:** This is a classic case where the static timing analysis is not capturing the full picture. Timing analysis is only as good as the constraints and the models it uses, and there are several reasons why a design can pass timing analysis but fail at high temperature.

The first thing I'd check is whether the timing analysis was run at the correct operating conditions. Most FPGA tools allow you to specify the speed grade and the operating temperature range, and the analysis uses derating factors to account for temperature and voltage. If the analysis was run at room temperature but the device is operated at maximum junction temperature, the actual delays will be longer than the analysis predicted. I'd re-run the timing analysis at the worst-case temperature and voltage corner — typically the slow-slow corner — and see if any paths fail. If they do, the issue is simply that the analysis was not run at the correct corner.

The second thing I'd check is whether the constraints are complete. Missing constraints are a common cause of "timing passes but hardware fails." For example, if a clock domain crossing is not constrained, the tool may not analyze it at all, and the design may have a metastability issue that only manifests at certain temperatures. I'd review the constraint file for completeness — every clock should have a create_clock constraint, every generated clock should have a create_generated_clock constraint, every I/O should have input/output delay constraints, and every clock domain crossing should have either a set_false_path or a set_max_delay constraint as appropriate. I'd also check for any set_false_path or set_multicycle_path constraints that may be too aggressive — if a path is falsely declared as false, the tool will not analyze it, and it may fail in hardware.

The third thing I'd check is whether the timing analysis is accounting for all the effects that matter at high temperature. For example, on-die variation, aging, and voltage droop can all affect timing, and some tools have options to include these effects. If the design is marginal at the slow-slow corner, even a small additional delay from these effects could cause a failure.

The fourth thing I'd check is whether the failure is actually a timing failure or something else. At high temperature, other things can go wrong — for example, a PLL may lose lock, a power supply may drift out of regulation, or a component may change behavior. I'd use the device's internal temperature sensor and any available debug tools to correlate the failure with temperature, and I'd check the power rails and clock signals at the point of failure.

If the issue is a genuine timing failure, the fix is to either improve the timing — by adding pipeline stages, reducing logic depth, or changing the placement — or to relax the constraints if the design has margin that the analysis is not capturing. I'd also consider whether the design needs to be re-analyzed with more accurate models, such as post-layout timing analysis with back-annotated delays.

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer on your team has implemented a clock domain crossing for a multi-bit data bus using a simple two-flop synchronizer on each bit, arguing that "the data is stable long enough that it will always be captured correctly." How do you handle this situation?
**Answer:** This is a situation where the engineer has misunderstood the purpose of a synchronizer and the nature of multi-bit CDC. I'd handle it by first making sure I understand their reasoning, then explaining why the approach is unsafe, and then working with them to implement a correct solution.

The first step is to ask questions rather than immediately correct. I'd ask the engineer to walk me through their reasoning — why they believe the data is stable long enough, and what they think happens if the data changes during the synchronizer's setup/hold window. This serves two purposes: it shows respect for their work, and it helps me understand whether they have a misconception about metastability, about the relationship between the source and destination clocks, or about the data itself.

The second step is to explain the fundamental issue. A two-flop synchronizer on each bit of a multi-bit bus does not guarantee that all bits are captured in the same destination clock cycle. Even if the data is stable for many source clock cycles, the individual bits can still be captured on different destination clock edges due to routing skew, differences in metastability resolution time, and the fact that the synchronizer only guarantees that each bit is stable at the destination flop's output — not that all bits are stable at the same time. If the destination logic reads the bus while some bits have updated and others have not, it will see a value that never existed in the source domain. This is a classic multi-bit CDC bug, and it can cause intermittent, difficult-to-reproduce failures.

The third step is to propose a correct solution. The right approach depends on the nature of the data. If the data is a control word that changes infrequently and the destination can tolerate a delay, a handshake-based scheme — where the source asserts a valid signal, the destination acknowledges, and the data is only captured when the handshake completes — is the safest. If the data is a stream that changes frequently and the destination needs a new value every cycle, a FIFO-based CDC is the right choice. If the data is a counter or a value that changes monotonically, a Gray code encoding can be used, where only one bit changes at a time, so a simple synchronizer on each bit is safe. The key is to choose a scheme that matches the data's behavior and the destination's requirements.

The fourth step is to make the review a learning opportunity rather than a criticism. I'd explain that this is a common mistake — even experienced engineers sometimes underestimate the subtleties of CDC — and that the goal of the review is to catch these issues before they become hardware bugs. I'd ask the engineer to update the design and present it again, and I'd offer to review it with them before the next meeting.

Finally, I'd consider whether the team needs additional training or resources on CDC. If this is a recurring issue, it may be worth adding a CDC checklist to the design review process, or providing a reference design that engineers can use as a starting point.

**Possible follow-ups:**
- How would you verify that a CDC scheme is correct, given that CDC bugs are often intermittent and difficult to reproduce in simulation?
- What would you do if the engineer disagreed with your assessment and insisted that their approach was correct?
