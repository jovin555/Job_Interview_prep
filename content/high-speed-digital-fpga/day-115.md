# high-speed-digital-fpga — Day 115

## Q1: How would you approach designing the power-up and configuration sequence for an FPGA that loads its bitstream from external flash, where the flash device has a non-trivial wake-up latency and the board may be power-cycled rapidly?
**Answer:** The core problem is that the FPGA's configuration engine starts driving the flash interface as soon as its own configuration-controlling rails are valid, but the flash may not yet be ready to accept commands after a fast power cycle. I'd treat this as a sequencing and handshaking problem rather than a timing-margin problem. First, define the power rail order from the device datasheet — typically core, then auxiliary, then I/O — and enforce it with a sequencer or supervisor so the FPGA never begins configuration before its own rails are stable. Second, gate the FPGA's configuration start on a flash-ready signal: either the flash's own ready/busy or reset pin, or a deliberate delay derived from the flash's worst-case wake-up time plus margin. Third, handle the rapid power-cycle case explicitly: if the board can be re-powered before the flash's internal state machine has fully reset, the flash may return garbage or NAK the first read. A common mitigation is to hold the flash in reset during the entire power-down and power-up window, and to add a supervisor that prevents the FPGA from releasing configuration until the flash's reset has been de-asserted for the specified wake-up time. I'd also verify the sequence with a power-cycling test that sweeps the off-time across the boundary — very short, marginal, and long — because that's where the failure lives. On the FPGA side, I'd make sure the configuration engine's error output is monitored so a failed read triggers a retry rather than a silent hang.
**Possible follow-ups:** How would you decide whether to add a dedicated supervisor IC versus using the FPGA's own power-good inputs? What would you do if the flash's wake-up time is not well characterized by the vendor?

## Q2: How would you approach debugging an FPGA design where the transceiver link passes its built-in PRBS checker at the physical layer, but application-level data is occasionally corrupted, and the corruption only appears at full line rate?
**Answer:** A passing PRBS check tells me the SerDes analog front end, CDR, and equalization are working — it does not tell me the digital path above the PMA is correct. So I'd split the problem: physical layer is proven, so the fault is in the PCS, the user logic, or the clocking between them. First, I'd confirm whether the corruption is a bit error or a word/framing error — a single flipped bit points to a CDC or FIFO issue, while a shifted or dropped word points to framing, comma alignment, or a FIFO overflow/underflow. Second, I'd check the elastic buffer between the recovered clock and the fabric clock: at full line rate the rate-matching FIFO has the least margin, and a small ppm offset between the reference and the incoming link can cause periodic overflow that only shows up under sustained traffic. Third, I'd look at the CDC between the transceiver's parallel output and the user logic — if the design assumes the transceiver's clock and the fabric clock are synchronous when they are not, occasional metastability will corrupt data only when the phase relationship drifts. Fourth, I'd instrument with the transceiver's built-in error counters and eye monitor at full rate, and add a PRBS check *after* the PCS (on the parallel side) to localize whether corruption happens before or after the gearbox. The fact that it only appears at full line rate strongly suggests a rate-matching or CDC margin issue rather than an analog problem.
**Possible follow-ups:** How would you distinguish a FIFO overflow from a CDC metastability event using only the transceiver's status registers? What changes if the corruption is bursty rather than single-bit?

## Q3: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?
**Answer:** The dangerous failure mode is a design that closes timing because the constraints are wrong, not because the logic is fast enough — so I treat constraint verification as a separate review activity from timing closure. My approach has four layers. First, completeness: cross-check every clock in the design against the constraint file, and confirm every clock domain crossing has either a proper synchronizer with a corresponding constraint or a documented exception. I'd use the tool's CDC report and unconstrained-path report as the starting checklist, not the answer. Second, correctness of exceptions: every false path and multicycle path should be justified in writing — why the path is genuinely asynchronous or genuinely multicycle — and reviewed by someone other than the author. A false path on a real synchronous path is the classic silent killer. Third, I/O timing: verify that input and output delays are derived from the actual external device's datasheet (setup/hold, clock-to-out, board skew) rather than guessed, and that the reference clock for each interface is the one the external device actually uses. Fourth, independent confirmation: run the design at multiple PVT corners, and where possible compare the static timing report against a gate-level simulation with back-annotated delays for the critical interfaces. I'd also insist on a constraint review sign-off as a gate item, because constraints are code and deserve the same review rigor as RTL.
**Possible follow-ups:** How would you catch a multicycle path constraint that is too aggressive for the actual data pattern? What role does the CDC report play versus manual review?

## Q4: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?
**Answer:** A via through a thick backplane leaves an unused portion — the stub — that acts as an open-circuited transmission line and creates a resonance that shows up as insertion-loss notches and return-loss peaks at frequencies determined by the stub length and the board's effective dielectric constant. The first lever is layout: use blind or buried vias so the via only spans the layers it needs to connect, which eliminates the stub entirely. If the stack-up and fabrication budget don't allow that, the next lever is back-drilling — removing the unused barrel after plating — which shortens the stub to whatever remains between the deepest used layer and the drill depth. The third lever is to move the transition: route the signal on layers that minimize the stub length, or use a via structure with a smaller drill and pad to reduce the stub's capacitance. On the simulation side, I'd extract the via with a 3D field solver and include it in the channel's S-parameter model, then check the channel's insertion loss and eye at the target rate with the stub included — a stub that looks harmless at 5 Gbps can be fatal at 10 or 25 Gbps. If back-drilling is not possible and the stub resonance falls inside the signal's bandwidth, I'd consider whether the link's equalization (Tx pre-emphasis, Rx CTLE/DFE) can compensate, but I'd treat that as a mitigation of last resort rather than a design choice.
**Possible follow-ups:** How would you decide the maximum acceptable stub length for a given line rate? What are the manufacturing risks of back-drilling that you'd need to control?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?
**Answer:** I'd treat this as a review-quality issue first and a technical issue second, and I'd handle it without embarrassing the engineer in front of the team. My first move is to ask the engineer to walk me through each exception and the reasoning behind it — not to challenge them, but to make the justification explicit. Some of the exceptions may well be legitimate; the problem is that "it closes with the exceptions" is not the same as "the exceptions are correct," and the review needs to separate those two claims. For each exception I'd ask three questions: is the path genuinely asynchronous or genuinely multicycle, is there a documented reason (a CDC synchronizer, a known-stable multi-cycle data path), and has someone other than the author reviewed it? Any exception that can't answer all three gets removed and the design re-closed honestly, even if that means the schedule moves. I'd also use the moment to reinforce the process: exceptions are design decisions, not closure tools, and they belong in a reviewed constraint file with a written rationale, not added at the end to make a report go green. The tone matters — the goal is to make the engineer a better reviewer of their own constraints, not to win the argument. If the schedule pressure is what drove the behavior, I'd address that separately with the project lead, because punishing the engineer for a systemic incentive is the wrong fix.
**Possible follow-ups:** How would you structure a constraint review process so this is caught before the design review? What would you do if the engineer's manager pushed back on reopening the closure?
