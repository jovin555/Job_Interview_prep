# high-speed-digital-fpga — Day 114

## Q1: How would you approach designing the power-up and configuration sequence for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?

**Answer:** The key insight is that "configuration done" and "device functional" are two different milestones, and the sequencing has to treat them separately. I'd start by extracting the vendor's power sequencing and reset requirements from the datasheet and pinning them down as explicit constraints: which rails must be stable before others, what the minimum ramp times and monotonicity requirements are, and what the minimum reset pulse widths are for each domain. Then I'd build a small supervisory state machine — either in a CPLD/supervisor IC or in the FPGA's own fabric once it's configured — that gates each stage on a real precondition rather than a fixed delay: core and auxiliary rails in regulation, then configuration engine released, then `INIT`/`DONE` observed, then PLLs locked (using the lock signals, not a timer), then transceiver quads released and their calibration completed, then the user logic's reset tree de-asserted domain by domain. The critical discipline is that every stage waits on a status signal that actually reflects readiness, with a timeout that flags a fault rather than hanging silently. I'd also make the reset architecture hierarchical: a global POR that only releases the configuration logic, then per-quad and per-PLL resets that are held until their own lock/calibration status is good, and finally a synchronized reset per clock domain so that no domain sees a reset release that's asynchronous to its own clock. On the debug side, I'd bring out the state machine's current state and the individual status bits to test points or a debug register so that a board that comes up "configured but dead" can be diagnosed by seeing exactly which gate never opened.

**Possible follow-ups:** How would you handle a PLL that occasionally fails to lock on the first attempt — retry, or treat it as a hard fault? And how do you make sure the supervisory state machine itself is robust if the fabric isn't configured yet?

## Q2: How would you approach debugging an FPGA design where the timing analysis reports that all constraints are met, but the design fails in hardware only when the device is operated at the maximum specified junction temperature?

**Answer:** A clean timing report at the nominal corner combined with a hot-only failure points at one of a few things, and I'd work through them systematically rather than guessing. First, I'd confirm which corners the sign-off actually covered — if the report was generated at the typical corner only, the first step is to re-run static timing at the slow corner with the hot temperature and the low-voltage supply, because delay scales with temperature and voltage in ways that a nominal run won't reveal. Second, I'd check whether the failing behavior correlates with a specific interface rather than the whole design: if it's an external memory or source-synchronous interface, the problem may be in the board-level timing budget (flight time, skew, and the FPGA's input/output delay constraints) rather than internal fabric timing, and those budgets shift with temperature because the I/O buffers and the external device both drift. Third, I'd look at clocking: PLL and MMCM behavior, jitter, and lock margin all degrade at temperature, so I'd verify the clock is still within spec at the hot condition and check whether any clock-domain-crossing paths have marginal synchronizer timing. Fourth, I'd consider whether the failure is really timing at all — thermal effects on the power delivery network (increased IR drop, reduced regulator margin) can produce the same symptom, so I'd measure the rails at temperature. Practically, I'd try to reproduce it in a controlled way with a thermal chamber or hot-air rework station, and use the on-chip debug resources — internal logic analyzer, eye-scan or margin analysis on the transceivers, and the memory controller's built-in sweep — to see which path is actually marginal rather than assuming.

**Possible follow-ups:** If the slow-corner timing run comes back clean too, what else would you suspect? And how would you distinguish a genuine silicon timing margin issue from a power-integrity issue at temperature?

## Q3: How would you approach designing the decoupling and bulk capacitance network for an FPGA's transceiver power rails, where the rails see both high-frequency switching noise from the SerDes and slower, larger current transients from the fabric, and you need to verify the network is adequate before committing to the layout?

**Answer:** I'd treat it as a two-part problem — a broadband impedance target and a transient-response target — and design and verify each separately. For the high-frequency end, the transceiver rails have a tight ripple spec, so I'd start from the vendor's recommended decoupling scheme and then verify it with an impedance-versus-frequency plot of the PDN: the goal is to keep the rail's impedance below a target derived from the allowable ripple divided by the worst-case transient current, across the band from a few hundred kHz up to the point where the on-die capacitance takes over. That means a ladder of capacitors — bulk electrolytic or polymer for the low end, a spread of ceramic values for the mid-band, and small high-frequency parts placed as close to the pins as the package allows — chosen so their self-resonant frequencies overlap and there are no impedance peaks between them. For the slower, larger fabric transients, the bulk capacitance and the regulator's loop response do the work, so I'd check the regulator's transient simulation against the expected current step and confirm the voltage stays within tolerance. Before committing to layout, I'd verify with a PDN simulation that includes the plane capacitance, the via inductance, and the capacitor placement parasitics, and I'd sanity-check the result against the vendor's reference design. After layout, I'd re-extract the actual geometry and re-simulate, and on the bench I'd measure the rail with a low-inductance probe under a representative load pattern to confirm the ripple and transient response match the model.

**Possible follow-ups:** How would you decide how much of the decoupling to place on the back side of the board versus the front? And what would you do if the measured ripple at the transceiver pins exceeded spec despite the simulation looking clean?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?

**Answer:** The core problem is that static timing analysis only checks what you told it to check, so the verification has to focus on constraint completeness and correctness rather than on the timing report's pass/fail line. I'd start by deriving the constraint set from the design's actual clocking and interface structure: enumerate every clock (including generated clocks from PLLs and MMCMs), every clock domain crossing, every external interface with its board-level timing budget, and every asynchronous path that legitimately deserves a false-path or multicycle exception. Then I'd cross-check that enumeration against the constraints actually written, looking specifically for clocks that are defined but never constrained at their endpoints, I/O paths with no input/output delay, and CDC paths that are neither properly synchronized nor explicitly excepted. I'd review every timing exception individually and require a written justification for each — a false path or multicycle path is a claim about the design's behavior, and it should be traceable to a specific architectural reason, not added to make a report close. I'd also run the vendor's CDC and clock-domain checks, and compare the constraint file against the previous revision to catch accidental changes. Finally, I'd confirm the sign-off covers all required corners (slow/hot/low-voltage, fast/cold/high-voltage) and that the reports were generated from the final placed-and-routed netlist, not an earlier build. A useful discipline is to have a second engineer independently review the constraint file against the schematic and the interface timing budgets before sign-off.

**Possible follow-ups:** How would you catch a constraint that is present and syntactically valid but simply wrong — for example, an input delay that doesn't match the actual board timing? And what's your process for reviewing timing exceptions added by someone else?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?

**Answer:** I'd treat it as a teaching moment rather than a confrontation, because the engineer's underlying reasoning may be partly right — some paths genuinely don't need single-cycle timing — but the process of adding exceptions to make a report close is exactly the failure mode that produces designs that pass analysis and fail in hardware. In the review, I'd ask the engineer to walk through each exception one at a time and explain, for that specific path, why the architectural behavior makes the exception valid: what the source and destination are, why the data is guaranteed stable for the required number of cycles, and what enforces that guarantee. For a multicycle path, that means identifying the logic that holds the data valid for the extra cycles; for a false path, it means showing the path is genuinely asynchronous and properly synchronized or genuinely never sensitized. If the justification holds up, the exception stays and we document it. If it doesn't, we've found a real timing problem that needs to be fixed in the RTL or the architecture, not masked in the constraints. I'd frame the conversation around the risk — an unjustified exception is invisible in the report but shows up as an intermittent field failure — and make clear that the goal isn't to reject the engineer's work but to make sure every exception is defensible. Going forward, I'd institute a rule that timing exceptions require a written justification and a second reviewer, and I'd pair the engineer with a senior person on the next closure cycle so they build the judgment about when an exception is legitimate.

**Possible follow-ups:** What would you do if the engineer's justification for an exception was plausible but you weren't fully convinced? And how would you handle it if the schedule pressure made fixing the real timing problem expensive?
