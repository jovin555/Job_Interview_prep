# high-speed-digital-fpga — Day 107

## Q1: How would you approach designing the power-up and reset sequencing for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?
**Answer:** I'd treat power-up as a state machine with explicit dependencies rather than a set of independent timers. The first layer is the board-level rail sequencing: the FPGA's core, auxiliary, and I/O rails must reach their minimum operating thresholds in the order and within the ramp-time window the device datasheet specifies, and the power-good signals from the regulators should be gated into a supervisor that only releases the FPGA's reset once all rails are valid and stable — not just above threshold, but past their ramp and settling. The second layer is the device-internal sequence: configuration must complete and the DONE/init handshake must be observed before any user logic that depends on the fabric is allowed to run, and PLLs and MMCMs must be locked before logic clocked by them is released from reset. The third layer is the transceiver quads, which typically need their reference clocks stable and their own reset pulse timed relative to the clock, and which should not be brought out of reset until the fabric-side logic that will service them is running. I'd implement this as a reset controller in the fabric (or a small external supervisor plus a fabric sequencer) that holds each domain in reset until its prerequisites are met, with the reset release synchronized into each clock domain so there's no asynchronous de-assertion. The key discipline is that every reset is either asynchronous-assert / synchronous-deassert, or fully synchronous, and that the dependency graph is documented and reviewed — because the failure mode of a wrong order is a device that configures fine and then hangs, which is much harder to debug than a device that fails to configure.

**Possible follow-ups:**
- How would you verify the sequencing logic before you have hardware — what would you simulate, and what would you deliberately leave to bench bring-up?
- If a board comes back from the field where the FPGA occasionally fails to come up on a fast power cycle, how would you narrow it down to a sequencing issue versus a configuration-flash issue?

## Q2: How would you approach deciding whether a given logic block should be clocked from a global clock buffer, a regional/banked clock resource, or a locally routed clock, when global clock resources are scarce and the block runs at a modest rate?
**Answer:** I'd start from the clock's fan-out and skew requirements rather than from habit. A global clock network buys low skew across the whole die and predictable timing, but it consumes a scarce global resource and burns more power than a regional net. A regional or banked clock reaches only a portion of the device, so it's appropriate when the logic it clocks is physically confined to one region — which is often true for a peripheral interface, a memory controller's user-side logic, or a self-contained processing pipeline. A locally routed clock (a plain routing resource used as a clock) is the last resort: it has uncontrolled skew, it's sensitive to placement, and it will make timing closure fragile, so I'd only use it for genuinely low-rate, non-timing-critical logic where the skew is bounded by the small physical extent of the load. The decision process is: enumerate the clocks, identify which ones need global reach (anything that must communicate synchronously across the die, or that feeds a hardened block with a dedicated clock input), assign those to globals first, then for the remainder ask whether the load is regionally confined and whether the rate and skew tolerance allow a regional buffer. I'd also check whether the tool can promote a regional clock to global automatically and whether that promotion would starve a more important clock — the constraint file should make the intent explicit so the fitter doesn't make that choice silently.

**Possible follow-ups:**
- What timing constraints would you write to make sure the tool doesn't quietly promote your regional clock to a global one and consume a resource you needed elsewhere?
- How would you sanity-check, after place-and-route, that the clock you intended to be regional actually stayed regional and didn't get routed as a general net?

## Q3: How would you approach debugging an FPGA design that passes timing analysis at the nominal corner but produces occasional corrupted samples only when the board is cold, below its specified operating range, and the corruption disappears once the board warms up?
**Answer:** Cold-only failures point at a few physical mechanisms, and I'd try to separate them before changing any RTL. First, I'd confirm the failure is actually in the FPGA and not in an analog front-end or reference that drifts at cold — a cold-only corruption in a data acquisition path is at least as likely to be an ADC reference or a clock oscillator issue as a fabric timing issue. On the FPGA side, the prime suspects are: timing margin that is genuinely marginal at the fast corner (cold usually means faster transistors, which can expose hold-time and short-path problems rather than setup problems), a PLL or MMCM that is not fully locked or whose lock is marginal at cold, and a source-synchronous interface whose capture window shifts because the forwarded clock and data paths have different temperature coefficients. I'd instrument with an on-chip logic analyzer or a lightweight error counter that flags the first bad sample and captures the surrounding state, run it in a cold chamber with a controlled ramp, and correlate the first failure with temperature and with any lock or calibration status bits. If it's a hold-time or short-path issue, the fix is usually in the constraints and the place-and-route, not in the logic — I'd check that the fast corner is actually being analyzed and that any multicycle or false-path exceptions are justified. If it's a PLL lock or a calibration that runs once at power-up and doesn't re-run, the fix is to make the calibration temperature-aware or to re-run it on a lock-loss event.

**Possible follow-ups:**
- Why would a cold failure more often be a hold-time problem than a setup-time problem, and how does that change where you look?
- If the calibration runs once at power-up and the board is powered up cold, how would you decide whether to re-calibrate periodically or to widen the calibration's operating window?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that a missing or incorrect constraint can produce a design that passes timing analysis but fails in hardware?
**Answer:** I treat constraint review as a separate deliverable from timing closure, because "all constraints met" only means "all the constraints I wrote are met" — it says nothing about the constraints I forgot. The process I'd use has several passes. First, a structural pass: enumerate every clock in the design from the clock sources (oscillators, transceiver recovered clocks, forwarded clocks from external devices) and confirm each one has a create_clock or create_generated_clock with the correct period, and that every clock domain crossing has either a proper synchronizer with a set_false_path or set_max_delay exception, or is genuinely synchronous and constrained. Second, a coverage pass: use the tool's unconstrained-path and clock-interaction reports to find paths that are being analyzed with no relationship, and treat every one as a question to answer rather than a warning to suppress. Third, an exception audit: every false path and multicycle path should have a written justification tied to the design intent, and I'd have a second engineer review them, because exceptions are where designs quietly break. Fourth, a cross-check against the interface specs: for every external interface, the constraint should be derived from the datasheet timing (setup/hold, skew, jitter) and not from what the tool happened to close at. Finally, I'd run the design at multiple corners and confirm the slack margins are consistent with the analysis, and I'd compare the constrained design against a version with the exceptions removed to see what the exceptions are actually buying.

**Possible follow-ups:**
- How would you catch a clock that exists in the design but was never constrained at all — what report or methodology surfaces that?
- What's your rule for when a multicycle path is legitimate versus when it's hiding a real problem?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented the DDR3 write path and, during the review, you notice they've sized the write FIFO from the average throughput rather than the worst-case burst, arguing that "the average rate is well below the memory bandwidth, so it can't overflow." How do you handle this situation?
**Answer:** I'd treat it as a teaching moment rather than a correction, because the reasoning is a common and understandable shortcut — and the fix is to make the worst case visible rather than to assert that the engineer is wrong. In the review, I'd ask them to walk me through the burst behavior of the source: what is the maximum number of words the ADC-side logic can produce back-to-back, and what is the maximum latency the memory controller can impose before it accepts a write — including refresh, bank conflicts, and arbitration with read traffic. The point I'd want to land is that a FIFO sized on averages is sized for the average case, and the failure mode is a rare overflow that corrupts data intermittently and is very hard to reproduce. I'd then work with them to derive the depth from the worst-case burst minus the worst-case drain over the same window, plus margin, and to add an overflow flag and a high-water-mark counter so the design can be monitored in bring-up rather than trusted. I'd keep the tone collaborative — the goal is that they own the corrected sizing and can defend it in the next review — and I'd follow up by adding "FIFO sizing rationale" as a standing item in the review checklist so the whole team benefits.

**Possible follow-ups:**
- How would you handle it if the engineer pushed back and said the memory controller's internal write buffer already absorbs the bursts?
- What would you add to the design so that a marginal FIFO depth shows up as a measurable event during validation rather than as a field failure?
