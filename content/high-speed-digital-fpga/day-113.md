# high-speed-digital-fpga — Day 113

## Q1: How would you approach designing the power-up and reset sequencing for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?

**Answer:** I'd treat this as a dependency-ordering problem and drive it from a single, explicit state machine rather than letting each block self-start. The sequence generally follows the device's power sequencing requirements first: bring up the rails in the vendor-specified order and hold everything in reset until all rails are within tolerance and stable — a power-good supervisor with a deliberate delay handles the ramp-rate differences between rails. Only then release the configuration engine and let the bitstream load; the configuration-done signal is the gate for everything downstream.

After configuration, the PLLs and MMCMs come next, because the transceiver quads and most of the fabric logic depend on their locked outputs. I'd wait on each PLL's lock signal with a timeout, and only release the logic that consumes that clock once lock is asserted and stable for a defined window. Transceiver quads come up after their reference clocks are present and the PLLs feeding them are locked; the quad reset and channel reset are sequenced per the transceiver's reset controller requirements, and I'd wait for the calibration-done indications before enabling the link.

The key design principles: every stage has an explicit "ready" condition and a timeout that drives a defined error state rather than hanging; resets are released synchronously to the clock domain they serve (asynchronous assert, synchronous de-assert) to avoid recovery/removal violations; and the whole sequence is observable through status registers so bring-up failures are diagnosable. I'd also make sure a warm reset re-runs the sequence cleanly without requiring a full power cycle, and that the state machine itself is robust to a partial failure — for example, a PLL that never locks should park the system in a safe state and flag it, not leave downstream logic running on an unlocked clock.

**Possible follow-ups:** How would you handle a transceiver quad that reports calibration done but then fails its internal PRBS check — where in the sequence would you place that check? What's your approach to verifying the reset sequencing in simulation, given that the vendor models may not accurately represent power-ramp behavior?

## Q2: How would you approach debugging an FPGA design where the DDR3 interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** This is a classic temperature-correlated margin problem, so my first instinct is that something is operating with insufficient margin and the warm-up is shifting a timing or voltage parameter past its limit. I'd start by characterizing the failure: does it correlate with junction temperature, board ambient, or time-since-power-on independent of temperature? A controlled thermal chamber or a hot-air rework station with a thermocouple on the FPGA and on the DRAM packages lets me separate those.

On the timing side, the prime suspects are the read capture window and the write leveling / read leveling results. Calibration performed cold may produce a delay tap setting that sits near the edge of the valid window; as the device warms, the delay chain and the DRAM's output timing drift, and the margin evaporates. I'd read back the calibration tap values at cold and at temperature and compare — if the chosen tap is not near the center of the passing region, that's the smoking gun. The fix is usually to re-run calibration at temperature or to bias the tap selection toward the center of the window rather than the first passing tap.

Other candidates: ODT and drive-strength settings that were marginal at cold and shift with temperature; the reference voltage (VREF) if it's derived from a resistor divider that drifts; and the memory controller's refresh behavior if the failure only appears under sustained traffic. I'd also check whether the failure is data-pattern dependent, which points at crosstalk or ISI rather than a pure timing-window issue. Throughout, I'd use the controller's built-in error reporting and, if available, an on-chip logic analyzer to capture the failing transaction and the state of the calibration registers at the moment of failure.

**Possible follow-ups:** If re-calibration at temperature isn't possible in the field, how would you make the cold-time calibration robust to the drift? How would you distinguish a DRAM-side thermal effect from an FPGA-side one?

## Q3: How would you approach designing the clock domain crossing for a multi-bit control word that is written by a slow serial interface (e.g., 10 MHz SPI) and consumed by a fast logic domain (e.g., 250 MHz), where the word changes infrequently but must never be observed in a partially updated state?

**Answer:** The core requirement is atomicity: the consumer must see either the old word or the new word, never a mix of bits from both. Since the word changes infrequently and the source is much slower than the destination, the cleanest approach is a handshake-based transfer rather than trying to synchronize the bits directly.

The pattern I'd use: the slow domain holds the word in a register and asserts a request toggle or level; that single control bit is synchronized into the fast domain through a two-flop synchronizer (or a toggle synchronizer, which is robust to the source being slower). The fast domain, on detecting the request, captures the entire multi-bit word into a destination register in a single clock edge — because the word has been stable in the source domain since well before the request was asserted, and the fast domain only samples it after the synchronized request arrives, there's no chance of catching it mid-update. The fast domain then asserts an acknowledge, which is synchronized back to the slow domain so the source knows it can update the word again.

The critical discipline is that the source must not change the word until it has seen the acknowledge — that's what guarantees the data is stable across the entire capture window. I'd also add a formal or structural CDC check (a CDC lint tool) to confirm the synchronizers are recognized and that no multi-bit bus crosses without a proper scheme. For a control word that changes this rarely, the latency of the handshake is irrelevant, so I'd favor the simplest, most provably correct structure over anything clever.

**Possible follow-ups:** How would this change if the word could be updated back-to-back faster than the handshake can complete? What's the difference between using a toggle synchronizer and a level-based request here, and when would you prefer one over the other?

## Q4: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?

**Answer:** A via that passes through a thick backplane but is only used for a signal on the top or bottom layer leaves an unused portion — the stub — that acts as an open-ended transmission line. At multi-gigabit rates, that stub resonates and creates a notch in the channel's insertion loss plus a reflection that degrades the eye, so the goal is to either eliminate the stub or push its resonance well above the signal's bandwidth.

The most effective fix is backdrilling: after plating, the unused portion of the via barrel is drilled out from the opposite side, leaving only the segment needed to reach the target layer. This is the standard production solution for thick backplanes, and I'd specify a backdrill depth with a controlled remaining stub — typically a few tens of mils at most, chosen so the stub's quarter-wave resonance sits comfortably above the Nyquist frequency of the link. The trade-off is cost and yield, since backdrilling adds a process step and requires depth control.

Where backdrilling isn't practical, alternatives include: routing the signal so the layer transition happens through a via whose stub is inherently short (e.g., transitioning between adjacent layers rather than top-to-bottom); using blind or buried vias if the fabrication technology supports them, which avoids the through-barrel entirely; or, as a last resort, compensating with transmitter pre-emphasis and receiver equalization to recover the eye, though that burns power and only buys back so much margin. I'd validate the choice with a 3D electromagnetic extraction of the via structure and a channel simulation that includes the connector and the backplane traces, checking the eye at the target BER before committing to the stack-up.

**Possible follow-ups:** How would you decide the maximum acceptable remaining stub length for a given line rate? What layout practices reduce stub impact when backdrilling is not available?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?

**Answer:** I'd treat this as a review-quality issue first and a technical disagreement second, and I'd handle it without making the engineer defensive — the goal is a correct design, not winning the argument. My first move is to ask the engineer to walk me through each exception and the reasoning behind it, path by path. Some exceptions are genuinely legitimate — a path from a static configuration register to logic that's only sampled after a documented settling time, or a multicycle path where the receiving logic genuinely has multiple cycles to capture. Others are not, and the way to tell the difference is to ask: what guarantees this path is safe, and where is that guarantee documented?

For each exception I'd want to see the justification tied to a real architectural fact, not to "it closes timing." A false path on a path that actually carries data is a latent hardware bug — it may pass in the lab and fail at temperature or on a different board. A multicycle path needs the source and destination to be analyzed for the actual number of cycles available, including any clock-domain relationship, and the setup and hold checks adjusted accordingly. If the justification doesn't hold up, the exception comes out and we fix the design — pipeline the path, restructure the logic, or add the missing constraint.

I'd frame the conversation around risk and process rather than blame: timing exceptions are a sign-off artifact that need review and documentation, and the review is exactly where we catch this. I'd also use it as a coaching moment — explain why an unjustified exception is more dangerous than a timing failure, because a timing failure is visible and an unjustified exception hides the problem. Then I'd follow up by making exception review a standing part of the sign-off checklist so it's caught systematically rather than depending on someone noticing.

**Possible follow-ups:** How would you verify after the fact that a set of timing exceptions is actually safe — what would you check beyond re-reading the justifications? If the engineer pushes back and insists the exceptions are fine, how do you resolve the disagreement without simply pulling rank?
