# high-speed-digital-fpga — Day 82

## Q1: How would you approach designing the interface between an FPGA and an external ADC that uses a source-synchronous, double-data-rate (DDR) output bus, where the data and a forwarded clock arrive at the FPGA with an unknown but bounded skew between them?
**Answer:** The core problem is that the forwarded clock and the data are launched together but arrive with an unknown skew, so the FPGA must recover the correct sampling point rather than assume a fixed phase relationship. I'd start by characterizing the skew budget: the ADC's output valid window, the board's trace-length mismatch between clock and data, and the FPGA input setup/hold requirements. That tells me whether a static delay (a fixed IDELAY tap) is sufficient or whether I need dynamic per-bit alignment.

For a DDR source-synchronous bus, I'd use the FPGA's input delay primitives (IDELAY/IDELAYE) on each data lane and, where available, on the forwarded clock, then run a training/calibration routine at startup. The routine sweeps the delay taps while the ADC outputs a known pattern (e.g., a PRBS or a walking-ones pattern), and I look for the center of the passing window — not just the first passing tap — so there's margin on both sides. Because the clock is DDR, I need to align both edges, which usually means treating the clock and data as separate delay groups and calibrating the relationship between them.

I'd also make sure the forwarded clock is routed into a clock-capable pin and through a suitable buffer (BUFG/BUFR or an MMCM if I need to phase-shift it), and I'd constrain the input timing properly in the tool so static timing analysis reflects the real interface. Temperature and voltage drift matter, so if the skew budget is tight I'd consider periodic re-calibration or at least verify the window holds across the operating range. Finally, I'd verify on hardware with an eye diagram or a bit-error test at the actual data rate, not just in simulation, because the board-level skew is what dominates here.

**Possible follow-ups:** How would you decide between using the forwarded clock directly versus regenerating it through an MMCM? What would you do if the passing window you found during calibration was narrower than your skew budget predicted?

## Q2: How would you approach debugging an FPGA design where the transceiver link passes its built-in PRBS checker at the physical layer, but application-level data is occasionally corrupted, and the corruption only appears at full line rate?
**Answer:** The fact that the PRBS checker passes tells me the physical layer — SerDes, CDR, equalization, and the raw serial path — is fundamentally healthy. So the corruption is almost certainly happening above the SerDes, in the logic that moves data between the transceiver's parallel interface and the application, or in the clock domain crossing between the recovered clock domain and the fabric clock domain.

I'd first narrow down where the corruption is introduced. A good technique is to insert a known pattern generator and checker at the application layer, or to use the transceiver's internal loopback modes at different points (serial loopback, parallel loopback, near-end/ far-end) to see at which stage the data first becomes wrong. If parallel loopback is clean but the full application path is not, the problem is in the fabric-side logic.

Common culprits at full line rate: a FIFO or elastic buffer that's too shallow for the burst behavior, a CDC that works at low rate but violates setup/hold margins when the rate rises, or a status/flag signal (like empty/full or a valid) that isn't synchronized properly. I'd also check whether the transceiver's parallel clock and the fabric clock have the relationship I assumed — a rate mismatch or an incorrect phase relationship can produce intermittent errors that only show up when the buffer is nearly full or empty.

I'd instrument with a logic analyzer or the transceiver's built-in eye-scan and error counters, and I'd deliberately stress the link — run it at full rate for a long time, vary the data pattern, and vary temperature — to make the intermittent failure reproducible. Once reproducible, I'd bisect the datapath by adding checkers at intermediate points until I find the stage where errors first appear.

**Possible follow-ups:** How would you distinguish a CDC problem from a FIFO-depth problem if both produce intermittent corruption? What role does the transceiver's elastic buffer play, and how would you verify it's sized correctly?

## Q3: How would you approach designing the return-current path for a high-speed digital board where a signal transitions between two reference planes (e.g., from a ground plane to a power plane) on its way through a via?
**Answer:** At high frequency, the signal's return current doesn't flow through the "ground" in a vague sense — it flows in the reference plane directly beneath (or above) the trace, following the path of least impedance, which at high frequency means the path of least inductance. When a trace references one plane and then, after a via, references a different plane, the return current has to jump between those planes. If there's no low-inductance path for it to do so, the return current is forced to take a long detour, which creates a loop, radiates, and degrades signal integrity.

The standard fix is to provide a nearby stitching capacitor between the two reference planes, placed as close as possible to the signal via — ideally within a fraction of a wavelength at the highest frequency of interest, and practically within a few millimeters. The capacitor gives the return current a low-inductance path to transfer from one plane to the other. For very high-speed signals, a single capacitor may not be enough; I'd use multiple capacitors in parallel to lower the effective inductance, and I'd keep the via-to-capacitor loop area small.

I'd also consider whether the plane transition is necessary at all. If I can keep the signal referencing the same plane for its entire route, I avoid the problem entirely. When a transition is unavoidable, I'd place the stitching capacitor right at the via, and I'd make sure the planes themselves are well-decoupled at the frequencies involved. On the layout side, I'd check that the return path is continuous — no slots or splits in the reference plane under the trace — because a split in the plane forces the return current to detour just as a plane transition does.

**Possible follow-ups:** How would you decide the value and number of stitching capacitors for a given signal rise time? What happens if the two reference planes are at different DC voltages — does that change your approach?

## Q4: How would you approach choosing between a global clock network and a regional/banked clock resource for a logic block that only needs to run at a modest rate, when the device's global clock resources are nearly exhausted?
**Answer:** Global clock networks are a scarce resource, and they're valuable because they offer low skew and low jitter across the whole device. If a logic block only runs at a modest rate and doesn't need to communicate synchronously with logic spread across the entire chip, it usually doesn't need a global clock. A regional or banked clock resource can drive a localized region with adequate skew for that region, freeing up the global network for the clocks that genuinely need it.

The decision hinges on a few questions. First, how far does the clock need to reach? If the logic it drives is confined to one clock region or a small number of adjacent regions, a regional resource is usually fine. Second, what's the skew and jitter requirement? A modest-rate block typically has relaxed timing, so the slightly higher skew of a regional network is acceptable. Third, does the block need to interact with logic in other regions at the same clock rate? If so, and if that interaction is timing-critical, a global clock may still be the right choice even at a modest rate.

I'd also consider whether the block can share an existing global clock. If two blocks run at the same frequency and are related, they can often share one global network, which is more efficient than giving each its own. And I'd check the device's clocking architecture — some devices have regional clocks that can be promoted to global, or global clocks that can be routed regionally, so the choice isn't always binary.

The practical approach: enumerate all the clocks in the design, identify which ones truly need global reach and low skew, assign those to global resources, and push everything else to regional or local resources. Then verify with static timing analysis that the regional clocks still meet their constraints, and check the clocking report to confirm no global resource is over-subscribed.

**Possible follow-ups:** What are the risks of using a regional clock for a block that later needs to expand across the chip? How would you verify that a regional clock's skew is acceptable for your timing budget?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?
**Answer:** This is a classic and serious issue, so my first priority is to make sure the engineer understands why it's a problem without making them feel attacked — the goal is a correct design, not a win in the review. I'd start by acknowledging that the intuition isn't unreasonable: if a signal is stable for a long time relative to the destination clock, it often does get captured correctly. But "often" isn't a guarantee, and the failure mode is exactly the kind of intermittent, hard-to-reproduce bug that's expensive to find later.

I'd explain the mechanism concretely: when a signal crosses into another clock domain, it can violate the destination flip-flop's setup or hold window, which puts the flip-flop into a metastable state. Metastability resolves eventually, but the resolution time is probabilistic — most of the time it resolves within a clock cycle, but occasionally it doesn't, and that's when you get a corrupted value or a signal that appears to change at the wrong time. A synchronizer (typically two flip-flops in series) doesn't eliminate metastability, but it reduces the probability of a metastable value propagating to the point where it's effectively zero for the design's lifetime.

I'd also point out that "stable long enough" is an assumption that may not hold across all conditions — temperature, voltage, and process variation can change the timing margins, and a signal that's stable at room temperature may not be at the corner cases. And if the signal is multi-bit, a simple two-flop synchronizer isn't even sufficient; you need a proper CDC structure like a handshake, a FIFO, or Gray coding, depending on the data.

Then I'd work with the engineer to fix it: identify the correct synchronization scheme for this signal (single-bit level, single-bit pulse, or multi-bit bus), implement it, and add a CDC constraint or a lint check so the tool flags this class of issue in the future. I'd frame it as a learning opportunity and make sure the review process catches these issues earlier — maybe add a CDC checklist to the design review template. The tone matters: I want the engineer to leave understanding the principle, not just the fix, so they apply it themselves next time.

**Possible follow-ups:** How would you handle it if the engineer pushed back and insisted the signal really is stable enough? What would you add to your design review process to catch this class of issue before it reaches review?
