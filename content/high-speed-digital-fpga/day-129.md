# high-speed-digital-fpga — Day 129

## Q1: How would you approach designing the clock domain crossing for a multi-bit data bus where the source and destination clocks are asynchronous and have no known frequency relationship, and the data must be transferred without corruption?
**Answer:** With no known frequency relationship, the safe default is a handshake-based CDC rather than a rate-matching scheme. The source domain registers the data and asserts a request; the request is synchronized into the destination domain through a two-flop synchronizer; the destination captures the data (which is now stable because the source holds it until acknowledged) and returns an acknowledge that is synchronized back. The data itself never passes through a synchronizer — only the request/acknowledge control signals do — so there is no risk of sampling a bus mid-transition. The trade-off is latency: a full round-trip handshake costs several destination clock cycles, so it suits control words and infrequent transfers, not streaming payloads. For streaming data with no known rate relationship, I would use an asynchronous FIFO built from dual-port block RAM, with Gray-coded read and write pointers synchronized across domains so the full/empty flags are safe. The key discipline is to constrain the CDC paths in the timing tool (set_false_path or set_max_delay with datapath_only) so the tool doesn't try to time a path that is by definition asynchronous, and to run a CDC lint check to catch any bus that slipped through unsynchronized.
**Possible follow-ups:** How would you decide the FIFO depth when neither side's rate is known in advance? What CDC violations would a lint tool catch that simulation typically would not?

## Q2: How would you approach debugging an FPGA design where the DDR3 interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?
**Answer:** A failure that appears only after warm-up points to a timing margin that is being consumed by temperature-dependent effects — either on-die (delay shifts, DLL/PLL behavior) or on the board (trace impedance, connector resistance). I would first establish whether the failure is in the memory device, the controller, or the channel by checking the controller's error status and whether calibration values drift. A useful technique is to re-run the read/write leveling after warm-up and compare the delay tap settings to the cold values — a large shift suggests the initial calibration was marginal. I would also look at the refresh behavior: as the die heats, refresh intervals shorten and the controller's scheduling changes, which can expose marginal timing. On the board side, I would check the VREF and termination voltages for drift and probe the DQ/DQS eye at temperature if a scope is available. The fix usually involves either increasing the timing margin (relaxing the speed grade, adjusting ODT, improving the reference voltage) or improving thermal management so the die stays within the range the calibration was validated for.
**Possible follow-ups:** How would you distinguish a controller-side margin issue from a DRAM-side one? What role does the write leveling calibration play in warm-up failures?

## Q3: How would you approach designing the decoupling network for an FPGA's core voltage rail, where the rail supplies a large, fast-changing current to the fabric and must stay within a tight tolerance across a broad frequency range?
**Answer:** The core rail's current demand has a broad spectrum — slow load steps from fabric activity plus fast transients from switching — so the decoupling network has to present a low impedance across that whole range, not just at one frequency. I would start from the target impedance: Z = allowed ripple / transient current, and design the network so the impedance stays below that from the regulator's bandwidth up to the frequencies where the on-die capacitance takes over. That means a layered approach: bulk electrolytic or polymer capacitors for the low-frequency end, a bank of ceramic capacitors in the mid-range, and small-value, low-ESL capacitors placed as close to the FPGA power pins as possible for the high end. The critical detail is loop inductance — the mounting inductance of the capacitor and the via/plane path dominate above a few MHz, so I would use multiple vias per capacitor pad, place them on the same side as the FPGA where possible, and keep the power/ground plane pair close together to maximize plane capacitance. I would verify the design with an impedance simulation of the PDN (capacitor models plus plane extraction) before layout, and confirm with a measurement on the first article.
**Possible follow-ups:** How would you decide how many vias per capacitor pad are enough? What would you do if the simulated impedance has a peak above target in the mid-frequency range?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?
**Answer:** The core risk is that the timing report only tells you about paths the tool knows to check, so the verification has to focus on constraint coverage rather than on the report's pass/fail. I would start by confirming that every clock is defined with the correct period, that generated clocks (PLL/MMCM outputs) are properly derived, and that all I/O is constrained with the correct input/output delay relative to the external device's datasheet. Then I would audit every timing exception — false paths and multicycle paths — individually, because an over-broad exception silently removes real paths from analysis. A useful cross-check is to run the design with exceptions removed and see what fails; anything that fails without the exception needs a documented justification. I would also run a CDC lint tool to catch unsynchronized crossings, check that asynchronous clock groups are declared, and review the constraint file against the interface control document so every external interface has a corresponding constraint. Finally, I would confirm the analysis was run at all required corners (slow, fast, and any temperature extremes the part specifies), since a design that closes at nominal can still fail at a corner.
**Possible follow-ups:** How would you catch a constraint that is present but numerically wrong, rather than missing? What is the risk of relying on a single corner for sign-off?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?
**Answer:** I would treat this as a review-quality issue rather than an accusation, and walk through the exceptions one at a time with the engineer. For each exception, I would ask for the specific justification: which path is it, why does it not need single-cycle timing, and what is the actual timing requirement it does need to meet? A legitimate multicycle path has a documented relationship between the launch and capture edges and a corresponding setup/hold analysis; a legitimate false path is a path that is genuinely never sensitized or is asynchronous. If the engineer can articulate that for each exception, the design is fine and we document it. If not, the exception is masking a real timing problem, and the fix is to either close the path properly or replace the exception with a correct constraint (e.g., a max_delay for a CDC path). I would also make the point that exceptions are a design decision with sign-off implications, so they need to be reviewed and recorded, not added ad hoc to make a report go green. The goal is to leave the engineer with a clear standard for what justifies an exception, not to embarrass them in the review.
**Possible follow-ups:** How would you structure a review process so timing exceptions get caught before sign-off? What would you do if the engineer disagreed and insisted the exceptions were correct?
