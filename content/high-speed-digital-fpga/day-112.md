# high-speed-digital-fpga — Day 112

## Q1: How would you approach designing the power-up and configuration sequence for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?

**Answer:** The core principle is that configuration is not a single event but a dependency chain, and each stage must be gated on a verified precondition rather than a fixed delay. I'd start by mapping the vendor's documented sequencing requirements onto a state machine: all supply rails within tolerance and stable (monitored via the power-good signals or a supervisor with a sequenced threshold), then the configuration engine released, then the configuration image loaded and the DONE/init handshake observed, and only then the PLLs and transceiver quads brought out of reset. The critical discipline is that each transition is triggered by an actual status signal — a PLL lock output, a transceiver calibration-done flag, a configuration-done pin — not by a timer that "should be long enough." Timers are a fallback timeout for fault detection, not the primary sequencing mechanism.

I'd also treat the reset tree itself as part of the design: separate resets for the configuration domain, the clocking domain, and the transceiver domain, with the release order enforced in logic rather than relying on RC delays or power-supply ramp order. Transceiver quads in particular need their reference clock stable and their calibration complete before the fabric logic that drives them is released, otherwise the link comes up in an undefined state. Finally, I'd make the sequence observable — status registers or LEDs for each stage — so that a board that comes up "configured but dead" can be diagnosed by seeing exactly which stage never completed.

**Possible follow-ups:**
- How would you handle a PLL that occasionally fails to lock on the first attempt — would you retry, and how would you bound the retry logic?
- What changes if the board can be power-cycled faster than the supplies can fully discharge, so the next power-up starts from a partially-charged state?

## Q2: How would you approach debugging an FPGA design where the DDR3 interface passes initialization and calibration at power-up, but produces intermittent read errors only after the board has been running for several minutes and has warmed up?

**Answer:** A failure that appears only after warm-up points to a timing margin that is being consumed by temperature-dependent effects — driver impedance shifts, propagation delay changes, and refresh behavior — rather than a logic bug. My first move is to establish whether the errors are data-pattern-dependent and address-dependent, because that separates a marginal timing window from a specific failing structure. Running a memory test that sweeps patterns (walking ones, checkerboard, random) and logs the failing addresses tells me whether errors cluster in a particular bank, rank, or bit lane.

Next I'd look at the calibration data itself: most DDR3 controllers expose per-bit read/write leveling delays and per-bit deskew values. If the calibrated window for a particular lane is narrow or sits near the edge of its valid range at power-up, warm-up will push it out of the window. Comparing the calibration results cold versus hot is often the single most informative measurement. On the hardware side, I'd check the reference voltage and termination — VREF and ODT are the usual suspects when margins are thin — and verify that the controller is issuing refreshes at the rate the temperature requires (higher temperature means more frequent refresh, and a controller configured for a fixed rate may under-refresh when hot). I'd also confirm the timing constraints in the FPGA were derived from the actual board delays and not from a generic reference design.

**Possible follow-ups:**
- If the per-bit calibration windows look healthy at both temperatures, where would you look next?
- How would you distinguish a DRAM-side thermal effect from an FPGA-side one without swapping parts?

## Q3: How would you approach designing the clock domain crossing for a multi-bit control word that is written by a slow serial interface (e.g., 10 MHz SPI) and consumed by a fast logic domain (e.g., 250 MHz), where the word changes infrequently but must never be observed in a partially updated state?

**Answer:** The key insight is that "changes infrequently" is not a synchronization guarantee — the consumer can sample at exactly the wrong moment regardless of how rarely the writer updates. So the design must make atomicity structural, not probabilistic. The standard approach is a handshake or a toggle-based scheme: the writer assembles the full word in its own domain, then asserts a request (or toggles a single bit) that is synchronized into the fast domain through a two-flop synchronizer. The fast domain detects the edge, captures the entire word in one clock, and returns an acknowledge that is synchronized back. Because the data bus is held stable from request assertion until acknowledge is received, the multi-bit value is never sampled mid-update — only the single control bit crosses asynchronously, and single-bit synchronizers are safe.

An alternative for a register that is read rather than pushed is a shadow-register pair with a synchronized select: the writer updates the shadow, then toggles the select, and the reader's synchronized select chooses which register to read. Either way, the rule is the same: only one bit crosses the asynchronous boundary through a synchronizer, and the multi-bit payload is guaranteed stable by protocol. I'd also add a formal or lint check for CDC structures, because these bugs are invisible in simulation unless the testbench happens to hit the exact race.

**Possible follow-ups:**
- What is the latency cost of the handshake, and when would that push you toward a different scheme?
- How would you verify this CDC in simulation given that the race is rare and timing-dependent?

## Q4: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?

**Answer:** A via through a thick backplane has an unused portion — the stub — that behaves as an open-circuited transmission line, producing a resonance that causes insertion-loss peaking and a notch at a frequency set by the stub length and the board's effective dielectric constant. At multi-gigabit rates that notch can land right in the channel's bandwidth and close the eye. The first-line mitigation is to eliminate the stub: use blind or buried vias so the via only spans the layers it needs to connect, or use backdrilling to remove the unused barrel below the last connected layer. Backdrilling is the standard production answer for thick backplanes and is usually specified with a controlled drill depth and a remaining stub budget.

Where backdrilling isn't feasible — cost, panel handling, or connector constraints — the alternatives are to move the layer transition to a location where the stub is short, to route the channel so the transition happens at a connector footprint where the stub is inherently minimal, or to accept the resonance and compensate with equalization (transmitter pre-emphasis and receiver equalization) if the link budget allows. I'd verify the choice with a 3D electromagnetic extraction of the via structure, not a 2D approximation, because the stub resonance is a 3D effect. The design review checkpoint is to have a documented stub-length budget per channel and to check every layer transition against it.

**Possible follow-ups:**
- How would you decide the maximum allowable stub length for a given line rate?
- What does the channel S-parameter plot look like when a stub resonance is present, and how would you recognize it?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?

**Answer:** I'd treat this as a review of the exceptions themselves rather than an accusation, because the engineer may well be right — multicycle paths and false paths are legitimate tools when they reflect the actual design intent. The problem is that an exception is an assertion about the design that the tool will no longer check, so every exception has to be justified individually and documented. My approach in the review is to go through the exception list one at a time and ask, for each: what is the physical or logical reason this path doesn't need single-cycle timing, and what constrains it instead? A multicycle path needs a corresponding multicycle setup/hold relationship and a reason the data is stable for that many cycles — typically a enable or a clock-enable structure that the synthesis tool can't infer. A false path needs a reason the path can never be sensitized, such as a static configuration register or a path between asynchronous domains that is properly synchronized elsewhere.

If the justification holds, I'd want it captured in a comment or a constraint file with a rationale, so the next engineer doesn't silently inherit an unexplained exception. If it doesn't hold — for example, a false path applied to a path that is actually functional, or a multicycle exception on a path with no enable — then the design isn't closed and the exception has to come out, which means the real fix is a pipeline stage, a restructure, or a legitimate architectural change. The tone matters: the goal is to teach the discipline that timing exceptions are design assertions with consequences, not a knob to turn until the report goes green. I'd also follow up by adding an exception-review step to the team's sign-off checklist so this is caught systematically rather than depending on someone noticing.

**Possible follow-ups:**
- How would you verify that a multicycle path exception is actually safe — what would you check beyond the constraint itself?
- What would you do if the engineer disagreed with your assessment and felt the exception was being second-guessed unfairly?
