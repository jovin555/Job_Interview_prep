# high-speed-digital-fpga — Day 94

## Q1: How would you approach designing the clock domain crossing for a multi-bit control word that is written by a slow serial interface (e.g., 10 MHz SPI) and consumed by a fast logic domain (e.g., 250 MHz), where the word changes infrequently but must never be observed in a partially updated state?

**Answer:** The key insight is that this is a "data changes infrequently, but must be atomic" problem — which is fundamentally different from a high-throughput streaming CDC. Because the word changes rarely, latency is not the constraint; coherency is. The classic robust approach is a handshake-based toggle scheme: the slow domain holds the data stable in a register, then toggles a single-bit "valid" flag. That flag is synchronized into the fast domain through a two-flop synchronizer (or a proper synchronizer primitive), and the fast domain detects the edge, captures the multi-bit word, and returns an acknowledge toggle back through its own synchronizer. The data itself never crosses through a synchronizer — it is held stable long enough that by the time the fast domain samples it (several fast-clock cycles after the synchronized flag edge), it is guaranteed valid. This is sometimes called a "MCP (multi-cycle path) handshake" or "toggle handshake" formulation.

The alternative — a two-flop synchronizer on every bit — is wrong here because bits can resolve on different cycles, producing a transient mixed value. Gray coding only helps if the data is a counter incrementing by one; a control word has no such structure. A dual-clock FIFO would also work but is overkill and adds latency and area for a register that changes infrequently. The handshake approach is minimal, provably correct, and easy to constrain: the data path gets a `set_max_delay`/`set_false_path` with the correct `-datapath_only` semantics, and the toggle flags get proper synchronizer constraints. I'd also add a CDC lint/formal check to confirm the tool sees the crossing as intentional.

**Possible follow-ups:** How would you constrain the data path in SDC so the tool doesn't try to time it as a single-cycle path? What happens if the fast domain is reset while the slow domain is mid-handshake, and how do you recover?

## Q2: How would you approach debugging an FPGA design where the DDR3 memory interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** A failure that only appears after warm-up is a strong signal that the margin was always thin and temperature has eaten into it — so I'd treat this as a margin/timing-budget problem, not a logic bug. First, I'd characterize the failure: is it a specific address range, a specific data pattern, a specific burst length, or truly random? That narrows whether it's a data-bit lane, a command/address lane, or a control-path issue. Then I'd instrument: enable the memory controller's error reporting and, if available, its per-bit error counters; run a long soak with a PRBS or March pattern while logging junction temperature and any error events, so I can correlate the first error with a temperature threshold.

The most likely culprits are: (1) write/read leveling or per-bit deskew values that were calibrated at cold and are now marginal at hot — many controllers re-calibrate on temperature change, and if that's disabled or the re-cal threshold is too coarse, errors appear; (2) ODT and drive-strength settings that were tuned for nominal and drift with temperature; (3) a marginal power rail or reference that sags as the board heats; (4) a timing violation on a path that only fails at the slow corner. I'd check whether the controller supports periodic re-calibration and whether it's enabled, then sweep the leveling/deskew settings at temperature to see how much margin actually exists. If margin is thin, the fix is usually to widen it — adjust ODT, drive strength, or board-level termination — rather than to chase a phantom logic bug. I'd also verify the rail with a scope at temperature, because a drooping VTT or VREF is a classic warm-up failure.

**Possible follow-ups:** How would you distinguish a DRAM-side thermal issue from an FPGA-side one? What would you change in the calibration strategy to make it robust across temperature?

## Q3: How would you approach designing the decoupling and bulk capacitance network for an FPGA's transceiver power rails, where the rails see both high-frequency switching noise from the SerDes and slower, larger current transients from the fabric, and you need to verify the network is adequate before committing to the layout?

**Answer:** The transceiver rails are a two-timescale problem, so I'd design the network in layers matched to frequency. At the highest frequencies (hundreds of MHz to GHz), the SerDes switching current is supplied by the on-package and on-die capacitance plus the smallest board capacitors placed as close to the pins as physically possible — the loop inductance of the mount dominates, so placement and via count matter more than the nominal value. At mid frequencies, a spread of small-to-medium MLCCs (different values, low ESR) covers the impedance valley. At the low-frequency end, bulk capacitance (polymer/tantalum or larger ceramics) supplies the slower, larger fabric transients and holds the rail through the regulator's response time. The regulator's control loop bandwidth sets where bulk hands off to the converter.

Before committing to layout, I'd build a PDN impedance model: extract the plane capacitance and via/mount inductance, model the capacitor network with its ESR/ESL, and plot |Z| versus frequency against the target impedance derived from the allowed ripple and the worst-case transient current. The goal is no anti-resonance peaks above target across the band. I'd also check the regulator's transient response in simulation and confirm the bulk bank can hold the rail during the converter's slew. On the bench, the verification is a VNA-based impedance measurement on a bare or populated board plus a scope measurement of rail ripple under a representative SerDes traffic pattern — because the model is only as good as its parasitics.

**Possible follow-ups:** How do you handle the anti-resonance between two capacitor values, and what would you do if a peak exceeded target? How would you measure PDN impedance on a board that's already assembled?

## Q4: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?

**Answer:** A via that passes through a thick backplane but is only used for a layer transition leaves an unused "stub" — the portion of the barrel below (or above) the signal layer. At multi-gigabit rates that stub is a resonant transmission-line discontinuity: it produces a notch in the channel's insertion loss and a corresponding bump in return loss at a frequency set by the stub length and the board's effective dielectric constant. The longer the stub relative to the data rate's Nyquist, the worse it gets. So the first step is to quantify: estimate the stub length from the stack-up, compute the quarter-wave resonance, and compare it to the signal's spectral content. If the notch falls inside the band of interest, it must be addressed.

The primary mitigation is backdrilling — removing the unused barrel portion with a controlled-depth drill so the remaining stub is short enough that its resonance is pushed well above the band. The design must reserve backdrill clearance in the stack-up and coordinate with the fabricator on drill depth tolerance. Alternatives or complements: route the transition on a thinner region of the board, use blind/buried vias so the barrel doesn't span the full thickness, or use a via-in-pad / laser-drilled structure. On the channel-design side, I'd also consider whether the link's equalization (transmitter pre-emphasis, receiver CTLE/DFE) can absorb the residual loss, but I would not rely on EQ to fix a deep notch — it's better to remove the discontinuity. Verification is a 3D field-solver extraction of the via structure plus a channel simulation (eye diagram, BER) before layout sign-off.

**Possible follow-ups:** How would you decide the maximum allowable stub length for a given data rate? What fabrication tolerances would you specify for backdrill depth, and why?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?

**Answer:** I'd treat this as a review-and-verify situation rather than an accusation, because timing exceptions are legitimate tools — the problem is that they're also the easiest way to make a design "close" while hiding a real violation. My approach is to walk through each exception with the engineer and ask them to justify it from the design's functional intent, not from the tool's output. For a multicycle path, the justification has to be "the destination only samples this data every N cycles, and here is the logic that guarantees it" — and then I'd want to see that the multicycle setup/hold relationship is actually enforced in the RTL (e.g., an enable that gates the capture). For a false path, the justification has to be "these two domains are genuinely asynchronous and the crossing is handled by a proper synchronizer" — and then I'd want to confirm the synchronizer exists and is constrained correctly.

The failure mode I'm guarding against is an exception applied to a path that *does* need to meet timing, which produces a design that passes static timing analysis and fails in hardware. So I'd cross-check the exceptions against the CDC report and the functional spec, and I'd ask for the exceptions to be documented with a rationale and an owner. If an exception can't be justified, it comes out and we fix the real path — even if that means adding a pipeline stage or restructuring logic. I'd frame this to the engineer as "help me understand why this is safe," not "you cheated," because the goal is a correct design and a shared understanding of why the constraint is valid. If the engineer is junior, this is also a coaching moment about how timing exceptions are one of the highest-risk parts of an FPGA design flow.

**Possible follow-ups:** How would you audit a design's timing exceptions systematically before sign-off? What would you do if removing an unjustified exception made the design fail to close with the schedule already tight?
