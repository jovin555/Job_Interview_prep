# high-speed-digital-fpga — Day 32

## Q1: How would you approach debugging an FPGA design where the configuration bitstream loads successfully, but the design fails to respond to external interrupts — the interrupt line asserts on the PCB, but the FPGA logic never seems to see it?

**Answer:** I'd start by verifying the signal actually reaches the FPGA pin. First, probe the interrupt source at the FPGA package pin with an oscilloscope to confirm the signal is present with correct voltage levels, rise/fall times, and no excessive ringing or noise that could cause multiple edges. Next, I'd check the I/O bank configuration — if the pin is in a bank powered at a different voltage than the signal's logic levels, or if the input standard is misconfigured (e.g., LVCMOS33 vs LVCMOS25), the input buffer may never see a valid logic transition. I'd also verify that the pin isn't accidentally assigned as an output or a differential pair partner in the constraints file. Then I'd check the clock domain — if the interrupt input is sampled by a clock that isn't running (e.g., a gated clock or a PLL that hasn't locked), the synchronizer flip-flops will never capture the event. I'd also look at whether the interrupt is being masked or cleared by firmware before the FPGA logic can latch it. Finally, I'd use an integrated logic analyzer (ILA) core or a simple counter that increments on any edge of the interrupt pin to determine whether the pin is toggling at the FPGA fabric level. If the counter increments but the interrupt handler doesn't fire, the issue is in the logic or firmware; if it doesn't increment, the issue is in the I/O configuration or physical layer.

**Possible follow-ups:** How would you distinguish between a physical-layer issue and a logic-layer issue without an oscilloscope? What if the interrupt is asynchronous to your system clock — how would you handle the synchronization?

## Q2: How would you approach designing a write data path in an FPGA that must handle a continuous 256-bit data stream at 300 MHz and write it to DDR3 memory, where the memory bus is 64 bits wide at 600 MHz (DDR — 1200 MT/s effective)?

**Answer:** The fundamental challenge here is matching the data rate and width between the FPGA fabric and the memory interface. The fabric produces 256 bits at 300 MHz, which is 76.8 Gbps. The DDR3 interface at 64 bits and 1200 MT/s also provides 76.8 Gbps, so the raw bandwidth matches — but the real issue is burst efficiency and the memory controller's scheduling overhead. I'd structure the design with a wide FIFO on the fabric side to absorb burst mismatches. The write side of the FIFO accepts 256-bit words at 300 MHz; the read side presents data to the memory controller in the controller's native bus width and clock domain. The FIFO depth needs to account for worst-case latency through the memory controller — including refresh cycles, read/write turnaround, and bank conflicts — not just the average throughput. I'd also consider whether the memory controller can accept back-to-back writes at full efficiency; if not, the FIFO must be deep enough to buffer data during periods when the controller is busy with refreshes or reads. On the memory side, I'd use burst lengths of 8 (which is standard for DDR3) and ensure the controller is configured for the appropriate CAS latency and additive latency to maximize write efficiency. I'd also verify that the address mapping spreads consecutive addresses across different banks to minimize bank conflicts. If the average write rate is close to the theoretical maximum, I'd need to either reduce the fabric clock rate, widen the fabric interface, or use a memory with higher bandwidth — but if the average rate is below peak, a properly sized FIFO with careful burst management should suffice.

**Possible follow-ups:** How would you size the FIFO depth given a specific worst-case memory latency? What happens when a refresh command interrupts a long write burst — how does the controller handle that, and how does it affect your FIFO sizing?

## Q3: How would you approach verifying that a high-speed FPGA design will meet its timing requirements when you have a mix of logic operating at 200 MHz and 400 MHz, and the design includes paths that cross between these domains?

**Answer:** The first step is to properly constrain the design so the tools know the real timing requirements. I'd create a clock constraint for each clock domain, define the clock relationship between the 200 MHz and 400 MHz clocks (whether they're derived from the same PLL with a known phase relationship, or asynchronous), and explicitly constrain any cross-domain paths. If the clocks are synchronous (derived from the same source), I'd let the tools analyze the cross-domain paths with proper setup/hold checks. If they're asynchronous, I'd use clock domain crossing (CDC) synchronization — typically a two-flop synchronizer for single-bit signals or an asynchronous FIFO for multi-bit data — and then set false path constraints on the synchronizer input paths so the tools don't try to meet timing on paths that are inherently asynchronous. For the synchronous paths within each domain, I'd run timing analysis and review the worst negative slack (WNS) and total negative slack (TNS) reports. If there are violations, I'd look at the critical paths to understand whether they're logic-depth limited, routing limited, or caused by high fan-out. For logic-depth issues, I'd pipeline the datapath. For routing issues, I'd try floorplanning or adjusting synthesis options. For high fan-out, I'd replicate registers or use dedicated clock enable structures. I'd also run timing analysis at multiple process corners (slow-slow, typical, fast-fast) and across temperature/voltage variations, since a design that meets timing at one corner may fail at another. Finally, I'd verify the CDC paths with a dedicated CDC analysis tool or careful manual review to ensure no metastability issues can cause functional failures even if timing is met.

**Possible follow-ups:** How would you handle a situation where the 400 MHz clock is derived from the 200 MHz clock using a PLL with a known phase relationship — would you still use an asynchronous FIFO for the cross-domain paths? What if the cross-domain path carries a control signal that changes very infrequently?

## Q4: How would you approach designing a finite state machine (FSM) in an FPGA that must control a high-speed data path, where the FSM must be resilient to transient errors in its state registers (e.g., from radiation-induced upsets) without adding excessive logic or latency?

**Answer:** The key trade-off is between resilience and cost — both in logic resources and in the critical path. I'd start by classifying the FSM's states by criticality. For a high-speed data path controller, some states are safety-critical (e.g., a state that enables writing to memory or controls a hardware safety function) and others are less critical (e.g., a wait state). For the critical states, I'd consider triple modular redundancy (TMR) — three copies of the state register with a majority voter on the output. This adds roughly 3x the flip-flops and some voting logic, but it's the most robust approach for single-event upsets. For less critical states, I'd use a one-hot encoding with a "safe state" detection mechanism: if the FSM ever ends up in a state where more than one bit is set (or no bits are set), a watchdog circuit forces it back to a known reset state. This is much cheaper than TMR but only detects errors — it doesn't correct them. Another approach is to use a Hamming code on the state register to detect and correct single-bit errors, which is more efficient than full TMR for larger state machines. I'd also add a timeout watchdog on any state that involves waiting for an external event — if the FSM stays in that state too long, it's likely stuck due to an upset, and the watchdog forces a reset. For the voting logic in TMR, I'd place the voter carefully to avoid it becoming a single point of failure — ideally, the voter itself should be triplicated or at least implemented in a way that a single upset in the voter can't cause a wrong output. Finally, I'd verify the resilience approach through fault injection testing — flipping bits in the state registers in simulation to confirm the FSM recovers correctly.

**Possible follow-ups:** How would you decide between TMR and Hamming code protection for a given FSM? What about the output logic — if the state registers are protected but the combinational output logic is not, can an upset still cause a wrong output?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer on your team has implemented the data path that captures samples from a 500 MSPS ADC and writes them to DDR3 memory. During the review, you notice that the engineer has used a single FIFO to cross from the ADC clock domain to the memory controller clock domain, but the FIFO depth is only 64 words. When you ask about the depth, the engineer explains that the average write rate is well below the read rate, so the FIFO should never overflow. However, you're concerned about burst behavior — the ADC can produce bursts of data that could temporarily exceed the memory controller's sustainable write rate. The engineer argues that the memory controller's write buffer will absorb the bursts. How do you handle this situation?

**Answer:** I'd approach this as a coaching opportunity rather than simply overriding the engineer's decision. First, I'd acknowledge the valid part of their reasoning — average-rate analysis is a reasonable starting point, and the memory controller's write buffer does provide some burst absorption. Then I'd guide them through the worst-case analysis. I'd ask them to walk through the specific burst scenario: what's the maximum burst size the ADC can produce, what's the memory controller's sustainable write rate during a burst (accounting for refresh cycles, read/write turnaround, and bank conflicts), and how much buffering does the controller's write buffer actually provide? I'd suggest they model the worst-case latency — from the moment the FIFO is full and the ADC is still producing data, through the memory controller accepting the write, to the FIFO draining — and calculate whether 64 words plus the controller's write buffer is sufficient. I'd also point out that the FIFO depth isn't just about overflow — a shallow FIFO can cause the ADC to stall (if it has a backpressure mechanism), which could cause missed samples and corrupt the data stream. Rather than dictating the answer, I'd ask the engineer to come back with a worst-case analysis showing the required FIFO depth, and I'd offer to review their calculations. If their analysis shows 64 words is sufficient, I'd accept it with the caveat that we should add margin for temperature/voltage variations and silicon differences. If it shows more depth is needed, we'd discuss the options — deeper FIFO, a different memory controller configuration, or a rate-limiting mechanism on the ADC side. The goal is to teach the engineer to think in terms of worst-case behavior, not just averages, while keeping the design review collaborative rather than adversarial.

**Possible follow-ups:** How would you handle the situation if the engineer's worst-case analysis shows the FIFO needs to be 10x deeper, but the engineer is resistant because it will require a larger FPGA or a redesign of the data path? What if the project schedule is tight and the redesign would cause a delay?
