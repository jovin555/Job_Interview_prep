# high-speed-digital-fpga — Day 118

## Q1: How would you approach designing the power-up and reset release sequence for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?

**Answer:** The core principle is that reset is not a single event but a dependency graph, and the release order must follow that graph strictly. I'd start by enumerating every reset domain in the device — the configuration engine, the MMCM/PLL lock signals, the transceiver quad resets, the fabric global resets, and any soft-logic resets — and write down the dependency for each: what must be stable and locked before this domain may be released. Configuration must complete and the device must assert its init/done handshake before any PLL is asked to lock, because the PLL reference inputs and the MMCM primitive itself are only valid post-configuration. PLL lock must be qualified (not just the lock pin — a counter that confirms lock has been stable for a bounded number of reference cycles) before the transceiver quad reset is released, since the quad's PMA needs a clean, locked reference. Only after the quads report their reset-done and the TX/RX datapaths are out of reset should the fabric logic that consumes those links be released.

Implementation-wise, I'd build a small reset sequencer in fabric — a state machine clocked from a free-running oscillator or a dedicated always-on clock that doesn't depend on any PLL — that walks through the domains in order, with a timeout on each step. If a step doesn't complete within its budget (PLL fails to lock, quad doesn't report ready), the sequencer holds the downstream domains in reset and raises a fault rather than proceeding, because releasing downstream logic into an unlocked clock is exactly how you get the "configured but non-functional" failure. I'd also make the sequencer idempotent and re-runnable so a soft re-init can be triggered without a full power cycle. Finally, I'd verify the sequence in simulation with the vendor's reset models, and on hardware by scoping the reset lines and lock signals during bring-up to confirm the order actually holds across power ramp rates and temperature.

**Possible follow-ups:** How would you handle a PLL that occasionally takes much longer to lock at cold temperature — would you extend the timeout, or is a long lock time itself a symptom you'd investigate? How do you keep the reset sequencer itself immune to the clock domains it's controlling?

## Q2: How would you approach debugging an FPGA design where the transceiver link passes its built-in PRBS checker at the physical layer, but application-level data is occasionally corrupted, and the corruption only appears at full line rate?

**Answer:** The PRBS checker passing tells me the SerDes PMA and the serial channel are healthy — the eye is open, the CDR is locking, and the raw bit stream is clean. So the corruption is almost certainly above the PMA: in the PCS, the gearbox, the elastic buffer, or the user logic that frames and moves the data. The fact that it only appears at full line rate is the key clue — it points at something rate-dependent, like the elastic buffer's read/write pointer drifting, a clock correction / channel bonding issue, or a FIFO in the datapath that's being overrun or underrun when the sustained rate is high.

My approach would be to isolate layer by layer. First, I'd move the PRBS checker's insertion point up the stack — instead of checking at the PMA, check after the PCS and after the elastic buffer, so I can see whether errors appear before or after the rate-matching stage. If the elastic buffer is the culprit, I'd look at whether the clock correction sequences are being sent and consumed correctly, and whether the buffer depth and the ppm offset between the local and remote reference clocks are within budget. Second, I'd check the user-side FIFO: at full line rate, any backpressure or read-side stall that the average-rate analysis missed will show up as overflow, so I'd instrument the FIFO's almost-full/almost-empty flags and count overflow events. Third, I'd look at the framing/gearbox logic for a width-conversion bug that only manifests when the data is continuous — idle insertion or a mis-sized gearbox can drop or duplicate words only when there's no gap to absorb the mismatch. I'd also confirm the reference clock ppm budget and the transceiver's clock correction settings, because a marginal ppm offset that's fine at low rate can cause periodic buffer slips at full rate. Throughout, I'd use the transceiver's built-in eye scan and error counters as a baseline, and add fabric-side error counters at each stage so I can localize the first point of corruption rather than guessing.

**Possible follow-ups:** How would you distinguish an elastic-buffer slip from a genuine bit error using only the transceiver's status registers? If the corruption turns out to be a FIFO overflow in user logic, how would you size that FIFO correctly given a bursty but bounded traffic profile?

## Q3: How would you approach designing the return-current path for a high-speed digital board where a signal transitions between two reference planes (e.g., from a ground plane to a power plane) on its way through a via?

**Answer:** The governing principle is that every signal current has a return current that follows the path of least impedance, and at high frequency that return current wants to flow on the reference plane directly beneath the trace. When a signal via transitions from a layer referenced to ground to a layer referenced to a power plane, the return current has to jump from the ground plane to the power plane — and if there's no low-inductance path for it to do so, it will find a long, indirect route, creating a loop that radiates and a discontinuity that degrades the signal.

The standard fix is to provide a deliberate return path at the transition: place a stitching capacitor (or a cluster of them, with low ESL and placed as close to the signal via as physically possible) between the ground and power planes adjacent to the signal via, so the return current can hop planes through the capacitor with minimal loop area. The capacitor value matters less than the placement and the mounted inductance — a 0.1 µF part with a long trace to the via is worse than a smaller part placed right at the via. Where the transition is between two ground-referenced layers, a ground stitching via adjacent to the signal via is the equivalent fix. I'd also consider whether the transition can be avoided entirely by keeping high-speed signals on layers referenced to the same plane for their whole run, and reserve plane transitions for slower signals.

In layout review I'd check every high-speed via for an adjacent return via or stitching cap, verify the plane pair being transitioned has decoupling nearby, and confirm the return path doesn't have to cross a plane split. In simulation, I'd look at the via transition in a 3D field solver or at least a 2D extraction to see the impedance bump, and on hardware I'd look for the signature — a resonance or a rise in radiated emissions at the transition — with a near-field probe.

**Possible follow-ups:** How would you decide between a stitching capacitor and a ground-to-ground via for a given transition? What's the risk of placing the stitching capacitor too far from the signal via, and how would you quantify "too far"?

## Q4: How would you approach choosing between a global clock network and a regional/banked clock resource for a logic block that only needs to run at a modest rate, when the device's global clock resources are nearly exhausted?

**Answer:** The decision hinges on what the block actually needs from its clock, not on the clock's frequency alone. Global clock networks buy you low skew across the whole die and the ability to reach any register, but they're a scarce resource and they carry a power cost because they drive a large capacitive tree. Regional/banked resources reach only a portion of the device but are cheaper in both resource and power, and for a modest-rate block that's physically localized, they're usually the right answer.

My reasoning order: first, does the block's clock need to reach registers spread across the die, or is the block confined to one clock region? If it's confined, a regional buffer is a natural fit. Second, does the block's timing budget actually depend on low skew across the die, or is it a self-contained synchronous block where local skew is fine? Third, is the clock a candidate for local routing entirely — if the block is small and slow, a locally routed clock (with the caveat that it won't get the dedicated low-skew network and the tools may not guarantee skew) can free a global resource at the cost of tighter physical constraints. Fourth, I'd check whether the block can share an existing global clock that's already running at a compatible frequency, which is often the cheapest answer of all.

The trade-offs to weigh: regional buffers may limit placement flexibility and can complicate timing closure if the block later grows beyond one region; local routing gives the least skew guarantee and should be used only where the timing margin is generous. I'd also confirm the vendor's rules on which buffers can drive which resources — some regional buffers can't reach certain dedicated pins or transceiver references. Finally, I'd let the tool report resource utilization after implementation and revisit if the global budget is still tight.

**Possible follow-ups:** What are the failure modes of using a locally routed clock for a block that later needs to interface to a global-clock domain? How would you migrate a block from a regional to a global clock late in the design if timing forced it?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?

**Answer:** I'd treat this as a teaching moment first and a correction second, because the engineer's reasoning — "it's stable long enough" — is a very common and very dangerous intuition, and the goal is for them to internalize why it's wrong rather than just accept a fix. In the review, I'd ask them to walk me through the timing: how long is the signal stable relative to the destination clock period, and what happens if the destination clock edge lands inside the setup/hold window? The point I'd make is that "stable long enough" addresses the functional value but not the metastability risk — a direct connection can still capture a metastable value at the destination flop, and that metastability can propagate into downstream logic and produce a failure that's rare, temperature- and voltage-dependent, and essentially impossible to reproduce in simulation. The fact that it works in the lab is not evidence; it's a sample of one.

Then I'd move to the fix: for a single-bit control signal, a two-flop synchronizer in the destination domain is the standard minimum, with the caveat that the signal must be stable for at least a couple of destination clock cycles for the synchronizer to be valid — if it's a pulse, it needs a pulse-stretcher or a toggle/handshake scheme instead. For multi-bit buses, a two-flop-per-bit synchronizer is not sufficient and we'd need a proper CDC structure (gray coding, handshake, or an async FIFO). I'd ask them to add the synchronizer, document the CDC in the design, and add a CDC lint check to the flow so this class of issue is caught automatically going forward. I'd frame the lint rule as a team improvement, not a personal criticism, and follow up in the next review to confirm the fix and that they understand the reasoning.

**Possible follow-ups:** How would you handle the case where the signal is a single-cycle pulse in the source domain — what changes about the synchronization scheme? What CDC verification would you add to the design flow so this is caught before review rather than during it?
