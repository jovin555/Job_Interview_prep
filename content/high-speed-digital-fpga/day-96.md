# high-speed-digital-fpga — Day 96

## Q1: How would you approach designing the power-up and configuration sequence for an FPGA that loads its bitstream from external flash, when the flash device itself has a non-trivial access latency and the board may be power-cycled rapidly?

**Answer:** The core problem is that configuration is a multi-rail, multi-device handshake, and rapid power cycling can catch any stage of it mid-flight. I'd start by defining the sequence explicitly rather than letting it emerge from whatever the rails happen to do. First, establish the rail ramp order and the "power good" thresholds for each rail — the FPGA's configuration logic must not be released until all rails it depends on (core, auxiliary, and the I/O bank that hosts the configuration pins) are valid and stable, not merely above some loose threshold. I'd use a supervisor or sequencer with defined thresholds and delays rather than relying on RC ramp behavior, because RC timing drifts with temperature and component tolerance.

Second, the flash device's wake-up and access latency has to be respected. Many serial configuration flashes need a power-on delay plus a status-poll before they'll respond, and if the FPGA starts clocking the configuration interface before the flash is ready, it reads garbage or hangs. The clean approach is to gate the start of configuration on a flash-ready signal — either a dedicated ready/busy line if the part has one, or a fixed worst-case delay derived from the datasheet across the full temperature range, with margin. I'd rather add a few hundred milliseconds of deliberate delay than race the flash.

Third, rapid power cycling is the real stress case. The danger is a brownout where the FPGA has partially configured, the rails dip, and the device re-enters configuration while the flash is still mid-transaction or while its internal state machine hasn't reset. I'd add a proper brownout detector that holds the FPGA in reset until all rails have fallen below their reset thresholds and then re-ramped cleanly — a "power-good must go low and come back high" interlock rather than a simple threshold. On the flash side, I'd make sure the configuration controller issues a clean reset/abort to the flash on every power-up rather than assuming it's in a known state.

Finally, I'd verify the whole thing on the bench with a programmable supply that can produce fast ramp-down/ramp-up cycles and brownout dips at various points in the configuration window, and I'd instrument the init/done handshake so I can see exactly where a failed cycle stopped. The design goal is that any power cycle, however ugly, resolves to either a fully configured device or a held-in-reset device — never a half-configured one.

**Possible follow-ups:** How would you decide between a dedicated supervisory IC and an FPGA-internal power-good monitor for this sequencing? What would you do if the flash's worst-case wake-up latency plus the FPGA's configuration time exceeded the system's boot-time budget?

## Q2: How would you approach designing the clock domain crossing for a multi-bit control word that is written by a slow serial interface (e.g., 10 MHz SPI) and consumed by a fast logic domain (e.g., 250 MHz), where the word changes infrequently but must never be observed in a partially updated state?

**Answer:** The key insight is that the word changes infrequently, so throughput is irrelevant and the only real requirement is atomicity — the consumer must see either the old word or the new word, never a mix of bits captured mid-update. That rules out per-bit two-flop synchronizers, which are fine for single bits but give no coherence guarantee across a bus.

The standard robust approach is a handshake-based transfer: the slow domain assembles the full word in a register, then toggles a request flag (a single bit, synchronized into the fast domain with a two-flop synchronizer). The fast domain sees the request toggle, captures the entire data bus in one clocked register, and returns an acknowledge toggle. Because the data bus is stable from the moment the request is asserted until the acknowledge comes back, the fast domain's single-register capture always sees a coherent word. The toggle (rather than a level) is important because it works correctly even if the request is asserted again before the acknowledge returns — each toggle is one transaction.

An alternative worth mentioning is a dual-clock or asynchronous FIFO, but for a single infrequently-updated control word that's overkill and adds latency and resource. A third option is a "shadow register + commit" scheme: the slow side writes a staging register and asserts a commit strobe, and the fast side loads the shadow into the active register on the synchronized commit. This is essentially the handshake with a different name and is a good pattern when there are several related words that must update together.

I'd also think about reset and initial state: the fast domain must come out of reset with a defined value, not an X, and the handshake must be initialized so the first transaction isn't lost. And I'd constrain the CDC in the timing tool — mark the data bus as a false path or use the tool's CDC constraints so the static timing analysis doesn't try to time a path that's intentionally asynchronous, while keeping the synchronizer flops properly constrained.

**Possible follow-ups:** How would you extend this to a group of control words that must all update atomically together? What CDC verification would you run to prove the synchronizers are correct before tape-out?

## Q3: How would you approach mitigating via stub effects on a high-speed serial channel that must transition between the top and bottom layers of a thick backplane?

**Answer:** A via through a thick backplane is a stub — the unused portion of the barrel below the layer where the signal enters or exits behaves as an open-circuited transmission line, and at multi-gigabit rates its resonance and the reflections it causes can close the eye. The first thing I'd do is quantify it: stub length times the board's propagation velocity gives the electrical length, and I'd compare the quarter-wave resonance against the channel's Nyquist frequency. On a thick backplane a through-via can easily be tens of mils of stub, which is significant at 10 Gbps and above.

The primary mitigation is to avoid the stub in the first place. Back-drilling removes the unused barrel below the signal layer, which is the most effective fix and is standard practice on thick backplanes for high-speed channels. The trade-off is cost and process control — back-drill depth tolerance matters, and you need to leave enough barrel for reliable plating. If back-drilling isn't available, blind or buried vias eliminate the stub by construction, at higher fabrication cost.

If the stub can't be removed, the next lever is to make it less harmful: use a via with a smaller barrel and pad (less capacitance), or add a "stub-tuning" structure — a short trace or a deliberate impedance at the stub end — though that's fiddly and layout-sensitive. Another approach is to keep the channel's loss budget generous enough (better connector, lower-loss material, or a retimer) that the stub-induced reflection is absorbed within margin. I'd also make sure the return path is continuous through the via transition — ground vias placed close to the signal via so the return current has a short path between reference planes, which reduces the discontinuity the stub sees.

Verification-wise, I'd extract the via with a 3D field solver and fold it into the channel simulation rather than trusting a rule of thumb, because stub effects are geometry-specific. Then confirm on the bench with TDR to see the actual impedance profile and with an eye-diagram/PRBS test at the target rate.

**Possible follow-ups:** How would you decide how much back-drill depth margin is acceptable given plating and depth tolerances? What does the TDR signature of a resonant stub look like, and how would you distinguish it from a connector discontinuity?

## Q4: How would you approach designing a spread-spectrum clocking scheme for a high-speed digital board where several clock sources (processor, FPGA, and a high-speed serial reference) must coexist, and you need to reduce radiated emissions without breaking the serial links?

**Answer:** Spread-spectrum clocking (SSC) reduces peak radiated emissions by deliberately modulating the clock frequency over a small range so the energy is smeared across a band instead of concentrated at a single harmonic. The benefit is real, but it interacts badly with anything that depends on a clean, stable frequency reference — which is exactly the risk with high-speed serial links.

The first decision is which clocks get spread and which don't. The serial reference is the sensitive one: many SerDes protocols assume a relatively clean reference, and if the transmitter and receiver aren't both tracking the same spreading profile, the SSC shows up as excessive jitter or as a frequency offset the CDR has to chase. So I'd generally not spread the serial reference unless the protocol explicitly supports SSC (some do, with defined down-spread profiles and limits). Instead I'd spread the processor and FPGA system clocks — the ones whose harmonics are the actual emission offenders — and keep the serial reference clean, or spread it only within the protocol's specified tolerance.

The second decision is the modulation profile and depth. Down-spread (modulating below the nominal frequency) is common because it keeps the average frequency at or below nominal, which is friendlier to timing. The modulation rate is chosen to be well outside the loop bandwidths of the PLLs that will track it — too fast and the PLL can't follow, producing jitter; too slow and you get audible/measurable tonal artifacts. I'd pick a modulation frequency and depth from the clock generator's supported profiles and verify against each PLL's tracking characteristics.

The third piece is verification. I'd confirm the emission reduction with a spectrum scan in a pre-compliance setup, and separately confirm the serial links still pass their BER/eye tests with the spreading active — because the failure mode is subtle (margin erosion, not outright link failure). I'd also check that any clock that feeds an ADC or other jitter-sensitive converter isn't spread, since SSC directly adds jitter that degrades SNR.

**Possible follow-ups:** How would you determine whether a given SerDes protocol tolerates SSC on its reference, and what would you check in the datasheet or spec? What's the risk of spreading a clock that feeds a PLL with a narrow loop bandwidth?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?

**Answer:** I'd treat this as a review-quality issue first and a people issue second, and I'd be careful not to frame it as "you cheated" — timing exceptions are a legitimate and necessary part of closing a design, and the engineer may well be right that some of them are correct. The problem is that exceptions are also the easiest way to make a design "close" while hiding a real failure, so each one has to be justified individually rather than accepted as a set.

My approach in the review would be to go through the exceptions one at a time and ask a simple question for each: what is the physical or architectural reason this path doesn't need single-cycle timing, and what is the evidence? For a genuine multicycle path, the evidence is that the destination register is enabled only every N cycles and the logic is structured that way — I'd want to see the enable logic and confirm the exception matches the actual data behavior. For a false path, the evidence is that the two endpoints are genuinely asynchronous or that the path is structurally unreachable — and for asynchronous crossings, the correct treatment is a CDC constraint plus a synchronizer, not just a false path that silences the tool. A false path on a path that actually carries synchronous data is a latent bug that will show up as an intermittent failure in hardware, which is exactly the kind of thing that's brutal to debug.

I'd also check the process around the exceptions: are they documented with a reason and an owner, are they reviewed by someone other than the author, and is there a CDC/exception lint step in the flow that flags exceptions added without justification? If the team doesn't have that discipline yet, this review is a good moment to introduce it — a short written justification per exception, reviewed at sign-off, catches most of these before they become hardware failures.

On the interpersonal side, I'd make it collaborative: "help me understand why this one is safe" rather than "remove this." If the engineer can justify it, great — it goes in the record. If they can't, that's the learning moment, and it's much more effective coming from the engineer's own attempt to explain it than from me asserting it. I'd also follow up by asking them to re-run closure with the questionable exceptions removed to see whether the design actually fails or whether the exception was unnecessary — sometimes it is, and that's useful information either way.

**Possible follow-ups:** How would you distinguish a legitimate multicycle path from one that's masking a real timing failure? What would you put in place so timing exceptions get reviewed consistently across the team rather than case by case?
