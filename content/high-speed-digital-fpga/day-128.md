# high-speed-digital-fpga — Day 128

## Q1: How would you approach designing the power-up and reset release sequence for an FPGA whose configuration engine, PLLs, and transceiver quads must all come up in a defined order, where an out-of-order release can leave the device configured but non-functional?

**Answer:** I'd treat this as a state-machine problem driven by *observed* conditions rather than fixed delays. The sequence starts with the power rails: each rail has a required ramp order and a minimum ramp time, and the sequencer should not release the next rail until the previous one is above its power-good threshold and has settled. Once all rails are good, the FPGA's configuration engine is released — but the key discipline is to wait for the *actual* configuration-done signal from the device, not a timer, because configuration time varies with bitstream size and clock source.

After configuration, the PLLs and MMCMs are brought up one at a time. Each PLL has a lock signal, and the design should gate downstream logic on lock *and* on a stable-lock qualifier — lock can assert momentarily during acquisition, so a short counter that confirms lock has held for N reference cycles is worth the small cost. Only after all PLLs are locked and their output clocks are stable does the transceiver quad come out of reset. Transceivers typically need their reference clock running and stable before the quad reset is released, and the reset pulse itself has a minimum width specified by the vendor — that width should be generated from a known-good clock, not an RC delay.

The critical insight is that each stage's release condition must be a *measured* signal (power-good, config-done, PLL-lock, clock-stable), and the whole chain should be observable — status bits readable over a debug interface so that a board that comes up non-functional can be diagnosed by seeing exactly which stage never completed. I'd also add a watchdog: if the sequence doesn't complete within a generous timeout, force a full reconfiguration rather than sitting in a half-initialized state.

**Possible follow-ups:** How would you handle a PLL that locks but then loses lock intermittently during operation — should that trigger a full re-sequence or just a local reset? And how would you make the sequencer itself robust against a glitch on one of the power-good signals?

## Q2: How would you approach debugging an FPGA design where the DDR3 interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** A warm-up-correlated failure points strongly at a timing margin that is adequate at room temperature but consumed as the die and board heat up. The first thing I'd do is separate the two heat sources: the FPGA die and the DRAM/board. Running the same workload with the FPGA held cool (or with the DRAM locally heated) tells you which side is drifting.

On the FPGA side, the usual suspects are the read capture window and the write leveling/read leveling results. Calibration performed cold establishes a delay tap setting that may sit near the edge of the valid window; as temperature rises, the internal delay lines and the I/O timing shift, and the window moves out from under the tap. I'd re-run calibration at temperature and compare the tap values to the cold values — a large shift, or a tap that lands near the window edge, confirms the theory. The fix is usually to center the tap in the window rather than take the first passing tap, and to re-calibrate periodically or on temperature change if the interface supports it.

On the board side, I'd look at the reference voltage and termination: VREF generated by a resistor divider drifts with temperature, and ODT settings interact with board impedance. I'd also check the power integrity of the DDR rail — as the FPGA draws more current when warm, rail droop can eat margin.

The debugging method matters as much as the suspects: I'd build a stress pattern that exercises the interface hard (not just a march test) and log the failing address/bit pattern, because a data-dependent failure points at crosstalk or a specific lane, while a random failure points at a global timing margin issue. Temperature correlation plus pattern correlation usually narrows it to one mechanism quickly.

**Possible follow-ups:** If re-calibration at temperature fixes it, how do you decide whether to re-calibrate periodically in the field versus just widening the initial margin? And what would a failing checkerboard-but-not-all-zeros pattern tell you?

## Q3: How would you approach designing the interface between an FPGA and an external ADC that uses a source-synchronous, double-data-rate output bus, where the data and a forwarded clock arrive at the FPGA with an unknown but bounded skew?

**Answer:** The core problem is that the forwarded clock and the data have a bounded but unknown phase relationship, so the capture must be robust across that entire skew range plus PVT variation. I'd start by characterizing the skew budget: the ADC's output skew spec, the PCB trace-matching tolerance, and the FPGA's input timing uncertainty all add up, and that total must fit inside one bit period with margin left over.

The standard approach is to capture the data with an IDELAY or similar programmable delay on either the clock or the data lanes, and to *train* the delay rather than fix it. The training works by sweeping the delay tap across its range and finding the window where the captured data matches a known pattern; the operating tap is then set to the center of that window, not the first passing tap. Centering is what buys margin against temperature and voltage drift.

Two details matter a lot. First, per-lane skew: even with matched traces, the FPGA's own input paths differ lane to lane, so each data lane should be trained independently rather than assuming one delay works for all. Second, the training pattern must exercise the worst case — alternating patterns and PRBS-style patterns catch ISI and crosstalk effects that a simple walking-ones pattern misses.

I'd also decide early whether to use the FPGA's dedicated source-synchronous capture resources (ISERDES with bitslip) or a generic IDELAY approach; the dedicated path handles the DDR deskew and word alignment more cleanly, but constrains which pins can be used. And the whole scheme needs a defined behavior if training fails — the interface should flag it rather than run with a bad tap.

**Possible follow-ups:** How would you handle the case where the training window is so narrow that centering still leaves inadequate margin — what are your options? And how do you verify the training logic itself is correct before you trust it on hardware?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?

**Answer:** The trap is trusting a clean timing report as evidence of correctness — a report only proves the constraints you gave it were met, not that the constraints describe the real hardware. So the verification has to attack the constraints themselves, not just the results.

I'd start with a constraint-coverage review: enumerate every clock in the design (including generated clocks from PLLs and MMCMs, and any clocks coming in from external devices), every I/O interface, and every clock-domain crossing, and confirm each has an explicit constraint. The dangerous gaps are usually generated clocks that were never derived, I/O paths constrained with a default that doesn't match the external device's actual timing, and CDC paths that were silently excluded rather than properly synchronized.

Then I'd audit every timing exception. False paths and multicycle paths are where designs get "closed" dishonestly — each one needs a written justification tied to a real architectural reason, and I'd want to see that the exception was reviewed by someone other than the person who added it. A false path on a path that actually carries data is a latent hardware failure.

I'd also cross-check with the CDC tooling: run the vendor's or a third-party CDC checker and treat every reported unsynchronized crossing as a finding to resolve, not a warning to suppress. And I'd compare the constraint set against the interface timing budgets derived from the external device datasheets — the numbers in the SDC should trace back to those budgets.

Finally, I'd want the constraints under version control with the RTL, and a regression that re-runs timing analysis on every build so a constraint change can't slip in unnoticed.

**Possible follow-ups:** How would you handle a disagreement where a designer insists a multicycle path exception is legitimate but can't point to the architectural reason? And what's your approach when the CDC tool reports thousands of crossings — how do you triage?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented the data path that captures samples from a high-speed ADC and writes them to DDR memory. During the review, you notice they've sized the capture FIFO from the average throughput rather than the worst-case burst, arguing that "the average rate is well below the memory bandwidth, so it can't overflow." How do you handle this situation?

**Answer:** I'd treat this as a teaching moment rather than a correction, because the underlying reasoning error — sizing a buffer from average rate instead of worst-case burst — is one that shows up repeatedly in high-speed design, and the engineer needs to internalize *why* it's wrong, not just fix this one FIFO.

In the review itself, I'd walk through the arithmetic with them rather than assert the conclusion. The FIFO depth has to cover the maximum *accumulated* difference between the write rate and the read rate over any interval, not the average difference. If the ADC can produce a burst that the memory controller can't absorb at that instant — because the controller is arbitrating, refreshing, or servicing a read — the FIFO fills at the burst rate, and the question is how deep it gets before the controller catches up. I'd ask them to construct the worst-case burst profile and compute the required depth from it, including the memory controller's own write buffer as part of the analysis rather than as a magic absorber.

I'd also make the point that "it works in simulation" is weak evidence here, because the simulation's traffic pattern is probably not the worst case. The right verification is a directed test that drives the maximum burst the ADC can produce against a memory controller model that includes refresh and arbitration.

Then I'd close the loop: have them revise the sizing with the worst-case analysis, and add the directed burst test to the regression so the assumption is checked going forward. The goal is that the next time they size a buffer, they reach for the burst analysis first.

**Possible follow-ups:** If the worst-case analysis shows the required FIFO depth is larger than the available block RAM, what trade-offs would you discuss with them? And how would you handle it if the engineer remained convinced the average-rate argument was sufficient?
