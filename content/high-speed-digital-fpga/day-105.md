# high-speed-digital-fpga — Day 105

## Q1: How would you approach designing the reset architecture for an FPGA design that spans several clock domains, a memory controller, and high-speed serial links, where an improperly sequenced reset can leave the device in a non-functional state?
**Answer:** I'd treat reset as a first-class architectural concern rather than an afterthought. The core principle is that every clock domain must receive a reset that is *synchronized to that domain's own clock* — an asynchronous assert, synchronous de-assert is the standard pattern, because releasing reset asynchronously risks different flops leaving reset on different cycles, which can put state machines into illegal states or cause a CDC handshake to start mid-transaction. I'd define a single reset source (external reset pin, power-good supervisor, or a soft reset from a control register) and then fan it out through per-domain reset synchronizers. Beyond that, I'd define a deliberate *ordering*: bring up the reference clocks and PLLs first and wait for lock, then release the reset on the clock-generation and CDC logic, then the memory controller (which needs its own calibrated, stable clock before it can train), then the transceiver links, and only then the application logic that depends on all of them. The serial links in particular need their reset released in coordination with the link-training state machine, otherwise you can get a link that reports up but never completes alignment. I'd also make sure the reset tree itself is glitch-free and that any reset crossing between domains goes through a proper synchronizer, not a raw wire. Finally, I'd verify it — both in simulation with randomized reset-release timing across domains, and on hardware by deliberately exercising partial resets and rapid power cycles to confirm the design always converges to a known state.

**Possible follow-ups:** How would you handle a soft reset that only affects the application logic without disturbing the already-trained memory and serial links? What would you check first if a board occasionally comes up with the transceiver link down after a fast power cycle?

## Q2: How would you approach debugging an FPGA design where the timing analysis reports all constraints met, but the design fails in hardware only at the maximum specified junction temperature?
**Answer:** A clean timing report at the nominal corner but failure at max junction temperature points to something the static timing analysis isn't capturing, or a margin that's been eaten by a real physical effect. My first move is to confirm the report was actually generated at the *worst-case* corner for the failing condition — slow-slow process, minimum voltage, maximum temperature — because a report at typical or fast corner tells you very little about hot operation. If the corner is right and it still passes, I'd suspect the constraint set is incomplete: missing I/O timing constraints, false paths that were over-applied, or generated clocks that weren't properly defined, so real paths are being excluded from analysis. Beyond constraints, temperature-dependent effects are the prime suspect: on-die variation shifting delay, a PLL or MMCM whose lock or jitter degrades hot, or a power delivery network whose impedance rises with temperature so the core rail sags more under transient load. I'd instrument the design — internal logic analyzers or a lightweight on-chip monitor — to see *where* it fails hot: is it a specific interface, a specific state machine, or a broad data corruption pattern? I'd also check whether the failure correlates with a particular clock domain or I/O bank, which narrows it to a clocking or signaling issue versus a logic issue. If it's marginal timing, the fix is usually to add pipeline margin on the critical paths or relax the clock, but I'd want to understand the mechanism before changing anything, because "it works when we slow it down" is a diagnosis, not a fix.

**Possible follow-ups:** How would you distinguish a genuine timing marginality from a power-integrity-induced failure at temperature? What would you do if the design passes at the slow corner but the failure only reproduces on a subset of boards?

## Q3: How would you approach designing the interface between an FPGA and an external ADC that uses a source-synchronous, double-data-rate output bus, where the data and a forwarded clock arrive with an unknown but bounded skew?
**Answer:** The key insight with a source-synchronous DDR interface is that the forwarded clock travels with the data, so the FPGA doesn't need to guess the absolute arrival time — it needs to capture each data bit at the center of its valid window, accounting for the bounded skew between clock and data and for the fact that DDR means two bits per clock period. I'd start by characterizing the skew budget: the ADC's specified clock-to-data skew, the PCB trace-length matching tolerance, and the FPGA's input setup/hold requirements, and confirm the total window is positive with margin across PVT. Then I'd use the FPGA's dedicated input delay/IDELAY resources (or the equivalent in the target family) to shift the capture point to the center of the eye, and I'd plan for per-bit or per-lane deskew if the skew is large enough that a single global delay won't cover all bits. The forwarded clock itself needs to be routed on a clock-capable pin and treated as a proper clock, not as data. I'd also consider whether the interface should be trained at startup — sweeping the delay taps and checking for a known pattern — versus fixed at a calculated value, because training buys margin against board-to-board variation at the cost of boot time and complexity. On the PCB side, I'd match trace lengths within the skew budget, keep the clock and data referenced to a continuous ground plane, and avoid layer transitions that introduce skew. Verification would include a margin test: sweep the delay tap across its range and confirm the interface works across a window, not just at one setting.

**Possible follow-ups:** How would you decide between a fixed delay setting and a runtime-trained one for a production board? What would you check if the interface works at room temperature but fails at temperature extremes?

## Q4: How would you approach choosing between a global clock network and a regional/banked clock resource for a logic block that only needs to run at a modest rate, when the device's global clock resources are nearly exhausted?
**Answer:** The decision comes down to what the block actually needs from its clock and what the global network is buying you. Global clock networks are designed for low skew and fan-out across the whole device, which matters when a clock drives logic spread across many regions or when skew between endpoints would break timing. A regional or banked clock resource has more limited reach but is perfectly adequate — and often preferable — for a self-contained block whose logic is physically localized, especially at a modest rate where skew is a small fraction of the period. So my first question is: is this block's logic confined to one region, and does it communicate with the rest of the design only through a small number of synchronized interfaces? If yes, a regional clock is a clean fit and frees a global resource for something that genuinely needs it. The trade-offs I'd weigh: regional clocks may have different jitter or duty-cycle characteristics, they may not be reachable from every clock source (some PLL/MMCM outputs only route to certain networks), and if the block later grows or moves during placement, a regional clock could become a constraint. I'd also check whether the block could simply *share* an existing global clock — if two blocks run at the same frequency and don't need to be phase-independent, sharing one global network is usually simpler than adding a second clock. The worst outcome is burning a global resource on a block that didn't need it and then being unable to clock something that does.

**Possible follow-ups:** What are the risks of moving a block to a regional clock late in the design cycle? How would you verify that a regional clock's skew is acceptable for the block's timing?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?
**Answer:** I'd treat this as a teaching moment first, because the engineer's reasoning contains a real grain of truth that's worth acknowledging before correcting. A signal that's stable for many destination clock cycles *will* usually be captured correctly — the problem is "usually" isn't a guarantee, and the failure mode is a metastable event that occurs rarely, unpredictably, and often only in the field at temperature or voltage extremes. So I'd start by asking them to walk me through the timing: how long is the signal stable relative to the destination clock period, and what happens if the destination clock edge lands exactly on the transition? That usually surfaces the gap in the reasoning without me having to assert it. Then I'd explain the standard fix — a two-flop synchronizer for a single-bit level signal, or a proper handshake or asynchronous FIFO if the signal carries multi-bit data or needs to be acknowledged — and note that the cost is one or two flops and a cycle of latency, which is almost always acceptable for a control signal. I'd also point out that this is exactly the kind of thing a CDC lint tool or a formal CDC check would flag, and that we should be running those checks as part of the review process so this class of issue is caught systematically rather than relying on reviewer vigilance. I'd want the engineer to own the fix and add a CDC constraint or waiver annotation so the tooling stays clean and the intent is documented. The goal is that they leave understanding *why* the rule exists, not just that they were told to add flops.

**Possible follow-ups:** How would you handle it if the engineer pushed back and said the synchronizer adds latency the control loop can't tolerate? What process change would you make so this kind of issue is caught before design review rather than during it?
