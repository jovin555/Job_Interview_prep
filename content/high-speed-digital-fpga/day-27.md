# high-speed-digital-fpga — Day 27

## Q1: How would you approach designing a clock domain crossing (CDC) scheme for a multi-bit data bus where the source and destination clocks are asynchronous, the data changes frequently, and you need to minimize latency while ensuring data integrity?

**Answer:** This is a classic asynchronous CDC problem where you can't use simple multi-flop synchronizers (they only work for single-bit signals) and you can't rely on gray coding (data changes frequently and isn't sequential). The key tension is between latency and safety.

My first step would be to characterize the requirements precisely: What's the acceptable latency? What's the data rate? Can we tolerate occasional dropped or repeated samples, or must every value be delivered exactly once?

For a frequently-changing multi-bit bus with minimal latency, I'd typically use an asynchronous FIFO with gray-coded pointers. The write side pushes data with its write clock, the read side pops with the read clock, and the full/empty flags are generated by synchronizing gray-coded pointers across the boundary. Gray coding ensures that only one bit changes at a time when the pointer increments, so the synchronizer can't capture a partially-updated pointer value. The FIFO depth needs to be sized based on the worst-case rate mismatch and burst behavior — not just the average rates.

If the data is truly continuous and latency must be absolutely minimized, another option is a handshake-based approach (four-phase or two-phase protocol) where the source asserts a request, the destination acknowledges, and data is held stable until the handshake completes. This adds more latency per transfer but guarantees no data loss. For higher throughput, you can pipeline the handshake.

The critical thing I'd verify is that the gray-code pointer comparison for full/empty generation is correct across all corner cases — particularly when the FIFO is nearly full or nearly empty, where a metastable pointer read could cause a false full or false empty indication. I'd also run formal CDC verification or at least extensive simulation with randomized clock phase relationships to prove the design is robust.

**Possible follow-ups:** How would you size the FIFO depth for this scenario? What happens if the write side bursts data faster than the read side can drain it?

## Q2: How would you approach debugging an FPGA design where the configuration bitstream loads successfully, but the design functions correctly at room temperature and fails only when the board is heated to its maximum specified operating temperature?

**Answer:** Temperature-dependent failures that appear only at the high end of the operating range usually point to one of several root causes: timing margin degradation, power supply issues, or component parametric drift.

My approach would be systematic. First, I'd try to narrow down whether the failure is in the FPGA logic itself or in the external interface. If I can observe which signals are failing (via embedded logic analyzers, ILA cores, or by capturing data at different points in the datapath), that tells me where to focus.

The most common cause is marginal timing. At elevated temperature, transistor switching speeds slow down, reducing setup and hold margins. If the design passed timing closure with little margin at the slow-slow corner, the actual silicon at temperature might be right at the edge. I'd check the timing reports for paths with the least slack, particularly paths that cross clock domains or involve external I/O where board-level delays (trace length, loading) add uncertainty. I'd also verify that my timing constraints accurately model the board delays — an unconstrained or incorrectly constrained I/O path is a prime suspect.

Second, I'd check the power supplies. Voltage regulators have thermal coefficients, and a supply that's marginally regulated at room temperature can droop further at temperature, especially under load. I'd measure the actual rail voltages at the FPGA pins at temperature, looking for droop below the device's minimum operating voltage. I'd also check for excessive ripple or noise that could be exacerbated by thermal effects on decoupling capacitors (capacitance decreases with temperature for some dielectric types).

Third, I'd consider external components: series termination resistors, pull-ups, clock oscillators. An oscillator's frequency can drift with temperature, and if the system has a PLL multiplying that reference, the drift is multiplied too. I'd verify the actual clock frequency and jitter at temperature.

For the debugging process itself, I'd use a thermal chamber to control temperature precisely, and I'd instrument the design to capture failure data — for example, adding CRC checks on data paths, or logging the first failing address/data pair. I'd also try to correlate the failure with specific operating conditions (does it fail at a specific temperature threshold? Does it recover when cooled?).

**Possible follow-ups:** How would you determine whether the issue is in the FPGA fabric versus the external I/O interface? What specific timing reports would you examine first?

## Q3: How would you approach implementing a finite state machine (FSM) in an FPGA that must control a high-speed data path with strict latency requirements (e.g., a packet processor that must make a forwarding decision within 10 clock cycles at 400 MHz)?

**Answer:** This is a design problem where the FSM architecture must be optimized for both speed and deterministic latency. At 400 MHz, you have only 25 ns to make the decision, and the FSM logic itself must not become the critical path.

My approach would start with the FSM structure. For high-speed operation, I'd prefer a one-hot encoded FSM over binary encoding — one-hot uses more flip-flops but reduces the combinational logic depth for state decoding, which directly helps timing closure. The next-state logic becomes simpler because each state has its own flip-flop and the transitions are encoded as individual logic terms.

I'd also carefully partition the FSM's responsibilities. If the decision requires complex combinational logic (e.g., comparing multiple header fields, looking up table entries), I'd pipeline the decision path. The FSM can be structured as a sequence of stages, where each stage performs part of the computation and passes intermediate results to the next stage. This adds latency in terms of clock cycles, but each stage has less combinational depth, allowing a higher clock frequency. The key is to balance the pipeline depth against the 10-cycle budget.

For the state encoding itself, I'd use synthesis attributes to ensure the tool doesn't re-encode the states in a way that hurts timing. I'd also consider whether the FSM can be decomposed into parallel sub-FSMs — for example, one that tracks packet arrival and another that performs the actual forwarding decision — communicating through simple handshake signals.

Another important technique is to precompute as much as possible. If certain decisions depend on data that's available earlier, I'd compute those in parallel with the FSM rather than serially. For example, if the forwarding decision depends on a destination address lookup, I'd start the lookup as soon as the address arrives, while the FSM is still processing header validation.

Finally, I'd verify the latency requirement through simulation with the actual timing constraints applied, and I'd use the timing report to identify any paths that are close to the limit. If a path is marginal, I'd look at whether the logic can be restructured, whether a different state encoding helps, or whether the FSM can be split into a two-stage pipeline.

**Possible follow-ups:** How would you decide between one-hot and binary encoding for this FSM? How would you handle the case where the 10-cycle budget can't be met with a single FSM?

## Q4: How would you approach designing a power distribution network (PDN) for an FPGA with multiple voltage rails, where the core rail (0.85V) has a transient current demand of up to 20A with a slew rate of 1A/ns, and you need to ensure the voltage stays within ±3% of nominal?

**Answer:** This is a demanding PDN design problem because the combination of high current, fast slew rate, and tight voltage tolerance leaves very little room for error. The target impedance for the core rail is approximately ΔV/ΔI = (0.85V × 0.06) / 20A ≈ 2.55 mΩ across the frequency range of interest — and that's a very low impedance to achieve.

My approach would be layered, addressing the PDN across multiple frequency decades:

**DC and low frequency (DC to ~1 kHz):** The voltage regulator module (VRM) must be able to supply 20A with adequate margin. I'd select a regulator with a current rating well above the peak demand, and I'd pay attention to its loop bandwidth and transient response. A multi-phase buck converter or a regulator with a fast transient response is essential. The feedback sense lines should be routed as a Kelvin connection directly to the FPGA's sense pins to avoid IR drops in the board traces being included in the regulation loop.

**Mid frequency (1 kHz to ~1 MHz):** This is where bulk capacitance (electrolytic or high-value ceramic) provides the energy during load transients before the VRM loop can respond. I'd calculate the required bulk capacitance based on the energy needed to hold the voltage within tolerance during the worst-case transient. The ESR and ESL of these capacitors matter as much as the capacitance value — I'd use multiple capacitors in parallel to reduce effective ESR/ESL.

**High frequency (1 MHz to ~100 MHz+):** This is where the PCB decoupling and the FPGA's on-chip capacitance take over. I'd place a mix of capacitor values (e.g., 100 nF, 10 nF, 1 nF) in a grid pattern close to the FPGA's power pins, with the smallest values closest to the device. The mounting inductance of the capacitors and the via inductance to the power plane are critical — I'd use multiple vias per capacitor pad to minimize inductance.

**Very high frequency (>100 MHz):** The power and ground planes themselves provide the lowest impedance. I'd use a dedicated power plane for the core rail with a solid ground plane directly adjacent, creating a low-inductance parallel-plate capacitor. The plane spacing (dielectric thickness) determines the high-frequency impedance — thinner dielectric gives lower impedance.

For verification, I'd perform a frequency-domain analysis using SPICE or a dedicated PDN tool, modeling the VRM output impedance, the capacitor networks, and the plane impedance. I'd also run a time-domain transient simulation with a current profile that matches the FPGA's worst-case switching pattern. On the bench, I'd measure the PDN impedance with a network analyzer and verify the transient response with a high-bandwidth oscilloscope probing directly at the FPGA power pins.

One additional consideration: the slew rate of 1A/ns means that even a few nanohenries of inductance in the path from the decoupling capacitors to the FPGA die will cause significant voltage droop. This is why the high-frequency decoupling must be as close to the FPGA as physically possible, and why the power plane design is so critical.

**Possible follow-ups:** How would you determine the target impedance for the PDN? What measurement techniques would you use to verify the PDN performance on the bench?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer on your team has implemented the data path that captures samples from a 500 MSPS ADC and writes them to DDR3 memory. During the review, you notice that the engineer has used a single FIFO to cross from the ADC clock domain to the memory controller clock domain, but the FIFO depth is only 64 words. When you ask about the depth, the engineer explains that the average write rate is well below the read rate, so the FIFO should never overflow. However, you're concerned about burst behavior — the ADC can produce bursts of data that could temporarily exceed the memory controller's sustainable write rate. The engineer argues that the memory controller's write buffer will absorb the bursts. How do you handle this situation?

**Answer:** This is a situation where I need to address both the technical concern and the junior engineer's development. The engineer's reasoning about average rates is sound as far as it goes, but it misses the critical distinction between average throughput and instantaneous burst behavior — which is exactly the kind of subtle issue that causes intermittent, hard-to-debug failures in production systems.

My approach would be to first acknowledge what the engineer got right: they correctly identified that the average write rate is below the read rate, and they're thinking about the system's overall data flow. Then I'd guide them through the burst analysis rather than simply overriding their decision. I'd ask questions like: "What happens if the ADC produces a burst of 128 samples while the memory controller is busy servicing a refresh cycle?" or "What's the worst-case latency for the memory controller to accept a write when it's also handling read requests?" These questions help the engineer discover the issue themselves.

I'd also suggest we work through the math together. We'd calculate the worst-case burst size from the ADC (based on its maximum continuous conversion rate), the memory controller's sustainable write bandwidth (accounting for refresh overhead, read/write turnaround, and bank conflicts), and the latency for the memory controller to accept a write request. If the worst-case burst exceeds the FIFO depth plus the memory controller's internal buffering, we have a potential overflow.

If the analysis shows the FIFO is indeed too shallow, I'd discuss the options: increasing the FIFO depth, adding flow control to throttle the ADC during bursts, or using a larger FIFO with a watermark interrupt to signal the memory controller to prioritize writes. I'd also emphasize that this kind of analysis should be documented in the design — not just the final decision, but the reasoning behind it, so future engineers understand why the FIFO depth was chosen.

Finally, I'd frame this as a learning opportunity. The distinction between average and burst behavior is one of the most common sources of intermittent failures in high-speed systems, and understanding it deeply is a key skill for FPGA design. I'd encourage the engineer to think about what other places in the design might have similar average-vs-burst assumptions that need verification.

**Possible follow-ups:** How would you verify that the FIFO depth is sufficient before the board goes to production? What if the engineer's analysis shows the FIFO is actually adequate — how would you handle that outcome?
