# high-speed-digital-fpga — Day 75

## Q1: How would you approach designing the clock domain crossing for a multi-bit Gray-coded counter value that increments continuously in a fast domain (e.g., 250 MHz) and must be sampled by a slower domain (e.g., 50 MHz) for logging, where the sampled value must always be a coherent snapshot and never a corrupted mix of bits?

**Answer:** The key insight is that a Gray code guarantees only one bit changes per increment, so a value sampled mid-transition can be off by at most one count — never a wildly wrong value from multiple bits resolving inconsistently. The standard approach is to register the Gray-coded counter in the source domain, then pass it through a two-flop synchronizer in the destination domain. Because only one bit can be in flight at a time, the worst case is that the destination captures either the old or the new value, both of which are valid adjacent counts. If the application needs an exact snapshot rather than a "close enough" value, I'd add a handshake or a request/acknowledge scheme, but for logging that tolerates a one-count lag, the synchronizer alone is sufficient and cheap. I'd also make sure the Gray encoding is done in the source domain before the synchronizer, not after — converting binary to Gray on the destination side would defeat the purpose. For verification, I'd constrain the synchronizer flops with the appropriate CDC constraints in the timing tool and run a CDC lint check to confirm no unsynchronized paths exist.

**Possible follow-ups:**
- What happens if the counter is wide enough that the Gray code wraps around during the synchronizer latency — does that change your approach?
- How would you verify in simulation that the synchronizer behaves correctly across all possible sampling phases?

## Q2: How would you approach debugging an FPGA design where the DDR3 memory interface passes its built-in calibration and memory test at power-up, but fails intermittently only after the device has been running for several minutes and the board has warmed up?

**Answer:** This pattern — passes cold, fails warm — points strongly toward a timing margin issue that shrinks as temperature rises, rather than a logic bug. I'd start by separating the problem into three areas: the memory device itself, the FPGA's memory controller and PHY, and the board-level signal integrity. First, I'd check whether the failure correlates with a specific access pattern or address region, which would narrow it to a particular byte lane or rank. Then I'd look at the calibration data captured at power-up versus what the eye looks like when warm — many controllers expose per-bit deskew or read/write leveling values that can be logged and compared. If the margins are marginal at cold and collapse at hot, the fix is usually in the board: trace length matching, reference plane integrity, or termination. On the FPGA side, I'd check whether the controller's timing parameters (tRCD, tRP, tRFC, etc.) are being derated for temperature — some controllers require different settings at different temperature ranges. I'd also verify the VREF and ODT settings are appropriate across the temperature range, since both can drift. Finally, I'd use the controller's built-in eye scan or margin check (if available) at both temperatures to quantify how much margin is actually being lost.

**Possible follow-ups:**
- How would you determine whether the issue is in the FPGA's PHY or in the DRAM device itself?
- What board-level changes would you consider if the margin loss is confirmed to be signal-integrity related?

## Q3: How would you approach designing the return-current path for a high-speed digital board where a signal transitions between two reference planes (e.g., from a ground plane to a power plane) on its way through a via?

**Answer:** The fundamental principle is that every signal current must return to its source, and at high frequency the return current follows the path of least impedance — which means it flows on the reference plane directly beneath (or above) the signal trace. When a signal via transitions from a layer referenced to ground to a layer referenced to a power plane, the return current has to jump from the ground plane to the power plane. If there's no nearby stitching capacitor, that return path is long and inductive, which creates a discontinuity that radiates and degrades signal integrity. The standard fix is to place a stitching capacitor — typically a small, low-inductance ceramic — as close as possible to the signal via, connecting the two reference planes. The capacitor provides a low-impedance path for the return current at the frequencies of interest. For very high-speed signals, I'd also consider whether the plane transition can be avoided entirely by keeping the signal referenced to the same plane throughout its route. If the transition is unavoidable, I'd place the stitching cap within a few millimeters of the via, use multiple vias for the capacitor to minimize its mounting inductance, and verify the design with a 3D electromagnetic simulation if the signal is fast enough that the discontinuity matters. On a mixed-signal board, I'd also be careful that the stitching capacitor doesn't create an unintended path between noisy and quiet planes.

- How would you decide the value and type of stitching capacitor for a given signal rise time?
- What are the trade-offs between using a stitching capacitor versus rerouting the signal to avoid the plane transition?

## Q4: How would you approach choosing between a global clock network and a regional/banked clock resource for a logic block that only needs to run at a modest rate, when the device's global clock resources are nearly exhausted?

**Answer:** The first question is whether the logic block actually needs a global clock at all. Global clock networks are designed for low skew across the entire device, which is essential for high-fanout, timing-critical paths, but they're a scarce resource. If the block is a self-contained function running at a modest rate — say, a slow control interface or a housekeeping state machine — a regional or banked clock resource is usually the better choice. Regional clocks have lower insertion delay and skew within their region, and they free up global resources for the paths that genuinely need them. The trade-off is that regional clocks can't reach every corner of the device, so I'd verify the placement constraints can keep all the clock's loads within the region. I'd also check whether the block can tolerate the slightly higher skew that a regional clock might introduce — for a modest-rate block, that's usually fine. If the block spans multiple regions or has loads that can't be confined, I'd reconsider. Another option is to use a clock enable on a slower global clock rather than a separate clock domain, which avoids consuming an additional clock resource entirely. The decision comes down to: what's the actual timing requirement, how many loads does the clock drive, and can those loads be physically confined to one region?

- What are the risks of using a clock enable instead of a separate clock domain, and how would you mitigate them?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer has implemented a critical control signal that is generated in one clock domain and consumed in another, and they've connected it directly without any synchronization, arguing that "the signal is stable long enough that it will always be captured correctly." How do you handle this situation?

**Answer:** I'd start by acknowledging that the engineer's observation — that the signal is stable for a long time relative to the clock period — is often true in practice, which is exactly why this class of bug is so insidious. The problem isn't whether it works today; it's that the timing relationship between the two domains is not guaranteed, and it can change with temperature, voltage, process variation, or even a minor RTL change that shifts placement. The right way to handle it is to treat it as a teaching moment rather than a criticism. I'd explain the concept of metastability and why a two-flop synchronizer (or a proper handshake, depending on the signal type) is the standard solution, and I'd show how a CDC lint tool would flag this path. Then I'd ask the engineer to add the synchronizer and re-run the CDC checks, and I'd offer to review the fix together. If the signal is multi-bit or has specific ordering requirements, I'd work with them to choose the right synchronization scheme — a handshake, a FIFO, or a Gray-coded transfer — rather than just a two-flop synchronizer. The goal is to make the fix part of the team's standard practice, not just a one-off correction. I'd also follow up by checking whether other paths in the design have the same issue, since this kind of mistake rarely appears in isolation.

**Possible follow-ups:**
- How would you handle it if the engineer pushed back, arguing that the synchronizer adds latency that the design can't afford?
- What process changes would you propose to catch this class of issue earlier in future designs?
