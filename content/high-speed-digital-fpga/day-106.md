# high-speed-digital-fpga — Day 106

## Q1: How would you approach designing the I/O planning for an FPGA that must drive a wide, high-speed parallel bus to an external memory device while also supporting a group of low-speed control signals, given that the device's I/O banks each have a fixed VCCO and a limited set of supported standards?

**Answer:** I'd start by grouping signals by their electrical requirements rather than by logical function, because the physical constraint is the bank's VCCO — every pin in a bank shares that rail, and the supported I/O standards follow from it. The high-speed memory bus needs a specific standard (e.g., SSTL-class) tied to its own VCCO, so I'd dedicate one or more banks to it and keep those banks free of unrelated signals. The low-speed control signals can share banks at a more convenient voltage, but I'd check that their standards are compatible with the VCCO I choose and that no bank ends up needing two incompatible standards.

Beyond voltage, I'd consider the physical placement: the memory bus should be placed on banks adjacent to the memory controller hard block or the relevant fabric region to keep routing short and to make length-matching feasible. I'd also look at the bank's available differential pairs and clock-capable pins, since the memory interface may need a forwarded clock or a dedicated reference. For the low-speed signals, I'd avoid putting them on pins that share a bank with the high-speed bus if that would force a voltage compromise, and I'd check for any pins with special functions (configuration, JTAG, dedicated clocks) that must be preserved.

Finally, I'd verify the plan against the device's pinout document and the board's schematic early, because I/O planning mistakes are expensive to fix after layout. A pin-swap review with the PCB designer before routing starts is worth the time.

**Possible follow-ups:** How would you handle a situation where the memory interface needs more pins than a single bank provides? What would you do if a late requirement change forced a low-speed signal onto a bank already committed to the memory bus?

## Q2: How would you approach debugging an FPGA design where the device configures successfully and runs correctly for a while, but then appears to lose its configuration — it stops responding and only recovers after a full reconfiguration?

**Answer:** I'd treat this as two separate questions: is the configuration actually being lost, or is the device still configured but the logic has entered a non-functional state that looks like a lost configuration? The first step is to instrument the board — monitor the configuration-done signal, the initialization status, and any error flags the device exposes, and log them over time so I can see whether the failure correlates with a specific event (a power transient, a temperature rise, an external stimulus).

If the configuration really is being lost, I'd look at the power rails first. A marginal core or auxiliary rail, a slow ramp, or a transient that dips below the device's minimum can cause the configuration to be cleared or the device to reset. I'd scope the rails during the failure, ideally with a fast capture triggered on the failure event, and check for glitches that a multimeter would miss. I'd also check the configuration flash interface — a noisy or marginal SPI/parallel link to the flash can cause a re-read to fail, and the device may then sit in an error state. The flash's own supply and its decoupling are worth reviewing.

If the device is still configured but the logic is stuck, I'd look at the reset architecture and any watchdog or error-recovery logic. A design that has no way to recover from an illegal state will look like a lost configuration. I'd also consider whether an external event — an ESD strike, a hot-plug, a supply brownout on a peripheral — is disturbing the device.

The key discipline is to distinguish "configuration lost" from "logic wedged" before changing anything, because the fixes are completely different.

**Possible follow-ups:** How would you design the board so that a configuration loss is recoverable without a power cycle? What role would a watchdog play, and where would you put it?

## Q3: How would you approach designing the clock domain crossing for a multi-bit status word that is updated in a fast domain (e.g., 250 MHz) and read by a slower domain (e.g., 50 MHz), where the word changes frequently and the read must always return a coherent snapshot, never a mix of old and new bits?

**Answer:** The core problem is that a multi-bit value crossing an asynchronous boundary can be captured mid-update, so individual bits may come from different update cycles. The standard solutions are a handshake, a Gray-coded encoding, or a dual-clock FIFO, and the choice depends on the update rate and latency tolerance.

For a status word that changes frequently, a simple two-flop synchronizer per bit is not acceptable — it guarantees metastability resolution but not coherence. A request/acknowledge handshake works when updates are infrequent relative to the slower clock: the source holds the data stable and asserts a request, the destination synchronizes the request, captures the data, and returns an acknowledge. The cost is latency and the need for the source to wait for the acknowledge before updating again, which may not suit a fast-changing word.

If the word changes often, a dual-clock FIFO is usually the cleanest answer: the fast domain pushes complete words into the FIFO, and the slow domain pops them. The FIFO's pointers are already synchronized internally, and the data is written and read as whole words, so coherence is guaranteed. The trade-off is depth and the possibility of overflow if the slow side can't keep up — I'd size the FIFO for the worst-case burst and add an overflow flag.

A third option is to encode the word in Gray code if only one bit changes per update, but that's rarely true for a general status word. I'd also add a data-valid or update-counter field so the reader can detect that it's seeing a fresh value.

**Possible follow-ups:** How would you decide between a handshake and a FIFO for a given update rate? What would you do if the slow domain occasionally stalls and the FIFO fills?

## Q4: How would you approach verifying that a high-speed FPGA design's timing constraints are complete and correct before sign-off, given that missing or incorrect constraints can produce a design that passes timing analysis but fails in hardware?

**Answer:** I'd treat constraint review as a formal step, not a byproduct of timing closure. The starting point is a constraint specification derived from the design's interfaces: every clock, every I/O interface, every clock domain crossing, and every asynchronous path should be accounted for. I'd cross-check that list against the actual constraints file and against the design's clock and reset structure, looking for clocks that are generated internally (PLL/MMCM outputs) and for paths that cross between them.

The most common failure mode is a false path or multicycle path that was added to make timing close rather than because the path is genuinely asynchronous or genuinely multi-cycle. I'd review every exception individually and require a justification tied to the design's behavior — for example, a path between two unrelated clock domains is a legitimate false path only if there's a proper synchronizer in between; a multicycle path is legitimate only if the logic actually has that many cycles to settle. I'd also check that the constraints cover the I/O timing: input and output delays relative to the external device's specifications, including board skew and the device's setup/hold requirements.

I'd run the timing analysis at all specified corners (slow, fast, and any temperature extremes the device supports) and look for paths that are unconstrained or only partially constrained. A useful check is to compare the number of constrained paths against the design's expected path count, and to review the unconstrained-path report if the tool provides one. Finally, I'd correlate the constraint set with the hardware bring-up plan — if a path is critical to a function that will be tested, its constraint should be traceable to that test.

**Possible follow-ups:** How would you handle a constraint that the timing tool reports as unconstrained but that you believe is genuinely asynchronous? What would you do if a late design change introduced a new clock domain that wasn't in the original constraint specification?

## Q5: Behavioral question — You're leading a design review for a high-speed FPGA-based data acquisition board. A junior engineer presents a timing closure report showing all constraints met, but you notice the report was generated with a set of timing exceptions (false paths and multicycle paths) that the engineer added to make the design close. The engineer argues that the exceptions are legitimate because "those paths don't need to meet single-cycle timing." How do you handle this situation?

**Answer:** I'd start by acknowledging the engineer's reasoning — timing exceptions are a legitimate tool, and the goal isn't to reject them but to make sure each one is justified by the design's actual behavior. I'd ask the engineer to walk me through each exception and explain why the path is genuinely asynchronous or genuinely multi-cycle, and what mechanism guarantees correctness if the exception is wrong. That turns the conversation from "I don't trust your report" into "let's verify the reasoning together," which is more productive and keeps the engineer engaged.

For each exception, I'd look for the evidence: is there a synchronizer on the path, is the multicycle count derived from the logic's actual latency, is the false path between truly unrelated clocks? If the justification holds, I'd document it so it's traceable and doesn't get lost. If it doesn't hold, I'd explain the risk concretely — a false path on a path that actually needs timing can produce a design that passes analysis and fails in hardware, and that failure is expensive to debug because it's intermittent and temperature-dependent.

I'd also use this as a teaching moment about the review process: the report should include the exception list and the justification, not just the "all constraints met" summary. That way the review catches this systematically rather than depending on someone noticing. And I'd make sure the engineer understands that the goal is a design that works, not a report that passes — the report is a means, not the end.

**Possible follow-ups:** How would you handle it if the engineer disagreed and insisted the exceptions were correct? What process change would you make to prevent this from recurring on the team?
