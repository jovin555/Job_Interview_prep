# embedded-linux-bsp — Day 119

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is usually a sign that the driver is talking to the wrong place, or that the hardware is not actually powered/clocked even though the software thinks it is. I'd work outward from the driver in layers.

First, confirm the driver is bound to the intended device: check `/sys/bus/<bus>/devices/` and the driver's sysfs entry to verify the device tree node that got matched is the one I expect, and that the address/reg values match the schematic. A common cause is a device tree `reg` or `compatible` that matches a different node, so `probe()` succeeds against a phantom peripheral.

Second, verify the bus is actually alive. For I2C/SPI, read a known register (e.g., a chip ID or WHO_AM_I) directly from the driver's probe path or via a small userspace tool, and confirm the value. If reads return all-ones or all-zeros, the device isn't responding — which points to power, clock, reset, or pinmux rather than the driver logic.

Third, check the physical preconditions the driver assumes: is the regulator actually enabled (measure the rail, or read the regulator's `state` in sysfs), is the clock running at the expected rate (`clk_summary`), is the reset GPIO released, and is the pinmux set to the peripheral function rather than GPIO? A driver that calls `regulator_enable()` and `clk_prepare_enable()` can still "succeed" if the device tree points at the wrong supply or the pinmux was never applied.

Fourth, add targeted instrumentation: enable dynamic debug for the driver, add a `dev_dbg` after each register write in probe, and confirm the writes land by reading them back. If writes don't stick, suspect the bus, the address, or write-protection.

Finally, if all software checks pass, scope the bus lines and the device's power/reset pins. Silence with no errors usually means the transaction completed at the bus level but the device ignored it — which is a hardware bring-up problem, not a driver bug.

**Possible follow-ups:** How would you distinguish a pinmux problem from a power problem without a scope? What would you check first if the chip ID read returns the correct value but subsequent register reads return garbage?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our changes on top, so we can pick up vendor updates without merge conflicts.

The clean mechanism is a `.bbappend` in our own layer that adds a config fragment via `SRC_URI`. Yocto's kernel class supports `file://fragment.cfg` entries in `SRC_URI`, and the kernel-yocto infrastructure merges them into the final `.config` using `merge_config.sh` semantics. So the append looks roughly like: `FILESEXTRAPATHS:prepend := "${THISDIR}/${PN}:"` and `SRC_URI += "file://board-fragment.cfg"`. The fragment contains only the options we need to change, in `CONFIG_FOO=y` / `# CONFIG_BAR is not set` form.

A few practices make this robust. Keep fragments small and single-purpose (one for a peripheral, one for a debug option) so they're auditable and easy to reason about. Use `# CONFIG_X is not set` explicitly when you need to disable something, because a fragment that only sets options can't turn things off. Validate the merged config with `bitbake -c kernel_configcheck` or by diffing the resulting `.config` against the vendor's reference, so you catch options that silently didn't apply because a dependency wasn't met. And pin the fragment to the kernel version it was written for — options get renamed or removed across versions, and a stale fragment can fail silently.

If the vendor recipe doesn't use the kernel-yocto class, the same idea still works via `do_configure:append` calling `merge_config.sh`, but that's a fallback; prefer the class-native mechanism.

**Possible follow-ups:** How would you detect that a fragment option was silently dropped because its dependency wasn't enabled? What's the risk of putting board config in `defconfig` instead of a fragment?

## Q3: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?

**Answer:** `EINTR` means a blocking syscall was interrupted by a signal that was delivered and handled (or whose handler was set to not restart the call). If nothing in the application is deliberately signalling, the signal is coming from somewhere else — the kernel, a library, a debugger, or the process's own environment.

First, identify the signal. Run the daemon under `strace -f -e trace=signal,ioctl` and look at what signal arrives just before the `EINTR`. Common culprits: `SIGCHLD` from a child process (e.g., a helper the daemon spawns), `SIGALRM` from a timer, `SIGIO`/`SIGURG` from async I/O or socket events, or `SIGPROF` from profiling. Also check whether the daemon is being run under a supervisor or `gdbserver` that sends signals.

Second, look at the driver side. If the driver's `ioctl` handler sleeps interruptibly (e.g., `wait_event_interruptible`), any signal delivered to the calling thread will wake it and return `-ERESTARTSYS`, which the kernel translates to `EINTR` (or restarts the syscall if `SA_RESTART` is set on the handler). So the driver may be behaving correctly; the question is why a signal is arriving.

Third, decide the right fix. If the signal is expected and benign (e.g., `SIGCHLD`), the application should either install the handler with `SA_RESTART` so blocking calls resume automatically, or explicitly loop on `EINTR` and retry the `ioctl`. A daemon that aborts on `EINTR` is fragile by design — retrying on `EINTR` is standard practice. If the signal is unexpected, find and eliminate its source. If the driver's blocking behavior is the problem, consider whether the `ioctl` should be non-blocking with `poll()`/`select()` instead, so the application controls when it waits.

The key point: `EINTR` is a contract between the kernel and userspace, and the fix is almost always in userspace (retry or `SA_RESTART`), not in the driver.

**Possible follow-ups:** How would `SA_RESTART` change the behavior, and what are its limits? When would you prefer a non-blocking `ioctl` plus `poll()` over a blocking `ioctl`?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path holds. That rules out a single mutex protecting the device, because a slow logging read could hold it while the real-time task waits.

The standard pattern is to separate the data path from the control path. The real-time task gets a lock-free or minimally-locked fast path: for a sensor, that usually means the driver's interrupt handler or a high-priority kthread reads the device into a pre-allocated buffer and publishes it via a lock-free ring buffer (single-producer/single-consumer, using `smp_store_release`/`smp_load_acquire` or a `kfifo` with the right memory barriers). The real-time consumer reads from the ring without ever taking a sleeping lock.

The logging task reads from a separate copy or a slower path. If it needs to issue its own device transactions (e.g., read configuration registers), those go through a mutex that the real-time path never touches — the real-time path only touches the data registers, which are independent. If the device has a single register interface that both must use, then the real-time path must own it and the logging path must be served from data the real-time path has already cached, never by issuing its own transactions.

On the scheduling side, the real-time task runs at `SCHED_FIFO` with a priority above the logging task, and the driver's interrupt handler is kept short — deferring work to a threaded handler at a priority that doesn't starve the real-time task. The logging task runs at normal priority and yields.

The design principle: the real-time path must be bounded and non-blocking, and any shared resource it touches must be either lock-free or held only for a bounded, short critical section that the logging path can never extend.

**Possible follow-ups:** How would you verify the real-time path's worst-case latency under logging load? What happens if the device only has one set of registers and both paths genuinely need to write to it?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination problem first and a technical problem second, because both teams have legitimate constraints and the risk is real on both sides.

First, I'd get the facts on the table: exactly which pins the hardware team needs, why the new peripheral can't use an alternative, and exactly how the manufacturing line uses the debug UART (is it a human watching boot messages, an automated test fixture parsing output, or both?). The manufacturing dependency is often the harder constraint to change, so I'd want to understand its tolerance for disruption before proposing anything.

Second, I'd look for options that don't force a binary choice. Can the new peripheral use a different pinmux group or a different peripheral instance? Can the debug UART move to a pinmux group that's still available at the earliest boot stage, so the bootloader and early kernel console keep working? Can we keep the current UART for manufacturing and add a second console for development? Often the pin conflict is narrower than it first appears.

Third, if a change is genuinely required, I'd propose a staged plan: update the bootloader and device tree in a branch, validate early boot console output on hardware, and coordinate with manufacturing to confirm their fixtures still work before merging. I'd want a rollback path and a clear owner for each side of the change.

Throughout, I'd keep the discussion focused on the shared goal — shipping a device that meets the new peripheral requirement without breaking the manufacturing line — rather than letting it become a hardware-versus-software debate. The decision should be documented, with the trade-offs and the validation evidence, so it's defensible later.

**Possible follow-ups:** What would you do if manufacturing says any change to the console output is unacceptable? How would you decide between moving the UART and finding a different pin for the new peripheral?
