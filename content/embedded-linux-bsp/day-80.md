# embedded-linux-bsp — Day 80

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is deferred indefinitely because a supplier it depends on never becomes available — with no obvious error in the kernel log?

**Answer:** `-EPROBE_DEFER` is a cooperative mechanism, not an error, so the kernel deliberately stays quiet about it — the driver is telling the framework "I'm not ready yet, try me again later." The first step is to confirm that deferral is actually what's happening rather than a silent failure. Enabling `initcall_debug` and dynamic debug for the driver core (`dyndbg="file drivers/base/* +p"`) usually surfaces the deferred-probe messages, and `/sys/kernel/debug/devices_deferred` (or the equivalent sysfs node) lists devices currently sitting in the deferred state. That tells you which supplier is missing.

From there the reasoning is about *why* the supplier never appears. Common causes: the supplier's own driver is not built into the kernel or not loaded as a module; the supplier's device tree node is absent, disabled (`status = "disabled"`), or has a mismatched `compatible` string; the supplier is on a bus that itself hasn't probed yet (a classic chain — regulator depends on I2C, I2C controller depends on clock, clock depends on a PMIC that hasn't come up); or there's a circular dependency where two drivers each wait on the other. Checking the device tree for the supplier node, verifying the driver is present in the kernel config, and walking the dependency chain from the deferred device upward usually isolates it. If it's a genuine cycle, the fix is to break it — for example by having one side register a stub or by reordering initialization — rather than to paper over it with a probe-order hack.

**Possible follow-ups:**
- How would you distinguish a genuine circular dependency from a simple missing supplier?
- What are the risks of "fixing" a deferred probe by forcing probe order with `initcall` levels or module load order?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer only deltas on top, so that when the vendor bumps their kernel you rebase a small fragment rather than a forked tree. The standard mechanism is the kernel's configuration fragment support: you place a `.cfg` fragment (or a `.scc`/`.cfg` pair) in your own layer and point the kernel recipe at it via `SRC_URI` using a `KERNEL_CONFIG_FRAGMENTS`-style variable or a `bbappend` that appends the fragment to the recipe's `SRC_URI`. The fragment contains only the options you need to change — `CONFIG_FOO=y`, `# CONFIG_BAR is not set` — and the kernel's `merge_config.sh` logic folds it into the base `defconfig` at build time.

The important discipline is to keep the fragment minimal and self-documenting: only the options that genuinely differ from the vendor default, with a comment explaining why each is needed. Avoid the temptation to snapshot a full `.config`, because that pins you to a specific kernel version and defeats the purpose. Put the fragment in a board-specific layer (or a `linux-yocto`-style append) so that a second board sharing the same SoC can have its own fragment without touching yours. Verify with `bitbake -c menuconfig virtual/kernel` that the merged result is what you expect, and check the generated `.config` in the work directory to confirm the fragment actually took effect — a fragment that silently fails to apply is a common and confusing failure mode.

**Possible follow-ups:**
- How would you handle a configuration option that the vendor's `defconfig` sets but you need to *disable*?
- What's the difference between a kernel config fragment and a full `defconfig` in terms of maintenance burden across kernel version bumps?

## Q3: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** Intermittent fallback to network boot usually means the primary boot path is failing *sometimes* and U-Boot's boot order is silently moving on to the next candidate. The first thing to establish is whether the eMMC read is actually failing or whether U-Boot is misinterpreting a successful read. Enabling verbose U-Boot output (`setenv bootdelay` and checking the full boot log, or building with `CONFIG_LOGLEVEL` raised) usually shows the moment the eMMC path is abandoned. If the log shows a read error, the question becomes why it's intermittent — marginal signal integrity on the eMMC interface, a power-rail ramp issue that occasionally leaves the eMMC not ready when U-Boot first touches it, or a timing/clock configuration that's outside the part's spec at temperature extremes.

If the log shows no error but the fallback still happens, the cause is usually in the environment itself: a stale `bootcmd` that chains multiple boot attempts, a `boot_targets` list that includes network, or a saved environment that differs from the default. Comparing the running environment (`printenv`) against the intended default, and checking whether the environment is being loaded from eMMC or from a fallback location, often reveals the discrepancy. The fix is usually to make the boot order explicit and to fail loudly rather than silently — for example, removing network from `boot_targets` on production units, or adding a deliberate halt on primary-boot failure so the failure is visible instead of masked by a fallback that "works" but shouldn't.

**Possible follow-ups:**
- How would you make the boot process fail deterministically rather than falling through to an unintended path?
- What hardware-level checks would you run to rule out marginal eMMC signal integrity as the root cause?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path holds, so the design has to separate the two access paths rather than serialize them behind a single mutex. The usual pattern is a lock-free or minimally-contended handoff: the real-time task writes into a pre-allocated ring buffer (or a double-buffered region) using atomic operations or a spinlock held for only a few instructions, and the logging task reads from the buffer at its own pace. The real-time side never waits for the logging side to finish; if the buffer is full, the real-time side either overwrites the oldest entry or drops, depending on which is acceptable for the application — and that decision should be made explicitly, not left to chance.

For the hardware access itself, if both tasks need to touch the same registers, the real-time task should own the hardware and the logging task should consume data the real-time task has already published, rather than both issuing I/O. If the logging task genuinely must issue its own reads, those reads should be structured so they can't hold a lock the real-time path needs — for example, by using a separate hardware channel, a separate register set, or a read that's guaranteed bounded. Priority inheritance or a real-time mutex can help if a shared lock is unavoidable, but the cleaner answer is to design the sharing away. The verification step is to measure worst-case latency on the real-time path under heavy logging load, because the failure mode here is subtle and only shows up under contention.

**Possible follow-ups:**
- How would you decide between dropping data and overwriting oldest data in the ring buffer?
- What kernel primitives would you use to guarantee the real-time path's worst-case latency, and how would you verify it?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** The first move is to separate the two concerns that are being conflated: the *technical* change (moving a UART to a different pinmux group) and the *process* risk (the manufacturing line depends on early console output). They're both real, but they have different owners and different mitigations, and treating them as one argument tends to stall the discussion. I'd want to understand from the hardware team why the new peripheral needs those specific pins and whether there's an alternative pinmux assignment that avoids the conflict — sometimes the constraint is softer than it first appears. In parallel, I'd want to understand from the software team exactly what the manufacturing line depends on: is it the UART itself, or the specific pins, or the fact that console output appears within a certain time window? Those are different requirements and may have different solutions.

If the change is genuinely necessary, the mitigation is to make it safe rather than to refuse it. That means updating the device tree and bootloader pinmux in a controlled way, verifying that early console output still works on the new pins, and — critically — giving the manufacturing line a way to validate the change before it ships. A staged approach (bring up the new pinmux on a small batch of boards, confirm the manufacturing flow still works, then roll out) reduces the risk to a level the team can accept. If the change can't be made safe within the schedule, the honest answer is to escalate the trade-off — new peripheral versus manufacturing continuity — to the people who own both, rather than letting the software team absorb a risk they didn't create.

**Possible follow-ups:**
- How would you structure the validation so that the manufacturing line's dependency is tested, not assumed?
- If the hardware team insists the change is non-negotiable and the schedule doesn't allow staged rollout, what would you do?
