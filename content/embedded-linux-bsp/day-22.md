## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of two identical I2C sensors on the same bus, while the other works fine?

**Answer:** This is a classic "same device, different result" problem that usually points to something specific about the board or the device tree rather than the driver itself. I'd start by confirming the basics: check `i2cdetect -l` to verify the bus is present, then `i2cdetect -y <bus>` to see if the missing sensor responds at all on the bus. If it doesn't appear in the scan, the issue is likely hardware-level — a bad solder joint, missing pull-up, wrong address strapping, or a power supply issue on that specific sensor's rail. If it does appear in `i2cdetect` but the kernel driver doesn't bind, then the problem is in the device tree — perhaps the node is missing, has the wrong `reg` address, or the compatible string doesn't match what the driver expects. I'd also check `dmesg` for probe errors, and verify the interrupt line if the sensor uses one — a shared interrupt that's misconfigured can prevent probe. One subtle thing I've seen: if the two sensors are on the same bus but at different addresses, and the device tree only declares one node, the kernel won't create a device for the second one even though it's electrically present. I'd also verify the address strapping pins on the sensor itself — if they're floating or mis-wired, the sensor could be responding at a different address than expected.

**Possible follow-ups:**
- What if both sensors have the same I2C address — how would you handle that in the device tree?
- How would you distinguish between a hardware issue and a software issue in this scenario?

## Q2: How would you approach implementing a kernel driver for a device that needs to perform a hardware-triggered DMA transfer, where the trigger comes from an external sensor's interrupt line, and the data must be processed and made available to userspace within a hard real-time deadline (e.g., 2 ms)?

**Answer:** The key here is to minimize latency at every stage of the pipeline while ensuring the DMA transfer is set up correctly. First, I'd use a threaded interrupt handler or a dedicated kernel thread rather than doing work in the hard IRQ context — the hard IRQ handler should just acknowledge the interrupt and wake the thread. The DMA transfer itself should be set up in advance, with the buffer pre-allocated and the DMA channel configured, so that when the interrupt fires, the only work is to trigger the transfer. I'd use the DMA engine API with a completion callback rather than polling, and I'd consider using a double-buffering scheme so that while one buffer is being filled by DMA, the previous one is being processed. For the userspace delivery, I'd use a character device with read() semantics backed by a ring buffer, or possibly `mmap` with a shared buffer and a poll() notification — this avoids the copy overhead. The 2 ms deadline means I need to be careful about anything that could block: no sleeping locks in the hot path, no dynamic memory allocation after initialization, and careful consideration of interrupt priorities. I'd also need to verify that the DMA controller can actually meet the bandwidth requirements and that the interrupt latency on the specific SoC is acceptable — this might require tuning the interrupt affinity or using a real-time scheduling class for the processing thread.

**Possible follow-ups:**
- How would you handle the case where the DMA transfer occasionally takes longer than the deadline?
- What are the trade-offs between using a threaded IRQ versus a dedicated kernel thread for this kind of work?

## Q3: How would you approach designing the device tree for a system where a single I2C bus has multiple sensors with different interrupt lines, and you need to ensure that interrupt-driven reads work reliably under heavy bus traffic?

**Answer:** The device tree needs to accurately describe both the I2C bus topology and the interrupt wiring. Each sensor node should have its own `interrupt-parent` and `interrupts` property pointing to the correct GPIO controller and interrupt line. I'd also make sure the `interrupt-controller` and `#interrupt-cells` properties are correctly set on the GPIO controller that provides the interrupt lines. One important consideration is whether the interrupts are level-triggered or edge-triggered — this affects how the kernel handles them, especially under heavy bus traffic. For level-triggered interrupts, the interrupt line stays asserted until the sensor is read, which means the handler will keep firing until the condition is cleared — this is actually good for reliability because you won't miss an event, but it requires careful handling to avoid interrupt storms. For edge-triggered interrupts, you can miss events if the line toggles while the handler is running. I'd also consider using `interrupts-extended` if the sensors are on different interrupt controllers. For reliability under heavy bus traffic, I'd make sure each sensor's interrupt handler doesn't do I2C transactions directly in the hard IRQ context — instead, use a threaded handler or defer the read to a workqueue, because I2C transactions can block and you don't want to stall the interrupt handling. The device tree should also specify the correct `clock-frequency` for the bus, and I might consider adding `pinctrl` settings to ensure the interrupt lines have proper pull-ups or pull-downs configured.

**Possible follow-ups:**
- How would you handle a situation where two sensors share the same interrupt line?
- What are the trade-offs between polling and interrupt-driven reads for I2C sensors?

## Q4: How would you approach implementing a kernel driver for a device that needs to be accessed by both a real-time safety-critical task and a non-real-time monitoring task, where the safety-critical task must never be blocked by the monitoring task?

**Answer:** The fundamental requirement is that the safety-critical path must have guaranteed access to the hardware, regardless of what the monitoring task is doing. I'd start by separating the access paths: the safety-critical task should have a dedicated, minimal interface to the hardware — ideally a set of functions that are lock-free or use only spinlocks with very short hold times. The monitoring task would go through a different interface, perhaps a separate device node or ioctl, that can afford to take mutexes and do more complex operations. The key is to avoid a shared lock between the two paths — if the monitoring task holds a mutex while doing a slow operation, the safety-critical task could be blocked. One approach is to use a read-copy-update (RCU) mechanism for shared state, or to have the monitoring task read from a snapshot buffer that the driver updates atomically. For the hardware access itself, I'd consider using a hardware mutex if the SoC provides one, or carefully partitioning the device registers so that the two paths access different registers and don't need to serialize. If they must share a register, I'd use a spinlock with a bounded wait — and I'd make sure the monitoring path never holds it for more than a few microseconds. I'd also think about priority inheritance: if the monitoring task is holding a resource the safety-critical task needs, the kernel's priority inheritance mechanism should boost the monitoring task's priority to avoid priority inversion. Finally, I'd add instrumentation to detect any unexpected blocking — for example, a watchdog or a latency counter that flags if the safety-critical path ever takes longer than expected.

**Possible follow-ups:**
- How would you verify that the safety-critical path never blocks, given that you can't test every possible interleaving?
- What are the trade-offs between using a spinlock versus a mutex in this scenario?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the hardware team reveals that they need to change the main processor's boot mode strap resistors to accommodate a new flash part. The change means the processor will boot from a different interface (e.g., from SPI NOR to eMMC), and the bootloader and kernel configurations are already tuned for the current boot source. The project is six weeks from the start of a clinical trial. How would you handle this situation?

**Answer:** First, I'd want to understand the full scope of the change — is it just the boot source, or does it affect other things like the memory map, clock configuration, or peripheral availability? I'd ask the hardware team for the exact strap configuration and the new flash part's specifications, and I'd verify that the new boot source is actually supported by our bootloader and kernel. Then I'd assess the impact: what needs to change in U-Boot (e.g., new driver, different environment variables, different partition layout), what needs to change in the kernel (e.g., different MTD or MMC driver, different root device), and whether the root filesystem needs to be reformatted or migrated. I'd also check if there are any regulatory or certification implications — changing the boot source might affect the device's security posture or the integrity verification chain, which could be relevant for the clinical trial. Once I have the scope, I'd work with the team to create a mitigation plan: ideally, we'd validate the new boot path on a development board or a small batch of prototype boards before committing to production. If that's not possible, I'd propose a fallback strategy — for example, keeping the SPI NOR as a secondary boot source with a fallback mechanism, or creating a bootloader that can handle both interfaces. I'd also be transparent with the project manager about the risks and the additional testing that might be needed. The key is to not panic, gather the facts, and work collaboratively to find a path that meets the clinical trial deadline without compromising reliability.

**Possible follow-ups:**
- How would you prioritize the work if the timeline is tight and you can't validate everything before the clinical trial?
- What specific risks would you flag to the project manager about this change?
