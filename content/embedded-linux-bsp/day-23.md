## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of two identical I2C sensors on the same bus, while the other works fine?

**Answer:** I'd start by confirming whether the problem is at the electrical, device tree, or driver level. First, I'd check `i2cdetect` to see if the device appears on the bus at all. If it doesn't show up, I'd verify the device tree entry — specifically the I2C address and whether the node is correctly instantiated. A common issue is an incorrect or conflicting address, or the node being disabled by default. I'd also check the kernel log for probe failures or deferred probe messages. If the address is correct but the device isn't detected, I'd move to hardware: measure the SDA/SCL lines with an oscilloscope during the address phase, verify pull-up resistors are present and correctly valued, and check that the sensor's power supply and reset pins are properly handled. If the device is detected but the driver fails to probe, I'd look at the driver's probe function — maybe it's checking an interrupt line or a GPIO that isn't wired correctly on this particular board. I'd also check whether the two sensors have different address strapping and whether the address in the device tree matches the actual hardware configuration. Finally, I'd verify that the driver supports the specific revision of the sensor, as identical-looking parts can have different register maps.

**Possible follow-ups:**
- How would you distinguish between a device tree issue and a hardware issue if the sensor is detected intermittently?
- What if the sensor is detected but returns incorrect data — how would you approach that?

## Q2: How would you approach implementing a kernel driver for a device that needs to be accessed by both a real-time safety-critical task and a non-real-time monitoring task, where the safety-critical task must never be blocked by the monitoring task?

**Answer:** The key is to ensure that the safety-critical path has guaranteed access to the hardware regardless of what the monitoring task is doing. I'd structure the driver so that the safety-critical task interacts with the hardware through a dedicated, minimal interface — ideally a direct register access or a tightly controlled ioctl that doesn't take any locks shared with the monitoring path. The monitoring task would use a separate, higher-level interface that can afford to sleep or block. If both tasks need to access the same hardware, I'd use a hardware-level arbitration mechanism rather than a software mutex — for example, a hardware semaphore or a lock-free ring buffer where the safety-critical task writes and the monitoring task reads. The driver would also need to handle the case where the monitoring task holds a lock and gets preempted — that's a classic priority inversion scenario. I'd use priority inheritance or a dedicated high-priority kernel thread for the safety-critical path. For the actual data flow, I'd use a lock-free ring buffer with proper memory barriers, where the safety-critical task is the producer and the monitoring task is the consumer. The monitoring task can miss data if it's too slow, but the safety-critical task must never be blocked.

**Possible follow-ups:**
- How would you handle the case where the monitoring task needs to configure the device, and that configuration could affect the safety-critical path?
- What kernel mechanisms would you use to ensure the safety-critical task's deadline is met?

## Q3: How would you approach designing the boot sequence for a system with two processors — an application processor running Linux and a safety-critical microcontroller — where the microcontroller must be fully initialized and running its safety monitoring routines before the Linux userspace starts any critical applications?

**Answer:** I'd structure this as a staged boot with explicit handshakes. The application processor's bootloader would be responsible for releasing the microcontroller from reset and waiting for a "ready" signal before proceeding to boot Linux. This could be implemented as a GPIO handshake or a message over a shared mailbox. The bootloader would power up the microcontroller, let it initialize its safety monitoring routines, and then wait for a status signal. Only after receiving that signal would the bootloader continue to load the kernel. In the kernel, I'd add a driver that performs a second handshake — verifying the microcontroller is still healthy before allowing userspace critical applications to start. This could be done in a kernel driver that exposes a sysfs node or a character device, and the init system would be configured to wait for that node to be ready before starting critical services. I'd also consider using the kernel's `probe` deferral mechanism: the driver for the critical application's hardware could defer probing until the microcontroller handshake is complete. For the overall design, I'd document the boot sequence clearly, including timeout and failure handling — what happens if the microcontroller doesn't respond? The system should fail safe, likely by not starting critical applications and entering a safe state.

**Possible follow-ups:**
- How would you handle the case where the microcontroller fails to initialize — what's the fail-safe behavior?
- How would you test this boot sequence to ensure it's reliable?

## Q4: How would you approach implementing a kernel driver for a device that needs to perform a hardware-triggered DMA transfer, where the trigger comes from an external sensor's interrupt line, and the data must be processed and made available to userspace within a hard real-time deadline (e.g., 2 ms)?

**Answer:** The critical design decision is where the data processing happens and how the DMA transfer is managed. I'd start by configuring the DMA controller to transfer data from the sensor's FIFO or data register to a pre-allocated DMA buffer in kernel memory. The sensor's interrupt line would be connected to a GPIO that's configured as a wakeup source and triggers a threaded interrupt handler. In the interrupt handler, I'd initiate the DMA transfer and return immediately — the actual data processing would happen in the DMA completion callback. The completion callback would run in a context that can process the data quickly and then either copy it to a userspace buffer or use a mechanism like `copy_to_user` if the data volume is small. For the 2 ms deadline, I'd need to ensure that the entire path — interrupt latency, DMA setup, transfer completion, and data delivery — fits within the budget. I'd use a kernel thread with `SCHED_FIFO` for the data processing to avoid being preempted by normal tasks. For userspace delivery, I'd use a character device with a read implementation that blocks until data is available, or use a netlink socket or a shared memory region with a notification mechanism. I'd also consider using `dma_alloc_coherent` for the DMA buffer to avoid cache coherency issues, and I'd profile the entire path to identify where the time is spent.

**Possible follow-ups:**
- How would you handle the case where the DMA transfer takes longer than the deadline?
- What if the sensor generates data faster than userspace can consume it — how would you handle backpressure?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the manufacturing team reveals that they need to substitute the currently qualified eMMC flash with a different vendor's part due to a supply chain shortage. The new eMMC has a different erase block size, different wear-leveling behavior, and a slightly different controller interface. The project is four weeks from the start of production, and the current eMMC is already qualified and tested. How would you handle this situation?

**Answer:** I'd start by acknowledging the supply chain reality — this is a legitimate constraint, and the manufacturing team isn't doing this arbitrarily. My first step would be to gather the technical details: the new eMMC's datasheet, its erase block size, its wear-leveling behavior, and any differences in the controller interface. I'd then assess the impact on our current software stack. The key areas to evaluate are: the filesystem (we're likely using ext4 or a similar journaling filesystem — the erase block size affects alignment and performance), the partition layout (if the new eMMC has a different erase block size, our current partition offsets might not be optimal), and the bootloader (U-Boot needs to be able to read from the new eMMC). I'd also check whether the new eMMC requires any different initialization sequence or has different power-on timing. Once I have the impact assessment, I'd work with the manufacturing team to get a sample of the new eMMC as early as possible. I'd then run a focused test campaign: boot the system, run the filesystem through its normal operations, and specifically test power-loss scenarios — that's where eMMC differences show up most. I'd also run a wear-leveling test to ensure the new part doesn't have unexpected behavior under sustained write load. If the new eMMC proves compatible, I'd document the qualification results and update the BSP to support both parts. If there are issues, I'd work with the manufacturing team to see if a different part from the same vendor or a different vendor altogether would be more suitable. Throughout this, I'd keep the project manager informed of the risk and the mitigation plan. The key is to be proactive — get the sample early, test thoroughly, and have a clear go/no-go decision before production starts.

**Possible follow-ups:**
- What specific tests would you run to qualify the new eMMC for a medical device?
- How would you handle the case where the new eMMC passes basic tests but shows subtle issues under sustained load?
