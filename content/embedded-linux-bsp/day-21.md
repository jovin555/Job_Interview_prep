# embedded-linux-bsp — Day 21

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel log shows "Failed to request IRQ" for a device that worked on the previous board revision?

**Answer:** I'd start by confirming the exact IRQ number and what's claiming it. The first step is to check `/proc/interrupts` to see which interrupts are already allocated and by which drivers. A common cause is an IRQ conflict — either two devices are configured with the same interrupt line in the device tree, or a driver is requesting an IRQ that's already taken by another driver that probed earlier. I'd also verify the device tree interrupt properties against the actual hardware connection: the GPIO controller, interrupt parent, and interrupt number all need to match the schematic. Another possibility is that the interrupt controller itself isn't fully initialized when the driver probes — this can happen if probe ordering changed due to a driver becoming built-in versus a module, or if a dependency (like a GPIO controller or interrupt controller) probes later. I'd check the probe order in the boot log and consider adding `depends-on` properties or deferred probe handling. I'd also verify the hardware: on a new board revision, the interrupt line might be floating or pulled to the wrong level, causing spurious interrupts that exhaust the IRQ. A logic analyzer or scope on the interrupt line during boot can confirm whether the line is behaving as expected. Finally, I'd check whether the driver is using `request_irq` with the right flags — for example, `IRQF_TRIGGER_FALLING` versus `IRQF_TRIGGER_LOW` — since a mismatch between the device tree interrupt type and the actual hardware signal can cause the request to fail or the interrupt to fire continuously.

**Possible follow-ups:** How would you determine whether the issue is a device tree problem versus a driver problem? What if the IRQ is shared — how would you debug that?

## Q2: How would you approach designing a kernel driver for a device that needs to wake the system from suspend, but the device is on an I2C bus that loses power during suspend?

**Answer:** This is a classic power-domain problem. The key constraint is that the wake-up source must remain powered during suspend, but the I2C bus it sits on is being cut. I'd first check the hardware design to see if the device has a separate always-on power rail or a wake-up pin that doesn't depend on the I2C bus. If the device has a dedicated interrupt line that can wake the system, I'd configure it as a wake-up source using `enable_irq_wake()` in the driver's suspend callback — this tells the interrupt controller to keep that line active during suspend. The tricky part is that the driver can't communicate with the device over I2C while suspended, so any wake-up handling that requires reading registers over I2C won't work until after resume. I'd design the driver so that the interrupt handler during suspend simply records that a wake event occurred and defers all I2C communication to the resume path. If the hardware doesn't have a dedicated wake pin, I'd need to work with the hardware team to add one, or use a GPIO that's on an always-on power domain. Another approach is to keep the I2C controller powered but put only the device into a low-power state — this depends on whether the I2C bus power is controlled independently. I'd also verify the suspend/resume ordering: the wake-up interrupt must be enabled before the I2C controller is suspended, and the interrupt handler must not try to access the bus until the controller is resumed. In the device tree, I'd use the `wakeup-source` property and ensure the interrupt is correctly described. Finally, I'd test the suspend/resume cycle thoroughly, including the case where the device generates an interrupt during suspend, to confirm the system wakes reliably and the driver re-initializes the device properly.

**Possible follow-ups:** How would you handle the case where the device needs to be re-initialized after resume because it lost power? What if the wake-up interrupt fires but the system doesn't actually need to wake — how would you filter that?

## Q3: How would you approach implementing a kernel driver for a device that needs to be accessed by both a real-time safety-critical task and a non-real-time monitoring task, where the safety-critical task must never be blocked by the monitoring task?

**Answer:** The fundamental requirement is that the safety-critical path must have guaranteed access to the hardware without being delayed by lower-priority work. I'd start by identifying the shared resource — is it a single register bank, a DMA channel, or a complete device? The cleanest approach is often to partition access at the driver level: the safety-critical task gets a dedicated interface that uses atomic operations or a spinlock with interrupts disabled, while the monitoring task uses a separate, slower path that can tolerate blocking. If both tasks need to access the same hardware registers, I'd use a priority-aware locking scheme. In the kernel, this could mean using a `mutex` for the monitoring path and a `spinlock` with `spin_lock_irqsave` for the safety-critical path — but you can't mix these on the same lock. A better approach is to use a `rt_mutex` with priority inheritance, which ensures that if the monitoring task holds the lock and the safety-critical task blocks on it, the monitoring task's priority is temporarily boosted so it finishes quickly and releases the lock. However, even priority inheritance has overhead, so for truly hard real-time requirements, I'd consider lock-free approaches: the safety-critical task writes to a dedicated hardware register or memory-mapped location that the monitoring task reads via a separate path, or the driver maintains a small ring buffer where the safety-critical task writes and the monitoring task reads with careful memory barriers. Another option is to use the `PREEMPT_RT` patch set, which makes the kernel fully preemptible and provides real-time mutexes as the standard locking primitive. I'd also consider whether the two tasks can use separate instances of the device — for example, two DMA channels or two register windows — to avoid contention entirely. Finally, I'd document the locking protocol clearly and add runtime assertions (like `might_sleep()` checks) to catch accidental blocking in the safety-critical path during testing.

**Possible follow-ups:** How would you verify that the safety-critical task never misses its deadline during testing? What if the monitoring task needs to read data that the safety-critical task is actively updating — how would you ensure consistency?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the hardware team reveals that they need to change the main processor's boot mode strap resistors to accommodate a new flash part. The change means the processor will boot from a different interface (e.g., from SPI NOR to eMMC), and the bootloader and kernel configurations are already tuned for the current boot source. The project is six weeks from the start of a clinical trial. How would you handle this situation?

**Answer:** I'd start by getting the full picture from the hardware team — why the change is needed, whether the new flash part is a like-for-like replacement or a fundamentally different interface, and whether the change is mandatory or optional. If it's mandatory, I'd immediately assess the impact on the boot flow: the bootloader (U-Boot) would need to be rebuilt with the new boot device enabled, the device tree would need the corresponding flash node, and the kernel command line might need changes for the root device. I'd also check whether the boot ROM on the processor supports booting from the new interface directly, or whether we need a fallback mechanism. The key risk is that this change touches the most critical part of the system — the boot path — and any mistake could brick the device. I'd propose a staged approach: first, verify the new boot source works on a development board with the same processor and flash part, ideally before the production boards are assembled. If that's not possible, I'd ask the hardware team to provide a few early prototypes for bring-up. I'd also work with the team to define a rollback plan: if the new boot source fails during bring-up, can we revert to the original flash part, or is there a hardware workaround? In parallel, I'd update the bootloader and kernel configurations, and I'd add a boot-time diagnostic that logs which boot source was used, so we can verify the change in production. I'd also flag the schedule risk to the project manager early — this is a change that could easily take two to three weeks to validate, and it needs to happen before the clinical trial. Finally, I'd document the change in the design history file, since this is a medical device and any hardware change needs to be traceable.

**Possible follow-ups:** How would you handle the situation if the hardware team says the change is already baked into the production boards and can't be reverted? What if the new boot source works in U-Boot but fails to load the kernel — how would you debug that?
