# embedded-linux-bsp — Day 49

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel log shows "Unhandled fault: external abort on non-linefetch" when a driver accesses a memory-mapped FPGA peripheral?
**Answer:** An external abort on non-linefetch typically indicates the CPU attempted a memory access that the bus fabric or peripheral rejected — this is different from a page fault, which is a Linux memory management event. My first step would be to identify the exact address being accessed when the fault occurs, since the kernel log usually includes the faulting address and the PC value. I'd then check whether that address falls within the expected memory window for the FPGA peripheral as defined in the device tree. Common causes include: the FPGA not being powered or clocked when the access occurs, the memory region not being properly mapped (wrong `reg` property, missing `ranges` in the parent bus node), a bus controller or chip-select not configured correctly, or the FPGA logic itself not responding because it hasn't been programmed yet. I'd verify the FPGA is actually programmed and its configuration done pin is asserted before the driver probes. I'd also check whether the access size matters — some FPGA registers only support 32-bit accesses, and an 8-bit or 16-bit access can trigger a fault on certain bus implementations. Using a logic analyzer or bus tracer to see whether the access reaches the FPGA and what response comes back would help isolate whether this is a Linux configuration issue or a hardware/FPGA logic issue. I'd also confirm the driver isn't accessing the peripheral before its clock is enabled in the kernel's clock framework.

**Possible follow-ups:**
- How would you determine whether this is a device tree problem versus an FPGA logic problem?
- What kernel configuration options or debug facilities would you enable to get more information about the fault?

## Q2: How would you approach designing a kernel driver for a device that needs to wake the system from suspend, but the device is on an I2C bus that loses power during suspend?
**Answer:** This is a common challenge in embedded systems where power domains are shut down during suspend to save energy. The key issue is that the wake source needs to be able to assert an interrupt even when its own power domain is off, and the interrupt controller must remain powered. I'd start by examining the hardware architecture: does the device have a separate always-on power rail for its wake logic, or does it communicate through a power-management IC (PMIC) that stays awake? If the device itself loses power, it can't generate an interrupt, so the wake path must go through something that remains powered — perhaps a GPIO on the SoC that's configured as a wake source, or the PMIC detecting a button press or external event. For the driver design, I'd separate the suspend path into stages: first, save device state and prepare for power loss; second, configure the wake source (e.g., set up a GPIO interrupt as a wakeup source using `enable_irq_wake()`); third, ensure the I2C controller is properly suspended. On resume, the driver needs to handle the fact that the device may have lost its configuration — it should reinitialize from scratch rather than assume register contents are preserved. I'd also consider whether the driver should use the kernel's `dev_pm_ops` with proper `suspend` and `resume` callbacks, and whether the device needs to be re-probed or just re-initialized. One important detail: if the I2C bus itself loses power, the controller may need to be reinitialized before any transactions can occur, so the resume path must sequence correctly — bus controller first, then device.

**Possible follow-ups:**
- How would you handle the case where the device needs to be accessed during the resume path before the I2C controller is fully restored?
- What role does the device tree play in describing the wake-up capabilities and power dependencies?

## Q3: How would you approach implementing a kernel driver for a device that uses DMA to transfer data from an FPGA to system memory, where the FPGA can generate data at rates exceeding what the CPU can process in real-time?
**Answer:** When the data rate exceeds what the CPU can handle in real-time, the design must ensure that DMA transfers complete without CPU intervention for each individual data item, and that the CPU only processes data in batches. I'd structure this around a ring buffer in system memory: the FPGA writes data via DMA into pre-allocated, physically contiguous buffers, and the driver manages ownership of buffer slots between hardware and software. The key design decisions are: buffer size and count (large enough to absorb bursts, but not so large that memory is wasted), interrupt strategy (interrupt on completion of each buffer, or on a watermark to reduce interrupt load), and the userspace delivery mechanism. For high throughput, I'd consider using the kernel's DMA engine API with `dma_alloc_coherent()` or `dma_map_single()` depending on whether the FPGA needs cache-coherent access. If the FPGA writes continuously, I'd use a double-buffering or multi-buffer scheme where the driver alternates between buffers being filled by DMA and buffers being processed or forwarded to userspace. For userspace delivery, options include: a character device with `read()` that copies data (fine for moderate rates), `mmap()` of the DMA buffers for zero-copy access, or netlink/relayfs for streaming data. If the CPU genuinely cannot keep up even with batched processing, I'd look at hardware flow control — can the FPGA be paused via a backpressure signal, or can the DMA controller be configured to drop or overwrite old data based on the application's requirements? For a medical device, data loss is typically unacceptable, so I'd ensure the buffer sizing accounts for worst-case latency in the userspace consumer and that the driver provides backpressure or error reporting if buffers overflow.

**Possible follow-ups:**
- How would you choose between interrupt-driven completion notification versus polling the DMA status register?
- What considerations apply if the data needs to be timestamped at arrival time for medical event correlation?

## Q4: How would you approach debugging a kernel panic that occurs only on every third or fourth boot, with no consistent trigger?
**Answer:** Intermittent boot-time panics are among the most challenging issues because the reproduction is unreliable and the root cause may be timing-dependent. I'd approach this systematically. First, I'd gather as much data as possible from each panic: the full stack trace, the faulting instruction, the register state, and any distinctive patterns in the log leading up to the crash. Even if the trigger seems random, there's usually a pattern — perhaps it correlates with a specific hardware revision, a temperature range, or a particular boot device. I'd instrument the boot process to add logging at key stages: early platform initialization, memory controller setup, driver probing, and filesystem mount. If the panic is in driver probe, I'd look for race conditions where two drivers or two initialization paths access shared hardware without proper locking. Another common cause is a race between interrupt handlers and initialization code — an interrupt arriving before the handler is fully set up, or a device asserting an interrupt before its driver has registered a handler. I'd also check for memory initialization issues: if the panic is in the memory allocator or involves corrupted pointers, it could be a hardware issue like marginal DRAM timing that only manifests under certain temperature or voltage conditions. Using `panic_on_oops` and `printk` with timestamps would help correlate the panic with specific boot events. I'd also try bisecting — booting multiple times with different kernel configurations, device tree changes, or hardware configurations to narrow down what changes the failure rate. If the issue is truly intermittent and hardware-related, tools like `memtest86` running overnight or thermal cycling the board might reveal marginal components. For a medical device, I'd also consider whether the system needs a hardware watchdog that can recover from boot failures and whether the bootloader should implement a "last known good" fallback.

- How would you use kernel debugging features like KASAN, lockdep, or ftrace to help isolate an intermittent issue like this?
- What role would statistical analysis of multiple panic logs play in your debugging approach?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during integration testing, you discover that the kernel's real-time scheduling class (SCHED_FIFO) is causing priority inversion on a shared hardware resource between your sensor driver and the display driver. The display team insists their driver needs the highest priority, and the sensor team says their data will be corrupted if they miss their deadline. How would you handle this situation?
**Answer:** Priority inversion on a shared resource is a classic real-time systems problem, and the first thing I'd do is make sure both teams understand the actual technical issue rather than letting it become a team conflict. I'd call a meeting with both teams and start by asking each to articulate their real requirements: what is the display driver's worst-case latency requirement, and what is the sensor's deadline and what happens when it's missed? Often, the stated priority requirements are based on assumptions that haven't been re-examined. The technical solutions I'd explore include: using priority inheritance or priority ceiling protocols where the shared resource is protected by a mutex (the kernel's `rt_mutex` supports priority inheritance), restructuring the code so the shared resource is accessed in a critical section that's short enough that blocking is bounded and acceptable, or partitioning the resource so each driver has its own private access path. If the shared resource is a hardware register or a bus, I might look at whether one driver can use a different access mechanism — for example, the display driver might be able to use a different programming interface that doesn't conflict. I'd also question whether both drivers genuinely need SCHED_FIFO, or whether one could run as a regular process with appropriate nice priority. If the requirements genuinely conflict — both drivers have hard deadlines that can't be met with the current hardware — then I'd escalate with data: measure actual worst-case blocking times, document the impact of each possible priority assignment, and present the trade-offs to the project manager and systems engineer. The decision might ultimately be a hardware change (separate buses, dedicated resources) or a system architecture change (moving one function to a different processor). Throughout this, my role is to facilitate a data-driven decision, not to pick a winner based on which team argues more persuasively.

**Possible follow-ups:**
- How would you go about measuring and documenting the actual worst-case blocking times to support your analysis?
- What if the project schedule doesn't allow time for a hardware change — how would you arrive at an acceptable interim solution?
