# embedded-linux-bsp — Day 102

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel's `probe()` for a platform driver is deferred indefinitely because a `regmap`-based I2C sensor's parent bus is not yet available at the time the driver is registered?

**Answer:** An indefinite `-EPROBE_DEFER` loop almost always means a dependency in the device tree graph is never being satisfied, not that the driver itself is broken. The first thing I'd do is confirm the deferral is actually happening and identify what it's waiting on — enabling `initcall_debug` and looking at the deferred-probe list (`/sys/kernel/debug/devices_deferred` where available) tells you which device is stuck and, with `driver_deferred_probe_timeout` or verbose logging, often which supplier it's waiting for. From there I'd walk the device tree: does the sensor node have a `vdd-supply`, `i2c-parent`, or clock `phandle` that points at a node which either doesn't exist, has a different `compatible` string than the driver that's supposed to bind to it, or is itself disabled (`status = "disabled"`)? A very common cause is a regulator or I2C controller node that's present but whose own driver never probes because of a missing clock or pinctrl — so the deferral cascades. I'd also check that the I2C bus controller itself is enabled and that the sensor is a child of the correct bus node, since a `regmap`-based driver can't get its regmap until the parent bus is live. If the supplier is a PMIC or regulator that's on a different bus, I'd verify that bus is up first. Finally, I'd rule out a `compatible` mismatch between the device tree node and the driver's `of_match_table` — a silent mismatch means the driver never even attempts to bind, which can look like a deferral if something else is also pending. The systematic approach is: identify the stuck device, enumerate its DT dependencies, and verify each one independently probes.

**Possible follow-ups:** How would you distinguish a genuine deferral from a driver that simply never matches the DT node? What would you change in the device tree if the supplier is legitimately optional?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our deltas on top through configuration fragments rather than a forked `.config` or a patched recipe. In Yocto terms, I'd create a `.cfg` fragment file containing only the `CONFIG_*` lines we need to add or change, and wire it into the kernel build via a `SRC_URI` entry with the `file://` scheme plus the `KERNEL_CONFIG_FRAGMENTS` or, more portably, a `.bbappend` that appends to `SRC_URI` and lets the kernel's `merge_config`/`configme` machinery combine fragments with the vendor defconfig. The fragment approach means the vendor recipe and defconfig stay untouched, so when the vendor bumps their kernel we rebase by re-checking that our fragment's symbols still exist and still mean the same thing — a much smaller surface than a full config diff. I'd keep fragments small and purpose-named (e.g., one for a new peripheral, one for a debugging option) so they're reviewable and can be enabled per-machine or per-image via `MACHINEOVERRIDES` or a distro feature. For symbols that depend on other symbols, I'd verify with `bitbake -c menuconfig` or by inspecting the generated `.config` in the workdir, because `merge_config` will silently drop a fragment line whose dependencies aren't met. I'd also add a sanity check in CI that diffs the resulting `.config` against expectations so a vendor kernel bump that renames a symbol gets caught immediately rather than at runtime.

**Possible follow-ups:** What happens if two fragments set the same symbol to different values, and how would you control precedence? How would you handle a configuration option that only exists after a vendor patch is applied?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path holds, so the design has to decouple them at the data-structure level rather than relying on scheduling priority alone. I'd structure the driver so the real-time access path takes only a short, bounded lock — ideally a spinlock held for a few instructions, or better, a lock-free single-producer/single-consumer ring buffer — while the logging path consumes from a separate buffer that the real-time path only ever writes into without waiting. Concretely: the real-time task's `ioctl` or `read` copies data into a pre-allocated ring buffer and returns immediately; the logging task drains that buffer at its own pace. If the ring fills because logging is slow, the real-time path must have a defined, non-blocking policy — drop oldest, drop newest, or overwrite — chosen so it never stalls. I'd avoid any mutex on the real-time path entirely, and avoid `copy_to_user` under a lock since page faults can sleep. For the shared hardware itself, if both paths touch the same registers, I'd serialize register access with a spinlock but keep the critical sections tiny, and make sure the logging path can't hold that lock across a sleeping operation. I'd also document the contract clearly: the real-time path has a worst-case latency budget, and the logging path is explicitly best-effort and may lose data. Testing would include deliberately starving the logging task to confirm the real-time path's latency stays bounded.

**Possible follow-ups:** How would you verify the real-time path's worst-case latency empirically? What changes if the logging task runs in userspace rather than in the kernel?

## Q4: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder classes of bug because the usual error paths are all clean, so I'd treat it as "the driver thinks it's talking to the hardware, but something between the driver and the actual device is wrong." First I'd confirm the driver is touching the right registers: dump the device tree node the driver bound to and compare the `reg` base address and size against the SoC's memory map and the schematic — an off-by-one in the address or a wrong `reg` size can mean reads return zeros or the writes go nowhere without faulting. Then I'd verify the clock and power are actually on: a peripheral whose clock gate was never enabled or whose regulator is in a low-power state will often accept register writes silently and return stale or zero data. I'd check the pinctrl state — if the pins are muxed to the wrong function, the bus may look idle rather than erroring. On a bus-attached device (I2C/SPI), I'd put a scope or logic analyzer on the lines during probe to see whether transactions are actually going out and whether the device ACKs; a device that NACKs every access but whose driver ignores the return code will "succeed" and do nothing. I'd also check whether the driver's `probe()` is initializing the hardware in the right order — some devices need a reset pulse or a specific power-up sequence before they respond, and skipping it leaves them in a state where they ignore the bus. Finally, I'd add temporary instrumentation: read back a known register (like a chip ID) right after probe and log it, which immediately tells you whether communication is real.

**Possible follow-ups:** If the chip ID reads back correctly but the device still doesn't function, where would you look next? How would you catch a driver that ignores bus error return codes?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd start by making sure both teams are working from the same facts rather than trading positions. The hardware team's need is real — they need those pins — and the software team's concern is real — the manufacturing line depends on early console output for test and debug. So I'd frame the conversation around what's actually at stake on each side: which pins, what the new peripheral needs, and exactly what the manufacturing line uses the console for (automated test scripts parsing boot output, manual debug, or both). Then I'd look for options that satisfy both rather than picking a winner. A common resolution is to keep a console available on the new pinmux group and update the bootloader and device tree together as a coordinated change, with the manufacturing test scripts updated in the same release — the risk isn't the change itself, it's the change landing out of sync with the line. I'd want a plan that includes: a single change set covering bootloader pinmux, device tree, and any test-script updates; a validation step on a bench unit that confirms early boot output still appears on the expected pins before the change goes anywhere near production; and a rollback path if the line hits a problem. If the manufacturing dependency turns out to be fragile — say, scripts that hard-code a specific UART — I'd flag that as a separate robustness issue worth fixing regardless. The key is to treat it as a coordination and sequencing problem, not a hardware-versus-software argument, and to get the manufacturing stakeholders into the conversation early rather than after the decision.

**Possible follow-ups:** What would you do if the manufacturing team can't update their test scripts before the hardware change is needed? How would you document the pinmux change so it's traceable for regulatory purposes?
