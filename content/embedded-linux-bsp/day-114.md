# embedded-linux-bsp — Day 114

## Q1: How would you approach debugging a situation where the kernel boots and the root filesystem mounts, but a userspace service that depends on a kernel driver starts before the driver has finished initializing, causing intermittent failures on first access?

**Answer:** This is fundamentally an ordering problem, and I'd resist the temptation to "fix" it by sprinkling retries into the userspace service — that masks the race rather than resolving it. The first step is to establish what the actual dependency is and where the kernel exposes it. If the driver registers a character device, the device node appearing in `/dev` is not proof the hardware is ready; `probe()` may have returned but deferred work (firmware load, calibration, first bus transaction) may still be pending. I'd check whether the driver signals readiness through a proper mechanism — a `completion` exposed via a sysfs attribute, a `devm_`-managed state flag readable through an `ioctl`, or a `uevent` the service can subscribe to. The cleanest fix is usually to make readiness observable and have the service block on it rather than poll a timer.

On the init side, I'd look at how the service is started. With systemd, a `After=` on the device unit plus a `Wants=`/`BindsTo=` relationship is the idiomatic answer, but that only works if the driver actually publishes a device unit — which requires the driver to call the right registration path so udev tags it. With SysV-style init or a custom supervisor, I'd add an explicit readiness gate: the service opens the device and blocks on a `read()` or `ioctl()` that the driver completes only when hardware is confirmed up. If the driver can't be changed, a udev rule that triggers a oneshot unit on device add is a reasonable shim, but I'd document it as a workaround.

The deeper question is whether the driver's `probe()` is doing too much synchronously or too little. If `probe()` returns before the hardware is usable, that's arguably a driver bug — `probe()` should either complete initialization or return `-EPROBE_DEFER` so the driver core retries later. I'd trace the boot with `initcall_debug` and timestamped `dmesg` to see the actual ordering, and confirm whether the failure window is milliseconds (a genuine race) or seconds (a missing dependency that should be modeled as one).

**Possible follow-ups:** If the driver can't be modified because it's from a vendor BSP, what options remain for making readiness observable from userspace? How would you distinguish this race from a genuine hardware initialization failure that happens to look intermittent?

## Q2: How would you approach structuring a Buildroot configuration for a small medical device where the root filesystem must be reproducible, minimal, and auditable, and where you expect to maintain it across several years of production?

**Answer:** Buildroot is a good fit here precisely because it produces a small, deterministic image from a single configuration — but "reproducible and auditable" requires discipline beyond just running `make`. I'd start by treating the Buildroot `.config` and the board directory as version-controlled source of truth, and pinning every package to an explicit version rather than tracking upstream. Buildroot's default of downloading tarballs at build time is a supply-chain risk for a regulated product; I'd mirror the sources internally and record checksums, so a rebuild years later produces the same bits even if upstream disappears.

For minimality, I'd use `make savedefconfig` to keep the configuration readable in review, enable only the packages the product actually needs, and be deliberate about the toolchain — an internal toolchain built by Buildroot gives reproducibility, whereas an external prebuilt toolchain introduces a dependency on whoever built it. I'd also strip the rootfs of documentation, locales, and development files via the target options, and consider a read-only rootfs with a separate writable partition for logs and configuration, which suits a medical device that must survive power loss.

For auditability, the key artifacts are the defconfig, the board overlay, any patches applied to packages (kept as explicit patch files in the board directory, not applied by hand), and a manifest of what went into the image. Buildroot can emit a license manifest and a package list; I'd archive those with each release build alongside the image hash. I'd also set up a CI job that rebuilds from a clean tree and compares hashes, because reproducibility claims that aren't continuously tested tend to quietly rot.

The trade-off versus Yocto is real: Buildroot is simpler and faster to bring up for a single-board product, but it has weaker support for layered customization across a product family and less mature tooling for SDK generation and package feeds. For a single device with a stable package set, that simplicity is an advantage; if the product line is expected to spawn variants, I'd reconsider.

**Possible follow-ups:** How would you handle a security update to a single package in a Buildroot image without rebuilding and requalifying everything? What would make you choose Yocto over Buildroot for this product, and at what point in the product's life would you revisit that decision?

## Q3: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder failure modes because every obvious signal says the system is healthy, so I'd start by questioning the assumption that `probe()` succeeding means the driver is talking to the hardware. The first thing I'd verify is whether the driver is bound to the device I think it is — check `/sys/bus/<bus>/devices/` and the driver's sysfs directory to confirm the binding, and confirm the device tree node that matched is the one I intended. A common cause is a compatible string that matches a more generic driver, or an `of_match` table entry that binds to the wrong node, so the "real" driver never runs.

Next I'd verify the register accesses are actually reaching the hardware. If the driver uses `regmap`, I can enable `regmap` debugfs and watch transactions; if it uses `readl`/`writel` directly, I'd add temporary instrumentation or use a bus analyzer on the relevant interface. A frequent culprit is a clock or reset that was never enabled — the driver reads back a register and gets zeros or all-ones, treats that as a valid value, and continues. Reading back a known register (an ID register, a revision register) and comparing against the datasheet is the fastest way to confirm the bus is live. If the read returns `0x00` or `0xFF` consistently, that points to the peripheral not being clocked, held in reset, or not powered.

I'd also check the pinmux and pad configuration — a peripheral can be clocked and addressed correctly but have its pins muxed to a different function, so the bus transactions go nowhere. On modern SoCs the pinctrl state is applied by the driver core based on device tree, but a missing or wrong `pinctrl-0` reference produces exactly this silent failure. Finally, I'd check whether the driver's interrupt handler is ever firing — if the device is configured for interrupt-driven operation and the IRQ is misrouted or the trigger type is wrong, the driver may sit waiting forever without logging anything.

**Possible follow-ups:** How would you use a logic analyzer or oscilloscope to confirm the bus is actually being driven, and what would you look for? If the register readback returns plausible-looking but wrong values, how would you narrow down whether it's an addressing error or a hardware fault?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path holds, so the design has to separate the two access paths at the data structure level rather than relying on priority inheritance to sort it out. I'd start by identifying what the real-time task actually needs from the driver — typically a small, bounded operation like reading a status register or pushing a sample into a buffer — and make that path lock-free or use a lock that the logging path never takes. A `spinlock` shared between the two would be the obvious mistake: even with `spin_lock_irqsave`, a logging task holding it while doing something slow (formatting a message, copying to a ring buffer) would stall the real-time task.

The standard pattern is a single-producer/single-consumer ring buffer between the driver and the logging path. The real-time path writes into the ring with a lock-free or `spin_trylock`-guarded operation and returns immediately; the logging path drains the ring at its own pace. If the ring fills, the real-time path drops the oldest entry or sets an overflow flag rather than blocking — losing a log line is acceptable, missing a deadline is not. For the hardware access itself, if both paths need to touch the same registers, I'd serialize only the register access with a short-held lock and keep everything else outside it, or better, give the real-time path a dedicated register window or a hardware FIFO it can read without contending with the logging path.

I'd also think about the interrupt context. If the real-time task is actually a threaded handler or a `SCHED_FIFO` userspace thread, the driver's job is to get data to it with minimal latency — an `irq` handler that does the minimum and wakes the waiter, with the heavy lifting deferred to a workqueue that the logging path can also use. And I'd be explicit about priority: the real-time thread should run at a priority above the logging thread, and the driver should not introduce any priority inversion by having the real-time path wait on a resource the logging path owns.

**Possible follow-ups:** How would you verify the real-time path's worst-case latency under load, and what tooling would you use? If the hardware only exposes a single register window that both paths must use, how would you restructure the access to keep the real-time path bounded?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination problem first and a technical one second, because the technical change is small but the blast radius touches manufacturing, which is where schedule risk lives. My first move would be to get the actual constraints on the table rather than let each team argue from its own corner. From hardware: which pins are needed, why this specific pinmux group, and whether there's an alternative routing that avoids the debug UART. From software: exactly what depends on the current console — is it the bootloader's early console, the kernel's `earlycon`, the userspace getty, or all three — and what the manufacturing line actually does with it (does it parse output, or just watch for a prompt?). From manufacturing: what the cost of a change is, and whether there's a window where both configurations could be supported.

With that information I'd look for a design that decouples the two concerns. The debug UART's pinmux is set in the bootloader and again in the kernel device tree; if the new peripheral's pins are only needed after boot, the UART could stay on its current pins through early boot and the peripheral could be muxed in later by its driver — that preserves the manufacturing console and gives hardware its pins. If the pins genuinely conflict from power-on, then the change is real and the question becomes how to stage it: update the bootloader and device tree together, verify the new console works on a bench unit before any production board is touched, and give manufacturing a documented procedure and a rollback path.

I'd also make sure the decision is recorded with its rationale, because in a regulated environment a pinmux change to the debug console is the kind of thing that shows up in a design history file review and needs a traceable justification. And I'd set a decision deadline — this is the kind of issue that can drift for weeks if nobody owns it — and escalate to the project lead if the teams can't converge, framing it as a schedule trade-off rather than a technical disagreement.

**Possible follow-ups:** If manufacturing insists the console must be available from the first instruction and the new peripheral also needs those pins at power-on, what options remain? How would you validate the change on a single board before committing the whole production line to it?
