# embedded-linux-bsp — Day 129

## Q1: How would you approach debugging a situation where the kernel boots successfully and the root filesystem mounts, but a userspace application that opens a character device and issues `ioctl()` calls intermittently fails with `EINTR`, even though nothing in the application is intentionally sending signals?

**Answer:** `EINTR` means a blocking syscall was interrupted by a signal that was delivered to the process and whose handler did not use `SA_RESTART`, or the signal was caught and the kernel returned early. The first step is to stop assuming "nothing is sending signals" and actually verify it: inspect `/proc/<pid>/status` for `SigPnd`/`ShdPnd`/`SigCgt`, run the daemon under `strace -f -e trace=signal,ioctl` to see exactly which signal arrives and from where, and check whether the process is being hit by something like `SIGCHLD` from a child, `SIGALRM` from a timer, or a signal from a watchdog/supervisor process. A very common cause is a library or helper thread installing a handler without `SA_RESTART`, so a `SIGCHLD` or profiling timer silently breaks the `ioctl`. Second, look at the driver side: if the driver's `ioctl` implementation sleeps on a wait queue and returns `-ERESTARTSYS`, the kernel will restart or return `EINTR` depending on whether the signal handler was set up with `SA_RESTART` — so a driver that returns `-ERESTARTSYS` from an interruptible wait is behaving correctly, and the fix belongs in userspace (retry on `EINTR`) or in the signal disposition. Third, confirm the application is not itself the source — e.g., a `SIGCHLD` from a `system()`/`popen()` call, or a thread library using signals internally. The robust fix is twofold: make the userspace call site loop on `EINTR` (this is correct practice for any interruptible syscall), and identify and eliminate the spurious signal source so the behavior is deterministic. For a medical device, I would also add logging around the retry so the event is visible in field logs rather than silently swallowed.

**Possible follow-ups:** What is the difference between `-ERESTARTSYS` and `-EINTR` from a driver's perspective, and when would a driver deliberately choose one over the other? How would you determine whether the signal is coming from inside the process (a thread) versus an external process?

## Q2: How would you approach structuring a Yocto BSP for a product family where several boards share a common SoC and vendor BSP but differ in peripherals, device tree, and userspace packages?

**Answer:** The organizing principle is to separate what is common from what varies, and to express the variation through layers and machine configuration rather than through copied recipes. I would structure it as: a common layer (or the vendor's BSP layer) holding the SoC family support — kernel recipe, bootloader, common kernel config fragments, common device tree includes (`.dtsi`), and shared userspace packages; then one thin machine layer per board, each defining its own `MACHINE` conf with the correct device tree, kernel config fragments, and any board-specific packages. The device tree should be factored so the SoC-level `.dtsi` is shared and each board's `.dts` only includes it and overrides/adds the board-specific nodes — this keeps the diff between boards small and reviewable. Kernel configuration should be handled with config fragments applied via `.bbappend` or `KERNEL_CONFIG_FRAGMENTS` rather than forking the vendor's `defconfig`, so a vendor kernel bump does not require re-merging. Userspace differences go into `IMAGE_INSTALL`/packagegroups per machine or per image, not into conditional logic inside recipes. For images, I would define a common image recipe and derive per-board or per-variant images that append packages. The payoff is that a change to the SoC support propagates to every board automatically, and adding a new board is a small, well-scoped layer rather than a fork. I would also keep a CI matrix that builds every machine on every change, because the failure mode of this structure is a board-specific break that only shows up when that machine is built.

**Possible follow-ups:** How would you handle a board variant that needs a different kernel version entirely — would you still keep it in the same layer? Where do you put a patch that applies to the vendor kernel for all boards versus just one?

## Q3: How would you approach debugging a kernel panic that occurs only on every third or fourth boot, with no consistent trigger?

**Answer:** Intermittent boot panics are almost always a race, an initialization-order dependency, or a hardware marginality, so the approach is to make the failure observable and then narrow the window. First, make sure you actually capture the panic: enable `panic=` with a timeout, configure `pstore`/ramoops or a persistent console so the log survives the reset, and if the board supports it, use a hardware watchdog with a reset-cause register you can read on the next boot to confirm it was a panic and not a silent hang. Second, get the panic message and stack trace — without that, you are guessing. Third, classify: is the trace in early boot (before init), in driver probe, in userspace init, or in a specific subsystem? A trace that varies between boots points to a race; a trace that is always in the same place points to an ordering or resource issue. Fourth, try to increase the reproduction rate: boot in a loop under a script, vary timing (add delays, change CPU frequency, change boot medium speed), and see whether the rate changes — if adding a delay in one place makes it disappear, you have found the dependency. Fifth, check the usual suspects for boot-time races: regulator and clock enable ordering, `probe` deferral that resolves differently depending on timing, DMA or cache coherency issues, memory that is marginal (run a memory test), and power sequencing that is marginal on some boots. Sixth, use `initcall_debug` and `loglevel` to see how far boot gets and where timing varies. Only once you have a reproducible trace and a narrowed window do you start changing code — changing things before you can observe the failure just moves the bug.

**Possible follow-ups:** How would you use `pstore`/ramoops to capture a panic that happens before the root filesystem is mounted? What would a stack trace that is identical every time tell you versus one that varies?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path holds, so the design has to decouple them rather than serialize them behind a single mutex. The pattern I would use is: the real-time path (interrupt handler or a high-priority threaded handler) does the minimum work — read the hardware, timestamp, and push the sample into a lock-free or wait-free ring buffer (single-producer/single-consumer, using atomics and memory barriers rather than a spinlock that the logging path also takes). The logging path drains that ring buffer at its own pace and writes to the log or userspace; if the buffer fills because logging is slow, the policy must be explicit — either drop oldest, drop newest, or block the producer, and for a real-time path you almost never block the producer, you drop and count the drops so the loss is visible. The real-time task's access to the hardware itself must be protected from the logging task's access to the same registers: either the logging task never touches the hardware directly (it only reads the ring buffer), or if it must, the hardware access is serialized with a lock that the real-time path can always acquire without unbounded waiting — which in practice means the logging task must not hold the lock across slow operations. I would also make sure the logging task runs at a lower priority and, if it does any I/O, that it does not run in a context that can preempt the real-time task for long. The verification is to measure worst-case latency of the real-time path under heavy logging load, not just average.

**Possible follow-ups:** How would you implement the ring buffer so that it is safe on a single-core system without disabling interrupts for long? What would you do if the logging task must also configure the device, not just read from it?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I would treat this as a coordination and risk-management problem rather than a purely technical one, and I would start by getting the facts on the table before anyone commits to a position. First, I would ask the hardware team to quantify why the move is necessary and whether there is an alternative pin or peripheral that avoids touching the debug UART — sometimes the constraint is softer than it first appears. Second, I would ask the software team to be precise about what "baked in" means: which files change (device tree pinmux node, bootloader pinmux setup, any early-console configuration), and what specifically the manufacturing line depends on (is it the UART itself, or a specific test fixture that expects console output at a specific point in boot?). Third, I would propose a path that de-risks the change rather than blocking it: make the pinmux change in a branch, verify early boot console still works on the new pins, and confirm with manufacturing that their fixture still sees what it needs — ideally by having them test against a prototype before the change is merged. Fourth, I would make the decision explicit and documented: if the change goes ahead, it needs a validation step on the manufacturing side and a rollback plan, and the schedule impact needs to be visible to the project manager rather than absorbed silently by the software team. Throughout, I would keep the tone collaborative — the hardware team has a real constraint, the software team has a real risk, and my job is to make both visible and find the option that satisfies both, or to escalate the trade-off with a recommendation rather than let it stall.

**Possible follow-ups:** What would you do if manufacturing cannot test the change before the merge deadline? How would you document the decision so that a future engineer understands why the pinmux is where it is?
