# embedded-linux-bsp — Day 109

## Q1: How would you approach debugging a situation where the kernel boots and the root filesystem mounts, but a userspace application that opens a character device and issues `ioctl()` calls intermittently fails with `EINTR`, even though nothing in the application is intentionally sending signals?

**Answer:** `EINTR` on an `ioctl()` means the call was interrupted by a signal before it completed — the kernel returned `-ERESTARTSYS` internally and the syscall layer translated it to `EINTR` because the signal handler was installed without `SA_RESTART`, or the driver used an interruptible wait. The first thing I'd do is establish whether the signal is actually being delivered to that thread: check `/proc/<pid>/status` for pending signals, and instrument the application with a `sigaction` handler that logs `siginfo_t` (signal number, sender PID, `si_code`) so I can see who is sending it. Common culprits are a watchdog or supervisor process sending `SIGCHLD`/`SIGUSR1`, a library spawning threads that inherit signal dispositions, or a timer signal (`SIGALRM`/`SIGVTALRM`) left over from an initialization path. On the driver side, I'd look at whether the `ioctl` handler is using `wait_event_interruptible()` or a mutex `_interruptible` variant where a non-interruptible wait would be more appropriate for a short, bounded operation — an interruptible wait is correct for long blocking operations but invites spurious `EINTR` for quick register reads. The fix is usually twofold: make the driver's wait non-interruptible where the operation is short and cannot be safely restarted, and make the application robust by retrying on `EINTR` (or installing handlers with `SA_RESTART` where semantics allow). I'd also verify the signal isn't a symptom of something else — e.g., a thread being cancelled, or a `SIGPIPE` from a related socket — because suppressing `EINTR` without understanding its source just hides the real problem.

**Possible follow-ups:** How would you tell the difference between a signal genuinely intended for the process and one delivered as a side effect of thread creation or `fork()`? What are the trade-offs of using `SA_RESTART` versus explicit retry loops in the application?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our deltas on top. I'd create a `.cfg` fragment file containing only the `CONFIG_*` lines we need to change, and reference it from a `.bbappend` in our own layer using `SRC_URI:append` plus `KERNEL_CONFIG_FRAGMENTS` (or the older `SRC_URI += "file://our-fragment.cfg"` pattern, depending on the kernel class version). The fragment should be minimal and additive — enabling a driver, setting a debug option, or disabling an unused subsystem — rather than a full `defconfig`, so that when the vendor bumps their kernel the merge stays trivial. I'd also add a `do_configure:prepend` sanity check or a `KERNEL_CONFIG_CHECK` step that greps the final `.config` for the options we care about, so a silent fragment-merge failure (e.g., a `CONFIG_` symbol that got renamed upstream) fails the build rather than shipping a kernel missing a driver. For anything that genuinely can't be expressed as a fragment — a patch to Kconfig or a driver source change — I'd carry it as a `.patch` in the same layer with `Upstream-Status` metadata, and keep the patch queue short and documented. The layer structure matters too: a `meta-<board>` layer that `LAYERDEPENDS` on the vendor BSP layer, with the fragment and patches in `recipes-kernel/linux/`, so the dependency graph is explicit and `bitbake-layers show-layers` makes the inheritance obvious to the next engineer.

**Possible follow-ups:** How would you handle a kernel config option that the vendor's recipe forcibly sets in a `do_configure` task rather than through a fragment? What's your approach when the vendor's kernel recipe doesn't use the standard `kernel-yocto` class and fragments aren't supported?

## Q3: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?

**Answer:** I'd treat this as a signal-delivery investigation first, because `EINTR` is by definition a signal interrupting a blocking syscall — the question is which signal and why. Step one is to make the failure observable: run the daemon under `strace -f -e trace=ioctl,rt_sigreturn` and capture the exact syscall that returns `EINTR`, plus the signal number from the preceding `rt_sigreturn`. If `strace` perturbs timing too much, I'd add a `sigaction` handler in the daemon that logs `siginfo_t` to a ring buffer and dumps it on abort. Step two is to check the environment: is a supervisor (systemd, a watchdog, a hardware monitor) sending `SIGUSR1`/`SIGCHLD`? Is a library spawning threads with inherited signal masks? Is `SIGALRM` armed by a timeout path that isn't cancelled? Step three is the driver side — if the `ioctl` handler uses `wait_event_interruptible()` for what should be a short register access, a signal arriving during that window produces `EINTR` even though the operation is trivially restartable; switching to a non-interruptible wait for bounded operations, or making the application retry on `EINTR`, resolves it. I'd also confirm the daemon isn't the target of a `SIGTERM` from a health-check that's being misread as a crash. The fix should address both sides: driver waits matched to operation duration, and application code that treats `EINTR` as a retryable condition rather than a fatal error.

**Possible follow-ups:** How would you distinguish a signal sent by the kernel (e.g., `SIGBUS` from a bad `mmap` access) from one sent by another process? What's the risk of masking all signals in the daemon versus handling them selectively?

## Q4: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder classes of bug because every layer reports healthy. I'd start by verifying that `probe()` is actually touching the hardware: add temporary `dev_dbg`/`dev_info` prints at each register write and read in `probe()`, and confirm via a bus analyzer (or a scope on the relevant lines) that the transactions actually appear on the wire — a driver can "succeed" while writing to a peripheral that isn't powered, isn't clocked, or is held in reset. Next I'd check the resource mapping: is the `ioremap`/`devm_ioremap_resource` returning a valid pointer to the right physical range, and does a read-back of a known register (e.g., a chip ID or revision register) return the expected value? A common failure is a device tree `reg` property that's correct in size but off by an offset, so writes go to a hole and reads return all-ones or all-zeros without erroring. I'd also verify the clock and regulator are actually enabled at the time of access — `clk_prepare_enable` can succeed while the parent clock is gated, and a regulator can report "on" while the rail is not actually up. Then I'd check the interrupt path: if the device is interrupt-driven, is the IRQ actually firing? `cat /proc/interrupts` before and after a stimulus tells you whether the line is wired and unmasked. Finally, I'd confirm the driver's `probe()` isn't returning success before the hardware is ready — e.g., a reset sequence that needs a delay the driver doesn't wait for — by adding a read-back of a status register after reset. The discipline is to bisect the path from "driver thinks it wrote" to "hardware actually changed state" using the bus analyzer as ground truth.

**Possible follow-ups:** How would you use a bus analyzer or logic analyzer to confirm a register write actually reached the peripheral? What would you check first if the chip ID register reads back correctly but all functional registers behave as if writes are ignored?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd start by making the actual risk concrete rather than trading assertions. The manufacturing line's dependency on the debug UART is a real constraint, but "baked into the device tree and bootloader" is a statement about where the change lives, not about whether it's safe — so I'd ask both teams to quantify: which manufacturing steps read the early console, at what boot stage, and what's the fallback if it's unavailable for a build or two? In parallel, I'd scope the software change: the pinmux is typically a device tree `pinctrl` node plus a U-Boot pinmux table, and the question is whether the new group can be brought up in a way that preserves the old console during a transition — e.g., a bootloader build that keeps the old UART for the manufacturing image and a separate production image with the new pinmux, or a device tree overlay selected by a build flag. I'd propose a short spike: hardware provides the new pinmux group and a board with the change, software brings up the new console and confirms early boot output still works, and manufacturing validates their line against it before we commit. If the spike shows the manufacturing dependency can't be met without a line change, that's a schedule and cost decision for the project manager, not something the two engineering teams should resolve by argument. The key is to separate "can we do it technically" from "what does it cost the line," and to give the decision-maker both answers with a recommended path and a fallback.

**Possible follow-ups:** How would you structure the transition so manufacturing isn't blocked while the new pinmux is validated? What would you do if the hardware team's new peripheral turns out to be optional and the pinmux change could be deferred to the next board revision?
