# embedded-linux-bsp — Day 126

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder failure modes because it means the driver's control flow completed without complaint, so the fault is almost certainly in what the driver *didn't* verify rather than in what it reported. I'd work from the outside in. First, confirm the driver is actually talking to the hardware it thinks it is: read back a known register (a chip ID or revision register is ideal) inside `probe()` and compare against the datasheet — a mismatched or all-`0xFF`/all-`0x00` read usually means a wrong address, a wrong bus instance, or a pinmux/clock that was never enabled, and the driver happily proceeded because it never checked. Second, verify the resources the driver requested are the ones the hardware actually uses: check `/proc/iomem` or the device tree node to confirm the register base, IRQ number, and any GPIO/regulator/clock phandles resolve to the intended hardware, not a stale or copy-pasted value from a reference board. Third, confirm the peripheral is actually powered and clocked — a device that responds to register reads but does nothing functional is often missing a clock enable, an unasserted reset line, or a regulator that was never brought up because the driver assumed it was already on. Fourth, instrument the driver: add `dev_dbg`/`dev_info` traces around each hardware access, and if the interface is I2C/SPI, put a scope or logic analyzer on the bus to see whether transactions are actually happening and whether the device is ACKing. Finally, check the userspace side — sometimes the driver is fine and the device node, permissions, or the application's access path is wrong. The discipline is to prove each layer independently rather than trusting the driver's "success" as evidence that the hardware is working.

**Possible follow-ups:** How would you distinguish a wrong register base from a clock that was never enabled, using only software-visible evidence? What would you add to `probe()` permanently so this class of bug is caught at bring-up instead of in the field?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and express only your deltas on top of it, so that vendor updates can be pulled in without a merge war. The clean mechanism is a kernel configuration fragment plus the `KERNEL_CONFIG_FRAGMENTS` (or `SRC_URI` with a `.cfg` file and `do_configure:append`/`kernel-yocto` merge, depending on the kernel class in use) so that your options are merged into the final `.config` at build time rather than replacing it. I'd put the fragment in a board-specific layer — a `meta-<board>` layer that `BBLAYERS` includes — with a `.bbappend` on the vendor's kernel recipe that adds the fragment and, if needed, a device tree or a small patch. The fragment should contain only the options you actually need to change, with the `CONFIG_` lines and their intended values, and I'd keep it minimal and commented so a reviewer can see why each option is there. I'd also make sure the fragment is validated: use `bitbake -c menuconfig` or `kernel_configcheck` to confirm the merged config matches intent, and add a build-time or CI check that the resulting `.config` contains the expected symbols, because a fragment that silently fails to apply is worse than no fragment. For device tree changes I'd prefer a separate `.dts`/`.dtsi` in the layer referenced by the recipe rather than editing the vendor's DTS in place. The key discipline is: no forking, deltas only, and every delta traceable to a layer and a reason.

**Possible follow-ups:** What happens if two layers both append a fragment that sets the same symbol to different values, and how would you make that conflict visible? How would you handle a vendor kernel update that renames or removes a symbol your fragment depends on?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path can hold, so the design has to decouple them rather than serialize them behind one lock. I'd start by making the real-time access path lock-free or minimally locked: the real-time task reads from the device into a pre-allocated buffer using a mechanism that doesn't take a mutex the logging path also takes — for example, a single-producer/single-consumer ring buffer where the real-time side only writes and advances a head pointer, and the logging side only reads and advances a tail pointer, with the appropriate memory barriers. The real-time side should never wait for the logging side to drain; if the ring fills, the real-time side either overwrites the oldest entry (if the data is periodic and the latest sample matters most) or drops and counts the drop, but it must not block. The logging side runs in a workqueue or a threaded context at best-effort priority and drains the ring at its own pace. If the device itself can only be accessed by one context at a time, I'd give ownership of the hardware to the real-time path and have the logging path consume only the copied data, never touch the device directly. I'd also make sure the real-time path doesn't allocate memory, take sleeping locks, or call anything that can schedule, and I'd verify with `PREEMPT_RT` or at least with latency tracing (`cyclictest`, ftrace) that the real-time path's worst-case latency is bounded and unaffected by logging load. The trade-off to state explicitly is that the logging path may lose data under sustained load — that's the price of never delaying the real-time path, and it should be a documented, deliberate choice.

**Possible follow-ups:** How would you size the ring buffer, and what would you do if the logging side is persistently slower than the producer? How would you prove to a reviewer that the logging path cannot delay the real-time path?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** An intermittent fallback to network boot means the boot ROM or U-Boot's boot target selection is failing to find a valid eMMC boot image some fraction of the time, and the fallback path is doing exactly what it was configured to do — so the real question is why eMMC boot fails intermittently, and secondarily why the fallback is reachable at all. I'd first make the failure observable: enable verbose U-Boot output, check the boot ROM's boot-source indication (often a register or a strap readout), and capture the console log on a failing boot versus a succeeding one to see whether U-Boot even started from eMMC or whether the ROM itself fell through. Common causes of intermittent eMMC boot are marginal power ramp timing (the eMMC not ready when the ROM samples it), a reset or clock glitch on the eMMC interface, a boot partition or boot image that is only sometimes valid (e.g., a partially written image, or a boot config that depends on a strap), or a hardware signal integrity issue on the eMMC bus that shows up only at certain temperatures or voltages. I'd stress it: cycle power many times, vary temperature and supply, and log which boot source was used each time to get a failure rate. In parallel, I'd close the fallback hole — the network boot path should be disabled or gated behind an explicit recovery condition (a GPIO strap, a magic button, a valid recovery image check) so that a transient eMMC failure doesn't silently boot something unintended. The fix is usually a combination of making eMMC boot robust (boot timing, power sequencing, image integrity) and making the fallback deliberate rather than accidental.

**Possible follow-ups:** How would you determine whether the failure is in the boot ROM or in U-Boot's own boot target selection? What would you change in the boot environment to make a network fallback safe to leave enabled for recovery?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams are right about something real: the hardware team needs the pins, and the software team is protecting a manufacturing dependency that is easy to underestimate. My first move would be to get the facts on the table in one place — exactly which pins are being freed, what the new peripheral needs, where the debug UART is currently defined (bootloader, device tree, and any manufacturing test scripts), and what the manufacturing line actually depends on (is it the console output itself, a specific test that parses it, or just a habit?). That usually reveals whether the dependency is hard or soft. Then I'd look for options that satisfy both sides: can the debug UART move to a pinmux group that is still available early in boot and still reachable by the manufacturing fixture, even if it's a different physical connector? Can the manufacturing test be updated to use the new console location, and what's the cost and lead time of that change? Can the new peripheral use a different pin or interface instead? I'd bring the manufacturing/test owner into the conversation early rather than deciding between hardware and software in isolation, because they own the dependency the software team is worried about. If the change is unavoidable, I'd sequence it so the bootloader and device tree change land together with an updated manufacturing test procedure and a validation run on the line before the old console is removed, and I'd document the change in the BSP so it's traceable. The outcome I'd push for is a decision that's explicit, validated on the manufacturing side, and reversible if the new pinmux causes early-boot problems — not a unilateral win for either team.

**Possible follow-ups:** How would you decide if the manufacturing dependency is hard enough to justify delaying the hardware change? What would you put in place so a future pinmux change doesn't surprise the manufacturing line again?
