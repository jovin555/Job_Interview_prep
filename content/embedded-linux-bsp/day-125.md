# embedded-linux-bsp — Day 125

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is usually a sign that the driver is talking to the wrong address, the wrong register layout, or a peripheral that is powered/clocked but not actually enabled at the pin level. I'd work outward from the driver in layers. First, confirm the driver is bound to the device I think it is — check `/sys/bus/<bus>/devices/` and the driver's sysfs symlink, and verify the device tree node that matched is the one I intended (a common trap is two similar nodes, or a `compatible` string that matches a fallback driver). Second, verify the register accesses are actually landing: read back a known register (a chip ID or a scratch register) via `devmem` or a debugfs hook and compare against the datasheet. If reads return all-zeros or all-ones, the bus isn't really reaching the device — check pinmux, chip-select, and clock enable. Third, confirm the peripheral's power and clock are actually on: a regulator that reports enabled in the device tree may not be physically enabled if the enable GPIO is wrong, and a clock that's gated will make register reads return garbage silently. Fourth, check interrupt wiring — if the driver relies on interrupts and they never fire, the device may be configured but never serviced; look at `/proc/interrupts` for the IRQ count. Finally, add targeted `dev_dbg`/`printk` at the point where the driver writes its first configuration register and reads it back, and compare the value to what the datasheet says it should be. The key discipline is to prove each layer independently — bus reachability, register correctness, power/clock, interrupt delivery — rather than assuming the driver logic is right because `probe()` returned zero.

**Possible follow-ups:** How would you distinguish between a pinmux problem and a clock-gating problem when register reads return all-zeros? What would you check first if the chip ID reads correctly but configuration writes don't stick?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe untouched and layer our changes on top through the standard configuration-fragment mechanism. I'd create a `.cfg` fragment file in our own layer containing only the `CONFIG_*` lines we need to add or override, and reference it from a `.bbappend` on the vendor's kernel recipe using `SRC_URI += "file://our-board.cfg"` plus `KERNEL_CONFIG_FRAGMENTS` (or the `config-fragments` class, depending on the Yocto release). The fragment is merged by `merge_config.sh` at build time, so the vendor recipe stays pristine and we can rebase onto a new vendor kernel drop without carrying a patch. I'd keep fragments small and single-purpose — one for board peripherals, one for debugging options, one for production hardening — so they're auditable and can be composed per image. For options that must be *disabled* (not just added), I'd use `# CONFIG_FOO is not set` syntax explicitly, because a fragment that simply omits an option won't turn it off if the vendor's defconfig enables it. I'd also add a build-time sanity check (a small `do_configure:append` or a CI script) that greps the final `.config` for the options we care about, so a silent regression in a vendor kernel bump gets caught immediately rather than at runtime. The layer structure matters too: the fragment and the bbappend live in our board layer, not in a fork of the vendor's layer, so `bblayers.conf` ordering makes our layer override cleanly.

**Possible follow-ups:** What happens if two fragments set the same option to different values, and how would you control which wins? How would you handle a vendor kernel bump that renames or removes a config symbol your fragment depends on?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never block on anything the logging path can hold. I'd design the driver so the real-time access uses a dedicated, non-blocking path — typically a spinlock-protected or lock-free ring buffer in the driver, with the real-time task reading or writing through a `mmap`'d region or a fast `ioctl` that only touches pre-allocated memory and never sleeps. The logging task would consume from a separate buffer that the real-time path writes into without ever waiting on the logger: the real-time side does a bounded, non-blocking enqueue (dropping or overwriting oldest data if the logger falls behind, depending on whether loss is acceptable), and the logger drains at its own pace. I'd avoid a mutex shared between the two paths entirely, because a mutex held by the logger would block the real-time task. If the hardware itself is shared, I'd serialize at the hardware level with a spinlock held only for the duration of the register access, never across a copy to userspace. For the userspace side, I'd expose the real-time path as a separate character device or a separate `mmap` region from the logging path, so a slow logger can't back-pressure the real-time reader through a shared file descriptor. I'd also consider whether the real-time task should be in the kernel at all — if it's a userspace RT task, `SCHED_FIFO` plus a lock-free shared buffer with the driver is often cleaner than trying to make a syscall path deterministic. The design rule is: the real-time path's worst-case latency must be independent of the logger's behavior, and I'd prove that with a latency measurement under logger-induced load.

**Possible follow-ups:** How would you handle the case where the real-time buffer overflows because the logger is stalled — drop newest, drop oldest, or block? What kernel primitives would you avoid in the real-time path and why?

## Q4: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?

**Answer:** `EINTR` means a signal was delivered to the process while it was blocked in a syscall, and the syscall was interrupted before completing. If nothing in the application is deliberately signaling, the usual suspects are: a signal handler installed for something like `SIGCHLD` or `SIGALRM` that fires asynchronously; a library or framework in the daemon that installs handlers; the process being in a process group that receives a terminal-generated signal; or a watchdog/supervisor sending a signal that the daemon doesn't expect. I'd start by identifying the signal: run the daemon under `strace -f -e trace=signal` (or `-e trace=rt_sigreturn`) and look at what signal is delivered right before the `EINTR`. That tells me whether it's `SIGCHLD` from a child, `SIGALRM` from a timer, `SIGUSR1` from a supervisor, or something else. Then I'd check whether the daemon installs a handler with `SA_RESTART` — if it does, most syscalls are automatically restarted and `EINTR` shouldn't surface; if it doesn't, the daemon needs to handle `EINTR` by retrying the `ioctl`, which is the correct defensive pattern regardless. The deeper question is *why* the signal is arriving: a `SIGCHLD` from a forked helper that the daemon doesn't reap, or a supervisor's health-check signal, are both common in embedded daemons. I'd also check whether the driver's `ioctl` implementation can return `-ERESTARTSYS` (which the kernel translates to `EINTR` for the userspace caller) — if the driver uses interruptible sleeps and a signal arrives, that's the mechanism. The fix is twofold: make the daemon's `ioctl` wrapper retry on `EINTR` (standard practice), and eliminate the unexpected signal source if it's a bug (e.g., an unreaped child). I'd want the daemon to log the signal number when it catches `EINTR` so the root cause is visible in the field, not just papered over.

**Possible follow-ups:** What's the difference between `EINTR` and `ERESTARTSYS`, and how does `SA_RESTART` change the behavior? How would you make the driver's `ioctl` path robust against being interrupted mid-operation?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a cross-team risk-and-tradeoff decision rather than a hardware-versus-software argument, and I'd want to make the tradeoffs explicit before anyone commits. First, I'd get the hardware team to state exactly which pins are needed, why the new peripheral can't use an alternative pinmux option, and what the schedule pressure is — sometimes there's a second pinmux option that avoids the conflict entirely. Second, I'd quantify the software impact honestly: the change touches the bootloader's early console setup, the device tree's pinmux node, and possibly the kernel command line, and the manufacturing line's test fixtures may depend on the console appearing at a specific point in boot. I'd ask manufacturing what specifically they rely on — is it the console output itself, or the timing of when it appears, or a test script that greps for a banner? That determines whether the risk is "console moves" (low) or "console disappears during a window the line depends on" (high). Third, I'd propose a path that de-risks the change: keep the old UART available as a secondary console during a transition period if the SoC supports multiple consoles, or stage the change behind a build variant so the manufacturing line can validate the new pinmux on a pilot batch before it becomes the default. Fourth, I'd set a decision checkpoint with a clear owner — if the hardware change is truly required for the new peripheral, the software work is a known, bounded task (bootloader pinmux table, device tree, manufacturing test script update), and the real question is whether the schedule absorbs it. I'd document the decision and the manufacturing validation step in the design review record so it's traceable, which matters for a medical device. The key is not to let it become "software is blocking hardware" — it's "here's the cost, here's the mitigation, here's who decides."

**Possible follow-ups:** How would you validate that the manufacturing line's console dependency is actually satisfied before switching the default? What would you do if manufacturing insists the old console must remain available indefinitely?
