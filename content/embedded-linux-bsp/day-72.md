# embedded-linux-bsp — Day 72

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function returns `-EPROBE_DEFER` in a loop and never succeeds, even though the driver it depends on is present in the device tree?
**Answer:** `-EPROBE_DEFER` means the kernel is telling the driver framework "I'm not ready yet, try me again later" — so the real question is *which* dependency is never resolving. The first step is to identify what the driver is actually waiting on: typically a clock, a regulator, a GPIO, a reset controller, a PHY, or a parent bus (I2C/SPI) that hasn't been registered yet. I'd add targeted logging or use `devm_*`-style deferred-probe tracing to see which `devm_clk_get`/`devm_regulator_get`/`devm_gpiod_get` call is returning `-EPROBE_DEFER` and why. Common root causes: the supplier node exists in the device tree but its own driver is also deferring (a chain of deferrals), the supplier's `status` is `"disabled"`, the phandle is wrong, or the supplier driver is built as a module that never gets loaded because it's not in the initramfs or rootfs. I'd check `dmesg` for the supplier's probe result, verify the phandle and `status` in the decompiled DTB (`dtc -I dtb -O dts`), and confirm the supplier driver is actually compiled in or loadable. If it's a genuine circular dependency, the fix is usually to break the cycle by making one side not depend on the other at probe time, or by using a deferred workqueue to complete initialization after both are up.
**Possible follow-ups:** How would you tell the difference between a deferral that will eventually resolve and one that is effectively a deadlock? What kernel mechanisms exist to observe deferred-probe activity without adding custom printk statements?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration option can be enabled without forking the vendor's kernel recipe?
**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer your changes on top, so that when the vendor bumps their kernel you rebase cleanly instead of merging a fork. The standard mechanism is a kernel configuration fragment: a `.cfg` file containing just the `CONFIG_*` lines you need, referenced from your board's `linux-yocto` (or vendor kernel) `.bbappend` via `SRC_URI` and `KERNEL_FEATURES` or the `KERNEL_CONFIG_FRAGMENTS` variable, depending on the kernel recipe's class. Bitbake's `kernel-yocto` class merges fragments on top of the base `defconfig` in a defined order, so you get a deterministic result without touching the vendor's tree. I'd keep the fragment minimal and documented — one fragment per logical feature — and put it in a board-specific layer (`meta-<board>`) that `LAYERSERIES_COMPAT` matches the vendor layer's release. For options that must not be silently overridden, I'd also add a `do_configure:append` sanity check or a `KERNEL_CONFIG_CHECK` to fail the build if the option didn't take effect. The alternative — a full `defconfig` replacement — is sometimes necessary but loses the vendor's baseline and makes rebasing painful, so I'd only do that if the fragment approach genuinely can't express the change.
**Possible follow-ups:** How would you verify at build time that your fragment actually won the merge and wasn't overridden by a later fragment? What's the difference between `KERNEL_FEATURES` and a plain `.cfg` fragment in terms of when they're applied?

## Q3: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts, even though nothing is intentionally sending it signals. How would you approach this?
**Answer:** `EINTR` on an `ioctl` means the call was interrupted by a signal before it completed — and the fact that it's intermittent and "nothing is sending signals" usually means something *is*: a timer signal (`SIGALRM`), a profiling signal, a signal from a library, or a signal delivered to the process by the kernel itself (e.g., `SIGCHLD` from a child, or a signal from a thread). The first step is to find out which signal: I'd run the daemon under `strace -f -e trace=signal,ioctl` and look at what's delivered right before the `EINTR`. If it's a signal the daemon itself installs (e.g., a watchdog or heartbeat timer), the fix is usually to make the `ioctl` restartable — either by using `SA_RESTART` on the handler, or by wrapping the call in a retry loop that checks `errno == EINTR` and re-issues it. If the `ioctl` is genuinely long-running and the driver can be made interruptible, the cleaner fix is to make the driver's `ioctl` handler return `-ERESTARTSYS` so the kernel automatically restarts it after the signal handler runs, rather than returning `-EINTR` to userspace. I'd also check whether the daemon is multi-threaded and whether the signal is being delivered to the wrong thread — signal delivery in a threaded process is per-thread, and a signal aimed at the process can land on any thread that doesn't block it. The robust pattern is to block all signals in worker threads and handle them in a dedicated thread, so a stray signal never interrupts a critical `ioctl`.
**Possible follow-ups:** What's the difference between `-EINTR` and `-ERESTARTSYS` from a driver's perspective, and when would you use each? How would you design a driver `ioctl` that must not be interrupted at all, and what are the trade-offs?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?
**Answer:** An intermittent fallback to network boot almost always means the primary boot path is failing *sometimes* and U-Boot's boot order is silently moving on to the next candidate. The first thing I'd do is stop treating it as a network problem and start treating it as "why did the eMMC boot fail this time?" — because the network boot is just the symptom. I'd enable verbose U-Boot output (`CONFIG_LOGLEVEL`, `bootargs` with early console) and capture the full boot log across many power cycles, looking for the exact point where the eMMC path fails: `mmc` init errors, a `MMC: no card found` message, a timeout, or a checksum failure on the boot image. Common root causes: marginal power-on timing (the eMMC needs more time to be ready than U-Boot allows), a bad `bootcmd` that doesn't `setenv` the boot target correctly, a corrupted or partially-written boot partition, or a `boot_targets` list that includes network as a fallback. I'd also check whether the fallback is happening because the eMMC *is* being detected but the boot script is failing — in which case the fix is in the script, not the hardware. To make it deterministic, I'd explicitly set `boot_targets` to only the intended device, remove network from the fallback list, and add a `bootcount`/`altbootcmd` mechanism so that a failed boot is logged and retried rather than silently falling through. If the eMMC readiness is the issue, I'd add a `mmc rescan` or a delay in the boot script, or fix the power sequencing.
**Possible follow-ups:** How would you use U-Boot's `bootcount` and `altbootcmd` to make a failed boot visible instead of silent? What are the risks of removing network from `boot_targets` entirely on a board that might need recovery?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?
**Answer:** The first thing I'd do is separate the two concerns: the *technical* change (moving a UART to a different pinmux group) and the *process* risk (the manufacturing line depends on early console output). They're both real, and neither should be dismissed. I'd start by getting the facts on the table: which pins are actually needed, whether the new peripheral can use a different pinmux group instead, and what exactly the manufacturing line uses the console for — is it a hard requirement for every unit, or a debug aid that could be moved to a different interface? If the console is genuinely load-bearing for manufacturing, that's a constraint the hardware team needs to design around, not a software inconvenience to be worked around. If the change is unavoidable, I'd propose a staged approach: update the device tree and bootloader pinmux in a branch, validate that early boot console still works on the new pins across a representative sample of boards, and only then commit to the change — with a rollback plan if the manufacturing line hits problems. I'd also push for the change to be made in a way that's configurable (e.g., a device tree overlay or a build-time variant) so the old pinmux remains available if needed. Throughout, I'd keep the conversation focused on the shared goal — shipping a device that works for manufacturing and for the product — rather than framing it as hardware vs. software. If the two teams can't agree, I'd escalate to the project lead with a clear statement of the trade-off and a recommendation, rather than letting it stall.
**Possible follow-ups:** How would you validate that early boot console output is reliable on the new pinmux before committing to the change? If the manufacturing line's dependency turns out to be undocumented tribal knowledge, how would you handle that?
