# embedded-linux-bsp — Day 112

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is never called even though the device tree node is present and the driver is built into the kernel?

**Answer:** This is a matching problem, so I'd work from both ends — the device tree node and the driver's match table — and confirm they actually agree. First I'd verify the node is really being parsed: check that it's under the correct bus node, that its `status` is `"okay"` (or absent, since `"disabled"` silently suppresses probing), and that it isn't sitting under a parent that is itself disabled. A node under a disabled parent is invisible to the driver core even though it looks fine in the source. Next I'd compare the node's `compatible` string byte-for-byte against the driver's `of_match_table` — a stray character, a different vendor prefix, or a missing entry in the table means the bus never creates the device. I'd also confirm the driver is actually linked in: if it's built-in, check that its Kconfig symbol is `y` in the running config (`/proc/config.gz` or the build's `.config`), because a driver compiled as a module that isn't loaded looks identical to "probe never called." Then I'd look at whether the device is being created at all — `/sys/bus/<bus>/devices/` and `/sys/firmware/devicetree/base/` tell me whether the kernel sees the node and whether a `platform_device` was instantiated from it. If the node exists but no device appears, the problem is in the bus/populate path; if the device appears but no driver binds, it's the match table or module loading. Finally, dynamic debug on the driver core (`dyndbg` on `drivers/base`) will show the match attempt and why it failed.

**Possible follow-ups:** How would this change if the driver were a loadable module rather than built-in? What's the difference between a node being present in the device tree and a `platform_device` being created from it?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our deltas on top, so we can absorb vendor updates without a merge. I'd create a `.bbappend` in our own layer that matches the vendor recipe's name and version, and in it use `SRC_URI` with `file://` entries pointing at configuration fragments plus the `kernel-yocto` machinery — specifically `SRC_URI:append` with `.cfg` fragments and the `merge_config`/`config-fragments` handling that the kernel class provides. Each fragment contains only the symbols we need to change (`CONFIG_FOO=y`, `# CONFIG_BAR is not set`), never a full defconfig, so the vendor's base config still drives everything else. I'd keep fragments small and purpose-named — one per feature or board variant — so they're reviewable and can be composed per machine. The machine `.conf` selects which fragments apply via a variable, which keeps variant logic out of the recipe itself. I'd also make sure the fragments are validated in the build: `kernel_configcheck` catches symbols that don't exist or that conflict, which prevents silent drift when the vendor bumps the kernel version. The key discipline is that our layer owns only the append and the fragments; we never copy the vendor recipe into our layer, because that's the fork that becomes unmaintainable.

**Possible follow-ups:** What happens to your fragments when the vendor bumps the kernel major version and a symbol is renamed or removed? How would you handle a configuration change that the vendor recipe actively sets the other way?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never block on anything the logging path controls, so I'd design the two paths to share data through a structure that gives the real-time side priority and bounded latency. For the real-time access I'd use a spinlock with interrupts disabled only for the shortest possible critical section around the actual register or DMA descriptor manipulation — never around a copy of bulk data, and never around anything that can sleep. The logging path would take the same lock only briefly to snapshot a pointer or index into a ring buffer, then do all the expensive work — formatting, copying to userspace, writing to storage — outside the lock. A lock-free single-producer/single-consumer ring buffer is often the cleanest fit: the real-time side writes and advances a head index with a release barrier, the logging side reads and advances a tail with an acquire barrier, and neither ever waits on the other. If the logging consumer falls behind, the real-time producer overwrites oldest entries or drops them by policy rather than blocking. I'd also make sure the logging task runs at a lower scheduling priority and, if it must touch the same hardware, that any hardware access it does is serialized through the same short critical section rather than a separate path. The design question I'd keep asking is: what is the worst-case time the real-time task can be delayed by anything the logging task does, and can I bound it?

**Possible follow-ups:** How would you verify the bounded latency claim — what would you measure and with what tooling? What changes if the logging task needs to read the same hardware registers rather than a shared buffer?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** Intermittent fallback means something in the boot order is non-deterministic, so I'd first pin down whether the fallback is coming from the saved environment, from a boot script's error path, or from the boot ROM itself. I'd start by dumping the effective environment (`printenv`) on a failing boot versus a good one and comparing `bootcmd`, `boot_targets`, and any `bootargs` differences — a saved environment in eMMC that differs from the compiled-in default is a classic cause, because someone ran `saveenv` once and it persisted. Then I'd look at whether the eMMC probe itself is intermittent: a marginal power rail, a slow ramp, or a timing issue on the eMMC interface can make the device fail to enumerate on some boots, and U-Boot's boot script then walks to the next target in `boot_targets`, which may include network. I'd check the U-Boot log for the eMMC init messages and any timeout or CRC errors, and I'd scope the eMMC clock and power rails on a failing unit if the log is inconclusive. I'd also verify that the network boot path isn't reachable by accident — confirm `boot_targets` doesn't list network, or that the network target is gated behind a condition that can't be satisfied on a normal boot. Finally, I'd make the boot deterministic by design: set an explicit, ordered `boot_targets` with no network entry, avoid relying on a saved environment that can drift, and if a fallback is genuinely wanted, make it explicit and logged rather than an accidental consequence of a probe failure.

**Possible follow-ups:** How would you make the saved environment and the compiled-in default stay in sync across firmware updates? What would you look for on the eMMC lines if the probe failure only happens on cold boots?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, and I'd start by getting the actual constraints on the table from both sides before anyone commits to a position. From hardware I'd want to know whether the new peripheral genuinely requires those specific pins or whether an alternative pinmux assignment exists, and what the schedule pressure is. From software and manufacturing I'd want to know exactly what depends on the current debug UART — is it just the manufacturing line's early boot visibility, or is it also used in field diagnostics and regulatory test procedures? That distinction changes the cost of the change enormously. Then I'd lay out the options with their real costs: keep the UART where it is and find another pin for the peripheral; move the UART and update the device tree, bootloader, and manufacturing test procedures in a coordinated change with a validation pass on the line; or move it but keep a secondary console path so manufacturing isn't blocked. I'd push for a decision that's explicit about who owns the validation and when, because the risk isn't the pinmux edit itself — it's an unvalidated change reaching the manufacturing line. If the change goes ahead, I'd want it staged: update the bootloader and device tree together, verify early console output on a representative board, and only then roll it to the line, with a rollback plan. Throughout I'd keep the discussion focused on the shared goal — shipping a device that meets its requirements without disrupting production — rather than letting it become a hardware-versus-software argument.

**Possible follow-ups:** How would you handle it if hardware insisted the move was non-negotiable and manufacturing said any line disruption was unacceptable? What would you document from this decision for the design history file?
