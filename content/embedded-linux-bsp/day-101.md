# embedded-linux-bsp — Day 101

## Q1: How would you approach deciding whether a peripheral driver should be built into the kernel image versus built as a loadable module, for a device that must be functional before the root filesystem is mounted?
**Answer:** The deciding factor is *when* the device must be available relative to the boot timeline, not code cleanliness. If the peripheral must be operational before the root filesystem is mounted — for example, it provides the storage that *is* the root filesystem, or it's needed to bring up the console or a regulator that other early drivers depend on — then it must be built in (`=y`), because loadable modules live on the root filesystem and can't be loaded until that filesystem is already mounted. That's a chicken-and-egg problem you can't solve with a module unless you use an initramfs, which adds its own complexity. For anything that can wait until userspace is up, a module (`=m`) is preferable: it keeps the kernel image smaller, lets you load drivers on demand, makes it easy to update a single driver without reflashing the whole kernel, and simplifies debugging during development. I'd also consider the practical maintenance angle — a built-in driver means every kernel rebuild touches it, whereas a module can be versioned and shipped separately. The trade-off is that modules introduce load-order and dependency concerns (firmware, symbols, `modules.dep`), so for a device that must be deterministic at boot, built-in is often the safer choice even when a module would technically work. I'd document the decision per peripheral so the reasoning survives the next kernel bump.
**Possible follow-ups:** How would an initramfs change your answer for a driver that needs to be available very early? What are the risks of a built-in driver that probes too early and defers indefinitely?

## Q2: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?
**Answer:** A silent success is usually a sign that the driver is talking to the wrong place, or that the hardware isn't actually enabled even though the software thinks it is. I'd start by confirming the driver is bound to the *right* device: check `/sys/bus/.../devices/` and the driver's sysfs entry to verify the device tree node matched, the resources (MMIO base, IRQ number, clocks, regulators) were actually acquired, and the driver didn't silently fall back to a default. Next I'd verify the register accesses are landing where I think they are — read back a known register (an ID or version register is ideal) and confirm it returns the expected value; if it reads all-zeros or all-ones, the peripheral's clock or power domain may not be enabled, or the address translation is wrong. I'd also check that the clock and regulator `enable` calls actually succeeded and that the hardware is out of reset — a driver can "succeed" while the block is still held in reset. On the bus side, I'd scope or logic-analyze the actual lines to confirm transactions are physically happening. Finally, I'd add temporary instrumentation in the driver to confirm the code path taken matches expectations, since "probe returned 0" doesn't mean every step inside it did what was intended.
**Possible follow-ups:** How would you distinguish a clock/power-domain problem from an address-mapping problem using only software tools? What would you check first if the ID register reads back correctly but data transfers still fail?

## Q3: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?
**Answer:** `EINTR` means a blocking syscall was interrupted by a signal before it completed — so the first question is *what signal*, and *why is the daemon not handling it*. I'd start by checking whether the daemon installs handlers for signals it doesn't expect, and whether it's using `signal()` versus `sigaction()` with `SA_RESTART`. A common cause is a signal delivered by the kernel or another process — for example, `SIGCHLD` from a child, `SIGALRM` from a timer, or a signal from a watchdog/supervisor process — that the daemon hasn't blocked or handled, and because the handler was installed without `SA_RESTART`, the `ioctl` returns `EINTR`. I'd trace signals with `strace -e trace=signal` or `perf` to see exactly which signal arrives and when, and correlate it with the daemon's own timers and child processes. The fix is usually twofold: make the daemon robust by retrying on `EINTR` (the correct pattern for any blocking syscall), and address the root cause by blocking or properly handling the unexpected signal. I'd also check whether the driver itself is doing something that generates a signal — e.g., a `SIGIO`/async notification path — and whether the daemon's signal mask is inherited incorrectly from its parent.
**Possible follow-ups:** Why is retrying on `EINTR` considered mandatory rather than optional for blocking syscalls? How would `SA_RESTART` change the behavior, and what are its limits?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?
**Answer:** An unintended fallback means the boot logic is reaching a failure path and then trying the next boot source in its list — so the real question is *why the primary boot is failing intermittently*, and *why the fallback is enabled at all*. I'd first capture the console log across many boots to see whether the eMMC initialization, partition read, or image load is failing, and whether the failure is consistent in timing or random. Intermittent eMMC failures often point to signal integrity, power sequencing, or a marginal clock, so I'd check whether the failure correlates with temperature, supply ramp, or specific boards. On the U-Boot side, I'd inspect `bootcmd`, `boot_targets`, and the `BOOT_ORDER`-style environment variables to confirm the fallback is actually configured and where it's coming from — it may be a default baked into the environment that was never overridden, or a saved environment that differs from the compiled-in default. I'd also verify whether the environment is being persisted to eMMC or to a redundant copy, since a corrupted environment can silently change boot behavior. The fix is to make the primary path robust *and* to explicitly disable or gate the network fallback for production, so a transient failure can't silently change the boot source.
**Possible follow-ups:** How would you make the boot source selection deterministic across power cycles? What would you check if the eMMC works fine in Linux but fails only in U-Boot?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?
**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams have legitimate concerns. First I'd get the facts on the table: exactly which pins are being freed, what the new peripheral needs, and what the manufacturing line actually depends on — is it the debug console specifically, or any early console output, and is that dependency documented or just institutional habit? Then I'd map the change surface: the pinmux lives in the bootloader, the device tree, and possibly the kernel command line, so the change isn't just a device tree edit — it's a coordinated update across the boot chain, and it needs to be validated on real hardware, not just in review. I'd propose a path that de-risks it: keep the current console as the default until the new pinmux is proven on prototype boards, add the new configuration behind a build-time or strap-selectable option so both can coexist during validation, and only switch the default once manufacturing has confirmed their early-boot visibility is preserved (or has an agreed alternative). I'd also make sure the change is captured in the requirements/interface documentation so it doesn't get lost. The goal is to say yes to the hardware need without gambling the manufacturing line's ability to see early boot failures.
**Possible follow-ups:** How would you validate that early boot console output still works on the manufacturing line without disrupting production? What would you do if manufacturing insists on keeping the old pinmux and hardware insists on the new one?
