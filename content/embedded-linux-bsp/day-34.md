# embedded-linux-bsp — Day 34

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel log shows "Unhandled fault: external abort on non-linefetch" when a driver accesses a memory-mapped FPGA peripheral?
**Answer:** An external abort on non-linefetch typically indicates the CPU attempted a memory access that the bus fabric or peripheral did not acknowledge — this is fundamentally different from a page fault, which is a Linux memory-management event. My first step would be to confirm the address being accessed and whether it falls within the expected physical address range for the FPGA. I'd check the device tree entry for the peripheral to verify the `reg` property matches the hardware address map, and confirm the driver is using the correct `ioremap`/`devm_ioremap_resource` calls. A common cause is a mismatch between the address decode logic in the FPGA and what the kernel expects — for example, the FPGA might only decode a subset of the address lines, or the base address might have moved between board revisions. I'd also check whether the access size matters: some FPGA registers only support 32-bit accesses, and a driver doing byte or 16-bit accesses can trigger an abort. Another angle is timing — if the FPGA's bus interface doesn't assert ready within the SoC's timeout window, you get an external abort. This could be a clocking issue, a reset issue (FPGA not fully configured when the driver probes), or a missing bus bridge enable. I'd use a logic analyzer or the SoC's bus error registers to narrow down whether the abort is at the SoC level or the FPGA level. If the FPGA is loaded after Linux boots (e.g., via FPGA manager), I'd verify the driver defers probing until the FPGA is actually programmed.

**Possible follow-ups:** How would you distinguish between an external abort caused by an address decode error versus one caused by a timing issue? What device tree properties would you check first?

## Q2: How would you approach designing a kernel driver for a device that needs to log sensor data to a file on the root filesystem at a fixed rate (e.g., 100 Hz) without causing filesystem corruption on unexpected power loss?
**Answer:** The key design principle here is that kernel drivers should not be doing file I/O directly — that's a userspace responsibility. Writing to a filesystem from kernel space is problematic for several reasons: filesystem code can sleep, which is fine in some contexts but not in interrupt handlers or atomic contexts; kernel crashes or power loss can leave the filesystem in an inconsistent state; and it's difficult to enforce proper error handling and backpressure. The right approach is to have the kernel driver collect sensor data into a ring buffer and expose it to userspace via a character device, `relayfs`, or a netlink socket. A userspace daemon then reads from that interface and writes to the filesystem. For power-loss safety, I'd use a filesystem that handles sudden power loss well — something like ext4 with `auto_da_alloc` and journaling, or a flash-friendly filesystem like UBIFS or F2FS if the storage is raw NAND. I'd also consider writing to a temporary file and renaming it atomically, or using a write-ahead logging approach where the daemon appends to a log file and periodically compacts it. If the data rate is high enough that buffering in RAM is a concern, I'd size the ring buffer to cover the maximum expected write latency and use a real-time scheduling class for the userspace writer to ensure it can keep up. For the kernel side, I'd make sure the driver uses DMA or interrupts rather than busy-polling, and that it handles the case where userspace isn't reading fast enough — either by dropping data with a counter, or by blocking the sensor acquisition if that's acceptable for the application.

**Possible follow-ups:** What filesystem features would you look for to ensure crash safety? How would you handle the case where the userspace writer falls behind the sensor data rate?

## Q3: How would you approach implementing a kernel driver for a device that uses DMA to transfer data from an FPGA to system memory, where the FPGA can generate data at rates exceeding what the CPU can process in real-time?
**Answer:** The fundamental constraint is that the CPU cannot keep up with the data rate, so the design must avoid involving the CPU in the data path as much as possible. I'd structure the driver around a DMA engine — either the SoC's built-in DMA controller or the FPGA's own DMA capability. The driver would set up a pool of DMA buffers (a ring of descriptors) in advance, and the FPGA would write into these buffers autonomously. When a buffer is full, the FPGA raises an interrupt, and the driver's interrupt handler simply rotates the buffer to a "ready" queue and immediately re-arms that descriptor with a fresh buffer. The CPU's job is only to manage buffer ownership, not to copy data. The key design decisions are: how many buffers to allocate (enough to cover worst-case interrupt latency and processing time), whether to use a single interrupt per buffer or a coalescing scheme to reduce interrupt load, and how to notify userspace. For userspace, I'd use `mmap` so the application can read data directly from the DMA buffers without a copy — this is essential at high data rates. I'd also consider using `dma_buf` or the `v4l2` framework's streaming model if the data is video-like. If the data rate truly exceeds what the CPU can process even with zero-copy, then the application needs to be designed to drop data gracefully — for example, by having the driver maintain a "dropped buffers" counter so the application knows data was lost. I'd also look at whether the FPGA can do some preprocessing or decimation to reduce the data rate before it hits the bus.

**Possible follow-ups:** How would you choose the DMA buffer size and count? What are the trade-offs between interrupt-driven completion and polling the DMA status registers?

## Q4: Behavioral — You're the BSP lead for a medical device project, and during integration testing, you discover that the kernel's real-time scheduling class (SCHED_FIFO) is causing priority inversion on a shared hardware resource between your sensor driver and the display driver. The display team insists their driver needs the highest priority, and the sensor team says their data will be corrupted if they miss their deadline. How would you handle this situation?
**Answer:** Priority inversion on a shared resource is a classic real-time systems problem, and the first thing I'd do is make sure everyone understands the actual failure mode rather than arguing about priorities. I'd call a meeting with both teams and ask each to explain, concretely, what happens when they miss their deadline — what's the impact on the patient, on the device, on the data. That reframes the discussion from "my driver is more important" to "what are the actual system requirements." Then I'd look at the technical options. The cleanest fix is usually to eliminate the shared resource contention altogether — for example, if both drivers are using the same lock to protect access to a hardware register, can we split the register access into separate locks, or use a hardware mutex? If the resource is a bus (like I2C), can we move one device to a different bus? If the contention is unavoidable, I'd look at priority inheritance or priority ceiling protocols — the kernel has `rt_mutex` with priority inheritance, which can help. Another option is to change the scheduling model: instead of both drivers being SCHED_FIFO, maybe the sensor driver should be in a higher-priority class but with a shorter execution time, or the display driver could use a periodic task with a lower priority but a longer period. I'd also check whether the display driver really needs to be in the real-time class at all — often display updates can tolerate some jitter, whereas sensor data cannot. Ultimately, I'd want to get the requirements on paper: what are the worst-case latencies each driver can tolerate, and what's the actual worst-case contention scenario? Then we can make a data-driven decision rather than a political one. If we can't resolve it technically, I'd escalate to the systems engineer or project manager with a clear analysis of the trade-offs — but I'd try hard to find a technical solution first.

**Possible follow-ups:** How would you go about measuring the actual worst-case latency for each driver? What if the two drivers genuinely both need hard real-time guarantees and the hardware can't be changed?

## Q5: How would you approach debugging a kernel panic that occurs only on every third or fourth boot, with no consistent trigger?
**Answer:** Intermittent boot failures are among the hardest problems to debug because the reproduction is unreliable and the root cause can hide in timing, hardware state, or initialization order. My approach would be systematic. First, I'd try to gather more data on each failure — enable `CONFIG_PANIC_ON_OOPS`, `CONFIG_DEBUG_INFO`, and `CONFIG_KALLSYMS` to get a full stack trace, and capture the serial console output from every boot, not just the failures. I'd also enable `CONFIG_DEBUG_OBJECTS` and lock debugging if the panic looks memory-related. I'd look for patterns across the failures: does the panic always happen at the same point in the boot sequence? Is it in the same driver? Does it correlate with a particular hardware revision or a specific peripheral? If the panic is in a driver that initializes a device, I'd suspect a race between the driver's probe and the device becoming ready — for example, a reset line that isn't held long enough, or a power rail that hasn't stabilized. I'd also consider whether the boot medium (eMMC, SD card, SPI flash) has marginal timing — a marginal signal on the data lines could cause intermittent read errors that manifest as corrupted kernel code or data. I'd check the boot logs for any earlier warnings or errors that precede the panic. If the panic is in the kernel's memory management, I'd suspect a hardware issue like marginal DRAM timing or a bad solder joint on a memory chip. I'd also try to bisect: if I can make the failure more frequent by changing a timing parameter (e.g., slowing down the memory clock or adding a delay in a driver), that gives a clue. If the panic is truly random, I'd consider using a hardware watchdog to capture the state at the moment of failure, or adding a crash dump mechanism (`pstore`/ramoops) so the panic log survives the reboot. Finally, I'd check whether the failure rate changes with temperature or supply voltage — that can point to a marginal hardware issue rather than a software bug.

**Possible follow-ups:** How would you use `pstore` or ramoops to capture the panic log across reboots? What would you look for in the boot logs to distinguish a hardware timing issue from a software race condition?
