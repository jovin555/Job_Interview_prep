## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of two identical I2C sensors on the same bus, while the other works fine?

**Answer:** This is a classic "same device, different result" problem that narrows the search space considerably. Since both sensors are identical and on the same bus, I'd start by verifying that the issue isn't a device tree problem — checking that both sensor nodes are actually present and correctly configured with unique addresses and interrupt lines. If the device tree looks correct, I'd check the hardware side first: measure the sensor's power supply, verify the I2C address is correct (many sensors have address-select pins that might be strapped differently), and check the interrupt line if the sensor uses one. A common issue is a floating address pin or a missing pull-up on the interrupt line that prevents proper probe. I'd also check the kernel log for any error messages specific to that sensor — sometimes the driver probes but fails during initialization, which points to a different problem than the sensor not being detected at all. If the sensor is truly not appearing on the bus, I'd use i2cdetect to see if the address shows up at all, which helps distinguish between a bus-level issue and a driver-level issue. If i2cdetect shows the device, the problem is in the driver or device tree binding; if it doesn't, the problem is likely hardware — bad solder joint, wrong address strapping, or a power issue.

**Possible follow-ups:**
- How would you distinguish between a sensor that's not being probed versus one that's probing but failing during initialization?
- What if both sensors have the same I2C address — how would you handle that in the device tree?

## Q2: How would you approach implementing a kernel driver for a device that needs to perform a hardware-triggered DMA transfer, where the trigger comes from an external sensor's interrupt line, and the data must be processed and made available to userspace within a hard real-time deadline (e.g., 2 ms)?

**Answer:** This requires careful design across the interrupt path, DMA setup, and userspace notification. The key is to minimize latency at each stage. First, I'd ensure the interrupt is registered as a fast interrupt (IRQF_NO_SUSPEND if needed) and that the handler does minimal work — just acknowledging the interrupt and triggering the DMA transfer. The actual data processing should not happen in the interrupt handler. For the DMA setup, I'd use the kernel's DMA engine API with a pre-allocated, coherent DMA buffer to avoid cache coherency issues. The DMA completion callback should wake up a kernel thread or use a wait queue to signal userspace. For the 2 ms deadline, I'd consider using a real-time kernel thread (SCHED_FIFO) rather than a workqueue, since workqueues can be delayed by other system activity. The userspace application would need to use a real-time scheduling policy as well, and I'd use a mechanism like poll() or an eventfd for notification rather than busy-waiting. I'd also need to think about what happens if the DMA transfer fails or takes too long — having a timeout mechanism and error handling path is critical. Finally, I'd profile the actual latency budget: interrupt latency, DMA setup time, transfer time, and wake-up latency all need to fit within the 2 ms window, and I'd verify this with instrumentation rather than assuming it works.

**Possible follow-ups:**
- How would you handle the case where the sensor generates interrupts faster than the DMA transfers can complete?
- What are the trade-offs between using a kernel thread versus a workqueue for the data processing after DMA completes?

## Q3: How would you approach designing the boot sequence for a system with two processors — an application processor running Linux and a safety-critical microcontroller — where the microcontroller must be fully initialized and running its safety monitoring routines before the Linux userspace starts any critical applications?

**Answer:** This is fundamentally about establishing a deterministic handshake between the two processors and enforcing ordering guarantees. I'd start by defining the communication mechanism — typically a shared memory region with a mailbox or GPIO-based signaling. The boot sequence would be: the application processor's bootloader (U-Boot) brings up the microcontroller first, either by releasing it from reset or loading its firmware, then waits for a "ready" signal from the microcontroller before proceeding to boot Linux. This ready signal should indicate that the microcontroller has completed its self-tests and is actively monitoring safety-critical parameters. The Linux kernel itself doesn't need to know about this handshake — it can boot normally — but the critical userspace applications must wait for confirmation that the microcontroller is operational. This could be implemented as a kernel driver that exposes a "microcontroller ready" status to userspace, or as a userspace service that checks a shared memory flag. The key design principle is that the safety-critical application should fail closed — if it can't confirm the microcontroller is running, it should not start. I'd also consider what happens during reboot: if Linux reboots but the microcontroller stays running, the handshake needs to handle that case. And if the microcontroller needs a firmware update, the boot sequence needs to accommodate a recovery mode where the microcontroller is held in reset while new firmware is loaded.

**Possible follow-ups:**
- How would you handle the case where the microcontroller fails to initialize — should Linux still boot?
- What if the microcontroller needs to be updated independently of the Linux system — how does that affect the boot sequence design?

## Q4: Behavioral — You're the BSP lead for a medical device project, and during integration testing, you discover that the kernel's real-time scheduling class (SCHED_FIFO) is causing priority inversion on a shared hardware resource between your sensor driver and the display driver. The display team insists their driver needs the highest priority, and the sensor team says their data will be corrupted if they miss their deadline. How would you handle this situation?

**Answer:** Priority inversion on a shared resource is a classic real-time systems problem, and the first step is to understand the actual resource contention rather than getting into a priority war between teams. I'd call a meeting with both teams and ask them to walk through exactly what resource is shared, how long each driver holds it, and what the actual deadline requirements are. Often, the solution isn't about who gets the higher priority but about eliminating the contention altogether. Options I'd explore: (1) Can the shared resource be accessed through a mutex with priority inheritance enabled (which the kernel supports via rt_mutex)? This would allow the lower-priority sensor driver to temporarily inherit the display driver's priority while holding the lock, preventing the display driver from being blocked indefinitely. (2) Can the sensor driver use a different access path that doesn't require the shared resource — for example, using DMA instead of PIO, or using a dedicated hardware buffer? (3) Can the display driver's critical section be shortened so it holds the resource for less time? I'd also ask both teams to provide data on their actual timing requirements — how much jitter can the display tolerate, and what's the sensor's hard deadline? With that data, we can make an informed decision rather than arguing about priorities. If a genuine conflict remains, I'd escalate to the systems engineer with the data and let them make the architectural call, documenting the decision and its rationale for the design history file, which is important for a medical device.

**Possible follow-ups:**
- How would you verify that priority inheritance is actually working correctly in your scenario?
- What if the shared resource is a hardware register that can't be protected by a kernel mutex?

## Q5: How would you approach debugging a situation where a custom board running Linux boots successfully, but the system clock is running roughly twice as fast as expected, and the RTC itself keeps correct time when read directly?

**Answer:** This symptom — system clock running at roughly double speed while the RTC is accurate — points to a clock source configuration problem rather than an RTC issue. The system clock is derived from a timer, and if that timer is being driven by a clock that's running at twice the expected frequency, the clock will advance too quickly. I'd start by checking which clock source the kernel is using: `cat /sys/devices/system/clocksource/clocksource0/current_clocksource`. If it's using a timer that's derived from a PLL or external oscillator, I'd verify the clock tree configuration in the device tree and the bootloader. A common cause is a mismatch between the actual crystal frequency and what the bootloader or kernel thinks it is — for example, if the board has a 24 MHz crystal but the bootloader configures the PLL assuming 12 MHz, everything derived from that PLL will run at double speed. I'd check the bootloader's clock initialization code and the device tree's clock nodes. Another possibility is that the timer is being fed by a clock that's supposed to be divided down but isn't — for example, a prescaler that's not being configured correctly. I'd also check `dmesg` for any clock-related warnings or errors during boot. The RTC keeping correct time is expected because it has its own independent oscillator — it's only the system's monotonic clock that's affected. Once I identify which clock is misconfigured, the fix is typically a device tree change or a bootloader clock initialization fix.

**Possible follow-ups:**
- How would you verify that the fix actually resolved the issue — what tests would you run?
- What if the clock rate is correct at boot but drifts over time — how would that change your debugging approach?
