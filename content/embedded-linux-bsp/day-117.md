# embedded-linux-bsp — Day 117

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is usually one of a few things: the driver is talking to the wrong register base, the peripheral's clock or power domain is gated, the pinmux is not actually routing the signals, or the driver is programming a shadow/indirect register window without committing it. I'd start by confirming the driver is bound to the intended device tree node — check `/sys/bus/platform/devices` and the driver's sysfs symlink, and verify the `reg` range it mapped matches the hardware address map. Then I'd read back the peripheral's ID/version register from userspace (via `devmem` or a small debugfs hook) to prove the CPU can actually see the block; if the ID reads as all-zeros or all-ones, it's a clock, power, or bus-matrix issue rather than a driver logic bug. Next I'd check the clock and reset state — is the clock enabled, is the reset deasserted, is the power domain on — because a driver that "succeeds" without enabling its clock will happily return 0 while the block sits dead. I'd also verify pinmux and pad configuration for any external interface, and use a scope or logic analyzer on the actual pins to see whether transactions are leaving the SoC at all. If the block uses indirect access (index/data register pairs), I'd confirm the commit/write strobe is being issued. Finally I'd add temporary register-dump instrumentation in the driver's probe and in the first I/O path to compare what the driver thinks it wrote against what the hardware reports.

**Possible follow-ups:** How would you tell the difference between a clock that's never enabled and a clock that's enabled but at the wrong rate? What would you check first if the ID register reads correctly but every data register reads back stale?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe untouched and layer configuration on top through the mechanisms Yocto already provides. I'd create a `.cfg` fragment containing only the `CONFIG_*` lines the board needs, and reference it from a `.bbappend` in my own layer using `SRC_URI` plus `KERNEL_CONFIG_FRAGMENTS` (or the `linux-yocto`-style `SRC_URI` fragment mechanism, depending on the kernel recipe class). The bbappend lives in my layer and matches the vendor recipe by name and version wildcard, so the vendor layer stays pristine and updatable. I'd keep fragments small and single-purpose — one for a peripheral, one for a debug option — so they're auditable and easy to rebase. For anything that must not be silently overridden, I'd use `KERNEL_CONFIG_FRAGMENTS` with the fragment applied after the base config, and verify the final `.config` in the build's work directory rather than trusting that the fragment "took." I'd also add a `do_configure:append` sanity check that greps the generated `.config` for the expected symbols and fails the build if they're missing, which catches the classic problem of a fragment being silently dropped because of a dependency. Finally, I'd document the fragment-to-feature mapping so a future kernel bump doesn't lose track of why each option exists.

**Possible follow-ups:** What happens if two fragments set the same symbol to different values, and how would you control which wins? How would you handle a configuration option that depends on another symbol being enabled first?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never block on anything the logging path can hold. I'd design the driver so the real-time access path takes only a short spinlock or, better, is lock-free on the data path — for example, the real-time side writes into a pre-allocated ring buffer or a double-buffered region and the logging side reads from the other buffer. The logging task would consume from the ring in process context, and if it falls behind, it drops or overwrites old entries rather than applying backpressure to the producer. I'd avoid any mutex or sleeping lock shared between the two paths; if a shared resource genuinely needs mutual exclusion, I'd use a spinlock held for the shortest possible critical section and make sure the logging side never holds it across a copy-to-userspace or a blocking operation. For the userspace interface, I'd expose the real-time data through a `mmap`'d buffer or a low-latency read path, and the logging data through a separate character device or debugfs file so the two never contend on the same file operations. I'd also consider whether the real-time consumer should be in-kernel (a high-priority kthread or a tasklet/threaded IRQ) rather than a userspace task, since userspace scheduling adds latency the logging path could perturb. Finally, I'd instrument worst-case latency on the real-time path under logging load to prove the isolation actually holds.

**Possible follow-ups:** How would you size the ring buffer, and what's the failure mode when the logging consumer can't keep up? Would you use a threaded IRQ or a tasklet for the real-time side, and why?

## Q4: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?

**Answer:** `EINTR` means a signal was delivered to the process while it was blocked in a syscall, so the first question is where that signal comes from — it's rarely truly "nothing." I'd check whether the daemon installs any signal handlers or timers, whether a library it links (or a watchdog/health-monitor supervisor) is sending signals, and whether the process is being stopped/continued by a job-control or cgroup mechanism. I'd also look at whether the driver's `ioctl` path can sleep and whether it's interruptible — an interruptible wait returns `EINTR` when a signal arrives, and a well-written daemon should retry on `EINTR` rather than abort. So part of the fix is on the userspace side: wrap the `ioctl` in a retry loop that treats `EINTR` as "try again," which is standard practice. But I'd also want to understand the root cause, because frequent signals suggest something else is wrong — a supervisor restarting the daemon, a debugger or `strace` attaching, or a real-time signal from another component. I'd use `strace -f -e trace=signal,ioctl` to see the signal delivery and the failing call together, and check `dmesg` and the supervisor's logs for correlated events. If the driver's `ioctl` is doing a long uninterruptible wait, I'd also reconsider whether that wait belongs in the `ioctl` at all or should be moved to a `poll`/`read` model.

**Possible follow-ups:** Which signals are delivered by default in a way that would interrupt a blocking syscall, and how does `SA_RESTART` change the picture? If the daemon must not be modified, how would you mitigate this from the driver or system side?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams have legitimate concerns. First I'd get the facts on the table: exactly which pins move, what the new peripheral needs, and what the manufacturing line actually depends on — is it the debug UART specifically, or any early console, and is that dependency documented or just habit? I'd want to know whether the change can be made without touching the boot console at all, for example by keeping the early console on the current pins and moving only the runtime debug UART, or by using a different console path for manufacturing. Then I'd quantify the risk: what breaks if early boot output is lost, how the manufacturing test would detect a boot failure without it, and what the fallback is. I'd propose a staged approach — make the pinmux change behind a build-time or device-tree variant, validate it on a small batch, and only then roll it into the production configuration, with the manufacturing team signing off on the test procedure. Throughout, I'd keep the discussion focused on the shared goal (shipping a board that meets the new requirement without breaking the line) and make sure the decision and its rationale are recorded, so it's not relitigated later. If the teams can't agree, I'd escalate with a clear options-and-tradeoffs summary rather than picking a side unilaterally.

**Possible follow-ups:** How would you structure the validation to catch a regression in early boot output before it reaches the manufacturing line? What would you do if the hardware team's timeline didn't allow for a staged rollout?
