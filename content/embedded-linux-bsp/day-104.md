# embedded-linux-bsp — Day 104

## Q1: How would you approach debugging a situation where the kernel boots successfully and the root filesystem mounts, but a userspace daemon that opens a character device and issues `ioctl()` calls intermittently fails with `EINTR` and aborts?

**Answer:** `EINTR` means a blocking system call was interrupted by a signal before it completed. The daemon's assumption that "nothing sends me signals" is usually wrong in one of a few ways, so I'd work outward from the syscall itself.

First, confirm the signal source. I'd run the daemon under `strace -f -e trace=signal,ioctl` and look at what arrives immediately before the `EINTR` return — the `rt_sigreturn` or signal delivery line will name the signal. Common culprits: `SIGCHLD` from a child process the daemon spawns (e.g., a helper or a shell-out), `SIGALRM` from an internal timer, `SIGIO`/`SIGURG` from async I/O or socket activity, or a debugger/`gdbserver` attaching. If the signal is `SIGCHLD`, the daemon may not have installed a handler and the default disposition is ignore — but the syscall still returns `EINTR` if the signal is delivered while blocked. That's a classic "nothing is sending me signals" red herring.

Second, check whether the driver's `ioctl` path is even interruptible. If the driver blocks in `wait_event_interruptible()` or `mutex_lock_interruptible()`, any signal delivered to the task will abort the wait. A driver that should not be interruptible by arbitrary signals should use `wait_event_killable()` (only fatal signals) or `wait_event()` (uninterruptible) — but that's a design decision with latency trade-offs, so I'd want to understand why the wait exists before changing it.

Third, look at the daemon's own signal mask and handlers. `sigprocmask`/`pthread_sigmask` state, `SA_RESTART` on handlers, and whether the daemon is multi-threaded (signals can be delivered to any thread not blocking them). A handler installed without `SA_RESTART` will cause `EINTR` on many syscalls even when the handler does nothing.

The fix is usually one of: install handlers with `SA_RESTART` where appropriate, block irrelevant signals in the thread doing the `ioctl`, or make the daemon retry on `EINTR` (the POSIX-correct pattern for any blocking call). I'd also ask whether the driver's `ioctl` should be restartable at all — if it's a long-running operation, the right answer may be to make it interruptible and have userspace handle `EINTR` as "retry or abort cleanly," not "crash."

**Possible follow-ups:**
- If the signal turns out to be `SIGCHLD` from a helper process, what's the cleanest way to stop it from perturbing the `ioctl` path without changing the driver?
- How would you decide between making the driver's wait uninterruptible versus making userspace retry on `EINTR`?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our deltas on top, so that when the vendor bumps their kernel we rebase our fragments rather than re-merging a fork.

The mechanism is `KERNEL_CONFIG_FRAGMENTS` (or the older `SRC_URI`-with-`.cfg` approach, depending on the kernel class version). I'd create a `.cfg` fragment file in our layer containing only the options we need to change — `CONFIG_FOO=y`, `CONFIG_BAR=m`, `# CONFIG_BAZ is not set` — and reference it from a `.bbappend` on the vendor's kernel recipe:

```
FILESEXTRAPATHS:prepend := "${THISDIR}/${PN}:"
SRC_URI += "file://board-fragment.cfg"
```

The fragment is merged by `merge_config.sh` during `do_configure`, after the vendor's defconfig is applied. This is the key property: the vendor's defconfig stays intact, and our fragment is applied as an overlay. If the vendor changes their defconfig, our fragment still applies on top and we only need to reconcile options we actually touched.

A few practical points I'd insist on:
- **Keep fragments minimal and named for their purpose** — e.g., `sensor-i2c.cfg`, `debug-uart.cfg` — rather than one giant "board.cfg". It makes it obvious what each delta is for and lets different images include different subsets.
- **Use `# CONFIG_X is not set` explicitly** when disabling an option the vendor enables, otherwise the merge may leave it on.
- **Validate the result** — after `do_configure`, diff the generated `.config` against the vendor's defconfig to confirm only intended options changed. A CI check that fails on unexpected deltas catches drift early.
- **Don't put device tree changes in the kernel fragment** — those belong in a separate `.bbappend` on the kernel or a device-tree recipe, so the two concerns stay independent.

If the vendor's recipe is genuinely unmaintainable (e.g., they hard-code a defconfig path), the fallback is a thin `.bbappend` that overrides `do_configure` to call `merge_config.sh` ourselves — but that's a last resort, because it couples us to the vendor's configure logic.

**Possible follow-ups:**
- How would you handle a fragment option that the vendor's kernel doesn't yet support (e.g., a driver only in a newer kernel)?
- What's your approach when two fragments in the same image set the same option to different values?

## Q3: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace application that `mmap()`s a register region of a custom FPGA peripheral and reads from it gets a segmentation fault on production hardware, while the same binary works on the development board. How would you approach this?

**Answer:** A segfault on `mmap`'d register access that differs between dev and production boards points at the mapping itself, not the application logic — the app is touching an address that isn't mapped in its address space on that board.

First, confirm the fault address. Run under `gdb` or check `dmesg` for the faulting address and the `segfault at ... ip ... sp ... error ...` line. Compare that address to what the app expects from its `mmap` return value. If the app is dereferencing a hard-coded physical address rather than the pointer returned by `mmap`, that's the bug — physical addresses are not valid in userspace, and the dev board may have happened to have that physical page mapped by coincidence (e.g., via a different mapping or a different DRAM layout).

Second, check the device tree. The FPGA node's `reg` property defines the physical address and size that `/dev/mem` or a UIO driver will expose. If production hardware has a different FPGA base address (different chip select, different address decode, different FPGA build), the device tree must reflect it. A dev board and production board sharing a DTS but differing in FPGA address is a common bring-up mistake — the fix is a board-specific DTS or an overlay, not an app change.

Third, check the mapping permissions and size. `mmap` with `PROT_READ|PROT_WRITE` on a region the kernel maps read-only, or a length that exceeds the `reg` size, will fault on access. On production hardware the FPGA may expose a smaller window than on dev.

Fourth, check whether the app is using `/dev/mem` versus a UIO or custom driver. `/dev/mem` access to a region not reserved in the device tree can be blocked by `CONFIG_STRICT_DEVMEM`, and the behavior can differ between kernel configs on the two boards. UIO or a proper driver is the robust path — it also gives you interrupt handling and avoids the "physical address in userspace" trap entirely.

The general principle: userspace should never know a physical address. It should `open()` a device node, `mmap()` the region the driver exposes, and use the returned pointer. If the app is doing anything else, that's the first thing to fix regardless of which board it runs on.

**Possible follow-ups:**
- How would you structure the device tree so that the FPGA region is reserved and exposed via UIO, and what would the userspace side look like?
- If the production FPGA genuinely has a different register layout, how would you keep one application binary working across both boards?

## Q4: How would you approach deciding the initialization order between two kernel drivers where one driver's device must be powered and clocked by a regulator and clock controller managed by another driver, and both are built as modules?

**Answer:** The short answer is: don't try to control module load order from userspace or `modprobe` config — express the dependency in the device tree and let the driver core's deferred-probe mechanism handle it. Manual ordering is fragile and breaks the moment someone loads modules in a different order or the initramfs changes.

The mechanism: the consumer driver's device tree node references the supplier via phandles — `vcc-supply = <&reg_foo>`, `clocks = <&clk_ctrl 0>`. When the consumer's `probe()` runs, it calls `devm_regulator_get()` and `devm_clk_get()`. If the supplier driver hasn't probed yet, those calls return `-EPROBE_DEFER`, and the driver core puts the consumer on a deferred-probe list and retries it after other drivers have probed. This works regardless of module load order, as long as both modules are loaded (or built in) before the deferred-probe retry gives up.

The practical requirements:
- **Both drivers must be loadable at boot** — either built in, or loaded from the initramfs before the deferred-probe queue is exhausted. If the supplier module is only in the root filesystem and the consumer is built in, the consumer will defer forever. So the supplier module needs to be in the initramfs (or built in) if the consumer is built in.
- **The device tree must actually express the dependency.** A common failure is a consumer node that hard-codes a register write to enable its own clock instead of referencing the clock controller — that "works" until the clock controller's driver changes its register layout or the clock isn't actually enabled yet.
- **`-EPROBE_DEFER` must be propagated correctly.** If the consumer's `probe()` gets `-EPROBE_DEFER` from `devm_regulator_get()` but swallows it and returns 0, the device is marked probed but non-functional. Every error path from a supplier getter must be returned, not masked.

For debugging, `/sys/kernel/debug/devices_deferred` (or the `deferred_probe` tracepoints) shows what's stuck and why. If a device is deferred indefinitely, the usual causes are: supplier module not loaded, phandle typo in the device tree, or the supplier's own `probe()` failing silently.

If for some reason the dependency can't be expressed in the device tree (e.g., a supplier that isn't a device-tree node), the fallback is an initcall ordering or a `-EPROBE_DEFER` from a manual lookup — but I'd treat that as a smell and push for fixing the device tree instead.

**Possible follow-ups:**
- What would you check first if a device shows up in `devices_deferred` and never leaves it?
- How would you handle a supplier that itself depends on a third driver, forming a chain — does deferred probe handle that correctly?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review the hardware team reveals that the SoC's boot ROM now requires the boot medium to be ready within a tighter window than the current design allows, because they changed the PMIC to a slower-ramping part to meet a new efficiency target. The bootloader and kernel are already tuned for the old PMIC timing, and the project is five weeks from the start of a clinical trial. How would you handle this situation?

**Answer:** The first thing I'd do is separate the problem into "what the boot ROM requires" and "what our software assumes," because those are different failure modes and may have different fixes.

I'd get the hardware team to quantify the new window — the boot ROM's maximum wait for the boot medium, the new PMIC's ramp time to the SoC's minimum operating voltage, and the margin between them. If the margin is positive but thin, the fix may be as simple as adjusting the bootloader's early delay or the PMIC's soft-start configuration; if it's negative, the boot medium itself needs to be ready faster, which is a hardware or boot-medium-selection problem, not a software one.

In parallel, I'd assess the software side: does the bootloader currently wait on the PMIC's power-good signal, or does it assume a fixed delay? If it assumes a fixed delay tuned to the old PMIC, that's the first thing to change — waiting on power-good is robust to PMIC changes, a fixed delay is not. I'd also check whether the kernel's early init has any similar assumptions (regulator constraints, clock rates set before the PMIC is stable).

Then I'd bring the stakeholders together — hardware, software, regulatory, and project management — with a clear statement of the risk: what the new timing means for boot reliability, what the options are (software fix, PMIC configuration change, boot medium change, schedule slip), and what each costs. For a clinical trial start, the regulatory angle matters: a boot reliability change may need to be reflected in the DHF and possibly re-tested, so the regulatory lead needs to be in the room early, not after the fix is chosen.

My recommendation would depend on the margin: if software can close the gap with a power-good-based wait and a validated boot test, that's the lowest-risk path and I'd push for it with a clear test plan (cold-boot cycling across temperature and voltage corners). If the margin is negative, I'd escalate to project management with a recommendation to either change the PMIC configuration or slip the trial start — not silently absorb the risk. The one thing I would not do is let the team "just add a delay" without understanding the margin, because that's how intermittent boot failures reach production.

**Possible follow-ups:**
- How would you structure the cold-boot validation to give confidence the fix holds across the full operating envelope?
- If the hardware team insists the PMIC change is non-negotiable and the margin is negative, what would your escalation look like?
