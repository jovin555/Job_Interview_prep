# embedded-linux-bsp — Day 12

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the real-time clock (RTC) drifts significantly (e.g., minutes per day) and the system is supposed to timestamp medical event logs?
**Answer:** I'd start by separating the problem into hardware and software causes. First, I'd verify the RTC's reference crystal and load capacitance against the datasheet specification — a common cause of drift is a crystal with the wrong load capacitance or excessive stray capacitance on the PCB layout, which pulls the oscillator frequency off nominal. I'd measure the actual frequency with a frequency counter or high-resolution oscilloscope over a long window to quantify the error. On the software side, I'd check whether the kernel RTC driver is using the correct compensation registers (if the RTC supports them) and whether the system is applying NTP or PTP corrections that might mask or interact with the underlying drift. I'd also check if the RTC is being read through the correct interface — some SoCs have multiple RTCs, and the wrong one might be selected in the device tree. If the hardware is confirmed correct, I'd look at temperature effects: if the device operates across a wide temperature range, the crystal's temperature coefficient could be the dominant factor, and a temperature-compensated crystal oscillator (TCXO) or software compensation using an on-board temperature sensor might be necessary. For a medical device, I'd also consider whether the drift matters for regulatory purposes — if timestamps are used for clinical decisions, the acceptable drift budget needs to be defined in the requirements, and the solution needs to be validated across the operating temperature range.

**Possible follow-ups:** How would you determine whether the drift is acceptable for a medical device? What if the drift only appears after the device has been running for several hours — how would you approach that?

## Q2: How would you approach designing the boot sequence for a system with two processors — an application processor running Linux and a safety-critical microcontroller — where the microcontroller must be fully initialized and running its safety monitoring routines before the Linux userspace starts any critical applications?
**Answer:** The key principle is establishing a deterministic boot order with explicit handshakes between the two processors. I'd start by defining the boot stages: power-on, bootloader on the application processor, microcontroller boot, and Linux kernel/userspace startup. The microcontroller should be held in reset by a GPIO from the application processor (or a hardware sequencer) until the application processor's bootloader is ready to release it — this ensures the MCU doesn't start executing before the system is stable. Once released, the MCU boots its own firmware and signals readiness via a shared handshake mechanism — either a mailbox interrupt, a shared memory flag with a defined protocol, or a dedicated GPIO line. The application processor's bootloader or early kernel code should wait for this handshake before proceeding to mount the root filesystem or start critical services. In the kernel, this could be implemented as a driver that probes early and blocks until the MCU signals ready, or the bootloader could pass a status via the device tree or ATAGs. For the Linux userspace, I'd use a service manager (systemd or similar) with explicit dependencies: the critical application services should have a `Requires=` or `After=` dependency on the service that confirms MCU readiness. I'd also consider a timeout with a defined failure path — if the MCU doesn't signal within a specified window, the system should either retry, enter a safe state, or log the failure and continue in a degraded mode, depending on the safety requirements. The handshake protocol itself needs to be robust: I'd use a versioned protocol with CRC-checked status words in shared memory, and the MCU should be able to signal fault conditions that the application processor must respect before starting normal operations.

**Possible follow-ups:** How would you handle the case where the MCU fails to boot or signals a fault during startup? How would you test this boot sequence to ensure it's reliable across power cycles?

## Q3: You're debugging a system where the kernel boots and the root filesystem mounts correctly, but a custom userspace application that communicates with an FPGA over a memory-mapped interface consistently fails with segmentation faults. The application works on the development board but not on the production hardware. How would you approach this?
**Answer:** I'd approach this systematically, starting with the assumption that the difference between development and production hardware is the root cause. First, I'd compare the device tree entries for the FPGA region between the two boards — a common issue is that the memory region size or physical address differs, or the `reg` property doesn't match the actual FPGA decode logic. I'd verify the physical address the application is using against the actual memory map on the production board. Next, I'd check whether the memory region is properly reserved in the kernel — if the FPGA is mapped into a region that the kernel also uses for other purposes, the application could be accessing memory that gets remapped or reclaimed. I'd look at the kernel log for any warnings about the reserved memory region. I'd also check the cache attributes: if the FPGA registers are mapped as cacheable when they should be device memory (or vice versa), you can get stale data or bus errors that manifest as segfaults. The `dma-ranges` property in the device tree is another thing to verify — if the FPGA's address translation differs between boards, the application's virtual-to-physical mapping could be wrong. I'd also check whether the production board has a different FPGA configuration or bitstream that changes the register layout. If the application uses mmap, I'd verify the file descriptor and offset handling — a common bug is assuming the FPGA is at the same offset when the device node or memory region size changed. Finally, I'd run the application under strace or with AddressSanitizer to pinpoint the exact faulting address and compare it against the expected FPGA memory window.

**Possible follow-ups:** How would you determine whether the issue is a cache-coherency problem versus an address mapping problem? What tools would you use to inspect the memory mappings of the running process?

## Q4: How would you approach implementing a kernel driver for a device that needs to perform a hardware-triggered DMA transfer, where the trigger comes from an external sensor's interrupt line, and the data must be processed and made available to userspace within a hard real-time deadline (e.g., 2 ms)?
**Answer:** I'd start by analyzing the timing budget: the interrupt latency, DMA setup time, transfer duration, and the time needed to make data available to userspace. The key design decision is whether the DMA transfer can be set up ahead of time or must be configured after the interrupt arrives. If the sensor triggers at a predictable rate, I'd pre-configure the DMA channel with a cyclic or double-buffered descriptor so that when the interrupt arrives, the DMA is already armed and waiting — this minimizes the latency between trigger and transfer start. The interrupt handler should be as short as possible: it should acknowledge the interrupt, possibly start the DMA if it wasn't pre-armed, and defer any processing to a tasklet or threaded IRQ. For the 2 ms deadline, I'd consider whether the entire transfer plus processing can fit in the interrupt handler itself, or whether a high-priority kernel thread (SCHED_FIFO) is needed. The data path to userspace is critical: using `read()` on a character device with blocking I/O is simple but may not meet the deadline if the scheduler delays the userspace process. Alternatives include using a shared memory region with a seqlock or a ring buffer that userspace polls, or using `poll()`/`epoll()` with a high-priority process. I'd also consider using `copy_to_user()` in the interrupt context if the data size is small, but this can be problematic with page faults. A more robust approach is to use a kernel buffer that's mapped into userspace via mmap, with a synchronization mechanism (e.g., a futex or eventfd) to signal data availability. For a medical device, I'd also need to consider what happens if the deadline is missed — the driver should have a mechanism to detect and report missed deadlines, and the system design should have a defined response (e.g., alarm, safe state). I'd also verify that the DMA controller and interrupt controller have the appropriate priority settings, and that no other driver on the system can block the interrupt for an extended period.

**Possible follow-ups:** How would you handle the case where the sensor triggers faster than the DMA can be re-armed? How would you verify that the 2 ms deadline is actually met under worst-case system load?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the manufacturing team reveals that they need to substitute the currently qualified eMMC flash with a different vendor's part due to a supply chain shortage. The new eMMC has a different erase block size, different wear-leveling behavior, and a slightly different controller interface. The project is four weeks from the start of production, and the current eMMC is already qualified and tested. How would you handle this situation?
**Answer:** I'd approach this as a risk management problem rather than a simple component swap. First, I'd acknowledge that the manufacturing team has a legitimate constraint, but I'd make it clear that a silent substitution without validation is not acceptable for a medical device. I'd propose a structured assessment: gather the datasheet for the new eMMC and compare it against the current part across all relevant parameters — not just the obvious ones like capacity and interface, but also power consumption, temperature range, endurance, and any timing parameters that could affect the storage driver. I'd also check whether the new part requires any driver or device tree changes — some eMMC controllers need different tuning parameters or have quirks that must be enabled in the kernel. I'd then propose a validation plan: a subset of the existing qualification tests that focus on storage reliability, power-loss resilience, and sustained write performance. The key question is whether we can run these tests within the four-week window. If we can, I'd work with the manufacturing team to get early samples and run the tests in parallel with other pre-production activities. If we can't complete full validation, I'd propose a risk-based approach: run the most critical tests (power-loss testing, extended write/read cycling, and the specific use-case workload) and document the residual risk. I'd also involve the regulatory team early to determine whether this change requires a design change notification or re-certification under the quality management system. Throughout this, I'd maintain clear communication with the project manager about the trade-off between schedule and risk, and I'd push back if the schedule pressure threatens to skip necessary validation. The goal is to find a path that respects both the supply chain constraint and the safety requirements — not to simply accept the change or refuse it outright.

**Possible follow-ups:** What specific tests would you prioritize if you only had two weeks for validation? How would you handle the situation if the new eMMC fails one of the critical tests but the manufacturing team says they have no alternative parts available?
