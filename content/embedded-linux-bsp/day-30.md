## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of two identical I2C sensors on the same bus, while the other works fine?

**Answer:** I'd start by confirming whether the issue is at the electrical, device tree, or driver level. First, I'd check `i2cdetect` to see if the device appears on the bus at all. If it doesn't show up, the problem is likely electrical or address-related — I'd verify the sensor's address pins are strapped correctly (since identical sensors often need different address bits), check the I2C bus pull-ups, and confirm the sensor's power supply and reset lines are actually toggling as expected. I'd also probe the bus with an oscilloscope to check for signal integrity issues like excessive rise times or missing ACKs, especially if the bus is running at 400 kHz. If the device does appear in `i2cdetect` but the kernel driver doesn't bind, I'd check the device tree entry — specifically the `reg` property, which must match the sensor's actual address, and the compatible string, which must match what the driver expects. I'd also verify that the interrupt line isn't shared or misconfigured, since a stuck interrupt on one sensor can prevent the other from probing. If the device probes but reads fail, I'd suspect a timing or register configuration issue specific to that sensor's initialization sequence. A systematic approach — confirming presence on the bus first, then checking the device tree binding, then the driver's probe path — usually isolates the problem quickly.

**Possible follow-ups:**
- How would you distinguish between a hardware addressing issue and a device tree configuration error?
- What if both sensors have the same address and you can't change it in hardware — how would you handle that?

## Q2: How would you approach designing a kernel driver for a device that needs to be accessed by both a real-time safety-critical task and a non-real-time monitoring task, where the safety-critical task must never be blocked by the monitoring task?

**Answer:** The core principle is that the safety-critical path must never depend on a lock that the non-real-time path can hold indefinitely. I'd start by identifying the shared resource — typically a hardware register set or a data buffer. If the hardware supports it, I'd use separate register windows or channels for each access path so they don't contend at all. If that's not possible, I'd use a lock-free design for the safety-critical path: the real-time task writes to a dedicated ring buffer or mailbox using atomic operations, and the monitoring task reads from it without ever blocking the writer. For the hardware access itself, I'd consider using a spinlock with interrupts disabled for the safety-critical section — but only if the critical section is very short and bounded. The monitoring task would use a mutex or a different locking mechanism, and it would never be allowed to hold that lock while doing something unbounded like sleeping or waiting on I/O. Another approach is to give the safety-critical task direct hardware access through a dedicated driver instance, while the monitoring task goes through a separate, slower path — for example, the safety-critical task uses a raw I/O region mapped into its address space, while the monitoring task uses the standard driver interface. The key is to design the concurrency model up front, document the locking hierarchy, and verify with stress testing that the safety-critical path's worst-case latency is bounded and acceptable.

**Possible follow-ups:**
- How would you verify that the safety-critical path never misses its deadline under heavy monitoring traffic?
- What role would priority inheritance or priority ceiling protocols play in this design?

## Q3: How would you approach implementing a kernel driver for a device that needs to perform a hardware-triggered DMA transfer, where the trigger comes from an external sensor's interrupt line, and the data must be processed and made available to userspace within a hard real-time deadline (e.g., 2 ms)?

**Answer:** I'd structure this as a two-stage pipeline: interrupt handling and DMA completion. The sensor's interrupt line would be configured as a GPIO interrupt in the device tree, and the driver's interrupt handler would be a threaded IRQ — the hard IRQ handler would be minimal, just acknowledging the interrupt and waking the threaded handler. The threaded handler would then configure and start the DMA transfer, since DMA setup can involve register writes that shouldn't happen in atomic context. The DMA completion callback would run in softirq context, so it needs to be fast — I'd copy the data to a pre-allocated buffer and wake a kernel thread or use a wait queue to signal userspace. For the 2 ms deadline, I'd need to account for the worst-case latency chain: interrupt latency, threaded handler scheduling, DMA setup time, transfer time, completion callback, and the wake-up path to userspace. I'd use a high-resolution timer to measure each stage and identify where the time goes. If the deadline is tight, I might consider using a real-time kernel patch or PREEMPT_RT, and I'd make sure the DMA channel has appropriate priority. For userspace notification, I'd use a blocking read with a timeout, or an eventfd/poll mechanism, rather than busy-waiting. I'd also pre-allocate all buffers and DMA descriptors at probe time to avoid allocation in the hot path, and I'd ensure the DMA is configured for double-buffering so the next transfer can start while userspace processes the current data.

**Possible follow-ups:**
- How would you measure and verify that the 2 ms deadline is actually met under worst-case system load?
- What would you do if the DMA transfer itself takes longer than the deadline allows?

## Q4: How would you approach structuring the root filesystem for an embedded Linux medical device that needs to support over-the-air (OTA) updates with a rollback mechanism, while ensuring that patient data and configuration settings survive the update process?

**Answer:** I'd use a dual-copy (A/B) partition scheme for the root filesystem, with a separate persistent data partition for patient data and configuration. The layout would look something like: bootloader, then two identical root filesystem partitions (A and B), then a data partition, and possibly a separate partition for the kernel or a combined kernel+rootfs image. The bootloader maintains a counter of successful boots — if the new version fails to boot or fails a health check, the bootloader falls back to the previous partition. For the root filesystem itself, I'd use a read-only or read-mostly filesystem like squashfs or ext4 mounted read-only, with all writable data redirected to the persistent data partition via bind mounts or symlinks. This ensures the rootfs is always in a known-good state and can be atomically swapped during an update. Patient data and configuration live on the data partition, which is never touched during an update — it's mounted read-write and formatted with a journaling filesystem like ext4 to survive power loss. The update process would write the new image to the inactive partition, verify its integrity (checksums, signatures), then flip the boot flag and reboot. After boot, a health-check service validates that critical applications start correctly and reports success back to the bootloader; if the check fails, the bootloader reverts. I'd also consider using U-Boot's `bootcount` mechanism or a similar watchdog-based approach to handle the case where the system hangs before the health check completes.

**Possible follow-ups:**
- How would you handle the case where the update itself is interrupted mid-write?
- What filesystem features would you use to ensure the data partition survives unexpected power loss?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the hardware team reveals that they need to change the main processor's boot mode strap resistors to accommodate a new flash part. The change means the processor will boot from a different interface (e.g., from SPI NOR to eMMC), and the bootloader and kernel configurations are already tuned for the current boot source. The project is six weeks from the start of a clinical trial. How would you handle this situation?

**Answer:** I'd start by treating this as a change-management issue, not just a technical one. The first step is to understand the full scope: I'd ask the hardware team for the exact strap configuration, the new flash part's datasheet, and any timing or electrical differences. I'd also check whether the bootloader and kernel already have support for the new boot source — if the SoC's boot ROM supports eMMC natively and U-Boot has an eMMC driver, the change might be mostly configuration, not new code. I'd then assess the risk: what's the worst case if the boot path fails, and how long would it take to debug? I'd propose a parallel workstream: the software team starts adapting the bootloader and kernel configuration immediately, while the hardware team provides a small number of boards with the new strap configuration for early testing. I'd also ask whether the change can be made optional — for example, if the straps can be populated either way, we could keep the current boot source for the clinical trial and qualify the new one in parallel. If the change is mandatory, I'd negotiate a clear milestone: the boot path must be validated on the new configuration at least two weeks before the trial starts, leaving time for fallback. I'd also update the risk register and ensure the regulatory documentation reflects the change, since boot source changes can affect the device's security and integrity posture. Throughout, I'd keep communication open — the goal is to make the change safely, not to block it, but the clinical trial date is a hard constraint that everyone needs to respect.

**Possible follow-ups:**
- How would you prioritize the work if the bootloader adaptation turns out to be more complex than expected?
- What specific tests would you require before signing off on the new boot configuration for the clinical trial?
