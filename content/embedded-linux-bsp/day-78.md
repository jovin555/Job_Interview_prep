# embedded-linux-bsp — Day 78

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is deferred indefinitely because a supplier it depends on never becomes available — with no obvious error in the kernel log?

**Answer:** `-EPROBE_DEFER` is a cooperative mechanism, not a failure — the driver framework is telling you "I'm not ready yet, try me again later." When it loops forever with no error, the dependency graph is broken somewhere, and the kernel is being polite about it rather than loud. My first move is to make the invisible visible: enable `initcall_debug` and dynamic debug for the driver core (`dyndbg="file drivers/base/dd.c +p"`), which prints each deferred probe attempt and the reason. From there I trace the supplier chain — if the driver depends on a regulator, clock, GPIO, or PHY, I check whether that supplier itself probed successfully. A common trap is a supplier that is present in the device tree but whose own `probe()` silently returned early, or a phandle that points at a node with no matching driver bound. I also check for circular dependencies: A defers on B, B defers on A, and neither ever resolves — the kernel has no cycle detection here, so it just spins. If the supplier is a built-in driver that should have probed before the consumer, I look at initcall ordering and whether the supplier is actually compiled in versus a module that never loaded. Finally, I confirm the device tree phandle resolves to the node I think it does — a typo'd `*-supply` property or a label pointing at the wrong node produces exactly this silent loop.

**Possible follow-ups:**
- How would you distinguish a genuine circular dependency from a supplier that simply hasn't probed yet due to initcall ordering?
- What kernel configuration options or tracepoints would you enable to get a definitive list of which device is deferring on which supplier?

## Q2: You're structuring a Yocto BSP for a product family where several boards share a common SoC and vendor BSP but differ in peripherals, device tree, and userspace packages. How would you organize the layers and recipes?

**Answer:** The organizing principle is to separate what's common from what varies, and to make the varying parts additive rather than forked. I'd start with a vendor BSP layer as the base — untouched, so it can be updated cleanly. On top of that, a common product layer holds the shared SoC configuration, the shared kernel recipe append, and any patches that apply to every board in the family. Then each board gets its own thin layer that contains only what's unique: its device tree, its machine configuration (`MACHINEOVERRIDES`), and any board-specific packages or kernel config fragments. The machine configuration is where the board identity lives — `MACHINE = "board-a"` pulls in the right device tree and the right overrides. For userspace differences, I'd use `IMAGE_FEATURES`, `PACKAGE_INSTALL` additions, or a small image recipe per variant rather than branching the whole image. Kernel configuration differences go in `.cfg` fragments applied via `SRC_URI`, not in a forked kernel recipe — that keeps the vendor kernel as the single source of truth. The test of a good structure is: adding a new board in the family should mean adding one thin layer and one machine conf, not touching the common layer or the vendor layer at all.

**Possible follow-ups:**
- How would you handle a board that needs a kernel patch the other boards don't, without forking the shared kernel recipe?
- Where would you put a userspace daemon that only two of the five boards need — in the common layer with a conditional, or in each board's layer?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path controls, so the design has to decouple them at the data structure level, not just the scheduling level. The real-time task gets a lock-free or minimally-contended path to the hardware — ideally a dedicated buffer or register window that the logging task never touches directly. The logging task reads from a separate ring buffer that the real-time path writes into, and the write is non-blocking: if the buffer is full, the real-time path overwrites the oldest entry or drops, but never waits. I'd use a lock-free single-producer/single-consumer ring buffer with atomic head/tail indices, or a `kfifo` if the access pattern allows it, and make sure the real-time side only ever does a bounded amount of work — no allocation, no sleeping locks, no `copy_to_user` on the hot path. The logging task drains the buffer on its own schedule and can afford to block, allocate, and write to the filesystem. If the hardware itself is shared and can't be split, I'd serialize access with a spinlock held only for the register transaction, never across a sleep, and I'd document the maximum hold time. The key discipline is that the real-time task's worst-case latency is bounded by the hardware access itself, not by anything the logging task does.

**Possible follow-ups:**
- How would you verify that the real-time path's worst-case latency is actually bounded, and what would you measure?
- What happens to your design if the hardware register access itself can block, for example on a slow bus?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** Intermittent fallback means the boot sequence is reaching a failure point some of the time and then walking down the boot order — so the first question is which stage is failing and why it's intermittent. I'd start by capturing the full U-Boot console output on a failing boot versus a successful one and diffing them; the fallback is usually preceded by a specific error (MMC init timeout, partition read failure, bad CRC on the environment) that only appears on the bad path. Common causes: the eMMC isn't ready when U-Boot probes it, so `mmc dev` fails and the boot script moves on; the environment is stored on eMMC and a corrupted or partially-written env causes `bootcmd` to fall through to the default; or the boot order in `boot_targets` includes network and the eMMC entry is silently skipped. I'd check whether the fallback is coming from `bootcmd` logic or from the distro boot framework's `boot_targets` list, and I'd make the intended behavior explicit rather than relying on defaults — set `boot_targets` to eMMC only, or add a hard stop after the eMMC attempt. If the root cause is eMMC readiness, I'd look at whether a delay or a retry loop is needed before the first MMC access, and whether the power sequencing gives the eMMC enough time to come up. The fix is usually to make the failure loud (halt on eMMC failure rather than silently falling through) and to address the underlying timing or env corruption.

**Possible follow-ups:**
- How would you determine whether the environment itself is being corrupted, versus the eMMC just not being ready in time?
- What would you change in the boot flow to make an unintended fallback impossible rather than just unlikely?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** This is a case where both teams are right about their own concern, and the job is to find out whether the conflict is real or just assumed. My first step is to get the actual constraint on the table: does the manufacturing line truly need the debug UART on those specific pins, or does it need *a* console at that stage of boot? Those are different requirements, and the second one is usually satisfiable. I'd bring the hardware and software leads together and walk through the boot sequence stage by stage — ROM, bootloader, kernel early console, userspace — and identify exactly where the console is used and by whom. If the manufacturing line only needs it during a specific window, there may be a way to keep a console available without pinning it to the exact pins in question, or to move the pinmux change to after the point where manufacturing needs it. If the change is genuinely incompatible with the manufacturing requirement, that's a decision for the project lead with the trade-off stated plainly: new peripheral versus manufacturing line disruption, with the cost and schedule impact of each. What I would not do is let the software team's "it's baked in" stand as a technical blocker without examining whether it's actually baked in or just currently configured that way — device tree and bootloader pinmux are changeable, the question is the cost and the risk. I'd also want the change validated on real hardware early, not assumed to work, because pinmux changes have a habit of surfacing issues in peripherals nobody was thinking about.

**Possible follow-ups:**
- If the manufacturing line's requirement turns out to be a hard constraint, how would you present the trade-off to the project lead?
- How would you validate a pinmux change without disrupting the manufacturing line during the transition?
