## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of two identical I2C sensors on the same bus, while the other works fine?

**Answer:** I'd start by confirming the problem is at the hardware level versus the device tree or driver level. First, I'd check `i2cdetect` to see if the sensor appears on the bus at all. If it doesn't appear, I'd verify the sensor's address — identical sensors should have different addresses set by their address pins, so I'd check that the address strapping is correct on the board. I'd also check the pull-up resistors and the actual I2C lines with an oscilloscope during probe to see if the sensor is ACKing its address. If the sensor is detected by `i2cdetect` but not bound to a driver, the issue is likely in the device tree — perhaps the second sensor's node has the wrong address, the wrong compatible string, or is missing a required property like an interrupt line that's already claimed by another device. I'd also check if the driver itself has a limitation, such as a fixed array of devices or a check that assumes only one instance. If the sensor is detected but communication fails intermittently, I'd look at bus speed — two devices on the same bus can have different maximum clock rates, and the faster device might be fine while the slower one fails at 400 kHz. Finally, I'd check the kernel log for any probe deferral messages, since the second sensor might be waiting on a resource (like a regulator or GPIO) that never becomes available.

**Possible follow-ups:** How would you determine whether the issue is a device tree problem versus a hardware problem? What if the sensor is detected but returns garbage data?

## Q2: How would you approach implementing a kernel driver for a device that needs to perform a hardware-triggered DMA transfer, where the trigger comes from an external sensor's interrupt line, and the data must be processed and made available to userspace within a hard real-time deadline (e.g., 2 ms)?

**Answer:** The key is to minimize latency at every stage while ensuring the DMA transfer is set up before the trigger arrives. I'd structure this as a two-part design: the interrupt handler and the DMA completion path. In the interrupt handler, I'd avoid any heavy work — just acknowledge the interrupt and, if the DMA channel is idle, start the transfer immediately. The DMA descriptor should be pre-allocated and pre-configured so that starting the transfer is just a register write. The DMA completion callback should run in a tasklet or threaded IRQ context, not in hard IRQ context, to allow for the data processing. For the userspace delivery, I'd use a character device with a ring buffer, and I'd consider using `poll()` or `epoll` so the application can block efficiently. If the 2 ms deadline is truly hard, I'd also evaluate whether the kernel's scheduling latency is acceptable — on a loaded system, a real-time priority class (e.g., `SCHED_FIFO`) for the processing thread might be necessary. I'd also consider whether the DMA completion interrupt could be delayed by other interrupts; if so, I might need to look at interrupt affinity or disable IRQ sharing on that line. Finally, I'd measure the actual end-to-end latency with a logic analyzer or by timestamping in the driver to verify the deadline is met under worst-case conditions, not just average conditions.

**Possible follow-ups:** How would you handle the case where the sensor generates interrupts faster than the DMA can be reconfigured? What if the data processing itself takes longer than the deadline — how would you decide what to drop or prioritize?

## Q3: How would you approach designing the boot sequence for a system with two processors — an application processor running Linux and a safety-critical microcontroller — where the microcontroller must be fully initialized and running its safety monitoring routines before the Linux userspace starts any critical applications?

**Answer:** The fundamental requirement is that the safety-critical microcontroller must be in a known-good state before any Linux application that depends on it starts. I'd structure this in stages. First, the bootloader (U-Boot) should power on the microcontroller and hold it in reset while the application processor initializes. Once the application processor is ready, the bootloader releases the microcontroller from reset and waits for a handshake — typically a shared GPIO or a message over a communication link (UART, I2C, or shared memory) indicating that the microcontroller has completed its self-test and entered its monitoring loop. Only after that handshake should U-Boot proceed to load the kernel. In the kernel, I'd have a driver that re-checks the microcontroller's status during boot — this is important because the kernel boot takes time, and the microcontroller should still be healthy. The driver would expose a sysfs node or a character device that userspace applications can query. The init system (e.g., systemd) should have a service dependency: the critical application service must wait for the microcontroller status to be "ready" before starting. I'd also implement a watchdog mechanism — if the microcontroller stops responding, the application processor should either restart it or enter a safe state. One subtle point is the reset line: if the microcontroller can be reset by a GPIO, the bootloader should ensure that GPIO is in the correct state so the microcontroller doesn't accidentally start before the application processor is ready. I'd also consider whether the microcontroller needs to be updated as part of the boot sequence — if so, the bootloader or a dedicated early userspace service should handle that before the handshake.

**Possible follow-ups:** How would you handle the case where the microcontroller fails its self-test during boot — should the system still boot Linux? How would you design the handshake mechanism to be robust against a hung microcontroller?

## Q4: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel log shows "Failed to request IRQ" for a device that worked on the previous board revision?

**Answer:** I'd start by identifying which IRQ is failing and why. The error message usually includes the IRQ number and the device name. First, I'd check if the IRQ is already claimed by another device — this can happen if the device tree has a shared interrupt line that's incorrectly assigned, or if two devices are accidentally using the same interrupt number. I'd check `/proc/interrupts` to see which IRQs are active and which drivers own them. Next, I'd verify the device tree: is the interrupt property correct for the new board revision? Perhaps the interrupt line moved to a different GPIO or a different interrupt controller cell. I'd also check the interrupt controller itself — if the new board uses a different GPIO controller or interrupt expander, the `interrupt-parent` property might need to change. Another possibility is that the IRQ is failing because the device is trying to request a shared IRQ without setting the `IRQF_SHARED` flag, or the driver is requesting a level-triggered interrupt on a line that's actually edge-triggered. I'd also check whether the previous board revision had a different interrupt controller driver enabled in the kernel config — if the new board uses a new interrupt controller, the driver might not be enabled. Finally, I'd look at the hardware: is the interrupt line actually connected? A floating interrupt line can cause spurious interrupts or prevent the request from succeeding. I'd use a logic analyzer or scope to verify the line is behaving as expected.

**Possible follow-ups:** How would you determine whether the IRQ is being claimed by the wrong driver? What if the IRQ request succeeds but the interrupt never fires?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the hardware team reveals that they need to change the main processor's boot mode strap resistors to accommodate a new flash part. The change means the processor will boot from a different interface (e.g., from SPI NOR to eMMC), and the bootloader and kernel configurations are already tuned for the current boot source. The project is six weeks from the start of a clinical trial. How would you handle this situation?

**Answer:** I'd treat this as a change-management problem with a hard deadline. My first step would be to understand the full scope: is this a change that affects only the boot source, or does it also change the memory map, the clock configuration, or the peripheral initialization? I'd ask the hardware team for the exact strap configuration and the new flash part's specifications. Then I'd assess the software impact: the bootloader needs to support the new boot interface, the kernel needs the correct driver enabled, and the device tree might need changes if the root filesystem moves to a different device. I'd also check whether the new flash part has any timing or voltage requirements that affect the boot sequence. Once I understand the scope, I'd create a risk assessment and a mitigation plan. The key question is whether we can validate the new boot path before the clinical trial. If we have prototype boards or can rework existing boards, I'd prioritize getting a bootable image on the new interface as soon as possible. If we can't validate in hardware, I'd consider a fallback: can we keep the current boot source as a secondary option? For example, can the bootloader be configured to try eMMC first and fall back to SPI NOR? That would reduce the risk. I'd also communicate clearly with the project manager about the risks and the validation plan — I wouldn't just commit to a date without understanding the unknowns. Finally, I'd make sure the change is documented in the design history file, since this is a medical device and traceability is critical. The clinical trial date is important, but patient safety and device reliability are more important — if the change can't be validated in time, I'd recommend delaying the trial rather than proceeding with an unvalidated boot path.

**Possible follow-ups:** How would you prioritize the validation tasks if you only have two weeks before the trial? What if the hardware team says the strap change is already baked into the production boards and can't be reworked?
