# embedded-linux-bsp — Day 97

## Q1: How would you approach deciding whether a peripheral driver should be built into the kernel image versus built as a loadable module, for a device that must be functional before the root filesystem is mounted?
**Answer:** The deciding factor is *when* the device must be available relative to the boot timeline. If the peripheral has to be operational before the root filesystem is mounted — for example, it provides the storage that *is* the root filesystem, or it's the console the bootloader hands off to, or it's needed by an initramfs stage — then it must be built in (`=y`), because loadable modules live on the very filesystem that isn't mounted yet. A classic example is the storage controller and its bus driver for the root device, or a display/console driver needed for early diagnostics. If the device is only needed by userspace after the rootfs is up, a module (`=m`) is preferable: it keeps the base kernel image smaller, allows loading on demand, and makes it easier to update or blacklist a driver without rebuilding the whole kernel. There's a middle ground too — building in a minimal driver for early boot and loading a fuller-featured one later — but that's usually more complexity than it's worth. I'd also weigh the practical side: modules add a dependency on `modprobe`/`modules.dep` being correct in the image, and on the module being present in the initramfs if it's needed early. For a medical device where boot determinism matters, I lean toward building in anything on the critical boot path and keeping modules for optional or late-bound peripherals. The decision should be documented in the BSP config so it's not accidentally changed later.
**Possible follow-ups:** How would you handle a driver that's needed both very early *and* wants to be updatable — what are the trade-offs of an initramfs versus building it in? What kernel config symbols would you check to confirm a driver is actually built in versus modular?

## Q2: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?
**Answer:** "Probe succeeded but nothing works" usually means the driver initialized *something*, but not the thing that actually matters — so I'd start by questioning the assumption that probe doing its job means the hardware is configured. First I'd add instrumentation inside probe to confirm each step actually took effect: read back registers after writing them, check that clock enable and regulator enable calls returned success and that the hardware reflects it (e.g., a status register shows the block is out of reset), and verify the resource addresses and interrupt numbers the driver received match the device tree and the schematic. A very common cause is a resource mismatch — the driver maps the right address but the peripheral's clock gate or power domain was never actually enabled because the driver assumed it was already on, or the reset line was never deasserted. Another common cause is a pinmux issue: the driver talks to the controller fine, but the pins aren't routed to the peripheral, so externally nothing happens. I'd also check whether the driver is binding to the *right* device instance — with multiple similar nodes, probe can succeed on a node that isn't the one wired up. Beyond that, I'd use a scope or logic analyzer on the actual bus lines to see whether the driver is even emitting traffic; if the bus is silent, the problem is upstream in the driver's enable path, and if the bus is active but the device doesn't respond, it's a hardware or addressing issue. Finally, I'd compare against a known-good reference (dev board, previous revision) to isolate whether it's a driver change or a board change.
**Possible follow-ups:** How would you confirm a clock or power domain is actually enabled at the hardware level, not just that the driver's enable call returned success? What would you check first if the bus shows activity but the device never acknowledges?

## Q3: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?
**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our changes on top, so we can absorb vendor updates without merge conflicts. In Yocto the clean mechanism is a `.bbappend` in our own layer that adds a config fragment via `SRC_URI` using the `file://` scheme with the `cfg` fragment type, plus `KERNEL_CONFIG_FRAGMENTS` (or the older `KERNEL_CONFIG_FRAGMENTS`/`do_configure:append` pattern depending on the kernel class version). The fragment file itself contains only the symbols we need to change — `CONFIG_FOO=y`, `# CONFIG_BAR is not set` — and the kernel's `merge_config.sh` machinery applies it on top of the vendor defconfig, so we never touch the vendor's `.config` or recipe. I'd keep fragments small and single-purpose (one per feature or board variant) so they're easy to review and reason about, and name them clearly. For multiple boards sharing a SoC, I'd use `MACHINEOVERRIDES` or per-machine `.bbappend` selection so each board only pulls in its own fragment. I'd also verify the result by inspecting the generated `.config` in the build's work directory and, ideally, add a build-time check that the expected symbols are set — because a fragment that silently fails to apply (e.g., a symbol renamed in a newer kernel) is a nasty class of bug. The key discipline is: our layer owns the delta, the vendor layer owns the base, and the delta is expressed declaratively rather than by editing files in place.
**Possible follow-ups:** What happens if a config fragment references a symbol that no longer exists in a newer kernel version — how would you catch that? How would you handle a fragment that needs to apply only to one machine in a multi-machine BSP?

## Q4: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?
**Answer:** `EINTR` means a blocking syscall was interrupted by a signal before it completed — so the first question is *what signal*, and the second is *why is the daemon treating it as fatal*. On the "what signal" side, I'd check whether the process is receiving signals it doesn't expect: a `SIGCHLD` from a child, a `SIGALRM` from a timer, a signal from a watchdog or supervisor, or even a signal delivered because of a terminal/session issue. `strace -f -e trace=signal` or `signalfd`-based logging would show exactly which signal arrives and when relative to the failing `ioctl`. On the "why fatal" side, the daemon's code is arguably wrong: a well-written blocking `ioctl` loop should handle `EINTR` by retrying, not aborting, because `EINTR` is a normal, expected condition. So there are two fixes: make the daemon robust (retry on `EINTR`, or use `SA_RESTART` where appropriate, or block the unexpected signals around the critical call), and eliminate the spurious signal source if it's genuinely unintended. I'd also consider whether the driver itself is returning `-ERESTARTSYS` from an interruptible wait — that's the kernel's way of saying "a signal arrived during your wait, restart the syscall" — which is correct driver behavior but surfaces as `EINTR` to a userspace caller that doesn't retry. So the root cause may be a legitimate signal (e.g., from a debugger, a profiling tool, or a supervisor sending `SIGCHLD`/`SIGUSR1`) hitting an unhardened daemon. I'd fix both ends: harden the daemon's syscall handling and identify/remove the unintended signal source.
**Possible follow-ups:** How would you distinguish a signal sent by the kernel (`-ERESTARTSYS` path) from one sent by another process? What's the correct way to make a blocking `ioctl` robust against `EINTR` without masking real errors?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?
**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams have legitimate concerns. First I'd get the facts on the table: exactly which pins move, whether the new pinmux group is electrically equivalent (same voltage domain, same drive strength, same alternate-function availability), and — critically — whether the debug UART is used by the manufacturing line as a *functional* interface (e.g., for test fixtures or provisioning) or just as a diagnostic convenience. That distinction changes the risk calculus entirely. Then I'd map the change across the boot chain: the pinmux is set in the bootloader (early console) and again in the device tree (kernel console), so both need to change together, and there's a window during boot where the console could go silent if they're out of sync. I'd propose a staged approach: make the change on a branch, verify early boot console output end-to-end on a prototype, and coordinate with manufacturing to confirm their fixtures still work — ideally with a fallback plan (keep the old pinmux as a build-time option for a transition period) so the line isn't blocked if something goes wrong. I'd also want the hardware team to own the electrical validation of the new pin group and the software team to own the boot-chain change, with a joint sign-off before it lands. The key is not to let it become a hardware-vs-software standoff: define the acceptance criteria together, sequence the work so manufacturing isn't surprised, and keep a rollback path. If the debug UART turns out to be load-bearing for manufacturing, that's a strong argument to either delay the change or provide an alternative test interface before removing it.
**Possible follow-ups:** How would you verify that early boot console output survives the pinmux change before the kernel takes over? If manufacturing can't tolerate any disruption, what alternatives would you propose to free up the pins?
