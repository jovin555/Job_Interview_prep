# embedded-linux-bsp — Day 4

## Q1: How would you approach debugging a U-Boot boot failure where the board hangs after "Starting kernel..." with no further console output?

**Answer:** This is a classic symptom where U-Boot has handed off to the kernel, but the kernel fails early before the serial console driver is initialized. I'd start by confirming the handoff parameters are correct — check that U-Boot is passing the correct device tree blob address and kernel image address via the `bootm` or `booti` command. I'd verify the device tree is valid by running `fdt list` in U-Boot to inspect key nodes like `chosen` (which should point to the correct console device) and the `serial` node itself. Next, I'd enable early printk in the kernel by adding `earlycon` (or a specific `earlycon=uart8250,mmio32,<address>`) to the kernel command line. This gives visibility into the very first kernel messages before the full console driver is up. If early printk shows nothing, the issue is likely before `start_kernel()` — possibly a bad kernel image, incorrect decompression, or a mismatch between the kernel configuration and the SoC's memory layout. I'd also verify the kernel was built with the correct decompressor support and that the U-Boot `bootm` address doesn't overlap with where the kernel expects to decompress. Finally, I'd check for a missing or incorrect `stdout-path` property in the device tree's `chosen` node.

**Possible follow-ups:** What would you do if early printk shows the kernel starts but crashes during device initialization? How would you determine if the issue is in the device tree versus the kernel configuration?

## Q2: You're designing a BSP for a system that must support over-the-air (OTA) firmware updates with a fallback mechanism in case the update fails. How would you structure the bootloader and partition layout to support this?

**Answer:** I'd implement an A/B (dual-copy) update scheme with a reliable fallback. The flash layout would have: a primary bootloader (U-Boot SPL if applicable), a secondary bootloader (full U-Boot), and then two sets of partitions — A and B — each containing a kernel, device tree, and root filesystem. Additionally, there would be a small metadata partition or U-Boot environment variable area that tracks which slot is active and the update status. The bootloader's logic would be: on boot, check the metadata to determine the active slot. If the metadata indicates the last update was incomplete or the slot failed to boot, the bootloader automatically switches to the other slot. I'd implement a "boot count" mechanism in U-Boot — increment a counter on each boot, and if the kernel doesn't set a "success" flag within a certain number of boots (or within a watchdog timeout), the bootloader marks that slot as failed and boots the other. For the update process itself, the running system would download the new image to the inactive slot, verify its integrity (checksum or signature), set the metadata to indicate a pending update, then reboot. The bootloader then attempts to boot the new slot. If it fails, the fallback mechanism kicks in. I'd also ensure the bootloader itself is protected — either by having a write-protected region or by using a recovery mode that can reflash the bootloader via a dedicated mechanism (e.g., USB DFU or SD card).

**Possible follow-ups:** How would you handle the case where both A and B slots are corrupted? What considerations would you have for the root filesystem type (squashfs vs. ext4 vs. ubifs) in an OTA context?

## Q3: How would you approach writing a platform driver in the Linux kernel for a custom FPGA peripheral that is memory-mapped and generates interrupts?

**Answer:** I'd structure this as a platform driver since the device is described in the device tree and is not on a discoverable bus like PCIe or USB. First, I'd define the device tree binding — a node under the appropriate bus with `compatible` string, `reg` for the memory-mapped address range, and `interrupts` property. The driver would use the platform driver model: implement `probe` and `remove` callbacks, register with `module_platform_driver()`. In `probe`, I'd use `platform_get_resource()` to obtain the memory region, `devm_ioremap_resource()` to map it, and `platform_get_irq()` to get the interrupt number. I'd register an interrupt handler using `devm_request_irq()` with `IRQF_SHARED` if multiple devices share the line. The interrupt handler should be a top-half handler that does minimal work — typically reading a status register to determine the interrupt source, clearing the interrupt, and potentially scheduling a threaded interrupt handler or workqueue for heavier processing. I'd create a character device interface using `alloc_chrdev_region()` and `cdev_add()` if userspace needs to interact with the peripheral, or use the kernel's existing subsystem (e.g., IIO, input, or ALSA) if the peripheral fits an existing framework. For DMA-capable transfers, I'd use the DMA engine API with `dma_request_chan()` and `dmaengine_prep_slave_sg()`. I'd also implement power management callbacks (`suspend`/`resume`) to save and restore the device state, and use `devm_*` APIs throughout to ensure automatic cleanup on driver unbind.

**Possible follow-ups:** How would you handle the case where the FPGA logic is reconfigured at runtime and the memory map changes? What debugging techniques would you use if the interrupt handler never fires despite the FPGA asserting the interrupt line?

## Q4: You're working on a system where the root filesystem is stored on an eMMC device, and you need to ensure reliable operation over years of use in a medical device. How would you configure the kernel and filesystem to handle this?

**Answer:** For long-term reliability on eMMC, I'd focus on wear leveling, power-loss protection, and filesystem integrity. First, I'd ensure the kernel's MMC subsystem has the correct eMMC tuning parameters — enable `MMC_DEBUG` during development to verify the timing modes (HS200/HS400) are stable, and consider using a slightly more conservative timing mode if there are any signal integrity concerns. I'd enable the eMMC's internal wear-leveling (which is handled by the eMMC controller itself) and ensure the `discard`/`TRIM` support is enabled in the kernel so the filesystem can inform the eMMC of unused blocks. For the filesystem, I'd choose ext4 with `journal` mode for data integrity (or `ordered` mode as a performance compromise), and mount with `noatime` to reduce writes. I'd also enable the `data=journal` option if the device must survive unexpected power loss without filesystem corruption. For additional protection, I'd configure the kernel's block layer to use a write-back cache with a short flush interval, or disable the write cache entirely (`echo 3 > /proc/sys/vm/drop_caches` is not sufficient — I'd use `hdparm -W 0` on the eMMC device). I'd also implement a robust shutdown sequence that syncs the filesystem and sends a `FLUSH CACHE` command to the eMMC before power-off. For the root filesystem itself, I'd consider using a read-only squashfs for the base system with an overlay filesystem (overlayfs) for writable data stored on a separate partition, which reduces wear on the root partition. Finally, I'd enable kernel features like `CONFIG_EXT4_FS_POSIX_ACL` and `CONFIG_EXT4_FS_SECURITY` only if needed, and ensure `CONFIG_EXT4_FS_JOURNAL` is enabled.

**Possible follow-ups:** How would you test the filesystem's resilience to power loss during a write operation? What metrics would you monitor to predict eMMC end-of-life?

## Q5: Behavioral — You're the BSP lead for a new product, and during a critical milestone review, the hardware team reveals that they changed the memory map — the UART peripheral is now at a different address, and the DRAM size is half of what was originally specified. The software team has already committed to a demo in two weeks. How would you handle this situation?

**Answer:** First, I'd acknowledge the change without assigning blame — hardware changes happen, and the priority is adapting. I'd immediately assess the impact: updating the device tree is straightforward for the UART address change (a single node modification), but the DRAM size reduction could be more significant. I'd check whether the current kernel and root filesystem fit within the new memory budget — if not, I'd need to trim the kernel configuration (remove unnecessary drivers, reduce buffer sizes) and possibly switch to a smaller root filesystem (e.g., from a full distribution to a minimal BusyBox-based system). I'd also verify that any memory-hungry applications or middleware can run within the new constraints. Next, I'd communicate with the project manager: explain the changes needed, estimate the effort (likely a few days for device tree updates, kernel reconfiguration, and testing), and propose a revised plan. I'd ask the hardware team to provide updated documentation (memory map, register addresses) in a formal revision, and I'd set up a quick verification test — boot the new kernel on the updated hardware to confirm the UART works and the system boots within the new memory limits. I'd also add a boot-time memory check that logs the detected DRAM size and warns if it doesn't match expectations, to catch future mismatches early. For the demo, I'd prioritize the critical path: get a booting system with the demo application running, even if some non-essential features are disabled. After the demo, I'd schedule a post-mortem to discuss how to catch such changes earlier — perhaps by requiring hardware change notifications to be reviewed by software before implementation, or by establishing a shared document where both teams track the memory map and key parameters.

**Possible follow-ups:** What if the hardware team says the DRAM reduction is permanent and the original specification was an error — how would you decide which features to cut? How would you prevent this situation from recurring on future projects?
