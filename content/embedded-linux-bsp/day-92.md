# embedded-linux-bsp — Day 92

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder failure modes because the kernel is telling you everything went fine, so the first move is to distrust the return path and verify the hardware actually did what the driver thinks it did. I'd start by confirming the driver is talking to the right register window: dump the device tree node the driver bound to, confirm the `reg` ranges and interrupt numbers match the schematic and the SoC's memory map, and check that the clock and regulator handles resolved to the intended parents rather than a dummy or always-on stub. A very common cause is a driver that programs a peripheral correctly but the peripheral's clock gate is never actually enabled — the register writes land in a bus that silently drops them, or the block is held in reset because a reset-controller line was never deasserted. So I'd read back key registers after writing them and confirm the values stick; if they read back as zero or as reset defaults, the block isn't powered or isn't clocked.

Next I'd separate "driver logic" from "hardware path." I'd add temporary instrumentation — read a known ID or status register that should have a fixed value, and print it. If the ID register reads correctly, the bus and addressing are fine and the problem is in configuration or in the data path downstream. If it reads garbage or all-ones, I'd suspect pinmux, bus timing, or a wrong chip-select/address. On the hardware side I'd reach for a scope or logic analyzer on the relevant bus lines and confirm activity actually appears when the driver runs — sometimes the driver "succeeds" because it's writing to a peripheral that was never enabled in the pinmux, so the pins are still in their default state and nothing reaches the device.

I'd also check the obvious-but-easy-to-miss items: is there a second driver or a firmware/early-boot stage that already claimed the peripheral and left it in a state the Linux driver doesn't expect? Is the driver's `probe()` ordering such that it runs before a dependency (PHY, power domain, external companion chip) is ready, and it just doesn't fail because it never checks? And I'd verify the device tree `compatible` string actually matched the driver — a fallback compatible can bind a generic driver that "succeeds" but does nothing useful. Finally, I'd compare against a known-good reference: does the same peripheral work on an eval board or previous revision with the same driver? That isolates whether it's a board-specific hardware/config issue versus a driver bug.

**Possible follow-ups:** How would you tell the difference between a clock that's gated and a reset line that's asserted, purely from software? What would you check first if the ID register reads correctly but data transfers still fail?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer your board-specific changes on top through configuration fragments rather than a copied-and-edited recipe. In Yocto the mechanism for this is `config-fragments` via `KERNEL_CONFIG_FRAGMENTS` or, more idiomatically, a `.scc`-style fragment set referenced from a bbappend. I'd create a `.cfg` fragment containing only the options my board needs — the driver enable, any `CONFIG_*` values that differ from the vendor default — and reference it from a `linux-vendor_%.bbappend` in my own layer. The bbappend appends to `SRC_URI` and to `KERNEL_CONFIG_FRAGMENTS`, so the vendor recipe is untouched and a vendor kernel bump doesn't clobber my changes.

The important discipline is keeping fragments minimal and additive. If a fragment sets an option that the vendor recipe also sets, you can get ordering surprises, so I'd prefer fragments that only add or explicitly override with a clear comment about why. I'd also make sure the fragment is validated: Yocto's kernel config audit (`do_kernel_configcheck`) flags options that were requested but not applied, or applied but not requested, which catches the classic "I added CONFIG_FOO but a dependency wasn't met so it silently stayed off" problem. For anything that genuinely can't be expressed as a config option — a source patch, for example — I'd carry it as a `.patch` in `SRC_URI` in the bbappend rather than editing the recipe, and keep patches small and rebased against each vendor kernel version.

I'd also think about where the fragment lives: board-specific fragments in a machine or board layer, SoC-family fragments in a shared layer, so a product family with several boards can share the common ones and only the deltas live per-board. And I'd document the fragment's intent in the layer README so the next person knows why each option is there and can prune it when the vendor catches up.

**Possible follow-ups:** How would you handle a config option that depends on another option being enabled first? What's your approach when a vendor kernel update changes a Kconfig symbol name your fragment references?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never contend for a lock or a resource that the best-effort path can hold, so the design has to physically separate the two access paths rather than just prioritize them. I'd start by asking what "hard real-time" means here in concrete terms — a deadline in microseconds or milliseconds, and whether the real-time consumer is in kernel space, a `SCHED_FIFO` userspace thread, or a separate core. That determines whether I can use a spinlock-protected fast path or need something stronger like a lock-free ring buffer between producer and consumer.

For the shared hardware, the cleanest structure is a single owner of the device — usually the driver — with two distinct interfaces. The real-time path gets a dedicated, pre-allocated buffer and a code path that takes only a short spinlock (or no lock at all, using per-CPU or single-producer/single-consumer ring buffers) and never sleeps, never allocates, and never waits on the logging side. The logging path reads from a separate snapshot or ring buffer that the real-time path publishes into, so logging latency is decoupled: if the logger is slow, it drops or overwrites old entries rather than back-pressuring the real-time producer. I'd make the buffer sizes and drop policy explicit and observable, because silent data loss in a medical context is itself a problem.

I'd also look at whether the two consumers can be split across cores or across a mailbox to a microcontroller, which removes the contention entirely. And I'd be careful about interrupt context: if the real-time access happens in an interrupt handler or a threaded IRQ at high priority, the logging work must be pushed to a workqueue or a lower-priority thread so it can't preempt the real-time path. Finally, I'd validate with latency measurements — `cyclictest`-style or ftrace `irqsoff`/`preemptoff` traces — to prove the logging path doesn't introduce jitter into the real-time path, and I'd test under worst-case logging load, not just nominal.

**Possible follow-ups:** What locking primitive would you avoid in the real-time path and why? How would you detect at runtime that the logging path is starting to affect real-time latency?

## Q4: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?

**Answer:** `EINTR` means a blocking syscall was interrupted by a signal that the process had a handler for (or that wasn't blocked/ignored), so the first question is "what signal, and where is it coming from?" — because "nothing is intentionally sending signals" usually means something is sending them unintentionally. I'd start by identifying the signal: `strace -f -e trace=signal` on the daemon, or checking `/proc/<pid>/status` for pending/blocked signals, and looking at whether the daemon installs handlers for signals like `SIGCHLD`, `SIGALRM`, `SIGIO`, or `SIGUSR*`. A very common culprit is `SIGCHLD` from a child process (the daemon forks something, or a helper does), or `SIGIO`/`SIGURG` from async I/O or socket activity, or a timer signal. If the daemon has a handler for it, any blocking `ioctl` in progress gets interrupted.

Once I know the signal, there are two layers to fix. On the daemon side, the correct pattern is to retry on `EINTR` — a blocking `ioctl` that returns `EINTR` should be retried in a loop unless the application has a reason to abort, and the code should distinguish "interrupted, retry" from a real error. That's the robust fix regardless of source. On the source side, I'd figure out why the signal is arriving: if it's `SIGCHLD` from a child the daemon doesn't actually need to wait on, setting `SA_NOCLDWAIT` or `SIG_IGN` for `SIGCHLD` (carefully, if it doesn't need child status) removes the interruption. If it's a timer or async notification, I'd check whether the handler is doing something that could be moved out of the signal path.

I'd also consider whether the driver's `ioctl` is the right interface at all — a blocking `ioctl` that can be interrupted is fine, but if the daemon is doing long waits, a `poll()`/`read()` model with proper `EINTR` handling is often cleaner. And I'd check for a subtler cause: a signal delivered because of a resource limit or a `SIGPIPE` from a closed pipe/socket the daemon writes to. The key discipline is that the daemon must treat `EINTR` as "retry," not "fatal," and the investigation should find the signal source so the retries aren't masking a real problem.

**Possible follow-ups:** How would you distinguish `EINTR` caused by a signal handler from `EINTR` caused by a `ptrace`-style stop? What's the risk of just wrapping every `ioctl` in a retry loop without finding the signal source?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams are right about their constraints. The hardware team needs the pins; the software team is protecting a manufacturing dependency that, if broken, shows up as "boards that won't talk on the line," which is expensive and hard to diagnose late. My first step would be to get the actual constraints on the table in one place: which pins the new peripheral needs, whether the debug UART can move to an alternate pinmux group that's still accessible, and exactly what the manufacturing line depends on — is it the UART specifically, or any early console, and at what stage of boot?

Then I'd look for a path that satisfies both. Options I'd evaluate: (1) move the UART to an alternate pinmux that the SoC supports, updating the device tree and bootloader pinmux tables together so early console and Linux console stay consistent; (2) keep the UART where it is and find the new peripheral's pins elsewhere, if the hardware team has flexibility; (3) if the move is unavoidable, stage it — update bootloader and device tree in the same change, verify early console on a bench unit, and coordinate with manufacturing so the line's test procedure and fixtures are updated in lockstep rather than discovering the break at production. I'd want the change to be a single coordinated commit set, not a hardware change that lands before software catches up.

I'd also make the risk explicit and owned: document what breaks if the pinmux and bootloader aren't updated together, add a boot-time check or a manufacturing test that exercises the console path, and agree on a verification gate before the change is accepted. If there's schedule pressure, I'd propose a fallback — keep the current UART for the current build and land the pinmux move behind a board revision or a build variant — so manufacturing isn't exposed while the change is validated. The through-line is that I'd refuse to let either team unilaterally "win"; I'd drive to a documented decision with the manufacturing dependency treated as a hard requirement, not an inconvenience.

**Possible follow-ups:** How would you verify the early boot console still works before the change reaches the manufacturing line? What would you do if the hardware team says the pin move is non-negotiable and there's no alternate pinmux for the UART?
