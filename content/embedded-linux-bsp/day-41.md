## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of two identical I2C sensors on the same bus, while the other works fine?
**Answer:** I'd start by confirming the problem is at the kernel level rather than the application level. First, I'd check whether the sensor is actually present on the bus using `i2cdetect` from userspace — if it shows up there, the issue is likely in the device tree binding or driver probe logic. If it doesn't show up, I'd move to hardware verification. Since the two sensors are identical, I'd compare their device tree entries carefully — a common mistake is an incorrect `reg` address, a wrong interrupt line, or a missing `status = "okay"` property. I'd also verify the sensor's address lines are strapped correctly on the PCB, since identical parts can have different I2C addresses depending on hardware configuration. Next, I'd check the kernel log for probe failures — sometimes the driver probes but fails during initialization due to a reset GPIO that isn't wired correctly, or a power supply rail that isn't enabled. I'd also look at whether the second sensor shares an interrupt line with another device; if the IRQ is already claimed, the driver may fail to probe. If the hardware checks out, I'd add debug prints or use `devicetree` overlays to test the sensor independently. Finally, I'd verify the driver itself isn't assuming a single instance — some drivers have global state that breaks when multiple instances are present.

**Possible follow-ups:** How would you distinguish between a device tree issue and a driver issue in this scenario? What if the sensor is detected by `i2cdetect` but the driver still fails to bind?

## Q2: How would you approach designing a kernel driver for a device that needs to be accessed by both a real-time safety-critical task and a non-real-time monitoring task, where the safety-critical task must never be blocked by the monitoring task?
**Answer:** The core principle is that the safety-critical path must have guaranteed access to the hardware without depending on locks or resources that the monitoring task could hold. I'd start by identifying what the safety-critical task actually needs — typically a small, bounded set of operations like reading a sensor value or setting an actuator state. The driver should expose two distinct interfaces: a lightweight, lock-free or spinlock-only path for the real-time task, and a more feature-rich interface for the monitoring task. For the real-time path, I'd avoid sleeping locks entirely — no mutexes, no wait queues, no operations that could block on I/O. If the hardware requires a register read-modify-write sequence, I'd use a spinlock with interrupts disabled for the critical section, keeping it short and bounded. The monitoring task can use the same hardware but through a separate interface that takes a mutex and may sleep. To prevent priority inversion, I'd ensure the monitoring path never holds the spinlock while doing anything that could block. If both tasks need to access the same hardware registers, I'd consider using a seqlock or a per-device state machine where the real-time task always has priority. In a medical device context, I'd also document the worst-case latency and ensure the real-time task's deadline is met even under contention. If the hardware allows, I'd consider dedicating a separate register bank or a shadow register set for the real-time path to eliminate contention entirely.

**Possible follow-ups:** How would you handle the case where the monitoring task needs to reconfigure the device in a way that could affect the safety-critical path? What if the hardware requires a multi-step transaction that can't be done atomically?

## Q3: How would you approach implementing a kernel driver for a device that needs to perform a hardware-triggered DMA transfer, where the trigger comes from an external sensor's interrupt line, and the data must be processed and made available to userspace within a hard real-time deadline (e.g., 2 ms)?
**Answer:** The key is to minimize latency at every stage of the pipeline. I'd structure the driver so that the interrupt handler does the absolute minimum work — just acknowledging the interrupt and triggering the DMA transfer. The DMA completion interrupt would then wake a kernel thread or use a workqueue to process the data, but for a 2 ms deadline, I'd need to be careful about scheduling latency. A better approach might be to use a dedicated kernel thread with a real-time scheduling policy (SCHED_FIFO) that blocks on a wait queue, so it's ready to run the moment the DMA completes. For the DMA setup, I'd pre-allocate and prepare the DMA buffers at probe time to avoid any allocation in the hot path. The DMA descriptor should be set up in advance, so the interrupt handler only needs to write a few registers to start the transfer. For the data processing, I'd keep it minimal — perhaps just a checksum or a format conversion — and then copy the data to a pre-allocated userspace buffer using `dma_mmap_coherent` or a ring buffer that userspace can read without a copy. If the processing is more complex, I'd consider doing it in userspace with a real-time scheduling policy, using a shared memory region mapped from the driver. I'd also need to consider cache coherency — using `dma_alloc_coherent` avoids cache maintenance issues but may have higher latency for small transfers. Finally, I'd measure the actual latency distribution under load, not just the average, to ensure the worst case meets the 2 ms deadline.

**Possible follow-ups:** How would you handle the case where the DMA transfer size varies between interrupts? What if the sensor generates interrupts faster than the processing can keep up — how would you detect and handle overrun?

## Q4: How would you approach debugging a situation where a custom board running Linux boots successfully, but the system clock is running roughly twice as fast as expected, and the RTC itself keeps correct time when read directly?
**Answer:** This sounds like a clock source or timer configuration issue rather than an RTC problem. Since the RTC reads correctly, the hardware clock itself is fine — the issue is in how the kernel derives its system time from the timer hardware. I'd start by checking which clock source the kernel is using: `cat /sys/devices/system/clocksource/clocksource0/current_clocksource`. If it's using a timer that's being clocked at a different frequency than expected, the system time will drift proportionally. A common cause is a mismatched timer frequency in the device tree — for example, the timer's clock-frequency property might be set to half the actual rate, causing the kernel to count twice as fast. I'd verify the timer's input clock against the schematic and the SoC reference manual. Another possibility is that the kernel is using the wrong timer entirely — perhaps a 32 kHz RTC timer is being used as the system clock source when it should be a higher-frequency timer. I'd also check the boot log for any clock-related warnings or errors. If the device tree looks correct, I'd verify the actual clock frequency using a scope or by reading the timer's control registers. In some cases, the issue is a missing or incorrect `assigned-clock-rates` property for the timer's parent clock. I'd also check whether the kernel's `CONFIG_HZ` setting or the `clocksource` rating is causing the kernel to prefer a different timer than intended. Finally, I'd compare the timer configuration against the vendor's reference BSP if one exists.

**Possible follow-ups:** How would you verify the actual timer frequency on the hardware? What if the clock source is correct but the time is still wrong — what else could cause this?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the hardware team reveals that they need to change the main processor's boot mode strap resistors to accommodate a new flash part. The change means the processor will boot from a different interface (e.g., from SPI NOR to eMMC), and the bootloader and kernel configurations are already tuned for the current boot source. The project is six weeks from the start of a clinical trial. How would you handle this situation?
**Answer:** My first step would be to understand the full scope of the change — not just the boot interface swap, but what it means for the entire boot chain. I'd call an immediate meeting with the hardware team, the bootloader engineer, and the kernel engineer to map out the impact. The key questions are: Does the new boot source change the bootloader's expected partition layout? Does it affect the kernel's root device specification? Are there any timing or voltage differences that could affect early boot? Once I have that picture, I'd assess what can be reused and what needs to change. The bootloader will likely need modifications to support the new flash interface — this could be as simple as enabling a different driver in U-Boot config, or as complex as writing a new board initialization sequence. I'd also check whether the new eMMC part requires any special initialization that the current bootloader doesn't perform. For the kernel, the main changes are likely in the device tree — the root device, the boot arguments, and possibly the storage driver configuration. I'd prioritize getting a minimal boot working first — just U-Boot to kernel to a shell — before worrying about the full application stack. I'd also set up a risk mitigation plan: if the new boot path can't be validated in time, can we fall back to the original flash part for the clinical trial? That might mean keeping the old boot configuration as a backup or ensuring the bootloader can support both interfaces. I'd communicate the risks and the mitigation plan to the project manager early, rather than waiting until the deadline approaches. Finally, I'd make sure we have a clear testing plan — boot stress tests, power cycle tests, and verification that the clinical application runs correctly on the new boot path.

**Possible follow-ups:** How would you prioritize the work if the team is already at capacity? What specific tests would you require before signing off on the new boot configuration for the clinical trial?
