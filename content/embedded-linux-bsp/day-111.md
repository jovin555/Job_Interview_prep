# embedded-linux-bsp — Day 111

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success from `probe()` is one of the trickier failure modes because the kernel has no reason to complain — the driver claimed the device and moved on. My first instinct is to question whether `probe()` is actually doing the work I think it is. A common cause is that the driver binds to the device tree node but never actually touches the hardware: the register base address from `platform_get_resource()` or `devm_ioremap_resource()` may be wrong (wrong `reg` in the DT, or a translation issue), so every subsequent read/write goes to a region that reads back as zeros or is silently ignored. I'd add temporary `dev_info()` prints of the mapped physical and virtual addresses and read back a known register (an ID or version register) to confirm the mapping is live.

Second, I'd check whether the driver is actually the one being bound. If two drivers match the same compatible string, or a generic fallback driver claims the node first, `probe()` may be running in a driver that doesn't do what I expect. `ls /sys/bus/platform/drivers/*/` and the `driver` symlink under the device's sysfs entry confirm which driver bound.

Third, I'd verify the clocks and resets. A peripheral whose clock gate is never enabled will accept register writes but the internal logic never runs — reads return stale or zero data, no bus error, no timeout. Checking `clk_prepare_enable()` return values and reading back the clock enable status register catches this. Same story for a reset line held asserted, or a power domain that was never turned on.

Finally, I'd confirm the interrupt actually fires: if the device is interrupt-driven and the IRQ never arrives (wrong trigger type, shared line not wired, or the peripheral's interrupt mask never cleared), the driver sits idle with no error. Instrumenting the ISR with a counter, or checking `/proc/interrupts` for the line's count incrementing, tells me quickly whether the problem is upstream (no interrupt) or downstream (interrupt fires but handler logic is wrong).

**Possible follow-ups:** How would you distinguish between a clock that's gated and a register map that's wrong, using only software-visible symptoms? What would you check in the device tree if the driver binds but the register reads return all-ones instead of all-zeros?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our deltas on top, so that when the vendor ships a kernel update we rebase our changes rather than merge a fork. The mechanism I'd use is a `.bbappend` in our own layer that adds a config fragment via `SRC_URI` with the `file://` and `apply=yes` conventions, plus `KERNEL_CONFIG_FRAGMENTS` or the `cfg` file mechanism depending on the kernel class in use. The fragment itself is a small file containing only the `CONFIG_*` lines we need to change — not a full defconfig — so it composes with whatever the vendor's base config is.

The important discipline is that the fragment must be *additive and minimal*. If we need `CONFIG_SPI_MYDEVICE=y`, the fragment says exactly that and nothing else. If we need to *disable* something the vendor enabled, we set `# CONFIG_FOO is not set` explicitly, because a fragment that simply omits a symbol won't turn it off. I'd also make sure the fragment is validated in CI: run `bitbake -c kernel_configcheck` (or the equivalent `do_configcheck` task) so that any symbol that didn't take effect — because a dependency wasn't met or the symbol was renamed — shows up as a warning rather than silently disappearing.

For maintainability across kernel version bumps, I'd keep the fragment in a version-agnostic location and document which kernel version each symbol was verified against. When the vendor bumps the kernel, the configcheck output tells us which symbols moved or were renamed, and we update the fragment in one place. The `.bbappend` itself should be scoped to the vendor's recipe name and, if necessary, a version wildcard (`_%`), so it applies to the vendor's updates without us editing it each time.

**Possible follow-ups:** What's the difference between a config fragment and a full defconfig in terms of how they compose, and when would you reach for each? How would you catch a fragment symbol that silently fails to apply because of a missing dependency?

## Q3: How would you approach debugging a situation where a custom board running Linux boots successfully, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts?

**Answer:** `EINTR` means a blocking system call was interrupted by a signal before it completed. The daemon isn't sending itself signals deliberately, so the question is: who is, and why is the daemon treating it as fatal? The first thing I'd establish is whether the signal is arriving from outside the process or being generated internally. `strace -f -e trace=signal,ioctl` on the daemon shows both the signal delivery and the interrupted `ioctl`, and the `siginfo` tells me the source — a `SIGCHLD` from a child, a `SIGALRM` from a timer, a `SIGUSR1` from a watchdog or supervisor, or a `SIGPIPE`/`SIGIO` from a socket or async I/O setup.

A very common culprit in embedded daemons is a `SIGCHLD` arriving because the process (or a library it uses) forks — for example, a `system()` call, a `popen()`, or a helper that shells out. If `SIGCHLD` isn't blocked or handled, it interrupts any blocking call in flight. Another frequent one is `SIGIO`/`SIGPOLL` if the driver or a socket was set up for async notification, or a `SIGALRM` from an interval timer used for housekeeping.

The fix has two parts. First, the daemon should be robust: any blocking `ioctl` (or `read`/`write`/`select`) must be wrapped in a retry loop that treats `EINTR` as "try again," not "abort." That's the correct POSIX behavior and it's a bug in the daemon if it doesn't. Second, if a particular signal is expected and handled, it should be blocked around critical sections with `sigprocmask`/`pthread_sigmask` so it can't interrupt a call that must complete atomically. I'd also check whether the driver's `ioctl` handler is itself returning `-ERESTARTSYS` correctly for interruptible waits — if it returns a raw error instead, the retry semantics break.

**Possible follow-ups:** What's the difference between `-ERESTARTSYS` and `-EINTR` from a driver's perspective, and how does the kernel decide whether to restart the syscall automatically? How would you make a driver's blocking `ioctl` wait uninterruptible versus interruptible, and what are the trade-offs?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path holds, so the design has to decouple them rather than serialize them behind a single mutex. The cleanest pattern is to give the real-time path a lock-free or minimally-contended fast path and hand data to the logging path through a buffer that the real-time side only ever *writes* to, never waits on.

Concretely, I'd structure it as a producer/consumer with a lock-free ring buffer (or a `kfifo` if the access pattern fits). The real-time task — whether it's an interrupt handler, a high-priority `SCHED_FIFO` kthread, or a hardware-triggered DMA completion — writes samples into the ring and returns immediately. The logging task drains the ring at its own pace. If the ring fills because logging falls behind, the real-time side must have a defined, non-blocking policy: drop oldest, drop newest, or overwrite, chosen based on whether losing a sample is acceptable. It must never spin waiting for space.

For the shared hardware register access itself, I'd avoid a coarse mutex. If both paths genuinely need to touch the same registers, I'd use a spinlock held only for the duration of a register read/write (microseconds), never across a wait or a copy to userspace. Better still, I'd structure the hardware access so the real-time path owns the data registers and the logging path only reads from the software ring, so they never contend on hardware at all.

I'd also be explicit about the real-time task's priority and isolation: pin it to a CPU if the platform allows, keep the logging kthread at normal priority, and make sure the logging path's userspace copy (`copy_to_user`) happens outside any lock the real-time path could touch. The invariant to state in review is: "the real-time path's worst-case latency is bounded by a single register access plus a ring write, and is independent of logging throughput."

**Possible follow-ups:** How would you size the ring buffer, and what would you monitor to know it's too small? What happens to your design if the logging task must also *write* configuration to the same device the real-time task reads from?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams have legitimate concerns and the real question is how to sequence the change so nothing breaks silently. The first thing I'd do is get the facts on the table in one place: exactly which pins move, what the new peripheral needs, and — critically — who and what depends on the current debug UART. The manufacturing line dependency is the one I'd want to understand precisely, because "the line relies on it" could mean anything from a human watching a console to an automated test fixture parsing boot output, and those have very different tolerance for change.

Next I'd separate the change into stages so the risk is contained. The pinmux change touches three places — the bootloader's early pin setup, the device tree's pinctrl node, and any board-specific console configuration — and I'd want to change them together in a branch and validate on a bench board before anything reaches the line. I'd also want a fallback: if the new pinmux group can coexist with the old one during a transition (even if only one is active at a time), we can validate the new path while keeping the old one recoverable.

On the process side, I'd bring the manufacturing representative into the review rather than negotiating through the software team, because they can tell us what a safe cutover looks like — a parallel build, a re-qualification window, a documented change notice. I'd propose a concrete plan: bench validation of the new pinmux, a manufacturing dry run on a small batch, and a defined rollback if the console output changes in a way the line can't tolerate. The message to both teams is that we're not choosing between the new peripheral and the line — we're sequencing so the line never sees an unvalidated change. If the schedule genuinely can't absorb that sequencing, that's a decision for the project lead with the risk stated explicitly, not something I'd quietly absorb by skipping validation.

**Possible follow-ups:** How would you decide whether the bootloader and kernel pinmux changes can be validated independently, or whether they must land together? If manufacturing says they can't tolerate any console change during the trial window, what options would you put in front of the project lead?
