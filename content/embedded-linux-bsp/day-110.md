# embedded-linux-bsp — Day 110

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder classes of bug because the kernel is telling you everything is fine, so the first move is to distrust the success and verify each assumption the driver makes independently. I'd start by confirming the driver is actually talking to the hardware it thinks it is: dump the device tree node the driver bound to (`/sys/firmware/devicetree/base/...` or `of_node` debugfs) and compare the `reg` address, interrupt specifier, and any `compatible`-specific properties against the schematic and the SoC reference manual. A common cause is a correct-looking probe that maps the wrong register base or an offset that's off by a bank, so every read returns a plausible-but-wrong value and the driver happily initializes against garbage.

Next I'd instrument the driver itself — add `dev_dbg`/`dev_info` around every register read/write in probe and in the first real access path, and enable dynamic debug (`dyndbg`) so I can turn it on without rebuilding. If the driver reads a chip-ID register, I'd log the raw value and compare it to the datasheet's expected ID; a mismatch there immediately tells me the bus, address, or pinmux is wrong even though probe "succeeded." I'd also check whether the driver is actually being exercised after probe — a device that probes but is never opened by userspace will look silent, so I'd verify the character device or sysfs entry exists and manually trigger a read.

On the hardware side, I'd reach for a scope or logic analyzer on the bus (I2C/SPI) during probe to confirm transactions are physically happening and being acknowledged. If the driver claims success but there's no activity on the wires, the problem is above the bus — clock not enabled, reset line held, or the peripheral's power rail not up. I'd cross-check the clock and regulator state in `clk_summary` and `regulator_summary` in debugfs. Finally, I'd check for a silent resource conflict: two drivers claiming overlapping register ranges, or a pinmux that routes the peripheral's pins to a different function so the SoC's internal peripheral is isolated from the external part. The systematic approach is: verify binding, verify register access, verify bus activity, verify clocks/power/pinmux — in that order, because each layer's "success" can mask the layer below being wrong.

**Possible follow-ups:** How would you tell the difference between a driver bug and a hardware/pinmux problem without a scope? What would you check first if the chip-ID register read back all zeros versus all 0xFF?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our deltas on top, so that when the vendor bumps their kernel we rebase a small, well-defined set of changes rather than re-merging a fork. I'd structure it with a clear separation: a `meta-<product>` layer that depends on the vendor BSP layer, and within it a `.bbappend` on the vendor's kernel recipe rather than a copy of the recipe.

For configuration specifically, I'd use kernel config fragments rather than editing a defconfig. Yocto's `kernel-yocto` class supports `SRC_URI` entries of the form `file://my-board.cfg`, and the fragments get merged in order via `merge_config.sh`. The `.bbappend` adds the fragment to `SRC_URI` and, if needed, sets `KERNEL_CONFIG_FRAGMENTS` or relies on the fragment mechanism directly. The key discipline is that each fragment should be minimal and single-purpose — one for enabling a peripheral driver, one for a security hardening option, one for a debugging option — so they're reviewable and can be enabled/disabled per image or per machine. I'd also add a `do_configure` sanity check or a `kernel_configcheck` step so a fragment that fails to apply (because the option was renamed upstream) fails the build loudly instead of silently dropping.

For machine-specific config, I'd tie fragments to the machine via `MACHINEOVERRIDES` so a multi-board product family shares one kernel recipe but each machine pulls its own fragment set. If the vendor recipe doesn't use `kernel-yocto` (some vendor kernels use a plain `do_configure` with a defconfig), I'd still avoid forking: append to `do_configure:append` to run `merge_config.sh` against the generated `.config`, or use `KERNEL_CONFIG_FRAGMENTS` if the class supports it. The trade-off to call out is that fragments are clean but can silently no-op if an option name changes across kernel versions, so I'd pair them with a config audit in CI that diffs the final `.config` against expectations.

**Possible follow-ups:** What happens if two fragments set the same option to conflicting values, and how does the merge order resolve it? How would you catch a fragment that silently stopped applying after a kernel version bump?

## Q3: How would you approach debugging a kernel panic that occurs only on every third or fourth boot, with no consistent trigger?

**Answer:** Intermittent boot panics are almost always a race, an uninitialized-state dependency, or a hardware timing margin issue, so the first job is to capture the panic reliably rather than chase it blind. I'd enable persistent storage of the kernel log across reboots — `pstore`/`ramoops` backed by a reserved memory region, or a serial console captured to a host — so that when the panic happens I have the actual oops text, register dump, and call trace instead of a blank screen. Without the trace, everything else is guessing.

Once I have traces from several failures, I'd look for patterns: is the faulting function always in the same subsystem (e.g., a driver's probe, or the memory allocator during early init)? Is it a NULL dereference, a use-after-free, or a data abort at a specific address? A fault address that looks like a device register offset suggests a driver touching hardware before its clock/power is up; a fault in slab code suggests memory corruption from an earlier driver. I'd enable `CONFIG_DEBUG_KMEMLEAK`, `KASAN` (if the SoC/perf budget allows on a debug build), and lockdep to catch ordering and lifetime bugs that only manifest under specific boot timing.

Because it's every third or fourth boot, I'd suspect timing: boot is a race between driver probe ordering, deferred probes, async probing, and hardware power-up sequencing. I'd check whether the kernel is using `async_synchronize_full` behavior or `-EPROBE_DEFER` loops that resolve differently depending on timing, and whether the panic correlates with a particular device being slow to come up. I'd also look at the bootloader side — is the bootloader leaving a peripheral in a state the kernel doesn't expect on some boots (e.g., a watchdog or DMA engine still armed from a previous boot)? Adding a known-good reset/cleanup in the bootloader or early kernel can mask or confirm that.

For hardware, intermittent boot failures can be power-rail sequencing or marginal timing on the boot medium (eMMC/SPI). I'd instrument boot time with `initcall_debug` and `bootgraph` to see where time varies between boots, and check supply ramp and reset timing on a scope if the software evidence points at a specific device. The discipline is: capture the trace, classify the fault, then bisect the timing window — not to "try things" until it stops happening.

**Possible follow-ups:** How would you use `initcall_debug` output to narrow down which driver is involved? What's the risk of "fixing" an intermittent panic by adding a delay, and how would you validate a real fix instead?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never block on anything the logging path controls, so the design has to decouple them at the data-structure level rather than relying on scheduling priority alone. I'd structure the driver so the real-time access path (typically an interrupt handler or a high-priority threaded IRQ) does the minimum: read the hardware, timestamp, and push the sample into a lock-free or carefully-bounded ring buffer. The logging path consumes from that buffer at its own pace. The real-time producer never takes a mutex the logger holds, never waits for the logger to drain, and never allocates memory.

For the shared buffer, I'd use a single-producer/single-consumer ring with atomic head/tail indices and memory barriers, sized so that under worst-case logging latency the buffer can't overflow — and if it does, the policy is to drop oldest or newest samples in a way that's defined and logged, never to stall the producer. If the hardware itself is shared (e.g., a single register set the logger also wants to read for diagnostics), I'd serialize only the hardware access with a spinlock held for the shortest possible critical section, and make sure the logger's access is non-blocking (trylock with a fallback to skip) so it can never hold the lock while the real-time path needs it.

For the userspace interface, I'd expose the real-time data via a mechanism that doesn't require the logger to be scheduled to make progress — e.g., a `mmap`'d ring buffer or a `read()` on a character device backed by the ring, with `O_NONBLOCK` semantics for the logger. The real-time consumer in userspace would be a `SCHED_FIFO` thread pinned to a core, and I'd verify with `cyclictest`-style measurement that its worst-case latency is unaffected when the logger is hammering the device. The key interview point is that priority inversion is prevented structurally — the logger can be starved or delayed arbitrarily without the real-time path noticing — rather than by hoping the scheduler orders them correctly.

**Possible follow-ups:** What happens if the ring buffer overflows, and how do you decide the drop policy? How would you prove the real-time path's worst-case latency is bounded when the logger is active?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a cross-team risk-and-trade-off decision rather than a software-vs-hardware argument, and my job as BSP lead is to make the cost and risk visible so the right people can decide with full information. First I'd get the facts straight: exactly which pins move, whether the new pinmux group is electrically equivalent (drive strength, pull configuration, voltage domain), and whether the debug UART is truly the only thing affected or whether the change ripples into other peripherals sharing that pinmux controller. I'd also confirm why the manufacturing line depends on the early console — is it a test fixture that parses boot output, a human operator watching for boot progress, or a scripted check — because that determines how much of the dependency is hard versus habitual.

Then I'd quantify the software impact honestly: the device tree pinmux node, the bootloader's early console setup (which often configures the UART before the kernel's pinctrl driver is up), and any test scripts or fixtures that assume the current console. I'd propose options rather than a yes/no: (a) move the UART and update both bootloader and device tree in a coordinated change, with the manufacturing fixture updated in the same release; (b) keep the debug UART where it is and find the new peripheral's pins elsewhere; (c) move the UART but provide a transitional path — e.g., keep the old console available via a second UART or a bootloader-selectable console — so manufacturing isn't cut over cold. I'd bring the manufacturing/test owner into the conversation early, because they own the risk of a broken line and should co-sign the plan.

Finally I'd frame the decision in terms of the project's stage and regulatory context: if we're close to a clinical trial or design freeze, a pinmux change that touches the boot path and manufacturing fixtures carries schedule and validation cost that has to be weighed against the new peripheral's benefit. I'd document the decision and the rationale in the design record, assign owners for the bootloader, device tree, and fixture changes, and define a verification step — boot the new image on a representative board and confirm the manufacturing fixture still passes — before declaring it done. The leadership behavior is to keep it collaborative, surface the hidden dependencies, and make sure the people who own the downstream risk are in the room.

**Possible follow-ups:** If manufacturing can't update their fixture in time, what transitional options would you propose? How would you verify the new pinmux didn't break anything else on that controller before the change ships?
