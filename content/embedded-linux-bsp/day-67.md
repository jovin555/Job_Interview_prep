# embedded-linux-bsp — Day 67

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is deferred indefinitely because a supplier it depends on never becomes available — with no obvious error in the kernel log?

**Answer:** Deferred probe is one of the more subtle failure modes because the kernel treats it as a normal, expected condition rather than an error — so nothing gets logged at `pr_err` level by default. The first thing I'd do is confirm that deferral is actually what's happening rather than a silent failure. The kernel exposes this directly: `/sys/kernel/debug/devices_deferred` lists every device currently sitting in the deferred-probe state, and enabling `initcall_debug` or dynamic debug on the driver core (`dyndbg="file drivers/base/dd.c +p"`) will print the reason each probe returns `-EPROBE_DEFER`. That tells me which supplier the driver is waiting on.

Once I know the supplier, the question becomes *why* that supplier never registers. Common causes: the supplier's own device tree node is missing or has a bad `status` property; the supplier driver is not enabled in the kernel config; the supplier is on a bus that itself hasn't probed yet (a classic chain — sensor waits on I2C controller, I2C controller waits on pinctrl, pinctrl waits on clock); or the supplier is a regulator/clock referenced by a `phandle` that doesn't resolve because of a typo or a missing `#clock-cells`. I'd walk the dependency chain from the deferred device upward, checking each node's `status`, its `compatible` string against the driver's match table, and whether the referenced providers are present in the compiled DTB (`dtc -I dtb -O dts` on the deployed blob, not the source — they can diverge).

If the chain looks correct but the supplier still never probes, I'd check whether the supplier driver is built as a module that never gets loaded, or whether it's waiting on a resource that will never arrive (e.g., a GPIO that's muxed to a conflicting function). The fix is usually one of: correcting the device tree dependency, enabling the missing driver, or — if the dependency is genuinely optional — making the consumer tolerate its absence rather than deferring forever. I'd also add a bounded retry or a timeout-based warning in the consumer driver so this class of bug surfaces loudly in the field instead of silently disabling a peripheral.

**Possible follow-ups:**
- How would you distinguish a genuine deferred probe from a driver that simply never matched the device tree node?
- If the supplier is a regulator that's expected to be always-on, how would you confirm the regulator framework is actually registering it?

## Q2: You're structuring a Yocto BSP for a product family where several boards share a common SoC and vendor BSP but differ in peripherals, device tree, and userspace packages. How would you organize the layers and recipes?

**Answer:** The guiding principle is to separate what's common from what varies, and to make the varying parts additive rather than forked. I'd start with the vendor's BSP layer untouched — never modify it in place, because that makes every future vendor update a merge conflict. On top of that I'd add a `meta-<product>-common` layer holding everything shared across the family: the SoC machine configuration, the common kernel recipe append, shared userspace packages, and the base image recipe. Then a thin `meta-<product>-<board>` layer per board, containing only that board's device tree, its machine override, and any board-specific packages or kernel config fragments.

The mechanism that makes this clean is `bbappend` files scoped by machine override. A board-specific kernel config fragment goes into a `.bbappend` on the kernel recipe with `SRC_URI:append:<machine> = " file://board-fragment.cfg"`, and the fragment is applied through the kernel's config fragment mechanism rather than by editing `defconfig`. Device trees are handled the same way — each board layer ships its own `.dts` and the machine config points `KERNEL_DEVICETREE` at it. Userspace differences are expressed as `IMAGE_INSTALL:append:<machine>` in the image recipe, so the common image stays common and each board adds only what it needs.

For the layer priority and `bblayers.conf` ordering, I'd keep the vendor layer lowest and the board layers highest, so overrides resolve predictably. The payoff is that adding a new board in the family means creating one small layer with a device tree and a machine conf — no touching of shared recipes, no forking, and vendor BSP updates apply cleanly to the whole family.

**Possible follow-ups:**
- How would you handle a board that needs a different kernel version from the rest of the family?
- What's your approach to keeping the common layer's image recipe from accumulating board-specific conditionals over time?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path controls, so the design has to decouple them completely. I'd start by identifying what "real-time access" actually means here — is it a register read/write with a hard deadline, or a data transfer? That determines the mechanism. For a register-level access, the real-time task should be able to touch the hardware without taking any lock the logging task can hold for an unbounded time. That usually means a lock-free or very short critical section on the real-time side, and pushing all the slow work — formatting, copying to a buffer, writing to a file — onto the logging side.

The standard pattern is a producer/consumer split with a lock-free ring buffer. The real-time path writes samples into the ring buffer with a single atomic index update and no blocking; the logging task drains the buffer at its own pace. If the buffer fills because logging falls behind, the real-time path must have a defined policy — either drop the oldest sample (acceptable for logging) or overwrite, but never wait. The key is that the real-time path's worst-case execution time is bounded by the buffer write, not by anything the logging task does.

For the hardware access itself, if both tasks genuinely need to touch the same registers, I'd serialize with a spinlock held only for the register access, never across a copy or a sleep. The logging task must not hold that lock while doing I/O. If the hardware supports it, I'd give the real-time task a dedicated path — a separate register bank, a DMA channel, or a hardware FIFO — so the two never contend at all. Where the hardware forces sharing, I'd document the contention and measure the real-time path's worst-case latency under logging load to prove the deadline holds. The design principle throughout: the real-time task's timing must be independent of the logging task's behavior, and that has to be verifiable, not just assumed.

**Possible follow-ups:**
- How would you verify that the real-time path's worst-case latency is actually bounded under heavy logging load?
- If the hardware only exposes one register set, what options do you have to avoid priority inversion between the two tasks?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** Intermittent fallback to network boot almost always means the primary boot path is failing *sometimes* and U-Boot's boot sequence is moving on to the next candidate in `bootcmd` or the boot order. So the first job is to find out what's failing on the eMMC path and why it's intermittent, not to just disable network boot — disabling it would mask a real reliability problem.

I'd start by capturing the full U-Boot console output on a failing boot versus a successful one. The difference usually points at the cause: an eMMC initialization timeout, a `mmc` device that isn't detected on that boot, a filesystem read error, or a corrupted environment variable. If the eMMC sometimes doesn't enumerate, that points at a hardware or timing issue — power sequencing, clock stability, or a marginal reset — rather than a software bug. If the eMMC enumerates but the boot script fails, I'd check whether the environment is being loaded from the right device and whether a stale or partially-written environment is causing the boot target to change.

I'd also look at the boot order configuration itself. U-Boot's `boot_targets` or the `bootcmd` chain determines the fallback sequence, and if network is in that list, any primary failure will fall through to it. The right fix depends on the root cause: if eMMC is genuinely unreliable, that's a hardware or driver issue to fix; if the fallback is simply too permissive, I'd tighten the boot order so a primary failure halts or retries rather than silently switching to an unintended path. For a medical device, silent fallback to network boot is a serious concern — it could mean booting unintended firmware — so I'd also want the bootloader to fail loudly and predictably rather than degrade silently. I'd verify the fix by running many power cycles and confirming the eMMC path succeeds every time, and that a deliberate eMMC failure produces a clear, intended behavior rather than a network boot.

**Possible follow-ups:**
- How would you make the bootloader fail safely rather than fall back, without bricking the device if the primary boot medium genuinely fails?
- What would you check in the eMMC power and clock sequencing if the device only fails to enumerate on cold boots?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** The first thing I'd do is separate the two concerns that are getting tangled: the *technical* question of whether the pinmux change is feasible, and the *process* question of what the manufacturing line actually depends on and when. I'd resist the urge to pick a side in the review — the hardware team has a legitimate need for the pins, and the software team has a legitimate concern about a dependency that's easy to underestimate.

Technically, moving a UART to a different pinmux group is usually straightforward in the device tree, but the risk the software team is flagging is real: the debug UART is often the only visibility you have during early boot, and if it moves, any boot failure before the console is up becomes much harder to diagnose. It's also frequently wired into test fixtures and manufacturing scripts, so "just change the device tree" can ripple into tooling that isn't in the room. I'd ask the manufacturing representative directly what depends on that console — is it a physical connector, an automated test step, a fixture — because that determines whether this is a software change or a line-wide change.

My approach would be to get the facts on the table first: confirm the pinmux change is technically sound, map exactly what depends on the current UART location, and understand the timeline pressure on the new peripheral. Then I'd look for options rather than a binary yes/no — for example, whether the new peripheral can use a different pin, whether the debug console can be preserved on the current pins while the new peripheral takes others, or whether a temporary second console can bridge the transition. If the change is unavoidable, I'd sequence it so the manufacturing dependency is updated and validated before the old pinmux is removed, not after. The goal is to make the decision with full information and a migration plan, rather than letting a design review turn into a hardware-versus-software standoff.

**Possible follow-ups:**
- If manufacturing can't update their fixtures in time, what would you propose as an interim solution?
- How would you make sure a change like this gets captured in the requirements traceability so it doesn't surprise a later reviewer?
