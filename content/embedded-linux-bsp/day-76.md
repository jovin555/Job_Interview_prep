# embedded-linux-bsp — Day 76

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is deferred indefinitely because a supplier it depends on never becomes available — with no obvious error in the kernel log?

**Answer:** `-EPROBE_DEFER` is a cooperative mechanism, not a failure — the kernel silently retries probe later, so the absence of an error message is expected and is exactly why this class of bug is easy to miss. The first step is to confirm the deferral is actually happening rather than assuming it: enable `initcall_debug` on the kernel command line, or add temporary `dev_dbg`/`pr_info` tracing around the `devm_regulator_get`/`devm_clk_get`/`devm_gpiod_get` calls, so you can see the driver being probed and returning `-EPROBE_DEFER` repeatedly. From there, the question is *which* supplier never materializes. Common causes: the supplier's own driver is not enabled in the kernel config, its device tree node is missing or has a bad `compatible` string so it never binds, its node is disabled (`status = "disabled"`), or there is a circular dependency where the supplier itself is waiting on something downstream. I would walk the dependency chain — regulator → clock → GPIO → pinctrl → bus controller — and verify each node is present, enabled, and bound (`/sys/bus/platform/drivers/.../` and `/sys/kernel/debug/devices_deferred` are useful here). If the supplier is genuinely optional, the driver should use the non-fatal `_optional` variants so it can proceed without it. The fix is usually a device tree correction or a config change, not a code change.

**Possible follow-ups:**
- How would you distinguish a genuine circular dependency from a simple missing supplier, and what would you do in the circular case?
- What are the risks of using `-EPROBE_DEFER` too liberally in a driver?

## Q2: You're structuring a Yocto BSP for a product family where several boards share a common SoC and vendor BSP but differ in peripherals, device tree, and userspace packages. How would you organize the layers and recipes?

**Answer:** I would separate concerns into distinct layers rather than branching a single monolithic BSP. A typical structure: a vendor/SoC layer (unmodified, pulled in as-is), a common product-family layer that holds shared recipes, the shared kernel recipe append, and common userspace packages, and then one thin machine layer per board that contains only what differs — the machine `.conf`, the device tree, and any board-specific package additions. The machine configuration is the natural place to express hardware differences: `MACHINE_FEATURES`, `KERNEL_DEVICETREE`, and `PREFERRED_PROVIDER`/`PREFERRED_VERSION` overrides. Peripheral differences that are purely device-tree-level should stay in the device tree, not leak into recipes. Userspace package differences are handled with `IMAGE_INSTALL` appends or a shared image recipe that pulls in board-specific package groups via `MACHINE`-conditional overrides. The key discipline is that the common layer never references a specific board, and each board layer is small enough to review in one sitting. This keeps the vendor layer upgradable without forking and makes adding a new board a matter of a new thin layer rather than a copy-paste of an existing one.

**Possible follow-ups:**
- How would you handle a peripheral that exists on two boards but is wired to different pins?
- Where would you put a kernel patch that applies to the whole product family versus one board?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never block on anything the logging path controls. I would design the driver so the two access paths are structurally separate rather than sharing a single lock. The real-time path — typically an interrupt handler or a high-priority thread — writes into a pre-allocated, lock-free ring buffer or a double-buffered region, using only atomic operations and no sleeping primitives. The logging path reads from that buffer at its own pace, and if it falls behind, it drops or overwrites old data rather than applying backpressure to the producer. If the hardware itself is a shared resource (e.g., a single register bank), I would give the real-time path priority access and have the logging path go through a deferred workqueue that only touches the hardware when the real-time path is idle, or better, have the hardware DMA into a buffer so neither path contends for the bus directly. I would avoid mutexes on the real-time path entirely; if a lock is unavoidable, it must be a spinlock held for the shortest possible window, and the logging path must use `spin_lock_bh`/`trylock` semantics so it can never hold the lock while sleeping. The design goal is that worst-case latency for the real-time task is bounded and independent of logging activity.

**Possible follow-ups:**
- How would you verify that the logging path truly cannot affect real-time latency — what would you measure?
- What happens if the ring buffer fills up and the real-time producer has nowhere to write?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** Intermittent fallback usually means the primary boot path is *sometimes* failing and the bootloader is silently moving to the next entry in its boot order. The first thing I would do is stop treating it as a network-boot problem and start treating it as an eMMC-reliability problem. I would inspect the boot order variables (`bootcmd`, `boot_targets`, `BOOT_ORDER` depending on the bootloader) and confirm whether network boot is even supposed to be in the list — if it is, removing it is a one-line fix, but that only masks the underlying eMMC failure. To find the real cause, I would enable verbose bootloader output and capture the console across many power cycles, looking for the specific error that precedes the fallback: eMMC initialization timeout, CRC errors reading the boot partition, or a partition table that is occasionally not detected. Common root causes are marginal power sequencing to the eMMC (it comes up before its supply is stable), a clock or timing margin issue on the eMMC interface, or a boot partition that is being written during the previous shutdown and is occasionally left in an inconsistent state. I would also check whether the fallback correlates with temperature, supply voltage, or a specific previous-boot state. The fix is usually in hardware bring-up timing or in making the bootloader retry the eMMC path explicitly before falling through.

**Possible follow-ups:**
- How would you make the bootloader fail loudly instead of silently falling back, so this is caught in manufacturing test?
- What would you check in the power sequencing to rule out an eMMC supply timing issue?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I would treat this as a coordination problem first and a technical problem second, because both teams have legitimate concerns and the disagreement is really about sequencing and risk ownership. My first move would be to get the two teams in the same room and separate the *what* from the *when*: the hardware team needs the pins, the software team needs the manufacturing line to keep working. Those are not actually in conflict if we stage the change. Technically, the pinmux change touches the device tree, the bootloader's early console configuration, and possibly the kernel command line — all of which are version-controlled, so the change is reviewable and reversible. I would propose that we implement the change on a branch, verify early boot console output on a prototype board, and only then coordinate with manufacturing on a cutover date. The critical question I would put to the hardware team is whether the new peripheral can wait until after the current manufacturing build, because if it can, we avoid disrupting a validated process for a change that is not yet urgent. If it cannot wait, then the software team's concern about the manufacturing line is a real schedule risk that needs to be surfaced to the project manager, not resolved unilaterally by either team. I would also make sure the manufacturing line's dependency on the debug UART is documented — if it is only used for diagnostics and not for programming or test, the risk may be smaller than the software team believes. The outcome I would push for is a staged change with a verified rollback, not a decision made by whoever argues loudest.

**Possible follow-ups:**
- What would you do if the hardware team insists the change must land before the next manufacturing build?
- How would you verify that early boot console output still works after the pinmux change, given that it happens before the kernel is fully up?
