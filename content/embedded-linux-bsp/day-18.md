## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of two identical I2C sensors on the same bus, while the other works fine?
**Answer:** I'd start by confirming the problem is at the hardware or software level, then systematically narrow it down. First, I'd check the device tree to verify both sensors are properly declared with unique addresses and that the reg properties match the actual hardware strapping. Then I'd use i2cdetect to see if the missing sensor appears on the bus at all — if it doesn't, that points to a hardware issue (wrong address strapping, missing pull-ups, cold solder joint, or the sensor not being powered). If it does appear but the kernel driver doesn't bind, I'd check dmesg for probe errors, verify the compatible string matches the driver's match table, and confirm the interrupt line (if used) isn't shared or misconfigured. I'd also check whether the driver's probe is failing due to a resource conflict — for example, if both sensors share a reset GPIO or power regulator that's only being enabled for the first one. A common gotcha is that the second sensor's supply rail is gated by a GPIO that the kernel hasn't been told to enable, so I'd verify the regulator and GPIO dependencies in the device tree. Finally, I'd check if there's a timing issue during probe — some sensors need a delay after power-up before they respond, and if the driver probes too quickly, the first read fails and the driver gives up.

- What if the sensor is detected by i2cdetect but the driver still fails to probe — what would you check next?

## Q2: How would you approach designing the device tree for a system where a single I2C bus has multiple sensors with different interrupt lines, and you need to ensure that interrupt-driven reads work reliably under heavy bus traffic?
**Answer:** The key is to model the hardware accurately in the device tree so the kernel can manage resources correctly. I'd start by defining each sensor as a child node of the I2C bus controller node, with the correct reg address and a compatible string that matches a real driver. Each sensor would have its own interrupt property referencing the appropriate GPIO controller or interrupt controller, with the correct trigger type (edge or level) matching the sensor's datasheet. For reliability under heavy bus traffic, I'd pay attention to a few things: first, ensure that interrupt lines are not shared unless the hardware truly supports it — if they are shared, the driver must handle it correctly, but it's better to use dedicated lines. Second, I'd verify that the interrupt controller properties (interrupt-parent, interrupts) are correct, and that the GPIO controller used for interrupts has the right configuration (e.g., input mode, pull-ups). Third, I'd consider whether the I2C bus speed is appropriate — if the bus is heavily loaded, I might need to use the kernel's I2C multiplexing or arbitration features if the hardware supports them. Finally, I'd make sure the device tree includes any necessary pinctrl settings so the I2C pins and interrupt pins are muxed correctly, and that power sequencing (regulators, enable GPIOs) is properly described so the kernel can manage power domains.

**Possible follow-ups:**
- How would you handle a situation where two sensors share an interrupt line and you need to determine which one triggered?
- What device tree properties would you use to describe an I2C bus that has a multiplexer in front of multiple sensor banks?

## Q3: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the hardware team reveals that they need to swap the main processor's clock source from a crystal oscillator to a MEMS oscillator to meet a new EMC requirement. The software team has already tuned the UART baud rate and USB PHY settings for the crystal's exact frequency tolerance. The project is four weeks from the start of a clinical trial. How would you handle this situation?
**Answer:** I'd approach this as a risk assessment and mitigation problem rather than a simple yes/no decision. First, I'd ask the hardware team for the specific frequency tolerance and jitter specifications of the MEMS oscillator compared to the crystal — many MEMS oscillators have comparable or better frequency stability, but the jitter profile can differ, which matters for USB and high-speed interfaces. I'd also ask whether the frequency is exactly the same (e.g., 25 MHz vs 24 MHz) or if it's a different nominal frequency that would require changing clock dividers. If the frequency is the same and the tolerance is within the USB spec (±500 ppm for full-speed, tighter for high-speed), the change might be low-risk. If it's a different frequency, I'd need to assess the impact on every peripheral that derives its clock from the main oscillator — UART baud rates, USB PHY, Ethernet, timers, and any audio or ADC sampling clocks. I'd then work with the software team to identify which settings are hard-coded versus derived from the clock tree, and whether the bootloader or kernel can be configured to handle the new frequency without code changes. I'd also check if the MEMS oscillator has a different startup time or enable sequence that might affect the boot flow. If the change is low-risk, I'd propose a rapid validation plan — boot the board, run a loopback test on UART, verify USB enumeration, and check for any timing-related errors. If it's higher-risk, I'd propose a staged approach: validate the change on a bench unit first, then decide whether to proceed with the clinical trial units. I'd also document the decision and the risk assessment in the project's risk management file, since this is a medical device and any change needs to be traceable.

**Possible follow-ups:**
- How would you quantify the risk of the clock change for USB compliance specifically?
- What would you do if the MEMS oscillator has a slightly different frequency (e.g., 24 MHz instead of 25 MHz) and the bootloader has hard-coded clock multipliers?

## Q4: How would you approach implementing a kernel driver for a device that needs to periodically read a sensor at 10 kHz and make the data available to a userspace application with minimal latency, on a single-core ARM Cortex-A processor?
**Answer:** At 10 kHz, you have a 100 µs period, which is tight but feasible on a Cortex-A if the design is careful. I'd first determine whether the sensor supports hardware triggering or DMA — if it does, that's the preferred path because it offloads the CPU. If the sensor is I2C or SPI, I'd use a hardware timer to trigger reads, and I'd use DMA for the data transfer if the controller supports it. For the driver architecture, I'd use a kernel thread with real-time priority (or a high-priority workqueue) rather than a bottom-half interrupt handler, because the read operation itself (I2C/SPI transaction) can't be done in atomic context. The interrupt would wake the thread, which performs the transaction and then copies the data to a ring buffer. For userspace access, I'd expose the data via a character device with read() and poll() support, or use a netlink socket if the data needs to be streamed. To minimize latency, I'd avoid copying data more than necessary — a single copy from the kernel buffer to the userspace buffer is unavoidable, but I'd use a lock-free ring buffer in the kernel to avoid contention. I'd also consider using the PREEMPT_RT patch set if the system needs hard real-time guarantees, and I'd ensure that the sensor driver doesn't sleep in a way that causes jitter. For the userspace side, I'd recommend the application use poll() with a timeout and read in large chunks rather than one sample at a time, to reduce syscall overhead.

**Possible follow-ups:**
- How would you handle the case where the sensor read occasionally takes longer than 100 µs due to bus contention?
- What are the trade-offs between using a kernel thread versus a bottom-half handler for this kind of periodic read?

## Q5: How would you approach debugging a situation where a custom board running Linux boots successfully, but the root filesystem on an eMMC device becomes read-only after a few hours of operation, with "I/O error" messages appearing in the logs?
**Answer:** This is a classic symptom of the kernel remounting the filesystem read-only after detecting I/O errors, which is a protection mechanism to prevent further corruption. I'd start by examining the kernel logs to identify the specific error — is it a CRC error, a timeout, or a command failure? The error pattern often tells you the root cause. Common culprits include: marginal signal integrity on the eMMC data lines (especially at higher bus speeds), insufficient power supply decoupling causing voltage droop under load, thermal issues causing the eMMC to exceed its operating temperature, or the eMMC entering a bad state due to a firmware bug. I'd check the eMMC's bus speed and timing configuration — if it's running at HS200 or HS400, I'd try dropping to a lower speed (e.g., DDR50 or SDR25) to see if the errors stop, which would point to a signal integrity issue. I'd also check the eMMC's power supply voltage and current draw, and look for any voltage regulator issues. If the errors are CRC errors, I'd suspect signal integrity or a marginal clock; if they're timeouts, I'd suspect power or the eMMC itself. I'd also check whether the issue is temperature-dependent — if it happens after a few hours, it could be thermal. I'd use the kernel's mmc debugfs interface to inspect the eMMC's health and error counters, and I'd check if the eMMC has a known erratum that requires a specific quirk flag. Finally, I'd review the device tree to ensure the eMMC's voltage, bus width, and timing are correctly configured, and I'd consider adding a kernel command-line parameter to disable the read-only remount behavior temporarily for debugging (though I'd never leave that in production).

**Possible follow-ups:**
- How would you distinguish between a hardware signal integrity issue and an eMMC firmware bug in this scenario?
- What filesystem-level mitigations would you consider to reduce the risk of corruption if the I/O errors are intermittent?
