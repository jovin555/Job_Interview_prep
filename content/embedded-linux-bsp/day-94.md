# embedded-linux-bsp — Day 94

## Q1: How would you approach deciding whether a peripheral driver should be built into the kernel image versus built as a loadable module, for a device that must be functional before the root filesystem is mounted?

**Answer:** The deciding factor is *when* the device is needed relative to the boot timeline. Anything required before the root filesystem is available — the storage controller for the rootfs itself, the console UART if you want early boot messages, the regulator/clock drivers that other early drivers depend on, and any device whose absence would prevent the rootfs from mounting — must be built in (`=y`), because modules live on the filesystem you're trying to mount. That's a chicken-and-egg problem you can't solve with a module unless you use an initramfs.

For everything else, I default to modules (`=m`) for several reasons: smaller kernel image and faster boot (only what's needed gets loaded), easier iteration during development (rebuild and reload without reflashing the whole kernel), and cleaner separation of concerns. On a production medical device I'd also weigh the regulatory angle — a built-in driver is part of the signed kernel image and its integrity is covered by the same verification as the kernel, whereas a module loaded from the rootfs is a separate artifact that needs its own integrity story (signature checking, dm-verity coverage, etc.).

Practically, I'd look at the dependency graph: if driver A's `probe()` needs to succeed before driver B can even find its device, and A is built-in, B probably needs to be too, or B needs to handle `-EPROBE_DEFER` gracefully. I'd also check whether the SoC's clock and pinctrl drivers are built-in — they almost always need to be, since nearly everything depends on them. The final decision gets validated by actually booting with the minimal config and seeing what fails.

**Possible follow-ups:** How would you handle a peripheral that's needed very early but whose driver is large and pulls in a lot of dependencies — would you accept the image size hit, or look for a way to defer it? What's the risk of building everything in and how would you mitigate it?

## Q2: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** "Probe succeeded but nothing works" usually means the driver thinks it initialized the hardware but the hardware disagrees, or the driver is talking to the wrong place. I'd work outward from the driver.

First, confirm the driver is actually bound to the device I think it is — check `/sys/bus/<bus>/devices/` and the driver's sysfs symlink, and confirm the device tree node it matched is the one I intended (a wrong `compatible` string can silently bind a generic driver). Then verify the register accesses are landing where I expect: read back a known register (an ID register is ideal) and confirm it returns the expected value. If it reads all-zeros or all-ones, that points to a clock not running, a power domain not enabled, a pinmux not applied, or a wrong base address — all of which can leave a device "probed" but dead.

Next I'd check the things `probe()` commonly forgets: is the clock actually enabled and at the right rate? Is the reset line deasserted? Is the regulator on? Is the pinmux applied to the right pins? A device that's clocked but held in reset, or powered but with no clock, will accept register writes into a void. I'd use a scope or a bus analyzer on the actual lines to confirm traffic is physically present — if the driver says it wrote to I2C but the analyzer shows nothing, the problem is upstream of the device.

Finally, I'd check whether the driver's `probe()` is returning success too early — e.g., it queues work to a delayed workqueue or threaded IRQ handler that never runs because the interrupt isn't wired, or it defers actual hardware init to a later callback that's never invoked. Adding targeted `dev_dbg`/`dev_info` at each init step and checking `dmesg` with dynamic debug enabled usually narrows it down quickly.

**Possible follow-ups:** How would you distinguish between "the driver never touched the hardware" and "the hardware ignored the driver" using only software tools? What would you check first if the device works after a warm reboot but not a cold boot?

## Q3: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to never touch the vendor's recipe or their `defconfig` — you layer on top. Yocto gives you the `.config` fragment mechanism via `KERNEL_CONFIG_FRAGMENTS` (or the older `SRC_URI` with `.cfg` files in a `linux-yocto`-style setup), and the kernel's `merge_config.sh` script combines fragments in order, with later fragments overriding earlier ones. So I'd create a `.cfg` fragment in my own layer containing only the deltas — the options I need to enable, disable, or set — and add it to the kernel recipe via a `.bbappend` in my layer that appends to `KERNEL_CONFIG_FRAGMENTS`.

The structure I'd use: a `meta-<product>` layer with `recipes-kernel/linux/linux-<vendor>_%.bbappend` that adds the fragment to `SRC_URI` and to `KERNEL_CONFIG_FRAGMENTS`, plus the fragment file itself under `recipes-kernel/linux/files/`. If the board has multiple variants, I'd use `OVERRIDES`-based conditional fragments so each machine gets its own delta without duplicating the common one. I'd also make sure the fragment is validated — Yocto will warn on options that don't exist in that kernel version, and I'd want that warning to be an error in CI so a kernel bump doesn't silently drop a config.

The key discipline is keeping the fragment minimal and documented: each line should have a comment explaining why it's there, because fragments accumulate cruft over time and become impossible to reason about. And I'd verify the merged config with `bitbake -c menuconfig` or by diffing the resulting `.config` against the vendor's to confirm only intended changes landed.

**Possible follow-ups:** What happens if the vendor kernel bumps to a new version and one of your fragment options no longer exists — how would you catch that before it reaches a build? How would you handle a fragment that needs to apply only to one machine variant in a multi-machine layer?

## Q4: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?

**Answer:** `EINTR` means a blocking syscall was interrupted by a signal before it completed — so *something* is delivering a signal to the process, even if the application didn't intend it. The first step is to find out what signal and from where. I'd check whether the daemon installs handlers for `SIGCHLD`, `SIGALRM`, `SIGUSR1/2`, or similar, and whether any of those are being delivered during the `ioctl`. A common culprit is a `SIGCHLD` from a forked child (or from a library that forks internally) arriving while the daemon is blocked in the `ioctl` — the handler runs, the syscall returns `EINTR`, and if the code doesn't retry, it treats it as fatal.

The correct fix on the application side is to retry the `ioctl` on `EINTR` in a loop — that's standard practice for any blocking syscall that can be interrupted. But I'd also look at *why* the `ioctl` is blocking long enough to be interruptible: if the driver's `ioctl` handler sleeps waiting for hardware, that's a design smell — `ioctl` should generally be quick, and long waits should be handled with `poll`/`select` and a non-blocking interface, or with a timeout the application controls. If the driver is holding a mutex or waiting on a completion, I'd check whether that wait is interruptible and whether it should be.

I'd also check whether the daemon is being sent a signal by the kernel itself — e.g., `SIGPIPE` from a broken pipe, or a `SIGTERM` from a supervisor/watchdog. `strace -f -e trace=signal,ioctl` on the daemon would show exactly which signal arrives and when, which usually makes the cause obvious. And I'd check whether the daemon is multi-threaded — a signal delivered to one thread can interrupt a syscall in another depending on how handlers are set up.

**Possible follow-ups:** If the driver's `ioctl` genuinely needs to block for a while, how would you redesign the interface so the application doesn't have to deal with `EINTR`? How would you distinguish a signal from the kernel versus one from another userspace process?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination problem first and a technical one second, because the technical change itself is small — the risk is in the blast radius across teams and the manufacturing line.

First I'd get the facts straight in the room: which pins exactly, what the new peripheral needs, whether the debug UART can share or be muxed elsewhere, and what specifically the manufacturing line depends on (is it the bootloader console, the kernel console, or both — and is it used for automated test fixtures or just human debugging?). I'd want the hardware team to confirm the new pinmux is electrically valid and that the UART's alternate pins are actually available on this package, because "free up pins" sometimes means "move the problem."

Then I'd propose a path that de-risks the change rather than blocking it: update the pinmux in the device tree and bootloader on a branch, verify early boot console output still works on a bench unit, and — critically — get the manufacturing/test engineering team to confirm their fixtures still work before the change lands on the mainline. If the manufacturing line's dependency is real and can't absorb the change on the project timeline, I'd push for either keeping the current UART for this revision and moving it on the next board spin, or adding a second debug path (e.g., a test point or an alternate console) so manufacturing isn't blocked. I'd document the decision and the rationale in the design review record so it's traceable.

The key is not to let it become "software says no" versus "hardware says yes" — it's a shared schedule and risk decision, and I'd want the manufacturing stakeholder in the conversation rather than hearing about the impact secondhand.

**Possible follow-ups:** What would you do if the hardware team insists the change must land this revision and manufacturing can't be ready in time? How would you verify the new pinmux doesn't break anything else that shares those pins?
