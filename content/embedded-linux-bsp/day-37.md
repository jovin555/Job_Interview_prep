## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of two identical I2C sensors on the same bus, while the other works fine?
**Answer:** I'd start by confirming the problem is at the hardware level versus the software level. First, I'd check `i2cdetect` to see if the device appears on the bus at all — if it doesn't, that points to a hardware issue (address conflict, missing pull-ups, bad solder joint, or the sensor not being powered). If it does appear in `i2cdetect` but the kernel driver doesn't bind, I'd check the device tree entry: is the correct address specified? Is the compatible string matching what the driver expects? Is there an interrupt line conflict or a GPIO that needs to be asserted for the sensor to wake up? I'd also verify that the sensor's address isn't conflicting with another device on the bus — sometimes two identical sensors need different address pins strapped, and if both are strapped the same way, only one will respond. I'd use a logic analyzer or oscilloscope to verify the I2C transactions are actually being acknowledged. If the device is detected but reads garbage, I'd suspect a timing issue — perhaps the bus speed is too fast for that particular sensor's datasheet limits, or the pull-up resistor values are marginal for the total bus capacitance. Finally, I'd check the kernel log for any probe errors or timeouts specific to that device, and compare the device tree entry against the working sensor's entry to spot any differences.

**Possible follow-ups:** How would you distinguish between a device that's not being detected at the hardware level versus one that's detected but failing to probe? What if the sensor works intermittently — how would you narrow down whether it's a timing, power, or addressing issue?

## Q2: How would you approach designing the boot sequence for a system with two processors — an application processor running Linux and a safety-critical microcontroller — where the microcontroller must be fully initialized and running its safety monitoring routines before the Linux userspace starts any critical applications?
**Answer:** The key principle is establishing a deterministic handshake between the two processors before any safety-relevant functionality is enabled. I'd structure this in stages. First, the bootloader (U-Boot) would release the microcontroller from reset and wait for a "ready" signal — this could be a GPIO line, a mailbox message, or a status register read. The microcontroller runs its own power-on self-test, initializes its safety monitors, and then asserts the ready signal. Only after the bootloader confirms this does it proceed to load the kernel. In the kernel, I'd have a driver that re-checks the microcontroller's status — not just trusting the bootloader's earlier check, since the kernel boot takes time and the microcontroller could have faulted in the interim. This driver would expose a sysfs node or use a kernel-internal flag that gates when the critical userspace applications are allowed to start. The init system (systemd or a custom init script) would wait on this flag before launching any safety-critical services. I'd also implement a watchdog mechanism: the microcontroller monitors the application processor's health, and vice versa, so that if either side fails, the system enters a safe state. For the communication itself, I'd use a shared memory region with a simple protocol (e.g., a mailbox with sequence numbers and CRC) rather than a complex bus, since shared memory is lower latency and more deterministic. The boot sequence should also handle the failure case: if the microcontroller doesn't assert ready within a timeout, the system should not proceed to start critical applications — it should either retry, enter a safe state, or log the failure and halt.

**Possible follow-ups:** How would you handle the case where the microcontroller is already running from a previous boot (e.g., a soft reset of the application processor)? What if the microcontroller needs to be updated independently of the Linux system — how does that affect the boot sequencing?

## Q3: How would you approach implementing a kernel driver for a device that needs to be accessed by both a real-time safety-critical task and a non-real-time monitoring task, where the safety-critical task must never be blocked by the monitoring task?
**Answer:** The fundamental requirement is that the safety-critical path must have guaranteed access to the hardware without being subject to lock contention or scheduling delays caused by the monitoring task. I'd approach this by separating the access paths at the hardware level if possible. If the device has separate register banks or channels, I'd partition them so each task gets its own dedicated registers — this avoids any locking entirely. If that's not possible, I'd use a lock-free design: the safety-critical task writes to a hardware register directly (using atomic operations or a hardware spinlock if the SoC provides one), and the monitoring task reads from a shadow copy that's updated via a DMA or a separate read path. In the kernel, I'd implement this as two distinct interfaces: a character device with a real-time priority access path (perhaps using `io_uring` or a dedicated syscall that bypasses normal locking) and a standard sysfs or debugfs interface for the monitoring task. The real-time path would use `spin_lock_irqsave` rather than a mutex, since it can't sleep. I'd also consider using the `PREEMPT_RT` patch set if the system allows it, which would give better real-time guarantees. For the data flow, I'd use a ring buffer in shared memory with atomic read/write pointers — the safety-critical task writes, the monitoring task reads, and neither ever blocks the other. The monitoring task might get stale data or miss some samples, but that's acceptable for its purpose. I'd also make sure the monitoring task's interface can be disabled entirely at runtime if it's causing any interference, and I'd add instrumentation to measure worst-case latency on the safety-critical path to verify the design meets its timing requirements.

**Possible follow-ups:** How would you handle the case where the hardware device itself can only be accessed by one task at a time (e.g., a single I2C bus)? What if the monitoring task needs to configure the device, but the safety-critical task is actively using it — how do you prevent configuration changes from disrupting the real-time path?

## Q4: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel log shows "Failed to request IRQ" for a device that worked on the previous board revision?
**Answer:** This is a classic board-revision regression, so I'd start by comparing the device tree and hardware configuration between the two revisions. The most common cause is an interrupt line conflict — the new revision may have moved a peripheral to a GPIO line that's already claimed by another device, or the interrupt controller's available lines have changed. I'd check `/proc/interrupts` to see which lines are already allocated, and cross-reference that against the device tree's `interrupts` property for the failing device. Another possibility is that the interrupt line is now shared with a device that doesn't properly support shared interrupts (i.e., it doesn't call `irq_handler` correctly for a shared line). I'd also check whether the GPIO controller that provides the interrupt has changed — perhaps the new revision uses a different GPIO bank or a GPIO expander, and the device tree still references the old controller. I'd verify the pin muxing: the new board revision might have changed the pin's function from GPIO to some other peripheral, so the interrupt can't be requested. I'd also look at the kernel log more carefully — is the failure happening at probe time, or later? If it's at probe time, the driver might be trying to request the IRQ before the interrupt controller is ready. I'd check the device tree's `interrupt-parent` property to make sure it points to the correct interrupt controller. Finally, I'd use a scope or logic analyzer to verify the interrupt line is actually toggling when the device needs attention — if the hardware isn't generating the interrupt, the request might succeed but the device never fires, which is a different symptom. If the IRQ request itself fails, I'd also check for a mismatch between the device tree's interrupt number and the actual hardware connection on the new revision.

**Possible follow-ups:** How would you handle a situation where the IRQ is successfully requested but the interrupt handler never fires? What if the failure is intermittent — sometimes the IRQ request succeeds, sometimes it fails?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the hardware team reveals that they need to change the main processor's clock source from a crystal oscillator to a MEMS oscillator to meet a new EMC requirement. The software team has already tuned the UART baud rate and USB PHY settings for the crystal's exact frequency tolerance. The project is four weeks from the start of a clinical trial. How would you handle this situation?
**Answer:** I'd start by acknowledging that this is a significant change with real technical implications, but it's not necessarily a blocker. The first step would be to get the specifications for the MEMS oscillator — its frequency tolerance, jitter, and startup characteristics — and compare them against the crystal's. The key question is whether the frequency difference is within the tolerance that the UART and USB PHY can handle. UART typically tolerates a few percent of baud rate error, and USB 2.0 has a specified tolerance of ±2500 ppm for the clock, so if the MEMS oscillator is within those bounds, the software changes might be minimal. I'd work with the hardware team to get a sample of the MEMS oscillator and run a bench test on a development board — measure the actual UART communication at various baud rates and verify USB enumeration and data integrity. If the tests show issues, I'd look at what software changes are needed: adjusting the UART clock divider to compensate for the frequency difference, or re-tuning the USB PHY settings. I'd also check whether the bootloader uses the clock for timing-critical operations like DDR initialization — if so, those timing parameters might need adjustment. In parallel, I'd assess the risk: the MEMS oscillator might actually be better in some ways (faster startup, better stability over temperature), so this could be an improvement. I'd document the change in the design history file, update the device tree if the clock frequency is specified there, and run a full regression test on the affected interfaces. For the clinical trial timeline, I'd propose a plan: bench testing this week, software changes if needed next week, and full integration testing the following week — which should still leave time before the trial starts. I'd also ask the hardware team if they can provide both oscillator options on the board (a footprint that supports both) to reduce risk, even if only one is populated for the trial.

**Possible follow-ups:** What if the MEMS oscillator's frequency is significantly different from the crystal (e.g., 12 MHz vs 25 MHz) — how does that change your approach? How would you communicate the risk and timeline impact to the project manager and regulatory team?
