# embedded-linux-bsp — Day 118

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is usually one of a few classes of problem, and the approach is to bisect the path from "driver thinks it's done" to "hardware actually does something." First, confirm the driver is talking to the right hardware: dump the resolved resources the driver received (MMIO base, IRQ number, clock handles, regulator handles) and compare them against the schematic and the SoC reference manual. A common cause is a device tree node that is syntactically valid but semantically wrong — a base address off by an offset, an interrupt that maps to the wrong line, or a `reg` property that describes a sub-block rather than the whole peripheral. Second, verify the peripheral is actually clocked and powered: read back the clock enable and regulator state from within the driver, or use `clk_summary` and regulator debugfs entries, because a driver can "succeed" while its clock gate is still closed. Third, check that the driver is writing to registers that have an effect — some peripherals require an unlock sequence, a soft-reset release, or a configuration-lock bit before writes take. Fourth, confirm the driver is not silently discarding errors: many `probe()` implementations call `devm_*` helpers and ignore return codes, or use `readl`/`writel` without checking that the bus is actually responding. A useful technique is to add temporary instrumentation that reads back a known register (an ID register or a scratch register) immediately after writing it, to prove the bus is live. Finally, if the driver is a bus client (I2C/SPI), verify the bus itself is functional by probing the device from userspace with `i2cdetect` or a small SPI test, because a bus that is misconfigured at the controller level can make every transfer "succeed" while returning garbage. The key discipline is to separate "software believes it configured the device" from "device is actually configured," and instrument the boundary between them.

**Possible follow-ups:** How would you tell the difference between a device tree resource problem and a clock/power problem without a schematic in hand? What would you do if the register readback shows the correct value but the peripheral still doesn't produce output?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer board-specific configuration on top through the mechanisms Yocto already provides, rather than copying the recipe into your own layer. The clean approach is to use a `.bbappend` in your board layer that adds a `SRC_URI` entry pointing at a config fragment, and to rely on the kernel's `merge_config.sh`-style fragment handling (via `KERNEL_CONFIG_FRAGMENTS` or the `cfg` file mechanism, depending on the kernel class version) so the fragment is merged into the defconfig at build time rather than replacing it. The fragment should contain only the deltas — the options you need to turn on or off — not a full defconfig, so that vendor updates to the base config flow through automatically. Keep the fragment in a `files/` directory next to the `.bbappend`, version it in the same layer as the board's device tree and bootloader recipes, and document which options are board-specific versus product-family-wide. If multiple boards in the family share most of the fragment, factor the common part into a shared include and have each board's `.bbappend` pull in the shared fragment plus its own delta. The important discipline is to avoid `do_configure:append` shell hacks that edit `.config` directly, because those are invisible to the kernel's config audit and break reproducibility. Also verify the merge with `bitbake -c menuconfig` and by diffing the resulting `.config` against the vendor baseline, so you can prove exactly what your layer changed.

**Possible follow-ups:** How would you handle a fragment option that depends on another option being enabled first, where the merge order matters? What would you do if the vendor updates their kernel recipe and your fragment no longer applies cleanly?

## Q3: How would you approach debugging a situation where a custom board running Linux boots successfully, but a USB 2.0 device (e.g., a data acquisition module) is intermittently not enumerated on cold boots, while working fine after a warm reboot?

**Answer:** A cold-boot-only enumeration failure that disappears on warm reboot points strongly at timing and power sequencing rather than the USB stack itself, because a warm reboot leaves the PHY, the device, and the power rails in a different state than a cold start. The first thing to check is the reset and power sequence: does the USB device see a valid VBUS and a clean reset before the host controller starts enumeration, or is the host controller probing before the device's internal power-on reset has completed? On the host side, check whether the root hub port power is enabled and stable before the controller begins its port reset, and whether the PHY clock is locked at the moment the controller expects it. On the device side, check whether the device's own reset line is released at the right time relative to VBUS — many devices need a minimum delay after power-good before they will respond to a reset. A useful diagnostic is to add a delay in the host controller's probe or in the port power-on path and see whether the failure rate changes; if it does, you've confirmed a sequencing issue. Also check the USB PHY configuration: some SoCs require a PHY tuning or calibration step that only completes correctly if the reference clock is stable, and a cold boot may catch the PHY mid-calibration. On the software side, enable USB core debug (`CONFIG_USB_DEBUG` or dynamic debug on the `usbcore` and `xhci_hcd`/`ehci_hcd` modules) and capture the enumeration log on a failing cold boot versus a passing warm boot — the point where the two diverge tells you whether the device is not responding to the first reset, responding with a bad descriptor, or never being seen at all. Finally, rule out signal integrity: a marginal D+/D- eye at cold temperature or with a cold connector can cause intermittent enumeration that a warm reboot masks because the connector has been "exercised."

**Possible follow-ups:** How would you distinguish a PHY calibration issue from a device power-sequencing issue using only software-visible symptoms? What would you change in the device tree or bootloader to make the sequencing deterministic?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never block on anything the logging path controls, so the design has to decouple them at the data-structure level rather than trying to arbitrate with a shared lock. The real-time access should own the hardware: it performs the register or DMA operations directly, with no sleeping locks, no mutexes that a logging thread could hold, and no allocation on the hot path. The logging path should consume data that the real-time path has already produced, through a lock-free or minimally-contended structure — a single-producer/single-consumer ring buffer is the classic choice, where the real-time side writes and advances a head pointer with a release barrier, and the logging side reads and advances a tail pointer with an acquire barrier, so neither side ever waits on the other. If the ring fills because logging is slow, the real-time side must have a defined policy: drop the oldest sample, drop the newest, or overwrite, but it must never block. For the hardware access itself, if both paths genuinely need to touch the same registers, the real-time path should be the only one that does; the logging path should be fed from a snapshot or a copy that the real-time path publishes. Interrupt handling should be split: a hard IRQ handler does the minimum (acknowledge, timestamp, enqueue to the ring), and any heavier processing is deferred to a threaded handler or a workqueue that runs at a priority below the real-time task. On the scheduling side, the real-time task should run under `SCHED_FIFO` with a priority above the logging thread, and the logging thread should be `SCHED_OTHER` or a low-priority `SCHED_FIFO`, so even if the logging thread is runnable it cannot preempt the real-time task. The design should be validated with a latency measurement — a GPIO toggle or a timestamp at the start and end of the real-time access — under worst-case logging load, to prove the logging path's activity does not show up in the real-time path's timing.

**Possible follow-ups:** How would you handle the case where the logging path needs to reconfigure the device (e.g., change a sample rate) while the real-time path is running? What would you do if the ring buffer's memory ordering guarantees are not sufficient on a weakly-ordered ARM core?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams are raising legitimate concerns and the cost of getting it wrong is asymmetric — a broken manufacturing console is a production-line stoppage, while a delayed peripheral is a schedule slip. The first step is to get the facts on the table in a shared forum: what exactly does the manufacturing line depend on (which console, at which stage of boot, for which test steps), and what is the actual pin budget — is the new peripheral truly blocked, or is there a pin that could be freed elsewhere? I'd ask the hardware team to show the pinmux map and the alternate-function options, because often there is a second candidate pin or a different peripheral that can be moved with less impact. If the move is genuinely necessary, I'd scope the software change explicitly: which device tree nodes, which bootloader configuration, and which early-console path are affected, and whether the change can be made in a way that preserves the manufacturing console on a different pin or a different UART instance. I'd propose a staged plan — make the change on a branch, validate early boot and manufacturing test steps on a small number of boards, and only then roll it into the mainline — so the manufacturing team sees evidence rather than assurances. I'd also make sure the decision and its rationale are documented in the design review record, with the manufacturing stakeholder as a signatory, so that if something does break there is a clear owner and a clear rollback path. Throughout, I'd keep the tone collaborative: the hardware team is not "breaking" the software, and the software team is not "blocking" the hardware — both are protecting their part of the system, and the job of the BSP lead is to find the option that protects both.

**Possible follow-ups:** What would you do if the manufacturing team refuses to accept any change to the console pin, even with a staged validation plan? How would you decide whether to escalate, and to whom?
