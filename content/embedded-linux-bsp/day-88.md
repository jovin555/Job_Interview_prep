# embedded-linux-bsp — Day 88

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel's `probe()` for a platform driver is deferred indefinitely because a `regmap`-based I2C sensor's parent bus is not yet available at the time the driver is registered?

**Answer:** An indefinite `-EPROBE_DEFER` loop almost always points to a dependency that never resolves, so I'd treat it as a dependency-graph problem rather than a driver bug. First I'd confirm the loop is real: enable `initcall_debug` and dynamic debug for the driver core (`dyndbg="file drivers/base/dd.c +p"`), or just read `dmesg` for the repeated "probe deferred" lines, and check `/sys/kernel/debug/devices_deferred` to see exactly which device is stuck and what supplier it is waiting on. That list is the fastest way to see the actual supplier name rather than guessing.

Then I'd work outward from the supplier. For a `regmap`-based I2C sensor, the deferred supplier is usually the I2C adapter itself, a clock, a regulator, or a GPIO controller. I'd verify the I2C controller node is present and enabled in the device tree, that its `status = "okay"`, and that the controller driver actually probed — if the adapter never registers, every child on that bus defers forever. I'd also check that the sensor node is a child of the correct I2C bus node and that the `reg` address matches the hardware strap. A common mistake is the sensor being placed under the wrong bus or with a mismatched address, so the bus never creates the child device.

If the supplier is a clock or regulator, I'd check that the `clocks` and `vcc-supply` phandles resolve to nodes that themselves probe successfully. A regulator that depends on an I2C PMIC which is itself deferred creates a chain, and the chain has to bottom out somewhere. I'd trace it to the root cause — often a pinmux, a missing clock provider, or a PMIC whose own bus isn't up. Finally, I'd confirm the driver's `of_match_table` actually matches the compatible string; a silent mismatch means the driver never binds at all, which looks similar in the log but is a different fix. The key discipline is to follow the deferred list to the leaf supplier and fix that, rather than adding retry hacks in the sensor driver.

**Possible follow-ups:** How would you distinguish a genuine dependency cycle from a slow-probing supplier that would eventually resolve? What would you change in the device tree if the supplier is a regulator that is optional for this sensor?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our changes on top through configuration fragments and `.bbappend` files, so a vendor kernel bump doesn't force us to re-merge a forked recipe. I'd start by creating a `linux-yocto`-style fragment — a small `.cfg` file containing only the `CONFIG_*` lines we need — and reference it from a `.bbappend` in our own layer using `SRC_URI:append` with the `file://` fragment and the kernel's `merge_config`/`config-fragments` mechanism. That way the fragment is applied at build time on top of the vendor defconfig, and the vendor recipe stays untouched.

Concretely, the layer layout would be something like `meta-<product>/recipes-kernel/linux/linux-<vendor>_%.bbappend` plus the fragment under `recipes-kernel/linux/files/`. The `.bbappend` adds the fragment to `SRC_URI` and, depending on the kernel class, either relies on the built-in fragment handling or adds a `do_configure:append` that runs `merge_config.sh` against the generated `.config`. I'd also add a `do_kernel_configcheck`-style sanity step or a small task that greps the final `.config` for our required options and fails the build if any are missing — that catches the case where a fragment silently gets dropped because of a Kconfig dependency.

The important discipline is that fragments should be minimal and self-documenting: one fragment per feature area (e.g., one for a new peripheral's driver, one for a debugging option), each with a comment explaining why. I'd avoid `CONFIG_` lines that depend on other options without also enabling the dependencies, because Kconfig will silently drop them. And I'd keep the fragment in version control alongside the `.bbappend` so the change is reviewable and reproducible. If the vendor later changes their defconfig, our fragments still apply on top, and we only need to revisit them if a symbol is renamed or removed.

**Possible follow-ups:** How would you verify in CI that a fragment actually took effect rather than being silently dropped? What's the trade-off between a fragment and patching the vendor defconfig directly?

## Q3: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** An intermittent fallback to network boot usually means the boot target isn't reliably available at the moment U-Boot tries it, and the boot command list is falling through to the next entry. I'd start by capturing the full U-Boot console log across many boots — not just one — because the failure is intermittent and the log will show which boot target failed and why. I'd look at `bootcmd`, the `boot_targets` ordering, and whether `BOOTCOMMAND` is a distro-boot-style list that tries mmc, then usb, then pxe, then dhcp. If the eMMC target fails for any reason, the list moves on, and network boot is the last resort that "succeeds" because the DHCP server answers.

Then I'd find out why eMMC is intermittently unavailable. Common causes: the eMMC needs more time after power-on than U-Boot allows before the first `mmc dev`/`mmc rescan`, so a retry or a small delay fixes it; the eMMC's `mmc` node isn't enabled in the SPL/U-Boot device tree on some builds; or the boot partition selection (`mmc part`, `bootpart`) is racing with card initialization. I'd check `mmc list`, `mmc info`, and the return code of the boot attempt, and I'd add explicit retries around the eMMC probe rather than relying on a single attempt.

The structural fix is to make the boot policy explicit rather than relying on a fall-through list. I'd set `boot_targets` to only the intended target (or put eMMC first and remove network from the list entirely on production units), and if a fallback is genuinely wanted for recovery, gate it behind a deliberate condition — a button press, a GPIO strap, or a magic environment variable — rather than an automatic last-resort. I'd also make sure the environment is stored where it can't be corrupted into a bad state, and that `saveenv` isn't writing a partially-updated `bootcmd`. Finally, I'd reproduce the failure under controlled conditions (power-cycle timing, cold vs warm boot, temperature) to confirm the fix addresses the actual race rather than masking it.

**Possible follow-ups:** How would you make the eMMC boot attempt deterministic without adding an unacceptable boot-time delay? What would you check in the SPL if the eMMC is sometimes not even enumerated at that stage?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path can hold, so the design has to separate the two paths at the data-structure level, not just at the scheduling level. I'd start by identifying what the real-time task actually needs from the device: typically a register read or a short transfer with a bounded worst-case latency. The logging task needs a copy of the data, but it can tolerate delay and jitter. So the driver should give the real-time path a lock-free or minimally-contended path to the hardware, and hand the logging path a snapshot through a separate buffer.

Concretely, I'd use a per-CPU or per-context buffer: the real-time path writes samples into a ring buffer with a single producer and a single consumer, using atomic indices and no sleeping locks. The logging task reads from the consumer side at its own pace. If the ring fills because logging is slow, the policy has to be explicit — either drop oldest samples (and count the drops) or overwrite, but never block the producer. For the hardware access itself, if the device is memory-mapped, the real-time path can do a direct `readl`/`writel` with no lock if the register is not shared with the logging path; if it is shared, I'd use a spinlock with interrupts disabled only for the shortest possible critical section, and make sure the logging path never takes that lock while holding anything else.

I'd also look at whether the two paths can be given separate hardware resources — a second register bank, a FIFO, or a DMA channel — so they don't contend at all. If the device only has one access port, then the real-time path gets priority and the logging path is explicitly best-effort, documented as such. On the scheduling side, the real-time task would run under `SCHED_FIFO` with a priority above the logging thread, but I'd rely on the lock-free design rather than priority alone, because priority inheritance doesn't help if the real-time task is spinning on a lock the logging task holds. Finally, I'd instrument worst-case latency on the real-time path and test it under logging load to prove the logging task can't push it past its deadline.

**Possible follow-ups:** How would you handle the case where the hardware register genuinely must be shared between both paths? What would you measure to prove the logging task cannot affect real-time latency?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination problem first and a technical problem second, because both teams are raising legitimate concerns and the real risk is that one side unilaterally changes something the other depends on. My first step would be to get the facts on the table in one place: which pins the new peripheral needs, which pinmux groups are available, what the manufacturing line actually depends on from the debug UART (is it just early boot logs, or is it a test fixture that parses specific output?), and what the change would cost on each side. I'd want the hardware team to show the pin conflict and the software team to show exactly where the UART pinmux is configured — device tree, bootloader, and any early-console setup — so we're arguing about the real dependency, not an assumption.

Then I'd look for options that don't force a straight either/or. Could the debug UART move to a different set of pins that the manufacturing fixture can still reach, with a corresponding fixture update? Could the new peripheral use a different pinmux group or a different interface entirely? Could we keep the current UART for early boot and switch pinmux later in the boot flow, so manufacturing still sees the console it relies on? I'd bring the manufacturing/test engineering representative into the conversation early, because they own the fixture and can tell us how hard a change actually is — often it's a cable or a config change, not a redesign.

If a change is unavoidable, I'd sequence it so nothing breaks silently: update the device tree and bootloader pinmux together, keep the old configuration available behind a build variant or a device-tree overlay during the transition, and validate on real hardware that early console output still appears where manufacturing expects it. I'd document the change and the rationale in the design record, since this is a medical device and traceability matters. The key is that I'd frame it as "we'll find the option that meets the pin requirement without breaking the manufacturing dependency, and if we can't, we'll make the trade-off explicitly with the people who own the risk" — rather than letting either team's concern be overridden by the other.

**Possible follow-ups:** How would you decide if the manufacturing dependency is worth the cost of changing the fixture versus changing the hardware plan? What would you put in the design record to make this decision traceable later?
