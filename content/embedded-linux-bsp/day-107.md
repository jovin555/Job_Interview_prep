# embedded-linux-bsp — Day 107

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is usually one of a few things: the driver is talking to the wrong address, the hardware isn't actually powered/clocked, or the driver is writing to registers that don't take effect because a gate (clock, reset, power, pinmux) is still closed. I'd start by confirming the driver is bound to the intended device — check `/sys/bus/platform/devices/` or the relevant bus directory and the `driver` symlink, and confirm the `of_node` matches the expected device tree node. Then I'd verify the register base address and size from the device tree against the SoC reference manual; a wrong `reg` value or a missing `ranges` translation in a parent bus can make every access land somewhere harmless. Next I'd check that the clock and reset lines are actually enabled — read back the clock enable registers or use `clk_summary` in debugfs, and confirm the reset deassert happened. I'd also probe the bus physically: for I2C/SPI, a bus analyzer or a scope on the lines tells you whether transactions are even leaving the SoC. If the driver uses a regmap, I'd enable regmap debugfs and read back a known register to see whether writes stick. A common trap is a driver that returns 0 from probe without ever verifying the device ID register — so I'd add a readback of the chip ID and log it. Finally, I'd check pinmux: if the peripheral's pins are still muxed to another function, the SoC-side controller works fine but nothing reaches the external device. The key discipline is to bisect the path — SoC controller, bus, pinmux, power/clock, external device — and confirm each hop independently rather than trusting that "probe returned 0" means the hardware is alive.

**Possible follow-ups:** How would you tell the difference between a pinmux problem and a clock/power problem without a schematic in front of you? What would you add to the driver to make this class of failure visible in the future?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the source of truth and layer our deltas on top. I'd create our own layer (say `meta-<product>`) with a `conf/layer.conf` that declares the right `LAYERSERIES_COMPAT` and priority, and a `recipes-kernel/linux/` directory containing a `.bbappend` against the vendor kernel recipe. In that bbappend I'd use `SRC_URI` with `file://` entries for a config fragment and set `KERNEL_CONFIG_FRAGMENTS` (or the older `SRC_URI += "file://fragment.cfg"` pattern with `do_configure:append` running `merge_config.sh`) so the fragment is merged into the defconfig rather than replacing it. The fragment itself should contain only the deltas — `CONFIG_FOO=y`, `# CONFIG_BAR is not set` — not a full config, so it stays reviewable and survives vendor defconfig updates. I'd keep the fragment in `recipes-kernel/linux/linux-<vendor>/` and version it alongside the bbappend. For reproducibility I'd pin the vendor layer to a specific revision in `bblayers.conf`/`layer.conf` and document the expected kernel version. I'd also add a build-time check — a small `do_configure:append` that greps the final `.config` for the options we require and fails the build if any are missing, so a vendor defconfig change can't silently drop our options. The same pattern works for device tree: a `.bbappend` adding our `.dts`/`.dtsi` via `SRC_URI` and `KERNEL_DEVICETREE`, rather than editing the vendor's tree in place.

**Possible follow-ups:** What are the trade-offs of `KERNEL_CONFIG_FRAGMENTS` versus a full custom defconfig? How would you handle a vendor kernel that doesn't use the standard kernel bbclass?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path holds. I'd design the driver so the real-time access path is lock-free or uses only a very short-held spinlock, and the logging path consumes data from a separate buffer that the real-time path writes into without waiting. Concretely: the real-time side (whether it's an interrupt handler, a high-priority kthread, or a userspace SCHED_FIFO task via a char device) writes samples into a pre-allocated ring buffer using a single-producer/single-consumer pattern with atomic head/tail indices — no mutex, no sleeping. The logging side reads from the ring buffer at its own pace; if it falls behind, it drops or overwrites old entries per policy rather than back-pressuring the producer. If the hardware itself is shared (e.g., a single register bank), I'd serialize only the actual register access with a spinlock held for a few instructions, and keep any formatting, copying to userspace, or file I/O outside that lock. For the userspace interface I'd expose two separate char devices or two ioctls: one for the real-time read (blocking or poll-based, minimal copy) and one for the logging drain (bulk read). I'd also make sure the logging path can't run in interrupt context or hold a lock across a `copy_to_user`. The verification is a latency test: run the real-time path under load with the logging path hammering, and measure worst-case latency with `cyclictest` or an in-driver timestamp — if the logging task can perturb it, the design is wrong.

**Possible follow-ups:** How would you handle the case where the hardware register itself must be read by both paths and a read has side effects? What happens to your design if the real-time consumer is in userspace rather than in the kernel?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** An intermittent fallback to network boot means the boot ROM or U-Boot's boot flow is failing to find a valid bootable image on eMMC on some boots and then walking down the boot order to the next device. I'd first confirm which stage is falling back — the SoC boot ROM (before U-Boot runs) or U-Boot's own `bootcmd`/`distro_bootcmd` — because the fixes are different. If it's the ROM, the eMMC may not be ready within the ROM's boot window on cold boots: check the eMMC power ramp, reset timing, and whether the part needs a longer initialization delay; a marginal supply or a slow-ramping rail can cause the ROM to time out intermittently. If it's U-Boot, I'd inspect the environment: `printenv bootcmd`, `boot_targets`, and whether `bootargs`/`bootcmd` were saved with `saveenv` at some point and now persist a network entry ahead of eMMC. I'd check for a corrupted or partially-written environment in eMMC — a bad CRC causes U-Boot to fall back to the default environment, which may include network boot. I'd also look at whether the eMMC's boot partition or the GPT/MBR is being read reliably: `mmc info`, `mmc part`, and a manual `fatload`/`ext4load` from eMMC on a failing boot tells you whether the medium is readable. On the hardware side, I'd scope the eMMC clock and data lines during a failing boot and check for signal integrity issues at the higher bus speed, and confirm the eMMC's `BOOT_BUS_WIDTH`/`BOOT_PARTITION_ENABLE` extcsd settings match what the boot flow expects. The fix is usually either a longer boot delay / power-on sequencing change, a corrected boot order in the environment, or disabling the unintended network target entirely so a fallback can't silently mask the real failure.

**Possible follow-ups:** How would you make the fallback visible in the logs so it doesn't go unnoticed? What's the risk of just removing the network boot target from the boot order?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a change-control and risk question rather than a purely technical one, because both teams are right about something. First I'd get the facts on the table: exactly which pins move, what the new peripheral needs, and what the manufacturing line actually depends on — is it the UART console for test logging, or is it a specific pin state at power-on? Those are different risks. Then I'd quantify the software impact: the pinmux change touches the bootloader's early console setup and the device tree's pinctrl node, and possibly the kernel command line if the console device name changes. I'd propose a path that de-risks it: keep the debug UART on its current pins for the current build, add the new peripheral on the freed pins only after confirming the manufacturing test flow can tolerate the console moving (or can be updated in lockstep), and stage the change behind a board revision or a build-time config so both variants can be validated. I'd bring manufacturing into the conversation early — they own the test fixture and the acceptance criteria, so their sign-off is part of the decision, not an afterthought. If the schedule forces a decision, I'd document the trade-off and the validation plan (boot on both variants, console output verified, manufacturing test pass) and get explicit agreement from the stakeholders rather than letting it be decided by whoever is loudest. The principle is: don't let a pinmux change silently break a downstream process; make the dependency visible and manage it as a controlled change.

**Possible follow-ups:** How would you validate that the manufacturing line's dependency is actually on the UART and not on some other pin state? What would you do if manufacturing couldn't update their fixture in time?
