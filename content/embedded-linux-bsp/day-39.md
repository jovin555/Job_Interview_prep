# embedded-linux-bsp — Day 39

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel log shows "Failed to request IRQ" for a device that worked on the previous board revision?
**Answer:** I'd start by confirming which IRQ is failing and whether the device tree actually matches the new board revision. A "Failed to request IRQ" error typically means one of three things: the IRQ number is invalid or not mapped in the interrupt controller, the IRQ is already claimed by another driver, or the interrupt controller itself isn't properly initialized for that line. First, I'd check the device tree to verify the interrupt parent and interrupt number are correct for the new revision — a common issue is that the hardware team moved a peripheral to a different GPIO bank or interrupt line, and the device tree wasn't updated. Next, I'd look at `/proc/interrupts` to see which IRQs are already allocated and whether there's a conflict. I'd also check the interrupt controller driver's probe order — if the GPIO controller or interrupt controller that provides the IRQ hasn't probed yet, the request will fail. A useful debugging step is to enable `CONFIG_DEBUG_IRQ` and `CONFIG_PROVE_LOCKING` to get more context, and to check the kernel log for earlier messages about the interrupt controller failing to initialize. If the IRQ is shared, I'd verify that all drivers using it set the `IRQF_SHARED` flag. Finally, I'd compare the working board's device tree and kernel config against the new one to isolate what changed.

**Possible follow-ups:** How would you determine whether the issue is a device tree problem versus a driver probe-order problem? What if the IRQ is requested successfully but never actually fires?

## Q2: How would you approach designing a kernel driver for a device that needs to log sensor data to a file on the root filesystem at a fixed rate (e.g., 100 Hz) without causing filesystem corruption on unexpected power loss?
**Answer:** The first principle is that you generally don't write to a filesystem directly from kernel space at a fixed rate — that's a userspace responsibility. The kernel driver's job should be to collect sensor data efficiently and make it available to userspace through a character device, a ring buffer, or a netlink interface. The userspace application then handles the file I/O. That said, if the requirement truly demands kernel-space logging, I'd use a deferred work mechanism rather than writing in interrupt context. The key concern is power-loss resilience: you need a filesystem that handles sudden power removal gracefully. I'd use a journaling filesystem like ext4 with `data=ordered` mode, or better yet, a log-structured filesystem like JFFS2 or UBIFS if the storage is raw NAND/NOR flash. For eMMC, ext4 with proper barriers enabled is reasonable. To avoid corruption, I'd write to a dedicated partition or a pre-allocated file, and I'd batch writes — accumulating data in a buffer and flushing periodically rather than writing every sample individually. I'd also consider using `fsync` or `fdatasync` at appropriate intervals to ensure data hits the media, but doing this at 100 Hz would be too slow, so I'd flush in larger batches (e.g., every second). For a medical device, I'd also implement a circular buffer in RAM that holds recent data, so that on reboot the system can recover the most recent samples that weren't yet flushed. An alternative approach is to use a small dedicated logging partition with a simple append-only format and a sequence number, which makes recovery after power loss straightforward.

**Possible follow-ups:** How would you handle the case where the filesystem becomes full during operation? What are the trade-offs between writing from kernel space versus using a userspace daemon?

## Q3: How would you approach implementing a kernel driver for a device that uses DMA to transfer data from an FPGA to system memory, where the FPGA can generate data at rates exceeding what the CPU can process in real-time?
**Answer:** The core challenge here is that the CPU can't keep up with the data rate, so the design must decouple data acquisition from data processing. I'd structure the driver around a large DMA ring buffer in system memory — the FPGA writes continuously into this buffer, and the driver manages the buffer boundaries. The key decisions are buffer size, DMA descriptor management, and how to notify userspace. For the DMA engine, I'd use the kernel's DMA engine API (`dmaengine_*` functions) rather than writing raw DMA controller code, since it abstracts the hardware and handles cache coherency. I'd set up a ring of DMA descriptors that the FPGA can cycle through — when the FPGA finishes writing to one buffer segment, it generates an interrupt, and the driver immediately reprograms that segment for the next transfer while handing the filled segment to userspace. This is a classic double- or multi-buffering scheme. The buffer needs to be large enough to absorb bursts where the CPU or bus is briefly busy. For the userspace interface, I'd use `mmap` so the application can directly access the DMA buffers without copying — this is critical at high data rates. I'd also implement flow control: if userspace isn't consuming data fast enough, the driver should either drop the oldest data (with a flag indicating data loss) or block the FPGA's write enable, depending on the system requirements. For a medical device, dropping data silently is unacceptable, so I'd implement a mechanism where the driver tracks buffer overruns and reports them to userspace so the application can flag the data as incomplete. I'd also consider using the `vfio` framework or a pre-allocated contiguous buffer (via `dma_alloc_coherent`) to avoid scatter-gather complexity if the data rate is very high.

**Possible follow-ups:** How would you handle cache coherency between the DMA writes and the CPU reading the data? What if the FPGA needs to be paused when the buffer is full — how would you implement that backpressure?

## Q4: How would you approach debugging a kernel panic that occurs only on every third or fourth boot, with no consistent trigger?
**Answer:** Intermittent kernel panics are among the hardest problems to debug because they're often timing-related or caused by hardware that's marginally failing. I'd approach this systematically. First, I'd gather as much data as possible from each panic — enable `CONFIG_PANIC_ON_OOPS`, `CONFIG_KALLSYMS`, and ensure the console output is captured to a serial port or pstore so I can see the full stack trace even after reboot. I'd also enable `CONFIG_DEBUG_INFO` and `CONFIG_DEBUG_KERNEL` to get more context. The stack trace will tell me which subsystem is panicking — is it memory management, a specific driver, or the scheduler? If it's a NULL pointer dereference, I'd look at which driver is involved. Next, I'd check for hardware issues: marginal power supply, failing RAM, or a loose connection. I'd run memtest86+ overnight to rule out RAM issues. I'd also check the power rails with an oscilloscope during boot to see if there's droop or noise. If the panic is in a driver, I'd suspect a race condition in the driver's probe or initialization — perhaps two devices are initializing in a different order on each boot, or an interrupt arrives before the driver is fully ready. I'd add debug prints or use ftrace to trace the initialization sequence across boots. Another angle is to check if the panic correlates with a specific hardware revision or temperature. I'd also try to reproduce it under controlled conditions — booting in a loop with a script that logs the serial console, then analyzing the logs to find common patterns. If the panic is in the kernel core rather than a driver, I'd suspect memory corruption — perhaps a driver is writing out of bounds. I'd enable `CONFIG_SLUB_DEBUG` and `CONFIG_DEBUG_PAGEALLOC` to catch these. Finally, I'd bisect recent kernel or device tree changes if the issue appeared after an update.

**Possible follow-ups:** How would you use ftrace or kprobes to narrow down the race condition? What if the panic only happens when the system is under heavy I/O load — how would that change your approach?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during integration testing, you discover that the kernel's real-time scheduling class (SCHED_FIFO) is causing priority inversion on a shared hardware resource between your sensor driver and the display driver. The display team insists their driver needs the highest priority, and the sensor team says their data will be corrupted if they miss their deadline. How would you handle this situation?
**Answer:** Priority inversion on a shared resource is a classic real-time systems problem, and the first step is to make sure everyone understands the actual constraints rather than just their own priorities. I'd call a meeting with both teams and ask each to quantify their requirements: what's the sensor's hard deadline, what's the maximum acceptable latency for the display, and how often does each driver actually access the shared resource? Often, the real issue isn't the priority assignment itself but the fact that a high-priority task is blocking on a lock held by a lower-priority task. I'd first check whether the shared resource is protected by a spinlock or mutex — if it's a spinlock, a high-priority task could be spinning while a lower-priority task holds the lock, which is the worst case. The proper fix depends on the nature of the resource. If it's a hardware register or a small data structure, I'd consider using a lock-free approach like a seqlock or a per-CPU buffer. If locking is unavoidable, I'd implement priority inheritance — the kernel's `rt_mutex` does this automatically, but only if the drivers use `rt_mutex` rather than plain mutexes or spinlocks. I'd also look at whether the shared resource access can be serialized through a single dedicated thread with a known priority, rather than having both drivers access it directly. For the priority assignment itself, I'd ask the sensor team to prove their deadline — if they can demonstrate that missing a deadline corrupts patient data, that's a safety issue and takes precedence. But I'd also ask the display team whether their "highest priority" requirement is actually a hard real-time constraint or just a performance preference. In a medical device, the safety-critical sensor data should generally win, but I'd want to see the actual numbers. I'd also consider using the kernel's `sched_setattr` with `SCHED_DEADLINE` if the sensor has a well-defined period and execution time — this gives better guarantees than SCHED_FIFO. Finally, I'd document the decision and the rationale in the design documentation, since this will come up again during regulatory review.

**Possible follow-ups:** How would you verify that the priority inheritance mechanism is actually working in your system? What if the display team's requirement is also safety-critical — how would you resolve that conflict?
