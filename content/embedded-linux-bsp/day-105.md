# embedded-linux-bsp — Day 105

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder classes of bug because the kernel is telling you nothing is wrong, so the first move is to distrust the assumption that probe actually did what you think it did. I'd start by instrumenting the driver itself: add temporary `dev_info()`/`dev_dbg()` prints at each step of probe — resource acquisition, clock enable, regulator enable, register read-back, interrupt request — and confirm each one actually returns what I expect rather than just not failing. A very common cause is that probe succeeds because every call returned 0, but one of them returned 0 without doing anything useful: a regulator that was already on, a clock that was a no-op stub, a `devm_regulator_get_optional()` that returned a dummy regulator because the supply wasn't described in the device tree. So I'd verify the device tree binding matches what the driver expects — supply names, clock names, `reg` address, interrupt specifier — because a mismatch often degrades silently rather than erroring out.

Next I'd confirm the hardware is actually being touched: read back a known register (a chip ID or a reset-default value) over the bus and check it against the datasheet. If the read returns 0x00 or 0xFF, the bus isn't really talking — wrong address, wrong bus instance, pinmux not applied, or the peripheral's power rail never came up. I'd also check whether the driver's `of_match_table` actually matched the node (the `compatible` string is a classic silent mismatch), and whether the driver bound to the right device instance when there are multiple.

Finally, I'd verify the userspace-visible side: is the char device or sysfs node actually created, and does a read from it return the expected data? If probe succeeded but the device node was never registered, the "silence" is really a missing registration step. The discipline is to bisect the probe path into observable checkpoints rather than staring at the log waiting for an error that will never come.

**Possible follow-ups:** How would you tell the difference between a device tree binding mismatch and a hardware fault using only software-visible signals? What would you change in the driver to make this class of failure louder in the future?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our deltas on top, so we can pick up vendor updates without a merge war. The clean mechanism is `config fragments` combined with `KERNEL_FEATURES` or a `.scc`-style description, applied through the kernel's own `merge_config.sh` machinery rather than by editing a defconfig by hand. In practice I'd create a board-specific layer (or a `recipes-kernel/linux/` append inside our BSP layer) that adds a `.cfg` fragment containing only the options we need to change, and reference it from the kernel recipe via `SRC_URI` plus the appropriate `KERNEL_CONFIG_FRAGMENTS` or `KERNEL_FEATURES` variable. That way the vendor's recipe and defconfig stay untouched, and our fragment is a small, reviewable, version-controlled file.

The important discipline is that fragments should be additive and minimal — only the options that differ — and each should be documented with why it exists, because fragments silently drift out of relevance as the kernel version moves. I'd also make sure the fragment is validated in CI: a build that fails to apply a fragment should fail loudly, not silently fall back to the vendor config. For options that depend on other options (the classic `select`/`depends on` chains in Kconfig), I'd verify the final `.config` after merge rather than trusting the fragment alone, since a fragment can enable a symbol that then gets overridden by a later dependency resolution.

If the change is large enough that it can't be expressed as a fragment — say, a patch series to the vendor's driver — that goes in as a `.patch` in `SRC_URI` with the same layering discipline, and I'd keep the patch queue small and rebased regularly against vendor drops.

**Possible follow-ups:** How would you detect that a fragment has become stale or is silently conflicting with a vendor config change? What's the trade-off between a fragment and a full custom defconfig for a board with many deltas?

## Q3: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel log shows "Failed to request IRQ" for a device that worked on the previous board revision?

**Answer:** "Failed to request IRQ" almost always means the interrupt resource the driver is trying to claim is either not described correctly, already claimed by something else, or not actually wired to the SoC the way the driver assumes. I'd start by reading the full error and the return code — `-EBUSY` means someone else holds the line, `-ENXIO` or `-EINVAL` usually means the interrupt specifier in the device tree doesn't resolve to a valid hardware IRQ, and `-EPROBE_DEFER` would be a different story entirely. That distinction immediately narrows the search.

Then I'd compare the device tree interrupt properties between the working board revision and the new one: the interrupt parent, the specifier cells, the trigger type (level vs edge), and whether the GPIO or pinmux that routes the interrupt is configured. A very common cause on a board revision is that the interrupt line moved to a different GPIO or a different interrupt controller input, and the device tree wasn't updated to match — so the driver requests an IRQ number that either doesn't exist or belongs to another peripheral. I'd also check `/proc/interrupts` on the running system to see whether the line is already claimed, and whether the number the driver computed matches what the hardware actually asserts.

If the device tree looks right, I'd go down to the hardware: scope the interrupt line and confirm it actually toggles when the device signals, and confirm the pull-up/pull-down and polarity match what the driver expects. On a new board revision, a swapped polarity or a missing pull-up can make the line look permanently asserted or never asserted, which can manifest as a request failure or as a request that succeeds but never fires. I'd also verify the interrupt controller's own configuration — sometimes the parent controller needs its own resources (clock, power domain) up before child interrupts can be requested.

**Possible follow-ups:** How would you distinguish an interrupt that fails to request from one that requests successfully but never fires? What would you check first if the same driver works on one board revision and fails on another with identical device tree interrupt properties?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never block on anything the logging path controls, so the two paths need to be decoupled rather than sharing a lock naively. I'd start by identifying what the real-time task actually needs from the device — typically a register read or a short transfer with a bounded worst-case latency — and make that path lock-free or use a very short, priority-inheriting critical section that the logging path can never hold for long. The logging path, which can tolerate latency, would go through a separate mechanism: a ring buffer or FIFO in kernel memory that the real-time path writes into without blocking, and that the logging path drains at its own pace.

Concretely, I'd use a lockless single-producer/single-consumer ring buffer for the data handoff, with the real-time side doing only a bounded copy and an index update, and the logging side reading from the other end. If the device itself can only be accessed by one context at a time (a shared bus or a single register window), I'd serialize access with a mutex that the real-time path takes only for the minimum transaction, and ensure the logging path's transactions are chunked so they never hold the mutex across a long operation. Where the hardware supports it, I'd prefer to give the real-time path its own dedicated channel — a separate DMA stream, a separate FIFO, or a hardware mailbox — so the two paths don't contend at all.

I'd also think about priority: the real-time task should run at a priority that preempts the logging task, and any kernel work the logging path triggers (workqueues, threaded IRQs) should be at a lower priority so it can't invert. The verification is a latency measurement on the real-time path under worst-case logging load — if the logging path can ever cause a missed deadline, the decoupling isn't complete.

**Possible follow-ups:** How would you verify that the logging path truly cannot delay the real-time path, short of a full formal analysis? What changes if the device is on a shared I2C bus rather than a memory-mapped peripheral?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination problem first and a technical one second, because both teams are right about their own constraints and the risk is in the handoff. My first step would be to get the actual facts on the table in one place: exactly which pins the new peripheral needs, exactly which pinmux group the debug UART currently uses, and exactly what the manufacturing line depends on — is it the UART console specifically, or any early boot output, and at what stage of the line does it matter? Often the "manufacturing depends on it" claim turns out to be narrower than it sounds, and clarifying that changes the options.

Then I'd lay out the options with their costs rather than arguing for one: keep the UART where it is and find the new peripheral different pins; move the UART and update the device tree and bootloader together with a coordinated change window; or move the UART but preserve early console output on the old pins through the bootloader stage and switch later. Each has a different risk profile and schedule impact, and the decision should be made against the project's actual constraints — clinical trial timeline, manufacturing qualification status, and whether the new peripheral is truly required now.

If a change is needed, I'd insist on a joint verification plan: the bootloader and device tree changes go in together, the manufacturing line gets a dry run with the new build before the old one is retired, and there's a documented rollback. I'd also make sure the decision and its rationale are recorded, because in a regulated medical context the traceability of "why did we move this pin" matters later. The behavioral point is that I'd rather surface the conflict early and drive it to a documented decision than let either team quietly work around the other.

**Possible follow-ups:** How would you handle it if the hardware team had already committed the pin change in a board spin before raising it with software? What would you do if the manufacturing team insisted on zero change to the early boot console?
