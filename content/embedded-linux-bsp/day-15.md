# embedded-linux-bsp — Day 15

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of the two identical I2C temperature sensors on the same bus, while the other one works fine?

**Answer:** This is a classic "works on one instance, not the other" problem that usually points to something specific to that particular device instance rather than the bus or driver as a whole. I'd start by checking the obvious: is the sensor actually powered? Is its address line strapped correctly, or did the address pins get populated with the wrong pull-up/pull-down resistors during assembly? I'd verify the device tree entry matches the actual hardware — maybe the second sensor is at a different I2C address than what's in the DT, or the reg property is wrong. I'd also check the schematic against the actual board — sometimes there's a footprint error or a missing solder bridge. If the hardware checks out, I'd look at the kernel side: does the driver probe fail, or does it probe but fail to communicate? I'd enable dynamic debug for the I2C subsystem and the sensor driver to see if there are NAKs or timeouts. I'd also check whether the sensor's interrupt line (if it has one) is properly configured — a misconfigured interrupt can prevent probe if the driver requires an interrupt to bind. Finally, I'd compare the working sensor's sysfs/debugfs entries against the non-working one to isolate where the difference appears.

**Possible follow-ups:**
- How would you distinguish between a hardware address-strap issue and a device tree configuration error?
- What if both sensors are at the same address — how would you handle that in the device tree?

## Q2: How would you approach implementing a kernel driver for a device that needs to perform a hardware-triggered DMA transfer, where the trigger comes from an external sensor's interrupt line, and the data must be processed and made available to userspace within a hard real-time deadline (e.g., 2 ms)?

**Answer:** The key here is to minimize latency at every stage while ensuring the data path is deterministic. First, I'd use a threaded interrupt handler for the sensor's IRQ — the hard IRQ handler should do the minimum (acknowledge the interrupt, possibly disable it) and defer the actual work to the threaded context, which can sleep and call DMA API functions. For the DMA transfer itself, I'd use the DMA engine API with a pre-allocated, coherent DMA buffer to avoid cache coherency issues and allocation latency. The transfer should be set up in advance — the descriptor prepared, the callback registered — so that when the interrupt fires, the driver just needs to submit the descriptor. After the DMA completes, the completion callback runs in softirq context; I'd use a completion variable or a wait queue to wake a kernel thread that does any necessary processing (e.g., byte-swapping, scaling) and then copies the data to a ring buffer accessible from userspace. For the userspace interface, I'd use a character device with read() and poll() support, or possibly mmap for zero-copy if the data volume justifies it. To meet the 2 ms deadline, I'd need to budget the time: interrupt latency, DMA setup, transfer time, and wake-up latency. If the DMA transfer itself takes longer than the deadline, I'd need to reconsider the approach — perhaps double-buffering so one buffer is being processed while the next is being filled. I'd also verify that the DMA channel has sufficient priority and that no other driver can monopolize it.

**Possible follow-ups:**
- How would you handle the case where the DMA transfer occasionally takes longer than the deadline?
- Would you use a kernel thread or a workqueue for the post-processing, and why?

## Q3: How would you approach designing a device tree binding for a custom FPGA peripheral that has multiple memory-mapped register banks, generates several interrupts, and needs to share a DMA channel with another peripheral?

**Answer:** I'd start by thinking about how the peripheral should be modeled — is it one logical device with multiple functions, or several logical devices that happen to live in the same FPGA? If it's one device with multiple functions, I'd create a single node with multiple register ranges (using reg with multiple entries, each with its own address and size) and multiple interrupt entries (using interrupts with the appropriate flag for each). The DMA channel sharing is the tricky part. I wouldn't put the DMA channel directly in the FPGA node's DT binding — instead, I'd model the DMA controller as a separate node, and have the FPGA node reference it via a phandle, using the standard dmas/dma-names properties. The DMA channel allocation itself should be handled by the DMA controller driver, which can arbitrate between consumers. If the two peripherals genuinely need to share a single channel, I'd need to think about arbitration — either the FPGA node gets the channel exclusively and the other peripheral requests it through a different mechanism, or the DMA controller driver supports multiplexing. In practice, I'd probably recommend using two separate channels if the hardware allows it, because sharing a single DMA channel between two independent peripherals introduces contention and makes the timing unpredictable. If sharing is unavoidable, I'd document the arbitration policy in the binding and implement a mutex or similar mechanism in the DMA controller driver.

**Possible follow-ups:**
- How would you handle the case where the FPGA bitstream changes and the register map shifts?
- What if the two peripherals need to use the DMA channel simultaneously — how would you arbitrate?

## Q4: How would you approach structuring the root filesystem for an embedded Linux medical device that needs to support over-the-air (OTA) updates with a rollback mechanism, while ensuring that patient data and configuration settings survive the update process?

**Answer:** I'd use a redundant A/B partition scheme for the root filesystem, with the bootloader selecting which partition to boot based on a "try count" or "boot success" flag. The root filesystem itself would be read-only — this is important for both reliability and security in a medical device. The read-only rootfs contains the kernel modules, applications, and libraries, all of which are replaced atomically during an update. Patient data and configuration would live on a separate, persistent data partition that is mounted read-write. This partition is never touched during an update, so it survives the process intact. For the update mechanism itself, I'd write the new image to the inactive partition, verify its integrity (checksum, possibly signature verification), then set a flag in a small metadata area (often in the bootloader environment or a dedicated partition) indicating that the new partition should be tried. After booting the new partition, the application would perform a self-test — verifying that critical services start, sensors are accessible, and the system is functional. If the self-test passes, the application clears the "try" flag, making the new partition permanent. If the system fails to boot or the self-test fails, the bootloader detects the failed attempt and automatically falls back to the previous partition. This gives us a robust rollback mechanism without requiring user intervention. For the data partition, I'd use a journaling filesystem like ext4 or UBIFS (for raw NAND) to minimize corruption risk on power loss, and I'd consider using fdatasync or fsync at critical write points to ensure data is actually on disk.

**Possible follow-ups:**
- How would you handle the case where the update itself is corrupted mid-write?
- How would you ensure that the application's self-test is thorough enough to catch real problems but fast enough to not delay boot significantly?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the manufacturing team reveals that the PCB for the main processor board has a routing error: the I2C pull-up resistors for a critical sensor bus are connected to the wrong voltage rail (3.3V instead of 1.8V). The sensor is rated for 1.8V I2C, and the board is already in production. The project is three weeks from the start of a clinical trial. How would you handle this situation?

**Answer:** This is a serious issue, but it's important to stay calm and assess the actual risk before jumping to a solution. First, I'd want to understand the electrical implications: is the sensor's I2C pins truly not tolerant to 3.3V, or is there some protection? I'd check the sensor's absolute maximum ratings and the I2C bus voltage specifications. If the sensor is genuinely at risk of damage, then running the clinical trial with these boards is not acceptable. I'd also check whether the pull-ups are actually needed at 1.8V — if the sensor has internal pull-ups or if the bus master can operate with weaker pull-ups, there might be a workaround. The immediate options are: (1) rework the boards — either remove the pull-ups and add external ones to the correct rail, or cut traces and bodge-wire to the 1.8V rail; (2) redesign the board and expedite a new batch — but that's likely more than three weeks; (3) use a level shifter or a different sensor variant that's 3.3V tolerant. I'd work with manufacturing to understand the rework cost and yield, and with the hardware team to determine if a rework is feasible. In parallel, I'd assess whether the firmware can mitigate — for example, if the sensor can operate at 3.3V with reduced reliability, or if we can configure the I2C controller to use open-drain with weaker pull-ups. I'd also involve the regulatory and clinical teams to understand the impact of a delay. Ultimately, I'd present the options with their risks and trade-offs to the project stakeholders and let them make the call, but I'd strongly recommend reworking the boards if the sensor is at risk, even if it means a short delay — a failed clinical trial due to sensor damage would be far worse.

**Possible follow-ups:**
- How would you prioritize between meeting the clinical trial deadline and ensuring the hardware is safe?
- What if the manufacturing team says rework is not feasible and the only option is a board redesign — how would you handle that?
