# embedded-linux-bsp — Day 113

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is usually a sign that the driver is talking to the wrong thing, or talking to the right thing in the wrong way, rather than that the hardware is dead. My first move is to verify the driver is actually bound to the device I think it is: check `/sys/bus/<bus>/devices/` and the driver's sysfs symlink, and confirm the device tree node the driver matched is the one I intended (a common trap is a stale or duplicated node, or a `compatible` string that matches a fallback entry in the driver's ID table). Next I'd confirm the register accesses are landing where I expect — read back a known register (an ID or revision register is ideal) and compare against the datasheet; if the read returns all-ones or all-zeros, the address translation, clock gating, or power domain is suspect even though `probe()` returned 0. I'd also check that the driver isn't silently swallowing errors: many `probe()` paths return success after a failed optional step (regulator, clock, reset) because the error was treated as non-fatal. Instrumenting with `dev_dbg`/dynamic debug, or a quick `devmem` read from userspace, usually narrows it down fast. Finally, I'd sanity-check the hardware path itself — is the peripheral actually powered, is the reset line released, is the bus clock running — because a driver can "succeed" against a peripheral that never came out of reset.

**Possible follow-ups:** How would you tell the difference between a driver bug and a hardware bring-up problem in that scenario? What would you check first if the ID register read back correctly but every subsequent access failed?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and express only the delta in my own layer. I'd create a `.bbappend` in my board layer that points at the vendor recipe by name and version, and use the kernel's configuration-fragment mechanism (`SRC_URI` entries of type `file` with the `cfg` fragment, plus `KERNEL_CONFIG_FRAGMENTS` or the `merge_config`/`config-fragments` class depending on the release) so my fragment is merged on top of the vendor defconfig rather than replacing it. The fragment itself should contain only the options I actually need to change, with the `CONFIG_...=y/m` lines and any dependencies called out, because a fragment that silently drops options is worse than no fragment. I'd keep the fragment in a versioned directory so it can track kernel version bumps, and I'd add a build-time check — a small task or a `do_configure` sanity step — that greps the final `.config` to confirm my options survived the merge. That last step matters because fragment merge order and `select`/`depends on` interactions in Kconfig can quietly override an option, and catching that at build time is far cheaper than catching it on a board.

**Possible follow-ups:** What happens if two fragments in the same build set the same option to different values, and how would you control the merge order? How would you handle an option that the vendor kernel doesn't expose at all because it's behind a patch?

## Q3: How would you approach debugging a situation where a custom board running Linux boots successfully, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts?

**Answer:** `EINTR` means a signal was delivered while the process was blocked in a slow or interruptible syscall, and the daemon's error handling treats that as fatal instead of retrying. The first question is *which* signal and *who* sent it — I'd check whether the daemon installs handlers for `SIGCHLD`, `SIGALRM`, `SIGUSR1`, or similar, whether a watchdog or supervisor is sending periodic signals, and whether the process is in a process group that receives terminal or job-control signals. I'd also look at whether the driver's `ioctl` path is sleeping interruptibly (e.g., waiting on a completion or a mutex with `TASK_INTERRUPTIBLE`) and whether it returns `-ERESTARTSYS` correctly, because a driver that returns `-EINTR` directly from a wait can surface spurious interruptions to userspace. On the userspace side, the correct pattern is to loop on `EINTR` for any syscall that can be interrupted, and to use `SA_RESTART` where appropriate — but I'd fix the root cause rather than just paper over it, since a signal arriving at a bad moment can also indicate a real race. If the signal turns out to be benign and expected, the fix is the retry loop; if it's unexpected, the fix is finding what's generating it.

**Possible follow-ups:** How would you determine which signal interrupted the syscall without adding a lot of instrumentation? What's the difference between a driver returning `-ERESTARTSYS` and `-EINTR`, and why does it matter to userspace?

## Q4: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace application that `mmap()`s a register region of a custom FPGA peripheral and reads from it gets a segmentation fault on production hardware, while the same binary works on the development board. How would you approach this?

**Answer:** A segfault on `mmap`'d register access almost always comes down to the mapping being wrong, not the application logic. I'd start by comparing the device tree memory node and the `reg` property between the two boards — a different base address, size, or `ranges` translation in the FPGA bridge node would produce exactly this symptom, and it's the most common cause when the same binary works on one board and not another. Next I'd check the driver's `mmap` implementation: whether it uses `remap_pfn_range` with the correct physical address and length, whether it validates the offset and size against the resource, and whether the VMA flags (`VM_IO`, cache attributes) are appropriate — a mapping that's too small or misaligned will fault on the first access past the boundary. I'd also verify the FPGA is actually configured and its bridge is up before the application runs, since accessing an unconfigured or unclocked region can produce a bus abort that surfaces as a segfault. On the production board specifically, I'd check for differences in the bootloader's FPGA load sequence, the bridge's address decode setup, and whether the kernel's reserved-memory or `no-map` regions overlap the FPGA window. A quick `devmem` read at the expected physical address from userspace, plus a look at `/proc/iomem`, usually tells me whether the problem is in the mapping or in the hardware path.

**Possible follow-ups:** How would you distinguish a segfault caused by a bad VMA from one caused by a bus abort on the peripheral? What would you check in the device tree if the FPGA window size differs between the two boards?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination problem first and a technical one second, because both teams are right about their own constraints. I'd start by getting the actual requirement on the table: which pins the new peripheral needs, whether the UART move is the only option or one of several, and what the manufacturing line's dependency on the early console actually is — is it a hard requirement for every unit, or a diagnostic convenience that could be met another way. Then I'd lay out the technical cost honestly: the pinmux change touches the bootloader's early console setup, the device tree, and possibly the kernel command line, so it's not a one-line change, but it's also not unbounded. I'd propose a path that de-risks it — for example, keeping the current UART as the manufacturing console and adding the new peripheral on the freed pins only if the hardware team can confirm the new peripheral doesn't need those specific pins, or staging the change behind a board revision so the manufacturing line has a stable target during the transition. The key is to make the trade-off explicit and get a decision from the people who own the schedule and the line, rather than letting the two teams negotiate it indirectly through review comments.

**Possible follow-ups:** How would you validate that the early boot console still works after the pinmux change, given that it's used before the kernel is up? What would you do if the hardware team insists the change is non-negotiable and the manufacturing line insists the console can't move?
