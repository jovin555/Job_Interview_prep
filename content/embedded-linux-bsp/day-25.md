## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel log shows "Failed to request IRQ" for a device that worked on the previous board revision?

**Answer:** I'd start by treating this as a regression between two hardware revisions, which narrows the investigation. First, I'd confirm the exact IRQ number and which device is failing — the kernel log usually identifies both. Then I'd check whether the IRQ is actually being claimed by another driver or is unavailable at the time the device probes. A common cause is a change in probe order: if the previous board revision had a different device ordering or timing, the failing device might now probe before its interrupt controller or GPIO expander is ready. I'd look at the device tree to verify the interrupt parent and interrupt number are correct for the new board revision — sometimes a hardware change (e.g., moving a pin to a different GPIO bank) isn't reflected in the device tree. I'd also check whether the interrupt line is actually being asserted or held in an unexpected state on the new board, which can cause the request to fail if the driver uses `IRQF_TRIGGER_*` flags that don't match the hardware. Using `cat /proc/interrupts` and checking the GPIO controller's status can help determine if the line is already allocated. Finally, I'd compare the kernel configuration and device tree between the two board revisions to isolate what changed.

**Possible follow-ups:** How would you determine whether the issue is a device tree problem versus a hardware wiring problem? What if the IRQ is shared with another device — how would that change your approach?

## Q2: How would you approach implementing a kernel driver for a device that needs to perform a hardware-triggered DMA transfer, where the trigger comes from an external sensor's interrupt line, and the data must be processed and made available to userspace within a hard real-time deadline (e.g., 2 ms)?

**Answer:** The key design constraint is that the 2 ms deadline includes interrupt latency, DMA setup, DMA completion, and the userspace notification path. I'd structure the driver around a threaded interrupt handler so that the hard IRQ handler stays minimal — just acknowledging the interrupt and triggering the DMA — while the heavy lifting happens in the threaded context, which can sleep if needed. For DMA, I'd use the kernel's DMA engine API with a pre-allocated, coherent DMA buffer to avoid allocation latency in the hot path. The buffer would be a ring buffer so that if the userspace consumer is slow, the driver can either drop the oldest data or flag an overrun rather than blocking. For the userspace notification, I'd use a combination of `poll()`/`epoll()` and a `miscdevice` with `read()` semantics, ensuring that the data is copied to userspace using `copy_to_user` in the read path rather than in the interrupt context. If the 2 ms deadline is truly hard, I'd also consider whether the CPU can be dedicated or isolated, and whether the DMA completion interrupt needs a higher priority than other interrupts. I'd also verify that the DMA controller's transfer size and burst settings are tuned so the transfer completes well within the budget, leaving margin for scheduling jitter.

**Possible follow-ups:** How would you handle the case where the sensor generates data faster than userspace can consume it? What if the DMA transfer itself takes longer than the deadline — how would you detect and handle that?

## Q3: How would you approach designing the boot sequence for a system with two processors — an application processor running Linux and a safety-critical microcontroller — where the microcontroller must be fully initialized and running its safety monitoring routines before the Linux userspace starts any critical applications?

**Answer:** The core requirement is that the safety-critical microcontroller must be in a known, verified state before any Linux userspace application that depends on it begins. I'd structure the boot sequence in stages. First, the bootloader (U-Boot) would power up the microcontroller, either by releasing it from reset or by writing to a mailbox register, and then wait for a handshake — for example, the microcontroller writing a "ready" status to a shared memory location or asserting a GPIO line. The bootloader would poll this with a timeout, and if the microcontroller fails to become ready, the bootloader would halt or fall back to a safe state rather than continuing to boot Linux. Once the handshake is received, the bootloader proceeds to load the kernel. In the kernel, I'd have a driver that performs a second, more detailed handshake — verifying the microcontroller's firmware version, checking its self-test results, and confirming that safety monitoring is active. This driver would be a built-in (not a module) and would be probed early, before any critical userspace services start. The init system (e.g., systemd) would have an ordering dependency: the critical application services would have `After=` and `Requires=` on the service that confirms the microcontroller handshake. If the handshake fails, the service would fail, and the system would enter a safe state — for example, shutting down or displaying an error rather than proceeding with normal operation.

**Possible follow-ups:** How would you handle the case where the microcontroller needs a firmware update — how would that affect the boot sequence? What if the handshake times out during boot — should the system retry or fail?

## Q4: How would you approach implementing a kernel driver for a device that needs to be accessed by both a real-time safety-critical task and a non-real-time monitoring task, where the safety-critical task must never be blocked by the monitoring task?

**Answer:** The fundamental principle is that the safety-critical path must have guaranteed access to the hardware, regardless of what the monitoring task is doing. I'd design the driver with separate access paths: the safety-critical task would use a dedicated interface (e.g., a character device with `O_RDWR` opened with real-time scheduling priority, or a netlink socket) that bypasses any locking that the monitoring path uses. The driver would use a lock-free or priority-inheritance-aware mechanism for the shared hardware. For example, if both tasks need to read from the same sensor, I'd use a seqlock or a per-CPU buffer so that the monitoring task can read a snapshot without blocking the safety-critical task. Alternatively, I'd give the safety-critical task exclusive access to the hardware and have the monitoring task read from a shadow buffer that the driver updates after each safety-critical read. If the hardware itself can only be accessed by one task at a time, I'd use a mutex with priority inheritance (`rt_mutex`) so that if the monitoring task holds the lock, the safety-critical task's priority is temporarily inherited, preventing priority inversion. I'd also ensure that the monitoring task's operations are interruptible (`mutex_lock_interruptible`) so it can be killed if it misbehaves, and that the safety-critical task's operations are non-blocking or have a bounded wait with a timeout. Finally, I'd verify the design with stress testing — running the monitoring task at high frequency while measuring the safety-critical task's worst-case latency.

**Possible follow-ups:** How would you handle the case where the monitoring task needs to configure the device (e.g., change sampling rate) while the safety-critical task is actively reading? What if the hardware has a shared interrupt line — how would you ensure the safety-critical task isn't delayed by the monitoring task's interrupt handling?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the manufacturing team reveals that the PCB for the main processor board has a routing error: the I2C pull-up resistors for a critical sensor bus are connected to the wrong voltage rail (3.3V instead of 1.8V). The sensor is rated for 1.8V I2C, and the board is already in production. The project is three weeks from the start of a clinical trial. How would you handle this situation?

**Answer:** This is a serious issue because it could damage the sensor or cause unreliable communication, which is unacceptable for a medical device. My first step would be to confirm the severity: I'd work with the hardware team to determine whether the sensor is actually at risk of damage or if it's just a marginal violation of the absolute maximum ratings. If the sensor can tolerate 3.3V on the I2C lines for a limited time, we might have options, but if it can't, we need to stop production immediately. I'd then assess the impact: how many boards are affected, and can we rework them? Reworking the pull-up resistors to the correct rail might be feasible if the board design allows it — for example, if there's a cut-and-jumper option. If rework isn't possible, we'd need to decide whether to scrap the affected boards or use a workaround, such as a level-shifter daughterboard, though that adds complexity and risk. In parallel, I'd work with the clinical trial team to understand the schedule impact and whether the trial can be delayed. I'd also initiate a formal root-cause analysis (e.g., 8D) to understand how the routing error escaped the design review and what process changes are needed to prevent recurrence. Throughout, I'd keep the project stakeholders informed with a clear risk assessment and a decision matrix: rework, scrap, or workaround, with cost and schedule implications for each. The key is to be transparent about the risk and not proceed with the clinical trial until we're confident the hardware is safe and reliable.

**Possible follow-ups:** How would you decide between reworking the boards versus scrapping them and re-spinning the PCB? What if the clinical trial cannot be delayed — would you consider proceeding with a workaround, and how would you document the risk?
