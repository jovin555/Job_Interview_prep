## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of two identical I2C sensors on the same bus, while the other works fine?

**Answer:** I'd start by confirming the problem is at the hardware level versus the software level, since two identical devices on the same bus failing asymmetrically often points to a board issue. First, I'd check the kernel logs with `dmesg` to see if the missing sensor is being probed at all — whether there's an I2C NAK, a timeout, or no attempt. If there's no probe attempt, I'd verify the device tree: is the second sensor's node present, is its address correct, and does it have the right compatible string? A common mistake is a typo in the reg property or a duplicate address that causes the I2C core to skip it. If the probe is attempted but fails, I'd use `i2cdetect` from userspace to see if the device responds on the bus at all. If it doesn't respond, I'd suspect a hardware issue: a cold solder joint, a missing pull-up on that particular device's lines, or an address strapping error on the sensor itself. I'd also check whether the two sensors share a reset line or power rail — if one is being held in reset or not powered, that would explain the asymmetry. If the device responds to `i2cdetect` but the kernel driver still fails, I'd compare the register dumps from both sensors to see if the failing one is in an unexpected state, perhaps requiring a different initialization sequence or a longer power-up delay.

**Possible follow-ups:**
- How would you determine whether the issue is a device tree problem versus a hardware problem, and what's the fastest way to isolate it?
- If the sensor responds to `i2cdetect` but the driver probe fails, what would you check next?

## Q2: How would you approach designing the inter-processor communication (IPC) mechanism for a system with an application processor running Linux and a safety-critical microcontroller handling sensor acquisition, where the safety-critical side must never be blocked by Linux?

**Answer:** The fundamental design principle is that the safety-critical microcontroller must own the shared resources and the timing — Linux is the guest, not the other way around. I'd start by defining the data flow: what data moves in each direction, at what rate, and what the latency and freshness requirements are. For the physical transport, I'd typically use a shared memory region for bulk data transfer, with a doorbell mechanism (mailbox or interrupt line) for signaling. The shared memory needs a well-defined protocol — a ring buffer or a double-buffer scheme with sequence numbers — so that both sides can detect corruption or stale data. The critical design choice is that the microcontroller writes the data and the Linux side reads it; the microcontroller never blocks waiting for Linux. On the Linux side, I'd implement the driver as a character device that reads from the shared region, using interrupts to wake a kernel thread rather than polling. For the safety-critical side, I'd ensure it has a watchdog on the communication: if Linux doesn't consume data within a defined window, the microcontroller continues operating with its last known-good state or falls back to a safe mode. I'd also partition memory carefully — the shared region should be cache-coherent or use explicit cache maintenance operations, and the memory should be reserved so Linux never allocates over it. Finally, I'd define a handshake protocol for initialization so that Linux can't start reading until the microcontroller signals it's ready, and I'd include a version field in the shared structure to catch mismatched firmware.

**Possible follow-ups:**
- How would you handle the case where the Linux side crashes and stops consuming data — what does the microcontroller do?
- What are the trade-offs between using a mailbox interrupt versus polling the shared memory on the Linux side?

## Q3: How would you approach implementing a kernel driver for a device that needs to perform a hardware-triggered DMA transfer, where the trigger comes from an external sensor's interrupt line, and the data must be processed and made available to userspace within a hard real-time deadline (e.g., 2 ms)?

**Answer:** The key is to minimize the latency path from the hardware interrupt to the userspace consumer while ensuring the DMA transfer is set up correctly before the trigger arrives. I'd structure the driver with three main components: the interrupt handler, the DMA completion path, and the userspace interface. In the interrupt handler, I'd avoid any heavy work — just acknowledge the interrupt and either start the DMA transfer immediately (if the hardware allows the sensor interrupt to directly trigger DMA) or schedule a tasklet/threaded IRQ to start it. If the hardware supports it, the ideal design is to have the sensor interrupt line connected to the DMA controller's hardware trigger, so the transfer starts without CPU involvement. For the DMA setup, I'd pre-allocate and pre-configure the DMA descriptors in advance so that starting a transfer is just a matter of writing a register. On DMA completion, the completion callback runs in interrupt context, so I'd do minimal processing there — perhaps just updating a timestamp and waking a kernel thread that does the data processing. For the userspace interface, I'd use a ring buffer of pre-allocated buffers that userspace can mmap, avoiding copies. The userspace application would block on a poll or read, and the driver would signal it via a wait queue. To meet a hard 2 ms deadline, I'd also need to consider the scheduling policy of the userspace thread — it should be a real-time thread (SCHED_FIFO) with appropriate priority, and the driver should use `wake_up_all` with a high-priority wait queue. I'd also profile the actual latency on the target hardware to find bottlenecks — interrupt latency, DMA setup time, cache effects, and scheduling jitter all add up.

**Possible follow-ups:**
- How would you measure and verify that you're actually meeting the 2 ms deadline under worst-case conditions?
- What are the trade-offs between doing the data processing in the kernel versus in userspace?

## Q4: How would you approach debugging a situation where a custom board running Linux boots successfully, but the root filesystem on an eMMC device becomes read-only after a few hours of operation, with "I/O error" messages appearing in the logs?

**Answer:** This pattern — the filesystem going read-only after extended operation — almost always indicates the kernel detected an unrecoverable I/O error and remounted the filesystem read-only to prevent further corruption. I'd start by examining the full kernel log to find the first I/O error, not the later ones that are consequences. The first error message will tell me whether it's a command timeout, a CRC error, or a hardware reset. I'd look at the eMMC controller's error counters and the device's health indicators. Common causes include: marginal signal integrity on the eMMC data lines that only manifests under certain temperature or voltage conditions; a power supply issue where the eMMC's voltage rail droops under load; or a firmware bug in the eMMC device itself that causes it to hang after a specific sequence of operations. I'd also check whether the errors correlate with specific operations — for example, do they happen during heavy write activity, or during a particular filesystem operation like journal commits? If the errors are write-related, I'd suspect the eMMC's write cache or a power management feature like the sleep/wake transition. I'd also check the kernel's eMMC tuning parameters — maybe the bus speed or timing mode is set too aggressively for this particular eMMC part. To isolate, I'd run a stress test that exercises the eMMC heavily while monitoring voltage rails and temperature, and I'd try reducing the bus speed or disabling certain features (like cache or packed commands) to see if the errors stop. If the issue is reproducible, I'd capture the eMMC controller registers at the moment of failure to understand what state the device is in.

**Possible follow-ups:**
- How would you determine whether the root cause is a hardware issue versus a software configuration issue?
- What changes would you consider making to the kernel configuration or device tree to improve eMMC reliability?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the manufacturing team reveals that the PCB for the main processor board has a routing error: the I2C pull-up resistors for a critical sensor bus are connected to the wrong voltage rail (3.3V instead of 1.8V). The sensor is rated for 1.8V I2C, and the board is already in production. The project is three weeks from the start of a clinical trial. How would you handle this situation?

**Answer:** First, I'd want to understand the full scope of the problem before proposing solutions. I'd ask the hardware team to confirm the electrical impact: is the sensor's I2C pins being overvolted, or is it just the pull-ups that are at the wrong level? If the sensor's pins are being exposed to 3.3V through the pull-ups, that's a reliability risk — the sensor might work initially but could fail over time or under certain conditions. I'd also check whether the sensor has internal protection or if the I2C bus has other devices that might be affected. Once I understand the risk, I'd evaluate options in parallel. The first option is a board rework — can the pull-ups be lifted and reconnected to the 1.8V rail with a bodge wire? This is feasible if the board has accessible test points or if the pull-up resistors are near the edge of the board. The second option is a software workaround — can the I2C bus be configured to use open-drain with the sensor's internal pull-ups, or can we disable the external pull-ups entirely? This depends on the sensor's internal design and the bus capacitance. The third option is to assess whether the 3.3V pull-up actually causes a functional problem — sometimes the sensor's I2C pins are 3.3V tolerant even if the logic levels are 1.8V, and the bus might work reliably. I'd want the hardware team to do a thorough analysis and, if possible, a quick bench test with a modified board to verify. Given the three-week timeline, I'd also consider whether we can qualify the boards as-is with additional testing, or whether we need to delay the clinical trial. In parallel, I'd work with the regulatory and quality teams to document the issue and the risk assessment — for a medical device, this needs to be tracked as a non-conformance with a formal disposition. I'd also check if there's an alternative sensor or a different board revision that could be used for the clinical trial, even if it means a smaller number of devices. The key is to make a data-driven decision quickly, with input from hardware, quality, and regulatory, rather than unilaterally deciding to proceed or delay.

**Possible follow-ups:**
- How would you weigh the risk of proceeding with the boards as-is versus the cost of delaying the clinical trial?
- What documentation or regulatory considerations would you need to address if you decide to proceed with a rework?
