# embedded-linux-bsp — Day 124

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is almost always a case of the driver talking to the right address but the wrong thing, or the hardware not being in the state the driver assumes. I'd work outward from the driver in layers. First, confirm the driver is actually bound to the intended device: check `/sys/bus/.../devices/` and the driver's sysfs symlink to verify the device tree node that probed is the one I think it is — a common trap is a stale or duplicated node, or an `okay` status on a node the hardware doesn't populate. Second, verify register access at the lowest level: read back a known register (a chip ID or revision register is ideal) and confirm the value matches the datasheet. If the read returns all-ones or all-zeros, the bus transaction is completing but the peripheral isn't responding — that points at address strapping, chip-select, or a missing power/clock enable that the driver never asserted because it assumed the bootloader left it on. Third, check the power and clock state: regulators enabled, clocks running at the expected rate, reset lines de-asserted. A driver that "succeeds" without touching these will happily return 0 while the silicon sits unpowered. Fourth, instrument the driver with register dumps at each init step and compare against a known-good reference (a dev board, or a logic analyzer capture on the bus). If the bus shows no traffic at all, the issue is above the driver — pinmux, bus controller, or the device never being matched. I'd also verify the compatible string matches exactly and that no other driver claimed the region first. The discipline is: don't trust `probe()` returning 0 as evidence the hardware works; prove it with a read-back.

**Possible follow-ups:** How would you tell the difference between a pinmux problem and a power/clock problem using only software-visible state? What would you add to the driver permanently so this class of failure is caught in bring-up next time?

## Q2: How would you approach deciding whether a peripheral driver should be built into the kernel image versus built as a loadable module, for a device that must be functional before the root filesystem is mounted?

**Answer:** The deciding question is dependency order: what does the driver need to be present for, and what does it itself depend on? If the peripheral is needed to mount the root filesystem — the storage controller, the bus it sits on, any regulator or clock driver in that chain — it must be built in, because modules live on the very filesystem you're trying to mount. That's a hard constraint, not a preference. Beyond that, I weigh a few things. Built-in costs image size and boot time (all initcalls run whether or not the hardware is present) but removes the userspace/firmware-loading dependency and simplifies the boot chain. A module is better when the driver is large, optional, or needs firmware loaded from the rootfs, and when you want the ability to reload it during development without reflashing. For a device that must work before rootfs mount, I'd also check whether the driver needs firmware at probe time — if so, either build the firmware into the kernel/initramfs or use an initramfs that carries the modules and firmware. The practical answer for early-boot-critical peripherals is usually built-in, with the module path reserved for things that come up after userspace. I'd document the reasoning in the BSP so the next person doesn't flip it casually.

**Possible follow-ups:** How does an initramfs change this decision? What kernel configuration options control whether a driver can even be a module?

## Q3: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to never touch the vendor's recipe or their defconfig directly, so upstream updates stay mergeable. I'd use the kernel's configuration fragment mechanism through the `linux-yocto`-style `.scc`/`.cfg` metadata, or for a vendor kernel recipe that supports it, the `SRC_URI` fragment append pattern: add a `.cfg` file to the board's layer and append it to `SRC_URI` with the appropriate override so the build system merges it on top of the base config. The fragment contains only the deltas — the options this board needs enabled or disabled — not a full defconfig, so it stays small and reviewable. I'd put it in a board-specific layer (or a `meta-<board>` sub-layer) with a clear naming convention, and wire it in via a `.bbappend` that appends to `SRC_URI` rather than replacing the recipe. For options that must be present, I'd consider `KERNEL_FEATURES` or a config check so the build fails loudly if a required option didn't take, rather than silently producing a kernel missing a driver. The key discipline: fragments are additive and declarative, the vendor recipe is untouched, and there's a verification step that the merged config actually contains what the board needs.

**Possible follow-ups:** How would you catch a case where two fragments set the same option to conflicting values? What's the risk of using `KERNEL_FEATURES` versus a plain `SRC_URI` fragment?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** Intermittent fallback means the boot logic is treating a failure as recoverable and moving to the next boot target in its list — so the real question is why the eMMC path sometimes fails, and why the fallback exists at all. I'd start by making the boot sequence observable: enable verbose U-Boot output, and capture the console across many cold boots to see whether the eMMC init, partition read, or kernel load is the step that fails, and whether the failure correlates with power-on vs. warm reset, temperature, or supply ramp. Common root causes are eMMC initialization timing (the part not ready within the timeout the bootloader allows), a marginal supply or reset timing on the eMMC, or a corrupted/partial environment that changes `bootcmd`. I'd also inspect the environment itself: is `bootcmd` a fallback chain, and is the network boot target present because of a default or a stale saved environment? If the fallback was never intended, the fix has two parts — remove or guard the unintended network path so a failure is loud rather than silent, and fix the underlying eMMC reliability issue. I'd verify with a soak test across many power cycles, not a single boot, since the failure is intermittent. The principle: a silent fallback masks a real fault, so make the primary path's failure visible before removing the safety net.

**Possible follow-ups:** How would you distinguish an eMMC init-timing problem from a corrupted U-Boot environment? Where would you look to confirm the fallback is coming from `bootcmd` versus a saved environment variable?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during integration testing you discover that the kernel's real-time scheduling class (SCHED_FIFO) is causing priority inversion on a shared hardware resource between your sensor driver and the display driver. The display team insists their driver needs the highest priority, and the sensor team says their data will be corrupted if they miss their deadline. How would you handle this situation?

**Answer:** First I'd reframe it from a priority argument into a shared-resource argument, because that's what it actually is — two real-time consumers contending for one resource, and priority alone can't fix a priority inversion; you have to fix the sharing. I'd get both teams to agree on the actual timing requirements in numbers: the sensor's deadline and jitter tolerance, the display's refresh and latency needs, and where the shared resource is held and for how long. That usually reveals whether the contention is a long critical section that can be shortened, a lock that should be a priority-inheriting mutex, or genuinely two workloads that shouldn't share the resource at all. Then I'd lay out options with trade-offs rather than picking a winner: priority inheritance on the shared lock, splitting the resource so each driver has its own path, moving one consumer off the shared path, or bounding the critical section so the inversion window is provably under the sensor's deadline. I'd bring the data back to both teams and drive toward a decision the requirements support, escalating to the systems/architecture owner if the two deadlines are genuinely incompatible and a design change is needed. Throughout, I'd keep it about the measurements and the shared-resource design, not about whose team "wins" the priority, and I'd document the decision and its rationale so it's defensible in a design review.

**Possible follow-ups:** How would you measure the actual critical-section hold time to prove whether priority inheritance is sufficient? If the deadlines turn out to be fundamentally incompatible, what design options would you put on the table?
