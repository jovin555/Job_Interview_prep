# embedded-linux-bsp — Day 122

## Q1: How would you approach deciding whether a given peripheral's driver should be compiled into the kernel image versus built as a loadable module, when the peripheral is needed during early boot but the root filesystem is on a separate, later-mounted partition?

**Answer:** The deciding factor is *when* the device must be functional relative to the boot timeline, not convenience. If the peripheral is required before the root filesystem is mounted — for example, the storage controller that hosts the rootfs, the console UART, or a regulator that other early drivers depend on — it must be built into the kernel image (`=y`), because loadable modules live on the rootfs and simply aren't reachable yet. For anything that only needs to be up after userspace starts, a module (`=m`) is preferable: it keeps the base image smaller, allows reloading during development, and lets you update a driver without reflashing the kernel.

The nuance is the middle ground. A common pattern is to build the driver in but keep the *firmware* or optional features as modules, or to use an initramfs that carries the modules needed to mount the real rootfs and then hands off. So the real question becomes: what is the minimal set of drivers needed to reach the point where the rootfs is available? That set goes in the kernel (or initramfs); everything else can be modular. I'd also weigh debuggability — during bring-up, modules are far easier to iterate on, so I might start modular and promote to built-in once the boot dependency is confirmed.

- How would an initramfs change your answer for a driver that's needed to mount the rootfs?
- What are the risks of building everything in "to be safe," and how would you trim that later?

## Q2: How would you approach debugging a situation where the kernel boots, the root filesystem mounts, but a userspace service that depends on a kernel driver starts before the driver has finished initializing, causing intermittent failures on first access?

**Answer:** This is fundamentally an ordering and synchronization problem, not a driver bug, so I'd resist the urge to "fix" it by sprinkling sleeps into the service. First I'd confirm the race: check whether the driver's device node or sysfs entry exists at the moment the service opens it, and whether the failures correlate with boot timing (e.g., disappear when the system is slow to start the service). Kernel logs with timestamps and the service's own startup logs side by side usually make the ordering visible.

Then I'd fix it at the right layer. The cleanest solution is to make the dependency explicit: have the service wait on the device to actually be ready rather than merely present — for example, blocking on a `read()`/`poll()` that the driver only satisfies once initialization completes, or waiting for a "ready" uevent/sysfs attribute. On the init side, systemd units can express `After=`/`Wants=` on the device unit, and `udev` rules can gate service start on device readiness. If the driver exposes a character device, opening it should ideally block or return a clear `-EAGAIN` until ready rather than succeeding and then failing on first I/O. The principle is: readiness must be observable and the consumer must wait on it, rather than relying on timing luck.

**Possible follow-ups:**
- How would you make a driver signal readiness to userspace without polling?
- What's the difference between a device *existing* and a device being *ready*, and where does that distinction live in the driver model?

## Q3: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace application that `mmap()`s a register region of a custom FPGA peripheral gets a segmentation fault on production hardware, while the same binary works on the development board. How would you approach this?

**Answer:** A segfault on `mmap()` access that works on one board and not another points at the mapping itself or the physical address behind it, so I'd separate "the mapping failed" from "the mapping succeeded but the access faults." First I'd check the return value of `mmap()` — if it returns `MAP_FAILED` and the code doesn't check, the subsequent access faults. Then I'd compare the device tree memory regions between the two boards: the FPGA's `reg` base address and size, and whether the reserved-memory / `memory` node overlaps it. A very common cause is that the production board's DRAM size or layout differs, so the FPGA aperture now collides with RAM that the kernel is using, and the mapping either fails or maps memory the kernel owns.

I'd also verify alignment and length: `mmap()` of device memory requires the offset to be page-aligned, and if the production FPGA aperture starts at a different offset, a previously-valid mapping becomes invalid. On the kernel side, I'd confirm the driver is using `ioremap`/`devm_ioremap_resource` correctly and that the region is marked reserved so the kernel doesn't hand it out. Tools: `cat /proc/iomem` on both boards to see who owns the physical range, and a small test that prints the `mmap()` return and errno. The fix is usually in the device tree or the reserved-memory declaration, not the application.

**Possible follow-ups:**
- How would `/proc/iomem` and the device tree reserved-memory nodes help you confirm an overlap?
- Why does `mmap()` of device memory require page-aligned offsets, and what happens if you violate that?

## Q4: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe untouched and layer our changes on top through configuration fragments and `.bbappend` files. I'd create our own layer (say a `meta-<product>` layer) that depends on the vendor's BSP layer, and in it add a `.bbappend` for the kernel recipe. The append points at a `SRC_URI` that includes one or more `.cfg` fragment files, and the kernel's `merge_config`/`config-fragments` machinery (via the `KERNEL_CONFIG_FRAGMENTS` or the `cfg` file handling in the kernel class) merges them into the final `.config` at build time. Each fragment contains only the deltas — the options we need to enable or disable — not a full defconfig, so it stays readable and rebases easily when the vendor bumps their kernel.

I'd keep fragments small and purpose-scoped (e.g., one for a peripheral, one for a debug option) so they can be reviewed and reused across board variants. For validation, I'd check the generated `.config` in the build's work directory and, importantly, confirm that requested options actually took effect — a fragment option that silently fails to apply because of a dependency is a classic trap, so I'd grep the final config and treat missing options as build errors where possible. This keeps the vendor recipe pristine, makes our changes auditable, and survives vendor updates.

**Possible follow-ups:**
- How would you detect that a fragment option was silently dropped because its dependency wasn't enabled?
- How would you share a common fragment across several board variants while keeping board-specific deltas separate?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a cross-team risk-and-tradeoff decision rather than a hardware-versus-software argument, and my first job is to make the actual constraints visible to everyone. I'd get the hardware team to state precisely which pins are needed, why the new peripheral can't use an alternative, and what the pinmux change costs in board rework. In parallel I'd have the software side enumerate exactly what depends on the current debug UART — bootloader console, kernel early console, the manufacturing test fixture, and any scripts that parse that output — because "the manufacturing line relies on it" needs to become a concrete list of dependencies, not a general objection.

With that on the table, I'd look for options that decouple the risk: can the new peripheral use a different pin or a different pinmux group that doesn't touch the debug UART? If the UART must move, can we keep a stable console by updating the bootloader and device tree together and validating on a small batch before the line sees it? I'd propose a staged plan — prototype the pinmux change on a bench board, confirm early boot console still works end to end, then coordinate with manufacturing on a fixture/script update window. The decision gets documented with the tradeoffs and owners, and I'd make sure manufacturing signs off on the validation criteria before we commit. The point is to convert a standoff into a sequenced, evidence-backed plan with clear acceptance criteria.

**Possible follow-ups:**
- How would you validate that early boot console output is intact before the change reaches the manufacturing line?
- If manufacturing can't absorb the change on the required timeline, how would you escalate or propose a fallback?
