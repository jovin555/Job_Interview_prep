# embedded-linux-bsp — Day 108

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is usually one of three things: the driver is talking to the wrong address, the hardware isn't actually powered/clocked, or the driver is programming registers but never reading back to confirm. I'd start by confirming the driver is bound to the intended device — check `/sys/bus/<bus>/devices/` and the driver's sysfs entry to make sure the device tree node matched the driver's compatible string and the probe ran against the right instance. Then I'd verify the physical layer: with a scope or logic analyzer on the bus lines, confirm that transactions are actually leaving the SoC and that the peripheral is acknowledging them. If the bus is silent, the issue is upstream — pinmux, clock gating, or a regulator that never came up. If the bus shows traffic but the device doesn't respond, I'd check the peripheral's power and reset state, since a device held in reset or unpowered will NAK or float silently. I'd also read back the registers the driver wrote to confirm the writes landed, and compare against the datasheet's reset values. A common trap is a driver that writes a configuration register with the wrong bit width or endianness — the write succeeds at the bus level but the device interprets it as garbage. Finally, I'd enable dynamic debug for that driver and add temporary readback logging in probe to see exactly what state the hardware is in when probe returns.

**Possible follow-ups:** How would you distinguish between a device-tree mismatch and a hardware power issue without a scope? What would you check first if the driver works on the development board but not on the production board?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our changes on top through configuration fragments rather than recipe forks. I'd create a `.cfg` fragment file containing only the `CONFIG_*` options we need, and reference it from our board's machine configuration or a `.bbappend` using `SRC_URI` with the `file://` scheme plus the kernel's built-in fragment merge mechanism (`KERNEL_CONFIG_FRAGMENTS` or the `merge_config.sh` path the vendor's kernel class supports). The fragment approach means the vendor can bump their kernel recipe and our delta stays a small, reviewable file. I'd keep the fragment minimal — only options that differ from the vendor defconfig — and document why each option is there, because a fragment that silently overrides a vendor choice is a maintenance hazard. I'd also verify the merge order: fragments are applied after the base config, so anything we set wins, but I'd confirm with `bitbake -c menuconfig` or by inspecting the generated `.config` in the work directory that our options actually took effect and weren't dropped by a dependency. For options that depend on other options, I'd include the dependencies explicitly in the fragment so a future kernel version bump doesn't silently disable our feature.

**Possible follow-ups:** What happens if a fragment sets an option that the vendor's defconfig explicitly disables, and how would you detect that conflict? How would you handle a kernel option that only exists in certain kernel versions?

## Q3: How would you approach debugging a situation where a custom board running Linux boots successfully, but a USB 2.0 device (e.g., a data acquisition module) is intermittently not enumerated on cold boots, while working fine after a warm reboot?

**Answer:** Cold-boot-only failures point at timing and power sequencing rather than the USB stack itself, because a warm reboot leaves the PHY, clocks, and the device already in a known-good state. I'd first check whether the failure correlates with the device being present at power-on versus hot-plugged — if it only fails when the device is connected during cold boot, the host controller may be enumerating before the device's power rail has stabilized or before its internal oscillator is running. I'd look at the USB PHY clock and reset sequencing in the device tree and the controller driver's probe order, and confirm the VBUS supply and any external hub or power switch are up before the host controller starts enumeration. On the software side, I'd enable USB core debug (`CONFIG_USB_DEBUG` / dynamic debug on `usbcore`) and capture `dmesg` from the earliest boot to see whether the port sees a connect event at all — if there's no connect event, it's a PHY or VBUS issue; if there's a connect but enumeration fails, it's a signaling or descriptor issue. I'd also check for a race between the host controller driver and the device's own firmware boot time, and consider adding a controlled delay or a retry in the port power-on path if the hardware can't guarantee the device is ready. Finally, I'd verify the failure is reproducible across multiple boards to rule out a marginal solder joint or connector.

**Possible follow-ups:** How would you determine whether the issue is on the host side or the device side? What would you change in the device tree if the root cause turned out to be PHY clock stabilization time?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never block on anything the logging path controls, so I'd separate the two concerns at the driver level rather than trying to arbitrate with a single lock. The real-time access path would use a dedicated, pre-allocated buffer and a lock-free or very short critical section — ideally the real-time task reads from a ring buffer the driver fills from interrupt context, so it never contends with userspace at all. The logging path would consume from a separate copy or a second ring buffer that the driver drains opportunistically, and if the logging consumer falls behind, the driver drops or overwrites log data rather than back-pressuring the real-time path. I'd avoid any mutex that both paths share; if shared state is unavoidable, I'd use a spinlock held only for a few instructions, or a seqlock for read-mostly data. For the userspace interface, I'd expose the real-time data through a `mmap`'d buffer or a `read()` on a dedicated char device with `O_NONBLOCK`, and the logging data through a separate file descriptor so a slow logger can't stall the real-time reader. I'd also make sure the driver's interrupt handler does the minimum work — timestamp and enqueue — and defers everything else to a threaded handler or workqueue at a lower priority.

**Possible follow-ups:** How would you verify that the logging path truly never delays the real-time path — what would you measure? What happens if the real-time consumer is slower than the producer, and how would you handle buffer overflow?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review the hardware team reveals that they need to change the main processor's boot mode strap resistors to accommodate a new flash part. The change means the processor will boot from a different interface (e.g., from SPI NOR to eMMC), and the bootloader and kernel configurations are already tuned for the current boot source. The project is six weeks from the start of a clinical trial. How would you handle this situation?

**Answer:** I'd treat this as a scope-and-risk conversation first, then a technical execution problem. My first step is to get the hardware and systems leads in a room and quantify what "tuned for the current boot source" actually means — which parts of the bootloader, device tree, and kernel config are boot-source-specific versus shared. That tells me whether this is a configuration change or a genuine re-architecture. I'd then lay out the options with honest effort estimates: adapt the existing boot flow to the new interface, keep a dual-boot capability so the current qualified path stays intact while the new one is validated, or push back on the hardware change if the flash part can be sourced another way. Given the clinical trial timeline, I'd want to protect the trial date by keeping the current boot path as the qualified baseline and bringing up the new interface in parallel, so a slip in the new path doesn't block the trial. I'd be explicit with the project manager about what's at risk — validation effort, regression testing, and the possibility that the new flash part's timing or wear behavior needs its own qualification — and I'd ask for a decision on whether the trial runs on the old configuration or waits for the new one. Throughout, I'd keep the regulatory angle visible: a boot-source change touches the device's validated configuration, so it needs to go through the same change-control and verification process, not be treated as a late-breaking tweak.

**Possible follow-ups:** How would you structure the parallel bring-up so the two boot paths don't interfere with each other? What would you do if the hardware team insisted the change was non-negotiable and the trial date couldn't move?
