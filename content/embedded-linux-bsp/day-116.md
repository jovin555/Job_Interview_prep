# embedded-linux-bsp — Day 116

## Q1: How would you approach debugging a situation where a kernel driver's `probe()` function returns success, but the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is usually a case of the driver believing it configured the hardware when it actually configured something else, or configured the right thing but never exercised it. I'd work outward from the driver's own assumptions.

First, confirm the driver is bound to the device I think it is. `probe()` returning success only means the driver's own checks passed — it doesn't prove the device tree node matched the intended compatible string, that the reg address is the one the hardware actually decodes, or that the driver instance I'm looking at is the one serving my device. Checking the sysfs device tree (`/sys/bus/platform/devices/`, the driver's `driver` symlink) and the kernel log for the bind message tells me whether the match happened at all.

Second, verify the register accesses are landing where I expect. If the driver uses `devm_ioremap_resource()` or `regmap`, I'd dump the mapped base address and compare it against the SoC's memory map and the device tree `reg` property. A wrong address often doesn't fault — it just reads back zeros or writes into a hole, and the driver happily continues. Reading back a known register (an ID register, a reset value) and comparing against the datasheet is the fastest way to catch this.

Third, check that the driver actually touches the hardware in `probe()`. Many drivers defer real initialization to `open()`, a workqueue, or a runtime-PM resume callback. If `probe()` only allocates structures and registers a char device, "non-functional" may simply mean the initialization path never ran — so I'd trace whether the userspace access path is reaching the driver at all.

Fourth, look at the physical layer: is the peripheral clock enabled, is the reset deasserted, is the power rail up? A driver that maps registers and returns success without enabling its clock will read garbage or zeros. `clk_summary` in debugfs and regulator state in sysfs confirm this. On a scope or logic analyzer, I'd check whether the bus lines actually toggle when the driver claims to be talking.

Finally, I'd add temporary instrumentation — `dev_dbg` around each register write, or a readback of the control register after configuration — to see exactly where the driver's view of the world diverges from the hardware's. The key discipline is not to trust "probe succeeded" as evidence of anything beyond the driver's own internal consistency.

**Possible follow-ups:** How would you tell the difference between a wrong register address and a peripheral that's held in reset? What would you check first if the device works after a warm reboot but not a cold boot?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of the kernel source and base config, and layer board-specific deltas on top through configuration fragments rather than recipe edits. Forking the recipe means every vendor update becomes a manual merge, and the delta becomes invisible to anyone reading the layer.

The mechanism is `config-fragments`: a `.cfg` file containing only the options I need to change, referenced from a `.bbappend` on the vendor's kernel recipe via `SRC_URI` and applied by the kernel's `merge_config.sh` during `do_configure`. The fragment should contain only deltas — `CONFIG_FOO=y`, `# CONFIG_BAR is not set` — not a full defconfig. Keeping it minimal means it stays readable and survives kernel version bumps, because unrelated options aren't frozen at old values.

For options that must not be silently overridden, I'd use `KERNEL_CONFIG_FRAGMENTS` with explicit ordering, and for anything that has to be validated I'd add a `do_configure:append` check that greps the final `.config` for required symbols and fails the build if they're missing. That turns a silent config regression into a build error.

I'd also separate concerns by layer: a common SoC layer holds fragments shared across all boards on that SoC, and a machine-specific layer holds only the board's own deltas. That way a new board on the same SoC inherits the common fragment and adds a small one of its own. The machine `.conf` sets `MACHINE` and points at the right device tree and fragment set.

The discipline that makes this maintainable is treating the fragment as code under review: every option in it should have a reason, and anything no longer needed should be removed rather than left to accumulate. A fragment that grows into a full defconfig has quietly become the fork it was meant to avoid.

**Possible follow-ups:** How would you handle a vendor kernel update that renames or removes a config symbol your fragment depends on? What's the difference between a config fragment and a `defconfig` in terms of how bitbake applies them?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never wait on anything the logging path controls. That rules out a shared mutex, a shared spinlock held across the logging work, or a single buffer that both paths write into. The design has to give the real-time path a wait-free route to the hardware and to its data, and let the logging path consume a copy asynchronously.

Concretely, I'd structure it as: the real-time path (whether that's an interrupt handler, a high-priority kthread, or a userspace task with `SCHED_FIFO`) owns the hardware access and writes each sample into a lock-free ring buffer — single producer, single consumer, with atomic head/tail indices and no locks. The logging path reads from the ring at its own pace. If the logger falls behind, the ring overwrites oldest data or drops, and that policy is explicit and documented; the real-time path never blocks on a full buffer.

For the hardware itself, if both paths need to touch the same registers, I'd serialize at the lowest level with a spinlock held only for the register transaction — never across a sleep, never across the logging work. Better still, if the hardware supports it, give the real-time path a dedicated channel (a separate FIFO, a DMA descriptor ring) so the two paths don't contend on the same registers at all.

The logging path should do its formatting and I/O in process context, sleeping freely, and should be the one that yields. If it needs to hand data to userspace, a `read()` on a char device backed by the ring is the natural interface, with the real-time path never entering that code.

The thing I'd verify rather than assume is the actual worst-case latency of the real-time path under logging load — measuring it with a tracer or a GPIO toggle on a scope, because "lock-free" in source doesn't guarantee bounded latency once cache effects and interrupt masking are in play.

**Possible follow-ups:** What happens to your design if the real-time consumer is in userspace rather than in the kernel? How would you bound the worst case if the hardware only exposes a single register set to both paths?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** An intermittent fallback means the boot ROM or U-Boot's own boot logic is failing to find a valid boot source and moving down its fallback list — so the real question is why eMMC boot fails sometimes, not why network boot happens. The network boot is a symptom.

I'd start by capturing the boot log on a failing unit with the console at full verbosity, and compare it against a passing boot. U-Boot prints which device it's probing and why it rejected it. If the fallback happens before U-Boot even runs, the boot ROM is doing it, and the log won't show it — in that case I'd check the boot strap pins and the eMMC's readiness timing, because a slow-ramping rail or a part that isn't ready within the ROM's window will intermittently fail enumeration.

Next, I'd look at what "intermittent" correlates with: cold vs warm boot, temperature, specific boards vs all boards, time since power-off. That narrows it to a hardware timing issue, a marginal solder joint, or a software race. If it's board-specific, it's hardware; if it's unit-independent and random, it's more likely timing or a race in U-Boot's device probe.

On the U-Boot side, I'd check the environment itself: is `bootcmd` falling through a list where the network entry is reachable, and is the eMMC probe returning an error that U-Boot treats as "try next"? I'd also check whether the environment is being corrupted or reset — a bad CRC causing a default environment load could re-enable a network boot path that was disabled in the saved environment. `env print` on a failing unit versus a passing one settles that.

The fix depends on the cause, but the safety measure is to make the fallback explicit and controlled: either remove the unintended network path from the boot list entirely, or gate it behind a deliberate condition, so that an eMMC failure produces a visible, diagnosable halt rather than a silent boot over the network.

**Possible follow-ups:** How would you distinguish a boot ROM fallback from a U-Boot fallback if the console shows nothing? What would you check on the eMMC side if the failure only appears on cold boots?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination problem first and a technical one second, because both teams are right about their own constraints and the conflict is real: the hardware team needs pins, the software team needs a stable manufacturing interface.

My first move is to get the actual constraints on the table rather than the positions. For the hardware side: which pins, why this pinmux group specifically, and is there an alternative routing that frees the pins without moving the debug UART? For the software side: exactly what depends on the current UART — is it the bootloader console, the kernel console, the manufacturing test fixture, or all three — and is the dependency on the physical pins or on the console being available at a particular point in boot? Often the manufacturing line needs *a* console early in boot, not that specific UART, which opens up options.

Then I'd lay out the options with their costs: keep the UART and find another pin for the new peripheral; move the UART and update bootloader, device tree, and the manufacturing fixture together with a transition plan; or keep the current UART for manufacturing and add a second debug path for development. Each has a schedule and validation cost, and the decision should be made with those visible, not by whichever team argues harder.

If moving the UART is the right call, I'd insist on a staged plan: update the bootloader and device tree in lockstep, validate early-boot console output on real hardware before the manufacturing line switches over, and give the manufacturing team a defined window where both paths work so they're never blocked. I'd also make sure the change is captured in the interface control documentation so it doesn't get lost.

Throughout, I'd keep the framing on the shared goal — shipping a device that meets the new peripheral requirement without disrupting production — and make sure the decision and its rationale are recorded, so that if it causes problems later there's a clear record of why it was made.

**Possible follow-ups:** What would you do if the hardware team's pin constraint turns out to be non-negotiable and the manufacturing line can't tolerate any transition window? How would you make sure the manufacturing team's dependency was captured before the next design review rather than surfacing as a surprise?
