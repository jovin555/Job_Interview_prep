# embedded-linux-bsp — Day 120

## Q1: How would you approach debugging a situation where the kernel boots successfully and the root filesystem mounts, but a userspace service that depends on a kernel driver starts before the driver has finished initializing, causing intermittent failures on first access?

**Answer:** This is fundamentally a boot-ordering and readiness problem, and I'd attack it from two directions: make the dependency explicit, and make the driver's readiness observable.

First, I'd confirm the diagnosis rather than assume it. The symptom — works after a retry, fails on first access — is consistent with a race, but it could also be a missing device node, a permissions issue, or a driver that registers its char device late. I'd check the kernel log timestamps against the service's start time, look at whether the device node exists at the moment the service opens it, and add logging on both sides to see the actual interleaving. Reproducing it reliably (e.g., by slowing the driver's probe with a temporary delay) confirms the race before I change anything.

For the fix, the cleanest approach is to make the driver signal readiness through a mechanism the init system understands. Options, roughly in order of preference:

- **Proper dependency in the init system.** With systemd, a device unit (`dev-mysensor.device`) or a `After=`/`Wants=` relationship on the driver's sysfs entry, combined with the service being ordered after it. With BusyBox init or a custom init, a wait loop that polls for the device node or a sysfs "ready" attribute before launching the service.
- **Driver-side readiness attribute.** Have the driver expose a sysfs attribute or only create the device node once initialization (including any deferred work) is genuinely complete. This is more robust than relying on probe returning, because probe can return success while asynchronous work is still pending.
- **udev rule.** If the device node is created by the kernel, a udev rule can trigger the service or set a flag the service waits on. This decouples the service from boot timing.

I'd avoid the tempting but fragile fix of just adding a `sleep` in the init script — it masks the race and will fail again when boot timing changes on different hardware or under different storage speeds. If a delay is used as a stopgap, it should be a bounded poll with a timeout and a clear failure path, not a fixed sleep.

Finally, I'd make the failure mode graceful: the service should retry with backoff on `ENODEV`/`ENOENT` rather than aborting, so a slow boot degrades to a slightly later start rather than a hard failure. And I'd add a boot-time test to the CI or factory test image that exercises the service immediately after boot to catch regressions.

**Possible follow-ups:** How would you distinguish this race from a genuine driver bug that only manifests on first access? What are the trade-offs of using systemd device units versus a udev rule for this?

## Q2: How would you approach structuring a Yocto BSP for a product that must produce both a production image and a factory-test image, where the factory image needs additional diagnostic tools, a different kernel command line, and a writable root filesystem?

**Answer:** The goal is to share everything that's common — the BSP layer, kernel, bootloader, device tree — and diverge only at the image and configuration layer, so the two images can't drift apart in ways that matter.

I'd structure it as follows:

- **A common BSP layer** (`meta-<product>-bsp`) containing the machine configuration, kernel recipe append, device tree, bootloader config, and the base packagegroup that both images need. This is the single source of truth for hardware support.
- **A distro or image layer** (`meta-<product>-distro` or just image recipes in the BSP layer) with two image recipes: `image-production.bb` and `image-factory-test.bb`. Both `require` a common `.inc` file that defines the shared base — `IMAGE_INSTALL`, `IMAGE_FEATURES`, `ROOTFS_POSTPROCESS_COMMAND`, etc. — and each adds only its deltas.
- **The factory image** adds diagnostic packages (memory test, storage test, bus scanners, a serial console tool, logging utilities) via `IMAGE_INSTALL:append`, sets a different `APPEND` for the kernel command line (e.g., enabling a verbose console or a test-mode flag), and uses `IMAGE_FEATURES += "read-only-rootfs"` removed / `debug-tweaks` or an explicit writable-rootfs configuration. The production image keeps the rootfs read-only or otherwise locked down.
- **Kernel command line** is best handled through the bootloader environment or a `KERNEL_CMDLINE` variable that differs per image, rather than editing the bootloader recipe twice. If the bootloader reads its environment from a partition, the factory image can ship a different default environment.
- **Machine features and overrides** can gate anything that should only exist in one image, but I'd be sparing with `MACHINEOVERRIDES` for image-level differences — image recipes are the right place for image-level divergence.

The key discipline is that the hardware support (kernel, DT, bootloader) lives in exactly one place, and the images differ only in userspace content and runtime configuration. That way a kernel fix lands in both images automatically, and the factory image is a genuine test of the same BSP the production image uses.

I'd also make the factory image's extra tooling auditable — a packagegroup `packagegroup-factory-test` — so it's obvious what's added and it can be reviewed against the production image's security posture.

**Possible follow-ups:** How would you ensure the factory image doesn't accidentally get shipped to customers? How would you handle a diagnostic tool that needs a kernel module not present in the production kernel?

## Q3: How would you approach debugging a kernel panic that occurs only on every third or fourth boot, with no consistent trigger?

**Answer:** Intermittent boot panics are almost always a race, an uninitialized resource, or a hardware timing marginality, and the first job is to capture evidence from the failing boots rather than trying to reason about it from the successful ones.

**Capture the panic.** The single most valuable thing is a persistent, reliable panic log. I'd enable `pstore`/`ramoops` (backed by a reserved memory region that survives reboot) or a persistent console log to flash, so the panic message and stack trace from the failing boot are available after the reset. Without this, I'm guessing. I'd also enable `panic_on_oops` and a panic timeout so the board reboots predictably and the log is captured, rather than hanging.

**Characterize the failure.** Is the panic always in the same function? Same driver? Same point in boot (before/after rootfs mount, before/after a particular service)? A panic that's always in the same place points at that code; a panic that moves around points at memory corruption, a race, or hardware. I'd collect the stack trace from several failing boots and compare.

**Narrow the trigger.** Since it's every third or fourth boot, I'd look at what varies between boots: DRAM training results, power ramp timing, clock/PLL lock, regulator sequencing, temperature, or a persistent state left in flash/RTC from the previous boot. A useful experiment is to add a delay at a suspect point (e.g., before a driver's probe) — if the panic disappears, it's a timing race. Another is to boot repeatedly with a known-good minimal configuration (fewer drivers, no userspace) to see if the panic persists — if it vanishes, the trigger is in the removed code.

**Common culprits to check:** uninitialized memory being used before init completes; a driver touching hardware before its clock/regulator is enabled (probe ordering); DMA or cache coherency issues; a watchdog or reset that leaves a peripheral in a bad state; and marginal DRAM or power. If the panic is a data abort or external abort, I'd look hard at memory-mapped register access timing and at whether the peripheral is actually powered.

**Use the tools.** `KASAN`/`KCSAN` in a debug build can catch use-after-free and data races that only manifest intermittently. `slub_debug` and `init_on_alloc` can surface uninitialized-memory bugs. If the panic is in early boot before the console is up, `earlycon` and `earlyprintk` help.

Only after I have a reproducible-enough signature would I start changing code — and I'd validate the fix by running the failing boot loop many times, not just once.

**Possible follow-ups:** How would you set up ramoops/pstore on a board where you don't yet have a working kernel? What would make you suspect hardware rather than software?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path does, so the design has to decouple them structurally rather than rely on scheduling luck.

**Separate the data paths.** The real-time task should interact with the hardware through a path with no shared locks that the logging task can hold. The cleanest pattern is a lock-free or minimally-locked producer/consumer split: the real-time side writes samples into a pre-allocated ring buffer (or a DMA-fed buffer) using atomic operations or a single-producer/single-consumer ring, and the logging side reads from that ring at its own pace. The real-time side never waits for the logger; if the ring is full, it either overwrites the oldest entry (for logging data, usually acceptable) or drops and counts the drop — it must not block.

**Keep the hardware access single-owner.** If both paths need to touch the same hardware registers, that's a problem — the real-time path should own the hardware, and the logging path should only consume data the real-time path has already published. If the logging path genuinely needs to issue commands (e.g., reconfigure a sensor), those should be queued and executed by the real-time context at a safe point, not issued directly from the logging context.

**Use the right synchronization primitives.** For the ring buffer, `smp_store_release`/`smp_load_acquire` or a proper lock-free ring avoids taking a mutex on the real-time path. If a lock is unavoidable, it must be a spinlock held for a bounded, tiny critical section, and the logging path must never hold it while doing slow work (no allocation, no I/O under the lock). A mutex is unacceptable on the real-time path because it can sleep and can be held by the logger.

**Consider the scheduling model.** If the real-time task is a userspace thread using `SCHED_FIFO`, the driver's `read()`/`ioctl()` path it uses must be non-blocking or bounded. If it's a kernel thread or interrupt context, the logging path must be strictly lower priority and must not run in interrupt context. I'd also look at whether the real-time access can be driven by the hardware (DMA + interrupt) so the CPU isn't in the loop at all for the critical path.

**Validate with measurement.** I'd instrument the real-time path's latency (e.g., timestamp at entry and exit, or use `cyclictest`-style measurement around the access) and run it under heavy logging load to prove the logging task doesn't perturb it. The proof is measured worst-case latency, not "it looks fine."

**Possible follow-ups:** What happens when the ring buffer fills because the logger is slow — how do you decide between dropping and blocking? How would you handle a logging path that needs to reconfigure the hardware?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during integration testing you discover that the kernel's real-time scheduling class (SCHED_FIFO) is causing priority inversion on a shared hardware resource between your sensor driver and the display driver. The display team insists their driver needs the highest priority, and the sensor team says their data will be corrupted if they miss their deadline. How would you handle this situation?

**Answer:** I'd treat this as a shared-resource contention problem to be solved with evidence and a system-level design decision, not as a tug-of-war between two teams' priorities.

**First, get the facts on the table.** Priority inversion means a high-priority task is waiting on a resource held by a lower-priority task, and the fix depends on which resource and how long it's held. I'd instrument both drivers to measure actual hold times on the shared resource and the actual latency each team is experiencing, and bring those numbers to a joint review. Often the "we need the highest priority" claim is a proxy for "we're missing deadlines," and the real fix is reducing hold time or removing the sharing, not reordering priorities.

**Then look for structural fixes, in order of preference:**

- **Eliminate the sharing.** If the sensor and display are contending on the same bus or register block, can the access be partitioned — separate buses, separate register regions, or a hardware arbiter? Removing the shared resource removes the inversion.
- **Bound the critical section.** If sharing is unavoidable, the holder must hold the resource for the shortest possible time, and the real-time path must not do slow work (allocation, I/O) while holding it. Priority inheritance (e.g., `rt_mutex`) can bound the inversion, but it's a mitigation, not a cure.
- **Reconsider the priority assignment.** Priorities should follow the actual deadline requirements, established by analysis (rate-monotonic or deadline-monotonic reasoning), not by which team asks loudest. If the display genuinely has a hard deadline and the sensor has a softer one, that's a legitimate basis for ordering — but it has to be justified with numbers, and the sensor team's corruption concern has to be addressed by making the sensor path robust to jitter (buffering, DMA) rather than by priority alone.

**On the people side,** I'd frame the discussion around the shared goal — the device has to meet its timing requirements as a system — and make clear that neither team gets to unilaterally set priority. I'd facilitate a joint session where both teams present their deadline and latency data, agree on the resource-sharing design, and document the decision and its rationale. If the teams can't converge, I'd escalate to the system architect with the data, because this is a system-level timing decision, not a driver-level one.

**Finally, I'd lock it in with a test** — a timing test that runs both paths under load and asserts the agreed latency bounds — so the resolution is verifiable and regressions are caught.

**Possible follow-ups:** How would you measure the actual hold time on the shared resource? What would you do if the analysis showed both teams genuinely have hard deadlines that can't both be met with the current hardware?
