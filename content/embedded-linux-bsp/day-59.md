# embedded-linux-bsp — Day 59

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `remove()` callback is never called during a clean shutdown, leaving a peripheral in an undefined state that causes problems on the next boot?
**Answer:** This is a shutdown-ordering and driver-lifecycle problem, and I'd approach it in layers. First, I'd confirm the driver is actually registered with a `remove()` callback and that the device is bound — check `/sys/bus/platform/drivers/<driver>/` to see the bound device, and confirm the driver struct has `.remove` populated (or `.remove_new` on newer kernels). A common cause is that the driver was built as a module and the module is never unloaded, so `remove()` only runs on module unload, not on system shutdown. On shutdown, the kernel calls `device_shutdown()`, which invokes each device's `shutdown()` callback if present, falling back to `remove()` only in some paths — so if the peripheral needs explicit quiescing at power-off, the driver should implement `.shutdown` rather than relying on `.remove`. I'd also check whether the device is being torn down by a parent bus before the child gets a chance to run its callback, which is an ordering issue that can be addressed by setting the device's shutdown priority or by handling the quiesce in the parent. To confirm the hypothesis, I'd add a printk or tracepoint in both `remove()` and `shutdown()` and watch the shutdown path. If the peripheral truly needs a defined state at power-off (e.g., a motor controller or a relay), the robust fix is often to drive it to a safe state in `.shutdown` and also add a hardware default (pull-down/pull-up) so an undefined state can't cause damage or a stuck condition on the next boot. For a medical device, I'd treat "peripheral left in undefined state across power cycles" as a risk item and verify it with a repeated power-cycle test rather than a single clean reboot.

**Possible follow-ups:**
- How would you decide between implementing `.shutdown` versus `.remove` for a peripheral that must be quiesced at power-off?
- What kernel mechanisms control the order in which devices are shut down, and how would you use them?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration option can be enabled without forking the vendor's kernel recipe?
**Answer:** The goal is to keep the vendor's layer pristine and express your delta as a separate, reviewable artifact. In Yocto, kernel configuration is typically applied through `KERNEL_FEATURES` and configuration fragments rather than by editing `defconfig` in place. I'd create a `.cfg` fragment containing just the `CONFIG_...=y` lines you need, place it in your own layer under something like `recipes-kernel/linux/linux-<vendor>/`, and reference it from a `.bbappend` on the vendor's kernel recipe using `SRC_URI` with the fragment and `KERNEL_FEATURES` or the `kernel-yocto` fragment mechanism. The `.bbappend` lives in your layer, so the vendor's recipe is untouched and can be updated independently. I'd also make sure the fragment is validated — Yocto can warn if a requested config symbol isn't actually set after merging, which catches the case where a dependency isn't met or the symbol name changed between kernel versions. For maintainability across kernel version bumps, I'd keep fragments small and named by feature (e.g., `myboard-spi.cfg`) rather than one giant file, and I'd document why each option is needed. If the vendor's kernel isn't using the yocto-kernel tooling, the fallback is a `do_configure:append()` that runs `scripts/config` against the generated `.config`, but that's more fragile and I'd only use it if fragments aren't supported. The key principle is: your layer owns your delta, and the vendor's layer stays replaceable.

**Possible follow-ups:**
- How would you verify that a configuration fragment actually took effect after a build, rather than being silently dropped?
- What's the trade-off between using a config fragment and carrying a full `defconfig` in your own layer?

## Q3: How would you approach debugging a situation where a custom board running Linux boots successfully, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently gets `EINTR` and aborts, even though no signals are intentionally sent to it?
**Answer:** `EINTR` means a blocking syscall was interrupted by a signal before it completed, and the daemon is treating that as fatal when it should generally retry. The first thing I'd check is whether the daemon is installing signal handlers — a common cause is that the process (or a library it links) installs a handler for `SIGCHLD`, `SIGALRM`, or a timer signal, and that signal arrives while the `ioctl` is blocked, causing the syscall to return `EINTR`. I'd use `strace -f -e trace=ioctl,rt_sigreturn` to see exactly which signal interrupts the call and how often. If the signal is expected (e.g., a timer or a child-process notification), the correct fix is for the daemon to loop on `EINTR` and retry the `ioctl`, which is standard practice for any blocking syscall. If the signal is unexpected, I'd trace where it's coming from — a library, a watchdog, or a parent process. There's also a kernel-side angle: if the driver's `ioctl` handler is itself returning `-EINTR` (e.g., because it's waiting on a completion that gets interrupted), the driver should be using `wait_for_completion_interruptible` only if it genuinely wants to be interruptible, and otherwise should use the non-interruptible variant or handle the retry internally. I'd also check whether the driver is holding a mutex or waiting on a condition that can be signaled. The fix is usually on the userspace side (retry on `EINTR`), but it's worth confirming the kernel side isn't generating spurious wakeups. For a medical device, I'd also make sure the retry loop has a bounded timeout so a persistently interrupted call can't hang the daemon indefinitely.

**Possible follow-ups:**
- How would you distinguish between a signal that's safe to ignore and one that indicates a real problem the daemon must handle?
- What's the difference between `wait_for_completion` and `wait_for_completion_interruptible`, and when would you choose each in a driver?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?
**Answer:** The core requirement is that the real-time path must never block on anything the logging path holds. I'd start by separating the two access paths at the data-structure level: the real-time task gets a lock-free or minimally-contended path to the hardware, and the logging task reads from a buffer that the real-time path writes to, rather than both contending for the same device lock. A common pattern is a single-producer/single-consumer ring buffer: the real-time task writes samples into the ring (using a lock-free index update or a very short spinlock held only for the index), and the logging task drains it from the other end. The real-time task never waits for the logging task; if the ring is full, the real-time task either overwrites the oldest entry or drops, depending on whether losing a log entry is acceptable — and for a medical device, that decision is a risk-management question, not just a coding one. For the hardware access itself, if both paths need to touch the same registers, I'd serialize only the register access with a short spinlock and keep the logging task's work (formatting, copying to userspace) outside that lock. If the hardware supports it, I'd give the real-time task a dedicated interrupt or DMA channel so it doesn't share a completion path with logging. I'd also consider whether the logging task should be in the kernel at all — often it's cleaner to expose a `read()` on a character device and let a userspace logger drain it, which keeps the kernel path minimal. The verification is a latency measurement: instrument the real-time path and confirm its worst-case latency is unaffected whether the logging task is idle or hammering the buffer.

**Possible follow-ups:**
- How would you decide between dropping log entries and blocking the real-time task when the ring buffer is full?
- What tools would you use to measure the real-time path's worst-case latency under load?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the hardware team reveals that the board's power-on reset (POR) timing has changed: the SoC now releases reset before the external PMIC has finished its soft-start ramp, and the software team says the current bootloader assumes the PMIC is stable when the SoC starts. The project is five weeks from the start of a clinical trial. How would you handle this situation?
**Answer:** I'd treat this as a boot-reliability risk first and a schedule problem second, because an unreliable POR can manifest as intermittent boot failures that are extremely hard to diagnose later. My first step is to get the hardware and software teams into the same conversation with the actual timing data — the PMIC soft-start ramp time, the SoC reset release timing, and the bootloader's first access to any PMIC-controlled rail. I'd want to know whether the bootloader is reading the PMIC over I2C before the rail is stable, or whether it's assuming a rail is up when it isn't. If the bootloader is the problem, there are usually software mitigations: add a delay or a poll-for-ready loop before the first PMIC access, or reorder the bootloader's initialization so it doesn't touch a rail until the PMIC signals power-good. If the PMIC has a power-good output that isn't currently routed to the SoC, that's a hardware change, but it might be a small one (a strap or a GPIO) that can be done on a rework basis for the trial units. I'd also check whether the bootloader can be made to retry the PMIC initialization rather than failing hard, so a marginal POR becomes a retry rather than a dead board. On the schedule side, I'd be honest with the project manager: the fix might be a bootloader change (fast, low risk) or a hardware change (slower, needs rework and re-testing), and I'd propose the smallest change that gives a reliable boot for the trial, with the full fix scheduled for production. I'd also want a test that exercises the POR path repeatedly — cold boots, warm boots, and brownout conditions — because a single successful boot proves nothing. The key is not to let the schedule pressure push us into shipping a boot path we don't trust, especially for a device that will be used in a clinical setting.

**Possible follow-ups:**
- How would you design a test to reliably reproduce a marginal POR condition without damaging boards?
- If the fix requires a hardware change, how would you decide whether to rework the trial units or delay the trial?
