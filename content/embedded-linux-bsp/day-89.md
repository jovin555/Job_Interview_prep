# embedded-linux-bsp — Day 89

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder failure modes because the kernel is telling you everything is fine, so the first job is to distrust that signal and verify each assumption independently. I'd start by confirming the driver is actually bound to the intended device instance — checking `/sys/bus/<bus>/devices/` and the driver's sysfs directory to make sure the match happened against the right node and not a stale or duplicate one. Then I'd verify the register accesses are landing where I think they are: dumping the peripheral's registers from userspace (via `/dev/mem` on a debug build, or a small test module) and comparing against the datasheet's reset values. A very common cause is a clock or power domain that was never actually enabled — the register writes go through and read back as written because the bus fabric is alive, but the peripheral's internal logic is held in reset or unclocked, so nothing happens. I'd check the clock framework (`/sys/kernel/debug/clk/clk_summary`) and any runtime-PM state. Next I'd look at pinmux: if the pins aren't muxed to the peripheral function, the SoC side looks healthy but the signal never reaches the outside world. After that, I'd instrument the driver itself — add dev_dbg traces around the init sequence, confirm the reset deassert timing meets the datasheet, and check that any required delays are actually being honored. Finally, I'd put a scope or logic analyzer on the physical interface to see whether the device is being talked to at all. The discipline is to bisect the chain — device tree match, clock/power, pinmux, register access, physical signaling — rather than assuming the driver logic is wrong just because the symptom is silence.

**Possible follow-ups:** How would you tell the difference between a clock that's gated and a peripheral that's held in reset, from software alone? What would you change in the driver's error handling so this class of failure surfaces as an error instead of silence?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our changes on top, so that when the vendor bumps their kernel we can rebase with minimal pain. The clean mechanism is a `.bbappend` in our own layer that adds a config fragment via `SRC_URI` using the `file://` and `kernel-config` fragment mechanism — the kernel-yocto class merges fragments into the final `.config` at build time, so we never touch the vendor's recipe or carry a full defconfig. I'd keep fragments small and purpose-scoped (one for a peripheral, one for a debug option, one for a security hardening set) rather than one giant blob, because small fragments are easier to review and to drop when they're no longer needed. I'd also make sure the fragment is validated — a config option that silently doesn't apply because its dependency isn't met is a classic trap, so I'd check the build log for the fragment merge output and confirm the option is actually set in the resulting `.config`. For anything that needs to be conditional on machine or distro, I'd use overrides in the bbappend rather than branching the recipe. And I'd document the fragment's intent in the layer's README so the next engineer knows why each option is there. The principle is: our layer owns our deltas, the vendor layer owns the baseline, and the merge happens mechanically at build time.

**Possible follow-ups:** What's the difference between a config fragment and a full defconfig in terms of maintenance burden when the vendor updates their kernel? How would you verify in CI that a fragment actually applied rather than being silently ignored?

## Q3: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** Intermittent fallback means the boot flow is reaching a failure path some fraction of the time and the fallback chain is doing exactly what it was configured to do — so the real question is twofold: why is the primary path failing intermittently, and why is the fallback enabled at all. I'd tackle both. First, I'd capture the console output across many boot cycles, ideally with a persistent serial logger, because the failure may only print a line or two before falling through. I'd look at whether the eMMC is failing to initialize (enumeration timeout, CRC errors, card not ready) or whether it initializes but the boot partition or image verification fails. Timing is a prime suspect — eMMC power-up and initialization have specified delays, and if the rail ramps slowly or the reset timing is marginal, some boots win and some lose. I'd check the `bootcmd` and `boot_targets` ordering and confirm whether the fallback is a deliberate `boot_targets` entry or a leftover default. Then I'd harden the primary path: add explicit retries with delays around eMMC init, verify the boot image integrity before jumping, and make the fallback conditional rather than automatic — for a production device, an unintended network boot is both a reliability and a security problem, so I'd want it disabled in the production environment entirely. Finally, I'd stress it: cold boots, warm boots, brownout-adjacent supply conditions, and temperature extremes if relevant, to characterize how often and under what conditions the primary path fails.

**Possible follow-ups:** How would you distinguish an eMMC initialization timing issue from a marginal signal-integrity problem on the eMMC bus? What's your approach to making the boot flow fail loudly and safely rather than silently falling back?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path controls, so the design has to decouple them at the data-structure level, not just the scheduling level. I'd structure the driver so the real-time access path takes only a short, bounded lock — ideally a spinlock held for a few instructions, or better, a lock-free single-producer/single-consumer ring buffer — and never allocates memory, never sleeps, and never waits on I/O. The logging path reads from a separate buffer that the real-time path writes into without ever waiting for the logger to drain it; if the logger falls behind, the real-time side either overwrites oldest data or drops, depending on whether lossless logging or real-time determinism matters more — and that's a requirements decision to make explicit, not an accident. I'd avoid a mutex shared between the two paths entirely, because priority inheritance helps but doesn't eliminate the blocking. For the logging side, I'd move the actual file or network I/O out of the driver into a userspace daemon that reads from the driver's buffer via a character device or a `read()`-style interface, so the slow work happens in a best-effort context where it belongs. I'd also make sure the real-time path's interrupt handler is minimal — top half does the time-critical capture, bottom half or a threaded handler does anything that can be deferred. The verification is to measure worst-case latency on the real-time path under heavy logging load and confirm it stays within budget.

**Possible follow-ups:** How would you decide between dropping data and overwriting oldest data on the logging side, and how would you surface that decision to the system designers? What kernel mechanisms would you use to measure the real-time path's worst-case latency under load?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination problem first and a technical problem second, because both teams are raising legitimate concerns and the resolution depends on facts neither side has fully established. My first step would be to get the actual constraints on the table: what does the manufacturing line actually depend on — is it the debug UART specifically, or any early console, and at what stage of the boot does it need to be available? Then I'd map the technical cost honestly: the pinmux change touches the bootloader's early pin configuration, the device tree, and possibly the kernel command line, and the risk is concentrated in the window before the console is up. I'd propose a path that de-risks it rather than just accepting or rejecting the change — for example, keeping a console available on the new pinmux group and validating it on a small batch of boards before committing, and coordinating with manufacturing so they know the console location is changing and can update their fixtures and procedures. If the manufacturing dependency turns out to be a hard constraint on the current pins, I'd push back on the hardware change with that evidence and ask whether the new peripheral can use different pins instead. The key is to make the decision on evidence — what manufacturing actually needs, what the boot-time risk actually is — rather than letting it become a software-versus-hardware standoff. I'd also make sure the outcome is documented in the design record, since for a medical device the rationale for a pinmux change and its verification belongs in the traceability trail.

**Possible follow-ups:** How would you structure the validation so that a pinmux change is proven safe before it reaches the manufacturing line? If manufacturing's dependency turns out to be informal rather than a hard requirement, how would you handle the conversation about changing their process?
