# embedded-linux-bsp — Day 99

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder failure modes because the kernel is telling you nothing is wrong, so the first move is to distrust the success and verify each assumption the driver makes. I'd start by confirming the driver is actually talking to the hardware it thinks it is: read back a known register (a chip ID or revision register is ideal) and compare against the datasheet. If the read returns all-zeros or all-ones, the bus transaction is likely not reaching the device — wrong chip-select, wrong I2C address, pinmux not applied, or the peripheral clock/power domain never enabled. If the read returns plausible but wrong data, suspect address translation or a device-tree `reg` that doesn't match the hardware.

Next I'd check whether `probe()` is doing what it claims: adding temporary `dev_dbg`/`dev_info` prints around each register write and read, or using `devmem`/`i2cget`/`spidev` from userspace to poke the same registers independently of the driver. That separates "driver logic is wrong" from "hardware path is wrong." I'd also verify the pinmux and pad configuration — a pin left in its reset state will happily accept writes and return nothing useful. On the clock and regulator side, I'd confirm the driver actually enables them (and that the enable succeeds) rather than assuming the bootloader left them on. Finally, I'd check whether the device needs a reset pulse or a settling delay after power-up that the driver is skipping — many peripherals ignore the first transactions until a post-reset delay has elapsed, which looks exactly like silent non-function.

**Possible follow-ups:** How would you tell the difference between a pinmux problem and a clock problem without a scope? What would you do if the chip-ID read works but every functional register read returns stale data?

## Q2: How would you approach deciding whether a peripheral driver should be built into the kernel image versus built as a loadable module, for a device that must be functional before the root filesystem is mounted?

**Answer:** The deciding factor is dependency order, not preference. If the device must be operational before the root filesystem exists — a storage controller holding the rootfs, a PMIC regulator feeding the SoC, a console UART, or a clock controller other drivers depend on — it has to be built in (`=y`), because modules can't be loaded until the rootfs is mounted and userspace (or an initramfs) runs. Anything that can wait until after rootfs mount and userspace init is a candidate for `=m`, which keeps the core image smaller and makes iteration faster during development.

There's a middle path worth knowing: an initramfs can load modules early, so a driver that must be present "very early" but isn't strictly needed to mount the real rootfs can be a module loaded from initramfs. I'd weigh that against the added complexity of maintaining an initramfs. I'd also consider the product's update and debug story — built-in drivers are simpler to reason about for a medical device where the boot path must be deterministic and auditable, while modules are convenient during bring-up. For a regulated product I'd lean toward built-in for anything on the critical boot path and treat module loading as a deliberate, documented decision rather than a default.

**Possible follow-ups:** What are the risks of building a driver in versus as a module from a security and update standpoint? How would you handle a driver that must be built in but also needs firmware loaded from the filesystem?

## Q3: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to never touch the vendor's recipe or their defconfig directly, so that vendor updates can be pulled in without merge conflicts. The standard mechanism is a `.bbappend` in your own layer that extends the vendor's kernel recipe, plus configuration fragments applied through the kernel's `merge_config.sh` machinery. In the append I'd set `SRC_URI` to include one or more `.cfg` fragment files, and use `KERNEL_CONFIG_FRAGMENTS` (or the older `KERNEL_CONFIG`/`do_configure:append` pattern depending on the Yocto release) so the fragments are merged on top of the vendor defconfig at configure time. Each fragment contains only the options you're changing, in `CONFIG_FOO=y` form, which keeps them small, reviewable, and easy to diff.

I'd organize fragments by concern — one for a new peripheral, one for a debug option, one for a security hardening set — rather than one giant file, so a reviewer can see exactly what a given feature touches. I'd also add a `do_configure:append` sanity check that greps the final `.config` for the options I expect, so a silent fragment-merge failure (an option that got dropped because a dependency wasn't met) fails the build loudly instead of shipping a kernel missing a driver. Layer priority matters too: the append must live in a layer with higher priority than the vendor's so it wins, and I'd document that ordering in the layer's README.

**Possible follow-ups:** What happens if a fragment sets an option whose dependency isn't enabled, and how would you catch it? How would you handle a board-specific fragment that must apply only to one machine in a multi-machine build?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** Intermittent fallback means the boot command sequence is reaching a failure path some of the time and then continuing to the next boot target in `bootcmd` or `boot_targets`. First I'd read the actual environment (`printenv`) on a failing unit and confirm what `bootcmd`, `boot_targets`, and any `bootargs` actually contain — a stale saved environment in eMMC can differ from the default compiled into U-Boot, which is a classic source of "it does something we never configured." I'd check whether `saveenv` was ever run on these units and whether the environment is being loaded from the expected location.

Then I'd look at why the eMMC boot path fails intermittently: marginal eMMC initialization timing, a partition or filesystem that isn't always readable, or a `bootbus`/`mmc` device index that changes depending on probe order. Enabling U-Boot debug output (`CONFIG_DEBUG_UART`, higher log level, or `setenv bootdelay` plus a serial capture) on a failing unit usually shows the exact command that returned non-zero before the fallback. I'd also check the fallback logic itself — if `bootcmd` uses a `||` chain or `boot_targets` includes network, any transient eMMC error silently advances to the next target. The fix is usually twofold: make the eMMC path robust (retries, correct delays, verified partition layout) and make the fallback explicit and loud — log it, and in a production image remove network from `boot_targets` entirely so an unintended fallback can't happen.

**Possible follow-ups:** How would you make the environment deterministic across a production batch? What would you check if the eMMC read succeeds on the bench but fails only on cold boot?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams have legitimate concerns. First I'd get the facts on the table: exactly which pins move, whether the new pinmux group is available on this SoC package, and what the manufacturing line actually depends on — is it the UART console itself, a specific test fixture wired to those pins, or log capture during programming? That determines whether this is a firmware change, a fixture change, or both.

Then I'd separate the change into stages so it can be de-risked. The device tree and bootloader pinmux changes are straightforward to make and test on a bench unit; the real risk is the manufacturing dependency, so I'd propose keeping the debug UART functional through the changeover and validating early-boot console output on a prototype before committing. I'd want the hardware team to confirm the new peripheral's pin requirements are final, because moving pins twice is worse than moving once. I'd bring manufacturing into the review early so they can assess fixture impact and schedule any rework, and I'd document the pinmux change in the board's design record — for a medical device the pinmap is part of the configuration that has to be traceable. If the timeline is tight, I'd propose a phased plan: prototype validation first, then manufacturing sign-off, then the production cut-in, rather than a single big-bang change.

**Possible follow-ups:** What would you do if manufacturing says the fixture can't be changed before the next build? How would you verify the new pinmux didn't break anything else that shares those pins?
