# embedded-linux-bsp — Day 106

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is usually a sign that the driver is talking to the wrong place, or that the hardware is not actually enabled even though the software thinks it is. I'd work outward from the driver's assumptions.

First, confirm the driver is bound to the device I think it is. `probe()` succeeding doesn't mean it succeeded on the right node — check `/sys/bus/<bus>/devices/` and the driver's sysfs symlink to confirm the device/driver pairing, and confirm the resources the driver received (base address, IRQ number, clock handles) match the datasheet and the device tree. A common cause is a device tree `reg` or `interrupts` property that is syntactically valid but wrong, so the driver maps a region that reads as all-zeros or all-ones.

Second, verify the hardware is actually powered and clocked. If the driver enables a regulator or clock in `probe()` but the enable call silently no-ops (e.g., a dummy regulator because the supply isn't described in the device tree), the peripheral will sit unpowered while the driver believes it initialized. I'd check the regulator and clock framework state in sysfs/debugfs, and confirm the pinmux is actually applied — a peripheral whose pins are still muxed to their reset function will not respond.

Third, do a register-level readback. If reading a known ID or status register returns 0x00 or 0xFF, the bus access itself is failing (wrong address, bus not clocked, or the peripheral held in reset). If the ID reads correctly but the device doesn't function, the issue is in the driver's initialization sequence — a missing soft-reset, a configuration write that needs a delay before the next access, or an endianness/bit-order mistake.

Finally, I'd instrument: add `dev_dbg`/`dev_info` around each register write in `probe()`, and if possible use a bus analyzer or scope to confirm the transactions actually appear on the wire. "No errors, no timeouts" often means the driver never actually touched the hardware in a way that would fail — so the fastest path is proving whether the bus traffic exists at all.

**Possible follow-ups:** How would you distinguish a device-tree resource problem from a driver initialization-order problem using only kernel logs and sysfs? What would you check first if the register readback returns a plausible but incorrect ID?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our changes on top, so we can absorb vendor updates without merge conflicts.

The mechanism is `config-fragments` via `KERNEL_CONFIG_FRAGMENTS` (or the older `SRC_URI` `.cfg` mechanism, depending on the kernel class version). I'd create a small `.cfg` file in our board layer containing only the deltas — `CONFIG_FOO=y`, `CONFIG_BAR=m` — and reference it from a `.bbappend` on the vendor's kernel recipe. The fragment is merged on top of the vendor's defconfig during `do_configure`, so the vendor recipe is untouched and the delta is explicit and reviewable.

A few practices that keep this maintainable: keep fragments small and single-purpose (one for a peripheral, one for a debug option) so they can be composed per image or per variant; use `CONFIG_...=y` lines only for what we actually need, and let `menuconfig`-style dependencies resolve; and validate the resulting `.config` with `bitbake -c diffconfig` or by diffing against the vendor defconfig so we can see exactly what changed. For options that must not be overridden by the vendor's defconfig, ordering matters — fragments are applied after the base config, so they win, but I'd still verify with `diffconfig` rather than assume.

If a change genuinely can't be expressed as a config fragment (e.g., a source patch), that goes in a separate `.patch` in the `.bbappend`'s `SRC_URI`, again leaving the vendor recipe intact. The rule I'd enforce in review: nothing in our layer edits the vendor recipe file itself.

**Possible follow-ups:** How would you handle a kernel option that the vendor's defconfig sets to `=y` but we need as `=m`? What's your approach when a vendor kernel update changes the meaning of an option we depend on?

## Q3: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is deferred indefinitely because a supplier it depends on never becomes available — with no obvious error in the kernel log?

**Answer:** An indefinite `-EPROBE_DEFER` loop means the driver is waiting on a resource that the kernel thinks isn't ready yet, and the supplier either never registers or registers under a name/phandle the consumer isn't matching. The kernel is deliberately quiet here because deferral is a normal, expected state — it's not an error until it never resolves.

First, confirm the deferral is real and identify what's being waited on. Enable `initcall_debug` and dynamic debug for the driver, or check `/sys/kernel/debug/devices_deferred` (and the driver core's deferred-probe list) to see the pending device and, where available, the reason. The `probe()` return path and any `dev_err_probe()` calls will usually name the supplier.

Second, check the supplier side. Is the supplier driver actually built and loaded? Is its device tree node present and enabled (`status = "okay"`)? A supplier node left at `status = "disabled"`, or a phandle pointing at a node that doesn't exist, produces exactly this silent loop. I'd also verify the supplier's own `probe()` isn't itself deferred on something further up the chain — deferral chains can be several links deep, and the visible symptom is at the leaf.

Third, check the matching. If the consumer looks up the supplier by name (e.g., a regulator supply name or a clock name), a mismatch between the device tree property name and what the driver requests will never resolve. Cross-check the binding documentation against the actual device tree.

Finally, if the supplier is a bus device (e.g., an I2C sensor whose parent bus isn't up yet), confirm the parent controller probes before the consumer. If ordering is genuinely wrong, the fix is usually in the device tree (correct `depends-on`-style phandles) or in making the consumer's dependency explicit rather than relying on probe order. I'd avoid "fixing" it by forcing probe order in code — that's fragile.

**Possible follow-ups:** How would you tell the difference between a deferral that will eventually resolve and one that is permanently stuck? What are the risks of working around a deferral by hard-coding initialization order?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never block on anything the logging path controls. That means separating the two paths at the data-structure level, not just at the scheduling level.

For the real-time access, I'd keep the critical section as short and lock-free as possible: the real-time task reads/writes the hardware directly (or via a minimal, pre-allocated buffer), and the only shared state is a small ring buffer or a double-buffered region protected by a spinlock held for a handful of instructions — or better, a lock-free single-producer/single-consumer ring so the real-time side never takes a lock the logging side can hold. The real-time task must never wait on a mutex, never allocate, and never sleep.

For the logging path, it consumes from the ring buffer at its own pace. If the buffer fills because logging falls behind, the policy must be explicit: either drop oldest samples (and count the drops) or overwrite — but never back-pressure the real-time producer. The logging task runs at normal priority and does the slow work (formatting, writing to a file or netlink) outside any lock the real-time path touches.

I'd also make sure the shared buffer is allocated once at `probe()` time (no runtime allocation), use `PREEMPT_RT` if the platform supports it and the deadline is tight, and document the drop policy so the system behaves predictably under load. The key review question: can the logging task, at any point, cause the real-time task to miss its deadline? If yes, the design is wrong.

**Possible follow-ups:** How would you verify the real-time path's worst-case latency under logging load? What changes if the real-time consumer is in userspace rather than in-kernel?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams have legitimate concerns and the real cost is in the transition, not the end state.

First, I'd get the facts on the table: exactly which pins move, what the new peripheral needs, and — critically — what the manufacturing line actually depends on. "Early boot console output" might mean a human watching a terminal, or it might mean an automated test fixture parsing boot logs. Those have very different risk profiles, and the answer changes the plan. I'd ask the manufacturing/test lead to confirm rather than assume.

Second, I'd scope the change honestly. Moving a UART pinmux touches the bootloader (early console), the device tree (kernel console and any userspace consumer), and possibly the test fixtures. I'd propose doing it in a way that de-risks the transition: keep the old console path working during a bring-up phase if the hardware allows both, or stage the change behind a build variant so the manufacturing line can validate the new configuration on a small batch before it becomes the default.

Third, I'd set a decision point with the project manager: the change is feasible, here's the work and the validation it needs, and here's the risk to the manufacturing schedule. I wouldn't unilaterally block the hardware change — the new peripheral presumably has a real requirement — but I'd make sure the cost is visible and owned, and that we agree on who validates the manufacturing line against the new boot console before the switch is flipped.

Throughout, I'd keep the tone collaborative: the goal is a design that meets both the peripheral requirement and the manufacturing constraint, not winning the argument.

**Possible follow-ups:** What would you do if the manufacturing team can't validate the new configuration before the hardware change is locked in? How would you document this decision so it's traceable later?
