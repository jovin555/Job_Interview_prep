# embedded-linux-bsp — Day 51

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel module that registers a platform driver never has its probe function called, even though the device tree node for the peripheral is present?
**Answer:** The first thing to establish is whether the driver is even a candidate for the device — a missing probe almost always means the match never happened, not that probe ran and failed silently. I'd start by confirming the driver is actually built and loaded: check `lsmod` or the built-in driver list, and verify the compatible string in the driver's `of_device_id` table matches the device tree node exactly, character for character. A common cause is a typo or a vendor prefix mismatch between the DTS and the driver. Next I'd check whether the node is actually being parsed — `ls /proc/device-tree/` or the sysfs `of_node` entries confirm the node survived into the live tree, and `dmesg` early in boot often shows "failed to find node" or deferred probe messages. Deferred probe is a frequent culprit: if the driver depends on a clock, regulator, or GPIO provider that hasn't probed yet, the kernel defers it, and if that dependency never resolves, probe never runs. I'd look for "probe deferred" in the log and trace which resource is missing. I'd also verify the node's `status` property isn't set to `disabled`, and that the parent bus node is enabled. If all that checks out, I'd add a print at the top of the match table or use dynamic debug to confirm the match function is being invoked at all. The systematic path is: is the driver present → does the compatible match → is the node live and enabled → are all dependencies satisfied → is probe being deferred or silently skipped.

**Possible follow-ups:** How would you tell the difference between a deferred probe that will eventually succeed and one that is stuck forever? What role does the `status` property play versus the parent node's status?

## Q2: How would you approach structuring a Yocto layer to add a vendor kernel patch and a custom device tree to an existing BSP without forking the vendor's layer?
**Answer:** The guiding principle is to never modify an upstream or vendor layer in place — you extend it from your own layer so that updates to the base layer don't collide with your changes. I'd create a new layer with the standard `layer.conf`, set its priority appropriately, and add it to `bblayers.conf` after the vendor layer so it takes precedence. For the kernel patch, I'd use a `.bbappend` on the vendor's kernel recipe, adding the patch through `SRC_URI` with a `file://` entry and a `do_patch` that applies cleanly, plus a `KERNEL_DEVICETREE` or `KERNEL_DEVICETREE_BUNDLE` override to point at my custom DTS. The device tree itself goes in the layer under a `files/` or `recipes-kernel/linux/files/` directory, and I'd reference it from the append. I'd keep the patch minimal and rebasable — a single logical change per patch file with a clear commit message — so that when the vendor bumps their kernel, rebasing is straightforward. I'd also pin the base layer revision in the manifest so builds are reproducible, and document which append touches which recipe. The key discipline is that everything custom lives in my layer, the vendor layer stays pristine, and a `bitbake-layers show-appends` confirms exactly what I'm overriding.

**Possible follow-ups:** How would you handle a situation where the vendor's kernel recipe changes its variable names between releases, breaking your append? What is the difference between `KERNEL_DEVICETREE` and `KERNEL_DEVICETREE_BUNDLE`?

## Q3: How would you approach debugging a U-Boot environment where the board boots from eMMC but intermittently falls back to a network boot, and the fallback is not intended?
**Answer:** Intermittent fallback to network boot usually means the primary boot device isn't being detected reliably, so U-Boot's boot order moves on to the next candidate. I'd first look at the boot order variable — `bootcmd` and the `boot_targets` list — to understand the intended sequence and confirm the fallback is genuinely unintended rather than a misconfigured order. Then I'd check whether the eMMC is being enumerated consistently: `mmc list` and `mmc dev` in the U-Boot console show whether the device appears, and if it sometimes doesn't, that points to a hardware or initialization timing issue — power sequencing, a slow eMMC that needs a longer reset delay, or a marginal clock. I'd compare a failing boot against a working one by capturing the full U-Boot log, looking for the point where the eMMC probe fails or times out. If the eMMC is present but the boot partition or files aren't found, the issue may be in the partition layout or the `bootargs`/`root=` path. I'd also check whether the environment itself is being corrupted or reset — a bad CRC on the saved environment can cause U-Boot to fall back to defaults, which might include network boot. The systematic approach is to separate "device not detected" from "device detected but boot failed" from "environment reset," because each has a different fix.

**Possible follow-ups:** How would you make the boot order deterministic so that an unintended fallback can't silently mask a primary boot failure? What would cause a saved U-Boot environment to fail its CRC check?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?
**Answer:** The core requirement is that the real-time path must never block on anything the logging path holds, so the design has to decouple them. I'd structure the driver so the real-time task's access path takes a short, bounded lock — ideally a spinlock held only for the register transaction itself — while the logging path never holds that lock during I/O or allocation. The logging task would read from a lock-free ring buffer that the real-time path writes into, or the driver would expose a separate read interface that snapshots data under a brief lock and copies it out afterward. The key is that the real-time path's worst-case latency is bounded by the spinlock hold time, not by anything the logger does. I'd avoid mutexes on the real-time path entirely, since a mutex can sleep and can be held indefinitely by a lower-priority task. If the hardware supports it, I'd use separate register banks or a FIFO so the two paths don't contend on the same resource at all. I'd also consider whether the logging path can be moved entirely to userspace reading from a `read()` interface that the driver fills from the ring buffer, keeping the kernel-side real-time path minimal. The design principle is: identify the shared resource, minimize the critical section, and ensure the real-time path's blocking is bounded and independent of the logging path's behavior.

**Possible follow-ups:** Why is a spinlock preferred over a mutex on a hard real-time path? How would you verify that the real-time path's worst-case latency is actually bounded?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?
**Answer:** I'd treat this as a change-management problem rather than a purely technical one, because the real risk is to a process the manufacturing line depends on. First I'd make sure everyone understands the actual constraint: the early boot console is used for factory test and diagnostics, so losing it isn't just an inconvenience — it removes a verification tool. I'd ask the hardware team to quantify what the new peripheral buys and whether the pin can be freed another way, since pinmux changes are often avoidable with a different package or a reallocation elsewhere. If the change is genuinely necessary, I'd propose a phased approach: keep the current debug UART on its existing pins for the current revision, and move it only on a future revision where the manufacturing process can be updated in step. I'd want the decision documented with the trade-off — what's gained, what's lost, and who owns updating the factory test procedure. If the change must happen now, I'd require that the new pinmux be validated on a prototype before the manufacturing line is touched, and that the bootloader and device tree changes be reviewed together so early boot and kernel console stay consistent. The goal is to avoid a situation where hardware ships a change that silently breaks a downstream process nobody re-validated.

**Possible follow-ups:** How would you decide whether the manufacturing line's dependency on the debug console is a hard constraint or something that can be reworked? What would you put in the change record to make the decision traceable later?
