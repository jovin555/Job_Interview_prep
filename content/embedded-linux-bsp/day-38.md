## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of two identical I2C sensors on the same bus, while the other works fine?

**Answer:** I'd start by confirming the problem is at the hardware level rather than the device tree or driver level. First, I'd check `i2cdetect` to see if the sensor appears on the bus at all. If it doesn't appear, I'd verify the sensor's address — identical sensors often have address-select pins that may be strapped differently on the board. I'd check the schematic to confirm the address pins are tied to the correct rails, and then measure the voltage on those pins with a multimeter to ensure they're actually at the expected logic levels. I'd also check the sensor's power supply and reset pins — a missing decoupling capacitor or a floating reset line can cause one sensor to power up in an undefined state. If the sensor does appear in `i2cdetect` but the kernel driver doesn't bind, I'd check the device tree entry — the address, the compatible string, and the interrupt line. A common issue is two nodes with the same address or an interrupt that's already claimed by another device. I'd also check `dmesg` for probe errors, which often tell you exactly what the driver is unhappy about. If the hardware and device tree look correct, I'd use a logic analyzer on the I2C lines while the driver probes to see if the sensor is actually ACKing its address — this distinguishes a sensor that's not responding from a driver that's not trying to talk to it.

**Possible follow-ups:**
- How would you distinguish between a device tree issue and a hardware issue in this scenario?
- What if both sensors have the same address and there's no address-select pin — how would you handle that?

## Q2: How would you approach designing a kernel driver for a device that needs to log sensor data to a file on the root filesystem at a fixed rate (e.g., 100 Hz) without causing filesystem corruption on unexpected power loss?

**Answer:** The first principle is that the kernel driver should not be writing to a filesystem directly. Filesystem writes belong in userspace, where you have access to proper file I/O, buffering, and crash recovery mechanisms. So I'd structure this as a kernel driver that collects sensor data into a ring buffer, and a userspace daemon that reads from the driver (via a character device or netlink) and handles the file logging. For the filesystem side, I'd use a journaling filesystem like ext4 or a flash-friendly filesystem like UBIFS or F2FS, depending on the storage medium. The daemon should write to a temporary file and then atomically rename it into place periodically, so a crash mid-write never leaves a partially-written log file. I'd also consider using `fsync` or `fdatasync` at appropriate intervals — not on every write, because that would kill throughput, but periodically (e.g., every second or every N records) to bound the amount of data that could be lost on power failure. If the data is critical, I'd also think about writing to a separate partition or using a circular buffer of log files so that a corrupted file doesn't take down the whole system. For the kernel side, I'd use a high-resolution timer or hrtimer to trigger sampling at 100 Hz, and I'd use a kernel workqueue or tasklet to move data from the interrupt context to the ring buffer. The userspace daemon would use `poll()` or `epoll()` on the character device to be notified when data is available, then read it in batches to minimize syscall overhead.

**Possible follow-ups:**
- What filesystem features would you look for to minimize data loss on power failure?
- How would you handle the case where the userspace daemon crashes or is killed — how does the driver behave?

## Q3: How would you approach implementing a kernel driver for a device that uses DMA to transfer data from an FPGA to system memory, where the FPGA can generate data at rates exceeding what the CPU can process in real-time?

**Answer:** The key is to decouple the DMA transfer rate from the CPU processing rate using buffering and flow control. I'd start by understanding the FPGA's DMA capabilities — does it support scatter-gather lists, or only contiguous transfers? Does it have a flow-control mechanism like a watermark interrupt or a pause signal? For the driver, I'd set up a pool of DMA buffers — typically a ring of 4-8 buffers, each sized to hold a reasonable chunk of data (e.g., 64 KB). The FPGA DMA controller writes into one buffer while the CPU processes another. When a buffer is full, the DMA controller raises an interrupt, and the driver's interrupt handler moves that buffer to a "ready" queue and hands the FPGA the next empty buffer from the pool. This is a classic double-buffering or multi-buffering approach. If the FPGA can outpace the CPU even with multiple buffers, I need flow control. Options include: having the FPGA pause when no empty buffers are available (via a GPIO or a register write), or using the DMA controller's flow-control feature if it exists. I'd also consider using the kernel's DMA API correctly — `dma_alloc_coherent` for buffers that need to be visible to both the device and the CPU, or `dma_map_single`/`dma_map_sg` for streaming DMA. For the userspace interface, I'd expose the ready buffers via a character device with `read()` or `mmap()`, and use `poll()` so userspace can block until data is available. If the data rate is truly higher than what the CPU can consume, the design needs to drop data gracefully — I'd implement a policy (e.g., drop oldest or newest) and expose a counter so userspace knows data was lost.

**Possible follow-ups:**
- How would you choose the number and size of DMA buffers?
- What happens when the FPGA outpaces the CPU for an extended period — how does the system behave?

## Q4: How would you approach debugging a kernel panic that occurs only on every third or fourth boot, with no consistent trigger?

**Answer:** Intermittent kernel panics are among the hardest problems to debug because the trigger is often timing-dependent or hardware-dependent. I'd approach this systematically. First, I'd capture the full panic message — not just the last few lines, but the complete oops output including the register dump, the call trace, and the "Kernel panic - not syncing" line. I'd enable `CONFIG_PANIC_ON_OOPS` and `CONFIG_DEBUG_INFO` in the kernel config so I get a usable stack trace. I'd also enable `CONFIG_DEBUG_PAGEALLOC`, `CONFIG_DEBUG_SLAB`, and `CONFIG_DEBUG_SPINLOCK` to catch memory corruption or locking issues early. Next, I'd try to correlate the panics with environmental factors — temperature, power supply behavior, or specific hardware states. If the panic happens during boot, I'd add `initcall_debug` to the kernel command line to see which initialization call is running when it crashes. I'd also try to reproduce it under controlled conditions — booting in a loop with a script that logs the serial console output to a file, so I can compare successful and failed boots. If the panic is in a driver, I'd suspect a race condition in the probe or initialization path. I'd review the driver code for missing locking, use-after-free, or improper DMA buffer handling. If the panic is in core kernel code, I'd suspect memory corruption from a driver writing out of bounds, or a hardware issue like marginal timing on the memory bus. I'd also check for known errata on the SoC or memory controller. If I can't reproduce it reliably, I'd add `CONFIG_KALLSYMS` and `CONFIG_DEBUG_BUGVERBOSE` to get more information, and I'd consider using `kexec` with a crash kernel to capture a full memory dump when the panic occurs.

**Possible follow-ups:**
- How would you use a crash dump (e.g., via kdump) to analyze the panic after the fact?
- What kernel config options would you enable to get more diagnostic information?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during integration testing, you discover that the kernel's real-time scheduling class (SCHED_FIFO) is causing priority inversion on a shared hardware resource between your sensor driver and the display driver. The display team insists their driver needs the highest priority, and the sensor team says their data will be corrupted if they miss their deadline. How would you handle this situation?

**Answer:** I'd start by getting both teams to agree on the facts — specifically, what the actual deadlines and worst-case execution times are for each driver. Priority inversion happens when a high-priority task is blocked by a low-priority task holding a shared resource, so the first step is to identify the shared resource and understand the locking protocol. I'd ask the display team to quantify what "needs the highest priority" means — what's the worst-case latency they can tolerate before the display visibly glitches? Similarly, I'd ask the sensor team to quantify the deadline and what happens if it's missed — is data corrupted, or just delayed? With those numbers, I can analyze whether the current priority assignment actually violates either deadline. If it does, I'd look at solutions that don't require changing priorities: using priority inheritance (e.g., `rt_mutex` instead of a plain spinlock), or restructuring the code so the shared resource is held for a shorter critical section. If the resource is a hardware register or a small data structure, I might be able to use a seqlock or a lock-free approach. If the conflict is fundamental, I'd propose a compromise — for example, the sensor driver gets higher priority but the display driver uses a double-buffer so it can tolerate occasional delays. I'd also check whether the display driver really needs SCHED_FIFO at all — many display updates can be handled by a normal priority thread with a small enough jitter. The key is to move the discussion from "my driver needs the highest priority" to "here's the deadline, here's the worst-case execution time, and here's the shared resource." I'd document the analysis and the decision in the design review so it's traceable for regulatory purposes.

**Possible follow-ups:**
- How would you verify that the priority assignment you choose actually meets both deadlines under worst-case conditions?
- What if the two teams can't agree on the analysis — how do you escalate or resolve the conflict?
