# embedded-linux-bsp — Day 65

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is deferred indefinitely because a supplier it depends on never becomes available — with no obvious error in the kernel log?

**Answer:** Deferred probe is one of the more frustrating classes of bring-up bugs precisely because it is silent by design — the kernel assumes the supplier will show up eventually, so it parks the consumer and moves on rather than logging a hard failure. The first thing I'd do is confirm that deferred probe is actually what's happening rather than a probe that simply never ran. The kernel exposes this through `/sys/kernel/debug/devices_deferred` (when debugfs is mounted), which lists devices currently sitting in the deferred state along with the reason string the driver passed to `-EPROBE_DEFER`. If the device isn't in that list at all, the problem is upstream — the device tree node isn't matching, the driver isn't built in, or the compatible string is wrong — and I'd pivot to checking `of_match_table` and the kernel config.

If it is deferred, the reason string usually names the missing supplier: a clock, a regulator, a PHY, a pinctrl state, or an upstream bus like an I2C controller. From there I'd walk the supplier chain. A common cause is a circular or mis-ordered dependency — for example, a sensor whose `vdd-supply` points at a regulator that itself depends on an I2C bus that isn't up yet, so neither side can complete. Another common cause is a supplier that is present in the device tree but whose own driver never probes because *its* supplier is missing, so the deferral cascades. I'd trace the chain with `devlink`-style reasoning: consumer → supplier → supplier's supplier, until I find the node that is genuinely absent, disabled (`status = "disabled"`), or bound to a driver that isn't compiled in.

On the hardware side, I'd also verify that the supplier is actually reachable — a regulator whose enable GPIO is misconfigured, or a clock that the bootloader never ungated, can leave the supplier driver stuck in its own probe. If the supplier is an external chip on I2C or SPI, I'd confirm it ACKs on the bus with a scope or a bus scan, because a supplier that never responds will keep the consumer deferred forever with no error. The fix is usually one of: correct the device tree dependency, enable the missing driver in the kernel config, fix the supplier's own probe, or — if the dependency is genuinely optional — make the consumer tolerate its absence rather than hard-requiring it.

**Possible follow-ups:**
- How would you distinguish a genuine deferred-probe loop from a one-time deferral that resolves on the next probe attempt?
- If the supplier is an external chip that only becomes ready after a firmware load, how would you sequence that so the consumer doesn't spin in deferred probe forever?

## Q2: You're structuring a Yocto BSP for a product family where several boards share a common SoC and vendor BSP but differ in peripherals, device tree, and userspace packages. How would you organize the layers and recipes?

**Answer:** The guiding principle is to push everything shared as far down the layer stack as possible and keep board-specific content in the thinnest possible layer on top. I'd typically end up with three tiers. At the bottom, the vendor's SoC BSP layer stays untouched — I never fork it, because forking means every vendor update becomes a manual merge. Above that, a common product-family layer holds the shared kernel recipe append, the shared U-Boot config, the common root filesystem package set, and any patches that apply to the whole family. On top, one thin machine layer per board holds only what genuinely differs: the machine conf (`MACHINE` definition, `KERNEL_DEVICETREE`, `SERIAL_CONSOLES`), the board's device tree source, and any board-only packages.

The mechanism that makes this clean is `MACHINEOVERRIDES`. I'd define a family-level override (say `myfamily`) that every board machine inherits, so a recipe can say "apply this patch for `myfamily`" and it lands on all boards, while a board-specific override (`myboard-a`) applies only to that board. That way the common layer doesn't need to know the board names, and adding a new board is mostly a matter of adding a machine conf and a device tree rather than editing shared recipes.

For the kernel specifically, I'd keep a single kernel recipe for the family and use `SRC_URI` with override-qualified device tree files and config fragments, so each board pulls in its own `.dts` and its own `cfg` fragment without forking the recipe. For userspace, I'd use `IMAGE_FEATURES` and `IMAGE_INSTALL` with override-qualified appends so that, for example, a board with a touchscreen pulls in the touchscreen userspace stack while a headless board doesn't. The test of whether the structure is right is: adding a new board should touch only the board layer, and a vendor BSP bump should require no changes to the family or board layers beyond rebasing patches.

**Possible follow-ups:**
- How would you handle a patch that applies to two of your boards but not the third, without duplicating it?
- What would you put in `local.conf` versus in the machine conf, and why does that boundary matter for reproducibility?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path controls, so the design has to decouple the two rather than have them share a lock. The cleanest pattern is a producer/consumer split: the real-time path acquires the data and hands it off through a lock-free or minimally-contended mechanism, and the logging path drains that mechanism at its own pace. If the real-time path and the logging path both take the same mutex around the device, then a slow logger holding the lock will stall the real-time task — that's the failure mode to design out from the start.

Concretely, I'd use a ring buffer between the two. The real-time path writes into the ring with a single-producer discipline — typically a memory barrier plus an index update, no sleeping, no allocation, no blocking calls. The logging path reads from the ring as a single consumer. If the ring fills because the logger is slow, the real-time path must not block; it either overwrites the oldest entry (if losing old log data is acceptable) or drops the new entry and increments a counter (if the newest data matters more). Which policy is correct depends on whether the log is for diagnostics or for a safety record, and that's a decision to make explicitly with the system owner rather than defaulting.

For the device access itself, if the hardware can be read without a lock — for example, a memory-mapped register that the real-time task owns — I'd give the real-time task exclusive ownership of the hardware and have it be the only thing that touches the device, with the logger consuming only the ring. If both genuinely need to touch the device, I'd look at whether the hardware supports separate channels or a hardware FIFO that the real-time task drains and the logger reads from a shadow copy. The logging path can afford to sleep, allocate, and write to the filesystem; the real-time path cannot. Keeping that asymmetry explicit in the code — separate functions, separate locking domains, a documented contract — is what makes the design hold up under load.

**Possible follow-ups:**
- How would you verify that the real-time path's worst-case latency is actually bounded, rather than just assuming it?
- If the ring buffer is in kernel space, how does the logging task get the data — a char device read, a `relayfs`-style interface, or something else, and what are the trade-offs?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** Intermittent fallback almost always means the primary boot path is failing *sometimes* and the bootloader is doing exactly what its boot order tells it to do — trying the next entry. So the first question is not "why is it network booting" but "why is the eMMC path failing intermittently." I'd start by capturing the full console log on a failing boot, because U-Boot prints the reason it moved on: a failed `mmc` initialization, a missing boot script, a bad image header, or a timeout. Without that log, everything else is guessing.

Common causes for intermittent eMMC boot failure include marginal power sequencing (the eMMC not being ready when U-Boot first probes it, which can be timing- or temperature-dependent), a boot partition or boot script that is occasionally corrupted, or a `bootcmd` that has a fallback chain the team didn't realize was there. I'd check the environment first: `printenv bootcmd` and the `boot_targets` variable, because a default environment from the vendor BSP often includes `pxe` or `dhcp` in the boot order, and if the eMMC entry fails even once, the fallback fires. If the fallback was never intended, the fix may be as simple as removing the network entries from `boot_targets` — but that treats the symptom, so I'd still chase the eMMC failure.

On the hardware side, I'd look at whether the eMMC's power rail and reset line are stable at the moment U-Boot probes it, and whether the boot mode straps are being read reliably. If the failure correlates with cold boot versus warm boot, or with temperature, that points at power sequencing or signal integrity rather than software. I'd also check whether the eMMC is being re-initialized correctly after a previous failed boot — a device left in an odd state by a prior attempt can fail the next one. The disciplined approach is to reproduce the failure with logging enabled, identify the exact point of failure, fix that, and only then decide whether the network fallback should be removed or kept as a deliberate recovery path.

**Possible follow-ups:**
- How would you make the fallback deterministic — either always present or always absent — rather than dependent on a race?
- If the eMMC failure only reproduces on a fraction of units, how would you decide whether it's a hardware population issue or a software timing issue?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** The first thing I'd do is separate the two concerns that are being conflated: the *technical* question of whether the pinmux can be moved, and the *process* question of what the manufacturing line actually depends on. Those have different owners and different timelines, and treating them as one argument tends to stall. I'd get the hardware team to state precisely which pins the new peripheral needs and whether there's an alternative pinmux option that avoids the debug UART, because "free up pins" sometimes has more than one solution. In parallel, I'd ask manufacturing to be specific about what they rely on — is it the console output during early boot, the physical connector location, or a test fixture that expects the UART on a particular header? Those are different constraints with different costs to change.

If the move is genuinely necessary, I'd treat it as a change with a migration plan rather than a yes/no. The device tree change is straightforward — update the pinmux node and the `stdout-path` — but the bootloader console and any manufacturing test scripts also reference the UART, so those need to move together or the line breaks in a way that's hard to diagnose. I'd want the change staged so that both the old and new console paths work during a transition window if that's feasible, or at minimum so that the manufacturing team has a validated new fixture before the old one is removed. The risk isn't the pinmux change itself; it's a silent break in a process that a different team owns.

The leadership part is making sure the decision is made with the right people in the room and the trade-off is explicit. I'd frame it as: here's what the change costs in software and manufacturing effort, here's what it buys in board real estate, and here's the schedule impact. If the hardware team's need is real and the manufacturing impact is manageable, we do it with a plan. If the manufacturing impact is severe and there's an alternative pinmux, we take the alternative. What I'd avoid is either team unilaterally deciding, because both have legitimate constraints and the cost of getting it wrong lands on the other.

**Possible follow-ups:**
- How would you decide whether to keep a transitional dual-console configuration versus a hard cutover?
- If manufacturing says the change is unacceptable and hardware says it's required, how would you escalate or resolve the deadlock?
