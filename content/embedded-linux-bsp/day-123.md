# embedded-linux-bsp — Day 123

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder classes of bug because the kernel is telling you everything went fine, so the fault is almost certainly in what the driver *didn't* verify rather than in what it reported. I'd start by questioning the assumption that "probe returned success" means the hardware is actually reachable. The first thing I'd do is confirm the driver is talking to the right register addresses — dump the device tree node the driver bound to (`/sys/firmware/devicetree/base/...` or via `of_node` debugfs) and compare the `reg`, `interrupts`, and clock/regulator phandles against the schematic and the SoC reference manual. A very common cause is a base address or size that's off, so the driver happily reads and writes to a region that decodes to nothing or to the wrong peripheral, and because the bus doesn't fault, no error surfaces.

Next I'd verify the driver is actually touching hardware at all. Adding a read-back of a known register — an ID register or a reset-default value — right after `probe()` is the cheapest possible sanity check, and if the value doesn't match the datasheet, the problem is upstream of the driver logic: pinmux, clock gating, power domain, or reset deassertion. I'd check `clk_summary` in debugfs to confirm the peripheral clock is actually running and at the expected rate, and check that the regulator supplying the device is enabled. A device that's clocked but unpowered, or powered but with its reset line still asserted, will accept register writes into a void and read back zeros or garbage without ever generating a bus error.

If the register access looks sane, I'd move outward: scope or logic-analyze the actual bus lines (I2C/SPI) during a transaction to see whether the driver's writes are physically leaving the SoC. That distinguishes "driver logic bug" from "hardware bring-up bug" definitively. On the software side I'd also check whether the driver's `probe()` is returning before it finishes initialization — for example, deferring work to a workqueue or threaded IRQ that never fires because the interrupt isn't actually wired or the trigger type in the device tree is wrong (edge vs level). A level-triggered interrupt configured as edge, on a line that's already asserted, will never fire and the driver will sit silently waiting.

Finally, I'd instrument rather than guess: add `dev_dbg`/`dev_info` at each hardware access in `probe()` and in the first read/write path, and enable dynamic debug for that driver. The goal is to turn "silence" into a trace of exactly which register accesses happened and what came back.

**Possible follow-ups:** How would you tell the difference between a pinmux problem and a clock/power problem without a schematic in front of you? What would you check first if the register read-back returned all-ones instead of all-zeros?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe and layer untouched so you can pull their updates, and express your board's differences as additive configuration on top. The clean mechanism for that is a kernel config fragment plus `KERNEL_FEATURES` or a `.scc`-style fragment referenced from your own layer's `linux-yocto`/vendor-kernel append, rather than editing the defconfig in place.

Concretely, I'd create a `.cfg` fragment in my layer containing only the `CONFIG_*` lines my board needs — the specific drivers, bus options, and debug settings — and reference it from a `SRC_URI` append in a `linux-<vendor>_%.bbappend` that lives in my layer. The fragment gets merged by the kernel's config machinery (`merge_config.sh` under the hood), so the vendor's base config stays authoritative and my additions are layered on top. If the vendor kernel is `linux-yocto`-style, I'd use the `.scc`/`KERNEL_FEATURES` route so the fragment is described as a named feature rather than a loose file. The key discipline is that the fragment contains *only* deltas — never a full defconfig copy — so when the vendor changes their base config, my fragment still applies and I can see exactly what I'm adding.

I'd also make the fragment reviewable and version-controlled alongside the board's device tree and bootloader config, so the whole board definition lives in one place. For validation, I'd add a build-time or CI check that the resulting `.config` actually contains the options I expect — a fragment that silently fails to apply (because a symbol was renamed or depends on something not yet enabled) is a classic trap, and `bitbake -c menuconfig` or a diff of the generated `.config` against expectations catches it. Where an option has dependencies, I'd enable the dependencies explicitly in the fragment rather than relying on `select` behavior, so the fragment is self-documenting.

**Possible follow-ups:** What happens if two fragments in the same build set the same symbol to different values, and how would you control which wins? How would you handle a board option that requires a source patch as well as a config change?

## Q3: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never block on anything the logging path controls, so the two paths need to be decoupled rather than sharing a single lock or a single buffer. I'd design the driver around a lock-free or minimally-contended handoff: the real-time access path (whether that's an interrupt handler, a high-priority threaded IRQ, or a `SCHED_FIFO` userspace thread doing `ioctl`) takes a short spinlock or uses per-CPU/atomic structures to grab the data, and the logging path consumes from a separate ring buffer that the real-time path only ever *appends* to.

The classic implementation is a single-producer/single-consumer ring buffer: the real-time side writes samples and advances a head pointer with release semantics; the logging side reads from the tail and advances it independently. Neither side takes a mutex the other can hold, so the logging task can be preempted, descheduled, or slow without ever blocking the producer. If the buffer fills because logging can't keep up, the real-time path must have a defined, non-blocking policy — drop oldest, drop newest, or overwrite — chosen so that data loss is bounded and the real-time deadline is still met. Dropping samples is almost always preferable to blocking the real-time path.

I'd also be careful about the hardware access itself. If both paths touch the same peripheral registers, the real-time path needs priority on the bus; I'd give the logging path its own read of a shadow/cached copy rather than letting it issue hardware transactions that could contend. For the interrupt side, a threaded IRQ with a high `sched_priority` and `IRQF_ONESHOT` handling, with the logging work pushed to a workqueue or a separate lower-priority thread, keeps the top half minimal. And I'd verify the design under load — run the logging consumer artificially slow (or stop it entirely) and confirm the real-time path's latency is unchanged, using `cyclictest` or an in-driver timestamp to measure worst-case jitter.

**Possible follow-ups:** How would you bound the worst-case latency of the real-time path if the ring buffer is full? What would change if the real-time consumer were in userspace rather than in the kernel?

## Q4: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?

**Answer:** `EINTR` means a blocking syscall was interrupted by a signal that was delivered and handled (or whose handler was set without `SA_RESTART`), so the first job is to find out what signal is arriving and why the daemon treats it as fatal. I'd start by checking whether the daemon installs handlers for signals it doesn't expect — `SIGCHLD` from a forked child, `SIGPIPE` from a socket, `SIGALRM` from a timer, or a real-time signal used by a library — and whether those handlers are installed without `SA_RESTART`, which is exactly what turns a blocking `ioctl` into an `EINTR` return. `strace -f -e trace=signal,ioctl` on the daemon is the fastest way to see the signal number and the syscall it interrupted.

The second angle is that the driver itself may be the source. If the driver's `ioctl` waits on a waitqueue or completion and the process receives a signal while waiting, the kernel returns `-ERESTARTSYS`, which the syscall layer translates to `EINTR` unless the driver used an uninterruptible wait. So I'd look at whether the driver's blocking path uses `wait_event_interruptible` (interruptible, returns `-ERESTARTSYS`) versus `wait_event` (uninterruptible). If the driver is *supposed* to be interruptible, then the daemon must handle `EINTR` by retrying — that's the correct userspace contract, and a daemon that aborts on `EINTR` is simply buggy. If the driver should not be interruptible for this particular operation, that's a driver fix.

I'd also consider whether the signal is coming from the environment: a watchdog or supervisor sending `SIGTERM`/`SIGUSR1`, a `systemd` unit with a `WatchdogSec` that fires, or a debug tool. And I'd check whether the daemon is multi-threaded — a signal delivered to one thread can interrupt a syscall in that thread while the main thread is unaware, which produces exactly this "nothing is sending signals" confusion.

The fix depends on which side is wrong: if the signal is legitimate and the operation is restartable, the daemon should loop on `EINTR`; if the driver is returning `EINTR` spuriously, fix the wait; if an unexpected signal is being delivered, find and remove its source. The one thing I would *not* do is blanket-retry without understanding, because that can mask a real termination request.

**Possible follow-ups:** How would you distinguish a signal delivered to the process from one delivered to a specific thread? What's the difference between `-ERESTARTSYS` and `-ERESTARTNOINTR` from the driver's perspective?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams are right about their own constraints and the real question is how to sequence the change so neither side's requirement is silently broken. My first move would be to get the actual constraints on the table in concrete terms: which pins the new peripheral needs, why that specific pinmux group, what the manufacturing line actually depends on (is it the UART console output itself, or a specific test that parses it?), and what the bootloader and device tree currently encode. Often the "manufacturing depends on it" concern turns out to be narrower than it sounds — a specific test fixture or a specific log string — which changes the solution space.

Then I'd look for options that decouple the two needs. The debug UART and the manufacturing console don't have to be the same physical port: the bootloader can be configured to output early console on one UART and hand off to the kernel on another, or the manufacturing test can be pointed at a different interface entirely. If the pinmux change is genuinely necessary, I'd want it staged so that the bootloader and device tree changes land together, with the manufacturing team given a build to validate against their fixtures *before* the change is declared done — not after. I'd also want a fallback: if the new pinmux breaks early boot console in a way that can't be resolved quickly, we need a known-good configuration to revert to, because a medical device project can't afford to be stuck mid-change near a milestone.

On the process side, I'd make sure the decision and its rationale are documented and that the manufacturing and quality stakeholders are in the loop, since in a regulated context a change to the boot console can touch validation evidence. I'd frame the conversation around "what does each team actually need, and what's the cheapest way to satisfy both" rather than "whose change wins," and I'd own the integration plan so the change is verified end-to-end rather than handed off between teams.

**Possible follow-ups:** How would you decide whether to accept the pinmux change at all versus pushing back on the hardware team? What would you do if the manufacturing team couldn't validate the new configuration before the milestone?

**Possible follow-ups (Q5 continued):** How would you document this decision so it's traceable for a later regulatory review?
