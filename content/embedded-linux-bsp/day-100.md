# embedded-linux-bsp — Day 100

## Q1: How would you approach deciding whether a peripheral driver should be built into the kernel image versus built as a loadable module, for a device that must be functional before the root filesystem is mounted?

**Answer:** The deciding factor is *when* the device is needed relative to the availability of userspace and the root filesystem. A loadable module can only be loaded after the kernel has mounted the root filesystem and started `modprobe`/`udev` (or an initramfs has provided the module). So if the peripheral must be operational before that point — for example, the storage controller that hosts the root filesystem itself, the console UART used for early boot logging, or a regulator/clock that other early drivers depend on — it must be built in (`=y`), not modular (`=m`).

The reasoning chain I'd walk through:

1. **Dependency ordering.** Map out what needs the device and when. If anything in the pre-rootfs path (bootloader handoff, early console, rootfs storage, initramfs) touches it, it's built-in.
2. **Rootfs chicken-and-egg.** A driver needed to *reach* the rootfs obviously cannot live on that rootfs as a module unless you use an initramfs to stage it — which adds complexity and boot time.
3. **Size and flexibility trade-off.** Modules keep the base image small and let you update a driver without reflashing the kernel, which is attractive for field serviceability. But that flexibility is worthless for a device that's on the critical boot path.
4. **Initramfs as the escape hatch.** If a driver is large or rarely used but still needed early, an initramfs with the module baked in gives you modularity without a monolithic kernel — at the cost of maintaining the initramfs.
5. **Regulatory/verification angle.** For a medical device, a built-in driver is part of the signed kernel image and simpler to lock down and verify; a loadable module adds another artifact to control and validate.

In practice I'd default critical-path drivers to built-in, keep optional/leaf peripherals as modules, and document the decision per driver so it's reviewable.

## Q2: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** "Probe succeeded but nothing works and there are no errors" usually means the driver believes it has configured the hardware, but something between the driver's assumptions and the actual silicon is wrong — and the failure mode is silent because nothing is timing out or erroring, it's just not doing anything observable. I'd work from the outside in:

1. **Confirm the device is actually being exercised.** Add instrumentation or use a bus analyzer / logic analyzer on the actual pins. If there's no traffic on the bus at all, the driver may be writing to a register block that isn't decoded, or the peripheral clock/power isn't actually on despite probe "succeeding."
2. **Check register access.** Read back a known register (e.g., a chip-ID or scratch register) and confirm the value matches the datasheet. A read that returns all-zeros or all-ones, or a write that doesn't stick, points to a clock/reset/power-domain problem or a wrong base address in the device tree.
3. **Verify the device tree description.** Wrong `reg` address, wrong interrupt number, missing `clocks`/`resets`/`power-domains` phandles, or a compatible string that binds to a driver expecting different register layout — all can let probe "succeed" while the driver talks to the wrong thing.
4. **Check pinmux.** If the pins aren't muxed to the peripheral function, the bus is electrically dead but the CPU-side register writes still complete — silent failure. Confirm the pinctrl state is applied.
5. **Look at the driver's own sequencing.** Does it enable the peripheral (set an enable bit, release reset, start a clock) that the hardware actually requires? A driver written against a reference board may skip a step the new board needs.
6. **Compare against a known-good path.** If the same IP works on a dev board, diff the device tree, pinmux, and clock/power setup between the two.

The key discipline is: don't trust "probe returned 0" as evidence the hardware is alive — prove it with a register read-back and a bus capture.

## Q3: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of the kernel source and base config, and layer your board-specific deltas on top through configuration fragments rather than editing the recipe or the defconfig directly. The mechanism is `config fragments` combined with `KERNEL_FEATURES` / `SRC_URI` in a `.bbappend`:

1. **Create a `.bbappend`** for the vendor kernel recipe in your own layer (e.g., `linux-vendor_%.bbappend`), so you never touch the vendor layer.
2. **Add a config fragment** as a `.cfg` file in your layer (e.g., `files/myboard.cfg`) containing just the `CONFIG_...=y/m` lines you need. Reference it via `SRC_URI` with the `file://` and let the kernel's `merge_config`/`config fragment` machinery apply it on top of the base config.
3. **Use `KERNEL_FEATURES`** if the fragments are organized as reusable features (`.scc` files), which is the more scalable approach when multiple boards share overlapping deltas.
4. **Keep fragments minimal and additive.** Only list what you change; don't paste a full defconfig, or you'll silently override vendor choices and create merge conflicts on kernel bumps.
5. **Validate the merged config.** After building, confirm the resulting `.config` has your options set and that nothing you depended on got dropped — `bitbake -c menuconfig` or diffing the generated config against the base catches drift.
6. **Version-control the fragments** and document why each option exists, so a kernel version bump can be re-validated rather than blindly carried forward.

This keeps the vendor recipe upgradable: when the vendor bumps their kernel, your `.bbappend` and fragments re-apply on top, and any option that no longer exists surfaces as a merge warning rather than a silent fork.

## Q4: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?

**Answer:** `EINTR` means a blocking syscall was interrupted by a signal before it completed. If nothing is *intentionally* signaling the daemon, the signal is coming from somewhere the application doesn't expect — and the daemon's bug is that it treats `EINTR` as fatal instead of retrying. I'd separate the two problems: *why is a signal arriving*, and *why does the daemon die on it*.

1. **Fix the daemon's error handling first (correctness).** A well-written daemon retries on `EINTR` for `ioctl`, `read`, `write`, `select`, etc. — `EINTR` is not an error, it's "try again." If the daemon aborts on `EINTR`, that's a latent bug regardless of the signal source. This is the robust fix and should go in regardless.
2. **Find the signal source.** Common culprits: a watchdog or supervisor sending `SIGCHLD`/`SIGTERM`/`SIGUSR`, a `SIGALRM` from an interval timer, a debugger or `strace` attaching, job-control signals, or the kernel delivering `SIGIO` if async I/O is enabled on a fd. Check `/proc/<pid>/status` for pending/blocked signals, and instrument with a signal handler that logs `siginfo` (signal number, sender PID) to identify the source.
3. **Check whether the driver itself is generating signals.** If the driver uses `fasync`/`SIGIO` for async notification, the daemon may be receiving `SIGIO` and its handler isn't `SA_RESTART`, so the `ioctl` gets interrupted. Either install handlers with `SA_RESTART` or handle `EINTR` explicitly.
4. **Check for `SA_RESTART` semantics.** Some syscalls are never restarted even with `SA_RESTART` (e.g., `ioctl` on certain fds, `select`, `poll` with timeout). So even a "well-behaved" signal can produce `EINTR` — reinforcing that the daemon must retry.
5. **Rule out a driver-side issue.** If the `ioctl` is blocking in the driver waiting on hardware and a signal arrives, the driver should return `-ERESTARTSYS` so the kernel restarts or returns `EINTR` cleanly. A driver that mishandles interrupted waits can produce spurious `EINTR` or worse.

Net: make the daemon resilient (retry on `EINTR`), then hunt the signal source to eliminate the surprise.

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** This is a cross-team trade-off between a hardware pin-budget need and a software/manufacturing dependency, and my job as BSP lead is to make the cost and risk visible and drive to a decision rather than let either side dig in. My approach:

1. **Understand both constraints precisely.** From hardware: which pins, why now, and is there an alternative pin or package option? From software/manufacturing: exactly what depends on the current debug UART — is it the bootloader console, the kernel `earlycon`, the manufacturing test fixture, or all three? "The manufacturing line relies on it" needs to be pinned down to specific scripts and fixtures.
2. **Quantify the change surface.** Moving the UART touches the bootloader pinmux, the kernel device tree pinctrl, possibly the `earlycon`/`stdout-path` in the chosen node, and any manufacturing test tooling that parses that console. I'd enumerate every artifact so the estimate is real, not hand-waved.
3. **Look for a lower-risk path.** Options to table: keep the debug UART where it is and move the *new* peripheral to the freed pins instead; add a second UART for debug and repurpose the old one; gate the change behind a board revision so existing units and the current manufacturing flow are untouched while new builds adopt the new pinmux.
4. **Protect manufacturing continuity.** If the console must move, the manufacturing fixture and test scripts need a transition plan — ideally the fixture auto-detects or supports both, or the change lands with a board revision boundary so there's no window where the line is broken.
5. **Make the decision explicit and documented.** Bring the trade-off (pin budget vs. revalidation cost and manufacturing risk) to the review with a recommendation, get sign-off from hardware, software, and manufacturing, and record it — because this kind of pinmux change has a habit of resurfacing late if it isn't written down.
6. **De-risk with a prototype.** Before committing the whole line, validate the new pinmux on a bench board: confirm bootloader console, `earlycon`, and kernel console all come up on the new pins, and that the freed pins actually work for the new peripheral.

The framing I'd use in the room: this isn't "hardware vs. software," it's "what's the cheapest way to get the new peripheral its pins without breaking a validated manufacturing dependency" — and a board-revision boundary is often the answer that satisfies both.

**Possible follow-ups:**
- If manufacturing insists the console must stay on the current pins for the life of the product, how would you negotiate a path forward with the hardware team?
- How would you structure the device tree and bootloader so a future pinmux change is a one-line diff rather than a scattered edit?
