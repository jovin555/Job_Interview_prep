## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of two identical I2C sensors on the same bus, while the other works fine?
**Answer:** I'd start by confirming the problem is at the hardware or software level. First, I'd check `i2cdetect` to see if the device appears on the bus at all. If it doesn't appear, I'd verify the sensor's address — identical sensors can have different addresses depending on strap pins or address-select lines, so I'd check the schematic to confirm the address pins are set correctly. I'd also check for a missing or incorrect pull-up on the address pin, or a solder issue on the board. If the device does appear in `i2cdetect` but the kernel driver doesn't bind, I'd check the device tree — the node may have the wrong address, the wrong compatible string, or be disabled. I'd also verify the interrupt line, since a sensor with a misconfigured or floating interrupt can fail to probe even though the I2C communication itself works. I'd use `i2cdump` to read the device registers and confirm it responds correctly, and check `dmesg` for probe errors. If the hardware checks out, I'd compare the working sensor's device tree node against the non-working one to spot any differences.

**Possible follow-ups:** How would you distinguish between a device tree issue and a hardware issue in this scenario? What if both sensors have the same address — how would you handle that?

## Q2: How would you approach implementing a kernel driver for a device that needs to be accessed by both a real-time safety-critical task and a non-real-time monitoring task, where the safety-critical task must never be blocked by the monitoring task?
**Answer:** The key is to ensure the safety-critical path never waits on the monitoring path. I'd design the driver so the safety-critical task operates on a dedicated, high-priority path — typically using a kernel thread with SCHED_FIFO or a hardirq/softirq context — while the monitoring task uses a separate, lower-priority interface. The driver would maintain two independent access paths to the hardware: the safety-critical task would have direct, lock-free access to the hardware registers or DMA buffers, possibly using per-CPU data or a lock-free ring buffer, while the monitoring task would access the same data through a separate interface that takes a mutex or uses copy_to_user. To prevent priority inversion, I'd avoid using spinlocks that the monitoring task could hold, or use priority inheritance mutexes. For the data path, I'd use a lock-free ring buffer with memory barriers for the safety-critical side, and the monitoring task would read from the same buffer using atomic operations. If the monitoring task needs to configure the device, I'd ensure that configuration changes are validated and applied atomically, and that the safety-critical task can detect and handle a configuration change without blocking. I'd also consider using the PREEMPT_RT patch set if the system requires hard real-time guarantees, and I'd document the locking and priority assumptions clearly in the driver.

**Possible follow-ups:** How would you handle a situation where the monitoring task needs to reconfigure the device while the safety-critical task is actively using it? What if the hardware requires a lock for all register access — how would you design around that?

## Q3: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel log shows "Failed to request IRQ" for a device that worked on the previous board revision?
**Answer:** I'd start by checking the device tree to see if the interrupt configuration changed between revisions — the interrupt number, trigger type, or the interrupt controller phandle may be wrong. I'd verify the actual interrupt line on the new board revision against the schematic, since a pin mux change or a different GPIO bank could shift the interrupt number. I'd also check if the interrupt is already claimed by another driver — a shared interrupt line with a conflicting handler can cause this. I'd look at `/proc/interrupts` to see which interrupts are active and whether the device's line is listed. If the interrupt is a GPIO-based one, I'd check the GPIO controller's device tree node and confirm the pin is configured as an input with the correct pull-up/pull-down. I'd also verify the interrupt controller's `interrupt-cells` property and the `interrupt-parent` reference. If the hardware is correct, I'd check the driver's probe order — the interrupt controller may not be ready when the device probes, which can happen if the device tree dependencies aren't properly declared. I'd use `interrupt-extended` if the interrupt parent is different from the default, and I'd check the kernel log for earlier errors from the interrupt controller itself.

**Possible follow-ups:** How would you determine whether the issue is a device tree problem versus a driver problem? What if the interrupt works in the bootloader but not in Linux?

## Q4: How would you approach designing the boot sequence for a system with two processors — an application processor running Linux and a safety-critical microcontroller — where the microcontroller must be fully initialized and running its safety monitoring routines before the Linux userspace starts any critical applications?
**Answer:** I'd structure this as a staged boot with explicit handshakes. The application processor's bootloader (U-Boot) would first release the microcontroller from reset and wait for a "ready" signal — this could be a GPIO line, a mailbox message, or a shared memory flag that the microcontroller sets after completing its self-test and initialization. Only after receiving that signal would U-Boot proceed to load the Linux kernel. In Linux, I'd have the BSP provide a driver that reads the microcontroller's status and exposes it to userspace, so the init system can verify the microcontroller is healthy before starting critical applications. The init system (e.g., systemd) would have a service dependency: a `safety-check.service` that runs before any critical application services, which reads the microcontroller status and fails if it's not ready. I'd also implement a watchdog mechanism — the microcontroller could monitor the application processor and vice versa, so if either fails, the system can take a safe action. For the handshake itself, I'd use a simple, robust protocol: the microcontroller sets a "ready" flag in shared memory and asserts a GPIO; U-Boot polls the GPIO with a timeout, and if it doesn't see the flag, it either retries, falls back to a safe mode, or halts with an error. The key is to make the dependency explicit at every stage and to have a clear failure path.

**Possible follow-ups:** How would you handle a situation where the microcontroller fails to become ready — what should the boot sequence do? How would you ensure the handshake is reliable across power cycles and resets?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the hardware team reveals that they need to change the main processor's boot mode strap resistors to accommodate a new flash part. The change means the processor will boot from a different interface (e.g., from SPI NOR to eMMC), and the bootloader and kernel configurations are already tuned for the current boot source. The project is six weeks from the start of a clinical trial. How would you handle this situation?
**Answer:** I'd treat this as a change-management issue with a hard deadline. First, I'd call an immediate meeting with the hardware team, the project manager, and the firmware team to understand the full scope: why the flash part changed, whether the new part is a like-for-like replacement or a different interface entirely, and what the hardware team's timeline is for the board change. I'd ask for the new part's datasheet and the updated schematic to assess the impact. Then I'd break the work into two tracks: what must change in the bootloader and kernel to support the new boot source, and what can be tested without the new hardware. For the bootloader, I'd need to verify that U-Boot supports the new flash interface and that the driver is enabled; for the kernel, I'd need to ensure the root filesystem driver and any related device tree changes are in place. I'd also check whether the new flash part has different timing or voltage requirements that affect the boot sequence. I'd work with the hardware team to get an early sample or a development board with the new part so we can test the boot path before the clinical trial. If that's not possible, I'd ask for a carrier board or an adapter to validate the boot flow. I'd also prepare a fallback plan: if the new boot source can't be validated in time, we could keep the current flash part for the clinical trial units and qualify the new part in parallel. I'd document all risks and mitigations in a change request and get sign-off from the project manager and regulatory lead, since this affects the device's configuration management. The key is to be transparent about the risk, work in parallel where possible, and have a clear decision point well before the trial starts.

**Possible follow-ups:** How would you handle the regulatory implications of changing the boot source? What if the hardware team says the new part is the only option and the timeline can't move — how would you prioritize the work?
