# embedded-linux-bsp — Day 93

## Q1: How would you approach choosing between a kernel module and a built-in driver for a peripheral that must be available very early in the boot sequence, before the root filesystem is mounted?

**Answer:** The deciding factor is *when* the device must be functional relative to the boot timeline. A loadable module can only be inserted after userspace and the module loader are up, so anything needed before that — the storage controller for the root filesystem, the console UART, a regulator or clock provider that other drivers depend on, or a watchdog that must be armed early — has to be built into the kernel image (`=y` rather than `=m`). For a peripheral that only needs to be available to applications after boot, a module is usually preferable: it keeps the core image smaller, allows the driver to be updated independently of the kernel, and makes it easier to blacklist or swap during bring-up. A practical middle ground is to build the driver in during development and early bring-up (so you can debug it without worrying about module loading order), then move it to a module once the boot dependencies are understood. The trap to avoid is a driver that is built as a module but is a dependency of something in the initramfs — that produces deferred-probe loops or a kernel that can't find its root device. I'd map out the dependency graph of the boot sequence first, mark every node that must exist before `rootfs` mount as built-in, and default everything else to modules unless there's a reason not to.

**Possible follow-ups:** How would you diagnose a boot hang caused by a driver that was accidentally left as a module but is needed by the initramfs? What are the trade-offs of using an initramfs to load storage drivers as modules instead of building them in?

## Q2: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function returns success and yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is usually one of a few classes of problem, and I'd work through them systematically rather than guessing. First, I'd confirm the driver is actually talking to the hardware it thinks it is: read back a known register (a chip ID, a revision register) over the bus and compare against the datasheet — if the read returns all-ones or all-zeros, the bus, address, or pinmux is wrong even though `probe()` "succeeded." Second, I'd check that the resources the driver requested are the ones the hardware actually uses: a device tree `reg` address that doesn't match the physical mapping, an interrupt line that's wired to a different GPIO, or a clock that's enabled but at the wrong rate will all let `probe()` complete while the device does nothing useful. Third, I'd verify the driver isn't silently swallowing errors — many drivers return 0 from `probe()` even when an internal initialization step failed, so I'd add temporary logging around each hardware access and check the return codes. Fourth, I'd look at whether the device needs an external enable or reset that the driver assumes is already asserted (a GPIO, a regulator, a power-good signal) but which the board actually leaves de-asserted. Finally, I'd use a scope or logic analyzer on the bus lines to confirm whether any traffic is actually leaving the SoC — that immediately separates "driver bug" from "hardware/pinmux bug." The key discipline is to instrument rather than assume; a silent device is almost always a mismatch between what the driver believes and what the board actually does.

**Possible follow-ups:** How would you tell the difference between a pinmux problem and a bus-addressing problem using only software-visible symptoms? What would you check first if the register readback returns the correct chip ID but writes appear to have no effect?

## Q3: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's layer untouched and express board-specific configuration as additive metadata in your own layer. In Yocto this is done with kernel configuration fragments: a `.cfg` file containing just the `CONFIG_*` lines you need, referenced from your board's machine or distro configuration via `KERNEL_CONFIG_FRAGMENTS` (or through a `.bbappend` on the kernel recipe that adds the fragment to `SRC_URI`). The fragment is merged on top of the vendor's defconfig at build time by the kernel's `merge_config` mechanism, so you never edit the vendor's recipe or defconfig directly. I'd organize it as: a `meta-<board>` layer with a `recipes-kernel/linux/` directory containing the `.bbappend` and the fragment files, plus a machine conf that sets the fragment list. For options that must be *disabled* rather than enabled, fragments work too, but I'd be careful — a fragment that turns off something the vendor's defconfig enabled can silently break other features, so I'd document why each override exists. I'd also keep fragments small and single-purpose (one per feature or board variant) so they're easy to review and to drop when no longer needed. The payoff is that a vendor kernel update becomes a rebase of the `.bbappend` rather than a merge of a forked tree, and the board-specific delta is visible in one place.

**Possible follow-ups:** How would you verify at build time that a fragment actually took effect rather than being silently overridden? What's the risk of using `KERNEL_CONFIG_FRAGMENTS` versus a full custom defconfig, and when would you choose the latter?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is to make the real-time path wait-free with respect to the logging path — the two must not share a lock that the logging task can hold while doing slow work. I'd structure the driver so the real-time access path takes only a short spinlock (or is lock-free via a per-CPU or single-producer/single-consumer ring buffer) and never blocks on I/O or on anything the logging task controls. The logging task would read from a ring buffer that the real-time path writes into, and if the buffer is full, the logging task drops or overwrites old entries rather than making the producer wait. For register access to the hardware itself, if both paths need the same device, I'd serialize only the actual bus transaction with a minimal critical section, and make the logging path's transactions non-blocking or batched so they can't hold the bus while the real-time task needs it. I'd also consider priority: the real-time task should run at a higher scheduling priority, and the driver should avoid any operation in the real-time path that can sleep (no `msleep`, no mutex, no `copy_to_user` that might fault). Where the hardware supports it, I'd use separate hardware resources for the two paths — e.g., a dedicated DMA channel or FIFO for real-time data and a separate path for logging — so they don't contend at all. The design rule is: the real-time path's worst-case latency must be bounded by the hardware transaction alone, independent of what the logging task is doing.

**Possible follow-ups:** How would you verify that the logging task truly cannot delay the real-time path — what would you measure and how? What happens if the ring buffer between the two paths overflows, and how would you make that behavior deterministic?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination problem first and a technical one second, because the technical change is small but the blast radius touches manufacturing. My first step would be to get the actual constraints on the table from all three sides: what pins the new peripheral needs and why, exactly which pinmux group the UART would move to and whether that group is free of conflicts, and precisely how the manufacturing line uses the early console — is it a human watching output, an automated test that parses specific strings, or a fixture that depends on the physical connector location? That last point matters because "the manufacturing line relies on it" could mean anything from "an operator glances at it" to "a test script fails the board if it doesn't see a specific banner." Once I understand the real dependency, I'd evaluate options: move the UART and update the device tree and bootloader together in a single coordinated change with the manufacturing team; keep the UART where it is and find a different pin for the new peripheral; or move the UART but preserve the manufacturing dependency by keeping the same logical console (same device tree alias, same bootloader stdout path) even if the physical pins change. I'd bring a concrete proposal to the review rather than just raising concerns — for example, a change plan that includes updating the device tree, the bootloader's early console configuration, and the manufacturing test fixture in the same release, with a verification step on a pilot board before the line switches over. The key is that I wouldn't let the hardware change land unilaterally and then discover the manufacturing break downstream; I'd make the software and manufacturing updates part of the same change, with a named owner for each and a rollback plan if the pilot reveals a problem.

**Possible follow-ups:** How would you decide whether to move the UART or push back on the hardware change entirely? What would you put in the change plan to make sure the manufacturing team isn't surprised on the day of the switchover?
