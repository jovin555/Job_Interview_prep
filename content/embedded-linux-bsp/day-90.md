# embedded-linux-bsp — Day 90

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder failure modes because the kernel has no reason to complain — the driver claimed the device and returned 0, so the framework moves on. I'd treat it as a "did the driver actually talk to the hardware, or did it just claim the resources?" problem and work outward from the register level.

First, confirm the driver is bound to the right device instance: check `/sys/bus/<bus>/devices/` and the driver's sysfs directory to make sure the device that probed is the one I think it is, not a phantom or a duplicate node. Then verify the resources the driver requested actually map to the hardware — read back a known register (a chip ID or revision register is ideal) from userspace via `devmem` or a small debugfs hook and compare against the datasheet. If the read returns all-ones, all-zeros, or a bus error, the problem is upstream of the driver logic: wrong base address in the device tree, wrong chip-select, a pinmux that never routed the bus, or a clock/regulator that's enabled but not actually supplying the rail.

If register reads look sane, I'd instrument the driver's init path — add `dev_dbg`/`dev_info` around each hardware access in `probe()` and confirm the writes are landing (read-back after write). A very common cause of "probe succeeds, device dead" is that the driver writes configuration but the peripheral's clock gate or reset line is still asserted, so writes are silently dropped. Checking the clock framework (`clk_summary` in debugfs) and the reset controller state usually exposes that.

Finally, I'd check whether the driver is using the right access width and endianness for the peripheral — a 32-bit register accessed as 8-bit, or a big-endian peripheral on a little-endian SoC, produces no error but garbage behavior. A logic analyzer or scope on the bus during probe is the definitive tiebreaker when software evidence is ambiguous.

**Possible follow-ups:** How would you tell the difference between a driver bug and a hardware bring-up issue in this scenario? What would you put in a debugfs interface to make this class of problem faster to diagnose next time?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe untouched so that vendor updates can be pulled in without merge conflicts, and to express our board-specific configuration as additive, reviewable fragments rather than a monolithic defconfig.

The mechanism I'd use is the kernel's configuration fragment support combined with a `.bbappend` in our own layer. In the append, I'd set `SRC_URI` to include one or more `.cfg` fragment files (via `file://` entries) and ensure `KERNEL_CONFIG_FRAGMENTS` or the recipe's fragment-merge logic picks them up. Each fragment contains only the `CONFIG_*` lines we actually need to change — enabling a driver, setting a value — and nothing else. The kernel's `merge_config.sh` script (which the Yocto kernel class invokes) applies fragments on top of the base config and warns on any symbol that couldn't be satisfied, which is exactly the feedback loop you want: if a fragment references a symbol that doesn't exist in this kernel version, you find out at build time, not at boot.

I'd keep fragments small and single-purpose — one for the board's peripheral set, one for debugging options, one for production hardening — so they can be composed per machine and reviewed independently. Machine-specific fragments go in the machine's `.conf` or a machine-specific append; anything shared across a product family goes in a common include. I'd also pin the base defconfig reference in the append so it's obvious what the fragments are layered on top of.

The discipline that makes this maintainable is treating the fragments as the source of truth for our deltas and periodically diffing the resulting `.config` against the vendor's to catch drift — if a vendor update changes a default we were relying on, the diff surfaces it.

**Possible follow-ups:** What happens if two fragments set the same symbol to different values, and how would you resolve that? How would you verify at build time that a fragment actually took effect rather than being silently dropped?

## Q3: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?

**Answer:** `EINTR` means a blocking syscall was interrupted by a signal that the process had a handler for (or that was delivered and not blocked), and the syscall returned early rather than restarting. The fact that "nothing is intentionally sending signals" is the key clue — the signal is coming from somewhere the application author didn't consider, and the daemon's error handling is treating a recoverable interruption as fatal.

First I'd find out what signal is actually arriving. `strace -f -e trace=signal,ioctl` on the daemon will show the signal delivery and the interrupted `ioctl` in sequence. Common culprits: `SIGCHLD` from a child process the daemon spawned (or from a helper it didn't know about), `SIGALRM` from a timer, `SIGIO`/`SIGPOLL` if async I/O is configured on some fd, or a signal sent by a watchdog/supervisor. I'd also check whether the daemon installs handlers with `SA_RESTART` — if it does, most blocking syscalls restart automatically and `EINTR` shouldn't surface; if it doesn't, every handled signal becomes an `EINTR` opportunity.

On the driver side, I'd confirm the `ioctl` is genuinely blocking and not returning `-ERESTARTSYS` in a way that leaks out as `EINTR` incorrectly. A well-written driver returns `-ERESTARTSYS` from interruptible waits so the kernel can restart the syscall transparently when the handler has `SA_RESTART`; if the driver returns `-EINTR` directly, it's defeating that mechanism and the fix belongs in the driver.

The application fix is to treat `EINTR` as "retry the call," not "abort" — wrap the `ioctl` in a loop that retries on `EINTR`. But I'd fix the root cause too: either block or ignore the stray signal in the daemon, or set `SA_RESTART` on the handler if the signal is legitimately needed. Leaving a latent `EINTR` path in a medical device daemon is a reliability bug waiting to fire at the worst moment.

**Possible follow-ups:** How does `SA_RESTART` interact with `ioctl` specifically, and are there cases where a syscall won't restart even with it set? If the signal turns out to be `SIGCHLD` from a helper process, what's the cleanest way to handle it without disturbing the main loop?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path's latency must be bounded and independent of whatever the logging path is doing, so the design has to prevent the two from sharing any lock, buffer, or bus transaction in a way that lets the slow path block the fast path.

The cleanest structure is to give the real-time consumer a dedicated, lock-free path to the data and give the logging task a separate, decoupled copy. Concretely: the driver's interrupt handler (or a high-priority threaded IRQ) services the hardware, timestamps the sample, and publishes it into a pre-allocated ring buffer using a single-producer/single-consumer pattern with atomic head/tail indices — no mutex on the fast path. The real-time task reads from that ring with a bounded, non-blocking operation. The logging task reads from a *second* consumer view of the same ring (or a mirrored buffer) at its own pace; if it falls behind, it drops samples or overwrites old ones per policy, but it never holds a lock the real-time path needs.

If the hardware itself is a shared resource — say both tasks need to issue transactions on the same I2C bus — then the real-time task must own the bus and the logging task must go through a request queue that the real-time context drains opportunistically, never the other way around. Priority inheritance on any unavoidable mutex is a fallback, not a design goal; the goal is to have no shared mutex on the fast path at all.

I'd also make the logging path's work explicitly preemptible and rate-limited: it runs at normal priority, uses `copy_to_user` outside any critical section, and its buffer sizing is chosen so that a slow logger causes sample drops (visible and counted) rather than back-pressure into the real-time path. Instrumenting worst-case latency of the real-time read with a cycle counter and asserting it stays under budget in testing is how I'd prove the isolation actually holds.

**Possible follow-ups:** How would you size the ring buffer and choose the drop policy for the logging consumer? What would you do if the hardware only supports one hardware FIFO shared between both consumers?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd start by making the actual risk concrete rather than letting "it's baked in" and "we need the pins" stay as competing assertions. The debug UART touches three separate places — the bootloader's early console, the kernel's earlycon/console setup, and the device tree pinmux — and the manufacturing line depends on console output at a specific point in boot. So the first thing I'd do is map exactly which stage of boot the line actually relies on and what would break if console output moved or disappeared for a few seconds.

Then I'd frame the decision around options rather than a yes/no. Option one: move the UART and update bootloader, device tree, and the line's test fixtures together, with a validation pass on the manufacturing test procedure before the change lands. Option two: keep the debug UART where it is and find the pins for the new peripheral elsewhere, or time-multiplex. Option three: move it but keep a transitional path — e.g., the bootloader still brings up the old UART for the first stage, then hands off — if the schedule can't absorb a full fixture update. Each option has a cost and a schedule impact, and I'd put those on the table with the hardware and manufacturing leads rather than deciding unilaterally.

The key process point is that this is a cross-team change with a manufacturing dependency, so it needs a joint validation plan, not just a software commit. I'd insist that whatever we choose, the manufacturing test procedure is re-run against the new configuration before the change is considered done, and that the device tree and bootloader changes are reviewed together so they can't drift. If the schedule genuinely can't absorb the fixture update before a milestone, I'd recommend deferring the pinmux move rather than shipping a change that silently breaks the line's ability to diagnose failures — a debug console that disappears during a production issue is a much bigger cost than a delayed peripheral.

**Possible follow-ups:** How would you structure the validation so the manufacturing team can sign off without a full regression cycle? If the hardware team says the new peripheral is on the critical path and can't wait, how would you sequence the work?
