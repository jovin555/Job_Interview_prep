# embedded-linux-bsp — Day 121

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel's `probe()` for a platform driver is deferred indefinitely because a `regmap`-based I2C sensor's parent bus is not yet available at the time the driver is registered?

**Answer:** `-EPROBE_DEFER` is a request, not a failure — the driver is telling the kernel "I can't proceed yet, retry me later." The first thing I'd do is confirm that's actually what's happening rather than assuming: enable `CONFIG_DEBUG_DRIVER` and the deferred-probe debugfs node (`/sys/kernel/debug/devices_deferred`), which lists exactly which devices are pending and, in newer kernels, the reason string. That turns a vague "silence" into a concrete dependency chain.

From there I'd trace the dependency. A `regmap`-based I2C sensor depends on its I2C adapter being registered, which depends on the I2C controller driver probing, which may itself depend on pinctrl, clocks, and regulators. The classic failure modes are: (a) the I2C controller node is disabled or missing in the device tree, so the bus never appears; (b) the controller probes but its pinctrl state is wrong, so the bus is dead and the sensor's first transfer fails in a way that surfaces as deferral rather than a clean error; (c) a circular dependency where the sensor's own regulator is on the same I2C bus — a genuinely nasty case that needs a device-tree restructure or a `regulator-always-on` workaround; (d) the driver is built as a module and the module load order never resolves because the supplier module isn't in the initramfs.

I'd check `/sys/bus/i2c/devices` to see whether the adapter exists at all, then `dmesg | grep -i defer` and the deferred list to see what the sensor is waiting on. If the supplier is a regulator or clock, I'd verify that driver actually probed successfully — a supplier that itself failed (not deferred) will never satisfy the consumer, and the consumer will defer forever with no obvious error. That's the trap: the real error is in the supplier's log, not the consumer's.

The fix depends on root cause. If it's ordering, I'd make sure the supplier is built-in or in the initramfs ahead of the consumer. If it's a device-tree wiring error, I'd fix the phandle. If it's a genuine circular dependency, I'd restructure the hardware description or use `-EPROBE_DEFER`-aware early registration. I would not paper over it with a fixed `initcall` order or a sleep-and-retry loop in the driver — that hides the real dependency and breaks on the next board revision.

**Possible follow-ups:** How would you tell the difference between a supplier that failed to probe and one that simply hasn't probed yet? What would you do if the dependency graph is genuinely circular and can't be restructured?

## Q2: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?

**Answer:** `EINTR` means a signal was delivered to the process while it was blocked in a slow system call, and the call was interrupted before completing. The daemon's assumption that "nothing sends me signals" is the thing to test first — because something almost certainly is. The usual suspects: a `SIGCHLD` from a child process reaping, a `SIGALRM` from a timer the daemon itself set up, a `SIGPIPE` from a write to a closed socket, or a signal from a watchdog/supervisor process. I'd start by instrumenting the daemon to log which signal arrived — a `sigaction` handler that records `siginfo_t`, or simply `strace -f -e trace=signal,ioctl` to see the signal delivery interleaved with the failing `ioctl`.

If it turns out no signal is being delivered and the `EINTR` is spurious, the next question is whether the driver is returning `-ERESTARTSYS` from an interruptible wait and the kernel is failing to restart the syscall. That happens when the driver uses `wait_event_interruptible` (or similar) and the signal handling path doesn't properly restart — the syscall returns `EINTR` to userspace even though the signal was handled and the process should have continued. That's a driver bug, and the fix is on the kernel side: use `wait_event_interruptible` correctly, return `-ERESTARTSYS` rather than `-EINTR`, and make sure the `ioctl` handler is restartable.

But the more important point is that a well-written userspace daemon should never abort on `EINTR` in the first place. `EINTR` is a normal, expected return from any blocking syscall, and the correct pattern is a retry loop: `do { ret = ioctl(...); } while (ret == -1 && errno == EINTR);`. A daemon that treats `EINTR` as fatal is fragile by construction, and I'd fix that regardless of what the underlying signal source turns out to be. So the answer has two layers: find and eliminate the spurious signal source if there is one, and harden the daemon's syscall wrappers so a stray signal can't take down a medical device's data path.

**Possible follow-ups:** How would you distinguish a driver returning `-ERESTARTSYS` incorrectly from a genuine signal? What's the risk of using `SA_RESTART` to paper over this, and when is it the wrong tool?

## Q3: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our deltas on top, so that when the vendor ships a kernel update we rebase our fragments rather than re-merging a fork. The mechanism is `KERNEL_CONFIG_FRAGMENTS` (or the older `SRC_URI`-with-`.cfg` approach, depending on the kernel class version) combined with a `bbappend` in our own layer.

Concretely: I'd create a layer (say `meta-<product>`) with a `recipes-kernel/linux/linux-<vendor>_%.bbappend`. In that bbappend I'd add our fragment files via `SRC_URI` as `.cfg` files and list them in `KERNEL_CONFIG_FRAGMENTS`. Each fragment contains only the `CONFIG_*` lines we actually need to change — `CONFIG_<PERIPHERAL>=y`, `# CONFIG_<UNWANTED> is not set`, and so on. The kernel's `merge_config.sh` (invoked by the kernel-yocto class) applies the fragments on top of the vendor's defconfig in order, so the result is deterministic and auditable. I'd keep fragments small and single-purpose — one for a peripheral, one for a debugging option, one for a security hardening set — so each is reviewable and can be dropped independently.

The critical discipline is to never edit the vendor's defconfig in place and never fork the recipe. If a fragment conflicts with the vendor's config, the merge will warn or fail loudly, which is exactly what you want — it surfaces the conflict at build time rather than as a silent behavioral difference at runtime. I'd also add a build-time check (a small `do_configure` postfunc or a CI step) that greps the final `.config` for the options we care about, so a vendor kernel bump that silently drops one of our fragments fails the build instead of shipping.

For a medical device this matters beyond convenience: the kernel configuration is part of the device's validated software, so it needs to be reproducible, version-controlled, and traceable to a specific product revision. A fragment-based structure gives you that — each fragment is a reviewable artifact, and the final `.config` can be archived per release as evidence.

**Possible follow-ups:** How would you handle a fragment that the vendor's defconfig actively conflicts with — say they set an option to `y` and you need it `n`? What's your strategy for keeping fragments in sync across multiple product variants that share the same vendor kernel?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core principle is that the real-time path must never block on anything the logging path controls. That rules out a shared mutex, a shared spinlock held across the logging work, or a single queue that both paths contend on. The design has to give the real-time path a guaranteed, bounded-latency route to the hardware, and give the logging path a way to observe without ever being in the critical path.

The standard pattern is a lock-free or minimally-locked producer/consumer split. The real-time task (whether it's a `SCHED_FIFO` userspace thread or an in-kernel hrtimer/IRQ handler) writes into a pre-allocated ring buffer using a single-producer/single-consumer design — atomic head/tail indices, no locks on the fast path, and the buffer sized so the producer never has to wait for the consumer. The logging task reads from the tail at its own pace. If the buffer fills because logging falls behind, the real-time path overwrites the oldest entries (or drops and counts them) rather than blocking — losing a log entry is acceptable; missing a deadline is not.

For the hardware access itself, I'd separate the register access from the data path. If both tasks need to touch the same device registers, the real-time path owns the device and the logging path only reads from the ring buffer — it never issues its own `ioctl` or register read that could contend for the bus. If the logging path genuinely needs device state, that state is snapshotted by the real-time path into the ring buffer, not fetched on demand.

I'd also be careful about the kernel's own preemption behavior. A `SCHED_FIFO` real-time thread in userspace can still be delayed by interrupt handlers, so the driver's IRQ handler should be as short as possible — top half does the minimum (acknowledge, timestamp, enqueue to the ring), bottom half or a threaded handler does the rest. And I'd verify the whole thing under load with `cyclictest` or a latency tracer running concurrently with the logging task, because the failure mode here is subtle: it works fine until the logging task happens to hold a resource at the wrong moment.

**Possible follow-ups:** How would you size the ring buffer, and what would you do if the logging task is persistently too slow to drain it? What happens to your design if the real-time task and the logging task are in different address spaces — does the ring buffer move to a shared-memory `mmap`?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination problem first and a technical one second, because the technical change is small but the blast radius touches manufacturing, which is where schedule risk lives. The first thing I'd do is get the actual constraints on the table from both sides rather than letting each team argue from its own assumptions. The hardware team's real need is "we need these pins for the new peripheral" — the debug UART move is their proposed solution, not necessarily the only one. The software team's real concern is "the manufacturing line's test fixtures and scripts depend on console output appearing on a specific physical connector at a specific baud rate from the very first boot stage." Those are both legitimate, and they're not actually in conflict if we separate "which pins the UART uses" from "where the console appears to manufacturing."

So I'd ask: can the UART move to a different pinmux group while still routing to the same physical test connector, or does the new pinmux group land on different pads? If it's the same connector, the change is mostly a device-tree and bootloader update with a validation pass, and the manufacturing impact is manageable. If it's a different connector, that's a real manufacturing change and needs to be scoped as such — new fixture, updated test procedure, revalidation — and that's a schedule conversation, not a software argument.

On the technical side, I'd insist the change be made in a way that's reversible and verifiable: update the pinmux in the bootloader and device tree together, keep the old configuration available as a build variant or a strap-selectable option during the transition, and validate early-boot console output on actual hardware before the manufacturing team is asked to change anything. I'd also want the manufacturing team in the room for the validation, because they know the failure modes of their line better than we do.

The leadership piece is making sure this doesn't become hardware-vs-software. I'd frame it as: here's the constraint from manufacturing, here's the constraint from hardware, here are two or three options with their costs, and here's who owns each. If the decision is above my pay grade — say it requires a schedule slip — I'd escalate with the options and a recommendation rather than letting the teams deadlock. And I'd document the decision and its rationale, because in a regulated environment the "why" matters as much as the "what" when someone reviews the design history a year from now.

**Possible follow-ups:** What would you do if the hardware team insists the change is non-negotiable and the manufacturing team says any fixture change pushes the launch date? How would you validate that the new pinmux doesn't break early boot before committing to it?
