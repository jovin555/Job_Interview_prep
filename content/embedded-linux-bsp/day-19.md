## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel is not detecting one of two identical I2C sensors on the same bus, while the other works fine?
**Answer:** I'd start by confirming whether the issue is at the hardware level, the device tree level, or the driver level. First, I'd check the kernel logs for any probe-related messages about the missing sensor — sometimes the driver attempts to probe but fails with an error like "failed to read device ID" or "no response at address 0xXX." If there's no probe attempt at all, I'd verify the device tree node is present and correctly specified: correct I2C bus, correct address, and compatible string matching the driver. If the node looks correct, I'd use `i2cdetect` from userspace to see if the device responds on the bus at all. If it doesn't appear, that points to a hardware issue — possibly a bad solder joint, a missing pull-up on the address pin, or an address conflict. If it does appear in `i2cdetect` but the kernel driver still doesn't bind, I'd check whether the driver's probe function is failing — perhaps the device ID register read is returning unexpected values, or the driver expects a reset GPIO that isn't wired correctly. I'd also check for address conflicts: if both sensors are identical, they might be strapped to the same I2C address, and only one would respond. Finally, I'd verify the bus itself — if the two sensors are on different physical branches of the bus, a layout issue on one branch (excessive capacitance, missing pull-ups) could cause marginal timing that only manifests on one device.

**Possible follow-ups:**
- How would you distinguish between a device tree configuration error and a driver probe failure?
- What tools would you use to inspect the I2C bus at the hardware level?

## Q2: How would you approach implementing a kernel driver for a device that needs to perform a hardware-triggered DMA transfer, where the trigger comes from an external sensor's interrupt line, and the data must be processed and made available to userspace within a hard real-time deadline (e.g., 2 ms)?
**Answer:** The key design decision is where to draw the line between kernel space and userspace, and how to structure the data path to meet the deadline. I'd structure the driver around a threaded interrupt handler: the sensor's interrupt line would trigger a hard IRQ that does minimal work — just acknowledging the interrupt and waking a threaded handler. The threaded handler would then configure and start the DMA transfer, since DMA setup can involve register writes that shouldn't happen in atomic context. Once the DMA completes, the completion callback would wake a kernel thread or use a wait queue to signal that data is ready. For the userspace interface, I'd use a character device with `read()` that blocks until new data is available, or better, use a ring buffer with `poll()` support so userspace can wait efficiently. To meet the 2 ms deadline, I'd need to ensure the entire path — interrupt latency, DMA setup time, transfer time, and wake-up latency — fits within budget. I'd also consider using DMA with double-buffering so that while one buffer is being filled, the previous one is being processed. If the deadline is truly hard, I'd need to verify that no other driver on the system can preempt my threaded handler for an unbounded time — this might require using `request_threaded_irq()` with a real-time priority for the handler thread, or even moving the data processing into the DMA completion callback if it's short enough. For the userspace side, I'd recommend using `O_DIRECT` or pre-allocated buffers to avoid page faults during the critical path, and possibly using `sched_setscheduler()` with `SCHED_FIFO` for the consuming application thread.

**Possible follow-ups:**
- How would you handle the case where the DMA transfer occasionally takes longer than the deadline?
- What are the trade-offs between using a threaded IRQ versus a tasklet or workqueue for this scenario?

## Q3: How would you approach designing the device tree for a system where a single I2C bus has multiple sensors with different interrupt lines, and you need to ensure that interrupt-driven reads work reliably under heavy bus traffic?
**Answer:** The device tree structure itself is fairly straightforward — each sensor gets a node under the I2C bus node, with its `compatible` string, `reg` address, and an `interrupt-parent` and `interrupts` property pointing to the appropriate GPIO controller or interrupt controller. The key considerations are more about how the interrupts are configured and how the drivers use them. First, I'd make sure each sensor has its own dedicated interrupt line rather than sharing one — sharing would require the driver to poll each device to determine which one generated the interrupt, which defeats the purpose. Second, I'd configure the interrupts as level-triggered or edge-triggered according to the sensor's specification, and make sure the GPIO controller's interrupt configuration matches. For reliability under heavy bus traffic, the critical issue is interrupt handling latency: if the I2C bus is busy when an interrupt arrives, the driver's interrupt handler needs to defer the actual I2C read to a context where it can wait for the bus. I'd use a threaded interrupt handler for each sensor, so the hard IRQ just records the event and wakes the thread, which then performs the I2C read. This prevents one sensor's interrupt handler from blocking the bus for other transactions. I'd also consider whether the sensors support a "data ready" flag that can be polled as a fallback — if an interrupt is missed due to bus contention, the driver can detect the flag on the next successful read. In the device tree, I'd also make sure the `interrupt-names` property is used if the driver needs to distinguish between multiple interrupt sources on the same device.

**Possible follow-ups:**
- How would you handle the case where two sensors share the same interrupt line due to pin constraints?
- What device tree properties would you use to configure interrupt debounce or filtering if needed?

## Q4: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the manufacturing team reveals that they need to substitute the currently qualified eMMC flash with a different vendor's part due to a supply chain shortage. The new eMMC has a different erase block size, different wear-leveling behavior, and a slightly different controller interface. The project is four weeks from the start of production, and the current eMMC is already qualified and tested. How would you handle this situation?
**Answer:** The first thing I'd do is assess the actual risk — not all eMMC differences are created equal. I'd ask the manufacturing team for the new part's datasheet and compare the key parameters against the current part: interface compatibility (eMMC 5.0 vs 5.1, for example), bus width support, timing modes, and any vendor-specific commands. The erase block size and wear-leveling behavior affect the filesystem and flash management layer, not the kernel driver itself, so the main software impact would be on the filesystem configuration — things like the erase block size used by UBI/UBIFS or the discard/TRIM behavior in ext4. I'd also check whether the new part requires any different initialization sequence or has quirks that need a kernel quirk flag. Given the four-week timeline, I'd propose a structured approach: first, get a sample of the new part and run a focused test campaign on the existing hardware — boot, filesystem stress testing, power-loss testing, and long-duration read/write cycles. In parallel, I'd review the kernel and bootloader code for any eMMC-specific configuration that might need adjustment. If the new part is functionally equivalent at the interface level, the changes might be minimal — perhaps just a device tree property or a kernel config change. If there are significant differences, I'd work with the manufacturing team to see if they can source a part that's more closely matched to the qualified one. I'd also document the risk assessment and testing results so the regulatory team can evaluate whether this constitutes a design change that requires notification. The key is to be systematic, not panic — most eMMC substitutions are manageable if you understand the interface and test thoroughly.

**Possible follow-ups:**
- How would you prioritize which tests to run given the four-week constraint?
- What would you do if the new eMMC requires a kernel driver change that can't be fully validated in time?

## Q5: How would you approach implementing a kernel driver for a device that needs to be accessed by both a real-time safety-critical task and a non-real-time monitoring task, where the safety-critical task must never be blocked by the monitoring task?
**Answer:** The fundamental requirement is to isolate the two access paths so that the monitoring task can never hold a lock or resource that the safety-critical task needs. I'd start by designing the driver around a lock-free or carefully partitioned data structure. One approach is to use a ring buffer with separate producer and consumer indices, where the safety-critical task is always the producer (or always the consumer) and the monitoring task operates on the other side. The indices can be managed with atomic operations or memory barriers, avoiding the need for a mutex or spinlock that could cause priority inversion. If the device itself is the shared resource — for example, a sensor that both tasks need to read — I'd consider whether the safety-critical task should have exclusive access to the hardware, with the monitoring task receiving data through a copy or a secondary path. If both tasks must access the hardware directly, I'd use a priority-inheritance-aware mutex (like `rt_mutex` in the kernel) so that if the monitoring task holds the lock and the safety-critical task blocks on it, the monitoring task's priority is temporarily boosted to avoid unbounded blocking. I'd also make sure the safety-critical task uses `SCHED_FIFO` with a high priority, and that the driver's interrupt handlers and bottom halves are configured to run at appropriate priorities. For the userspace interface, I'd expose two separate file descriptors or ioctl paths — one for the safety-critical task with minimal overhead and no blocking operations, and one for the monitoring task that can afford to wait. The safety-critical path should avoid any operation that could sleep indefinitely, such as waiting on I2C bus arbitration or a DMA completion that might be delayed by other bus traffic.

**Possible follow-ups:**
- How would you verify that the safety-critical task's timing requirements are actually met under worst-case conditions?
- What are the trade-offs between using a spinlock versus a mutex in this scenario?
