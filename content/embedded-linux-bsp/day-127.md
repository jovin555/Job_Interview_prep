# embedded-linux-bsp — Day 127

## Q1: How would you approach designing the device tree representation for a system where a single SoC has two identical I2C controllers, but only one of them has a set of sensors behind a mux, and the mux channel selection is controlled by a GPIO?
**Answer:** I'd start by modelling the physical topology faithfully rather than flattening it. Each I2C controller gets its own node under the SoC's bus hierarchy, with its own `reg`, clock, and pinctrl references — even if they're the same IP block, they're distinct instances and should be described as such. The controller that has no devices behind it still needs a node if it's enabled in hardware, but it can be left with no children; if it's genuinely unused, I'd consider marking it `status = "disabled"` so the kernel doesn't waste time probing it.

For the populated controller, the mux is the interesting part. An I2C mux is a real device with its own driver (`i2c-mux-gpio` or a dedicated mux driver), so it should be a child node of the controller, with the GPIOs it uses listed as `mux-gpios` and the number of channels declared. Each downstream channel then becomes a nested `i2c@N` node under the mux, and the sensors sit under the appropriate channel. This matters because the mux driver needs to know which channel to select before any child device on that channel is probed — the kernel's I2C core handles this by deselecting all channels at mux probe time and selecting on demand, but only if the topology is described correctly.

I'd also make sure the GPIO for the mux is requested by the mux driver, not by a separate gpio-hog or userspace consumer, so there's a single owner and no contention. If the mux has an enable or reset line, that goes in the mux node too. And I'd double-check the `reg` values on the downstream sensor nodes — they're the 7-bit addresses on the *downstream* bus, not the upstream one, which is a common source of confusion when the same sensor address appears on multiple channels.

The reason to get this right at the device-tree level rather than papering over it in a driver is that the kernel's I2C mux framework, the device tree bindings, and the probe ordering all depend on the topology being expressed structurally. If you flatten it, you end up writing a custom driver that manually toggles GPIOs before every transfer, which is fragile and doesn't compose with existing sensor drivers.

**Possible follow-ups:** How would you handle a sensor that needs to be probed on a specific mux channel before another sensor on a different channel, if both are on the same upstream bus? What happens if the mux GPIO is also used by the bootloader to select a default channel — how do you avoid a glitch during handover?

## Q2: How would you approach debugging a situation where the kernel boots, the root filesystem mounts, but a systemd service that depends on a kernel driver fails on first start with "No such device," and succeeds if restarted manually a few seconds later?
**Answer:** This is almost always a probe-ordering or asynchronous-probe race, not a driver bug per se. The service is starting before the driver's `probe()` has completed, and the driver is either deferring (returning `-EPROBE_DEFER`) or being probed asynchronously while the service's `open()` runs. The fact that a manual restart works tells me the device node or sysfs entry eventually appears — so the driver is fine, the timing is wrong.

My first step is to confirm the ordering empirically rather than guess. I'd add `initcall_debug` to the kernel command line, which prints timestamps for every initcall and probe, and correlate that with the service's start time from `journalctl -b`. If the driver's probe finishes after the service's `ExecStart`, that's the smoking gun. I'd also check `dmesg` for `deferred probe` messages — the kernel logs a summary of devices still pending deferred probe at late init, which tells me whether the driver is waiting on a supplier (regulator, clock, GPIO, another bus) that isn't ready yet.

Once confirmed, there are a few legitimate fixes, and I'd pick based on what the dependency actually is. If the service genuinely needs the device, the cleanest fix is to make the service depend on the device being present — a `systemd` unit with `After=sys-devices-...device` or a `ConditionPathExists=` on the device node, or a udev rule that tags the device and a `.device` unit that the service `Requires=`. That expresses the real dependency instead of a sleep. If the driver is deferring because a supplier isn't ready, the right fix is on the driver side — make sure it returns `-EPROBE_DEFER` correctly and that the supplier's probe is ordered properly, rather than adding a `msleep()` in the driver. If the driver is being probed asynchronously and the service can tolerate waiting, `udevadm settle` in the service's `ExecStartPre` is a blunt but sometimes acceptable tool — though I'd prefer the dependency-based approach because it's deterministic.

What I would *not* do is add a fixed `sleep 5` to the service. That's the classic anti-pattern: it works until it doesn't, and it hides the real ordering problem. I'd also want to understand *why* the driver is slow to probe — if it's doing a long calibration or firmware load in `probe()`, that's worth knowing, because it affects boot time budgeting and may be worth moving to a workqueue with a `probe()` that returns quickly and signals readiness via a completion or sysfs attribute.

**Possible follow-ups:** How would you express the dependency in a Yocto-built image where the service is packaged in a recipe — where does the unit file's ordering come from? If the driver is built as a module and loaded by udev, how does that change the race?

## Q3: How would you approach structuring a Yocto BSP for a product where the same image must boot on two board variants that differ only in whether a particular optional peripheral (say, a secondary Ethernet PHY) is populated, and the kernel must not fail to boot on the variant where it's absent?
**Answer:** The key principle is that the device tree, not the kernel config, should express what's physically present, and the kernel should tolerate absent hardware gracefully. So I'd structure this as one machine (or two closely related machines sharing a common `include`) with two device tree files, or one device tree with the optional peripheral's node marked `status = "disabled"` and a variant that enables it. The kernel config stays identical between variants — the driver for the optional PHY is built in either way, because building it out for one variant and in for the other doubles the test matrix for no benefit.

The layer structure I'd use: a common `meta-<product>` layer with the shared recipes, kernel, and bootloader; a `meta-<product>-bsp` layer with the machine definitions and device trees; and the two variants as either two `MACHINE` values that share a `.inc` file, or one machine with two device tree entries selected at build time via a variable. Two machines is cleaner if the variants are genuinely different products with different part numbers and different factory test procedures; one machine with a device-tree-selection variable is cleaner if they're the same product with a population option. I'd lean toward two machines for a medical device because the regulatory file (DHF) wants each variant to be a distinct, traceable configuration.

The critical part is the boot behaviour on the variant without the peripheral. If the device tree node is `disabled`, the kernel won't probe the driver at all, so there's no failure — that's the whole point of `status`. The trap is a device tree that *enables* the node but the hardware isn't there: the driver probes, fails to read the PHY ID over MDIO, and either defers forever or logs errors. So the variant-specific device tree must be the source of truth, and I'd want a build-time check that the right DTB is paired with the right machine — a `do_deploy` sanity check or a test in the image that reads `/proc/device-tree` and asserts the expected peripheral state.

I'd also think about the bootloader: if U-Boot selects the DTB by name, the variant detection has to happen before the DTB is loaded. That could be a GPIO strap read in U-Boot, or two separate boot partitions, or a U-Boot environment variable set at manufacture. For a medical device I'd prefer the strap-read approach with a fallback to a safe default, because it's deterministic and testable, and it means a single image can be flashed to both variants — which simplifies manufacturing and reduces the chance of flashing the wrong image.

**Possible follow-ups:** How would you test that the "peripheral absent" variant actually boots cleanly, given that you may not have that hardware on every engineer's desk? What's the risk of using a GPIO strap to select the DTB, and how would you make it fail-safe?

## Q4: How would you approach implementing a platform driver for a custom FPGA peripheral that exposes a register bank over a memory-mapped interface, generates a level-triggered interrupt, and needs to be accessible from userspace via `ioctl` for configuration and `read()` for streaming data?
**Answer:** I'd split this into three concerns and handle each explicitly: the register access layer, the interrupt handling and data path, and the userspace ABI.

For register access, the device tree node describes the `reg` range, and the driver uses `devm_platform_ioremap_resource()` to map it. I'd define a small set of accessor functions or use `regmap` with a custom bus if the register layout is regular enough to benefit — `regmap` gives you locking, caching, and debugfs for free, which is worth it for anything beyond a handful of registers. For a custom FPGA peripheral with a bespoke layout, a plain `readl()`/`writel()` wrapper with `__iomem` annotations is often simpler and clearer than forcing it into `regmap`. Either way, all register access goes through those accessors, never raw pointer arithmetic, so the sparse annotations catch mistakes.

For the interrupt, the device tree declares the interrupt line and the driver requests it with `devm_request_irq()`. A level-triggered interrupt from an FPGA means the handler must clear the source in the FPGA before returning, or the interrupt will re-fire immediately — this is the classic level-triggered trap. The handler should do the minimum: read the status register, acknowledge/clear the source, and either push data into a buffer or schedule a threaded handler / workqueue for the heavier processing. If the data rate is high, I'd use a threaded IRQ with the top half doing only the ack, and the bottom half doing the DMA or FIFO drain. For streaming data to userspace, a ring buffer with `read()` blocking until data is available, and `poll()` support so userspace can wait efficiently, is the standard pattern — I'd model it on how `iio` does buffered reads, or use `iio` directly if the peripheral fits the IIO model, which for a sensor-like FPGA peripheral it often does.

For the `ioctl` ABI, I'd define a small, versioned set of commands using `_IOW`/`_IOR` macros, with fixed-width types and explicit padding, and document it. The ABI is a contract — once userspace depends on it, changing it breaks things, so I'd version it from day one and reject unknown commands with `-ENOTTY`. Configuration that's really just "set these registers" can often be expressed as sysfs attributes instead of `ioctl`, which is more discoverable and scriptable; I'd reserve `ioctl` for operations that don't fit the attribute model (atomic multi-register updates, starting/stopping a stream, etc.).

The thing I'd be most careful about is concurrency: the `ioctl` path and the interrupt path both touch the same registers, so there needs to be a lock (spinlock for the IRQ context, mutex for the `ioctl` context, with the IRQ path using the spinlock and the `ioctl` path taking the mutex and then the spinlock for the register access). Getting that wrong produces intermittent corruption that's very hard to debug later.

**Possible follow-ups:** How would you decide between a character device with `ioctl` and an IIO device for this peripheral? What would you put in the device tree binding, and how would you document it so another engineer could bring up a second instance of the same FPGA block?

## Q5: Behavioral — You're the BSP lead on a medical device project, and during a pre-production review the hardware team announces that the SoC's reference clock is being changed from a 24 MHz crystal to a 25 MHz crystal to match a new oscillator that's cheaper and has better availability. The kernel, bootloader, and all the peripheral timing (UART baud, USB PHY, SD card clock) are currently tuned for 24 MHz. The project is four weeks from the start of a clinical trial. How would you handle this situation?
**Answer:** The first thing I'd do is resist the urge to say "no" reflexively, and also resist the urge to say "yes, we'll make it work" without understanding the blast radius. A reference clock change is not a one-line change — it touches the bootloader's clock tree setup, the kernel's clock driver and device tree, every peripheral whose timing is derived from that clock, and potentially the USB PHY calibration and the SD card timing. So my first move is to get the hardware team, the software team, and the systems/regulatory lead in a room and quantify the actual work, because the decision needs to be made on facts, not on the cheapest oscillator.

I'd structure the assessment around three questions. First, what's the actual driver for the change — is it cost, availability, or a technical requirement? If it's availability and the 24 MHz part has a long lead time, that's a real supply-chain risk that has to be weighed against the schedule risk of the change. Second, what's the minimum viable change to get through the clinical trial — can we keep the 24 MHz part for the trial units and qualify the 25 MHz part for production, which decouples the two risks? Third, what's the full change list, and can any of it be done in parallel with the trial preparation?

On the technical side, I'd want to know whether the SoC's clock tree can generate the required peripheral clocks from 25 MHz with acceptable accuracy. UART baud rates are the usual problem — a 25 MHz reference divides less cleanly than 24 MHz for standard baud rates, so the baud error may exceed the UART's tolerance, which for a medical device talking to a host or a module could be a real interoperability issue. USB is usually fine because the PHY has its own PLL, but the PHY calibration values may be reference-clock-dependent. SD card timing is derived from the same tree and may need retuning. I'd ask the silicon vendor for the clock tree spreadsheet and work through it before committing to anything.

If the assessment says the change is feasible but the schedule is tight, my recommendation would be to split it: keep the current 24 MHz configuration for the clinical trial build (which is already validated and is what the trial protocol and the regulatory submission are based on), and treat the 25 MHz change as a separate change with its own verification and its own regulatory impact assessment. Changing the reference clock mid-trial would invalidate the configuration that the trial is running on, and for a medical device that's a regulatory problem, not just a schedule problem. If the hardware team insists the change must happen before the trial, then the conversation becomes about what slips — and that's a decision for the project manager and the systems lead, not something I'd absorb silently into the software schedule.

The behavioral point I'd want to land is that this is a cross-functional trade-off, and my job as BSP lead is to make the technical consequences visible so the right people can make the call, not to unilaterally accept or reject the change. I'd also want the decision documented — a short memo with the options, the risks, and the recommendation — because in a regulated environment, "we changed the reference clock three weeks before the trial" needs a paper trail.

**Possible follow-ups:** If the decision is made to proceed with the 25 MHz change before the trial, what would your verification plan look like, and what would you insist on testing before signing off? How would you handle the situation if the hardware team had already ordered the new oscillators before raising the change with software?
