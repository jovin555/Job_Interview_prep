# embedded-linux-bsp — Day 115

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder failure modes because the kernel is telling you everything it knows and nothing is wrong from its perspective. I'd treat it as a "the driver thinks it's talking to hardware, but the hardware isn't listening" problem and work outward from the driver.

First, verify the driver is actually touching the right registers. Dump the resource it was given — `cat /proc/iomem` for memory-mapped devices, or check the `reg` property in the device tree against the SoC reference manual. A common cause is a device tree `reg` that's correct in width but wrong in base address, or a `reg-names` mismatch that makes the driver map the wrong bank. If it's an I2C/SPI device, confirm the bus number and chip-select/address the driver bound to match the schematic.

Second, confirm the driver's register accesses are actually reaching the bus. For I2C/SPI, enable bus tracing (`CONFIG_I2C_DEBUG_CORE`, or a logic analyzer on the lines) and check whether transactions appear at all. If the driver reports success but no transactions hit the wire, the issue is usually a missing clock enable, a regulator that was never turned on, or a reset line held asserted — the peripheral is unclocked and reads return zeros or the bus silently NAKs. Check `clk_summary` in debugfs and the regulator state.

Third, read back a known register. If a read of a device ID register returns all-zeros or all-ones, that's a strong signal the peripheral isn't powered/clocked or the address decode is wrong. If it returns plausible-but-wrong data, suspect endianness or a wrong register offset.

Fourth, check for silent error suppression. Some drivers ignore return values from `regmap_read`/`regmap_write` or from `request_irq` in a way that hides failures. Add temporary `dev_err` on every register access and on the return of each init step, rebuild, and watch what actually happens.

Finally, if the device is interrupt-driven, confirm the interrupt actually fires — check `/proc/interrupts` for the IRQ count incrementing when you'd expect activity. A probe that "succeeds" but never receives an interrupt often means the interrupt line is misconfigured in the device tree (wrong trigger type, wrong parent) or the peripheral's interrupt enable bit was never set because an earlier register write silently failed.

**Possible follow-ups:** If the register read returns all-zeros, how would you distinguish "peripheral unclocked" from "wrong base address" without a schematic? / How would you instrument a driver to catch silently-ignored register access failures without leaving debug code in the production build?

## Q2: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer our changes on top, so that when the vendor ships a kernel update we rebase our fragments rather than re-merge a fork.

The mechanism is `KERNEL_CONFIG_FRAGMENTS` (or the older `SRC_URI`-based `.cfg` approach). I'd create a `.cfg` fragment file in our own layer containing only the `CONFIG_*` lines we need — `CONFIG_OUR_SENSOR=y`, `CONFIG_PREEMPT=y`, and so on — and reference it from a `.bbappend` on the vendor's kernel recipe. The fragment is merged by `merge_config.sh` during `do_configure`, so the vendor's `defconfig` stays untouched and our delta is explicit and reviewable.

A few practices that keep this maintainable:

- **One fragment per concern**, not one giant file — e.g., `sensors.cfg`, `rt.cfg`, `debug.cfg`. When a concern is dropped or a board variant doesn't need it, you remove one file rather than editing a monolith.
- **Use `CONFIG_X=y` and `CONFIG_X is not set` deliberately.** A fragment that only sets `=y` can't turn off a vendor default; if you need to disable something, write `# CONFIG_X is not set` explicitly so the merge is deterministic.
- **Validate the merged config.** After `do_configure`, diff the resulting `.config` against the vendor `defconfig` and confirm only your intended symbols changed. A fragment that silently fails to apply (wrong symbol name, dependency not met) is a common trap — `bitbake -c diffconfig` is the tool for this.
- **Keep fragments in a versioned layer** with a `layer.conf` and `conf/layer.conf` priority set so they apply predictably across boards.
- **For multiple boards sharing a SoC**, put common fragments in a shared include and board-specific ones in per-machine `.conf` files, so the machine definition selects which fragments apply.

The payoff is that a vendor kernel bump becomes "rebase the `.bbappend` and re-run `diffconfig`," not "re-merge a fork and hope."

**Possible follow-ups:** How would you handle a fragment that depends on a kernel version-specific symbol that gets renamed between vendor releases? / What's the difference between a `.cfg` fragment and a `defconfig` in terms of how bitbake applies them, and when would you choose one over the other?

## Q3: How would you approach debugging a situation where a custom board running Linux boots successfully, but a USB 2.0 device (e.g., a data acquisition module) is intermittently not enumerated on cold boots, while working fine after a warm reboot?

**Answer:** Cold-boot-only failures with warm-reboot success almost always point to a timing or power-sequencing difference between the two paths — on a warm reboot the device, PHY, or host controller retains state that masks the problem.

I'd start by characterizing the difference. On a cold boot, capture `dmesg` with `usbmon` or `CONFIG_USB_DEBUG` enabled and look for where enumeration stops: does the host see the device attach at all (port status change), does it get through reset, does it fail at address assignment, or at descriptor read? Each stage failing points to a different layer.

Common cold-boot-specific causes:

- **Power sequencing.** The device or its VBUS may not be stable when the host controller starts enumeration. Check whether the board's VBUS switch or the device's own supply has a soft-start that's slower than the host's port-power-on delay. A scope on VBUS and D+/D- during cold boot usually shows whether the device is even powered when the host probes.
- **PHY or controller reset timing.** If the USB PHY is held in reset or its clock isn't stable when the controller driver probes, the controller may come up in a degraded state that only a warm reboot (which skips full re-init) avoids. Check the reset and clock lines in the device tree and the driver's probe ordering.
- **Device-side firmware.** Some USB devices need a fixed delay after power-on before they respond to enumeration. If the host probes too early, the device NAKs or drops off the bus. A warm reboot gives the device time to settle.
- **Cable/connector or ESD.** Intermittent cold-boot enumeration can be a marginal signal-integrity issue that only manifests when the device is cold; a warm reboot re-establishes the link at a different eye margin.

I'd instrument with a USB protocol analyzer on the D+/D- lines during cold boot to see exactly where the handshake breaks, and correlate with a scope on VBUS and the device's reset line. If the failure is timing, the fix is usually in the device tree (port power-on delay, `maximum-speed`, PHY tuning) or in the board's power sequencing — not in the USB stack itself.

**Possible follow-ups:** How would you distinguish a host-side enumeration timing issue from a device-side readiness issue using only `dmesg` and a scope? / If the device is behind a hub, how does that change your debugging approach?

## Q4: How would you approach designing the boot sequence for a system with two processors — an application processor running Linux and a safety-critical microcontroller — where the microcontroller must be fully initialized and running its safety monitoring routines before the Linux userspace starts any critical applications?

**Answer:** The core requirement is a verified handshake: Linux userspace must not start critical work until the MCU has confirmed it's alive and monitoring. I'd design this as an explicit synchronization point rather than relying on timing.

**Boot sequencing.** The MCU should be the first thing brought out of reset — either the AP holds the MCU in reset until the AP's bootloader releases it, or the MCU self-starts from its own boot ROM. The MCU runs its self-test and safety-monitor init, then asserts a "ready" signal. That signal can be a GPIO, a shared-memory flag, or a message over the inter-processor channel (mailbox/shared memory). The AP's bootloader or early kernel waits for that signal before proceeding past a defined point.

**Where to put the gate.** I'd put the hard gate in the bootloader or early kernel, not in userspace, so that a userspace bug can't bypass it. The bootloader can poll the ready GPIO or shared-memory flag with a timeout; if the MCU doesn't come up, the bootloader halts or enters a safe recovery mode rather than booting Linux into a state where critical apps run without monitoring.

**Userspace gating.** Even with a bootloader gate, I'd add a second check in the init system: a systemd unit or init script that depends on a device node or sysfs attribute the kernel driver exposes only after the MCU handshake completes. Critical application services `Requires=`/`After=` that unit, so ordering is enforced by the init system rather than by sleep timers.

**Failure handling.** Define what happens if the MCU fails its self-test or stops heartbeating: the AP should detect loss of the heartbeat (via the IPC channel or a watchdog GPIO) and transition critical apps to a safe state. This is a safety requirement, not just a boot requirement.

**Resource partitioning.** Agree up front on which peripherals each processor owns, and encode that in the device tree (the AP's nodes should exclude MCU-owned peripherals) and in the MCU's linker/memory map. Shared resources (shared memory regions, mailboxes) get explicit addresses and sizes documented in an interface control document so both sides can't drift.

**Possible follow-ups:** How would you implement the heartbeat/liveness check between the two processors once the system is running, and what's the failure response if it's lost? / If the MCU is on the same die (heterogeneous SoC) versus a separate chip, how does that change the handshake mechanism?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams have legitimate concerns and the real question is how to sequence the change so nobody gets surprised.

First, I'd get the facts on the table in one place: exactly which pins move, what the new peripheral needs, and what specifically depends on the current UART pinmux. That means asking the software team to enumerate every consumer of the debug UART — bootloader console, kernel `earlycon`, the manufacturing test fixture, any scripts that parse boot logs — and asking hardware to confirm the new pinmux group is electrically compatible (voltage domain, pull configuration, whether the pins are shared with anything else). Often the "risk" is narrower than it first sounds, or it turns out the manufacturing line only needs the console during a specific test phase.

Second, I'd propose a path that de-risks the change rather than blocking it. Options to evaluate: keep the debug UART on its current pins and move the *new* peripheral to a different pinmux group instead (if the SoC allows); or make the UART pinmux a build-time or boot-time selection so the manufacturing image keeps the old mapping while the production image uses the new one; or stage the change so the bootloader and kernel are updated together with a documented rollback. The right answer depends on whether the manufacturing dependency is a hard constraint or a convenience.

Third, I'd make the decision explicit and documented: who owns the change, what the acceptance criteria are (boot console still works on the manufacturing fixture, new peripheral enumerates), and what the rollback plan is if the manufacturing line hits a problem. I'd want the hardware team to own the pinmux change in the schematic and the software team to own the device tree/bootloader update, with a joint test on the manufacturing fixture before the change is declared done.

Finally, I'd escalate only if the teams can't agree on sequencing — the goal is to keep the project moving without either team feeling overridden. The framing I'd use in the review is "we're not saying no, we're saying here's the order and the safety net."

**Possible follow-ups:** If the manufacturing line's dependency turns out to be a hard constraint (the fixture physically can't be changed), how would that change your recommendation? / How would you document the pinmux ownership so this doesn't recur when the next peripheral needs pins?
