# embedded-linux-bsp — Day 103

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel driver's `probe()` function is called and returns success, yet the device is completely non-functional — no errors in the log, no timeouts, just silence?

**Answer:** A silent success is one of the harder classes of bug because it removes the usual breadcrumbs. I'd treat it as a "verify each assumption in the probe path" exercise rather than chasing the log. First, I'd confirm the driver is actually talking to the hardware the device tree describes — dump the resolved resources the driver received (`/sys/kernel/debug/devices_deferred`, the platform device's `resource` entries, the `of_node` properties) and compare them against the schematic and the SoC's memory map. A very common cause is a resource mismatch: the driver got a base address, IRQ, or clock that is valid but wrong (e.g., an off-by-one register offset, a shared interrupt line that never fires, a clock that is enabled but at the wrong rate). Second, I'd instrument the probe path itself — add temporary `dev_dbg`/`dev_info` at each step (regulator enable, clock enable, reset deassert, register read-back) and confirm each one actually took effect by reading the hardware back, not just checking the return code. Third, I'd verify the device is really on the bus: for I2C/SPI, a bus scan or a known-register read-back (e.g., a chip-ID register) tells you whether the device is responding at all. Fourth, I'd check power and reset sequencing — a device that is powered but held in reset, or powered at the wrong rail, will happily accept register writes into a void. Finally, I'd look at whether the driver's `probe()` is returning success but the device is being left in a low-power or standby state because a power-management callback or a default register value wasn't applied. The discipline is: don't trust "probe returned 0" as evidence the hardware is alive — prove liveness with a read-back before concluding anything.

**Possible follow-ups:** How would you distinguish between a device that isn't responding on the bus versus one that is responding but being misconfigured? What would you check first if the chip-ID read-back also returned the expected value but the device still didn't function?

## Q2: How would you approach deciding the initialization order between two kernel drivers where one driver's device must be powered and clocked by a regulator/clock controller that is itself managed by another driver, and both are built as modules?

**Answer:** The kernel already gives you the right tool for this — `-EPROBE_DEFER` — and the job is to make sure both drivers use it correctly rather than relying on module load order. The consumer driver (the one that needs the regulator/clock) should request its supplies through the standard frameworks (`devm_regulator_get`, `devm_clk_get`) and, if the supplier isn't registered yet, return `-EPROBE_DEFER` so the driver core re-queues it. The supplier driver must register its regulator/clock provider during its own `probe()` before returning success, so the framework's lookup can find it. The subtle part is that this only works if the device tree expresses the dependency correctly — the consumer's `regulator-supply` and `clocks` phandles must point at the supplier's node, and the supplier must be described as a provider (`#clock-cells`, `regulator-...` properties). If the dependency is expressed only in code and not in DT, deferred probe has nothing to key on and you get a race that depends on module load order. I'd also make sure neither driver is doing its own manual "wait for the other one" polling loop — that's a sign the DT binding is wrong. For modules specifically, I'd verify the supplier module is actually loaded (or built-in) before the consumer, and I'd avoid `module_init` ordering hacks like `late_initcall` as a substitute for proper deferred probe. The test is to load them in both orders and confirm the consumer always ends up probing successfully once the supplier is present.

**Possible follow-ups:** What are the failure modes if the supplier driver registers its provider but then fails later in its own probe — how does the consumer behave? How would you debug a case where deferred probe keeps looping forever?

## Q3: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?

**Answer:** `EINTR` means a signal was delivered to the process while it was blocked in a syscall, and the syscall was interrupted before completing. If nobody is "intentionally" sending signals, the usual suspects are: a signal handler installed for something like `SIGCHLD` or `SIGALRM` that fires asynchronously; a `SIGTERM`/`SIGHUP` from a supervisor or init system restarting the daemon; a debugger or `strace` attaching; or — very commonly on embedded systems — the process being stopped/continued by job control or a watchdog-related signal. The first step is to find out *which* signal: run the daemon under `strace -f -e trace=signal,ioctl` and look at what's delivered right before the `EINTR`, or install a temporary `sigaction` that logs `siginfo_t` (signal number, sender PID, `si_code`) so you can see the source. Once you know the signal, you can decide whether the right fix is to stop the sender (e.g., a supervisor misconfigured to send `SIGHUP`), to block/ignore the signal in the daemon, or — most robustly — to make the `ioctl` call restartable. The daemon should be written to handle `EINTR` correctly: either use `SA_RESTART` on the relevant handlers so the kernel restarts the syscall automatically, or wrap the `ioctl` in a retry loop that re-issues it on `EINTR`. A daemon that aborts on `EINTR` is fragile regardless of who's sending the signal, so I'd fix the daemon's error handling as the durable fix and separately chase down the unexpected signal source as the root cause.

**Possible follow-ups:** Which signals are *not* restartable with `SA_RESTART`, and how does that affect your retry-loop design? How would you tell the difference between a signal sent by another process and one generated by the kernel (e.g., `SIGSEGV` from a bad `ioctl` argument)?

## Q4: How would you approach structuring a Yocto BSP so that a board-specific kernel configuration fragment can be applied cleanly without forking the vendor's kernel recipe?

**Answer:** The goal is to keep the vendor's kernel recipe as the single source of truth and layer your board-specific changes on top through configuration fragments rather than a forked `.config` or a patched recipe. In Yocto, the mechanism is `KERNEL_CONFIG_FRAGMENTS` (or the older `SRC_URI` with `.cfg` files appended via `KERNEL_CONFIG_FRAGMENTS` in a `.bbappend`): you create a small `.cfg` file containing only the options you need to change (e.g., `CONFIG_SPI_MYDEVICE=y`), and add it to the kernel recipe's fragment list from your board layer's `.bbappend`. The kernel's `merge_config.sh`-based configuration step then applies the fragment on top of the vendor's defconfig, so you get a deterministic, reviewable diff without touching the vendor recipe. The important disciplines: keep fragments minimal and single-purpose (one fragment per feature or board variant, not a giant dump of the full config); use `# CONFIG_FOO is not set` syntax explicitly when you need to *disable* something, because a fragment that simply omits an option won't turn it off; and make sure the fragment is applied *after* the vendor's defconfig in the merge order. For multiple board variants sharing a SoC, I'd put the common fragment in a shared layer and the variant-specific fragment in the variant's layer, so the composition is explicit. I'd also add a build-time check (or a CI step) that greps the resulting `.config` for the expected options, so a vendor kernel bump that renames or removes an option fails loudly instead of silently dropping your fragment.

**Possible follow-ups:** What happens if a fragment sets an option that the vendor defconfig doesn't have a dependency for — how do you catch that? How would you handle a vendor kernel bump that changes the name of a config symbol your fragment depends on?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a cross-team risk-and-tradeoff conversation rather than a yes/no on the pinmux change, and I'd start by making the actual constraints explicit to everyone. First, I'd get the hardware team to state precisely *why* the new peripheral needs those specific pins and whether there's any alternative pinmux option or package variant that avoids the conflict — sometimes the "must move" is softer than it first appears. Second, I'd quantify the software-side risk concretely: which boot stages print to that UART (bootloader, early kernel console, userspace getty), which manufacturing-line fixtures and scripts depend on that console, and what the failure mode looks like if the console moves (silent boot, no recovery path on a bricked unit). Third, I'd propose a path that de-risks the change rather than blocking it: keep the debug UART where it is for the current build, add the new peripheral on the alternate pins if the SoC supports it, and if the move is truly required, stage it — update the bootloader and device tree together, add a second console or a fallback so manufacturing isn't blind during the transition, and validate the new pinmux on a small batch before committing the line. Fourth, I'd make sure the decision and its rationale are documented and owned by the right person (likely the systems lead or PM), because this is a schedule and validation tradeoff, not purely a technical one. The key is that I don't want to be the person who says "no, the device tree is baked" — I want to be the person who says "here's what it costs, here's how we de-risk it, and here's the decision we need to make together."

**Possible follow-ups:** If the hardware team insists the move is non-negotiable and the schedule won't allow a staged transition, what would you do? How would you make sure the manufacturing team's console dependency is captured as a requirement rather than discovered late?
