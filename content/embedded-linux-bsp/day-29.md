# embedded-linux-bsp — Day 29

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel log shows "Unhandled fault: external abort on non-linefetch" when a driver accesses a memory-mapped FPGA peripheral?

**Answer:** This type of fault typically indicates a bus-level error — the CPU attempted a transaction that the interconnect or the peripheral itself rejected. I'd start by confirming the exact address and access size from the fault log, then verify that address against the memory map in the device tree and the SoC reference manual. Common causes include: the peripheral clock is gated or not enabled, the memory region isn't marked as prefetchable or device memory in the page tables (which can cause alignment or access-size issues), the FPGA bitstream wasn't loaded before the driver probed, or the address is simply wrong (e.g., a missing address-cells or size-cells translation in the device tree). I'd check whether the access works from U-Boot or via devmem at the same address — if it fails there too, it's a hardware or FPGA configuration issue rather than a Linux driver issue. If it works from devmem but not from the driver, I'd look at how the driver requests the memory region (ioremap vs. of_iomap), whether the bus controller has any error handling that needs to be configured, and whether the FPGA requires a specific access protocol (e.g., a handshake register before data reads). I'd also check the kernel config for the appropriate bus error handling options — some SoCs need explicit error handler registration to recover gracefully rather than panicking.

**Possible follow-ups:** How would you distinguish between a device-tree address translation problem and a hardware bus issue? What kernel configuration options affect how external aborts are handled?

## Q2: How would you approach designing a kernel driver for a device that needs to be accessed by both a real-time safety-critical task and a non-real-time monitoring task, where the safety-critical task must never be blocked by the monitoring task?

**Answer:** The core principle is that the safety-critical path must have exclusive access to the hardware resource, with the monitoring task operating on copies or through a separate interface. I'd structure this with the safety-critical task using a dedicated kernel driver interface that guarantees bounded access time — for example, using a lock-free ring buffer or a single-reader/single-writer pattern with memory barriers, where the safety-critical side never waits on the monitoring side. The monitoring task would read from the same ring buffer or from a separate shadow buffer that the driver updates, never directly from the hardware registers. If the hardware itself can't be shared safely, I'd consider whether the safety-critical task should own the device entirely and expose data to the monitoring task via a shared memory region or a character device interface with non-blocking semantics. Priority inheritance or careful use of mutexes vs. spinlocks matters here — in a real-time context, I'd avoid mutexes that can be held by the monitoring task, and instead use spinlocks with bounded hold times or lock-free techniques. I'd also verify the real-time task's worst-case latency by instrumenting the driver to measure interrupt response and critical section durations, and I'd document the timing analysis as part of the design.

**Possible follow-ups:** How would you handle the case where the monitoring task needs to configure the device (e.g., change sampling rate) without risking interference? What happens if the safety-critical task misses its deadline — how would you detect and respond?

## Q3: How would you approach implementing a kernel driver for a device that needs to perform a hardware-triggered DMA transfer, where the trigger comes from an external sensor's interrupt line, and the data must be processed and made available to userspace within a hard real-time deadline (e.g., 2 ms)?

**Answer:** The key is to minimize latency between the hardware event and the data reaching userspace, which means avoiding any blocking operations in the interrupt path. I'd structure this with the sensor's interrupt line connected to a GPIO that's configured as a wakeup-capable interrupt source. In the interrupt handler (which should be a threaded IRQ if any processing is needed), I'd immediately arm the DMA channel — the DMA descriptor should be pre-built and cached so that arming is just a register write. The DMA completion interrupt would then signal a wait queue or use a completion variable. For the 2 ms deadline, I'd evaluate whether the standard kernel path (interrupt → tasklet → wake_up → userspace read) meets the requirement, or whether I need to use a real-time priority kernel thread that's always blocked on a wait queue and gets woken by the DMA completion. I'd also consider using the DMA engine's callback mechanism to copy data into a pre-allocated userspace buffer via dma_mmap_coherent or similar, avoiding an extra copy. The userspace application would use a blocking read with a timeout, and I'd measure the actual end-to-end latency under worst-case load to verify the deadline is met. If the deadline can't be met with standard kernel mechanisms, I'd look at PREEMPT_RT, reducing interrupt latency by disabling certain power management features, or moving the processing to a dedicated real-time core if available.

**Possible follow-ups:** How would you measure and verify that the 2 ms deadline is actually met under system load? What alternatives would you consider if the standard kernel path can't meet the deadline?

## Q4: How would you approach structuring the root filesystem for an embedded Linux medical device that needs to support over-the-air (OTA) updates with a rollback mechanism, while ensuring that patient data and configuration settings survive the update process?

**Answer:** I'd use a dual-partition A/B update scheme with a separate data partition. The root filesystem would be read-only (e.g., squashfs or a read-only ext4) to ensure integrity, with the system booting from either partition A or B. The bootloader (U-Boot) would track which partition is current and maintain a counter of successful boots — if the kernel fails to reach a "ready" state within a timeout or the application doesn't signal successful startup, the bootloader increments a failure counter and switches to the other partition on the next boot. Patient data and configuration would live on a separate data partition (e.g., ext4 with journaling) that's mounted read-write and is never touched during an update. The update process would write the new image to the inactive partition, verify its checksum, then set a flag for the bootloader to switch. For the data partition, I'd consider using a filesystem with good power-loss resilience (ext4 with ordered journaling mode) and would mount it with the `noatime` option to reduce writes. I'd also implement a mechanism to detect filesystem corruption on boot (e.g., fsck with a timeout) and have a fallback that mounts read-only if the check fails, preventing further damage while still allowing the device to function in a degraded mode.

**Possible follow-ups:** How would you handle the case where an update is installed but the new version has a software bug that only manifests after hours of operation? How would you ensure the data partition survives a failed update attempt?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the hardware team reveals that they need to change the main processor's boot mode strap resistors to accommodate a new flash part. The change means the processor will boot from a different interface (e.g., from SPI NOR to eMMC), and the bootloader and kernel configurations are already tuned for the current boot source. The project is six weeks from the start of a clinical trial. How would you handle this situation?

**Answer:** I'd start by acknowledging the change and immediately assessing the full scope of impact rather than pushing back — the hardware team presumably has a valid reason for the change, and my job is to make it work within the timeline. First, I'd call a focused meeting with hardware, firmware, and project management to confirm the exact new boot interface, the flash part's specifications, and whether this is a permanent change or a temporary substitution. Then I'd create a detailed impact assessment: what changes are needed in U-Boot (new driver, different configuration, potentially a different SPL stage), what kernel changes are required (device tree for the new storage device, root filesystem type, boot arguments), and what testing is needed to qualify the new boot path. I'd identify which changes can be done in parallel — for example, the kernel device tree changes can be developed and tested on a development board with the new flash part while U-Boot work proceeds separately. I'd also check if the new flash part has any quirks (e.g., different erase block size, different timing requirements) that might affect the bootloader's ability to load the kernel. I'd be transparent with project management about the risks and the testing needed, and I'd propose a mitigation plan: develop the new boot path on a development board immediately, have a fallback plan to keep the current flash part for the clinical trial if the new one isn't qualified in time, and schedule a dedicated bring-up window for the new configuration. I'd also make sure the change is documented in the design history file, since this is a medical device and traceability is critical.

**Possible follow-ups:** How would you prioritize the work if the timeline is truly fixed and you can't get everything done? What specific tests would you require before signing off on the new boot configuration for a clinical trial?
