# embedded-linux-bsp — Day 7

## Q1: How would you approach debugging a situation where a custom GPIO-expander on I2C is correctly detected during kernel probe, but reading from it in userspace via the sysfs or gpiochip interface returns incorrect values?

**Answer:** This suggests the device is responding on the bus but something is wrong in the communication or configuration. I'd start by verifying the I2C transaction at the bus level using a logic analyzer or oscilloscope — check that the address byte, register address, and data bytes match the datasheet protocol. If the waveform looks correct, I'd then check the device tree binding: ensure the `reg` property matches the hardware address, and that any `#gpio-cells`, `gpio-controller`, and interrupt properties are correctly specified. Next, I'd examine the kernel driver's probe function to confirm the initialization sequence (e.g., configuration registers for direction, pull-ups, or interrupt mask) is being written correctly. A common issue is that the driver assumes default register values that don't match the actual hardware state after power-on. I'd add debug prints or use `i2cget`/`i2cset` from userspace to manually read back the configuration registers after probe and compare against expected values. If the expander has multiple banks or requires a specific access pattern (e.g., auto-increment vs. sequential reads), I'd verify the driver handles that correctly. Finally, I'd check for bus contention or address conflicts — another device on the same I2C bus might be responding to the same address if pull-up resistors or address pins are misconfigured.

**Possible follow-ups:** How would you distinguish between a hardware-level bus issue and a driver-level register configuration problem? What if the expander works correctly when probed but intermittently returns wrong values after the system has been running for hours?

## Q2: You're designing a BSP for a system that must support two different display panels — one LVDS and one MIPI DSI — connected to the same SoC, selected by a hardware strap pin read at boot. How would you structure the device tree and bootloader to handle this?

**Answer:** I'd handle this at the bootloader level rather than trying to support both in a single kernel device tree. The bootloader (U-Boot) would read the strap GPIO during early initialization, then select and load the appropriate device tree blob (DTB) before booting the kernel. This means maintaining two separate `.dts` files — one for each display configuration — but sharing a common `.dtsi` include for the SoC and shared peripherals. The kernel image itself remains identical; only the DTB changes. In U-Boot, I'd implement this in the board initialization code: read the strap pin, set an environment variable like `panel_type`, and use a script in the bootcmd that loads the correct DTB from a predefined partition or filesystem path (e.g., `/boot/lvds.dtb` or `/boot/mipi.dtb`). Alternatively, if the bootloader has device tree overlay support, I could load a base DTB and apply a panel-specific overlay at boot time — this reduces duplication but adds complexity in overlay management. The key trade-off is maintainability: two static DTBs are simpler to test and validate, while overlays offer more flexibility if additional panel variants are added later. I'd also ensure the display timing parameters, backlight GPIOs, and regulator supplies are correctly specified in each DTB variant.

**Possible follow-ups:** How would you handle the case where the strap pin is read incorrectly due to noise or a floating input? What if the product later adds a third display option — how would your approach scale?

## Q3: How would you approach implementing a kernel driver for a device that needs to periodically read a sensor at 10 kHz and make the data available to a userspace application with minimal latency, on a single-core ARM Cortex-A processor?

**Answer:** At 10 kHz, we have 100 microseconds between samples — that's tight for a general-purpose OS like Linux. I'd start by analyzing whether the sensor uses a bus protocol that can sustain that rate. For I2C at 400 kHz, a single register read takes roughly 30-50 µs, leaving little margin. SPI would be preferable for this rate. For the driver architecture, I'd use a combination of hardware trigger (if the sensor has a data-ready pin) and DMA. The data-ready GPIO would trigger an interrupt; the interrupt handler would be minimal — just schedule a threaded IRQ or trigger a DMA transfer. Using DMA to move samples directly into a pre-allocated kernel buffer avoids CPU involvement for each transfer. The driver would maintain a circular buffer in kernel memory, and userspace would access it via a character device using `read()` or `mmap()`. For `mmap()`, I'd allocate a DMA-coherent buffer and export it to userspace, allowing zero-copy access. To minimize scheduling jitter, I'd set the IRQ handler to use a real-time priority class (`IRQF_NO_THREAD` if the handler is fast enough, or a high-priority threaded IRQ). On the userspace side, the application should use `sched_setscheduler()` with `SCHED_FIFO` and lock memory with `mlockall()` to prevent page faults. I'd also consider using `poll()` or `epoll()` with `EPOLLET` (edge-triggered) to wake the application only when new data is available. If the processor simply can't keep up with 10 kHz sampling while running other tasks, I'd evaluate using a dedicated microcontroller to buffer samples and communicate via shared memory or UART at a lower rate.

**Possible follow-ups:** How would you handle the case where the sensor occasionally misses its data-ready signal due to interrupt latency? What if the DMA controller doesn't support scatter-gather and you need to handle variable-length transfers?

## Q4: Behavioral — You're the BSP lead for a medical device project, and during a design review, the systems engineer proposes replacing the current single-core ARM Cortex-A processor with a dual-core Cortex-A processor running in SMP mode to handle increased processing requirements. The hardware team has already started the PCB layout for the single-core version. How would you handle this situation?

**Answer:** First, I'd acknowledge the proposal and ask for the specific processing requirements that aren't being met — is it raw CPU throughput, interrupt latency, or the need to run additional software stacks? Understanding the root need might reveal alternatives that don't require a board respin. If the dual-core is genuinely necessary, I'd assess the impact systematically. On the software side, moving from single-core to SMP is relatively straightforward with a standard Linux kernel — the same kernel image can run on both, and the scheduler handles core distribution. The device tree would need updates for the second core's GIC interfaces and any core-specific peripherals. The bigger concern is hardware: changing the SoC likely means different pin compatibility, power delivery requirements, and possibly a different package. I'd ask the hardware team for a delta analysis: what PCB changes are needed, what's the timeline impact, and can the existing layout be adapted with minor rework? I'd also check if the dual-core variant is pin-compatible with the single-core — some SoC families offer this. If the board must be redesigned, I'd work with project management to understand the schedule impact and propose a phased approach: continue with the single-core prototype for early software development and integration testing, while the hardware team respins for the dual-core. This keeps the project moving. I'd also flag that SMP brings new challenges — cache coherency, interrupt affinity, and potential priority inversion between cores — that need to be tested thoroughly, especially for a medical device. I'd recommend adding specific SMP stress tests to the verification plan.

**Possible follow-ups:** What if the systems engineer insists on asymmetric multiprocessing (AMP) instead of SMP, arguing that the real-time tasks need a dedicated core? How would you evaluate that trade-off?

## Q5: How would you approach implementing a kernel module that needs to control a PWM fan for thermal management, where the fan speed must be adjusted based on temperature readings from multiple sensors, and the system must never allow the fan to stop completely (to prevent overheating)?

**Answer:** I'd structure this as a kernel module that registers as a thermal governor or uses the existing thermal framework (`drivers/thermal/`) rather than reinventing the logic. The Linux thermal subsystem already provides thermal zones, cooling devices, and governors — I'd leverage that. First, I'd register each temperature sensor as a thermal zone using the `thermal_zone_device_register()` API, specifying the trip points and polling interval. The PWM fan would be registered as a cooling device using `thermal_cooling_device_register()`, with the `get_max_state()` and `get_cur_state()` callbacks mapping to PWM duty cycle values. The key requirement — never allowing the fan to stop completely — means the minimum cooling state should correspond to a non-zero PWM duty cycle (e.g., 20% minimum). I'd enforce this in the cooling device's `set_cur_state()` callback by clamping the requested state to a minimum value. If using the `step_wise` or `power_allocator` governor, I'd configure the trip points so that even in the "cool" or "idle" state, the fan runs at the minimum safe speed. For additional safety, I'd implement a watchdog mechanism: a kernel timer that checks the fan's actual RPM (if a tachometer signal is available) or verifies the PWM output is still active. If the fan appears stalled or the PWM driver fails, the module should trigger a thermal shutdown or at least log a critical alert. I'd also expose the minimum fan speed as a module parameter so it can be tuned per product variant without recompiling. For a medical device, I'd add a hardware fail-safe: a separate thermal cutoff circuit that forces the fan to full speed if the temperature exceeds a critical threshold, independent of software control.

**Possible follow-ups:** How would you handle the transition between cooling states to avoid audible "whooshing" as the fan speed changes rapidly? What if one temperature sensor fails — how would you ensure the system still maintains safe operation?
