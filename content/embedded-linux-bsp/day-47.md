# embedded-linux-bsp — Day 47

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel log shows "Unhandled fault: external abort on non-linefetch" when a driver accesses a memory-mapped FPGA peripheral?
**Answer:** An external abort on non-linefetch typically indicates the CPU attempted a memory access that the bus fabric or peripheral rejected — this is different from a page fault, which is a Linux memory management event. My first step would be to confirm the physical address being accessed and verify it against the memory map. I'd check whether the address falls within the FPGA's assigned region in the device tree, and whether the region is properly described with the correct `reg` properties and compatible string. A common cause is a mismatch between the address the driver is using and the actual decode range programmed into the FPGA or the SoC's chip-select logic. I'd also check whether the FPGA is actually powered and out of reset — if the FPGA is held in reset or its configuration hasn't loaded, any access will abort. I'd verify the clock is running and that any required enable bit in the SoC's peripheral control registers is set. Another angle is the bus width and alignment: if the driver does a 32-bit access but the FPGA only supports 16-bit accesses at that offset, the bus controller may abort. I'd also look at whether the access is happening from an interrupt context where the bus controller is in a particular state. To isolate, I'd use devmem or a minimal test module to access the address directly, bypassing the driver, to determine if the problem is in the driver's address calculation or in the hardware configuration itself. If the abort only happens after certain operations, I'd suspect the FPGA is deasserting its "ready" signal or the access is occurring while the FPGA is busy with an internal operation that blocks the bus.

**Possible follow-ups:** How would you distinguish between a driver bug and a hardware configuration issue in this scenario? What kernel configuration options or debug tools would you enable to get more information about the faulting access?

## Q2: How would you approach designing a kernel driver for a device that needs to wake the system from suspend, but the device is on an I2C bus that loses power during suspend?
**Answer:** This is a classic power-domain problem. The key constraint is that the wake-up source must remain powered and functional while the rest of the system — including the I2C bus it sits on — is suspended. First, I'd check the hardware design to understand the power topology: is the I2C bus on a rail that gets cut during suspend, or is it always-on? If the bus loses power, the device can't be accessed via I2C during suspend, which means the wake-up path has to be purely interrupt-driven. The device's interrupt line would need to be routed to a GPIO or interrupt controller that stays powered. In the driver, I'd implement the appropriate power management callbacks: during `suspend`, I'd disable the I2C communication path but leave the interrupt enabled, and configure the device (if possible before the bus loses power) to assert its interrupt when the wake condition occurs. The device tree would need to describe the interrupt as a wake-up source, likely using the `wakeup-source` property, and the GPIO controller handling the interrupt would need to be in an always-on power domain. If the device has a separate always-on supply pin for its wake logic, that's ideal — the driver would need to ensure that rail is enabled. In the `suspend` callback, I'd also need to consider whether to put the device into a low-power mode that still allows wake detection, or leave it fully powered. The tricky part is the resume path: when the system wakes, the I2C bus may need time to stabilize, and the device may need re-initialization if its state was lost. I'd handle this in the `resume` callback by re-initializing the device and re-establishing communication. I'd also verify that the interrupt controller itself can wake the CPU — on some SoCs, only specific interrupts can serve as wake sources, and this needs to be configured in the platform code or via device tree. Finally, I'd test the suspend/resume cycle thoroughly, including edge cases like wake events arriving during the suspend transition itself.

**Possible follow-ups:** How would you handle the case where the device needs to be configured over I2C before it can generate a wake interrupt, but the bus is already powered down by the time your suspend callback runs? What if the interrupt line is shared with another device?

## Q3: How would you approach implementing a kernel driver for a device that uses DMA to transfer data from an FPGA to system memory, where the FPGA can generate data at rates exceeding what the CPU can process in real-time?
**Answer:** When the data rate exceeds what the CPU can handle, the design has to shift from interrupt-per-transfer to a DMA-driven, buffer-oriented approach. The core principle is that the DMA controller moves data into memory without CPU involvement, and the CPU only gets involved when a buffer is full and ready for processing. I'd start by understanding the data flow: what's the sustained data rate, what's the burst pattern, and what's the acceptable latency between data arrival and processing? The driver would use a ring buffer of DMA descriptors, each pointing to a pre-allocated buffer in memory. The FPGA or DMA controller would be programmed to cycle through these descriptors continuously. When a buffer is filled, the DMA controller generates an interrupt, and the driver's interrupt handler would hand that buffer to a kernel thread or a workqueue for processing, then immediately re-arm the descriptor so the DMA can continue. The key is to have enough buffers in the ring to absorb bursts while the CPU is busy processing previous buffers. I'd use the kernel's DMA API (`dma_alloc_coherent` or `dma_map_single`) to ensure the buffers are properly allocated for DMA — cache-coherent allocation avoids cache maintenance overhead, which is critical at high data rates. For the processing side, I'd consider using a high-priority kernel thread rather than doing heavy work in the interrupt handler, since interrupt handlers should be minimal. If the data needs to go to userspace, I'd look at mechanisms like `dma_buf`, `v4l2` buffers, or a simple character device with `read()` that blocks until data is available. The userspace application would need to be designed to keep up with the data rate, or the system needs flow control — otherwise buffers will overflow and data will be lost. I'd also consider whether the DMA descriptors themselves need to be updated by the FPGA or by the DMA controller's linked-list feature, which allows the hardware to chain transfers without CPU intervention. For very high rates, I might use a double-buffering scheme where the driver alternates between two large buffers, giving the CPU a full buffer's worth of time to process data before the next one fills. The critical design question is whether the system can afford to drop data — in a medical device, it typically cannot, so the driver needs to detect and report overflow conditions rather than silently losing data.

**Possible follow-ups:** How would you choose between coherent and streaming DMA mappings for this scenario? How would you handle the case where the FPGA can generate data faster than the DMA controller can service the descriptors?

## Q4: How would you approach debugging a kernel panic that occurs only on every third or fourth boot, with no consistent trigger?
**Answer:** Intermittent kernel panics are among the most challenging debugging scenarios because the lack of reproducibility makes bisection and testing difficult. My approach would be systematic: first, I'd maximize the information captured from each panic. I'd enable `CONFIG_PANIC_ON_OOPS` and ensure `CONFIG_DEBUG_INFO` is set so the stack trace is meaningful. I'd also enable `CONFIG_KALLSYMS` to get symbol resolution. If the system has a serial console, I'd make sure the panic output is captured there — a serial log is often the only way to get the full trace when the display or network is unreliable. I'd also consider enabling `pstore` or `ramoops` to capture the panic across reboots. Once I have a few panic traces, I'd look for commonalities: are they always in the same function or module? Is the stack trace similar? If the panics are in different places each time, that suggests a memory corruption issue — something is writing to memory it shouldn't, and the corruption manifests differently depending on what gets clobbered. For memory corruption, I'd enable `CONFIG_DEBUG_PAGEALLOC`, `CONFIG_SLUB_DEBUG`, and `CONFIG_KASAN` if the architecture supports it. These tools can catch out-of-bounds accesses and use-after-free bugs at the point they occur, rather than when the corruption causes a panic. I'd also look at hardware factors: intermittent panics on every third or fourth boot can be caused by marginal timing, power supply issues, or memory timing that's right at the edge of specification. I'd check the boot log for any warnings about memory timing or training. If the panic is in driver probe, I'd look at the order of device initialization — is there a race between two drivers accessing shared hardware? I'd also consider whether the panic correlates with a specific hardware revision or temperature. If I can't find the root cause from traces alone, I'd use a binary search approach: disable drivers and kernel features one at a time to narrow down the trigger. I'd also try changing the kernel command line to add `nmi_watchdog=1` or `lockdep` to catch subtle locking issues. For truly intermittent issues, I'd set up automated testing that reboots the system repeatedly and captures logs, so I can gather many data points without manual intervention.

**Possible follow-ups:** How would you distinguish between a software race condition and a hardware timing issue in this scenario? What specific kernel configuration options would you enable to help catch the problem earlier?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during integration testing, you discover that the kernel's real-time scheduling class (SCHED_FIFO) is causing priority inversion on a shared hardware resource between your sensor driver and the display driver. The display team insists their driver needs the highest priority, and the sensor team says their data will be corrupted if they miss their deadline. How would you handle this situation?
**Answer:** Priority inversion on a shared resource is a classic real-time systems problem, and in a medical device context, the stakes are high because both teams have legitimate safety concerns. My approach would start with data, not opinions. I'd ask both teams to quantify their actual requirements: what is the sensor's worst-case deadline, what is the display's worst-case deadline, and what is the actual worst-case hold time for the shared resource? Often, the perceived requirements are more conservative than the real ones, and having hard numbers helps move the conversation from "my driver is more important" to "here's what the system actually needs." I'd also investigate the nature of the shared resource — is it a lock, a hardware register, a DMA channel? If it's a lock, I'd look at whether the critical sections can be shortened or made interrupt-safe. If it's a hardware resource, I'd look at whether access can be serialized through a dedicated thread rather than allowing both drivers to contend directly. One common solution is to use the priority inheritance protocol (`rt_mutex` in the kernel) which temporarily boosts the priority of the low-priority task holding the lock, preventing the medium-priority tasks from preempting it and causing the high-priority task to wait indefinitely. If the kernel's `CONFIG_RT_MUTEXES` is enabled, I'd recommend switching from standard mutexes to rt_mutexes for the shared resource. Another approach is to restructure the drivers so they don't share the resource directly — for example, having the sensor driver own the resource and provide an API for the display driver to request access, with the sensor driver's real-time constraints taking precedence. I'd also consider whether the display driver actually needs SCHED_FIFO at all — display refresh might be better handled by a high-priority thread that's still below the sensor's priority, or by using DMA with interrupt-driven updates rather than CPU-intensive rendering. In terms of process, I'd call a meeting with both teams, present the data, and facilitate a decision based on system-level requirements rather than team preferences. I'd document the decision and the rationale, and I'd propose adding a stress test that exercises both drivers simultaneously to verify the solution works under worst-case conditions. If we genuinely can't meet both requirements with the current architecture, I'd escalate to the systems engineer to discuss hardware changes — for example, moving the display to a different bus or adding a dedicated controller — but that's a last resort given the schedule impact.

**Possible follow-ups:** How would you verify that the priority inheritance solution actually works under worst-case conditions? What if the two teams can't agree on the priority assignment even after you present the data?
