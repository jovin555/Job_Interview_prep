# embedded-linux-bsp — Day 14

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but the root filesystem on an eMMC device becomes read-only after a few hours of operation, with "I/O error" messages appearing in the logs?
**Answer:** This is a classic symptom of an eMMC device dropping off the bus or hitting a hardware-level fault, and I'd approach it systematically. First, I'd capture the full kernel log around the first I/O error to identify which device and driver is involved — is it the MMC block layer, the controller driver, or the filesystem layer? I'd look for patterns: do errors start on a specific command type (e.g., erase, write, read), or after a specific event like a temperature rise or a voltage fluctuation? Next, I'd check the eMMC's health indicators — the device's extended CSD registers contain wear indicators, and I'd verify whether the device is hitting its endurance limits or if there's a bad block issue. I'd also examine the hardware side: marginal power delivery to the eMMC, signal integrity on the data lines, or an incorrect bus speed/timing configuration in the device tree could all cause intermittent failures that worsen as the device warms up. I'd check whether the issue reproduces with a different eMMC part or on a known-good board to isolate hardware vs. software. On the software side, I'd review the MMC driver's error recovery path — if the driver isn't properly handling command timeouts or CRC errors, it might be putting the device into a bad state. I'd also verify the filesystem is mounted with appropriate options for eMMC (e.g., noatime, proper barriers) and that the kernel's I/O scheduler isn't causing issues. Finally, I'd consider whether the device is overheating — eMMC parts can have thermal shutdown behavior that manifests as I/O errors.

- How would you distinguish between a hardware fault and a software/driver issue in this scenario?
- What specific device tree properties or kernel configuration options would you check for the eMMC controller?

## Q2: How would you approach implementing a kernel driver for a device that needs to handle multiple simultaneous I2C sensor reads while maintaining deterministic timing in a medical monitoring application?
**Answer:** The key challenge here is that I2C is inherently a shared, half-duplex bus with no built-in arbitration for multiple masters, so "simultaneous" reads need to be serialized at the bus level. I'd start by analyzing the timing requirements: what's the worst-case latency each sensor can tolerate, and what's the total bus bandwidth available at the configured I2C speed? If the sensors can tolerate sequential reads within a time window, I'd design the driver to use a single workqueue or kernel thread that services all sensors in a round-robin or priority-based order, with careful attention to worst-case scheduling latency. For tighter timing, I'd consider using the kernel's I2C multiplexer framework if the sensors are on separate buses, or a hardware I2C controller with built-in FIFO and DMA support to minimize CPU involvement. I'd also evaluate whether interrupt-driven reads are appropriate — many I2C sensors have a data-ready interrupt, but the actual read still needs to happen over the bus, so the interrupt just triggers the scheduling of the read. For truly deterministic timing, I'd need to ensure the I2C controller driver itself doesn't introduce variable delays — some controllers have quirks with clock stretching or repeated-start handling. I'd also consider whether the sensors could be read via a different interface (e.g., SPI) if the timing requirements are too tight for I2C. Finally, I'd implement proper error handling — a sensor that fails to ACK shouldn't block the entire bus or cause the driver to miss subsequent reads.

**Possible follow-ups:**
- How would you handle a sensor that occasionally fails to respond within its expected time window?
- What are the trade-offs between using a kernel thread vs. a workqueue for this kind of periodic sensor polling?

## Q3: How would you approach designing the boot sequence for a system with two processors — an application processor running Linux and a safety-critical microcontroller — where the microcontroller must be fully initialized and running its safety monitoring routines before the Linux userspace starts any critical applications?
**Answer:** This is fundamentally about establishing a deterministic boot-time handshake between the two processors. I'd start by defining the boot phases and the state machine that governs the handshake. The microcontroller should boot first — either it has its own boot source (e.g., its own flash) or the application processor's bootloader releases it from reset. Once the microcontroller is running its safety monitoring, it should signal readiness through a dedicated mechanism — a GPIO line, a shared memory mailbox, or a combination of both. The application processor's bootloader should check this signal before handing off to the kernel, or alternatively, the kernel can check it during early boot. The critical design decision is where to enforce the dependency: if the kernel's device tree includes a node for the microcontroller's status, a driver can block until the handshake completes. I'd also consider using a hardware watchdog on the microcontroller that's only armed after it confirms the application processor has acknowledged its readiness — this prevents a scenario where the microcontroller is running but the application processor never starts. In the Linux userspace, I'd use a systemd service or init script that explicitly waits for the handshake to complete before starting any critical applications, with a timeout and failure handling. The key is to make the handshake explicit, observable (via logs or a status file), and fail-safe — if the microcontroller never signals readiness, the system should enter a defined error state rather than proceeding with unmonitored operation.

**Possible follow-ups:**
- How would you handle the case where the microcontroller fails to boot or doesn't signal readiness within a timeout?
- What are the trade-offs of enforcing the handshake in the bootloader vs. in the kernel vs. in userspace?

## Q4: How would you approach debugging a situation where a custom SPI NOR flash device is detected correctly in U-Boot but fails to mount as the root filesystem in Linux?
**Answer:** This is a classic "works in bootloader but not in kernel" problem, and I'd approach it by systematically comparing the two environments. First, I'd check the device tree — is the SPI controller node correctly configured with the right compatible string, chip-select, and maximum speed? U-Boot often uses a simplified driver model that might not exercise the same code path as the kernel's SPI framework. I'd verify the SPI mode (CPOL/CPHA), clock speed, and whether the device tree specifies the correct flash size and partitioning. Next, I'd check the kernel log for the SPI NOR probe — does the kernel detect the flash at all? If it does, I'd compare the detected JEDEC ID with what U-Boot reports. A common issue is that the kernel's SPI NOR driver might be using a different read command (e.g., 4-byte addressing vs. 3-byte) or a different erase block size than what U-Boot configured. I'd also check whether the kernel is trying to use a higher SPI clock speed than the flash supports — U-Boot might run at a conservative speed while the kernel's device tree specifies a faster rate. If the flash is detected but mounting fails, I'd check the MTD partition layout — if U-Boot and the kernel disagree on partition offsets, the kernel might be trying to mount a filesystem at the wrong offset. I'd also verify that the kernel has the correct filesystem driver built in (e.g., JFFS2, UBIFS) and that the MTD device is properly registered. Finally, I'd check for any timing or voltage issues that might only manifest at the kernel's higher clock speeds.

**Possible follow-ups:**
- How would you verify that the SPI controller is actually running at the expected clock speed in both U-Boot and Linux?
- What kernel configuration options are essential for SPI NOR flash support, and how would you verify they're enabled?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a pre-production review, the manufacturing team reveals that the PCB for the main processor board has a routing error: the I2C pull-up resistors for a critical sensor bus are connected to the wrong voltage rail (3.3V instead of 1.8V). The sensor is rated for 1.8V I2C, and the board is already in production. The project is three weeks from the start of a clinical trial. How would you handle this situation?
**Answer:** This is a serious issue that requires immediate, structured action. My first priority is to assess the actual risk — I'd ask the hardware team to quantify the electrical stress on the sensor: is the 3.3V pull-up going to damage the sensor's I2C pins, or will it just cause incorrect logic levels? Many sensors have absolute maximum ratings that exceed 3.3V on I2C pins, but the logic thresholds would be wrong, potentially causing communication failures or data corruption. I'd also check whether the sensor has internal pull-ups or clamping diodes that might mitigate the issue. In parallel, I'd have the firmware team test with a bench setup that simulates the 3.3V pull-up condition to see if communication is actually reliable. If the sensor can tolerate the voltage and communication is reliable, we might be able to proceed with a documented deviation and a rework plan for later. If not, I'd need to evaluate options: can the boards be reworked (cutting traces and adding bodge wires to the correct rail)? Can the sensor be replaced with a variant that's 3.3V-compatible? Is there a software workaround, like using open-drain with the sensor's internal pull-ups? I'd also immediately engage the regulatory and quality teams — for a medical device, this is a non-conformance that needs formal documentation, risk assessment, and potentially a CAPA. I'd push for a decision framework: what's the risk to patient safety if we proceed, what's the risk of delaying the clinical trial, and what's the cost of rework vs. scrap? My recommendation would be to rework the boards if feasible, even if it delays the trial slightly — a known electrical issue on a critical sensor bus in a medical device is not something to proceed with without strong evidence that it's safe.

**Possible follow-ups:**
- How would you communicate this issue to the clinical trial team and the regulatory body?
- What would you do if the rework is not feasible and the sensor cannot tolerate the 3.3V pull-up?
