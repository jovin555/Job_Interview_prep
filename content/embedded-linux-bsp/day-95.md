# embedded-linux-bsp — Day 95

## Q1: How would you approach deciding whether a peripheral driver should be built into the kernel image versus built as a loadable module, for a device that must be functional before the root filesystem is mounted?

**Answer:** The deciding factor is *when* the device is needed relative to the boot timeline. If the peripheral must be operational before the root filesystem is available — for example, a storage controller that the rootfs lives on, a console UART used for early boot logging, or a regulator/clock provider that other drivers depend on — it has to be built in (`=y`), because loadable modules can only be loaded once userspace and the rootfs exist. Anything that is only needed after userspace starts, or that is optional/hot-pluggable, is a good candidate for a module (`=m`): it keeps the core image smaller, lets you load it on demand, and makes iteration faster during development because you can rebuild and reload without reflashing.

The practical way to reason about it is to trace the dependency graph from the boot sequence: what does the kernel need to reach `init`? Those drivers are built in. Then look at what `init` and the early userspace services need — those can often be modules loaded from an initramfs or from the rootfs via `modules-load.d` or explicit `modprobe` in the init scripts. A subtle trap is deferred probe: if a built-in driver depends on a module that hasn't loaded yet, it will sit in `-EPROBE_DEFER` until the supplier appears, so mixing built-in consumers with modular suppliers can create ordering headaches. I'd also weigh debuggability — a built-in driver is easier to get early console output from, while a module is easier to swap during bring-up. For a production medical device I'd lean toward building in anything on the critical boot path and keeping the module set minimal and version-locked, since fewer moving parts means a smaller attack surface and a more deterministic boot.

**Possible follow-ups:** How would you handle a driver that must be built in but whose firmware blob is only available on the rootfs? What are the implications of module signing and versioning for a regulated product?

## Q2: How would you approach debugging a situation where a custom board running Linux boots successfully, but the kernel's `probe()` for a platform driver is deferred indefinitely because a `regmap`-based I2C sensor's parent bus is not yet available at the time the driver is registered?

**Answer:** An indefinite `-EPROBE_DEFER` almost always means the supplier the driver is waiting on never registers, so the first job is to confirm *what* it's waiting for rather than guessing. I'd start by enabling deferred-probe debugging — the kernel's `deferred_probe` debugfs nodes and the `driver_deferred_probe_enable` / `deferred_devices` files let you see the pending probe list and, with `initcall_debug`, the ordering of initcalls. That tells me whether the I2C adapter itself is the missing supplier, or whether it's a clock, regulator, pinctrl, or GPIO that the I2C controller depends on.

From there I'd work the chain: is the I2C controller node present and enabled in the device tree, is its `status = "okay"`, and are its own suppliers (clock, pinctrl, reset) resolving? A common cause is that the I2C bus controller is itself deferred because its pinctrl or clock provider hasn't probed, so the sensor's regmap can never attach. Another is a device-tree mismatch — the sensor node's `reg` address or compatible string doesn't match what the driver expects, or the bus node is disabled. I'd also check whether the driver is even bound: `ls /sys/bus/i2c/devices` and the driver's sysfs `bind`/`unbind` entries confirm whether the device was instantiated at all. If the bus is up but the sensor still defers, I'd look at whether the regmap config is trying to grab an optional supply that's declared but never provided. The fix is usually either correcting the device tree dependency or making the driver's probe tolerant of a genuinely optional resource.

**Possible follow-ups:** How would you distinguish a genuine missing supplier from a driver that returns `-EPROBE_DEFER` on an error path it shouldn't? What kernel config options help you trace initcall ordering?

## Q3: You're bringing up a board where the kernel boots and the root filesystem mounts, but a userspace daemon that talks to a kernel driver via `ioctl` intermittently fails with `EINTR` and aborts. Nothing is intentionally sending it signals. How would you approach this?

**Answer:** `EINTR` means a blocking syscall was interrupted by a signal that was delivered and handled (or whose handler was set without `SA_RESTART`). If nobody is "intentionally" signalling the daemon, the first suspects are signals the process is generating against itself or receiving from the environment: `SIGCHLD` from a child process exiting, `SIGALRM` from a timer, `SIGPIPE`, or a signal sent by a watchdog/supervisor. I'd instrument before theorizing — strace with `-e trace=signal,ioctl` (or `-f` to follow threads) will show exactly which signal arrives and at what point the `ioctl` returns. Checking `/proc/<pid>/status` for `SigCgt`/`SigBlk`/`SigPnd` tells me which signals are caught, blocked, or pending.

Once I know the signal, the fix depends on intent. If the signal is expected and benign, the daemon should handle `EINTR` correctly — retry the `ioctl` in a loop rather than treating it as fatal, which is standard robust-syscall practice. If the signal is unexpected, I'd find its source: a supervisor configured to poke the process, a `SIGCHLD` from a forked helper, or a library installing a timer. I'd also check whether the driver's `ioctl` implementation is doing something that makes it interruptible in a way the caller doesn't expect — e.g., sleeping on a wait queue without `TASK_UNINTERRUPTIBLE` semantics where the caller assumed it couldn't be interrupted. The durable fix is usually both: make the userspace caller `EINTR`-safe, and eliminate the spurious signal source.

**Possible follow-ups:** How would you tell whether the `EINTR` originates in the driver's wait or in the syscall entry path? What's the difference between `SA_RESTART` and manual retry, and when would you choose one over the other?

## Q4: How would you approach debugging a U-Boot environment where the board is supposed to boot from eMMC but intermittently falls back to a network boot that was never intended to be enabled?

**Answer:** An intermittent fallback to network boot means the boot script's primary path is failing some fraction of the time and the fallback is being taken silently. The first thing I'd do is make the failure visible: raise the U-Boot loglevel, enable `bootdelay`/`preboot` diagnostics, and capture the full console output across many boot cycles so I can see *which* command in the eMMC path returns non-zero. Intermittency points at timing or state rather than a hard misconfiguration — eMMC initialization that occasionally times out, a partition or filesystem that isn't always ready, or a `bootcmd` that chains commands with `;` instead of `&&` so a failure doesn't stop the chain.

I'd then look at the boot logic itself. If `bootcmd` is something like `run emmcboot; run netboot`, the semicolon means network boot runs regardless of whether eMMC succeeded — that's a design bug, and the fix is to gate the fallback explicitly (only fall back on a defined condition, or remove it entirely for production). I'd also check the eMMC side: is `mmc rescan`/`mmc dev` reliably detecting the device, is the partition table stable, and does `ext4load`/`fatload` occasionally fail on a cold boot versus a warm one? Power sequencing is a classic culprit — if the eMMC rail isn't fully settled when U-Boot probes it, detection can fail intermittently. Finally, I'd confirm the environment itself isn't being corrupted or reset (saved env in eMMC vs. default env), since a fallback to default environment could re-enable a network boot path that was disabled in the saved env.

**Possible follow-ups:** How would you make the boot path fail loudly instead of silently falling back? What would you check if the eMMC detection failure only happens on cold boots?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams have legitimate concerns. The hardware team needs the pins; the software team is protecting a manufacturing dependency that, if broken, causes line downtime that's far more expensive than the change itself. My first move is to get the facts on the table: exactly which pins are being freed, what the new peripheral needs, and precisely where the debug UART pinmux is defined — bootloader, device tree, or both — and whether the manufacturing line's dependency is on the *physical* debug header, the *console output during boot*, or both. Those are different problems with different fixes.

Then I'd look for options that decouple the change from the risk. Could the debug UART move but keep the same physical connector via a pinmux remap that's transparent to the line? Could we keep the old UART available as a secondary console during a transition period, or provide an alternate early-console path (e.g., a different UART that's already exposed) so manufacturing isn't blocked while the primary moves? If the change is unavoidable, I'd propose a staged plan: update bootloader and device tree together, validate early console on prototypes, and coordinate a manufacturing cut-over date with the line so the change lands with a known-good image rather than mid-production. Throughout, I'd keep the decision documented — what changed, why, and what the rollback is — because in a regulated context this is exactly the kind of change that needs a traceable rationale. The goal is to say yes to the hardware need without letting the manufacturing dependency become collateral damage.

**Possible follow-ups:** How would you validate that early boot console output still works before the change reaches the line? What would you do if the hardware team's timeline didn't allow for a staged cut-over?
