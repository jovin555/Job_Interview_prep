# embedded-linux-bsp — Day 56

## Q1: How would you approach debugging a situation where a custom board running Linux boots successfully, but a kernel module that registers a platform driver never has its probe function called, even though the device tree node for the peripheral is present?

**Answer:** A silent no-probe is almost always a binding or dependency problem rather than a driver bug, so I'd work outward from the device tree. First, confirm the kernel actually parsed the node: check `/proc/device-tree` or `/sys/firmware/devicetree/base` for the node and its properties, and confirm the `status` property is `"okay"` rather than `"disabled"` or absent. Second, verify the `compatible` string in the node exactly matches one of the `of_device_id` entries in the driver — a single character difference or a vendor prefix mismatch means the match table never fires, and the kernel will not complain. Third, check whether the driver is even built and loaded: `lsmod`/`modinfo` for a module, or confirm the symbol is present in the kernel image for a built-in, and check that the Kconfig option was actually enabled in the running config (`/proc/config.gz` or the build `.config`). Fourth, look for deferred probe: if the driver's probe returns `-EPROBE_DEFER` because a clock, regulator, GPIO, or PHY it depends on isn't ready yet, it will retry later — `dmesg` often shows "probe deferred" or the dependency's own probe failing. Fifth, check for resource conflicts: the node may be present but its `reg` range, interrupt, or pinmux overlaps something already claimed, in which case probe fails with a specific error rather than silently. Finally, if all of that looks correct, add a `pr_info` at the top of the probe function and rebuild to confirm whether it's being entered at all — that single data point splits the problem cleanly into "never matched" versus "matched but bailed early."

**Possible follow-ups:**
- How would you tell the difference between a driver that was never matched and one that was matched but returned an error from probe?
- What tools would you use to inspect the live device tree and confirm a node's `compatible` and `status` properties on a running target?

## Q2: How would you approach structuring a Yocto layer to add a vendor kernel patch and a custom device tree to an existing BSP without forking the vendor's layer?

**Answer:** The goal is to keep the vendor's layer untouched so it can be updated cleanly, and express all your changes as additions on top. I'd create a new layer (with its own `layer.conf` and priority set appropriately) that depends on the vendor BSP layer, and use a `.bbappend` on the vendor's kernel recipe rather than copying the recipe. Inside the append, I'd add the patch via `SRC_URI` with a `file://` entry and a `SRC_URI[md5sum]`/`sha256sum` or `LIC_FILES_CHKSUM` as required, and list it in the recipe's patch-application mechanism so it applies after the vendor's own patches. For the device tree, I'd add the `.dts`/`.dtsi` files through `SRC_URI` as well and reference them from the kernel's `KERNEL_DEVICETREE` variable in the append, so the build produces the right `.dtb` without editing the vendor's machine conf. If the change is machine-specific, I'd define a custom machine conf in my layer that `require`s the vendor machine and overrides only what differs. The key discipline is: never edit files inside the vendor layer, always append or override from mine, and keep the layer priority and `BBFILE_PRIORITY` such that my append wins. That way a vendor layer update is a rebase of my small append, not a merge of a forked tree.

- How would you handle a situation where the vendor's kernel recipe applies its own patches and your patch conflicts with one of them?
- What's the difference between overriding a variable in a `.bbappend` versus in a machine conf, and when would you use each?

## Q3: How would you approach debugging a U-Boot environment where the board boots from eMMC but intermittently falls back to a network boot, and the fallback is not intended?

**Answer:** Intermittent fallback usually means the primary boot path is failing some of the time and U-Boot is proceeding down its boot order to the next entry. I'd start by capturing the full U-Boot console log on a failing boot and reading the boot order — `bootcmd`, `boot_targets`, and any `distro_bootcmd`-style sequence — to see exactly which step failed and why it moved on. Common causes: the eMMC device isn't enumerated in time (a power-up or clock-stabilization timing issue), the boot partition or filesystem isn't readable on that attempt (marginal signal integrity, a flaky card, or a filesystem that's occasionally not clean), or the boot script's `load`/`fatload` command returns non-zero and the script's error handling falls through instead of stopping. I'd check whether the fallback is triggered by a genuine read error or by a timeout — `mmc` errors in the log point to the former, a missing "MMC: no card present" or a slow init points to the latter. I'd also verify the environment itself: if `bootcmd` is stored in eMMC and the environment load occasionally fails, U-Boot may use a default environment that includes network boot. To isolate, I'd temporarily disable the network boot target and see whether the board then hangs on the eMMC failure (confirming the fallback was masking a real intermittent fault) or boots fine (suggesting the fallback logic itself is the problem). The fix is usually to make the primary path fail loudly rather than silently fall through, and to address the underlying timing or signal issue.

**Possible follow-ups:**
- How would you make the boot sequence fail explicitly instead of silently falling back to the next target?
- What would you check in the eMMC power and clock sequencing to rule out an init-timing problem?

## Q4: How would you approach implementing a kernel driver for a device that must be accessed by both a hard real-time task and a best-effort logging task, where the logging task must never delay the real-time access?

**Answer:** The core requirement is that the real-time path must never block on anything the logging path holds, so I'd design the two paths to share as little as possible. The real-time task gets a dedicated, non-blocking interface — typically a character device or a `ioctl`/`read` path that acquires a short-lived lock (a spinlock or a mutex held only for the register access itself) and returns immediately, with no allocation, no sleeping, and no waiting on the logging side. The logging task reads from a separate buffer that the real-time path writes into, and the handoff is done with a lock-free or minimally-contended structure: a ring buffer with a single producer (the real-time path) and a single consumer (the logging path), using atomic indices so the producer never waits for the consumer. If the buffer is full, the real-time path drops or overwrites the oldest entry rather than blocking — logging is best-effort by definition, so losing a log entry is acceptable where delaying the real-time access is not. I'd also make sure the logging path does its file I/O outside any lock the real-time path needs, and consider giving the real-time task a higher scheduling priority (or running it in a real-time class) so that even brief contention resolves in its favor. The design principle is: the real-time path owns the hardware and the buffer head; the logging path only ever reads behind it.

**Possible follow-ups:**
- How would you size the ring buffer, and what would you do if the logging task can't keep up with the real-time producer?
- Would you use a spinlock or a mutex for the register access, and how does that choice depend on whether the real-time task runs in interrupt context?

## Q5: Behavioral — You're the BSP lead for a medical device project, and during a design review the hardware team proposes moving the main processor's debug UART to a different pinmux group to free up pins for a new peripheral. The software team says the current pinmux is baked into the device tree and bootloader, and changing it risks breaking early boot console output that the manufacturing line relies on. How would you handle this situation?

**Answer:** I'd treat this as a coordination and risk-management problem rather than a purely technical one, because both teams have legitimate concerns. First, I'd get the facts on the table: exactly which pins the new peripheral needs, whether the UART can move without conflicting with anything else, and what specifically depends on the current UART pinmux — not just "the manufacturing line" in the abstract, but which scripts, fixtures, and test steps read that console. Then I'd separate the two risks. The hardware change itself is likely straightforward; the real risk is the manufacturing and early-boot dependency, which is a process risk, not a silicon one. I'd propose a path that de-risks it: implement the pinmux change in the device tree and bootloader on a branch, verify that early boot console still works on the new pins, and confirm with manufacturing what they actually need — if they need console output during bring-up, the new pins can serve that just as well once the fixture is updated, and the fixture update can be scheduled. If manufacturing genuinely can't absorb the change in the current window, I'd look for a compromise: keep the UART where it is and find the new peripheral's pins elsewhere, or stage the change for the next board revision. Throughout, I'd keep the decision explicit and documented — who owns the fixture update, what the fallback is, and what the schedule impact is — so it's a conscious trade-off rather than a surprise. The worst outcome is letting the change land without manufacturing knowing, and discovering the broken console during a production run.

**Possible follow-ups:**
- How would you verify that early boot console output still works after a pinmux change, before committing to it?
- If manufacturing can't update their fixture in time, what alternatives would you propose to free up the pins without moving the UART?
