## Q1: How would you approach calculating the maximum bus capacitance for an I2C bus operating at 400 kHz with multiple devices, and what happens if you exceed that limit?

**Answer:** For I2C fast-mode (400 kHz), the maximum allowable bus capacitance is typically 400 pF as specified in the I2C specification. To calculate the total bus capacitance, I would sum the pin capacitance of each device on the bus (typically 5–10 pF per device from datasheets), the trace capacitance (roughly 1–2 pF per centimeter for typical PCB traces, depending on stack-up), and any connector capacitance. If the total exceeds 400 pF, the rise time of the SDA and SCL lines becomes too slow, causing the bus to fail at the specified frequency. The practical symptoms are intermittent communication failures, especially at higher speeds, as the signals don't reach valid logic thresholds within the required timing window. Mitigation strategies include reducing the number of devices, shortening trace lengths, using lower-capacitance devices, or dropping to standard-mode (100 kHz) which allows up to 400 pF as well but with slower rise time requirements. Alternatively, you can use a bus buffer or repeater to segment the bus into multiple capacitive domains, each staying under the limit.

## Q2: You're designing a system where an SPI master needs to communicate with three slaves, each requiring different clock polarity and phase settings. How would you approach the hardware and firmware architecture?

**Answer:** This is a common challenge because SPI's clock polarity (CPOL) and clock phase (CPHA) settings are per-transaction, not per-slave, on most SPI peripherals. There are several approaches depending on the microcontroller's capabilities. The cleanest hardware approach is to use independent chip select lines for each slave, which is standard practice anyway. For the firmware, if the SPI peripheral allows reconfiguration between transactions, I would reconfigure CPOL and CPHA before each chip select assertion. This adds a small overhead but is straightforward. If the peripheral doesn't support runtime reconfiguration easily, or if the overhead is unacceptable, I would consider using multiple SPI peripherals if available, each configured for one slave's mode. Another option is to use a GPIO-based bit-banged SPI for the oddball slave, though this limits speed. In terms of layout, I would keep the SPI clock trace as short as possible and ensure all slaves see clean clock edges regardless of mode. One important consideration: if two slaves have incompatible modes (e.g., mode 0 and mode 3), they cannot share the same bus without reconfiguration because the clock idle state differs. Mode 0 (CPOL=0, CPHA=0) has idle low and samples on rising edge, while mode 3 (CPOL=1, CPHA=1) has idle high and samples on rising edge—these are actually compatible for data sampling but the idle state difference can cause issues if a slave interprets the clock line state as a start condition. I would verify this in the slave datasheets.

**Possible follow-ups:** What if one slave requires mode 0 and another requires mode 2—are these compatible on the same bus? How would you handle a scenario where reconfiguring the SPI peripheral between transactions introduces timing issues for a time-critical sensor readout?

## Q3: In a medical device using RS-485 for communication between a central controller and several distributed sensor nodes, you're experiencing intermittent data corruption. How would you approach debugging this?

**Answer:** RS-485 corruption can stem from several sources, so I'd approach this systematically. First, I'd characterize the failure: is it bit-level corruption, missing bytes, or complete packet loss? Does it correlate with any external events like motor activation or pump cycling? I'd start with the physical layer: verify termination resistors are correctly placed—typically one 120-ohm resistor at each end of the bus, not at every node. I'd check for stub lengths exceeding the rule of thumb (stub length in meters should be less than 1/10 of the bit period in microseconds; for 115.2 kbps, that's roughly 0.87 meters). Next, I'd examine common-mode voltage range: RS-485 transceivers typically handle -7V to +12V common mode, but in medical environments with long cable runs, ground potential differences can push beyond this. I'd check if a third wire for signal ground is present, or if the system relies on isolated transceivers. I'd also look at fail-safe biasing: if the bus is undriven (all transmitters in high-impedance), the receiver inputs float and can produce random data. Proper fail-safe biasing pulls the differential pair to a known idle state. On the firmware side, I'd verify half-duplex turn-around timing—the delay between releasing the transmitter and enabling the receiver must account for the last bit propagating and the bus settling. I'd also check for reflections by looking at the signal with an oscilloscope at the farthest node, particularly at the rising and falling edges for overshoot or ringing.

**Possible follow-ups:** How would you determine the correct fail-safe bias resistor values for a given transceiver and bus termination? What would you look for on an oscilloscope to confirm a stub length issue?

## Q4: How would you approach selecting between USB 2.0 interrupt transfers and bulk transfers for a medical device that needs to send periodic sensor data to a host computer, with a requirement that no data be lost?

**Answer:** This requires understanding the guarantees each transfer type provides. USB interrupt transfers guarantee a maximum latency (the bInterval field in the endpoint descriptor specifies the polling interval, from 1 ms to 255 ms for full-speed, or 125 µs to 32.768 ms for high-speed). However, interrupt transfers do not guarantee bandwidth—if the bus is busy, the host may skip polling cycles. Bulk transfers guarantee delivery through error detection and retransmission, but have no latency guarantee—they only get bus time when no isochronous or interrupt transfers are pending. For a medical sensor where data loss is unacceptable but some latency is tolerable, I would lean toward bulk transfers because of the guaranteed delivery via automatic retransmission. The trade-off is that under heavy bus load, bulk transfers can be delayed indefinitely. To mitigate this, I would implement a buffer in the device firmware large enough to hold several seconds of sensor data, and include sequence numbers in each packet so the host can detect gaps. If the application has a hard real-time requirement (e.g., data must arrive within 10 ms), I would use interrupt transfers with a short polling interval and accept the small risk of occasional missed polls, but add a higher-level acknowledgment protocol on top to detect and request retransmission of lost packets. In practice, for a dedicated medical device that is the only USB device on the host, bulk transfers with adequate buffering are usually reliable enough.

**Possible follow-ups:** How would you calculate the required buffer size for a sensor sampling at 1 kHz with 16-bit samples? What happens if the host suspends the USB bus—how would your device handle that?

## Q5: Imagine you're leading a design review where a firmware engineer proposes using a single UART with a software-based multiplexer to communicate with four different sensors, each with different baud rates and protocols. The hardware engineer argues this is unreliable and wants four separate UART peripherals. How would you guide the team to a decision?

**Answer:** This is a classic trade-off between hardware simplicity and firmware complexity, and I'd approach it by evaluating the specific requirements rather than taking sides. First, I'd ask the firmware engineer to clarify the multiplexing scheme: is it a time-division approach where the UART is reconfigured between sensors, or a more complex framing protocol where sensors share the bus? I'd probe the timing constraints: what are the sensor sampling rates and latency requirements? If sensors need to be polled at different rates, the multiplexer must ensure no sensor's timing is violated. I'd also ask about error handling: if a sensor's transaction fails, how does the system recover without blocking other sensors? For the hardware engineer's proposal, I'd ask about the microcontroller's available UART peripherals and whether adding four separate UARTs requires a larger, more expensive MCU or external UART chips. I'd then facilitate a structured comparison: list the failure modes of each approach. The software multiplexer risks missing sensor data if the UART is busy with another sensor when a time-critical reading is due, and baud rate reconfiguration adds overhead and potential for misconfiguration. The four-UART approach is more robust but increases BOM cost, PCB area, and possibly power consumption. My recommendation would depend on the criticality: for a medical device where sensor data loss could affect patient safety, I'd lean toward dedicated UARTs despite the cost. If the sensors are non-critical and the timing analysis shows the multiplexer can meet all requirements with margin, I'd accept the software approach but require a detailed timing analysis and failure mode documentation. I'd also suggest a hybrid: use two UARTs for the most time-critical sensors and multiplex the less critical ones.

**Possible follow-ups:** What specific timing analysis would you ask the firmware engineer to present? How would you test the reliability of the software multiplexer approach before committing to it in the design?
