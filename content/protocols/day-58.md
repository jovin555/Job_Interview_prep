## Q1: How would you approach debugging an I2C bus where a slave device holds SDA low after a transaction, preventing any further communication until power is cycled?

**Answer:** A stuck-low SDA line almost always means a slave lost synchronization with the master mid-byte — it thinks it's still transmitting a zero while the master has already moved on. The first step is to confirm the diagnosis with a scope or logic analyzer: check whether SCL is still toggling while SDA is held low, and whether the slave's clock input is actually receiving edges. Common root causes are a master reset mid-transaction (the slave never sees the stop condition), a glitch on SCL that the slave counts as an extra bit, or a slave that entered an undefined state due to a brownout.

The standard recovery is clocking the bus manually: temporarily reconfigure SCL as a GPIO, toggle it up to nine times at a safe rate, and watch for SDA to release. If the slave was mid-byte, it will finish shifting out its remaining bits and then release SDA on the ninth clock, at which point the master can issue a proper STOP. If nine clocks don't free it, the slave is likely latched in a fault state and needs a hardware reset line or power cycle.

For the permanent fix, I'd look at three things: whether the master firmware can be interrupted mid-transaction (e.g., by a watchdog or a higher-priority ISR), whether the slave has a reset pin that should be driven on bus recovery, and whether the bus has proper timeout handling. Many modern I2C peripherals support a bus-clear or timeout feature that automates the nine-clock recovery. I'd also add a supervisory task that periodically checks bus health and triggers recovery proactively rather than waiting for a hang.

- How would you distinguish a stuck-low SDA caused by a slave fault from one caused by a shorted trace or a failed pull-up?
- Would you implement the nine-clock recovery in hardware, firmware, or both, and why?

## Q2: In a system where an SPI master talks to several slaves at different clock speeds, how would you approach structuring the firmware so that mode and speed changes are handled safely?

**Answer:** SPI has no protocol-level handshake, so every parameter change — clock polarity, clock phase, bit order, clock frequency, and chip-select timing — has to be applied by the master before the transaction begins and torn down after it ends. The cleanest approach is to treat each slave as a device descriptor that owns its full configuration, and to have a single SPI transaction API that takes a device handle, applies the descriptor's settings, performs the transfer, and restores a safe idle state.

The subtle failure modes are worth calling out. First, changing CPOL or CPHA while a slave is selected can generate a spurious clock edge that the slave interprets as a bit — so the mode change must happen with all chip selects deasserted. Second, some slaves require a minimum delay between CS assertion and the first clock edge (setup time), and others require a hold time after the last edge before CS deasserts; these need to be part of the descriptor, not hardcoded. Third, if the master's SPI peripheral shares a clock prescaler across all slaves, changing speed for one slave affects the others, so the firmware must serialize transactions or use a peripheral that supports per-transfer clock configuration.

On a Zephyr-based system, this maps naturally onto the SPI device model: each slave is a `struct spi_config` with its own frequency, operation flags, and CS control, and the SPI driver handles the register writes. The key discipline is to never let application code touch the raw SPI peripheral directly — everything goes through the device abstraction so that mode and speed are always consistent with the target slave.

**Possible follow-ups:**
- How would you handle a slave that requires a longer CS-to-clock setup time than the master's hardware supports?
- What would you do if two slaves on the same bus needed incompatible bit orders (MSB-first vs LSB-first)?

## Q3: You're debugging a CAN-FD network where a node occasionally transmits an error frame that corrupts an in-progress message from another node, but only under heavy bus load. How would you approach this?

**Answer:** An error frame that appears only under load points to a marginal physical layer or a timing/bit-rate mismatch rather than a logic bug. The first thing I'd do is capture the bus with a CAN analyzer that can decode both the arbitration phase and the data phase separately, because CAN-FD allows different bit rates in each. If the error frame is being generated by a specific node, the analyzer will show which bit position it flagged — a form error, a CRC error, a stuff error, or an ACK error — and that narrows the cause considerably.

Under heavy load, the most common culprits are: (1) the sample point in the data phase is misconfigured on one node relative to the others, so it samples a bit at the wrong time and flags a bit error; (2) the transceiver's loop delay plus the cable propagation delay exceeds the bit time at the data-phase rate, so the node's own transmitted bit doesn't match what it reads back; (3) a marginal termination or stub is causing reflections that only matter when the bus is busy and the signal has less settling time. I'd check the bit timing registers on every node first — they must all agree on the nominal bit rate, data bit rate, sample point, and SJW. Then I'd measure the actual differential signal at the worst-case node with a scope, looking at rise/fall times and ringing.

If the physical layer checks out, I'd look at whether the error frame is actually a symptom of a node that's losing arbitration repeatedly and then transmitting late, or a node whose error counter is climbing toward error-passive. The fix is usually a combination of correcting the bit timing on the offending node, shortening stubs, and possibly reducing the data-phase bit rate if the bus length can't support it.

**Possible follow-ups:**
- How would you determine the maximum data-phase bit rate for a given bus length and transceiver loop delay?
- What's the difference between an error frame generated by a bit error versus one generated by a stuff error, and how does that change your debugging approach?

## Q4: How would you approach designing a protocol abstraction layer for a medical device that needs to support multiple physical interfaces (I2C, SPI, UART, CAN-FD) for different sensor modules, while keeping the application code independent of the specific transport?

**Answer:** The goal is to define a transport-agnostic interface at the boundary between the application and the physical layer, so that swapping a sensor from I2C to SPI — or adding a CAN-FD variant — doesn't ripple into the application logic. I'd start by identifying what the application actually needs from a transport: a way to send a request, receive a response, handle errors, and possibly register for asynchronous events. That becomes the abstract interface — something like `transport_send`, `transport_receive`, `transport_register_callback`, and a set of error codes that are meaningful regardless of whether the underlying bus is I2C or CAN-FD.

Each physical transport then implements that interface. The I2C implementation knows about device addresses, register reads, and clock stretching; the SPI implementation knows about chip selects and mode settings; the CAN-FD implementation knows about message IDs and DLC encoding. The application never sees any of that — it just calls the abstract interface with a device handle and a payload.

The tricky part is that the transports have genuinely different semantics. I2C and SPI are master-initiated and request/response; CAN-FD is message-based and can be multi-master; UART is a byte stream with no framing. So the abstraction has to be honest about what it can and can't guarantee. I'd define the interface around the lowest common denominator — request/response with a timeout — and then expose transport-specific capabilities through optional extensions rather than trying to force every transport into the same mold. For a medical device, I'd also make sure the abstraction carries through the error and timeout semantics that the risk analysis requires, so that a transport failure is reported consistently no matter which bus it came from.

**Possible follow-ups:**
- How would you handle a transport that supports asynchronous events (like CAN-FD) versus one that's strictly polled (like I2C)?
- Where would you put the protocol framing — above or below the abstraction layer — and why?

## Q5: Imagine you're leading a design review where a junior engineer proposes using a single shared interrupt line for three different peripherals — a UART, an SPI sensor, and a GPIO alarm input — arguing that it saves pins and the firmware can just poll the peripherals to find out which one fired. How would you guide the team to evaluate this approach?

**Answer:** I'd start by acknowledging the legitimate motivation — pin count matters, especially on a small MCU — and then walk through the failure modes that shared interrupts introduce in a medical context. The core issue is that the ISR now has to disambiguate which peripheral fired, and that disambiguation takes time. If the alarm input is a safety-critical signal, the worst-case latency is no longer the interrupt latency of the MCU; it's the interrupt latency plus the time to poll the UART and SPI status registers plus the time to service whatever else was pending. That's a very different number, and it needs to be compared against the system's timing requirements.

The second issue is priority inversion. If the UART and SPI share an interrupt line, a high-priority alarm can be delayed behind a low-priority UART byte. On an MCU with a proper NVIC, separate interrupt lines let you assign different priorities; sharing a line collapses them into one priority level. For a medical device, that's usually a risk-management concern, not just a performance one.

The third issue is spurious or missed interrupts. If two peripherals assert simultaneously, the ISR must handle both in one pass, and if it only clears one flag, the other may be lost. That's a classic source of intermittent bugs that are very hard to reproduce.

My guidance to the team would be: quantify the pin savings against the timing and risk impact. If the alarm input is truly safety-critical, it should have its own interrupt line and its own priority. The UART and SPI might be able to share if their timing requirements are loose and the ISR is written carefully — but that's a decision that should be documented in the risk analysis, not made casually to save two pins. If pin count is genuinely the constraint, I'd look at other options first: a GPIO expander, a different package, or moving a non-critical function to a polled task.

**Possible follow-ups:**
- How would you structure the shared ISR to guarantee that no peripheral's flag is missed?
- What documentation would you expect the team to produce to justify a shared interrupt in a regulatory submission?
