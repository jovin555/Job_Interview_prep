## Q1: How would you approach debugging a CAN-FD network where the bus is clean at the nominal (arbitration) bit rate but nodes intermittently report CRC or form errors only during the data phase at the higher bit rate?

**Answer:** This pattern points almost entirely at the data-phase physical layer, because arbitration and the data phase use the same transceivers and the same topology — the only thing that changed is the bit time. I'd start by separating "timing" from "signal integrity" causes. On the timing side, the sample point in the data phase is set by the transceiver loop delay, the propagation delay of the bus, and the controller's secondary sample point (SSP) configuration. If the SSP is not compensated for the actual measured loop delay, nodes will sample near the edge of the bit and produce CRC errors that look random. So I'd measure the transceiver loop delay on a scope and verify the SSP offset is set from that measurement rather than a datasheet typical. On the signal-integrity side, a shorter bit time means the same stub length and the same termination now represent a much larger fraction of the bit — reflections that were invisible at the nominal rate arrive inside the data-phase sample window. I'd check termination at both physical ends, stub lengths, and whether the data-phase bit rate is compatible with the total bus length. I'd also look at whether the errors correlate with specific nodes or specific payload lengths, since a node with a marginal transceiver or a long stub will fail first. Finally, I'd confirm the error counters are actually data-phase errors and not a misconfigured DLC or bit-rate-switch (BRS) setting on one node, because a single node with the wrong data-phase timing will corrupt everyone's frames.

**Possible follow-ups:** How would you measure transceiver loop delay in-system without a dedicated test point on every node? If the bus length is fixed and cannot be shortened, what levers do you have to make the data phase reliable?

## Q2: How would you approach calculating pull-up resistor values for an I2C bus that must support both standard-mode (100 kHz) and fast-mode (400 kHz) operation with multiple devices on the bus?

**Answer:** The pull-up is bounded from both sides, and the binding constraint is usually different at the two speeds. The upper bound on resistance comes from the rise-time requirement: the bus must rise from VOL to VIH within the spec'd rise time (roughly 1000 ns for standard mode, 300 ns for fast mode), and rise time is set by R times the total bus capacitance, so a larger R gives a slower edge. The lower bound comes from the sink current the weakest device can pull: at VOL the driver must sink the current through the pull-up plus the current from other devices, and the spec caps IOL (typically 3 mA). So R_min is roughly (VDD − VOL_max) / IOL. You compute both bounds at each speed and take the intersection — the resistor must satisfy the fast-mode rise time (the tighter upper bound) and the sink-current limit (the lower bound). Then you add bus capacitance from every device pin plus trace capacitance, and if the resulting window is empty, the bus is over-capacitated and you need an active pull-up, a bus buffer/expander, or to split the bus. I'd also account for the fact that capacitance is temperature- and voltage-dependent, so I'd leave margin rather than sit at the edge, and I'd verify with a scope at the worst-case corner rather than trusting the calculation alone.

**Possible follow-ups:** What would you do if the calculated window is empty because the bus capacitance is too high? How does a bus buffer or repeater change the capacitance calculation?

## Q3: How would you approach designing a USB 2.0 device that must support both bus-powered and battery-powered operation, where the device needs to maintain functionality when the host is in suspend mode?

**Answer:** The first thing I'd do is separate the two power domains cleanly and make the firmware aware of which source is active, because the suspend behavior and the current budget are completely different in each case. On the USB side, the device must honor the suspend current limit — a bus-powered device that draws more than the suspend budget will be non-compliant and may be reset or refused by the host. So in suspend, the USB-facing circuitry has to drop into a low-power state, and the device must be able to detect resume signaling (and optionally remote wakeup) without drawing more than the allowed current. On the battery side, the device can keep running its application — sensor sampling, logging, alarm monitoring — because it is not dependent on VBUS. The tricky part is the transition logic: VBUS detection tells you when the host is present, but VBUS can be present while the host is suspended, so you cannot equate "VBUS present" with "host active." I'd design a small power-path manager that selects the source, charges the battery when VBUS is available, and switches to battery without glitching the rails. Firmware would expose the power state to the application so that, for example, a patient alarm can trigger remote wakeup while the host is suspended, but routine telemetry is buffered rather than forced out. I'd also make sure the descriptor declares the correct power attributes (bus-powered vs self-powered, and the max power) so the host's enumeration and power budgeting are correct.

**Possible follow-ups:** How would you implement remote wakeup so it is reliable across different host controllers? What happens to in-flight transfers when the host suspends mid-transfer, and how would you recover?

## Q4: You're debugging an RS-485 network where the system works at 9600 baud but fails intermittently at 115200 baud over a long cable run with many nodes. How would you approach isolating whether the cause is termination, stub length, or turnaround timing?

**Answer:** I'd treat the three hypotheses as separable by experiment rather than by argument. First, termination: at 115200 the bit time is short enough that reflections from a mismatched termination arrive within the same bit and corrupt it, whereas at 9600 they settle long before the sample point. I'd verify there is exactly one termination at each physical end of the trunk, that the values match the cable's characteristic impedance, and that no node has its own termination enabled in the middle of the bus. Second, stub length: each node's drop from the trunk is a stub, and stubs create reflections whose severity scales with stub length relative to the bit time. I'd measure or estimate the longest stub and compare it against the rule of thumb that stub length should be a small fraction of the electrical length of one bit. Third, turnaround: at higher baud the driver-enable/receiver-enable timing and the transceiver's driver-disable time become a larger fraction of the frame, so a node that releases the bus slightly late can collide with the next node's response. I'd isolate this by testing with a single transmitter/receiver pair at 115200 (removes multi-node effects), then adding nodes one at a time, and by scoping the differential pair at the far end to see whether corruption appears at frame boundaries (turnaround) or mid-frame (termination/stub). I'd also check common-mode range and whether the cable is actually twisted pair with a reference conductor, since a long run with poor common-mode rejection will fail at high speed first.

**Possible follow-ups:** If you cannot change the cable or the topology, what firmware or electrical mitigations remain? How would you distinguish a termination problem from a stub problem on a scope?

## Q5: You're leading a design review where a junior engineer proposes using a single UART with a software-based protocol multiplexer to communicate with four different sensors, each with different baud rates and protocols. The hardware engineer argues this is unreliable and wants four separate UART peripherals. How would you guide the team to evaluate this approach?

**Answer:** I'd reframe the disagreement from "which is right" to "what does the system actually require," because both positions can be correct depending on the constraints. The first thing I'd do is make the requirements explicit: what is the worst-case latency each sensor can tolerate, what is the maximum sustained throughput, how often do sensors need to be serviced, and what happens if a transaction is delayed or dropped. Then I'd have the team walk through the failure modes of the software-multiplexed approach honestly — reconfiguring a UART's baud rate and framing between transactions takes time and creates a window where a byte can be lost if the sensor transmits unsolicited; if any sensor has a strict response timeout, the multiplexer's serialization can violate it; and a bug in the multiplexer state machine can silently corrupt one sensor's data with another's. I'd also have them walk through the cost of four UARTs — pin count, board space, cost, and whether the MCU even has four usable UARTs with the required DMA/interrupt resources. The decision usually falls out of that analysis: if the sensors are polled and tolerant of serialization, the multiplexer is fine and I'd ask for a clear state machine, per-sensor timeout handling, and a test that exercises the worst-case interleaving. If any sensor has a hard real-time response requirement, the multiplexer is the wrong architecture and I'd support the hardware engineer. The key is that I'd make the junior engineer defend the design against the failure modes rather than just overrule them, so the team owns the decision and the reasoning is documented for the design history file.

**Possible follow-ups:** How would you structure the test plan to prove the multiplexer is safe under worst-case interleaving? If the decision goes to four UARTs, how would you keep the firmware architecture from becoming four copies of the same driver?
