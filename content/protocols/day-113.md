## Q1: How would you approach debugging an I2C bus where a slave device occasionally stretches the clock longer than the master's timeout allows, causing the master to abort mid-transaction and leave the bus in an inconsistent state?

**Answer:** I'd separate the problem into three layers: why the slave is stretching so long, why the master's timeout is shorter than the slave's worst-case stretch, and what state the bus is left in after the abort.

First, characterize the stretch. Put a logic analyzer on SCL/SDA with deep memory and trigger on the clock-low period exceeding the master's timeout. Capture the transaction that precedes the long stretch — often the slave is stretching during a read of a slow-conversion sensor, or after a command that triggers an internal calibration or EEPROM write cycle. Check the slave datasheet for its specified maximum clock-low period; if the observed stretch exceeds the datasheet value, that's a slave-side or signal-integrity issue (weak pull-up, excessive bus capacitance making the rise time slow enough that the slave mis-samples and holds the clock). If it's within spec, the master's timeout is simply misconfigured.

Second, fix the timeout. The master's clock-stretching timeout must be set above the slave's worst-case stretch with margin, not at some default. If the master hardware can't support a long enough timeout, that's a part-selection problem — either move the slow slave to a different bus, or use a master that supports the required stretch.

Third, handle the abort cleanly. When a master aborts mid-transaction, the slave may still be holding SDA low waiting to finish its stretch. The recovery procedure is to issue up to nine clock pulses on SCL with SDA released, letting the slave shift out its remaining bits and release the bus, then generate a STOP condition to resynchronize. Firmware should treat a timeout as a recoverable fault: run the bus-recovery routine, reinitialize the peripheral, and retry the transaction a bounded number of times before flagging the sensor as failed. In a medical device, that failure path also needs to be defined — does the reading get marked invalid, does the system fall back to a redundant sensor, does it alarm?

The key insight is that clock stretching is a legitimate protocol feature, not an error; the design must budget for the slave's worst-case stretch and provide deterministic recovery when the budget is exceeded.

## Q2: How would you approach structuring firmware so that an SPI master can talk to several slaves requiring different clock speeds and different CPOL/CPHA modes, without mode changes corrupting transactions?

**Answer:** The core risk is that CPOL/CPHA and clock speed are properties of the SPI peripheral configuration, and changing them mid-stream while a transaction is in flight — or while a slave is still driving MISO — can corrupt data or leave a slave's internal shift register out of sync.

I'd structure this as a bus manager layer that owns the SPI peripheral and serializes all access. Each slave gets a device descriptor containing its mode (CPOL/CPHA), max clock, word size, and chip-select GPIO. The manager exposes a transaction API — assert CS, configure the peripheral for that device's mode and speed, transfer, deassert CS — and guarantees that reconfiguration only happens while all chip selects are deasserted and the peripheral is idle.

The ordering matters: deassert the previous slave's CS and wait for the peripheral's busy flag to clear before reconfiguring. If you reconfigure the clock polarity while a slave is still selected, that slave sees a clock edge it didn't expect and can shift out a spurious bit. Similarly, changing the clock divider while the bus is active can produce a glitch on SCL.

For efficiency, group transactions by mode: if the application needs to poll several sensors, sort the poll list so all devices sharing a mode and speed are serviced together, minimizing reconfigurations. On an RTOS, protect the bus with a mutex so a high-priority task can't preempt mid-transaction and reconfigure the peripheral underneath the lower-priority task. If the hardware supports per-slave configuration registers (some SPI peripherals do), use them so the mode switch is atomic with chip-select assertion.

Finally, verify with a logic analyzer that every mode/speed transition happens with CS high and SCL idle, and add a firmware assertion that catches any attempt to reconfigure while a transfer is active.

**Possible follow-ups:** What would you do if one slave's required clock speed is below what the peripheral's minimum divider can produce? How would you handle a slave that needs a mode change but shares a chip-select line with another device?

## Q3: You're debugging a CAN-FD network where a node intermittently enters error-passive state and then recovers on its own, with no obvious pattern. How would you approach this?

**Answer:** Error-passive means the node's transmit error counter (TEC) or receive error counter (REC) has exceeded 127, so the controller is accumulating errors faster than it's recovering. The fact that it recovers on its own tells me the errors are transient and the counters are decrementing on successful frames — so I'm looking for an intermittent physical-layer or timing problem, not a hard fault.

First, get the error counters and error types out of the node. Most CAN controllers expose TEC/REC and a protocol status register with error-warning, error-passive, bus-off, and last-error-code fields. Log these continuously. If TEC is climbing, the node is failing to transmit successfully — look at acknowledgments (is anyone ACKing?), bit errors, or stuff errors. If REC is climbing, the node is receiving corrupted frames — look at CRC errors and form errors. The distinction points at different root causes: TEC growth suggests the node's own transmissions are being corrupted or not acknowledged; REC growth suggests it's mis-sampling the bus.

Second, check the physical layer. Measure the differential signal at the node with a scope during the error window: is the amplitude within spec, are the rise/fall times clean, is there ringing or common-mode shift? Intermittent error-passive with no pattern often traces to marginal termination, a stub that's too long for the data-phase bit rate, or a connector with intermittent contact. CAN-FD's fast data phase is much less forgiving of stub length and impedance discontinuities than classic CAN, so a bus that worked at 500 kbit/s arbitration may fail in the 2–5 Mbit/s data phase.

Third, check the bit timing. Sample point and SJW must be consistent across all nodes, and the data-phase timing is configured separately from the arbitration phase. A node with a slightly off oscillator or a misconfigured data-phase sample point will accumulate errors only when certain bit patterns or bus loads occur — which explains the "no obvious pattern."

Fourth, correlate with bus load. If error-passive only appears under heavy traffic, look at whether the node is losing arbitration repeatedly and whether its error frames are themselves disturbing other nodes.

The fix depends on the finding: physical-layer fixes for signal integrity, timing reconfiguration for sample-point issues, or firmware changes to handle error-passive gracefully (the node should keep operating in a degraded mode and log the event rather than silently dropping data).

**Possible follow-ups:** How would you distinguish a node-local problem from a bus-wide problem using only the error counters? What firmware behavior should a medical device node exhibit while it's error-passive?

## Q4: How would you approach selecting between RS-422 and RS-485 for a medical device that needs to connect a central controller to several distributed sensor modules?

**Answer:** The decision hinges on topology and directionality, because the two standards share the same differential electrical layer but differ in how many drivers can share a bus.

RS-422 is a point-to-point or one-driver-to-many-receivers arrangement: one driver, up to ten receivers, full-duplex possible with separate transmit and receive pairs. RS-485 is a true multi-point bus: multiple drivers share one pair, with half-duplex being the common configuration, and the transceivers are designed to contend for the bus and go high-impedance when not driving.

For a central controller talking to several distributed sensor modules, the question is whether the sensors ever need to transmit. If the architecture is strictly master-polls-slave — the controller asks, one sensor answers, sensors never initiate — then RS-485 half-duplex on a single twisted pair is the natural fit: one pair of wires, all nodes on the same bus, the controller enables its driver to poll and each sensor enables its driver only to respond. That minimizes cabling, which matters in a distributed medical device where cable runs and connector count affect cost, weight, and reliability.

If the sensors need to stream continuously and simultaneously — say, several high-rate waveform channels — then a full-duplex arrangement with separate transmit and receive paths is worth considering, and RS-422's one-driver-many-receivers model fits a broadcast-from-controller, stream-from-one-sensor topology. But if multiple sensors must transmit concurrently, neither standard gives you that on a shared pair; you'd need separate pairs per sensor or a different bus altogether.

Other factors: RS-485 transceivers are specified for a wider common-mode range and are the more common choice for multi-drop, so parts availability and fail-safe biasing options favor RS-485 for a bus. For a medical device, I'd also weigh the regulatory and safety angle — the bus is inside the device, so it's about reliability and fault tolerance rather than patient isolation per se, but fail-safe biasing and termination still matter because a floating bus produces undefined logic levels that a receiver can interpret as valid data.

My default for a polled multi-sensor medical device would be RS-485 half-duplex, with RS-422 considered only if the traffic pattern is genuinely one-directional streaming.

**Possible follow-ups:** How would the choice change if the sensor modules needed to be hot-swappable? What termination and biasing would you specify for a half-duplex RS-485 bus with several nodes?

## Q5: How would you handle a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** I'd handle it in three phases: contain the immediate problem, fix the root cause, and change the process so it doesn't recur — while keeping the junior engineer's confidence intact, because the goal is a corrected design and a stronger team, not blame.

Containment first. The compliance test has failed, so I need to understand exactly what failed, what the test was verifying, and whether the failure is a protocol bug or a test-setup issue. I'd pull the test report and the failing capture, reproduce it on the bench, and scope the actual defect. Then I'd assess schedule impact honestly with the project lead: what's the minimum fix, what re-testing is required, and what the critical path looks like. If there's a workaround that lets other test phases proceed in parallel, I'd take it.

Root cause second. I'd sit down with the junior engineer — privately, not in a review — and walk through the protocol as implemented against the requirement. The framing is "help me understand the design decision," not "you got it wrong." Often the bug traces to a requirement that was ambiguous or a test case that wasn't written, and that's a process gap, not just an individual error. We'd fix the protocol together, and I'd have them own the correction so they learn the debugging path.

Process third. The real question is why a protocol defect survived to regulatory testing. That points at missing verification earlier: no protocol conformance test, no fault-injection testing, no independent review of the framing and error handling. I'd add a protocol test plan that exercises malformed frames, length-field corruption, sequence-number gaps, and error-recovery paths on the bench before formal testing. I'd also make sure protocol designs get a peer review with a checklist covering the classic failure modes — length validation, sequence numbers, CRC coverage, timeout handling, resynchronization after errors.

The leadership point is that a defect found in compliance testing is a system failure, not just an engineer's failure. The engineer implements what the process allows; if the process let an unverified protocol through, that's on the process. I'd say that explicitly to the team so the junior engineer isn't scapegoated, and so everyone understands the fix is structural.

**Possible follow-ups:** How would you decide whether to fix the protocol or add a workaround given the schedule pressure? What would you put in a protocol design review checklist to catch this class of defect earlier?
