# protocols — Day 114

## Q1: How would you approach debugging an I2C bus where a device intermittently NACKs its address, but only at 400 kHz and only after the board has warmed up for a while?

**Answer:** This pattern — speed-dependent, temperature-dependent, and time-delayed — points to a marginal timing or electrical condition rather than a logic bug, so I'd work from the physical layer upward. First, I'd capture the bus with a scope or logic analyzer at the moment of failure, triggering on the NACK, and look at the actual waveform: rise/fall times, whether SDA is still settling when SCL's setup/hold window closes, and whether the pull-up network is adequate at the faster edge rates. At 400 kHz the bus has roughly a quarter of the timing margin of 100 kHz, so a pull-up that's fine at standard mode can push rise times past the fast-mode limit. Warm-up suggests something drifting with temperature — a pull-up resistor's value shifting, a transceiver's input thresholds moving, or a slave's internal timing relaxing as it heats. I'd measure the pull-up values and compare the observed rise time against the RC time constant implied by bus capacitance, then check whether the slave's datasheet specifies a maximum rise time or a minimum bus-free time the master might be violating. I'd also verify the slave's supply rail is stable and within spec at temperature, since a sagging rail can shift its input thresholds. If the scope shows a clean waveform but the NACK persists, I'd look at whether the master is issuing a repeated start too quickly or whether another device is briefly driving the bus. The fix usually lands on adjusting pull-ups, reducing bus capacitance (shorter stubs, fewer devices), or lowering the clock rate until the root cause is confirmed.

**Possible follow-ups:** How would you distinguish a pull-up problem from a slave timing problem using only a scope? What would you do if the NACK only appears with a specific combination of devices on the bus?

## Q2: How would you approach selecting between RS-422 and RS-485 for a medical device that needs to connect a central controller to several distributed sensor modules?

**Answer:** The core distinction is that RS-422 is a point-to-point or one-driver-to-many-receivers topology, while RS-485 is a true multi-point bus where multiple drivers share the same pair and take turns. So the first question is whether the sensor modules ever need to transmit back to the controller. If the architecture is strictly controller-to-sensors with sensors only responding on a separate path, RS-422 can work and gives you the simplicity of a dedicated driver per direction. But in most medical sensor networks the modules need to send data back — status, measurements, fault flags — so you need bidirectional communication on a shared pair, which is RS-485's job. Beyond topology, I'd weigh: the number of nodes and whether that count is likely to grow (RS-485 supports far more nodes per bus), the cable length and whether termination and fail-safe biasing will be needed (both standards benefit but RS-485 multi-point makes it mandatory), and the common-mode voltage range the transceivers must tolerate in the installed environment. For a medical device I'd also factor in the regulatory documentation burden — a multi-point bus with defined fail-safe states is easier to argue as deterministic and safe than an ad-hoc mix. My default for a distributed sensor network with bidirectional traffic is RS-485, reserving RS-422 for cases where the direction of data flow is genuinely fixed and the node count is small.

**Possible follow-ups:** What changes if the sensors are physically close together and the cable run is under a meter? How would you handle a mixed network where some modules are RS-422-only?

## Q3: How would you approach structuring firmware so that an SPI master can talk to several slaves requiring different clock speeds and different CPOL/CPHA modes, without mode changes corrupting transactions?

**Answer:** The risk is that changing CPOL/CPHA or the clock divider while a transaction is in flight, or leaving a slave selected across a mode change, produces glitches that corrupt data on either the old or new slave. I'd structure the SPI driver around a per-transfer configuration descriptor rather than a global bus state: each slave has an associated struct holding its clock rate, CPOL, CPHA, word size, and chip-select line, and the transfer API takes that descriptor so the driver knows exactly what to program before asserting CS. The sequence per transaction is: assert the target's CS only after the peripheral is configured and idle, run the transfer, deassert CS, then allow reconfiguration. Critically, I'd never change mode or speed while any CS is asserted — the driver should enforce that by tracking bus state and refusing or queuing a reconfiguration if a transfer is active. On many MCUs the SPI peripheral must be disabled and re-enabled to change CPOL/CPHA, which can glitch the clock line, so I'd verify on a scope that the clock idles at the correct level for the new mode before the first edge. I'd also consider grouping slaves by mode so consecutive transfers to same-mode devices don't require reconfiguration, reducing the number of mode switches and the associated risk. Finally, I'd wrap all of this behind a small bus-manager layer so application code just says "transfer to sensor B" and the driver handles the sequencing, and I'd unit-test the state machine with a mock peripheral to prove no mode change can occur mid-transaction.

**Possible follow-ups:** What would you do if two slaves share a chip-select line but need different modes? How would you verify on hardware that a mode change isn't glitching the clock?

## Q4: You're debugging a CAN-FD network where a node occasionally transmits an error frame that corrupts an in-progress message from another node, but only under heavy bus load. How would you approach this?

**Answer:** An error frame under load usually means a node is detecting a bit error, stuff error, CRC error, or form error on a frame it's receiving, and its error flag then collides with whatever is on the bus — so the visible corruption is a symptom, not the cause. I'd start by capturing the bus with a CAN analyzer that timestamps error frames and correlates them with the frame that was in progress, then look at which node flagged the error and what type it reported. Under heavy load, the common culprits are: sample-point mismatch between nodes (one node sampling too early or late relative to the others, so it misreads a bit near the tolerance boundary), propagation delay from long stubs or poor termination pushing the sample point out of the safe region, or a node whose oscillator tolerance is marginal so its bit timing drifts at the data-phase bit rate. CAN-FD makes this worse because the data phase runs much faster than arbitration, so the same physical layer that's fine in arbitration can be marginal in the data phase. I'd check that all nodes agree on the nominal and data bit timing, verify the sample point is in the recommended range for the data rate, and measure the actual differential waveform at the worst-case node to see whether ringing or slow edges are eating the margin. I'd also look at whether the erroring node is the one with the longest stub or the weakest termination. The fix is usually tightening bit timing, improving termination/stub layout, or reducing the data-phase rate until the margin is restored.

**Possible follow-ups:** How would you determine the correct sample point for a given bus length and data rate? What's the difference between an error frame caused by a bit error versus a stuff error, and why does it matter for diagnosis?

## Q5: How would you handle a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** The first priority is to contain the problem and protect the schedule before assigning blame. I'd get the team together to understand exactly what the compliance test exposed — which protocol behavior failed, whether it's a functional defect or a documentation/traceability gap, and what the minimum viable fix is. Then I'd separate the immediate remediation (a targeted fix plus a focused re-test of the affected area) from the systemic question of how the defect escaped earlier review and unit testing. On the people side, I'd talk with the junior engineer privately and frame it as a learning event rather than a failure — the goal is that they understand the root cause and can spot it next time, not that they feel punished. I'd also look honestly at whether the process let them down: was there a design review that should have caught it, was the protocol spec ambiguous, was there no conformance test before formal compliance testing? If the answer is yes to any of those, the fix belongs in the process, not just in the code. I'd document the root cause and the corrective action in whatever form the quality system requires, since in a regulated environment the investigation itself becomes part of the record. Finally, I'd communicate upward early and honestly about the schedule impact with a concrete recovery plan, because surprises discovered late are far worse than a known delay with a path forward.

**Possible follow-ups:** How would you decide whether to fix forward or roll back to a previous protocol implementation? What would you change in the review process to catch this class of defect earlier?
