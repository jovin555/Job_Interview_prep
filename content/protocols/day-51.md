## Q1: How would you approach designing a half-duplex RS-485 link where the driver enable and receiver enable must be switched at exactly the right moment, and the turnaround time budget is tight?
**Answer:** The core problem is that in half-duplex RS-485, the transceiver's DE (driver enable) and /RE (receiver enable) pins must be toggled around every transmission, and any error in that timing either truncates the last byte or causes the node to drive the bus while another node is still talking. The approach starts with understanding where the timing comes from: the UART's transmit-complete signal versus its transmit-empty signal. Transmit-empty fires when the shift register can accept a new byte; transmit-complete fires only after the last bit has actually left the shift register. For DE control you want transmit-complete, because de-asserting DE on transmit-empty will chop the final stop bit off the wire. On many microcontrollers this means using the transmit-complete interrupt, or in some cases a dedicated RS-485 DE pin that the UART hardware toggles automatically — that hardware assist is worth using when available because it removes firmware latency from the critical path entirely.

The second half of the problem is the receive side. After the master finishes transmitting, it must release the bus and re-enable its receiver, but it must also allow time for the line to settle and for the far-end driver to turn around. A common mistake is to re-enable the receiver immediately and start listening while the line is still ringing from the last transition. Adding a small guard delay — on the order of one or two bit times, or a few microseconds depending on baud — before re-enabling the receiver avoids interpreting that ringing as a start bit. On the slave side, the same logic applies in reverse: the slave must not begin driving until it has confirmed the master has released the bus, which usually means waiting for an idle line condition rather than reacting to the last received byte.

For a tight turnaround budget, I would calculate the worst-case total: master's last stop bit, plus driver disable propagation delay, plus line settling, plus slave's detection of idle, plus slave's driver enable propagation delay, plus slave's first start bit. If that sum exceeds the budget, the options are to raise the baud rate (which shrinks bit times but not the fixed propagation delays), to use a transceiver with faster enable/disable times, or to restructure the protocol so that turnaround happens less often — for example, batching responses rather than replying to each poll individually. I would also verify the timing on a scope with the DE pin and the differential pair probed together, because datasheet propagation delays are typical values and the real board may be slower.

**Possible follow-ups:** How would you handle the case where the slave's firmware crashes mid-transmission and leaves DE asserted, holding the bus? What role does fail-safe biasing play in making sure an idle bus is read as a defined logic level rather than floating?

## Q2: You're debugging a CAN-FD network where nodes occasionally enter error-passive state and recover, but the root cause is unclear. How would you approach this?
**Answer:** The first thing to establish is whether the errors are transmit errors, receive errors, or both, because the error counters increment differently depending on direction and that narrows the search considerably. A node that goes error-passive because its own transmissions are failing is usually a physical-layer or bit-timing problem local to that node. A node that goes error-passive because it is failing to receive correctly is more often a network-wide issue — termination, stub length, or a mismatch in bit-timing configuration between nodes.

I would start by reading the error counters and the last error code register on each node, ideally logging them continuously rather than only checking after a failure, because the error state is transient. The last error code tells you whether the failure was a bit error, a form error, a stuff error, an ACK error, or a CRC error, and each points in a different direction. A stuff error or form error often indicates a bit-timing mismatch — one node sampling at the wrong point in the bit, so it sees a transition where there shouldn't be one. A CRC error with otherwise clean timing suggests noise on the bus. An ACK error means nobody acknowledged, which points to a node that is present electrically but not participating, or a bus that is broken between the transmitter and the rest of the network.

The CAN-FD-specific wrinkle is that the arbitration phase and the data phase run at different bit rates, and each phase has its own timing segments. A node can be perfectly configured for the arbitration bit rate and still fail in the data phase if its sample point or its propagation segment is wrong for the higher rate. So I would verify the bit-timing registers on every node against the calculated values for the actual bus length and transceiver delays, not just against the nominal bit rate. Two nodes can both claim "1 Mbit/s data phase" and still disagree on sample point by enough to cause intermittent errors.

On the physical side, I would check termination at both ends and only at both ends, measure the differential signal at the worst-case node with a scope to look for ringing or excessive attenuation, and confirm that stub lengths are short relative to the data-phase bit time. CAN-FD's faster data phase makes stub length far more critical than in classical CAN, so a stub that was fine before may now be marginal. I would also check whether the error-passive events correlate with a particular node transmitting or with a particular time of day or temperature, since intermittent physical faults often have a trigger.

**Possible follow-ups:** How would you distinguish a bit-timing mismatch from a genuine noise problem if both produce CRC errors? What would you do if the errors only appear when a specific third-party node is on the bus?

## Q3: How would you approach choosing between a star topology and a daisy-chain topology for a multi-drop sensor network in a medical device, given that the sensors are physically distributed?
**Answer:** The choice is really driven by the electrical characteristics of the physical layer, not by convenience of cabling, so I would start by identifying which physical layer is actually in play. RS-485 and CAN are inherently bus topologies — they want a single terminated line with short stubs, and a star topology creates multiple unterminated branches that cause reflections and impedance discontinuities. If the network is RS-485 or CAN, a true star is usually a mistake unless the star is very small relative to the bit time, and even then it is fragile. A daisy-chain that runs from node to node with short stubs is the topology those standards expect.

I2C is the opposite: it is a bus in the logical sense but it does not have controlled impedance or termination, so its limits are capacitance and pull-up strength rather than reflections. A star or a tree can work on I2C as long as the total bus capacitance stays within the limit for the chosen speed and the pull-ups are sized accordingly. But a long star with many branches adds capacitance fast, and the pull-up has to charge all of it within the rise-time budget, so a star that looks fine at 100 kHz may fail at 400 kHz.

For a medical device with physically distributed sensors, the practical questions are: how far apart are the nodes, how many are there, what data rate is needed, and is the cabling fixed at design time or field-configurable? If the sensors are spread across a patient monitoring system with cable runs of tens of meters, RS-485 or CAN with a daisy-chain is the natural fit, and I would design the harness so that each node taps the bus with a short stub rather than branching the main run. If the sensors are all on one board or within a small enclosure, I2C or SPI with a star-like routing is fine and simpler.

There is also a hybrid worth considering: a daisy-chain backbone with a short star at each node, where the star is small enough that its stub length is a small fraction of the bit time. That is often what real installations end up being anyway, and it works as long as the stubs are kept short and the termination is correct. The failure mode to watch for is a star at the end of a long run, where the reflection from the star combines with the attenuation of the run and produces marginal signal at the far nodes.

I would also factor in serviceability. A daisy-chain means a break anywhere takes down everything downstream, which is a reliability concern in a medical device. A star means a single node failure is isolated, but the topology may not be electrically viable. If reliability matters more than topology purity, the answer may be to use a physical layer that tolerates the topology the mechanical design requires, rather than forcing the mechanical design to fit the physical layer.

**Possible follow-ups:** How would you calculate the maximum stub length for a given bit rate and transceiver? What would you do if the mechanical design forces a star topology on an RS-485 network?

## Q4: How would you approach implementing flow control on a UART link where the receiver occasionally cannot keep up with the transmitter, but the protocol does not have a built-in backpressure mechanism?
**Answer:** The first question is whether the flow control can be handled in hardware or has to be handled in the protocol. Hardware flow control using RTS/CTS is the cleanest solution when both ends support it and the connector has the pins available, because it lets the receiver de-assert CTS before its buffer overflows and the transmitter stops mid-stream without any protocol involvement. The subtlety is that RTS/CTS has latency — the transmitter may have already sent a byte or two after the receiver de-asserted CTS — so the receiver's buffer must have enough headroom to absorb those in-flight bytes. That headroom is a function of the baud rate and the round-trip latency of the flow-control signal, and it needs to be calculated, not guessed.

If hardware flow control is not available, the next option is software flow control using XON/XOFF, but that has its own problems: the flow-control characters have to be distinguishable from data, which means either escaping them in the payload or reserving them, and the same latency issue applies. It also fails badly if the link is carrying binary data that happens to contain the XON or XOFF byte. For a medical device carrying sensor data, that is often a non-starter.

If neither hardware nor software flow control is viable, the answer is to change the protocol so that the receiver is never asked to absorb more than it can handle. That usually means moving from a streaming model to a request/response or credit-based model, where the transmitter only sends when the receiver has explicitly granted permission. A credit-based scheme is more efficient than strict request/response because the receiver can grant several credits at once, but it requires the receiver to track credits and the transmitter to respect them, and it requires a way to recover if a credit is lost.

The other lever is to reduce the peak data rate so the receiver's worst-case processing time is always less than the time between bytes. That is often the simplest fix: if the receiver is spending too long in an interrupt handler or a flash write, the answer may be to restructure the receiver's firmware so that it drains the UART FIFO promptly and buffers the data for later processing, rather than trying to process each byte as it arrives. A DMA-driven receive path with a ring buffer can absorb bursts that would overflow a byte-at-a-time interrupt handler.

In a medical device, I would also want a defined behavior for the case where the receiver does overflow despite everything — a dropped byte should be detectable, not silent. That usually means a framing or checksum error at the protocol layer, and a defined recovery path such as a NAK and retransmit, or a resynchronization sequence.

**Possible follow-ups:** How would you size the receiver buffer given a known worst-case processing latency and baud rate? What would you do if the flow-control signal itself is unreliable due to noise on the cable?

## Q5: Imagine you're leading a design review where a junior engineer proposes using a single shared interrupt line for three different peripherals (a UART, an SPI sensor, and a GPIO alarm input), arguing that it saves pins and the firmware can just poll the peripherals to find out which one fired. How would you guide the team to evaluate this approach?
**Answer:** I would start by separating the two claims in the proposal: that sharing an interrupt line saves pins, which is true, and that the firmware can just poll to find out which peripheral fired, which is where the real risk lives. The pin savings are real and sometimes necessary, but the cost is that the interrupt handler now has to determine the source before it can do anything useful, and that determination takes time — time during which the other peripherals' events are still pending and the system is not yet servicing any of them.

The first thing I would ask the team to quantify is the worst-case latency for each peripheral's event. The alarm input is the one that worries me most: if it is a patient alarm or a safety-relevant signal, its latency budget is probably the tightest of the three, and sharing an interrupt line with a high-traffic UART means the alarm handler may be delayed by however long it takes to service the UART's event first. If the alarm's latency budget cannot absorb that, the shared line is not viable for that signal regardless of the pin savings.

The second thing is the polling cost itself. To find out which peripheral fired, the handler has to read each peripheral's status register in turn, and each read is a bus transaction with its own latency. If the peripherals are on different buses or have slow register access, that polling can take longer than the actual event handling. There is also a correctness concern: some peripherals clear their interrupt flag on status read, so a naive polling loop can accidentally clear an event before it has been handled. The handler has to be written carefully to read status, dispatch, and only then clear, and that ordering has to be verified for each peripheral.

The third thing is the interaction between events. If two peripherals fire at nearly the same time, the handler will see both flags set and has to service both, which means the latency of the second event is the sum of the first event's handling plus the polling overhead. That is usually acceptable for low-priority events but not for a safety-relevant one.

My guidance to the team would be: if the pin savings are genuinely necessary, the shared line can work, but only if the alarm input is either given its own interrupt line or is handled by a mechanism that does not depend on the shared handler — for example, a hardware latch that the handler reads first, before polling the other peripherals. If the alarm cannot be given its own line and cannot be latched, then the shared line is the wrong trade and the pin savings are not worth the latency risk. I would also want the team to document the worst-case latency calculation for each peripheral under the shared-line design, so the decision is made on numbers rather than on the appeal of saving pins.

**Possible follow-ups:** How would you structure the shared interrupt handler to minimize the latency of the highest-priority event? What would you do if the shared line is a hardware constraint that cannot be changed?
