# protocols — Day 112

## Q1: How would you approach debugging a USB 2.0 device that works on most hosts but intermittently fails enumeration on one specific host, where the failure appears as a control-transfer timeout during the GET_DESCRIPTOR phase?

**Answer:** I'd treat this as a host-tolerance problem first, not a device-firmware bug, because the same device enumerates elsewhere. The GET_DESCRIPTOR timeout usually means the device didn't respond within the host's control-transfer timeout window, so I'd instrument the device side to timestamp when it receives SETUP and when it queues the response, and compare that against the host's expected turnaround. Common culprits: the device taking too long to service the control endpoint because the main loop is blocked (e.g., a long flash write or sensor read), a slow interrupt latency on the control endpoint, or a stall condition the host interprets as a timeout. I'd also capture a bus trace on the failing host to see whether the device ACKs the SETUP at all, whether it NAKs repeatedly, or whether it goes silent — those three look identical to the host but point to different root causes. On the descriptor side, I'd check for anything the host might reject or mishandle: a descriptor length that doesn't match the actual bytes returned, a configuration descriptor whose wTotalLength disagrees with the sum of its sub-descriptors, or a string descriptor with an unusual encoding. Some host controllers are stricter than others about these. I'd also verify the device isn't relying on a particular ordering of standard requests that the failing host does differently. The fix is usually to make the control endpoint serviced with bounded latency and to make descriptors strictly spec-conformant rather than "works on my host."

**Possible follow-ups:** How would you distinguish a device-side latency problem from a host-driver quirk using only a bus analyzer? What would you change in firmware to guarantee the control endpoint is always serviced within the timeout window?

## Q2: How would you approach calculating pull-up resistor values for an I2C bus that must support both standard-mode (100 kHz) and fast-mode (400 kHz) operation with multiple devices on the bus?

**Answer:** The pull-up value is bounded from both sides, and you have to satisfy both bounds at the fastest speed you'll actually run. The upper bound comes from rise time: the bus capacitance and pull-up form an RC, and the spec limits rise time to roughly 1000 ns for standard mode and 300 ns for fast mode. So R_max ≈ t_r / (0.847 × C_bus) for the 30–70% rise-time convention — the constant depends on the threshold definition, so I'd use the datasheet's stated formula. The lower bound comes from sink current: each device must be able to pull the line below V_IL (typically 0.3 × VDD) while sinking no more than its rated I_OL (3 mA for standard/fast mode). That gives R_min ≈ (VDD − V_OL) / I_OL. You then pick a value inside [R_min, R_max] that works at 400 kHz, since a resistor sized for 100 kHz will be too weak at 400 kHz. The practical trap is bus capacitance: with many devices and long traces, C_bus climbs and R_max shrinks until it collides with R_min — at which point no single resistor works and you need an active pull-up, a bus buffer/expander, or you split the bus. I'd also account for the fact that the effective pull-up is the parallel combination of every pull-up on the bus, including ones baked into modules, and that some devices' input capacitance is worse than the datasheet typical. I'd verify on the bench with a scope looking at rise time at the worst-case corner (max capacitance, min VDD, hot and cold), not just trust the calculation.

**Possible follow-ups:** What would you do if the calculated R_max falls below R_min because of excessive bus capacitance? How does the presence of a bus buffer or repeater change the pull-up calculation on each segment?

## Q3: You're debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward. How would you approach this?

**Answer:** Bus-off means the node's transmit error counter exceeded 255, so the question is what drove the TEC up — and the fact that the bus looks healthy afterward tells me the fault was transient or node-local, not a permanently broken bus. I'd start by reading the controller's error counters and error-code capture register at the moment of bus-off, because most CAN-FD controllers latch the last error type (bit error, stuff error, CRC error, ACK error, form error) and often the bit position. That single register usually narrows it dramatically. If it's ACK errors, the node is transmitting when no other node is listening — a topology, termination, or lone-node-on-bus problem. If it's bit errors, suspect a physical-layer issue: termination, stub length, common-mode, or a marginal transceiver. If it's stuff or form errors, suspect a baud-rate mismatch or a node transmitting malformed frames. I'd also check whether the node is the only one awake at the time — a node that transmits into a bus with no other active nodes will accumulate ACK errors and go bus-off legitimately. Then I'd look at whether the node's automatic bus-off recovery is disabled in the driver, which would explain why it stays off until reset; many stacks require an explicit recovery request, and if the application never issues it, the node is stuck by design. Finally, I'd check for a firmware bug where the node transmits faster than the bus can absorb — e.g., a retry loop that keeps hammering the bus after errors, driving TEC up quickly. The fix depends on which of these it is, but the error-code register is where I'd start.

**Possible follow-ups:** How would you decide whether to enable automatic bus-off recovery versus requiring an application-level recovery request in a medical device? What does a rising TEC with a stable REC tell you versus both counters rising together?

## Q4: How would you approach selecting between RS-422 and RS-485 for a medical device that needs to connect a central controller to several distributed sensor modules?

**Answer:** The decision usually comes down to topology and whether you need multi-drop bidirectional communication. RS-422 is a point-to-point or one-driver-many-receivers arrangement — one driver, up to ten receivers, full-duplex over four wires. RS-485 is a true multi-point bus — multiple drivers and receivers on the same two wires, half-duplex, with the drivers tri-stated when not transmitting. If the central controller is the only talker and the sensors only listen, RS-422 is simpler and avoids the turnaround and arbitration concerns entirely. But if the sensors need to talk back — and in a medical sensor network they almost always do — RS-485 is the natural fit because it supports multiple drivers on one pair. The trade-offs I'd weigh: RS-485 half-duplex requires driver-enable timing discipline and fail-safe biasing so the bus doesn't float when no one is driving; RS-422 full-duplex avoids that but doubles the wire count and doesn't scale to many talkers. I'd also consider common-mode range, since both share similar electrical characteristics but the multi-drop case stresses it more. For a medical device I'd lean RS-485 for the multi-drop case, with careful attention to termination, biasing, and turnaround, and I'd document the topology and termination scheme in the design file because it's the kind of thing that gets audited.

**Possible follow-ups:** What are the practical consequences of using RS-422 in a topology where more than one node needs to transmit? How does fail-safe biasing differ between a two-wire RS-485 bus and a four-wire RS-422 link?

## Q5: You're leading a design review where a junior engineer proposes using a single UART with a software-based protocol multiplexer to communicate with four different sensors, each with different baud rates and protocols. The hardware engineer argues this is unreliable and wants four separate UART peripherals. How would you guide the team to evaluate this approach?

**Answer:** I'd frame it as a requirements question before a technology question, because both positions can be right depending on the constraints. First I'd ask what the timing requirements actually are: do any of the four sensors have a hard latency or determinism requirement, or is this best-effort polling? A software multiplexer that reconfigures one UART's baud rate and protocol between transactions introduces reconfiguration latency and a window where a byte arriving for the wrong protocol gets misinterpreted — that's fine for slow polling, dangerous for anything with a deadline. Second, I'd look at whether the sensors can tolerate being time-shared at all: some devices time out if not serviced within a window, and a multiplexed UART makes that window a function of the other three sensors' traffic. Third, I'd quantify the pin and peripheral cost honestly — four UARTs may be genuinely unavailable on the chosen MCU, in which case the question becomes "which MCU" rather than "which architecture." Fourth, I'd ask about failure modes: with a shared UART, one sensor's misbehavior (e.g., a stuck transmitter, a framing error storm) can corrupt traffic to the others, whereas separate peripherals isolate faults — which matters in a medical device where fault containment is a design goal. My guidance would be: if the sensors are slow, tolerant of sharing, and the MCU genuinely lacks peripherals, a carefully designed multiplexer with per-sensor framing validation and timeouts is defensible; if any sensor has a real-time requirement or the fault-isolation argument is strong, the hardware engineer is right and we should either add UARTs or move to a bus that natively supports multi-drop. I'd want the decision documented with the reasoning, because "we multiplexed one UART" is exactly the kind of choice a reviewer will question later.

**Possible follow-ups:** What safeguards would you require in the software multiplexer design if the team decides to go that route? How would you decide between adding UART peripherals and moving to a multi-drop bus like RS-485 or CAN-FD?
