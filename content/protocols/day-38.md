## Q1: You're debugging a system where a UART link between a microcontroller and a wireless module works reliably at 9600 baud but produces frequent framing errors at 115200 baud. The link is approximately 10 centimeters on the same PCB. How would you approach this?

**Answer:** Since the trace length is short and the failure is baud-rate dependent, I'd first suspect the clock source rather than the physical layer. The most common cause is baud rate mismatch due to oscillator tolerance. At 115200 baud, the bit time is roughly 8.7 microseconds, so even a 2–3% clock error can push the sampling point outside the valid window, especially if both ends have errors in opposite directions. I'd start by measuring the actual clock frequency on both the microcontroller and the wireless module with a frequency counter or high-resolution oscilloscope, and compare against the datasheet tolerance. If the MCU is using an internal RC oscillator, I'd check whether the calibration routine is running correctly and whether the tolerance is specified across the operating temperature range. I'd also verify the actual baud rate generated by the UART peripheral, since some MCUs have limited baud rate generator resolution at higher speeds — the divider may not produce an exact 115200. If the clocks check out, I'd look at signal integrity: even on a short trace, a poorly routed line near a switching regulator or a digital bus can cause edge degradation that matters more at higher data rates. I'd probe the RX line with an oscilloscope to check rise/fall times, ringing, and noise margin. Finally, I'd check whether the wireless module's UART has any internal flow control or timing requirements that change at higher baud rates — some modules have a fixed inter-character gap or require CTS/RTS handling that becomes problematic at higher speeds.

**Possible follow-ups:** How would you determine whether the error is on the transmit side or the receive side? What if the clock measurements show both devices are within spec — what would you check next?

## Q2: How would you approach designing a fail-safe mechanism for a UART-based communication link in a medical device where a sensor must never be left in an unknown state if the main controller resets or loses power mid-transaction?

**Answer:** The core principle is that the sensor must have a deterministic default state that it returns to whenever it detects that the link is no longer healthy — it should never rely on the controller to "clean up" after a failure. I'd start by defining the protocol so that every transaction has a clear start and end marker, plus a checksum, so the sensor can detect a truncated or corrupted message. The sensor firmware would implement a watchdog timer that starts at the beginning of each transaction; if the full message isn't received within the timeout, the sensor discards the partial data and returns to its safe state. The timeout needs to be longer than the worst-case legitimate inter-message gap but short enough that the sensor doesn't hold an unsafe state for long. On the hardware side, I'd consider whether the sensor has a hardware reset input that the controller can assert, and whether the sensor's power rail can be independently switched — that gives a second layer of recovery. I'd also think about the electrical state of the UART lines during controller reset: some MCUs float their TX pin during reset, which could be interpreted as a break condition or noise. I'd add pull-up or pull-down resistors to define the idle state, and the sensor firmware should treat a break condition or a line that stays in an invalid state for longer than a defined period as a link failure. For a medical device, I'd document this behavior in the risk management file — the failure mode, the detection mechanism, and the resulting safe state — and verify it through fault injection testing where the controller is reset or powered off at random points during transactions.

**Possible follow-ups:** How would you choose the watchdog timeout value? What if the sensor itself needs to initiate communication — how does that change the fail-safe design?

## Q3: You're designing a medical device where a central controller needs to communicate with several sensor modules over a shared bus. Some sensors require deterministic, low-latency response, while others generate high-volume data that can tolerate delay. How would you approach selecting between I2C, SPI, UART, RS-485, and CAN-FD for this architecture?

**Answer:** I'd start by separating the requirements into hard constraints and preferences. The deterministic, low-latency sensors are the driving constraint — I need to know the worst-case latency they can tolerate, the message size, and the update rate. The high-volume sensors matter for aggregate throughput but are more flexible on timing. I'd also consider physical topology: are the sensors on the same PCB, on a separate board via a cable, or distributed over distance? That immediately rules out some options — I2C and SPI are really for board-level or short flex-cable connections, while RS-485 and CAN-FD handle longer cable runs with better noise immunity. For a medical device, I'd also factor in electrical safety: if sensors are patient-connected, isolation requirements may constrain the bus choice. If the sensors are on the same board, I'd likely use separate buses for the two classes — a dedicated I2C or SPI bus for the deterministic sensors with a fixed polling schedule, and a higher-throughput SPI or UART link for the high-volume data. Mixing them on one bus forces a scheduling compromise. If the sensors are distributed over a cable, CAN-FD is attractive because it provides message prioritization through arbitration — the deterministic sensors can use high-priority IDs and the high-volume data uses lower priorities, so latency is bounded by the worst-case blocking time from higher-priority messages, which can be calculated. RS-485 with a master-slave polling scheme can also work, but the master controls all timing, so the deterministic latency depends on the polling cycle design — it's deterministic but potentially slower to react to asynchronous events. I'd also consider whether any sensor needs to initiate communication spontaneously; if so, CAN-FD's event-driven arbitration is a better fit than a polled RS-485 bus. Finally, I'd think about the firmware complexity and testability: CAN-FD has more protocol overhead to get right, but it provides error detection and retransmission built in, which is valuable in a medical device.

**Possible follow-ups:** How would you calculate the worst-case latency for the deterministic sensors on a CAN-FD bus? What if the high-volume sensor data is so large that it would starve the lower-priority messages — how would you handle that?

## Q4: Imagine you're leading a design review where a junior engineer proposes using a single UART with a software-based protocol multiplexer to communicate with four different sensors, each with different baud rates and protocols. The hardware engineer argues this is unreliable and wants four separate UART peripherals. How would you guide the team to a decision?

**Answer:** I'd frame this as a requirements and risk trade-off rather than a personal preference. First, I'd ask the junior engineer to walk through the timing budget: what's the worst-case latency for each sensor's data, and can the software multiplexer guarantee that while switching baud rates and protocols? The key risk with a single UART is that you can only talk to one sensor at a time, and switching baud rates mid-stream requires careful synchronization — if the sensor sends data while you're reconfiguring the UART, you lose it. I'd ask for a concrete analysis of the aggregate data rate versus the UART throughput, including protocol overhead and the time lost to baud rate switching. I'd also ask about failure modes: if the multiplexer gets stuck in a state where it's waiting for a response from one sensor, how does it recover, and what happens to the other three sensors' data during that time? On the hardware side, I'd ask the hardware engineer to quantify the cost of four UART peripherals — pin count, MCU package size, PCB routing complexity, and whether the MCU actually has four UARTs available. Then I'd guide the team toward a decision based on the data: if the timing analysis shows the single UART has sufficient margin and the failure modes are acceptable, it could be a valid cost-saving choice, but I'd want to see a written analysis and a fallback plan. If the timing is tight or the sensors have asynchronous event-driven data, four UARTs are the safer choice. I'd also suggest a middle ground: two UARTs, grouping sensors by baud rate or by timing criticality, which reduces the multiplexing complexity while saving pins. The decision should be documented with the rationale, and I'd ask the junior engineer to own the analysis and present it back — that builds their skills while keeping the design review rigorous.

**Possible follow-ups:** What specific failure modes would you ask the junior engineer to analyze in the single-UART approach? How would you decide whether the cost savings justify the added firmware complexity?

## Q5: You're debugging a system where an RS-485 network works reliably at 9600 baud but experiences intermittent corruption at 115200 baud. The cable run is approximately 150 meters with 12 nodes. How would you approach isolating the root cause?

**Answer:** I'd approach this systematically, starting with the physical layer since the baud-rate dependence points there. At 115200 baud, the bit time is about 8.7 microseconds, and at 150 meters, the propagation delay is roughly 750 nanoseconds one-way — that's about 8.6% of a bit time, which is significant but not necessarily fatal. The first thing I'd check is termination: at 150 meters with 12 nodes, proper termination at both ends is critical. I'd verify that termination resistors match the cable characteristic impedance, typically 120 ohms, and that they're placed at the physical ends of the bus, not at the controller or at a convenient node in the middle. I'd also check for unterminated stubs — any node connected with a long drop from the main bus acts as a reflection point, and at higher baud rates, reflections that were tolerable at 9600 baud become problematic. I'd measure the signal at multiple points along the bus with an oscilloscope, looking at the waveform shape at the far end — checking for ringing, overshoot, and whether the signal crosses the receiver threshold cleanly. I'd also check the bias resistors: RS-485 receivers need fail-safe biasing to hold the bus in a known state when no driver is active, and at higher baud rates, the bias network interacts with the termination and cable capacitance, potentially slowing the signal edges. I'd verify the common-mode voltage range — if the ground potential differs between nodes, the receiver might be operating near its input limits. On the firmware side, I'd check the driver enable timing: in half-duplex mode, the transmitter must disable its driver after the last stop bit, and if the turn-around time is too slow, the next node might start transmitting while the previous driver is still active, causing bus contention. I'd also check whether the baud rate generator on all nodes is accurate enough — at 115200, a 2% clock error on one node can cause framing errors. I'd use a protocol analyzer to capture the actual corrupted frames and look for patterns: are the errors always at the start of a message, at the end, or random? That would help distinguish between reflection issues, contention, and clock mismatch.

**Possible follow-ups:** How would you determine whether the issue is reflections versus driver turn-around timing? What measurements would you take to confirm the root cause before making a change?
