## Q1: How would you approach designing a fail-safe mechanism for a UART-based communication link in a medical device where a sensor must never be left in an unknown state if the main controller resets or loses power mid-transaction?

**Answer:** The core requirement is that the sensor must reach a known, safe state regardless of when or how the main controller goes away. I'd approach this at multiple layers. First, at the protocol level, every transaction should have a defined structure with a clear end-of-message marker, so the sensor can detect an incomplete transaction. The sensor should implement a transaction timeout — if it hasn't received the expected number of bytes or a valid terminator within a defined window, it discards the partial data and returns to its idle state. Second, at the hardware level, I'd consider whether the sensor needs a hardware reset line from the controller, or whether the sensor's own watchdog timer should be independent of the communication link. Third, I'd think about the sensor's default state on power-up or reset — it should default to the safest operating mode, not to whatever state it was last commanded into. Finally, I'd add a health-check mechanism: the controller periodically sends a status request, and if the sensor doesn't receive one within a defined interval, it assumes the controller is gone and transitions to its safe state. The key design principle is that the sensor must not rely on the controller being alive to know that the controller is dead — it needs its own independent timeout and recovery logic.

**Possible follow-ups:** How would you handle the case where the sensor is in the middle of a multi-byte write when the controller resets? What if the sensor itself needs to initiate communication to report an alarm — how does that interact with the fail-safe design?

## Q2: You're debugging a system where an RS-485 network with 16 nodes works reliably at 9600 baud but experiences intermittent corruption at 115200 baud over a 150-meter cable run. How would you approach isolating the root cause?

**Answer:** I'd start by recognizing that this pattern — works at low baud, fails at high baud over a long cable — points to signal integrity issues that become significant only when the bit time shrinks. At 9600 baud, the bit time is roughly 104 microseconds; at 115200, it's about 8.7 microseconds, so any reflections, ringing, or skew that was negligible at the lower rate now falls within the sampling window. My first step would be to look at the physical layer: check the termination resistors at both ends of the cable — are they present, correctly valued (typically matching the cable's characteristic impedance, often 120 ohms), and placed at the actual ends of the bus? I'd also check for unterminated stubs, which act as transmission line discontinuities. Next, I'd examine the transceiver's fail-safe biasing — at higher baud rates, the bias network may not be strong enough to hold the bus in a valid state during the inter-frame gap, especially if the cable is long and has high capacitance. I'd also verify that all nodes are using the same transceiver type and that the driver's slew rate is appropriate — some transceivers have limited slew rate that becomes marginal at higher speeds. I'd use an oscilloscope at the farthest node to look at the actual waveform: check rise/fall times, overshoot, ringing, and the voltage at the receiver's input during transitions. I'd also check the ground path between nodes — a long cable run with poor grounding can create common-mode voltage differences that become problematic at higher data rates. Finally, I'd verify the firmware isn't the issue: check that the UART baud rate tolerance is adequate, that the driver enable/deassert timing (turn-around time) is correct, and that there's no bit stuffing or framing issue in the protocol layer.

**Possible follow-ups:** How would you determine whether the issue is reflections versus common-mode noise? What measurements would you take to confirm the fix?

## Q3: How would you approach designing a clock stretching strategy for an I2C bus in a medical sensor device where one slave device needs more time to process a read request than the master's timeout allows?

**Answer:** This is a common tension in I2C design: the slave needs time to prepare data, but the master has a watchdog timeout to prevent bus hangs. I'd approach this by first understanding the actual timing requirements — how long does the slave need, and is that time consistent or variable? If the slave's processing time is bounded and predictable, the cleanest solution is to configure the master's timeout to accommodate the worst-case stretch duration, with margin. But if the stretch can be very long or unbounded, that approach breaks down because a stuck slave would look identical to a slow slave. In that case, I'd consider a few strategies. One option is to use a repeated-start or a two-phase read: the master sends a command to trigger the measurement, then polls the slave's status register until it indicates data is ready, then performs the actual read. This avoids clock stretching entirely because the slave never needs to hold SCL low while preparing data. Another option is to implement a software timeout in the master that distinguishes between "slave is legitimately stretching" and "bus is stuck" — for example, by tracking how long SCL has been held low and comparing it against the slave's documented maximum stretch time. If the timeout fires, the master should generate a bus recovery sequence (toggle SCL while releasing SDA, then issue a STOP) rather than just resetting the peripheral. I'd also consider whether the slave can be configured to stretch only for a bounded time and return NACK if it can't meet the deadline, rather than stretching indefinitely. For a medical device, I'd document the worst-case timing in the design specification and verify it under test, because clock stretching behavior can be temperature- and voltage-dependent.

**Possible follow-ups:** How would you distinguish between a slave that is legitimately stretching the clock and one that has hung the bus? What happens if the slave stretches beyond the master's hardware timeout — can the master recover without a full bus reset?

## Q4: Imagine you're leading a design review where a junior engineer proposes using a single SPI bus with daisy-chain configuration to connect four different sensors, each requiring different clock polarity and phase settings. How would you guide the team to evaluate this approach?

**Answer:** I'd start by acknowledging that daisy-chain SPI can save pins and PCB space, but it imposes constraints that need careful evaluation. The most fundamental issue is that in a true daisy-chain, all devices share the same clock polarity (CPOL) and clock phase (CPHA) because they're all clocked simultaneously from the same master. If the four sensors require different modes, a daisy-chain configuration simply won't work — you'd need to either find sensors that can operate in a common mode or abandon the daisy-chain approach. I'd guide the team to first verify the actual mode requirements of each sensor from their datasheets, not just assume they differ. Some sensors are flexible and can operate in multiple modes, in which case you might find a common mode that works for all. But even if a common mode exists, I'd ask the team to evaluate the other implications of daisy-chaining: data latency increases because each device must shift through the entire chain before the master sees the response; if one device in the chain fails, the whole chain is broken; and the firmware becomes more complex because the master must track which device's data is at which position in the shift register. I'd also ask about the data rates involved — if any sensor needs high throughput, daisy-chaining adds overhead that might not be acceptable. My guidance would be to evaluate independent chip selects as the baseline, and only consider daisy-chain if there's a clear benefit (like pin count on a very small package) that outweighs the added complexity and risk. If daisy-chain is pursued, I'd require a detailed timing analysis and a fault-mode analysis showing what happens when one device in the chain fails.

**Possible follow-ups:** What if the sensors can all operate in a common SPI mode — would you then recommend daisy-chain? What other factors would you consider? How would you handle the case where one sensor in the chain needs to be isolated for debugging?

## Q5: How would you approach handling a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** I'd approach this in two phases: immediate response and systemic improvement. In the immediate phase, my priority is to understand the full scope of the problem before assigning blame. I'd call a meeting with the junior engineer, the test engineer who found the issue, and any other relevant stakeholders to review the specific failure, the protocol specification, and the implementation. The goal is to determine: Is this a misunderstanding of the specification, a coding error, or a gap in the specification itself? Once we understand the root cause, I'd work with the team to develop a correction plan — this might involve a code fix, a specification clarification, or both. I'd also assess whether the same error pattern exists elsewhere in the codebase, because a protocol implementation error often reflects a systematic misunderstanding rather than an isolated mistake. In parallel, I'd communicate transparently with project management about the schedule impact and what we're doing to mitigate it. In the second phase, after the immediate issue is resolved, I'd focus on preventing recurrence. This means reviewing our verification process — why didn't our unit tests, integration tests, or pre-compliance testing catch this? I'd look at whether we had adequate test coverage for protocol conformance, whether we were testing against the right version of the specification, and whether the junior engineer had adequate review support. I'd also have a private, constructive conversation with the junior engineer to understand their thought process and identify any training or mentoring gaps. The key is to treat this as a process failure, not a personal failure — the goal is to improve the system so the same class of error is caught earlier next time. For the junior engineer, I'd make it clear that finding errors during testing is exactly what testing is for, and that the important thing is what we learn from it.

**Possible follow-ups:** How would you handle the schedule pressure from management while ensuring the fix is thorough? What changes to the development process would you propose to catch protocol errors earlier? How would you support the junior engineer's professional development after this incident?
