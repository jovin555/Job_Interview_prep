## Q1: How would you approach debugging an I2C bus where a slave device holds SDA low after a transaction, preventing any further communication until power is cycled?

**Answer:** This is the classic "bus stuck" or "SDA held low" condition, and the first thing I'd do is confirm which side is actually holding the line. With a scope or logic analyzer on SDA and SCL, I'd check whether SCL is still toggling freely while SDA is pinned low — if so, the master's clock is fine and a slave is holding the data line. The usual root cause is a slave that was mid-transaction when the master reset, or that missed a clock edge and is waiting for more clocks to finish shifting out a bit. The standard recovery is to manually clock SCL up to nine times while SDA is released, which lets the slave shift out whatever remaining bits it has and eventually release SDA; then issue a STOP condition to resynchronize the bus state machine. In firmware, I'd implement this as a bus-recovery routine that runs before any I2C transaction if the bus is detected as stuck, using GPIO bit-banging on the SCL/SDA pins rather than the hardware peripheral. Beyond the immediate recovery, I'd want to understand why it happened: check for a master reset mid-transaction (add a proper STOP or bus-clear on init), verify the slave's datasheet behavior on partial transactions, and consider whether a bus switch or reset line to the offending slave is warranted. In a medical device, I'd also make sure the recovery is bounded and logged, and that the system can flag a persistent stuck-bus as a fault rather than silently retrying forever.

**Possible follow-ups:** How would you detect a stuck bus in firmware without a scope, and what timeout would you use? Would you add a hardware reset line to every I2C slave, and what are the trade-offs?

## Q2: How would you approach structuring firmware for an SPI master that must talk to several slaves running at different clock speeds and using different CPOL/CPHA modes?

**Answer:** The key insight is that SPI mode and clock rate are per-transaction properties, not per-bus properties, so the firmware needs a clean abstraction that makes the mode and speed explicit at every transfer. I'd define a device descriptor structure per slave — chip-select pin, CPOL, CPHA, max clock, word size, and any inter-byte delay — and have a single transfer function that takes that descriptor, reconfigures the SPI peripheral to the required mode and prescaler, asserts the correct chip select, performs the transfer, and de-asserts. The reconfiguration must happen while the bus is idle and the peripheral is disabled, otherwise you can get glitchy clock edges or a partial frame. I'd also guard against two tasks trying to use the bus concurrently with a mutex, since reconfiguring mid-transaction from another context would corrupt the transfer. On the hardware side, I'd verify that the chosen prescaler values actually land within each slave's rated clock, and that the board layout supports the fastest device's signal integrity. For testability, I'd expose the descriptor table so a test harness can exercise each device independently and verify mode/speed changes don't leak between transactions.

**Possible follow-ups:** What happens if you change CPOL/CPHA while chip select is still asserted, and how would you prevent it? How would you handle a slave that needs a delay between the last clock and chip-select de-assertion?

## Q3: How would you approach designing fail-safe biasing for an RS-485 bus, and why does it matter more in a medical device than in a general industrial network?

**Answer:** Fail-safe biasing ensures that when no driver is active — all transceivers in receive mode — the differential pair sits at a defined logic level rather than floating into the indeterminate region around zero volts, which could cause receivers to output random or oscillating states. The standard approach is a pull-up on one line (A or B depending on convention) and a pull-down on the other, sized so the differential voltage exceeds the receiver's fail-safe threshold (typically a few hundred millivolts) while still presenting an acceptable load to the active driver. The resistor values depend on termination: with a 120-ohm termination at each end, the bias network forms a divider, and you have to budget the bias current against the driver's drive capability and the total bus load. You also have to account for the number of nodes and their input impedance, since too many receivers loading the bus will drag the biased differential voltage down. In a medical device, the reason it matters more is that an indeterminate bus state during an idle period could be interpreted as a spurious start bit or a false frame, and in a safety-critical context a phantom message or a missed alarm is far worse than in a general industrial network where a retry is acceptable. So I'd be more conservative with the bias margin, verify it across the full temperature and node-count range, and confirm it during compliance testing rather than assuming the textbook values are sufficient.

**Possible follow-ups:** How would you calculate the bias resistor values for a bus with 32 nodes and 120-ohm terminations at both ends? What happens to fail-safe biasing if a node loses power and its transceiver presents a low impedance to the bus?

## Q4: How would you approach selecting between interrupt transfers and isochronous transfers for a USB 2.0 medical device that streams real-time sensor data to a host, where the requirement is that no data be lost?

**Answer:** The two transfer types have fundamentally different guarantees, so the requirement "no data lost" immediately points away from isochronous. Isochronous transfers reserve bandwidth and guarantee timing, but they provide no retry and no error detection at the USB level — a corrupted or dropped packet is simply gone, which is fine for audio or video where a glitch is tolerable but unacceptable for a medical sensor stream where every sample matters. Interrupt transfers, by contrast, are guaranteed-delivery with error detection and retry, and they have a bounded latency (the endpoint's polling interval), which makes them a good fit for moderate-rate periodic data that must not be lost. So my default would be interrupt transfers for the sensor stream, sized so the endpoint's max packet and polling interval comfortably cover the data rate with margin. The trade-off is that interrupt transfers consume a guaranteed slice of bus bandwidth and have a latency floor set by the polling interval, so if the data rate were very high I'd have to check whether the host schedules enough bandwidth. If the application genuinely needed isochronous timing (e.g., a continuous waveform with hard real-time constraints), I'd layer application-level sequence numbers and a small buffer on top to detect and mask drops, but I'd treat that as a compromise, not a first choice. I'd also consider a bulk endpoint for the same data if latency were less critical, since bulk gives guaranteed delivery with flow control but no timing guarantee.

**Possible follow-ups:** How would you size the interrupt endpoint's max packet size and polling interval for a given sample rate? What would you do if the host couldn't schedule enough interrupt bandwidth for your required rate?

## Q5: You're leading a design review where a junior engineer proposes using a single UART with a software-based protocol multiplexer to talk to four sensors, each with a different baud rate and protocol. The hardware engineer argues this is unreliable and wants four separate UART peripherals. How would you guide the team to a decision?

**Answer:** I'd frame this as a requirements and risk question rather than a hardware-versus-software argument, because both positions have merit and the right answer depends on the actual constraints. First I'd get the facts on the table: what are the four sensors' baud rates, their timing requirements (do any need deterministic latency?), their error tolerance, and how much data each moves. Then I'd evaluate the software-multiplexer approach against those facts — the real risks are that reconfiguring a UART's baud rate mid-stream costs time and can drop bytes, that a single UART serializes all four conversations so one slow sensor blocks the others, and that error handling becomes ambiguous when a framing error could belong to any of four protocols. I'd ask the junior engineer to walk through how the multiplexer handles a sensor that needs to respond within a tight window while another sensor is mid-transaction, and how errors are attributed. Then I'd have the hardware engineer quantify the cost of four UARTs — pin count, board space, MCU peripheral availability, cost. With both sides' constraints explicit, the decision usually falls out: if the sensors are low-rate and tolerant of serialization, the multiplexer may be fine and saves hardware; if any sensor has real-time needs or the error attribution is genuinely ambiguous, the dedicated peripherals are the safer engineering choice. I'd make the decision as a team, document the rationale and the risks we accepted, and if we went with the multiplexer, define the test cases that would prove it's reliable before we commit.

**Possible follow-ups:** If you chose the software multiplexer, what specific tests would convince you it's safe for a medical device? How would you handle the case where the MCU simply doesn't have four UART peripherals available?
