## Q1: How would you approach designing a fail-safe biasing scheme for an RS-485 bus, and why does fail-safe biasing matter more in a medical device than in a general industrial network?

**Answer:** Fail-safe biasing exists to guarantee that when no driver is actively transmitting — the idle state — the differential voltage across the twisted pair settles into a defined logic level rather than floating near the receiver's switching threshold. A floating bus is the worst case: small amounts of noise, leakage, or capacitive coupling can push the differential voltage across the threshold, and the receiver can interpret that as a start bit or as random transitions. In a half-duplex multi-drop network, the bus spends a large fraction of its time idle between transactions, so this is not a corner case — it is the normal operating condition.

The mechanism is a pull-up resistor on one line (typically the non-inverting line, A or D+) and a pull-down on the other (B or D−), sized so that the resulting differential voltage exceeds the receiver's input threshold with margin, while still presenting an acceptable load to the active driver. The classic trade-off is that the bias resistors form a divider with the termination resistors, so the bias network has to be sized against the termination value, and the total load the driver sees must stay within its drive capability. A common approach is to compute the bias current needed to develop a few hundred millivolts of differential idle voltage across the parallel combination of the two terminations, then pick resistor values that deliver that current without overloading the driver. If the bias is too weak, the idle state is marginal; if it is too strong, the driver has to sink or source more current than it is rated for, and the differential swing during active transmission is degraded.

Why this matters more in a medical device: an RS-485 link in a patient monitoring or control system is often carrying data where a spurious transition is not just a corrupted packet — it can be interpreted as a valid-looking message, a spurious alarm, or a control command. The receiver cannot distinguish "no one is talking" from "someone is talking and the line is noisy" unless the idle state is unambiguous. Fail-safe biasing makes the idle state deterministic, which means the protocol layer can rely on "no activity" being a real, trustworthy condition. It also interacts with fault detection: if the bus is properly biased and the receiver still sees activity when no node should be transmitting, that is a meaningful diagnostic signal rather than an ambiguous one.

There is also a regulatory angle. In a device that has to demonstrate predictable behavior under fault conditions, an undefined bus state is a hazard that has to be either eliminated or shown to be detected. Fail-safe biasing is one of the cheaper ways to eliminate it at the physical layer, so the firmware does not have to carry the entire burden of detecting and recovering from an ambiguous idle state.

## Q2: How would you approach debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward?

**Answer:** Bus-off is a specific, well-defined state: the controller's transmit error counter has exceeded 255, which means the controller has accumulated enough transmit errors that it has removed itself from the bus to avoid disrupting other nodes. The fact that it stays off until reset, and that the bus looks healthy afterward, tells you something important — the controller is not automatically recovering, which means either the controller is configured for one-shot bus-off recovery (or no automatic recovery at all), or the recovery attempt is failing for a reason that is not visible on the bus.

The first thing I would do is separate the two questions: why did the node go bus-off in the first place, and why does it not come back? These are often different problems.

For the first question, I would look at the error counters and the error state transitions. CAN controllers expose the transmit and receive error counters, and the pattern of how they increment tells you a lot. If the transmit error counter is climbing steadily, the node is failing to get acknowledgments — which usually means either no other node is acknowledging its frames, or its own transmissions are being corrupted on the wire. If the receive error counter is also climbing, the node is seeing malformed frames, which points to a physical-layer or bit-timing problem rather than a protocol problem. A common cause of bus-off in a network that otherwise looks healthy is a bit-timing mismatch: the node's sample point or bit rate in the arbitration phase does not match the rest of the network closely enough, so it mis-samples bits that other nodes see correctly. This can be intermittent because it depends on the exact bit pattern and the phase relationship between the node's clock and the bus.

For the second question — why it does not recover — I would check the controller configuration. Many CAN controllers have a bus-off recovery mode that is either automatic (the controller waits for 128 occurrences of 11 recessive bits and then re-integrates) or manual (the firmware has to explicitly request recovery). If the firmware is not handling the bus-off interrupt and requesting recovery, the node will sit in bus-off indefinitely. That is a firmware bug, not a hardware one, and it is a very common one because bus-off is often treated as a rare event that "should not happen" and therefore is not handled.

I would also consider whether the node is going bus-off because of a transient that has since cleared, in which case automatic recovery would be the right behavior, versus a persistent fault that would cause it to go bus-off again immediately. If it is the latter, automatic recovery just creates a flapping node, which is worse than staying off — it disrupts the bus repeatedly. So the recovery strategy has to be paired with a diagnostic: the node should record why it went bus-off, and the system should be able to report that.

In a medical device context, I would also want to know what the node was doing when it went bus-off. If it was carrying safety-critical data, the system needs a defined behavior for "this node is offline" — the rest of the network should not silently continue as if the data were still valid. That is a system-level requirement that sits above the CAN controller, but the bus-off handling has to feed into it.

- How would you distinguish a bit-timing mismatch from a physical-layer problem using only the error counters and a scope?
- What would you log or report from a node that has gone bus-off, so that a field failure can be diagnosed without reproducing it?

## Q3: How would you approach implementing flow control on a UART link where the receiver occasionally cannot keep up with the transmitter, but the protocol has no built-in backpressure mechanism?

**Answer:** The first thing to establish is whether the receiver's inability to keep up is a steady-state condition or a transient one. If the receiver is fundamentally slower than the transmitter's average data rate, no amount of flow control will fix it — the link is over-subscribed and the protocol or the data rate has to change. Flow control is for the transient case: the receiver is normally fast enough, but occasionally it has a burst of higher-priority work (an interrupt, a flash write, a sensor conversion) and its receive buffer fills before it can drain it.

If the hardware supports RTS/CTS, that is the cleanest answer, because it is handled by the UART peripheral and does not require the firmware to be in the data path. The receiver asserts its RTS line when its buffer crosses a high-water mark and de-asserts it when it drops below a low-water mark. The hysteresis between the two thresholds matters — if they are too close, the line chatters; if they are too far apart, the buffer can still overflow between the assertion and the transmitter actually stopping. The transmitter has to respect CTS, which means the UART driver has to be configured to check CTS before each byte (or each FIFO load), not just at the start of a transfer. A common bug is a driver that checks CTS once and then streams a whole buffer, which defeats the purpose.

If the hardware does not support RTS/CTS, or if the lines are not available, the options are software flow control (XON/XOFF) or a protocol-level acknowledgment scheme. XON/XOFF is simple but has a well-known failure mode: the flow-control characters are in-band, so if the data payload can contain the same byte values, the receiver can misinterpret data as flow control. That can be mitigated by escaping or by choosing byte values that cannot appear in the payload, but both add complexity and both fail if the link is already corrupted. A protocol-level scheme — the receiver sends an explicit "ready for more" message, and the transmitter waits for it — is more robust but adds latency and requires the protocol to be designed for it, which the question says it is not.

Given that the protocol has no built-in backpressure, the most practical approach is usually to add flow control at the transport layer without changing the application protocol: wrap the existing protocol in a framing layer that includes a sequence number and an acknowledgment, and have the transmitter limit its outstanding unacknowledged frames. This is essentially sliding-window flow control, and it can be implemented in the UART driver or a thin layer above it. The application protocol does not have to know about it. The cost is added latency and complexity, and the benefit is that the receiver can never be overrun regardless of its instantaneous load.

There is also a buffer-sizing angle. If the receiver's buffer is large enough to absorb the worst-case burst, flow control may not be needed at all. That is often the simplest fix, but it trades memory for robustness, and in a memory-constrained embedded system it may not be available. The right answer depends on the worst-case burst size and the receiver's worst-case service latency, both of which should be measured rather than assumed.

- How would you size the high-water and low-water marks for RTS/CTS flow control, and what happens if they are set incorrectly?
- If you add a sliding-window layer above the UART, how do you handle the case where the acknowledgment itself is lost?

## Q4: How would you approach choosing between a star topology and a daisy-chain topology for a multi-drop sensor network in a medical device, given that the sensors are physically distributed?

**Answer:** The choice is driven by a small number of physical and system-level constraints, and the right answer usually falls out once those are made explicit.

The first constraint is the electrical one. A star topology — a central hub with a separate point-to-point link to each sensor — gives each link its own impedance environment, its own termination, and its own noise coupling. That makes each link easier to design and easier to debug, because a fault on one link does not affect the others. The cost is that the hub needs a separate transceiver and connector per sensor, and the cabling is longer in total because every run goes back to the center. A daisy-chain topology — sensors tapped off a single bus — uses one transceiver at the controller and one cable that runs past every sensor, which is cheaper in cabling and connector count, but every sensor sees the same bus, so a fault or a misbehaving node can affect the whole network. It also imposes stub-length limits: each tap off the main bus is a stub, and stubs cause reflections that degrade signal integrity at higher bit rates. The longer the stub and the faster the bit rate, the worse the problem.

The second constraint is the physical layout. If the sensors are distributed along a line — say, along a patient bed or a piece of equipment — a daisy-chain follows the physical layout naturally and minimizes cable length. If they are clustered around a central point, a star is more natural. If the layout is a mix, a hybrid (a few daisy-chained clusters, each star-connected to the hub) is often the best answer, and it is worth considering rather than treating the two as mutually exclusive.

The third constraint is fault tolerance and serviceability. In a medical device, the ability to isolate a fault matters. In a star topology, if one sensor fails, the others keep working, and the failed link can be diagnosed independently. In a daisy-chain, a shorted or failed node can bring down the whole bus, and locating the fault requires either a physical inspection or a time-domain reflectometry approach. If the system has a requirement that a single sensor failure must not take down the network, that pushes toward a star or a segmented daisy-chain with isolation. If the system can tolerate a bus-wide outage and the priority is cost and cabling simplicity, a daisy-chain is acceptable.

The fourth constraint is the protocol. A multi-drop bus like RS-485 or CAN-FD is naturally daisy-chained, and the protocol has to handle arbitration and addressing. A star topology with point-to-point links can use simpler protocols (UART, SPI) because there is no shared medium to arbitrate. If the protocol is already chosen, it may constrain the topology — or vice versa.

In practice, I would start by laying out the sensors on a diagram, then overlay the cable routing, then check the stub lengths and bit rate against the signal-integrity budget, and then check the fault-tolerance requirement. The topology that satisfies all four is usually obvious by that point.

## Q5: How would you approach handling a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** The first priority is to separate the technical problem from the process problem, because they need different responses and conflating them makes both worse.

On the technical side, the immediate question is: what is the actual defect, and what is the minimum change that fixes it without introducing new risk? Regulatory testing is not the place to redesign a protocol. The fix should be as narrow as possible, and it should be verified against the same test that caught the problem, plus a regression set that covers the rest of the protocol. If the defect is in a corner of the protocol that is not exercised by the rest of the test suite, that is itself a finding — the test coverage has a gap, and it should be closed as part of the fix.

On the process side, the question is: how did this get through design review, unit testing, and integration testing, and only surface at compliance testing? That is almost never a single person's failure. It usually means one of a few things: the protocol specification was ambiguous or incomplete, so the engineer implemented a reasonable interpretation that happened to be wrong; the review process did not include someone who understood the regulatory requirements for that interface; or the test coverage was focused on "does it work" rather than "does it meet the standard." The right response is to fix the process gap, not to assign blame. A junior engineer implementing a protocol incorrectly is a normal event; a system that lets it reach compliance testing undetected is the actual problem.

In terms of how I would handle the conversation with the engineer: I would be direct about the impact — schedule delay is real and the team feels it — but I would frame it as a shared problem to solve, not a personal failing. The engineer needs to understand why the defect matters and what the correct behavior is, and they need to be part of the fix, because that is how the learning sticks. If the response is to take the work away from them, they learn nothing and the team loses capacity. If the response is to blame them, they become defensive and hide future problems, which is far more dangerous in a regulated environment.

I would also look at the schedule impact honestly. A significant delay at compliance testing is often recoverable if the fix is narrow and the test house can re-run the affected tests without re-running everything. That is a conversation to have early, with the test house and with the project lead, rather than waiting until the fix is complete. The worst outcome is to discover after the fix that the re-test window is weeks away.

Finally, I would feed the lesson back into the design review checklist and the test plan, so that the same class of defect is caught earlier next time. In a medical device program, the compliance test is the last line of defense, not the first, and every defect that reaches it should tighten the earlier stages.

- What would you change in the design review process to catch protocol defects earlier, without adding so much review overhead that the team slows down?
