# protocols — Day 98

## Q1: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The core idea is to separate *what* a sensor transaction means from *how* it is physically carried. I would define a transport-agnostic interface at the boundary between application logic and the physical layer — something like a small set of operations: open/configure, read register, write register, read block, write block, and a status/error return. Each physical transport implements this interface in its own driver module, translating the generic operations into the specific framing that transport requires (a register address plus repeated-start for I2C, a command byte plus dummy clocks for SPI, a framed packet for UART or CAN-FD). The application and the sensor-specific logic then only ever call the generic interface.

The important design decisions are: (1) keep the interface *semantic*, not byte-oriented — if the abstraction leaks "here is a buffer of raw bytes," the application ends up knowing transport details anyway; (2) define a single, transport-neutral error model (timeout, NACK/no-response, CRC/framing error, busy) so callers handle failures uniformly; (3) put timing and retry policy in the transport layer, since retry semantics differ wildly between, say, an I2C NACK and a CAN-FD lost-arbitration event; and (4) make the interface testable by providing a mock transport so sensor logic can be unit-tested without hardware. For a medical device this also helps traceability — the same sensor driver can be verified once and reused across transports, and the abstraction boundary is a natural place to document the interface control.

**Possible follow-ups:** Where would you put end-to-end integrity checking — in the abstraction layer or in each transport driver? How would you handle a transport that has no concept of a "register," like a streaming UART sensor?

## Q2: You're debugging an I2C bus where communication works reliably at 100 kHz but produces intermittent NACKs at 400 kHz, with the same devices and the same PCB. How would you approach this?

**Answer:** Same hardware, same devices, only the rate changed — so the first hypothesis is that something that had margin at 100 kHz has lost it at 400 kHz. I would work through the physical layer first, because that's where the rate dependence bites hardest. Bus capacitance and pull-up strength: at 400 kHz the rise time budget is roughly a quarter of what it is at 100 kHz, so a bus that was marginal-but-passing at 100 kHz can fail to reach the logic-high threshold in time at 400 kHz. I'd scope SDA and SCL and look at rise times against the fast-mode spec, and check the effective pull-up (parallel combination of all pull-ups on the bus) against the total bus capacitance.

Next, I'd look at whether the NACKs correlate with a specific device or a specific transaction type — a NACK on address means the slave didn't recognize or couldn't respond in time; a NACK on data can mean the slave is busy. Some devices legitimately need clock stretching and can't service a request within the faster frame; if the master's timeout is tight, that surfaces as a NACK or a bus error. I'd also check for marginal setup/hold at the slave pins, series termination on the lines, and whether long stubs or connector transitions are adding reflections that only matter at the higher edge rate. Finally I'd confirm the master's actual SCL frequency and duty cycle — some peripherals produce a faster-than-expected clock or asymmetric duty at the higher setting. The fix is usually a combination of stronger/appropriate pull-ups, reducing bus capacitance or stub length, and honoring clock stretching.

**Possible follow-ups:** How would you distinguish a rise-time problem from a clock-stretching problem using only a scope? What would you change first if you couldn't touch the PCB?

## Q3: You're debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward. How would you approach this?

**Answer:** Bus-off means the node's transmit error counter crossed the threshold — the controller decided it had caused too many errors and removed itself from the bus. The fact that the bus looks healthy *afterward* tells me the fault is intermittent and probably local to that node or its interaction with the bus, not a permanently broken wire. I'd start by capturing the error counters and the error state transitions over time, and correlating bus-off events with what else is happening: a particular message being transmitted, a temperature or supply condition, a connector being disturbed, or a specific other node coming online.

Common root causes I'd investigate: (1) a physical-layer problem local to that node — a marginal transceiver, a bad termination or stub at that drop, a ground offset pushing common-mode out of range, so its own transmissions are corrupted and it accumulates transmit errors; (2) a bit-timing mismatch — the node's sample point or SJW doesn't match the rest of the network, so it misreads frames under certain conditions and generates error frames; (3) the node transmitting into a bus that is momentarily disturbed (another node's fault, a hot-plug event); (4) firmware that doesn't implement automatic bus-off recovery, so once it goes off it stays off by design until reset. I'd separate "why did it go bus-off" from "why didn't it recover" — the second is often just a missing recovery policy. The fix is usually physical-layer (termination, grounding, transceiver) plus a deliberate, standards-compliant recovery strategy with logging so the event is visible.

**Possible follow-ups:** What does the CAN error-counter model tell you about whether the fault is on transmit or receive? How would you design bus-off recovery so it's safe in a medical device rather than just auto-resetting blindly?

## Q4: In a system where an SPI master talks to several slaves at different clock speeds and with different CPOL/CPHA modes, how would you approach structuring the firmware so that mode and speed changes are handled safely?

**Answer:** The risk is that mode and speed are properties of the *bus configuration*, not of an individual transfer, so if you change them carelessly you can corrupt the transaction in flight or leave a slave seeing edges it doesn't expect. I'd structure the firmware around a bus-manager layer that owns the SPI peripheral configuration and serializes all access. Each slave gets a descriptor that declares its required CPOL/CPHA and maximum clock, and the bus manager reconfigures the peripheral to match *before* asserting that slave's chip select, and only when the configuration actually differs from the current state — avoiding needless reconfigures that can glitch the clock.

Key practices: (1) never change mode or speed while any chip select is asserted; deassert, reconfigure, then assert; (2) insert the required setup/hold time around chip-select edges, since some slaves need a minimum CS-to-clock delay; (3) keep a "current configuration" shadow so the manager knows whether a change is needed; (4) make the whole transfer atomic from the caller's perspective — the caller asks "read these registers from slave N" and the manager handles mode/speed/CS sequencing; and (5) if the MCU supports per-transfer configuration in its SPI peripheral (many do), use it so the hardware applies the change cleanly at the frame boundary rather than in firmware with timing gaps. I'd also verify on a scope that mode changes don't produce runt clocks or CS glitches, because those are the classic failure mode.

**Possible follow-ups:** What would you do if two slaves needed the same chip select but different modes? How would you handle a slave that requires a mode change mid-transaction?

## Q5: How would you handle a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** My first priority is to contain the problem and protect the patient-facing and regulatory consequences, then fix the process so it doesn't recur — blame is not the useful frame here. Concretely: I'd get the team together to characterize the defect precisely — what the protocol does versus what the spec requires, what test exposed it, and whether it's a functional-safety issue or a documentation/traceability gap — because those have very different remediation paths. I'd involve the regulatory lead early to understand what re-testing and documentation impact looks like, and I'd resist the temptation to quietly patch and re-run without assessing whether the same class of error exists elsewhere in the protocol implementation.

On the people side, I'd talk with the junior engineer privately and factually, focused on understanding how the error escaped review and test rather than on fault. In my experience these escapes usually point at a process gap — missing protocol conformance tests, an ambiguous spec, or a review that didn't cover the protocol state machine — and framing it that way keeps the engineer engaged in the fix instead of defensive. Then I'd put concrete guardrails in place: a protocol conformance test plan that exercises normal and fault conditions, a review checklist for protocol implementations, and traceability from protocol requirements to tests so the next gap is caught before compliance testing. I'd also make sure the schedule recovery plan is honest and communicated upward rather than absorbed silently by the team.

**Possible follow-ups:** How would you decide whether to fix forward or roll back the protocol implementation under schedule pressure? What would you change in the review process so a protocol defect is caught before compliance testing next time?
