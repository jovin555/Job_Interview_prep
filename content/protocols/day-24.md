## Q1: How would you approach designing a fail-safe mechanism for a UART-based communication link in a medical device where a sensor must never be left in an unknown state if the main controller resets or loses power mid-transaction?

**Answer:** The core concern here is that a partial or interrupted UART transaction could leave the sensor in an indeterminate configuration state, which is unacceptable in a medical context. My approach would be multi-layered. First, at the protocol level, I'd design every transaction to be idempotent and self-describing — each message should carry a command identifier, a sequence number, and a length field so the receiver can detect and discard incomplete or out-of-order frames. I'd also include a checksum or CRC to reject corrupted frames. Second, I'd implement a state machine on the sensor side that has a defined "safe state" it returns to on any error condition, timeout, or invalid sequence — never leaving it in a partially configured mode. Third, I'd add a hardware-level safeguard: a dedicated reset line or a "ready" handshake signal from the controller that the sensor monitors. If the controller resets, this line de-asserts, and the sensor immediately reverts to its default safe state. Finally, I'd consider a watchdog mechanism — either a hardware watchdog on the sensor or a periodic "heartbeat" command from the controller — so that if the link goes silent for longer than a defined interval, the sensor autonomously transitions to its safe state. The key design principle is that the sensor must have a deterministic response to every possible failure mode, and that response must be the safe state.

**Possible follow-ups:** How would you handle the case where the sensor is in the middle of a multi-byte write when the controller resets? What if the sensor itself needs to initiate communication — how does the fail-safe design change?

## Q2: You're debugging a system where an RS-485 network works reliably at 9600 baud but experiences intermittent corruption at 115200 baud. The cable run is approximately 150 meters with 12 nodes. How would you approach this?

**Answer:** This is a classic symptom of signal integrity issues that only manifest at higher data rates. At 115200 baud, the bit period is roughly 8.7 microseconds, so any reflections, ringing, or skew that was negligible at 9600 baud now becomes significant. I'd approach this systematically. First, I'd verify the physical layer fundamentals: check that termination resistors are correctly placed at both ends of the bus, with values matching the cable's characteristic impedance (typically 120 ohms for RS-485). I'd also check for unterminated stubs — any node connection that branches off the main bus creates a reflection point, and at higher baud rates even short stubs can cause problems. Second, I'd examine the cable itself: is it twisted-pair with proper shielding? Is the shield grounded at one end only? Third, I'd look at the transceiver characteristics — some transceivers have slower slew rates that help with EMI but may limit maximum baud rate over long distances. Fourth, I'd check the common-mode voltage range: at 150 meters, ground potential differences between nodes can be significant, and at higher baud rates the receiver's common-mode rejection becomes more critical. I'd verify that fail-safe biasing is present to keep the bus in a defined state when no node is driving it. Finally, I'd use an oscilloscope to look at the actual waveform at the farthest node — checking for overshoot, undershoot, and whether the signal crosses the receiver's threshold at the correct time. The fix might be as simple as adjusting termination, adding biasing resistors, or it might require a different transceiver with better slew-rate control.

**Possible follow-ups:** How would you determine whether the issue is reflections versus ground potential differences? What if the corruption only occurs when a specific node transmits — how does that change your debugging approach?

## Q3: How would you approach implementing a deterministic scheduling scheme for a mixed-protocol medical device that uses I2C for sensor reads, SPI for high-speed data logging, and UART for a user interface, all on a single microcontroller running Zephyr RTOS?

**Answer:** The key challenge is ensuring that each protocol's timing requirements are met without one starving the others, while maintaining system responsiveness. In Zephyr, I'd structure this around the concept of prioritized work queues and interrupt-driven peripheral handling rather than blocking polling loops. For the I2C sensor reads, which are typically periodic and low-bandwidth, I'd use a timer-driven thread at a fixed rate, but I'd make the actual I2C transactions interrupt-driven using Zephyr's asynchronous I2C API — the thread initiates the transfer and then blocks on a semaphore, allowing other work to proceed while the hardware handles the bus. For SPI data logging, which is higher bandwidth and potentially bursty, I'd use DMA-based transfers with a dedicated thread that has a higher priority, and I'd use a ring buffer to decouple the SPI driver from the data source. The UART user interface is typically event-driven and low-priority, so I'd use interrupt-driven reception with a message queue to a low-priority thread. The critical piece is the scheduling policy: I'd assign thread priorities based on the consequences of missing deadlines — sensor reads might be time-critical for patient monitoring, so they get higher priority than UI updates. I'd also use Zephyr's timing mechanisms carefully: for the I2C reads, I'd use a deadline-based approach where the thread wakes up at the scheduled time, initiates the transfer, and if it doesn't complete within a bounded time, it logs an error and moves on rather than blocking indefinitely. For the SPI logging, I'd implement flow control — if the data source is producing faster than the SPI can write, I'd either drop non-critical data or signal the source to slow down, depending on the application requirements. I'd also consider using Zephyr's work queue for short, non-blocking tasks and reserve threads for operations that must block. The overall goal is to make the scheduling deterministic — each protocol's timing requirements are analyzed, priorities are assigned accordingly, and the system is tested under worst-case load to verify that no deadline is missed.

**Possible follow-ups:** How would you handle the case where an I2C sensor clock-stretches longer than expected, potentially delaying other tasks? How would you verify that your scheduling scheme meets all timing requirements?

## Q4: How would you approach selecting between I2C and SPI for a new sensor interface in a battery-powered medical device where the sensor is on a separate PCB connected by a 15-centimeter flex cable, and the sensor must wake from sleep periodically to take a measurement?

**Answer:** This is a trade-off analysis that touches on power, signal integrity, and system complexity. Let me walk through the key considerations. For power: I2C typically has higher pull-up resistor values (which means lower current draw when the bus is idle), but both buses can be powered down or put into low-power states when not in use. The bigger power consideration is the sensor's wake-up mechanism — with I2C, the sensor can be addressed at any time, but with SPI, you typically need a dedicated chip-select line that must be asserted to wake the sensor, which means an extra GPIO on the controller. For signal integrity over a 15-centimeter flex cable: SPI at moderate clock rates (1–5 MHz) is generally more robust because it's a synchronous protocol with a dedicated clock line, and the higher drive strength of SPI outputs can overcome cable capacitance more easily. I2C's open-drain architecture with pull-up resistors can be problematic over longer cables because the RC time constant of the pull-up resistor and cable capacitance limits the maximum bus speed — at 15 centimeters, this is manageable but still a consideration. For the flex cable specifically, I'd be concerned about crosstalk between adjacent traces — SPI has more lines (SCLK, MOSI, MISO, CS) which increases crosstalk risk, but the synchronous nature means timing margins are more forgiving. I2C has fewer lines (SDA, SCL) but is more susceptible to noise on the open-drain lines. For the wake-from-sleep requirement: I2C has an advantage in that the sensor can be woken by an address match, whereas SPI requires the chip-select line to be asserted, which means the controller must have a GPIO dedicated to that purpose. However, SPI's chip-select can also serve as an interrupt line from the sensor, which can be useful. Ultimately, I'd lean toward SPI for this application if the sensor supports it, because the synchronous nature and stronger drive are better suited to the flex cable, and the power management can be handled with careful GPIO control. But I'd also consider the sensor's specific requirements — if the sensor only supports I2C, or if the sensor has a very low standby current that's easier to achieve with I2C's pull-up architecture, that could tip the balance. I'd also factor in the controller's available peripherals — if the controller has limited SPI peripherals but multiple I2C peripherals, that might simplify the design.

**Possible follow-ups:** How would you handle the flex cable's impedance and shielding considerations for either protocol? What if the sensor needs to be addressed by two different controllers — does that change your selection?

## Q5: Imagine you're leading a design review where a junior engineer proposes using a single I2C bus at 400 kHz to connect five sensors, a real-time clock, and an EEPROM, all on a 30-centimeter PCB with long traces. The engineer argues that the bus capacitance is within the 400 pF limit. How would you guide the team to evaluate this approach?

**Answer:** I'd start by acknowledging that the engineer has done the right first step — checking the bus capacitance against the I2C specification limit. But I'd guide the team to look beyond just the raw capacitance number. First, I'd ask about the actual capacitance calculation: the 400 pF limit is a maximum, not a target — at 400 kHz, you need to consider the rise-time requirements, which are typically 300 nanoseconds maximum for fast mode. The pull-up resistor value must be chosen to achieve that rise time with the actual bus capacitance, and at 400 pF, you'd need pull-ups in the range of 750 ohms or lower, which increases current draw — a significant concern in a battery-powered device. Second, I'd ask about the physical layout: 30-centimeter traces on a PCB are quite long, and I'd want to know the trace width, spacing, and whether there are vias or connectors that add capacitance. I'd also ask about the sensor's individual input capacitance and whether any of them have higher-than-typical values. Third, I'd raise the issue of signal integrity beyond just capacitance: long traces on a PCB can act as antennas, picking up noise that can corrupt I2C transactions, especially in a medical device that might be near other equipment. Fourth, I'd ask about the failure modes: with seven devices on the bus, if any one device fails in a way that holds SDA or SCL low, the entire bus is dead — that's a single point of failure for all seven devices. I'd also ask about address conflicts: five sensors might have address conflicts that require address muxing or additional hardware. Finally, I'd ask about the system-level implications: what happens if the bus is slow due to clock stretching from one device? Does that affect the timing requirements of other devices? My guidance would be to consider a more distributed architecture — perhaps splitting the devices across two I2C buses, or using a different protocol like SPI for the higher-bandwidth sensors. The key point is that meeting the capacitance limit is necessary but not sufficient — you need to consider power, signal integrity, reliability, and system-level robustness.

**Possible follow-ups:** How would you calculate the actual pull-up resistor values needed for this configuration? What would you propose as an alternative architecture, and how would you justify it?
