# protocols — Day 103

## Q1: How would you approach debugging an I2C bus where transactions succeed at 100 kHz but intermittently fail with arbitration-lost errors at 400 kHz, even though there is only one master on the bus?

**Answer:** Arbitration-lost errors on a single-master bus are a red flag, because true multi-master arbitration shouldn't be happening at all. The first thing I'd suspect is that the controller is misinterpreting a bus condition as arbitration loss — commonly a glitch on SDA or SCL that the peripheral samples as another device pulling the line low while it drives high. At 400 kHz the timing margins shrink, so a marginal rise time, excessive bus capacitance, or a slow/weak pull-up can produce edges that look like contention. I'd start by scoping SDA and SCL at the failing speed and looking at rise/fall times against the fast-mode spec, checking whether the pull-ups are sized for the actual capacitance (including trace and connector capacitance, not just the datasheet device count). I'd also check for a slave that briefly drives the bus outside its expected window — for example a device that holds SDA during a repeated start or stretches in a way the master doesn't tolerate. Another common cause is a slave that isn't fully fast-mode capable and produces marginal AC timing at 400 kHz. I'd isolate by dropping to a single slave at a time, then reintroducing devices, and by substituting a known-good master or a bus analyzer to see whether the "arbitration loss" is real contention or a sampling artifact. Finally, I'd verify the controller's input filtering and spike-suppression settings — some peripherals have configurable digital filters that need to be tuned for the higher speed.

**Possible follow-ups:** If the scope shows clean edges but the error persists, what would you check next in the controller configuration? How would you distinguish a genuine second master (e.g., a stray device or a debug tool) from a false arbitration report?

## Q2: How would you approach designing the electrical layer of an RS-485 link that must survive a fault where one node's transceiver fails and holds the bus in a permanent dominant state?

**Answer:** A stuck-dominant driver is one of the nastier RS-485 failure modes because it silences the entire bus — no other node can transmit, and depending on the receiver thresholds, everyone may read a continuous break-like condition. The design approach has to combine prevention, detection, and containment. On prevention: use transceivers with thermal shutdown and current limiting, add series resistors or a PTC in the driver path to limit fault current, and make sure the driver-enable is actively controlled by firmware with a defined default (disabled) at power-up and reset, so a crashed MCU releases the bus rather than holding it. On detection: the protocol layer should include a bus-idle or heartbeat monitor — if a node sees the bus held dominant longer than the maximum legal frame time, it flags a bus fault. On containment: you can't electrically force a failed transceiver to release the bus, so the practical answer is segmentation — partition the network into segments with a repeater or hub so a single stuck node only takes down its segment, and provide a way to isolate a segment (a controlled switch or the repeater's own fault handling). For a medical device specifically, I'd also want the fault to be detectable and annunciated rather than silently degrading, and I'd design the protocol so that loss of the bus triggers a defined safe state on each node rather than leaving actuators in an unknown condition. I'd validate all of this with a fault-injection test: deliberately hold one node's driver enabled and confirm the rest of the system detects it, isolates it, and enters the intended safe state.

**Possible follow-ups:** How would the fail-safe biasing interact with a stuck-dominant fault — could it mask or worsen the detection? What would you put in the protocol to distinguish a stuck bus from a very long legitimate frame?

## Q3: How would you approach structuring a firmware architecture so that a single application layer can drive sensors over I2C, SPI, UART, and CAN-FD without the application code knowing which transport is underneath?

**Answer:** The core idea is to separate *what* a sensor needs (a command/response or streaming semantic) from *how* it gets there (the transport). I'd define a transport-agnostic device interface — something like open/close, read register, write register, and a streaming read — expressed in terms of the sensor's logical operations, not bus primitives. Each physical transport implements that interface as a driver: the I2C driver knows about addresses and repeated starts, the SPI driver knows about chip selects and CPOL/CPHA, the UART driver knows about framing and flow control, and the CAN-FD driver knows about message IDs and DLC. Above that, a thin device layer maps a specific sensor's register map and semantics onto the generic interface, so the application talks to "the pressure sensor" and never sees a bus handle. The important design decisions are: keep the interface narrow and synchronous-or-async consistent (mixing blocking and callback styles across transports is where these layers rot), push error semantics up in a transport-neutral form (timeout, NACK, CRC failure, bus fault) rather than leaking raw peripheral error codes, and make the transport binding a compile-time or init-time choice so the same application binary can be built for different hardware variants. For testability, I'd provide a mock transport so the device and application layers can be unit-tested without hardware, and I'd keep timing/latency expectations documented per transport so the application doesn't accidentally assume CAN-FD latency when running over I2C. In an RTOS like Zephyr this maps naturally onto the device driver model plus a service layer, but the pattern holds bare-metal too.

**Possible follow-ups:** How would you handle a sensor that has genuinely different capabilities depending on the transport (e.g., streaming only possible over SPI)? Where would you put retry logic — in the transport driver or the device layer — and why?

## Q4: How would you approach guaranteeing that a high-priority safety-critical CAN-FD message is never delayed beyond a bounded time when lower-priority telemetry shares the same bus?

**Answer:** The guarantee comes from worst-case response-time analysis, not from hoping the higher bit rate solves it. CAN arbitration is priority-based and non-preemptive once a frame starts, so the worst case for a high-priority frame is: it becomes ready just after a lower-priority frame has won the bus, and it must wait for that frame to finish, plus any higher-or-equal-priority frames already queued ahead of it. So the analysis has three parts. First, bound the *blocking time*: the longest lower-priority frame that can be in progress when our message becomes ready — this is where CAN-FD's longer payloads hurt, because a 64-byte telemetry frame occupies the bus far longer than a classic 8-byte frame, so I'd cap telemetry payload sizes or split them to keep the maximum frame time small. Second, bound the *queuing delay* from higher-or-equal-priority traffic — sum the transmission times of all higher-priority frames that can be released in the busy period, iteratively, since releases can cascade. Third, add the message's own transmission time and account for error frames and retransmission (a single error can add a full frame time, so the analysis must include a retransmission allowance). Design levers: assign the safety message the highest ID, keep its payload short so its own frame time is minimal, constrain telemetry frame sizes and rates, and consider a time-triggered or scheduled-window scheme (or a higher-layer token/round-robin) if pure priority arbitration can't meet the bound. I'd validate with bus-load stress testing and worst-case injection — deliberately saturating the bus with telemetry and measuring the safety message's latency distribution, including under induced error frames — rather than trusting the arithmetic alone.

**Possible follow-ups:** How does the CAN-FD data-phase bit rate change the blocking-time calculation compared to classic CAN? If the analysis shows the bound can't be met with the current telemetry load, what would you change first and why?

## Q5: You're leading a design review where a junior engineer proposes a custom application-layer protocol over UART for a medical device, and you notice the framing has no length field validation and no sequence numbers. How would you guide the team to evaluate and improve the design?

**Answer:** I'd frame this as a constructive review, not a takedown — the goal is to get the team to see the failure modes themselves. I'd start by asking the engineer to walk through what happens on a single bit error, a dropped byte, or a receiver that resets mid-frame: without a validated length field, a corrupted length can cause the receiver to swallow subsequent valid frames as payload, and without sequence numbers there's no way to detect a lost or duplicated frame or to distinguish a stale frame from a fresh one. I'd then connect that to the medical context — the consequence isn't just a dropped packet, it's silently wrong data reaching a clinical decision, which is exactly the kind of hazard the risk file and IEC 60601 / ISO 14971 thinking is meant to catch. From there I'd guide the team toward a concrete fix set: a start delimiter plus a length field protected by its own checksum (or a fixed-length header with a header CRC), a whole-frame CRC, sequence numbers with a defined wrap and resync behavior, and an explicit resynchronization strategy (scan for delimiter, discard until a valid header+CRC is found). I'd also raise the process point: this is the kind of defect that surfaces late in compliance testing if it isn't caught in design review, so I'd want the protocol spec to include a fault-injection test plan — bit flips, truncation, duplication, reordering — as part of the design deliverable. The tone matters: I'd credit the parts of the design that are sound, make the review a shared risk-analysis exercise, and assign the engineer to own the revised spec so it's a learning outcome rather than a reprimand.

**Possible follow-ups:** How would you decide between a fixed-length header with a header CRC versus a delimiter-plus-length scheme? What would you put in the fault-injection test plan to prove the resynchronization actually works?
