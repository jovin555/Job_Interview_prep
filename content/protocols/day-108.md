# protocols — Day 108

## Q1: How would you approach debugging an I2C bus where a slave device occasionally stretches the clock longer than the master's timeout allows, causing the master to abort mid-transaction and leave the bus in an inconsistent state?

**Answer:** I'd start by separating the two problems: the slave's stretching behavior and the master's recovery behavior. First, characterize the stretch — scope SCL and SDA together and measure how long the slave actually holds SCL low, and under what conditions (which register access, which operating mode, temperature, supply voltage). Datasheets often quote a typical stretch time but the worst case can be much longer, especially for sensors doing an internal conversion or calibration on a specific command. If the stretch is legitimate and within the slave's spec, the fix belongs on the master side: increase the timeout to cover the documented worst case plus margin, or restructure the transaction so the master doesn't block on a long conversion — issue the trigger, release the bus, and come back later to read the result. If the stretch is longer than the slave should ever produce, that's a slave-side or signal-integrity issue: check whether SCL is being pulled low by noise, whether the pull-up is too weak for the bus capacitance (slow rise time can look like stretching), and whether the slave is browning out. Second, the inconsistent-state problem: a master that aborts mid-transaction must not just return an error and walk away. The recovery path should issue a defined bus-clear sequence — typically up to nine clock pulses with SDA released so any slave mid-byte can finish and let go, followed by a STOP condition — then verify the bus is idle (both lines high) before the next transaction. I'd also make the driver mark the affected transaction as failed and retry at the application layer rather than silently resuming, because a half-completed read may have left the slave's internal pointer in an unknown place. In a medical device context, the recovery must be bounded and observable: log the event, count it, and if it exceeds a threshold, surface it as a fault rather than retrying forever.

**Possible follow-ups:** How would you distinguish clock stretching from a slave holding SDA low, and does the recovery sequence differ? What would you change in the driver architecture so a long conversion doesn't block the whole bus?

## Q2: How would you approach selecting between independent chip selects and a daisy-chain SPI configuration for connecting several sensors in a medical device where PCB space is limited but the sensors have different clock polarity and phase requirements?

**Answer:** The CPOL/CPHA requirement is close to a deciding factor here. In a true daisy-chain, all devices share one chip select and one clock, so every device on the chain sees every bit shifted through — which means they must all agree on the same SPI mode and effectively the same clock rate. If the sensors genuinely need different modes, daisy-chain is the wrong topology unless you insert logic or re-clock between stages, which defeats the space savings. So I'd first confirm whether the mode differences are real or just conservative datasheet defaults — many parts support multiple modes and the constraint may be softer than it looks. Assuming they're real, independent chip selects are the straightforward answer, and the space cost is usually modest: one GPIO per slave, and if pins are tight you can use a small decoder or an I/O expander to generate the selects, at the cost of a little latency and one more device to manage. The trade-offs I'd lay out for the team: independent CS gives per-device mode and clock freedom, simpler fault isolation (a dead slave doesn't block the chain), and easier bring-up; daisy-chain saves pins and routing but serializes access, complicates fault isolation, and locks everyone to one mode. For a medical device I'd also weigh what happens at power-up and reset — with independent selects, an undriven CS can float and accidentally select a device, so each needs a pull-up or pull-down to its inactive state, and that has to be verified during bring-up. I'd also check MISO contention: with independent selects, only one slave should drive MISO at a time, and any slave that tri-states slowly can glitch the bus, so I'd review the timing in the datasheets.

**Possible follow-ups:** If you use a decoder for the chip selects, what failure modes does that introduce compared to direct GPIOs? How would you handle a slave whose CS setup time is longer than the others?

## Q3: You're debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward. How would you approach this?

**Answer:** Bus-off means the controller's transmit error counter crossed its limit, so the node accumulated errors faster than it recovered — the bus looking healthy afterward is expected, because the node has removed itself from the network. The question is what drove the counter up. I'd start by capturing the error counters and the controller's error state over time, plus the specific error types (bit error, stuff error, CRC error, ACK error, form error) if the controller exposes them. The pattern of which error dominates points at the cause: ACK errors suggest the node is transmitting when no one else is listening or the bit timing is off; bit errors suggest a physical-layer or termination problem, or a node transmitting into a dominant bit it didn't expect; stuff/CRC errors suggest noise or a marginal signal. I'd also check whether the node is the only transmitter at the moment of failure — a lone transmitter with no ACK will retry and accumulate errors quickly. On the physical side: termination and stub length, common-mode range, ground offsets between nodes, and whether the bit timing (including the data-phase sample point in CAN-FD) is correctly configured for the actual bus length and transceiver delays. CAN-FD makes this sharper because the data phase runs much faster, so sample-point and propagation-delay margins that were fine at classic rates can fail. Then the recovery behavior: many controllers require an explicit re-initialization after bus-off, and if the firmware doesn't implement the recovery sequence (wait for the bus-idle condition, then re-init), the node stays off. I'd make sure the recovery is implemented, bounded, and logged, and that a node coming back doesn't immediately re-offend — a backoff or a diagnostic counter helps. Finally, I'd ask whether the node should be transmitting at all in that state; in a medical device, a node that keeps going bus-off is a fault condition that should be reported, not silently retried forever.

**Possible follow-ups:** How would you tell apart a termination problem from a bit-timing problem using only the error counters? What does the CAN-FD data-phase sample point change about your debugging approach?

## Q4: How would you approach implementing flow control on a UART link where the receiver occasionally cannot keep up with the transmitter, but the protocol has no built-in backpressure mechanism?

**Answer:** I'd treat it as two layers: what the hardware can do and what the protocol must add. At the hardware level, if RTS/CTS lines are available, use them — hardware flow control is the cleanest fix because the receiver deasserts CTS before its FIFO overflows, and the transmitter stops mid-stream without any software involvement. If the lines aren't there, the options are software flow control (XON/XOFF) or a protocol-level credit/ack scheme. XON/XOFF is simple but fragile: the flow-control characters can appear in binary payloads, and if a character is lost the link can deadlock, so it needs escaping or a restricted payload alphabet. A credit-based or sequence-number-plus-ack scheme is more robust: the receiver advertises how much buffer it has, the transmitter never sends more than that, and the receiver acks as it drains. That also gives you retransmission on loss, which XON/XOFF doesn't. I'd also look at why the receiver can't keep up — is it a FIFO depth issue, an interrupt latency issue, or is the transmitter simply faster than the link budget allows? Sometimes the right answer is to size the receiver buffer and DMA properly rather than add flow control. In a medical device, I'd want the flow-control mechanism to fail safe: if the ack or credit stops arriving, the transmitter must stop and report a fault rather than keep pushing and silently dropping data, and the receiver must be able to detect a stalled link and recover. I'd also make sure the flow-control state is reset cleanly on either side's restart, because a stale credit count after a reset is a classic source of overrun.

**Possible follow-ups:** How would you handle the case where the receiver resets mid-stream and the transmitter still thinks it has credits? What's the trade-off between a larger receive buffer and adding flow control?

## Q5: You're leading a design review where a junior engineer proposes using a single UART with a software-based protocol multiplexer to communicate with four different sensors, each with different baud rates and protocols. The hardware engineer argues this is unreliable and wants four separate UART peripherals. How would you guide the team to evaluate this approach?

**Answer:** I'd frame it as a requirements question before a technology question, and get both engineers to agree on the criteria. The key axes are: how often does each sensor need to be serviced, how tight is the latency on each, what happens if a transaction is delayed or corrupted, and how much pin/board budget is actually available. A software multiplexer on one UART means the port is reconfigured between baud rates and protocols, so every switch costs time and creates a window where a byte can be lost or a frame misaligned — and if two sensors need to be serviced concurrently, one waits. That's often acceptable for slow, polled sensors and unacceptable for anything with a real-time or safety-critical read. I'd ask the junior engineer to show the timing budget: worst-case time to switch, worst-case transaction time per sensor, and the resulting latency for the most critical one, including the case where a lower-priority sensor is mid-transaction when a high-priority read is due. I'd ask the hardware engineer to quantify the cost of four UARTs — pins, board space, and whether the chosen MCU even has four. Then I'd look for the middle ground: maybe two UARTs, grouping sensors by baud rate and criticality, is enough and cheaper than four. I'd also insist on the failure modes being written down: what does the multiplexer do if a sensor stops responding mid-frame, and how does it guarantee the port is left in a known state before the next sensor is serviced? The goal of the review isn't to pick a winner but to make the trade-off explicit and documented, so the decision is defensible later — especially in a medical device where the rationale may be examined during design review or audit.

**Possible follow-ups:** If the timing budget shows the multiplexer meets latency but with little margin, how would you decide whether that's acceptable? How would you document this decision so it holds up in a design history file?
