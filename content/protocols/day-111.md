# protocols — Day 111

## Q1: How would you approach debugging a USB 2.0 device that works on most hosts but fails to enumerate on one specific host, where the failure appears as a control-transfer timeout during the GET_DESCRIPTOR phase?

**Answer:** I'd treat this as a host-tolerance problem first, because the device is proven functional elsewhere — the variable is the host's USB stack and its timing expectations. The enumeration sequence is fixed: reset, address assignment, then a series of control reads for device, configuration, string, and interface descriptors. A timeout during descriptor reads usually means the device is responding too slowly, returning a malformed descriptor that the host rejects and retries, or stalling a request the host considers mandatory.

My first step is to capture the actual bus traffic with a protocol analyzer on the failing host and compare it byte-for-byte against a passing host. That tells me whether the device ever ACKs the SETUP packet, how long it takes to return the data stage, and whether the host is retrying the same request. If the device is slow to respond, I'd look at firmware: is descriptor handling done in the main loop behind other work, so a busy period delays the control endpoint? Control transfers have generous but finite timeouts, and a device that services EP0 with any latency is asking for trouble. The fix is to make the control endpoint interrupt-driven and prioritized, with descriptors held in RAM and returned immediately.

If the timing looks fine but the host still retries, I'd scrutinize the descriptor contents — total length fields, bMaxPacketSize0, the configuration's wTotalLength, and whether string descriptors are present when the host asks for them. Some hosts are strict about a device that reports a max packet size of 64 on EP0 but then sends a short packet mid-descriptor, or that NACKs a request it should answer. I'd also check for a mismatch between what the device advertises and what it actually does — for example, claiming a configuration the firmware can't fully support.

Finally, I'd consider electrical and timing factors specific to that host: whether it's a root port vs. a hub, whether the host applies a shorter reset or inter-packet delay, and whether VBUS rise time or D+ pull-up timing affects the initial speed detection. A device that enumerates on a hub but not a root port often has a signal-integrity or pull-up timing issue rather than a protocol bug. The systematic approach is: capture traffic, isolate whether it's device latency, descriptor content, or electrical/timing, and fix the root cause rather than adding retries.

**Possible follow-ups:** If the analyzer shows the device ACKs the SETUP but never sends the data stage, where would you look first in firmware? How would you determine whether the host is applying a non-standard timeout versus the device genuinely being too slow?

## Q2: How would you approach calculating pull-up resistor values for an I2C bus that must support both standard-mode (100 kHz) and fast-mode (400 kHz) operation with multiple devices on the bus?

**Answer:** The pull-up value is bounded from both sides, and the job is to find the window that satisfies both bounds at the fastest speed you need to support — because the fast-mode constraint is the tighter one and, if met, standard mode is automatically satisfied.

The upper bound comes from rise time. I2C specifies a maximum rise time (roughly 1000 ns for standard mode, 300 ns for fast mode), and the bus rise is an RC curve dominated by the pull-up and the total bus capacitance: t_r ≈ 0.847 × R × C for the 30–70% portion, or you can use the vendor's rule-of-thumb R_max ≈ t_r / (0.847 × C). So I first estimate total bus capacitance: each device's pin capacitance from its datasheet, plus PCB trace capacitance (roughly 1–3 pF per cm depending on stackup), plus connector and cable capacitance if the bus leaves the board. That sum, plugged into the fast-mode rise-time limit, gives the maximum allowable pull-up.

The lower bound comes from sink current. Each device must be able to pull the line below V_OL(max) — typically 0.4 V — while sinking the current the pull-up sources plus the current from other devices on the bus. With VDD = 3.3 V and V_OL = 0.4 V, the current through the pull-up when the line is low is (3.3 − 0.4)/R, and the device's I_OL rating (often 3 mA for standard parts, sometimes 20 mA for fast-mode-capable ones) caps how small R can be. So R_min ≈ (VDD − V_OL)/I_OL. There's also a total-current sanity check: the sum of sink currents across all devices must stay within spec.

The window is then R_min ≤ R ≤ R_max, and I pick a standard value comfortably inside it — often 2.2 kΩ or 1.8 kΩ for a lightly loaded 3.3 V fast-mode bus, dropping toward 1 kΩ as capacitance grows. If the window is empty — capacitance too high for the required speed — the answer isn't a smaller resistor; it's reducing capacitance (shorter traces, fewer devices, a bus buffer/repeater, or splitting the bus). I'd also verify with a scope: measure actual rise time at the worst-case corner (highest capacitance, lowest temperature where driver strength is weakest) and confirm the eye is clean at 400 kHz. Datasheet math gets you the starting value; the scope confirms it.

**Possible follow-ups:** How would you handle a bus where the calculated window is empty because total capacitance exceeds the fast-mode limit? What role does the device's input leakage current play in the low-level margin, and when would you worry about it?

## Q3: You're debugging a CAN-FD network where a node occasionally transmits an error frame that corrupts an in-progress message from another node, but only under heavy bus load. How would you approach this?

**Answer:** An error frame that appears only under load points to a node that is losing synchronization with the bus — it's detecting a bit error, stuff error, or CRC error on a frame it should be receiving cleanly, and its error flag then destroys the frame for everyone. The load dependence is the key clue: at low load, timing margins are comfortable; at high load, arbitration is frequent, back-to-back frames leave little idle time, and any marginal behavior in one node's transceiver or bit timing surfaces.

I'd start by identifying which node is transmitting the error frames. Most CAN controllers expose error counters and a bus-error or protocol-error interrupt; I'd log the error type (bit, stuff, CRC, form, ACK) and the node ID per event. The error type narrows the cause: a stuff error on reception suggests a bit-timing or sample-point mismatch; a bit error during arbitration suggests the node is transmitting when it shouldn't; an ACK error suggests no other node is acknowledging, which can happen if the node is the only one awake or if its own transmission is malformed.

Next I'd check bit timing and sample point across all nodes. CAN-FD has two bit rates — the arbitration phase and the data phase — and each needs its own prescaler and sample point. A common failure is nodes configured with mismatched data-phase timing, or a sample point that's fine at low load but marginal when the bus is busy and propagation delay plus oscillator tolerance eat into the margin. I'd verify the oscillator tolerance (crystal vs. internal RC matters a lot here) and confirm the sample point is in the recommended 75–80% region for the data phase. I'd also check the transceiver: a marginal transceiver, a long stub, or missing termination can cause reflections that only corrupt bits when frames are long and fast — which is exactly the high-load, high-data-rate case.

I'd also look at whether the "corrupting" node is actually the victim rather than the culprit — a node that's slightly out of tolerance may be the one that can't keep up, and its error frames are a symptom of the bus, not the cause. Loopback and listen-only mode on individual nodes, plus a bus analyzer that timestamps error frames, helps separate cause from effect. The fix is usually in bit-timing configuration, termination/stub cleanup, or replacing a marginal transceiver — not in the application protocol.

**Possible follow-ups:** How would you distinguish a bit-timing mismatch from a physical-layer reflection as the root cause? What would you check first if the error frames only appear when a specific pair of nodes transmit back-to-back?

## Q4: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The goal is to invert the dependency: the application depends on an abstract sensor/transport interface, and each physical transport is an implementation behind it. I'd define a small, transport-agnostic contract — something like open/configure, a read/write of a logical register or message, and a status/error return — and make the application code call only that contract. The transport-specific details (I2C address and register map, SPI mode and chip select, UART framing, CAN-FD message IDs and DLC) live entirely inside the driver implementations.

The key design decisions are where to put the seam and how to handle the differences that don't abstract cleanly. A register-oriented interface works well for I2C/SPI sensors but maps awkwardly onto CAN-FD, which is message-oriented; so I'd likely define the abstraction at the level of "sensor operations" (read measurement, configure range, get status) rather than raw bytes, and let each transport driver translate those operations into its native transactions. That keeps the application honest — it never assumes a register model that CAN-FD doesn't have.

I'd also make error semantics uniform. Each transport has different failure modes: I2C NACKs and arbitration loss, SPI has no ACK at all, UART has framing/overrun errors, CAN-FD has error states and bus-off. The abstraction should map these into a common status enum (OK, timeout, bus error, device fault) so the application's error handling is transport-independent, while still allowing a transport-specific detail field for diagnostics.

For testability, I'd put the interface behind a function-pointer table or a thin HAL so I can substitute a mock transport in unit tests and run the same application logic against simulated I2C, SPI, and CAN-FD backends. That also lets me swap a sensor from one bus to another during development without touching application code — which is the real payoff. The trade-off to watch is over-abstraction: if the interface tries to expose every transport feature, it becomes leaky and the application starts branching on transport type, which defeats the purpose. I'd keep the contract minimal and push transport-specific tuning into configuration, not into the application.

**Possible follow-ups:** How would you handle a sensor that needs a transport-specific feature (e.g., I2C clock stretching or a CAN-FD multi-frame transfer) without leaking that detail into the application? Where would you draw the line between the abstraction layer and the sensor driver itself?

## Q5: You're leading a design review where a junior engineer proposes using a single UART with a software-based protocol multiplexer to communicate with four different sensors, each with different baud rates and protocols. The hardware engineer argues this is unreliable and wants four separate UART peripherals. How would you guide the team to evaluate this approach?

**Answer:** I'd frame this as a requirements-and-risk trade rather than a binary "reliable vs. unreliable" argument, and get both engineers to agree on the criteria before debating the solution. The criteria I'd put on the table: worst-case latency per sensor, jitter tolerance, CPU load, pin budget, PCB area, firmware complexity, and — because this is a medical device — verifiability and traceability of the communication path.

First, the facts. A single UART physically cannot run four baud rates simultaneously; a software multiplexer means time-slicing the UART, reconfiguring the baud rate and protocol between transactions. That's feasible if the sensors are polled slowly and none has a hard real-time deadline. It becomes fragile if any sensor needs deterministic latency, because a reconfiguration plus a transaction on sensor A delays sensor B, and the delay is data-dependent. So the first question to the junior engineer is: what are the actual timing requirements per sensor, and what's the worst-case latency budget? If the answer is "each sensor polled every 100 ms, no hard deadline," the multiplexer may be perfectly adequate and saves three UART peripherals and pins. If any sensor has a tight or jitter-sensitive deadline, the multiplexer is the wrong architecture regardless of how clever the software is.

Second, I'd have the hardware engineer quantify the cost of four UARTs: pin count, whether the MCU actually has four UARTs or would need an external expander, board area, and cost. Often the "four peripherals" option is cheaper than it sounds, or the MCU doesn't have them, which changes the calculus.

Third, I'd separate the reliability concern into concrete failure modes and ask how each is mitigated. Baud-rate reconfiguration glitches, framing errors during switching, buffer overruns if a sensor responds while the UART is being reconfigured — these are real, but they're testable. I'd propose a prototype or a bench test that exercises the multiplexer under worst-case load and measures error rates, rather than settling it by assertion. If the multiplexer passes with margin, the hardware engineer's concern is addressed with evidence; if it fails, the junior engineer learns where the limit is.

Finally, I'd make the decision explicit and documented: chosen architecture, the requirements it satisfies, the risks accepted, and the mitigation. In a medical device context, that record matters for design history and for the next review. The leadership point is to turn a disagreement into a shared evaluation against agreed criteria, and to let data — not seniority — decide.

**Possible follow-ups:** If the timing analysis shows one sensor has a hard deadline the multiplexer can't meet, what hybrid architecture would you propose? How would you structure the bench test so its results are credible to both engineers?
