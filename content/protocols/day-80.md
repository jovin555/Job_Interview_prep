## Q1: How would you approach debugging an I2C bus where a slave device holds SDA low after a transaction, preventing any further communication until power is cycled?

**Answer:** This is the classic "stuck bus" condition, and the first thing to establish is whether the slave is genuinely stuck or whether the master is misinterpreting the line state. I'd start by scoping SDA and SCL with a logic analyzer or scope to see exactly where in the transaction the line gets held — mid-byte, after the ACK bit, or after a stop condition that never completed. A common cause is a slave that was interrupted mid-transaction (by a reset, a glitch, or a missed clock edge) and is now waiting for more clocks to finish shifting out a bit, so it keeps SDA driven. The standard recovery is to manually clock SCL as a GPIO for up to nine pulses while SDA is released, then issue a stop condition — this lets the slave shift out its remaining bits and release the line. If that doesn't work, the slave may be in a latched fault state that only a power cycle or a dedicated reset pin clears, which is a design smell worth fixing. On the prevention side, I'd look at whether the master has a timeout on every transaction, whether the bus has proper pull-ups sized for the capacitance and speed, and whether any slave has a known erratum about holding SDA. For a medical device, I'd also want the firmware to detect the stuck condition and attempt recovery automatically rather than requiring a power cycle, since that's not acceptable in the field.

**Possible follow-ups:**
- How would you distinguish a stuck slave from a master that's driving SDA low due to a firmware bug?
- What hardware provisions would you add to a new design to make bus recovery more reliable?

## Q2: In a system where an SPI master talks to several slaves at different clock speeds and with different CPOL/CPHA modes, how would you approach structuring the firmware so that mode and speed changes are handled safely?

**Answer:** The core risk is that SPI mode and clock changes are global to the peripheral, so if you change them while a transaction is in flight — or while a slave is still expecting a particular mode — you can corrupt data or leave a slave in an undefined state. I'd structure the firmware around a single SPI bus abstraction that owns the peripheral configuration, and every transfer goes through it. Each slave gets a descriptor that specifies its CPOL, CPHA, max clock, word size, and chip-select line. Before any transfer, the abstraction reconfigures the peripheral to match that slave's descriptor, and it only does so when no transfer is active. The chip-select for the target slave is asserted only after the mode and clock are stable, and deasserted before any reconfiguration for the next slave. I'd also add a small guard delay between mode changes and the first clock edge, because some slaves need setup time after CS goes low. For determinism, I'd avoid changing modes inside an interrupt context — instead, queue transfers and let a single task or state machine drive the bus. If two slaves happen to share the same mode and speed, I'd group them so the reconfiguration cost is paid once. And I'd make the descriptor table the single source of truth so a new sensor can be added without touching the bus driver.

**Possible follow-ups:**
- What would you do if a slave's datasheet specifies a mode that the MCU's SPI peripheral doesn't support directly?
- How would you verify in test that mode changes aren't happening mid-transaction?

## Q3: You're debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward. How would you approach this?

**Answer:** Bus-off means the controller's transmit error counter exceeded 255, which happens after repeated failed transmissions — so the question is what's causing those failures, and why the controller isn't recovering. First I'd confirm whether the controller is configured for automatic bus-off recovery or whether it requires a software-initiated recovery; many CAN controllers default to staying off until the host clears the state, and if the firmware doesn't do that, the node is effectively dead until reset. That's a firmware bug, not a bus problem. Then I'd look at why the errors accumulated in the first place. Common causes are a bit-rate mismatch between nodes (especially in the data phase of CAN-FD, where the sample point and prescaler are separate from the arbitration phase), a missing or incorrect termination, a stub that's too long for the data-phase bit rate, or a single node with a marginal transceiver that's corrupting frames. I'd use a CAN analyzer to capture the error frames and see which node is generating them and at what point in the frame. I'd also check whether the node is the only one going bus-off — if so, it's likely that node's own configuration or hardware. For a medical device, I'd want the firmware to log the error counters and the bus-off event, attempt recovery with a bounded retry, and if it keeps happening, fail safe rather than silently dropping off the network.

**Possible follow-ups:**
- How would you determine whether the bus-off is caused by the node itself or by another node corrupting its transmissions?
- What's the trade-off between automatic bus-off recovery and requiring an explicit recovery command?

## Q4: How would you approach selecting between RS-422 and RS-485 for a medical device that needs to connect a central controller to several distributed sensor modules?

**Answer:** The key difference is that RS-422 is a full-duplex, point-to-point or one-driver-to-many-receivers interface, while RS-485 is a half-duplex, multi-point bus that supports multiple drivers sharing the same pair. So the first question is whether the central controller needs to talk to all sensors simultaneously in both directions, or whether it can poll them one at a time. If the sensors only ever respond when polled, RS-485 is the natural fit — one differential pair, multiple transceivers, and the controller arbitrates who talks. If the sensors need to stream continuously and independently, or if you need full-duplex communication with each, RS-422 with separate transmit and receive pairs per sensor is simpler but costs more cable and more transceivers. For a medical device, I'd also weigh cable length and node count: RS-485 supports up to 32 unit loads per bus (more with low-load transceivers) and long runs, but the half-duplex turnaround timing adds latency and complexity. RS-422 doesn't have the multi-driver arbitration problem, so it's easier to reason about determinism. I'd also consider whether the sensors need power over the same cable, which favors a single pair with a shared power scheme. And I'd check the common-mode voltage range and isolation requirements, since patient-connected devices often need galvanic isolation on the bus.

**Possible follow-ups:**
- How would you handle a mix where some sensors need full-duplex and others only need to be polled?
- What isolation scheme would you consider for a patient-connected RS-485 bus?

## Q5: How would you approach handling a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** The first priority is to contain the problem and understand its scope before assigning blame or jumping to a fix. I'd pull the failing test case and the protocol implementation together, confirm exactly what the test expected versus what the implementation does, and determine whether it's a single edge case or a systemic misunderstanding of the spec. Then I'd assess the regulatory impact: does this affect the device's safety case, or is it a functional nonconformance that can be corrected and re-tested? That determines whether we need to involve regulatory affairs and whether the delay is a re-test or a re-submission. On the people side, I'd talk to the engineer privately, not in a review, to understand how the error happened — was the spec ambiguous, was there no unit test for that path, was the review process too shallow? The goal is to fix the process, not to punish. I'd then work with the engineer to implement the fix, add a regression test that would have caught it, and update the protocol test plan so the gap is covered going forward. I'd also communicate the schedule impact honestly to stakeholders with a revised plan, and if the delay is significant, look at whether other work can proceed in parallel. The lesson I'd carry forward is that protocol conformance needs to be verified against the spec early, not left to formal compliance testing.

**Possible follow-ups:**
- How would you prevent this kind of gap from recurring without slowing down the team?
- What would you do if the engineer's mistake was caused by an ambiguous requirement rather than a coding error?
