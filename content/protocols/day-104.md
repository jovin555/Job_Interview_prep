# protocols — Day 104

## Q1: How would you approach debugging an I2C bus where a slave device occasionally stretches the clock for longer than the master's timeout allows, causing the master to abort the transaction and leave the bus in an inconsistent state?

**Answer:** I'd start by confirming the failure mode precisely: capture the bus with a logic analyzer and measure the actual stretch duration versus the master's configured timeout, and check whether the slave is stretching on every transaction or only under specific conditions (e.g., after a write that triggers an internal conversion). The root cause is usually a mismatch between the slave's worst-case processing time and the master's timeout, so the fix has two sides. On the master side, I'd check whether the timeout is configurable and whether it can be extended to cover the slave's datasheet worst case with margin — but I'd be cautious, because an unbounded stretch can stall the whole bus and starve other transactions. On the system side, I'd look at whether the slave's stretch can be avoided entirely: for a sensor that needs conversion time, it's often better to trigger the measurement, wait a known interval, then read the result, rather than relying on clock stretching as the handshake. If stretching must be supported, I'd make the master's abort path deterministic — on timeout, issue a recovery sequence (clock out up to nine pulses to let the slave release SDA, then a STOP) so the bus never stays wedged, and log the event so it's visible in field diagnostics. For a medical device, I'd also want the recovery to be bounded and testable, because a bus that silently wedges is a patient-safety concern, not just a reliability nuisance.

**Possible follow-ups:** How would you decide between extending the master timeout and redesigning the transaction to avoid stretching altogether? What would you put in the firmware to detect that the bus has recovered cleanly after an abort?

## Q2: How would you approach selecting between RS-232, RS-422, and RS-485 for a medical device that needs to connect a central controller to several distributed sensor modules?

**Answer:** I'd frame the decision around four axes: topology, distance, noise environment, and whether the link needs to be multi-drop. RS-232 is point-to-point, single-ended, and limited in distance and noise immunity — it's fine for a short cable to a single accessory or a service port, but it doesn't scale to multiple distributed modules. RS-422 is differential and full-duplex, so it's good for a point-to-point or one-driver/multiple-receiver arrangement with high noise immunity over longer runs, but it doesn't naturally support multiple drivers on the same pair. RS-485 is differential and half-duplex multi-drop, which is usually what a distributed sensor network wants: one twisted pair, many nodes, long cable runs, good common-mode rejection. The trade-offs I'd weigh are that RS-485 is half-duplex, so turnaround timing and bus arbitration become firmware concerns, and that termination and fail-safe biasing have to be designed deliberately. I'd also consider whether the modules need power over the same cable, since that affects conductor count and whether RS-485's two-wire topology is an advantage. For a medical device I'd add the regulatory angle: the chosen physical layer has to be justifiable in the risk file, and its failure modes (stuck driver, lost termination, ground potential differences) need to be analyzed.

**Possible follow-ups:** When would RS-422's full-duplex capability actually justify the extra pair over RS-485? How does the number of nodes and cable length change your termination strategy?

## Q3: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** I'd define a transport-agnostic interface at the boundary the application actually cares about — something like open/close, a read/write or transfer call, and an event/error callback — and keep all bus-specific mechanics (addressing, chip-select handling, framing, retries, timing) below that line. The key design decision is what the interface exposes: if it leaks transport details like "register address" or "chip select," the abstraction is fake. So I'd model the sensor as a device with a register or command model, and let each transport backend translate that into the right wire sequence. I'd also make error semantics uniform across transports — a NACK, a framing error, and a CAN bus-off should all surface as a defined error class the application can reason about, rather than raw peripheral status bits. For testability, I'd put a mock backend behind the same interface so application logic can be exercised without hardware, and I'd keep the backend implementations small and independently testable. The trade-off to be honest about is that a lowest-common-denominator interface can hide useful transport-specific features (e.g., CAN-FD's larger payloads or SPI's full-duplex nature), so I'd expose optional capability flags rather than forcing everything through the narrowest path.

**Possible follow-ups:** How would you handle a transport-specific feature that the generic interface can't express without breaking the abstraction? Where would you put retry logic — in the backend or above the abstraction?

## Q4: You're debugging a CAN-FD network where a node occasionally transmits an error frame that corrupts an in-progress message from another node, but only under heavy bus load. How would you approach this?

**Answer:** I'd treat this as a timing and error-confinement problem rather than a wiring problem, since it only appears under load. First I'd capture the bus with a CAN analyzer that timestamps error frames and correlates them with the message that got corrupted, to identify which node is generating the error frame and what error type it is — bit error, stuff error, form error, or ACK error. Under heavy load, a common cause is a node whose sample point or bit timing is marginal relative to the rest of the network, so it mis-samples a bit and flags an error that then aborts another node's frame. I'd check that all nodes share consistent bit timing and sample-point settings for both the arbitration and data phases, and that the transceiver loop delay is accounted for at the chosen data-phase bit rate. I'd also look at whether the error counters on the offending node are climbing toward error-passive, which would confirm it's the source rather than a victim. On the design side, I'd consider whether the bus load itself is the problem — if utilization is near the limit, adding margin by reducing load or raising the data-phase rate may be the real fix. For a medical device, I'd want the error-confinement behavior documented and tested, because a node that can disrupt other nodes' traffic is a system-level risk.

**Possible follow-ups:** How would you verify that all nodes' bit timing is consistent without taking the network down? What would you do if the offending node turns out to be a third-party module you can't reconfigure?

## Q5: How would you handle a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** I'd separate the immediate problem from the systemic one. Immediately, the priority is containment and a credible recovery plan: understand exactly what's wrong, assess whether it's a test-setup issue or a real protocol defect, quantify the schedule impact honestly, and bring the options to the project lead rather than absorbing the delay silently. I'd involve the junior engineer in the diagnosis rather than sidelining them — they know the implementation best, and being part of the fix is how the lesson sticks. Then I'd look at why it escaped: was there no protocol conformance test before formal testing, was the review too shallow, or was the requirement ambiguous? The fix is usually to add a pre-compliance test pass and a review checklist that covers framing, error handling, and boundary conditions, so the same class of defect is caught earlier next time. I'd be careful about blame — the goal is a process that catches this earlier, not a person to hold responsible. I'd also make sure the junior engineer gets specific, actionable feedback in private and a clear path to rebuild confidence, because a demoralized engineer after a public failure is a bigger long-term cost than the schedule slip.

**Possible follow-ups:** How would you decide whether to add a formal pre-compliance test phase versus tightening design review? What would you say to the junior engineer in the first conversation after the failure is confirmed?
