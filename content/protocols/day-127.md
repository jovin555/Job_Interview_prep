## Q1: How would you approach debugging an I2C bus where a slave device occasionally holds SDA low after a transaction, preventing any further communication until power is cycled?

**Answer:** This is the classic "stuck bus" condition, and the first thing I'd do is confirm the mechanism rather than guess. A slave can hold SDA low if it was mid-transaction when the master stopped clocking — for example, the master reset or aborted mid-byte, leaving the slave waiting to drive the next data bit. Because the slave only releases SDA on a subsequent SCL edge, and the master can't start a new transaction while SDA is low, the bus deadlocks.

My approach would be:

1. **Confirm the state** — scope SCL and SDA at the slave. If SCL is idle high and SDA is held low, it's a stuck-slave condition, not a wiring fault.
2. **Identify the trigger** — correlate the lockup with master resets, watchdog events, aborted transfers, or power sequencing. A common root cause is the master being reset while a slave transaction was in flight.
3. **Recover in firmware** — implement the standard clock-pulse recovery: reconfigure SCL as a GPIO, toggle it up to nine times until SDA releases, then issue a manual STOP condition, then reinitialize the I2C peripheral. Nine clocks is enough to flush any partial byte the slave is holding.
4. **Prevent recurrence** — ensure the master completes or cleanly aborts transactions before reset, add a bus-recovery routine to the boot path, and consider a bus switch or reset line to the offending slave if it's a known offender.

The recovery routine should be part of the driver, not an afterthought, because in a medical device a hung bus can mean lost sensor data.

**Possible follow-ups:** How would you decide whether to reset the slave via a dedicated GPIO versus relying on clock-pulse recovery? What would you check if the bus still doesn't recover after nine clocks?

## Q2: How would you approach selecting between RS-422 and RS-485 for a medical device that needs to connect a central controller to several distributed sensor modules?

**Answer:** The decision hinges on topology and duplex requirements more than raw electrical performance, since both share the same differential signaling foundation.

- **RS-422** is a point-to-point or one-driver-to-many-receivers arrangement — one transmitter, up to ten receivers, full-duplex over four wires. It's the right choice when the central controller is the only talker and the sensor modules only listen, or when each module has its own dedicated link back.
- **RS-485** is a true multi-point bus — multiple drivers and receivers sharing a two-wire half-duplex pair (or four-wire full-duplex). It's the right choice when the sensor modules need to talk back to the controller on the same physical medium, which is almost always the case for a sensor network.

For a central controller talking to several distributed sensor modules that must report data back, RS-485 is the natural fit because it supports multi-drop bidirectional communication on a single pair, reducing cabling. RS-422 would force either a dedicated pair per module or a separate return path.

I'd also weigh: cable length and data rate (both handle long runs, but RS-485's multi-drop nature means termination and stub management matter more), common-mode range (both are similar, but RS-485 transceivers often specify wider ranges), and fail-safe biasing (needed on RS-485 to define the idle state when no driver is active). In a medical device, the fail-safe and termination discipline is non-negotiable because a floating bus can produce spurious edges that corrupt data.

**Possible follow-ups:** How would the choice change if the sensor modules were strictly output-only? What termination and biasing would you specify for a multi-drop RS-485 bus with several nodes?

## Q3: How would you approach structuring firmware so that an SPI master can talk to several slaves requiring different clock speeds and different CPOL/CPHA modes, without mode changes corrupting transactions?

**Answer:** The core risk is that changing CPOL/CPHA or clock speed mid-stream can produce a glitch on SCL or misinterpreted edges if the peripheral isn't fully quiesced between transactions. The safe pattern is to treat each slave as owning a complete bus configuration, and to apply that configuration only at transaction boundaries.

My approach:

1. **Per-device configuration descriptor** — each slave has a struct holding its clock speed, CPOL, CPHA, word size, and chip-select polarity. The application never touches the SPI peripheral directly; it calls a transfer function with the device handle.
2. **Serialize access** — a mutex or transaction queue ensures only one transfer is in flight at a time, so configuration changes can't race.
3. **Quiesce before reconfiguring** — ensure the peripheral is idle (TX FIFO empty, no pending transfer), deassert the current chip select, then reprogram the clock divider and mode bits, then assert the target chip select. On many MCUs the mode bits can only be changed when the peripheral is disabled, so the sequence is disable → configure → enable.
4. **Verify with a scope** — confirm that SCL idles at the correct level for each mode and that no runt pulses appear at the mode transition. A common bug is changing CPOL while the clock line is still being driven.
5. **Consider hardware partitioning** — if two slaves need very different speeds and the reconfiguration overhead is significant, a second SPI peripheral or an external mux may be cleaner than frequent reconfiguration.

The key discipline is that mode and speed are properties of the transaction, applied atomically, never changed in the middle of a byte.

**Possible follow-ups:** What would you check if you saw a corrupted first byte only on the slave that runs at the slowest clock? How would you handle a slave that requires a chip-select setup time longer than the others?

## Q4: You're debugging a CAN-FD network where the bus is clean at the nominal (arbitration) bit rate but nodes intermittently report CRC or form errors only during the data phase at the higher bit rate. How would you approach this?

**Answer:** This pattern — clean arbitration, errors only in the fast data phase — points at the physical layer and timing margins specific to the higher bit rate, not at the protocol logic. At the nominal rate the bus has generous margin; at the data-phase rate the bit time shrinks dramatically, so anything that was marginal becomes an error.

My debugging sequence:

1. **Scope the data phase** — look at the differential signal during the BRS-to-data-phase transition. Check rise/fall times, ringing, and whether the signal reaches valid levels within the sample point. At high bit rates, stub length and termination mismatch dominate.
2. **Check sample point and bit timing** — verify the transceiver's loop delay and the configured sample point (typically 75–80% of the bit time). If the sample point is too early or the propagation delay isn't accounted for, the receiver samples during a transition.
3. **Transceiver and topology** — confirm all nodes use CAN-FD-capable transceivers (not classic CAN transceivers with limited symmetry), check that termination is correct at both ends, and measure stub lengths. Long stubs that were fine at the nominal rate can cause reflections that corrupt the fast data phase.
4. **Bit-rate vs bus-length trade-off** — the data-phase bit rate sets a hard limit on bus length. If the bus is longer than the data rate allows, no amount of tuning will fix it; the data rate must come down or the topology must change.
5. **Node-by-node isolation** — if only some nodes report errors, swap transceivers or move nodes to see whether it's a specific transceiver's symmetry or a specific stub.

The fix is usually a combination of reducing the data-phase bit rate, shortening stubs, and ensuring transceiver symmetry — not changing the protocol.

**Possible follow-ups:** How would you determine the maximum allowable data-phase bit rate for a given bus length? What role does transceiver loop delay play in setting the sample point?

## Q5: How would you handle a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** The first priority is to stabilize the situation and protect the patient-safety and regulatory position, then fix the root cause, then prevent recurrence — in that order.

1. **Contain and assess** — work with the test team to characterize exactly what failed and whether it's a test-setup issue or a genuine protocol defect. Determine whether the failure is safety-relevant or a documentation/conformance gap. This scopes the regulatory impact and whether a deviation or re-test is needed.
2. **Fix without blame** — sit with the engineer, walk through the protocol against the requirement, and identify the defect together. The goal is a correct fix and a learning engineer, not a post-mortem that makes them defensive. I'd frame it as "the process let this through, let's fix both."
3. **Recover the schedule** — re-plan the compliance testing with the test house, communicate the revised timeline to stakeholders early, and look for parallelizable work so the delay is minimized. Transparency up front is far better than a surprise later.
4. **Root-cause the process gap** — why wasn't this caught earlier? Usually it's a missing protocol conformance test, an unclear requirement, or a review that didn't cover the framing/error-handling path. Add a targeted test or review checkpoint so the same class of defect is caught before formal testing next time.
5. **Follow up** — verify the fix with a focused regression test before re-entering formal compliance testing, and document the lesson in the team's design-review checklist.

The behavioral core is: separate the person from the defect, treat the schedule hit as a process problem to solve collaboratively, and make the fix durable.

**Possible follow-ups:** How would you decide whether to escalate the delay to leadership immediately or first attempt to recover the schedule internally? What would you add to the design-review checklist to catch protocol framing defects earlier?
