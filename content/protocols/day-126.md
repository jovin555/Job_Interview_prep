# protocols — Day 126

## Q1: You're debugging an I2C bus where the master occasionally reads back a stale value from a sensor register — the transaction completes with an ACK, but the data is one sample old. How would you approach this?

**Answer:** A clean ACK with stale data points away from electrical integrity and toward a protocol/sequencing problem, so I'd first confirm the transaction is actually doing what the firmware thinks it is. The classic cause is a repeated-start read that isn't structured correctly: the master writes the register pointer, issues a repeated START, then reads — but if the write phase is silently retried or the pointer write is skipped on a retry path, the sensor returns whatever register its internal pointer was left on. I'd put a logic analyzer on SCL/SDA and decode the actual byte sequence, not the driver's view of it, and compare against the datasheet's required read sequence.

Second suspect is the sensor's internal update model: many devices latch a conversion into a shadow register only on a specific event, or require a "new data" status bit to be polled before reading. If the firmware reads on a fixed timer without checking the data-ready flag, it will happily read the previous conversion. I'd check whether the stale value correlates with read timing relative to the sensor's conversion period.

Third, I'd rule out a caching layer — either in the driver (a read-through cache returning a buffer that wasn't refreshed) or in the sensor's FIFO if it has one. The way to separate these is to read the same register twice back-to-back with a known stimulus change between them; if the second read is correct, it's a sequencing/timing issue, not a bus issue.

**Possible follow-ups:** How would you distinguish a sensor-side shadow-register issue from a firmware caching bug without changing the firmware? What would you look for in the decoded bus trace to confirm the repeated-start sequence is correct?

## Q2: How would you approach choosing between independent chip selects and a daisy-chain SPI configuration when several sensors on the same board have different CPOL/CPHA requirements and PCB space is tight?

**Answer:** The CPOL/CPHA requirement is close to a deciding factor on its own. In a daisy-chain, all devices share one chip select and one clock, so every device in the chain sees every clock edge — they must all agree on the same mode, and they must all tolerate data being shifted through them that isn't theirs. Devices with different modes fundamentally can't share a daisy chain, so if the sensors genuinely differ in mode, independent chip selects are the only workable option unless you add external gating.

That said, I'd frame the trade study properly rather than stopping at "modes differ." Independent chip selects cost N GPIO pins and N traces routed to each device, which is the PCB-space concern — but the routing is usually simple point-to-point stubs, and you can reclaim pins with an I2C GPIO expander or a small decoder if the MCU is pin-constrained. Daisy-chain saves pins and traces but costs you: a single point of failure on the shared clock/CS, longer effective transaction time (you shift through all devices to reach the last one), and much harder debug because a fault in one device corrupts the whole chain's data.

For a medical device I'd also weigh fault isolation: with independent chip selects, one sensor misbehaving on MISO can be isolated and the others still read; in a daisy chain, one bad device can take down the whole bus. Given tight space, I'd first try to reduce pin count (expander/decoder) and keep independent chip selects, and only consider daisy-chain if all devices share a mode and the space savings are truly decisive.

**Possible follow-ups:** If you had to daisy-chain devices with different modes, what external logic could make that work, and what would it cost you? How does the transaction latency of a daisy chain scale with the number of devices, and when would that matter?

## Q3: How would you approach debugging a CAN-FD network where the bus is clean at the nominal (arbitration) bit rate but nodes intermittently report CRC or form errors only during the data phase at the higher bit rate?

**Answer:** Errors confined to the data phase at the higher bit rate are almost always a physical-layer or timing-margin problem, because the arbitration phase is running at a bit rate the bus already tolerates. I'd treat it as a signal-integrity investigation first and a protocol investigation second.

Concretely: I'd scope the bus at the transceiver pins and look at the data-phase waveform — rise/fall times, ringing, overshoot, and whether the sample point sits in a clean region. At the higher data-phase rate, bit time shrinks dramatically, so the same stub length, termination mismatch, or node-to-node propagation skew that was harmless at the nominal rate now eats a meaningful fraction of the bit. I'd check termination at both ends, stub lengths off the main trunk, and whether the sample-point setting (TSEG1/TSEG2 and SJW) in each node's controller is appropriate for the actual measured loop delay — a sample point that's fine at the nominal rate can be marginal at the data rate.

I'd also check for node-to-node transceiver skew and whether all nodes are actually configured for the same data-phase bit rate and sample point; a single misconfigured node will generate errors that look like a bus problem. And I'd verify the transceivers are rated for the data-phase rate — some older parts are fine at the arbitration rate but too slow for the fast data phase.

The disciplined sequence: measure the eye at the data phase, compute the timing budget from cable delay + transceiver delay + oscillator tolerance, compare against the configured sample point, and only then start changing termination or bit timing.

**Possible follow-ups:** How would you calculate whether the configured sample point has enough margin given the measured loop delay? What's the first thing you'd change if the eye looks clean but errors persist?

## Q4: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The goal is to make the transport a configuration detail, not a compile-time dependency of the application. I'd structure it in three layers: a transport-agnostic sensor/device interface at the top, a set of transport drivers at the bottom, and a thin dispatch layer in between.

At the top, define an interface in terms of what the application actually needs — "read register," "write register," "read block," "subscribe to data-ready" — not in terms of bus primitives. The application holds a handle to that interface and never sees a bus type. Below it, each transport driver implements the same interface: the I2C driver does the register-pointer write + repeated-start read; the SPI driver handles the mode/clock setup and chip-select framing; the UART driver handles framing and flow control; the CAN-FD driver maps the request onto a message ID and payload. The dispatch layer just routes calls to the right driver based on the handle's configured transport.

Two things make this actually work in practice. First, the interface has to be honest about transport differences — a UART or CAN-FD link is message-oriented and may not support a true "read register" without a request/response protocol on top, so the abstraction should expose a request/response model that all transports can satisfy, rather than pretending every transport is memory-mapped. Second, error semantics need to be normalized: a NACK, a CRC failure, and a UART framing error should all surface as a common "transaction failed" result with a transport-specific detail code, so the application's error handling doesn't branch on transport.

I'd keep the abstraction thin — no attempt to hide timing or latency characteristics, because the application may legitimately need to know a CAN-FD round trip is slower than an I2C read. And I'd make it testable by providing a mock transport so the application layer can be unit-tested without hardware.

**Possible follow-ups:** How would you handle a transport that can't do a blocking read, like an interrupt-driven UART, without leaking asynchrony into the application interface? Where would you put retry logic — in the transport driver or the abstraction layer — and why?

## Q5: You're leading a design review where a junior engineer proposes a custom application-layer protocol over UART for a medical device, and you notice the framing has no length-field validation and no sequence numbers. How would you guide the team to evaluate and improve the design?

**Answer:** I'd resist the urge to just declare it wrong and instead walk the team through what failure modes the missing pieces create, so the fix is understood rather than imposed. The framing without length validation is the more dangerous of the two: if a single bit flips in a length field, the receiver can consume the next several valid frames as payload and silently corrupt data — and in a medical device, silent corruption is worse than a visible error. Sequence numbers address a different failure: detecting dropped or duplicated frames and reordering, which matters if the link carries anything where a missing sample changes a clinical interpretation.

I'd frame the review around three questions. First, what's the consequence of each failure mode — corrupted payload, dropped frame, duplicated frame — and which of those are safety-relevant for this device? That drives how much protection is warranted. Second, what's the cheapest robust framing: a length field with a sanity bound (reject lengths outside the expected range), a header checksum or CRC over the frame, and a sequence number with a wrap-aware check. Third, how do we prove it works — a fault-injection test plan that flips bits in the length field, drops frames, and duplicates frames, and confirms the receiver detects and recovers rather than silently mis-parsing.

I'd also connect it to the regulatory context: this is exactly the kind of design weakness that surfaces during compliance testing and costs schedule, so it's cheaper to fix now. The tone matters — I'd position it as "here's how we make this defensible," credit the engineer for the working prototype, and assign the framing hardening as a concrete, reviewable change rather than a vague "make it more robust."

**Possible follow-ups:** How would you decide between a simple checksum and a full CRC for this link, given the UART's error characteristics? What would your fault-injection test plan look like, and which failure would you test first?
