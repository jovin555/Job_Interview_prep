# protocols — Day 52

## Q1: How would you approach debugging a CAN-FD network where a node intermittently transitions into error-passive state and then recovers on its own, with no obvious pattern in when it happens?

**Answer:** Error-passive is a symptom, not a root cause — the controller is telling you its transmit or receive error counters crossed a threshold, so the first job is to figure out *which* counter is climbing and *why*. I'd start by instrumenting the node to log the error counter values over time along with the error type (bit error, stuff error, CRC error, form error, ACK error), because the error type narrows the search space enormously. An ACK error points at the transmitter not being heard — a wiring, termination, or transceiver issue. A bit error during arbitration points at two nodes transmitting simultaneously with different IDs, which usually means a duplicate message ID or a misconfigured filter. A stuff or form error points at bit timing or a node with a marginal clock. Since CAN-FD has separate arbitration and data-phase bit rates, I'd also check whether the failures correlate with the data phase specifically — that's where the higher bit rate and the BRS switch happen, and it's where a marginal sample point or insufficient propagation delay margin shows up first. I'd then look at physical-layer factors: bus length versus the chosen data-phase bit rate, stub lengths, termination at both ends only, common-mode range, and whether the transceiver's loop delay is compatible with the configured sample point. On the firmware side I'd check that all nodes agree on the bit timing registers and that no node is transmitting outside its time slot. The key discipline is to treat the error counters as a diagnostic channel rather than just a nuisance — they tell you whether the problem is electrical, timing, or protocol.

**Possible follow-ups:**
- How would you distinguish a termination problem from a bit-timing problem using only the error counter behavior?
- What would you change in the network if the failures only appear when a particular node transmits?

## Q2: You're designing a half-duplex RS-485 link where the driver-enable and receiver-enable must switch at exactly the right moment, and the turnaround budget is tight. How would you approach this?

**Answer:** The core problem is that the driver must be enabled before the first bit and disabled after the last bit has actually left the shift register — not after the firmware has written the last byte to the transmit buffer. If you disable too early you truncate the final byte; if you disable too late you hold the bus and block the other nodes. So the first thing I'd do is make sure the firmware waits for a "transmission complete" flag rather than a "transmit buffer empty" flag before releasing the driver enable. On the receive side, the receiver should be enabled before the driver is disabled, or there's a window where the line is undriven and the receiver sees noise. I'd also account for the transceiver's own enable/disable propagation delays, which are usually in the tens of nanoseconds but matter at high baud rates. For the turnaround budget itself, I'd calculate the worst-case time as: driver enable delay + last bit time + driver disable delay + line settling + receiver enable delay, and compare that against the protocol's required response window. If the budget is genuinely tight, I'd consider whether the protocol can be restructured — for example, giving the responder a fixed guard time, or using a transceiver with automatic direction control so the hardware handles the turnaround. I'd also add fail-safe biasing so that during the undriven window the line sits at a defined idle level rather than floating, which prevents spurious start bits from being seen as framing errors.

**Possible follow-ups:**
- How would you verify the actual turnaround timing on the bench without a protocol analyzer?
- What happens to the fail-safe biasing if you add more nodes to the bus?

## Q3: How would you approach selecting between a star topology and a daisy-chain topology for a multi-drop sensor network in a medical device, given that the sensors are physically distributed?

**Answer:** The choice is driven by the electrical characteristics of the physical layer, the cable routing constraints in the device, and the failure modes you're willing to accept. A daisy-chain (bus) topology is the natural fit for RS-485 and CAN because those standards assume a single terminated transmission line with short stubs — reflections are controlled by terminating only the two physical ends, and every node taps in with a stub kept short relative to the bit rate. A star topology, by contrast, creates multiple branches from a central point, which means each branch is an unterminated stub unless you add complexity, and reflections at the branch point degrade signal integrity as the data rate rises. So if the sensors are spread along a single cable run, daisy-chain is almost always the better electrical choice. But the trade-off is mechanical and serviceability: a daisy-chain means a fault or a disconnected node in the middle can break the bus for everything downstream, and adding a node requires breaking the run. A star makes each node independently reachable and easier to service, but you pay for it in signal integrity and often in cable volume. For a medical device I'd also weigh whether the sensors are in a patient-connected area where cable routing is constrained, and whether the network needs to keep operating if one branch is disconnected. My approach would be to start from the physical layer's requirements — what bit rate, what cable length, what termination scheme — and let that rule out topologies that can't meet the signal integrity budget, then choose among the survivors based on serviceability and fault tolerance.

**Possible follow-ups:**
- If the mechanical design forces a star, how would you mitigate the signal integrity penalty?
- How would you decide whether a repeater or hub is justified versus changing the topology?

## Q4: How would you approach implementing flow control on a UART link where the receiver occasionally cannot keep up with the transmitter, but the protocol does not have a built-in backpressure mechanism?

**Answer:** If the protocol has no backpressure, you have to add one at a layer the protocol doesn't control, or you have to make the receiver fast enough that it never falls behind. The cleanest option is hardware flow control — RTS/CTS — where the receiver deasserts RTS when its buffer is nearly full and the transmitter's UART hardware automatically pauses. That requires both ends to support it and the cable to carry the extra signals, which isn't always possible. If hardware flow control isn't available, the next option is software flow control using XON/XOFF characters, but that only works if the payload is text or can be escaped, because the flow-control characters can collide with data. If neither is possible, I'd look at the receiver side: is the bottleneck the UART interrupt rate, the buffer size, or the processing after the byte arrives? Often the fix is to use DMA to move bytes into a ring buffer so the CPU isn't servicing a per-byte interrupt, and to size the ring buffer to absorb the worst-case burst. I'd also look at whether the transmitter can be throttled at the application layer — for example, by having the receiver send an application-level acknowledgment that the transmitter waits for, effectively adding backpressure above the protocol. The decision comes down to what the protocol allows you to change and how much latency the application can tolerate: hardware flow control is transparent and fast, software flow control is cheaper but fragile, and application-level pacing is the most flexible but adds round-trip latency.

**Possible follow-ups:**
- How would you size the receive ring buffer if you can't add flow control at all?
- What are the risks of XON/XOFF if the payload is binary?

## Q5: Imagine you're leading a design review where a junior engineer proposes using a single shared interrupt line for three different peripherals — a UART, an SPI sensor, and a GPIO alarm input — arguing that it saves pins and the firmware can just poll the peripherals to find out which one fired. How would you guide the team to evaluate this approach?

**Answer:** I'd want the team to separate the pin-saving benefit from the latency and determinism cost, because those are the two things that actually decide whether this is acceptable. The first question is: what is the worst-case latency budget for each of the three sources? The GPIO alarm input is the one I'd worry about most — if it's a patient alarm, the system may have a hard requirement on how quickly it's acknowledged, and polling three peripherals to find the source adds latency that's hard to bound. The UART is next: if it's a high-baud-rate link, the receive FIFO can overflow while the firmware is polling the other two, and you lose data. The SPI sensor is usually the most tolerant because the master controls the timing, so a small delay in noticing its interrupt is often harmless. So the approach isn't "shared interrupt bad" or "shared interrupt good" — it's matching the interrupt architecture to the latency requirements of each source. I'd also point out that a shared interrupt line doesn't have to mean polling: many microcontrollers can route multiple peripherals to a single interrupt vector and provide a status register that tells you which one fired, so the firmware reads one register instead of polling three peripherals. That preserves most of the pin savings while keeping the latency bounded. If the part doesn't support that, I'd ask whether the pin savings are actually necessary — sometimes the constraint that drove the proposal turns out to be negotiable once the latency cost is on the table. The goal of the review is to get the team to make the trade-off explicitly rather than defaulting to the pin-count argument.

**Possible follow-ups:**
- How would you structure the interrupt handler if the part does support a shared status register?
- What would you do if the alarm input genuinely needs sub-millisecond response and the shared line can't guarantee it?
