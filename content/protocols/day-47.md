## Q1: How would you approach designing a fail-safe mechanism for an RS-485 network where a sensor node must never hold the bus in a dominant state if its firmware crashes or the node loses power mid-transmission?

**Answer:** The core risk in RS-485 is a node driving the bus continuously, which blocks all other communication. I'd approach this at multiple layers. First, at the hardware level, I'd ensure the driver enable line is controlled by a dedicated GPIO with a pull-down resistor, so if the MCU resets or loses power, the driver defaults to disabled (high-impedance). I'd also consider using a transceiver with a built-in timeout feature that automatically disables the driver if the enable line is held high beyond a configured duration — some transceivers offer this. Second, at the firmware level, I'd implement a watchdog that monitors transmission duration; if a transmission exceeds the maximum expected frame time, the firmware forces the driver disable line low. Third, at the protocol level, I'd add a maximum frame length check — any node receiving a frame that exceeds the defined maximum should treat it as an error and ignore it. Finally, I'd consider adding a bus guardian or supervisory circuit that monitors bus activity and can physically disconnect a node if it detects continuous dominant state beyond a threshold. For a medical device, this would also feed into the risk analysis — the failure mode of a stuck bus needs a defined mitigation with a documented response time.

**Possible follow-ups:** How would you test this fail-safe mechanism during compliance testing? What happens if the supervisory circuit itself fails?

## Q2: How would you approach calculating the maximum bus capacitance for an I2C bus operating at 400 kHz with multiple devices, and what happens if you exceed that limit?

**Answer:** The I2C specification defines a maximum bus capacitance of 400 pF for fast-mode (400 kHz) operation. This capacitance includes the trace capacitance, the pin capacitance of each device on the bus, and any connector or cable capacitance. To calculate the total, I'd sum the input capacitance of each device (from datasheets, typically 5–10 pF per pin), add the trace capacitance (roughly 1–2 pF per centimeter for standard PCB traces, more for flex cables), and include any protection circuitry. If the total approaches or exceeds 400 pF, the rise time of the SDA and SCL lines becomes too slow because the pull-up resistors must charge a larger capacitance. This slows the signal edges, which can cause devices to misinterpret logic levels, especially at higher speeds. The practical consequences are marginal timing, intermittent communication errors, or complete bus failure. If I need to exceed the capacitance limit, I'd consider reducing pull-up resistor values (within the current sink capability of the devices), using a bus buffer or multiplexer to segment the bus into smaller capacitive sections, or reducing the bus speed to 100 kHz where the capacitance limit is more lenient. I'd also verify the actual waveform with an oscilloscope — measuring rise time against the spec — rather than relying solely on calculated estimates.

**Possible follow-ups:** How would you determine the optimal pull-up resistor value for a given bus capacitance? What are the trade-offs of using a bus buffer?

## Q3: You're debugging a system where a USB 2.0 device enumerates correctly on most hosts but fails on a specific embedded host controller. The device uses a composite descriptor with both HID and vendor-specific interfaces. How would you approach isolating whether the problem is in the descriptor configuration, the host controller driver, or the device firmware?

**Answer:** I'd approach this systematically, starting with the most likely and easiest-to-test causes. First, I'd capture the enumeration traffic on both a working host and the failing host using a USB protocol analyzer. Comparing the two traces would show exactly where the enumeration process diverges — whether the host stops requesting descriptors, rejects a specific descriptor, or the device fails to respond to a particular request. If the analyzer shows the host sending the same requests but the device responding differently, the issue is in firmware. If the host stops requesting after a specific descriptor, the issue is likely in the descriptor content — perhaps a descriptor field that the embedded host interprets more strictly. I'd also check the device's power configuration: embedded hosts sometimes have stricter current limits during enumeration, so I'd verify the configuration descriptor's power requirements match what the device actually draws. I'd also test with a different cable and check the device's pull-up resistor on D+ — some embedded hosts are more sensitive to signal quality during the speed negotiation phase. If the issue appears to be host-side, I'd check for known errata or driver updates for that specific host controller. Finally, I'd simplify the device to a single-interface HID device to see if the composite configuration is the trigger — this isolates whether the problem is in the composite descriptor structure specifically.

**Possible follow-ups:** How would you structure the descriptor hierarchy to maximize compatibility across different host controllers? What role does the device's bMaxPower setting play in enumeration reliability?

## Q4: How would you approach selecting between a daisy-chain SPI configuration and independent chip selects for connecting multiple sensors in a medical device where PCB space is limited, but the sensors have different clock polarity and phase requirements?

**Answer:** This is a trade-off between hardware simplicity and protocol flexibility. Independent chip selects give each sensor its own SPI transaction, which means I can reconfigure the SPI peripheral's clock polarity and phase before each transaction — this works cleanly even if sensors have incompatible modes. The cost is one additional GPIO per sensor and more routing. Daisy-chain configuration saves pins and routing but requires all devices to share the same clock polarity and phase, and it imposes a specific data flow where each device's output feeds the next device's input. If the sensors have different CPOL/CPHA requirements, daisy-chaining is essentially ruled out unless I add external logic to generate separate clocks, which defeats the purpose. In a medical device, I'd also consider the failure modes: with independent chip selects, a fault in one sensor is isolated; with daisy-chain, a fault in any node can corrupt the entire chain. Given the constraints described, I'd likely recommend independent chip selects even if it costs more GPIOs — the flexibility and fault isolation are worth more than the PCB space savings. If PCB space is truly critical, I'd look for sensors that support compatible SPI modes or consider whether a different bus (like I2C) might be more appropriate for some of the sensors.

**Possible follow-ups:** How would you handle the GPIO pin count limitation if you have more sensors than available chip select pins? Would you consider using a GPIO expander or a multiplexer?

## Q5: Imagine you're leading a design review where a junior engineer proposes using a single CAN-FD bus for a medical device that carries both a safety-critical control message requiring delivery within 2 ms and high-volume telemetry from multiple sensors. The engineer argues that CAN-FD's higher data rate in the data phase eliminates any bandwidth concerns. How would you guide the team to evaluate this approach?

**Answer:** I'd start by acknowledging that CAN-FD does offer higher data throughput, but I'd guide the team to evaluate the proposal against the actual requirements rather than accepting the bandwidth argument at face value. The key distinction is between throughput and determinism — a safety-critical message with a 2 ms deadline needs guaranteed worst-case latency, not just average bandwidth. I'd walk through a structured analysis: first, calculate the worst-case bus load including all messages, their periods, and their data lengths. Then, consider the arbitration mechanism — CAN-FD still uses arbitration for message priority, so a high-priority message will win arbitration, but I need to verify that no lower-priority message can hold the bus during its data phase in a way that delays the critical message. I'd also consider the error handling: if a node enters bus-off state or experiences repeated errors, how does that affect the timing? I'd ask the team to model the worst-case blocking time for the critical message, including the longest possible data phase of any lower-priority message. I'd also raise the question of whether the telemetry data can tolerate being delayed or dropped during error conditions — if not, we need a priority scheme or separate bus. Finally, I'd recommend a quantitative bus load analysis and, if the calculated worst-case latency is close to the 2 ms requirement, suggest either reducing telemetry volume, increasing the critical message priority, or using a separate bus for the safety-critical traffic. The decision should be data-driven, not based on the assumption that higher bit rate solves all problems.

**Possible follow-ups:** How would you calculate the worst-case latency for the safety-critical message? What bus utilization threshold would you consider acceptable for a medical device with a hard real-time requirement?
