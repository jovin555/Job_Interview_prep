## Q1: How would you approach debugging an I2C bus where a slave device holds SDA low after a transaction, preventing any further communication until power is cycled?

**Answer:** This is the classic "stuck bus" condition, and the first step is to distinguish between two root causes: the slave genuinely believes it's still mid-transaction, or the slave has lost synchronization with the master's clock edges and is holding the line as part of a data bit it thinks is still in progress. I'd start by scoping SDA and SCL simultaneously on a logic analyzer to see whether SCL is still toggling freely (master side is fine, slave is stuck) or whether both lines are idle-high with SDA pulled low (bus is wedged). If SCL is free but SDA is held low, the standard recovery is to manually clock SCL as a GPIO for up to nine pulses — enough to walk the slave through any remaining bits of a byte — then issue a STOP condition by pulling SDA high while SCL is high. If that releases the line, the root cause is almost always a slave that missed a clock edge, which points to signal integrity, a marginal pull-up, or a slave that was reset mid-transaction by a brownout. If clocking doesn't release it, the slave may have entered a latched fault state, and the only recovery is a hardware reset line or power cycle — which is a strong argument for adding a dedicated reset GPIO to any I2C slave in a design where a wedged bus would be a safety concern. Longer term, I'd look at whether the master is issuing STOP conditions reliably, whether there's a bus reset mechanism in the driver, and whether the pull-up values are appropriate for the actual bus capacitance.

**Possible follow-ups:**
- How would you implement automatic bus recovery in firmware without a dedicated reset line, and what are the risks of doing so during a safety-critical transaction?
- If the stuck condition only appears after hours of operation, what would that suggest about the underlying cause versus a design flaw?

## Q2: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The core idea is to define a transport-agnostic interface at the boundary between the application and the physical layer, and to keep everything above that boundary expressed in terms of operations the application actually cares about — read a register, write a register, send a command, receive a response — rather than in terms of bytes on a wire. I'd define a small set of function pointers or an abstract base class with operations like `init`, `read`, `write`, `transfer`, and `deinit`, plus a status/error enum that normalizes the different failure modes (NACK, timeout, CRC error, bus-off) into a common vocabulary. Each transport then implements that interface: an I2C backend wraps the HAL calls and handles address formatting, an SPI backend handles chip-select and mode configuration, a UART backend handles framing and flow control, and a CAN-FD backend handles message ID mapping and segmentation. The application layer only sees the abstract interface, so swapping a sensor from I2C to SPI becomes a matter of instantiating a different backend. The tricky parts are the semantic mismatches: I2C and SPI are register-oriented and synchronous, while UART and CAN-FD are message-oriented and may be asynchronous. I'd handle that by defining the interface around a request/response model with an optional callback for asynchronous completion, so synchronous transports can complete inline and asynchronous ones can signal later. I'd also keep transport-specific configuration (bus speed, address, chip-select pin) out of the application and in a board-support or device-tree layer, so the same application code can run on different hardware revisions.

**Possible follow-ups:**
- How would you handle error semantics that don't map cleanly between transports — for example, a CAN-FD bus-off versus an I2C NACK?
- Where would you draw the line between the abstraction layer and the driver layer, and what would you deliberately not abstract?

## Q3: You're debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward. How would you approach this?

**Answer:** Bus-off means the controller's transmit error counter exceeded 255, which happens after a sustained run of errors — it's not a single-event failure, it's an accumulation. The fact that the bus looks healthy afterward tells me the physical layer is probably fine and the problem is either intermittent or specific to that node's transmit path. I'd start by capturing the error counters and the error state transitions over time, either through the controller's diagnostic registers or by logging error frames on a CAN analyzer. The key question is whether the node is accumulating errors because it's transmitting into a bus that's momentarily busy or misconfigured, or because it's receiving errors from other nodes. Common causes I'd check: a bit-timing mismatch between that node's sample point and the rest of the network (especially at the higher CAN-FD data-phase bit rate, where sample point tolerance is tighter), a transceiver that's marginal at the data-phase rate, a stub or termination issue that only manifests at certain bit patterns, or a node that's transmitting at the wrong arbitration-to-data-phase ratio. I'd also check whether the node's automatic bus-off recovery is disabled — many controllers require explicit re-initialization after bus-off, and if the firmware doesn't do that, the node stays off until reset. If the errors correlate with specific traffic patterns, that points to a timing or signal-integrity issue; if they're random, I'd look at the transceiver and the physical layer. The fix is usually a combination of correcting the bit timing, verifying the transceiver's data-phase capability, and implementing a controlled bus-off recovery in firmware with a backoff strategy so the node doesn't immediately re-enter bus-off.

**Possible follow-ups:**
- How would you decide between automatic bus-off recovery and requiring an explicit application-level reset, and what are the safety implications of each?
- If the node only goes bus-off under heavy bus load, what would that suggest about the arbitration or data-phase configuration?

## Q4: How would you approach selecting between RS-422 and RS-485 for a medical device that needs to connect a central controller to several distributed sensor modules?

**Answer:** The decision usually comes down to topology and directionality rather than electrical performance, because both share the same differential signaling fundamentals and similar noise immunity. RS-422 is a point-to-point or one-driver-to-many-receivers topology — one transmitter, up to ten receivers, full-duplex over four wires. RS-485 is a true multi-point bus — multiple drivers and receivers on the same two wires, half-duplex, with the drivers tri-stated when not transmitting. So the first question is whether the central controller needs to talk to one sensor at a time (RS-485 half-duplex is fine and saves wiring) or whether it needs simultaneous bidirectional communication with a single remote device (RS-422 full-duplex is simpler). For a patient monitoring system with several distributed sensor modules, RS-485 is usually the right choice because it minimizes cabling and supports the multi-drop topology naturally. But I'd also weigh: the number of nodes and the resulting bus loading, the cable length and whether the data rate is achievable over that length, whether the protocol needs deterministic polling (which favors RS-485 with a master-slave scheme), and whether any node needs to initiate communication (which complicates half-duplex RS-485 and might push toward a different architecture). I'd also consider fail-safe biasing and termination, which are more involved on RS-485 because the bus is shared. In a medical context, I'd add a layer of scrutiny around what happens when a node misbehaves — on RS-485, a stuck driver can hold the bus, so the protocol and the transceiver's enable logic need to be designed so a single fault doesn't take down the whole network.

**Possible follow-ups:**
- How would you handle a node that needs to send an alarm asynchronously on an RS-485 half-duplex bus where the master controls polling?
- What changes in your termination and biasing strategy if you move from a short backplane to a long cable run in a clinical environment?

## Q5: Imagine you're leading a design review where a junior engineer proposes using a single shared interrupt line for three different peripherals — a UART, an SPI sensor, and a GPIO alarm input — arguing that it saves pins and the firmware can just poll the peripherals to find out which one fired. How would you guide the team to evaluate this approach?

**Answer:** I'd start by acknowledging the legitimate motivation — pin count matters, especially on a small microcontroller — and then walk the team through the failure modes rather than just rejecting the idea. The core issue is that a shared interrupt line turns a hardware event into a software polling problem, and the latency of that polling is now part of the system's worst-case response time. For the GPIO alarm input, that's the most concerning: an alarm is exactly the kind of event where you can't afford to be second in line behind a UART byte or an SPI transfer. I'd ask the team to quantify the worst-case latency for each source: how long does the UART ISR take, how long does the SPI transaction take, and what's the maximum time before the alarm input gets serviced if all three fire close together. If the alarm's required response time is tighter than that worst case, the shared line is disqualified regardless of pin savings. I'd also point out that polling to identify the source adds its own latency and can mask the original event if the peripheral's flag is cleared by the poll itself. Then I'd offer alternatives: use a shared line only for the two lower-priority sources and give the alarm its own pin, or use a priority encoder or interrupt controller if the MCU supports it, or accept the pin cost and use a larger package. The goal isn't to win the argument — it's to get the team to make the trade-off explicitly, with the safety-critical path protected. If the junior engineer can show that the worst-case latency still meets the alarm requirement, then the shared line might be acceptable, and that's a legitimate outcome.

**Possible follow-ups:**
- How would you document the latency analysis so it's traceable for regulatory review, and what would you do if the analysis showed the shared line was marginal?
- If the team decides to keep the shared line, what firmware safeguards would you require to ensure the alarm is never missed?
