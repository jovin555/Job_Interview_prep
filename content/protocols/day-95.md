## Q1: How would you approach debugging a USB 2.0 device that intermittently fails enumeration on a specific host, where the failure appears as a control-transfer timeout during descriptor reads, but the same device enumerates reliably on other hosts?

**Answer:** I'd treat this as a layered isolation problem, because a control-transfer timeout during descriptor reads can originate in the device firmware, the descriptor content, the physical layer, or the host's controller/driver behavior. The first step is to capture what's actually happening on the wire with a USB protocol analyzer, since "timeout during descriptor read" is a symptom, not a cause. I'd look at exactly which descriptor request fails — GET_DESCRIPTOR for device, configuration, string, or a specific interface — and whether the device ACKs the setup stage but then stalls or fails to return the data stage. That distinction splits the problem: a setup-stage failure points at the device controller or firmware endpoint handling, while a data-stage stall points at descriptor length or content.

On the descriptor side, I'd check the things that vary between hosts: whether `bMaxPacketSize0` matches what the device actually implements for endpoint 0, whether the configuration descriptor's `wTotalLength` is consistent with the sum of the interface, endpoint, and class-specific descriptors it contains, and whether string descriptors are well-formed with correct length prefixes and valid character encoding. A malformed or truncated descriptor can cause some host stacks to retry and eventually time out while more forgiving stacks tolerate it. I'd also verify the device responds correctly to the initial 8-byte GET_DESCRIPTOR request that hosts use to learn the endpoint-0 packet size, since some hosts are stricter about the sequencing here.

On the physical and timing side, I'd check whether the device is meeting the timing windows the spec requires — the response time to a setup packet, the inter-packet delays, and whether the device handles the case where the host issues a reset or re-requests descriptors during enumeration. Some embedded host controllers have tighter tolerances or different retry behavior than PC host stacks, so a device that's marginal on response latency can pass on one host and fail on another. I'd also confirm VBUS detection and the connect/disconnect signaling are clean, since a slow or noisy attach can cause the host to sample the device state inconsistently.

Finally, I'd compare host controller types — EHCI versus a companion controller, or an embedded host with a nonstandard stack — and check whether the failure correlates with a particular transfer scheduling behavior. If the analyzer shows the device behaving correctly and the host still timing out, the issue may be host-side, and the practical fix is often to make the device more conservative: respond faster, keep descriptors minimal and standards-compliant, and avoid relying on host tolerance. The key discipline is to let the analyzer evidence drive which layer to fix rather than guessing.

**Possible follow-ups:** If the analyzer shows the device ACKs the setup packet but never sends the data stage, where would you look first in the firmware? How would you determine whether the problem is the device's endpoint-0 handling or the host's retry policy?

## Q2: How would you approach selecting a communication protocol for a medical sensor network where some nodes require deterministic low-latency response for closed-loop control, while other nodes generate bursty high-volume telemetry, and all must share one physical medium?

**Answer:** I'd start by characterizing the traffic rather than picking a protocol by reputation. The two traffic classes have fundamentally different requirements: the closed-loop control path needs bounded worst-case latency and low jitter, while the telemetry path needs throughput and can tolerate delay. The question is whether one medium can serve both without the telemetry starving the control traffic, and that depends on whether the protocol provides priority arbitration or whether I have to impose it at a higher layer.

I'd build a requirements table first: for each traffic class, the message size, the period or burst profile, the deadline, the acceptable jitter, the node count, the cable length, and whether power must travel on the same cable. That table usually narrows the field quickly. For example, if the control loop needs sub-millisecond bounded latency across many nodes, a shared bus with priority-based arbitration is attractive because the arbitration itself enforces priority; if the nodes are physically spread over hundreds of meters, the electrical layer constrains the achievable bit rate and therefore the latency budget.

Then I'd evaluate candidate protocols against those requirements. CAN-FD is strong when I need multi-drop, priority arbitration, and bounded latency, because lower-priority frames yield during arbitration and the data-phase bit rate can be raised independently of the arbitration phase. But I'd be careful: the higher data-phase rate doesn't automatically solve latency, because arbitration and error handling still run at the arbitration bit rate, and bus length trades against achievable bit rate. RS-485 with a well-designed master-slave polling scheme can give deterministic latency if the master controls the schedule, but it requires careful turnaround timing and doesn't provide priority arbitration natively. Ethernet-based approaches offer bandwidth but add complexity and may not give the determinism a closed-loop control path needs without additional mechanisms.

I'd also consider whether the two traffic classes should share a medium at all. Sometimes the cleanest architecture is to separate them — a deterministic fieldbus for control and a higher-bandwidth link for telemetry — because forcing both onto one medium creates a scheduling problem that's hard to validate and harder to certify. If they must share, I'd want the protocol to provide priority or time-slot guarantees, and I'd validate the worst-case latency analytically and then empirically under worst-case telemetry load.

For a medical device, I'd fold regulatory considerations in early: the chosen protocol and its failure modes need to be analyzable for risk management, and the determinism claims need to be testable and documented. A protocol that's elegant on paper but whose worst-case behavior can't be demonstrated under fault conditions is a poor choice for a safety-relevant control path.

**Possible follow-ups:** How would you validate the worst-case latency claim empirically once you've chosen a protocol? If the telemetry load grows after the design is frozen, what's your process for confirming the control path still meets its deadline?

## Q3: How would you approach calculating pull-up resistor values for an I2C bus that must support both standard-mode (100 kHz) and fast-mode (400 kHz) operation with multiple devices on the bus?

**Answer:** The pull-up value is bounded from both sides, and the job is to find the window that satisfies both bounds across all the operating modes the bus must support. The upper bound comes from the rise-time requirement: the bus capacitance and the pull-up form an RC network, and the rise time must be fast enough for the mode in use. Standard-mode allows a longer rise time than fast-mode, so fast-mode sets the tighter upper bound on resistance. The lower bound comes from the sink-current capability of the devices: when a device pulls the line low, the pull-up must not demand more current than the weakest device can sink while still holding a valid low voltage. That sets a minimum resistance.

So I'd start by estimating the total bus capacitance — the sum of the pin capacitances of every device on the bus plus the trace capacitance, which for a long or heavily loaded board can dominate. Then I'd apply the rise-time relationship for the fastest mode required: the rise time from the low threshold to the high threshold must be within the mode's limit, which gives a maximum resistance for that capacitance. Then I'd check the sink-current constraint at the low level to get the minimum resistance. If the window is non-empty, I pick a value comfortably inside it, favoring the higher resistance for lower power consumption as long as rise time margin is adequate.

The complication with supporting both 100 kHz and 400 kHz is that the fast-mode rise-time limit is the binding constraint, so the resistor must be small enough for 400 kHz. But a smaller resistor increases the low-level sink current, which may exceed what some devices can handle, and it increases power draw when the bus is idle-low. If the window collapses — capacitance too high for the fast-mode rise time at any resistance the devices can sink — then the bus is over-loaded and I need to reduce capacitance, split the bus with a buffer or repeater, or reconsider whether 400 kHz is achievable on that topology. I'd also account for the fact that the actual rise time depends on the pull-up plus any series resistance and the driver characteristics, so I'd verify with a scope rather than trusting the calculation alone, especially at the corners of temperature and voltage.

I'd document the calculation — capacitance estimate, chosen resistor, margin against both bounds — because in a regulated design the bus timing is part of what gets verified, and a reviewer will want to see that the choice was reasoned rather than copied from a reference design.

**Possible follow-ups:** If the calculated window is empty because bus capacitance is too high, what are your options short of reducing the device count? How would you verify the actual rise time on the bench, and what would you look for on the scope?

## Q4: How would you approach debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward?

**Answer:** Bus-off means the controller's transmit error counter exceeded its limit, so the node accumulated enough errors to be removed from the bus by the protocol. The fact that it stays off until reset tells me the firmware isn't implementing automatic bus-off recovery, or the recovery is gated on something that isn't happening. The first question is why the error counter climbed in the first place, and the second is why recovery isn't occurring.

For the error accumulation, I'd want to know whether the errors are transmit-side or receive-side, and what error type dominates — bit errors, stuff errors, CRC errors, or acknowledgment errors. A node that goes bus-off because it can't get its transmissions acknowledged suggests a problem with that node's own transceiver or its connection to the bus, or that it's transmitting when no other node is listening. A node that accumulates receive errors suggests it's mis-sampling the bus — a bit-timing or transceiver issue, or a mismatch in the data-phase bit rate configuration between nodes. In CAN-FD specifically, the data-phase bit rate and sample point must be consistent across all nodes, and a node configured with a different data-phase timing can generate errors only when long data frames are transmitted, which would explain an intermittent pattern tied to certain traffic.

I'd use the controller's error counters and error flags, plus a bus analyzer that can decode error frames, to see which node is generating errors and when. I'd correlate the bus-off events with specific traffic — a particular message ID, a particular data length, or a particular bus load — because that correlation often points at the mechanism. I'd also check the physical layer: termination, stub lengths, and whether the bus length is compatible with the chosen bit rates, since CAN-FD's higher data-phase rate shortens the allowable bus length and marginal wiring can cause errors that only appear under certain patterns.

For the recovery side, I'd check whether the firmware implements the standard bus-off recovery sequence — waiting for the bus-off recovery time and then re-initializing the controller — and whether it's being blocked by a state machine that doesn't expect the controller to leave the bus. Some controllers require an explicit re-initialization after bus-off, and if the firmware doesn't do that, the node stays off. I'd also make sure the recovery doesn't create a storm: if the underlying error isn't fixed, the node will go bus-off again immediately after recovery, so recovery without root-cause fix just masks the problem. The right sequence is to fix the error source, then verify recovery works, then confirm the node doesn't re-enter bus-off under sustained load.

**Possible follow-ups:** If the analyzer shows the node accumulating acknowledgment errors only when it transmits a specific message, what would that suggest? How would you distinguish a data-phase bit-timing mismatch from a physical-layer problem using the error counters alone?

## Q5: How would you approach handling a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** The first priority is to stabilize the situation before assigning blame: understand exactly what's wrong, what the compliance impact is, and what the fastest safe path to resolution looks like. I'd pull together the test failure evidence, get the engineer who wrote the code and whoever ran the test into the same conversation, and make sure we agree on the actual defect rather than the symptom. Compliance test failures can be misleading — the test may be exercising a corner case the implementation never considered — so I'd want a clear reproduction and a clear statement of which requirement is violated.

Then I'd assess the regulatory consequence honestly. Some protocol defects are implementation bugs that can be fixed and retested; others touch the device's documented behavior or its risk analysis, in which case the fix may need to flow through the design history file and risk management process, not just the code. I'd involve the regulatory lead early rather than discovering later that the fix itself needs documentation. The schedule conversation follows from that assessment: I'd give stakeholders a realistic revised timeline based on the actual scope, not an optimistic one, and I'd be clear about what's fixed versus what's still uncertain.

On the team side, I'd separate the technical problem from the people problem. A junior engineer making a protocol mistake is a normal part of learning, and the more important question is why the mistake wasn't caught earlier — was there a design review gap, a missing test, an unclear specification? I'd treat it as a process signal rather than a personal failing, because that's what actually prevents recurrence. I'd coach the engineer through the fix so they understand the root cause and the reasoning, and I'd make sure they're not left feeling that the failure is solely theirs when the review and test process also had a role.

I'd also look at whether the same class of defect could exist elsewhere — if one protocol implementation was wrong, sibling implementations may share the flaw — and expand the investigation accordingly rather than fixing only the failing case. Finally, I'd add a regression test that captures the compliance scenario so the defect can't silently return, and I'd feed the lesson back into the review checklist so future protocol work gets scrutinized for the same issue. The goal is to come out of the delay with a fixed device, a documented rationale, and a process that's harder to trip over the same way again.

**Possible follow-ups:** How would you decide whether the fix requires a formal change to the risk analysis versus a straightforward code correction? What would you change in the design review process to catch this class of protocol defect before compliance testing?
