## Q1: How would you approach debugging a UART link where the receiver occasionally reports framing errors, but only when the transmitter is also driving a high-current load on the same board?

**Answer:** Framing errors mean the receiver's start/stop bit sampling doesn't line up with what the transmitter sent, so I'd treat this as a signal integrity problem first, not a protocol problem. The correlation with a high-current load strongly suggests a ground-bounce or supply-rail disturbance coupling into the UART lines or the receiver's reference ground. I'd start by scoping the UART TX/RX lines and the local ground reference simultaneously during the load switching event, looking for ground shift or ringing that pushes the stop bit outside the sampling window. I'd also check whether the UART lines run near the load's switching node or return path, and whether the receiver's ground is star-connected or shares a noisy return. Mitigations typically include improving the ground return path, adding series termination or a small RC filter on the UART lines, increasing hysteresis if the receiver supports it, or physically separating the UART routing from the power stage. If the disturbance is on the supply, decoupling and bulk capacitance near the transceiver can help. Only after ruling out electrical causes would I look at baud-rate tolerance, clock source accuracy, or firmware-level issues like interrupt latency causing missed bytes.

- How would you distinguish a ground-bounce problem from a baud-rate mismatch using only a scope and the error pattern?
- If the UART lines must run alongside the power stage due to mechanical constraints, what layout or filtering techniques would you apply?

## Q2: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The goal is to define a transport-agnostic interface at the boundary the application cares about — typically a set of operations like "read register," "write register," "send message," or "subscribe to events" — and then implement that interface once per physical transport. The application layer holds a handle or pointer to the interface and never includes transport-specific headers. Each transport implementation translates the generic operation into its native framing: an I2C register read becomes a start-address-write plus repeated-start-read, an SPI read becomes a command byte plus dummy cycles, a CAN-FD send becomes a frame with the appropriate ID and DLC. Error semantics need to be normalized too — a NACK, a CRC failure, and a timeout should all surface as a common error type the application can reason about, with transport-specific detail available for logging. I'd keep the interface narrow and synchronous where possible, and push asynchronous or streaming behavior behind a callback or queue so the abstraction doesn't leak timing assumptions. Testability improves because you can implement a mock transport that returns canned data or injects faults, letting you exercise application logic without hardware.

**Possible follow-ups:**
- How would you handle a transport that has fundamentally different semantics, like CAN-FD's multi-master broadcast versus I2C's addressed request-response?
- Where would you draw the line between what belongs in the abstraction layer and what belongs in a transport-specific driver?

## Q3: You're debugging a CAN-FD network where one node intermittently goes error-passive and then recovers on its own, with no obvious pattern. How would you approach this?

**Answer:** Error-passive means the node's transmit or receive error counter has crossed the threshold, so I'd want to know which counter is climbing and why. First I'd capture the error counters over time and correlate them with bus activity — is it happening during specific message bursts, at particular bus loads, or when a specific other node transmits? A node that goes error-passive on transmit usually has a problem with its own output stage, its bit timing, or its sample point relative to the rest of the network. A node that goes error-passive on receive often has a bit-timing mismatch, a marginal transceiver, or is seeing corrupted frames from a specific source. I'd check the bit-timing configuration across all nodes — sample point and SJW should match closely, especially in the data phase where CAN-FD's higher bit rate makes timing margins tighter. I'd also look at physical-layer issues: termination, stub length, common-mode range, and whether the node's transceiver is being disturbed by nearby switching. If the node recovers on its own, that suggests the error condition is transient and the counter is decrementing during error-free periods, which points toward an intermittent physical or timing issue rather than a hard fault.

**Possible follow-ups:**
- How would you use the CAN error frame contents or a bus analyzer's error log to narrow down whether the fault is local to the node or network-wide?
- What bit-timing parameters would you verify first if you suspected a data-phase sample-point mismatch?

## Q4: How would you approach selecting between RS-422 and RS-485 for a medical device that needs to communicate with multiple sensors distributed across a patient monitoring system?

**Answer:** The key difference is that RS-422 is a point-to-point or one-driver-to-many-receivers topology, while RS-485 supports multiple drivers sharing a single bus with tri-state control. If the architecture is a central controller polling several sensors and only the controller ever transmits, RS-422 can work and gives you a simpler, always-on driver with no turnaround timing to manage. But if any sensor needs to transmit back — even just acknowledgements or status — you need RS-485's multi-driver capability and the associated driver-enable control. For a patient monitoring system, I'd also weigh cable length and node count against the standard's limits, common-mode voltage range (important if sensors are at different ground potentials), and whether the system needs half-duplex or full-duplex. RS-485 half-duplex is usually the pragmatic choice for multi-drop because it halves the conductor count, but it introduces turnaround timing that the firmware must handle carefully. I'd also consider fail-safe biasing so the bus doesn't float into an undefined state when no driver is active, and whether the chosen transceivers meet the isolation requirements that medical devices often need for patient-connected equipment.

## Q5: How would you approach handling a situation where a junior engineer on your team implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** The first priority is to understand the actual failure and its scope before assigning blame or jumping to a fix. I'd sit down with the engineer, review the test failure together, and trace it back to the specific protocol behavior that's wrong — whether it's a framing issue, a timing violation, an error-handling gap, or a misunderstanding of the specification. That conversation needs to be collaborative, not punitive; the goal is to fix the problem and prevent recurrence, not to make anyone defensive. Once the root cause is clear, I'd assess the impact: does the fix require a firmware change only, or does it touch hardware or the test setup? I'd bring in the regulatory lead early because any change during compliance testing may need to be documented and may affect the test plan or the device's risk file. For the schedule, I'd work with the team to re-sequence remaining tests so that unaffected areas can proceed in parallel while the fix is developed and verified. Afterward, I'd look at the process gap that let the error reach compliance testing — was the protocol specification unclear, was there no unit-level test for that behavior, was the design review too shallow? — and address that so the same class of error doesn't recur.

**Possible follow-ups:**
- How would you structure a design review or code review process to catch protocol implementation errors before they reach compliance testing?
- If the fix requires a change to the device's risk documentation, how would you coordinate that with the regulatory team without stalling the whole project?
