## Q1: How would you approach debugging an I2C bus where a device intermittently NACKs its address, but only when the bus is running at 400 kHz and only after the board has warmed up for a while?

**Answer:** This pattern — speed-dependent and temperature-dependent — points at marginal timing rather than a logic bug, so I'd treat it as a signal-integrity and timing-budget problem first. My starting hypothesis list: rise times degraded by bus capacitance and pull-up sizing, a slave whose internal timing drifts with temperature, or a setup/hold violation on the slave's address sampling that only shows up when edges are slow.

Concretely, I'd first scope SCL and SDA at the slave pins with a fast probe and look at rise time against the fast-mode spec, plus the actual high/low levels. If rise time is close to or over the limit, the pull-ups are too weak for the accumulated capacitance — warming the board can shift things just enough to cross the threshold. I'd also check whether the NACK correlates with a specific transaction type (e.g., a read after a write) rather than the address itself, since a slave that's still busy internally can appear to NACK.

Next I'd separate "the slave didn't hear the address" from "the slave heard it and refused." A NACK with clean edges and correct levels suggests the device is genuinely not ready or has reset; a NACK with distorted edges suggests the device never decoded the address correctly. Checking whether the device's supply rail or its own reset pin is drifting with temperature helps rule out the device browning out or resetting.

If it's marginal timing, mitigations include reducing pull-up values (within the sink-current budget), shortening or rerouting the bus, lowering the bus speed for that segment, or inserting a buffer/repeater. I'd also confirm the master isn't violating the spec — e.g., insufficient setup time before the first clock, or a repeated-start that's too tight. The key discipline is to instrument rather than guess: capture the failing transaction and compare it to a passing one at 100 kHz on the same hardware.

**Possible follow-ups:** How would you distinguish a slave that's internally busy from one that genuinely didn't decode its address, using only the scope and the datasheet? If you can't change the pull-ups, what other levers do you have to make the bus reliable at 400 kHz?

## Q2: How would you approach structuring firmware so that an SPI master can talk to several slaves requiring different clock speeds and different CPOL/CPHA modes, without mode changes corrupting transactions?

**Answer:** The core risk is that CPOL/CPHA and clock rate are properties of the *transaction*, not the bus, and changing them mid-stream while a slave is mid-frame or while the bus is in an indeterminate state is what causes corruption. So I'd design around three principles: make mode/speed part of the per-device descriptor, sequence reconfiguration so it only happens at a clean boundary, and never let two devices' transactions interleave.

Structurally, I'd define a device descriptor that carries the bus handle, chip-select, clock frequency, CPOL/CPHA, bit order, and word size. A bus-manager layer owns the SPI peripheral and exposes a "transaction" API that takes a device descriptor plus buffers. Before each transaction, the manager checks whether the current hardware configuration matches the descriptor; if not, it reconfigures — but only after ensuring the previous transaction has fully completed (TX empty, RX drained, CS deasserted) and the bus has been idle for the required setup time. Reconfiguring while CS is still asserted or while the shift register is draining is exactly how you get a corrupted last byte or a spurious clock edge.

I'd also guard against the classic pitfalls: deassert CS and insert a small inter-transaction gap before changing mode, because some slaves need time to release MISO; and never share a bus between two devices without serializing access through the manager (a mutex or a single-owner task), otherwise a context switch mid-transaction can flip the mode under a slave. On an RTOS, I'd make the bus manager the sole owner of the peripheral and have device drivers call into it, so the reconfiguration logic lives in one place and is testable.

Finally, I'd make the mode/speed handling observable — log or expose the active configuration — so that when a corruption appears, you can immediately tell whether the wrong mode was applied to the wrong device.

**Possible follow-ups:** What specifically can go wrong if you change CPOL while CS is still asserted? How would you test that the reconfiguration sequencing is correct without a logic analyzer on every transaction?

## Q3: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The goal is to keep the application's view of a sensor at the level of "read this measurement" or "configure this parameter," and push all transport-specific mechanics below a stable interface. I'd structure it in layers: a transport interface (open/close, read, write, and a way to express transaction boundaries), a device driver per sensor that speaks the sensor's register/command model on top of that interface, and the application on top of the driver.

The transport interface needs to be honest about the differences between buses rather than pretending they're identical. I2C and SPI are master-initiated register transactions; UART is a byte stream with framing; CAN-FD is message-oriented with IDs and arbitration. So the interface should expose a transaction concept (write-then-read, with a device handle) and let each transport implement it appropriately — for UART that might mean a request/response framing layer, for CAN-FD it means mapping a logical device to a message ID. The application never sees a bus address, a chip select, or a CAN ID; those live in configuration bound at initialization.

I'd keep the sensor driver's register model transport-agnostic by having it call the transport interface with logical operations, and inject the concrete transport at construction (dependency injection or a small vtable). That makes the driver unit-testable against a mock transport and lets the same sensor driver run over I2C in one product and SPI in another.

Two things I'd be careful about: don't leak transport-specific error semantics upward (a NACK, a framing error, and a CAN bus-off should map to a common error taxonomy the application can reason about), and don't hide timing/determinism differences — if the application has real-time constraints, the abstraction should let it express them so the transport can honor or reject them.

**Possible follow-ups:** How would you handle a sensor that has genuinely different capabilities depending on the transport (e.g., interrupt-driven vs polled)? Where would you put retry logic — in the transport layer or the device driver?

## Q4: You're debugging a CAN-FD network where a node occasionally transmits an error frame that corrupts an in-progress message from another node, but only under heavy bus load. How would you approach this?

**Answer:** An error frame that corrupts another node's in-progress message means some node detected an error and signaled it, which by design aborts the current frame for everyone. Under heavy load, the usual suspects are: a node whose bit timing is marginal (sample point or SJW misconfigured for the actual bus length and data-phase bit rate), a node that's losing arbitration and then mis-sampling, or a physical-layer issue (reflections, stub length, termination) that only manifests when the bus is busy and edges are dense.

I'd start by capturing the bus with a CAN analyzer that can decode error frames and tell me *which* node transmitted the error frame and *what* error it flagged (bit error, stuff error, CRC error, form error, ACK error). That single piece of information splits the problem: if the error frame comes from a node that's consistently the victim, it's likely a receiver-side timing or signal-integrity problem at that node; if it comes from a node that's consistently the aggressor, that node may be transmitting outside its slot or have a faulty transceiver.

Then I'd check the bit-timing configuration against the physical bus: CAN-FD's data phase runs much faster than the arbitration phase, so the sample point and SJW that work at the arbitration rate can be wrong for the data rate, especially on a long bus. I'd verify propagation delay and loop delay fit the chosen data-phase bit rate, and confirm all nodes agree on the same nominal and data bit timing. Under heavy load, the bus is at its densest, so marginal timing shows up there first.

On the physical side, I'd check termination at both ends, stub lengths, and whether the error correlates with a particular node's traffic. A common fix is to reduce the data-phase bit rate, adjust the sample point, or fix termination/stubs. I'd also look at whether the "aggressor" is actually a node whose error counters are climbing — repeated error frames from one node suggest it's the one with the marginal configuration.

**Possible follow-ups:** How would you use the error counters and error-state transitions to narrow down which node is at fault? If the error only appears at the highest data-phase bit rate, what's your first trade-off to make the network robust?

## Q5: How would you handle a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** I'd separate the immediate containment from the root-cause and process fix, and be deliberate about tone — the goal is a correct device and a team that learns, not a blame exercise.

First, containment: understand exactly what the protocol defect is, what test it failed, and whether it's a functional safety issue or a conformance/documentation issue. I'd pull the failing test evidence, reproduce it on the bench if possible, and get a clear picture of scope — is it one message type, one state, or systemic? That determines whether we need a targeted fix or a broader review. I'd bring the regulatory/test stakeholders in early so the schedule impact is communicated honestly and the path to re-test is planned rather than discovered late.

Second, root cause: why did this escape? Usually it's one of a few things — the protocol spec was ambiguous or incomplete, the implementation wasn't tested against the spec's edge cases, or the review didn't cover the protocol state machine. I'd look at whether we had a written protocol spec with explicit framing, error handling, and state transitions, and whether the test plan covered fault injection and boundary conditions. If the spec was the gap, that's a process fix; if the implementation diverged from a clear spec, that's a review/testing gap.

Third, the human side: I'd talk with the engineer privately, focus on the system that allowed the defect through rather than the individual, and make sure they're part of the fix — that's how you build ownership rather than defensiveness. I'd also use it as a trigger to add protocol conformance tests and a review checklist so the same class of defect is caught earlier next time.

Finally, I'd document the deviation, the fix, and the re-test evidence properly, since in a regulated environment the corrective action record matters as much as the code change.

**Possible follow-ups:** How would you decide whether to fix forward or roll back to a known-good protocol version given the schedule pressure? What would you add to the design review process to catch protocol defects before compliance testing?
