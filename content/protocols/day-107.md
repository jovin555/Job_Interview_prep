# protocols — Day 107

## Q1: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The core idea is to separate *what* a sensor transaction means from *how* it is physically carried. I would define a small transport-agnostic interface — typically a handle plus an operations table (or vtable) with a handful of primitives: open/init, a combined write-then-read "transfer" call, a write-only call, and a control call for transport-specific settings like bus speed or addressing. Each physical transport implements that interface in its own driver, translating the generic transfer into the concrete sequence — an I2C repeated-start read, an SPI full-duplex exchange with chip-select assertion, a UART frame with framing and checksum, or a CAN-FD message with the right ID and DLC.

Above that layer sits a sensor driver per device that speaks the sensor's register model or command set and calls only the abstract transfer primitives. The application then talks to sensor objects, never to a bus. Two things make this work in practice: first, the abstraction must not leak timing or error semantics that differ between transports — so the interface should return a normalized status (OK, timeout, bus error, CRC error, device NACK) rather than raw peripheral flags. Second, transport-specific concerns like addressing, chip-select, and bus arbitration belong entirely inside the transport driver, configured at init time, so the sensor driver never branches on "which bus am I on."

The payoff is testability: you can drop in a mock transport that returns scripted responses and unit-test the sensor logic on a host without hardware. The trade-off to watch is that a lowest-common-denominator interface can hide useful capabilities — for example, CAN-FD's hardware filtering or SPI's full-duplex nature — so I'd keep the core interface minimal and expose optional extended operations through the control call rather than bloating the base interface.

**Possible follow-ups:** How would you handle a transport that needs asynchronous completion (e.g., a CAN-FD transmit that queues) when the interface was designed around blocking calls? Where would you put retry logic — in the transport driver, the sensor driver, or the application?

## Q2: You're debugging a CAN-FD network where a node intermittently enters error-passive state and then recovers on its own, with no obvious pattern. How would you approach this?

**Answer:** Error-passive means the node's transmit error counter (TEC) or receive error counter (REC) has crossed 127, so the first job is to find out *which* counter is climbing and *why*. I'd start by instrumenting the node to log the error counters and the error type each time a counter increments — bit error, stuff error, CRC error, form error, ACK error — because the error type narrows the cause dramatically. A node that is the only one seeing CRC or stuff errors while everyone else is healthy usually points at a local physical-layer problem: a marginal transceiver, a termination issue, a stub, or a ground offset. A node that sees ACK errors is transmitting but nobody is acknowledging, which points at bus wiring or a bit-rate mismatch.

Because it recovers on its own, the counters are oscillating around the passive threshold rather than saturating to bus-off, which suggests a marginal, intermittent condition rather than a hard fault. I'd correlate the error events with external activity: temperature (solder joint or transceiver drift), bus load (more traffic means more chances to hit the marginal condition), and specific message IDs (a particular frame length or bit pattern hitting a timing problem). I'd also verify the arbitration-phase and data-phase bit timing and sample-point settings are consistent across all nodes — a sample-point mismatch that only bites at certain bit patterns is a classic cause of intermittent, self-recovering errors. Finally, I'd scope the bus at the suspect node during an event to look for ringing, reflections, or a slow edge that a receiver samples differently depending on phase of the moon.

**Possible follow-ups:** How would you distinguish a sample-point mismatch from a termination problem using only error-counter data? What would you change in firmware to make the node fail more gracefully while you root-cause the physical issue?

## Q3: You're designing a half-duplex RS-485 link where the driver-enable and receiver-enable must switch at exactly the right moment, and the turnaround budget is tight. How would you approach this?

**Answer:** Half-duplex RS-485 turnaround is fundamentally a timing-budget problem, so I'd start by writing that budget down explicitly: the time from the last stop bit leaving the UART shift register, through the transceiver's driver-disable propagation delay, the bus settling time, the remote transceiver's receiver-enable and the remote UART's start-bit detection, plus margin. If the sum doesn't fit inside the required turnaround, no amount of clever firmware fixes it — you need a faster transceiver, a higher baud rate, or a protocol that tolerates more gap.

On the firmware side, the classic mistake is disabling the driver the instant the UART reports "transmit complete," which on many MCUs means the shift register is empty but the last bit is still on the wire — disabling then truncates the final character. I'd use the transmit-complete flag that specifically indicates the last bit has shifted out, then add the transceiver's disable delay before releasing the bus. For the receive side, I'd enable the receiver *before* the driver is fully disabled where the transceiver allows it, or use a transceiver with a combined DE/RĒ pin driven so there's never a window where both driver and receiver are off and the first bit of the response is missed.

I'd also make the turnaround robust rather than razor-thin: build in a small guard time and, critically, design the protocol so the master doesn't depend on sub-microsecond turnaround — for example, the slave waits a defined inter-frame gap before responding, so the master's receiver is guaranteed to be enabled and settled. Then I'd verify the whole thing on a scope at the worst-case node (longest cable, most capacitance) across temperature, because propagation delays drift.

**Possible follow-ups:** How would you handle a slave that is slow to respond — do you extend the master's timeout, or is there a risk of colliding with the next master transmission? What role does failsafe biasing play in the idle state between turnaround?

## Q4: How would you approach selecting between USB 2.0 interrupt transfers and isochronous transfers for a medical device that streams real-time sensor data to a host, with a requirement that no data be lost?

**Answer:** The requirement "no data lost" immediately rules out isochronous as the primary mechanism, because isochronous transfers reserve bandwidth and guarantee timing but provide *no* retry and no handshake — a missed or corrupted packet is simply gone. Isochronous is the right choice when you need guaranteed, jitter-bounded delivery and can tolerate occasional loss (streaming audio/video being the classic case). For a medical sensor stream where every sample matters, interrupt transfers are the better fit: they're polled at a bounded interval (giving you a latency guarantee the host honors), they're retried by the host controller on error, and they carry a handshake so the device knows the data arrived.

The trade-off is bandwidth and latency: interrupt transfers reserve a guaranteed slice of frame bandwidth but that slice is small, so you size the endpoint's max packet and polling interval to your sample rate and accept that latency is bounded by the polling interval rather than truly continuous. If the data rate is high enough that interrupt bandwidth becomes the bottleneck, the usual pattern is a hybrid: interrupt or bulk for the reliable data path, and reserve isochronous only for a low-latency "live preview" that can afford to drop frames, with the authoritative record going over the reliable path. I'd also make sure the device firmware buffers samples so that a transient host stall (busy scheduling, suspend) doesn't overflow — the endpoint type protects against corruption, not against the host simply not polling fast enough.

**Possible follow-ups:** How would you size the interrupt endpoint's polling interval and max packet size for a given sample rate? What happens to your buffering strategy if the host enters selective suspend mid-stream?

## Q5: You're leading a design review where a junior engineer proposes using a single shared interrupt line for three different peripherals — a UART, an SPI sensor, and a GPIO alarm input — arguing that it saves pins and the firmware can just poll the peripherals to find out which one fired. How would you guide the team to evaluate this approach?

**Answer:** I'd treat this as a teaching moment about the difference between *saving a pin* and *preserving a guarantee*, and steer the discussion toward the worst-case timing rather than the typical case. The pin saving is real and worth acknowledging — on a constrained MCU it can matter. But the proposal quietly converts three independent, hardware-latched events into a single shared signal whose source must be discovered by polling, and that changes the latency and the failure modes.

The key question I'd put to the team is: what is the maximum acceptable latency for each of these three events, and what happens if two fire at once? The GPIO alarm input is the sharpest case — if it's a safety-relevant alarm, polling it behind a UART and an SPI transaction means its detection latency now depends on how long those other handlers take, which is exactly the kind of coupling you don't want in a medical device. The UART and SPI peripherals usually have their own status flags that the ISR can read cheaply, so those are less problematic, but the alarm input has no such flag — it's a level, and if it's a brief pulse it can be missed entirely between polls.

I'd guide the team to a middle path: keep the shared line only if the firmware can, in the shared ISR, read each peripheral's status register directly (not "poll" in the slow sense) and dispatch in bounded time, and only if the alarm input is either level-held long enough to be caught or given its own dedicated interrupt. I'd ask them to document the worst-case service time for the shared ISR and show it meets the tightest deadline among the three. If it doesn't, the pin saving isn't worth the lost determinism, and I'd rather spend a pin or use a pin-mux/expander than compromise an alarm path. The goal is to have the junior engineer walk away able to make this trade-off themselves next time, not to just overrule them.

**Possible follow-ups:** How would you structure the shared ISR so that a slow peripheral can't starve a fast one? If the alarm input must stay on the shared line, what hardware or firmware change would make it safe?
