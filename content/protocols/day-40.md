## Q1: How would you approach designing a clock stretching strategy for an I2C bus in a medical sensor device where one slave device (a complex sensor) needs more time to process a read request than the master's timeout allows?

**Answer:** Clock stretching is a legitimate I2C mechanism where a slave holds SCL low to pause the transaction while it prepares data. The key design challenge is balancing the slave's need for processing time against the master's responsibility to detect and recover from a genuinely stuck bus. I'd approach this in layers. First, at the hardware level, I'd verify the slave's maximum clock-stretch duration from its datasheet and ensure the master's I2C peripheral (or software bit-bang implementation) has a timeout that exceeds that worst-case value with margin — typically 2–3× the specified maximum. Second, at the firmware level, I'd configure the master's timeout to a value that accommodates the slave's stretch but still detects a true bus fault — for example, if the slave specifies a 5 ms maximum stretch, a 25–50 ms timeout gives reasonable protection without masking a real failure. Third, I'd implement a recovery path: on timeout, release the bus, issue a bus-clear sequence (up to 9 clock pulses with SDA released), and attempt a re-initialization of the slave. In a medical device, I'd also consider whether the slave's clock stretching could be avoided altogether by restructuring the protocol — for example, having the slave buffer data and using a "data ready" register that the master polls, which eliminates the need for long stretches and makes timing more predictable. This is particularly relevant in battery-powered devices where the master may be in a low-power state and a stretched transaction could prevent it from entering sleep.

**Possible follow-ups:** How would you distinguish between a slave that is legitimately clock-stretching and one that has hung the bus? What happens if the slave stretches SCL indefinitely due to a firmware bug — how would you design the system to recover safely?

## Q2: You're debugging a system where an RS-485 network with 16 nodes works reliably at 9600 baud but experiences intermittent corruption at 115200 baud over a 150-meter cable run. How would you approach isolating the root cause?

**Answer:** This is a classic symptom of a system that is marginal at higher data rates, and I'd approach it systematically. The first thing I'd check is the electrical characteristics of the cable and termination. At 115200 baud, the bit time is roughly 8.7 µs, and if the cable has significant capacitance or the termination is incorrect, signal edges will be slowed and distorted. I'd verify that termination resistors match the cable's characteristic impedance (typically 120 Ω for twisted-pair) and are placed at both physical ends of the bus — not just at the controller. I'd also check for unterminated stubs; at 115200 baud, stub lengths should ideally be kept under about 1 meter, and any longer stubs could cause reflections that corrupt data. Second, I'd look at the transceiver's slew rate and driver strength. Many RS-485 transceivers have a slew-rate-limited mode for lower data rates; if the device is in that mode, it may not transition fast enough at 115200 baud. I'd check the transceiver datasheet and ensure the configuration is appropriate for the target data rate. Third, I'd examine the common-mode voltage range. At higher baud rates, ground potential differences between nodes become more significant, and if the common-mode voltage exceeds the transceiver's input range, data will be corrupted. I'd check whether the network has a proper ground reference — a single common ground connection is typically recommended, and I'd verify there are no ground loops. Fourth, I'd use an oscilloscope to look at the actual signal at the farthest node — checking rise/fall times, ringing, and eye diagram quality. This would immediately reveal whether the issue is signal integrity (slow edges, reflections) or something else like noise coupling. Finally, I'd check the firmware's bit timing — at 115200 baud, the UART's baud rate tolerance is tighter, and if the nodes use internal RC oscillators with poor accuracy, the accumulated timing error could exceed the UART's tolerance. I'd verify the actual baud rate on each node with a frequency counter or by measuring the bit width on a scope.

**Possible follow-ups:** How would you determine whether the issue is signal integrity versus baud rate mismatch between nodes? What changes would you make to the termination scheme if the cable run were extended to 300 meters?

## Q3: How would you approach implementing a deterministic scheduling scheme for a medical device that uses I2C for sensor reads, SPI for high-speed data logging, and UART for a user interface, all on a single microcontroller running Zephyr RTOS?

**Answer:** The core challenge is ensuring that each protocol's timing requirements are met without one starving another, and that the system remains responsive to safety-critical events. I'd start by characterizing the timing requirements of each interface: the I2C sensor reads might need to happen at a fixed rate (e.g., every 10 ms) with bounded jitter; the SPI data logging might be bursty but high-volume; the UART interface needs to remain responsive to user input without blocking. In Zephyr, I'd structure this using threads with appropriate priorities and use the RTOS's synchronization primitives rather than busy-waiting. I'd assign the I2C sensor reads to a high-priority thread that wakes on a timer or uses a Zephyr sensor driver with a polling interval; the SPI logging could run in a medium-priority thread that processes data from a queue; the UART interface would use interrupt-driven or DMA-based reception with a lower-priority thread handling command parsing. The key is to avoid blocking operations in high-priority contexts — for example, the I2C thread should never wait on a mutex held by the SPI thread. I'd use Zephyr's message queues or ring buffers for data passing between threads, and I'd carefully consider whether to use the RTOS's I2C/SPI drivers (which are typically asynchronous and callback-based) or write custom drivers. For the I2C bus specifically, I'd consider whether clock stretching from the sensor could block the bus and affect other transactions — if so, I might isolate the sensor on its own bus or use a separate I2C controller if available. I'd also think about power management: in a battery-powered device, the scheduling scheme should allow the MCU to enter low-power states between transactions, which means the RTOS tick and timer configuration need to support this. Finally, I'd add instrumentation — such as a debug UART or logic analyzer trigger — to measure actual timing during development and verify that the scheduling meets the requirements under worst-case conditions.

**Possible follow-ups:** How would you handle the case where a high-priority I2C transaction is delayed because the SPI logging thread is in the middle of a long DMA transfer? How would you verify that the scheduling meets timing requirements under worst-case conditions?

## Q4: Imagine you're leading a design review where a junior engineer proposes using a single SPI bus with four slaves, each on an independent chip select, to connect a high-resolution ADC, a flash memory for data logging, a real-time clock, and a temperature sensor in a battery-powered medical device. The engineer argues that SPI's high data rate and simple architecture make it the obvious choice. How would you guide the team to evaluate this approach?

**Answer:** I'd start by acknowledging that SPI is a reasonable choice for this set of peripherals — it's simple, fast, and each slave has its own chip select, which avoids the address conflicts you'd have with I2C. But I'd guide the team to evaluate the decision against the system's actual requirements rather than just the protocol's raw capabilities. The first question I'd ask is about power consumption: in a battery-powered medical device, the bus architecture affects how long the MCU and peripherals need to be awake. SPI typically requires the master to actively clock every transaction, and if the ADC needs to be sampled frequently, the bus and the MCU may need to stay active longer than with a protocol that supports more efficient wake-up patterns. I'd ask the engineer to estimate the duty cycle of each transaction and the total active time per measurement cycle. Second, I'd ask about the physical layout: four slaves on one SPI bus means the MISO line has four potential drivers, and while independent chip selects prevent contention, the bus capacitance and trace lengths need to be considered — especially if the ADC is a high-resolution device sensitive to noise. I'd ask whether the ADC's analog front-end could be affected by digital switching noise from the SPI bus, and whether the layout separates analog and digital domains. Third, I'd ask about the real-time clock: RTCs typically need a backup power domain and may have specific requirements for bus access — for example, some RTCs have a "bus lockup" issue if the bus is held in an undefined state. I'd ask how the design handles the case where the MCU resets mid-transaction and the RTC's chip select is left asserted. Fourth, I'd ask about firmware complexity: with four slaves on one bus, the driver needs to manage chip selects carefully, and if any slave requires a different clock polarity or phase, the master may need to reconfigure the SPI peripheral between transactions — which adds complexity and potential for errors. Finally, I'd ask whether the engineer has considered the alternative of using two separate buses — for example, putting the ADC on its own dedicated SPI bus (or even I2C) to isolate it from digital noise and reduce bus capacitance, while keeping the flash and RTC on the main bus. The goal is to guide the team to a decision based on power, noise, layout, and firmware complexity — not just "SPI is fast."

**Possible follow-ups:** How would you decide whether to split the peripherals across two buses versus keeping them on one? What specific power-consumption analysis would you ask the engineer to perform?

## Q5: How would you approach handling a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** I'd approach this in three phases: immediate response, root-cause analysis, and process improvement. In the immediate response, my priority is to understand the scope of the issue and communicate transparently with stakeholders. I'd work with the engineer to characterize the failure — what exactly is failing, which test cases are affected, and whether it's a systemic protocol error or an edge case. I'd also assess whether there's a workaround that allows testing to continue on other aspects of the device while the protocol issue is being fixed. The key here is to avoid blame and keep the team focused on solving the problem. In the root-cause phase, I'd lead a structured investigation — similar to an 8D process — to understand why the error occurred and why it wasn't caught earlier. I'd ask questions like: Was the protocol specification ambiguous? Was there a misunderstanding of the requirements? Were there adequate unit tests or integration tests? Was the design review thorough enough? This is where I'd look for systemic issues, not just the individual's mistake. For example, if the error was in the framing of a UART message, I'd ask whether there was a protocol conformance test that should have caught it, and whether the test plan was adequate. In the process improvement phase, I'd implement changes to prevent recurrence — this might include adding protocol-level tests (e.g., using a logic analyzer to capture actual bus traffic and compare against the specification), improving the design review checklist, or adding a peer-review step for protocol implementations. I'd also work with the engineer to ensure they understand the error and feel supported in fixing it — this is a learning opportunity, not a punitive one. In a medical device context, I'd also consider whether the error has implications for the risk management file — if the protocol error could have caused a safety issue, it needs to be documented and the risk assessment updated. Finally, I'd communicate the findings and the corrective actions to the regulatory team and management, being clear about the impact on the schedule and the steps being taken to mitigate it.

**Possible follow-ups:** How would you balance the need to fix the issue quickly against the need to understand the root cause before making changes? What specific test would you add to the verification plan to catch this class of error in the future?
