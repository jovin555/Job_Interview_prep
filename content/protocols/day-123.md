# protocols — Day 123

## Q1: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The core idea is to define a transport-agnostic interface at the boundary between the application and the drivers, then implement that interface once per physical transport. Concretely, I'd define an abstract "sensor transport" contract with a small set of operations — open/configure, a read or transaction call, a write call, and a way to register a completion or error callback — expressed in terms of logical operations (e.g., "read register N," "stream samples") rather than bus-specific primitives. Each transport then provides an adapter that maps those logical operations onto its own mechanics: I2C does a repeated-start register read, SPI asserts a chip select and clocks bytes, UART frames a request/response, CAN-FD packs the request into a message ID and payload. The application layer only ever sees the abstract contract and a device descriptor that says which transport instance to bind to.

The important design decisions are: (1) keep the interface *synchronous-looking* even if the underlying transport is async, by having the adapter own the state machine and expose either a blocking call or a completion callback consistently; (2) push all transport-specific error semantics (NACK, CRC error, framing error, bus-off) into a normalized error enum so the application can reason about "retryable vs fatal" without knowing the bus; (3) keep timing and buffering policy in the adapter, since a UART needs flow control while SPI does not; and (4) make the binding configurable at build or init time so the same application binary can run against a bench harness that fakes the transport. The payoff is testability — you can unit-test the application against a mock transport — and portability when a sensor moves from one bus to another during a redesign.

**Possible follow-ups:** Where would you put retry logic — in the adapter or the application — and why? How do you handle a transport that has fundamentally different latency characteristics (e.g., a 2 ms CAN-FD round trip vs a 50 µs SPI read) without leaking that into the application's timing assumptions?

## Q2: You're debugging an I2C bus where communication works reliably at 100 kHz but produces intermittent NACKs at 400 kHz, with the same devices and the same PCB. How would you approach this?

**Answer:** Since the devices and board are identical, the difference is purely timing and signal integrity at the higher edge rate, so I'd treat it as a physical-layer problem first and a protocol problem second. At 400 kHz the rise times matter much more: I'd start by scoping SDA and SCL and looking at rise time versus the I2C spec limit, checking whether the pull-ups are too weak for the actual bus capacitance. A bus that's marginal at 100 kHz can look fine because there's plenty of time to settle, then fail at 400 kHz because the rise time eats into the setup/hold window. I'd measure the actual bus capacitance (or estimate from trace length and device pin capacitance) and recompute the pull-up value against both the rise-time requirement and the sink-current limit of the drivers.

Next I'd look at whether the NACKs correlate with a specific device or a specific transaction type — a slave that's slow to respond, or one whose internal state machine can't keep up at the faster clock. I'd check for clock stretching behavior and whether the master's timing respects it. I'd also look at whether the failures cluster when multiple devices are active, which points to cumulative capacitance or a shared pull-up that's undersized for the total load. If the scope shows clean edges but NACKs persist, I'd suspect a device that's genuinely marginal at 400 kHz and consider dropping that segment to 100 kHz, splitting the bus, or using a bus buffer/expander to isolate capacitance. The disciplined approach is to separate "is the waveform compliant" from "is the device responding," because those lead to different fixes.

**Possible follow-ups:** How would you decide between lowering the bus speed versus adding a buffer versus splitting into two buses? What would you check first if the scope showed a clean waveform but NACKs still occurred only on one device?

## Q3: You're designing a half-duplex RS-485 link where the driver-enable and receiver-enable must switch at exactly the right moment, and the turnaround budget is tight. How would you approach this?

**Answer:** Half-duplex RS-485 turnaround is fundamentally a timing-budget problem, so I'd start by writing down the budget explicitly: the time from the last stop bit leaving the UART, through the transceiver's driver-disable propagation delay, the bus settling time (dominated by the termination and cable), the receiver-enable and transceiver receive delay, and the time for the first start bit to be sampled. If that sum exceeds the gap the protocol allows, the link will drop or corrupt the first byte after turnaround, and it'll be intermittent and load-dependent, which is the worst kind of bug.

On the hardware side I'd make sure the transceiver's enable pins are driven by a GPIO with known, fast, deterministic timing rather than sharing a slow-expanding signal, and I'd check whether the transceiver has separate DE and /RE pins so I can control transmit and receive independently rather than tying them together. On the firmware side I'd drive the enable from the UART's transmit-complete interrupt rather than from "I wrote the last byte to the FIFO," because the FIFO-empty interrupt fires far too early and you'll disable the driver mid-byte. I'd also add a small guard delay after transmit-complete before releasing the bus, sized from the transceiver datasheet plus margin, and I'd verify the whole thing on a scope at the worst-case baud rate and cable length. If the budget is genuinely too tight, the options are to lower the baud rate, shorten the cable, or move to a protocol that tolerates a longer turnaround (or full-duplex RS-422 if the topology allows).

**Possible follow-ups:** How would you verify the turnaround timing on a scope, and what would you look for in the waveform? What happens if two nodes both think the bus is idle and start driving at the same moment?

## Q4: In a CAN-FD network, how would you approach guaranteeing that a high-priority safety-critical message is never delayed by more than a bounded time, given that lower-priority telemetry also shares the bus?

**Answer:** The guarantee comes from the arbitration model, but only if you design the whole system around it rather than assuming it. CAN-FD is priority-based with deterministic arbitration: a lower-ID frame wins arbitration over a higher-ID frame, and once a frame starts transmitting it can't be preempted (except by an error frame). So the worst-case latency for the critical message is bounded by the longest frame that could already be in flight when it becomes ready, plus the arbitration and transmission time of the critical frame itself, plus any error-recovery time. I'd start by assigning the critical message the lowest numeric ID so it always wins arbitration, then compute the worst-case blocking time from the largest possible lower-priority frame — which in CAN-FD means a 64-byte data-phase frame at the higher bit rate, so the data-phase bit rate directly shrinks that blocking term.

Then I'd bound the *arrival* jitter: the critical message must be queued and ready to transmit within a known time, so I'd make sure its producer task has deterministic scheduling and isn't blocked behind telemetry processing. I'd also account for error frames and bus-off recovery, because a single error frame can add a retransmission delay — so the guarantee has to include a stated error-rate assumption or a worst-case error-recovery budget. Finally I'd validate it empirically with bus-loading tests at the maximum telemetry rate and measure the actual latency distribution, not just the average, because the guarantee is about the tail. If the computed worst case exceeds the requirement, the levers are: raise the data-phase bit rate, cap the maximum telemetry frame size, reduce telemetry rate, or move telemetry to a separate bus.

**Possible follow-ups:** How does the CAN-FD data-phase bit rate change the worst-case blocking time compared to classic CAN? What would you do if a single error frame could still blow the latency budget?

## Q5: You're leading a design review where a junior engineer proposes a custom application-layer protocol over UART for a medical device, and you notice the framing has no length-field validation and no sequence numbers. How would you guide the team to evaluate and improve the design?

**Answer:** I'd treat this as a teaching moment rather than a "this is wrong" moment, because the goal is for the team to see the failure modes themselves. I'd start by asking the engineer to walk through what happens when a single bit flips in the length field — that's usually enough to make the problem concrete: the receiver consumes the next several valid frames as payload and silently corrupts data, with no way to detect it. Then I'd ask what happens on a dropped or duplicated frame, which is where sequence numbers come in. Framing the review around "what failure modes must this protocol survive" rather than "what's missing" gets the whole team engaged and produces a better design than me dictating one.

From there I'd guide toward a concrete set of improvements: a length field with a sanity bound (reject frames claiming more bytes than the buffer can hold), a checksum or CRC over the frame so corruption is detected rather than silently accepted, sequence numbers so the receiver can detect loss and duplication, and a defined resynchronization strategy so the receiver can recover after a bad frame instead of staying permanently out of sync. I'd also connect it to the regulatory context — for a medical device, silent data corruption is exactly the kind of failure that has to be designed out and documented, so the protocol needs to be defensible in the risk analysis, not just "it works on the bench." I'd assign the engineer to revise the design and bring it back, which keeps ownership with them and turns the review into a growth step.

**Possible follow-ups:** How would you decide between a simple checksum and a full CRC for this link? How do you document a protocol design like this so it holds up in a regulatory submission?
