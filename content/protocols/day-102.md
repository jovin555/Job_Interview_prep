# protocols — Day 102

## Q1: You're debugging a USB 2.0 device that draws more than 100 mA but is configured as a bus-powered device with a single configuration descriptor claiming 100 mA. It enumerates fine on a self-powered hub but resets intermittently when plugged directly into a host root port. How would you approach this?

**Answer:** The symptom pattern — works behind a self-powered hub, fails on a root port — points at the power budget negotiation rather than the USB protocol itself. A bus-powered device is only guaranteed 100 mA until it is configured; after `SetConfiguration`, it may draw up to the `bMaxPower` value it declared in the configuration descriptor (in 2 mA units, so 50 = 100 mA). If the firmware actually draws more than it declared, the host has no way to know, and a root port with a tight current limit or a polyfuse with a slow trip characteristic will brown out or reset the device under load. The self-powered hub masks this because its downstream port can source more current than the root port's budget.

My approach would be: first, measure actual current draw in each state (unconfigured, configured-idle, configured-active) and compare against the declared `bMaxPower`. Second, check whether the device ever exceeds 100 mA before `SetConfiguration` completes — that is a spec violation regardless of what the descriptor says later. Third, if the real draw genuinely exceeds 100 mA, the correct fix is to declare the true `bMaxPower` (up to 500 mA for USB 2.0) so the host can refuse configuration on a port that can't supply it, rather than letting it brown out silently. Fourth, if the device is capable of running self-powered, consider exposing two configurations or using the `bmAttributes` self-powered bit so the host treats the budget differently. I'd also look at inrush — a large bulk decoupling cap that charges at attach can trip a root port's overcurrent protection even if steady-state draw is fine, so soft-start or inrush limiting may be needed.

**Possible follow-ups:** How would you distinguish an inrush problem from a steady-state overcurrent problem using only a scope and a USB protocol analyzer? What does the host do if a device tries to draw more than its declared `bMaxPower` — is there any enforcement mechanism, or is it purely advisory?

## Q2: In an I2C system with a master and several slaves, one slave's address is fixed in silicon and collides with another device you need on the same bus. You cannot change either address. How would you approach resolving this?

**Answer:** Address collision with immutable addresses is a common real-world constraint, and the solution space is really about inserting isolation or indirection rather than changing the devices. The options, roughly in order of preference:

First, an I2C multiplexer or switch — a device that presents one upstream address to the master and fans out to multiple downstream segments, only one of which is connected at a time. This is the cleanest fix because it also gives you bus capacitance relief and fault isolation, which matters on a medical device where a stuck slave shouldn't take down the whole bus. The cost is an extra control transaction before every access and a small added latency.

Second, if the two colliding devices are never accessed concurrently and one is on a removable or optional module, a bus switch (a simple analog mux on SDA/SCL) gated by a GPIO can isolate the offending device when it's not in use. This is cheaper than a full I2C mux but requires careful sequencing so the switch is never toggled mid-transaction.

Third, if one of the devices supports an address-select pin or an alternate address via a strap, use it — even if the datasheet lists a "fixed" default, many parts have a strappable variant.

Fourth, a last resort is a small microcontroller acting as a protocol bridge: it owns the colliding device on a private bus and exposes a different address upstream. This adds firmware and a failure mode, so I'd only do it if the first three options are physically impossible.

Whichever route, I'd document the topology and the access sequencing in the interface control document, because a future engineer adding a device to the bus needs to know the collision exists.

**Possible follow-ups:** What are the trade-offs of an I2C mux versus a bus switch in terms of fault containment and added latency? How would you verify that the mux's own address doesn't collide with anything else on the upstream segment?

## Q3: You're bringing up a new board where an SPI flash device shares the bus with a sensor, and the flash is on a separate power rail that comes up later than the MCU. During early boot, the MCU probes the sensor and sees corrupted responses. How would you approach this?

**Answer:** The classic cause here is a partially-powered slave on a shared bus. An unpowered or ramping SPI slave can present a low-impedance path on MISO through its ESD protection diodes, effectively pulling the shared MISO line toward its rail and corrupting transactions to the *other* device — even though the other device is healthy. The sensor's responses get mangled because MISO is being fought over by a device that isn't even supposed to be talking.

My approach: first, confirm the mechanism by scoping MISO during a sensor transaction while the flash rail is off — you'd expect to see the line clamped or dragged rather than cleanly driven. Second, check the sequencing: does the flash's chip select float or get driven during the window when its rail is down? A floating CS on an unpowered device is worse than a driven-high one, because the device may partially power itself through the CS pin. Third, the fixes are architectural: either bring the flash rail up before any bus traffic (sequencing), or add a bus switch / series isolation on the flash's MISO so it can't load the bus while unpowered, or ensure the flash's CS is held high (and its rail is the last to come up) so it stays tri-stated. Fourth, in firmware, gate all SPI access behind a "rail ready" check so the driver never probes a device whose supply isn't valid.

The general principle is that on a shared bus, every slave must be in a defined, high-impedance state whenever it isn't the selected device — and "unpowered" is not a defined state unless you design for it.

**Possible follow-ups:** How would you decide between adding a bus switch versus simply resequencing the power rails? What firmware-side safeguards would you put in place to catch a similar issue on a future board revision?

## Q4: You're designing a sensor network for a medical device where one node is a closed-loop pressure controller that must see fresh data every 2 ms, and another node streams high-volume waveform data that can tolerate 50 ms of latency. They must share one physical medium. How would you approach the architecture?

**Answer:** The core tension is determinism versus throughput on a shared medium, and the right answer usually comes from separating the two concerns rather than trying to make one protocol serve both. I'd start by characterizing the traffic: the control node needs small, frequent, bounded-latency messages; the waveform node needs large, bursty, latency-tolerant transfers. Those are almost opposite requirements, which suggests either a protocol with priority arbitration (CAN-FD, or a time-slotted scheme) or physically separating the paths.

If a single medium is a hard requirement, CAN-FD is attractive because arbitration is priority-based and non-destructive: the control node's low-ID frames win arbitration deterministically, and the waveform node's higher-ID frames yield. The key design work is then to bound the control node's worst-case latency — which means analyzing the waveform node's maximum frame size and the resulting blocking time, and possibly capping the waveform payload or splitting it across multiple frames so a single long frame can't monopolize the bus. I'd also reserve a time slot or use a periodic schedule if the control loop's deadline is truly hard, because priority arbitration alone gives you a bound only if you can bound the longest lower-priority frame.

If the medium can be split, a cleaner architecture is a dedicated deterministic link for the control node (a point-to-point or small dedicated bus) and a separate higher-throughput link for telemetry, with the two meeting at a gateway. That trades cabling and connector cost for much simpler timing analysis.

Either way, I'd write the latency budget down explicitly — control node deadline, worst-case blocking, jitter allowance — and verify it against the actual frame sizes and bit rates before committing to the topology.

**Possible follow-ups:** How would you bound the worst-case latency of the control frame if the waveform node is allowed to send maximum-size CAN-FD frames? What would change if the control loop deadline were 500 µs instead of 2 ms?

## Q5: A junior engineer on your team has implemented a custom framing protocol over UART, and during regulatory compliance testing it's discovered that a single bit error in the length field causes the receiver to consume the next several valid frames as payload, silently corrupting data. How would you handle the situation?

**Answer:** The first priority is containment and root cause, not blame. I'd treat it as a design defect in the protocol, not a personal failing — the framing scheme lacked a resynchronization mechanism, which is a design-level gap that a review should have caught. My sequence would be:

First, stop the bleeding: assess whether the corrupted data could have affected any safety-relevant function or any test result already submitted, and if so, escalate through the quality system immediately. In a regulated context, a data-integrity defect discovered during testing is a finding that needs to be documented and dispositioned, not quietly patched.

Second, root-cause the protocol: the length field has no protection, and there's no way for the receiver to detect that it has lost frame alignment. The fix is a proper framing layer — a start delimiter plus a length field protected by its own checksum, a frame CRC covering the whole frame, and an explicit resynchronization rule (e.g., scan for the next start delimiter after a CRC failure, with a bounded resync window). I'd also add a maximum-frame-length sanity check so a corrupt length can't cause an unbounded read.

Third, process: this is exactly the kind of defect a protocol conformance test plan should catch before regulatory testing — fault injection on the length field, truncated frames, and bit-flip tests. I'd add those cases to the test plan and to the design review checklist so the next protocol gets reviewed against a framing-robustness template.

Fourth, on the people side: I'd walk the engineer through the failure mechanism and the fix collaboratively, framing it as "the review process missed this too," and make sure they own the corrected design and the new test cases. That turns a schedule hit into a durable process improvement rather than a demoralizing incident.

**Possible follow-ups:** What specific fault-injection tests would you add to the conformance plan to catch this class of defect earlier? How would you handle the schedule impact with project management — what would you communicate and when?
