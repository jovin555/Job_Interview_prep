## Q1: How would you approach debugging an I2C bus where a device intermittently NACKs its address, but only when the bus is running at 400 kHz and only after the board has been running warm for a while?

**Answer:** The two qualifiers — speed-dependent and temperature-dependent — are the diagnostic keys, and I'd treat them as separate hypotheses that may interact. First, I'd confirm the failure is genuinely an address NACK and not a misclassified arbitration loss or bus error by capturing the bus with a logic analyzer or scope with I2C decode, triggering on the NACK. That tells me whether the device is present but not responding, or whether the transaction is being corrupted before the address byte completes.

On the speed axis, at 400 kHz the rise times through the pull-ups and bus capacitance become significant. If the pull-ups are sized for 100 kHz, the bus may not reach a valid high level within the fast-mode timing budget, and a marginal device can sample the address bits incorrectly. I'd measure actual rise time against the fast-mode spec and check total bus capacitance against the 400 pF limit, then recalculate pull-ups for the worst-case combination of VOL, leakage, and capacitance. I'd also check whether the device's own timing margins are being eroded — some parts have minimum bus-free and setup times that get tight at 400 kHz.

On the temperature axis, warm-up drift points at analog margin: pull-up resistors with poor temperature coefficient, a device whose internal timing or reference drifts, or a marginal solder joint or connector that opens slightly with thermal expansion. I'd use freeze spray or a heat gun to localize which component is temperature-sensitive, and check whether the NACK correlates with a specific board region. If the device has a configurable address or an address pin tied through a resistor, thermal drift on that node could push the threshold.

The interaction matters too: a device that's marginal on setup time at 400 kHz may only fail once temperature shifts its internal delays. So I'd fix the electrical margin first — pull-ups, capacitance, decoupling — and then re-test across temperature to confirm the margin is genuinely restored rather than just masked.

**Possible follow-ups:** How would you distinguish a genuine address NACK from a bus error or arbitration loss on the capture? If recalculating the pull-ups doesn't fix it, what's your next hypothesis?

## Q2: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The goal is to keep transport mechanics out of application logic while not hiding the properties the application genuinely needs — latency, determinism, error semantics, and payload size limits differ enough between these transports that a leaky abstraction causes real bugs. So I'd design around a small transport-agnostic interface: open/close, a read and a write that take a buffer and length, and a status/error return. Everything transport-specific — addressing, framing, retries, timing — lives behind that interface in per-transport drivers.

The key design decision is where framing sits. If each transport does its own framing, the application sees different message boundaries depending on the bus, which defeats the purpose. I'd put a common message layer above the transport interface that handles length, sequence numbers, and integrity checking, and let the transport layer only move bytes. That way a sensor driver written against the message layer works unchanged whether the bytes go out over I2C or CAN-FD.

I'd also expose transport capabilities as metadata rather than assuming uniformity: maximum payload, whether the link is reliable or best-effort, typical and worst-case latency, and whether it supports broadcast. The application can then make informed choices — for example, choosing a shorter poll interval on a deterministic link — without hard-coding a specific bus.

For testability, I'd provide a loopback or mock transport so the application and message layers can be unit-tested without hardware, and a conformance test suite that runs the same behavioral tests against every transport implementation. That's how you catch a driver that quietly violates the contract.

**Possible follow-ups:** How would you handle a transport that can't guarantee message delivery — does retry belong in the transport layer or above it? Where would you put error reporting so the application can distinguish "sensor fault" from "bus fault"?

## Q3: You're debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward. How would you approach this?

**Answer:** Bus-off means the transmit error counter exceeded 255, so the controller has removed itself from the bus by design. The fact that the bus looks healthy afterward tells me the fault was transient and the node isn't recovering on its own — either auto-recovery isn't enabled or the recovery logic isn't running. I'd separate those two questions: why did the error counter climb, and why didn't the node come back?

For the first, I'd capture the bus around the event and look at what the node was transmitting when errors accumulated. Common causes: a bit-timing mismatch between nodes (sample point or SJW set differently, so one node misreads bits at the data-phase rate), a node transmitting into a dominant bit it didn't expect, termination or stub issues that corrupt the data phase at the higher bit rate, or a transceiver that's marginal. CAN-FD makes this sharper because the data phase runs much faster than arbitration, so a bus that's fine at the arbitration rate can fail only in the data phase — I'd check whether bus-off correlates with long-payload frames.

I'd also look at the error counters over time rather than just at the bus-off moment. A node creeping up on TEC suggests repeated errors on transmit; a node with high REC suggests it's hearing corrupted traffic. That distinction points at the culprit versus the victim.

For the recovery question, I'd check the controller configuration: is automatic bus-off recovery enabled, and if not, is the firmware's recovery path actually being reached? A common bug is that the recovery is implemented but the error interrupt that should trigger it is masked or the handler doesn't clear the condition properly. I'd also consider whether recovery should be automatic in a medical device — an uncontrolled auto-recovery can flap, so a deliberate recovery with logging and a bounded retry policy is often the safer design.

**Possible follow-ups:** How would you determine whether the bus-off node is the cause or a victim of the errors? What recovery policy would you choose for a safety-critical node, and why?

## Q4: How would you approach selecting between RS-422 and RS-485 for a medical device that needs to connect a central controller to several distributed sensor modules?

**Answer:** The core difference is that RS-422 is a point-to-point or one-driver-to-many-receivers arrangement, while RS-485 is a true multi-point bus where multiple drivers share the same pair and take turns. So the first question is topology: if the central controller is the only transmitter and the sensor modules only ever receive, RS-422 gives you a simpler, inherently collision-free link with a dedicated driver. If the modules need to transmit back — which they almost always do for sensor data — you need RS-485's multi-driver capability with turn-around management.

I'd then weigh the practical consequences. RS-485 half-duplex means every node must switch between transmit and receive at the right moment, which introduces turn-around timing, driver-enable control, and the risk of bus contention if two nodes drive at once. That's real firmware and hardware complexity, and in a medical device it's also a failure mode to analyze. RS-422 avoids that but costs you a separate pair per direction, which matters if cabling is constrained.

Other factors: node count and cable length against the data rate, common-mode voltage range (RS-485 typically specifies a wider range, which matters in electrically noisy clinical environments), fail-safe biasing requirements, and termination strategy. For a medical device I'd also factor in what happens on a fault — a stuck driver on an RS-485 bus can hold the whole bus dominant, so I'd want fail-safe biasing and possibly isolation.

My default for a multi-drop sensor network where modules must talk back is RS-485, but I'd document the reasoning against RS-422 rather than treating it as automatic, because if the traffic pattern is genuinely one-way, RS-422 is simpler and easier to validate.

**Possible follow-ups:** How does the common-mode voltage range requirement differ between the two, and why does it matter clinically? What would push you toward adding galvanic isolation on either interface?

## Q5: How would you handle a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** My first priority is containment and honesty: understand exactly what's wrong, how it affects the test results and any data already collected, and communicate that to the project lead and quality function promptly. In a regulated environment, an issue found in testing isn't just a schedule problem — it's a traceability and documentation problem, so I'd want the finding captured formally rather than fixed quietly.

Then I'd separate the technical fix from the process question. Technically, I'd work with the engineer to characterize the defect precisely — what the protocol does versus what it should do, which test cases exposed it, and whether the fix is localized or touches the framing, state machine, or error handling broadly. I'd want a regression test that reproduces the failure before the fix, so we can prove it's actually resolved and that the fix doesn't break adjacent behavior.

On the process side, the honest question is why it escaped earlier review and unit testing. That's usually a gap in the test plan or review checklist, not just an individual mistake, and I'd frame it that way — the goal is to strengthen the process, not assign blame. I'd look at whether the protocol spec was clear enough, whether there were conformance tests against it, and whether review actually covered the framing and error paths.

With the engineer, I'd be direct but constructive: explain the impact, involve them in the fix and the test design so they own the correction, and make sure they understand why the gap mattered. Blame shuts down learning; a clear-eyed review of what happened and what changes prevents the next one.

**Possible follow-ups:** How would you decide whether to fix forward or re-run the full compliance test campaign? What would you change in the review process to catch this class of defect earlier?
