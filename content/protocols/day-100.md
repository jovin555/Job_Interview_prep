## Q1: How would you approach debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward?

**Answer:** Bus-off means the node's transmit error counter (TEC) exceeded 255, so the first question is *why* the node accumulated that many errors — the bus looking healthy afterward is a red herring, because the fault may be transient or may be specific to that node's view of the bus. I'd start by pulling the node's error counters and error-warning/error-passive transitions from logs or a diagnostic interface, and correlate the timing of bus-off events with what else is happening on the network. Common root causes fall into a few buckets: a bit-timing mismatch (sample point or SJW configured differently from the rest of the network, so the node mis-samples under certain bit patterns), a physical-layer issue local to that node (bad transceiver, marginal termination at its stub, common-mode drift), or a firmware issue where the node transmits when it shouldn't — for example retrying a frame in a tight loop, or transmitting before the controller is fully synchronized after a wake-up. I'd also check whether the node is the only one with a particular transceiver or layout variant. On the recovery side, staying bus-off until a manual reset is itself a design smell: per the CAN standard, recovery requires 128 occurrences of 11 recessive bits, and most controllers can do that automatically if the firmware re-enables the controller after the bus-off interrupt rather than latching the fault. So I'd separate two fixes — root-cause the error accumulation, and make the recovery path automatic and observable (log the event, count it, and only escalate to a safe state if bus-off recurs within a defined window).

**Possible follow-ups:** How would you distinguish a bit-timing/sample-point problem from a physical-layer problem using only the error counters and a scope? What safe-state behavior would you define for a node that has recovered from bus-off but may have missed safety-critical frames while off the bus?

## Q2: How would you approach selecting between RS-422 and RS-485 for a medical device that needs to connect a central controller to several distributed sensor modules?

**Answer:** The decision usually comes down to topology and directionality rather than raw electrical performance, since both share the same differential signaling basis. RS-422 is essentially point-to-point or one-driver-to-many-receivers: one transmitter, up to ten receivers, full-duplex if you use two pairs. RS-485 is multipoint: multiple drivers share one pair, half-duplex, with driver enable arbitration and the associated turnaround timing. So if the architecture is a central controller polling distributed sensor modules — many nodes, one bus, nodes only speak when addressed — RS-485 is the natural fit and RS-422 would force a star of separate pairs back to the controller, which is usually impractical over distance. If instead the controller streams continuously to displays or receiver-only modules and never needs the reverse path on the same pair, RS-422's simpler, always-driven configuration removes turnaround and arbitration concerns entirely. I'd also weigh: number of nodes and whether any node ever needs to initiate, cable length and stub constraints, whether the protocol needs a reverse channel for acknowledgements or firmware update, and the fail-safe biasing and termination burden (RS-485 multipoint needs bias and termination sized for the whole bus; RS-422 point-to-point is simpler). For a medical device I'd add that the chosen topology should make failure modes easy to reason about — a half-duplex bus where one node can hold the driver enabled is a hazard you have to design against, whereas a receive-only path can't create that failure.

**Possible follow-ups:** If the sensor modules are receive-only today but you expect a future firmware-update requirement, does that change your answer? How would termination and biasing differ between the two in a multi-drop layout?

## Q3: You're debugging a USB 2.0 device that intermittently fails enumeration on one particular host, where the failure appears as a control-transfer timeout during descriptor reads, but the same device enumerates reliably on other hosts. How would you approach this?

**Answer:** A control-transfer timeout during descriptor reads, host-specific, points at the interaction between the device's control endpoint behavior and that host's timing/tolerance — not at the descriptors being malformed, since other hosts parse them fine. I'd first capture a bus trace on the failing host (a hardware analyzer if available, otherwise host-side USBPcap/Wireshark) and compare it to a passing host: where exactly does it stall — after SETUP, during the DATA stage, or waiting for the status stage? That tells me whether the device is slow to respond, returning a STALL, or the host is retrying in a way the device mishandles. Frequent culprits: the device taking too long to prepare the first descriptor response after reset (some hosts have tighter timeouts than others), a control endpoint that doesn't correctly handle the zero-length status stage or a SETUP arriving while a previous transfer is still pending, or a max-packet-size mismatch on EP0 causing the host to expect more data. I'd also check whether the failing host is behind a hub or a different controller type (EHCI vs xHCI vs a legacy companion controller), since some embedded hosts are stricter about babble, NAK timing, or short packets. On the firmware side I'd make EP0 handling strictly event-driven and never block the control endpoint while servicing other interfaces, and verify the device responds to standard requests (GET_DESCRIPTOR, SET_ADDRESS, SET_CONFIGURATION) within spec timing. The fix is usually making the device more conservative and spec-exact rather than special-casing the host.

**Possible follow-ups:** How would you tell apart a device-side timing problem from a host-driver quirk if you can't get a bus analyzer? What descriptor or EP0 configuration choices make a device more tolerant of strict hosts?

## Q4: How would you approach designing fail-safe biasing for an RS-485 bus, and why does it matter more in a medical device than in a general industrial network?

**Answer:** Fail-safe biasing guarantees a defined logic level on the differential pair when no driver is active — otherwise the idle bus floats and receivers can output random states or oscillate, generating spurious start bits and framing errors. The standard approach is a pull-up on one line and a pull-down on the other, sized so the differential voltage stays above the receiver's threshold (typically a few hundred millivolts) even with termination loading and the worst-case number of transceivers on the bus. The calculation has to account for the parallel termination resistance, the input leakage/bias current of every receiver, and the supply rail — and it interacts with termination: you can't size bias resistors in isolation from the termination network. Many modern transceivers have "true fail-safe" receivers with a shifted threshold that reduce or eliminate the need for external bias, which is worth checking before adding resistors that load the bus. It matters more in a medical device because an undefined bus state isn't just a data-integrity nuisance — it can manifest as a spurious byte or a false frame that a higher layer might interpret as a command or an alarm, and because the bus may sit idle for long periods (between patient readings) where a floating line is the steady state rather than a transient. So I'd treat fail-safe biasing as part of the safety analysis, not just a signal-integrity nicety, and verify it across the full node count and temperature range rather than at nominal.

**Possible follow-ups:** How would you verify fail-safe biasing empirically on a populated bus? What happens to your bias calculation if nodes are hot-plugged or powered down while the bus stays powered?

## Q5: How would you handle a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** First I'd separate the immediate from the systemic. Immediately: contain the schedule and compliance impact — understand exactly what the protocol defect is, whether it's a functional failure or a documentation/traceability gap, whether any test results are invalidated, and what the shortest defensible path to re-test is. I'd get the facts before assigning blame, because "discovered in compliance testing" often means the defect was latent and the test process did its job. Then I'd work the root cause honestly: was the protocol spec ambiguous, was there no unit/integration test that would have caught it earlier, was the review process skipped, or was it a genuine implementation mistake? The answer changes the corrective action — if the spec was ambiguous, fixing the engineer alone doesn't prevent recurrence. I'd involve the junior engineer in the investigation rather than sidelining them; the goal is a learning event, not a punishment, and they'll understand the failure mode better than anyone. Systemically, I'd add the missing verification layer — protocol conformance tests, a fault-injection test pass, or a review gate — so this class of defect is caught before formal testing next time, and I'd feed the lesson into how the team reviews protocol code. I'd also be candid with stakeholders about the schedule impact and the plan, without scapegoating, because a team that hides defects to avoid blame is a bigger risk than the delay itself.

**Possible follow-ups:** How would you decide whether to re-run the full compliance test suite or only the affected subset? What would you change in your review process to catch protocol defects before formal testing?
