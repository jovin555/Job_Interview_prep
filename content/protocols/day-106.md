# protocols — Day 106

## Q1: How would you approach debugging an I2C bus where a slave device occasionally stretches the clock longer than the master's timeout allows, causing the master to abort mid-transaction and leave the bus in an inconsistent state?

**Answer:** I'd start by characterizing the failure rather than guessing. First, capture the bus with a logic analyzer or scope in protocol-decode mode and measure the actual stretch duration against the master's configured timeout — the gap between the slave releasing SCL and the master resuming is the number that matters. If the stretch is only marginally over the timeout, the fix may be as simple as raising the master's timeout to a value the slave datasheet actually guarantees, since many masters default to a timeout far shorter than the slowest slave's worst-case conversion time.

If the stretch is legitimately long (a sensor doing an internal conversion, for example), the real question is architectural: either the master must tolerate it, or the transaction must be restructured so the slave isn't asked to hold the bus while it works. That usually means splitting a blocking read into a "start conversion" write followed later by a "read result" transaction, so the slave never needs to stretch at all. That's the cleaner fix in a medical device because it removes the timing dependency entirely.

For the inconsistent-state problem after an abort: the master must have a recovery path. If it aborted mid-byte, the slave may still be driving SDA. The standard recovery is to clock SCL manually (as GPIO) up to nine times until the slave releases SDA, then issue a STOP condition, then re-init the peripheral. I'd build that recovery into the driver rather than leaving it to a power cycle, and I'd add a bus-health check before the next transaction so a stuck bus is detected and recovered deterministically instead of silently corrupting the next read.

**Possible follow-ups:**
- How would you decide whether to raise the master timeout versus restructure the transaction, and what evidence would drive that call?
- What would you log or count to prove the recovery path actually works over long-run testing rather than just on the bench?

## Q2: How would you approach selecting between a star topology and a daisy-chain topology for a multi-drop sensor network in a medical device where the sensors are physically distributed?

**Answer:** I'd frame it as a signal-integrity and fault-containment trade-off, not a wiring-convenience one. A star (home-run) topology gives each node its own segment back to a central point, which keeps stub lengths short, limits the capacitance and reflections any one node contributes, and — importantly for a medical device — contains a single node's fault to its own branch. The cost is cable volume and connector pin count at the hub, which matters if the device is wearable or the cable bundle has to flex.

A daisy-chain keeps the harness simple and the cable mass low, but every node sits on one continuous bus, so total capacitance, stub length, and the effect of one bad transceiver are shared by everyone. Termination also gets harder because the ends of the chain are far apart and any intermediate tap is a stub.

My approach: enumerate the physical constraints first — maximum cable run, node spacing, whether nodes are on a flex circuit, whether the device moves during use — then check them against the electrical limits of the chosen PHY (RS-485 stub length and common-mode range, or CAN-FD's bit-rate-versus-bus-length curve). If any node's spacing or the total run pushes past those limits, star or a segmented hybrid wins. If the harness must be minimal and the run is short, daisy-chain is fine. For a safety-relevant network I also weigh fault containment heavily: a star makes it far easier to guarantee that one failed node can't take down monitoring for the others.

**Possible follow-ups:**
- How would a hybrid — a star of short daisy-chained segments — change your analysis, and where would you put the segment boundaries?
- How does the choice interact with termination and fail-safe biasing at the physical layer?

## Q3: You're debugging a CAN-FD network where a node intermittently enters error-passive state and then recovers on its own, with no obvious pattern. How would you approach this?

**Answer:** Error-passive means the node's transmit or receive error counter crossed the threshold, so the first job is to find out which counter is climbing and why, rather than treating "it recovers" as good enough. I'd instrument the node to log the error counters and the specific error types — bit error, stuff error, CRC error, form error, ACK error — with timestamps, and correlate against bus traffic. The error type usually points straight at the cause: ACK errors suggest the node is transmitting when no one else is listening or the bus is being disconnected momentarily; bit errors suggest a physical-layer or termination problem; stuff/CRC errors suggest a marginal signal or a baud-rate mismatch between nodes.

The "no obvious pattern" part is the interesting clue. Intermittent, self-recovering error-passive transitions often trace to something environmental or timing-dependent: a connector or termination that's marginal and shifts with temperature or vibration, a node whose sample point or bit timing is set slightly differently from the rest so it's the first to fail as margins shrink, or a ground-offset issue between nodes that only shows up under certain load. I'd check that all nodes share identical bit-timing and sample-point configuration first, since a single mis-configured node will consistently be the weakest link. Then I'd look at the physical layer — termination at both ends, stub lengths, common-mode — and try to reproduce the event by stressing temperature, supply, or bus load.

The recovery behavior itself also deserves scrutiny: a node that goes error-passive and comes back is masking a real fault, so I'd want the firmware to log and ideally flag it rather than silently continue, especially in a medical device where degraded communication is itself a reportable condition.

**Possible follow-ups:**
- How would you distinguish a bit-timing/sample-point mismatch from a physical-layer marginality using only the error counters and a scope?
- What would you want the firmware to do on entering error-passive in a safety-relevant device — keep transmitting, back off, or flag to the application?

## Q4: How would you approach implementing flow control on a UART link where the receiver occasionally cannot keep up with the transmitter, but the protocol has no built-in backpressure mechanism?

**Answer:** I'd first separate two cases: whether the hardware has RTS/CTS available and just isn't using it, or whether the link genuinely has no flow-control pins. If RTS/CTS pins exist, enabling hardware flow control is almost always the right answer — it's handled by the UART peripheral, it's fast enough to react within a byte or two, and it doesn't consume CPU. The receiver asserts RTS when its buffer crosses a high-water mark and de-asserts below a low-water mark, with hysteresis so it doesn't chatter.

If there are truly no flow-control lines, I'd add backpressure at the protocol layer: an ACK/credit scheme where the transmitter is only allowed a bounded number of outstanding frames, or a simple XON/XOFF software scheme if the payload can be escaped so control characters never appear in data. XON/XOFF is cheap but fragile — it adds latency and breaks if the receiver's own buffer overflows before it can send XOFF — so I'd only use it where the data rate is modest and the receiver has enough headroom to react.

The other lever is to make the receiver fast enough that backpressure is rarely needed: size the RX ring buffer to absorb the worst-case burst, and make sure the ISR or DMA path drains it promptly. In a medical device I'd also want the link to fail safe — if the receiver does drop data despite everything, the protocol needs a sequence number or checksum so the application knows a frame was lost rather than silently using stale or partial data.

**Possible follow-ups:**
- How would you size the receive buffer, and what determines the high/low water marks for RTS?
- Why is XON/XOFF risky when the payload is binary, and how would you make it safe if you had to use it?

## Q5: How would you handle a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** The first priority is containment and honesty: understand exactly what's wrong, what test it failed, and whether it's a test-setup artifact or a genuine design defect, because those lead to very different responses. I'd get the facts straight before assigning blame — pull the failing test evidence, reproduce it, and confirm the root cause with the engineer rather than announcing a conclusion. Then I'd communicate upward early with a clear picture: what failed, the likely fix, the impact on schedule, and options — because a delay discovered late is far worse if leadership hears about it after the fact.

With the engineer, my stance is that this is a process gap to close, not a person to punish. A protocol defect that only surfaces in compliance testing usually means the verification earlier in the cycle didn't exercise that path — so the constructive conversation is "what would have caught this sooner," and the answer is usually a missing test case, a spec ambiguity, or a review that didn't cover the error/framing behavior. I'd have them own the fix and the new test that proves it, which turns the mistake into a durable improvement rather than a demoralizing event.

On schedule: I'd look for whether the fix can be validated in parallel with other compliance work, whether a firmware-only change avoids a hardware respin, and whether there's any interim mitigation. I'd also feed the lesson back into the design-review and test-plan process so the same class of defect gets caught by review next time. The goal is to come out of it with the device fixed, the schedule recovered as far as possible, and the team more careful — not with someone afraid to raise problems early.

**Possible follow-ups:**
- How would you change the design-review or test-plan process so protocol error paths get exercised before compliance testing?
- How would you handle it if the engineer were defensive or tried to minimize the defect?
