## Q1: How would you approach debugging a UART link where the receiver reports framing errors only when a high-current load (e.g., a motor or heater) switches on the same board?
**Answer:** A framing error means the receiver sampled a stop bit where it expected a logic high, so the first question is whether the corruption is electrical or timing-related. I'd start by correlating the failures with the load switching event — if the errors only appear at the instant the load turns on or off, that points to a transient on the supply or ground rather than a steady-state baud-rate mismatch. I'd scope the UART lines and the supply rail simultaneously, using a differential or at least a properly grounded probe, to see whether the RX line is glitching, whether the ground reference is bouncing, or whether the MCU's clock is momentarily disturbed. Common culprits are shared ground return impedance between the high-current path and the logic ground, insufficient decoupling on the transceiver or MCU supply, or inductive kickback coupling into the cable. Mitigations typically include separating the high-current return path from the signal ground, adding bulk and local decoupling, adding series termination or a small RC filter on the UART lines, and if the link is off-board, moving to a differential physical layer like RS-485 so common-mode shifts don't corrupt the single-ended signal. I'd also check whether the load switching is causing a brownout that resets or disturbs the UART peripheral, which would show up as a burst of errors rather than isolated ones.
**Possible follow-ups:** How would you distinguish a ground-bounce problem from a supply-decoupling problem with a scope? Would you consider galvanic isolation, and what would drive that decision?

## Q2: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?
**Answer:** The goal is to define a transport-agnostic interface at the boundary the application cares about — typically something like open/close, read, write, and maybe a transaction or register-access primitive — and then implement one backend per physical transport behind that interface. The application should express intent in terms of the sensor or the data, not the bus: for example, "read the pressure register" rather than "write these bytes to address 0x4A." Each backend translates that into the transport-specific sequence, handles its own framing, retries, timeouts, and error codes, and maps them into a common error taxonomy so the application doesn't have to know that I2C returns NACKs while CAN-FD returns error frames. I'd keep the interface narrow and avoid leaking transport-specific concepts like clock stretching or chip-select into the abstraction, because that defeats the purpose. For testability, I'd make the backends swappable at build or runtime so the application can be exercised against a mock transport, and I'd define the contract clearly enough that a new transport can be added without touching application code. The trade-off is that a lowest-common-denominator interface can hide useful transport-specific features, so I'd expose optional capabilities through a query mechanism rather than baking them into the core interface.
**Possible follow-ups:** How would you handle a transport-specific feature like CAN-FD's larger payload without breaking the abstraction? Where would you put retry logic — in the backend or the application?

## Q3: In a CAN-FD network, how would you approach guaranteeing that a high-priority safety-critical message is never delayed by more than a bounded time, given that lower-priority telemetry also shares the bus?
**Answer:** The starting point is that CAN's arbitration is priority-based and non-preemptive once a frame has started, so the worst-case latency for a high-priority message is the sum of the longest lower-priority frame that can be in progress when it becomes ready, plus its own transmission time, plus any blocking from error frames or retransmissions. To bound that, I'd first assign the safety-critical message the lowest numerical identifier so it wins arbitration against telemetry, then compute the worst-case response time analytically using the standard priority-ceiling style analysis, accounting for the maximum frame length any lower-priority node can transmit. If the bound is too large, the levers are: shorten the maximum telemetry frame (CAN-FD's larger payload helps here, but a long frame is a long blocking window), increase the data-phase bit rate to shrink transmission time, reduce bus load so the critical message rarely has to wait, or move telemetry to a separate bus or a time-triggered schedule. I'd also consider whether the critical message needs to be periodic with a guaranteed slot, in which case a time-triggered or TDMA-style schedule on top of CAN-FD gives a stronger guarantee than pure priority arbitration. Finally, I'd verify the bound empirically with worst-case traffic injection, because real error frames and retransmissions can eat into the margin.
**Possible follow-ups:** How does an error frame from another node affect your worst-case bound? Would you ever split safety-critical and telemetry traffic onto separate buses, and what would that cost?

## Q4: You're debugging an I2C bus where communication works reliably at 100 kHz but produces intermittent NACKs at 400 kHz, with the same devices and the same PCB. How would you approach this?
**Answer:** Since the same hardware works at standard mode but not fast mode, the problem is almost certainly marginal timing or signal integrity rather than a logic bug. At 400 kHz the bus has less time for the signal to settle, so rise time becomes critical — if the pull-up resistors are too weak for the total bus capacitance, the lines won't reach the logic-high threshold before the next clock edge, and a device may sample a low or fail to recognize its address, producing a NACK. I'd measure the actual rise time and the high/low levels on SDA and SCL with a scope at the far end of the bus, and compare against the I2C specification's rise-time limits for fast mode. I'd also check the effective bus capacitance — long traces, connectors, and many devices all add up — and recalculate the pull-up value for the target rise time, remembering that lowering the resistor increases current draw and must stay within what the devices can sink. Beyond pull-ups, I'd look at whether any device is stretching the clock or has a slower maximum frequency than assumed, whether there's crosstalk between SDA and SCL on long parallel runs, and whether the ground reference is clean. If the bus is simply too capacitive for 400 kHz, the options are to reduce capacitance, lower the speed, or split the bus.
**Possible follow-ups:** How would you calculate the maximum pull-up value for a given rise-time target? What would you do if a device on the bus can't tolerate the higher sink current a smaller pull-up requires?

## Q5: How would you approach handling a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?
**Answer:** The first priority is to contain the problem and understand its scope before assigning blame — the goal is to get the product back on track, not to make anyone feel punished for surfacing an issue. I'd pull together the relevant people to characterize exactly what's wrong, whether it's a misunderstanding of the protocol, a missing edge case, or a gap in the requirements or review process, and to assess whether the fix is localized or affects other interfaces. I'd be direct but constructive with the junior engineer: explain the impact, walk through the correct behavior, and make sure they understand the reasoning rather than just applying a patch, because the same misunderstanding may exist elsewhere. Then I'd look at the process that let it reach compliance testing — was the protocol specified clearly, was there a review, was there a test that should have caught it earlier? — and fix that gap so it doesn't recur. On the schedule side, I'd communicate transparently with stakeholders about the delay and the recovery plan, and I'd resist the temptation to skip verification steps to make up time, since that's how you get a second, worse failure. The longer-term move is to treat it as a learning opportunity for the team and to strengthen early verification so protocol errors are caught at the bench, not at the test house.
**Possible follow-ups:** How would you decide whether to fix the protocol or renegotiate the requirement with the test house? What would you change in your review process to catch this class of error earlier?
