# protocols — Day 105

## Q1: You're debugging a USB 2.0 device that works on most hosts but intermittently fails enumeration on one particular host, where the failure appears as a control-transfer timeout during descriptor reads. How would you approach this?

**Answer:** I'd treat this as a layered isolation problem rather than immediately assuming a firmware bug, because the fact that it works on most hosts points to an interaction effect rather than a hard defect. First I'd capture a bus trace with a hardware analyzer on the failing host to see exactly where the control transfer stalls — whether the SETUP stage completes and the DATA stage times out, whether the device NAKs indefinitely, or whether the host gives up before the device responds. That distinction matters: a NAK storm suggests the device firmware isn't servicing endpoint 0 promptly, while a timeout with no response at all suggests a signaling or timing issue.

Next I'd look at the descriptor request pattern itself. Some host stacks request descriptors in a different order or with different wLength values than others — for example requesting the first 8 bytes of the device descriptor, then the full descriptor, then configuration descriptors in a specific sequence. If the device firmware has a state machine that assumes a particular request order, or if it stalls on a request it doesn't expect, that would explain host-specific behavior. I'd verify the device handles GET_DESCRIPTOR for device, configuration, string, and any class-specific descriptors in any reasonable order, and that it returns a proper STALL rather than hanging on unsupported requests.

I'd also check the timing budget. Control transfers have a defined timeout at the host, and if the device's interrupt latency or endpoint-0 handling is marginal — say, because a higher-priority task is blocking the USB stack — a slower or more conservative host controller might time out where a faster one succeeds. Looking at whether the failure correlates with host controller type (UHCI vs EHCI vs xHCI, or an embedded host with a slower scheduler) helps confirm this.

Finally, I'd check the physical layer: signal integrity on D+/D−, whether the device is bus-powered and drawing near the limit, and whether the failing host's port has different VBUS characteristics. A marginal eye or a slow attach could cause the host to mis-time the first control transfer. The fix depends on which layer the trace points to — firmware state machine, endpoint-0 responsiveness, descriptor correctness, or signal integrity.

**Possible follow-ups:** How would you determine whether the device is NAKing because it's not ready versus because it's waiting on a resource held by another task? What would you change in the descriptor set to make enumeration more robust across host stacks?

## Q2: How would you approach calculating pull-up resistor values for an I2C bus that must support both standard-mode (100 kHz) and fast-mode (400 kHz) operation with multiple devices on the bus?

**Answer:** The pull-up value is bounded from both sides, and the design has to satisfy both bounds simultaneously across all the devices on the bus. The upper bound comes from the rise-time requirement: the bus capacitance and the pull-up form an RC network, and the rise time to the input threshold must be fast enough for the chosen mode. Standard-mode allows a 1000 ns rise time; fast-mode allows 300 ns. So R_max ≈ t_r / (0.847 × C_bus) for the standard approximation, where C_bus is the total capacitance — every device's pin capacitance plus trace and connector capacitance. If the bus has, say, 200 pF total, fast-mode caps the pull-up at roughly 1.8 kΩ, while standard-mode would allow around 5.9 kΩ. Since the bus must work at 400 kHz, the fast-mode bound governs.

The lower bound comes from the sink-current capability of every device on the bus. When a device pulls the line low, it must sink the current flowing through the pull-up plus the current from any other pull-ups, and still hold V_OL below the specified threshold (typically 0.4 V). So R_min = (V_DD − V_OL_max) / I_OL_max, where I_OL_max is the weakest sink capability among all devices. A device rated for 3 mA sink at 0.4 V with a 3.3 V rail gives R_min ≈ 967 Ω. So the valid window is roughly 1 kΩ to 1.8 kΩ, and I'd pick something in the middle — say 1.5 kΩ — to leave margin on both sides.

The practical complications: bus capacitance is often underestimated because people forget connector and cable capacitance, and if the bus is long or has a flex cable, C_bus can blow past the 400 pF fast-mode limit entirely, in which case no pull-up value saves you and you need a bus buffer or a different topology. Also, some devices have weaker sink capability than the datasheet headline suggests at temperature extremes, so I'd check the worst-case I_OL over the operating range. And if the bus is powered from different rails on different boards, I'd make sure the pull-ups are referenced to a single rail and that no device is exposed to a voltage above its absolute maximum when its own rail is off.

**Possible follow-ups:** What would you do if the calculated window is empty — R_min exceeds R_max? How does an active pull-up or a bus buffer change the calculation?

## Q3: You're debugging a CAN-FD network where a node occasionally transmits an error frame that corrupts an in-progress message from another node, but only under heavy bus load. How would you approach this?

**Answer:** An error frame under load usually means some node is detecting a bit error, stuff error, CRC error, or form error on a frame it's receiving, and the error frame it emits aborts the frame in progress for everyone. The load dependence is the key clue: it suggests a timing margin that's fine when the bus is quiet but violated when arbitration and data-phase switching are happening back-to-back.

First I'd capture the bus with a CAN analyzer that timestamps error frames and correlates them with which node was transmitting and which node flagged the error. If the same node consistently flags errors on frames from one particular transmitter, that points to a bit-timing or sample-point mismatch between those two nodes rather than a global bus problem. CAN-FD makes this more likely because the data phase runs at a higher bit rate than the arbitration phase, and the sample point in the data phase has to be configured per-node; if one node's data-phase timing is marginal, it will only fail when the bus is busy enough that its oscillator tolerance and the accumulated phase error push it past the sample point.

I'd check the bit-timing configuration on every node — prescaler, propagation segment, phase segments, and sample point — and verify they're consistent, especially for the data phase. I'd also check the transceiver's loop delay and whether the chosen data-phase bit rate leaves enough margin given the cable length and stub lengths; CAN-FD's higher data rate shrinks the bit time, so the same physical bus that's fine at 500 kbit/s arbitration may be marginal at 2 or 5 Mbit/s in the data phase. Signal integrity on the bus — reflections from stubs, termination, common-mode — becomes much more critical at the higher data rate.

I'd also look at whether the error is a stuff error caused by a node transmitting outside its time slot, which can happen if a node's transmit request is triggered by an interrupt that's delayed under load. And I'd check whether any node is in a state where it's transmitting error frames repeatedly, which could indicate it's near error-passive and its error counters are climbing. The fix is usually a combination of correcting bit timing, tightening the physical layer, and ensuring the firmware doesn't queue transmissions in a way that causes late arbitration.

**Possible follow-ups:** How would you distinguish a bit-timing mismatch from a physical-layer signal integrity problem using only the analyzer trace? What's the risk of a node going error-passive under sustained load, and how would you design the firmware to recover gracefully?

## Q4: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The goal is to separate what the application wants — read a sensor, configure a threshold, stream samples — from how the bytes get there. I'd structure it in layers: a transport interface at the bottom that each physical bus implements, a device driver layer above it that knows the sensor's register map and command semantics, and an application layer on top that only sees typed operations.

The transport interface would be a small set of operations — open, close, write, read, and a transfer that combines write-then-read for register-style access — with each transport implementing them. I2C and SPI map naturally to a register read/write model; UART and CAN-FD are message-oriented, so the driver layer above has to frame commands into whatever the sensor's protocol expects. The key design decision is where to put the framing: if the sensor speaks a register model over UART, the UART transport can carry a small framing layer that emulates register access; if it speaks a message protocol, the driver layer handles message construction and the transport just moves bytes.

I'd keep the interface asynchronous or at least non-blocking-friendly, because CAN-FD and UART may have latency that I2C/SPI don't, and the application shouldn't be structured around blocking calls that only work for fast buses. A completion callback or a request/response handle model lets the application issue a read and get notified, which works uniformly across transports.

I'd also make error semantics uniform: a NACK on I2C, a CRC failure on CAN-FD, and a framing error on UART should all surface as a transport error with enough context to log, but the application shouldn't have to know which physical event caused it. And I'd keep timing and retry policy in the transport layer, since retry behavior differs — I2C may need a bus-recovery sequence, CAN-FD may need to wait for the controller to recover from error-passive, UART may just retransmit.

The testability benefit is the real payoff: with a mock transport, the driver and application layers can be tested without hardware, and swapping a sensor from I2C to SPI becomes a transport implementation change rather than an application rewrite.

**Possible follow-ups:** How would you handle a sensor that has fundamentally different semantics on different transports — for example, a streaming mode that only exists on SPI? Where would you put timeout and retry policy, and why?

## Q5: You're leading a design review where a junior engineer proposes using a single shared interrupt line for three different peripherals — a UART, an SPI sensor, and a GPIO alarm input — arguing that it saves pins and the firmware can just poll the peripherals to find out which one fired. How would you guide the team to evaluate this approach?

**Answer:** I'd start by acknowledging the legitimate motivation — pin count is real, and on a constrained MCU sharing an interrupt line is a recognized technique. Then I'd walk the team through what the shared line actually costs, because the trade-off is not just "poll to find out who fired."

The first issue is latency and determinism. With a shared line, the ISR has to read each peripheral's status register to identify the source, and that takes time — but more importantly, the alarm input is the one that can't afford to wait behind a UART or SPI status check. If the alarm is a safety-relevant signal, its response time now depends on how long the other peripherals' status reads take and on whether the ISR is already busy servicing a UART byte. I'd ask the team to quantify the worst-case latency from alarm assertion to handler execution, and compare it against the alarm's required response time. If the margin is thin, that alone may rule out the shared line for the alarm.

The second issue is missed or merged events. If two peripherals assert simultaneously, the ISR sees one edge and has to check both — fine if the status registers latch, but if a peripheral's interrupt flag is cleared by reading its data register, the order of checks matters and a naive implementation can drop an event. I'd ask the junior engineer to walk through the ISR pseudocode for the simultaneous-assertion case and for the case where a second event arrives while the ISR is still running.

The third issue is diagnosability. When something goes wrong in the field, a shared line makes it harder to attribute a fault to a specific peripheral, and in a medical device that matters for root-cause analysis and for the risk file.

My guidance would be: keep the shared line only if the alarm can be given a dedicated pin or if the latency analysis shows comfortable margin, and if the ISR is structured so that the highest-priority source is checked first and every source's flag is latched. Otherwise, spend the pin. I'd frame it as a decision to be made with numbers — latency budget, pin budget, and risk — rather than a stylistic preference, and I'd ask the team to bring those numbers to the next review.

**Possible follow-ups:** How would you structure the ISR so that a shared line doesn't drop events when two peripherals assert at once? If the pin budget truly can't accommodate a dedicated alarm line, what else would you change in the architecture to recover the determinism?

**Possible follow-ups (Q5 continued):** What would you document in the risk file about the shared interrupt line, and how would you verify the latency claim during testing?
