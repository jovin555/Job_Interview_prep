## Q1: How would you approach designing a fail-safe mechanism for a UART-based communication link in a medical device where a sensor must never be left in an unknown state if the main controller resets or loses power mid-transaction?

**Answer:** The core concern here is that a partial transaction — say, the controller sends half of a command and then resets — could leave the sensor in an indeterminate configuration. I'd approach this in layers. First, at the protocol level, every command should be framed with a start delimiter, a length field, and a checksum or CRC, so the sensor can detect an incomplete or corrupted frame and discard it rather than acting on partial data. Second, the sensor should have a defined idle or safe state that it returns to if it doesn't receive a complete, valid command within a timeout window. That timeout needs to be short enough to be clinically meaningful but long enough to avoid false triggers during normal operation. Third, on the controller side, I'd add a "transaction complete" acknowledgment handshake where the sensor confirms it has received and acted on a command; if the controller resets mid-transaction, it can query the sensor's state on boot and re-synchronize. Finally, at the hardware level, I'd consider a reset line or a dedicated "enable" signal that the controller asserts only when it's ready to communicate, so the sensor knows that de-assertion means "ignore anything partial and return to safe state." The key principle is that the sensor must never rely on receiving a well-formed command to stay safe — it must default to safety when communication is absent or ambiguous.

**Possible follow-ups:** How would you handle the case where the sensor itself is the one that resets mid-transaction? What if the UART link uses hardware flow control — how does that change the fail-safe design?

## Q2: You're debugging a system where an RS-485 network works reliably at 9600 baud but experiences intermittent corruption at 115200 baud. The cable run is approximately 150 meters with 12 nodes. How would you approach isolating the root cause?

**Answer:** I'd start by recognizing that this is a classic signal-integrity-versus-timing problem, and the fact that it works at 9600 but fails at 115200 narrows the field considerably. At higher baud rates, the bit period shrinks from roughly 104 microseconds to about 8.7 microseconds, so any reflection, skew, or timing margin issue that was tolerable at low speed becomes critical. I'd work through several hypotheses in order. First, termination: at 150 meters with 12 nodes, improper termination — missing, wrong value, or incorrectly placed — causes reflections that settle within the long bit period at 9600 but corrupt the short bit period at 115200. I'd verify that termination resistors match the cable's characteristic impedance and are placed at both physical ends of the bus, not at intermediate nodes. Second, stub lengths: each node's connection to the main bus acts as a transmission line stub; at 115200 baud, the critical wavelength is much shorter, so even modest stubs can cause reflections. I'd check that stubs are as short as possible, ideally under about 10–15 centimeters. Third, bias and common-mode: I'd verify fail-safe biasing is present and that all nodes share a common ground reference, since ground potential differences that were harmless at low speed can cause bit errors at higher data rates. Fourth, I'd look at the transceiver's slew rate and driver strength — some transceivers have slower rise/fall times that are fine at low baud but marginal at higher rates. Finally, I'd use a differential probe and oscilloscope to look at the actual eye diagram at the farthest node, measuring signal amplitude, rise time, and overshoot. The scope trace would quickly tell me whether this is a reflection problem, a level problem, or a timing problem.

**Possible follow-ups:** How would you decide between adding termination versus reducing the baud rate as the fix? What if the cable is unshielded twisted pair — how does that factor in?

## Q3: How would you approach selecting between RS-422 and RS-485 for a medical device that needs to communicate with multiple sensors distributed across a patient monitoring system?

**Answer:** The first thing I'd clarify is the actual topology and communication pattern, because that drives the decision more than raw electrical specs. RS-485 is a true multi-drop bus — up to 32 unit loads on a single pair of wires, half-duplex, with all nodes sharing the same two wires and arbitrating who talks when. RS-422 is typically point-to-point or multi-drop in one direction only — one driver can drive multiple receivers, but it's not designed for multiple drivers on the same pair, so it's effectively simplex or one-way broadcast. For a patient monitoring system where sensors need to send data back to a central unit, RS-485 is usually the right choice because it supports bidirectional communication on a shared bus. However, if the sensors are purely one-way — say, they only transmit data and never receive commands — RS-422 could work and has the advantage of not needing bus arbitration or turn-around timing. I'd also consider the data rate and distance: both support similar distances and rates, but RS-485's half-duplex nature means you need to manage the turn-around time when switching between transmit and receive, which adds protocol overhead and latency. For a medical device, I'd also think about fault tolerance: RS-485's fail-safe biasing and the ability to isolate nodes that fail are important. If the system needs deterministic, low-latency communication from the central unit to all sensors simultaneously, RS-422's one-to-many broadcast might be simpler. If sensors need to respond back, RS-485 is the practical choice. I'd also check whether the sensors themselves have a preferred interface — many industrial medical sensors natively support RS-485, which would simplify the design.

**Possible follow-ups:** How would the choice change if the system needed to support hot-swapping sensors while the system is running? What about if the cable run were over 500 meters?

## Q4: How would you approach implementing a deterministic scheduling scheme for a medical device that uses I2C for sensor reads, SPI for high-speed data logging, and UART for a user interface, all on a single microcontroller running Zephyr RTOS?

**Answer:** I'd start by separating the problem into two parts: the RTOS scheduling of tasks that use these peripherals, and the arbitration of the peripherals themselves. In Zephyr, I'd model each communication interface as a driver with its own thread or as a set of operations that can be invoked from a cooperative scheduler. The key is to avoid blocking — a task that waits on I2C should not stall the entire system. I'd use Zephyr's asynchronous or interrupt-driven APIs where available, or wrap synchronous calls in a way that yields to the scheduler. For deterministic behavior, I'd assign priorities: the I2C sensor reads might be periodic and time-critical, so they'd run in a high-priority thread with a fixed period, using a timer or a Zephyr workqueue. The SPI data logging is high-throughput but can tolerate some latency, so it could run in a lower-priority thread that processes data in batches. The UART user interface is event-driven and low-rate, so it could be interrupt-driven with a small ring buffer. The critical piece is the arbitration between I2C and SPI if they share any resources — like a DMA controller or a common clock — so I'd check the microcontroller's peripheral multiplexing and ensure that the scheduler never allows two tasks to configure the same peripheral simultaneously. I'd also use Zephyr's mutexes or semaphores to protect shared peripheral access, but carefully — a mutex held during a long SPI transfer could block a higher-priority I2C read. A better pattern is to use a mailbox or message queue where each communication task posts requests and a dedicated peripheral manager thread executes them in priority order. For true determinism, I'd measure the worst-case execution time of each transaction and verify that the sum of all periodic transactions fits within the scheduling period, leaving headroom for the UART and any sporadic events.

**Possible follow-ups:** How would you handle the case where an I2C sensor occasionally clock-stretches for longer than expected, delaying other transactions? How would you verify the determinism of your schedule during testing?

## Q5: Imagine you're leading a design review where a junior engineer proposes using a single CAN-FD bus for a medical device that carries both a safety-critical control message requiring delivery within 2 ms and high-volume telemetry from multiple sensors. The engineer argues that CAN-FD's higher data rate in the data phase eliminates any bandwidth concerns. How would you guide the team to evaluate this approach?

**Answer:** I'd acknowledge that CAN-FD's higher data phase rate does increase raw throughput, but I'd steer the discussion toward the distinction between bandwidth and determinism. The safety-critical message's 2 ms requirement isn't just about how many bits can be pushed through the bus — it's about worst-case latency, which depends on arbitration, bus load, and the priority scheme. I'd guide the team to work through a quantitative analysis. First, calculate the worst-case queuing delay: if a lower-priority telemetry frame has already started transmitting when the safety-critical message becomes ready, the critical message must wait for that frame to finish. With CAN-FD, the arbitration phase is still at the standard rate, and the maximum frame length — including stuffing bits, CRC, and overhead — determines the maximum blocking time. Second, I'd ask the engineer to estimate the total bus utilization: sum the bit times of all periodic telemetry messages plus the safety-critical message, and check whether the bus is loaded beyond a reasonable threshold — typically I'd want to stay well below 50–60% utilization for a system with hard real-time requirements, because higher utilization increases the probability of queuing delays. Third, I'd discuss whether the telemetry can be scheduled or rate-limited so that it doesn't coincide with the critical message — for example, using time-triggered transmission or CAN-FD's payload size to batch telemetry into fewer, larger frames. Fourth, I'd raise the question of error handling: if the bus enters a busy or error-passive state, how does that affect the critical message's latency? Finally, I'd suggest a practical test: implement the actual message set, measure worst-case latency under full load using a bus analyzer, and verify it against the 2 ms requirement with margin. The point isn't to reject the single-bus approach — it may be perfectly viable — but to ensure the team proves it rather than assuming the higher data rate solves everything.

**Possible follow-ups:** How would you decide whether to split the traffic onto two separate buses instead? What if the telemetry is bursty rather than periodic — how does that change the analysis?
