## Q1: How would you approach debugging a USB 2.0 device that works on most hosts but intermittently fails enumeration on one particular host, where the failure shows up as a control-transfer timeout during descriptor reads?

**Answer:** I'd treat this as a layered isolation problem and try to determine whether the fault is in the descriptor content, the device firmware's control-endpoint handling, or the host's tolerance for timing. First, capture a bus trace on the failing host with a hardware analyzer so I can see exactly which descriptor request times out — device descriptor, configuration descriptor, or a string descriptor — and whether the device ever ACKs the SETUP stage. That single observation splits the problem in half: if the device never responds, it's firmware or PHY; if it responds but the host gives up, it's a timing or descriptor-size issue.

On the descriptor side, I'd check for things hosts are known to be picky about: the configuration descriptor's `wTotalLength` matching the sum of the interface, endpoint, and class-specific descriptors actually returned; the device responding to a request for only the first 8 bytes of the device descriptor before the host re-requests the full length; and string descriptor indices that point to valid, correctly-encoded UTF-16LE strings. A common failure mode is a device that returns a full configuration descriptor when the host asked for a partial one, or vice versa, causing a babble or stall that some host stacks tolerate and others don't.

On the firmware side, I'd look at how the control endpoint handles the status stage and whether it can service a new SETUP packet while a previous transfer is still in flight — older or embedded host controllers often pipeline requests more aggressively. I'd also check the device's response latency against the host's timeout budget; if the firmware does anything blocking in the interrupt context (like a flash write or a long sensor read) during enumeration, a slow host will time out where a fast one won't. The fix is usually to make the control endpoint's descriptor path fully non-blocking and to serve descriptors from RAM rather than generating them on the fly.

**Possible follow-ups:** How would you confirm whether the host is retrying the request or giving up after the first timeout? What would you change in the descriptor hierarchy if the device is composite with both HID and a vendor-specific bulk interface?

## Q2: How would you approach calculating pull-up resistor values for an I2C bus that must support both standard-mode (100 kHz) and fast-mode (400 kHz) operation with multiple devices on the bus?

**Answer:** The pull-up value is bounded from both sides, and the job is to find the window that satisfies both modes and all devices. The upper bound comes from the rise-time requirement: the bus must reach the logic-high threshold within the specified rise time for the mode in use — roughly 1000 ns for standard mode and 300 ns for fast mode. Since rise time is set by the RC of the pull-up and the total bus capacitance, a larger pull-up slows the edge, so the fast-mode rise time sets the tighter upper limit on R. The lower bound comes from the sink-current capability of the weakest device: at VOL(max), each device must be able to pull the line low through the pull-up without exceeding its rated IOL. A smaller pull-up draws more current when the line is low, so the device's IOL spec sets the lower limit on R.

The practical procedure is: measure or estimate total bus capacitance (trace capacitance plus each device's pin capacitance plus any connector or cable capacitance), compute the maximum R from the fast-mode rise-time equation, compute the minimum R from the sink-current equation using the device with the lowest IOL, and check that the window is non-empty. If it isn't — which happens on long buses with many devices — the options are to reduce bus capacitance (shorter traces, fewer devices per bus, a bus buffer/expander that splits the bus into segments), lower the bus speed, or use an active pull-up. I'd also verify the chosen value against the VIL/VIH thresholds at both speeds and confirm the total high-level leakage current across all devices doesn't drag the bus below VIH when the line is supposed to be high.

One thing I'd flag in a design review: the "400 pF limit" is a rule of thumb tied to the standard-mode spec, not a hard physical limit, and a bus can be within the capacitance limit yet still fail at 400 kHz because the pull-up is too weak for the faster rise time. The two constraints have to be checked together, not independently.

**Possible follow-ups:** How would you handle a bus where the calculated window is empty because one device has a very low IOL? What role does clock stretching play in whether a marginal pull-up value is acceptable?

## Q3: You're debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward. How would you approach this?

**Answer:** Bus-off means the node's transmit error counter exceeded 255, so the question is what's driving the error counter up — and the fact that the bus looks healthy afterward tells me the fault is intermittent and probably tied to a specific condition rather than a permanent wiring problem. I'd start by instrumenting the node to log the error counters and the error state transitions with timestamps, plus the type of error (bit error, stuff error, CRC error, ACK error, form error) at the moment of each increment. The error type is the biggest clue: ACK errors point to no other node acknowledging, bit errors point to a transmitter seeing a different level than it drove (often a physical-layer or termination issue), and stuff/CRC errors point to corruption on the wire.

Then I'd correlate those timestamps against system activity — what else was happening when the node went bus-off? Common causes are a marginal termination or stub that only bites at certain data-phase bit rates, a ground offset between nodes that shifts the common-mode voltage outside the transceiver's range during a particular load condition, or a node that transmits while another is mid-frame because of a scheduling bug. CAN-FD makes this trickier than classic CAN because the data phase runs at a much higher bit rate, so the same physical layer that's fine at the arbitration rate can fail in the data phase — I'd check whether the bus-off events correlate with frames that have long data phases or high bit-rate switching.

I'd also look at the recovery behavior itself. A node that stays off until reset suggests either the controller isn't configured for automatic bus-off recovery, or the application isn't calling the recovery sequence, or the recovery is attempted but the node immediately re-errors because the underlying condition persists. I'd verify the recovery is actually being attempted and log whether the node re-enters bus-off immediately after recovery — that pattern points strongly at a persistent physical-layer or configuration issue rather than a transient.

**Possible follow-ups:** How would you distinguish a termination problem from a common-mode offset problem using only a scope and the error counters? What would you check in the bit-timing configuration if the bus-off only happens at the highest data-phase bit rate?

## Q4: How would you approach choosing between a star topology and a daisy-chain topology for a multi-drop sensor network in a medical device, given that the sensors are physically distributed?

**Answer:** The choice is really driven by the electrical characteristics of the physical layer, the cable routing constraints in the device, and the failure-mode requirements — not by a generic preference. For a differential bus like RS-485 or CAN, a daisy-chain (bus) topology is the natural fit because it keeps stub lengths short and presents a single terminated transmission line; star topologies on those buses create long stubs and impedance discontinuities that cause reflections, so they're only viable with a repeater or hub at the center. For a point-to-point or master-to-many scheme where each sensor has its own link (like independent SPI chip selects or separate UARTs), a star is fine electrically but costs pins and cable.

So I'd frame the decision around a few questions. First, what's the physical layer? If it's a shared differential bus, daisy-chain is strongly preferred and star should be ruled out unless the distances are tiny. Second, how are the sensors distributed mechanically — can the cable be routed as a single run with short taps, or does the mechanical design force long branches? If the mechanical design forces a star, that pushes toward either a hub/repeater or a different physical layer. Third, what are the failure-mode and serviceability requirements? A daisy-chain means one broken link can take down everything downstream, which matters in a medical device where a sensor loss has clinical consequences; a star means a single cable fault only affects one sensor, which can be preferable for fault isolation even at higher wiring cost.

I'd also weigh termination and biasing: a daisy-chain with proper end termination is straightforward, while a star needs careful analysis of each branch's length and reflection behavior. And I'd consider whether the network needs to be expandable — daisy-chain is easy to extend along a cable run, star is easy to add nodes at the hub. The answer usually falls out of the physical layer plus the fault-isolation requirement, and I'd document the trade-off explicitly rather than defaulting to whichever is simpler to wire.

**Possible follow-ups:** How would you handle a star topology on a differential bus if the mechanical design truly requires it? What termination strategy would you use for a daisy-chain with very short stubs versus one with longer taps?

## Q5: How would you handle a situation where a junior engineer on your team implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** The first priority is containment and honest assessment, not blame. I'd get the facts quickly: what exactly failed, which requirement or test case it maps to, whether it's a functional defect or a documentation/traceability gap, and what the realistic fix and re-test timeline looks like. Then I'd communicate that assessment to the project lead and regulatory stakeholders promptly — in a regulated environment, a discovered nonconformance during testing is a known quantity that has to be handled through the quality system, and delaying that conversation only makes the schedule impact worse. I'd want the team to understand that surfacing the problem early is the right behavior, even though it's uncomfortable.

On the technical side, I'd work with the engineer to do a proper root-cause analysis rather than just patching the symptom — was the protocol spec ambiguous, was the implementation not reviewed against the spec, was there a gap in the test plan that let it through, or was it a genuine mistake? The answer determines whether the fix is a code change, a spec clarification, or a process change. I'd also check whether the same class of error exists elsewhere in the codebase, since protocol bugs tend to repeat across similar interfaces.

On the process side, I'd look at why it wasn't caught earlier and strengthen the review and verification steps without turning it into a punitive exercise. That might mean adding protocol conformance checks to the unit/integration test suite, requiring a spec-to-implementation traceability review before compliance testing, or pairing the junior engineer with a senior reviewer on protocol work for a while. The goal is to make the engineer more capable and the process more robust, not to single anyone out — a culture where people hide mistakes is far more dangerous in medical devices than one where mistakes get surfaced and fixed.

**Possible follow-ups:** How would you decide whether to fix the defect in firmware or request a deviation, given the regulatory timeline? What would you change in the design review process to catch protocol errors before compliance testing?
