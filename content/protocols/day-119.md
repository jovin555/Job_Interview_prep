# protocols — Day 119

## Q1: How would you approach debugging a USB 2.0 device that draws more current than its configuration descriptor declares, causing intermittent resets on a host root port but working fine through a self-powered hub?
**Answer:** The asymmetry between root port and self-powered hub is the key clue — it points at the host's per-port power budget rather than a fundamental enumeration problem. A root port typically enforces its current limit aggressively and may drop VBUS or issue a port reset when the budget is exceeded, whereas a self-powered hub has its own supply headroom and can absorb the overage. I'd start by confirming the actual current draw with an inline measurement or a current probe on VBUS, both at enumeration (before configuration is set) and during normal operation, because the descriptor's `bMaxPower` is a declaration, not a limit the device enforces on itself. Then I'd check whether the overage is transient — inrush at plug-in, or a burst when a radio or motor briefly activates — since a short spike can trip a root port's protection even if average draw looks compliant. On the firmware side, I'd verify the device isn't enabling subsystems before it's configured, and that it correctly enters a low-power state during suspend. The fix is usually one of three things: correct the descriptor to declare the true worst-case draw (and accept that some hosts will refuse to enumerate it), reduce the actual draw so it fits within the declared budget, or redesign for self-powered operation with proper VBUS detection so the device knows when it can draw full current. I'd also make sure the device handles a host-initiated port reset gracefully rather than latching into a bad state.
**Possible follow-ups:** How would you distinguish an inrush problem from a steady-state overcurrent problem using only a scope and a USB analyzer? What does the USB spec require the device to do when it detects it has been suspended?

## Q2: How would you approach calculating termination resistor values for an RS-485 network, and how do stub length and node count change your answer?
**Answer:** The starting point is the characteristic impedance of the cable — typically 100 to 120 ohms for twisted pair — and the rule that termination should match it at both physical ends of the bus to absorb reflections. That gives a single 120-ohm resistor at each end for a standard point-to-point or multi-drop bus, which presents the driver with roughly 60 ohms differential. The complications come from topology. Stub length matters because each node tapping off the main trunk creates a discontinuity; as a rule of thumb, stubs should be kept short relative to the bit period — a common guideline is that the round-trip delay down a stub should be a small fraction of the rise time, which at high baud rates means stubs of just a few centimeters. If nodes are widely spaced with long stubs, no termination value will save you; the topology itself needs to change, for example by daisy-chaining the transceivers so the trunk passes through each node. Node count affects the load: each transceiver presents input capacitance and leakage, and with many nodes the cumulative capacitance rolls off the edges and eats into the eye. At that point I'd consider whether the bus can still meet timing at the target baud rate, and whether AC termination (a resistor-capacitor network) is worth the trade-off of reduced DC load versus added edge slowing. I'd also account for fail-safe biasing, since the bias resistors form a divider with the termination and shift the effective differential levels — the bias network has to be sized so the idle differential voltage stays above the receiver's threshold with the full termination load attached.
**Possible follow-ups:** Why does AC termination help at high baud rates but hurt at low ones? How would you measure whether your termination is actually correct on a live bus?

## Q3: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?
**Answer:** The goal is to keep the application expressing intent — "read the pressure sensor's latest sample" — while the transport layer owns the mechanics of how that intent becomes bytes on a wire. I'd structure it in layers. At the bottom, a transport driver interface with a small, uniform set of operations: open/configure, a synchronous or asynchronous transfer primitive, and error reporting. Each concrete transport implements that interface, hiding whether a transaction is an I2C address-plus-register write, an SPI chip-select-and-clock sequence, a framed UART message, or a CAN-FD identifier with a payload. Above that, a device abstraction per sensor type, which knows the sensor's register map or command set and translates semantic operations into transport calls. The application talks only to the device abstraction. The critical design decisions are where errors get normalized — a NACK, a CRC failure, and a timeout should all surface as a common, meaningful error taxonomy rather than leaking transport-specific codes upward — and how timing and buffering are handled, since a blocking I2C read and an asynchronous CAN-FD response have very different latency profiles. I'd keep the interface asynchronous-capable from the start even if the first transport is synchronous, because retrofitting async later is painful. For testability, I'd put a mock transport behind the same interface so the device layer can be unit-tested without hardware, and I'd be careful that the abstraction doesn't hide properties the application genuinely needs — for example, a safety-critical path may need to know whether a reading is fresh within a bounded time, which is a transport-dependent guarantee that shouldn't be flattened away.
**Possible follow-ups:** Where would you put end-to-end integrity checking — in the transport layer or the device layer — and why? How do you avoid the abstraction becoming a leaky one when one transport has a capability the others lack?

## Q4: You're debugging a CAN-FD network where a node intermittently enters error-passive state and then recovers on its own, with no obvious pattern. How would you approach this?
**Answer:** Error-passive means the node's transmit error counter has crossed the threshold, so the question is what's incrementing it — and the fact that it recovers on its own tells me the counter is decrementing successfully on good frames, which means the errors are intermittent rather than a hard fault. I'd start by capturing the error counters and the error type over time, either through the controller's diagnostic registers or a bus analyzer that logs error frames and their context. The error type narrows the search: bit errors point at the physical layer — termination, stub reflections, common-mode issues, a marginal transceiver — while form or stuff errors point at bit-timing mismatch between nodes, which often means the sample point or the data-phase bit rate isn't consistent across the network. CAN-FD makes this trickier because the arbitration phase and data phase run at different rates, so a node can be fine at the nominal bit rate and marginal in the data phase; I'd check that every node's data-phase timing and sample point are configured consistently and that the transceivers support the data-phase rate. ACK errors would suggest a node transmitting when no one else is listening, or a wiring break that only manifests under certain traffic. I'd also look at whether the errors correlate with specific traffic patterns, temperature, or cable flexing, since intermittent physical faults often track one of those. The recovery behavior itself is worth checking too — a node that goes error-passive and recovers is behaving correctly, but if it's flapping repeatedly it may be masking a marginal physical layer that will eventually fail hard.
**Possible follow-ups:** How would you distinguish a bit-timing mismatch from a termination problem using only the error counters? What's the difference between error-passive and bus-off in terms of what the node can still do?

## Q5: You're leading a design review where a junior engineer proposes a single shared interrupt line for a UART, an SPI sensor, and a GPIO alarm input, arguing it saves pins and the firmware can just poll the peripherals to find out which one fired. How would you guide the team to evaluate this approach?
**Answer:** I'd want the team to reason about it rather than just vote, so I'd frame the review around what the shared line costs in each of the three cases. The first question is latency: polling to identify the source adds a detection delay that depends on how fast the firmware can walk the peripherals, and for the alarm input that delay may be unacceptable if it's a safety-relevant signal — so I'd ask what the worst-case response time is for each source and whether the alarm path can tolerate it. The second is the failure mode: a shared line means one stuck-low peripheral can mask or spuriously trigger the others, and the firmware has to be able to distinguish "this peripheral is asserting" from "this peripheral is holding the line low because it's wedged." That's a diagnosability problem, and in a medical device it matters. The third is whether the pin savings are real — often the peripherals already have dedicated interrupt pins available, or the MCU has enough pins that the saving buys nothing. I'd also point out that a shared line with polling isn't inherently wrong; it's a legitimate technique when the sources are low-rate and non-critical, and the firmware can afford the scan. So the guidance is to make the trade-off explicit: if the alarm is safety-relevant, give it its own line or a dedicated wake path; if the UART and SPI sensor are both low-rate and the polling latency is bounded and acceptable, sharing may be fine, but the firmware needs a clear arbitration and recovery strategy for a stuck line. I'd ask the junior engineer to bring the timing numbers and the failure-mode analysis to the next review rather than rejecting the idea outright — the goal is to teach the reasoning, not just the answer.
**Possible follow-ups:** How would you design the firmware so a stuck-low peripheral on a shared interrupt line can be identified and isolated? What would change if the alarm input were the only safety-relevant source on that line?
