# protocols — Day 110

## Q1: How would you approach debugging a USB 2.0 device that draws more current than its configuration descriptor declares, causing it to reset intermittently on a host root port but enumerate fine through a self-powered hub?

**Answer:** The symptom pattern is the tell: a self-powered hub can supply the full per-port budget regardless of what the device claims, while a root port enforces the descriptor's declared `bMaxPower` and will current-limit or drop VBUS when the actual draw exceeds it. So the first step is to confirm the mismatch rather than assume it — measure actual current draw in each operating state (idle, enumeration, peak activity) and compare against the `bMaxPower` value in the configuration descriptor. If the device genuinely needs more than 100 mA, the correct fix is to declare it properly: either bump `bMaxPower` to the real worst-case figure (up to 500 mA for a high-power bus-powered device) or, if the design can't stay within the bus-powered budget, move to a self-powered configuration with the descriptor's self-powered bit set and the max-power field reflecting the bus draw only. I'd also check whether the peak draw is transient — inrush at plug-in or a motor/heater switching on — because a brief spike above the declared value can trip host protection even when average current looks fine; bulk decoupling and soft-start on the load help there. The key discipline is that the descriptor is a contract, not documentation: the host is entitled to enforce it, and behavior that "works" on a lenient hub is a latent field failure.

**Possible follow-ups:** How would you structure the descriptor if the device needs to support both bus-powered and self-powered modes? What would you check first if the device still resets on the root port after correcting `bMaxPower`?

## Q2: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** I'd start by defining the boundary in terms of what the application actually needs — a transport-agnostic sensor interface with operations like read register, write register, stream samples, and a status/error model — and keep every transport-specific concept (chip select, clock stretching, arbitration, DLC, endpoint addresses) strictly below that line. The layer typically has three tiers: a thin per-transport driver that knows the electrical and framing details, a common message/transaction model that normalizes request-response semantics and error reporting, and the application-facing sensor API. The hard part isn't the happy path, it's normalizing failure and timing: I2C NACKs, SPI MISO contention, UART framing errors, and CAN-FD error-passive states all mean different things electrically but need to map onto a coherent set of application-visible outcomes (retryable, fatal, degraded). I'd also make timing characteristics explicit in the interface — a call that blocks for a CAN-FD round trip behaves very differently from a buffered SPI read — so the application can reason about latency without knowing the transport. Finally, I'd keep the abstraction testable by providing a mock transport so the application layer can be exercised without hardware, and I'd resist the temptation to over-generalize: if only two transports are ever used, a simpler interface with a clear seam beats a fully generic framework.

**Possible follow-ups:** How would you handle a transport that supports multi-byte burst reads natively versus one that doesn't, without leaking that difference upward? Where would you put retry logic — in the transport driver or the abstraction layer?

## Q3: You're debugging an RS-485 network where the system works at 9600 baud but fails intermittently at 115200 baud over a long cable run with many nodes. How would you approach isolating whether the cause is termination, stub length, or turnaround timing?

**Answer:** The baud-rate dependence points at the physical layer first, because bit time shrinks by roughly an order of magnitude while the cable's electrical characteristics don't change — reflections and stubs that are electrically invisible at 9600 baud become significant when the bit time approaches the propagation delay of the stub. I'd work through it systematically. First, verify termination: a properly terminated bus has a single termination at each physical end matching the cable's characteristic impedance, with no extra terminators on intermediate nodes; I'd measure the differential impedance and check for missing, doubled, or misplaced resistors. Second, quantify stubs: each node's drop from the main trunk adds a stub whose length should be kept short relative to the bit time — long stubs create reflections that corrupt edges at high baud. Third, separate turnaround timing from signal integrity: if corruption clusters at the start of a response right after the driver/receiver switch, that's a turnaround or enable-timing problem, not a reflection problem; if it's spread through the payload, suspect termination and stubs. I'd use a scope or differential probe at multiple points along the bus to look at edge quality and ringing, and I'd test with a reduced node count and shortened cable to see whether the failure scales with stub count or length. The discipline is to change one variable at a time so the root cause is proven, not guessed.

**Possible follow-ups:** How would you calculate the maximum allowable stub length for a given baud rate? What would you check if the corruption persists after fixing termination and stubs?

## Q4: How would you approach guaranteeing that a high-priority safety-critical CAN-FD message is never delayed beyond a bounded time when lower-priority telemetry shares the same bus?

**Answer:** The bound comes from worst-case response-time analysis, not from hoping the higher data rate in the data phase solves it. CAN arbitration is priority-based and non-preemptive once a frame starts, so the worst case for a high-priority frame is: it waits for any lower-priority frame already in progress to finish (blocking), plus the transmission time of every higher-or-equal-priority frame that can be queued ahead of it during that window, plus its own transmission time including any error-frame recovery. I'd start by assigning the safety-critical message the highest arbitration ID so it always wins contention, then compute the blocking term from the longest possible lower-priority frame — which is where CAN-FD's 64-byte payloads hurt, because a long low-priority frame can block for a surprisingly long time. Mitigations include capping the payload length of low-priority telemetry frames, rate-limiting telemetry so the bus utilization stays well below saturation, and where the controller supports it, using a separate CAN-FD channel or a time-triggered schedule for the safety-critical traffic. I'd also account for error frames and bus-off recovery in the analysis, since a single error frame can add a full frame time to the worst case. The output should be a documented worst-case latency budget with margin, verified by measurement under worst-case load, not an average-case throughput number.

**Possible follow-ups:** How does the error-frame overhead enter the worst-case calculation? What would you do if the analysis shows the bound can't be met with the current telemetry load?

## Q5: How would you handle a situation where a junior engineer on your team implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** I'd separate the immediate response from the systemic one. Immediately, the priority is containment and honesty: understand exactly what's wrong and its safety impact, stop the failing test cleanly, and escalate to the project lead and quality/regulatory early — a compliance failure discovered late is a schedule and possibly a filing problem, and the team needs accurate information to decide whether to fix-and-retest or re-plan. I'd bring the junior engineer into the root-cause work rather than sidelining them, because the goal is a corrected design and a learning engineer, not blame. Then the systemic question: why did this escape? Usually it's a gap in the verification chain — the protocol wasn't exercised against fault conditions before formal testing, or the requirements weren't traceable enough to catch the omission in review. I'd use a structured root-cause method (an 8D-style investigation fits well here) to distinguish the technical defect from the process gap, and fix both: correct the implementation, add the missing test coverage, and tighten the review or traceability step that should have caught it. Throughout, I'd keep the tone developmental — a junior engineer who is afraid to surface problems is a much bigger risk than one who made a mistake — while being clear that the process fix is non-negotiable.

**Possible follow-ups:** How would you decide whether to fix and retest versus re-sequence the compliance testing? What would you change in the design review process to catch this class of error earlier?
