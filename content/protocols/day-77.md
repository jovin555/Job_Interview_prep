# protocols — Day 77

## Q1: How would you approach debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward?

**Answer:** Bus-off is not a random event — it's the CAN controller's terminal state after its transmit error counter (TEC) exceeds 255, so the first step is to treat it as a symptom of accumulated errors rather than a fault in itself. I'd start by reading the node's error counters and the controller's error code capture register, which usually tells you whether the errors were transmit-side (TEC climbing) or receive-side (REC climbing). A TEC-dominated bus-off almost always points to the node's own transmissions being corrupted or unacknowledged — a missing ACK from a peer, a bit-timing mismatch, or a transceiver that can't drive the bus cleanly during the data phase. An REC-dominated bus-off points outward: noise, a dominant-stuck peer, or a wiring/termination problem.

Because CAN-FD has separate arbitration and data-phase bit rates, I'd specifically check whether the failures correlate with the data phase — a node that works fine at classic CAN rates but goes bus-off only on long FD frames often has a sample-point or propagation-delay issue in the data phase, where the higher bit rate shrinks the margin for transceiver loop delay and bus settling. I'd verify the sample point settings across all nodes (they must agree), confirm the transceiver's loop delay is within the data-phase budget, and check that termination and stub lengths are appropriate for the data-phase rate rather than the arbitration rate.

I'd also look at whether the node recovers automatically. Many controllers support automatic bus-off recovery after a defined number of integration cycles; if the firmware leaves it in a manual-recovery state, a transient error becomes a permanent outage. For a medical device that's a design decision worth revisiting — automatic recovery with a bounded retry and a logged event is usually safer than requiring a reset, provided the application can tolerate the node being briefly absent. Finally, I'd capture the error frames on a bus analyzer with timestamps to see whether the bus-off is preceded by a burst of form/stuff/CRC errors, which would localize the problem to a specific frame or a specific transmitter.

**Possible follow-ups:**
- How would you distinguish a bit-timing/sample-point problem from a physical-layer (termination, stub, transceiver) problem using only a scope and the controller's error registers?
- If the node is safety-critical, what would you want the firmware to do during the bus-off window before recovery completes?

## Q2: How would you approach selecting between RS-422 and RS-485 for a medical device that needs to connect a central controller to several distributed sensor modules?

**Answer:** The core difference is topology and directionality, so I'd start by asking whether the link is point-to-point or multi-drop, and whether any node ever needs to transmit. RS-422 is a four-wire, full-duplex, single-driver/multiple-receiver standard — one transmitter, up to ten receivers, no bus contention possible. RS-485 is a two-wire (or four-wire) multi-point standard that supports multiple drivers sharing one pair, which requires half-duplex turnaround management and driver-enable control. If the architecture is genuinely one controller broadcasting to many listen-only sensors, RS-422 is simpler and removes an entire class of failure modes: no turnaround timing, no driver-enable races, no risk of two nodes driving simultaneously.

If the sensors need to talk back — which is typical for a patient monitoring system where each module reports its own readings — then RS-485 is the natural fit, and I'd accept the added complexity of half-duplex arbitration. That means budgeting for turnaround time, defining a master-slave polling protocol so only one node transmits at a time, and adding fail-safe biasing so the bus doesn't float into an undefined state between transmissions. I'd also check the common-mode voltage range: RS-485 receivers typically handle a wider common-mode window than RS-422, which matters when nodes are spread across a patient monitoring system with different ground references.

Other selection factors: cable length and data rate (both standards trade off the same way, so the real question is whether the required rate and distance fit the chosen transceivers), whether power-over-bus is needed (RS-485 is the more common choice for that), and whether the medical device's isolation requirements push toward a particular transceiver family. I'd also consider whether a mixed approach makes sense — RS-422 for a dedicated high-rate downlink and RS-485 for the shared uplink — but that usually adds cost and connector complexity without a clear benefit unless the traffic patterns genuinely diverge.

**Possible follow-ups:**
- How would you handle fail-safe biasing on an RS-485 bus where nodes are added or removed during service?
- What changes if the sensors are powered from the same cable (power-over-data-line)?

## Q3: You're debugging a UART link where the receiver reports framing errors only when a high-current load (e.g., a motor or heater) switches on the same board. How would you approach this?

**Answer:** Framing errors that correlate with a switching load are almost always a signal-integrity or ground-reference problem, not a UART configuration problem — the UART is correctly reporting that the stop bit wasn't where it expected it, which means the received waveform was distorted at the moment of the switching event. I'd start by scoping the UART line and the load's switching node simultaneously, triggering on the load's edge, to see whether the corruption is a glitch on the data line, a shift in the ground reference between the two endpoints, or a brief loss of the receiver's ability to distinguish mark from space.

The most common causes are: ground bounce from the high-current return path sharing impedance with the UART's ground reference, capacitive coupling from the switching node into the UART traces, and power-rail droop causing the receiver's input threshold to shift momentarily. I'd check the layout first — is the UART return path separate from the motor/heater return, or do they share a plane or trace? Is the UART routed near the switching node or its gate drive? A quick experiment is to temporarily reroute the UART with a twisted pair and a separate ground return; if the errors disappear, it's a grounding/coupling issue rather than a UART peripheral issue.

On the firmware side, I'd confirm the error is genuinely a framing error and not a symptom of the receiver being reset or the clock being disturbed — some MCUs will report framing errors if the peripheral's clock source glitches. I'd also check whether the errors are one-sided (only when the load switches on, or also when it switches off) and whether they persist after the load settles. If the root cause is coupling, the fixes are layout and filtering: separate the return paths, add series termination or a small RC on the UART line if the edge rate is excessive, and consider whether the load's switching edge can be slowed without violating its own requirements. If the root cause is ground shift, the fix is usually a proper star ground or an isolated UART transceiver — which for a medical device may also be required for patient isolation anyway.

**Possible follow-ups:**
- How would you decide between adding an isolated UART transceiver versus fixing the grounding, given the cost and board-space trade-offs?
- What would you check in the UART configuration itself to rule out a baud-rate or oversampling issue before blaming the hardware?

## Q4: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The goal is to separate *what* the application wants (read a sensor register, send a command, receive a stream of samples) from *how* it gets there (which bus, which framing, which timing). I'd start by defining a transport-agnostic interface at the level of the operations the application actually performs — something like `read_register(device, address, buffer, length)`, `write_register(...)`, and for streaming devices a `subscribe(callback)` or a ring-buffer handle. The interface should not leak transport-specific concepts: no "chip select," no "clock stretching," no "CAN ID" in the application-facing API.

Underneath, each transport implements that interface. An I2C backend knows about device addresses and repeated-start sequences; an SPI backend knows about chip-select lines and CPOL/CPHA; a UART backend knows about framing and flow control; a CAN-FD backend knows about message IDs and segmentation for payloads larger than a single frame. The application picks a transport at initialization — often via a device descriptor table that maps a logical sensor to a concrete backend — and never changes afterward. This is where a small device-descriptor structure helps: it holds the transport pointer, the transport-specific addressing, and any per-device timing constraints, so the application just iterates over devices.

Two design points matter for medical devices. First, error semantics must be normalized: a NACK on I2C, a CRC failure on CAN-FD, and a framing error on UART should all surface to the application as a common "transaction failed" result with enough detail for logging, but not as transport-specific error codes the application has to interpret. Second, timing and blocking behavior must be consistent — if the application expects a read to complete within a bounded time, the abstraction should enforce that, either by making all backends non-blocking with a completion callback or by giving each backend a timeout that maps to the same application-visible contract. I'd also keep the abstraction thin: it's tempting to build a full protocol stack, but the value is in decoupling, not in reimplementing each bus. Testability comes from being able to substitute a mock backend that returns canned data, which lets the application logic be tested without any hardware.

**Possible follow-ups:**
- How would you handle a transport that supports a feature the others don't — for example, CAN-FD's multi-frame segmentation — without leaking that into the application API?
- Where would you put the boundary between the abstraction layer and the RTOS (e.g., Zephyr's device model), and why?

## Q5: Imagine you're leading a design review where a junior engineer proposes using a single shared interrupt line for three different peripherals — a UART, an SPI sensor, and a GPIO alarm input — arguing that it saves pins and the firmware can just poll the peripherals to find out which one fired. How would you guide the team to evaluate this approach?

**Answer:** I'd treat this as a legitimate trade-off to evaluate rather than a proposal to reject, because pin count is a real constraint and the engineer's instinct — share the line, resolve in firmware — is a known pattern. The question is whether the *cost* of resolving in firmware is acceptable for this system. I'd frame the discussion around three axes: latency, determinism, and failure modes.

On latency: a shared interrupt means the ISR must poll all three peripherals to find the source, and the worst case is that the alarm input fires while the UART is mid-burst and the SPI sensor is asserting. The alarm is the one that matters most in a medical device — if it's a patient alarm, the time from assertion to the application being notified is a safety-relevant number, and it should be bounded and small. Polling three peripherals adds a few microseconds at best, but if any of them requires a slow register read or a bus transaction to clear its flag, the alarm latency becomes dependent on unrelated peripherals. That's the kind of coupling that's hard to reason about later.

On determinism: with separate interrupt lines, each peripheral's ISR runs independently and the priority scheme is explicit. With a shared line, the firmware has to impose an ordering — usually alarm first, then the others — and that ordering has to be maintained as the system evolves. It's doable, but it's a policy that lives in code rather than in the hardware, and it's easy to break during a later change.

On failure modes: a shared line means a stuck-asserting peripheral can mask the others. If the SPI sensor's interrupt line latches high due to a fault, the alarm input may never be seen. That's a single point of failure that wouldn't exist with separate lines. For a medical device, that's usually the deciding argument.

I'd guide the team to a decision by asking: what's the actual pin budget, and is there a middle ground? Often there is — for example, share the line between the two non-safety-critical peripherals and give the alarm its own dedicated interrupt, or use a small I/O expander with per-pin interrupt status so the shared line is resolved in hardware rather than by polling. If the team still wants to share all three, I'd ask them to document the latency budget, the priority policy, and the failure-mode analysis, and to add a test that verifies the alarm is still seen when the other two peripherals are active. That turns the proposal into something reviewable rather than a hand-wave.

**Possible follow-ups:**
- How would you verify the alarm latency claim during bring-up — what would you measure, and against what budget?
- If the team later needs to add a fourth peripheral, how would the shared-line design scale, and at what point would you insist on a different approach?
