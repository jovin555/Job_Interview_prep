# protocols — Day 101

## Q1: How would you approach debugging an I2C bus where a device intermittently NACKs its address, but only at 400 kHz and only after the board has warmed up for a while?

**Answer:** This pattern — speed-dependent and temperature-dependent — points at the analog layer rather than the protocol layer, so I'd start by separating those two hypotheses. First I'd confirm the failure is genuinely a NACK on the address byte (not a lost arbitration or a stuck bus) by capturing the transaction with a logic analyzer or scope and looking at where in the frame the failure occurs. Then I'd look at the physical signals at 400 kHz: rise and fall times on SDA/SCL, whether the pull-up values are marginal for the actual bus capacitance, and whether the high level is reaching a valid V_IH at the device with margin. Warm-up dependence strongly suggests something drifting with temperature — pull-up resistor tolerance, a marginal timing margin in the device's setup/hold, or a clock-stretching timeout being exceeded as the slave's internal timing shifts. I'd measure the actual rise time against the I2C spec limits for fast mode, check the effective bus capacitance against what the pull-ups were sized for, and probe at the device pin rather than at the master to see how much margin is being eaten by the interconnect. I'd also check whether the master's timeout for clock stretching is tight enough that a slightly slower slave response at temperature trips it. The fix is usually to re-size pull-ups for the real capacitance and target rise time, reduce bus capacitance (shorter stubs, fewer devices per segment), or relax the master's timing assumptions — but I'd want the measurement to drive which one.

**Possible follow-ups:** How would you calculate the pull-up range that satisfies both the rise-time requirement and the sink-current limit of the devices? If the scope shows clean edges but the NACK persists, where would you look next?

## Q2: How would you approach structuring firmware so that an SPI master can talk to several slaves requiring different clock speeds and different CPOL/CPHA modes, without mode changes corrupting transactions?

**Answer:** The core risk is that CPOL/CPHA and clock rate are properties of the *transaction*, not the bus, so any code path that changes them mid-stream or leaves the peripheral in an inconsistent state between transfers can produce a corrupted frame — a slave seeing a spurious edge, or a transfer starting before the new mode has settled. I'd structure this as a per-device descriptor that carries its mode, max clock, word size, and chip-select, and route every access through a single bus-manager layer that: selects the correct chip select, reconfigures the peripheral to that device's mode and speed, performs the transfer, and then returns the bus to a safe idle state (clock idle at the correct polarity, CS deasserted). Critically, I'd enforce that reconfiguration only happens while all chip selects are deasserted, so no slave is ever listening during a mode change. I'd also guard the bus with a mutex so that a higher-priority task can't interleave a transfer to a different-mode device halfway through. On the hardware side I'd confirm that the slaves tolerate the clock idling at whatever level the previous device's CPOL left it — some parts are sensitive to the state of SCK at CS assertion — and if not, explicitly park the clock at the level the next device expects before asserting its CS. Testing this means exercising back-to-back transfers alternating between devices with opposite modes and different speeds, and scoping the boundaries to confirm no glitch on SCK or CS.

**Possible follow-ups:** What would you do if two slaves on the bus require incompatible idle clock levels and neither tolerates the other's? How would you verify the mode-change sequencing under RTOS preemption?

## Q3: You're debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward. How would you approach this?

**Answer:** Bus-off means the controller's transmit error counter crossed the threshold, so the question is what was generating errors fast enough to accumulate that count — and why the node doesn't recover on its own. First I'd check whether automatic bus-off recovery is even enabled in the controller configuration; many CAN controllers can be set to stay off until software intervenes, which would explain the "stays off" behavior and is a configuration issue rather than a bus issue. Then I'd dig into *why* the TEC climbed: I'd enable error counters and error-warning/error-passive interrupts and log the error state transitions with timestamps, and capture the bus to see whether the node is the one transmitting error frames or whether it's being disturbed by another node. Common causes are a marginal bit-timing configuration (sample point or SJW not matched to the actual bus length and bit rate), a transceiver with poor common-mode behavior, a stub or termination problem that only bites at the data-phase bit rate, or a single dominant-stuck condition from another node. Because CAN-FD has a much faster data phase, bit-timing margins that were fine at classic rates can fail only in the data phase, so I'd specifically verify the data-phase timing against the physical bus. I'd also check whether the node is transmitting at a rate that collides repeatedly with a higher-priority frame — repeated arbitration loss doesn't cause bus-off, but repeated errors during its own transmission do. The recovery strategy in firmware should log the event, count occurrences, and only auto-recover after confirming the bus is idle, so a persistent fault doesn't cause an endless error loop.

**Possible follow-ups:** How would you distinguish a bit-timing problem from a physical-layer problem using only the error counters and a bus capture? What safeguards would you put around automatic bus-off recovery in a medical device?

## Q4: How would you approach selecting a communication protocol for a medical sensor network where some nodes need deterministic low-latency response for closed-loop control while others generate bursty high-volume telemetry, all sharing one physical medium?

**Answer:** I'd treat this as a requirements-partitioning problem before a protocol-selection problem. The two traffic classes have genuinely different needs — one wants bounded latency and jitter, the other wants throughput and can tolerate delay — and forcing both onto one medium is where most of the risk lives. So I'd first quantify: what's the actual worst-case latency budget for the control loop, what's the peak and average telemetry volume, how many nodes, what cable length and topology, and are there power-over-bus or isolation requirements. With those numbers I'd compare candidates against the binding constraint. CAN-FD is attractive when determinism matters because arbitration gives priority-based bounded latency and the data phase gives throughput, but I'd check whether the telemetry volume plus the control traffic still leaves the control message's worst-case latency within budget under worst-case bus load — the higher data rate doesn't remove the need for that analysis. RS-485 with a well-designed master-scheduled protocol can give determinism through time-slotted polling, but the turnaround timing and the polling overhead become the constraint at scale. A star or switched topology (e.g., point-to-point links to a hub) can physically separate the two traffic classes, which is often the cleanest answer if the cabling allows it. I'd also weigh the regulatory and lifecycle cost: a simpler, well-understood protocol with clear fault behavior is easier to justify in a medical submission than a complex one. My default instinct is to avoid a single shared medium carrying both classes if the control loop's latency budget is tight, and instead either prioritize rigorously on a priority-capable bus or physically separate the paths.

**Possible follow-ups:** If you had to keep both classes on one CAN-FD bus, how would you prove the control message's worst-case latency? What would make you reject a shared-medium approach outright?

## Q5: How would you handle a situation where a junior engineer on your team implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** First priority is containment and honesty: understand exactly what's wrong, assess whether it affects safety or only the test outcome, and make sure the finding is documented and escalated through the correct channels rather than quietly patched. Then I'd separate the technical fix from the process question, because both matter. Technically, I'd get the engineer and a reviewer to reproduce the failure in a bench setup, characterize the actual protocol deviation against the spec, implement and verify the fix, and re-run the affected compliance tests — with a clear record of what changed for the submission. Process-wise, the real question is why the defect escaped to compliance testing, and I'd want to look at that without turning it into a blame exercise: was there a protocol conformance test that should have caught it earlier, was the spec ambiguous, was the review too shallow on the protocol layer? I'd add the missing test or review gate so the same class of error can't recur. With the junior engineer specifically, I'd frame it as a learning opportunity, walk through the failure and the reasoning that would have caught it, and pair them with a senior reviewer on the fix so they own the correction rather than being sidelined. I'd also be candid with stakeholders about the schedule impact and the recovery plan rather than softening it. The goal is a fixed defect, a strengthened process, and an engineer who's more capable afterward — not a scapegoat.

**Possible follow-ups:** How would you decide whether the schedule slip requires re-sequencing other work or adding resources? What would you change in the review process to catch protocol errors before compliance testing?
