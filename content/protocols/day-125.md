# protocols — Day 125

## Q1: How would you approach debugging an I2C bus where a slave device holds SDA low after a transaction, preventing any further communication until power is cycled?

**Answer:** This is the classic "stuck bus" scenario, and the first thing to establish is *which* condition is actually present: SDA held low, SCL held low, or both. I'd scope both lines and look at the state right at the moment the bus wedges — whether the slave is mid-byte, whether the master aborted a transaction partway, or whether a glitch on SCL caused the slave's bit counter to desynchronize from the master's. A very common root cause is a master reset or firmware abort occurring mid-transaction: the slave is left expecting more clock edges to finish the byte it was shifting out, so it keeps driving SDA low waiting for clocks that never come. The recovery mechanism is to manually clock SCL as a GPIO for up to nine pulses while monitoring SDA, then issue a STOP condition — this walks the slave's state machine to the end of its byte and lets it release the line. Beyond recovery, I'd want to understand *why* it happened: is the master timing out and resetting the peripheral mid-transfer? Is there a missing repeated-START or a spurious STOP? Is the slave's datasheet specifying a maximum hold time the master is violating? The fix is usually a combination of a bus-recovery routine in the driver's error path (clock out nine pulses, generate STOP, reinit the peripheral) plus eliminating the firmware behavior that abandons transactions mid-flight. In a medical device I'd also want the recovery to be automatic and logged, because a bus that requires a power cycle to recover is not acceptable in the field.

**Possible follow-ups:** How would you distinguish a slave holding SDA low from a bus contention issue caused by two devices driving simultaneously? Would you put the recovery routine in the driver, the application, or a supervisory task, and why?

## Q2: How would you approach selecting between RS-232, RS-422, and RS-485 for a medical device that needs to connect a central controller to several distributed sensor modules?

**Answer:** I'd start from the topology and electrical environment rather than from the protocol names. RS-232 is point-to-point, single-ended, short-reach, and referenced to a common ground — it's fine for a local console or a single nearby peripheral, but it doesn't scale to multiple distributed nodes and it's vulnerable to ground potential differences and common-mode noise. RS-422 is differential and point-to-point (one driver, multiple receivers), so it gives good noise immunity and longer reach but doesn't support multiple drivers on the same pair. RS-485 is differential *and* multi-drop with tri-state drivers, so multiple nodes can share one twisted pair in half-duplex — which is usually what "several distributed sensor modules" implies. So the decision tree is: does the topology need more than one transmitter on the bus? If yes, RS-485. If it's genuinely one talker and many listeners, RS-422 is simpler and avoids turnaround complexity. If it's a single short local link, RS-232 may be adequate and cheapest. Then I'd layer in the medical-specific requirements: common-mode voltage range (RS-485 transceivers typically handle a wider range, which matters with distributed grounds), isolation (patient-connected equipment often needs galvanic isolation on the bus), fail-safe biasing so an idle or disconnected bus doesn't float into an undefined state, and termination strategy for the cable length and node count. I'd also consider whether the modules need to be powered over the same cable, which pushes toward RS-485 with power-over-data-line. The answer usually lands on RS-485 for a multi-node distributed medical sensor network, but I'd want the topology, cable length, node count, and isolation requirements on the table before committing.

**Possible follow-ups:** What would change in your answer if the modules were all within a single enclosure on one PCB? How would you handle a mixed system where some modules are RS-485 and one legacy module is RS-232?

## Q3: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The core idea is to define a transport-agnostic interface at the boundary the application cares about — typically a small set of operations like `open`, `read`, `write`, `ioctl`/`configure`, and `close`, expressed in terms of *messages* or *register accesses* rather than bus-specific primitives. Each transport then implements that interface as a driver: the I2C backend turns a register-read request into a START, address, register, repeated-START, read, STOP sequence; the SPI backend turns it into a chip-select assertion, mode/clock setup, full-duplex transfer, and deassertion; the UART backend frames it with whatever framing the protocol uses; the CAN-FD backend maps it onto message IDs and DLCs. The application layer holds a handle to the interface and never sees a bus type. Two things make this work in practice. First, the interface has to be designed around the *semantics* the application needs — if the application needs "read 16-bit register at address X from device Y," that's the abstraction; if it needs "send this 64-byte payload and get an ack," that's a different abstraction, and trying to serve both with one interface leads to leaky, lowest-common-denominator APIs. Second, transport-specific concerns like timing, retries, error codes, and power management need a defined home: I'd keep retry policy and error mapping in the transport layer (an I2C NACK and a CAN-FD bus-off are different failures that shouldn't leak upward as raw codes), and expose a normalized error taxonomy to the application. For testability, the abstraction also lets you substitute a mock transport in unit tests, which is a big win for a medical device where you want to exercise application logic without hardware. The trade-off to be honest about is that a too-generic interface can hide transport-specific capabilities the application genuinely needs (e.g., CAN-FD's priority arbitration, or I2C clock stretching behavior), so I'd allow an optional escape hatch — a transport-specific `ioctl` — rather than forcing everything through the lowest common denominator.

**Possible follow-ups:** How would you handle a transport that needs asynchronous completion (e.g., a CAN-FD transmit that completes via interrupt) when the interface was designed as blocking? Where would you put end-to-end integrity checking — in the abstraction layer or in each transport?

## Q4: You're debugging a CAN-FD network where a node intermittently enters error-passive state and then recovers on its own, with no obvious pattern. How would you approach this?

**Answer:** Error-passive means the node's transmit error counter (TEC) or receive error counter (REC) has crossed 128, so the first job is to find out *which* counter is climbing and *what error type* is incrementing it. Most CAN controllers expose per-error-type counters or at least the last error code — I'd instrument the firmware to log TEC, REC, and the last error code (bit error, stuff error, CRC error, form error, ACK error) on every transition, with a timestamp, and correlate against bus traffic. The pattern matters: if it's the *receive* counter climbing, the node is seeing errors on frames it's trying to receive — often a sign of a bit-timing problem at the data-phase bit rate, a marginal transceiver, or a node whose clock tolerance is off. If it's the *transmit* counter, the node is failing to get its own frames acknowledged or is losing arbitration in a way that suggests a physical-layer issue on its branch of the bus. The "recovers on its own" detail is a strong clue: error-passive is not latched, so a node that stops transmitting for a while will see its TEC decay and return to error-active — meaning the node is probably only error-passive during bursts of activity, which points at a load- or timing-dependent cause. I'd then look at the physical layer: sample-point settings and SJW for the data phase, whether all nodes agree on the same nominal and data bit rates, termination and stub lengths, and whether the transceiver's loop delay is compatible with the chosen data-phase rate. A very common cause is a data-phase bit rate that's too aggressive for the bus length and transceiver delays, so errors only appear when a particular node transmits a long frame. I'd also check for a single misbehaving node that's corrupting frames for everyone — in that case the *other* nodes' error counters climb too, and the culprit is the one whose TEC stays low. The fix depends on the finding: retune bit timing, shorten stubs, fix termination, replace a marginal transceiver, or reduce the data-phase rate.

**Possible follow-ups:** How would you distinguish a bit-timing problem from a physical-layer problem using only the error counters and a scope? What would you do if only one node ever goes error-passive and every other node is clean?

## Q5: How would you handle a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** The first priority is containment and honesty: understand exactly what's wrong, what the compliance impact is, and whether the finding is a test failure that can be re-run after a fix or something that affects the submission itself. I'd pull the engineer in immediately — not to assign blame, but because they know the implementation best and the fastest path to a correct fix runs through them. In parallel I'd get the compliance lead and project manager into the loop with a clear, factual description of the defect, the likely fix, and a realistic re-test timeline, because schedule decisions are theirs to make and they need accurate information early. Then I'd structure the technical response as a proper root-cause exercise: what was the requirement, what did the implementation do, why did the gap survive design review and unit test, and what test or review would have caught it. That last question is the important one — a defect that reaches compliance testing usually means a gap in the verification process, not just a coding mistake, and fixing only the code leaves the process gap in place. On the human side, I'd be deliberate about how the feedback lands: the engineer is likely already stressed, and the useful message is "here's the gap, here's how we close it, here's what we change in our process so this class of error gets caught earlier" — not a post-mortem that makes them defensive. I'd also look at whether the review process itself failed: was the protocol spec ambiguous, was there no independent reviewer, was the test plan derived from the spec or from the implementation? If the spec was ambiguous, that's a shared failure and I'd say so. Finally, I'd capture the lesson in the team's checklist or review template so the next protocol implementation gets scrutinized the same way, and I'd follow up with the engineer afterward to make sure the experience didn't make them risk-averse about raising issues early.

**Possible follow-ups:** How would you decide whether to fix the implementation or revise the requirement, if the requirement itself turns out to be ambiguous? What would you change in the design-review process to catch protocol framing errors before compliance testing?
