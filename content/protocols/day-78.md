## Q1: How would you approach debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward?

**Answer:** Bus-off is a terminal error state the controller enters after its transmit error counter exceeds a threshold, so the first question is *why* the node accumulated errors in the first place — the "healthy bus afterward" observation is a red herring, because the node has stopped participating by then and can no longer generate errors. I'd approach it in layers. First, capture the error counters (TEC/REC) and the last error code register before the reset, since most controllers latch the reason for the most recent error — bit error, stuff error, form error, ACK error, or CRC error. That single register usually narrows the search dramatically. An ACK error with a healthy bus often points to a timing or sample-point mismatch: the node's bit timing (prescaler, TSEG1/TSEG2, SJW) may be marginally off relative to the rest of the network, so it fails to see the ACK slot correctly under certain conditions. A bit error during arbitration can point to a transceiver issue or a ground-offset problem between nodes. Second, I'd check whether the failure correlates with bus load, temperature, or a specific message — bus-off that only appears under heavy load often traces to insufficient SJW or a sample point that drifts with oscillator tolerance. Third, I'd verify the physical layer: differential voltage levels, common-mode range, termination, and whether the node's transceiver is being driven into a marginal region. Finally, I'd look at the recovery strategy itself — many controllers require software to explicitly clear the bus-off state and re-enter the bus after the recovery sequence, and if that logic is missing or wrong, the node will stay off. So the debugging splits into "why did it go bus-off" and "why didn't it recover," and both need answers.

**Possible follow-ups:**
- How would you distinguish an oscillator-tolerance problem from a transceiver problem using only the error counters and a scope?
- What automatic bus-off recovery behavior would you design into the firmware, and what are the risks of recovering too aggressively?

## Q2: You're designing a half-duplex RS-485 link where the driver-enable and receiver-enable must switch at exactly the right moment, and the turnaround budget is tight. How would you approach this?

**Answer:** Half-duplex RS-485 turnaround is fundamentally a timing problem with three components: when the last bit leaves the driver, when the line settles, and when the receiver is ready to sample. The classic mistake is de-asserting the driver enable too early — the UART's transmit-complete flag fires when the shift register is empty, but the last bit may still be on the wire, so the driver must stay enabled until the transmit-complete (not transmit-empty) condition, plus a small margin for the transceiver's propagation delay. On the receive side, the receiver enable should be asserted before the driver is fully disabled, or you risk clipping the first bit of the response. I'd approach it by first characterizing the transceiver's enable/disable times and the line settling time from the datasheet and, if needed, a scope. Then I'd structure the firmware so the enable/disable is driven by a hardware timer or the UART's own transmit-complete interrupt rather than a software delay, because software delays are not deterministic under interrupt load. If the turnaround budget is genuinely tight, I'd consider a transceiver with automatic direction control (some parts sense the TX line and switch automatically), which removes the firmware timing dependency entirely. I'd also add a guard interval on the receive side and verify the whole sequence with a scope or logic analyzer at the worst-case baud rate and temperature, since transceiver timing shifts with temperature.

**Possible follow-ups:**
- How would you verify the turnaround timing margin across the full temperature range without a dedicated test fixture?
- What happens if two nodes on the bus both enable their drivers at the same time, and how would you prevent it?

## Q3: How would you approach implementing flow control on a UART link where the receiver occasionally cannot keep up with the transmitter, but the protocol has no built-in backpressure mechanism?

**Answer:** When the protocol has no backpressure, you have to add it at a layer the protocol doesn't control — either the electrical layer (hardware flow control) or the framing layer (software flow control), or you change the data flow itself. The cleanest option, if the hardware supports it, is RTS/CTS: the receiver de-asserts its RTS when its buffer crosses a high-water mark and re-asserts below a low-water mark, and the transmitter's UART hardware automatically pauses. That removes the software timing problem entirely, but it requires two extra wires and both ends to honor it. If the link is only TX/RX, software flow control (XON/XOFF) is possible but risky in a binary protocol, because the flow-control bytes can collide with payload data unless the protocol reserves them or uses an escape scheme. A third approach is to change the data flow: reduce the transmitter's average rate, add application-level acknowledgements, or insert idle gaps so the receiver's buffer drains. In a medical device I'd also want the failure mode to be safe — if the receiver's buffer is about to overflow, dropping data silently is usually unacceptable, so the design should either block the transmitter deterministically or flag the overflow as an error the application can act on. The choice depends on whether the link is lossless by requirement or best-effort, and that requirement should drive the mechanism.

**Possible follow-ups:**
- How would you size the receiver's buffer and set the high/low water marks to avoid overflow without stalling throughput unnecessarily?
- If the protocol is binary and you can't use XON/XOFF, what other in-band flow-control schemes would you consider?

## Q4: In a system where an SPI master talks to several slaves at different clock speeds and with different CPOL/CPHA modes, how would you approach structuring the firmware so that mode and speed changes are handled safely?

**Answer:** The core risk is that SPI mode and clock speed are properties of the *transaction*, not the bus, so any code path that changes them must do so atomically with respect to other transactions and must guarantee the bus is idle before the change. I'd structure the firmware around a per-device descriptor that carries its CPOL, CPHA, max clock, word size, and chip-select line, and a single bus-access function that takes that descriptor, reconfigures the peripheral if the requested mode differs from the current one, asserts the correct chip select, performs the transfer, and de-asserts. The reconfiguration must happen only when no chip select is asserted — changing CPOL/CPHA mid-transaction corrupts the frame, and changing the clock divider while a transfer is in flight can glitch the clock. I'd also serialize access through a mutex or a single-owner task so two callers can't interleave a mode change with another device's transfer. On the hardware side, I'd verify that the chip-select lines are all de-asserted during reconfiguration and that no slave is left selected. For performance, I'd group transactions by device where possible to minimize reconfigurations, but correctness comes first — a mode change is cheap compared to a corrupted frame. Finally, I'd make the descriptor table the single source of truth so a new device can't be added with an inconsistent mode.

**Possible follow-ups:**
- How would you handle a slave that requires a mode change mid-transfer, such as a device that switches CPHA between command and data phases?
- What would you check on a scope to confirm the mode change is clean and no slave is left selected?

## Q5: How would you approach handling a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** The first priority is to separate the technical problem from the people problem, because conflating them makes both worse. Technically, I'd want to understand exactly what the protocol does versus what the specification requires — is it a functional bug, a robustness gap, or a documentation mismatch? That determines whether it's a firmware fix, a spec clarification, or both. I'd pull the relevant requirements and the test evidence together so the team is working from facts, not assumptions. Then I'd assess the schedule impact honestly and look for the least-risk path: can the fix be scoped and verified in a way that satisfies the test house, or does it require a re-test cycle? On the people side, I'd avoid framing it as the junior engineer's failure in front of the team — the more useful question is why the error wasn't caught earlier, which usually points to a gap in review, unit testing, or requirements traceability rather than one person's mistake. I'd have a private conversation to understand what happened, make sure they have the support to fix it, and then address the systemic gap: stronger protocol conformance tests, earlier review of the interface against the spec, and clearer traceability from requirement to test. The goal is to fix the immediate problem, protect the schedule as much as possible, and make sure the same class of error is caught earlier next time — not to assign blame.

**Possible follow-ups:**
- How would you decide whether to fix the protocol in firmware or seek a deviation from the test house, and what factors would drive that decision?
- What changes to your review or test process would you put in place to catch protocol conformance issues before regulatory testing?
