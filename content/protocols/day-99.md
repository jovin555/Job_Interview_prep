# protocols — Day 99

## Q1: How would you approach debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward?

**Answer:** The key insight is that "bus-off" is a state the controller enters after its transmit error counter (TEC) exceeds 255, and the controller only leaves it after 128 occurrences of 11 consecutive recessive bits — so if it stays off, either the recovery condition is never met or the firmware never re-enables the controller. I'd separate those two possibilities first. On the recovery side, I'd check whether the node's firmware explicitly handles the bus-off interrupt and initiates recovery, or whether it relies on the controller's automatic recovery and that feature is disabled. Many controllers require the application to clear the init bit or wait out the recovery sequence, and a firmware that treats bus-off as a fatal error will sit there forever. On the cause side, I'd look at why TEC climbed in the first place: a node that is the only transmitter of a particular frame ID with no other node acknowledging it will accumulate errors rapidly, so a disconnected or unpowered peer can drive a healthy-looking bus into bus-off for the remaining node. I'd also check for a bit-timing mismatch — a node whose sample point or prescaler is slightly off will generate error frames under certain arbitration patterns and recover between bursts, which matches the "appears healthy afterward" symptom. Practical steps: log the error counters and error codes over time, use a CAN analyzer to capture the exact frames preceding each bus-off, verify every node's nominal and data-phase bit timing against the same clock tolerance assumptions, and confirm the firmware's bus-off recovery path is actually exercised in a test. The fix is usually either correcting bit timing on one node or making the firmware's recovery deterministic and observable.

**Possible follow-ups:** How would you distinguish a bit-timing problem from a missing-acknowledgment problem using only error-counter telemetry? What would you change in the firmware to make bus-off recovery testable in a bench setup?

## Q2: How would you approach selecting a communication protocol for a medical sensor network where some nodes require deterministic low-latency response for closed-loop control, while other nodes generate bursty high-volume telemetry, and all must share one physical medium?

**Answer:** I'd start by writing down the requirements as numbers rather than adjectives: worst-case latency for the control loop, jitter tolerance, peak and average telemetry bandwidth, cable length and topology constraints, node count, power budget, and whether any node needs power over the bus. Then I'd evaluate candidates against those numbers. For deterministic low-latency control sharing a medium with bursty traffic, the decisive property is whether the protocol gives you bounded arbitration latency by design — CAN-FD's priority-based arbitration gives you a computable worst-case response time for the highest-priority frame, whereas a polled RS-485 master-slave scheme gives determinism only if you can bound the polling cycle, and a CSMA-style scheme gives you none. The trade-off is that CAN-FD's payload per frame and bus length are constrained by bit rate, so high-volume telemetry may need segmentation or a separate path. A common sound architecture is to split by traffic class: keep the closed-loop control on a deterministic bus (CAN-FD or a dedicated point-to-point link), and put bulk telemetry on a separate interface or on lower-priority frames with explicit bandwidth budgeting. I'd also consider whether the control loop truly needs to cross the network at all — moving the loop local to the actuator often removes the hardest requirement. Finally, I'd validate the choice with a schedulability or utilization analysis before committing, and document the assumptions so they can be re-checked if node count or rates change.

**Possible follow-ups:** How would you compute a worst-case response time for the highest-priority CAN-FD frame in a mixed-traffic system? What would make you decide that two separate physical networks are justified over one shared bus?

## Q3: How would you approach designing fail-safe biasing for an RS-485 bus, and why does it matter more in a medical device than in a general industrial network?

**Answer:** Fail-safe biasing guarantees that when no driver is active — all transceivers in receive mode — the differential pair sits at a defined logic level rather than floating near the threshold, where noise can produce spurious start bits and garbage bytes. The standard approach is a pull-up on one line and a pull-down on the other, sized so the bias network presents enough differential voltage to exceed the receiver's threshold with margin, while still presenting an acceptable load to the active driver. The calculation has to account for the termination resistors in parallel with the bias network, the number of receivers, and the worst-case driver differential output — and the bias resistors must be small enough to develop the required voltage but large enough not to overload the driver or waste power. It matters more in a medical device because a spurious byte on a bus carrying patient-parameter data or control commands is a safety-relevant event, not just a retry: a phantom frame could be interpreted as a valid message if the protocol layer isn't defensive, and in a half-duplex system a floating bus during turnaround is exactly when this happens. So I'd treat fail-safe biasing as part of the safety argument, not just a signal-integrity nicety, and pair it with protocol-level defenses — framing checks, sequence numbers, CRC, and timeouts — so that a single physical-layer glitch can't be mistaken for data. I'd also verify the bias network across the full common-mode range and temperature, since resistor tolerance and transceiver threshold drift both eat into the margin.

**Possible follow-ups:** How would you verify fail-safe biasing on the bench without a protocol analyzer that can see sub-bit glitches? What happens to your bias calculation if a node's transceiver fails in a state that partially loads the bus?

## Q4: You're debugging a USB 2.0 device that intermittently fails enumeration on one particular host, where the failure appears as a control-transfer timeout during descriptor reads, but the same device enumerates reliably on other hosts. How would you approach this?

**Answer:** I'd treat it as a three-way isolation problem: descriptor content, device firmware timing, and host controller behavior. First, I'd capture the actual bus traffic with a USB analyzer on the failing host to see exactly which control transfer times out and at what stage — whether it's the initial GET_DESCRIPTOR for the device descriptor, a later descriptor, or a SET_ADDRESS/SET_CONFIGURATION step. That tells me whether the device is responding slowly, responding with a malformed packet, or not responding at all. If the device is slow, I'd look at firmware: whether descriptor requests are handled in the interrupt context or deferred to a task that can be delayed, whether the device stalls on a request it doesn't recognize instead of returning a proper STALL, and whether the endpoint zero max packet size and the reported descriptor lengths are self-consistent. If the device responds correctly on the analyzer but the host still times out, the problem is host-side — some host controllers are stricter about timing, retry behavior, or descriptor consistency, and a device that relies on the host being lenient will fail there. I'd also check for a known class of issues: a device that reports a descriptor length larger than what it actually returns, or that changes its descriptor between the first and second read, will confuse hosts that cache the first read. The fix is usually to make the descriptor set internally consistent and to make endpoint-zero handling deterministic and fast, then re-test across the full host matrix rather than just the one that failed.

**Possible follow-ups:** What specific descriptor inconsistencies most commonly cause this kind of host-dependent enumeration failure? How would you build a host-compatibility test matrix that catches this before a customer does?

## Q5: How would you handle a situation where a junior engineer on your team implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** I'd separate the immediate response from the systemic response. Immediately, the priority is containment and honest assessment: understand exactly what's wrong, whether it affects safety or only conformance, what the smallest correct fix is, and what the realistic schedule impact is — then communicate that to the project lead and quality early rather than letting it surface later. I'd resist the instinct to assign blame in the moment; the engineer needs to be part of the fix, not sidelined by it. For the fix itself, I'd want the correction reviewed by someone other than the original author, and I'd want a test that reproduces the failure so we can prove the fix works and prevent regression. Then the systemic part: a protocol error that survives to compliance testing usually means the gap was in verification, not just in one person's work — so I'd look at whether the protocol had a written specification with testable requirements, whether there was a conformance test plan executed before formal testing, and whether code review covered protocol state machines rather than just style. The constructive framing with the engineer is that this is a process gap we're closing together, and the specific lesson is about testing against the spec rather than against the happy path. I'd also make sure the retrospective captures the root cause in a way that improves the next project's verification plan, not just this one's schedule.

**Possible follow-ups:** How would you decide whether to fix forward in the current build or roll back to a known-good protocol implementation? What would you change in the design review process to catch protocol state-machine errors earlier?
