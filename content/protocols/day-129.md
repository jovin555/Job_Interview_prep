# protocols — Day 129

## Q1: How would you approach debugging a USB 2.0 device that enumerates and works correctly on a self-powered hub but intermittently drops off the bus when connected directly to a host root port, with the disconnects correlating with periods of high data throughput?

**Answer:** This pattern points at the power/current budget rather than the protocol itself. A self-powered hub supplies its own VBUS current, so the device can draw more than the host root port is willing to give; a root port enforces the host controller's per-port current limit and will drop the port on an overcurrent or brownout condition. The first step is to measure actual current draw in the failing scenario — not just the average, but the transient peaks during high-throughput bursts, since the radio/PHY or a switching regulator can pull a spike that trips the port protection. I'd compare that against what the configuration descriptor declares in `bMaxPower` and against the host's advertised capability. If the declared budget is lower than the real draw, that's a descriptor bug that also happens to be a spec violation. Beyond current, I'd check VBUS droop with a scope at the device connector during the burst — a marginal bulk cap or a long/thin cable can cause the rail to sag below the UVLO threshold, which looks like a disconnect. I'd also rule out signal integrity: a root port may have different trace lengths and ESD protection than a hub downstream port, so eye-diagram and termination on D+/D− are worth checking. The fix depends on the cause: correct the descriptor and add bulk capacitance / inrush limiting if it's a power issue, or address the PHY/layout if it's signal integrity. In a medical device I'd also want the failure mode to be safe — a disconnect mid-stream must not leave the host displaying stale data.

**Possible follow-ups:** How would you distinguish a VBUS droop from a genuine protocol-level disconnect using only a scope and the host's kernel logs? What would you change in the descriptor if the device genuinely needs more than 100 mA?

## Q2: How would you approach selecting between RS-485 and CAN-FD for a medical device network where a central controller must talk to a mix of motor-control nodes needing bounded-latency commands and sensor nodes producing periodic telemetry?

**Answer:** I'd frame the decision around four axes: determinism, topology, fault containment, and the regulatory/documentation burden. CAN-FD gives you hardware arbitration with priority-based access, so a high-priority command frame wins the bus by ID — that's a strong fit for bounded-latency motor control, and the multi-master model means nodes can also originate traffic (fault reports, alarms) without the controller polling them. RS-485 is a physical layer only; determinism comes from whatever higher-layer protocol you impose (typically a master-slave poll), which means latency scales with poll cycle and node count, and a chatty node can't preempt. On the other hand, RS-485 is simpler, cheaper per node, tolerant of long cable runs, and easy to make fail-safe with biasing — and it's well understood by certification bodies. CAN-FD's data-phase bit rate buys throughput but shortens the achievable bus length, so if the nodes are physically spread out I'd check the bit-rate/length trade-off carefully. I'd also weigh error handling: CAN has built-in error counters, error frames, and bus-off recovery, which is attractive for safety-related traffic, but bus-off behavior itself needs a defined recovery policy. For a medical device I'd add the documentation angle — whichever I pick, the protocol behavior, timing budget, and failure modes have to be traceable in the risk file. My default lean: CAN-FD if bounded latency and multi-master fault reporting are hard requirements; RS-485 with a disciplined polling protocol if the topology is simple, long, and cost-sensitive.

**Possible follow-ups:** If you chose RS-485, how would you guarantee the motor command latency bound as node count grows? What CAN-FD bus length would you expect at a 5 Mbit/s data phase, and how would that constrain your physical layout?

## Q3: How would you approach designing the descriptor hierarchy for a USB 2.0 medical device that must present a HID interface for simple status reporting and a vendor-specific bulk interface for firmware updates, while enumerating reliably across a wide range of hosts?

**Answer:** I'd start from the principle that the descriptor set is the device's contract with an unknown host, so it should be conservative and standards-compliant rather than clever. The device descriptor declares the class at the interface level (class 0x00, "defined at interface"), not at the device level, so the host doesn't try to bind a single class driver to the whole device. Then a configuration descriptor with two interfaces: interface 0 as HID (class 0x03) with its HID descriptor and a single interrupt IN endpoint for status, and interface 1 as vendor-specific (class 0xFF) with a bulk IN and bulk OUT pair for the update path. I'd keep the HID report descriptor minimal and well-formed — a malformed report descriptor is a classic cause of enumeration failures on stricter host stacks. For the update interface, I'd make sure the endpoint max packet sizes and the `bInterval` values are sane and that the total configuration power declaration is honest. I'd also consider whether the two interfaces should be in a single configuration or split into alternate settings; a single configuration with both interfaces is simpler and avoids the host having to switch. The firmware-update path is the risky one — I'd want it to be inert until explicitly activated, so a host that only binds HID never touches the bulk endpoints. Finally, I'd test against a matrix of host controllers (EHCI, xHCI, and at least one embedded host) because descriptor parsing strictness varies, and I'd capture the enumeration trace on each so failures are diagnosable.

**Possible follow-ups:** Why might a host reject a device whose HID report descriptor is technically valid but unusually large? How would you handle the case where the host binds a generic HID driver to interface 0 and never exposes interface 1 to your update tool?

## Q4: You're debugging a CAN-FD network where the bus is clean at the nominal arbitration bit rate but nodes intermittently report CRC and form errors only during the data phase at the higher bit rate. How would you approach this?

**Answer:** The fact that the arbitration phase is clean tells me the topology, termination, and nominal-rate timing are broadly sound, so I'd focus on what changes in the data phase: the bit rate goes up, the bit time shrinks, and the sample point moves. First I'd verify the sample-point configuration on every node — if one node samples at, say, 75% while another samples at 80%, the effective margin shrinks and errors appear only at the higher rate. I'd check that all nodes agree on the data-phase bit timing and that the transceiver's propagation delay and symmetry are within what the higher rate allows; a slow or asymmetric transceiver that's fine at 500 kbit/s can fail at 2–5 Mbit/s. Next, physical layer: at the higher rate, stub lengths and termination matter much more, so I'd look at the bus with a scope or eye-diagram probe at the data-phase rate and check for reflections, ringing, and common-mode shifts. I'd also check whether the data-phase length is being pushed beyond what the cable supports — CAN-FD's higher rate shortens the maximum bus length, and a run that worked at the nominal rate may be marginal in the data phase. Finally, I'd look at whether the errors correlate with specific nodes or specific payload lengths, since a node with a marginal oscillator or a long ground return can be the sole offender. The fix is usually a combination of tightening bit-timing agreement, correcting termination/stubs, and possibly backing off the data-phase rate until the eye is clean.

**Possible follow-ups:** How would you measure the data-phase eye diagram on a live CAN-FD bus without disturbing it? If only one node reports errors, how would you determine whether it's the transmitter or the receiver that's marginal?

## Q5: A junior engineer on your team has implemented a custom framing protocol over UART, and during regulatory compliance testing it's discovered that a single bit error in the length field causes the receiver to consume the next several valid frames as payload, silently corrupting data. How would you handle the situation?

**Answer:** First, I'd treat it as a design defect with a safety implication, not a junior-engineer mistake to be blamed — the framing design lacked the defenses that would have caught this, and that's a review failure as much as an implementation one. I'd contain it immediately: characterize the failure mode precisely (which bit positions, what the receiver does, whether corrupted data can reach a clinical function), document it, and decide with the quality/regulatory lead whether it's a reportable issue or a design change to be captured in the risk file. Then I'd fix the design at the protocol level rather than patching the parser: add a length-field sanity check against the maximum frame size, add a header checksum or CRC that covers the length field, add sequence numbers so a dropped or merged frame is detectable, and add a resynchronization strategy (e.g., a start-of-frame delimiter plus a timeout that flushes the receiver). I'd also add a fuzz/negative test to the verification plan that injects bit errors into every field and asserts the receiver rejects rather than misinterprets. On the people side, I'd walk the junior engineer through the failure analysis so they understand *why* the defenses matter, and I'd use it as a case study in the team's design-review checklist so future custom protocols get the same scrutiny. Finally, I'd re-run the compliance test and capture the evidence for the submission.

**Possible follow-ups:** How would you decide whether this defect requires a design change versus a documentation update to the risk file? What would you add to the design-review checklist so a length-field vulnerability is caught before compliance testing?
