# protocols — Day 94

## Q1: How would you approach debugging a USB 2.0 device that fails enumeration on some hosts but works on others, where the failure appears to be a control-transfer timeout during descriptor reads?
**Answer:** I'd treat this as a host-tolerance problem rather than a device-broken problem, because the device clearly works on some hosts. The first step is to capture what's actually happening on the wire — a USB protocol analyzer on the failing host, so I can see exactly which control transfer stalls or times out and at what stage of enumeration (device descriptor, configuration descriptor, string descriptors, or a class-specific request). That tells me whether the device is NAKing too long, returning a malformed length, or simply not responding in time.

From there I'd reason about the common causes. Descriptor reads are the classic failure point: if the device reports a `bMaxPacketSize0` that doesn't match what it actually implements, or returns a configuration descriptor whose `wTotalLength` disagrees with the sum of the sub-descriptors, a stricter host will reject it while a lenient one tolerates it. I'd also check whether the device is doing too much work inside the control-transfer handler — for example blocking on a slow peripheral read before it can return the descriptor — which can exceed the host's control-transfer timeout on a slower or more heavily loaded host controller. And I'd verify the device handles the standard "read first 8 bytes, then re-read the full descriptor" pattern that many hosts use, since a device that assumes a single full-length read will fail on hosts that do the two-step.

The fix direction depends on what the capture shows: correct the descriptor lengths and packet-size fields, make the control endpoint handler non-blocking and fast (stage the descriptor in RAM, never touch hardware in the interrupt path), and add margin against host timeouts. I'd then re-test across the widest set of hosts I can get — old PCs, embedded hosts, different OS stacks — because "works on my laptop" is exactly the trap here.

**Possible follow-ups:** How would you decide whether the bug is in your descriptor configuration versus the host controller driver, when you can't change the host? What would you look for first in the analyzer trace to distinguish a NAK-storm from a malformed descriptor?

## Q2: How would you approach calculating pull-up resistor values for an I2C bus that must support both standard-mode (100 kHz) and fast-mode (400 kHz) operation with multiple devices on the bus?
**Answer:** The pull-up value is bounded from both sides, and the job is to find the window that satisfies both bounds at the fastest speed you need to support — here 400 kHz, since that's the tighter constraint.

The upper bound comes from rise time. The bus is an RC network formed by the pull-up and the total bus capacitance (trace capacitance plus every device's pin capacitance plus any connector/cable capacitance). Each mode specifies a maximum rise time — roughly 1000 ns for standard mode and 300 ns for fast mode — and the rise time of an RC node is about 0.847·R·C for the 30–70% window the spec uses. So `R_max ≈ t_r / (0.847 · C_bus)`. If total capacitance is, say, a few hundred picofarads, that already pushes you toward the low-kilohm range at 400 kHz.

The lower bound comes from sink current: when a device pulls the line low, it must be able to sink the current through the pull-up while keeping VOL below the specified threshold (typically 0.4 V). That gives `R_min ≈ (VDD − VOL_max) / I_OL_max`. There's also a practical lower bound from not exceeding the device's rated sink current and not wasting static current — which matters in a battery-powered medical device, where a small pull-up burns continuous current whenever the bus is idle-low.

So the procedure is: sum the capacitance honestly (including cable, which people forget), compute R_max from the rise-time spec at 400 kHz, compute R_min from the sink-current spec, and pick a standard value comfortably inside that window — not at either edge, because capacitance and device characteristics vary over temperature and part tolerances. If the window closes (capacitance too high for any legal pull-up at 400 kHz), that's the signal that the bus is overloaded and needs an active pull-up, a bus buffer/expander, or a lower bus speed — not a resistor you can just shrink.

**Possible follow-ups:** What happens if you exceed the maximum bus capacitance — how does the failure actually manifest, and why can't you just lower the pull-up further? How would you account for the fact that different devices on the bus may have different input capacitance and different sink-current ratings?

## Q3: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?
**Answer:** The goal is to put a stable, transport-agnostic interface between the application and the physical buses, so the application expresses *what* it wants (read this sensor register, send this command, subscribe to this data stream) and never *how* it's carried.

I'd structure it in layers. At the bottom, a thin transport driver per physical bus that implements a common set of primitives — open/close, a transactional read, a transactional write, and an event/callback hook for asynchronous data. Above that, a device abstraction: each sensor type gets a driver that speaks the sensor's actual command set but issues those commands only through the transport primitives. The application talks to the device abstraction, never to the transport directly. The key discipline is that the transport interface must be defined in terms of *semantics that all four buses can honor* — for example, a "transaction" that is atomic from the caller's perspective, with the transport layer responsible for mapping that onto an I2C repeated-start, an SPI chip-select-framed transfer, a UART request/response with timeout, or a CAN-FD request/response message.

The hard parts are the places where the buses genuinely differ, and I'd handle those explicitly rather than pretending they don't exist. Latency and determinism differ wildly — a CAN-FD message may be delayed by arbitration, an I2C transfer by clock stretching — so the interface should expose completion as either synchronous-with-timeout or asynchronous-with-callback, and let the application choose. Error semantics differ: I2C has NACKs, SPI has no acknowledgement at all, UART has framing/parity errors, CAN-FD has error frames and bus-off. I'd normalize these into a common error taxonomy (timeout, transport-error, device-rejected, bus-fault) so the application can react sensibly without bus-specific knowledge. And I'd keep configuration (addresses, chip selects, baud rates, CAN IDs) in a board-support/configuration layer, not scattered through application code.

For testability, the abstraction is also what lets you swap in a mock transport and unit-test the device drivers and application logic on a host without hardware — which is a large part of why the layering is worth the up-front cost.

**Possible follow-ups:** How would you handle a sensor that exists in two variants — one on I2C and one on SPI — without duplicating the device driver? Where would you put retry logic: in the transport layer, the device driver, or the application, and why?

## Q4: You're debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward. How would you approach this?
**Answer:** Bus-off means the node's transmit error counter exceeded the threshold, so the controller removed itself from the bus — that part is expected CAN behavior. The interesting question is *why* it accumulated errors, and why it doesn't recover on its own. I'd separate those two problems.

First, recovery: per the CAN specification, a bus-off node is allowed to recover automatically after 128 occurrences of 11 consecutive recessive bits (bus-off recovery), but many controllers require the firmware to explicitly clear the bus-off state or re-initialize the controller. If the node stays off until a reset, that strongly suggests the firmware isn't implementing the recovery sequence — either it never re-enables the controller after bus-off, or it's waiting for an external reset. So I'd check the driver's bus-off handling path first; that's often the direct cause of "stays off."

Second, the root cause of the errors. A node that goes bus-off while the bus "looks healthy" afterward usually accumulated errors during a transient — a burst of bit errors, a period where its own transmissions were corrupted, or a mismatch in bit timing. I'd look at: bit-timing configuration (sample point and SJW) versus the rest of the network, especially across the arbitration-to-data-phase bit-rate switch in CAN-FD, where a poorly chosen data-phase sample point can cause errors only at certain cable lengths or node counts; termination and stub issues that corrupt only during certain traffic patterns; and whether the node is transmitting into a bus that momentarily has no other active node (e.g., it's the only transmitter and gets no acknowledgement, which increments its error counter). I'd also check whether the node's error counters are being logged — the TEC/REC values over time tell you whether it's a slow accumulation (marginal signal integrity) or a sudden burst (a specific event).

So my approach is: fix the recovery path so the node rejoins the bus automatically and safely, *and* instrument the error counters and capture the bus around the bus-off event to find the transient that triggered it. Fixing only the recovery would mask a real signal-integrity or timing problem.

**Possible follow-ups:** How would you make bus-off recovery safe in a medical device — what should the node do with its outputs while it's off the bus? How would you distinguish a bit-timing/sample-point problem from a physical-layer signal-integrity problem using only the error counters and a scope?

## Q5: How would you approach handling a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?
**Answer:** My first priority is containment and honesty: understand exactly what's wrong, how it affects the compliance result, and what the realistic path back is — then communicate that clearly to the people who own the schedule, rather than letting the team absorb the delay silently. Regulatory testing is expensive and re-testing has a lead time, so the earlier the impact is understood and escalated, the more options everyone has.

Technically, I'd get the failure characterized precisely before assigning blame or jumping to a fix. "The protocol is implemented incorrectly" is too vague to act on — I'd want the specific nonconformance, the test that exposed it, and whether it's a functional bug, a spec-interpretation gap, or a test-setup artifact. Sometimes what looks like a firmware protocol bug is actually a mismatch between the implementation and the standard's requirement, which is a requirements/traceability problem as much as a coding one. Getting that distinction right determines whether the fix is a code change, a requirements clarification, or a test-procedure correction.

On the people side, I'd be deliberate about how I handle the junior engineer. The instinct to protect them matters — a compliance failure is a system failure, and if the process allowed an incorrect protocol implementation to reach formal testing, that's a review and verification gap, not solely an individual's fault. I'd involve them in the root-cause analysis and the fix, because that's how they learn and because they know the implementation best. I'd also ask the harder process question: why didn't design review, unit tests, or protocol conformance testing catch this before formal compliance testing? That's where the durable fix lives — adding the missing verification step so the next protocol change doesn't repeat the pattern.

Then I'd drive a recovery plan: fix, re-verify against the specific requirement, re-run the affected compliance tests, and document the whole thing for the regulatory file, since a discovered-and-corrected nonconformance needs a clean paper trail. I'd also look for whether the same class of error exists in other interfaces before re-testing, so we don't discover a second instance after the first re-test.

**Possible follow-ups:** How would you decide whether to fix-and-retest versus request a deviation, and who needs to be involved in that call? What would you change in the verification process so a protocol error is caught before formal compliance testing next time?
