## Q1: How would you approach debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward?

**Answer:** Bus-off is the CAN controller's terminal error state — the transmit error counter (TEC) has exceeded 255, so the controller has removed itself from the bus. The fact that it stays off until reset tells me the recovery policy is the first thing to examine, but I'd resist stopping there, because the interesting question is *why* the TEC climbed in the first place.

I'd start by separating the two problems: the trigger and the recovery. For the trigger, I'd pull the controller's error counters and error state transitions out over a long capture — most CAN-FD controllers expose TEC/REC and a protocol status register, and many support an error-interrupt or bus-off interrupt that logs the transition. If the node goes bus-off repeatedly at the same point in a transaction, that points to a systematic issue: a bit-timing mismatch between nodes (sample point or SJW differences that only bite at the data-phase bit rate), a node transmitting into a dominant bit it didn't expect, or a wiring/termination problem that produces bit errors under specific traffic patterns. If it's random, I'd look at physical-layer integrity — stub lengths, termination, common-mode — and at whether the node is being asked to transmit while the bus is marginal.

A key CAN-FD-specific angle: the data phase runs at a much higher bit rate than arbitration, so a bus that looks electrically fine at the arbitration rate can still produce bit errors in the data phase. I'd check the transceiver's rated data rate, the loop delay and symmetry, and whether the sample point in the data phase is set correctly for the actual bus length. I'd also verify that all nodes agree on the bit-rate switching (BRS) configuration — a node that doesn't support or isn't configured for the higher data rate will generate errors when it sees a frame it can't decode.

For the recovery side: many controllers require an explicit recovery sequence (or a reset) after bus-off, and the application firmware may simply not be implementing it. I'd check whether the driver enables automatic bus-off recovery, and if not, whether the application has a supervised recovery path — typically a controlled re-initialization after a delay, with the node re-entering the network cleanly rather than resuming mid-stream. In a medical device I'd want that recovery to be observable and logged, and I'd want the node to signal that it lost sync so downstream consumers don't act on stale data.

**Possible follow-ups:** How would you distinguish a bit-timing/sample-point problem from a physical-layer problem using only the error counters and a scope? What would your bus-off recovery policy look like in a safety-critical node — automatic, supervised, or requiring a higher-level decision?

## Q2: How would you approach selecting between RS-422 and RS-485 for a medical device that needs to connect a central controller to several distributed sensor modules?

**Answer:** The core electrical difference is that RS-422 is a point-to-point or one-driver-to-many-receivers arrangement — a single driver, up to a handful of receivers, full-duplex over four wires — while RS-485 is a true multi-point bus: multiple drivers and receivers sharing a two-wire (or four-wire) medium, with the drivers tri-stated except when transmitting. So the selection usually comes down to the topology the system actually needs.

If the architecture is genuinely one central controller broadcasting to sensor modules that only ever listen and respond on a separate path, RS-422 can be simpler and avoids the bus-contention and turnaround-timing problems entirely. But the moment more than one node needs to *talk* on the same pair — which is almost always the case for a sensor network where the controller polls modules and they reply — RS-485 is the right fit, because it's designed for exactly that shared-medium, half-duplex (or full-duplex four-wire) operation.

Beyond topology, I'd weigh: how many nodes and over what distance (both standards handle long runs, but RS-485 is the one specified for multi-drop), whether I need half- or full-duplex, common-mode voltage range and grounding practice, and the fail-safe biasing and termination requirements that come with a multi-driver bus. For a medical device I'd also factor in the regulatory and validation burden — a shared bus with arbitration-by-protocol (polling) is well understood and testable, but it introduces failure modes (a node stuck driving the bus) that need to be designed against. RS-422's single-driver simplicity removes some of those failure modes at the cost of flexibility.

I'd also consider the protocol layer on top: RS-485 gives you a physical bus but no addressing or arbitration, so the firmware must implement polling, timeouts, and error recovery. That's a real design cost that should be weighed against the wiring savings of a shared bus.

**Possible follow-ups:** If you chose RS-485, how would you protect the bus against a node that fails while holding the driver enabled? What would push you toward a four-wire full-duplex RS-485 arrangement instead of two-wire half-duplex?

## Q3: How would you approach designing fail-safe biasing for an RS-485 bus, and why does it matter more in a medical device than in a general industrial network?

**Answer:** Fail-safe biasing exists to guarantee that when no driver is actively driving the bus — every driver tri-stated, which is the normal idle condition on a half-duplex multi-drop bus — the differential voltage across A and B settles to a defined logic state (a known idle/mark) rather than floating into the indeterminate region near zero volts. Without it, receivers can output random or oscillating states during idle, and the first bits of a transmission can be misread as the bus transitions from floating to driven.

The mechanism is a resistor divider: a pull-up on one line and a pull-down on the other, sized so that the bias network, in combination with the termination resistors and the parallel combination of all receiver input impedances, produces a differential voltage comfortably above the receiver's threshold — while still presenting an acceptable load to the active driver. The calculation has to account for the *worst case*: the bias resistors in parallel with both terminations and every receiver on the bus, because each additional unit load pulls the idle differential down. That's why bias values that work on a two-node bench setup can fail on a fully populated bus. The bias is usually placed at one point (often co-located with the termination at the master end) and only at one point, so the bias networks don't fight each other.

Why it matters more in a medical device: an indeterminate bus state during idle is a *silent* failure mode — it doesn't announce itself, it just means a receiver may see spurious start bits or garbage framing at the moment a real message begins. In a patient-monitoring context, a corrupted or falsely-triggered message at the boundary between idle and active traffic is exactly the kind of intermittent fault that's hard to reproduce and expensive to diagnose later. Fail-safe biasing turns an undefined electrical condition into a defined one, which is both a reliability improvement and something you can point to in a design review as a deliberate, analyzed choice rather than an accident of resistor values.

I'd also connect it to the broader fail-safe story: biasing handles the *idle* case, but you still need protocol-level timeouts and integrity checks for the case where a node dies mid-transmission. Biasing is necessary but not sufficient.

**Possible follow-ups:** Walk me through how you'd calculate the bias resistor values for a bus with two terminations and N unit-load receivers. What happens to the idle differential if someone adds a second bias network at the far end of the bus?

## Q4: In a system where an SPI master talks to several slaves at different clock speeds and with different CPOL/CPHA modes, how would you approach structuring the firmware so that mode and speed changes are handled safely?

**Answer:** The central risk is that SPI has no protocol-level framing or acknowledgement — the master owns the clock, and the mode (CPOL/CPHA) and speed are properties of the *transaction*, not the bus. If the firmware changes mode or speed while a transaction is in flight, or changes it without the slave being in a state to accept the new timing, you get corrupted data with no error indication. So the firmware structure has to make "configure, then transfer, then restore" an atomic, enforced sequence rather than something each caller remembers to do.

I'd structure it around a per-device descriptor that captures everything that varies: clock speed, CPOL/CPHA, word size, chip-select polarity and setup/hold timing, and any inter-byte delay the slave requires. The low-level transfer function takes that descriptor, applies the bus configuration, asserts the correct chip select, runs the transfer, deasserts, and — critically — leaves the bus in a known safe state afterward. Callers never touch the SPI configuration registers directly; they hand a buffer and a device handle to the transport layer. That keeps the mode/speed knowledge in one place and makes it reviewable.

The sequencing details matter. Before changing mode or speed, I'd ensure the bus is idle: chip select deasserted, no transfer pending, and the peripheral's FIFOs drained. Some controllers require disabling the SPI peripheral before reconfiguring clock polarity/phase; others allow live changes but only between frames. I'd consult the reference manual rather than assume, and I'd add an assertion or state check that catches a reconfiguration attempt while a transfer is active. For slaves that need a settling time after a mode change or after chip-select assertion, I'd encode that as a delay in the descriptor rather than sprinkling it through call sites.

I'd also think about the shared-bus contention angle: if multiple tasks can initiate transfers, the transport layer needs a mutex or a single-owner model so two devices' transactions can't interleave. And I'd make the whole thing testable — a loopback or known-pattern test per device that exercises each mode/speed combination, so a regression in the descriptor table shows up immediately rather than as an intermittent field failure.

**Possible follow-ups:** What would you do if one slave requires a mode change mid-transaction that the SPI peripheral can't perform without a full disable/enable cycle? How would you verify the actual clock polarity and phase on a scope against what the descriptor claims?

## Q5: How would you approach handling a situation where a junior engineer on your team has implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** My first priority is to separate the technical recovery from the people situation, because they need different handling and conflating them makes both worse.

On the technical side: the immediate question is scope and risk. I'd want to understand exactly what's wrong — is it a protocol-conformance defect, a robustness gap, or something that only manifests under the test conditions — and whether it affects only the tested interface or other interfaces built on the same code. I'd get the failure characterized precisely before deciding on a fix, because "the protocol is implemented incorrectly" can mean anything from a byte-order bug to a fundamental state-machine flaw, and the remediation path is completely different. Then I'd work with the compliance/test team on what re-testing is required and whether there's a defensible path to a partial re-test versus a full one, and I'd communicate the revised schedule early rather than letting it be discovered.

On the people side: the instinct to assign blame is understandable but counterproductive. A defect that survives to regulatory testing usually means the *process* had a gap — the protocol wasn't verified against a conformance test or a reference implementation before formal testing, or the review didn't catch it. I'd frame it that way with the engineer: this is a process failure we own together, not a personal failing. I'd want them involved in the fix, because they understand the implementation best and because being part of the recovery is how people learn from it rather than becoming defensive. I'd be direct that the defect is serious and the schedule impact is real, but I'd keep the conversation on the work.

Then I'd close the loop on prevention: add a protocol conformance test or a golden-reference comparison to the pre-compliance gate, so the next implementation is checked against the spec before it reaches formal testing. The lesson isn't "the junior engineer was careless" — it's "we didn't have a verification step that would have caught this class of error, and now we do."

**Possible follow-ups:** How would you decide whether to fix forward in the current design or revert to a known-good protocol implementation, given the schedule pressure? What would you say to the engineer in a one-on-one to make sure they come out of this more capable rather than demoralized?
