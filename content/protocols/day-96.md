## Q1: How would you approach debugging an I2C bus where a device intermittently NACKs its address, but only when the bus is running at 400 kHz and only after the board has warmed up for a while?

**Answer:** I'd treat this as a timing-margin problem that temperature is eroding, and work from the physical layer upward. First, I'd capture the actual bus waveforms at the failing condition — not at room temperature on a bench — and measure rise and fall times against the I2C spec limits for fast-mode. A common culprit is that the pull-up resistors were sized for 100 kHz and are marginal at 400 kHz; as temperature rises, leakage and driver characteristics shift, and the effective rise time creeps past the point where the device can reliably sample SDA/SCL during the address phase. I'd also check bus capacitance: if the calculated capacitance is close to the 400 pF fast-mode limit, any added stray capacitance from a probe or a long trace pushes it over. Beyond passives, I'd look at whether the master's clock is actually meeting the 400 kHz timing with the specified low/high periods, and whether there's any clock stretching happening that the master isn't honoring. I'd also verify the device's own timing requirements — some parts specify a minimum bus-free time or setup/hold that's tighter than the generic spec. The systematic approach is: reproduce at temperature, measure the eye at the address phase, compare against both the generic I2C limits and the specific device datasheet, then adjust pull-ups, reduce capacitance, or drop to a lower speed with margin. I would not accept "it works at room temperature" as evidence the design is sound.

**Possible follow-ups:** How would you decide whether to lower the bus speed versus re-specify the pull-ups, given that both affect power consumption in a battery-powered device? What role does the device's input hysteresis play in marginal NACK behavior?

## Q2: How would you approach structuring firmware so that an SPI master can talk to several slaves that require different clock speeds and different CPOL/CPHA modes, without mode changes corrupting transactions?

**Answer:** The core risk is that CPOL/CPHA and clock speed are properties of the bus configuration, not the individual transfer, so any change must happen while the bus is idle and must be atomic with respect to other users of the bus. I'd structure this as a bus-manager layer that owns the SPI peripheral and serializes all access. Each slave gets a descriptor containing its required mode, max clock, word size, and chip-select line. Before a transaction, the manager checks whether the current bus configuration matches the target slave's; if not, it reconfigures the peripheral only when no transaction is in flight, and it does so with the chip selects all deasserted. The critical discipline is that reconfiguration and the subsequent transfer happen as one locked operation, so a higher-priority task can't slip in and change the mode mid-sequence. On the hardware side, I'd make sure each slave's chip select is genuinely deasserted during reconfiguration — some peripherals glitch the clock line when you rewrite the control register, and a slave that's still selected will see that as a clock edge. I'd also keep the per-slave descriptors in one place so the mode/speed requirements are auditable rather than scattered through call sites, and I'd add a test that deliberately interleaves transactions to slaves with conflicting modes to prove the manager never leaves the bus in the wrong state.

**Possible follow-ups:** How would you handle a slave that requires a mode change but whose chip select shares a line with another device? What would you do if the SPI peripheral can't change mode without a full disable/enable cycle that costs several microseconds?

## Q3: You're debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself looks healthy afterward. How would you approach this?

**Answer:** Bus-off means the transmit error counter crossed its limit, so the question is what's driving that node's error count up — and the fact that the bus looks healthy afterward tells me the fault is intermittent and probably tied to that node's own view of the bus. I'd start by reading the node's error counters and the controller's error state history before the reset wipes them, and I'd enable logging of the last error type (bit error, stuff error, CRC error, ACK error, form error) so I know whether it's a transmit-side or receive-side problem. An ACK error pattern points at the node transmitting when no other node is listening or when its bit timing is off relative to the rest of the network. A bit-error pattern often means the node is sampling at the wrong point — a sample-point or oscillator-tolerance mismatch between nodes, which is exactly the kind of thing that shows up intermittently under temperature or voltage drift. I'd also check whether the node is the only one awake at certain times, whether its transceiver is entering a low-power or listen-only state, and whether there's a wiring or termination issue specific to that node's stub. The recovery behavior matters too: a controller that stays bus-off until reset may simply not have automatic bus-off recovery enabled, which is a firmware configuration issue rather than a bus fault. So I'd separate "why did it go bus-off" from "why didn't it recover," and fix both.

**Possible follow-ups:** How would you distinguish an oscillator-tolerance problem from a termination/stub problem using only the error counters and a scope? What's your view on enabling automatic bus-off recovery in a safety-critical medical network?

## Q4: How would you approach choosing between a star topology and a daisy-chain topology for a multi-drop sensor network in a medical device where the sensors are physically distributed?

**Answer:** I'd frame it as a trade between signal integrity, wiring practicality, and fault containment, and let the physical constraints drive the decision rather than picking a favorite. A daisy-chain (or bus-with-short-stubs) is the natural fit for a differential bus like RS-485 or CAN-FD: it keeps stub lengths short, which matters because long stubs cause reflections that corrupt high-speed edges, and it uses less cable. But it has a real drawback in a medical device — a single break or a failed node in the middle can take down everything downstream, and troubleshooting a fault in a chain is harder because you have to localize it. A star topology centralizes the wiring at a hub, which makes fault isolation and node replacement easier and contains a single node failure, but it multiplies cable runs, adds capacitance and length to each leg, and if the hub is a passive star the impedance discontinuities can hurt signal quality unless it's an active hub. For a medical device I'd also weigh serviceability and sterility — how easy is it to swap a sensor in the field — and whether the topology needs to survive a single point of failure. My approach would be to prototype the worst-case leg length and node count for each candidate, measure the eye at the far end, and then decide; if the daisy-chain meets margin with short stubs, it's usually the better signal-integrity choice, and I'd add fault-detection at each node to compensate for the containment weakness.

**Possible follow-ups:** How would an active star hub change your analysis, and what failure modes does it introduce? How would you detect a broken cable in a daisy-chain before it causes a patient-visible fault?

## Q5: How would you handle a situation where a junior engineer on your team implemented a communication protocol incorrectly, and the error is only discovered during regulatory compliance testing, causing a significant schedule delay?

**Answer:** My first priority is to contain the problem and protect the patient-facing function, then deal with the process failure honestly. I'd get the team together to characterize exactly what's wrong — is it a protocol conformance issue, a robustness gap under fault conditions, or a documentation/traceability mismatch — because the remediation path and the regulatory impact differ for each. I'd bring in the regulatory lead early rather than trying to quietly patch it, since a change discovered during compliance testing usually means the design history file and the test evidence need to be revisited, and hiding that is both unethical and a much bigger problem later. On the schedule side, I'd re-plan transparently: identify what testing can proceed in parallel, what needs to be re-run, and what the realistic new date is, and communicate that upward with the reasoning rather than just a slip. With the junior engineer, I'd focus on the systemic cause — was the protocol spec ambiguous, was there no conformance test before formal testing, was the review too shallow — because blaming the individual doesn't prevent recurrence. The constructive outcome is usually a pre-compliance protocol test harness and a clearer interface control document, so the same class of error gets caught at bench level next time. I'd also make sure the engineer isn't scapegoated; the failure is a process failure, and the team owns it.

**Possible follow-ups:** How would you decide whether the fix requires a formal design change and re-verification versus a documentation correction? What would you change in the review process to catch protocol errors before formal testing?
