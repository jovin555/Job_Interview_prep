## Q1: How would you approach designing a USB 2.0 device that must support both bus-powered operation and battery-powered operation, where the device needs to maintain functionality when the host is in suspend mode?
**Answer:** The first step is to clearly define the power states and what functionality must remain active in each. In bus-powered mode, the device is limited to 100 mA before enumeration and 500 mA after configuration, so I'd need to budget the power budget carefully—particularly for any sensors or wireless radios that might draw significant current. For suspend mode, USB 2.0 requires the device to draw no more than 2.5 mA from VBUS unless it has been configured for remote wakeup. If the device has its own battery, I'd design a power architecture with a load switch or power multiplexer that can seamlessly transition between VBUS and battery power. The firmware would need to handle the suspend/resume interrupt sequence properly: detecting the suspend condition (no bus activity for 3 ms), entering a low-power state, and optionally enabling remote wakeup if the host has granted that capability. I'd also consider how the battery charging circuit interacts with the USB data lines—during charging, the D+/D− lines might need to be isolated to prevent enumeration issues. A key design decision is whether the device should enumerate as a bus-powered device (declaring its current draw in the configuration descriptor) or as a self-powered device with a battery, since this affects how the host manages power and whether it will allow remote wakeup.

**Possible follow-ups:** How would you handle the transition when the host disconnects while the device is running on battery? What considerations would you give to inrush current during hot-plug enumeration?

## Q2: In a CAN-FD network for a medical device, you need to transmit a 64-byte safety-critical payload with a 16-bit CRC at the application layer. How would you approach implementing end-to-end protection beyond the CAN-FD controller's built-in CRC?
**Answer:** CAN-FD provides a CRC that covers the entire frame, but it doesn't protect against certain failure modes like a node incorrectly accepting a message due to a bit error that happens to produce a valid CRC, or a message being delivered to the wrong node due to an addressing error. For safety-critical medical data, I'd implement end-to-end protection at the application layer. This would include a message counter or sequence number to detect missing or duplicated messages, a source and destination identifier to catch routing errors, and a separate CRC or checksum computed over the payload and metadata. The choice of CRC polynomial depends on the required Hamming distance and the maximum message length—for 64 bytes, a CRC-16 with a good polynomial can detect all single and double bit errors, and most burst errors. I'd also consider using a message timeout mechanism: if a safety-critical message isn't received within a defined window, the receiving node should enter a safe state. The key principle is defense in depth—the CAN-FD controller's CRC catches transmission errors, but the application layer must catch logical errors like stale data, wrong source, or misordered messages. I'd also think about whether the 16-bit CRC should be computed over the payload only or over the payload plus a header containing the sequence number and identifiers, since including the header protects against errors in the metadata as well.

**Possible follow-ups:** How would you handle the trade-off between CRC length and bandwidth overhead for a high-rate telemetry stream? What would you do if the application-layer CRC detects an error—retransmit or enter a safe state?

## Q3: You're debugging an RS-485 network where the system works correctly at 9600 baud but fails at 115200 baud. The cable run is approximately 150 meters with 12 nodes. How would you approach this?
**Answer:** The first thing I'd check is whether the bit rate is actually achievable over that cable length. At 115200 baud, the bit time is about 8.7 microseconds, and the round-trip propagation delay over 150 meters of cable (approximately 5 ns per meter, so about 750 ns one-way, 1.5 µs round-trip) is a significant fraction of the bit time. This can cause reflections and signal integrity issues, especially if the termination isn't matched to the cable impedance. I'd start by verifying the termination resistors—for a 120-ohm characteristic impedance cable, I'd expect 120-ohm termination at both ends. I'd also check for unterminated stubs: at 115200 baud, the maximum stub length is roughly 1/10 of the wavelength, which is about 26 meters for a 5 ns/m cable, but in practice, stubs should be kept much shorter—ideally under 0.3 meters. Next, I'd look at the transceiver's slew rate limiting. Many RS-485 transceivers have a slew-rate-limited mode for low data rates (like 9600 baud) and a high-speed mode for rates above 1 Mbps. If the transceiver is in the wrong mode, the edges will be too slow at 115200 baud, causing intersymbol interference. I'd also check the fail-safe biasing: at higher bit rates, the bias resistors might need to be adjusted to ensure the bus is properly biased during idle periods. Finally, I'd use an oscilloscope to look at the actual waveform at the farthest node—checking for ringing, overshoot, and whether the signal crosses the receiver's threshold at the right time. If the waveform looks clean but errors persist, I'd suspect a firmware issue like incorrect bit timing or a driver that isn't releasing the bus fast enough after transmission.

**Possible follow-ups:** How would you decide between lowering the baud rate versus improving the physical layer (better cable, termination, or transceivers)? What role does the common-mode voltage range play in this scenario?

## Q4: How would you approach implementing a protocol abstraction layer for a medical device that needs to support multiple physical interfaces (I2C, SPI, UART, CAN-FD) for different sensor modules, while keeping the application code independent of the specific transport?
**Answer:** I'd design a transport abstraction layer with a consistent API that hides the physical interface details from the application. The core idea is to define a common set of operations—init, read, write, transaction, and control—that each transport driver implements. For example, an I2C driver would handle addressing, repeated starts, and clock stretching internally, while an SPI driver would manage chip selects and clock polarity/phase. The application would interact with a logical device handle rather than a physical bus. I'd structure this with three layers: the application layer that uses logical device IDs, a transport abstraction layer that maps logical devices to physical buses and handles protocol-specific details, and the hardware driver layer that directly manipulates the peripherals. For a medical device, I'd also include error handling and retry logic at the abstraction layer, since different transports have different failure modes—I2C can hang on clock stretching, SPI can have MISO contention, UART can have framing errors, and CAN-FD can have bus-off conditions. The abstraction layer should normalize these into a common error model. I'd also consider whether the abstraction should support transactions that span multiple operations, like an I2C write-then-read sequence, since some sensors require this for register access. For testing, this abstraction makes it easy to mock the transport layer and run unit tests on the application logic without real hardware. One important design decision is whether to use a synchronous or asynchronous API—for a medical device with real-time requirements, I'd lean toward a synchronous API with timeouts, or an asynchronous API with completion callbacks, depending on whether the RTOS supports event-driven programming.

**Possible follow-ups:** How would you handle a sensor that requires a specific timing sequence across multiple bus transactions? How would you ensure that the abstraction layer doesn't introduce unacceptable latency for time-critical data?

## Q5: Imagine you're leading a design review where a junior engineer proposes using a single I2C bus at 400 kHz to connect five sensors, a real-time clock, and an EEPROM, all on a 30-centimeter PCB with long traces. The engineer argues that the bus capacitance is within the 400 pF limit. How would you guide the team to evaluate this approach?
**Answer:** I'd start by acknowledging that the engineer has done some homework—knowing the 400 pF limit for fast-mode I2C is a good baseline. But I'd guide the team to look beyond just the total capacitance number. First, I'd ask about the actual trace lengths and whether the 30-centimeter figure is the total bus length or the longest branch. I2C is a shared bus, so the total capacitance includes all traces, stubs, and device pin capacitance. At 400 kHz, the rise time requirement is 300 ns maximum, and the pull-up resistors need to be sized to achieve that rise time with the total bus capacitance. If the capacitance is near the limit, the pull-up resistors might need to be very small, which increases current draw and can cause issues with devices that have weak output drivers. I'd also ask about the physical layout: are the sensors distributed along the bus, or are there long stubs to each sensor? Long stubs create reflections and can cause signal integrity issues even if the total capacitance is within spec. I'd also raise the question of whether all devices on the bus support 400 kHz—some sensors might only support standard-mode 100 kHz, which would force the entire bus to run slower. Another consideration is clock stretching: if any device stretches the clock, it can affect the timing of other devices on the bus. For a medical device, I'd also ask about fault tolerance: if one sensor fails and holds SDA low, the entire bus is blocked. I'd suggest the team consider whether a multi-bus architecture would be more robust—for example, grouping sensors by speed requirement or criticality on separate buses. Finally, I'd recommend the engineer calculate the actual pull-up resistor values for the worst-case capacitance and verify the rise time with a scope during prototyping, rather than relying solely on the datasheet limit.

**Possible follow-ups:** How would you decide between using one bus with a bus buffer or splitter versus multiple I2C peripherals? What failure modes would you specifically test for during validation?
