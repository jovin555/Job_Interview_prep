# protocols — Day 93

## Q1: How would you approach debugging a USB 2.0 device that fails to enumerate on some hosts but works on others, where the failure appears to be a control-transfer timeout during descriptor reads?

**Answer:** Enumeration failures that are host-dependent almost always point to timing or descriptor-content issues rather than a dead link, so I'd first separate "the device never responds" from "the device responds but the host gives up." The fastest way to do that is a bus analyzer or a software sniffer on the failing host: if I can see the SETUP packet go out and no response come back, the problem is on the device side (interrupt latency, endpoint stall, firmware not armed in time). If I see the device respond but the host retries and eventually times out, the problem is more likely descriptor content or a response that's too slow.

On the descriptor side, I'd check the basics that trip up marginal hosts: `bMaxPacketSize0` must match what the device actually implements for endpoint 0 (a mismatch is a classic cause of control-transfer timeouts on stricter host controllers); the configuration/interface/endpoint descriptors must be internally consistent (total length field, number of interfaces, endpoint addresses, `wMaxPacketSize` encoding including the high-bandwidth bits); and string descriptors must be well-formed with correct length prefixes, since some hosts choke on a malformed string index. I'd also verify the device handles the standard requests in the right order and returns STALL correctly for unsupported requests rather than hanging.

If descriptors look clean, I'd look at timing: how long after VBUS/reset the device is ready to answer the first GET_DESCRIPTOR, whether the pull-up on D+ is released at the right moment, and whether the firmware's interrupt latency under load could cause it to miss the setup stage. A useful experiment is to slow the host down (or insert a hub) — if the device then enumerates reliably, it's a timing margin problem, not a protocol error. I'd also test across several host controllers and OSes to characterize the failure pattern rather than chasing a single host.

**Possible follow-ups:** How would you tell the difference between a device-side timing problem and a host-driver quirk without a hardware analyzer? What would you change in the descriptor set to make a composite device more forgiving across hosts?

## Q2: How would you approach selecting a communication protocol for a medical sensor network where some nodes need deterministic low-latency response and others generate bursty high-volume data, all sharing one physical medium?

**Answer:** I'd start by writing down the requirements as numbers before touching a protocol: worst-case latency for the control-critical nodes, sustained and burst throughput for the telemetry nodes, maximum cable length and node count, whether nodes need power over the bus, and the fault-tolerance/regulatory expectations. Those numbers usually eliminate most options quickly.

The core tension is that determinism and high-volume burst traffic don't coexist gracefully on a shared medium unless the protocol has a priority mechanism. CAN-FD is attractive here because arbitration is priority-based and non-destructive — a high-priority control frame wins the bus by ID, and the data-phase bit rate gives you reasonable payload efficiency for the bursty nodes. The trade-off is that CAN-FD's arbitration phase bit rate is bounded by bus length, so long cable runs force you to slow the arbitration rate, which eats into your latency budget. RS-485 with a master-scheduled protocol (polling or a time-slotted scheme) gives you full control over determinism because the master owns the schedule, but you're then responsible for building the priority and error-handling semantics yourself, and a single master is a single point of failure unless you design for it. I2C and SPI are really chip-to-chip buses — fine inside an enclosure, not for distributed nodes over cable.

So my approach is: if the control-critical latency requirement is tight and the bus is short-to-moderate, CAN-FD with careful ID assignment (control messages get the lowest numerical IDs) is a strong default. If the run is long or the topology is awkward, RS-485 with a master-scheduled, priority-aware protocol is more controllable. Either way I'd reserve bandwidth explicitly for the control traffic — either through ID priority or through a dedicated time slot — rather than hoping the scheduler naturally favors it, and I'd validate the worst-case latency analytically and then on a loaded bus, not just on an idle bench.

**Possible follow-ups:** How would you assign CAN IDs so that control traffic is never blocked behind telemetry? What would make you reject a shared-medium approach entirely in favor of separate physical links?

## Q3: You're debugging an RS-485 half-duplex link where occasional corrupted bytes appear only at higher baud rates and longer cable runs. How would you approach isolating whether the cause is termination, stub length, or turnaround timing?

**Answer:** I'd treat the three suspects as separable experiments rather than guessing. First, termination and stub length are physical-layer issues that show up as reflections and ringing, so a scope probe at the far end of the bus during a transition tells you a lot: excessive overshoot, ringing that crosses the receiver threshold multiple times, or a slow settling tail all point to impedance mismatch. I'd verify the termination is correct for the characteristic impedance of the cable (typically a single 120 Ω at each physical end, not at every node), that the ends are actually the ends, and that stubs off the main line are short relative to the bit period — long stubs are a classic cause of rate-dependent corruption because they act as resonant branches.

Turnaround timing is a different failure mode: if the driver is disabled before the last bit has cleared the line, or the receiver is enabled too late, you clip or miss bits at the boundaries. That tends to corrupt the first or last byte of a frame rather than random bytes in the middle, so the position of the corruption is a strong clue. I'd measure the driver-enable-to-first-bit and last-bit-to-driver-disable timing against the transceiver's propagation delays and the firmware's GPIO latency, and check whether the firmware is accounting for the transceiver's enable/disable times, not just the UART's.

A practical way to separate them: drop the baud rate. If corruption disappears at low speed but the topology is unchanged, it's almost certainly a physical-layer margin issue (termination/stubs/cable) because turnaround timing scales with the bit period too but usually has more slack at low rates. Then I'd fix termination and stubs first, re-test, and only then tighten turnaround timing. I'd also check common-mode range and grounding, since a ground-potential difference between distant nodes can corrupt data in a way that looks rate-dependent.

**Possible follow-ups:** How would you measure stub length limits for a given baud rate? What role does fail-safe biasing play when the bus is idle between transactions?

## Q4: How would you approach structuring firmware so that an SPI master can talk to several slaves that require different clock speeds and different CPOL/CPHA modes, without mode changes corrupting transactions?

**Answer:** The key insight is that CPOL/CPHA and clock speed are properties of the *transaction*, not of the bus, so the firmware needs a per-slave configuration descriptor that the low-level driver applies atomically before any transfer to that slave. I'd define a small structure per slave — chip-select pin, clock frequency, CPOL, CPHA, word size, and any inter-byte delay the slave needs — and have a single `spi_transfer(slave, ...)` entry point that reconfigures the peripheral from that descriptor, asserts the correct chip select, runs the transfer, and de-asserts. Application code never touches the SPI registers directly; it just names the slave.

The subtle part is the reconfiguration sequence. On most MCUs you must disable the SPI peripheral (or at least ensure it's idle) before changing CPOL/CPHA and the clock divider, because changing mode bits mid-frame produces glitches on SCLK that a slave can interpret as clock edges. So the driver should: wait for the peripheral to be idle, disable it, program the new mode and divider, re-enable it, then assert chip select. I'd also make sure only one chip select is ever asserted at a time, and that the driver enforces that — a shared-bus bug where two slaves are selected simultaneously is a classic source of MISO contention.

For mixed speeds on the same bus, I'd keep the bus at the slowest common speed only if the fast slaves genuinely don't need the speed; otherwise per-transaction reconfiguration is the right model. I'd also add a small guard delay after mode changes if any slave is sensitive to SCLK settling, and I'd unit-test the driver against a logic analyzer capture to confirm the mode bits actually change between transactions to different slaves.

**Possible follow-ups:** What happens on the bus if you change CPOL while a slave is selected? How would you handle a slave that needs a different word size (e.g., 16-bit) than the others?

## Q5: Imagine you're leading a design review where a junior engineer proposes a single shared interrupt line for a UART, an SPI sensor, and a GPIO alarm input, arguing it saves pins and the firmware can just poll to find out which peripheral fired. How would you guide the team to evaluate this approach?

**Answer:** I'd frame it as a question of what the shared line costs you in the worst case, not whether it works in the common case. The proposal is fine when events are rare and latency-tolerant, but the alarm input is exactly the kind of signal where you can't afford to be wrong about latency — if the alarm and a UART byte arrive close together, the ISR has to figure out which fired, and if it guesses or polls in the wrong order, the alarm response is delayed by however long the UART handling takes. That's a safety-relevant trade-off, so I'd want the team to quantify it rather than hand-wave it.

I'd ask the junior engineer to walk through the ISR logic: on a shared-line interrupt, how does the handler determine the source? If it polls each peripheral's status register in sequence, what's the worst-case time to reach the alarm check, and is that within the alarm's response budget? If two peripherals assert simultaneously, does the handler service both before returning, or could one be missed if its status flag clears? Those questions usually surface whether the design is actually safe or just pin-efficient.

Then I'd lay out the alternatives: dedicate the alarm line (it's the one with the hard latency requirement), and share the UART and SPI if their timing is soft enough; or use a small interrupt controller / GPIO expander with per-source status if pin count is the real constraint. I'd steer the team toward dedicating interrupts to anything with a hard deadline and sharing only among latency-tolerant sources, and I'd want the decision documented with the latency analysis so it's defensible at design review and later at regulatory review. The goal isn't to overrule the junior engineer — it's to make the trade-off explicit and let the requirements decide.

**Possible follow-ups:** How would you structure the ISR if the shared line is kept, to guarantee the alarm is never missed? What documentation would you want in the design file to justify the choice?

**Note on scope:** These five rotate across USB enumeration, protocol-selection methodology, RS-485 physical-layer debugging, SPI mode/speed management, and a behavioral design-review scenario — deliberately avoiding the I2C capacitance/clock-stretching, CAN-FD error-state, and UART flow-control angles already heavily covered in the prior log.
