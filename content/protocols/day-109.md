## Q1: How would you approach debugging an I2C bus where communication works at 100 kHz but intermittently fails at 400 kHz, and the failures only appear when several slaves are active at once?

**Answer:** The first thing I'd do is separate the electrical problem from the protocol/timing problem, because "works slow, fails fast" almost always points to one of a small set of causes. At 400 kHz the bus has roughly a quarter of the timing margin it had at 100 kHz, so anything marginal — rise times, capacitance, pull-up strength, clock stretching behavior — that was invisible at 100 kHz becomes a failure.

I'd start by scoping the bus: look at SDA and SCL rise and fall times against the fast-mode spec, check whether the edges are RC-dominated (rounded) versus sharp, and measure the actual bus capacitance indirectly by comparing measured rise time to the pull-up value. If rise times are near the limit, the fix is usually reducing pull-up resistance (within the sink-current budget of every device) or shortening/reducing capacitance — not adding more slaves. I'd also check for ground offset between master and slaves, since a few hundred millivolts of ground difference eats into the noise margin that's already thinner at speed.

Then I'd look at the protocol side: which slaves are active when it fails, and does it correlate with a specific device? A slave that stretches the clock longer than the master's timeout will fail more often at 400 kHz simply because transactions are shorter and timeouts are tighter. I'd capture the failing transaction with a logic analyzer and look at exactly where it breaks — a NACK on address, a lost arbitration, a stuck SDA, a clock stretch that runs past the timeout. That tells me whether it's a physical-layer margin issue or a device-behavior issue.

Finally, I'd check whether the failures cluster when multiple slaves are addressed in quick succession — repeated STARTs, back-to-back transactions, and bus turnaround all stress the same margins. If it's reproducible only under concurrent activity, I'd suspect cumulative capacitance/rise-time effects or a slave that doesn't release the bus cleanly.

**Possible follow-ups:** How would you decide whether to lower the pull-up resistance versus reduce the bus speed? What would you do if the failing device is a fixed-function sensor you can't modify?

## Q2: How would you approach designing the electrical layer of an RS-485 link that must remain safe if one node's transceiver fails and holds the bus in a permanent dominant state?

**Answer:** A stuck-dominant transceiver is one of the nastier RS-485 failure modes because it silently takes down the whole bus — every other node sees a permanent "bus busy" condition and no communication gets through. In a medical device that's not just an inconvenience; it can mean loss of monitoring, so the design has to assume it can happen and bound the damage.

The first layer is detection. Since a healthy bus idles in the biased (recessive) state, a node that sees the bus stuck dominant for longer than any legitimate transmission could last should flag it. That timeout has to be derived from the worst-case frame length at the configured baud rate plus turnaround, with margin — not a guessed number. Each node (or the master) can run this watchdog independently.

The second layer is isolation. The cleanest approach is per-node isolation of the transceiver's driver from the bus — either a series element that can be switched out, or a transceiver with an enable that can be forced off by supervisory logic independent of the main firmware. If the failing node can be electrically disconnected from the bus, the rest of the network recovers. The trade-off is cost and board space per node versus the value of fault containment.

The third layer is fail-safe biasing and termination design so that a single failed driver doesn't shift the bus into an ambiguous state for the remaining nodes — proper biasing keeps the idle state well-defined even with one driver misbehaving, and termination should be placed so a fault at one point doesn't create reflections that confuse receivers.

I'd also think about the system-level response: the master should be able to detect "bus stuck" and enter a defined safe state (alarm, fallback to a redundant path, or controlled shutdown) rather than hanging indefinitely. In a medical context, the requirement isn't just "recover the bus" — it's "never leave the patient-facing function in an undefined state."

**Possible follow-ups:** How would you set the stuck-bus timeout without false-triggering on legitimate long frames? Would you put the isolation on every node or only on the master side, and why?

## Q3: How would you approach implementing end-to-end integrity protection for a safety-critical CAN-FD payload, beyond the CRC the controller already provides?

**Answer:** The controller CRC protects the frame on the wire, but it doesn't protect against faults that occur inside a node — a corrupted RAM buffer, a software bug that assembles the wrong bytes, a gateway that mangles data between segments, or a stale value being retransmitted. For a safety-critical payload, the standard approach is a separate application-layer protection layer, often called E2E protection, layered on top of the transport.

The core elements are: a data integrity check (typically a CRC computed over the payload plus a counter and any identifying fields), a sequence counter so the receiver can detect lost, duplicated, or out-of-order messages, and a message identifier/timeout so the receiver can detect stale data. The CRC polynomial and width should be chosen for the expected data length and the residual error rate you're willing to accept — a 16-bit CRC over a 64-byte payload gives a known residual error probability that you can document in the risk file.

The important design decisions are where the CRC is computed and verified, and what the receiver does on failure. The CRC must be computed as close as possible to the point where the data is produced and verified as close as possible to where it's consumed, so that no intermediate layer can silently alter it. On failure, the receiver should not just drop the message silently — it should increment an error counter, and if failures exceed a threshold, transition to a defined safe state. That behavior needs to be specified and tested, not left to chance.

There's also a timing dimension: the counter and timeout together let the receiver distinguish "no new data" from "data arrived but is corrupt." For a closed-loop control function, stale-but-valid data is often more dangerous than no data, so the timeout has to be tight enough to catch a stalled producer.

**Possible follow-ups:** How would you choose between a 16-bit and 32-bit CRC for a given payload size? How would you handle the case where a gateway between two CAN-FD segments has to re-frame messages — where does the E2E check live?

## Q4: How would you approach selecting between USB interrupt transfers and isochronous transfers for a medical device that streams real-time sensor data to a host, given a requirement that no data be lost?

**Answer:** The requirement "no data lost" is the deciding factor, and it points away from isochronous. Isochronous transfers guarantee bandwidth and timing but explicitly do not guarantee delivery — there's no retry, and a missed packet is simply gone. That's fine for audio or video where a dropped frame is imperceptible, but for medical sensor data it's usually unacceptable unless the loss is bounded and the application can tolerate it.

Interrupt transfers, by contrast, are retried by the host controller on error and are scheduled with a guaranteed maximum latency (the endpoint's polling interval). The trade-off is that interrupt transfers have a maximum packet size and a bounded bandwidth allocation per frame, so you have to size the endpoint and polling interval to carry the required data rate with margin. If the data rate exceeds what a single interrupt endpoint can carry, you either use multiple endpoints, reduce the sample rate, or reconsider the transport.

The other consideration is host-side behavior: interrupt transfers are handled by the host controller's periodic schedule, which is shared with other periodic traffic. On a busy host, the guaranteed latency can degrade, so the design should include buffering on the device side and a defined behavior if the host falls behind — for example, a ring buffer with an overflow flag that the application can detect, rather than silent loss.

If the data genuinely must be both real-time and lossless, the honest answer may be that USB is the wrong transport for the hard-real-time portion, and the architecture should split: a lossless path (bulk or interrupt with retry) for the data that matters, and a best-effort path for anything that can tolerate loss. I'd want the requirement clarified — "no data lost" under what conditions, and what's the acceptable latency bound?

**Possible follow-ups:** How would you size the interrupt endpoint's polling interval and packet size for a given sample rate? What would you do if the host's periodic schedule can't accommodate the required bandwidth?

## Q5: You're leading a design review where a junior engineer proposes a custom application-layer protocol over UART for a medical device, and you notice the framing has no length-field validation and no sequence numbers. How would you guide the team to evaluate and improve the design?

**Answer:** I'd start by making the failure modes concrete rather than just asserting the design is wrong — a junior engineer (and the rest of the team) will learn more from walking through what actually goes wrong than from a verdict. I'd ask the engineer to trace what happens when a single bit flips in the length field, or when a byte is dropped, or when the receiver resyncs mid-frame. Usually that walkthrough surfaces the problem on its own: a corrupted length field causes the receiver to consume subsequent valid frames as payload, and without sequence numbers there's no way to detect that data was lost or duplicated.

From there I'd frame the discussion around what the protocol needs to guarantee for this device's risk profile — not "best practice" in the abstract, but "what does the application need to detect, and what does it need to do when it detects it?" That reframes the review from style to requirements. A length field with a checksum over the header, a sequence counter, and a defined resynchronization strategy (e.g., a start-of-frame delimiter plus a maximum frame length so the receiver can bound its search) are the minimum set for a protocol carrying medical data.

I'd also want to talk about testability: how would we prove the protocol handles corruption correctly? That means a fault-injection test plan — deliberately corrupt length fields, drop bytes, inject noise — and a documented expected behavior for each case. If the protocol can't be tested against those cases, it isn't ready for regulatory submission.

Throughout, I'd keep the tone collaborative: the goal is to raise the design, not to embarrass the engineer. I'd ask them to own the revised framing spec and present it back, which turns the review into a growth opportunity and keeps the team bought in.

**Possible follow-ups:** How would you decide how much framing overhead is acceptable given the UART's bandwidth? What's the minimum set of fault-injection tests you'd require before signing off on the protocol?
