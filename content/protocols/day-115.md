# protocols — Day 115

## Q1: How would you approach debugging an RS-485 network that works reliably at low baud rates but shows intermittent corruption at high baud rates over a long cable with many nodes — how would you separate the contributions of termination, stub length, and turn-around timing?

**Answer:** I'd treat the three suspects as independent variables and try to isolate them one at a time rather than changing several things at once.

First, I'd characterize the physical layer with a scope at the far end of the bus. Termination problems show up as reflections — I'd look for ringing or overshoot on the differential pair at the last node, and check that the termination resistance actually matches the characteristic impedance of the cable (typically 120 Ω for twisted pair) and that terminators are only at the two physical ends, not at every node. A quick test is to temporarily remove or add termination and see whether the error rate changes; if it does, that's a strong signal.

Stub length is the next thing I'd examine. Long stubs off the main trunk create impedance discontinuities that matter more as the edge rate increases — at high baud the bit period shrinks and reflections that were previously settled by the sampling point now land inside it. I'd measure or estimate stub lengths and compare against the rule of thumb that stubs should be kept short relative to the rise time and bit period. If a node has a long drop cable, moving it closer to the trunk or re-routing is a direct test.

Turn-around timing is the third axis and is often the real culprit at high baud. In half-duplex RS-485 the driver must be disabled and the receiver enabled before the other end starts driving, and the firmware's enable/disable timing has to account for transceiver propagation delay and the time for the line to settle. At low baud there's plenty of margin; at high baud the margin evaporates. I'd instrument the DE/RE lines and the bus itself on a scope to confirm the driver is actually tri-stated before the next node talks, and check whether the last byte is being truncated because the driver is disabled too early.

To separate them cleanly: change baud rate with everything else fixed (isolates timing/edge-rate effects), then change termination with baud fixed, then physically shorten a stub. Whichever change moves the error rate tells you which mechanism dominates. I'd also confirm it's not a common-mode issue by checking the ground potential difference between nodes — that can masquerade as a termination problem.

**Possible follow-ups:** How would you decide whether to add bias resistors versus changing the transceiver? What would you look for on the scope to distinguish a reflection from a common-mode problem?

## Q2: How would you approach designing a protocol abstraction layer so that application code can talk to sensors over I2C, SPI, UART, or CAN-FD without knowing which transport is underneath?

**Answer:** The goal is to keep the transport-specific mechanics — addressing, framing, timing, error semantics — below a stable interface that the application sees. I'd structure it in layers.

At the bottom, a transport driver layer: one implementation per physical transport, each exposing a small, uniform set of primitives like open/close, a read/write of a byte buffer, and a way to report errors. Each driver owns its own quirks — I2C addressing and clock stretching, SPI chip-select and mode handling, UART framing and flow control, CAN-FD message IDs and DLC encoding — so none of that leaks upward.

Above that, a device/sensor layer: each sensor gets a driver that knows its register map and command set, and it talks to the transport through the uniform primitives. This is where you'd translate "read the pressure register" into whatever byte sequence the transport needs.

At the top, the application talks only to the sensor-layer API — "get pressure reading" — and never sees a bus type. The key design decisions are: define the interface in terms of operations and data, not in terms of bus transactions; make error reporting uniform (timeout, NACK, CRC failure, bus-off) so the application can handle faults generically; and keep timing/latency expectations explicit in the interface contract, because a CAN-FD read and an I2C read have very different latency profiles and the application needs to know the bounds, not the mechanism.

I'd also build in a way to inject a mock transport for testing, so the application and sensor layers can be exercised without hardware. And I'd be careful about where buffering and retries live — putting retry logic in the transport layer keeps it consistent, but the application may need to know a retry happened for safety-critical paths, so that has to be surfaced.

**Possible follow-ups:** Where would you put end-to-end integrity checking — in the transport layer or the sensor layer? How would you handle a transport that has fundamentally different latency characteristics without the application needing special cases?

## Q3: How would you approach selecting between USB 2.0 interrupt transfers and isochronous transfers for a medical device that streams real-time sensor data to a host, given a requirement that no data be lost?

**Answer:** The requirement "no data lost" is the deciding constraint, and it points away from isochronous transfers. Isochronous transfers reserve bandwidth and guarantee timing, but they have no retry mechanism — if a packet is corrupted or the host misses its service interval, that data is simply gone. That's fine for audio or video where a dropped frame is imperceptible, but it's the wrong trade-off when the requirement is zero loss.

Interrupt transfers, by contrast, are retried by the host controller on error and are scheduled with a guaranteed maximum latency (the endpoint's polling interval), so they give you both reliability and bounded latency — just not the hard real-time guarantee of isochronous. For a medical sensor stream where losing a sample matters, interrupt transfers are usually the right default.

The trade-off is bandwidth and latency jitter: interrupt transfers have more protocol overhead and the polling interval sets a floor on latency, and under heavy bus load the host may not service every interval. So I'd size the endpoint and polling interval against the actual data rate and the acceptable latency, and confirm the host can sustain it. If the data rate were high enough that interrupt transfers couldn't keep up, I'd reconsider the architecture — perhaps bulk transfers for the lossless path plus a separate mechanism for timing, or reducing the per-sample payload.

I'd also think about what "no data lost" means end to end: USB's CRC and retry protect the link, but the application still needs sequence numbers or a similar mechanism to detect gaps introduced above the link layer (host buffering, driver issues). So the transport choice is necessary but not sufficient — I'd pair it with application-level integrity.

**Possible follow-ups:** How would you handle a host that can't sustain the required interrupt polling rate? What role would bulk transfers play if the data were bursty rather than continuous?

## Q4: How would you approach debugging a CAN-FD network where a node occasionally goes bus-off and stays off until the controller is reset, even though the bus itself appears healthy afterward?

**Answer:** Bus-off means the controller's transmit error counter exceeded its limit, so the node accumulated enough errors to be taken off the bus by the protocol. The fact that the bus looks healthy afterward tells me the fault is intermittent and probably localized to that node's view of the bus, not a permanent wiring problem.

I'd start by reading the controller's error counters and error state history — most CAN controllers expose transmit/receive error counts and the last error code. That tells me whether the node was accumulating errors on transmit (suggesting it's the one being corrupted or failing to win arbitration cleanly) or on receive. I'd log the error counters over time to see the pattern: a steady climb suggests a persistent marginal condition, while a sudden jump suggests a discrete event.

Common causes I'd investigate: a bit-timing mismatch — the node's sample point or baud-rate prescaler doesn't match the rest of the network, so it misreads bits under certain conditions; a physical-layer issue local to that node, like a marginal transceiver, a bad connector, or a stub that's too long for the data-phase bit rate; and termination or common-mode problems that affect that node's position on the bus more than others. CAN-FD makes bit timing more sensitive because the data phase runs at a higher rate, so a node that was fine at classic CAN rates can fail in the data phase.

I'd also check whether the bus-off correlates with specific traffic — for example, only when a particular high-priority message is being sent, or only under heavy load, which would point at arbitration or error-frame interactions. And I'd verify the node's automatic recovery behavior: some controllers require explicit re-initialization after bus-off, which would explain why it stays off until reset.

The systematic approach: capture the error counters and bus traffic with an analyzer, correlate bus-off events with what's on the bus at that moment, then narrow to timing, physical layer, or a specific message pattern.

**Possible follow-ups:** How would you distinguish a bit-timing problem from a physical-layer problem using only the error counters? What would you change in the node's recovery logic to make bus-off less disruptive?

## Q5: You're leading a design review where a junior engineer proposes a custom application-layer protocol over UART for a medical device, and you notice the framing has no length-field validation and no sequence numbers. How would you guide the team to evaluate and improve the design?

**Answer:** I'd frame the review around consequences rather than just pointing at the missing fields, so the team understands why they matter — especially in a medical context where silent data corruption is a safety issue, not just a bug.

First, I'd walk through the failure mode concretely: without length-field validation, a single bit error in the length byte causes the receiver to consume the wrong number of bytes, which desynchronizes the frame boundary and can cause it to swallow subsequent valid frames as payload. That's silent corruption — the receiver thinks it got good data. Without sequence numbers, the receiver can't detect a dropped or duplicated frame, so a lost reading looks like a valid one. I'd ask the team to trace what happens to a patient-facing value if either of those occurs.

Then I'd steer toward fixes at the right layer. Length validation means a length field plus a check that the received length is within bounds and consistent with the actual bytes received before the frame is accepted. Sequence numbers give ordering and gap detection. I'd also raise whether a checksum or CRC over the frame is present — length and sequence alone don't catch bit flips in the payload. And I'd ask about resynchronization: how does the receiver recover cleanly after a bad frame rather than staying desynced?

I'd keep the tone collaborative — ask the junior engineer to walk through their reasoning and the failure cases, and let the team converge on the requirements. The outcome I'd want is a documented framing spec with explicit rules for length, sequence, integrity check, and resync, plus a test plan that injects bit errors and dropped frames to prove the receiver behaves safely. Given it's a medical device, I'd also connect it back to the risk analysis: these failure modes should be captured and their mitigations traceable.

**Possible follow-ups:** How would you decide between a checksum and a CRC for this frame? What should the receiver do when it detects a sequence gap — drop the frame, flag it, or something else?
