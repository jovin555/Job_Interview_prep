# space-rad-hard — Day 115

## Q1: How would you approach designing a radiation-tolerant analog-to-digital conversion subsystem where the ADC's voltage reference is a COTS part with no radiation data, and the measurement must hold accuracy over a multi-year mission?

**Answer:** I'd start by treating the reference as the accuracy bottleneck and quantifying the risk before choosing a mitigation. The three failure modes to bound are: TID-induced drift (including enhanced low-dose-rate sensitivity, which can make low-dose-rate drift worse than the high-dose-rate data you might extrapolate from), single-event transients on the reference output that propagate straight into every conversion, and long-term drift that a one-time calibration can't catch. My first move is to look for any published radiation data — even a manufacturer's internal report or a similar-die part — because "no data on the datasheet" is not the same as "no data exists." If nothing credible exists, I'd either fund a targeted TID and heavy-ion test on a small sample, or design around the part. Designing around it means: (1) adding a second, independent reference and comparing them in firmware so a divergence flags a fault; (2) using a ratiometric measurement where the same reference drives both the sensor excitation and the ADC, so reference drift largely cancels; (3) placing a low-pass filter and a clamp on the reference output to blunt SET spikes, accepting that this trades transient rejection against settling time; and (4) scheduling periodic in-flight calibration against a stable on-board standard, with the calibration cadence set by the expected drift rate. The key discipline is to write down an error budget that separates initial accuracy, temperature drift, TID drift, and SET-induced error, and show that the sum still meets the measurement requirement with margin — if it doesn't, the part is disqualified regardless of how convenient it is.

**Possible follow-ups:** How would you distinguish reference drift from sensor drift during in-flight calibration? What would make you decide a dual-reference comparison scheme is worth the board area and power?

## Q2: You're reviewing a design where a junior engineer has used a single-ended, non-redundant analog signal chain — sensor, amplifier, ADC — for a measurement that feeds a control loop. The engineer argues that the digital side already has TMR, so the analog side is "covered." How would you evaluate this argument?

**Answer:** The argument has a category error in it: TMR protects against upsets in the digital logic, but it does nothing for a fault that originates upstream of the ADC. If the amplifier latches, drifts, or produces a transient, all three TMR replicas receive the same corrupted input and vote unanimously on the wrong answer — TMR gives you confident agreement on bad data. So the first thing I'd do is trace the failure modes of the analog chain and ask, for each one, whether any downstream mechanism can detect it. A single SET on the amplifier output that lands inside the ADC sampling window is invisible to the digital side unless there's an independent plausibility check. I'd then propose proportionate mitigations rather than reflexively duplicating the whole chain: a second, cheaper signal path (different amplifier topology or a different sensor channel) for cross-checking, range and rate-of-change plausibility limits in firmware so an implausible reading is rejected rather than acted on, and a hold-last-good or safe-state policy when the cross-check disagrees. The point I'd make in the review is that redundancy has to be independent to be worth anything — replicating the same single point of failure three times is not redundancy, it's triplication of the same risk.

**Possible follow-ups:** How would you set the plausibility limits without masking a genuine fast transient the loop needs to respond to? Where would you draw the line between "add a second path" and "accept the risk and document it"?

## Q3: How would you approach designing a fault-tolerant power distribution scheme for a payload where several loads share a common upstream rail, and a single-event latch-up in any one load must not collapse the rail for the others?

**Answer:** The core principle is that the shared rail must never be able to see a faulted load directly — every load gets its own current-limited branch, and the branch is what absorbs the latch-up, not the upstream converter. I'd structure it as: a primary rail from the DC-DC, then per-load protection (a current-limiting switch or an eFuse with a defined trip threshold and a latch-off or retry policy), sized so that one branch's worst-case fault current stays within what the primary can supply without drooping below the other loads' minimum operating voltage. The sizing calculation is the crux: you need the sum of all branch limits plus margin to stay under the primary's current capability, otherwise two simultaneous faults take the rail down. I'd also think about where the boundary between "shared" and "isolated" belongs — housekeeping and telemetry loads probably want their own branch so a fault in a high-power actuator can't blind you to what's happening. On the latch-up response itself, I'd decide per load whether to latch off and require a commanded retry or to auto-retry with a backoff, because auto-retry into a persistent latch just burns power and heats the part. Finally, I'd add rail monitoring with a fast comparator so an undervoltage event is logged with a timestamp — that telemetry is what lets you diagnose which branch faulted after the fact.

**Possible follow-ups:** How would you handle inrush from a highly capacitive load without nuisance-tripping its branch protection? What's your approach if two loads must share a branch for cost or space reasons?

## Q4: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt (SEFI) that leaves the processor still drawing current and still toggling a heartbeat line, but no longer executing the control loop?

**Answer:** The hard part is that the failure signature you're testing for is specifically designed to defeat the naive detector — a heartbeat GPIO that's still toggling looks healthy to anything watching only that pin. So the test plan has to prove that the recovery mechanism keys off something the hung processor can't fake. I'd structure the plan around fault injection rather than waiting for radiation: on the bench, use a debugger or a test hook to freeze the control loop while leaving the heartbeat task running, and confirm the system still detects and recovers. That means the detector must be a challenge-response or a watchdog that requires the control loop itself to service it — not a task that a stuck scheduler can keep feeding. The plan would cover: (1) injection of the exact SEFI signature (loop halted, heartbeat alive) and verification that recovery occurs within the specified time; (2) injection of a true hard hang (heartbeat also stopped) to confirm the simpler path still works; (3) verification that recovery restores safe actuator state before resuming control, not just that the processor reboots; (4) a check that the recovery event is logged with enough context to diagnose it later; and (5) repeated injections to catch marginal timing. Where radiation beam time is available, I'd run the same pass/fail criteria under beam to confirm the injected-fault model matches reality — but the bench injection is what gives you repeatable coverage.

**Possible follow-ups:** How would you design the watchdog so it can't be fed by a hung-but-scheduled task? What would you do if the recovery itself depends on a resource that the SEFI corrupted?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** I'd start by separating the person from the proposal — the engineer has done real analysis, and the fastest way to lose the room is to make it feel like the work is being dismissed. My approach is to ask them to walk through their margin calculation and their assumptions out loud, and to make the specific assumption I'm worried about explicit rather than arguing about the conclusion. Usually the disagreement resolves into one of two buckets: either they've made an assumption I think is wrong (for example, extrapolating high-dose-rate data to a low-dose-rate mission, or treating "no failures seen in test" as "no failures possible"), or they've made a reasonable assumption I hadn't considered. If it's the first, I'd frame it as "help me understand how this holds if assumption X is off" and let the analysis do the persuading — a good engineer will follow the logic. If we still disagree, I'd move it from opinion to evidence: what test, datasheet, or analysis would settle it, and can we get that in time? I'd also be explicit about who owns the risk decision and make sure the concern is documented in the review record either way, so if the under-margined choice is taken, it's a known and accepted risk rather than an oversight. The goal isn't to win — it's to make sure the decision is made with the risk visible.

**Possible follow-ups:** What would you do if the schedule doesn't allow time to gather the evidence that would settle it? How do you keep a review constructive when the engineer is more senior or more invested than in this case?
