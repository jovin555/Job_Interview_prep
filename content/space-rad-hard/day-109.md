# space-rad-hard — Day 109

## Q1: How would you approach designing a radiation-tolerant power distribution scheme for a payload where several loads share a common upstream rail, and a single-event latch-up (SEL) in any one load must not collapse the rail for the others?

**Answer:** The core principle is that a latch-up is a local fault and must be contained locally — the shared rail should never be the thing that carries the fault current. I'd structure the design around a hierarchy: a primary bus feed, then per-load protection, then the loads themselves. Each load gets its own current-limiting element — a latching current limiter or an eFuse with a defined trip threshold and a controlled response — placed between the shared rail and the load. The trip threshold is set above the load's worst-case inrush and steady-state current but well below the point where the shared rail would sag enough to disturb other loads. Critically, the protection must be able to distinguish a transient inrush from a sustained latch-up: a simple fast-trip breaker will nuisance-trip on capacitive loads, so I'd use a current-limit-then-retry or a timed foldback characteristic.

The second layer is the shared rail itself. I'd size the upstream converter and its output capacitance so that even if one load's protection takes some microseconds to act, the rail droop stays within the tolerance of the other loads. That means analyzing the worst-case fault current the latched load can draw before its limiter engages, and making sure the bulk capacitance and converter loop bandwidth can absorb that charge without the rail collapsing. If the numbers don't close, the answer is to segment the rail — give the most critical loads their own regulated branch off the primary bus rather than sharing a single point of distribution.

I'd also think about the fault's persistence. A latch-up only clears on power removal, so the protection element needs a way to cycle the load — either a controlled restart after a timeout or a command from the housekeeping controller. And I'd want telemetry on each branch's current and trip status so the system can report which load latched and decide whether to retry it or leave it isolated. The boundary between "shared" and "isolated" is really a question of how much fault current the shared rail can tolerate and how critical each load is — the more critical the load, the more I'd push toward giving it an independent branch.

**Possible follow-ups:** How would you set the trip threshold and response time for the per-load limiter, and what would you do if a load's normal inrush current is close to the latch-up current you're trying to catch? How would you verify the containment behavior on the ground without being able to induce a real latch-up?

## Q2: You're reviewing a design for a space-deployed system that uses a COTS linear regulator to generate a 1.2V core voltage for an FPGA. The regulator's datasheet shows no radiation data, and the output voltage is specified as 1.2V ±2%. The FPGA requires 1.2V ±5% and draws up to 3A. How would you evaluate this choice and what alternatives would you recommend?

**Answer:** The first thing I'd flag is that the tolerance stack-up is much tighter than it looks. The regulator's ±2% is a room-temperature, pre-irradiation number. Over TID the reference inside the regulator will drift, and with no radiation data you have no bound on how much — it could be a few millivolts or it could be tens. Add temperature drift, load regulation at 3A, and line regulation, and the ±2% budget is likely consumed before you even get to radiation. The FPGA's ±5% is the total window the part will tolerate, and you generally want margin inside that window for transient droop and for the FPGA's own tolerance to supply variation. So the honest answer is: the nominal numbers might close, but the uncharacterized radiation drift makes the margin unknowable, which is not the same as adequate.

The second concern is that a linear regulator at 3A is dissipating real power — if it's dropping from a higher rail, that's watts of heat in a vacuum, which brings thermal derating into the picture on top of the electrical margin. And a COTS linear regulator may also be susceptible to single-event transients on its reference or error amplifier, producing output glitches that the FPGA sees directly.

For alternatives, I'd look at three directions. First, a radiation-characterized regulator or a rad-hard point-of-load module, even at higher cost and lower efficiency, because it comes with data you can design against. Second, if a COTS part is unavoidable, characterize it — at minimum a TID test to bound the drift, and ideally SEE testing — and then re-run the tolerance stack with the measured drift included, plus a guard band. Third, restructure the architecture: if the FPGA has an internal or external voltage supervisor and the core rail can tolerate a wider window with a different part, or if the design can use a switching regulator with a rad-tolerant reference, that may buy back margin. I would not sign off on "the datasheet says ±2%, so it fits" — the missing radiation data is the whole question.

**Possible follow-ups:** If TID testing shows the regulator drifts 3% at end of life, does the design still close, and what would you change? How would you handle the single-event transient risk on the regulator's output if you keep a COTS part?

## Q3: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt (SEFI) that leaves the processor still drawing current and still toggling a heartbeat line, but no longer executing the control loop?

**Answer:** The defining feature of this failure is that the usual "is it alive?" indicators lie — current draw is normal, the heartbeat GPIO is still toggling, but the control loop is dead. So the test plan has to be built around detecting functional death, not electrical death. I'd start by defining what "executing the control loop" actually means in observable terms: a counter that increments only inside the loop, a sequence number in the telemetry, an output that changes in response to a known stimulus. The test needs an independent observer — a test harness or a second processor — that watches those functional indicators rather than the heartbeat.

Then I'd design fault injection that reproduces the SEFI state without radiation. That could be a debugger halt of the core while leaving peripherals running, a firmware-injected branch to a tight loop that still services the heartbeat, or a hardware fault injector that corrupts the program counter or a state variable. The point is to create the exact signature: heartbeat alive, loop dead. I'd run each injection many times and measure the recovery time and the recovery path — does the watchdog catch it, does the external supervisor reset it, does it recover on its own?

The critical part is verifying the recovery mechanism actually works against this signature. A simple watchdog that the firmware pets from a timer interrupt will not catch a SEFI where the timer interrupt still runs but the main loop is stuck — so the test must confirm the watchdog is fed only by evidence of loop progress, or that a second, independent monitor exists. I'd also test the boundary cases: recovery when the fault hits during a critical write, recovery when the fault hits the watchdog service routine itself, and repeated injections to check the system doesn't degrade into a state where it recovers but with corrupted state. Finally, I'd define pass criteria up front — maximum recovery time, no loss of critical state, no unsafe output during recovery — so the test produces a clear verdict rather than an anecdote.

**Possible follow-ups:** How would you design the watchdog so it can't be fooled by a heartbeat that keeps toggling? What would you do if the recovery mechanism itself is susceptible to the same SEFI?

## Q4: How would you approach selecting and qualifying a voltage supervisor or reset IC for a space-deployed system, given that most commercial parts are not radiation-characterized?

**Answer:** A voltage supervisor is a deceptively simple part that sits in a critical path — it decides when the processor is allowed to run — so I'd treat the lack of radiation data as the central problem, not an afterthought. I'd start by defining what the supervisor actually has to do in this system: hold reset through power-up until the rail is valid, assert reset if the rail droops, and release reset cleanly. Then I'd ask which of those functions is radiation-sensitive. The reference and comparator inside the supervisor can drift with TID, which shifts the trip threshold; the output stage can glitch on a single-event transient, which could cause a spurious reset or, worse, fail to assert when it should.

For selection, I'd prioritize parts with at least some radiation pedigree — a QML-listed or rad-hard supervisor if the budget allows, or a part with published TID and SEE data even if it's not fully qualified. If I have to use an uncharacterized COTS part, I'd bound the risk: TID test a sample to see how far the threshold moves, and consider whether the system can tolerate that shift. A supervisor whose threshold drifts by tens of millivolts over mission life may still be fine if the margin to the processor's minimum operating voltage is large; it may be unacceptable if the margin is tight.

I'd also design for the failure modes rather than trusting the part. Add hysteresis so a drifting threshold doesn't cause chatter. Consider a redundant or diverse reset path — for example, an external supervisor plus a processor-internal brown-out detector, so a single point of failure doesn't leave the system un-reset. And I'd think about the transient response: a SET on the supervisor output that momentarily releases reset while the rail is still invalid is a real hazard, so a small RC filter or a latching behavior on the reset output can help. The qualification plan would combine whatever radiation data I can get with a functional test at temperature and a documented rationale for the residual risk.

**Possible follow-ups:** If the supervisor's threshold drifts upward over life, what failure mode does that create, and how would you detect it? How would you decide between a rad-hard supervisor and a COTS part plus a redundant internal detector?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** The first move is to separate the person from the proposal. The engineer has done real analysis, so I'd start by acknowledging that and asking them to walk the review through their assumptions — specifically, what radiation environment they assumed, what data they used, and where the margin actually sits. Often the disagreement isn't about the conclusion but about an unstated assumption, and making that explicit in front of the room is more productive than me asserting "this is under-margined."

Then I'd reframe the discussion around the decision criteria rather than my opinion. What margin does the program require? What's the consequence of the margin being consumed — a degraded measurement, a latch-up, a loss of function? If we can agree on the criteria, the technical question becomes objective: does the proposal meet them, and if not, by how much? I'd ask the engineer to quantify the worst case with the radiation effects included, and I'd do the same, so we're comparing numbers rather than positions. If their analysis holds up, I should be willing to change my mind — that's the point of the review.

If the gap is real, I'd frame the path forward as a joint problem: what would it take to close the margin — a different part, a derating change, a test to characterize the part, a design change — and who owns each option. That turns "you're wrong" into "here's what we need to do." I'd also be careful not to let the review become a referendum on the engineer's competence; the goal is the right decision, and a junior engineer who feels heard is more likely to raise the next concern early rather than defend a position. If we can't converge in the room, I'd take it to a follow-up with the specific data we each need, and document the decision and its rationale so it's traceable. The one thing I wouldn't do is let a schedule pressure override a real margin gap silently — if we accept the risk, it should be a conscious, recorded decision, not an oversight.

**Possible follow-ups:** What would you do if the engineer's analysis turns out to be correct and your concern was unfounded? How would you make sure a junior engineer feels able to push back on you in future reviews?
