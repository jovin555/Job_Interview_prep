# space-rad-hard — Day 14

## Q1: How would you approach designing a radiation-tolerant real-time clock (RTC) subsystem for a space-deployed system that must maintain accurate timekeeping across a multi-year mission?

**Answer:** A radiation-tolerant RTC subsystem needs to address both timekeeping accuracy and data integrity. First, I'd evaluate whether a dedicated RTC IC is necessary or whether the main microcontroller with an external crystal could suffice — this depends on power constraints and whether the system needs to keep time during low-power or off states. For the RTC itself, I'd look for parts with known radiation performance, but since most commercial RTCs lack radiation data, I'd plan for mitigation. Key considerations include: using a crystal oscillator with appropriate drive level and load capacitance for stability across temperature and TID-induced frequency shifts; implementing periodic time synchronization from a known-good source (e.g., GPS or ground command) to correct cumulative drift; and protecting the timekeeping registers with error detection and correction — either SEC-DED ECC in software or triple-redundant storage with majority voting. I'd also consider that single-event upsets could corrupt the time value, so the firmware should validate time reads (e.g., reading twice and comparing, or using a checksum) and have a mechanism to detect and recover from invalid time states. For the battery or supercapacitor backup, I'd use radiation-tolerant power-switching circuitry to prevent latch-up in the backup path and ensure the RTC can survive power cycling of the main bus. Finally, I'd characterize the crystal's frequency stability under TID — some crystals show frequency shifts after irradiation — and budget for that drift in the mission timeline.

**Possible follow-ups:** How would you handle the case where the RTC's backup battery is also exposed to radiation and may degrade over the mission? What if the system requires time synchronization across multiple distributed nodes — how would you approach that?

## Q2: You are reviewing a design for a space-deployed system that uses a radiation-hardened FPGA and an external ADC for precision analog measurements. The designer has placed a ferrite bead in series with the ADC's analog supply to filter noise, but the ferrite bead is not radiation-characterized. How would you evaluate this choice?

**Answer:** This is a common situation where a passive component with no radiation data is used in a critical path. Ferrite beads are generally considered relatively radiation-tolerant because they're passive magnetic components, but they can exhibit changes in impedance and saturation characteristics under TID, particularly at high total dose levels. My evaluation would start with understanding the ferrite bead's role: it's providing high-frequency noise isolation between the noisy digital supply and the sensitive analog supply. The concern is that if the ferrite bead's impedance changes under radiation, the filtering effectiveness could degrade, potentially allowing noise to couple into the ADC reference or supply and affecting measurement accuracy. I'd also consider whether the ferrite bead is operating near its saturation current — if the ADC draws transient currents, the bead could saturate and lose its filtering properties. For mitigation, I'd recommend: (1) characterizing the ferrite bead's impedance before and after irradiation at the expected TID level, even if it's a simple bench test; (2) adding a parallel capacitor bank after the bead to provide a low-impedance path for transient currents; (3) considering whether the bead is even necessary — sometimes a properly sized pi-filter with capacitors and a small resistor can be more predictable; and (4) ensuring the ADC's power supply rejection ratio (PSRR) is adequate for the expected noise levels, so the design doesn't rely solely on the bead for filtering. If the mission is long-duration and the analog measurement is critical, I might recommend using a radiation-qualified EMI filter or a simple RC filter with known radiation-tolerant components instead.

**Possible follow-ups:** What if the ferrite bead is also used in the ADC's reference voltage path — would that change your assessment? How would you verify the filtering effectiveness after irradiation?

## Q3: How would you approach designing a firmware-based fault detection and recovery strategy for a space-deployed system that uses multiple microcontrollers communicating over a shared bus, where a single-event upset in one node could corrupt the bus and affect all nodes?

**Answer:** This requires a layered approach to fault detection and recovery. At the bus level, I'd implement a protocol with robust error detection — CRC or checksum on every message, message timeouts, and bus arbitration that prevents any single node from holding the bus indefinitely. Many standard protocols like CAN already have built-in error handling, but for simpler buses like I²C or SPI, I'd add a bus supervisor that can detect a stuck-bus condition and force a reset or re-initialization. At the node level, each microcontroller should have a watchdog timer that's independent of the bus — if a node stops communicating or becomes unresponsive, the watchdog resets it. But the key is making the recovery automatic and coordinated: when a node resets, it should re-initialize its bus interface and rejoin the network without requiring manual intervention. I'd also implement a health-monitoring scheme where each node periodically broadcasts a status message, and other nodes can detect if a neighbor has gone silent. For the corrupted-data scenario, I'd use message sequence numbers and duplicate detection so that a stale or corrupted message can be identified and discarded. One important consideration is avoiding a "reset storm" where one node's failure causes other nodes to reset in a cascade — so I'd add a random backoff or staggered reset timing. Finally, I'd design the system to degrade gracefully: if one node is persistently failing, the others should be able to continue operating with reduced functionality rather than the entire system shutting down. This might involve a master-slave election protocol or a pre-defined priority scheme for which nodes are essential.

**Possible follow-ups:** How would you test this fault recovery strategy to ensure it works under real radiation conditions? What if the bus itself is the single point of failure — how would you add redundancy?

## Q4: Imagine you are leading a design review for a space-deployed system, and a junior engineer proposes using a commercial real-time clock (RTC) IC that has no radiation data, arguing that "it's just a simple I²C device and the probability of an upset is low." The RTC is used for mission-critical event logging. How would you handle this disagreement?

**Answer:** I'd approach this constructively, acknowledging that the engineer's reasoning has some merit — the RTC is a relatively simple device and the probability of a single-event upset in any given moment is indeed low. However, the issue is about mission reliability over years, not instantaneous probability. I'd walk through the risk assessment: what happens if the RTC's time register gets corrupted? If it's used for event logging, corrupted timestamps could make the logs useless for post-mission analysis. What if the I²C interface latches up? That could hang the entire bus and affect other devices. The probability of an upset might be low per hour, but over a multi-year mission with continuous operation, the cumulative probability becomes significant. I'd also point out that the RTC's internal oscillator and divider chain are particularly sensitive to single-event transients — a transient on the oscillator could cause the time to jump by seconds or minutes, which might go undetected. My recommendation would be to either: (1) select a radiation-qualified RTC if one exists, (2) implement the RTC function in firmware using the main microcontroller's timer with periodic synchronization from a known-good source, or (3) use the commercial RTC but with robust mitigation: triple-redundant time storage with voting, periodic validation against a reference, and a bus supervisor that can isolate the RTC if it misbehaves. I'd frame this as a risk-management discussion rather than a rejection of the engineer's idea — the goal is to make the risk explicit and decide consciously whether to accept it, mitigate it, or avoid it. I'd also encourage the engineer to research whether any radiation testing data exists for similar RTC parts, as sometimes commercial parts have been characterized by other organizations.

**Possible follow-ups:** How would you quantify the risk to make this decision data-driven? What if the mission can tolerate some data loss — how would that change your recommendation?

## Q5: How would you approach designing a power supply sequencing and monitoring scheme for a space-deployed system with multiple voltage rails (e.g., 3.3V, 1.8V, 1.2V, and an analog 5V rail), where the FPGA and ADC have specific power-up ordering requirements and the system must survive single-event latch-up events?

**Answer:** I'd start by documenting the power-up sequencing requirements for each device — the FPGA might require core voltage before I/O voltage, or the ADC might need its analog supply before the digital interface. The sequencing can be implemented in hardware using a sequencer IC or in firmware using GPIO-controlled enable pins on the DC-DC converters. For space applications, I'd prefer a hardware sequencer with a watchdog function, because firmware-based sequencing can fail if the microcontroller itself is upset. The sequencer should have programmable delays and monitor each rail's voltage to confirm it's within tolerance before enabling the next rail. For latch-up protection, I'd add current-limiting on each rail — either using the DC-DC converter's current limit or a separate current-sense circuit — so that if a device latches up and draws excessive current, the rail is shut down or current-limited rather than dragging down the entire bus. After a latch-up event, the system needs to recover: the affected rail should be power-cycled (turned off, held off for a period, then re-enabled) and the device reset. I'd also add voltage supervisors on each rail that generate a reset signal if the voltage drops below a threshold, ensuring the FPGA and other devices are held in reset during power-up and brown-out conditions. For monitoring, I'd use an ADC to sample each rail's voltage and current, with thresholds for over/under-voltage and over-current that trigger an interrupt to the main controller. The monitoring data should be logged for post-mission analysis. One subtle point is the sequencing of the analog and digital grounds — I'd ensure the analog and digital supplies are sequenced to avoid latch-up in mixed-signal devices, and I'd add proper decoupling and filtering at each rail to prevent noise coupling during power transitions.

**Possible follow-ups:** How would you handle the case where a latch-up event occurs during the power-up sequence itself? What if the sequencer IC is not radiation-qualified — how would you mitigate that?
