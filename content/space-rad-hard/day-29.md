## Q1: How would you approach designing a radiation-tolerant communication protocol between two FPGAs over a high-speed serial link, where single-event upsets can corrupt both the data payload and the link synchronization state?

**Answer:** I'd approach this as a layered problem, because radiation effects manifest differently at each layer of the protocol stack. At the physical layer, I'd first consider whether the serial transceiver itself is radiation-tolerant — a single-event transient on the clock recovery circuitry can cause bit slips that are much harder to recover from than individual bit errors. If the transceiver is COTS, I'd need to characterize its single-event transient behavior or add external mitigation. At the link layer, I'd implement a framing scheme with a robust sync pattern that includes error detection, so a corrupted sync word doesn't cause false framing. The key design decision is how to handle loss of synchronization: a naive approach might immediately re-sync, but if the sync pattern itself is corrupted, you can end up in a lock-up loop. I'd use a "hysteresis" approach — require multiple consecutive valid frames before declaring sync re-acquired, and require multiple consecutive CRC failures before declaring sync lost. This prevents a single upset from causing a disruptive re-sync event. At the data layer, I'd add forward error correction (FEC) rather than just error detection, because retransmission over a space link can be slow and the error rate may be too high for ARQ to be efficient. A SEC-DED code or a short Reed-Solomon block code would handle the expected single-bit error density. Finally, I'd add end-to-end sequence numbers and a higher-level integrity check so that even if a corrupted frame slips through the link layer, the application can detect and discard it. The trade-off is latency and overhead — FEC adds coding delay and bandwidth, so I'd size the code to the expected upset rate rather than over-provisioning.

**Possible follow-ups:** How would you decide between FEC and ARQ for this link? What if the two FPGAs are on separate boards connected through a backplane — how would that change your approach?

## Q2: You are reviewing a design for a space-deployed system that uses a radiation-hardened FPGA and a COTS high-speed ADC. The ADC's digital output interface is LVDS, and the designer has placed series resistors in the LVDS lines for impedance matching but has not added any termination at the FPGA receiver. The designer argues that the FPGA's internal termination is sufficient. How would you evaluate this approach?

**Answer:** I'd evaluate this carefully because LVDS termination is not just about signal integrity — it's also about reliability and noise margin, both of which matter in a radiation environment. First, I'd check the FPGA's documentation to confirm that internal termination is actually available on the specific I/O bank and pins being used, and that it can be enabled in the configuration. Many FPGAs offer internal 100-ohm differential termination, but it's not always available on all pins or all I/O standards. If internal termination is available, the next question is whether it's a precision termination — internal terminations are often implemented with a tolerance of ±20% or worse, whereas an external 100-ohm resistor can be selected with 1% tolerance. In a high-speed link, a 20% mismatch can cause reflections that degrade the eye diagram, reducing noise margin. That matters in space because single-event transients on the ADC's output drivers or on the LVDS lines themselves can inject noise, and a marginal eye makes the receiver more likely to misinterpret a transient as a valid bit. I'd also consider that the series resistors the designer added — if they're in series with each line — actually increase the impedance seen by the receiver, which can worsen the mismatch if the internal termination is already imprecise. My recommendation would be to use external 100-ohm differential termination at the receiver, placed as close to the FPGA pins as possible, and remove the series resistors unless they're specifically needed for ESD protection. If the designer wants to keep internal termination, I'd require a signal integrity simulation showing adequate eye margin across the full temperature and process range, plus derating for radiation-induced timing drift in the ADC's output timing.

**Possible follow-ups:** How would you verify the termination is working correctly during board bring-up? What if the LVDS lines are long enough that transmission line effects become significant?

## Q3: How would you approach designing a radiation-tolerant firmware architecture for a system that must perform critical control functions, where a single-event upset in a shared data structure could corrupt the state of multiple independent control loops?

**Answer:** I'd start by identifying which data structures are truly shared and which control loops are truly independent — often the coupling is more apparent than real, and reducing shared state is the first and most effective mitigation. For data that must be shared, I'd apply a combination of techniques. First, I'd use a "single-writer, multiple-reader" pattern where each control loop owns its own state variables and other loops only read them through a defined interface. This prevents one loop from corrupting another's state through a stray write. Second, I'd add redundancy at the data level: store critical variables in triplicated form with a voting scheme on read, or use a checksum that's verified before each use. For a control loop, a corrupted setpoint or gain value can cause a dangerous output, so I'd validate every parameter read against its redundant copies or checksum before using it. Third, I'd design the control loops to be fail-safe: if a parameter fails validation, the loop should revert to a safe default state rather than continuing with potentially corrupted data. This is a key design principle — the recovery behavior must be defined in advance, not improvised at runtime. Fourth, I'd use a periodic "scrubbing" task that walks through all critical data structures, validates them, and repairs any corruption. This bounds the time window during which corrupted data can persist. Finally, I'd consider partitioning: if the control loops are truly independent, they could run in separate memory regions with memory protection units (MPUs) enabled, so a wild pointer in one loop cannot corrupt another's data. The trade-off is that MPUs add complexity and can cause priority inversion if not carefully managed. The overall architecture should be designed so that a single upset can cause at most one control loop to take a safe fallback action, not multiple loops to fail simultaneously.

**Possible follow-ups:** How would you test this architecture to verify that a single upset in a shared data structure doesn't cause cascading failures? How would you handle the case where two control loops genuinely need to share a variable that changes frequently?

## Q4: Imagine you are leading a design review for a space-deployed system that uses a radiation-hardened FPGA for data processing and a COTS DC-DC converter for the 3.3V rail. The converter's datasheet specifies a maximum output voltage of 3.47V under worst-case conditions, and the FPGA's absolute maximum rating is 3.6V. A junior engineer argues that the 130 mV margin is acceptable because "the FPGA will never actually see 3.47V in practice — the converter will typically output 3.3V, and the FPGA's absolute maximum rating already includes some safety margin." How would you handle this disagreement?

**Answer:** I'd handle this by reframing the discussion from "what will typically happen" to "what could happen under worst-case conditions," because that's the basis for reliable space system design. The engineer's argument conflates two different things: the converter's typical output and its worst-case output. The datasheet specifies 3.47V maximum under worst-case conditions — that includes temperature extremes, input voltage variation, load transients, and component aging. In space, the converter will experience all of these, and the FPGA's absolute maximum rating is not a "safety margin" — it's the limit beyond which damage can occur. I'd walk through the specific worst-case scenarios: at cold temperature, the converter's reference voltage can drift high; at maximum input voltage, the duty cycle changes; under a load transient, the output can overshoot. Any of these could push the output toward 3.47V. I'd also point out that the FPGA's absolute maximum rating is typically specified for a short duration, not continuous operation — running at 3.47V continuously, even if it doesn't immediately destroy the part, can accelerate electromigration and reduce long-term reliability. The margin between 3.47V and 3.6V is only 130 mV, which is less than the typical output ripple of many DC-DC converters — so the FPGA could see voltage spikes above 3.47V even if the average output is 3.3V. My recommendation would be to add margin by either selecting a converter with tighter regulation, adding a post-regulator, or using a voltage supervisor that forces a reset if the rail exceeds a safe threshold. I'd also ask the engineer to calculate the worst-case output voltage including all contributing factors — reference tolerance, feedback resistor tolerance, load regulation, and ripple — and compare that to the FPGA's recommended operating range, not just the absolute maximum. The goal is to have margin at the recommended operating range, not to be barely within the absolute maximum.

**Possible follow-ups:** What if the converter's worst-case output is within the FPGA's recommended operating range but still close to the absolute maximum — how would you decide if that's acceptable? How would you verify the actual worst-case output voltage during testing?

## Q5: How would you approach designing a test plan to verify that a space-deployed system can recover from a single-event functional interrupt (SEFI) that causes the main microcontroller to stop executing code, when you cannot inject actual radiation events during ground testing?

**Answer:** I'd approach this by recognizing that you can't test the radiation event itself, but you can test the system's recovery mechanisms thoroughly by simulating the effects of a SEFI. The key is to identify all the ways a SEFI can manifest — the microcontroller stops executing, the program counter jumps to an invalid address, the watchdog stops being serviced, the stack pointer becomes corrupted, or the processor enters an undefined state — and then inject each of these conditions deliberately. For the "stop executing" case, I'd use a debugger to halt the processor and verify that the external watchdog times out and resets the system. For the "invalid program counter" case, I'd use the debugger to set the PC to an invalid address and verify that the reset mechanism catches it. For the "watchdog not serviced" case, I'd disable the watchdog service routine in firmware and verify that the external watchdog fires. I'd also test the recovery path itself: after reset, does the system reinitialize correctly? Does it restore critical state from non-volatile memory or from redundant copies? Does it resume normal operation without operator intervention? I'd also test edge cases: what happens if the SEFI occurs during a critical operation like a flash write? What if it occurs during boot? What if the reset occurs while the system is communicating with a ground station — does the communication link recover cleanly? I'd use fault injection at the firmware level — deliberately corrupting memory, setting invalid states, and skipping critical instructions — to simulate the broader effects of a SEFI. I'd also test the recovery time: how long does it take from the SEFI to full recovery? Is that within the mission's requirements? Finally, I'd document all the test cases and results so that when the system does experience a real SEFI in flight, we can compare the observed behavior to the tested scenarios and confirm the recovery worked as designed. The limitation is that you can't test every possible manifestation of a SEFI, so the test plan should focus on the most likely and most critical failure modes, and the recovery design should be robust enough to handle unexpected variations.

**Possible follow-ups:** How would you test the recovery mechanism if the SEFI corrupts the reset vector itself? How would you verify that the system doesn't enter a reset loop where it repeatedly resets but never successfully recovers?
