# space-rad-hard — Day 129

## Q1: How would you approach designing a radiation-tolerant, high-reliability power feed for a payload that has two independent 28V bus inputs, where the system must survive a shorted or latched load on one feed without losing the other, and must also handle hot-swap events without disturbing the bus?

**Answer:** I'd start by treating the two feeds as genuinely independent sources that are only combined at the point of load, so a fault on one cannot propagate backward into the other. That means each feed gets its own input protection and its own ORing element — ideal-diode controllers or ORing FETs rather than simple Schottky ORing, because the diode drop and the thermal dissipation in vacuum are both unwelcome. The ORing stage has to be fast enough to block reverse current when one feed collapses, and it needs to tolerate the transient when a latched load drags its feed down.

For the latch-up case specifically, I'd put a current-limiting and latching-current-breaker function between each feed and its downstream loads, sized so that a hard short trips the breaker without the upstream bus sagging below the other feed's operating window. The two feeds should be diode-ORed or FET-ORed into a common downstream rail only after that protection, so a shorted load on feed A is isolated at the breaker and feed B keeps the payload alive. I'd also want the breaker to be resettable or latching-with-telemetry rather than auto-retrying indefinitely, because a persistent SEL will just retry into the same fault.

Hot-swap is a separate problem: inrush into the bulk capacitance on the payload side has to be controlled with a slew-rate-limited hot-swap controller and a defined dV/dt, plus a current limit that's above the steady-state load but below what would disturb the bus. The hot-swap FET also needs SOA analysis for the worst-case inrush event, and the controller needs to ride through a hot-plug without nuisance trips. I'd verify the whole thing with a test that shorts one feed while the other is loaded, and a separate test that hot-plugs a fully discharged payload onto a live bus while monitoring bus droop.

**Possible follow-ups:** How would you decide the trip threshold and response time of the breaker so it doesn't nuisance-trip on legitimate inrush but still catches a SEL? What telemetry would you want from each feed to distinguish a latched load from a genuine overcurrent?

## Q2: You're reviewing a design where a junior engineer has proposed using a single commercial LDO with no radiation data to post-regulate a critical analog rail, arguing that the upstream DC-DC is already rad-tolerant so "the LDO doesn't matter." How would you evaluate this argument?

**Answer:** The argument has a real kernel of truth — the upstream converter being rad-tolerant does remove a lot of the risk — but it conflates "the input is clean" with "the regulator is safe." The LDO is still an active semiconductor in the radiation environment, and it has its own failure modes: total ionizing dose can shift its reference and its dropout behavior over mission life, enhanced low-dose-rate sensitivity can make the degradation worse at the low dose rates actually seen in orbit than in a high-dose-rate test, and a single-event transient on the pass transistor or the error amplifier can put a glitch directly onto the analog rail. A single-event latch-up in the LDO is also possible and would drag the rail down or crowbar it.

So the question I'd put back to the engineer is: what is the LDO actually protecting against, and what protects the LDO? If the analog rail feeds a precision measurement, a TID-induced reference drift in the LDO is indistinguishable from sensor drift unless there's a calibration path, and a SET on the rail during a conversion is a corrupted sample. I'd want either a part with at least some radiation characterization, or a topology that tolerates the LDO misbehaving — for example, a redundant LDO with a comparator that switches over, or a shunt reference for the critical node that's independent of the LDO's reference. At minimum I'd want the LDO's failure modes analyzed in the FMEA and a test plan that exercises TID drift and SET injection on that rail.

The framing I'd use in review is not "you're wrong" but "the upstream being rad-tolerant changes the probability, not the consequence — and the consequence on a critical analog rail is a silent measurement error, which is the worst kind." That usually gets the engineer to do the analysis rather than defend the shortcut.

**Possible follow-ups:** If the LDO has no radiation data at all, what would you do short of a full TID test — what analysis or architecture would let you fly it? How would you detect in-flight that the LDO's reference has drifted?

## Q3: How would you approach designing a memory scrubbing strategy for an SRAM-based FPGA in a space application, and what trade-offs would you weigh?

**Answer:** The starting point is that scrubbing is only meaningful if you know what you're scrubbing and why. For an SRAM-based FPGA, configuration memory upsets are the dominant concern because a single flipped configuration bit can change the function of a logic cell or a routing resource, and unlike a data upset it persists until it's overwritten. So the scrubber's job is to periodically read back the configuration memory, compare against a golden image, and correct any discrepancies — either by rewriting the affected frame or by triggering a partial or full reconfiguration.

The trade-offs are the interesting part. Scrub rate versus availability: scrubbing consumes configuration port bandwidth and can momentarily disturb the logic if you're not careful about which frames you touch, so you have to decide whether to scrub continuously in the background or in bursts during idle windows. Blind scrubbing versus readback-and-compare: blind scrubbing is simpler and faster but rewrites everything whether it needs it or not, which increases the exposure window on the configuration port; readback-and-compare is more surgical but needs a trusted golden image and a comparison engine, and the comparison itself has to be robust against upsets in the scrubber's own memory. Granularity: frame-level versus block-level versus full-device, which trades recovery latency against overhead.

I'd also want to think about what happens when scrubbing can't keep up — if the upset rate exceeds the scrub rate, you need a fallback, which is usually a full reconfiguration from a known-good source, and that source (flash) has its own upset problem. And I'd want the scrubber itself to be simple and independently verifiable, ideally in a rad-hard companion device or a hardened region of the FPGA, because a scrubber that gets upset is worse than no scrubber. Finally, I'd want telemetry on scrub events — how many corrections per unit time — because that's the best in-flight indicator of the actual upset rate and whether the margin is holding.

**Possible follow-ups:** How would you protect the golden image itself from corruption? What would you do if the scrubber reports a rising correction rate that suggests the environment is worse than the design case?

## Q4: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt (SEFI) that leaves the processor still drawing current and still toggling a heartbeat line, but no longer executing the control loop?

**Answer:** The hard part here is that the failure mode is specifically designed to defeat the naive detection — the processor looks alive, so a simple "is it drawing current" or "is the heartbeat toggling" check passes. So the test plan has to verify that the recovery mechanism detects loss of *function*, not loss of *liveness*.

I'd structure it in layers. First, define what "executing the control loop" observably means — a sequence counter that increments only when the loop completes, a checksum over the loop's outputs, a watchdog kick that's tied to loop completion rather than to a timer interrupt. Then build a fault-injection harness that can force the processor into the SEFI state on demand: halt the core in a debugger, or better, inject a fault that leaves the core running but stuck in a loop that still toggles the heartbeat GPIO. The point is to reproduce the exact signature — current draw normal, heartbeat toggling, loop dead — so the test is honest.

Then verify each layer of the recovery chain independently and then together: the functional watchdog fires within its specified window; the reset is asserted and released cleanly; the processor reinitializes and the loop resumes; the system state is restored to a safe value rather than resuming from corrupted state; and the event is logged with enough context to diagnose it later. I'd also test the boundary conditions — what if the SEFI happens during the recovery itself, what if it happens during initialization, what if the watchdog itself is upset. And I'd run it many times, because a recovery mechanism that works once but has a race is worse than none.

The other thing I'd insist on is that the test be runnable without a particle beam, because you can't schedule beam time for every regression. A debugger-driven or firmware-injected SEFI is the workhorse; beam time is for validating that the injected fault is representative.

**Possible follow-ups:** How would you design the functional watchdog so it can't be defeated by the same SEFI that kills the loop? What would you log on a SEFI recovery, and how would you get that log off a system that just reset?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** The first thing I'd do is separate the person from the proposal in my own head, and then make that separation visible in the room. The engineer has done real work, and the fastest way to lose the review is to make them feel like the work was wasted. So I'd start by having them walk through the analysis they did — what environment they assumed, what part data they used, what margin they calculated — and I'd listen for where the assumption diverges from the design case rather than jumping to the conclusion.

Usually the disagreement isn't "you're wrong," it's "you used a different environment or a different part data set than the one the program is actually designing to." If that's the case, the fix is to make the assumption explicit and let the numbers speak: put the assumed environment, the part's characterized limits, and the resulting margin side by side, and ask whether the margin is adequate for the consequence of the failure. If the engineer's analysis holds up under the correct assumptions, I should be the one updating my view — that's the review working.

If the margin really is thin, I'd frame it as a risk decision rather than a correctness decision: here's the consequence if the part degrades or upsets, here's the cost of the more robust option, here's what the program's risk posture is. That moves it from "senior engineer overrules junior engineer" to "team makes an informed trade." And I'd make sure the decision and its rationale get recorded, so it's not relitigated and so the engineer gets credit for the analysis either way.

The behavioral piece I'd watch in myself is not to use seniority as the argument. If I can't articulate the technical reason the margin is inadequate, I don't have a review comment — I have a preference, and I should say so and let the team decide.

**Possible follow-ups:** What would you do if the engineer's analysis was correct but the program can't afford the more robust option? How do you make sure a junior engineer feels safe raising a disagreement with you in the other direction?
