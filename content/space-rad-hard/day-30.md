# space-rad-hard — Day 30

## Q1: How would you approach designing a fault-tolerant analog output stage for a space-deployed system where a single-event transient (SET) on a DAC's reference voltage could cause a momentary but dangerous output spike to an actuator?
**Answer:** I'd approach this from three layers: circuit-level mitigation, system-level monitoring, and fail-safe actuation. At the circuit level, I'd add a low-pass filter between the reference and the DAC's reference input, sized to attenuate transients in the expected SET pulse-width range (typically nanoseconds to microseconds) without degrading the DAC's settling time for legitimate updates. I'd also consider a reference buffer with a large bypass capacitor to hold the reference voltage stable during a transient. However, filtering alone can't eliminate all risk, so I'd add output-side protection: a window comparator on the DAC output that detects excursions beyond a safe range and triggers a fast crowbar or series switch to disconnect the actuator. This needs to be an analog, hardware-only path — not dependent on firmware — because firmware may be affected by the same radiation event. Finally, the actuator itself should have a fail-safe state: if the drive signal is removed or the output is clamped, the actuator should default to a safe position (e.g., spring-return valve, brake engaged). I'd also consider redundancy — two DAC channels with cross-monitoring, or a voting scheme — if the actuator is critical enough to justify the cost. The key trade-off is between response speed and false-trip immunity: the window comparator must be fast enough to catch a real SET but not so fast that normal transient behavior during legitimate output changes triggers a spurious shutdown.

**Possible follow-ups:** How would you determine the appropriate filter cutoff frequency for the reference? What if the actuator requires a continuous analog signal and cannot tolerate being disconnected?

## Q2: You are reviewing a design for a space-deployed system that uses a radiation-hardened FPGA and a COTS precision voltage reference for an ADC. The reference's datasheet specifies initial accuracy of ±0.1% and temperature drift of ±20 ppm/°C, but has no radiation data. The designer argues that because the reference is "precision" and the system has a calibration routine, radiation-induced drift can be calibrated out. How would you evaluate this approach?
**Answer:** I'd push back on the assumption that calibration can fully compensate for radiation-induced drift. Calibration is effective for static, predictable errors — initial offset, gain error, and temperature drift that follows a known curve. But radiation-induced drift in a voltage reference is not necessarily monotonic or predictable over time. Total ionizing dose (TID) effects can cause gradual parametric shifts, but the rate and direction of drift depend on the specific part's internal technology and bias conditions, and single-event transients (SETs) can cause sudden, momentary excursions that calibration cannot address at all. A calibration routine performed at power-up or periodically would capture the cumulative drift at that moment, but it cannot correct for drift that occurs between calibrations, nor for transient events. I'd also note that the calibration routine itself relies on a reference — if the system's calibration reference is the same drifting part, the calibration is circular. My recommendation would be: first, check if there's any radiation data for the part family from the manufacturer or from published test reports — many precision references have been characterized even if not formally qualified. If no data exists, I'd treat the reference as a risk item and consider alternatives: a radiation-characterized reference, a reference with known TID performance, or a design that uses a ratiometric measurement approach where the ADC reference and the sensor excitation share the same reference, making the measurement insensitive to absolute reference drift. If the COTS part must be used, I'd require radiation testing of a sample lot, and I'd add a secondary, known-good reference on the board that can be used to periodically verify and correct the primary reference's drift.

**Possible follow-ups:** What if the system has two independent references and the calibration routine cross-checks them — would that change your assessment? How would you design a ratiometric measurement to eliminate reference drift sensitivity?

## Q3: How would you approach designing a radiation-tolerant firmware update strategy for a space-deployed system where the application firmware resides in flash memory that is susceptible to single-event upsets, and a corrupted update could render the system unrecoverable?
**Answer:** The core principle is that the update path must never be the single point of failure — the system must always retain a known-good boot capability. I'd structure the firmware memory as at least two regions: a small, immutable bootloader in protected memory (ideally radiation-hardened or write-protected by hardware) and at least two application image slots (A/B partitioning). The bootloader's job is minimal: validate the application image (checksum or signature), select the valid image, and jump to it. During an update, the new image is written to the inactive slot, validated, and then the boot flag is flipped. If validation fails, the old image remains intact and the system boots from it. For radiation-induced corruption of the stored images, I'd add periodic background scrubbing: read the active image, verify the checksum, and if a single-bit error is detected, correct it in place (if the flash supports it) or mark the image as degraded. If the active image becomes unrecoverable, the bootloader falls back to the backup image. For the update process itself, I'd use a multi-stage approach: download the image to RAM first, validate it there, then write to flash. This prevents a partial flash write from corrupting the active image. I'd also add a "golden image" concept — a third, immutable copy of the most recent known-good firmware that can be restored if both A and B images are corrupted. The trade-off is flash space versus robustness: more image slots and more redundancy consume memory, so the number of slots should be driven by the mission criticality and the expected upset rate. Finally, the update protocol itself needs error detection and retransmission — a corrupted command stream should never trigger a partial update.

**Possible follow-ups:** How would you handle the case where the bootloader itself is in flash that can be corrupted? What checksum or signature scheme would you use, and how would you protect the signing key?

## Q4: Imagine you are leading a design review for a space-deployed system that uses a radiation-hardened FPGA for data processing and a COTS microcontroller for housekeeping. The microcontroller has a built-in watchdog timer that the firmware enables during initialization. The designer argues that the internal watchdog is sufficient and no external watchdog is needed. How would you handle this disagreement?
**Answer:** I'd acknowledge that the internal watchdog provides a baseline level of protection, but I'd explain why it's insufficient as the sole recovery mechanism in a radiation environment. The concern is common-cause failure: a single-event effect that disrupts the microcontroller's clock, power, or internal logic can also disable or defeat the internal watchdog. For example, a single-event functional interrupt (SEFI) might halt the CPU core while leaving the watchdog timer running — the watchdog would still fire, which is good — but a more subtle failure could corrupt the watchdog's configuration registers, disabling it entirely, or a clock glitch could cause the watchdog to count incorrectly. The internal watchdog also shares the same power domain and the same silicon — a latch-up event that disrupts the microcontroller's power supply will affect the watchdog equally. An external watchdog provides diversity: it's a separate part, likely on a separate power rail, with independent timing. It can also monitor things the internal watchdog cannot, such as whether the microcontroller is executing the expected code path (via a windowed watchdog or by requiring a specific sequence of kick commands) rather than just toggling a GPIO. My recommendation would be to use both: the internal watchdog as a first line of defense and an external watchdog as a backstop. The external watchdog should be a simple, radiation-characterized or at least radiation-tolerant part, with a timeout long enough to avoid false trips during legitimate long operations but short enough to recover from a hang in a reasonable time. I'd also add a hardware reset path that the external watchdog can trigger, independent of the microcontroller's own reset logic. The cost is small — one additional IC and a few passive components — compared to the risk of an unrecoverable hang in a mission-critical system.

**Possible follow-ups:** What if the external watchdog is also a COTS part with no radiation data — how would you qualify it? How would you set the watchdog timeout to avoid false trips during legitimate long operations?

## Q5: How would you approach designing a fault-tolerant clock distribution network for a space-deployed system that uses multiple FPGAs and ADCs requiring synchronized sampling?
**Answer:** Clock distribution is a classic common-mode failure point — if the clock fails or is corrupted, every device downstream is affected simultaneously. I'd start by identifying the synchronization requirements: what is the acceptable skew between ADC sampling instants, and what is the maximum clock jitter that still meets the system's signal-to-noise requirements? These drive the architecture. For a system with multiple FPGAs and ADCs, I'd consider a tree topology: a single master oscillator (ideally radiation-hardened or at least radiation-characterized) feeding a clock buffer or fan-out chip that distributes to each device. The buffer provides isolation — a single-event transient on one output doesn't propagate to the others. For redundancy, I'd use two oscillators with automatic or manual switchover: a secondary oscillator that can be selected if the primary fails or drifts out of spec. The switchover logic needs to be glitch-free to avoid generating runt pulses on the clock lines. At the board level, I'd route clock traces as controlled-impedance lines with proper termination, and I'd keep clock routing away from high-current switching circuits to minimize noise coupling. For the ADCs specifically, I'd consider whether true simultaneous sampling is required or whether the ADCs can sample with a known, fixed offset that can be corrected in post-processing — this gives more flexibility in the clock distribution. I'd also add clock monitoring: a simple frequency or phase detector that can flag a clock that has drifted or stopped, triggering the switchover or a system alert. The key trade-off is between a single, simple clock source (fewer parts, less complexity, but a single point of failure) versus a redundant, more complex distribution (more parts, more failure modes to analyze, but better fault tolerance). For a mission-critical system, I'd lean toward redundancy with careful analysis of the switchover behavior.

**Possible follow-ups:** How would you handle the case where the two oscillators drift apart over time due to TID effects? How would you verify that the clock switchover is glitch-free during ground testing?
