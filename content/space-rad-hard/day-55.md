# space-rad-hard — Day 55

## Q1: How would you approach designing a latch-up protection scheme for a mixed-signal board where the sensitive analog front-end and the digital processing section share a common 3.3V rail, and a single-event latch-up in either section could drag the whole rail down?

**Answer:** The core problem is that a shared rail couples the failure of one domain into the other, so the first design decision is whether the two domains should really share a rail at all. If the analog front-end has tight noise requirements and the digital section has large transient currents, separating them — even from the same upstream converter — gives you independent current limiting and lets you isolate a latch-up event to one domain. From there, the standard approach is per-domain current limiting rather than a single bulk limit: a latch-up is a low-impedance, self-sustaining overcurrent condition, so the protection has to sense current fast enough to act before the die overheats, and it has to act locally so that tripping one domain doesn't remove power from the other.

In practice I'd think about three layers. First, a current-limited load switch or eFuse per domain, with the trip threshold set above the worst-case inrush and transient demand but below the level that would damage the part — and with a latch-up recovery strategy, which usually means a timed power cycle rather than a latching shutdown, because the latch persists until power is removed. Second, the upstream converter itself should be chosen or configured so that its own current limit is coordinated with the downstream switches — you don't want the converter folding back before the local switch has had a chance to trip, or vice versa. Third, at the layout level, guard rings and substrate/well ties around sensitive analog devices reduce the collection efficiency for the charge that initiates the latch, and keeping the analog and digital return paths separate until a single star point limits how much of a digital transient couples into the analog domain.

The trade-off is that every added series element costs you headroom and efficiency, and a current-limit threshold that's too tight will nuisance-trip on legitimate transients. So the threshold has to be derived from the actual load profile, not guessed, and the recovery behavior has to be defined up front — does the domain come back automatically, does it need a command, and how does the rest of the system know it went away?

**Possible follow-ups:**
- How would you coordinate the trip thresholds between the upstream converter and the per-domain switches so that you don't get an ambiguous shutdown?
- If the analog domain is the one that latches, how do you keep the digital section from misinterpreting the resulting supply droop as a valid sensor reading?

## Q2: You're reviewing a design where a junior engineer has proposed using a single commercial LDO with no radiation data to post-regulate a critical analog rail, arguing that the upstream DC-DC is already rad-tolerant so "the LDO doesn't matter." How would you evaluate this argument?

**Answer:** The argument conflates two different things: the radiation tolerance of the upstream converter and the radiation behavior of the LDO itself. A rad-tolerant DC-DC protects the system from the converter failing; it does nothing to protect the LDO from TID-induced parameter drift, SETs on its internal reference or error amplifier, or SEL in its pass element. So the upstream tolerance is necessary but not sufficient.

The evaluation I'd want to do is component-level. First, what does the LDO actually do in this signal chain? If it's post-regulating a rail that feeds a precision ADC reference or an analog front-end, then its output accuracy, noise, and transient response directly set the measurement floor — and those are exactly the parameters that drift under TID and that can be momentarily corrupted by an SET. A part with no radiation data isn't "probably fine"; it's uncharacterized, which means the risk is unknown rather than low. Second, what's the failure mode if the LDO does drift or glitch? If the answer is "the measurement is wrong but the system notices and flags it," that's a different risk posture than "the control loop acts on a corrupted value." Third, is there a path to characterizing it — a low-dose-rate test, a proton test, or at minimum a review of the process technology and any published data on similar parts from the same fab?

The recommendation would depend on the criticality. For a non-critical housekeeping rail, a COTS LDO with a documented rationale and a mitigation (redundant measurement, plausibility check) might be acceptable. For a rail that sets measurement accuracy, I'd push for either a part with radiation data or a design that doesn't depend on the LDO's absolute accuracy — for example, ratiometric measurement against the same reference, or a calibration scheme that can detect drift. The key point is that "the upstream part is rad-tolerant" is not a reason to skip the analysis on the downstream part.

**Possible follow-ups:**
- How would you decide whether a given rail is critical enough to justify the cost of a rad-characterized regulator?
- If you can't find a rad-hard LDO that meets the noise requirement, what design alternatives would you consider?

## Q3: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt that puts the main processor into a state where it's still drawing current and still toggling a heartbeat line, but no longer executing the control loop?

**Answer:** The hard part of this scenario is that the usual recovery mechanism — an external watchdog that expects a periodic toggle — is defeated, because the processor is still toggling. So the test plan has to verify recovery from a failure mode that looks, from the watchdog's point of view, like normal operation. That means the test has to inject the fault in a way that reproduces the "alive but not working" state, and it has to verify that whatever secondary mechanism you've designed actually catches it.

The first thing I'd do is define what "not working" means observably. If the control loop has a known output cadence, or if it writes a sequence number or timestamp to a shared location, then the recovery mechanism can be based on that rather than on a bare heartbeat. The test plan then needs to verify that the mechanism trips when the sequence stops advancing, even though the heartbeat continues. On the ground, without a radiation source, you can inject this by halting the control task in a debugger while leaving the heartbeat task running, or by corrupting the state that the control loop depends on so that it spins without producing output. The point is to reproduce the *observable signature* of the SEFI, not the physical cause.

The test plan should cover: (1) the fault is injected, (2) the secondary mechanism detects it within the specified window, (3) the recovery action (reset, task restart, or power cycle) executes, (4) the system returns to a known-good state and the control loop resumes, and (5) the event is logged so you can tell it happened. I'd also test the boundary cases — what if the fault occurs during the recovery itself, what if two processors fault at once, what if the fault occurs during a critical write. And I'd want to verify that the recovery doesn't itself cause a hazardous output transient, which is often the real risk in a control system.

**Possible follow-ups:**
- How would you distinguish, in the logs, between a genuine SEFI and a software bug that produces the same signature?
- If the recovery mechanism is a full power cycle, how do you bound the time the system is out of service, and is that acceptable for the mission?

## Q4: How would you approach derating for a space-deployed board, and how does derating interact with the radiation tolerance you're trying to achieve?

**Answer:** Derating is the practice of operating a part below its rated limits — voltage, current, power, junction temperature, and often frequency — to buy margin against the combined effects of manufacturing spread, aging, and the environment. In a space application the environment includes radiation, and that's where the interaction gets interesting: radiation effects and derating aren't independent, they compound.

Take TID. A part's parametric drift under total dose is often worse at higher bias and higher temperature, so a part that's derated on voltage and junction temperature may survive a higher total dose than the same part run at its rated limits. That means derating isn't just about reliability margin in the conventional sense — it's a lever you can use to extend the radiation tolerance of a part that's marginal on paper. The reverse is also true: a part that looks fine on a derating table can fail its radiation requirement if the derating analysis didn't account for the fact that the parameter you derated (say, output drive) is the one that degrades most under dose.

The practical approach is to derate against the *worst-case post-irradiation* parameters, not the datasheet typicals. That means for any part where you have radiation data, you derate from the post-irradiation limits; for parts without data, you either characterize them or you apply a conservative margin and document the assumption. Junction temperature derating matters more in vacuum because the only heat path is conduction, so the thermal margin you thought you had on a bench may not exist on orbit. And for anything with a known single-event sensitivity, derating voltage reduces the SEL cross-section, which is a real and useful mitigation — but it doesn't eliminate the need for current limiting, because derating reduces probability, not consequence.

**Possible follow-ups:**
- How would you handle a part where the post-irradiation datasheet limits aren't published, only typicals?
- Where does derating stop being useful and start being a substitute for proper part selection?

## Q5: You're leading a design review and a junior engineer has proposed a power architecture you believe is under-margined for the radiation environment. The engineer has done real analysis and is confident. How would you handle the disagreement so the review stays constructive and the right decision gets made?

**Answer:** The first thing I'd do is separate the technical question from the interpersonal one. The engineer has done real work, which means the analysis is probably internally consistent — the disagreement is likely about assumptions, not arithmetic. So the productive move is to find the assumption where we diverge, rather than to assert that the conclusion is wrong. That keeps it about the design and not about who's right.

In practice that means asking questions rather than making statements. "What radiation environment did you assume for this rail?" "What's the failure mode if the part drifts past its spec?" "What's the consequence if this rail glitches during a critical measurement?" Those questions either surface an assumption I disagree with — in which case we can argue about the assumption with evidence — or they surface something the engineer hadn't considered, in which case the engineer usually updates their own position. Either way the review moves forward.

If we still disagree after that, I'd want to make the disagreement explicit and decidable: what evidence would change each of our minds, and can we get it? Sometimes the answer is a test, sometimes it's a datasheet the engineer hadn't seen, sometimes it's a precedent from a previous program. If it can't be resolved with evidence in the time available, then it becomes a risk decision, and risk decisions belong to whoever owns the program risk — so I'd frame it that way rather than as a technical veto. And I'd be explicit that the goal is a design that survives the environment, not a design that wins the argument. A review where the junior engineer feels heard and the decision is documented is worth more than one where I overrule them and they stop raising concerns.

**Possible follow-ups:**
- What would you do if the engineer's analysis was correct but the program schedule didn't allow the fix?
- How do you make sure a decision like this gets documented so it doesn't get relitigated later?
