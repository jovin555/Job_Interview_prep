# space-rad-hard — Day 112

## Q1: How would you approach designing a radiation-tolerant, high-reliability power feed for a payload that has two independent 28V bus inputs, where the system must survive a shorted or latched load on one feed without losing the other, and must also handle hot-swap events without disturbing the bus?
**Answer:** I'd start by treating the two feeds as genuinely independent domains rather than assuming they'll behave symmetrically. Each feed gets its own input protection stage — reverse-polarity protection, transient suppression, and a fuse or electronic breaker sized to the feed's fault current — so a fault on one feed can't propagate backward into the other. The two feeds then combine through an ORing stage: either ideal-diode controllers or Schottky ORing, with the choice driven by efficiency and reverse-leakage requirements. The key architectural decision is where to draw the boundary between "shared" and "isolated." I'd keep the ORing point as far downstream as practical so each feed retains its own protection and filtering, and I'd make sure the ORing stage itself can't fail short and couple the two feeds together. For hot-swap, the concern is inrush into the bulk capacitance when a feed is inserted or a breaker re-closes. I'd use a hot-swap controller with programmable current slew and a dV/dt-limited gate drive, plus a soft-start that ramps the load rather than stepping it. I'd also add a latch-up detection path: a current-sense comparator that trips the electronic breaker on a sustained overcurrent, with a retry policy that distinguishes a transient inrush from a true latch. The retry policy matters — a naive auto-retry can oscillate against a latched load and disturb the bus, so I'd want either a timed retry with backoff or a latch-off that requires a command to re-enable, depending on criticality. Throughout, I'd verify the design against the actual bus transient environment, not just steady-state, because the hot-swap event is where the two feeds interact most.
**Possible follow-ups:** How would you decide between a latch-off and an auto-retry policy for a load that's critical to the mission? What would you do if the ORing controller itself is a COTS part with no radiation data?

## Q2: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt (SEFI) that leaves the processor still drawing current and still toggling a heartbeat line, but no longer executing the control loop?
**Answer:** The defining feature of this failure mode is that the usual "is it alive?" indicators lie — current draw and a heartbeat GPIO both look normal, so a naive watchdog that just checks the heartbeat will never fire. I'd start by defining an observable that's causally tied to the control loop actually running, not just to the processor being powered. That could be a counter that the control loop increments and that the supervisory logic reads and compares against a deadline, or a sequence of expected outputs that only a running loop would produce. The test plan then needs to inject the SEFI condition without radiation. On a bench, I'd use a debugger or a fault-injection hook to freeze the control loop while leaving the heartbeat task and the main clock running — that reproduces the exact signature. I'd verify three things: that the supervisory logic detects the stalled loop within the required time, that the recovery action (reset, re-init, or switchover) actually restores control, and that the recovery doesn't itself depend on the stalled processor. I'd also test the boundary cases — a loop that's slow but not stalled, a heartbeat that stops but the loop continues, and a recovery that races with a second fault. For radiation testing specifically, I'd plan beam time around capturing the SEFI signature and confirming the detector fires, but I'd rely on fault injection for the bulk of the coverage because beam time is expensive and non-deterministic.
**Possible follow-ups:** How would you design the supervisory logic so it doesn't share a failure mode with the control loop it's watching? What's the risk of making the detection deadline too tight?

## Q3: How would you approach selecting and qualifying a voltage supervisor or reset IC for a space-deployed system, given that most commercial parts are not radiation-characterized?
**Answer:** I'd frame this as a risk-allocation problem rather than a part-hunting problem. First I'd ask what the supervisor actually has to guarantee: a threshold accuracy over temperature and life, a reset pulse width, and — critically — that it doesn't false-trigger or fail to assert under radiation. Then I'd look at what radiation data exists, even indirectly: has the manufacturer or a third party published TID or SEE results, is the part built on a process with known behavior, is there a QML or EPPL listing? If there's no data at all, I'd consider whether the function can be moved to a rad-hard supervisor, or implemented in a way that's inherently more tolerant — for example, a supervisor built from a rad-hard comparator and reference rather than a single COTS IC. Where a COTS part is unavoidable, I'd bound the risk: characterize a sample lot at a facility if budget allows, add margin to the threshold so TID drift doesn't cross the load's operating window, and design the reset path so a failed supervisor degrades to a safe state rather than a silent no-reset. I'd also look at whether the supervisor's output stage can latch or float under SEE, because a reset line that goes high-impedance is worse than one that sticks low. Finally, I'd document the residual risk explicitly — what happens if the part drifts, what the detection coverage is — so the decision is traceable rather than implicit.
**Possible follow-ups:** How would you bound the risk if you can't afford radiation testing on the COTS supervisor? What's the argument for building the supervisor from discrete rad-hard parts versus using a single COTS IC?

## Q4: You're reviewing a design where a junior engineer has proposed using a single commercial LDO with no radiation data to post-regulate a critical analog rail, arguing that the upstream DC-DC is already rad-tolerant so "the LDO doesn't matter." How would you evaluate this argument?
**Answer:** The argument has a real kernel — the upstream converter being rad-tolerant does remove some of the risk — but it conflates two different things: the LDO's ability to survive radiation, and the LDO's ability to keep the analog rail within spec while it does so. The upstream DC-DC being tolerant says nothing about the LDO's own TID-induced reference drift, its SET response, or its SEL susceptibility. For a critical analog rail, the failure mode I care about most is a slow drift that stays inside the LDO's "working" range but pushes the rail out of the ADC's accuracy budget — that's a silent degradation, not a hard failure, and it's exactly the kind of thing a calibration routine may not catch if the drift is monotonic. I'd ask the engineer to show me the error budget: what's the allowed rail tolerance, what does the LDO contribute over TID, and what's the margin left for everything else? If the answer is "we don't know because there's no data," that's the gap. I'd also probe the SET path — a transient on the LDO's reference or pass element can couple straight into the analog rail, and the upstream converter's tolerance doesn't help there. My recommendation would likely be either to move the post-regulation to a rad-hard LDO or to a discrete rad-hard reference-plus-pass topology, or to add enough filtering and margin that the LDO's unknown drift can't cross the accuracy budget — and to document which of those we chose and why.
**Possible follow-ups:** How would you structure the error budget to make the LDO's unknown contribution visible? What would change your mind and make the COTS LDO acceptable?

## Q5: How would you approach designing a radiation-tolerant analog signal chain for a spacecraft instrument where the sensor output is a low-level differential signal, and both the amplifier front-end and the ADC reference can experience single-event transients (SETs)?
**Answer:** I'd treat the front-end and the reference as two separate SET entry points and design mitigation for each, because they fail differently. On the amplifier side, a low-level differential signal means the SET has to be large relative to the signal to matter, but the amplifier's gain means a small transient at the input can become a large one at the output. I'd start with the topology: a differential front-end with good common-mode rejection helps reject transients that couple common-mode, and I'd keep the signal path as short and as low-impedance as the sensor allows so there's less loop area to pick up transients. I'd add bandwidth limiting after the amplifier — an RC or active filter with a corner set by the measurement bandwidth, not by convenience — so a fast SET is attenuated before it reaches the ADC's sample-and-hold. On the reference side, the concern is that a transient on the reference corrupts the conversion of every channel sharing it, so I'd either use a separate buffered reference per critical channel or add a reference filter with a time constant long enough to ride through a transient but short enough to settle within the sampling budget. I'd also consider whether the ADC's own sample-and-hold can be protected by a series resistor and a small capacitor that limits the transient's energy. Throughout, I'd want to know the SET cross-section and pulse width the parts are expected to see, because the filter design depends on whether I'm defending against nanosecond transients or microsecond ones — and if there's no data, I'd design for the worst plausible case and verify with fault injection.
**Possible follow-ups:** How would you decide the filter corner frequency without over-filtering the measurement bandwidth? What's the trade-off between per-channel references and a single shared reference?
