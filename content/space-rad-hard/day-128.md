# space-rad-hard — Day 128

## Q1: How would you approach designing a radiation-tolerant power distribution scheme for a payload where several loads share a common upstream rail, and a single-event latch-up (SEL) in any one load must not collapse the rail for the others — and how would you decide where to draw the boundary between "shared" and "isolated"?

**Answer:** The core principle is that the shared rail should be a *source*, not a *victim* — nothing downstream should be able to pull it out of regulation. I'd start by partitioning loads by criticality and by their credible fault modes, then place a current-limiting or latching protection element at each branch point so that a fault in one branch is contained to that branch.

Concretely, the architecture usually looks like: a primary bus → a main fuse/breaker or current-limited hot-swap controller → a shared regulated rail → per-load branch protection (eFuse, current-limited load switch, or a latching current limiter) → the load. The branch protection must do two things: limit steady-state current to a value the upstream rail can supply without drooping below the minimum input of the other loads, and *latch off* rather than thermally cycle, so a persistent SEL doesn't repeatedly hammer the rail. A retry policy (e.g., a few retries with backoff, then latch off and report) is often better than infinite auto-retry, because a hard SEL will just re-trigger.

The boundary decision is a trade study, not a rule. I'd draw the line where the cost/complexity of isolation is justified by (a) the criticality of the *other* loads on that rail, (b) the credible fault current of the load versus the rail's source capability, and (c) whether the load has its own internal protection. Loads that are themselves radiation-tolerant and well-behaved can share a branch; a COTS-heavy or high-current load gets its own protected branch. I'd also consider whether the shared rail needs a "crowbar" or foldback response versus a hard latch, and whether the branch protection device itself is radiation-characterized — a protection device that upsets open is as bad as one that fails short.

Finally, I'd verify the scheme against the actual SEL current profile, not just steady-state: an SEL can present as a near-short with a fast di/dt, so the branch protection's response time and the rail's bulk capacitance have to be co-designed so the transient doesn't droop the shared rail below the other loads' brownout threshold.

**Possible follow-ups:** How would you decide between a latching current limiter and a resettable fuse for a branch, given that neither may be radiation-characterized? What would you do if the branch protection device itself is a COTS part with no SEL data?

## Q2: How would you approach designing a fault-tolerant boot sequence for a space-deployed system that uses an SRAM-based FPGA with external configuration memory (flash), where both the FPGA configuration bitstream and the flash memory are susceptible to single-event upsets?

**Answer:** The boot path is a chain of trust that has to survive corruption at every link, so I'd design it as a layered recovery scheme rather than a single "load and go" sequence.

First, the bitstream in flash needs integrity protection independent of the FPGA: a CRC or hash over the configuration image, checked by a small, radiation-tolerant boot controller (a rad-hard CPLD, a rad-hard MCU, or a hardened portion of the FPGA fabric that comes up first) before the FPGA is allowed to configure. If the primary image fails its check, fall back to a redundant copy in a separate flash region — ideally a separate device or at least a separate erase block with independent error correction — and if that fails, fall back to a known-good "golden" image that is write-protected.

Second, the FPGA configuration itself needs to be monitored after load. SRAM-based FPGAs are vulnerable to configuration upsets during operation, so I'd use the device's built-in configuration error detection (frame ECC or CRC) where available, plus periodic readback and comparison against the golden image, with a scrub or reload on mismatch. The scrub rate is a trade against bus bandwidth and power; a full reload is the last resort.

Third, the boot controller must be able to *reset and re-drive* the FPGA configuration port even if the FPGA is in a bad state — including the case where the FPGA refuses to accept a new bitstream until power-cycled. That means the boot controller needs control of the FPGA's power or its PROGRAM/INIT pins, and the sequence needs a bounded retry count with escalation (reload → power-cycle → golden image → safe mode).

Finally, I'd make the whole sequence observable: log which image was used, how many retries, and any CRC failures to telemetry, so a ground operator can distinguish "recovered cleanly" from "limping on the golden image."

**Possible follow-ups:** How would you protect the golden image from being overwritten by a corrupted update? What's the trade-off between scrubbing frequency and the risk of a scrub itself being interrupted by an upset?

## Q3: You're reviewing a design where a junior engineer has proposed using a single commercial LDO with no radiation data to post-regulate a critical analog rail, arguing that the upstream DC-DC is already rad-tolerant so "the LDO doesn't matter." How would you evaluate this argument?

**Answer:** The argument has a kernel of truth — a clean upstream rail reduces the LDO's stress — but it conflates *input quality* with *the LDO's own radiation response*, and those are independent failure modes. I'd walk through them explicitly.

First, TID: an uncharacterized LDO can drift in output voltage, reference, and dropout over dose, and the drift is not bounded by the upstream converter's tolerance. A rad-tolerant DC-DC feeding an LDO that shifts 3% over mission life still gives you a 3% shift on the analog rail. For a critical analog rail feeding an ADC reference or a sensor front-end, that drift may be exactly the error budget you can't afford.

Second, SEE: the LDO's pass element and control loop can experience SETs that produce output transients, and the error amplifier can latch or the bandgap reference can glitch. A rad-tolerant upstream converter does nothing to prevent an SET *inside* the LDO from reaching the load. Whether that matters depends on the load's tolerance to transients and whether downstream filtering attenuates them — but "the upstream is fine" is not an argument that the LDO is fine.

Third, SEL: the LDO is a candidate latch-up site in its own right, and if it latches, the upstream converter's protection may or may not catch it depending on the current limit and the LDO's latch current.

So my evaluation would be: what is the LDO actually protecting against, and what does the load need? If the LDO is purely a noise filter and the load can tolerate its drift and transients, the risk may be acceptable with mitigation (downstream filtering, a clamp, a monitored rail with a comparator). If the LDO is setting the accuracy of a critical measurement, I'd want either a radiation-characterized part, a topology that removes the LDO from the accuracy path (e.g., a filtered divider from a characterized reference), or an explicit test/qualification plan for the COTS part with margin analysis. The decision should be documented as a risk with a rationale, not waved away.

**Possible follow-ups:** What downstream mitigation would you add if you had to keep the COTS LDO? How would you bound the TID drift if you can't test the part?

## Q4: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt (SEFI) that leaves the processor still drawing current and still toggling a heartbeat line, but no longer executing the control loop?

**Answer:** The hard part is that the failure signature is *deceptive* — the processor looks alive to any monitor that only checks "is it drawing current" or "is the heartbeat toggling." So the test plan has to (a) create that state deliberately, and (b) verify that the recovery mechanism detects it despite the misleading indicators.

For (a), since I can't rely on a particle beam for routine testing, I'd build fault injection into the firmware: a test hook that forces the processor into a "zombie" state — e.g., disable the control-loop task but keep a low-priority task toggling the heartbeat GPIO and keep the core in a busy loop so current draw stays nominal. This can be triggered by a debug command or a special test image. I'd also use a hardware fault injector (JTAG halt, or a debugger that freezes the core while peripherals keep running) to create variants of the state.

For (b), the recovery mechanism has to be *semantically* aware, not just liveness-aware. That means the watchdog can't be fed by the heartbeat alone; it needs a "control loop ran" token — e.g., the control task sets a sequence counter or a challenge-response that only advances if the loop actually executed. The external watchdog (or a supervisory MCU) checks that the counter advances within a window, and if not, asserts reset. The test then verifies: inject zombie state → confirm the heartbeat is still toggling (so the test is actually exercising the deceptive case) → confirm the supervisor detects the stale counter within the specified window → confirm reset and clean re-initialization → confirm the control loop resumes and the system returns to a known-safe state.

I'd also test the *boundary* cases: a slow control loop that's still running but late (should not trip), a genuine hang with the heartbeat stopped (should trip via the simpler path), and repeated injection to confirm the recovery is repeatable and doesn't leave the system in a degraded state. And I'd verify the safe state during the window between fault and reset — the actuators should be in a defined safe condition, not just "whatever they were."

**Possible follow-ups:** How would you design the challenge-response so it can't be spoofed by a partially-functional processor? What's the risk of the supervisor itself being upset, and how do you cover that?

## Q5: How would you approach derating and part selection for a space-deployed board, and how does derating interact with the radiation tolerance you're trying to achieve?

**Answer:** Derating and radiation tolerance are two separate margins that multiply, not add — and the interaction is where designs get into trouble. I'd treat them as a combined margin budget.

Derating is about keeping each part within a fraction of its rated stress (voltage, current, power, junction temperature, etc.) so that wear-out and parametric drift don't consume the life of the part. Radiation tolerance is about how much the part's parameters shift, or how it fails, under dose and SEE. The interaction: a part derated to 50% of its voltage rating may still be fine after TID shifts its threshold, but a part derated to 90% may cross a spec limit after the same shift. So the derating analysis has to be done against the *post-irradiation* parameters, not the datasheet fresh values — which means you need radiation data (or a conservative assumption) for the parts on the critical path.

In practice: I'd start from the mission environment (TID, SEE rates, displacement damage for optoelectronics), select parts with either qualified radiation data or a documented qualification plan, then apply derating on top of the worst-case post-rad parameters. For parts with no radiation data, the derating has to be more conservative and the part should be either non-critical or covered by a mitigation (redundancy, monitoring, calibration). I'd also watch for derating rules that conflict with radiation behavior — e.g., derating a bipolar part's operating current very low can push it into a region where ELDRS effects are worse, or derating a regulator's load can change its stability margin.

The other interaction is thermal: in vacuum, derating for junction temperature is harder because the only path is conduction, so the thermal derating and the radiation derating have to be evaluated together — a part running hot has less margin for post-rad parameter shift.

**Possible follow-ups:** How would you handle a part that meets derating but has no radiation data and sits on a critical path? What derating rules would you relax, if any, for a part with strong radiation characterization?

**Possible follow-ups (Q5 continued):** How do you document the combined margin so a reviewer can see both derating and radiation assumptions in one place?
