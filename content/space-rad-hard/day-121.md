# space-rad-hard — Day 121

## Q1: How would you approach designing a radiation-tolerant power distribution scheme for a payload where several loads share a common upstream rail, and a single-event latch-up (SEL) in any one load must not collapse the rail for the others?

**Answer:** The core principle is that a latch-up is a local fault and must be contained locally — the shared rail should never be the element that propagates it. I'd start by drawing a clear boundary between the "shared" upstream rail and each load's "isolated" branch, and put a current-limiting element at every branch boundary: an eFuse, a current-limiting load switch, or a latching current limiter (LCL), depending on the load's current and the recovery behavior I want. The limiter's job is to detect the overcurrent signature of a latch-up, clamp the current to a safe value, and — critically — not let the rail sag below the point where the other loads brown out. That means the upstream source impedance and bulk capacitance have to be sized so that a single branch pulling its clamp current doesn't droop the rail beyond the other loads' tolerance.

I'd also make the isolation recoverable rather than permanent: a latching limiter that requires a command to reset is often better than an auto-retry fuse, because auto-retry into a still-latched load just keeps hammering the rail. The controller should be able to power-cycle individual branches, and there should be per-branch current telemetry so the fault is observable. Finally, I'd think about the upstream protection as a backstop, not the primary defense — a coordinated design where the branch limiter trips well before the upstream protection does, so a single SEL never takes down the whole rail.

**Possible follow-ups:** How would you decide the trip threshold and response time for the branch limiter so it doesn't nuisance-trip on legitimate inrush? What changes if the load is a motor or other inductive load whose normal current signature looks latch-up-like?

## Q2: You're reviewing a design where a junior engineer has used a single-ended, non-redundant analog signal chain — sensor, amplifier, ADC — for a measurement that feeds a control loop. The engineer argues that the digital side already has TMR, so the analog side is "covered." How would you evaluate this argument?

**Answer:** I'd separate the two concerns the engineer is conflating. TMR protects against a single upset in the digital logic — it does nothing for a single-event transient that corrupts the analog signal before it's ever digitized. A SET in the amplifier front-end or a glitch on the ADC reference produces a wrong-but-plausible digital value, and TMR downstream will faithfully vote on three copies of the same wrong number. Redundancy only helps if the redundant paths are independent at the point where the fault enters.

So the real question is: where can a single fault corrupt the measurement, and is there any diversity across that path? For a control-loop measurement I'd want at least one of: a second independent sensor/amplifier path with comparison and voting or plausibility checking, a temporal check (rate-of-change limits, sample-to-sample consistency) that flags physically impossible jumps, or a reference/architecture that lets the system detect a bad conversion rather than silently trust it. I'd also look at whether the control loop can tolerate a single bad sample — if it can't, that's the design gap, not the TMR.

I'd frame the feedback constructively: the engineer's instinct to use TMR is right, but the threat model for the analog side is different, and "covered" needs to mean "covered against the faults that can actually reach this node."

**Possible follow-ups:** How would you implement a plausibility/rate-of-change check without adding so much latency that the control loop suffers? If you add a second analog path, how do you keep the two paths genuinely independent rather than sharing a common failure point?

## Q3: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt (SEFI) that leaves the processor still drawing current and still toggling a heartbeat line, but no longer executing the control loop?

**Answer:** The hard part is that the failure mode is designed to fool the obvious detectors — the processor looks alive. So the test plan has to verify recovery against a fault that a naive watchdog wouldn't catch. I'd structure it in layers.

First, define the observable "liveness" signals that are independent of the processor's own self-report: a control-loop execution counter or a task-completion flag that only advances if the loop actually runs, distinct from a GPIO that firmware toggles in a timer ISR. The test injects a fault that halts the control loop while leaving the heartbeat toggling, and confirms the recovery mechanism triggers on the *loop-liveness* signal, not the heartbeat.

Second, since you can't inject real radiation on the bench, emulate the SEFI in firmware or with a debugger: freeze the control task, keep the heartbeat ISR running, and observe whether the external supervisor / watchdog diversity detects the stall and resets. I'd test the full recovery path — detection, reset assertion, re-initialization, and confirmation that the control loop resumes and outputs return to safe values.

Third, I'd test the boundaries: how long does detection take, does the reset itself complete cleanly, does the system come back to a known-safe state, and does it recover repeatedly without accumulating state corruption. I'd also verify the failure is *detected* even when the heartbeat is healthy, which is the whole point.

**Possible follow-ups:** How would you design the loop-liveness signal so it can't be spoofed by a partially-hung processor? What would you do if the recovery mechanism itself depends on the same clock or power domain that the SEFI could affect?

## Q4: How would you approach selecting and qualifying a voltage supervisor or reset IC for a space-deployed system, given that most commercial parts are not radiation-characterized?

**Answer:** I'd treat it as a risk-managed selection rather than a binary "qualified or not" decision. First, define what the supervisor actually has to guarantee: correct reset threshold behavior across temperature and life, no false resets, and — importantly — that it doesn't fail in a way that *withholds* a needed reset. That last one is the dangerous failure mode, so the part's behavior under TID and SEE matters more than its nominal accuracy.

Then I'd work the options in order of confidence. A QML-listed or radiation-characterized supervisor is the clean answer if the budget and schedule allow. If not, I'd look for parts with published radiation test data even if not formally qualified — sometimes a manufacturer has characterization data that de-risks the choice. Failing that, I'd consider a discrete or FPGA-based supervisor built from components I can reason about, or a topology where the supervisor's failure is detectable (e.g., a windowed supervisor whose "stuck" output is caught by a second independent check).

For a truly uncharacterized COTS part, I'd bound the risk: estimate the TID the part will actually see, check whether the vendor has any TID/ELDRS data or comparable-family data, and plan a targeted radiation test if the part is critical enough to justify it. I'd also design so the supervisor isn't a single point of failure — pair it with an independent reset path or a watchdog with diverse timeout behavior.

**Possible follow-ups:** What specific failure modes of a supervisor would you worry about most under TID, and how would you detect them in-system? How would you justify a COTS supervisor to a reviewer who insists on QML-only parts?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** I'd start by making sure I actually understand their reasoning before I push back — confidence plus real work usually means they've thought about it, and there may be an assumption I'm missing or a constraint I'm not weighing. So the first move is to ask them to walk through their margin analysis and the threat model they used: what faults did they consider, what environment did they assume, and where does the margin come from. That does two things — it respects the work, and it surfaces whether we disagree on the *facts* or on the *risk posture*.

If it's a factual gap — they missed a failure mode, used optimistic environment numbers, or didn't account for TID drift over life — that's a teaching moment, and I'd walk through it with them rather than just asserting the answer. If it's a risk-posture disagreement — they think the margin is acceptable and I don't — then I'd make the trade-off explicit: what's the consequence if the margin is wrong, how detectable is the failure, and what does it cost to add margin. Framing it as "here's the failure we're insuring against and here's the premium" moves it from opinion to decision.

I'd keep the decision with the review, not with me personally — document the concern, the rationale, and the agreed action, whether that's adding margin, gathering data to close the gap, or accepting the risk with eyes open. And I'd follow up with the engineer afterward so the relationship isn't defined by the one disagreement.

**Possible follow-ups:** What would you do if, after all that, the engineer still disagrees and the schedule pressure favors their position? How do you make sure a junior engineer's good idea doesn't get dismissed just because it came from a junior engineer?
