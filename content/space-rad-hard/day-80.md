# space-rad-hard — Day 80

## Q1: How would you approach designing a radiation-tolerant analog signal chain for a spacecraft instrument where the sensor output is a low-level differential signal, and both the amplifier front-end and the ADC reference can experience single-event transients (SETs)?
**Answer:** The core problem is that a low-level differential signal has very little margin against a transient that appears anywhere in the chain, so I would treat SET immunity as a signal-chain architecture decision rather than a component afterthought. First, I would push gain as early as possible in the chain so the signal is well above the noise and offset floor before it reaches any stage that could be hit — a transient that couples in after the first stage is proportionally smaller relative to the signal. Second, I would use a differential topology end-to-end, including the ADC, because a common-mode transient that couples into both legs tends to be rejected by the differential stage's CMRR, whereas a single-ended chain has no such rejection. Third, for the ADC reference specifically, I would not rely on the reference IC alone: I would add passive filtering close to the reference pin, and consider a reference topology that is inherently less sensitive to a single-node transient — for example, a filtered reference with a large local reservoir, or a ratiometric arrangement where the same reference feeds both the sensor excitation and the ADC so that a transient affects both proportionally and cancels in the ratio. Fourth, I would add plausibility checking in firmware: a single SET produces a physically implausible sample, so a median-of-three or slew-rate limit on the digitized value can reject it without discarding the whole measurement. Finally, I would validate the design against the actual transient environment — heavy-ion or laser testing on the analog front-end, not just the digital side — because SET sensitivity in analog parts is not captured by TID data alone.
**Possible follow-ups:** How would you decide between a ratiometric reference scheme and an independent precision reference for this kind of measurement? What firmware techniques would you use to distinguish a genuine fast transient in the sensor signal from an SET-induced spike?

## Q2: You're reviewing a design for a space-deployed system that uses a COTS linear regulator to generate a 1.2V core voltage for an FPGA. The regulator's datasheet shows no radiation data, and the output voltage is specified as 1.2V ±2%. The FPGA requires 1.2V ±5% and draws up to 3A. How would you evaluate this choice and what alternatives would you recommend?
**Answer:** The first issue is that the ±2% initial tolerance is not the number that matters — what matters is the tolerance over the mission, including TID-induced drift, temperature, load regulation, and any SET behavior. With no radiation data, I cannot bound the post-irradiation output, so I cannot claim the ±5% FPGA window is met. The second issue is that a linear regulator at 3A is dissipating significant power, and in vacuum that heat has to conduct out; the thermal path becomes part of the radiation-tolerance question because a part running hot will typically degrade faster under TID. My evaluation would proceed in stages: (1) check whether the regulator has any published TID or SEE data, even from a similar family, and whether the manufacturer can provide characterization data under NDA; (2) if not, treat it as unqualified and either replace it or qualify it. For replacement, I would look for a rad-tolerant or rad-hard LDO or a rad-hard switching regulator with a downstream filter, accepting the efficiency trade-off if the thermal budget allows. If qualification is the only path, I would plan a TID test at the expected dose with margin, plus SEE testing at the relevant LET, and I would design the board so the regulator can be swapped for a qualified alternative without a respin — same footprint, compatible pinout. I would also add margin in the FPGA's decoupling and a voltage supervisor with a threshold set to catch an out-of-window rail before the FPGA is damaged.
**Possible follow-ups:** How would you set the supervisor threshold given the FPGA's ±5% window and the regulator's uncertain post-irradiation behavior? What would you do if the only qualified alternative has a different footprint and the schedule doesn't allow a respin?

## Q3: How would you approach designing a fault-tolerant I²C bus for a space-deployed system where multiple sensor nodes share the same bus, given that single-event upsets can corrupt data or cause bus lock-ups?
**Answer:** I²C is a poor fit for a fault-tolerant space bus because it is single-ended, has no inherent error detection beyond the ACK bit, and a single stuck node can hold SDA or SCL low and lock the entire bus. So the design has to compensate at the protocol and physical layers. At the physical layer, I would use a bus buffer or multiplexer with per-segment isolation so that a locked segment can be isolated without taking down the whole bus, and I would add series resistors and TVS-style clamps for transient protection. At the protocol layer, I would add a CRC or checksum to every message, because the ACK bit alone will not catch a corrupted payload. I would implement a bus recovery routine: if SCL is held low longer than a timeout, the master issues up to nine clock pulses on SCL to let the stuck slave release SDA, then issues a STOP condition — this is the standard I²C recovery sequence and it handles the common lock-up mode. For a node that is truly hung, I would add a per-node reset line so the master can power-cycle or reset an individual sensor without disturbing the others. I would also consider whether I²C is the right choice at all: for a multi-node space bus, RS-485 or CAN-FD with differential signaling and built-in CRC and arbitration is far more robust, and the trade-off is usually worth it. If I²C must stay, I would treat it as a best-effort bus with a redundant path or a secondary bus for critical nodes.
**Possible follow-ups:** How would you implement the bus recovery routine without a dedicated I²C controller that supports clock stretching? What would you do if a sensor node's I²C address is corrupted by an SEU and it starts responding to another node's address?

## Q4: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt (SEFI) that puts the main processor into a state where it's still drawing current and still toggling a heartbeat line, but no longer executing the control loop?
**Answer:** The key insight is that a heartbeat line is not a reliable indicator of health — a processor can be stuck in a loop that toggles a GPIO while the control loop is dead, so the test plan has to verify recovery from a state that a naive watchdog would miss. I would structure the test plan around three things: fault injection, observability, and recovery verification. For fault injection, since I cannot inject actual radiation on the ground, I would use a debugger or a test harness to force the processor into the target state — for example, halt the control loop task while leaving a timer interrupt running that toggles the heartbeat, or corrupt the control loop's state variable so it computes a constant output. For observability, I would instrument the system so that the control loop's liveness is independently observable — a counter that increments only when the control loop completes a full cycle, a checksum over the control state, or a comparison of the commanded output against a plausibility window. The recovery mechanism should be designed so that it does not depend on the heartbeat: for example, a watchdog that is kicked only by the control loop itself, not by a generic timer, or a supervisor that checks the control loop's output against a window and resets if it is out of range for too long. For recovery verification, I would confirm that after the injected fault, the system detects it within the specified time, resets cleanly, reinitializes, and returns to normal control within the specified recovery time — and I would repeat this across the full operating envelope, including at temperature extremes and with the bus at minimum and maximum voltage. I would also test the case where the fault occurs during the recovery itself, to make sure the recovery mechanism is not itself vulnerable.
**Possible follow-ups:** How would you design the watchdog so that it is kicked by the control loop and not by a generic timer, without adding a lot of complexity? What would you do if the control loop's output is legitimately out of the plausibility window during a valid transient, such as a startup or a commanded step change?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?
**Answer:** The first thing I would do is separate the person from the proposal — the engineer has done real work, and that work deserves to be engaged with on its technical merits, not dismissed because I have a prior. I would start by asking the engineer to walk me through the margin calculation: what environment are they designing to, what is the worst-case part behavior, and where does the margin come from? Often the disagreement is not about the conclusion but about an assumption — a dose level, a derating factor, a temperature, a transient amplitude — and making that assumption explicit is the fastest way to resolve it. If the assumption is wrong, the engineer will usually see it themselves once it is on the table, and the review stays collaborative. If the assumption is defensible but I still believe the margin is insufficient, I would frame it as a risk question rather than a correctness question: what is the consequence if the margin is consumed, what is the cost of adding margin, and what is the cost of being wrong? That reframes the discussion from "you're wrong" to "here is the trade-off," which is a much more productive conversation. If we still disagree, I would not overrule in the room — I would ask for a written margin analysis with the assumptions stated, and take it to a second reviewer or a formal risk review. That protects the engineer's ownership, keeps the decision auditable, and makes sure the decision is made on evidence rather than on seniority. Throughout, I would be explicit that the goal is the right technical outcome, not winning the argument, and I would credit the engineer's work where it is sound.
**Possible follow-ups:** What would you do if the engineer's margin analysis is correct but the schedule does not allow the fix you believe is needed? How would you handle it if the same engineer repeatedly proposes under-margined designs?
