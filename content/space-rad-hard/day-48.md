# space-rad-hard — Day 48

## Q1: How would you approach designing a fault-tolerant analog output stage for a space-deployed system where a single-event transient (SET) on a DAC's reference voltage could cause a momentary but dangerous output spike to an actuator?

**Answer:** I'd approach this by first recognizing that the reference voltage is the single most sensitive node in the analog chain—a transient there propagates directly to the output with gain. My first line of defense would be at the reference itself: use a precision reference with known radiation performance, add a low-pass filter (RC or active) at the reference output sized to attenuate transients shorter than the control loop's response time, and place a local bypass capacitor with low ESR right at the reference pin. The filter time constant needs to be short enough not to affect normal dynamic response but long enough to clip the majority of SET pulse widths, which typically range from nanoseconds to a few microseconds.

Beyond the reference, I'd add output-stage protection that doesn't rely solely on the DAC being correct. A hardware window comparator monitoring the output voltage against a safe range, with a fast disconnect or clamp path to the actuator, provides an independent safety net. The clamp must be able to sink or source the fault current without itself being damaged. I'd also consider a series pass element (e.g., a MOSFET) between the DAC output and the actuator that can be shut off within microseconds when the window comparator trips. In firmware, I'd implement rate limiting on the DAC command updates so that even if a transient corrupts the digital value, the output can only slew at a bounded rate—this prevents step changes from reaching the actuator. Finally, I'd verify the design by injecting transients at the reference node during test and observing the output response, ensuring the protection engages before the actuator sees a dangerous level.

**Possible follow-ups:** How would you choose the filter cutoff frequency without compromising the control loop's bandwidth? What if the actuator requires a continuous analog signal and cannot tolerate being disconnected?

## Q2: How would you approach designing a radiation-tolerant firmware update strategy for a space-deployed system where the application firmware resides in flash memory that is susceptible to single-event upsets, and a corrupted update could render the system unrecoverable?

**Answer:** The fundamental principle is that you must never be in a position where a single corrupted update can brick the system. I'd structure the flash memory into at least two regions: a permanent bootloader in protected memory and two application image slots (A/B partitioning). The bootloader is written once, ideally at the factory, and is designed to be as simple and robust as possible—it only needs to validate and launch an application image, and support the update process itself. The bootloader should be stored in a memory type less susceptible to upsets, or protected with strong ECC and multiple redundant copies that are voted on at boot.

For the update process itself, I'd require the new image to be transmitted with strong error detection (e.g., CRC-32 or better) and ideally error correction coding. The image is first written to the inactive slot while the system continues running from the active slot. Only after the full image is received, validated, and verified does the system attempt to switch slots. The bootloader validates the new image's checksum and, if possible, performs a test boot with a watchdog timeout—if the new image fails to start or crashes, the bootloader automatically reverts to the previous known-good image. I'd also add a "last known good" flag that the application sets only after it has successfully initialized and passed self-tests. If the flag isn't set within a timeout, the bootloader reverts. For radiation-induced corruption of the stored images themselves, I'd implement periodic scrubbing of the inactive image slot, reading it back and correcting any single-bit errors using the ECC, and triggering a re-update if uncorrectable errors are found.

**Possible follow-ups:** How would you handle the case where the bootloader itself becomes corrupted? What if the communication link to the ground station is unreliable and an update is interrupted mid-transfer?

## Q3: You are reviewing a design for a space-deployed system where a junior engineer has proposed using a single commercial voltage regulator with no radiation data for a critical analog rail, arguing that "the rail is only 5V and the load is only 50mA, so the risk is minimal." You've explained the risks of TID drift, SETs, and SEL, but the engineer pushes back, saying that the system has a calibration routine and the ADC can tolerate brief supply transients. How would you handle this continued disagreement, and how would you ensure the design review process remains constructive rather than adversarial?

**Answer:** When an engineer continues to push back after the technical risks have been explained, it usually means either they don't fully appreciate the severity of the failure modes, or they feel their design is being dismissed without fair consideration. I'd first acknowledge the legitimate aspects of their argument—yes, the load is small, and yes, calibration can handle some drift. Then I'd reframe the discussion around what we don't know rather than what we do. The issue isn't whether the regulator will work on day one; it's whether we can bound its behavior over the full mission. Without radiation data, we have no way to predict TID-induced drift in the output voltage or reference, no way to know the SEL threshold, and no way to estimate SET magnitude and duration on the output. A calibration routine can correct for slow drift if we have a stable reference to calibrate against—but if the regulator itself is the reference source, we're calibrating against an unknown.

I'd propose a structured way to resolve the disagreement: rather than arguing opinions, we define the acceptance criteria and the evidence needed to meet them. Can we find any radiation test data for this part or its die family? If not, can we run a limited test at a facility, or is there budget to qualify a known part instead? I'd also suggest a design change that reduces the risk without abandoning the engineer's approach entirely—for example, adding a radiation-characterized reference diode or a simple shunt regulator after the commercial part to stabilize the rail, or adding a current-limiting circuit to mitigate SEL consequences. This gives the engineer a path forward that preserves their design intent while addressing the safety gap. Throughout, I'd keep the tone collaborative—this is a shared engineering problem, not a contest of authority. The goal is to make the right decision for the mission, and I'd make clear that I value their input in finding that solution.

**Possible follow-ups:** What if the engineer still disagrees after you've proposed alternatives? How would you escalate the issue if needed?

## Q4: How would you approach designing a fault-tolerant clock distribution network for a space-deployed system that uses multiple FPGAs and ADCs requiring synchronized sampling?

**Answer:** Clock distribution in a space environment has two distinct challenges: maintaining signal integrity across multiple loads, and ensuring that a single-event upset in the clock path doesn't cause loss of synchronization or metastability across the system. I'd start with a single, radiation-characterized oscillator as the master clock source, since having multiple independent oscillators invites frequency drift and phase misalignment over temperature and radiation exposure. The master clock feeds a distribution buffer or fan-out tree, with each output having its own series termination and proper impedance-controlled routing to its destination.

For synchronized sampling across multiple ADCs, I'd use a scheme where the clock is distributed along with a synchronization pulse or frame sync signal. The ADCs are configured to start conversion on the sync edge, so even if there's slight skew in the clock arrival times, all conversions begin on the same sync event. The sync signal itself should be generated by a counter in the FPGA that's protected with TMR or ECC, so a single-event upset in the counter can't cause a spurious or missed sync pulse. I'd also add a phase-locked loop or delay-locked loop at each ADC to align the clock edge to the data sampling instant, compensating for trace length differences and buffer propagation delays.

For fault tolerance, I'd monitor the clock presence at each destination—a loss-of-clock detector that flags if the clock stops or becomes irregular. If the master clock fails, the system needs a fallback. I'd consider a secondary oscillator that can be switched in, with a glitch-free clock mux to avoid runt pulses during the switchover. The switchover decision should be made by logic that's itself radiation-tolerant, and the system should log the event for telemetry. In terms of layout, I'd keep the clock traces short, use a solid ground reference beneath them, and avoid routing them near high-current switching nodes or analog inputs. Finally, I'd verify the design by measuring skew at each ADC clock pin and testing the sync accuracy across temperature and after radiation exposure.

**Possible follow-ups:** How would you handle the case where one ADC loses its clock but the others are fine? What clock frequency would you choose and how does that affect your distribution strategy?

## Q5: Imagine you are leading a design review for a space-deployed system where a junior engineer has proposed using a single commercial voltage regulator with no radiation data for a critical analog rail, arguing that "the rail is only 5V and the load is only 50mA, so the risk is minimal." You've explained the risks of TID drift, SETs, and SEL, but the engineer pushes back, saying that the system has a calibration routine and the ADC can tolerate brief supply transients. How would you handle this continued disagreement, and how would you ensure the design review process remains constructive rather than adversarial?

**Answer:** This scenario is fundamentally about risk ownership and evidence-based decision-making, not just the technical merits of the regulator. When an engineer continues to push back after the risks have been laid out, I'd shift the conversation from "is this acceptable?" to "who accepts the risk, and on what basis?" In a space program, the design review isn't just a technical discussion—it's a formal gate where risk decisions get documented and owned. I'd suggest we formally capture the disagreement: the engineer's position, the identified risks, and the open questions that need answers before we can close the review. This isn't about winning an argument; it's about ensuring the decision is traceable and that we've identified what evidence would change our minds.

I'd also propose a middle path that addresses the engineer's concern about over-engineering while still bounding the risk. For example, we could keep the commercial regulator but add a radiation-characterized voltage reference and a simple comparator-based overvoltage/undervoltage monitor on the rail. If the regulator drifts or transients exceed the window, the monitor can shut down the load or switch to a redundant path. This preserves the engineer's design while adding an independent safety net. I'd also ask the engineer to help define the test that would validate the regulator's behavior—what would we need to see in a radiation test to feel comfortable? This turns the disagreement into a shared problem-solving exercise. If we genuinely cannot reach consensus, I'd escalate to the project's systems engineer or chief engineer with a clear summary of both positions and the risk assessment, so the decision is made at the appropriate level with full information. Throughout, I'd emphasize that the review process is about making the mission successful, not about individual design preferences.

**Possible follow-ups:** What specific evidence would change your assessment of the commercial regulator? How would you document the residual risk if the decision is made to proceed without radiation testing?
