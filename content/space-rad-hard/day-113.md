# space-rad-hard — Day 113

## Q1: How would you approach designing a radiation-tolerant analog-to-digital conversion subsystem where the ADC's voltage reference is a COTS part with no radiation data, and the measurement must hold accuracy over a multi-year mission?

**Answer:** The reference is the accuracy anchor for the whole conversion chain, so an uncharacterized reference is the highest-risk element — any drift there appears as a gain error that no amount of downstream filtering can remove. I'd start by treating the reference's behavior as an unknown with three distinct failure modes: total ionizing dose drift (including enhanced low-dose-rate sensitivity, which can make low-dose-rate space exposure worse than the high-dose-rate data you'd get from a short test), single-event transients on the reference output that momentarily shift the conversion gain, and long-term drift from displacement damage if the part sees significant particle flux.

The first mitigation is architectural rather than part-level: don't let the reference be a single point of failure for accuracy. I'd consider a ratiometric measurement where the same reference drives both the ADC and the sensor excitation, so slow reference drift cancels in the ratio — this converts a gain error into a common-mode effect. Where ratiometric sensing isn't possible, I'd add a second, independent reference of a different technology and periodically cross-check them; divergence beyond a threshold flags the channel as degraded and lets the system fall back to a conservative mode. A calibrated, rad-hard voltage reference as the primary and a COTS part as the cross-check monitor is often a cheaper architecture than trying to qualify two precision references.

For the SET problem specifically, I'd filter and average at the reference output — an RC with a time constant well beyond the expected SET duration — and, more importantly, validate each conversion against a plausibility window so a transient reading can't propagate into a control action. If the measurement is time-sensitive and can't simply be retried, I'd add a sample-and-hold with a second conversion path or a comparator-based sanity check that rejects the sample.

Finally, I'd plan for the reference to drift and design the calibration strategy around that: a periodic calibration against an on-board transfer standard, with the calibration coefficients stored in protected memory and the drift budget explicitly allocated in the error analysis. If the part truly has no data, I'd budget a small radiation test — even a limited-dose-rate run on a handful of units — because the cost of that test is almost always less than the cost of discovering the drift in orbit.

**Possible follow-ups:** How would you distinguish reference drift from sensor drift if both are uncharacterized? What would you do if the cross-check reference and the primary disagree and you can't tell which is wrong?

## Q2: You're reviewing a design where a junior engineer has used a single-ended, non-redundant analog signal chain — sensor, amplifier, ADC — for a measurement that feeds a control loop. The engineer argues that the digital side already has TMR, so the analog side is "covered." How would you evaluate this argument?

**Answer:** The argument has a category error in it: TMR protects against upsets in the logic that processes a value, but it does nothing about the value being wrong before it ever reaches the logic. If the analog front-end produces a corrupted sample, all three TMR lanes will faithfully agree on the corrupted number and vote it through. Redundancy downstream of a single point of failure doesn't remove that failure — it just makes the failure unanimous.

I'd walk through the failure modes the analog chain is actually exposed to. A single-event transient on the amplifier output or the ADC's sample-and-hold can produce a spurious reading that lasts one conversion; if that reading feeds a control loop, the loop acts on it. A drift in the amplifier's gain or offset over the mission shifts every reading. A latch-up or stuck node in the ADC can freeze the output at a plausible-looking value. None of these are caught by digital TMR.

The right response is defense in depth at the analog layer: plausibility limits and rate-of-change checks on each sample before it enters the control loop, so a single wild sample is rejected; a second, independent signal path — even a lower-precision one — for cross-checking critical measurements; and where the measurement is truly safety-critical, genuine analog redundancy with diverse sensing (different sensor types or different amplifier topologies) so a common-mode fault doesn't take both paths down. I'd also make sure the control loop has a defined safe state it enters when the measurement is flagged as untrustworthy, rather than continuing to act on suspect data.

I'd frame the feedback constructively: the engineer's instinct to use TMR is right, but the coverage model needs to extend to where the data originates. The question to ask in review is "where can a single fault corrupt the value before redundancy sees it?" — and the analog front-end is almost always one of those places.

**Possible follow-ups:** How would you set plausibility limits without knowing the true signal range in advance? Would you accept a lower-precision redundant path, and how would you arbitrate between the two?

## Q3: How would you approach designing a fault-tolerant power distribution scheme for a payload with multiple loads of different criticality, where a single-event latch-up in any one load must not take down the rest of the system?

**Answer:** The core principle is that the boundary between "shared" and "isolated" should be drawn by criticality and by the fault current a load can demand, not by convenience of layout. I'd start by classifying loads into tiers — mission-critical (must never lose power), essential (can be shed briefly), and non-essential (can be dropped entirely) — and then design the distribution tree so that no single latch-up event can propagate upstream past its own branch.

Practically, that means each load, or each small group of similar-criticality loads, gets its own current-limited branch off the main rail, with a latch-up detection and protection element — a current-sense resistor plus a comparator driving a disconnect switch, or a dedicated protection IC — sized so that the branch trips before the upstream rail sags below the operating threshold of the other loads. The upstream rail itself needs enough bulk capacitance and a stiff enough source to ride through the transient while the branch protection responds. For the mission-critical tier, I'd consider fully independent feeds with ORing diodes or ideal-diode controllers, so even a fault in the distribution switch for one branch can't take the critical load down.

The tricky part is the interaction between protection speed and nuisance tripping. Inrush from capacitive loads at power-up looks like a fault to a fast comparator, so the protection needs a defined response curve — a fast trip for hard shorts, a slower trip for overloads — and the inrush energy has to be budgeted so the branch doesn't trip on legitimate startup. I'd also make sure the protection is latching rather than auto-retrying for a confirmed latch-up, with a controlled retry policy, because an auto-retry into a persistent latch just cooks the part.

Finally, I'd verify the whole scheme against the actual fault scenarios: simulate or bench-test a shorted load on each branch and confirm the other branches stay within their operating window, and confirm the protection itself is tolerant of the radiation environment — a protection circuit that upsets is worse than none.

**Possible follow-ups:** How would you decide the trip threshold when a load's normal current and its latch-up current are close together? What happens if the protection switch itself latch-ups?

## Q4: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt (SEFI) that leaves the processor still drawing current and still toggling a heartbeat line, but no longer executing the control loop?

**Answer:** The defining feature of this failure is that the usual "is it alive?" indicators lie — current draw is normal and the heartbeat is still toggling, so a naive watchdog that just checks for a heartbeat edge will never fire. The test plan has to specifically exercise the gap between "the processor is running something" and "the processor is running the right thing."

I'd structure the plan around fault injection rather than waiting for real radiation. On the bench, I'd use a debugger or a test harness to force the processor into the target state — halt the control loop task while leaving a low-priority heartbeat task running, or corrupt the control loop's state so it spins without producing output — and then verify that the system's recovery mechanism detects it. That means the recovery mechanism can't be a simple heartbeat monitor; it needs a functional check, such as a watchdog that requires the control loop to check in with a computed token (a "windowed" or challenge-response watchdog), or an independent supervisor that monitors the control loop's actual output — actuator commands, DAC updates, a counter that only advances when the loop runs — rather than a generic liveness signal.

The test plan should cover the detection latency (how long until the fault is caught), the recovery action (reset, task restart, or failover to a redundant channel), and the post-recovery state (does the system come back to a safe, known state, and does it re-enter the control loop correctly). I'd also test the boundary cases: a heartbeat that toggles but at the wrong rate, a control loop that runs but produces stale output, and a fault that occurs during recovery itself.

For the radiation side, since you can't inject a SEFI on demand in a beam run, I'd use the beam time to characterize the distribution of failure modes — how often does the processor end up in this "alive but not working" state versus a clean reset — and use that to validate that the bench-injected fault is representative. The bench test proves the recovery logic works; the beam data tells you whether you're testing the right fault.

**Possible follow-ups:** How would you design a watchdog that can't be fooled by a stuck-but-toggling processor? What recovery action would you choose if a full reset would lose critical state?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** The first thing I'd do is separate the person from the proposal. The engineer has done real analysis, and that deserves to be taken seriously — dismissing it out of hand both demoralizes them and risks missing something they saw that I didn't. So I'd start by asking them to walk through their margin calculation and the assumptions behind it, and I'd listen for where the disagreement actually lives. Often it's not "is this number right" but "what environment are we designing to" — a margin that looks fine under one radiation assumption looks thin under another.

Then I'd make the disagreement explicit and evidence-based rather than authority-based. I'd put the two positions side by side: here's the environment specification, here's the failure mode I'm worried about, here's the margin I'd expect, here's what your analysis assumes. If the gap is an assumption, we can resolve it with data — a datasheet, a test result, a calculation. If the gap is a judgment call about acceptable risk, that's a decision that should be made with the whole review group and documented, not settled by seniority.

I'd also be open to being wrong. If the engineer's analysis holds up and my concern was based on a stale assumption, I should say so clearly — that builds the trust that makes the next disagreement easier. If my concern stands, I'd frame the path forward as "here's what would change my mind" — a test, a derating calculation, a worst-case analysis — so the engineer has a concrete way to strengthen the proposal rather than just being overruled.

Throughout, I'd keep the language on the design, not the designer: "this margin worries me because..." rather than "you've under-margined this." And I'd make sure the decision and its rationale get recorded in the review minutes, so the reasoning is visible to the whole team and to whoever inherits the design. The goal isn't to win the argument — it's to make sure the board survives the environment, and to leave the engineer feeling that their work was engaged with fairly.

**Possible follow-ups:** What would you do if the engineer remained convinced and the schedule pressure was to accept their design? How do you make sure a junior engineer's good idea doesn't get lost because they lost the argument?
