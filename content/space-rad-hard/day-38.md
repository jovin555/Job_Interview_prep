# space-rad-hard — Day 38

## Q1: How would you approach designing a fault-tolerant analog multiplexing scheme for a space-deployed system where a single-event transient (SET) on the mux select lines could route the wrong sensor channel to a precision ADC, potentially causing an incorrect control action?

**Answer:** The core problem is that a single-event transient on the mux select lines can cause the wrong channel to be sampled, and if that sample drives a control action, the system could respond to a sensor it didn't intend to read. I'd approach this at multiple levels. First, at the circuit level, I'd add filtering on the select lines—RC low-pass filters with time constants chosen to reject transients shorter than the expected SET duration while still allowing normal switching speeds. I'd also consider using a mux with built-in address decoding that requires a valid "chip select" strobe, so a glitch on the address lines alone isn't sufficient to switch channels. Second, at the system level, I'd implement a "read-verify-read" pattern in firmware: read the channel, then read it again after a short delay, and only accept the value if both readings agree within a tolerance. For truly critical channels, I'd consider dedicating a separate ADC input per sensor rather than multiplexing at all—the cost of an extra ADC channel is often worth eliminating the single point of failure. Finally, I'd add a plausibility check on the measured value itself: if the reading is outside the expected physical range for that sensor, flag it as suspect and default to a safe control action rather than acting on the data.

**Possible follow-ups:** How would you choose the RC filter time constant without slowing down the mux switching too much? What if the system can't afford the latency of a read-verify-read approach?

## Q2: You are reviewing a design for a space-deployed system that uses a radiation-hardened FPGA and a COTS operational amplifier for a critical analog signal conditioning path. The op-amp has no radiation data, but the designer argues that "it's a simple, mature part with a well-understood topology, and the system has a calibration routine." How would you evaluate this approach?

**Answer:** I'd push back on the assumption that "mature and well-understood" translates to "radiation-tolerant." The failure modes we care about—TID-induced input offset drift, bias current changes, and single-event transients on the output—are not captured by the datasheet's normal operating specifications. A calibration routine can correct for static offset drift, but it cannot correct for a transient that occurs between calibrations, and it cannot correct for a SET that lands on the output during a critical measurement. I'd ask three questions: First, what is the op-amp's role in the signal chain? If it's a buffer for a non-critical housekeeping channel, the risk may be acceptable with proper mitigation. If it's in the critical control path, I'd want a radiation-characterized part or at least a part with published radiation test data from a reputable source. Second, what is the failure consequence? If a SET on the op-amp output causes a transient that could trigger an unsafe actuator command, that's a safety issue, not just an accuracy issue. Third, can we mitigate the risk with circuit-level techniques? For example, adding a low-pass filter at the op-amp output to attenuate short transients, or using a redundant signal path with voting. If the part is truly critical and no rad data exists, I'd recommend a radiation test of the specific part—even a limited test with a few samples at a single dose rate can reveal gross TID sensitivity. The cost of testing is usually far less than the cost of a mission failure.

**Possible follow-ups:** What specific radiation test would you run on the op-amp, and what parameters would you measure? How would you determine whether the calibration routine is sufficient to handle TID-induced drift?

## Q3: How would you approach designing a radiation-tolerant firmware update strategy for a space-deployed system where the application firmware resides in flash memory that is susceptible to single-event upsets, and a corrupted update could render the system unrecoverable?

**Answer:** The fundamental requirement is that a corrupted update must never brick the system. I'd design the update strategy around three principles: redundancy, validation, and atomicity. For redundancy, I'd use a dual-bank flash architecture—one bank holds the current known-good firmware, the other receives the new update. The bootloader always boots from the known-good bank unless a valid update is staged and verified. For validation, I'd compute a cryptographic hash (e.g., SHA-256) of the new firmware image before and after writing it to flash, and verify the hash matches the expected value from the command uplink. I'd also validate the image structure—checking that the vector table, entry point, and key sections are within expected bounds—before ever attempting to boot from it. For atomicity, I'd write the new image to the inactive bank, verify it completely, then flip a "boot from bank B" flag in a separate, protected memory location. Only after the new image boots successfully and passes a self-test would I mark the old bank as replaceable. If the new image fails to boot or fails self-test, the bootloader automatically reverts to the known-good bank. I'd also consider using a triple-redundant copy of the bootloader itself, with majority voting at startup, since the bootloader is the last line of defense. Finally, I'd implement a "golden image" in a write-protected region—a minimal fallback firmware that can at least receive a new update over the command link, even if the main application banks are both corrupted.

**Possible follow-ups:** How would you handle the case where the flash write itself is interrupted by a single-event upset mid-write? How would you protect the "boot from bank B" flag from being corrupted?

## Q4: Imagine you are leading a design review for a space-deployed system where a junior engineer has proposed using a single commercial voltage regulator with no radiation data for a critical analog rail, arguing that "the rail is only 5V and the load is only 50mA, so the risk is minimal." How would you handle this disagreement?

**Answer:** I'd acknowledge the engineer's point that the load is small, but I'd reframe the discussion around what "risk is minimal" actually means in a space environment. The risk isn't just about the electrical stress—it's about the failure modes that radiation introduces. A commercial linear regulator can experience TID-induced output voltage drift, increased quiescent current, or complete loss of regulation. It can also experience single-event transients on the output that could couple into the analog signal chain. None of these are captured by the datasheet's normal operating specifications. I'd walk through the specific consequences for this rail: if the 5V rail drifts by 10%, what happens to the sensor bias? What happens to the ADC reference? What is the impact on the measurement accuracy that the mission depends on? I'd also point out that the "load is only 50mA" argument cuts the other way—a small load means the regulator is likely operating in a light-load regime where its behavior under radiation may be even less predictable. I'd then propose a path forward: either select a radiation-characterized regulator from the QML list, or if a COTS part is truly necessary, run a limited radiation test on the specific part to characterize its TID response and SET behavior. I'd also suggest circuit-level mitigations—such as a post-regulator filter or a voltage supervisor that monitors the rail and resets the system if it goes out of tolerance—as a belt-and-suspenders approach. The key is to move the conversation from "the risk is minimal" to "we have characterized the risk and accepted it with mitigations in place."

**Possible follow-ups:** How would you decide whether to run a radiation test on the COTS part versus redesigning around a qualified part? What would you include in the test plan?

## Q5: How would you approach designing a fault-tolerant clock distribution network for a space-deployed system that uses multiple FPGAs and ADCs requiring synchronized sampling?

**Answer:** The challenge is twofold: maintaining phase alignment between multiple devices, and ensuring that a single-event upset in the clock path doesn't cause a loss of synchronization or a frequency transient that corrupts sampling. I'd start with a single, radiation-tolerant master oscillator—preferably a crystal oscillator with known TID performance—and distribute it through a clock buffer tree. The buffer tree should have enough fan-out to drive all loads with proper termination, and I'd use point-to-point routing with series termination to minimize reflections and jitter. For the FPGAs and ADCs, I'd use dedicated clock inputs with internal PLLs or DLLs to clean up the clock and generate the required frequencies. The key design decision is how to handle a clock glitch or temporary loss of the master clock. I'd add a clock monitor circuit that detects frequency or phase anomalies and generates an interrupt to the system controller. The controller can then decide whether to reset the clock tree, switch to a redundant oscillator, or initiate a system-level recovery. For the ADCs, I'd design the sampling trigger to be edge-based rather than level-based, so a single glitch on the clock line doesn't cause a double-sample or missed sample. I'd also consider adding a "sample sync" pulse that is distributed separately from the clock—this gives a common reference point that all ADCs can align to, even if the clock itself has minor phase variations. Finally, I'd verify the clock distribution network's timing margins across temperature and voltage extremes, and I'd test the system's behavior under injected clock faults to ensure the recovery mechanism works as designed.

**Possible follow-ups:** How would you handle the case where one FPGA's PLL loses lock while the others remain locked? What redundancy would you build into the clock tree itself—a second oscillator, or a different approach?
