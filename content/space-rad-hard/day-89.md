# space-rad-hard — Day 89

## Q1: How would you approach designing a radiation-tolerant analog-to-digital conversion subsystem where the ADC's voltage reference is a COTS part with no radiation data, and the measurement must hold accuracy over a multi-year mission?

**Answer:** I'd start by treating the reference as the accuracy bottleneck and characterizing the risk explicitly rather than assuming it away. The first step is to bound the problem: what accuracy does the measurement actually need, and how much of the error budget can the reference consume? A COTS reference with no radiation data has two distinct concerns — total ionizing dose drift (including enhanced low-dose-rate sensitivity, which can make a part that looks fine at high dose rate fail at mission-representative low dose rates) and single-event transients on the reference output, which propagate directly into every conversion.

For TID, I'd want at minimum a low-dose-rate characterization or a documented rationale for why the part's topology is expected to be stable — for example, buried-zener references tend to be more TID-tolerant than bandgap references, but that's a hypothesis to verify, not a guarantee. If budget doesn't allow testing, I'd design the system so the reference's absolute accuracy is not load-bearing: use a ratiometric measurement where the same reference drives both the sensor excitation and the ADC, so slow reference drift cancels in the ratio. I'd also add a periodic calibration path against an on-board or commanded standard, and log the reference's behavior over time so drift is observable rather than silent.

For SETs, the reference output is a low-impedance node, so a transient there is a short voltage excursion. I'd follow the reference with an RC filter sized so the transient is attenuated below the ADC's resolution at the sampling bandwidth, and I'd add a plausibility check in firmware — reject or flag conversions that fall outside a physically expected window, and require N-of-M agreement before a reading is used in a control loop. If the reference is truly critical and untestable, the honest answer is that it becomes a program risk that needs to be accepted formally, not a design detail to be hand-waved.

**Possible follow-ups:** How would you distinguish reference drift from sensor drift during in-flight calibration? What would you do if the reference's low-dose-rate behavior turned out to be much worse than the high-dose-rate data suggested?

## Q2: How would you approach designing a fault-tolerant I²C bus for a space-deployed system where multiple sensor nodes share the same bus, given that single-event upsets can corrupt data or cause bus lock-ups?

**Answer:** I²C is a deceptively fragile bus in a radiation environment because it has several failure modes that aren't just "a bit flipped." The classic one is a slave holding SDA low after an upset — the master can't generate a START, and the whole bus is dead until something forces the slave to release the line. So the design has to address three layers: electrical robustness, protocol robustness, and recovery.

Electrically, I'd use a bus with proper pull-ups sized for the capacitance and speed, and I'd consider a bus buffer or switch per segment so that one stuck node can be isolated rather than taking down every node. If the topology allows, segmenting the bus behind a mux or a bus switch means a lock-up is contained to one branch.

At the protocol layer, I'd add a CRC or at least a checksum to every transaction payload, sequence numbers or transaction IDs so a duplicated or replayed message is detectable, and timeouts on every read so a non-responding node doesn't stall the master. I'd also avoid relying on a single read for anything safety-relevant — read back, or use a write-verify pattern.

For recovery, the standard trick is clock pulsing: if SDA is stuck low, the master toggles SCL up to nine times to walk the stuck slave through any pending bits and release the line, then issues a STOP. I'd implement that in firmware as an automatic recovery routine triggered by a bus timeout, and I'd log the event so the ground can see how often it happens. If a node repeatedly locks up, the recovery routine should be able to power-cycle that node individually — which means each node needs its own switchable supply or reset, not a shared rail.

**Possible follow-ups:** How would you decide between a segmented bus and a single bus with per-node power switching? What's the risk of the clock-pulsing recovery itself causing a problem on a bus with a node that's mid-transaction?

## Q3: You're reviewing a design for a space-deployed system that uses a COTS linear regulator to generate a 1.2V core voltage for an FPGA. The regulator's datasheet shows no radiation data, and the output voltage is specified as 1.2V ±2%. The FPGA requires 1.2V ±5% and draws up to 3A. How would you evaluate this choice and what alternatives would you recommend?

**Answer:** The first thing I'd do is separate the two independent problems: DC accuracy margin and radiation behavior. On DC accuracy alone, ±2% on a 1.2V rail is ±24 mV, and the FPGA's ±5% window is ±60 mV, so there's nominally 36 mV of headroom — but that's before you account for the regulator's load regulation at 3A, its line regulation, temperature drift over the mission, and the sense-point error if the regulator isn't Kelvin-connected at the load. By the time you stack those, the margin may be much thinner than it looks, and a 3A linear regulator also has to dissipate real power, which in vacuum is a thermal problem as much as an electrical one.

On radiation, the absence of data is the real issue. A linear regulator is a relatively simple part, but it still contains a bandgap reference and an error amplifier, both of which are TID-sensitive, and the pass element can be susceptible to single-event transients that show up as output glitches — which on a core rail means the FPGA sees a supply excursion. There's also single-event latch-up risk in any COTS part, and a latch-up on a 3A rail is a serious overcurrent event.

My recommendation would be: first, check whether a rad-tolerant or rad-hard LDO exists in the same footprint and current class — that's the cleanest fix. If not, I'd want at minimum a low-dose-rate TID characterization of the candidate part, and I'd add a supply supervisor on the 1.2V rail so the FPGA is held in reset if the rail leaves its window, plus current limiting or a latch-up protection switch upstream. I'd also reconsider whether a linear regulator is the right topology at 3A in vacuum — a rad-tolerant switching regulator with a well-filtered output may be the better thermal answer, at the cost of more EMI work.

**Possible follow-ups:** How would you set the supervisor threshold given the FPGA's ±5% requirement and the regulator's ±2% spec? What's the argument for and against derating the regulator's output current below 3A?

## Q4: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt that leaves the processor still drawing current and still toggling a heartbeat line, but no longer executing the control loop?

**Answer:** This is the nasty SEFI case, because the usual recovery mechanism — "watchdog sees no heartbeat, resets the processor" — is exactly what fails here. The processor is alive enough to toggle a GPIO but not alive enough to run the control loop, so a naive watchdog is satisfied and the fault persists silently. The test plan has to prove that the recovery logic catches this state, and since you can't inject real radiation on the bench, you have to inject the *behavior*.

The core technique is fault injection in firmware: build a test build that can deliberately enter the stuck state — for example, a command that disables the control-loop task but leaves a low-priority task toggling the heartbeat, or that corrupts the control-loop state machine into a terminal state. Then run the full recovery chain against it and verify the system returns to nominal within the required time, with the event logged.

The design implication is that the heartbeat has to be *semantically meaningful*, not just a toggle. I'd have the control loop itself produce a "loop completed" signature — a counter incremented at the end of each control cycle, or a sequence of expected values — and have the external supervisor check that the signature is advancing and plausible, not merely that a pin is toggling. A windowed watchdog that requires the heartbeat within a time window, plus a challenge-response where the supervisor asks the processor to compute something and checks the answer, catches the "alive but not executing" case much better than a simple toggle.

The test plan should cover: the stuck-heartbeat case, the stuck-heartbeat-with-correct-timing case (the hardest one), recovery time measurement, repeated-injection to check the recovery logic itself doesn't latch up, and verification that the recovery doesn't disturb outputs in a way that's worse than the fault. I'd also test the case where the supervisor itself is the thing that's upset, since a single-point recovery mechanism is its own risk.

**Possible follow-ups:** How would you implement a challenge-response watchdog without adding so much complexity that the checker itself becomes unreliable? What recovery time would you consider acceptable, and how would you derive it?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** The first move is to separate the person from the proposal and make the disagreement about evidence rather than authority. If the engineer has done real work, that work is an asset — I want to use it, not override it. So I'd start by restating their reasoning back to them accurately, including the parts I agree with, and then name the specific assumption I think is under-margined. "You've assumed the reference drift stays within X; I think the low-dose-rate data doesn't support that" is a much more productive framing than "this isn't good enough."

Then I'd try to convert the disagreement into a question that can be answered rather than a position that has to be won. What data would change my mind? What data would change theirs? If the answer is "we don't have that data," that itself is the finding — it becomes a risk item with an owner and a decision date, not a stalemate. In a design review, the goal is a documented decision with a rationale, not unanimity.

I'd also be explicit about the consequence asymmetry. Under-margining in a radiation environment tends to fail late and expensively — in qualification, or on orbit — so the burden of proof sits with the optimistic assumption. I'd say that plainly but without making it personal: "the cost of being wrong here is a re-spin, so I need the margin demonstrated, not asserted."

Finally, I'd give the engineer a concrete path to resolve it — run the analysis, get the part characterized, propose a mitigation that preserves their architecture — and commit to backing the decision if the evidence supports it. That keeps the review constructive and keeps the engineer engaged rather than defensive, which is how you get the right technical answer instead of the loudest one.

**Possible follow-ups:** What would you do if the engineer's evidence came back ambiguous and the schedule didn't allow more testing? How do you make sure a decision like this gets documented so it isn't relitigated in the next review?
