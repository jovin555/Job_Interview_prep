# space-rad-hard — Day 127

## Q1: How would you approach designing a radiation-tolerant analog-to-digital conversion subsystem where the ADC's voltage reference is a COTS part with no radiation data, and the measurement must hold accuracy over a multi-year mission?

**Answer:** The reference is the accuracy anchor for the whole conversion, so I'd treat its unknown radiation behavior as a top-level risk rather than a detail. My approach would be layered. First, I'd characterize what I can: pull whatever TID and ELDRS data exists — even from a similar process or a sibling part — and if the budget allows, run a low-dose-rate biased irradiation on a small sample to bound drift rather than assume it. Second, I'd design the reference so its drift is observable in flight: route it to a dedicated ADC channel through a stable divider, or compare it against a second, independent reference of a different technology, so the system can detect and compensate slow drift rather than silently absorb it. Third, I'd reduce the reference's influence architecturally — use a ratiometric measurement where the sensor excitation and the ADC reference share the same source, so reference drift largely cancels in the ratio. Fourth, I'd add periodic calibration against an on-board transfer standard or a known injected signal, and store calibration coefficients in protected memory. Finally, I'd set an error budget that explicitly allocates a TID-drift term and a margin for ELDRS, and define a drift threshold beyond which the system flags the measurement as degraded rather than reporting a confident wrong number. The key mindset is: if I can't qualify the part, I make the system tolerant of it drifting.

**Possible follow-ups:** How would you distinguish reference drift from sensor drift in flight if both are slow and monotonic? What would make you decide the COTS reference is simply unacceptable and force a qualified part?

## Q2: You're reviewing a design where a junior engineer has used a single-ended, non-redundant analog signal chain — sensor, amplifier, ADC — for a measurement that feeds a control loop. The engineer argues that the digital side already has TMR, so the analog side is "covered." How would you evaluate this argument?

**Answer:** I'd separate the two claims. TMR on the digital side protects against upsets in the logic that processes the number — it does nothing for errors that enter before the first flip-flop. A single-event transient on the amplifier, a corrupted sample-and-hold, or a mux glitch produces a plausible-looking but wrong digital value, and TMR will faithfully vote on three copies of the same wrong input. So the analog front-end is a single point of failure for measurement integrity, and "the digital side has TMR" doesn't cover it. I'd walk through the failure modes: SET in the amplifier producing a transient spike, SET on the ADC reference or sample-and-hold corrupting one conversion, and stuck or drifted analog behavior from TID. Then I'd discuss proportionate mitigation rather than reflexively demanding full triple redundancy — options include a second independent signal path with comparison and plausibility limits, temporal redundancy (multiple samples with median or outlier rejection) where the measurement bandwidth allows, range and rate-of-change sanity checks in firmware, and a watchdog on the control loop so a bad sample can't drive an actuator indefinitely. The point isn't "add TMR everywhere," it's "make sure no single analog fault can silently become a confident wrong control action."

**Possible follow-ups:** If the measurement is time-sensitive and you can't simply re-sample, how does that change your mitigation? How would you decide how much analog redundancy is enough given mass and power constraints?

## Q3: How would you approach designing a fault-tolerant I²C bus for a space-deployed system where multiple sensor nodes share the same bus, given that single-event upsets can corrupt data or cause bus lock-ups?

**Answer:** I'd think about it in three layers: electrical, protocol, and recovery. Electrically, I²C's open-drain lines are vulnerable to a node holding SDA or SCL low and wedging the bus, so I'd want bus isolation — a mux, switch, or segmented bus — so one stuck node can be electrically removed rather than taking down every sensor. I'd also consider bus capacitance and pull-up sizing for the radiation and temperature range, and whether a bus buffer with rise-time acceleration is warranted. At the protocol layer, I'd add integrity: CRC or checksums on payloads, sequence numbers, and acknowledgment discipline, because a corrupted byte that still looks like a valid transaction is worse than a detected error. I'd define a timeout on every transaction so a hung transfer is detected rather than blocking forever. For recovery, I'd implement a bus-clear routine — clocking SCL a fixed number of times to let a stuck slave release SDA, then issuing a stop condition — and escalate to power-cycling or isolating the offending node if that fails. I'd also add a supervisory layer that tracks per-node error rates and quarantines a node that keeps misbehaving. The design goal is graceful degradation: lose one sensor, keep the bus and the rest of the system alive.

**Possible follow-ups:** How would you detect which node is holding the bus low without a scope in flight? What are the trade-offs of segmenting the bus versus keeping it flat and relying on recovery logic?

## Q4: How would you approach designing a radiation-tolerant, high-reliability power feed for a payload that has two independent 28V bus inputs, where the system must survive a shorted or latched load on one feed without losing the other, and must also handle hot-swap events without disturbing the bus?

**Answer:** I'd structure it as two independent input channels that are diode-OR'd or actively OR'd into a common downstream rail, so loss of either feed doesn't drop the load — but with the OR-ing done in a way that a fault on one channel can't propagate backward onto the healthy bus. Each feed gets its own protection: a fuse or eFuse with current limiting, reverse-polarity and reverse-current blocking, and transient suppression. For a latched or shorted downstream load, I'd want per-load current limiting and a latch-up detection-and-retry scheme so a single SEL trips only its branch, not the whole rail. For hot-swap, the critical concerns are inrush into bulk capacitance and the disturbance that a plug-in event injects onto the bus — so I'd use a hot-swap controller with controlled dV/dt, inrush limiting, and fault isolation, plus bulk and EMI filtering sized so the insertion transient stays within the bus's allowed ripple. I'd also think about the OR-ing element's failure mode: an ideal-diode controller is more efficient than a Schottky but adds an active device that itself needs to fail safe. Throughout, I'd define the fault tree — shorted feed, latched load, hot-swap transient, single-channel loss — and verify the architecture survives each without taking down the other feed or the common rail.

**Possible follow-ups:** How would you decide between passive diode-OR and an active ideal-diode scheme given the efficiency and failure-mode trade-offs? How would you test hot-swap behavior on the ground without a live spacecraft bus?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** I'd start by respecting the work — the engineer has done real analysis, so the conversation should be about the analysis, not about who's right. I'd ask them to walk the room through their margin calculation and, specifically, what radiation environment and what failure modes they assumed. Often the gap is an unstated assumption — they sized for nominal TID but not ELDRS, or for SEU rate but not SEL, or they used a typical rather than worst-case number. I'd frame my concern as a question the design has to answer rather than a verdict: "What happens to this node if the reference drifts by X over the mission?" or "What's the consequence if this part latches?" That keeps it collaborative and lets the data drive the conclusion. If we still disagree, I'd propose a concrete way to close the question — a worst-case analysis, a derating check against the applicable guideline, or a small test — rather than pulling rank. I'd also make sure the decision and its rationale get documented, including the dissenting view, so it's traceable later. The goal is a defensible decision the whole team understands, not winning the argument; if the engineer's approach turns out to be adequately margined once we pin down the assumptions, I should be genuinely open to that.

**Possible follow-ups:** What would you do if the engineer's approach is technically defensible but you still believe the risk is too high for the mission class? How do you make sure a junior engineer feels heard without the review becoming a debate about confidence rather than evidence?
