# space-rad-hard — Day 61

## Q1: How would you approach designing a radiation-tolerant analog output stage for a space-deployed system where a single-event transient (SET) on a DAC's reference voltage could cause a momentary but dangerous output spike to an actuator?
**Answer:** The core problem is that an SET is a transient, not a permanent fault, so the mitigation strategy has to act faster than the actuator can respond to a bad command. I'd start by separating the reference path from the signal path: instead of letting the DAC drive the actuator directly from a single reference, I'd use a filtered, buffered reference with a low-pass corner well below the expected SET pulse width, so a short spike gets attenuated before it reaches the DAC's reference pin. On top of that, I'd add an analog clamp or window comparator on the output stage itself — if the output exceeds a safe band for longer than a defined blanking window, the stage is forced to a safe state (e.g., a defined safe voltage or high-impedance) rather than passing the transient through. I'd also consider whether the actuator itself has mechanical or electrical inertia that naturally rejects very short transients, because that changes how much analog filtering is actually needed versus how much is over-design. Finally, I'd want the fault to be latched and reported, not silently absorbed — the system should know an out-of-band event occurred so it can decide whether to retry, hold safe, or flag for ground intervention. The trade-off is always response time versus false-trigger immunity: too aggressive a clamp trips on legitimate fast commands, too slow a clamp lets a dangerous spike through.

**Possible follow-ups:**
- How would you determine the blanking window and clamp thresholds without access to real SET pulse-width data for that specific DAC?
- If the actuator is safety-critical, would you consider a redundant DAC channel with voting, and what would that cost you in board area and power?

## Q2: How would you approach selecting and qualifying a voltage supervisor or reset IC for a space-deployed system, given that most commercial parts are not radiation-characterized?
**Answer:** I'd treat this as a risk-tiered selection problem rather than a binary "rad-hard or not" decision. First, I'd define what the supervisor actually has to do: hold reset through power-up, assert reset on undervoltage, and release reset only when the rail is stable. Then I'd ask what failure of that function looks like — a supervisor that fails to assert reset on a brownout is far more dangerous than one that asserts reset slightly early. For parts with no radiation data, I'd look at the underlying process and topology: a simple comparator-based supervisor with a bandgap reference and a fixed threshold is a very different risk profile from a microcontroller-based supervisor with internal state. I'd check whether the vendor has any total ionizing dose data even informally, whether the package and process are known to be ELDRS-sensitive, and whether the part has a history of use in similar environments. Where data doesn't exist, I'd either budget for a targeted radiation test on a small sample, or design around the uncertainty — for example, using a discrete comparator-plus-reference implementation where I can characterize each element separately, or adding an independent second supervisor with a different topology so a common-mode failure is less likely. The key is documenting the assumption and the residual risk, not pretending the part is qualified when it isn't.

**Possible follow-ups:**
- How would you structure a limited-budget radiation test to get the most decision-relevant data from a handful of samples?
- If you can't test and can't find data, what design techniques let you tolerate an unknown supervisor failure mode?

## Q3: You are reviewing a design for a space-deployed system that uses a COTS FPGA with no radiation characterization. The design uses external configuration memory stored in a parallel NOR flash. How would you evaluate the risk of configuration bit upsets, and what mitigation strategies would you recommend beyond just using TMR on the FPGA fabric?
**Answer:** The first thing I'd separate is where the upsets can occur: in the FPGA's internal configuration SRAM, in the external flash holding the bitstream, and in the interface between them. TMR on the fabric protects the logic, but it does nothing for the configuration memory itself — a single upset there can change routing or logic function in a way that TMR can't vote out, because all three redundant copies may be affected by the same configuration corruption. So I'd want to know the FPGA's built-in configuration error detection and correction capability, if any, and whether it can report and recover from a configuration upset without a full reconfiguration. For the external flash, I'd look at whether the bitstream is stored with error detection (CRC or ECC) and whether the boot process verifies it before loading. Beyond that, I'd recommend a scrubbing or periodic reconfiguration strategy — either partial reconfiguration of the affected region or a full reload from a known-good source — plus a watchdog that detects when the FPGA stops behaving correctly and triggers a reload. I'd also want a golden image or fallback configuration path so a corrupted primary image doesn't leave the system dead. The honest framing is that without radiation data on the FPGA, you're managing an unknown, so the architecture should assume configuration corruption will happen and make recovery automatic rather than relying on the part being immune.

**Possible follow-ups:**
- How would you decide between partial reconfiguration and a full reload, given the mission's availability requirements?
- What would you do if the FPGA vendor's built-in error detection only reports errors but doesn't correct them?

## Q4: How would you approach designing a fault-tolerant communication bus for a space-deployed system where multiple sensor nodes must reliably report data to a central controller, and single-event upsets (SEUs) can corrupt individual messages?
**Answer:** I'd start by deciding what level of integrity the bus actually needs, because that drives everything else. For a sensor bus, the failure modes I care about are corrupted payload, corrupted addressing (message delivered to the wrong place or from the wrong source), and lost messages. The first line of defense is message-level integrity: a CRC strong enough to catch the expected corruption patterns, plus a sequence number or timestamp so the controller can detect gaps and duplicates. That handles corruption and loss detection, but not necessarily correction — for that, I'd consider whether retransmission is acceptable given the latency budget, or whether I need forward error correction for time-critical data. On top of that, I'd think about bus-level robustness: what happens if a node's transceiver is stuck driving the bus, or if an SEU causes a node to transmit continuously? That argues for some form of bus arbitration or timeout that lets the controller isolate a misbehaving node rather than letting it monopolize the bus. I'd also consider whether the physical layer itself needs redundancy — a second bus or a ring topology — but that's a cost/complexity trade-off that depends on how critical continuous data is. The design principle is: detect corruption at the message level, detect misbehavior at the node level, and have a defined recovery path for both.

**Possible follow-ups:**
- How would you handle a node that is alive but sending plausible-looking but incorrect data due to an SEU in its sensor front-end?
- Would you use a time-triggered or event-triggered protocol, and how does that choice interact with SEU tolerance?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?
**Answer:** The first thing I'd do is separate the person from the proposal — the engineer has done real work, and that deserves acknowledgment before any technical critique. I'd start by asking them to walk me through their reasoning and the assumptions behind it, because sometimes the disagreement is actually about a missing piece of information rather than a difference in judgment. If the gap is real, I'd try to make it concrete rather than abstract: instead of saying "this isn't rad-tolerant enough," I'd ask what happens under a specific worst-case condition — a particular TID level, a particular transient — and let the analysis surface the gap. If we still disagree after that, I'd want to move the discussion to a shared basis: what data do we have, what data do we need, and what's the cost of being wrong in each direction? Sometimes the right answer is to test or simulate rather than argue. I'd also be clear about who owns the decision and why — if it's a safety or mission-critical margin issue, I'd explain that the decision isn't mine to make on confidence alone, and that we need evidence or a documented risk acceptance. Throughout, I'd keep the tone collaborative: the goal is the right design, not winning the argument, and a junior engineer who feels heard is more likely to raise concerns early next time.

**Possible follow-ups:**
- What would you do if the engineer's proposal is actually correct and your initial concern was based on an outdated assumption?
- How would you document the disagreement and its resolution so it's useful if the issue resurfaces later in the program?
