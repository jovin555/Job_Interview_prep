# space-rad-hard — Day 111

## Q1: How would you approach designing a radiation-tolerant analog-to-digital conversion subsystem where the ADC's voltage reference is a COTS part with no radiation data, and the measurement must hold accuracy over a multi-year mission?

**Answer:** I'd start by treating the reference as the dominant unknown in the error budget, because in a precision measurement chain the reference drift maps one-to-one onto every conversion result — there's no downstream correction that recovers accuracy you've lost at the reference. The first step is to characterize rather than assume: even a limited test campaign (a few biased/unbiased parts at a representative dose rate, plus a low-dose-rate leg if ELDRS is a concern for the process) gives you a drift bound you can design against, and that's usually cheaper than discovering the problem in flight. If testing isn't feasible, I'd bound the risk analytically from the datasheet's temperature coefficient and topology, then add margin.

Architecturally, I'd consider three levers. First, ratiometric or reference-independent conversion where the topology allows it — if the sensor excitation and the ADC reference share the same source, reference drift largely cancels in the ratio. Second, a periodic in-flight calibration against a more stable secondary standard, such as a precision shunt or a characterized bandgap, with the calibration coefficients stored in protected memory and the calibration cadence chosen so drift between calibrations stays inside the accuracy budget. Third, redundancy at the reference level — two references of different technologies, compared periodically, so a divergent reading flags a suspect part rather than silently corrupting the measurement. I'd also watch the reference's output capacitor and buffer amplifier, since those are often the actual SET-sensitive nodes rather than the bandgap itself.

**Possible follow-ups:** How would you distinguish reference drift from sensor drift during in-flight calibration? What would make you decide a periodic calibration scheme is insufficient and a rad-hard reference is mandatory?

## Q2: You're reviewing a design where a junior engineer has proposed using a single commercial LDO with no radiation data to post-regulate a critical analog rail, arguing that the upstream DC-DC is already rad-tolerant so "the LDO doesn't matter." How would you evaluate this argument?

**Answer:** The argument has a real kernel — a clean upstream rail does reduce what the LDO has to reject — but it conflates "the input is well-behaved" with "the regulator is not a risk." The LDO is itself an active device with a bandgap, an error amplifier, and a pass element, and each of those has its own radiation response: TID-induced reference drift and dropout increase, SETs on the error amplifier that produce output transients, and SEL susceptibility in the process. A rad-tolerant converter upstream does nothing about any of those. It also doesn't help with the failure mode that matters most here — the LDO's own output drifting or glitching and taking the analog rail with it, which is precisely the rail the measurement depends on.

So I'd reframe the review around what the LDO is protecting and what protects the LDO. If the analog rail feeds a precision measurement, I'd want either a radiation-characterized part, or a topology where the LDO's weaknesses are bounded — for example, a shunt reference plus a pass element whose drift is calibrated out, or a filter and clamp network that limits how far an SET transient can propagate into the ADC. I'd also ask for the failure-mode analysis: what does the system do if this LDO's output walks 3% over mission life? If the answer is "the calibration routine catches it," then the calibration routine needs to be shown to actually catch it, with a defined detection threshold and a recovery path. That's the conversation I'd want to have — not "you're wrong," but "show me the error budget with this part's unknowns included, and show me the detection path."

**Possible follow-ups:** If the team can't afford a rad-hard LDO, what design changes would let a COTS part be acceptable? How would you verify the calibration routine actually detects a slow rail drift rather than assuming it does?

## Q3: How would you approach designing a fault-tolerant I²C bus for a space-deployed system where multiple sensor nodes share the same bus, given that single-event upsets can corrupt data or cause bus lock-ups?

**Answer:** I²C is a deceptively fragile choice for a shared bus in a radiation environment, because it has no inherent error detection, no arbitration recovery, and a well-known failure mode where a slave holds SDA low and wedges the whole bus. So I'd design at three layers. At the protocol layer, I'd add a checksum or CRC to every payload, sequence numbers to detect lost or duplicated transactions, and a defined retry policy with bounded attempts — a corrupted read should be retried, not trusted. At the electrical layer, I'd make sure each node can be isolated: individual bus switches or muxes per segment so one wedged node doesn't take down the others, and pull-ups sized so a single stuck-low device can be detected rather than masked. At the recovery layer, I'd implement the standard bus-clear sequence — clock SDA free with up to nine SCL pulses, then issue a STOP — driven by the master's supervisory logic, and if that fails, power-cycle the offending segment through its switch.

The other half of the design is deciding what "the bus is healthy" means. I'd have the master track per-node error rates and timeouts, and treat a node that exceeds a threshold as suspect: quarantine it, keep the rest of the bus running, and report the fault in telemetry. That turns a bus lock-up from a system-level failure into a contained, observable event. I'd also consider whether a differential bus with built-in error detection is a better fit for the critical nodes, and reserve I²C for housekeeping where a lost transaction is tolerable.

**Possible follow-ups:** How would you implement the bus-clear sequence without a dedicated I²C peripheral that supports it? What's the risk of automatic power-cycling a segment, and how would you bound it?

## Q4: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt (SEFI) that leaves the processor still drawing current and still toggling a heartbeat line, but no longer executing the control loop?

**Answer:** The hard part of this test is that the failure is defined by what the processor *stops* doing while everything observable at the pins looks normal — so the test plan has to be built around proving the recovery logic detects a silent hang, not around proving the processor resets. I'd start by defining the detection mechanism explicitly: a heartbeat that only the control loop can produce, with a signature the loop must update (a counter, a sequence, a checksum over loop state) rather than a simple GPIO toggle that a stuck-but-running peripheral could keep generating. The external supervisor compares that signature against a deadline; if it doesn't advance, the supervisor asserts reset independently of the processor.

For the test itself, since I can't inject radiation on the bench, I'd emulate the SEFI deterministically: a debug hook or test firmware that freezes the control loop while leaving the heartbeat generator running, or better, freezes the loop *and* keeps the heartbeat toggling to prove the supervisor isn't fooled by the easy case. I'd run that across the operating envelope — temperature extremes, supply margins, worst-case clock, maximum bus load — because the supervisor's timeout has to be correct at the corner where the loop is slowest, not just at nominal. Then I'd verify the full recovery sequence: reset asserted, processor reinitializes, control loop restarts, state is restored or safely reinitialized, and the event is logged in non-volatile telemetry with enough context to diagnose it later. I'd also test the failure-of-the-recovery-path case — what happens if the supervisor itself is the thing that's upset — and confirm the system fails safe rather than oscillating.

**Possible follow-ups:** How would you set the supervisor timeout so it's tight enough to catch a hang but loose enough not to false-trigger at the worst-case loop timing? How would you test the recovery path when the reset itself is the thing being exercised?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** The first thing I'd do is separate the person from the proposal in my own head, because a confident engineer who's done real analysis is exactly who you want on the team — the goal is to redirect the analysis, not to win the argument. In the review itself, I'd start by having the engineer walk through their margin calculation and their assumptions explicitly, and I'd ask questions rather than pronounce judgment: "What dose are you assuming at end of life? What's the worst-case SET amplitude you're designing against? What happens if this parameter drifts 5% instead of 2%?" Often the gap is a missing assumption rather than a wrong conclusion, and letting the engineer surface it themselves is far more durable than me overriding them.

If the disagreement survives that, I'd move it from opinion to evidence: ask for the margin to be written down against the environment spec, with the unknowns called out, and compare it to the program's margin policy. That makes it a question of "does this meet the documented requirement" rather than "I think you're wrong." If the analysis genuinely can't close the gap, I'd frame the decision as a risk trade with the engineer's input — what would it cost to add margin, what's the exposure if we don't, and who owns that risk. And I'd be explicit that a decision to accept risk is a decision, recorded and owned, not a silent default. Throughout, I'd keep the tone on the design and the data, credit the work that was done well, and make clear that the standard I'm applying is the one I'd apply to my own proposal.

**Possible follow-ups:** What would you do if the engineer's analysis is actually correct and your concern was unfounded? How do you make sure a decision to accept residual risk gets documented and revisited rather than forgotten?
