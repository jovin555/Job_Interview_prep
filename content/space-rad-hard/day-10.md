# space-rad-hard — Day 10

## Q1: How would you approach designing a fault-tolerant power distribution architecture for a satellite payload that must survive a single-event latch-up (SEL) on any single load without losing the entire system?

**Answer:** The core principle is to isolate fault domains so that a latch-up on one load cannot drag down the shared bus or reset healthy loads. I'd start by defining the power tree with per-load current limiting and latching current limiters (or electronic circuit breakers) rather than relying solely on fuses, since fuses are one-shot and don't support recovery. Each load's input would have its own current-sense resistor and a MOSFET-based switch that can be tripped by a dedicated latch-up detection circuit — typically a window comparator that watches for current exceeding a programmable threshold for longer than a few microseconds, which distinguishes a real SEL from normal inrush or transient load steps.

The detection circuit should be independent of the load's own microcontroller, because the load's processor may itself be in a latch-up state and unable to respond. I'd use a simple analog comparator with a latching output that holds the switch off until a command or a timed retry cycle clears it. For the retry strategy, I'd implement an automatic power-cycle sequence: off for a defined period (long enough for the thyristor to recover), then re-apply power with a soft-start ramp to limit inrush. I'd also add a retry counter — after N consecutive failures, the channel stays off and raises a telemetry flag rather than endlessly cycling.

At the system level, I'd use a hierarchical approach: a main bus (e.g., 28V) feeding point-of-load converters, with each converter's output protected by its own latch-up limiter. The key is that the protection must be fast enough to prevent the fault current from causing the bus voltage to sag below the undervoltage lockout of other loads. This means the current limit must trip in microseconds, not milliseconds, and the bus capacitance needs to be sized to hold the voltage up during the detection window. I'd also consider using a "crowbar then disconnect" approach for very high-energy faults, though that's more common at the board level than the payload level.

**Possible follow-ups:** How would you set the current threshold to avoid nuisance trips during normal operation? What happens if the latch-up detection circuit itself is affected by radiation?

## Q2: You are reviewing a design for a space-deployed system that uses a COTS FPGA with no radiation characterization. The design uses external configuration memory stored in a parallel NOR flash. How would you evaluate the risk of configuration bit upsets, and what mitigation strategies would you recommend beyond just using TMR on the FPGA fabric?

**Answer:** The risk here is twofold: the configuration memory (the NOR flash) can suffer bit flips from single-event upsets, and the FPGA's configuration SRAM (if it's SRAM-based) can also be upset in flight. Even if the flash itself is relatively immune to upsets (floating-gate devices are less sensitive to SEUs than SRAM), the configuration bitstream loaded into the FPGA at power-up is stored in SRAM cells that are highly susceptible. A single bit flip in the configuration frame can change routing, logic functions, or I/O standards — potentially causing anything from a silent functional error to a catastrophic short between power and ground.

My evaluation would start with a risk assessment: what is the mission duration, the expected particle environment (orbit altitude, inclination, solar cycle), and the criticality of the functions implemented in the FPGA? If the FPGA is doing housekeeping or non-critical data processing, the risk tolerance is different than if it's controlling a propulsion system. I'd also look at the specific FPGA family — some have built-in configuration scrubbing features, error correction on configuration frames, or the ability to read back and verify the configuration.

For mitigation, I'd layer several approaches. First, configuration scrubbing: a dedicated controller (either the FPGA itself or an external rad-tolerant CPLD/microcontroller) continuously reads back the configuration frames, compares them to a golden copy stored in radiation-tolerant memory (or uses CRC checking), and rewrites any corrupted frames. This is the standard approach for SRAM-based FPGAs. Second, triple-redundant storage of the golden bitstream in the NOR flash — store three copies and vote on readback, or use EDAC (error detection and correction) codes. Third, periodic full reconfiguration — even with scrubbing, a SEFI in the configuration logic may require a full reload. I'd design the system to support a full reconfiguration on command or on watchdog timeout.

I'd also consider whether the FPGA can be replaced with a flash-based or anti-fuse FPGA that is inherently more radiation-tolerant for configuration storage, though those have their own trade-offs in logic density and reconfigurability. Finally, I'd make sure the configuration interface itself is protected — the flash should be on a bus that can be isolated or reset, and the FPGA's configuration pins should have pull-ups/pull-downs to defined states so a glitch doesn't trigger an unintended reconfiguration.

**Possible follow-ups:** How would you decide between scrubbing continuously versus periodically? What metrics would you use to determine whether the COTS FPGA is acceptable at all?

## Q3: How would you approach implementing triple modular redundancy (TMR) for a critical control loop in firmware, such as a PID controller that adjusts a motor speed in a life-support system? What are the practical challenges you would need to address?

**Answer:** TMR in firmware is fundamentally different from TMR in hardware because you're replicating logic in time and memory rather than in physical space. The first question is whether the three "copies" are running on the same processor (spatial redundancy in memory, but temporal correlation in execution) or on three separate processors (true spatial redundancy). For a life-support system, I'd strongly prefer three separate processors with independent clocks and power supplies, because a single-event upset that corrupts the processor's register file or program counter would affect all three copies running on the same CPU simultaneously.

Assuming three independent processors, each runs its own copy of the PID loop, sampling its own sensor input (ideally from three independent sensors, but at minimum from the same sensor through three independent ADC channels). Each processor computes its output, and the three outputs are voted — either in hardware (a majority voter circuit) or by exchanging values over a communication bus and voting in software. The voted output drives the motor.

The practical challenges are numerous. First, synchronization: the three processors must sample the sensor at approximately the same time, or the inputs will differ slightly, and the outputs will diverge even without any faults. This requires a common time base or a synchronization pulse. Second, the voting itself must be fault-tolerant — if you vote in software on one processor, that processor becomes a single point of failure. A hardware voter or a distributed voting scheme (each processor votes on the other two's outputs) is more robust. Third, the PID gains and integrator states must be initialized identically, or the loops will diverge over time. This means the integrator anti-windup and state reset logic must be deterministic across all three copies.

Another challenge is handling disagreement: when one processor's output differs from the other two, you need a strategy. Do you immediately fail that channel, or do you allow transient disagreements (e.g., due to slightly different sampling times) to be tolerated? I'd implement a "soft voting" scheme where the median of the three outputs is used, rather than strict majority voting, because the median naturally handles small variations while still rejecting a single large fault. The system should also log disagreements and flag a channel for maintenance if it consistently disagrees.

Finally, there's the challenge of the actuator itself — the motor driver. If the three processors each have their own output stage, you need a voter at the power level, which is complex. More commonly, the processors vote on a digital command word, and a single (or triple-redundant) driver converts that to motor power. In that case, the driver and its power supply are still single points of failure, and you need to address those separately — perhaps with a second driver in cold redundancy.

**Possible follow-ups:** How would you handle the integrator state in the PID controllers to prevent windup when one channel is temporarily faulted? What happens if the three processors disagree on the sensor reading itself?

## Q4: How would you approach designing a test plan to qualify a COTS microcontroller for use in a space-deployed system, given that the microcontroller is not on any qualified manufacturers list (QML) and you have limited budget for radiation testing?

**Answer:** With limited budget, I can't afford full MIL-STD-883 qualification or extensive heavy-ion testing across all operating conditions, so I need to prioritize based on risk. The first step is a thorough literature review: many COTS microcontrollers have published radiation data from academic groups, other space programs, or the manufacturer's own testing. I'd look for data on the specific die revision, not just the part number, because radiation tolerance can change with process node or mask set changes. I'd also check for any known issues — some parts have documented SEL thresholds or SEFI modes that would be disqualifying regardless of budget.

Next, I'd do a risk assessment to determine which radiation effects are most critical for my application. For a microcontroller, the main concerns are SEL (which can be destructive), SEFI (which can cause lock-up or reset), and SEU in the register file and SRAM (which can corrupt data or program state). TID is usually less of a concern for modern CMOS parts at typical mission doses, but I'd still check the part's total dose tolerance from any available data.

With limited budget, I'd focus testing on the most critical and least-characterized effects. A heavy-ion SEL test is probably the highest priority, because a single SEL event can destroy the part. I'd test a small sample (5-10 parts) at a range of linear energy transfer (LET) values to determine the SEL threshold and cross-section. If the part shows SEL at LET values expected in the mission environment, I'd either select a different part or implement external SEL mitigation (current limiting with latching shutdown and power cycling) — but I'd need to verify that the mitigation is fast enough to protect the part.

For SEU/SEFI, I'd consider a proton test (often cheaper than heavy-ion) to characterize upset rates in the register file and SRAM, and to identify any SEFI modes. Proton testing is particularly relevant for low-earth orbit missions where protons dominate the environment. I'd also do a TID test using a Co-60 source, even if just to a few krad, to confirm the part doesn't have catastrophic total-dose failure (like increased leakage current or loss of functionality) at the mission dose.

Throughout, I'd use a "test like you fly" approach: the test board should replicate the final circuit's decoupling, clock, and I/O loading, because radiation response can depend on operating conditions. I'd also include firmware in the test that exercises the peripherals and memory in the same way the flight software will, so I'm testing the actual usage mode. Finally, I'd document all assumptions and limitations in a radiation test report, and I'd build in margin — if the part's SEL threshold is close to the mission environment's worst-case LET, I'd consider that a high-risk finding and look for alternatives.

**Possible follow-ups:** How would you decide between spending budget on more radiation testing versus adding external mitigation (like current limiting and watchdogs)? What would you do if the part passes testing but has no lot traceability?

## Q5: Imagine you are leading a team designing a radiation-hardened control board for a satellite payload. During a design review, a junior engineer presents a plan to use a single, large FPGA for all digital processing, with TMR applied only to the critical state machines. The engineer argues that applying TMR to the entire design would exceed the FPGA's logic capacity and that the non-critical logic (e.g., configuration registers, housekeeping interfaces) is "safe enough" without redundancy. How would you handle this disagreement?

**Answer:** I'd start by acknowledging the practical constraint — the engineer is right that full TMR on everything may not fit in the FPGA, and that's a legitimate design trade-off. But I'd push back on the assumption that "non-critical" logic is safe without redundancy, because in a radiation environment, a single upset in a seemingly non-critical register can have system-level consequences. For example, a configuration register that controls an I/O standard or a clock enable could, if corrupted, cause a bus contention or a clock glitch that affects the critical logic. Similarly, a housekeeping interface that reports telemetry could silently corrupt data, making it impossible to diagnose other faults.

My approach would be to reframe the discussion around a systematic risk analysis rather than a binary critical/non-critical split. I'd ask the engineer to walk through each functional block and identify: (1) what happens if a single bit flips in that block, (2) what happens if two bits flip, and (3) what the system-level consequence is. This forces a concrete analysis rather than a hand-waving "it's probably fine." I'd also point out that TMR isn't the only mitigation — for non-critical logic, we could use error-detecting codes (parity, CRC) with a reset-on-error strategy, or we could use configuration scrubbing to correct upsets in the FPGA's configuration memory, which protects all logic regardless of whether it's TMR'd.

I'd also challenge the assumption that the FPGA is the right partitioning. If logic density is the constraint, we could split the design across two FPGAs, or move some non-critical functions to a separate, smaller rad-tolerant microcontroller or CPLD. That might give us room for full TMR on the critical functions without sacrificing the non-critical ones. Alternatively, we could use a rad-hard FPGA with more logic capacity, though that has cost and schedule implications.

In terms of handling the disagreement in the room, I'd make it a collaborative engineering discussion rather than a directive. I'd ask the engineer to do a failure modes and effects analysis (FMEA) on the non-critical logic and bring it back to the next review. I'd also bring in the systems engineer or the mission assurance lead to weigh in on the system-level risk tolerance. The goal isn't to win the argument but to make sure the decision is based on data and risk analysis, not on an assumption that "non-critical" means "doesn't matter."

If the engineer's analysis shows that the non-critical logic truly has no system-level consequence when corrupted (e.g., it's a status LED that can be wrong without affecting anything), then I'd accept a reduced mitigation approach for that block. But I'd want that documented in the risk register with a clear rationale, and I'd want a mechanism to detect and recover from upsets in that logic (e.g., periodic re-initialization) so that a single upset doesn't accumulate into a persistent error.

**Possible follow-ups:** How would you decide what level of TMR is "enough" for a given function? What if the schedule doesn't allow time for a full FMEA — how would you prioritize which logic to protect?
