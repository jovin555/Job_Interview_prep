# space-rad-hard — Day 101

## Q1: How would you approach designing a radiation-tolerant, high-reliability power feed for a payload that has two independent 28V bus inputs, where the system must survive a shorted or latched load on one feed without losing the other, and must also handle hot-swap events without disturbing the bus?

**Answer:** I'd start by treating the two feeds as genuinely independent sources that must never be allowed to back-drive each other, so the first architectural decision is how to combine them. The cleanest approach is a diode-OR or ideal-diode (ORing controller) arrangement per feed, so that a fault on one feed cannot pull down the other. If the two feeds are expected to share load, I'd use active ORing with current sharing rather than simple diodes, because diode drops waste headroom and dissipate heat — a real concern in vacuum. The key requirement is that loss of one feed must be a graceful degradation, not a bus collapse.

For the shorted/latched load case, each downstream load branch needs its own protection — a current-limiting switch or eFuse with a latch-off or retry behavior — so a single SEL event trips only that branch and the upstream rail stays up. I'd size the current limit above the load's worst-case inrush but below the point where the rail sags enough to disturb other loads. Coordination matters: the branch protection must trip before the upstream converter's own current limit engages, otherwise one bad load takes the whole rail down.

For hot-swap, the concern is inrush into the bulk capacitance of a newly inserted card. I'd use a hot-swap controller with controlled slew-rate turn-on and a defined dV/dt, plus a safe operating area (SOA) check on the pass FET so it survives the inrush energy. I'd also add transient suppression and EMI filtering at the input per the applicable MIL-STD-461 requirements, and make sure the hot-swap event doesn't inject a transient that trips the other branch's protection.

Throughout, I'd derate the pass elements and the ORing devices conservatively, and I'd think about single-event effects on the protection circuitry itself — a protection FET that latches up is worse than no protection, so the control ICs need to be either rad-tolerant or have a recovery path.

**Possible follow-ups:**
- How would you verify that the branch protection trips before the upstream converter current-limits, and what would you do if the margins overlap?
- What happens if the hot-swap controller itself experiences a single-event transient during turn-on — how would you make the turn-on sequence safe?

## Q2: How would you approach designing a radiation-tolerant analog-to-digital conversion subsystem where the ADC's voltage reference is a COTS part with no radiation data, and the measurement must hold accuracy over a multi-year mission?

**Answer:** The reference is the accuracy anchor for the whole measurement chain, so an uncharacterized reference is a real risk that has to be managed rather than assumed away. I'd start by characterizing what I can: initial accuracy, temperature coefficient, long-term drift, and — critically — whether the part is likely to show enhanced low-dose-rate sensitivity (ELDRS), since many bipolar references drift far more at low dose rate than at the high dose rates used in typical qualification testing. If the vendor has no data, I'd budget for at least a screening irradiation at low dose rate on a sample, because ELDRS behavior is not something you can reason your way to from a datasheet.

Architecturally, I'd avoid making the reference a single point of failure for accuracy. Options include: using a ratiometric measurement where the ADC's reference and the sensor excitation share the same source, so reference drift cancels to first order; adding a stable, radiation-characterized secondary reference or a monitor channel that lets the system detect reference drift and compensate in firmware; and designing the signal chain so the reference's contribution to error is a small fraction of the total error budget, leaving headroom for drift.

I'd also plan for in-flight calibration or cross-calibration against a known stimulus, so that slow drift over the mission can be tracked and corrected rather than simply endured. The key is to treat the reference as a component whose behavior is uncertain, quantify the uncertainty, and design the system so that the uncertainty is either bounded by measurement or compensated by architecture — not left to chance.

**Possible follow-ups:**
- How would you distinguish reference drift from sensor drift in flight, if both are slowly changing?
- What would you do if the low-dose-rate screening showed the reference drifting outside your error budget — what are the fallback options?

## Q3: You're reviewing a design where a junior engineer has used a single-ended, non-redundant analog signal chain — sensor, amplifier, ADC — for a measurement that feeds a control loop. The engineer argues that the digital side already has TMR, so the analog side is "covered." How would you evaluate this argument?

**Answer:** I'd start by acknowledging the engineer's point — TMR on the digital side is genuinely valuable — but explain that it protects a different failure domain. TMR protects against upsets in the digital logic; it does nothing for a single-event transient that corrupts the analog measurement before it ever reaches the ADC. If the analog front-end produces a wrong value, all three TMR lanes will faithfully agree on the wrong value, and the voter will happily pass it through. Redundancy only helps if the redundant copies fail independently, and a single shared analog chain is a single point of failure for the measurement.

I'd frame the discussion around the control loop's tolerance for a bad measurement: how long does a spurious reading persist, what does the loop do with it, and what's the consequence? If the answer is "the actuator gets a wrong command for one sample period," that may be tolerable with filtering and plausibility checks. If it's "the actuator moves dangerously," then the analog chain needs its own mitigation.

Mitigations don't have to mean full triple redundancy of the analog path, which is expensive in board area and power. Options include: a plausibility/range check in firmware that rejects out-of-bounds readings; a second, cheaper measurement channel (different sensor or different amplifier topology) used as a cross-check; a sample-and-hold or track-and-hold with a compare against a redundant sample; or a ratiometric/dual-slope conversion that is inherently more robust to transients. I'd ask the engineer to bring a quantitative argument — what's the expected SET rate, what's the loop's response, what's the consequence — and let the data drive whether the current design is adequate or needs a cross-check channel.

**Possible follow-ups:**
- How would you design a plausibility check that catches a corrupted reading without also rejecting legitimate fast transients in the real signal?
- If a second analog channel is added as a cross-check, how do you decide which one to trust when they disagree?

## Q4: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt (SEFI) that leaves the processor still drawing current and still toggling a heartbeat line, but no longer executing the control loop?

**Answer:** The hard part here is that the failure mode is specifically designed to defeat the naive recovery mechanism — a watchdog that only checks "is the heartbeat toggling?" will be fooled. So the test plan has to verify recovery from a *silent* hang, not just a dead processor.

On the ground, since I can't inject real radiation, I'd build fault-injection hooks into the firmware: a debug command or a test build that deliberately freezes the control loop while leaving the heartbeat toggling, or that corrupts the program counter / stack in a controlled way. Then I'd run the system through its recovery path and verify: does the watchdog (or whatever supervisor) detect the hang within the specified time? Does the reset sequence bring the system back to a known-good state? Does the control loop resume with correct state, or does it come back with stale/corrupted state that causes a wrong output?

I'd also verify the detection mechanism itself is diverse — if the heartbeat is generated by the same code that's hung, it's not a real heartbeat. A better design uses an independent supervisor that checks for *progress* (e.g., a sequence counter that must advance, or a challenge-response from the supervisor) rather than a simple toggle. The test plan should confirm that the supervisor catches the frozen-but-toggling case, and that the recovery is bounded in time and doesn't itself introduce a hazardous transient (e.g., an actuator glitch during reset).

Finally, I'd test the recovery repeatedly and across corner cases — power-on during a hang, hang during a critical control phase, hang while a communication transaction is in flight — because recovery that works in the lab but corrupts state in the field is worse than no recovery.

**Possible follow-ups:**
- How would you design the supervisor so that it detects a frozen-but-toggling processor without adding a second processor?
- What would you check to confirm the control loop resumed with valid state rather than stale state?

## Q5: Imagine you are leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** First, I'd make sure the engineer feels heard — they've done real analysis, and dismissing it out of hand would both demoralize them and risk me missing something. I'd ask them to walk through their margin calculation and the assumptions behind it, and I'd listen for where the disagreement actually lives: is it the radiation environment assumption, the part behavior, the derating philosophy, or the consequence analysis?

Then I'd separate the technical question from the interpersonal one. The technical question is: what's the margin, against what requirement, and what's the consequence if the assumption is wrong? I'd try to make the disagreement concrete and quantitative rather than a clash of opinions — "here's the number I get, here's the number you get, here's why they differ." If the gap is an assumption (e.g., expected dose, or whether a COTS part's behavior is characterized), I'd propose a way to resolve it: pull the radiation data, run a screening test, or check against a similar design's field history.

I'd also be explicit about risk ownership and the decision framework: if the margin is genuinely thin, the question isn't "who's right" but "what does the program need to accept this risk, and who signs off?" That reframes it from a personal argument into a process question. If the engineer's analysis holds up, I'd say so and change my position — that's the point of the review. If it doesn't, I'd explain specifically where the reasoning breaks down and what evidence would change my mind, and I'd give them the chance to go get it rather than forcing a decision in the room.

Throughout, I'd keep the tone collaborative and focused on the design, not the designer, and I'd make sure the outcome — whatever it is — is documented with the rationale, so the decision is defensible later.

**Possible follow-ups:**
- What would you do if the engineer's analysis is sound but the program schedule doesn't allow time to close the margin properly?
- How would you make sure a junior engineer comes out of a disagreement like this more confident rather than less?
