# space-rad-hard — Day 123

## Q1: How would you approach designing a radiation-tolerant power distribution scheme for a payload where several loads share a common upstream rail, and a single-event latch-up (SEL) in any one load must not collapse the rail for the others — and how would you decide where to draw the boundary between "shared" and "isolated"?

**Answer:** The core principle is that a latch-up is a low-impedance fault, so the only way to keep one load's SEL from dragging down a shared rail is to ensure the fault current is interrupted before the upstream source can sag. That means every load branch needs its own current-limiting element — a fuse, a resettable polyfuse, or better, an active current-limit switch with a defined trip threshold and response time — placed as close to the branch point as possible. The upstream rail then only sees the sum of healthy load currents plus a brief, bounded fault transient, not an indefinite short.

Deciding the shared/isolated boundary is a fault-containment and criticality exercise. I'd start by classifying loads: life-critical or control-loop loads get their own isolated branch with independent current limiting and, ideally, their own local regulation so a fault elsewhere can't perturb their supply. Housekeeping or non-critical loads can share a branch, but even then I'd group them so that a single fault takes out only a coherent, non-essential cluster. The boundary should also account for the source's transient response — if the upstream DC-DC can ride through the worst-case fault transient without dropping below the undervoltage threshold of the other loads, sharing is acceptable; if not, isolate. I'd also add a bulk capacitance and, where warranted, an ideal-diode OR-ing stage so that a branch fault doesn't back-feed. Finally, I'd verify the scheme against the actual latch-up current a part can draw (from its SEL test data or a conservative assumption) rather than a nominal load current, because the fault current is what sets the trip threshold.

**Possible follow-ups:** How would you coordinate the trip thresholds and response times of the branch current limiters with the upstream converter's own current limit so you don't get nuisance trips or a cascade? What would you do if a critical load's branch limiter trips and the load is still needed — how does recovery work?

## Q2: You're reviewing a design where a junior engineer has used a single-ended, non-redundant analog signal chain — sensor, amplifier, ADC — for a measurement that feeds a control loop. The engineer argues that the digital side already has TMR, so the analog side is "covered." How would you evaluate this argument?

**Answer:** The argument conflates two different fault domains. TMR on the digital side protects against logic upsets after the signal has been digitized; it does nothing for a single-event transient that corrupts the analog signal before the ADC samples it, or for a SET inside the ADC's sample-and-hold or reference that produces a wrong digital word that TMR then faithfully replicates. In fact, a single-ended chain with no redundancy means a SET on the amplifier output, the ADC input, or the reference can inject an error that the digital voting logic has no way to detect — all three TMR lanes see the same corrupted input. So the digital redundancy is real but it's protecting the wrong layer for this failure mode.

I'd evaluate it by tracing the measurement path and asking, for each stage, what a SET does and whether anything downstream can catch it. Mitigations I'd consider: differential signaling from sensor to ADC to reject common-mode transients; a second, independent signal chain (even a lower-grade one) for cross-checking, with a plausibility or rate-of-change check in firmware; redundant or filtered references; and temporal redundancy — oversampling and median/consensus filtering — where the measurement bandwidth allows. I'd also check whether the control loop can tolerate a single bad sample (e.g., a slew-rate limiter or a "reject outliers" filter) versus whether one corrupted sample causes a dangerous actuator command. The key point to make to the engineer is that redundancy has to be applied at the layer where the fault occurs, and "the digital side is covered" is only true for faults that originate in the digital domain.

**Possible follow-ups:** If a full second analog chain is too expensive in board area or power, what cheaper partial-redundancy options would you propose? How would you decide whether a plausibility check in firmware is sufficient versus needing hardware redundancy?

## Q3: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt (SEFI) that leaves the processor still drawing current and still toggling a heartbeat line, but no longer executing the control loop?

**Answer:** The hard part is that the failure signature is deceptive: the processor looks alive by the two crudest health metrics — current draw and a heartbeat GPIO — so a naive watchdog that just checks "is the heartbeat toggling?" will never fire. The test plan has to prove that the recovery mechanism detects loss of *functional* liveness, not just electrical liveness.

I'd structure it in layers. First, define what "executing the control loop" observably means — a sequence counter updated each loop iteration, a checksum over loop state, an output that changes in a predictable way — and make the recovery logic keyed to that, not to the heartbeat. Second, since you can't inject real radiation on the bench, build a fault-injection harness: firmware hooks or an external fixture that freezes the control loop while leaving the heartbeat task and current draw intact, so you reproduce the exact SEFI signature deterministically. Third, verify the detection path end-to-end: the functional-liveness monitor times out, the recovery action (reset, re-init, switch to redundant controller) executes, and the system returns to a known-good state with the control loop running. Fourth, test the boundaries — how long does detection take, does the recovery itself glitch the actuator output, does a second SEFI during recovery leave the system in a safe state. Fifth, if beam time is available, correlate the bench-injected signature with what a real SEFI looks like to confirm the model is faithful. I'd also include a "stuck heartbeat but loop dead" case explicitly as a named test case so it can't be quietly dropped.

**Possible follow-ups:** How would you design the functional-liveness monitor so it doesn't itself become a single point of failure or get fooled by a partially-executing loop? What's your acceptance criterion for "recovered correctly" — how do you prove the control loop is genuinely running and not just producing plausible-looking output?

## Q4: How would you approach selecting and qualifying a voltage supervisor or reset IC for a space-deployed system, given that most commercial parts are not radiation-characterized?

**Answer:** A voltage supervisor is deceptively critical — it's the part that decides when the processor is allowed to run and when to force a reset — so an upset in it can either hold the system in reset forever or, worse, fail to reset a processor that needs it. Since most commercial supervisors have no radiation data, I'd treat selection as a risk-management problem rather than a datasheet-shopping problem.

First, characterize what the part actually has to do and what failure modes matter: threshold accuracy over TID, any tendency toward SEL, and whether a SET on the output can produce a spurious or missing reset pulse. Then look for parts with at least some radiation pedigree — QML-listed, or with published TID/SEE test data, even if from a different lot — and prefer simple topologies (a comparator with a bandgap reference and a delay) over complex ones with internal state that can be upset. Where no data exists, I'd plan a targeted test: TID to the mission dose plus margin, and heavy-ion or proton SEE testing focused specifically on the reset output behavior, because that's the function that matters. In parallel, I'd design for graceful failure — e.g., an external RC or a redundant supervisor, or a supervisor whose output is combined (AND/OR) with a second independent reset source so a single stuck output can't hold the system hostage. I'd also derate the threshold margins generously and document the residual risk explicitly, because "no data" is not "no risk."

**Possible follow-ups:** If budget only allows one radiation test, would you spend it on TID or on SEE for a supervisor, and why? How would you architect the reset tree so a single failed supervisor can't prevent recovery?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** The first thing I'd do is separate the person from the proposal — the engineer has done real analysis, and dismissing it outright both demoralizes them and risks missing something I haven't considered. I'd start by asking them to walk through their margin calculation and the assumptions behind it, specifically what radiation environment and what part behavior they assumed. Often the disagreement isn't about the arithmetic but about an unstated assumption — e.g., they assumed a datasheet typical, or they assumed the part's behavior is unchanged by TID, or they sized margin against nominal rather than worst-case. Surfacing that assumption is usually more productive than asserting "it's under-margined."

Then I'd reframe the discussion around risk rather than opinion: what's the consequence if the margin is wrong, how detectable is the failure in test, and what's the cost of adding margin versus the cost of a field failure. I'd bring the data — radiation test reports, derating guidelines, the relevant standard — rather than my authority. If we still disagree, I'd propose a concrete way to resolve it: a targeted test, a worst-case analysis, or a design change that adds margin cheaply. And I'd be explicit that the decision is mine to own as lead, but that I want their input to be part of it and I'll document the rationale either way. The goal is that the engineer leaves understanding *why* the decision went the way it did, not feeling overruled.

**Possible follow-ups:** What would you do if, after all that, the engineer's analysis turns out to be correct and your concern was unfounded — how do you handle being wrong in front of the team? How do you make sure a "we'll test it later" resolution doesn't become a way to defer a decision that needs to be made now?
