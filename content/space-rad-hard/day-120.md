# space-rad-hard — Day 120

## Q1: How would you approach designing a radiation-tolerant power distribution scheme for a payload where several loads share a common upstream rail, and a single-event latch-up (SEL) in any one load must not collapse the rail for the others?

**Answer:** The core principle is that a latch-up is a local fault and must be contained locally — the shared rail should never be the thing that carries the fault current. I'd structure the architecture in tiers. The upstream rail is sized and protected for the aggregate load, but each downstream load gets its own current-limited branch — an eFuse, a current-limiting switch, or a latching current limiter — placed as close to the load as practical. The branch protection has to do two jobs: limit steady-state current to a value the load can tolerate without damaging itself, and limit the fault energy delivered into the rail so the upstream bus doesn't sag below the undervoltage threshold of the other loads. That second point is the one people miss — a hard short on one branch can pull the shared rail down transiently even if the branch eventually trips, so the branch limiter needs to act fast enough and the upstream bulk capacitance needs to be sized to ride through the trip delay.

I'd also think about the trip behavior. A latching current limiter that folds back and stays in current limit is often better than one that hard-trips, because a hard trip removes power from a load that might be recoverable, and repeated trip/retry cycles can stress the upstream converter. For loads where recovery matters, I'd add a controlled retry with a defined duty cycle and a fault counter, so a persistent latch-up eventually latches the branch off rather than oscillating. Finally, I'd verify the whole thing against the actual fault scenarios: simulate or bench-test a shorted load on each branch and confirm the shared rail stays within spec for the other loads, and confirm the upstream converter doesn't go into hiccup or foldback.

**Possible follow-ups:** How would you decide the current-limit threshold for a branch whose load has a wide inrush profile? And how would you keep the branch protection itself from being the single point of failure?

## Q2: You're reviewing a design where a junior engineer has proposed using a single commercial LDO with no radiation data to post-regulate a critical analog rail, arguing that the upstream DC-DC is already rad-tolerant so "the LDO doesn't matter." How would you evaluate this argument?

**Answer:** The argument has a kernel of truth — the upstream converter being rad-tolerant removes one class of failure — but it doesn't follow that the LDO is therefore benign. The LDO is in the signal path for the analog rail, so anything that happens to it shows up directly in the measurement. I'd evaluate it on three axes. First, TID: an uncharacterized LDO can drift in output voltage and, more importantly, in dropout and quiescent current over dose; a slow drift on an analog rail is exactly the kind of error that a one-time calibration won't catch. Second, single-event transients: an LDO's error amplifier and pass element can produce output glitches under heavy-ion strike, and a glitch on an analog rail feeding an ADC reference or front-end is a measurement error, not just a supply hiccup. Third, SEL: a commercial LDO may have a latch-up threshold below the mission's LET environment, and a latched LDO on a critical analog rail is a hard failure.

I'd also push back on the framing that "the upstream is rad-tolerant so downstream doesn't matter." Radiation tolerance isn't inherited — each part sees the environment on its own. The right response is to treat the LDO as a component that needs either radiation data, a mitigation (e.g., a rad-tolerant equivalent, or a topology that tolerates its drift), or an explicit, documented risk acceptance with a test plan to characterize it. If the part genuinely can't be characterized, I'd want to know what the fallback is and whether the analog rail's accuracy budget can absorb the worst-case drift.

**Possible follow-ups:** If the LDO can't be replaced, what design changes would let you tolerate its drift? And how would you structure the risk acceptance so it's defensible in a design review?

## Q3: How would you approach designing a fault-tolerant clock distribution network for a space-deployed system that uses multiple FPGAs and ADCs requiring synchronized sampling?

**Answer:** I'd start by separating two concerns: keeping the clocks running, and keeping them synchronized. For keeping them running, the question is what happens when a single-event transient hits the clock net or the clock source. A glitch on a clock line can cause a synchronous logic failure across every device on that net, so the clock tree itself needs protection — typically a rad-tolerant clock buffer or fanout with good SET immunity, and where the budget allows, redundant clock sources with a glitchless switchover. The switchover logic is the tricky part: it has to detect a bad source without itself being fooled by a transient, so I'd want a detection scheme with some persistence (e.g., a missing-edge or frequency-error detector that requires multiple bad cycles before switching) rather than a single-event trip.

For synchronization, if the ADCs need coherent sampling, I'd distribute a common reference clock and use deterministic, matched-length routing so skew is controlled, then handle the residual skew in the digital domain with a known, calibrated offset. If the FPGAs are far apart or on separate boards, I'd consider a source-synchronous or JESD-style interface with its own clock recovery, so a transient on one link doesn't corrupt the sampling phase of the others. I'd also make sure the clock network has a defined behavior on reset — a coherent reset distribution so all devices come up in a known phase relationship, rather than each free-running and hoping the alignment works out.

**Possible follow-ups:** How would you detect that a clock source has degraded rather than failed outright? And what's the trade-off between a redundant clock source and simply making the single source robust?

## Q4: How would you approach designing a test plan to verify that a system recovers correctly from a single-event functional interrupt (SEFI) that leaves the processor still drawing current and still toggling a heartbeat line, but no longer executing the control loop?

**Answer:** The defining feature of this failure is that the usual "is it alive?" indicators lie — current draw and a heartbeat GPIO both look normal, so a naive watchdog that just checks the heartbeat will never fire. The test plan has to specifically exercise that blind spot. On the bench, I'd build a fault-injection harness that can put the processor into exactly that state — either by halting the core in a debugger while leaving peripherals running, or by injecting a corrupted state that stops the control loop but keeps the heartbeat task alive. Then I'd verify that the recovery mechanism actually catches it: the watchdog has to be fed by something that proves the control loop ran, not just that the heartbeat task ran. That usually means a windowed watchdog or a challenge-response scheme where the control loop must acknowledge a changing token within a deadline, so a stuck loop can't satisfy it.

I'd structure the test around the recovery path end to end: detect, reset, reinitialize, and confirm the control loop resumes with correct state. I'd also test the boundary cases — a SEFI that occurs during the reset sequence, a SEFI that recurs immediately after recovery, and a SEFI in the watchdog's own logic. Since I can't inject real radiation on the bench, I'd use fault injection at the register/memory level to emulate the stuck state, and I'd document the mapping between the injected fault and the real SEFI mechanism so the coverage argument is credible. Finally, I'd define pass criteria in terms of time-to-recovery and state integrity, not just "it came back."

**Possible follow-ups:** How would you design the watchdog feed so it can't be satisfied by a stuck loop? And how would you test the case where the SEFI hits the watchdog itself?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** The first thing I'd do is separate the person from the proposal. The engineer has done real analysis, so the review should start by acknowledging that and asking them to walk through their margin calculation — what environment they assumed, what part data they used, and where the numbers came from. Often the disagreement isn't about the conclusion but about an input: they may have used a typical value where I'd want worst-case, or a datasheet number where I'd want radiation test data. Making that explicit turns it from "I think you're wrong" into "let's check the assumptions together," which is a much easier conversation and usually resolves it on the merits.

If the gap is real, I'd frame it in terms of consequence and risk acceptance rather than authority. What happens if the margin is consumed — does the system degrade gracefully or fail hard? Is there a cheap mitigation that closes the gap without redesigning? And if the engineer still believes the design is adequate, I'd ask them to document the risk and bring it to the review board as an explicit acceptance, which is the right mechanism for a judgment call. That keeps the decision with the team and the process rather than with me personally. Throughout, I'd keep the tone collaborative — the goal is a design that survives the environment, not a winner in the room — and I'd make sure the engineer leaves the review feeling their work was taken seriously, because that's what keeps good engineers engaged.

**Possible follow-ups:** What would you do if the review board sided with the engineer and you still believed the margin was inadequate? And how would you make sure a junior engineer's proposal gets a fair hearing in a room full of senior people?
