# space-rad-hard — Day 108

## Q1: How would you approach designing a radiation-tolerant analog signal chain for a spacecraft instrument where the sensor output is a low-level differential signal, and both the amplifier front-end and the ADC reference can experience single-event transients (SETs)?

**Answer:** The core problem is that a low-level differential signal has very little margin against a transient that appears as an offset or spike, so the design has to make SETs both less likely to reach the ADC and detectable when they do. I'd start by treating the front-end and the reference as two separate threat paths.

For the amplifier front-end, the first move is to keep the signal path differential all the way to the ADC and to keep the common-mode operating point well-defined, because a differential topology rejects common-mode transients that a single-ended chain would pass straight through. I'd also add passive filtering — an RC or RCR network at the amplifier input and at the ADC input — sized so the filter's time constant is long relative to the expected SET pulse width but short relative to the signal bandwidth. That doesn't eliminate SETs, but it attenuates narrow transients and gives the downstream logic a chance to reject them. Where the signal is genuinely slow, a longer time constant is cheap insurance.

For the reference, the key insight is that a reference SET is a common-mode-like error across the whole conversion, so it can't be rejected by differential signal routing — it has to be handled at the conversion level. Options include a reference with a large output capacitor and a series resistor to slow transients, a filtered reference buffer, and a conversion scheme that takes a ratiometric measurement so reference drift partially cancels. I'd also consider a dual-reference or reference-checking scheme where the ADC periodically measures a known internal reference and flags a conversion if the reference has moved outside a window.

On top of the analog mitigation, I'd add plausibility checking in firmware: rate-of-change limits, comparison against a redundant or secondary sensor, and rejection of samples that violate physical constraints. The important design principle is that the analog chain should be designed so a single SET produces an out-of-range or implausible sample rather than a plausible-but-wrong one, because the latter is what actually causes a bad control action.

**Possible follow-ups:** How would you decide the filter time constant when the signal bandwidth and the SET pulse width are close together? What would you do if the sensor itself, not just the amplifier, is susceptible to SETs?

## Q2: You're reviewing a design where a junior engineer has proposed using a single commercial LDO with no radiation data to post-regulate a critical analog rail, arguing that the upstream DC-DC is already rad-tolerant so "the LDO doesn't matter." How would you evaluate this argument?

**Answer:** The argument has a kernel of truth — the upstream converter being rad-tolerant does remove some of the risk — but it conflates two different things: the converter's radiation tolerance and the LDO's own behavior under radiation. The LDO is a separate active device with its own bandgap reference, error amplifier, and pass element, and each of those can drift with TID, exhibit enhanced low-dose-rate sensitivity, or produce SETs on its output. A rad-tolerant upstream converter does nothing to protect the LDO's internal reference from drifting, and it does nothing to stop the LDO from passing a transient through to the analog rail.

The way I'd frame the review is: what is the LDO actually protecting against, and what new failure modes does it introduce? If the LDO's job is to clean up switching noise and provide a stable analog rail, then its own stability under radiation is part of the requirement, not an afterthought. I'd ask for the LDO's TID data, its SET behavior, and — critically — what happens to the analog rail if the LDO's reference drifts or its pass element latches. If there's no data, the honest position is that the rail is uncharacterized, and the design either needs characterization testing, a different part with data, or a mitigation that makes the LDO's failure non-critical (for example, a redundant LDO with output ORing, or a monitoring ADC that flags an out-of-window rail).

I'd also point out that "the LDO doesn't matter" is only true if the analog rail's accuracy requirement is loose enough that LDO drift is negligible — and if that's the case, the engineer should be able to show the error budget. If the error budget shows the LDO's drift is a small fraction of the total, the argument may actually hold. So the review outcome isn't "you're wrong," it's "show me the error budget and the radiation data, and if either is missing, here's the mitigation path."

**Possible follow-ups:** How would you structure the error budget to decide whether the LDO's drift is acceptable? If the LDO has no radiation data and there's no budget for testing, what's your fallback?

## Q3: How would you approach designing a fault-tolerant boot sequence for a space-deployed system that uses an SRAM-based FPGA with external configuration memory (flash), where both the FPGA configuration bitstream and the flash memory are susceptible to single-event upsets?

**Answer:** The boot sequence is a chain of trust, and the design principle is that every link in the chain must be verifiable and every failure must be recoverable without ground intervention. I'd structure it in layers.

First, the flash. The configuration bitstream stored in flash can be corrupted by an SEU, so the boot logic can't assume the stored image is good. I'd store the bitstream with a strong checksum or CRC — ideally a cryptographic hash if the boot logic can afford it — and verify it before loading. If the primary image fails verification, fall back to a secondary image stored in a separate region or a separate device. The two images should be written and verified independently so a single upset can't corrupt both.

Second, the FPGA configuration itself. SRAM-based FPGAs lose their configuration on any disruption, and the configuration memory is itself susceptible to upsets during operation, so the boot logic needs a way to detect a bad configuration and reload. That means a configuration controller — either a rad-tolerant microcontroller or a dedicated configuration manager — that can hold the FPGA in reset, reload from flash, and verify that the FPGA came up correctly (for example, by having the FPGA run a self-test and report a known-good signature). If the FPGA fails to configure or fails self-test, the controller retries, then falls back to the secondary image, then to a safe mode.

Third, the controller itself. The thing managing the boot sequence is a single point of failure, so it needs its own watchdog and, ideally, a way to be reset by an independent supervisor. I'd also make the boot sequence idempotent — power-cycling and re-running it should always converge to a known state — and log the boot outcome so the ground can see how many retries occurred and which image was used.

The trade-off to be explicit about is boot time versus robustness: each verification and retry adds latency, and for a payload that needs to come up quickly after a reset, there's a real cost. I'd make the fast path the verified primary image and accept the slower fallback path only when needed.

**Possible follow-ups:** How would you protect the checksum or hash itself from being corrupted? What would you do if both images fail verification?

## Q4: How would you approach designing a radiation-tolerant current-sense circuit for a spacecraft power bus, where the sense resistor itself is exposed to radiation and its value may drift over the mission lifetime?

**Answer:** The sense resistor is the reference for the whole measurement, so its drift directly becomes a gain error in every current reading. The first question is what kind of resistor it is: a metal-foil or bulk-metal-foil resistor has a much lower radiation-induced drift than a thin-film part, and the datasheet may already give a TID drift figure. If the part has data, the design can budget for that drift; if it doesn't, the design has to either characterize it or make the measurement insensitive to it.

The most robust approach is to make the measurement ratiometric or self-calibrating. If the current-sense amplifier's gain is set by a resistor ratio, and the sense resistor and the gain-setting resistor are the same material and experience the same environment, their drifts partially cancel. That's not always possible, but it's worth designing for. A second approach is to add a calibration channel: a known reference current or a precision shunt that's switched in periodically, so the system can measure the sense resistor's actual value in situ and correct for drift. That costs a switch and some firmware, but it turns an uncharacterized drift into a measured, correctable error.

I'd also think about where the sense resistor sits physically. If it's on a board that sees the full dose, its drift is the full drift; if it can be placed in a shielded or lower-dose location, the drift is reduced. And I'd consider a non-resistive sensing method — a Hall-effect or fluxgate current sensor — where the sensing element's radiation behavior is different and may be better characterized, though those bring their own drift and SET considerations.

Finally, the firmware should treat the current measurement as having a known uncertainty that grows over the mission, and the protection thresholds should be set with that uncertainty in mind, so a drifted sense resistor doesn't cause either false trips or missed overcurrent events.

**Possible follow-ups:** How would you implement the in-situ calibration channel without adding a single point of failure? What's the trade-off between a resistive shunt and a Hall-effect sensor for this application?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** The first thing I'd do is separate the person from the proposal. The engineer has done real work, and that work deserves to be taken seriously — if I walk in and say "this is under-margined," I've made it about my judgment versus theirs, and the review becomes adversarial. Instead I'd frame it as a shared question: "Help me understand the margin calculation — what environment are we designing to, and where does this land relative to it?" That invites the engineer to show their reasoning, and it often surfaces either a genuine gap or a piece of information I didn't have.

If the gap is real, I'd want to make it concrete rather than abstract. "Under-margined" is a conclusion; the useful thing is the number. So I'd ask for the derating analysis, the radiation environment spec, and the part's data, and then work through it together — if the part's TID tolerance is X and the mission dose is Y, the margin is Y/X, and that's a fact we can both look at. Often the engineer will see the gap themselves once it's laid out, which is far more durable than being told.

If the engineer pushes back with a real argument — say, that the system has a calibration routine or that the exposure is lower than I assumed — I'd take that seriously and adjust. The goal is the right decision, not winning. If we still disagree after working through the numbers, I'd escalate the decision to the appropriate technical authority or document it as a risk with a named owner, rather than forcing it in the room. And I'd make sure the engineer knows their work was heard and that the disagreement is about the margin, not about them.

**Possible follow-ups:** What would you do if the engineer's manager is in the room and the disagreement becomes public? How do you make sure a documented risk doesn't just become a way to avoid making a decision?
