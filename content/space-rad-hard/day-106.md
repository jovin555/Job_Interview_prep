# space-rad-hard — Day 106

## Q1: How would you approach designing a radiation-tolerant analog-to-digital conversion subsystem where the ADC's voltage reference is a COTS part with no radiation data, and the measurement must hold accuracy over a multi-year mission?

**Answer:** The reference is the accuracy anchor for the whole chain, so I'd treat "no radiation data" as a risk to be actively managed rather than a reason to reject the part outright. First, I'd characterize what I can: initial accuracy, temperature coefficient, long-term drift, and — critically — whether the part's topology suggests ELDRS sensitivity (many bandgap references drift more at low dose rate than at the high dose rates used in typical qualification testing, so a part that looks fine in a fast test can still walk away over a multi-year mission). I'd pull whatever low-dose-rate or proton data exists, even from similar parts in the same family, and if the budget allows, run a small TID screen at low dose rate on a handful of units.

Architecturally, I'd avoid depending on the reference's absolute value. Options include: (1) periodic recalibration against a more trustworthy on-board standard, or against a ratiometric measurement where the same reference feeds both the sensor excitation and the ADC, so reference drift largely cancels; (2) a redundant reference with comparison and voting, so a drifting reference is detected rather than silently trusted; (3) designing the measurement so the accuracy budget tolerates the reference's worst credible drift, with margin. I'd also add health monitoring — the firmware can watch for reference voltage moving outside an expected window and flag it, which converts an undetected slow drift into a detectable fault. The key point is that a calibration routine only helps if the drift is slow and monotonic enough to be tracked; if the reference can suffer single-event transients, calibration doesn't cover that, so SET mitigation (filtering, median-of-N sampling, plausibility checks) has to sit alongside it.

**Possible follow-ups:** How would you distinguish reference drift from sensor drift during in-flight calibration? What would make you decide a redundant reference is worth the board area and power?

## Q2: You're reviewing a design where a junior engineer has used a single-ended, non-redundant analog signal chain — sensor, amplifier, ADC — for a measurement that feeds a control loop. The engineer argues that the digital side already has TMR, so the analog side is "covered." How would you evaluate this argument?

**Answer:** The argument conflates two different fault domains. TMR on the digital side protects against upsets in the logic that processes the measurement — it does nothing about a corrupted measurement arriving at the input. If the analog front-end produces a wrong value, all three TMR lanes will faithfully agree on the wrong number, and the voter will happily pass it through. In fact TMR can make the situation worse by lending false confidence: the system looks redundant while the single point of failure sits upstream of all the redundancy.

I'd walk through the failure modes of the analog chain: an SET on the amplifier output, a transient on the ADC reference, a stuck sample-and-hold, a mux selecting the wrong channel. Then I'd ask what the control loop does with a bad sample — if it's a slow loop with heavy filtering and plausibility limits, a single bad sample may be tolerable; if it's a fast loop driving an actuator, it may not be. The mitigation doesn't have to be full triple redundancy of the analog chain, which is expensive in board area and power. Cheaper options include: a second, dissimilar measurement path for cross-checking; ratiometric or differential sensing to reject common-mode transients; median-of-N sampling in firmware; range and rate-of-change plausibility checks before the value enters the control loop; and a safe-state action if the measurement fails plausibility. The right answer depends on the criticality of the measurement, but "the digital side has TMR" is not an answer to an analog single point of failure.

**Possible follow-ups:** How would you decide how many redundant analog paths are justified for a given control loop? What plausibility checks would you put in firmware before trusting a sample?

## Q3: How would you approach designing a fault-tolerant I²C bus for a space-deployed system where multiple sensor nodes share the same bus, given that single-event upsets can corrupt data or cause bus lock-ups?

**Answer:** I²C is a weak link in a radiation environment because it's open-drain, has no built-in error detection, and a single disturbed node can hold SDA or SCL low and wedge the whole bus. I'd attack it at three levels. At the protocol level: add a CRC or checksum to every payload, use sequence numbers so a duplicated or reordered message is detectable, and require acknowledgment with retry so a corrupted transfer is caught rather than silently accepted. At the electrical level: keep bus capacitance and pull-up values within spec so edges stay clean, and consider a bus buffer or isolator per segment so one wedged node can be electrically isolated rather than taking down the trunk. At the recovery level: implement bus-clear logic — if SDA is stuck low, the master clocks SCL up to nine times to let the stuck device release the line, then issues a STOP; if that fails, power-cycle the offending segment. I'd also give each node a local watchdog so a hung node resets itself rather than waiting for the master.

For critical data, I'd consider a redundant bus (two independent I²C channels with the master cross-checking) or moving the most critical nodes to a more robust protocol like CAN-FD or RS485 with differential signaling and built-in error detection. The trade-off is complexity and harness mass versus robustness; for housekeeping telemetry a single protected I²C bus with good recovery logic is often enough, but for a control-critical path I'd want the stronger physical layer.

**Possible follow-ups:** How would you detect a node that is responding but returning corrupted data rather than failing outright? What are the trade-offs of adding a bus isolator per segment?

## Q4: How would you approach designing a radiation-tolerant power distribution scheme for a payload where several loads share a common upstream rail, and a single-event latch-up in any one load must not collapse the rail for the others?

**Answer:** The core principle is that no single load's fault should be able to pull the shared rail down, so each load needs its own protection between it and the rail — the rail itself should be the last thing to see a fault. I'd put an independent current-limiting switch or eFuse on each load branch, sized so that a latched load trips its own limit and is disconnected before the upstream converter's current limit or the rail's bulk capacitance is dragged down. The trip response has to be fast enough relative to the rail's energy storage and the converter's loop bandwidth; a slow electronic fuse that lets the rail sag for milliseconds may still disturb the other loads. I'd also add per-branch fault reporting so the system knows which load latched and can attempt a controlled retry or leave it off.

Beyond the per-load protection, I'd think about the rail's stiffness: adequate bulk and decoupling so a brief current surge on one branch doesn't couple into the others, and a converter with good load-transient response and, ideally, current-limit behavior that folds back rather than shutting down hard. For SEL specifically, the protection must latch off and require a deliberate re-enable — an auto-retry that keeps re-powering a latched device can cook it. I'd also consider whether the loads have different criticality: the most critical loads might get a dedicated converter or a separate rail so that a fault in a non-critical branch can't even reach them. Finally, I'd verify the scheme with fault-injection testing — short each branch and confirm the rail stays within spec and the other loads keep running.

**Possible follow-ups:** How would you size the per-branch current limit against the load's legitimate inrush? What's the trade-off between latching off a faulted load and auto-retrying it?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** First, I'd separate the person from the proposal. The engineer has done real analysis, so I'd start by acknowledging the work and asking them to walk through their assumptions and margins — often the gap is in an assumption rather than the analysis itself, and hearing it laid out lets everyone see where the disagreement actually lives. I'd frame my concern as a question rather than a verdict: "What's the worst-case radiation environment this has to survive, and how does the design behave there?" That keeps it collaborative and gives the engineer room to either defend the margin with evidence or discover the gap themselves.

If the disagreement persists, I'd try to make it empirical rather than a contest of opinion. Can we bound the risk with existing data — a similar part's test results, a derating calculation, a worst-case analysis? If the margin is genuinely uncertain, I'd propose a path that resolves it: a small radiation screen, a bench test that emulates the worst case, or a design change that adds margin cheaply. I'd also be clear about the decision criteria up front — what margin the program requires and who owns the risk — so the discussion is about meeting a standard, not about who's right. If we still disagree after that, I'd make the call as the lead, document the rationale and the residual risk, and make sure the engineer understands it's a program-risk decision, not a judgment on their work. The goal is a decision the whole team can stand behind and a reviewer who feels heard, not overruled.

**Possible follow-ups:** How would you handle it if the engineer's under-margined approach was actually cheaper and the schedule was tight? What would you do if the disagreement surfaced after the design was already built?
