# space-rad-hard — Day 22

## Q1: How would you approach designing a fault-tolerant analog output stage for a space-deployed system where a single-event transient (SET) on a DAC's reference voltage could cause a momentary but dangerous output spike to an actuator?

**Answer:** The first step is to characterize the actual risk: how long is the transient, how much does the reference deviate, and what is the actuator's response time and tolerance to a brief overdrive? If the actuator can respond fast enough to cause damage, I'd look at mitigation at multiple levels. At the reference itself, I'd use a radiation-tolerant voltage reference with a large bypass capacitor to slow the SET's effect — the capacitor acts as a charge reservoir that holds the reference voltage stable during the transient. I'd also consider a reference with internal filtering or one that's been characterized for SET response. At the DAC output, I'd add a low-pass filter with a time constant longer than the expected SET duration but shorter than the control loop's bandwidth, so legitimate control signals pass through while transients are attenuated. For the highest-risk cases, I'd add a window comparator that monitors the output voltage and, if it exceeds a safe range, triggers a fast analog switch that disconnects the actuator or clamps the output to a safe level. The comparator and switch need to be radiation-tolerant themselves and fast enough to act before the actuator can respond. Finally, I'd verify the design with transient injection testing — pulsing the reference and measuring the output response — to confirm the mitigation actually bounds the output excursion.

**Possible follow-ups:** How would you choose the filter time constant if the control loop bandwidth is close to the SET duration? What if the actuator requires a continuous analog signal and can't tolerate being disconnected?

## Q2: You are reviewing a design for a space-deployed system that uses a radiation-hardened FPGA and a COTS precision voltage reference for an ADC. The reference's datasheet specifies initial accuracy of ±0.1% and temperature drift of ±20 ppm/°C, but has no radiation data. The designer argues that because the reference is "precision" and the system has a calibration routine, radiation-induced drift can be calibrated out. How would you evaluate this approach?

**Answer:** Calibration can correct for static or slowly varying errors, so it's a reasonable tool for total ionizing dose (TID) effects that cause gradual drift — as long as the calibration routine can be run periodically and the reference's drift remains within the ADC's adjustment range. But the argument has a critical flaw: it assumes all radiation effects are slow and monotonic. Single-event transients (SETs) on the reference output are fast, non-deterministic spikes that calibration cannot correct — they occur between calibration points and can corrupt individual measurements. Also, TID drift is not always monotonic or predictable; some references exhibit rebound effects or sudden shifts at certain dose levels. So I'd push back on the "calibration solves it" assumption. I'd recommend: first, check if the reference has any radiation data from the manufacturer or third-party testing, even at higher dose rates; second, if no data exists, consider a small radiation test campaign to characterize TID drift and SET response; third, design the system to detect and reject SET-induced outliers — for example, by taking redundant samples and comparing them, or by adding a window comparator on the reference output. Calibration is part of the solution, but it's not sufficient on its own.

**Possible follow-ups:** How would you design the calibration routine to distinguish between legitimate drift and a SET-induced error? What if the reference's TID drift exceeds the calibration range mid-mission?

## Q3: How would you approach designing a firmware-based fault detection and recovery strategy for a space-deployed system where a single-event upset (SEU) in a shared memory region could corrupt data used by multiple independent control loops?

**Answer:** The key principle is to prevent a single corrupted value from propagating across multiple control loops before it's detected. I'd start by partitioning memory: each control loop gets its own private data region, and shared data is stored in a dedicated, protected area with explicit access rules. For the shared region, I'd use error detection and correction — either hardware ECC if the memory controller supports it, or software-based checksums and triple-redundant storage with majority voting for critical values. Each control loop would read shared data through a validated accessor function that checks the integrity of the data before returning it; if the check fails, the function returns a "data invalid" flag rather than a corrupted value. The control loops would then have defined behavior for invalid data — for example, hold the last known-good output, switch to a safe mode, or trigger a system-level recovery. I'd also implement a periodic background task that scans the shared memory region, verifies checksums, and repairs any corrupted values from redundant copies. The recovery strategy needs to be tiered: local correction for single-bit errors, loop-specific safe mode for persistent corruption, and a system-level reset or reconfiguration if the corruption indicates a more serious fault like a SEFI. Finally, I'd make sure the fault detection and recovery logic itself is simple, stateless, and stored in protected memory, so it can't be corrupted by the same upset that corrupted the data.

**Possible follow-ups:** How would you handle the case where the redundant copies themselves are corrupted by a multi-bit upset? How would you test this strategy to verify it works under realistic fault injection?

## Q4: Imagine you are leading a design review for a space-deployed system that uses a radiation-hardened FPGA for data processing and a COTS DC-DC converter for the 3.3V rail. The converter's datasheet specifies a maximum output voltage of 3.47V under worst-case conditions, and the FPGA's absolute maximum rating is 3.6V. A junior engineer argues that the 130 mV margin is acceptable because "the FPGA will never actually see 3.47V in practice — the converter will typically output 3.3V." How would you handle this disagreement?

**Answer:** I'd acknowledge that the engineer's point about typical operation is technically correct, but I'd explain that worst-case analysis exists precisely because "typical" is not what we design for. The datasheet's 3.47V maximum already accounts for line, load, temperature, and component tolerances — if we ignore it, we're designing to a condition that the manufacturer explicitly says can occur. The 130 mV margin might seem comfortable, but it's not a real margin: it's the difference between two worst-case specifications, and it doesn't account for additional factors like transient overshoot during load steps, ripple, or measurement uncertainty in the actual system. Also, in a space environment, the converter's output could shift due to TID effects, and the FPGA's absolute maximum rating is a hard limit — exceeding it, even briefly, can cause latent damage that doesn't show up immediately. I'd recommend a more rigorous approach: measure the actual output voltage across the full operating range — input voltage variation, load steps, temperature — and verify the worst-case output stays below the FPGA's rating with additional margin. If the measured worst case is close to 3.47V, I'd consider adding a post-regulator or adjusting the converter's feedback network to lower the nominal output voltage, trading a small amount of logic headroom for a larger safety margin. The goal isn't to prove the engineer wrong; it's to ensure the design has real, verified margin, not assumed margin.

**Possible follow-ups:** What if the measured worst-case output is 3.45V — would you accept that, or would you still require a design change? How would you quantify the "additional factors" like transient overshoot and TID drift?

## Q5: How would you approach designing a test plan to verify that a space-deployed system can recover from a single-event functional interrupt (SEFI) that causes the main microcontroller to stop executing code, when you cannot inject actual radiation events during ground testing?

**Answer:** Since we can't create real SEFIs on demand, the test plan has to simulate the effects at the system level. The goal is to verify that the recovery mechanisms — watchdog timers, reset logic, boot sequence — work correctly when the processor is in various failure states. I'd structure the test in three phases. First, fault injection at the processor level: I'd use the debug interface (JTAG or similar) to halt the processor, corrupt the program counter, fill memory with random patterns, or disable interrupts — each simulating a different SEFI signature. For each fault, I'd verify that the watchdog fires, the reset sequence completes, and the system returns to a known-good state within the specified time. Second, fault injection at the power level: I'd simulate the effects of a latch-up or power glitch by momentarily dropping or interrupting the supply voltage, then verify the power-on reset and boot sequence recover correctly. Third, fault injection at the communication level: I'd corrupt the data on external buses — for example, sending garbage on the UART or I²C lines — to verify that the system doesn't hang waiting for valid data and that the communication protocol recovers. Throughout all phases, I'd monitor key health indicators — heartbeat GPIO, telemetry output, memory contents — to confirm the system actually returns to normal operation, not just that the reset pin toggled. I'd also test the recovery path from a cold boot versus a warm reset, since they can behave differently. The test plan should document each fault scenario, the expected recovery behavior, and pass/fail criteria, so the results provide evidence that the recovery mechanisms are effective across the range of plausible SEFI signatures.

**Possible follow-ups:** How would you verify that the recovery mechanism itself isn't corrupted by the same event that caused the SEFI? What if the system recovers but with corrupted state — how would you detect that?
