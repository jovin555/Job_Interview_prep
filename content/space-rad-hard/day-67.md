# space-rad-hard — Day 67

## Q1: How would you approach designing a radiation-tolerant, high-reliability power feed for a payload that has two independent 28V bus inputs, where the system must survive a shorted or latched load on one feed without losing the other, and must also handle hot-swap events without disturbing the bus?

**Answer:** The architecture I'd reach for is a diode-OR (or ideal-diode/ORing-controller) front end per feed, so each 28V input can supply the downstream rail independently and a fault on one feed cannot back-feed or drag down the other. Each feed gets its own protection chain: a fuse or eFuse for hard overcurrent, a current-limiting/hot-swap controller to bound inrush into the downstream bulk capacitance, and reverse-blocking so a shorted feed doesn't pull current from the healthy one. The key sizing trade-off is coordinating the hot-swap current limit against the fuse's I²t curve so a legitimate inrush doesn't nuisance-trip the fuse, while a true latch-up event still clears fast enough to protect the load. For latch-up specifically, I'd want per-load current limiting with a defined trip threshold and a latch-off or retry behavior, plus a way to command a power cycle of just the affected load rather than the whole payload. On the bus side, I'd add input EMI filtering and transient suppression, and I'd verify the ORing and hot-swap behavior with inrush and fault-injection testing — shorting a load and confirming the other feed holds regulation. The whole point is fault containment: one bad load or one bad feed should degrade gracefully, not take the payload down.

**Possible follow-ups:**
- How would you decide between latch-off and auto-retry for a load that trips on overcurrent?
- What would you check to make sure the two feeds don't fight each other during a hot-swap transient?

## Q2: How would you approach designing a radiation-tolerant current-sense circuit for a spacecraft power bus, where the sense resistor itself is exposed to radiation and its value may drift over the mission lifetime?

**Answer:** The core problem is that any sense element's value can shift with total ionizing dose, temperature, and time, so a design that trusts a fixed resistor value will accumulate measurement error over a multi-year mission. I'd start by choosing a sense technology with the most stable, best-characterized behavior under radiation — a metal-foil or bulk-metal-element resistor tends to have far better TID and temperature stability than a thin-film part, and I'd look for radiation data or at least a construction that's known to be robust. Beyond part choice, I'd design the measurement to be ratiometric or self-referencing where possible: for example, compare the sense voltage against a stable reference derived from the same physical principle, so common-mode drift cancels. I'd also add margin in the signal chain — a low-offset, radiation-tolerant instrumentation amplifier with good CMRR — and I'd build in periodic in-situ calibration: inject a known current or use a second, independent sense path and cross-check the two. If the two disagree beyond a threshold, that's a flag that the sense element or its amplifier has drifted. Finally, I'd derate the sense resistor well below its power rating so self-heating doesn't compound the drift, and I'd document the expected drift budget so the control loop's tolerance accounts for it.

**Possible follow-ups:**
- How would you implement the cross-check without adding a second full measurement channel?
- What would you do if the two sense paths disagreed but you couldn't tell which one was correct?

## Q3: You are reviewing a design for a space-deployed system that uses a COTS FPGA with no radiation characterization. The design uses external configuration memory stored in a parallel NOR flash. How would you evaluate the risk of configuration bit upsets, and what mitigation strategies would you recommend beyond just using TMR on the FPGA fabric?

**Answer:** First I'd separate the two failure domains: the SRAM-based FPGA's configuration memory (CRAM) and the external NOR flash that holds the bitstream. CRAM is the more immediate concern — a single upset in a configuration bit can change routing or logic function, and TMR on the fabric doesn't protect the configuration bits that define the fabric itself. So I'd want configuration scrubbing: either internal scrubbers if the device supports them, or an external controller that periodically reads back the configuration and compares against a golden copy, correcting via partial reconfiguration. For the NOR flash, the risk is a corrupted stored bitstream that gets loaded at boot, so I'd store the bitstream with error-detecting/correcting coding, keep a redundant golden image in a separate region or device, and verify the image (CRC/hash) before and after load. I'd also add a configuration watchdog: if the FPGA fails to configure or the design's heartbeat stops, force a reconfiguration from the known-good image. Beyond TMR, I'd consider configuration memory scrubbing, bitstream integrity checks, a fallback image, and possibly a rad-tolerant supervisor to detect and recover from configuration lock-ups. The honest framing is that without radiation data on the COTS part, you're managing risk rather than eliminating it — so the mitigation strategy has to assume upsets will happen and make them recoverable.

**Possible follow-ups:**
- How would you decide how often to scrub, given the cost of readback and reconfiguration?
- What's the difference in risk between an upset during configuration versus an upset during normal operation?

## Q4: How would you approach designing a fault-tolerant I²C bus for a space-deployed system where multiple sensor nodes share the same bus, given that single-event upsets can corrupt data or cause bus lock-ups?

**Answer:** I²C is a weak point in a radiation environment because it's a shared, open-drain bus with no inherent error detection and a well-known failure mode where a glitch leaves a slave holding SDA low, locking the whole bus. So I'd attack it on three fronts. First, protocol robustness: add a CRC or checksum to every transaction, sequence numbers or transaction IDs so a corrupted or duplicated message is detectable, and timeouts on every read so a non-responding node doesn't stall the master. Second, bus recovery: implement the standard clock-pulse recovery sequence (toggle SCL as a GPIO until SDA releases, then issue a STOP) so a stuck slave can be cleared without a full power cycle, and consider a bus switch or mux so a failed segment can be isolated rather than taking down all nodes. Third, physical and architectural: keep bus capacitance and stub lengths controlled, use a bus buffer/repeater if needed, and where criticality justifies it, give the most important sensors a redundant path — either a second bus or a point-to-point link — so a single bus fault doesn't lose the critical measurement. I'd also make sure the master can detect a lock-up and trigger recovery autonomously, since in space there's no one to power-cycle the box.

**Possible follow-ups:**
- How would you distinguish a bus lock-up from a slave that's simply slow to respond?
- Would you put the recovery logic in the master firmware or in dedicated hardware, and why?

## Q5: You're leading a design review where a junior engineer has proposed a solution you believe is under-margined for the radiation environment. The engineer is confident and has done real work on it. How would you handle the disagreement so that the review stays constructive and the right technical decision gets made?

**Answer:** The first thing I'd do is separate the person from the proposal — the engineer has done real analysis, so I'd acknowledge that and engage with the substance rather than just asserting my conclusion. I'd ask them to walk me through their assumptions: what radiation environment did they design to, what data are they relying on, what margin did they apply, and what happens at the corner cases. Often the gap is in the assumptions rather than the analysis, and making those explicit lets us find the disagreement together. If it's a data question — say, no radiation characterization on a part — I'd frame it as a risk question: what's the failure mode, how likely is it, and what's the consequence if it happens? That moves the conversation from "you're wrong" to "here's the risk we're accepting." If we still disagree, I'd propose a concrete way to resolve it: a test, a derating calculation, a second opinion from another engineer, or a documented risk-acceptance decision with the right stakeholders. Throughout, I'd keep it about the design and the mission, not about winning. And I'd make sure the engineer leaves the review feeling heard, because the goal is a good decision and a team that keeps bringing forward analysis — not a team that stops proposing things because they got shot down.

**Possible follow-ups:**
- What would you do if the engineer's approach was technically defensible but you still felt the risk was too high?
- How would you document the decision so it's traceable later?
