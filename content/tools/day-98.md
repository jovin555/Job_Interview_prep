## Q1: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** I'd start by treating the decoder as a specification problem before it's a tooling problem. First I'd get the framing definition nailed down in writing — bit-level: what marks the start of a frame, how many bits the header occupies, where the payload begins, whether there's a length field, what the checksum covers, and what the idle state looks like. Non-byte-aligned headers are the classic trap, so I'd express everything in bit offsets rather than bytes and confirm the bit order (MSB- or LSB-first) against a known-good capture.

Then I'd capture a long trace of known traffic — ideally a transaction where I can predict the payload from the firmware side — and use the analyzer's generic SPI/I2C decoder or raw edge view to sanity-check my bit boundaries against the actual waveform before writing any custom decode logic. Most logic analyzers with a scripting layer (Python-based protocol decoders, or a vendor SDK) let you build a state machine: wait for the start condition, shift in N header bits, parse the length, then emit payload bytes and validate the checksum. I'd build it incrementally and validate each stage against the known-good capture.

The important discipline is to make the decoder fail loudly — flag framing errors, checksum mismatches, and unexpected idle periods rather than silently producing garbage. A decoder that quietly mis-frames is worse than no decoder, because it can send you chasing a firmware bug that doesn't exist. I'd also version-control the decoder script alongside the firmware so it stays in sync with protocol changes, and document the bit-level spec it encodes.

**Possible follow-ups:** How would you handle a protocol where the frame length is encoded in the header but the encoding itself is variable-length? What would you do if the decoder works on your bench capture but produces framing errors on a different unit?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The core principle is that the build configuration is a controlled artifact, not a developer's local preference. I'd start by treating the project file itself as source — checked into version control, reviewed like code, and changed only through a defined process. In Keil that means the target options (optimization level, warnings-as-errors, C standard, floating-point ABI), the scatter file / linker script, and the startup assembly are all explicit and documented, with a short rationale for each non-obvious setting.

For a medical device, the optimization level is a regulatory concern, not just a performance knob: debug builds at `-O0` and release builds at `-O2` can behave differently around timing, volatile access, and undefined behavior, so the level used for formal verification must be the level shipped. I'd pin it per target and add a build-time check — a pre-build step or a script that greps the project file and fails the build if the optimization level or scatter file path doesn't match the released configuration. That turns a silent drift into a hard error.

I'd also make the build reproducible: fixed toolchain version recorded in the project, a documented list of include paths and defines, and a post-build step that emits a map file and a build manifest (toolchain version, git commit, config hash) archived with the release. For auditability, the manifest plus the tagged source is what lets you reconstruct exactly what went into a device. Finally, I'd keep a "known-good" reference build and diff the map file and section sizes against it on every release candidate — unexpected shifts in code or RAM usage are an early warning that a setting or source changed.

**Possible follow-ups:** How would you catch a developer who quietly changed the optimization level locally to "make a bug go away"? What's your approach if the linker script needs to reserve flash for calibration data that must survive firmware updates?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The measurement is a reflection measurement: the tracking generator sweeps a known stimulus, the directional coupler separates the reflected wave from the incident wave, and the analyzer displays return loss (or VSWR) versus frequency. The setup discipline matters more than the math. I'd calibrate the reference plane first — a full one-port calibration (open/short/load, or at minimum a normalization with the coupler and cables in place) so the fixture and cabling are removed from the result. The calibration reference plane must be where the front-end actually connects, otherwise you're measuring your test cable, not the circuit.

Before trusting anything, I'd sanity-check the setup with known standards: measure a 50-ohm termination and confirm it reads as a good match across the band, then a known mismatch and confirm the reading matches expectation. I'd also check the coupler's directivity — a coupler with poor directivity limits the return-loss floor you can resolve, so if the front-end is well-matched you may be measuring the coupler, not the DUT. Sweep power should be low enough not to drive the front-end's active devices into nonlinearity, which would corrupt the impedance reading.

Deciding whether to act: I'd look for consistency across repeated sweeps and across a couple of connection cycles (to rule out connector repeatability), compare against the simulated input impedance from the front-end's SPICE model, and check that any resonance or mismatch lines up with a physical feature (input filter, protection network, cable length). If measurement and simulation disagree, that's a signal to investigate the model or the fixture before changing the design. I'd only act on a result that's repeatable, calibrated at the right plane, and physically explicable.

**Possible follow-ups:** How would you extend this to a differential front-end where you don't have a differential tracking generator? What would a poor directivity in the coupler look like in the data, and how would you work around it?

## Q4: How would you approach setting up a Segger J-Link's RTT (Real-Time Transfer) logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?

**Answer:** RTT is attractive here precisely because it uses the debug probe's memory-access channel rather than a peripheral, so it doesn't consume the UART and doesn't require pins beyond the existing SWD/JTAG connection. The setup is: enable RTT support in the Zephyr configuration, allocate the RTT control block and up/down buffers in RAM, and have the host-side J-Link RTT Viewer or a scripted client poll the buffer. The target writes into a ring buffer; the probe reads it asynchronously.

The timing-perturbation concern is real and is the part I'd design around deliberately. RTT writes are fast but not free — they touch memory and can involve locking — so I'd keep the logging calls off any hard-real-time path and out of interrupt handlers where possible, or use a lock-free single-producer/single-consumer ring buffer so the target never blocks waiting for the host. Buffer sizing matters: if the host stops reading, the target must either drop messages (and count the drops) or block — blocking is unacceptable in a safety path, so I'd configure non-blocking mode with an overflow counter so I can tell when logging was lossy. I'd also measure the actual cost: toggle a GPIO around the logging call and look at it on a scope, or compare worst-case interrupt latency with logging on versus off, to confirm the perturbation is within budget.

For a safety-critical system, I'd treat RTT logging as a debug-only feature gated behind a build configuration, not something present in the released image, and I'd document that gating so it's clear the production build has no logging path at all. That keeps the timing analysis of the shipped firmware clean.

**Possible follow-ups:** How would you capture a crash dump over RTT if the system hard-faults before the host has drained the buffer? What's your approach if the RTT control block can't be found by the host tool?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** First I'd separate the technical issue from the interpersonal one, because they need different handling. Technically, the engineer isn't wrong that peaks show up — but resolution bandwidth and detector mode change the measured amplitude and the noise floor, so a scan with the wrong settings can both miss a marginal failure and misreport the margin on a real one. That's the point I'd make, concretely: show the same emission measured with the correct versus incorrect settings side by side, so the difference is visible rather than asserted. That converts "the peaks show up either way" into "here's why the number matters."

Interpersonally, I'd avoid framing it as the engineer being wrong in front of others. I'd pull them aside, explain the standard's requirement and why it exists, and walk through the settings together so they understand the reasoning rather than just being corrected. The goal is that they can set up the next scan correctly on their own. I'd also own part of it — if the test procedure didn't specify the required settings clearly, that's a process gap I should close, not just an individual mistake.

For the schedule: the lab time is booked and non-refundable, so the practical move is to fix the settings tonight, do a quick verification scan with the correct configuration to confirm the setup is sound, and go into tomorrow's formal scan with a known-good configuration and a written checklist of the required settings. I'd also add that checklist to the lab procedure so this doesn't recur. If there's any doubt the setup can be corrected in time, I'd rather flag it to the lab and reschedule than run a formal scan that produces numbers we can't defend in a regulatory submission.

**Possible follow-ups:** How would you handle it if the engineer pushed back and argued the standard's settings were overly conservative? What process change would you put in place so lab setups are verified before a booked session?
