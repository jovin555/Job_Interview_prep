## Q1: How would you approach setting up a logic analyzer's protocol decoder for a Manchester-encoded sensor bus where the clock is embedded in the data stream, so there's no separate clock line to trigger on — and how would you verify the decoder is actually interpreting the framing correctly before trusting it?

**Answer:** The core challenge with Manchester is that there's no clock to trigger on, so the first job is establishing a stable trigger from the data itself. I'd start by capturing a long, free-running acquisition at a sample rate well above the bit rate — at least 10x, ideally more, since Manchester edges carry both clock and data and you want clean edge timing. For triggering, I'd set up an edge or pattern trigger on a known preamble or sync pattern in the frame rather than trying to trigger on individual bits. Many logic analyzers let you define a multi-bit pattern trigger; if the preamble is a recognizable alternating sequence, that's a good anchor.

For the decoder itself, I'd build a custom protocol decoder rather than trying to force a built-in one. The decoder needs to: detect edges, classify each edge as a rising or falling transition within a bit period, map the transition direction to a bit value (depending on the Manchester convention — IEEE 802.3 vs. Thomas vs. G.E. Thomas, they differ), and then reassemble bits into bytes according to the frame structure. The non-byte-aligned header is the tricky part — I'd handle that by decoding at the bit level first and only grouping into bytes after the header boundary is identified, rather than assuming byte alignment from the start.

Before trusting the decoder, I'd verify it three ways. First, sanity-check against a known-good transmission: if I can get the sensor to send a fixed test pattern or a known command response, I compare the decoded output to the expected bytes. Second, cross-check the bit timing — measure the actual bit period from the captured edges and confirm it matches the expected baud rate within tolerance; if the decoder is misinterpreting edges, the implied bit period will be off. Third, look for framing errors and consistency: a correct decoder should produce clean start/stop boundaries and consistent CRC or checksum results across many frames. If the checksums pass consistently, that's strong evidence the framing is right. I'd also compare against a second capture at a different timebase to rule out aliasing artifacts.

**Possible follow-ups:** How would you handle a decoder that works most of the time but occasionally produces a frame with a bad checksum — how would you distinguish a decoder bug from a real bus error? What would you do if the Manchester convention used by the sensor isn't documented and you have to infer it from captures?

## Q2: How would you approach configuring a Keil uVision project so that the optimization level, linker script, and startup code are locked down and auditable, rather than left at whatever the IDE defaults to?

**Answer:** The goal is reproducibility and traceability — anyone building the project, at any time, should get the same binary from the same source, and an auditor should be able to see exactly what settings produced a released image. I'd treat the project file itself as a controlled artifact and drive as much as possible from explicit, version-controlled configuration rather than IDE defaults.

For optimization level, I'd set it explicitly per target (e.g., a debug target at -O0 or -Og with full debug info, a release target at the chosen production level) and document the rationale — optimization level affects timing, code size, and debug visibility, and for a medical device it needs to be a deliberate, reviewed decision, not an accident. I'd avoid relying on the IDE's "default" because defaults can change between toolchain versions. Where possible I'd pin the toolchain version and record it.

For the linker script and startup code, I'd keep them in source control as explicit project files, referenced by relative path, and reviewed like any other source. The startup code especially — vector table, stack/heap sizing, memory region definitions — should be a known, versioned file, not something regenerated silently. I'd add a build step or script that records the exact compiler/linker invocation, the toolchain version, and a hash of the linker script and startup file into the build output or a manifest, so a released binary can be traced back to its inputs.

For auditability, I'd make the build reproducible: same source + same toolchain + same settings = same output, and I'd verify that by rebuilding and comparing. I'd also keep the project configuration under version control and review changes to it the same way as code changes — a change to optimization level or linker script is a design change and should be traceable. Finally, I'd document the build procedure so it doesn't depend on one engineer's local IDE state.

**Possible follow-ups:** How would you handle a situation where the toolchain vendor's newer version changes default behavior and breaks reproducibility? What would you put in a build manifest to satisfy a regulatory auditor?

## Q3: How would you approach setting up a power integrity simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?

**Answer:** The fundamental problem is that the switching regulator injects ripple and transient currents into a PDN that the analog front-end also depends on, so the simulation has to capture both the regulator's behavior and the PDN's impedance across frequency, and then connect that to the analog circuit's sensitivity.

I'd structure it in layers. First, a DC/transient simulation of the regulator itself — its switching behavior, output ripple, and load transient response — to understand what it's injecting. Second, a PDN impedance extraction: model the planes, vias, decoupling capacitors, and their parasitics, and look at the impedance seen by the analog load across the frequency range of interest. The goal is to find where the PDN impedance peaks (anti-resonances between capacitor values, plane resonances) and whether the regulator's switching harmonics or load transients excite those peaks. Third, couple that to the analog front-end — either through a simplified sensitivity model or by injecting the simulated ripple into the analog supply and observing the effect on the signal chain.

Deciding what's trustworthy is the hard part. I'd validate the model against measurement at each stage: measure the actual regulator ripple and transient response on a prototype and compare to simulation; measure PDN impedance with a VNA or impedance analyzer and compare to the extracted model; measure the analog output noise with the regulator active and compare to the coupled simulation. Where simulation and measurement diverge, I'd investigate the model's assumptions — capacitor derating and ESR/ESL, via inductance, plane modeling simplifications, load model accuracy. I'd only act on simulation results that have been anchored to at least one measurement at the relevant node, and I'd treat unvalidated results as directional guidance rather than design decisions. For a medical device, the conservative approach is to design margin around the validated worst case rather than optimize to the simulation's nominal.

**Possible follow-ups:** How would you model decoupling capacitor parasitics realistically, and what's the risk of trusting datasheet ESR/ESL values? How would you decide whether a PDN resonance is a real problem or a simulation artifact?

## Q4: How would you approach setting up a cross-probe workflow between OrCAD Capture and Cadence Allegro so a layout review can move efficiently between schematic and PCB, and what would you check to confirm the link actually works before relying on it in a review?

**Answer:** Cross-probing depends on the two tools sharing a consistent design database and a live communication channel, so the first step is making sure the schematic and layout are genuinely in sync — same design, same revision, netlist matched. I'd confirm the design is fully annotated and that the PCB was imported/updated from the current schematic, not a stale netlist. A mismatch here is the most common reason cross-probing "works" but points to the wrong thing.

For the setup itself, I'd enable cross-probing in both tools, confirm the communication method (often a shared session or IPC channel) is active, and set the selection preferences so that selecting a component, net, or pin in one tool highlights the corresponding object in the other. I'd also configure which object types cross-probe — sometimes you want component-level, sometimes net-level, sometimes pin-level — and make sure both tools agree.

Before relying on it in a review, I'd run a deliberate verification: pick a known component in the schematic, cross-probe to the PCB, and confirm the correct footprint is highlighted (not just any component); pick a specific net and confirm the correct traces and pins highlight; pick a pin and confirm the right pad highlights. I'd test across a few object types and a few locations, including one near a dense area where a wrong highlight would be easy to miss. I'd also check behavior after any design change — re-annotate or re-import and re-verify, because the link can silently go stale. If the tools are on different machines or the session drops, I'd have a fallback (e.g., searching by reference designator) so the review isn't blocked.

**Possible follow-ups:** What would you do if cross-probing highlights the right component but the wrong pin? How would you handle a review where the schematic and PCB are on different engineer's machines?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has been tasked with setting up the automated firmware test environment for a medical device. On the day before a critical regression test run, you discover that the engineer has configured the test script to skip the safety-critical test cases because they were failing intermittently, and the engineer is confident this is acceptable because "the failures are just timing issues in the test harness, not real bugs." The test results will be used for a regulatory submission milestone. How would you handle this situation?

**Answer:** The immediate priority is that the test run cannot proceed with safety-critical cases silently skipped — that's a regulatory and patient-safety issue, not a scheduling inconvenience. But I'd handle it in a way that addresses the engineer's reasoning rather than just overruling them, because the underlying observation (intermittent failures) may be real and worth understanding.

First, I'd stop and get the facts: which cases are being skipped, what the failure signature looks like, how often it occurs, and what evidence supports the "test harness timing" explanation versus a real firmware issue. I'd make clear that skipping safety-critical cases without documented justification and sign-off isn't a decision an individual engineer can make — it's a change to test coverage that affects the regulatory submission, and it needs to be visible and approved.

Then I'd separate the two questions: is the test harness genuinely flaky, and is the firmware genuinely correct? Those are different problems with different fixes. If the harness has a timing race, that's a real defect in the test environment that needs fixing — a flaky test that's skipped is worse than no test, because it creates false confidence. If the failures might be real firmware behavior, skipping them hides a potential safety issue. Either way, the right move is to investigate, not to skip.

For the immediate milestone, I'd escalate transparently: inform the project lead and quality/regulatory stakeholders that the test run is at risk, explain what's being investigated, and get a decision on how to proceed — options might include fixing the harness quickly, running the cases with the known flakiness documented and a plan to resolve it, or delaying the run. I'd make sure the engineer understands this isn't about distrust but about the standard we hold safety-critical verification to, and I'd involve them in the investigation so they learn how to distinguish harness flakiness from real defects. The key is that nothing gets silently excluded from a regulatory submission.

**Possible follow-ups:** How would you go about determining whether an intermittent failure is a harness race or a real firmware bug? What would you put in place so this situation doesn't recur on the next milestone?
