## Q1: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?
**Answer:** The core problem is that a built-in decoder assumes a known framing convention, so when the frame header isn't byte-aligned, the decoder will either fail to sync or produce garbage. I'd start by treating the decoder as a two-stage problem: a low-level bit/edge capture, then a custom parser on top. First, I'd capture raw transitions at a sample rate well above the bit rate — at least 4–10× the fastest edge rate — so I have enough resolution to reconstruct bit boundaries even if the header starts mid-byte. Then I'd characterize the physical layer independently: measure the idle level, the start condition (a specific edge or a level transition), the bit period, and whether the protocol is LSB- or MSB-first. That tells me the "grammar" the decoder needs. For the decoder itself, most logic analyzer tools let you write a custom protocol decoder in a scripting language (Python, or a vendor-specific SDK). I'd implement a state machine: wait for the start pattern, shift in bits according to the measured bit period, detect the header boundary, then parse the payload fields. The key is to make the decoder tolerant of jitter — use a sampling point near the middle of each bit rather than the edge, and allow a small tolerance window. I'd validate the decoder against a known-good transaction captured from a working device, then against a deliberately corrupted frame to confirm it flags errors rather than silently misparsing. For a medical device, I'd also log the raw capture alongside the decoded output so the decode can be audited later — the decoder is a convenience, not the source of truth.
**Possible follow-ups:** How would you handle a protocol where the bit period changes mid-frame (e.g., a variable-rate header)? What would you do if the decoder works on one unit but not another, and you suspect a timing tolerance issue?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?
**Answer:** The risk with IDE-managed build settings is that they're easy to change accidentally and hard to diff in review — a checkbox flipped in a dialog doesn't show up in a code review the way a source change does. My approach is to treat the build configuration as a versioned artifact, not a set of GUI state. First, I'd move as much as possible out of the IDE's project file and into explicit, text-based files: the linker script as a standalone `.sct` or `.ld` file under version control, the startup code as a checked-in assembly or C file rather than an IDE-generated stub, and the optimization level and preprocessor defines driven by a build script or makefile that the IDE invokes. Where the IDE must own a setting, I'd document why and pin it explicitly rather than leaving it at "default." Second, I'd make the build reproducible: a clean checkout plus a single build command should produce a byte-identical binary (modulo timestamps), which means controlling the toolchain version, the include paths, and any auto-generated files. Third, for auditability, I'd capture the full build log and the map file as release artifacts — the map file is especially valuable because it shows exactly where every symbol landed, which matters for a medical device where you need to prove that calibration data or safety-critical code occupies the intended memory region. Finally, I'd add a check that fails the build if the optimization level or linker script hash doesn't match the expected value, so a silent change can't slip through. The goal is that anyone reviewing the release can reconstruct exactly how the binary was produced without opening the IDE.
**Possible follow-ups:** How would you handle a third-party library that ships as a pre-built binary with its own optimization assumptions? What's your approach to verifying that the linker script actually places safety-critical code in the intended memory region?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?
**Answer:** A tracking generator plus a directional coupler lets you measure return loss (S11 magnitude) across frequency, which you can convert to impedance if you also know the phase — and that's the first caveat: magnitude-only return loss tells you *how much* is reflected, not *what* the impedance is. To get the full picture you either need a VNA or a way to measure phase, so I'd be explicit about what the setup can and can't tell me. The measurement chain matters: the tracking generator output goes to the coupler's input port, the coupler's coupled port goes to the analyzer's input, and the DUT connects to the through port. I'd calibrate the setup first — a full one-port calibration (open, short, load) at the reference plane where the DUT connects, because cable and connector parasitics will otherwise dominate the result at higher frequencies. Then I'd sweep the band of interest and look at return loss. A deep null means a good match at that frequency; a flat, high return loss means the front-end is poorly matched across the band. To decide trustworthiness, I'd check several things: Is the calibration still valid (did anything move)? Is the DUT powered and biased as it would be in operation, since an unpowered front-end can present a completely different impedance? Are there any strong interferers or spurious responses in the environment? And does the result make physical sense given the component values — if the measured impedance at low frequency doesn't roughly match what the input network predicts, something in the setup is wrong. I'd also repeat the measurement with a known reference load to confirm the setup is behaving. Only after the measurement is repeatable and physically consistent would I act on it — for example, to adjust a matching network. For a medical device, I'd document the calibration state and the measurement conditions, because an impedance measurement taken under the wrong bias conditions is worse than no measurement.
**Possible follow-ups:** How would you extend this to measure the front-end's impedance under different input signal levels, since some front-ends are nonlinear? What would you do if the return loss looks fine but the front-end still performs poorly in the system?

## Q4: How would you approach setting up a Segger J-Link's RTT (Real-Time Transfer) logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?
**Answer:** RTT is attractive here precisely because it uses the debug interface's memory access rather than a peripheral, so it doesn't consume the UART. The setup is: the target firmware includes the RTT control block and writes log data into a ring buffer in RAM; the J-Link reads that buffer over SWD/JTAG without halting the CPU. On the Zephyr side, that means routing the logging backend to RTT instead of the default UART backend, and making sure the RTT buffer is placed in a memory region the debugger can access. The timing concern is real: even though RTT doesn't halt the CPU, the logging call itself takes time, and if the buffer fills faster than the host drains it, the firmware either blocks or drops messages depending on the configured mode. For a safety-critical system, I'd want the logging to be non-blocking and bounded — the firmware should never wait on the debugger. That means using a ring buffer with a defined overflow policy (drop oldest or drop newest, and count the drops), and keeping the log messages short and infrequent enough that the buffer doesn't saturate during normal operation. I'd also be careful about where logging is called from: logging from an ISR or a high-priority thread can add jitter to the very timing you're trying to observe. A good practice is to log a compact event ID and timestamp rather than formatted strings, and do the formatting on the host side. To verify the logging isn't perturbing the system, I'd measure a known timing-critical operation with logging enabled and disabled — if the timing changes, the logging is too intrusive and needs to be trimmed or moved off the critical path. Finally, I'd make sure the RTT buffer and control block are excluded from the production build, or at least that the production build doesn't depend on a debugger being attached.
**Possible follow-ups:** How would you handle a situation where the RTT buffer overflows only under a rare, hard-to-reproduce fault condition? What's your approach to correlating RTT log timestamps with an external logic analyzer capture?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?
**Answer:** The first thing I'd do is separate the technical issue from the interpersonal one, because they need different responses. Technically, the engineer isn't wrong that peaks show up either way — but the settings determine whether the measured amplitude is meaningful against a limit line. Resolution bandwidth affects the noise floor and the measured level of broadband versus narrowband emissions, and detector mode (peak, quasi-peak, average) changes the reading depending on the signal's characteristics. A scan with the wrong settings can miss a marginal failure or report a false pass, and for a pre-compliance scan that's the whole point of the exercise. So the settings aren't a preference; they're part of the measurement's validity. I'd explain that distinction rather than just asserting "you're wrong" — showing the engineer the standard's requirement and, if possible, re-running a quick spot check at one frequency with both settings so they can see the difference themselves. That turns it into a learning moment instead of a correction. On the logistics: the lab time is booked and the formal scan is tomorrow, so I'd assess whether the current setup can be corrected in time. If the settings can be fixed and a quick verification scan run before the formal session, we proceed. If not, I'd rather delay or re-book than run a scan whose results we can't trust — a pre-compliance scan that gives false confidence is worse than no scan, because it can lead to a failed formal test later. I'd also look at why this happened: was the engineer given clear test requirements, or were they left to figure out the settings from a tutorial? If it's the latter, that's a process gap I own as the lead, and I'd fix it by documenting the required settings for each test type so the next person doesn't have to guess. The tone throughout would be that we're solving the problem together, not assigning blame — the engineer's confidence is a good trait; it just needs to be paired with a way to verify against the standard.
**Possible follow-ups:** How would you handle it if the engineer pushed back and said the standard's settings are overly conservative for a pre-compliance scan? What would you change in the team's process to prevent this kind of setup error from reaching the day before a booked lab session?
