## Q1: How would you approach setting up a schematic library in Altium Designer so that symbols stay consistent and traceable across a multi-year medical device program, where the same part may be reused across several board revisions?

**Answer:** The core problem is that a schematic library is a living artifact, not a one-time deliverable, and in a regulated program the library becomes part of the design history. I'd start by deciding the library architecture before adding a single symbol: a version-controlled library repository, with symbols organized by functional category rather than by project, so a part used on multiple boards has exactly one authoritative symbol. Each symbol would carry structured metadata in its parameters — manufacturer part number, manufacturer name, a description, and a house part number — because those fields are what later drive the BOM and the traceability matrix. I'd enforce a naming convention that encodes the function and the package, so a reviewer can tell at a glance whether a symbol is a generic resistor or a specific sensor variant.

For consistency, I'd standardize on a symbol grid, pin-length, and text-size convention, and I'd define which pin properties are mandatory (electrical type, pin number, pin name) so that ERC has something meaningful to check. I'd also decide up front how to handle multi-part components and alternate footprints — a part that exists in several package sizes should be modeled deliberately, not by copy-pasting symbols and editing them, because that's where drift creeps in.

Traceability comes from treating the library like source code: every change goes through a review, gets a revision comment, and is committed with a message that says what changed and why. When a symbol is used on a released board, I'd freeze that revision and record which library revision the board was built against, so that if a question comes up years later during an audit, there's a defensible answer. The key discipline is that nobody edits a released symbol in place — they create a new revision and let the change propagate through a controlled update, so the design history stays intact.

**Possible follow-ups:** How would you handle a situation where a symbol needs a correction but it's already used on several released boards? What's your approach to migrating an existing ad-hoc library into this structure without breaking in-flight designs?

## Q2: How would you approach configuring a Keil uVision project so that the optimization level, linker script, and startup code are locked down and auditable, rather than left at whatever the IDE defaults to?

**Answer:** The risk with IDE-managed build settings is that they're easy to change silently and hard to diff, so the goal is to make the build configuration explicit, version-controlled, and reproducible. I'd start by treating the project file itself as a reviewed artifact — it goes into version control alongside the source, and changes to it get the same scrutiny as code changes. Then I'd make the critical settings visible and justified: the optimization level chosen deliberately per build configuration (with the reasoning documented, since optimization can change timing and expose latent bugs), the linker script checked in as a source file rather than generated, and the startup code pinned to a known revision.

For auditability, I'd separate the build configurations clearly — a debug configuration with low or no optimization and full debug info, and a release configuration with the production optimization level — and I'd make sure the release build is the one that produces the artifacts used for verification, so there's no gap between "what we tested" and "what we ship." I'd also record the toolchain version, because a compiler upgrade can change code generation and invalidate prior test results.

The other half is making the settings hard to change accidentally. Where the toolchain supports it, I'd drive as much of the build as possible from a script or a makefile-style invocation rather than relying on someone opening the IDE and clicking through dialogs, so the build is reproducible on a clean machine. And I'd add a check — even a simple one — that verifies the release configuration's key settings before an artifact is accepted, so a stray optimization-level change gets caught before it reaches a test run rather than after.

**Possible follow-ups:** How would you verify that a change in optimization level hasn't altered the behavior of timing-sensitive code? What would you do if you discovered the release build had been using a different linker script than the one under review?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The tracking generator plus directional coupler gives you a scalar reflection measurement — you're looking at return loss across frequency, and from that you can infer how well the front-end's input is matched. The setup matters as much as the instrument: the directional coupler's directivity sets the floor on how small a reflection you can resolve, so I'd pick a coupler whose directivity is comfortably better than the return loss I expect to see, and I'd calibrate out the test setup — cables, connectors, and the coupler's own response — before trusting anything. A reference measurement with a known load (open, short, and a matched termination) tells me whether the system is behaving and where its noise floor sits.

Then I'd sweep the band of interest and look at the return loss curve, keeping in mind that this is a scalar measurement: it tells me magnitude, not phase, so it can't distinguish an inductive mismatch from a capacitive one. If the front-end is a differential or high-impedance input, I'd also think carefully about whether a single-ended 50-ohm measurement is even representative, and whether I need a balun or a different fixture.

Deciding whether to act on the result comes down to three questions: is the measurement repeatable (does it come back the same on a second run and after re-seating connectors), is it consistent with an independent check (a time-domain reflectometry measurement or a simulation of the same network), and is the deviation actually meaningful for the circuit's function? A return loss bump that's well within the front-end's tolerance isn't worth chasing; one that coincides with a band where the sensor signal lives is. I'd only change the design once the measurement is corroborated, because a single scalar sweep with an uncharacterized fixture is exactly the kind of result that sends people chasing phantom problems.

**Possible follow-ups:** How would you extend this to a differential front-end where you can't directly connect a 50-ohm source? What would make you distrust a return-loss measurement even if it looked clean?

## Q4: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** When the framing doesn't map onto a built-in decoder, the first job is to get the physical layer right before worrying about the protocol layer. I'd confirm the sample rate is high enough — comfortably more than the minimum for the clock or bit rate, since a non-byte-aligned header often means short pulses and tight timing that a marginal sample rate will smear. I'd set the threshold and probe placement so the captured waveform is clean, and I'd capture a known-good transaction first, because you can't debug a decoder against data you don't trust.

For the decoder itself, I'd start by writing a simple custom decoder that does the minimum: find the frame boundary using the header pattern, then extract the fields in the order and width the protocol defines, without assuming byte alignment. Most logic analyzer software lets you write a decoder in a scripting language, and the discipline is to make it explicit about bit positions rather than trying to coerce the data into bytes. I'd validate the decoder against a capture where I already know the expected values — either from a reference implementation or from manually decoding the waveform by hand — so that when it later flags something odd, I know the decoder isn't the problem.

The subtle part with a non-standard protocol is that the decoder is only as good as its assumptions about framing, so I'd build in a way to see the raw bits alongside the decoded fields, and I'd test it against deliberately malformed frames to make sure it fails visibly rather than silently misinterpreting. Once the decoder is trustworthy, it becomes a reusable asset for the whole team, which is worth the upfront effort on a protocol that no off-the-shelf tool understands.

**Possible follow-ups:** How would you handle a protocol where the frame length itself is encoded in the header, so the decoder has to be stateful? What would you do if the decoder worked on one board but produced garbage on another with the same firmware?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** The first thing I'd do is separate the technical issue from the interpersonal one, because they need different handling and mixing them makes both worse. Technically, the engineer isn't wrong that the peaks show up either way — the problem is that the amplitude and the comparison to the limit line depend on the settings, so a scan done with the wrong resolution bandwidth and detector can't be used to make a pass/fail judgment. That's the point I'd make, concretely: it's not that the scan is useless, it's that it answers a different question than the one the formal test asks.

I'd sit down with the engineer and walk through why the standard specifies those settings — resolution bandwidth affects how closely spaced emissions are resolved and how the noise floor reads, and the detector mode changes what amplitude gets reported for a given signal. Framing it as "here's what the standard is actually measuring and why" tends to land better than "you did it wrong," and it builds the judgment they'll need next time rather than just correcting this instance. Then we'd fix the configuration together and, if there's time, re-run a quick scan with the correct settings to confirm the setup behaves as expected before the formal run.

On the schedule: the lab time being booked and non-refundable is a real constraint, so I'd prioritize getting the configuration corrected tonight over re-litigating how it happened. If the corrected setup can't be validated in time, I'd rather flag the risk to the project lead and decide whether to proceed with a documented caveat than let a formal scan go out with settings nobody can defend. Afterward, I'd add the correct instrument configuration to the test procedure so it's not dependent on someone remembering it, and I'd make sure the engineer knows the correction was about the process, not about them.

**Possible follow-ups:** How would you handle it if the engineer pushed back in front of the rest of the team? What would you change in the lab's test procedures so this class of mistake is caught before the day of the test?
