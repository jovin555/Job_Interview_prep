## Q1: How would you approach setting up a Gerber and drill-file verification workflow in Gerbv for a medical device PCB, so that fabrication issues are caught before the files leave for the board house?

**Answer:** I'd treat Gerbv as the last human-eyes layer on top of whatever automated checks the CAD tool already ran, not as a replacement for them. The workflow starts with generating a complete, self-consistent output set from a single tagged revision: copper layers, soldermask, silkscreen, paste, board outline, and the drill files (both plated and non-plated, in the format the fab house expects). The first thing I verify in Gerbv is that every layer I expect is actually present and that the layer stack order matches the fab drawing — a missing inner layer or a swapped mask layer is the kind of error that survives a DRC because the CAD tool never knew the output job was incomplete.

Then I load the drill file and check registration against the copper: drill hits should land centered in their pads, and I look specifically at vias and connector pins where a small offset is easy to miss. I check the board outline is a closed contour with no gaps or stray segments, because an open outline can confuse the fab's panelization. I look at soldermask expansion around fine-pitch pads and around any test points, and I confirm silkscreen doesn't overlap pads — silkscreen on a pad is a cosmetic issue on a prototype but a real assembly problem in production. For a medical device I also confirm the revision marking and any required regulatory silkscreen is present and legible.

The key discipline is doing this against a checklist tied to the specific board, not from memory, and recording that the check was performed against a named revision. That record matters for the device history file. I'd also compare the Gerber set against the drill table and the fab drawing one more time as a cross-check, because the most common escape is a mismatch between what the drill file says and what the fabrication notes say.

**Possible follow-ups:** How would you catch a soldermask sliver between two fine-pitch pads that the DRC didn't flag? What would you do if the fab house's CAM engineer reports a discrepancy you can't see in Gerbv?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is that a build is reproducible from the repository alone, with no dependence on whatever state a developer's IDE happens to be in. I'd start by treating the project file itself as a reviewed artifact: the optimization level, the linker script path, the startup file, the include paths, and the preprocessor defines all live in the project and are checked into version control, so a change to any of them shows up in a diff and gets reviewed like code. I'd avoid per-developer overrides entirely — if the IDE supports local settings that shadow the project, I'd disable or standardize them.

For the optimization level specifically, I'd pin it explicitly rather than leaving it at a default, and I'd document why that level was chosen, because optimization interacts with timing, stack usage, and debug visibility. For a safety-related build I'd want the same optimization level used in verification as in release, or a documented justification for any difference. The linker script and startup code I'd treat as source: they live in the repo, they're reviewed, and the memory map they define is checked against the actual part and against any reserved regions such as calibration or bootloader areas. A startup file that silently differs from the one the team thinks is in use is a classic source of hard-to-find initialization bugs.

To make it auditable, I'd drive the build from a script or command-line invocation of the toolchain rather than relying on someone clicking build in the GUI, so the exact compiler version, flags, and inputs are captured. The build output should record the toolchain version and the commit hash. Then anyone can regenerate the same binary later and compare, which is exactly what a regulatory audit or a field-issue investigation will ask for.

**Possible follow-ups:** How would you detect that a developer's local build differs from the official build? What would you do if a compiler upgrade changes code generation and the binary no longer matches the verified one?

## Q3: How would you approach setting up a cross-probe workflow between OrCAD Capture and Cadence Allegro so a layout review can move efficiently between schematic and PCB, and what would you check to confirm the link actually works before relying on it in a review?

**Answer:** Cross-probing is only useful if it's trustworthy, so I'd set it up and then deliberately test it before the review rather than discovering mid-review that selecting a net in the schematic highlights nothing in the layout. The setup itself is about making sure both tools are pointed at the same design database and the same revision — the schematic and the layout must be the matched pair, not a schematic from one branch and a layout from another. I'd confirm the cross-probe session is actually connected, that the selection mode is configured the way the team expects (select in one, highlight in the other, versus bidirectional), and that net, component, and pin-level selection all behave.

To verify it works, I'd pick a few known reference points and test them explicitly: a specific net that I know spans several layers, a component with multiple pins where I want to confirm pin-level selection, and a net that crosses a hierarchy boundary in the schematic so I can confirm the mapping survives hierarchical sheets. If any of those fail to highlight correctly, the link is not reliable and I'd fix it before the review. I'd also check that the highlight colors are visible against the layout's color scheme — a highlight that's technically working but invisible is the same as broken.

The reason I test it deliberately is that a broken cross-probe during a review wastes everyone's time and undermines confidence in the review itself. A two-minute pre-check on a few known nets is cheap insurance. And I'd note in the review record which revision pair was cross-probed, so the review is traceable to a specific schematic-layout combination.

**Possible follow-ups:** What would you do if cross-probing works for nets but not for components? How would you handle a review where the schematic and layout are known to be out of sync?

## Q4: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The measurement is a reflection measurement: the tracking generator sweeps a known signal, the directional coupler separates the incident and reflected waves, and the analyzer displays return loss, which I convert to impedance. The first thing I'd do is calibrate the setup at the reference plane I actually care about — the input to the front-end — using a short, open, and load (and ideally a known thru) so the systematic errors of the coupler, cables, and connectors are removed. Without that calibration, the measurement is dominated by the test setup, not the device.

Then I'd think about whether the front-end is safe to measure this way. An active front-end may not tolerate the tracking generator's output level, and it may present a wildly different impedance depending on whether it's powered and in what state. So I'd confirm the drive level is within the front-end's linear range, decide whether to measure powered or unpowered and document which, and check that the coupler's directivity is adequate for the return loss I expect — a coupler with poor directivity will floor the measurement and make a good match look bad.

The trust decision comes down to a few checks. Does the measured return loss change smoothly and plausibly across frequency, or does it show artifacts that move when I wiggle a cable? Does a known reference — a 50-ohm load, or a deliberately mismatched known impedance — measure as expected through the same setup? Does the result agree with a rough calculation from the front-end's input network? If the measurement is stable, calibration-verified, and consistent with the expected circuit behavior, I'll act on it. If it's marginal or the setup is suspect, I'd rather improve the setup than design to a measurement I don't trust.

**Possible follow-ups:** How would you handle a front-end that can't tolerate the tracking generator's output without distorting? What does poor directivity in the coupler do to your confidence in the result?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** My first move is to separate the two issues: the technical problem (the settings are wrong for a formal scan) and the interpersonal one (the engineer is confident and I don't want to just override them). On the technical side, I'd explain concretely why the settings matter — resolution bandwidth affects the noise floor and the measured amplitude of narrow emissions, and detector mode changes what the analyzer reports for a given signal, so "the peaks show up" is not the same as "the peaks are measured correctly." I'd show the difference on the actual instrument if I can, because seeing the number move is more convincing than being told it should.

On the interpersonal side, I'd frame it as a shared standard rather than my opinion versus theirs: the test standard defines the settings, and the scan has to be defensible, so we're both accountable to the same reference. I'd avoid making it about who's right. Then I'd get practical about the schedule — the lab time is booked, so the question is whether we can reconfigure and re-run within the booked window. If the setup can be corrected quickly, we do that and proceed. If not, I'd rather reschedule or extend the booking than produce a scan that can't be trusted, because a bad scan that has to be redone costs more than a short delay.

Afterward, I'd turn it into a process fix: a written pre-scan checklist that includes the standard's required settings, so the next person doesn't have to rediscover this. That protects the engineer too — they get a clear standard to work from instead of a correction from me.

**Possible follow-ups:** How would you handle it if the engineer felt publicly corrected in front of the team? What would you put on the pre-scan checklist to prevent this recurring?
