## Q1: How would you approach setting up a schematic symbol and footprint library in KiCad for a medical device project where the same component appears in multiple variants — different package sizes, tolerance grades, or temperature ratings — so the library stays maintainable and traceable across revisions?

**Answer:** The core problem is that a naive library creates one symbol per variant, which explodes the symbol count and makes it easy to pick the wrong part. A better structure separates the *logical* component from its *physical* variants. I would create one generic symbol per functional device (e.g., a precision op-amp) with a generic pin map, and then attach multiple footprints to that symbol as alternate footprint assignments. The variant selection then happens at the schematic level via the footprint field, not by choosing a different symbol. For traceability, each footprint and symbol carries metadata fields — manufacturer part number, tolerance grade, temperature range, and a revision identifier — stored as KiCad symbol/footprint properties rather than free-text notes, so they survive library updates and can be exported into a BOM. I would keep the library in a Git repository with a defined review process, tag releases, and treat any change to a symbol or footprint as a change-controlled event, because in a medical device context a footprint change can invalidate prior layout validation. Finally, I would add a library audit step — a script or checklist that flags symbols with missing metadata, duplicate names, or footprints that don't match the declared package — and run it before each release.

## Q2: How would you approach setting up a power integrity (PI) simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?

**Answer:** I would start by defining what question the simulation actually needs to answer — usually "does the analog rail see unacceptable ripple or impedance at the frequencies the sensor cares about?" — rather than trying to simulate everything. The workflow: extract the power distribution network geometry (planes, traces, vias, decoupling placement) into the PI tool, assign realistic component models (capacitor ESR/ESL, regulator output impedance, load current profiles), and run an impedance sweep plus a transient or AC analysis at the analog front-end's input. The key discipline is model fidelity: a simulation is only as trustworthy as its parasitics and its source/load definitions. I would validate the model against a measurement — for example, injecting a known load step and comparing the simulated rail response to a scope measurement at the same node — before trusting any result. Results I would act on are ones that are consistent across parameter sweeps (e.g., decoupling value, via count) and that reproduce a physically explainable mechanism. Results that only appear under one narrow set of assumptions, or that depend on parasitics I can't bound, I would treat as directional and confirm on the bench.

## Q3: How would you approach configuring a Segger J-Link for a Zephyr RTOS target where an automated test harness needs to flash the device, run a test sequence, and capture a crash dump without manual intervention — and what failure modes would you design around?

**Answer:** I would drive the J-Link through its command-line tooling and scripting interface rather than a GUI, so the harness can call it deterministically. The sequence is: connect and verify target voltage and SWD/JTAG link, erase and flash the image, reset and run, then either poll for a test-complete signal or capture output over RTT/serial. For crash capture, I would configure the debugger to halt on fault, read the fault status registers and the stacked frame, and dump RAM regions of interest to a file the harness can parse. The failure modes I would design around are the ones that make automated bring-up flaky: target not powered or wrong voltage reference, SWD pins repurposed by firmware after boot (so the debugger loses the link), clock configuration that changes the debug interface timing, flash protection or readout protection left enabled, and the target resetting mid-sequence so the harness reads stale state. I would add explicit timeouts, retries with a full power-cycle, and a pre-flight check that confirms the debugger can halt the core before flashing. I would also log the raw debugger output so a failure can be diagnosed after the fact rather than only reported as "test failed."

**Possible follow-ups:**
- How would you capture a crash dump if the firmware disables the debug interface early in boot for security or power reasons?
- What would you change in the harness to distinguish a genuine firmware crash from a debugger connection failure?

## Q4: How would you approach using a spectrum analyzer with a near-field probe to locate the source of a radiated emissions failure at a specific frequency during pre-compliance testing, and how would you confirm which component is responsible?

**Answer:** I would work from the board outward. First, characterize the failing frequency precisely — its exact value and whether it drifts with load or operating mode — because that narrows the candidate sources: a switching regulator's fundamental or harmonic, a clock harmonic, or a data-bus edge rate. Then, with a near-field probe (both H-field loop and E-field stub), I would scan systematically across the board in a grid, logging amplitude at the failing frequency, and build a spatial map of where the field is strongest. The hotspot usually points to the aggressor or the coupling path. To confirm the source rather than just the hotspot, I would perturb it: change the switching frequency slightly and see if the emission moves, disable or gate the suspect clock and see if the emission disappears, or add a temporary snubber or ferrite and observe the effect. Confirmation means the emission responds predictably to a change in the suspected source. I would also check whether the field is common-mode or differential-mode by comparing probe orientation and by using a current probe on cables, since that changes the mitigation strategy.

**Possible follow-ups:**
- How would you distinguish a near-field hotspot that is the source from one that is simply a coupling path or a resonant structure?
- What would you do if the emission only appears when the enclosure is assembled, and the near-field scan on the bare board looks clean?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the Altium Designer output job configuration for a medical device PCB release, and you discover the fabrication outputs are missing the drill table and the assembly drawings reference an outdated revision of the schematic. The board house is expecting the files tomorrow, and the engineer is confident the outputs are complete because "the Gerbers look fine." How would you handle this situation?

**Answer:** The immediate priority is the release, so I would separate the technical fix from the conversation. Technically, I would verify the output job against a release checklist — Gerbers, drill files and drill table, assembly drawings tied to the correct schematic revision, BOM, and any fabrication notes — regenerate the missing and stale outputs, and do a cross-check that the assembly drawing revision matches the schematic revision actually being released. If the board house deadline can still be met with corrected files, we send corrected files; if not, I would escalate early rather than let a known-incomplete package ship, because a missing drill table or a mismatched assembly revision can cause real manufacturing and traceability problems on a medical device. On the people side, I would avoid framing it as "you were wrong." The engineer's confidence came from checking the Gerbers, which is a reasonable but incomplete check. I would walk through the release checklist with them, show specifically what was missing and why it matters, and then work with them to turn that checklist into a documented, reusable output job template so the same gap can't recur. The goal is a corrected release and a stronger process, not a reprimand.

**Possible follow-ups:**
- How would you build a release checklist that catches this class of error without becoming so long that people skip it?
- If the board house had already started fabrication with the incomplete package, what would your escalation and containment steps be?
