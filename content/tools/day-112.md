## Q1: How would you approach setting up a hierarchical schematic in Altium Designer so that a shared power supply block is reused across several board variants, and how would you keep the variants from drifting apart over time?
**Answer:** The core discipline is to make the reused block a single source of truth rather than a copy. I'd build the power supply as its own schematic sheet with a clearly defined, minimal interface — input rails, output rails, enable/sequencing signals, and any status lines — exposed through sheet entries or ports, and I'd document that interface in a short spec so downstream sheets depend only on the contract, not on internal component references. For variants, I'd avoid duplicating the sheet; instead I'd drive the differences through parameters and variant management (or, where the differences are structural, through controlled alternate parts and DNP settings) so the same sheet instance is used everywhere. To stop drift, the block lives in a versioned library or a shared repository with its own revision history, and each project references a specific revision rather than a floating copy. I'd also add a review checklist item that any change to the block's interface triggers a re-check of every consuming project, and I'd keep the block's own ERC/DRC clean so problems surface at the source. The trade-off is upfront discipline versus long-term maintainability — for a multi-year program with several board revisions, that discipline pays for itself.
**Possible follow-ups:** How would you handle a case where one variant genuinely needs a different topology in that block, not just different part values? What would you put in the block's interface spec to make it safe to reuse without re-reading the whole schematic?

## Q2: How would you approach configuring a Segger J-Link for unattended automated testing on a Zephyr RTOS target, where the harness must flash the device, run a test, and capture a crash dump — and what failure modes would you design around?
**Answer:** I'd drive the J-Link through its command-line/scripting interface rather than a GUI, so the whole sequence is reproducible and can run in CI. The flow is: reset and halt, program the image, verify, reset and run, then let the test execute while the harness monitors for completion — either via a test-complete signal the firmware emits or by polling a known memory location. For crash capture, I'd pre-configure the debugger to halt on fault exceptions and dump the relevant core registers, fault status registers, and a region of RAM/stack, so the dump is captured without needing firmware print statements. Failure modes I'd design around: the target not being detected (stale connection, wrong interface speed, target held in reset) — so the script needs bounded retries and a clear "no target" error rather than hanging; flash programming failures or verify mismatches — fail loudly, don't proceed to run; the test hanging — a watchdog timeout in the harness that resets the target and marks the run failed; and the debugger session being left open, blocking the next run — so every path must release the probe cleanly. I'd also make the harness log the exact firmware image hash and probe serial number per run, so a failure can be tied to a specific build and a specific piece of hardware.
**Possible follow-ups:** How would you distinguish a genuine firmware crash from a debugger-induced halt in the captured dump? What would you do if the same test passes interactively but fails only in the automated run?

## Q3: How would you approach using a spectrum analyzer with a near-field probe to confirm whether a radiated emission at a particular frequency is coming from a switching regulator or from a digital clock, and how would you decide the measurement is trustworthy enough to act on?
**Answer:** The first step is arithmetic, not measurement: list the candidate sources and their harmonics — the switcher's fundamental and its harmonics, and each clock's fundamental and harmonics — and see which ones actually land on the failing frequency. That narrows the search before I touch the probe. Then I'd use a small shielded loop or H-field probe and scan methodically over the board, starting near the suspect components, watching the amplitude at the frequency of interest. The key discriminator is correlation: if I can change the switcher's operating point — load, or where safe, its switching frequency — and the emission tracks that change, that's strong evidence for the switcher; if it tracks a clock enable/disable or a clock divider change instead, it's the digital source. I'd also look at the harmonic family: a switcher tends to show a broad comb of harmonics at its fundamental spacing, while a clock shows a narrower, more regular comb. On trustworthiness: I'd confirm the probe and cable are appropriate for the frequency, check that the analyzer isn't being overloaded (reduce gain, confirm the peak scales sensibly), verify the result is repeatable across probe placement and board orientation, and make sure I'm not just seeing ambient pickup by moving the probe away and confirming the signal drops. Only when the correlation and the spatial localization agree would I act on it.
**Possible follow-ups:** How would you tell a near-field reading caused by the probe's own resonance from a real board emission? If the emission tracks both a clock and the switcher, how would you separate the two contributions?

## Q4: How would you approach setting up a KiCad project so that schematic, PCB, footprints, and 3D models stay consistent across revisions, and how would you catch footprint-to-schematic mismatches before fabrication?
**Answer:** I'd treat the project as a set of versioned artifacts with a single authoritative library source. Footprints and symbols live in project-local or team libraries under version control, not scattered across personal libraries, and every component in the schematic references a specific library footprint by name. The 3D models are referenced by path relative to the project so they travel with it. For consistency across revisions, I'd commit the schematic, PCB, libraries, and a generated BOM together, tag releases, and keep a short revision note describing what changed. To catch mismatches before fabrication, I'd lean on KiCad's own checks first — run ERC on the schematic and DRC on the board, and specifically use the footprint-vs-schematic comparison (the "update PCB from schematic" diff and the footprint assignment check) so any part whose footprint changed or is unassigned shows up. I'd also do a visual cross-check: a footprint courtyard/pad-count sanity pass against the datasheet for any new or changed part, and a 3D view to catch a part that's the wrong package. Finally, a pre-release checklist that includes "all footprints assigned and verified," "3D models present for all mechanical-critical parts," and "BOM matches schematic" catches the class of error that DRC alone won't.
**Possible follow-ups:** How would you handle a part that exists in two package variants that share a symbol? What's the risk of relying only on DRC to catch a wrong footprint, and what would you add?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has configured the lab's spectrum analyzer for an EMI pre-compliance scan using settings copied from a tutorial — wrong resolution bandwidth, wrong detector, and no correction for antenna and cable losses. The engineer is confident because "the peaks show up either way," and the formal scan is booked for tomorrow. How would you handle this situation?
**Answer:** I'd treat it as a coaching moment first and a schedule problem second, and I'd be careful not to make the engineer feel ambushed in front of others. I'd sit down with them and walk through why the settings matter rather than just declaring them wrong: resolution bandwidth affects noise floor and whether you resolve closely spaced emissions, the detector determines whether you're capturing peak or quasi-peak values that the standard actually specifies, and without antenna/cable correction factors the amplitude numbers are meaningless in absolute terms. The "peaks show up either way" point is exactly the trap — a quick scan can show you where energy is, but it can't tell you whether you pass or fail. Then I'd make it a shared fix: re-run the scan with the correct settings and correction factors applied, and if there's time before tomorrow, do a quick sanity comparison so the engineer sees the difference for themselves. On the schedule side, I'd check whether the booked slot can still be used productively — if the corrected setup is ready in time, proceed; if not, I'd raise the risk with the project lead early rather than let a bad scan become a false pass. And I'd follow up by turning the correct setup into a documented, reusable procedure so the next person doesn't start from a tutorial.
**Possible follow-ups:** How would you handle it if the engineer pushed back and insisted the tutorial settings were fine? What would you change in the team's process so this doesn't recur on the next scan?
