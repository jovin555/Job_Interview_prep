## Q1: How would you approach setting up a logic analyzer's protocol decoder for a Manchester-encoded sensor bus where the clock is embedded in the data stream, so there's no separate clock line to trigger on — and how would you verify the decoder is actually interpreting the framing correctly before trusting it?

**Answer:** The core problem is that with Manchester encoding there's no independent clock to sample against, so the decoder has to recover timing from the transitions themselves. I'd start by characterizing the physical layer: measure the bit period from the shortest consistent transition spacing, confirm the encoding convention (IEEE 802.3 vs. G.E. Thomas differ in which direction represents a 1), and check whether the bus is truly DC-balanced or has long runs that could stress the recovery. Then I'd configure the analyzer's Manchester decoder with the measured bit rate and the correct polarity, and set the trigger on a known preamble or sync pattern rather than a clock edge — often the frame starts with a distinctive transition sequence that's a reliable trigger anchor.

The critical step is verification, because a decoder that's silently mis-framing will produce plausible-looking garbage. I'd cross-check against an independent reference: capture the raw analog waveform on the oscilloscope simultaneously and manually decode a few frames by eye, comparing bit-for-bit against what the decoder reports. I'd also inject a known test pattern from a signal generator or a firmware test mode and confirm the decoder reproduces it exactly. If the protocol has a checksum or CRC, I'd verify that the decoder's output passes it consistently — a decoder that's off by one bit will almost never produce valid CRCs across many frames. Finally, I'd stress it with worst-case timing (jitter, temperature drift if relevant) and confirm the decode stays stable, because a decoder that works at nominal but falls apart at the edges of the timing budget isn't trustworthy for debug.

**Possible follow-ups:** How would you handle a bus where the bit rate isn't documented and you have to infer it from the waveform alone? What would you do if the decoder passes CRC on most frames but fails intermittently — how would you tell whether it's a decoder problem or a real bus fault?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is to make the build configuration a controlled, reviewable artifact rather than a set of GUI checkboxes that drift between engineers and machines. I'd start by treating the project file itself as source-controlled and reviewing changes to it like code — but the deeper fix is to move as much configuration as possible out of the IDE's opaque settings and into explicit, diffable files. For the linker, I'd use an explicit scatter file (or linker script) checked into the repo, referenced by a fixed path, so the memory map is visible and versioned. For startup code, I'd keep the startup assembly and system-init files in the repo and confirm the project references those exact files rather than a copy buried in a pack directory.

For optimization, I'd pin the level per build target and document why — for a medical device, debug builds often need `-O0` or `-Og` for traceability and reproducible debugging, while release builds use a defined higher level, and the choice should be justified and recorded, not left to whoever last opened the dialog. I'd verify the actual flags the compiler receives by inspecting the build log or the generated command line, because the IDE's displayed setting and the effective flag can diverge. I'd also lock the toolchain version — the compiler version is part of the build's identity, and an upgrade should be a deliberate, tested change. Finally, I'd make the build reproducible: a clean build from a fresh checkout on a clean machine should produce a binary that matches, and I'd capture the map file and build log as release artifacts for audit.

**Possible follow-ups:** How would you detect that someone had quietly changed the optimization level between a tested build and a released one? What's your approach when a vendor toolchain update changes code generation and you need to prove the firmware still behaves identically?

## Q3: How would you approach setting up a via structure strategy in Cadence Allegro for a mixed-signal PCB that carries both high-speed digital signals and sensitive analog traces, and how would you verify that the vias don't compromise signal integrity or manufacturability?

**Answer:** I'd start by defining via classes tied to signal type rather than using one default via everywhere. High-speed digital nets get vias sized and back-drilled or stub-tuned as needed for the frequencies involved, with impedance matched to the trace; sensitive analog nets get vias placed to minimize loop area and kept away from return-path discontinuities, often with ground vias stitched adjacent to signal vias to give the return current a clean path. Power vias get their own class sized for current and thermal considerations. In Allegro I'd set these up as physical via definitions and constrain them through the constraint manager so the router and DRC enforce the right via per net class rather than relying on the designer to remember.

Manufacturability is the other half: I'd confirm the via drill sizes and annular rings meet the fab house's capability, check aspect ratios against their limits, and verify that via-in-pad (if used) is either filled and capped or explicitly agreed with the fab, since unfilled via-in-pad causes wicking and assembly defects. I'd also check via-to-via and via-to-trace clearances against the DFM rules.

Verification is where I'd be deliberate: run DRC with the via constraints active and confirm zero violations, then do a visual and cross-section-style review of a representative region. For signal integrity, I'd extract the via structures into the SI tool and look at the impedance discontinuity and stub resonance for the high-speed nets, and for the analog side I'd check that return paths are continuous. If the design has a ground plane split, I'd specifically verify no signal via crosses the split without a stitching via nearby.

**Possible follow-ups:** How would you decide whether back-drilling is worth the cost for a given high-speed net? What would you check first if a prototype showed an unexpected resonance on a net that looked fine in layout review?

## Q4: How would you approach setting up a Git-based version control workflow for a KiCad project that includes schematic files, PCB layout, 3D models, and a Bill of Materials, ensuring that design reviews and releases are properly tracked?

**Answer:** KiCad's files are text-based, which is a real advantage over binary CAD formats — schematics and boards diff meaningfully, so Git works well if the workflow is disciplined. I'd structure the repo with clear separation: the KiCad project files, a libraries directory (symbols, footprints, 3D models) either vendored or referenced by a pinned path, and a docs directory for the BOM, fabrication notes, and review records. The key discipline is that the libraries are versioned alongside the design, so a checkout at a given commit reproduces the exact design — not "whatever the shared library happened to contain that day."

For reviews, I'd use branches and pull requests even for a solo or small team, because the PR is where the review record lives: the diff shows what changed, reviewers comment, and the merge commit is the approval. For releases, I'd tag commits with a clear scheme (revision identifier plus date), and generate the BOM and fabrication outputs from that tagged commit so the released artifacts are traceable back to an exact design state. I'd keep generated outputs out of the main history or in a release artifacts location, so the repo stays clean and the outputs are clearly derived.

The 3D models and any large binaries are the friction point — I'd keep them in the repo if they're small and stable, or use Git LFS if they're large, and document the choice. I'd also set up a simple convention for commit messages that reference the change and the review, so the history reads as a design record rather than a pile of "update" commits.

**Possible follow-ups:** How would you handle a merge conflict in a KiCad schematic file — is it ever safe to resolve by hand? What would you put in a release checklist to confirm the tagged commit actually produces the artifacts you're shipping?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has been tasked with setting up the automated firmware test environment for a medical device. On the day before a critical regression test run, you discover that the engineer has configured the test script to skip the safety-critical test cases because they were failing intermittently, and the engineer is confident this is acceptable because "the failures are just timing issues in the test harness, not real bugs." The test results will be used for a regulatory submission milestone. How would you handle this situation?

**Answer:** My first move is to stop the clock on the assumption that the run can proceed as configured — not to blame anyone, but because the stakes here are regulatory, and a test suite that silently excludes safety-critical cases produces a result that misrepresents what was actually verified. I'd sit down with the engineer and treat their claim seriously: intermittent failures in a test harness genuinely can be harness timing issues, and that's worth investigating rather than dismissing. But "probably a harness issue" is a hypothesis, not a conclusion, and the correct response to an intermittent failure in a safety-critical test is to characterize it, not to skip it.

I'd work with them to reproduce the failures, capture logs and timing, and determine whether the root cause is in the harness (e.g., a race in the test sequencing, insufficient settling time, a flaky fixture connection) or in the firmware under test. If it's genuinely the harness, the fix is to make the harness deterministic — add synchronization, increase margins, stabilize the fixture — and then re-enable the tests, not to leave them disabled. If it's the firmware, that's exactly the kind of finding the regression run exists to catch, and it needs to be surfaced, not hidden.

On the process side, I'd make sure the skip is visible and documented rather than buried in a script: any excluded test should be flagged in the results with a reason and an owner, so the regulatory record is honest about what was and wasn't covered. I'd escalate the schedule risk to the project lead promptly, because the honest options — delay the run to fix the harness, or run with documented exclusions and a remediation plan — are decisions above my pay grade to make unilaterally when a submission milestone is involved. And I'd frame the conversation with the engineer around the shared goal: we both want the test results to mean something, and a skipped safety-critical test means the result doesn't.

**Possible follow-ups:** How would you distinguish a genuine harness timing issue from a real firmware race condition when both produce intermittent failures? What would you do if the schedule simply couldn't absorb a delay and leadership wanted to proceed with the exclusions?
