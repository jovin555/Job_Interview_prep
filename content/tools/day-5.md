## Q1: How would you approach setting up a hierarchical schematic design in Altium Designer for a complex mixed-signal medical device that has multiple identical sensor channels?

**Answer:** For a design with repeated sub-circuits, I'd start by creating a top-level sheet with sheet symbols representing each functional block (e.g., power management, sensor interface, microcontroller, isolation barrier). Each sheet symbol would reference a child schematic sheet. For the identical sensor channels, I'd use Altium's multi-channel design feature: create one sensor channel schematic, then place multiple sheet symbols that all point to the same child sheet. Altium automatically handles netlist expansion by appending suffixes (like _Ch1, _Ch2) to each instance's nets. I'd define parameters at the sheet symbol level (e.g., channel address, gain setting) that propagate down to the child sheet as design directives. For the power and ground nets that are shared across channels, I'd use global power port symbols or explicit net labels with a defined net class in the project options to avoid floating nets. The hierarchical approach keeps the schematic readable, makes it easy to update all channels by editing one sheet, and simplifies the transition to PCB layout where I can use room-based placement and copy routing for the repeated channels.

**Possible follow-ups:** How would you handle a situation where one of the identical channels needs a minor component value change (e.g., a different feedback resistor) without breaking the multi-channel structure? What are the trade-offs of using global power ports versus hierarchical ports for power distribution in a multi-channel design?

## Q2: Walk me through your process for using LTSpice to simulate the noise performance of a precision analog front-end for a medical sensor, and how you would correlate those simulations with real-world measurements.

**Answer:** I'd start by building the circuit schematic in LTSpice using manufacturer-supplied SPICE models for the op-amp, ADC driver, and any precision references. For noise simulation, I'd run an AC analysis from 0.1 Hz to 1 MHz, then plot the output noise spectral density (V/√Hz). I'd use the waveform math to integrate the noise over the bandwidth of interest to get RMS noise. I'd also add a .noise statement to get the total integrated noise and see which component contributes most (noise contribution breakdown). To correlate with real-world measurements, I'd build the prototype and use a low-noise preamplifier and spectrum analyzer to measure the output noise floor. Key correlation steps: ensure the measurement bandwidth matches the simulation bandwidth; account for the spectrum analyzer's noise floor and any external interference (60 Hz pickup, switching regulator ripple) that isn't in the ideal simulation; and verify that the op-amp's actual gain-bandwidth product matches the model. If the measured noise is significantly higher, I'd check for layout-induced issues like ground loops or inadequate decoupling that the simulation doesn't capture. I'd also run a transient noise simulation with a time-domain noise source to see how noise affects the ADC's output code distribution, which is more directly comparable to collecting ADC samples on the bench.

**Possible follow-ups:** How would you model the effect of a switching regulator's ripple on the analog front-end noise performance in LTSpice? What techniques would you use to measure sub-microvolt noise levels without the measurement equipment's own noise dominating the reading?

## Q3: How would you approach using a logic analyzer to debug a CAN-FD bus where the node occasionally enters bus-off state after several hours of operation, but only under specific temperature conditions?

**Answer:** This is a classic intermittent fault that requires a systematic approach. First, I'd set up the logic analyzer with CAN-FD protocol decoding enabled, capturing on a trigger condition like "error frame detected" or "bus-off state entered." I'd configure a deep memory buffer (or use segmented memory) to capture long traces, since the fault may take hours to appear. I'd probe the CAN_H and CAN_L lines differentially (using a differential probe if available, or two single-ended probes with math subtraction) to see the actual bus voltage levels, not just the logic-level decoded output. I'd also probe the node's CAN controller TX and RX pins to see what the microcontroller is sending versus what appears on the bus. When the fault occurs, I'd look for: bit timing errors (dominant bits that are too short or too long), missing ACK slots, or CRC errors that precede the bus-off condition. Since temperature is a factor, I'd use a thermal chamber or heat gun to accelerate the fault while monitoring. I'd also look at the bus termination resistors and common-mode voltage — temperature drift in termination or transceiver characteristics can cause signal integrity issues at the edges of the specification. If the logic analyzer shows that the node is transmitting valid frames but the bus doesn't acknowledge them, the problem might be in the transceiver or the physical layer rather than the protocol layer.

**Possible follow-ups:** How would you distinguish between a bus-off condition caused by the node's own bit timing errors versus one caused by noise on the bus corrupting its transmissions? What additional measurements would you take with an oscilloscope to complement the logic analyzer data?

## Q4: How would you approach configuring a Segger J-Link debugger for non-intrusive real-time monitoring of a Zephyr RTOS-based system, where you need to capture a crash dump and the last several seconds of system state without halting the CPU?

**Answer:** The J-Link's Real-Time Transfer (RTT) and trace capabilities are key here. For crash dump capture, I'd configure the J-Link to use its RTT buffer for logging — the firmware writes diagnostic data (task states, stack usage, sensor readings) to an RTT up-channel in a circular buffer. When a crash occurs, the J-Link's RTT Viewer or a custom script can read the last N entries from the buffer without halting the CPU. For more detailed post-mortem analysis, I'd enable the J-Link's data watchpoint feature: set a hardware watchpoint on the hard fault handler entry address, and configure the J-Link to capture a trace of the program counter and key register values leading up to the fault. If the target microcontroller supports ETM (Embedded Trace Macrocell), I'd use the J-Link's trace capability with a 4-bit trace port to capture instruction execution history. For the "last several seconds" requirement, I'd use a combination of RTT for high-frequency log data and a periodic snapshot of the RTOS kernel state (task list, semaphore states) written to a reserved RAM region that survives reset. On the host side, I'd write a Python script using pylink or J-Link Commander that polls the target periodically, reads the RTT buffer, and stores timestamps — so even if the target crashes, the host has a time-correlated log of what was happening. For automated testing, I'd configure the J-Link to trigger a trace capture on a specific RTT event and dump the trace to a file for offline analysis.

**Possible follow-ups:** How would you handle the case where the crash corrupts the RTT buffer or the reserved RAM region before you can read it? What are the trade-offs between using RTT versus semihosting for debug output in a real-time system?

## Q5: (Behavioral) Imagine you are leading the bring-up of a new medical device prototype, and you discover that the KiCad project files have become corrupted — the schematic and PCB are no longer synchronized, and the last clean commit was three weeks ago. The project is already behind schedule, and a junior engineer on your team was responsible for the KiCad project management. How would you handle this situation?

**Answer:** First, I'd assess the damage without assigning blame. I'd ask the junior engineer to walk me through what happened — did they notice any error messages, did they try to recover the files, what was the last thing they did before the corruption occurred. Meanwhile, I'd check if there are any backup files KiCad automatically creates (.sch-bak, .kicad_pcb-bak) or if the project was stored on a network drive with versioning. If the corruption is limited to the schematic-PCB cross-reference, I'd try using KiCad's "Update PCB from Schematic" tool with the "Re-associate footprints by reference" option to see if the netlist can be recovered. If that fails, I'd look at whether we have PDF exports or Gerber files from the last known-good state that could serve as a reference for manual recovery. For the team communication, I'd call a brief stand-up meeting to explain the situation factually: "We have a project file issue that will require some recovery effort. Here's what we know, here's what we're doing to recover, and here's the estimated impact on the schedule." I'd explicitly avoid blaming the junior engineer in the meeting — instead, I'd frame it as a process improvement opportunity. After recovery, I'd implement safeguards: enforce daily commits to a Git repository (even for KiCad files, using a .gitignore that excludes auto-generated files), set up automated backups of the project folder, and create a written procedure for proper KiCad project hygiene (always close the project before copying files, use "Save Schematic" and "Save PCB" explicitly, never edit files in two instances simultaneously). I'd pair the junior engineer with a more experienced team member for the next week to rebuild confidence and ensure they understand the new workflow.

**Possible follow-ups:** What would you do if the recovery effort reveals that the junior engineer had been making manual edits to the PCB file without updating the schematic, and that's what caused the desynchronization? How would you balance the need to recover the project quickly with the opportunity to mentor the junior engineer through the recovery process?
