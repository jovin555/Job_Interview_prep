## Q1: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?
**Answer:** Start by treating the decoder as a layered problem rather than a single monolithic script. The lowest layer is edge/timing capture: get the sample rate high enough that the smallest pulse width in the protocol is at least several samples wide, and confirm the capture is trustworthy by checking that a known-good transaction decodes cleanly before writing any custom logic. The next layer is framing — a state machine that hunts for the sync pattern, then counts out the header, payload, and checksum fields according to the protocol spec. If the header is non-byte-aligned, the decoder must track bit position explicitly rather than assuming byte boundaries, which is the main reason built-in decoders fail here. Above that, add a field-extraction layer that maps raw bits to named fields (sensor ID, reading, status flags) and a validation layer that checks the checksum/CRC and flags frames that fail. Keep the decoder's output in a form that can be exported to CSV so it can be diffed against firmware logs or a reference capture. Two practical points: first, version the decoder alongside the firmware, because a protocol change that isn't reflected in the decoder produces silently wrong decodes; second, validate the decoder against a known stimulus — a signal generator or a second device replaying a captured frame — so you're not debugging the decoder and the device at the same time.
**Possible follow-ups:** How would you handle a protocol where the clock is embedded in the data (e.g., Manchester or a self-clocked line) rather than a separate clock line? What would you do if the decoder works on one unit but not another, and the difference turns out to be a slightly different bit timing?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?
**Answer:** The core principle is that the build configuration is a controlled artifact, not a set of IDE checkboxes that happen to be set correctly on one engineer's machine. Concretely: keep the project file under version control and treat changes to it as reviewable diffs; pin the compiler/toolchain version explicitly rather than letting the IDE pick up whatever is installed; set the optimization level deliberately and document why (for safety-critical code, `-O0` or a low level during verification is common, with a documented rationale if a higher level is used for release); and make the linker script and startup code first-class source files in the repo, not generated or hand-edited in the IDE. For auditability, the build should be reproducible from a clean checkout with a single command, and the resulting binary should be identifiable — a build ID or version string embedded in the image, plus a hash of the source tree. A useful discipline is to have a "release" configuration and a "debug" configuration that differ only in well-defined ways (optimization, assertions, logging), with the differences enumerated in a document. Finally, run a static check or a build-time assertion that the expected configuration is actually in effect — for example, a compile-time check on the optimization level or a post-build script that inspects the map file — so a misconfigured build fails loudly rather than silently shipping.
**Possible follow-ups:** How would you handle a situation where a third-party library only builds correctly at a specific optimization level? What would you put in the build log to make a regulatory audit of a specific release straightforward?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?
**Answer:** The measurement is essentially a reflection measurement: the tracking generator sweeps a known signal into the front-end through a directional coupler, and the analyzer measures the reflected power, from which return loss and then impedance can be derived. The setup details matter more than the math. First, calibrate the setup — a full one-port calibration (open/short/load) at the reference plane where you want to know the impedance, using the same cables and coupler you'll use for the measurement, because cable and connector parasitics will otherwise dominate the result. Second, keep the incident power low enough that the front-end stays in its linear region; a front-end with active devices can compress or even be damaged by a careless sweep. Third, watch the frequency range: the useful data is where the coupler and the analyzer are both well-behaved, and outside that range the result is an artifact of the instrument, not the device. On trustworthiness: repeat the measurement with the device powered and unpowered, and with a known reference load in place of the device, to confirm the setup reproduces the expected result. If the two disagree, the setup is suspect. Also check that the result is stable across sweeps and doesn't change when you touch or move the cables — if it does, the measurement is dominated by fixturing, not the device. Only act on the result once the reference measurement and the device measurement are both clean and repeatable.
**Possible follow-ups:** How would you extend this to a differential front-end, where a single-ended measurement doesn't capture the full picture? What would you do if the front-end is powered and the measurement shows a resonance that doesn't appear in simulation?

## Q4: How would you approach setting up a Segger J-Link's RTT (Real-Time Transfer) logging for a Zephyr RTOS target where you need continuous debug output but the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?
**Answer:** RTT is attractive here precisely because it uses the debug interface rather than a UART, so it doesn't compete with the safety-critical protocol for a peripheral. The setup is: enable RTT in the Zephyr configuration, allocate a reasonable buffer size (larger buffers absorb bursts and reduce the chance of dropped messages), and make sure the J-Link control block is discoverable by the host tool. The harder part is the perturbation question. RTT logging still costs CPU cycles and memory bandwidth, and if the logging call blocks or the buffer fills, it can change the timing of the very code you're trying to observe. Mitigations: use non-blocking logging where possible, keep the log level low in timing-sensitive paths, and — critically — measure the impact rather than assuming it's negligible. A practical way to do that is to toggle a GPIO at the start and end of a timing-critical section and compare the pulse width with logging enabled and disabled; if the difference is outside the tolerance for that section, the logging is too intrusive for that path. Also be aware that RTT requires the debug probe to be attached, which may not be acceptable in some test configurations, and that the host-side tool can itself become the bottleneck if it can't drain the buffer fast enough. For a safety-critical system, the logging should be treated as a diagnostic aid that can be compiled out entirely for the release build, with a clear boundary between what's logged in debug and what's logged in production.
**Possible follow-ups:** How would you handle a situation where the RTT buffer overflows and messages are dropped — how would you know, and what would you change? What's your approach to making sure the logging code itself doesn't introduce a race condition in a multi-threaded Zephyr application?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?
**Answer:** The first thing is to separate the technical issue from the interpersonal one. Technically, the engineer isn't wrong that peaks show up either way — the problem is that the amplitude and the comparison to the limit line are not valid with the wrong RBW and detector, so a scan that "looks fine" can miss a marginal failure or report a false pass. That's the point to make, and it's worth making concretely: show the same emission measured with the correct settings versus the current ones, so the difference is visible rather than asserted. On the people side, the goal is to correct the setup without making the engineer defensive, because the next scan will depend on them. Frame it as "the standard specifies these settings, and here's why" rather than "you got it wrong." Then deal with the schedule: the settings can usually be corrected in minutes, so the immediate fix is to reconfigure and re-run a quick verification scan before the formal one. If there's any doubt about whether the earlier scan's data is usable, treat it as not usable and re-scan — a pre-compliance scan that isn't trustworthy is worse than no scan, because it creates false confidence. Going forward, the real fix is a written scan procedure with the standard's settings baked in, so the setup doesn't depend on any one person's memory or judgment.
**Possible follow-ups:** How would you decide whether the earlier scan's data can be salvaged or must be discarded? What would you put in the scan procedure to prevent this from recurring without making it so rigid that it can't be adapted to a different standard?
