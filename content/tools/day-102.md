## Q1: How would you approach setting up a Gerber and drill-file verification workflow in Gerbv for a medical device PCB, so that fabrication issues are caught before the files leave for the board house?

**Answer:** I'd treat Gerbv as the last human-eye check in a pipeline, not the only check. The workflow starts upstream: the CAD tool's own DRC and output job produce the layer set, and Gerbv is where I confirm that what was *intended* is what was *exported*. Concretely, I'd load every layer — copper layers, soldermask, silkscreen, paste, board outline, and the drill file — and verify them in a fixed order. First, registration: do all layers align to the same origin, and does the board outline close cleanly with no gaps or self-intersections? Second, drill: does the drill file overlay correctly on the copper pads, are there any pads with no drill or drills with no pad, and are tool sizes plausible for the vias and through-holes in the design? Third, soldermask and paste: any mask openings where there shouldn't be (exposed traces), any paste apertures misaligned with pads. Fourth, silkscreen: no silk over pads or fiducials, reference designators legible and not clipped. I'd also check the layer polarity — a negative plane layer rendered wrong is a classic silent failure — and confirm the file units and format (e.g., 2:5 vs 2:4) match what the fab expects. The key discipline is that Gerbv shows you geometry, not intent, so I keep a checklist tied to the fab's capabilities and the design's critical features, and I record the verification as part of the release record. For a medical device, that record matters as much as the check itself.

**Possible follow-ups:** How would you catch a missing or duplicated layer that Gerbv wouldn't flag on its own? What would you do if the fab's DFM report came back flagging something your Gerbv review missed?

## Q2: How would you approach configuring a Keil uVision project so that the optimization level, linker script, and startup code are locked down and auditable, rather than left at whatever the IDE defaults to?

**Answer:** The goal is that a build is reproducible and that the settings that affect behavior are explicit and version-controlled, not buried in a GUI. I'd start by treating the project file itself as a reviewed artifact — it goes into version control and changes to it go through the same review as source. For optimization, I'd set the level deliberately per build configuration (e.g., a debug configuration at low/no optimization for debuggability, a release configuration at the level validated during testing), and I'd document *why* each level was chosen, because optimization can change timing and expose latent undefined behavior. The linker script I'd keep as a separate, versioned file referenced by the project rather than edited in the IDE, so the memory map — flash regions, RAM, any reserved calibration or bootloader sectors — is visible and diffable. Startup code likewise: the startup assembly and the vector table should be explicit files in the tree, not regenerated silently. I'd also pin the toolchain version, since a compiler upgrade can change code generation and warnings. Then I'd add a build-time check — a script or a post-build step — that asserts the expected optimization flag, linker script path, and startup file are actually in effect, so a stray IDE change gets caught rather than shipped. The auditability comes from the combination: versioned project and linker files, pinned toolchain, and a verification step that fails loudly if the configuration drifts.

**Possible follow-ups:** How would you handle a situation where the validated release build used one optimization level but a later maintenance build needs a different one? What's your approach to confirming the linker script's memory regions match the actual device?

## Q3: How would you approach setting up a Segger J-Link's RTT logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?

**Answer:** RTT is attractive here precisely because it doesn't consume a UART — it uses the debug probe's memory access to a ring buffer in target RAM, so the safety-critical UART stays untouched. The setup has two halves: target side and host side. On the target, I'd enable the RTT backend in the Zephyr logging configuration and size the up-buffer and down-buffer deliberately — big enough to absorb bursts between host polls, small enough not to waste RAM or blow the timing budget. On the host, the J-Link software polls the buffer; the polling rate and buffer size together determine whether messages are dropped under load. The timing concern is real: even though RTT is lighter than semihosting or printf-over-UART, writing to the buffer still costs cycles and can take a lock, so I'd keep the logging calls off the hot path and out of interrupt context where possible, or use a deferred/log-thread mode so the logging work happens at low priority. I'd also consider a "panic mode" buffer so the last messages survive a crash. To verify the logging isn't perturbing timing, I'd measure the same timing-sensitive operation with logging enabled and disabled — using a GPIO toggle and scope, or the system's own timing instrumentation — and confirm the delta is within budget. If it isn't, the fix is usually smaller buffers, deferred logging, or moving the log calls out of the critical section entirely.

**Possible follow-ups:** How would you decide between RTT and a RAM-based trace buffer for capturing the last few seconds before a crash? What would you check first if RTT messages were arriving truncated or out of order?

## Q4: How would you approach setting up a power integrity simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?

**Answer:** I'd frame this as a question of *where the current actually flows and what impedance it sees*, and build the model in layers of increasing fidelity, stopping when the answer stops changing. First, a stackup and plane-pair model: get the copper thickness, dielectric thickness and Dk, and the plane shapes right, because the PDN impedance is dominated by the plane cavity and the decoupling network, not by the traces. Second, assign the VRM as a source with its output impedance and the load as a current sink with the actual transient profile — for a switching regulator, that means modeling the ripple and the load steps, not just DC. Third, place the decoupling capacitors with realistic parasitics (ESL and ESR, plus mounting inductance), because a capacitor that looks fine on a datasheet can be useless at the frequency that matters if its loop inductance is too high. Then run AC impedance (looking for anti-resonances where the PDN impedance peaks) and, if the tool supports it, a transient or ripple simulation to see the actual noise at the analog load. The trust question is the important one: I'd validate the model against measurement before acting on it — measure the PDN impedance with a VNA or the ripple at the analog supply with a scope, and compare. If the simulation and measurement disagree, the model is wrong somewhere (usually the capacitor parasitics or the plane model), and I'd fix the model before trusting its predictions. I'd also do sensitivity checks: does the conclusion change if I vary a capacitor's ESL by 50%? If not, the recommendation is robust; if it does, I need better data before committing to a layout change.

**Possible follow-ups:** How would you decide how many decoupling capacitors are enough without over-designing? What's your approach when the simulation says the PDN is fine but the bench measurement shows noise at the analog front-end?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** I'd separate the technical issue from the people issue and deal with both, in that order of urgency but not of importance. Technically, the engineer's intuition isn't wrong that peaks show up either way — but the *amplitude* and the *decision* depend on the settings. Resolution bandwidth affects the noise floor and how a broadband vs narrowband emission is displayed, and detector mode (peak vs quasi-peak vs average) changes the measured level in ways that the standard cares about. So a scan with the wrong settings can either miss a marginal failure or flag a false one, and either way it isn't evidence you can submit. My first move is to explain *why* the settings matter with a concrete demonstration if the equipment allows — change the RBW and detector and show the reading move — because that turns "trust me" into "see for yourself." Then I'd fix the setup: correct RBW and detector per the standard, verify with a known reference if possible, and re-run. On the scheduling pressure: I'd rather use the booked lab time correctly than use it wrongly and have to redo it, so I'd check whether the corrected scan fits in the slot; if not, I'd escalate early to rebook rather than let a bad scan become the record. On the people side, I'd be careful not to make it a public correction — the goal is a engineer who understands the standard's requirements, not one who's embarrassed. I'd frame it as "here's how we make sure the result holds up in review," and I'd ask them to own the corrected setup so the lesson sticks. The underlying principle is that in a regulated context, "the peaks show up" isn't the bar — the bar is a measurement that would survive an auditor's questions.

**Possible follow-ups:** How would you build a checklist or lab SOP so this kind of setup error is caught before the scan starts? If the rebooked lab time slipped the project schedule, how would you communicate that upward?
