## Q1: How would you approach setting up a spectrum analyzer for a conducted emissions pre-compliance scan on a medical device's AC input, and what would you check before trusting the first measurement?

**Answer:** I'd start by treating the setup as a chain where every element has to be characterized before the measurement means anything. The device under test sits on an LISN (line impedance stabilization network) that provides a defined, repeatable RF impedance to the mains and isolates the measurement from the ambient mains noise; the LISN's measurement port feeds the spectrum analyzer through a transient limiter and a high-pass filter to protect the front end and reject the 50/60 Hz fundamental. Before scanning, I'd verify the analyzer's own calibration status and run a self-calibration if the instrument supports it, then confirm the LISN's correction factor and the cable/attenuator losses are entered as a correction table so the displayed amplitude is the actual emission level, not the raw port level. I'd set the resolution bandwidth and detector to what the applicable standard requires — typically a defined RBW per band and quasi-peak or average detection, not peak — and set the scan time and step size so the sweep isn't undersampling narrow emissions. Then I'd run a "quiet" baseline with the DUT powered off to see the ambient floor and confirm nothing in the room is dominating. Only after that would I power the DUT and scan. The things I'd check before trusting the first result: is the ambient floor well below the limit line, are the correction factors actually applied, is the detector mode correct for the standard, is the DUT operating in its worst-case mode, and is the LISN bonded to a proper reference ground. If any of those is uncertain, the number on screen is a starting point, not a result.

**Possible follow-ups:** How would you distinguish a real emission from ambient noise if the two are close in amplitude? What would you do if the DUT's worst-case operating mode isn't obvious from the product spec?

## Q2: How would you approach configuring a Keil uVision project so that the optimization level, linker script, and startup code are locked down and auditable rather than left at whatever the IDE defaults to?

**Answer:** The goal is that a build is reproducible and that the settings that affect behavior are visible and version-controlled, not buried in a dialog someone clicked once. I'd start by treating the project file itself as a reviewed artifact — the `.uvprojx` and any scatter file or startup assembly go into version control alongside the source, and changes to them go through the same review as code. For optimization, I'd set the level explicitly per target and document why: debug builds at low or no optimization so stepping and variable inspection behave predictably, release builds at the chosen level with the rationale recorded, and I'd avoid mixing levels between modules unless there's a specific reason. For the linker, I'd use an explicit scatter file rather than relying on the IDE's auto-generated memory layout, so section placement, stack/heap sizes, and any reserved flash regions (calibration data, bootloader, persistent storage) are declared in a file that can be diffed and reviewed. The startup code I'd keep as a checked-in source file with the vector table and initialization sequence visible, not a black-box generated blob. To make it auditable, I'd add a build step or script that dumps the effective compiler and linker command lines and the resulting memory map into the build output, so anyone can confirm what was actually used. Finally, I'd tie the toolchain version itself into the record — the compiler version is part of reproducibility, and a silent toolchain upgrade can change code generation just as surely as a flag change.

**Possible follow-ups:** How would you catch a situation where someone changed an optimization flag locally but the committed project file looks unchanged? What's your approach to keeping debug and release configurations from drifting apart over time?

## Q3: How would you approach setting up a Segger J-Link's RTT logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?

**Answer:** RTT is attractive here precisely because it uses the debug probe's memory-access channel rather than a peripheral, so it doesn't consume the UART and doesn't require the target to block on a slow serial link. The setup is: enable the RTT control block in the firmware, point the J-Link at it (either by address or by having the probe search RAM for the ID string), and read the up-channel from the host side. The timing concern is the real engineering problem. RTT writes go into a RAM ring buffer, so if the host isn't draining fast enough the buffer fills and the logging call either blocks or drops — and a blocking log call inside a timing-critical path is exactly what you don't want. So I'd size the buffer generously, configure the logging mode to non-blocking with drop-on-full for anything in the hot path, and keep the log calls themselves short — format off the critical path where possible, log a compact event ID and timestamp rather than a long formatted string. I'd also be deliberate about *where* logging is allowed: instrumenting an interrupt handler or a control loop changes its execution time, so I'd either exclude those or gate the logging behind a compile-time switch that's off in the production image. To confirm the logging isn't perturbing timing, I'd measure a known periodic event with and without logging enabled — a GPIO toggle on the scope is the simplest reference — and check that the period and jitter are unchanged. If they move, the logging is too intrusive for that path and needs to be moved or made lighter.

**Possible follow-ups:** How would you decide between RTT and a memory-backed trace for capturing events that happen faster than the host can drain? What would you do if the RTT control block address moves between builds?

## Q4: How would you approach setting up a cross-probe workflow between OrCAD Capture and Cadence Allegro so a layout review can move efficiently between schematic and PCB, and what would you check to confirm the link actually works before relying on it in a review?

**Answer:** Cross-probing is only useful if it's trustworthy, so I'd set it up and then deliberately test it before the review rather than discovering mid-review that selecting a net in the schematic highlights nothing in the layout. The mechanics: both tools need to be pointed at the same design database, the cross-probe link enabled on both sides, and — importantly — the schematic and layout need to be the same revision. A stale link between a current schematic and an older layout is worse than no link, because it will happily highlight the wrong thing. Before relying on it I'd run a few sanity checks: select a specific component in the schematic and confirm the correct footprint highlights in Allegro; select a net and confirm the same net highlights on both sides; pick a component that exists in multiple instances and confirm the right instance is selected, not just the first match. I'd also check that the link survives a save-and-reload cycle, since a link that only works in the session where it was established is a trap. During the review itself, the workflow I'd want is: schematic drives the conversation (here's the block, here's the net), layout confirms the physical realization, and any discrepancy gets flagged immediately. If the link is flaky, I'd rather fall back to a disciplined manual cross-reference — designator and net name — than let a broken link create false confidence.

**Possible follow-ups:** What would you do if the schematic and layout are legitimately different revisions because an ECO is in progress? How would you structure a review so the cross-probe is used to confirm rather than to discover?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** The first thing I'd do is separate the person from the problem — the engineer isn't wrong that the peaks show up either way; they're wrong that "showing up" is the same as "measuring to the standard." So I'd explain the *why* rather than just overriding: resolution bandwidth affects the amplitude a narrow emission reads at, detector mode determines whether you're capturing peak versus quasi-peak versus average, and a scan that isn't set up per the standard can't be used to demonstrate compliance — it can only tell you roughly where to look. That reframes it from "you did it wrong" to "here's what this measurement is for." Then I'd deal with the schedule honestly. The right move is to fix the settings and re-run, and if that means the booked lab time isn't enough, I'd rather raise that now and negotiate more time or a narrower scope than submit a scan I don't trust. I'd also check whether the "get a feel for it" scan has value — it does, as a quick localization pass — so I'd keep it as a preliminary step and make the formal scan the one that counts. Going forward, I'd want the standard's required settings written down as a checklist that lives with the instrument, so the next person doesn't have to rediscover them, and I'd pair the engineer on the corrected setup so the lesson sticks. The underlying principle: a measurement you can't defend to a reviewer isn't a measurement, it's a guess with a plot attached.

**Possible follow-ups:** How would you handle it if the engineer felt you were second-guessing them in front of the team? What would you put in place so the lab's default instrument state matches the standard rather than the last person's convenience?
