## Q1: How would you approach setting up a spectrum analyzer for a conducted emissions pre-compliance scan on a medical device's AC input, and what would you check before trusting the first measurement?

**Answer:** Conducted emissions on the AC mains input is measured with a LISN (line impedance stabilization network) inserted between the EUT and the mains supply, so the measurement sees a defined, repeatable RF impedance rather than whatever the building wiring happens to present. The spectrum analyzer connects to the LISN's RF output port, and the standard prescribes the detector (typically quasi-peak and average), resolution bandwidth (commonly 9 kHz for the 150 kHz–30 MHz band), and scan time. Before trusting anything, I'd verify the setup itself: confirm the LISN is bonded to a reference ground plane, that the EUT is positioned and cabling arranged per the standard rather than for convenience, and that the analyzer's input attenuation and preamp settings aren't compressing or masking the noise floor. I'd run a baseline scan with the EUT powered off to characterize ambient and instrument noise — anything that shows up there isn't the EUT. I'd also check that the LISN's internal 50 Ω termination and any high-pass filter are configured correctly, and that the analyzer has been calibrated recently. Only after the ambient floor is clean and the setup matches the standard would I trust the first EUT scan, and even then I'd repeat it to confirm stability.

- How would you distinguish a real EUT emission from ambient pickup in a noisy lab environment?
- What changes in your setup if the device is battery-powered and has no AC input?

## Q2: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** I'd start by capturing the raw waveform and understanding the physical layer before touching any decoder: clock or clockless, idle level, bit order, and where the frame boundaries actually fall. If the header isn't byte-aligned, a built-in decoder will misalign everything downstream, so I'd write a custom decoder rather than trying to force a standard one. Most logic analyzer software (Saleae, Sigrok, etc.) supports a scripting interface where you define states — idle, header detection, payload accumulation, checksum — and emit decoded fields. I'd build it incrementally: first a decoder that just finds and flags the header pattern, verify it against a known-good capture, then add payload extraction, then the checksum. I'd validate the decoder against a capture where I already know the correct values from a working transaction, and I'd deliberately test edge cases — back-to-back frames, a frame with a corrupted checksum, a truncated frame. The decoder is a measurement instrument in its own right, so it needs the same skepticism as any other: if it disagrees with what the firmware thinks it sent, I need to know which one is wrong before drawing conclusions.

**Possible follow-ups:**
- How would you handle a protocol where the clock is embedded in the data (e.g., Manchester or a self-clocked line)?
- What would you do if the decoder works on one capture but fails intermittently on others?

## Q3: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The core problem is that IDE project files are easy to change silently and hard to review, so for a regulated build I'd treat the build configuration as a controlled artifact. Concretely: pin the optimization level explicitly per target rather than inheriting a default, and document why that level was chosen — optimization can change timing and expose latent undefined behavior, so it needs a rationale and a verification step, not a checkbox. The linker script and startup code should live in version control as first-class source files, referenced by the project rather than embedded in IDE settings, so a diff shows exactly what changed. I'd keep the project file itself under version control and review changes to it the same way as code, since a stray flag change is a real defect vector. For auditability, I'd make the build reproducible — same toolchain version, same flags, same output — and capture the toolchain version and build settings alongside the released binary. Where the toolchain allows it, I'd drive the build from a script or makefile that the IDE merely invokes, so the authoritative configuration isn't buried in a GUI. Finally, I'd add a check that fails the build if critical settings drift from the approved values.

**Possible follow-ups:**
- How would you verify that a change in optimization level hasn't altered the behavior of timing-sensitive code?
- What's your approach to managing the toolchain version itself as part of the controlled build?

## Q4: How would you approach setting up a cross-probe workflow between OrCAD Capture and Cadence Allegro so a layout review can move efficiently between schematic and PCB, and what would you check to confirm the link actually works before relying on it in a review?

**Answer:** Cross-probing depends on the two tools sharing a consistent netlist and a live session, so the first thing I'd confirm is that the Allegro board was imported from the current Capture design and that the two are in sync — a stale netlist will cross-probe to the wrong place or silently fail. I'd set up the session so Capture and Allegro are communicating (typically via the Cadence inter-tool link), then verify the link with a deliberate test: select a specific component or net in the schematic and confirm the corresponding object highlights in the layout, and vice versa. I'd test both directions, because they can fail independently. I'd also check that reference designators and net names match exactly — a mismatch from a manual edit or a renamed net is a common cause of "cross-probe does nothing." Before a review, I'd do this sanity check on a couple of known components rather than assuming it works, because discovering the link is broken mid-review wastes everyone's time. During the review itself, cross-probing lets the team jump between intent (schematic) and implementation (layout) quickly, which is exactly where layout errors like a missing decoupling cap or a swapped pin get caught.

**Possible follow-ups:**
- What would you do if cross-probing works for components but not for nets?
- How would you run a layout review if the two tools couldn't be linked at all?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** The engineer isn't wrong that the peaks show up either way — the issue is that the amplitude and the pass/fail margin depend on the detector and bandwidth, so a "get a feel for it" scan can't be used to judge compliance. I'd separate the two concerns: acknowledge that the quick scan did its job of finding where the energy is, and explain specifically why the formal scan needs the standard's settings — quasi-peak versus average can differ by many dB on a broadband emission, and resolution bandwidth changes both the noise floor and the measured level. I'd frame it as "the scan found the suspects; now we need the measurement that the standard will actually accept." Then I'd fix the settings and, if there's time, re-run a quick pass with the correct configuration to confirm nothing surprising appears before the booked session. I'd avoid making it about the engineer being wrong — the mistake is a reasonable one for someone who hasn't run a formal scan, and the teaching moment is understanding why detector and bandwidth are specified rather than arbitrary. If the lab time is genuinely at risk, I'd prioritize getting the correct settings in place over re-litigating the decision, and follow up afterward so the lesson sticks.

**Possible follow-ups:**
- How would you build a checklist or template so the correct scan settings are used by default next time?
- If the formal scan did reveal a marginal failure, how would you decide whether it's a real issue or a setup artifact?
