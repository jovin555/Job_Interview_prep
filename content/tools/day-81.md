## Q1: How would you approach setting up a spectrum analyzer for a conducted emissions pre-compliance scan on a medical device's AC input, and what would you check before trusting the first measurement?

**Answer:** Conducted emissions measurements are only meaningful if the entire signal path is controlled, so I would treat setup verification as part of the measurement itself rather than a preliminary step. The instrument side starts with the correct front-end: a LISN (line impedance stabilization network) inserted between the AC source and the device under test, with the analyzer's input fed from the LISN's RF port through a properly rated attenuator if the expected levels could exceed the mixer's safe input range. I would confirm the LISN's ground return is bonded to the same reference as the device and the analyzer — a floating or high-impedance ground path is one of the most common reasons a scan looks clean when it isn't.

Before trusting any trace, I would verify the analyzer's own noise floor and residual response with the LISN terminated and the device powered off. If the ambient or instrument noise floor sits within a few dB of the limit line at any frequency of interest, the measurement is not valid regardless of what the trace shows. I would also check that the resolution bandwidth, detector mode (quasi-peak versus average versus peak), and scan time match what the applicable standard requires — a peak-only scan is useful for finding suspects but is not a compliance result, and mixing detector modes between runs makes comparisons meaningless.

Beyond the instrument, I would confirm the device is running in its worst-case emissions mode: maximum load, all radios and switching supplies active, and any cabling dressed the way it will be in real use, since cable routing often dominates conducted emissions at the lower frequencies. I would take a baseline scan, then repeat it once to confirm repeatability before drawing any conclusions. Only after the setup is verified would I start interpreting peaks — and even then, I would treat the first scan as a map of where to investigate, not as a pass/fail verdict.

**Possible follow-ups:**
- How would you distinguish a genuine emission from a measurement artifact caused by the LISN or the grounding arrangement?
- If the ambient noise floor is too high in your lab, what options do you have to still get a usable pre-compliance result?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The core problem with IDE-managed build settings is that they live in project files that are easy to change accidentally and hard to review in a diff, so my approach is to make the critical settings explicit, version-controlled, and verifiable rather than implicit. I would start by treating the project file itself as a reviewed artifact — it goes into version control alongside the source, and any change to optimization level, linker script path, or startup file selection shows up as a diff that a reviewer must approve, rather than being silently toggled in a dialog.

For the settings themselves, I would pin the optimization level deliberately rather than inheriting a default. For safety-critical or regulatory-bound firmware, that often means a known, documented level (frequently `-O0` or a specific `-O1`/`-O2` with justification) chosen for predictable behavior and debuggability, with the rationale recorded. I would make sure the linker script is referenced by an explicit path in the project rather than resolved from a search path, so there is no ambiguity about which memory layout is in use — this matters especially when calibration data or bootloader regions live at fixed addresses. The startup code should likewise be an explicit, named file in the project, not an auto-selected variant.

To make this auditable, I would add a build step or post-build script that extracts the effective compiler and linker flags from the build output and logs them into the build artifact or a manifest. That way, the actual flags used for a given binary are recorded, not just the ones someone believes are set. I would also consider a CI check that fails the build if the optimization level or linker script path deviates from the approved configuration. The goal is that anyone — including an auditor — can look at a released binary and trace exactly which settings produced it, without having to trust that no one touched a dialog box.

**Possible follow-ups:**
- How would you handle a situation where a third-party library requires a different optimization level than the rest of the project?
- What would you check to confirm the linker script actually placed calibration data where the firmware expects to find it?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** A tracking generator plus directional coupler lets you measure return loss (and from that, impedance) across frequency by injecting a known signal and observing how much reflects back, so the first thing I would do is establish the measurement's reference plane and calibration. I would calibrate out the cables, connectors, and the coupler's own response — typically with a short/open/load calibration at the point where the front-end will connect — because without that, the cable and connector parasitics get folded into the result and you end up "measuring" your test setup rather than the circuit.

With the setup calibrated, I would sweep the band of interest and look at return loss versus frequency. A well-matched front-end shows a deep, broad return loss dip at its design frequency; a poor match shows shallow or shifting dips. From return loss I can back out the reflection coefficient and estimate the impedance, but I would be careful about over-interpreting a single number — the front-end's impedance is frequency-dependent and often load-dependent, so a match that looks good at the design frequency can be poor at harmonics or at the frequencies where the sensor actually operates.

Deciding whether to trust the result comes down to a few checks. First, does the measurement repeat if I disconnect and reconnect the setup? Connector repeatability is a common source of error at higher frequencies. Second, does the result make physical sense given the circuit topology — if the front-end has a known series element or a bias network, the impedance curve should reflect that. Third, I would cross-check against a complementary method where possible, such as a network analyzer if available, or a time-domain reflectometry measurement, or simply a bench measurement of the front-end's behavior with a known source impedance. If two independent methods agree, I am comfortable acting on it; if they disagree, I investigate the discrepancy before changing any component values. The measurement is a tool for forming a hypothesis, not a verdict on its own.

**Possible follow-ups:**
- How would the presence of an active device (like an amplifier or a biased sensor) in the front-end complicate this measurement?
- If the return loss looks acceptable but the front-end still performs poorly in the system, where would you look next?

## Q4: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** When the framing doesn't match a built-in decoder, the first step is to resist the temptation to force-fit an existing decoder and instead build the decode from the physical layer up. I would start by capturing raw transitions on the relevant lines — clock, data, and any framing or enable signals — and confirming the basic electrical behavior: idle levels, edge polarity, clock frequency or bit period, and how the frame boundaries are actually marked. For a non-byte-aligned header, that often means the frame starts with a specific number of bits that don't land on a byte boundary, so I would measure the header length in bits directly from the capture rather than assuming it aligns to 8.

Once I understand the physical framing, I would write a custom decoder — most modern logic analyzers support a scripting interface (Python or a similar language) for exactly this. The decoder's job is to consume the raw edges and emit structured fields: header, payload, checksum, and any status bits. I would build it incrementally, validating each stage against a known-good capture before adding the next. A useful technique is to capture a transaction where I already know the expected values — for instance, a sensor reading I can cross-check against a reference instrument — and use that as a test vector for the decoder.

The critical discipline is to treat the decoder as a hypothesis about the protocol, not as ground truth. If the decoded output doesn't match what the system is actually doing, the decoder is wrong, not the system. I would also document the protocol as I reverse-engineer it, because on a medical device the decode logic often becomes part of the test and verification tooling, and it needs to be reviewable and reproducible. Finally, I would keep the raw capture alongside the decoded output so that any disagreement can be traced back to the actual signal.

**Possible follow-ups:**
- How would you handle a protocol where the clock is not continuous and only runs during active frames?
- What would you do if the checksum algorithm is unknown and you need to infer it from captured frames?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** The immediate priority is to separate the technical issue from the interpersonal one, because both need addressing and conflating them makes both worse. Technically, the engineer is partly right — the peaks do show up either way — but that's exactly the trap: a quick scan with the wrong resolution bandwidth and detector mode can show a peak that looks compliant when the correct settings would show it failing, or vice versa. The detector mode in particular changes the measured amplitude of a peak, so a peak-only scan is not a compliance result. I would explain this concretely rather than abstractly, ideally by re-running the same scan with the correct settings and showing the difference on the same screen. That turns the correction into a shared observation rather than a correction from authority.

On the interpersonal side, I would avoid framing it as "you got it wrong." The engineer set up a scan that was appropriate for its stated purpose — getting a feel for the emissions profile — and the mistake was in treating that scan as if it were the formal one. That's a process gap as much as an individual one, and it's worth asking whether the team has a written checklist for pre-compliance scans that specifies the required settings. If not, that's the real fix: a documented setup procedure that anyone can follow, so the correct settings aren't dependent on someone remembering them under time pressure.

For tomorrow's scan, I would not cancel the lab time if it can be salvaged. I would arrive early, verify the settings against the standard, and re-run the scan properly. If the settings can't be corrected in time or the scan needs to be redone from scratch, I would make the call to reschedule rather than produce a result that can't be trusted — a non-compliant scan that looks compliant is worse than no scan, especially on a medical device where the result feeds into a regulatory submission. I would also make sure the engineer is part of the corrected run, so the lesson lands as experience rather than as a reprimand.

**Possible follow-ups:**
- How would you decide whether the incorrect scan can be salvaged or whether the whole scan needs to be redone?
- What would you put in place to prevent this kind of setup error from recurring on future scans?
