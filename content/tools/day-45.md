## Q1: How would you approach setting up a repeatable firmware build and release process for a medical device that uses Zephyr RTOS, where you need to produce auditable artifacts for regulatory purposes?

**Answer:** For a medical device, the build process itself becomes part of the design history file, so reproducibility and traceability are the primary drivers. I'd start by establishing a single source of truth for the toolchain — pinning the Zephyr SDK version, the west version, the compiler, and any Python dependencies. This typically means using a container image or a dedicated build machine where the environment is frozen and documented. The build itself should be driven by a script that takes a specific commit hash or release tag, performs a clean build, and records the exact environment (toolchain versions, west manifest hash, git commit ID) into a build manifest file.

For the west workspace, I'd use a manifest file with locked revisions rather than floating branches, so that a build performed six months later reproduces the exact same code. The output artifacts — the final binary, the hex file, the ELF with debug symbols, and the build manifest — should all be archived together with checksums. For regulatory traceability, I'd tag the release in git, and the build script would refuse to build from a dirty working tree or from an untagged commit unless explicitly overridden with a documented reason.

I'd also separate the production build from development builds. The production build should have deterministic settings: optimization level fixed, debug information included but stripped from the shipped binary if needed, and all safety-critical configuration options explicitly set rather than relying on defaults. The build script should fail on warnings for the production configuration, since a warning that seems harmless today could indicate a real issue in a different optimization context. Finally, I'd generate a software build record that includes the date, the person or system that initiated the build, the source revision, and the checksums — this becomes part of the audit trail for the regulatory submission.

**Possible follow-ups:** How would you handle the case where a field issue requires rebuilding an older release that used a different Zephyr version? What information would you include in the build manifest to make it useful for debugging a field failure months later?

## Q2: How would you approach using a mixed-signal oscilloscope to characterize noise coupling between a switching regulator and a precision analog sensor on the same PCB, and how would you determine whether the coupling is conducted, radiated, or through the ground plane?

**Answer:** The first step is to establish a repeatable measurement setup. I'd power the board from a clean bench supply and use a differential probe or a ground-spring technique on the oscilloscope to avoid introducing measurement artifacts. The key measurements are: the switching node of the regulator, the output ripple at the regulator's output capacitor, the supply pin of the analog sensor, the sensor's output signal, and the ground reference at both locations. I'd trigger on the switching node and use the oscilloscope's averaging mode to extract the periodic noise component from the sensor output, then use FFT to identify the frequency content.

To distinguish coupling paths, I'd use a systematic elimination approach. First, I'd measure the noise at the sensor's supply pin while the sensor is disconnected or in a known state — if the noise is present on the supply, it's likely conducted through the power distribution network. Then I'd probe the ground at the sensor location relative to the regulator ground — if there's a significant voltage difference at the switching frequency, ground bounce or ground plane impedance is the likely path. To check for radiated coupling, I'd use a near-field probe or simply move a small loop antenna near the suspected coupling path while watching the sensor output; if the noise changes when I move the probe, radiation is contributing.

For the ground plane question specifically, I'd measure the voltage difference between two ground points using a differential probe with the probe tips as close together as possible. A significant high-frequency component at the switching frequency indicates that the ground plane has enough impedance — due to splits, slots, or poor via placement — that return currents are creating voltage gradients. I'd also check whether the analog sensor's ground reference and the regulator's ground reference are at different potentials by looking at the DC offset and the AC content separately. Once I've identified the dominant path, the fix differs: conducted noise suggests better filtering or a pi-filter on the supply; ground coupling suggests via stitching, a solid ground plane, or relocating the sensor; radiated coupling suggests shielding or layout changes to reduce the loop area.

**Possible follow-ups:** How would you set up the oscilloscope's trigger and acquisition settings to capture intermittent noise that only appears under certain load conditions? What if the noise is broadband rather than at discrete switching frequencies — how would that change your diagnostic approach?

## Q3: How would you approach setting up a component library management strategy in KiCad for a medical device project that needs to maintain strict revision control and regulatory traceability, given that KiCad's library format is file-based rather than database-driven?

**Answer:** KiCad's file-based libraries actually lend themselves well to version control, which is the backbone of regulatory traceability. The key principle is that the library files themselves — symbols, footprints, and 3D models — must be treated as controlled documents with the same rigor as the schematic and PCB files. I'd structure the repository so that each library component has a clear path and naming convention that encodes its part number and revision, and I'd use git tags or branches to mark approved library releases.

For symbol libraries, I'd maintain a single project-specific library rather than relying on the default KiCad libraries, because the default libraries can change between KiCad versions and aren't under your control. Each symbol should have a documented source — the manufacturer's datasheet and part number — stored in the symbol description field or in a companion document. When a component changes, the symbol file gets a new revision, and the git history provides the audit trail of what changed and when. I'd also enforce a review process where library changes go through a pull request, and the merge into the main branch represents approval.

For footprints, the critical traceability link is the association between the symbol's footprint field and the actual footprint file. I'd verify that the footprint's pad layout matches the manufacturer's recommended land pattern from the datasheet, and I'd store the datasheet reference in the footprint description. The 3D model files should be versioned alongside the footprint, since a mismatch between the 3D model and the actual component can cause mechanical interference issues that only appear at assembly.

A practical workflow would be: each component gets a folder containing the symbol, footprint, 3D model, and a small text file with the manufacturer part number, datasheet revision, and approval date. The schematic and PCB files reference these components by name, and the library is tagged at each design release. Before a design freeze, I'd run a script that verifies every component in the schematic has a corresponding footprint and that no library files have been modified since the last tag without an accompanying revision note. This gives you the traceability required for a design history file without needing a commercial library management tool.

**Possible follow-ups:** How would you handle a situation where a component becomes obsolete mid-project and needs to be replaced with a pin-compatible alternative? How would you ensure that the library files remain consistent when multiple engineers are working on the same project?

## Q4: How would you approach using a logic analyzer to debug a SPI bus where the master device intermittently fails to receive data from a slave, but only after the system has been running for several hours and the temperature inside the enclosure has risen?

**Answer:** This is a classic thermal-dependent intermittent failure, and the logic analyzer is the right tool because it can capture the protocol-level behavior over long periods. The first challenge is that the failure is intermittent and temperature-dependent, so I'd need to set up a long-duration capture. Most logic analyzers have deep memory or streaming capability, so I'd configure the trigger to capture the failure event — for example, trigger on the slave not driving MISO during a read transaction, or on a missing clock edge. I'd also record temperature alongside the logic analyzer data, either by logging the enclosure temperature with a thermocouple or by having the firmware report the internal temperature sensor reading over a debug UART.

Before the long capture, I'd characterize the failure conditions. I'd run the system in a thermal chamber or use a heat gun to accelerate the temperature rise, while monitoring the SPI bus. The key is to determine whether the failure is in the master, the slave, or the interconnect. I'd look at the timing margins: is the slave's MISO data valid relative to the clock edge? Is the clock frequency shifting as the temperature changes? Are the rise times or fall times degrading, suggesting that a driver is weakening as it heats up? I'd also check whether the slave is actually receiving the correct commands — a logic analyzer with protocol decoding will show if the slave is responding with valid data but the master is misinterpreting it, versus the slave not responding at all.

Once I've captured the failure, I'd compare the waveform at the failure moment against a known-good capture from cold operation. Common findings include: the slave's MISO output is delayed beyond the master's setup time because the slave's internal timing shifts with temperature; the clock signal has excessive ringing or slow edges at temperature, causing double-clocking; or the slave is entering a fault state and releasing MISO to high-impedance, which the master reads as all-ones. I'd also check the voltage levels — if the supply rail is drooping at temperature, the logic thresholds shift and the timing margins degrade. The logic analyzer tells you what's happening at the protocol level, but I'd pair it with an oscilloscope probe on the actual signals to check analog characteristics like edge rates and voltage levels, since those are often the root cause of temperature-dependent digital failures.

**Possible follow-ups:** How would you distinguish between a slave that's not responding because it's in a fault state versus one that's responding but with corrupted data? What changes would you make to the test setup if the failure only occurs when the system is under vibration as well as at elevated temperature?

## Q5: (Behavioral) Imagine you are leading a project where a junior engineer has been tasked with setting up the automated firmware test environment for a medical device. On the day before a critical regression test run, you discover that the engineer has configured the test script to skip the safety-critical test cases because they were failing intermittently, and the engineer is confident this is acceptable because "the failures are just timing issues in the test harness, not real bugs." The test results will be used for a regulatory submission milestone. How would you handle this situation?

**Answer:** This situation has two distinct problems that need to be addressed separately: the immediate decision about the regression test run, and the underlying issue of how the engineer came to believe that skipping safety-critical tests was acceptable.

For the immediate decision, the answer is clear: we cannot run the regression suite with safety-critical tests disabled and claim the results support a regulatory milestone. The test results would be meaningless for that purpose, and submitting them would be both ethically wrong and technically indefensible. I would stop the test run, explain to the engineer that the intermittent failures are exactly the kind of issue that safety-critical testing is designed to catch — a timing issue in the test harness might indicate a real timing margin problem in the device that only manifests under specific conditions. I would also point out that if the failures are truly test harness artifacts, we need to fix the harness, not hide the failures.

The practical path forward is to investigate the intermittent failures before running the full suite. I'd ask the engineer to walk me through the failing test cases and the failure logs. We'd look at whether the failures correlate with system load, temperature, or specific test ordering. If the failures are in the harness — for example, a race condition in the test script or an incorrect timing assumption — we fix the harness and document the fix. If the failures are in the device firmware, we've just found a real bug that needs to be addressed before the regression run. Either way, the test suite runs complete, with all safety-critical cases enabled.

For the underlying issue, I'd have a separate conversation with the engineer about the reasoning that led to this decision. The core problem isn't technical — it's a misunderstanding of the purpose of safety-critical testing and the integrity of the regulatory process. I'd explain that in medical device development, the test results are evidence, and evidence that has been selectively filtered is worse than no evidence at all because it creates a false sense of security. I'd also discuss the professional responsibility aspect: when test results will be used for a regulatory submission, the engineer has an obligation to report failures transparently, not to make them disappear. I'd frame this as a learning opportunity rather than a reprimand, but I'd also make it clear that this kind of decision — unilaterally disabling safety tests — should never happen without explicit discussion with the project lead and a documented risk assessment.

Finally, I'd review the test environment configuration to ensure there are no other similar issues, and I'd add a check to the test script that fails the run if any test cases are skipped, so that this can't happen silently again.

**Possible follow-ups:** How would you handle the situation if the engineer's manager pushes back and says the schedule is more important than investigating the intermittent failures? What would you do if, during the investigation, you discover that the intermittent failures are caused by a real firmware bug that will take weeks to fix, and the regulatory submission deadline is immovable?
