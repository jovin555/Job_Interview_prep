## Q1: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** I'd start by treating the custom protocol as a timing problem before a decoding problem. First, capture a long enough trace at a sample rate comfortably above the fastest edge in the bus — a common rule of thumb is at least 5–10× the clock or bit rate, and more if the edges are slow or the bus is noisy — so the decoder has clean transitions to work from. Then I'd manually annotate one known-good transaction: identify the idle level, the start condition or sync pattern, the bit period, and how the frame header is delimited. If the header is non-byte-aligned, the key is to define the frame boundary explicitly rather than assuming byte alignment — most logic analyzers let you build a decoder from a state machine or a scripted decoder (Python/Lua-style) where you can specify "wait for this edge pattern, then sample N bits at this period, then parse fields." I'd encode the field layout as offsets from the frame start, not from a byte boundary, and add a checksum/CRC field check as an assertion so the decoder flags bad frames rather than silently misparsing. Before trusting the decoder, I'd validate it against a known stimulus — either a bench pattern generator or a firmware test mode that emits a fixed, documented frame — and confirm the decoded output matches the expected bytes and field values. I'd also build in a "raw bits" view so that when a frame fails to decode, I can see the actual bit stream rather than just an error. Finally, I'd version-control the decoder script alongside the firmware protocol definition so the two stay in sync, and document the frame format in the same place the firmware team documents it — that shared source of truth prevents the decoder from drifting from the real protocol.

**Possible follow-ups:** How would you handle a protocol where the bit period itself varies (e.g., a clock-stretching or variable-length encoding)? What would you do if the decoder works on the bench but fails intermittently on a production unit?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The core principle is that the build configuration is a controlled artifact, not an IDE state that lives only on one engineer's machine. I'd start by making the project file itself version-controlled and reviewed like source code, and I'd explicitly set — not inherit — the optimization level per target, the linker script path, the startup file, the preprocessor defines, and the include paths, so nothing depends on a default that could change between IDE versions or installations. For a medical device, I'd typically pin a known optimization level for release builds and document why (debug builds may use a lower level for traceability, but the release configuration is fixed and justified). The linker script and startup code would be treated as first-class source files with their own revision history, and I'd add a build-time check — a script or a post-build step — that verifies the actual compiler/linker command line and the resulting map file match the intended configuration, so a silent change gets caught. I'd also capture the toolchain version and the exact build command in the build log, and archive the map file and the generated artifacts with each release so the build is reproducible and auditable. Where possible, I'd drive the build from a script or makefile that invokes the toolchain directly rather than relying on a human clicking "Build" in the IDE, because a scripted build is far easier to audit and reproduce than an IDE session. The IDE project then becomes a convenience wrapper around a controlled build, not the source of truth.

**Possible follow-ups:** How would you detect that someone changed the optimization level locally without updating the controlled configuration? What's your approach to keeping debug and release configurations from diverging in ways that hide bugs?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The tracking generator plus directional coupler gives you a reflection measurement — you're measuring the return loss (or S11 magnitude) of the front-end across frequency, and from that you can infer input impedance. The setup matters as much as the math: I'd calibrate the measurement plane first, using a short/open/load (or the analyzer's built-in calibration routine) at the reference plane where the front-end connects, so the cable and coupler losses are removed from the result. The directional coupler's directivity sets the floor on how small a reflection you can trust — if the coupler's directivity is only, say, 20 dB, then return losses better than that are inside the measurement's uncertainty and you shouldn't over-interpret them. I'd also check the tracking generator's output level is low enough not to drive the front-end into nonlinearity (an active front-end can compress or shift its input impedance at higher drive levels), and I'd sweep slowly enough to resolve any narrow resonances. To decide whether the result is trustworthy, I'd cross-check against a known reference — a precision resistor or a characterized load — at the same reference plane, and confirm the measured impedance matches the expected value within the analyzer's specified accuracy. I'd also repeat the measurement with the front-end powered and unpowered, since bias conditions can change input impedance, and compare against the datasheet or simulation. If the measured and expected values agree on the reference load and the front-end result is stable across repeats, I'd act on it; if the reference load itself is off, I'd fix the setup before drawing any conclusion about the front-end.

**Possible follow-ups:** How would you extend this to a differential front-end where you can't simply reference one port to ground? What would cause the measured impedance to differ from simulation even when the setup is calibrated correctly?

## Q4: How would you approach setting up a Segger J-Link's RTT (Real-Time Transfer) logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?

**Answer:** RTT is attractive here precisely because it uses the debug probe's memory-access channel rather than a peripheral, so it doesn't consume the UART — but the perturbation risk is real and has to be designed around. I'd start by sizing the RTT buffer deliberately: a small up-buffer means the target blocks or drops messages when the host isn't draining fast enough, which both loses data and injects timing jitter, so I'd size it for the worst-case burst and configure the "block if full" versus "skip" behavior explicitly based on whether losing a log line is acceptable. For timing-sensitive code, I'd avoid logging inside interrupt handlers or tight control loops at all, or gate it behind a compile-time flag so the release build has zero RTT calls in the hot path. I'd measure the perturbation rather than assume it's negligible: toggle a GPIO at the start and end of a logging call and look at the added latency on a scope, and compare a timing-critical loop's period with RTT enabled versus disabled. If the added latency or jitter is unacceptable, I'd move logging to a low-priority thread that drains a lock-free ring buffer, so the hot path only pays the cost of a buffer write. I'd also confirm the debug probe's RTT polling rate on the host side is fast enough to keep up, and check that the RTT control block placement in RAM doesn't collide with anything the linker script has reserved. The decision of whether the logging is trustworthy comes down to whether the measured timing impact is within the budget the safety-critical protocol can tolerate — if it isn't, RTT logging stays a debug-only feature and never ships in the safety path.

**Possible follow-ups:** How would you detect that RTT logging is silently dropping messages under load? What's your approach if the debug probe connection itself is unreliable in the target environment?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** I'd treat this as a coaching moment first and a schedule problem second, because the underlying issue is that the engineer doesn't yet see why the settings matter — and that's fixable in a short conversation. I'd sit down with them and explain concretely: resolution bandwidth affects the noise floor and how a broadband versus narrowband emission is displayed, and detector mode (peak versus quasi-peak versus average) changes the measured amplitude in ways that can turn a pass into a fail or vice versa — so "the peaks show up either way" is exactly the trap, because the peak's *height* is what the standard judges, and that height depends on the settings. I'd show them the standard's required settings and, if time allows, do a quick side-by-side capture of the same emission with the wrong and right settings so the difference is visible rather than asserted. Then I'd fix the setup: reconfigure the analyzer to the standard's RBW and detector, re-verify against a known reference if one is available, and do a fast sanity scan tonight to confirm the setup is producing sensible numbers before the formal run. On the schedule, I'd rather spend an hour tonight correcting the configuration than burn non-refundable lab time tomorrow on invalid data — and I'd frame it to the engineer that way, as protecting the team's lab budget, not as assigning blame. Afterward I'd add a pre-scan checklist (settings, calibration, reference check) so the next person doesn't have to rediscover this, and I'd make sure the junior engineer owns updating that checklist — turning the mistake into a durable process improvement and giving them ownership of the fix.

**Possible follow-ups:** How would you handle it if the engineer pushed back and insisted the settings don't matter? What would you do if you discovered the issue only after the formal scan had already started?
