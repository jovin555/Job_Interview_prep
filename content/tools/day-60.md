## Q1: How would you approach setting up a Zephyr RTOS project using the west build system so that a single codebase can produce both a production image and a debug image with extra logging and assertions, without maintaining two separate trees?
**Answer:** The cleanest way is to treat the difference as configuration, not code. In Zephyr that means driving the two variants through Kconfig and devicetree overlays rather than `#ifdef` scattered through application source. I'd define a base board configuration, then layer a debug overlay that enables the logging subsystem at a higher verbosity, turns on assertions and stack sentinel checks, and pulls in any debug-only shell commands. The production build simply doesn't include that overlay. West is well suited to this because it separates the application, the manifest, and the build invocation — so I'd keep the variant selection in the build command or a small wrapper script rather than in the source. The key discipline is that both variants build from the same application code and the same drivers; only the configuration differs. That keeps the debug image a faithful representation of production behavior, which matters for a medical device where you don't want the thing you tested to diverge structurally from the thing you ship. I'd also make sure the build artifacts are clearly named and versioned so there's no ambiguity about which image is which.
**Possible follow-ups:** How would you prevent debug-only code from accidentally leaking into the production image? How do you keep the two configurations from drifting apart over time?

## Q2: How would you approach configuring a Segger J-Link for a Zephyr RTOS target where an automated test harness needs to flash the device, run a test sequence, and capture a crash dump — and what failure modes would you design around?
**Answer:** I'd script the J-Link side rather than rely on a GUI, because automation needs deterministic, repeatable commands. The flow is: reset and halt, flash the image, reset and run, then let the test sequence execute while the harness monitors for completion or a fault. For crash capture, the important part is that the target's fault handler leaves recoverable state — a fault log or a known memory region — that the debugger can read back after the fact without needing to have been attached at the moment of the fault. So I'd design the firmware to persist a crash record, and the harness to read that region on the next connection. Failure modes I'd plan around: the target not being in a known state at connect time (so always start with a reset/halt), the debug connection dropping mid-test (retry logic and a clean teardown), flash verify failures (always verify, don't assume), and the harness hanging if the target never signals completion (timeouts everywhere). I'd also make sure the debug interface can't be left in a state that blocks the next run.
**Possible follow-ups:** How would you distinguish a genuine firmware crash from a debugger connection problem? What would you log to make a failed run diagnosable after the fact?

## Q3: How would you approach setting up a power integrity simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?
**Answer:** I'd start by modeling the power distribution network as an impedance network — the regulator's output impedance, the plane and trace inductance, the decoupling network, and the load current profile of both the digital and analog sections. The goal is to see where the PDN impedance peaks relative to the frequencies the switching regulator injects and the frequencies the analog front-end is sensitive to. The trustworthy results are the ones where the model's assumptions match reality: a stackup and copper geometry that reflect the actual layout, component models that include ESR and ESL rather than ideal capacitors, and a load profile that reflects real switching behavior. I'd be skeptical of any result that depends heavily on a parameter I can't verify, and I'd treat the simulation as a way to rank design choices — which decoupling placement, which plane split, which regulator placement — rather than as a prediction of an absolute number. Then I'd validate the highest-risk conclusions with bench measurement, because the simulation tells you where to look, not what you'll find.
**Possible follow-ups:** How would you decide whether a resonance in the PDN impedance is actually a problem? What measurements would you use to confirm the simulation?

## Q4: How would you approach setting up a cross-probe workflow between OrCAD Capture and Cadence Allegro so a layout review can move efficiently between schematic and PCB, and what would you check to confirm the link actually works before relying on it in a review?
**Answer:** Cross-probing depends on the two tools sharing a consistent netlist and reference designator mapping, so the first thing is to confirm the schematic and layout are synchronized — same netlist, same reference designators, no unresolved components. Once that's true, I'd verify the link with a deliberate test: select a specific net or component in the schematic and confirm the corresponding object highlights in the layout, and vice versa. I'd test a few cases that are easy to get wrong — a net that spans multiple pages, a component with multiple parts, a net that's been renamed. If any of those fail to cross-probe correctly, the link isn't trustworthy and I'd fix the synchronization before the review. The value in a review is that you can move from "this net looks wrong in the schematic" to "here's where it's routed" without manual searching, which keeps the review focused on the design rather than on navigation. But that only works if you've confirmed the link is real, not assumed it.
**Possible follow-ups:** What would cause cross-probing to silently point at the wrong object? How would you handle a review where the schematic and layout are known to be out of sync?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the Altium Designer output job configuration for a medical device PCB release, and you discover the fabrication outputs are missing the drill table and the assembly drawings reference an outdated revision of the schematic. The board house is expecting the files tomorrow, and the engineer is confident the outputs are complete because "the Gerbers look fine." How would you handle this situation?
**Answer:** The immediate priority is the release — a fabrication package that's missing the drill table or references a stale schematic revision is not something to send, regardless of the deadline. So I'd first stop the release and verify exactly what's missing and what's stale, then decide whether it can be corrected in time or whether the board house needs to be told the files are coming a day later. That's a schedule conversation, not a technical one, and it's better had honestly than papered over. On the human side, I'd avoid framing this as the engineer being wrong — the mistake is understandable, because "the Gerbers look fine" is exactly the trap: the Gerbers can be correct while the package as a whole is incomplete. I'd walk through what a complete release package actually contains and why each piece matters, and I'd use it as a reason to build a release checklist that the output job enforces rather than relies on memory. The goal is that the next release doesn't depend on someone remembering the drill table.
**Possible follow-ups:** How would you build a release checklist that catches this kind of omission automatically? How would you handle the conversation with the board house about the delay?
