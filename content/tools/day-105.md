# tools — Day 105

## Q1: How would you approach setting up a repeatable, auditable release process for a hardware design in Altium Designer, so that the fabrication and assembly outputs for a given revision can be regenerated identically months later?

**Answer:** The core problem is that an output job is only reproducible if everything it depends on is pinned: the schematic/PCB revision, the output job configuration itself, the layer stack and design rules, and the tool version. I'd start by treating the output job file as a versioned artifact in the same repository as the design, not a local setting that lives on one engineer's machine. The job would define every output the release needs — Gerbers per layer with a consistent naming convention, NC drill and drill table, pick-and-place with a defined origin and rotation convention, assembly drawings, BOM in a fixed format, and a PDF of the schematic — and I'd make the output paths relative so the job works from any checkout location.

For traceability, I'd tie each release to an immutable tag or baseline in the design repository, and record in the release notes the tool version, the output job revision, and a checksum of the generated archive. That way, if a question comes up during regulatory review or a supplier query, you can check out the exact tag, re-run the same job, and compare. I'd also build in a verification step before the files leave: open the Gerbers in an independent viewer, confirm the drill table matches the drill files, confirm the assembly drawing revision matches the schematic revision, and check that the BOM line items reconcile with the schematic. The point is that "the Gerbers look fine" is not a check — the check is that the outputs are internally consistent and match the tagged revision.

**Possible follow-ups:** How would you handle a situation where the tool version has changed between the original release and the regeneration, and the outputs no longer match byte-for-byte? What would you include in the release archive beyond the fabrication files themselves?

## Q2: How would you approach setting up a constraint manager in Cadence Allegro for a mixed-signal board where high-speed digital nets and sensitive analog nets share the same design, and how would you verify the constraints are actually being honored rather than just defined?

**Answer:** I'd structure the constraint set in layers of specificity. At the top, physical and spacing rules that apply globally — minimum trace width, default clearance, via-to-via spacing — set from the fabrication capability of the board house with margin. Then net-class-level rules: a class for the high-speed digital interfaces with their impedance targets and length-matching tolerances, a class for the analog signal nets with wider spacing to aggressors and, where relevant, a keep-out from the digital region, and a class for power nets with their own width and via-count rules. Then, where needed, individual net or pair rules that override the class defaults — for example, a specific differential pair with a tighter skew budget than the class.

The important part is that the constraint manager is only useful if the constraints are enforced and visible. I'd make sure the online DRC is running with the full rule set during routing, not just at the end, and I'd use the constraint-driven routing features so the router is actually honoring the targets rather than the engineer eyeballing them. For verification, I'd run a full DRC and review the report, but I wouldn't stop there — I'd also do targeted checks: measure the actual routed lengths and skew on the matched interfaces, confirm the impedance targets are reflected in the stackup and trace geometry, and check that the analog nets haven't been routed through or adjacent to the digital region in a way the spacing rules wouldn't catch (for example, a parallel run at a distance that passes the clearance rule but is still a coupling concern). The rule set catches what it's written to catch; the review catches what it isn't.

**Possible follow-ups:** How would you decide the spacing between an analog net and a high-speed digital net when the fabrication clearance rule is much smaller than what you'd want for noise reasons? What would you do if a constraint conflict forces a trade-off between two interfaces?

## Q3: How would you approach configuring a Keil uVision project so that the optimization level, linker script, and startup code are locked down and auditable, rather than left at whatever the IDE defaults to?

**Answer:** The risk with IDE-managed build settings is that they're easy to change accidentally and hard to review — someone flips the optimization level to debug a problem and forgets to flip it back, or the linker script gets edited in the IDE and the change never makes it into version control in a reviewable form. So the first principle is: the build configuration should be a versioned file, and changes to it should go through the same review as code.

Concretely, I'd keep the project file and the linker script under version control, and I'd treat the optimization level, the C standard, the warning levels, and the define set as deliberate, documented choices rather than defaults. For a medical device, the optimization level used for the released build should be the one that was tested — if development and testing happen at one level and release at another, you've changed the code the compiler generates without re-testing it, which is a classic source of "works in the lab, fails in the field" bugs. I'd also make sure the startup code and the vector table are pinned to a known revision and that the memory layout in the linker script matches the actual part — flash and RAM regions, any reserved regions for calibration data or bootloader, and the stack/heap sizes. A mismatch there can silently corrupt data.

For auditability, I'd generate a build manifest as part of the release: tool version, optimization level, defines, linker script revision, and a hash of the output binary. That manifest goes into the design history file alongside the source tag. And I'd verify the built image on the target — check that the vector table is where the linker script says it is, that the calibration region is untouched, and that the image size and memory map match expectations.

**Possible follow-ups:** How would you handle a situation where a bug only reproduces at one optimization level — what's your process for deciding which level ships? What would you check first if the built image behaved differently from the debug build on the same hardware?

## Q4: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The measurement is a reflection measurement: the tracking generator sweeps a known source into the front-end through a directional coupler, and the analyzer measures the reflected signal, from which you derive return loss and then impedance. The setup details matter more than the sweep. I'd start by calibrating out the test setup — the cables, the coupler, and any adapters — using a reference standard or a thru/short/open calibration at the plane where the front-end connects, because at RF frequencies the cable and connector parasitics are a significant fraction of what you're trying to measure. I'd set the sweep to cover the band of interest with enough points to resolve any resonances, and I'd keep the source power low enough not to drive the front-end's active devices into nonlinearity, which would invalidate the measurement.

Then the trust question. A single sweep that looks plausible isn't enough. I'd check repeatability — reconnect and re-measure, and see whether the result is stable. I'd check the measurement against a known reference, like a resistor or a characterized attenuator, to confirm the setup is reading what it should. I'd look at whether the result is physically sensible: does the impedance trajectory make sense for the topology of the front-end, or is it showing an artifact of a bad cal or a connector problem? And I'd be suspicious of any feature that appears at the same frequency regardless of what's connected — that's usually the setup, not the device. Only when the measurement is repeatable, reference-checked, and physically consistent would I act on it, and even then I'd cross-check against a simulation of the front-end's input network before changing a component value.

**Possible follow-ups:** What would you do if the measurement showed a resonance you didn't expect — how would you determine whether it's real or a setup artifact? How would you extend this to a differential front-end?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** The first thing is to separate the technical issue from the interpersonal one. Technically, the engineer isn't wrong that the peaks show up either way — a quick scan with a wide resolution bandwidth and a peak detector will show you where the energy is. But pre-compliance results are only meaningful if they're measured the way the standard specifies, because resolution bandwidth and detector mode change the measured amplitude, and a scan that isn't done to the standard can't be used to demonstrate compliance or to justify a design change. So the settings need to be corrected before the formal scan, and the earlier quick scan should be treated as a scoping exercise, not a result.

On the interpersonal side, I'd avoid framing it as "you did it wrong." I'd explain why the settings matter — what the standard requires and what changes when you use them — and I'd walk through it with the engineer so they understand the reasoning rather than just being told to change a setting. That's how you build judgment rather than compliance. Then I'd deal with the schedule: the lab time is booked, so the practical question is whether the correct settings can be applied and the scan re-run within the booked window. If the setup can be corrected quickly, we do that and proceed. If not, I'd rather reschedule or extend the lab time than run a formal scan with the wrong settings and have to explain later why the results aren't usable — a scan done wrong is worse than a scan done late, because it creates a false record.

**Possible follow-ups:** How would you prevent this from happening on the next scan — what would you put in place so the setup is verified before the formal run? How would you handle it if the engineer felt you were second-guessing their competence?
