## Q1: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?
**Answer:** I'd treat this as a two-stage problem: first capture a trustworthy waveform, then teach the tool the protocol. For capture, I'd start with the highest sample rate the analyzer supports and a deep enough memory buffer to hold several complete transactions, because a non-byte-aligned header means I can't rely on the analyzer's clock-recovery assumptions — I need raw edges. I'd trigger on the first edge of a suspected frame and capture enough pre-trigger to see the idle state before it. Then I'd manually decode one frame by hand from the waveform: identify the header pattern, count the bits between edges, and confirm the bit period is consistent. Only once I understand the framing would I write a custom decoder — most analyzers (Saleae, Sigrok/PulseView, some Keysight and Tektronix units) let you script a decoder in Python or a simple state-machine description. I'd build it incrementally: decode the header first and verify it against known-good traffic, then add the payload, then the checksum. A key trap with non-byte-aligned frames is that the analyzer's default "bit order" and "clock edge" settings may be wrong; I'd expose those as parameters rather than hard-coding them. I'd also validate the decoder against a known reference — for example, a captured frame where I already know the sensor value from a separate measurement — before trusting it for debugging. Finally, I'd save the decoder and its settings as part of the test setup so the next engineer doesn't have to reverse-engineer it again.
**Possible follow-ups:** How would you handle a protocol where the bit period varies slightly between frames (e.g., a clock-stretching slave)? What would you do if the custom decoder works on captured data but the live decode shows errors?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?
**Answer:** The core principle is that the build configuration is a controlled artifact, not a personal preference. I'd start by treating the `.uvprojx` (or `.uvproj`) project file as source-controlled and reviewed like code — no one edits it locally without a commit. For the optimization level, I'd set it explicitly per target (e.g., `-O0` for debug, a defined level for release) and document *why* that level was chosen, because optimization can change timing and expose latent bugs. I'd avoid relying on the IDE's "default" because defaults can shift between toolchain versions. For the linker script, I'd keep it in the project tree, not in the toolchain install directory, and reference it by relative path so the build is reproducible on another machine. I'd add a post-build step that dumps the memory map and the compiler/linker command line into the build log, so the actual flags used are recorded — that's the auditable evidence. For startup code, I'd pin a specific version and treat changes to it as a design change requiring review, since startup code affects stack setup, vector table placement, and clock initialization. I'd also add a pre-build check that fails the build if the optimization level or linker script path doesn't match the expected value — a simple script that greps the project file. That turns "we think it's set correctly" into "the build fails if it isn't." Finally, I'd document the toolchain version (Keil MDK version, ARM compiler version) alongside the project, because the same project file can behave differently across compiler versions.
**Possible follow-ups:** How would you handle a situation where a third-party library was only validated at a different optimization level? What's your approach to verifying that the release build's memory map matches what the linker script intended?

## Q3: How would you approach setting up a spectrum analyzer for a conducted emissions pre-compliance scan on a medical device's AC input, and what would you check before trusting the first measurement?
**Answer:** Conducted emissions on the AC input is a measurement where the setup dominates the result, so I'd spend most of my effort on the setup before looking at any trace. First, the LISN (line impedance stabilization network): it must be the correct type for the standard being targeted, properly bonded to the reference ground plane, and the EUT's power cord must be the specified length and routed as the standard requires — a coiled or shortened cord changes the measurement. I'd verify the LISN's own noise floor by terminating its EUT port with a 50-ohm load and scanning with no EUT connected; if the floor isn't clean, nothing downstream is trustworthy. Second, the analyzer settings: resolution bandwidth, detector mode (quasi-peak vs. peak vs. average), and scan time must match the test standard, because a peak detector will overstate emissions relative to quasi-peak and can send you chasing a non-failure. I'd set the start/stop frequencies and the limit line from the standard, not from memory. Third, the environment: I'd do a background scan with the EUT off to identify ambient signals (broadcast AM, switching supplies in the lab) that could be mistaken for EUT emissions. Fourth, the EUT operating mode: for a medical device, I'd confirm it's in its worst-case emission mode — typically maximum load, all radios transmitting, display at maximum brightness — because a scan in idle mode proves very little. Only after all of that would I trust the first trace. I'd also record the setup (LISN model, cable lengths, analyzer settings, EUT mode) so the scan is repeatable and so a formal test house can compare.
**Possible follow-ups:** How would you distinguish an ambient signal from a real EUT emission if they overlap in frequency? What would you do if the pre-compliance scan passes but the formal test fails?

## Q4: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?
**Answer:** The tracking generator plus directional coupler gives me a return-loss (or reflection coefficient) measurement, from which I can derive impedance. The setup matters more than the math. I'd first calibrate out the test setup: connect the coupler's coupled port to the analyzer, terminate the through path with a known 50-ohm load, and store that as the reference — this removes the coupler's directivity error and cable loss from the measurement. Then I'd measure a known standard (an open, a short, and a 50-ohm load) to verify the calibration is actually valid across the frequency range of interest; if the open/short traces don't look like textbook opens and shorts, the calibration is bad and I shouldn't trust anything downstream. For the actual DUT measurement, I'd keep the connection to the front-end as short as possible and use the same connector type throughout, because a pigtail adapter introduces its own impedance discontinuity. The trustworthiness question comes down to three checks: (1) does the measurement reproduce if I disconnect and reconnect the DUT? (2) does the result make physical sense given the front-end's topology — for example, a high-impedance input should show a return loss that's poor at low frequency and improves as the input capacitance dominates? (3) does a SPICE simulation of the front-end's input network predict roughly the same shape? If the measurement and simulation disagree, I'd suspect the setup before I suspect the circuit. I'd also be honest about the limits: a directional coupler has finite directivity, so very high return loss (near-perfect match) can't be measured accurately — I'd note that as a measurement floor rather than claim a precise number.
**Possible follow-ups:** How would you extend this to measure impedance at a frequency where your coupler's directivity is poor? What's the difference between using a tracking generator versus a VNA for this measurement, and when would you choose one over the other?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?
**Answer:** The first thing I'd do is separate the technical issue from the interpersonal one, because they need different responses. Technically, the engineer isn't wrong that peaks show up either way — what changes with RBW and detector mode is the *amplitude* of those peaks and therefore whether they're above or below the limit line. A peak detector with a wide RBW can overstate emissions and send the team chasing a non-failure; a narrow RBW with the wrong detector can understate them and let a real failure through. So this isn't a cosmetic setting, and I'd explain that concretely rather than just asserting it. I'd sit down with the engineer, pull up the standard's requirements for RBW and detector, and walk through what each setting does to the trace — ideally by re-scanning one known emission with both settings so the difference is visible, not theoretical. That converts "you're wrong" into "here's what the tool is actually doing." On the schedule: I'd check whether the correct settings can be applied and the scan re-run in the booked time — often they can, because the setup is already done and only the analyzer configuration changes. If the full scan can't be redone, I'd prioritize re-scanning the frequency bands where the limit margin is tightest, and document that the rest of the scan used non-compliant settings and needs to be repeated. I'd avoid framing this as the engineer's failure; the real gap is that the project didn't have a written test procedure specifying the settings, so I'd fix that too — a one-page procedure that lists RBW, detector, scan time, and limit line for each band, so the next person doesn't have to guess. Finally, I'd communicate to the project lead that the formal scan may need a follow-up, so the schedule risk is visible early rather than discovered at the test house.
**Possible follow-ups:** How would you handle it if the engineer pushed back and said the standard's settings were "overly conservative"? What would you put in the test procedure to prevent this from recurring on the next project?
