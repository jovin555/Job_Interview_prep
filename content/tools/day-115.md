## Q1: How would you approach setting up a Segger J-Link's RTT (Real-Time Transfer) logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?

**Answer:** RTT is attractive here precisely because it doesn't consume a peripheral — it works through the debug probe reading a shared-memory ring buffer on the target, so the safety-critical UART stays untouched. The setup has three parts. First, on the target side, I'd enable the Zephyr RTT backend (or wire the SEGGER RTT library in directly), allocate the up-buffer in a known RAM region, and confirm the linker places it where the probe expects — the control block address is what the host tool keys off, so a mismatch between the linked address and what the host assumes is the classic first failure. Second, on the host side, I'd connect J-Link RTT Viewer or the RTT client library and verify the control block is found before trusting any output. Third, and most important for a safety-critical system, I'd think hard about perturbation: RTT writes are fast but not free, and a blocking write when the buffer is full will stall the logging thread. So I'd use non-blocking/skip-on-full mode, keep messages short and pre-formatted, avoid logging inside ISRs or timing-critical sections, and size the buffer so normal burst rates don't overflow. I'd also confirm the debug probe connection itself doesn't halt the core — RTT is designed for this, but I'd verify the target keeps running. Finally, I'd measure: toggle a GPIO around the logging call and check on a scope that the added latency is acceptable, and compare timing with logging on versus off.

**Possible follow-ups:** How would you detect at runtime that the RTT buffer is overflowing and messages are being dropped? What would you do if the debug probe had to be disconnected during a long-duration test — how does your logging strategy degrade?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is that a build is reproducible and that every setting affecting the binary is visible and under version control, not buried in a GUI dialog someone clicked once. I'd start by treating the project file itself as a reviewed artifact — the `.uvprojx` and any scatter file go into version control, and changes to them get the same scrutiny as source code. For optimization, I'd pin the level explicitly per target (often `-O0` or `-O1` for debug, a defined level for release) and document why, because optimization level can change timing and expose latent undefined behavior; leaving it at "whatever the IDE picked" is exactly the risk to avoid. The linker/scatter file defines memory layout — flash regions, RAM, any reserved calibration or bootloader areas — and I'd make sure it's an explicit, versioned file rather than an auto-generated default, with the memory map cross-checked against the datasheet and the bootloader's reserved regions. Startup code and the vector table I'd keep as reviewed source, not a black-box generated file, so the reset path and stack/heap setup are auditable. Then I'd add a build-time check: a script that diffs the effective compiler/linker flags against an expected baseline and fails the build on drift, plus archiving the map file and the exact toolchain version with each release so the binary can be regenerated and traced later.

**Possible follow-ups:** How would you catch a situation where someone changed the optimization level locally and the binary "works" but differs from the released one? What role does the map file play in your audit trail?

## Q3: How would you approach setting up a power integrity simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?

**Answer:** I'd frame it around the question the simulation actually needs to answer: how much switching noise reaches the analog front-end through the PDN, and is the decoupling and plane structure adequate. The workflow starts with an accurate model of the PDN — stackup with real dielectric and copper thickness, plane shapes, via transitions, and the regulator's output impedance plus its loop behavior. I'd run an AC impedance sweep of the PDN from the regulator output to the analog load point, looking for resonances and anti-resonances where impedance peaks, then overlay the current draw spectrum of the switching regulator to see which harmonics land on those peaks. That tells me where the risk is before I ever look at a transient. Trust is the hard part: a PI simulation is only as good as its models, so I'd validate against measurement — a VNA impedance measurement of a bare or populated board at the same nodes, or a scope measurement of ripple at the analog rail under real load — and if the simulated and measured impedance curves don't roughly agree, I don't act on the simulation. I'd also treat results as directional rather than absolute: the simulation is reliable for comparing decoupling strategies and spotting resonances, less reliable for predicting an exact millivolt number. I'd only make a design change when the effect is large relative to model uncertainty and corroborated by measurement.

**Possible follow-ups:** What would make you distrust a clean-looking impedance curve? How would you decide whether a resonance is the regulator's fault or the decoupling network's?

## Q4: How would you approach setting up a cross-probe workflow between OrCAD Capture and Cadence Allegro so a layout review can move efficiently between schematic and PCB, and what would you check to confirm the link actually works before relying on it in a review?

**Answer:** Cross-probing depends on the two tools agreeing that they're looking at the same design, so the first thing I'd verify is that the Capture project and the Allegro board are tied to the same netlist and the same design name — a stale or mismatched netlist is the usual reason cross-probe silently does nothing or highlights the wrong part. I'd confirm both tools are launched in a way that establishes the link (the standard Capture-to-Allegro session), then do a deliberate smoke test before the review: select a specific component in the schematic and confirm the correct footprint highlights in the layout, then go the other direction — click a pad or component in Allegro and confirm the right symbol and net highlight in Capture. I'd test a net as well as a component, since net-level cross-probing is where mismatches show up. I'd also check that the highlight colors are visible against the board's color scheme, because a "working" link that highlights in a color nobody can see is useless in a live review. Only once those round-trips are confirmed would I run the review off it, and I'd keep the netlist sync step explicit so nobody reviews against a board that's drifted from the schematic.

**Possible follow-ups:** What would you do if cross-probe works for components but not for nets? How would you handle a review where the layout was generated from an older netlist revision than the current schematic?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** I'd treat it as a teaching moment first and a scheduling problem second, because the engineer isn't wrong that peaks show up — they're missing why the settings matter. I'd explain concretely: resolution bandwidth affects the measured amplitude of broadband versus narrowband emissions and how close peaks can be resolved, and detector mode (peak versus quasi-peak versus average) changes the number you report, so a "get a feel for it" scan can both miss a marginal failure and misreport a passing one. The point isn't that the peaks are invisible; it's that the number attached to them isn't the number the standard cares about. Then I'd fix it: reconfigure to the standard's RBW and detector, re-run the scan, and compare against the quick scan so the engineer sees the difference for themselves — that's more convincing than an argument. On logistics, I'd check whether the corrected scan fits in the booked time; if not, I'd prioritize the frequency bands and suspect emissions rather than cancel, and be honest with whoever owns the schedule that the earlier settings weren't compliant. I'd avoid blaming the engineer publicly — the failure is really that the setup procedure wasn't documented and checked, so I'd turn the corrected configuration into a written pre-scan checklist so the next person doesn't repeat it.

**Possible follow-ups:** How would you build that pre-scan checklist so it's actually used rather than ignored? If the corrected scan revealed a marginal failure the quick scan had hidden, how would you communicate that to the project?
