## Q1: How would you approach setting up a Zephyr RTOS project to support multiple hardware revisions where the sensor interface changes from I2C to SPI between revisions, without duplicating the entire application code?

**Answer:** The key is to use Zephyr's device tree (DT) and Kconfig configuration system to abstract the hardware differences away from the application logic. I would structure the project with a common application layer that calls sensor APIs through Zephyr's sensor subsystem, rather than directly manipulating I2C or SPI registers. Each hardware revision gets its own device tree overlay file (e.g., `boards/board_rev1.overlay` and `boards/board_rev2.overlay`) that defines the sensor node with the appropriate bus binding — `spi-device` or `i2c-device` — along with the correct chip-select pin, speed, and any revision-specific GPIOs. The application code then uses `device_get_binding()` with a fixed label (like `sensor0`) and the standard sensor API (`sensor_sample_fetch()`, `sensor_channel_get()`), so the bus protocol change is invisible to the application. For build-time selection, I'd use a Kconfig option or a CMake variable to pick the right overlay, and the `west build` command would reference the appropriate board target. I'd also verify that the devicetree bindings for the sensor driver support both bus types — if the vendor driver only supports one bus, I'd need to write a small shim driver that wraps the vendor driver and presents a unified interface. Finally, I'd add a compile-time sanity check (e.g., a `BUILD_ASSERT` on the chosen bus type) to catch misconfiguration early.

**Possible follow-ups:**
- How would you handle a case where the sensor driver itself is not upstream in Zephyr and you need to integrate a vendor SDK?
- What would you do if the two revisions also differ in the sensor's register map, not just the bus interface?

## Q2: Walk me through your process for using LTSpice to simulate the effect of a long power cable (e.g., 2 meters) on the stability of a buck converter powering a sensitive analog sensor, and how you would validate the simulation with real measurements.

**Answer:** A long cable introduces series inductance and resistance, plus parasitic capacitance, which can destabilize a buck converter's control loop or cause ringing at the load. In LTSpice, I'd model the cable as a lumped-element T-network: series inductance (roughly 0.5–1 µH per meter for twisted pair, depending on geometry), series resistance (from wire gauge), and shunt capacitance to ground. I'd place this network between the buck converter output and the load (the sensor and its analog front-end). The simulation would include the converter's output capacitor, the load's input decoupling, and the sensor's current draw profile — including any dynamic load steps (e.g., when the sensor wakes up or an ADC samples). I'd run a transient analysis with a load-step stimulus to observe the response at the load: look for excessive ringing, voltage droop, or oscillation. I'd also run an AC analysis (if the converter model supports it) to check the loop gain and phase margin at the load, not just at the converter output. To validate, I'd measure the voltage at the load with an oscilloscope using a differential probe (or two matched probes in A-B mode) during a load step, and compare the ringing frequency, damping, and settling time against the simulation. If they match within reasonable tolerance (accounting for cable parasitics uncertainty), the model is trustworthy. If not, I'd refine the cable model — for example, measure the actual cable inductance with an impedance analyzer or estimate it from the ringing frequency.

**Possible follow-ups:**
- How would you decide whether to add a bulk capacitor at the load end versus increasing the converter's output capacitance?
- What if the cable also carries digital signals — how would you model the coupling between the power and digital lines?

## Q3: How would you approach using a logic analyzer to debug a CAN-FD bus where the node occasionally enters bus-off state after several hours of operation, but only when the system is under vibration?

**Answer:** Intermittent bus-off under vibration strongly suggests a physical-layer issue — likely a loose connector, cracked solder joint, or marginal termination — rather than a protocol or firmware logic problem. My approach would be to capture the bus traffic leading up to the bus-off event, not just the event itself. I'd set up the logic analyzer with a deep memory buffer and a trigger on the bus-off condition (e.g., the node's error frame pattern or the transition to bus-off state). CAN-FD requires sampling at a high rate — at least 10× the bit rate, so for 5 Mbps FD, I'd sample at 50 MS/s or higher. I'd also probe the physical layer: the CAN_H and CAN_L lines differentially (using two channels in A-B mode or a differential probe), plus the node's TX pin and the transceiver's error/status pin if available. The key is to correlate the bus-off with physical-layer anomalies: look for glitches, amplitude droops, or bit-timing violations that occur just before the error counter increments. Under vibration, a marginal connection can cause brief signal dropouts or reflections that corrupt a single bit — the CAN controller sees a bit error, increments the TEC, and eventually enters bus-off after 256 consecutive errors. I'd also check the termination resistors — a loose or intermittent ground connection can cause the common-mode voltage to shift, which is a classic cause of vibration-induced CAN failures. If the logic analyzer shows clean digital signals but the physical layer is marginal, I'd use an oscilloscope with a differential probe to look at the actual analog waveform during vibration, checking for amplitude, slew rate, and ringing against the transceiver's specifications.

**Possible follow-ups:**
- How would you distinguish between a bit error caused by a physical-layer issue versus a bit-stuffing or protocol violation?
- What changes would you make to the test setup to increase the likelihood of capturing the event?

## Q4: (Behavioral) Imagine you are leading the bring-up of a new medical device prototype, and you discover that the firmware team has been using a different version of the CAN-FD protocol than what the hardware actually implements — the firmware is expecting a specific data field ordering and bit-rate switch configuration, but the hardware's CAN-FD controller is configured differently. The integration testing is scheduled to start in two days, and both teams are confident their implementation is correct. How would you handle this situation?

**Answer:** The first priority is to de-escalate the "my implementation is correct" standoff and get to the facts. I'd call a short, focused meeting with both teams' leads and the relevant engineers, and frame it as a joint debugging session rather than a blame assignment. I'd bring the actual protocol specification (or the ICD — Interface Control Document) to the meeting, and we'd walk through the data field ordering and bit-rate switch configuration line by line, comparing what the firmware expects against what the hardware controller is configured for. If the ICD is ambiguous or missing, that's the root cause — and we'd need to resolve the ambiguity by looking at the original requirements or the system architect's intent. If the ICD is clear, then one side is wrong, and we'd identify which one based on the document. Once we know the correct configuration, I'd assess the impact: if it's a firmware-only change (e.g., reordering data fields in the TX buffer), that's a quick fix — a few hours of work and a recompile. If it's a hardware configuration change (e.g., the CAN-FD controller's bit-rate switch settings are set via external pins or a one-time-programmable fuse), that's more serious and might require a hardware rework or a workaround in firmware. I'd also check whether the two-day integration testing window can absorb the fix — if the change is firmware-only, we can likely make it; if it requires hardware rework, I'd need to communicate the schedule impact to management and propose a revised plan (e.g., test other subsystems first, or use a software CAN implementation as a temporary workaround). Throughout, I'd emphasize that the goal is to get the system working correctly, not to assign blame, and I'd document the resolution so the same issue doesn't recur in future projects.

**Possible follow-ups:**
- How would you handle it if the ICD itself is ambiguous and both teams have reasonable interpretations?
- What process changes would you propose to prevent this type of mismatch in future projects?

## Q5: How would you approach setting up a differential pair routing constraint in Cadence Allegro for a USB 2.0 interface on a mixed-signal medical device PCB, and how would you verify that the constraints are actually met in the final layout?

**Answer:** USB 2.0 requires a 90-ohm differential impedance (with a typical tolerance of ±10–15%) and length matching between D+ and D- to minimize skew. In Allegro, I'd start in the Constraint Manager under the Electrical constraints set. I'd create a differential pair object for the D+/D- nets and assign the following constraints: a target impedance of 90 ohms (which Allegro uses for the physical rule deck), a differential pair spacing rule (e.g., 8 mils edge-to-edge, depending on the stackup), and a length matching tolerance (e.g., 5 mils or less for USB 2.0 at 480 Mbps). I'd also set the maximum total length to control signal attenuation. The impedance target is only meaningful if the stackup is defined correctly — I'd verify the dielectric thickness, copper weight, and layer stack with the board house's capabilities before setting the impedance rule. For the physical layout, I'd route the pair with the "differential pair" routing tool, which maintains the spacing and length matching automatically. After routing, I'd run the Constraint Manager's analysis to check for violations — it will flag any nets that exceed the length mismatch or spacing rules. I'd also use the cross-section editor to verify the calculated impedance for the actual trace width and spacing used, and if possible, request a coupon on the fabrication panel so the board house can measure the actual impedance. Finally, I'd review the routing visually: the pair should be routed together on the same layer, with no vias that break the symmetry, and the return path (ground) should be continuous beneath the pair.

- How would you handle a situation where the board stackup forces a trace width that is too wide for the available routing space?
- What additional considerations would you have for USB 2.0 if the device is battery-powered and the cable is long?
