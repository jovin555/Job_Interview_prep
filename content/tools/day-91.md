## Q1: How would you approach setting up a schematic library in Altium Designer so that symbols stay consistent and traceable across a multi-year medical device program, where the same part may be reused across several board revisions?

**Answer:** The core problem is that a schematic symbol is a contract — pin numbers, pin names, electrical types, and the mapping to a footprint all have to remain stable for the life of the program, because a change to a symbol silently propagates into every schematic that uses it. I'd start by treating the library as a controlled artifact rather than a scratch pad: a dedicated library repository under version control, with the library itself released as a numbered revision rather than edited in place. Each symbol gets a unique part number and a revision field, and the schematic references that part number rather than a free-text value. When a part genuinely needs to change — a datasheet revision, a pinout correction — I'd create a new revision of the symbol rather than editing the existing one, so that existing designs keep pointing at the revision they were validated against, and the change is a deliberate migration rather than an accident.

For consistency I'd enforce a symbol convention document: grid, pin length, pin grouping by function, power pins handled the same way every time, and a rule that the symbol's pin numbers must match the footprint's pad numbers exactly. Electrical type (input, output, power, passive, bidirectional) matters more than people think — it's what makes ERC meaningful, so I'd set it deliberately rather than leaving everything passive. I'd also keep the symbol and footprint as a linked pair in the same library database, with the footprint name encoded in the symbol's parameters, so a part can't be placed without its footprint association being explicit.

Traceability is the other half. For a medical program, the library revision that a given board revision was built from needs to be recoverable years later, so I'd tag library releases and record the library revision in the design's release documentation. That way, when someone asks "what symbol did we use for this sensor on the board we shipped," the answer is a specific revision, not "whatever was in the library at the time." I'd also run a periodic library audit — a script or a report that flags symbols whose footprint link is broken, whose parameters are incomplete, or which have been modified since the last release — because library drift is slow and invisible until it bites you at fabrication.

**Possible follow-ups:** How would you handle a situation where a symbol needs to change but several released designs depend on the old version? What would you put in the symbol's parameters to make BOM generation and regulatory documentation easier downstream?

## Q2: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** The first step is to resist the temptation to start from a built-in decoder and bend it. If the framing is genuinely non-standard, a decoder built on wrong assumptions will produce plausible-looking garbage, which is worse than no decode at all. Instead I'd work from the protocol specification — or, if there isn't one, from a captured waveform I've manually verified against the sensor's datasheet timing — and build the decoder from the physical layer up.

Concretely: I'd first capture a known-good transaction with the logic analyzer at a sample rate comfortably above the bit rate (at least 4–10× the fastest edge, more if the clock is embedded), and manually annotate the capture to confirm I understand where the frame starts, how the header is delimited, where the bit boundaries fall, and how the payload is encoded. Only once I can hand-decode a frame correctly do I write the decoder. For a non-byte-aligned header, the decoder needs to work in terms of bit offsets rather than byte offsets — most logic analyzer scripting environments (Saleae's HLA, Sigrok's Python decoders, etc.) let you define arbitrary bit-level state machines, so I'd model the protocol as an explicit state machine: idle → header sync → header field(s) → payload → checksum/CRC → end-of-frame, with each state transition tied to a specific edge or bit count.

The checksum is the decoder's self-check. If the protocol has a CRC, I'd implement it in the decoder and flag frames that fail it — a decoder that reports clean frames with valid CRCs is strong evidence the framing is right; one that reports constant CRC failures means my bit alignment is off. I'd also build in tolerance for the things that actually happen on a real bus: clock stretching, inter-frame gaps, and the occasional glitch, so the decoder reports an error rather than silently mis-framing. Finally, I'd validate the decoder against a known stimulus — either a captured transaction whose contents I already know from firmware debug output, or a signal generator replaying a synthetic frame — before trusting it on a live debug session.

**Possible follow-ups:** How would you handle a protocol where the bit rate isn't constant, or where the clock is recovered from the data rather than a separate line? What would you do if the decoder works on captured data but produces errors when running live at full speed?

## Q3: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The underlying issue is that an IDE project file is a build recipe, and for a regulated device the build recipe is part of the product definition — if the optimization level or linker script can drift between the build that was tested and the build that ships, the verification doesn't apply to what's in the field. So I'd treat the project configuration as a controlled artifact, not a developer preference.

Practically, I'd start by making every build-affecting setting explicit rather than inherited: optimization level per target, the exact linker script path, the startup file, the preprocessor defines, the include paths, and the floating-point ABI settings. I'd remove or avoid reliance on IDE defaults wherever the toolchain allows it, and where the toolchain supports it, I'd drive the build from a script or makefile that invokes the compiler with an explicit, version-controlled set of flags, with the IDE project as a thin wrapper for debugging convenience. That way the authoritative build is reproducible outside any one engineer's machine.

For auditability, the key is that the build must be reproducible and the inputs must be recorded. I'd pin the toolchain version (compiler, linker, and the device pack / CMSIS version) and record it alongside the source revision, because a compiler upgrade can change code generation even at the same optimization level. The linker script and startup code go under version control with everything else, and I'd add a build-time check that the linker script in use matches the expected hash — a simple guard against someone pointing the project at a stale or modified script. I'd also generate a map file and keep it with each release build, so the memory layout can be reconstructed later, and I'd verify the output image's checksum or signature as part of the release process.

The cultural piece matters too: I'd document in the project's build instructions which settings are locked and why, so a new engineer doesn't "helpfully" change the optimization level to debug something and forget to change it back. If a debug build with different settings is genuinely needed, it should be a separate, clearly labeled configuration that can never be mistaken for the release build.

**Possible follow-ups:** How would you detect that a release build was accidentally produced with a different optimization level than the verified build? What's your approach when a compiler upgrade is required mid-program — how do you re-qualify the build?

## Q4: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The measurement is a reflection measurement: the tracking generator sweeps a known stimulus, the directional coupler separates the reflected wave from the incident wave, and the analyzer displays the return loss (or, with the right calibration, the impedance) versus frequency. The value of the technique is that it shows you how the front-end's input impedance behaves across frequency — not just at one point — which is exactly what you need to know when the source driving it has finite output impedance, or when you're worried about resonance with cable or filter reactance.

The setup details are where the measurement is won or lost. I'd start by characterizing the measurement system itself: connect the coupler and cables with the front-end replaced by a known load (a precision 50 Ω termination, then an open and a short) and confirm the analyzer reads what it should across the band of interest. That establishes the directivity and loss of the coupler and cables, and it's the reference the actual measurement is compared against. Then I'd perform a full one-port calibration — open/short/load — at the reference plane where the front-end connects, so the calibration removes the fixture and cable effects rather than measuring them. The reference plane matters: if I calibrate at the analyzer's port and then measure through a cable and a probe, I'm measuring the cable and probe as much as the front-end.

Deciding whether to trust the result comes down to a few checks. First, is the return loss within the analyzer's and coupler's dynamic range? A very high impedance front-end reflects almost everything, and a very low impedance reflects almost nothing — both push toward the limits where the measurement is dominated by directivity error, so I'd want to know the coupler's directivity spec and treat results near that floor with suspicion. Second, is the result stable and repeatable — does it change when I move the cable, touch the board, or repeat the sweep? Instability usually means the fixture is radiating or the connection is poor. Third, does the measured impedance make physical sense given the front-end's topology? If I know there's a differential amplifier with a defined input network, the measured impedance should be consistent with that at low frequency, and any surprise resonance should be explainable by a component or a parasitic I can identify. If I can't explain a feature, I don't act on it until I can.

**Possible follow-ups:** How would you extend this to a differential front-end, where a single-ended reflection measurement doesn't directly apply? What would you do if the front-end is powered and active — how does that change the measurement and its interpretation?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** The first thing I'd do is separate the technical question from the interpersonal one, because they need different handling and mixing them makes both worse. Technically, the engineer isn't wrong that the peaks show up either way — a fast scan with a wide resolution bandwidth and a peak detector will absolutely reveal that energy is present at a frequency. What it won't do is give a number that's comparable to the limit line, because resolution bandwidth affects the measured amplitude of broadband versus narrowband emissions differently, and detector mode (peak versus quasi-peak versus average) changes the result in ways the standard specifically defines. So the scan isn't useless — it's a good pre-scan — but it can't be the basis for a compliance judgment, and if we present it as one we could either miss a marginal failure or chase a phantom one.

I'd explain that distinction to the engineer directly and without making it a criticism of their work — the fast scan was the right first step, it's the interpretation that needs to change. Then I'd look at what's actually possible before tomorrow. If the instrument can be reconfigured and the scan re-run in the booked time, that's the clean answer: set the resolution bandwidth and detector per the standard, re-scan, and compare against the limit line. If the full formal scan can't be completed in the available time, I'd prioritize — run the corrected scan over the bands most likely to be problematic given what the fast scan showed, and be explicit in the report about what was and wasn't covered. I would not let a non-compliant scan be recorded as if it were a compliant one, because that's a documentation integrity problem, not just a measurement problem.

On the people side, I'd frame it as a shared lesson rather than a failure: this is exactly the kind of thing that's easy to get wrong and worth building a checklist around. After the immediate issue is resolved, I'd want the lab setup to have a documented configuration per test standard — a saved instrument state or a written procedure — so the next person doesn't have to rediscover the right settings under time pressure. And I'd make sure the engineer knows the correction was about the measurement, not about them, because the goal is someone who flags uncertainty next time rather than someone who defends a setup to avoid looking wrong.

**Possible follow-ups:** How would you decide which bands to prioritize if you can't complete the full corrected scan in the available time? What would you put in the lab's standard operating procedure to prevent this from recurring?
