## Q1: How would you approach setting up a schematic library in Altium Designer so that symbols stay consistent and traceable across a multi-year medical device program, where the same part may be reused across several board revisions?

**Answer:** The core problem is that a schematic symbol is a controlled document in a regulated program, so the library has to be treated as a revisioned artifact rather than a folder of files that anyone edits in place. I would start by deciding on a single source of truth — either a managed content server (Altium 365 or a Concord Pro-style vault) or, if that isn't available, a dedicated library repository under version control with a documented folder structure and a change-approval step. Every symbol gets a unique internal part number, and the symbol's parameters carry the manufacturer part number, the datasheet revision it was drawn from, and a link to the approved-manufacturer record. That way, when a part is reused on a later board revision, the design points at a specific library revision rather than "whatever the symbol looks like today."

For consistency, I'd enforce a symbol style guide — pin naming conventions, power pin orientation, how multi-part devices are split, how alternate functions are annotated — and back it with library DRC rules so violations are caught mechanically rather than by review. Traceability comes from never editing a released symbol in place: changes create a new revision, and the schematic records which revision it used. When a part is obsoleted or a datasheet changes, the old revision stays in the library so historical boards remain reproducible, and a new revision is issued for new designs. I'd also keep a change log per part so an auditor can see why a symbol changed and who approved it.

**Possible follow-ups:** How would you handle a situation where a symbol error is discovered after several boards have already been released using it? What's the difference in traceability between a vault-managed library and a Git-managed file library, and where does each break down?

## Q2: How would you approach setting up a constraint manager in Cadence Allegro for a mixed-signal PCB that has both high-speed digital interfaces and sensitive analog sensor inputs, and how would you verify the constraints are actually being honored?

**Answer:** I'd structure the constraint manager in layers, because a mixed-signal board has two very different sets of rules that can conflict. First, the physical/electrical constraint sets: impedance targets and tolerance for each high-speed net class (USB differential pairs, SPI clock and data, any parallel bus), propagation-delay and length-matching rules within each bus, and differential-pair gap/width rules derived from the stackup. Second, the analog side: net classes for sensitive sensor traces with rules that keep them short, keep them away from switching nodes, and control their reference plane. Third, the spacing rules that enforce the separation between the two worlds — keepouts around switching regulators, minimum spacing from digital aggressors to analog traces, and plane-stitching guidance.

The key discipline is to drive constraints from net classes and bus definitions rather than hand-assigning rules to individual nets, so the rules scale and stay consistent as the design changes. I'd also set up the stackup first, because impedance and delay rules are meaningless until the stackup is fixed.

Verification is where a lot of teams get lazy. I'd run the Allegro constraint-driven DRC as a gate, but I wouldn't trust a clean DRC alone — I'd also run a report of actual versus target for impedance-critical and length-matched nets, and visually inspect the analog/digital separation in the areas the DRC can't reason about (return-path continuity, plane splits under analog traces). For the highest-risk interfaces, I'd follow up with an SI/PI check on the extracted layout rather than relying purely on rule compliance.

**Possible follow-ups:** How would you resolve a case where the length-matching rule for a digital bus forces routing that violates your analog separation rule? What would you check first if the DRC passes but the board still shows noise on the analog channels?

## Q3: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is that a build is reproducible and that the settings which affect behavior are explicit, reviewed, and version-controlled — not buried in a project file that someone toggled in the GUI. I'd start by treating the project file itself as a controlled artifact in version control, and by making the critical settings visible and documented rather than left at defaults. That means explicitly setting the optimization level per target (and documenting why — for example, a debug target at low optimization for debuggability, a release target at the validated level), explicitly selecting the linker script rather than letting the toolchain pick a default, and explicitly listing the startup file and the vector table source.

For auditability, I'd keep the linker script and startup code in the repository as first-class source files with their own revision history, and I'd add a build-time check that fails the build if the expected optimization level or linker script isn't the one in use — a small script that parses the build output or the project settings and compares against the approved configuration. I'd also capture the toolchain version, because the same source built with a different compiler version can behave differently, and that has to be pinned for a regulated build. Finally, I'd produce a build manifest — compiler version, optimization level, linker script hash, source commit — as part of the release artifact, so the binary can be traced back to exactly the configuration that produced it.

**Possible follow-ups:** How would you handle the case where a bug only reproduces at one optimization level — what does that tell you, and how do you decide which level ships? What's your approach to keeping the debug and release configurations from drifting apart over time?

## Q4: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The measurement is essentially a reflection measurement: the tracking generator sweeps, the directional coupler separates the forward and reflected waves, and the analyzer displays return loss (or VSWR) versus frequency. The first thing I'd do is calibrate the setup at the reference plane — a full one-port calibration (open/short/load) at the end of the cable that will connect to the front-end, so the cable and coupler losses are removed from the measurement. Without that, the numbers are dominated by the fixture, not the device.

Then I'd think about what "input impedance" means for this front-end. If it's a high-impedance sensor input, the return loss will be poor by design and the measurement is really about confirming there's no unexpected resonance or instability; if it's a matched 50-ohm input, return loss is a direct quality metric. I'd sweep the band of interest plus margin, and I'd look for the shape of the curve, not just a single number — a smooth curve is believable, a jagged one usually means fixture or grounding problems.

Deciding whether to trust it comes down to a few checks: does the calibration verification (measuring a known standard) come back clean; is the result stable when I wiggle the cable or re-seat the connector; does it change when I add or remove a ferrite on the cable (which would indicate the measurement is picking up common-mode currents on the shield rather than the device); and does it agree with a sanity check — for example, a rough calculation or a measurement with a different fixture. If those don't line up, I treat the measurement as a fixture artifact and fix the setup before drawing any conclusion.

**Possible follow-ups:** What would cause a return-loss measurement to look better than the device actually is, and how would you catch it? How would you extend this to a two-port measurement if you needed to characterize gain and matching together?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** The first thing I'd do is separate the technical issue from the interpersonal one, because the engineer isn't being careless — they're reasoning from a reasonable but incomplete premise. "The peaks show up either way" is true for locating a source, but it's not true for a compliance measurement: resolution bandwidth and detector mode change the measured amplitude, so a scan with the wrong settings can pass something that would fail, or fail something that would pass. I'd explain that distinction concretely rather than just asserting authority — show them how the same emission reads differently under different RBW and detector settings, so the lesson sticks.

Then I'd deal with the schedule. The right move is not to cancel the lab time but to use it correctly: re-configure the analyzer to the standard's settings tonight, run a quick verification against a known reference if one is available, and use tomorrow's booked slot for the compliant scan. If there's any doubt the settings are right, I'd rather spend the first part of the session confirming the setup than produce a number we can't defend. I'd also make sure the engineer is the one who reconfigures and re-runs it, with me reviewing — that turns the mistake into ownership rather than a reprimand.

Longer term, the fix is procedural: a written pre-scan checklist for the standard being targeted, with the RBW, detector, and sweep settings called out, so the setup is verified before the lab time is spent. That protects the next engineer from the same trap.

**Possible follow-ups:** How would you handle it if the re-configured scan then showed a failure that the earlier quick scan had hidden? What would you change about how the lab setup is handed off between engineers so this doesn't recur?
