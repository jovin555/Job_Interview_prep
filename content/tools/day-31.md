## Q1: How would you approach setting up a board-to-board interconnect strategy for a system where a main processor board and a sensor board need to carry both high-speed digital signals and sensitive analog signals through the same connector?

**Answer:** The first step is to define the signal inventory and classify each net by its electrical characteristics — high-speed digital (clock, data, SPI), sensitive analog (sensor outputs, reference voltages), and power/ground. This classification drives the connector pin assignment, which is the most critical decision. I would allocate dedicated ground pins between signal groups to provide return path continuity and isolation, and avoid placing high-speed digital adjacent to high-impedance analog inputs. For the connector itself, I would evaluate options based on bandwidth requirements — a standard 2.54mm header might work for slower signals, but for high-speed interfaces I would consider a connector with controlled impedance characteristics and shorter pin-to-pin spacing. I would also think about whether the analog signals need to be buffered or conditioned on the sensor board before crossing the connector, rather than sending raw high-impedance signals across a potentially noisy interconnect. On the PCB side, I would ensure the ground pins are tied directly to the solid ground plane without neck-downs, and that the return current path for each signal group is not forced to detour around cutouts or splits. Finally, I would document the pin assignment rationale in the interface control document so that both board designers understand the constraints — this prevents someone from reassigning pins later without understanding the signal integrity implications.

**Possible follow-ups:** How would you decide whether to use a mezzanine connector versus a cable assembly for this interconnect? What additional considerations apply if the two boards are in a sealed enclosure with limited airflow?

## Q2: How would you approach using a mixed-signal oscilloscope to characterize the noise coupling between a switching regulator and a precision analog sensor on the same PCB?

**Answer:** I would start by identifying the specific noise coupling path I'm trying to characterize — is it conducted through the shared power rail, radiated from the inductor or switching node, or coupled through the ground plane? The measurement setup depends on the hypothesis. For power rail coupling, I would use a low-inductance probing technique — a short ground spring on a passive probe, or better, a differential probe across the analog supply pins — and trigger on the switching node of the regulator to correlate noise events. I would measure the ripple at the regulator output, then at the analog sensor's supply pin, and compare the amplitude and frequency content to see what's being attenuated or amplified by the PCB trace impedance and decoupling. For radiated coupling, I would use a near-field probe connected to the oscilloscope's spectrum analysis capability, or use FFT on the time-domain signal to identify the switching frequency and its harmonics. A key technique is to measure the analog sensor's output noise floor with the regulator running versus with the regulator disabled (powering the analog section from a bench supply instead) — this gives a baseline for how much noise the regulator actually contributes. I would also look at the time-domain waveform of the sensor output synchronized with the switching events to see if there's a periodic disturbance at the switching frequency. The goal is to build a complete picture of the coupling mechanism before deciding on a fix — whether that's improved filtering, layout changes, or a different regulator topology.

**Possible follow-ups:** How would you distinguish between noise coupled through the ground plane versus noise coupled through the power trace? What probing technique would you use to avoid introducing measurement artifacts?

## Q3: How would you approach creating a reusable schematic block for a sensor interface that needs to be instantiated multiple times in a hierarchical design, while maintaining clear documentation and avoiding copy-paste errors?

**Answer:** I would design the sensor interface as a hierarchical sheet or a multi-channel block, depending on the EDA tool. The key is to define a clean interface — the ports that connect the block to the rest of the system should be explicit and well-named, such as `SENSOR_I2C_SCL`, `SENSOR_I2C_SDA`, `SENSOR_INT`, `SENSOR_PWR_EN`. Inside the block, I would include the sensor itself, its decoupling, any level shifting or signal conditioning, and the connector or footprint. I would use parameters or variants to handle differences between instances — for example, different I2C addresses strapped by pull-up resistors, or different filter component values for sensors with different bandwidth requirements. The critical practice is to review the first instance thoroughly — schematic, footprint, and layout — before replicating it, because any error gets multiplied across all instances. I would also use the tool's multi-channel feature where available, which automatically handles net naming and component reference designators (like U1A, U1B, U1C) rather than manually copying and renumbering. For documentation, I would add a text frame on the sheet explaining the design intent, the expected signal levels, and any assumptions about the sensor's configuration. Finally, I would verify that the ERC (electrical rules check) catches issues like unconnected pins or mismatched net names across all instances, not just the first one.

**Possible follow-ups:** How would you handle a situation where one instance of the block needs a different sensor variant with a different register map? How would you ensure that the layout team understands which components belong to which channel?

## Q4: How would you approach setting up a systematic firmware regression test strategy for a medical device that uses Zephyr RTOS, where you need to verify that changes to one subsystem don't break functionality in another?

**Answer:** I would structure the regression strategy around three layers: unit tests, integration tests, and hardware-in-the-loop (HIL) tests. For unit tests, I would use Zephyr's built-in test framework (ztest) to test individual modules — sensor drivers, protocol handlers, state machines — with mocked hardware dependencies. These tests run on the host or in a simulated environment and catch logic errors quickly. For integration tests, I would run the firmware on the actual target hardware with a test harness that exercises multiple subsystems together — for example, verifying that a sensor read triggers the correct data processing and that the display updates correctly. The key is to automate these tests so they can run on every commit or at least nightly. I would use a test runner that programs the device via a debugger, runs the test sequence, and captures pass/fail results. For the HIL layer, I would use simulated sensor inputs to verify that the firmware responds correctly to edge cases — sensor failures, out-of-range values, communication timeouts — without needing physical stimuli. The critical practice is to maintain a clear mapping between test cases and requirements, so that when a test fails, you can trace it back to the requirement it verifies. I would also establish a baseline test suite that runs before any code merge, and require that new features come with corresponding regression tests. For the medical device context, I would pay special attention to tests that verify safety-critical behavior — for example, that a sensor failure leads to the correct alarm state and not a silent malfunction.

**Possible follow-ups:** How would you handle a regression test that is flaky — passing sometimes and failing other times without code changes? How would you prioritize which tests to run for a quick pre-merge check versus a full nightly regression?

## Q5: (Behavioral) Imagine you are leading a project where a junior engineer has been tasked with setting up the automated firmware test environment. On the day before a critical regression test run, you discover that the engineer has configured the test script to skip the safety-critical test cases because they were failing intermittently, and the engineer is confident this is acceptable because "the failures are just timing issues in the test harness, not real bugs." The test results will be used for a regulatory submission milestone. How would you handle this situation?

**Answer:** The first priority is to understand the situation fully before taking action. I would sit down with the engineer and ask them to walk me through the failing tests — what the failures look like, how they diagnosed them as test harness issues, and what evidence they have for that conclusion. I would also look at the test logs myself to see the failure patterns. The concern here is twofold: first, skipping safety-critical tests for a regulatory submission is never acceptable, regardless of the reason; second, intermittent failures in safety-critical tests are exactly the kind of issue that needs to be investigated, not worked around. If the engineer's analysis is correct and the failures are indeed test harness timing issues, the right fix is to correct the harness — for example, adding proper synchronization or increasing timeouts — and then re-run the tests to confirm they pass consistently. If the failures turn out to be real firmware bugs, skipping the tests would have hidden them. Either way, the test script must be corrected to include all safety-critical cases before the regression run proceeds. I would also explain the regulatory context — that the test results will be reviewed as evidence of the device's safety, and that any gaps in coverage or unexplained failures would raise questions about the entire verification process. The immediate action is to fix the test configuration and re-run the full suite, even if it means delaying the milestone. I would also use this as a coaching opportunity — the engineer's instinct to get the tests passing is understandable, but the approach of hiding failures rather than investigating them is a significant process issue that needs to be addressed. I would work with them to establish a clear policy: no test can be skipped without documented justification and review by at least one other engineer.

**Possible follow-ups:** How would you verify that the intermittent failures are actually resolved and not just masked by the test harness changes? How would you communicate this issue to the project manager who is expecting the test results for the regulatory milestone?
