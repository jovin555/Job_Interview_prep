# tools — Day 100

## Q1: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?
**Answer:** I'd start by treating the decoder as a specification problem before it's a tooling problem. First, I'd write down the frame structure explicitly — header bit pattern and length, payload field boundaries, any bit-stuffing or escape rules, checksum/CRC coverage, and the idle/clocking assumptions — because a decoder built from a vague mental model will produce confident-looking garbage. Then I'd capture a known-good transaction first: a single, simple, well-understood message (e.g., a fixed command with a known response) so I have ground truth to validate the decoder against before pointing it at anything ambiguous.

For implementation, most logic analyzers let you extend the decoder framework in a scripting language (Python for Saleae-style tools, or a custom decoder in the vendor's SDK). I'd build it in layers: a low-level bit/edge layer that finds frame boundaries using the header pattern, a field-extraction layer that maps bit offsets to named fields, and a presentation layer that renders the decoded frame readably. The key discipline is to make the decoder *fail loudly* — if the header doesn't match or the checksum fails, it should flag the frame as invalid rather than silently misaligning and decoding noise as data. I'd validate against several captures including deliberately corrupted frames, and I'd keep the decoder under version control alongside the protocol spec so it stays in sync as the protocol evolves.

**Possible follow-ups:** How would you handle a protocol where the frame length is itself encoded in the header, so the decoder has to be stateful across frames? What would you do if the bus is shared with another device whose traffic you also need to filter out?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?
**Answer:** The core principle is that the build configuration is a controlled artifact, not a set of GUI checkboxes someone toggles. I'd start by defining the build configuration explicitly — optimization level, C standard, warning levels, preprocessor defines, include paths, linker script path, and startup file — and then make those settings visible and reviewable rather than buried in a `.uvprojx` file that only opens in the IDE. Where the toolchain allows, I'd drive the build from a script or makefile that invokes the compiler and linker with explicit flags, so the exact command line is captured in version control and reproducible on a clean machine. If the team insists on the IDE, I'd at least document the required settings in a build-configuration spec and add a post-build check that verifies the produced image's properties (e.g., optimization-dependent code size or a build-ID string) match expectations.

For auditability, I'd make the build emit a manifest — toolchain version, flags, git commit hash, linker script hash — that gets archived with each release candidate. The linker script and startup code deserve special attention because they define memory layout and initialization order; I'd treat them as reviewed source files with their own change history, not as IDE-generated boilerplate. And I'd add a CI step that builds from a clean checkout and compares the output against the reference build, so a silent configuration drift gets caught before it reaches a regulated release.

**Possible follow-ups:** How would you detect that someone changed the optimization level locally and shipped a build that behaves differently from the tested one? What's your approach to keeping the linker script in sync when the memory map changes between hardware revisions?

## Q3: How would you approach setting up a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?
**Answer:** The measurement is a reflection measurement: the tracking generator sweeps a known stimulus, the directional coupler separates the incident and reflected waves, and the analyzer displays return loss (or VSWR) versus frequency. Before trusting anything, I'd do a full one-port calibration at the reference plane — open, short, and load standards — because without calibration the coupler's directivity, the cable loss, and the connector mismatch dominate the result, especially when the front-end's impedance is close to 50 Ω and the return loss is high. I'd also verify the coupler's directivity and the tracking generator's flatness across the band of interest, since a poor coupler makes a good load look bad.

Deciding whether to act on the result comes down to uncertainty budgeting. I'd ask: what's the calibration residual error, what's the coupler directivity, what's the cable/connector repeatability, and how does the measured return loss compare to those error bars? If the front-end is a high-impedance sensor input, the return loss may be so high that the measurement is dominated by the fixture — in which case I'd switch to a different method (e.g., a impedance analyzer or a bridge) rather than over-interpret a noisy trace. I'd also sanity-check against the schematic: does the measured resonance or impedance dip line up with the expected input filter and bias network? A measurement that agrees with an independent prediction is far more trustworthy than one that merely looks clean.

**Possible follow-ups:** How would you extend this to a two-port measurement of the front-end's transfer function, and what extra calibration would that require? What would you do if the front-end is powered and active during the measurement — how does that change your setup?

## Q4: How would you approach setting up a Segger J-Link's RTT (Real-Time Transfer) logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?
**Answer:** RTT is attractive here precisely because it uses the debug probe's memory-access channel rather than a peripheral, so it doesn't consume the UART. The setup is: enable the RTT control block in the firmware (Zephyr has a logging backend for it), allocate a reasonable up-buffer, and configure the host-side J-Link RTT Viewer or a scripted client to poll it. The critical design question is the buffering mode — blocking mode will stall the application when the buffer fills, which is exactly the timing perturbation I want to avoid, so I'd use non-blocking/skip mode and size the buffer generously, accepting that under heavy logging some messages may be dropped rather than letting logging change the system's behavior.

To keep logging from perturbing timing, I'd be deliberate about *where* log calls happen: avoid logging inside ISRs or time-critical loops, or gate those logs behind a compile-time flag that's off in the timing-sensitive build. I'd also measure the impact — compare a timing-critical loop's execution with logging enabled versus disabled, using a GPIO toggle and oscilloscope or the DWT cycle counter — to confirm the overhead is acceptable. And I'd make sure the RTT buffer lives in a memory region that doesn't collide with the safety-critical protocol's buffers, and that the debug probe's background memory access doesn't contend with the CPU in a way that shows up as jitter.

**Possible follow-ups:** How would you handle the case where the RTT buffer overflows during a burst of events you actually need to see? What's your approach to correlating RTT log timestamps with external events captured on a logic analyzer?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?
**Answer:** First, I'd separate the technical issue from the interpersonal one. Technically, the engineer isn't wrong that peaks show up either way — but the standard specifies RBW and detector (e.g., quasi-peak versus peak) because those settings determine whether a given emission actually *passes or fails* the limit, not just whether it's visible. A peak detector with a wide RBW can overstate or understate the quasi-peak level depending on the signal's characteristics, so "the peaks show up" is not the same as "the measurement is valid." I'd explain that distinction concretely — show the standard's requirement and, if time allows, demonstrate the difference by re-scanning a known emission with both settings so the engineer sees the number move.

On the process side, I wouldn't humiliate the engineer in front of the team; I'd frame it as a checklist gap rather than a personal failing, and then fix the root cause: create a pre-scan configuration checklist that's verified before lab time is used, so this doesn't recur. For tomorrow's scan, I'd correct the settings now, do a quick verification scan to confirm the setup is sane, and if there's any doubt about whether the booked lab time is sufficient, I'd raise it with the lab immediately rather than discover it mid-scan. The goal is to protect the schedule *and* the validity of the data — a scan with wrong settings that gets repeated is more expensive than a scan that starts correctly.

**Possible follow-ups:** How would you decide whether the earlier "get a feel for it" scan data is worth keeping at all? What would you change in the team's lab workflow so that configuration verification isn't dependent on one person's memory?
