## Q1: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** I'd start by treating the decoder as a hypothesis to be validated, not a black box to trust. First, I'd capture a long, clean trace of the bus with the highest sample rate the analyzer supports relative to the bit rate — for a non-byte-aligned frame, you need enough oversampling to resolve the exact bit boundaries, so I'd want at least 10x the bit clock, ideally more. Then I'd manually decode one or two frames by eye from the raw waveform: identify the sync pattern or header, measure the bit period, and confirm where the payload actually begins. Only once I understand the framing by hand would I write a custom decoder — most analyzers (Saleae, Sigrok, etc.) let you script a decoder in Python or a similar language, where you define states: idle, header-detect, bit-count, payload, checksum. The key discipline is to make the decoder emit not just decoded bytes but also a confidence or error flag when the framing doesn't match expectations, so a misaligned frame shows up as an error rather than silently producing plausible garbage. I'd validate the decoder against a known-good capture — ideally one where I can cross-check the decoded values against what the firmware or a reference device reports — before using it to debug anything. For a medical device, I'd also document the decoder and its validation in the test records, because if it's used to support a verification activity, the tool itself needs to be trustworthy.

**Possible follow-ups:** How would you handle a protocol where the bit rate drifts slightly between frames, so a fixed bit-period assumption in the decoder starts to fail? What would you do if the decoder worked on the bench but produced errors when the device was under load?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is to make the build reproducible and to make any deviation from the approved configuration visible. I'd start by moving as much as possible out of the IDE's GUI settings and into version-controlled files: the linker script as a checked-in `.sct` file referenced explicitly, the startup code as a checked-in source file rather than an IDE-generated one, and the optimization level set per-target in the project file, which itself is checked in. Then I'd add a build-time assertion — a small script or a pre-build step — that reads back the effective compiler and linker flags and fails the build if the optimization level, the linker script path, or key defines don't match the approved configuration. That way, if someone opens the project and changes a setting in the GUI, the next build either fails loudly or produces a log entry showing the deviation. I'd also capture the full command line for each translation unit in the build log and archive it with the release artifacts, so the exact flags used for a given firmware image are recoverable months later. For a medical device, this ties directly into the DHF: the approved build configuration is a controlled item, and the build log is evidence that the released binary was produced with it. The optimization level matters especially because `-O0` versus `-O2` can change timing and expose or mask latent bugs, so it should never be an implicit IDE default.

**Possible follow-ups:** How would you handle a third-party library that ships with its own project file and its own optimization settings? What would you check first if a firmware image built with the "locked" configuration behaved differently from one built during development?

## Q3: How would you approach setting up a cross-probe workflow between OrCAD Capture and Cadence Allegro so a layout review can move efficiently between schematic and PCB, and what would you check to confirm the link actually works before relying on it in a review?

**Answer:** Cross-probing depends on the two tools agreeing on the design's connectivity and reference designators, so I'd verify that foundation before touching the cross-probe feature itself. First, confirm the Allegro board was netlisted from the current Capture schematic — not an older revision — and that the reference designators and net names match exactly. Then I'd enable cross-probing in both tools (in Allegro this is typically the cross-probe filter settings, and in Capture the corresponding session setting), and test it in both directions on a handful of known components: select a part in Capture and confirm the correct footprint highlights in Allegro, then select a footprint in Allegro and confirm the correct symbol highlights in Capture. I'd deliberately test edge cases — a multi-part component, a net that spans several pages, a component with a non-standard reference designator — because those are where cross-probe tends to fail silently. I'd also confirm the two tools are pointed at the same design database and that no stale session is cached. Only after that would I use it in a live review. The reason to be strict: a cross-probe that highlights the wrong component is worse than no cross-probe at all, because it can send a review down the wrong path and waste the room's time.

**Possible follow-ups:** What would you do if cross-probing worked for components but not for nets? How would you structure a layout review so that the cross-probe is used to drive the agenda rather than just as an ad-hoc lookup?

## Q4: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The measurement is essentially a reflection measurement: the tracking generator sweeps a known signal, the directional coupler separates the incident and reflected waves, and the analyzer displays the return loss or reflection coefficient, from which you can derive impedance. The first thing I'd do is calibrate the setup — a full one-port calibration (open, short, load) at the reference plane where the front-end connects, using the same cables and coupler that will be in the measurement, because the coupler's directivity and the cable losses are exactly the error terms that will otherwise masquerade as impedance. Then I'd verify the calibration by measuring a known load — a 50-ohm termination should read close to 50 ohms across the band, and an open should read as a clean high impedance. If those don't come out right, nothing downstream is trustworthy. For the front-end itself, I'd sweep over the band of interest and look at the return loss curve, but I'd also sanity-check it against the expected circuit behavior — if the front-end has a known input filter or matching network, the measured resonance should land where the design predicts. I'd treat any result that disagrees with the expected topology as suspect until I can explain the discrepancy. Finally, I'd check for measurement artifacts: is the front-end powered or unpowered, is it in-circuit or isolated, and does the result change when I move my hand near the probe or change the cable dress? If the measurement is stable and matches the expected circuit behavior, I'd act on it; if not, I'd fix the setup before drawing conclusions.

**Possible follow-ups:** How would you handle a front-end that is differential rather than single-ended — what changes in the setup? What would you do if the return loss looked fine but the device still behaved poorly in-system?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** I'd treat this as a teaching moment first and a schedule problem second, because the engineer's reasoning — "the peaks show up either way" — is the exact misconception that causes pre-compliance scans to miss marginal failures. I'd sit down with them and explain why the settings matter: resolution bandwidth affects the noise floor and the measured amplitude of broadband versus narrowband emissions, and detector mode (quasi-peak versus peak versus average) changes what the standard actually requires you to demonstrate. A peak that "shows up" under a wide RBW and peak detector can look compliant when it would fail under the standard's quasi-peak measurement. Then I'd have them re-run the scan with the correct settings and compare — seeing the difference on the same DUT is far more persuasive than an argument. On the schedule: I'd check whether the correct settings can be applied and the scan re-run within the booked lab time, which is often possible if the setup is otherwise sound. If not, I'd escalate honestly — tell the project lead that the formal scan needs to be re-booked or that the current slot can only produce an indicative, non-compliant scan — rather than let a scan with the wrong settings stand in for a formal result. The one thing I would not do is sign off on the scan as-is, because in a regulated context that's a documentation and compliance risk, not just a technical one.

**Possible follow-ups:** How would you make sure this doesn't recur on the next project — what would you put in place so the correct settings are the default rather than something someone has to remember? How would you handle it if the engineer felt you were undermining them in front of the team?
