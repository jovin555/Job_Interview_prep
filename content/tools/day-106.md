## Q1: How would you approach setting up a scripted, repeatable flashing and test sequence for a Zephyr RTOS target using a Segger J-Link, where the harness needs to program the device, run a test, and capture a crash dump without manual intervention — and what failure modes would you design around?

**Answer:** I'd build this in layers so each stage is independently verifiable. The foundation is a J-Link script or command file that does connect → halt → erase → program → verify → reset → run, driven by the J-Link Commander or the J-Link SDK, with the device selection and interface speed pinned explicitly rather than auto-detected. On top of that, the test harness invokes the flash step, waits for a deterministic "target running" signal (a GPIO toggle or an RTT banner string, not a fixed sleep), then triggers the test sequence — either through a debugger-issued command or through the firmware's own test entry point. Crash capture is the part people get wrong: I'd configure the target so a hard fault lands in a known handler that writes a fault record (stack frame, fault status registers, PC/LR) to a reserved RAM region or a no-init section, then have the harness halt the core and read that region back over the debug probe before the next reset wipes it. If the part supports it, I'd also enable instruction trace or at least a small RAM ring buffer for the last N events.

The failure modes I'd design around: probe not enumerated or already claimed by another session (retry with backoff, and fail loudly rather than silently proceeding); target held in reset or in a low-power state that blocks SWD attach (use connect-under-reset); flash programming succeeding but verify failing on a marginal part; the test hanging so the harness waits forever (hard timeout, then halt-and-dump rather than kill); and the crash record being clobbered by a watchdog reset before it's read (read first, reset second). I'd also make the whole sequence idempotent so a re-run after a partial failure starts from a clean state, and log the probe firmware version and script revision with every run so results are attributable.

**Possible follow-ups:** How would you distinguish a genuine firmware crash from a debug-probe attach failure that merely looks like one? What would you change if the same harness had to run against several hardware variants with different flash sizes?

## Q2: How would you approach setting up a spectrum analyzer for a conducted emissions pre-compliance scan on a medical device's AC input, and what would you check before trusting the first measurement?

**Answer:** Before touching the analyzer, I'd verify the physical setup, because conducted emissions measurements are dominated by the transducer and grounding, not the instrument. That means confirming the LISN is rated for the current the device draws, that it's bonded to a reference ground plane the way the test standard expects, and that the device's enclosure and cable routing match how it will actually be installed — a scan of a device sitting on a bench in an arbitrary orientation tells you very little. I'd also confirm the analyzer's input isn't being overdriven: start with a high attenuation pad or the LISN's built-in transient limiter, because switching transients at plug-in can damage a front end.

For settings, I'd set the resolution bandwidth and detector to what the applicable standard calls for rather than whatever gives a fast sweep — pre-compliance scans done with a wide RBW and a peak detector will overstate or understate results depending on the emission's nature, and the numbers won't be comparable to a formal lab run. I'd check the noise floor of the setup with the device off but connected, so I know which peaks are ambient (broadcast AM, nearby switching supplies) and which are the device. I'd verify the analyzer's amplitude accuracy against a known reference — a calibrator or a signal generator at a couple of frequencies — because a 2–3 dB offset changes whether you're passing with margin or failing. Finally, I'd scan the full band of interest, not just the frequencies I expect, and repeat the scan a couple of times to confirm peaks are stable and not intermittent artifacts of the device's operating state.

**Possible follow-ups:** How would you tell whether a peak that appears only when the device is powered is genuinely from the device or from its power supply being loaded differently? What would make you decide the pre-compliance result is trustworthy enough to skip a formal lab run?

## Q3: How would you approach setting up a power integrity simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?

**Answer:** I'd structure the workflow around the questions I actually need answered, because a full-board PI simulation can produce a lot of impressive-looking output that doesn't change any decision. The first question is impedance: what does the PDN look like from the analog front-end's supply pins across the frequency range that matters — from the regulator's control loop bandwidth up through the frequencies where the decoupling network stops being effective. That's a port-based AC analysis, and it tells me whether there's a resonance where the analog section will see high supply impedance. The second question is coupling: how much switching noise from the regulator reaches the analog rail, which needs either a transient simulation with a realistic load profile or a transfer-function analysis between the two points. The third is DC drop, which is straightforward and worth doing because it's cheap and catches real mistakes.

Trustworthiness is the crux. I'd only act on results where the model has been correlated against measurement on at least one similar board — a simulated impedance curve that's never been checked against a VNA measurement of an actual PDN is a hypothesis, not a result. I'd check that the stackup, dielectric properties, and component models (especially capacitor ESR/ESL and their mounting inductance) are realistic, because PI results are extremely sensitive to parasitic inductance that a naive model omits. I'd run sensitivity checks: if changing a capacitor value by 20% flips the conclusion, the result isn't robust. And I'd treat anything above the frequency where the model's assumptions break down — typically where the board's dimensions approach a wavelength — as indicative only, not actionable.

**Possible follow-ups:** How would you correlate a simulated PDN impedance curve against a real measurement, and what would you do with the discrepancy if they didn't match? Where would you draw the line between "simulate this" and "just build it and measure"?

## Q4: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The measurement is a reflection measurement: tracking generator out through the directional coupler's forward port into the front-end, reflected signal out the coupled port back to the analyzer, and the ratio gives return loss, which converts to impedance magnitude. The setup details matter more than the math. I'd calibrate the setup — open/short/load at the reference plane, or at minimum a through-and-open normalization — so the coupler's directivity, the cable losses, and the analyzer's frequency response are removed from the result. Directivity is the limiting factor: a coupler with 20 dB directivity can't reliably resolve return loss better than about 20 dB, so if the front-end is well-matched, the measurement floor is set by the coupler, not the device. I'd keep the drive level low enough not to push the front-end's input devices into nonlinearity, and check by repeating at a lower level — if the result changes, I was overdriving it.

Trustworthiness comes down to a few checks: does the measured return loss agree with what the schematic and component tolerances predict, at least in order of magnitude? Does the result repeat across cable reconnection and a second reference-plane calibration? Does sweeping slowly versus quickly change the curve shape (if it does, I'm seeing settling artifacts)? And critically — is the front-end powered and in its normal operating state, or am I measuring a dead board's parasitic input capacitance? An unpowered measurement of an active front-end is often meaningless. If all those line up, I'll act on the result for matching-network decisions; if not, I'd rather characterize with a VNA that has better directivity than trust a marginal coupler setup.

**Possible follow-ups:** How would you extend this to measure impedance phase, not just magnitude, and why would phase matter for a matching network? What would you do if the front-end's input impedance changed significantly with signal level?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** My first move is to separate the technical question from the interpersonal one, because they need different handling and conflating them makes both worse. Technically, the engineer isn't wrong that the peaks show up — the issue is that the amplitude and the comparability to the limit line depend on RBW and detector, so a scan with the wrong settings can't tell you whether you pass. I'd demonstrate that rather than assert it: take one scan with the current settings and one with the standard's settings on the same emission, and let the difference in reported level speak for itself. That converts a disagreement about authority into a shared observation about the measurement.

On the people side, I'd be careful not to make this a public correction — the engineer set up the bench in good faith and "the peaks show up" is a reasonable intuition that happens to be wrong for this purpose. I'd frame it as a calibration of the setup, not a mistake, and I'd ask them to walk me through why they chose those settings, because there may be a legitimate reason (speed, or a tutorial that was about a different measurement) worth understanding. Then I'd make the fix collaborative: have them reconfigure to the standard's settings and re-run, so they own the corrected setup and learn the reasoning.

Practically, the lab time is booked and the formal scan is tomorrow, so I'd prioritize getting the setup correct tonight over preserving anyone's feelings about the original configuration, and I'd add a pre-scan checklist to the lab procedure so the next person doesn't have to rediscover this. If the reconfiguration eats into the booked time, that's a scheduling problem to solve, not a reason to run the formal scan with settings that won't hold up.

**Possible follow-ups:** What would you do if the engineer pushed back and argued the standard's settings were unnecessarily slow for a pre-compliance scan? How would you make sure this kind of setup error gets caught earlier next time without making the junior engineer feel policed?
