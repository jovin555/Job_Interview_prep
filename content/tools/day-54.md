## Q1: How would you approach setting up a Segger J-Link scripted flashing and test sequence for a Zephyr RTOS target, where the test harness needs to program the device, run a test, and capture a crash dump without manual intervention — and what failure modes would you design around?

**Answer:** I'd treat this as a pipeline with three distinct stages, each of which needs its own error handling, because the failure modes are different at each step.

For flashing, the J-Link Commander script (`JLinkExe` with a `.jlink` command file) or the `JLink` Python wrapper gives repeatable, scriptable access. The script should: connect to the target via SWD at a conservative clock rate, halt the core, erase the relevant flash sectors, program the image, verify the programmed contents, and reset. Verification after programming is non-negotiable in an automated context — a silent flash failure that leaves stale firmware is one of the worst failure modes because the test then runs against the wrong image and produces a misleading pass. I'd also read back the device ID / target voltage as a sanity check before programming, so a disconnected or unpowered board fails fast rather than hanging.

For running the test, the harness needs a way to know when the test has finished and whether it passed. Options include a UART log with a sentinel string, a GPIO toggle the harness can watch, or a semihosting/RTT channel. RTT is attractive because it's fast and doesn't consume a UART, but it requires the debug probe to stay connected, which conflicts with using the probe for crash capture. A common pattern is to keep the probe connected throughout and use RTT for both the test log and the crash dump.

For crash capture, the key is that the target must not be reset or halted by the harness before the dump is extracted. If the firmware has a hard-fault handler that writes a structured dump to a known RAM region or a reserved flash sector, the harness can read that region via the J-Link after the fault. Alternatively, the J-Link can halt on fault via the vector catch, and the harness reads the stacked registers (PC, LR, xPSR, and the fault status registers like CFSR/HFSR/MMFAR/BFAR) directly. The advantage of the vector-catch approach is that it works even if the firmware's fault handler itself is broken — which is exactly the situation where you most need the dump.

Failure modes I'd design around: (1) target not powered or probe not enumerated — detect and report distinctly from a test failure; (2) flash verify mismatch — abort and flag as an infrastructure failure, not a DUT failure; (3) test hangs — a watchdog timeout in the harness that resets the target and marks the run as inconclusive; (4) crash dump region overwritten by a subsequent reset — capture before any reset; (5) probe firmware/driver version drift between machines — pin the J-Link software version in the harness environment. The overarching principle is to distinguish "the DUT failed" from "the test infrastructure failed," because conflating them destroys trust in the results.

**Possible follow-ups:** How would you structure the harness so that a crash dump from one test doesn't contaminate the next test's run? What would you log per run to make a flaky failure reproducible later?

## Q2: How would you approach organizing a KiCad project for a medical device so that the schematic, PCB, footprints, and 3D models stay consistent across revisions, and how would you catch footprint-to-schematic mismatches before they reach fabrication?

**Answer:** KiCad's file-based model means consistency has to be enforced by discipline plus tooling, because there's no database backend to guarantee it. I'd start with a project structure that separates concerns: a project-local library directory containing only the symbols and footprints actually used by this design, a `3dmodels` directory, and the schematic/PCB files at the top level. The critical rule is that the project uses its own libraries, not the global KiCad libraries, so that a library update elsewhere can't silently change a released design. Each symbol and footprint gets a revision identifier in its metadata, and the project's library is frozen once the design is released.

For revision consistency, I'd use Git with a clear tagging convention (e.g., `rev-A`, `rev-B`) and treat the schematic, PCB, and project-local libraries as a single atomic unit — a commit that changes one without the others is a red flag in review. The `.kicad_pro` file and the schematic/PCB files all need to be committed together. 3D models are large binaries; I'd either commit them if they're small and stable, or use Git LFS, but I'd avoid a situation where the model referenced by a footprint lives outside version control.

For catching footprint-to-schematic mismatches before fabrication, the main tools are: (1) KiCad's built-in "Update PCB from Schematic" with the "delete footprints with no symbols" and "delete symbols with no footprints" options enabled, run as a deliberate check rather than a routine sync; (2) the ERC, configured to flag unconnected pins, missing power flags, and conflicting pin types; (3) the DRC, configured with the fabrication house's actual rules, not KiCad defaults; and (4) a footprint-to-BOM cross-check — every footprint on the board should map to a line in the BOM and vice versa. A mismatch often shows up as a footprint with no matching BOM line, or a BOM line with no footprint.

The subtle failure mode is a footprint that exists and is placed but has the wrong pad geometry or pin numbering relative to the symbol — the ERC won't catch this because the netlist is technically consistent. To catch that, I'd do a visual footprint review against the datasheet for every new footprint, and I'd add a "footprint verification" step to the design review checklist where a second person confirms pad count, pitch, and pin-1 orientation against the manufacturer drawing. For high-pin-count or fine-pitch parts, a 1:1 printout of the footprint overlaid on the datasheet land pattern is a cheap and effective check.

## Q3: How would you approach using a spectrum analyzer with a near-field probe to locate the source of a radiated emissions failure at a specific frequency during pre-compliance testing, and how would you confirm which component is responsible?

**Answer:** The near-field probe is a localization tool, not a compliance measurement — it tells you where the field is strongest, not whether the product passes or fails. I'd use it in a structured way: first, establish the failing frequency and its harmonics from the far-field or semi-anechoic measurement, then use the near-field probe to scan the board systematically.

The scan should be methodical: divide the board into a grid, hold the probe at a consistent height and orientation, and record the amplitude at the frequency of interest at each grid point. The probe orientation matters — a magnetic loop probe is sensitive to H-field and needs to be oriented to couple to the trace or loop carrying the current, while an E-field probe is sensitive to voltage nodes. For a radiated emissions failure, the H-field probe is usually more useful because it localizes current loops, which are the usual culprits. I'd scan with both orientations at each point to avoid missing a source whose field is orthogonal to the first orientation.

Once I've found the hot spot, the confirmation step is where the real work is. The near-field probe tells me "the field is strongest here," but the source could be the component at that location, a trace passing under it, a cable, or a ground-plane resonance. To confirm, I'd use a combination of: (1) temporarily disabling or slowing the suspected source (e.g., stopping a clock, changing a switching frequency) and observing whether the emission at that frequency changes; (2) probing the suspected source's pins directly with a scope to see the actual waveform and its harmonic content; (3) if the frequency matches a known clock or switching harmonic, calculating the expected harmonic series and checking whether the observed frequency aligns; and (4) if it's a cable-driven emission, moving or ferriting the cable and observing the change.

A common trap is assuming the component at the hot spot is the source when it's actually a victim or a passive radiator. For example, a heat sink or a metal enclosure can re-radiate a field generated elsewhere. The way to distinguish is to see whether the field persists when the suspected source is disabled — if it does, the hot spot is a re-radiator, not the source.

**Possible follow-ups:** How would you distinguish a common-mode cable emission from a differential-mode trace emission using the near-field probe? What would you do if the failing frequency doesn't match any obvious clock or switching harmonic?

## Q4: How would you approach setting up a cross-probe workflow between OrCAD Capture and Cadence Allegro so that a layout review can move efficiently between schematic and PCB, and what would you check to confirm the link is actually working before relying on it in a review?

**Answer:** Cross-probing between Capture and Allegro relies on both tools being open on the same design database and the cross-probe link being enabled. In Capture, the setting is under Options → Preferences → Miscellaneous, where "Enable Intertool Communication" must be checked. In Allegro, the corresponding setting is under Setup → User Preferences, where the `allegro_intertool_communication` and related preferences need to be enabled. Both tools must be pointed at the same design — the netlist in Allegro must have been generated from the Capture schematic currently open, not from an older revision.

Before relying on it in a review, I'd verify the link with a few deliberate tests. First, select a component in Capture and confirm it highlights in Allegro — and vice versa. Second, select a net in Capture and confirm the corresponding traces highlight in Allegro. Third, check a component that exists in the schematic but might be missing from the layout (or vice versa) to confirm the tools are actually synchronized and not just showing a cached state. If the highlight appears but is stale — e.g., highlighting a component that was moved or renamed — the netlist is out of sync and the review is operating on bad data.

A common failure mode is that the two tools are open on different revisions of the design, so cross-probing appears to work but highlights the wrong objects. The way to catch this is to check the design revision or timestamp in both tools before starting, and to regenerate the netlist if there's any doubt. Another failure mode is that the intertool communication is blocked by a firewall or by the tools running in different user sessions — this is more common in remote or VM setups, and it manifests as cross-probing simply not working rather than working incorrectly.

For the review itself, I'd use cross-probing to walk through the design net by net: select a net in Capture, see where it routes in Allegro, check that the routing matches the intent (e.g., a sensitive analog net is short and away from switching nodes), and flag any discrepancies. The efficiency gain is real, but only if the link is verified first — a broken or stale link is worse than no link, because it gives false confidence.

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the Altium Designer output job configuration for a medical device PCB release, and you discover the fabrication outputs are missing the drill table and the assembly drawings reference an outdated revision of the schematic. The board house is expecting the files tomorrow, and the engineer is confident the outputs are complete because "the Gerbers look fine." How would you handle this situation?

**Answer:** The immediate priority is to not send incomplete files to the board house, because a fabrication run on bad outputs is far more expensive than a one-day delay. So the first action is to pause the release and tell the board house that the files will be delayed — better to communicate early than to send something wrong and try to recall it.

With the junior engineer, I'd approach it as a teaching moment rather than a blame moment, because the root cause is almost certainly that the output job was set up by copying a template or by following a tutorial that didn't cover the full release package. The engineer's confidence that "the Gerbers look fine" is actually a reasonable belief if they've only been taught to check the Gerbers — the gap is in knowing what a complete release package contains. I'd walk through the output job together: what each output is for (Gerbers for the copper layers, drill files for the holes, drill table for the fab drawing, assembly drawings for the assembler, BOM for procurement, pick-and-place for the assembly house), and why each one matters. The drill table omission is a classic — the Gerbers show the pads but not the hole sizes in a human-readable form, and some fab houses will ask for it or make assumptions if it's missing. The outdated assembly drawing is more serious because it could lead to the wrong parts being placed.

For the fix, I'd have the engineer correct the output job with me reviewing, rather than me fixing it myself — the goal is that they can set up a complete release package independently next time. I'd add a release checklist to the project: a documented list of every output that must be present, with a verification step for each (e.g., open the Gerbers in a viewer and confirm layer count and drill hits, open the assembly drawing and confirm the revision matches the schematic). The checklist becomes part of the release process, not a one-off correction.

For the schedule, I'd assess whether the delay is one day or more. If the output job just needs the drill table added and the assembly drawing regenerated from the current schematic, it might be a few hours. I'd communicate the revised timeline to the board house and to the project stakeholders, and I'd use the delay to do a full review of the release package rather than just patching the two known issues — if two things were missed, there may be a third.

The broader lesson I'd take from this is that release packages need a defined standard and a verification step, not just an engineer's judgment that "it looks fine." In a medical device context, the release package is part of the design history file, so completeness and traceability aren't optional.

**Possible follow-ups:** How would you structure the release checklist so it's actually used rather than ignored under schedule pressure? If the board house had already started fabrication when you caught the error, what would you do?
