## Q1: How would you approach setting up a Zephyr RTOS project using the west build system so that a single codebase produces both a production image and a debug image with extra logging and assertions, without maintaining two separate trees?
**Answer:** The cleanest way is to treat the difference as configuration, not code. In Zephyr that means leaning on Kconfig and devicetree overlays rather than `#ifdef` blocks scattered through the source. I'd define a board-level defconfig that captures the production baseline — the real sensor drivers, the release optimization level, logging compiled down to error-only, and assertions off where the safety analysis permits. Then I'd add a separate debug configuration fragment (a `debug.conf` and a matching overlay) that flips on `CONFIG_LOG` at debug level, enables `CONFIG_ASSERT`, turns on thread analyzer and stack sentinel, and swaps in a mock sensor driver via a devicetree overlay that points the application at a simulated node instead of the real one. The application code binds to devicetree labels, so it doesn't know or care which driver is behind the label. West ties it together: `west build -b <board> -- -DEXTRA_CONF_FILE=debug.conf -DDTC_OVERLAY_FILE=debug.overlay` for the debug image, plain `west build` for production. The key discipline is that both images build from the same commit and the same `west.yml` manifest, so the only delta is the config fragment — which is itself reviewed and version-controlled. I'd also wire both into CI so a change that breaks the debug build is caught immediately, and I'd keep a short README documenting exactly which fragments constitute each image so nobody has to reverse-engineer it later.
**Possible follow-ups:** How would you prevent the debug configuration from silently drifting away from production over time? What would you do if a bug only reproduces in production but not in the debug image?

## Q2: How would you approach setting up a constraint manager in Cadence Allegro for a mixed-signal PCB that has both high-speed digital interfaces and sensitive analog sensor inputs, and how would you verify the constraints are actually being honored?
**Answer:** I'd start by classifying nets before touching the constraint manager — that classification is the real design decision, and everything downstream depends on it. High-speed digital nets (USB, fast SPI, any clock above a few tens of MHz) get their own net class or bus with impedance targets, differential-pair rules where applicable, and length-matching tolerances derived from the timing budget rather than picked arbitrarily. Sensitive analog nets get a separate class with rules that are more about separation and isolation than impedance: keep-out spacing from digital and switching nodes, restricted layers, no routing parallel to noisy aggressors, and controlled return-path rules. Power nets get their own class for width and via count. Once the classes exist, I'd build the constraint set as a spreadsheet-driven rule set so it's reviewable as a document, not buried in a GUI. Verification is the part people skip: I'd run the DRC with the full constraint set enabled and treat violations as blocking, but I'd also do a manual spot-check on a sample of nets using the constraint manager's reporting and the post-route length/impedance reports, because a rule that's defined but not actually enabled or scoped correctly will pass silently. I'd confirm the differential pairs are recognized as pairs, that the analog keep-outs are actually being enforced on the layers that matter, and that the return-path rules are catching the cases I care about by deliberately introducing a test violation and confirming it flags.
**Possible follow-ups:** How would you decide the length-matching tolerance for a high-speed interface when the datasheet gives a range rather than a single number? What's your approach when a constraint you need isn't expressible in the tool's rule set?

## Q3: How would you approach using a spectrum analyzer with a near-field probe to determine whether a radiated emissions failure at a specific frequency is coming from a switching regulator's harmonic or from a digital clock harmonic, and how would you confirm your hypothesis?
**Answer:** The first move is arithmetic, not measurement: list every candidate source's fundamental and see which ones can actually land on the failing frequency. A switching regulator at a known switching frequency and a digital clock at a known rate will each have a comb of harmonics, and often only one comb has a tooth at the exact frequency — that alone narrows it. Then I'd use the probe spatially: a small H-field loop swept slowly over the board, watching the amplitude at the failing frequency, to find the hotspot. The component under the strongest hotspot is a candidate, but proximity alone isn't proof, because a probe couples to whatever is nearby. So I'd confirm by perturbation: temporarily change the switching frequency (if the regulator allows it) or halt/park the digital clock, and see whether the emission moves or disappears. If shifting the regulator's switching frequency shifts the emission, it's the regulator; if gating the clock kills it, it's the clock. I'd also look at the harmonic structure — a regulator's harmonics often have a characteristic roll-off and sidebands from jitter or burst mode, while a clock harmonic is a cleaner narrow line — and check whether the emission tracks load or operating mode, since a regulator's spectrum changes with load current while a clock's generally doesn't. Only after the perturbation test agrees with the arithmetic and the spatial scan would I call the source identified and start on the fix.
**Possible follow-ups:** What would you do if two candidate sources both have a harmonic at the failing frequency? How would you distinguish a genuine radiated emission from something coupled onto your probe cable?

## Q4: How would you approach setting up a scripted, repeatable flashing and test sequence for a Zephyr RTOS target using a Segger J-Link, where the harness needs to program the device, run a test, and capture a crash dump without manual intervention — and what failure modes would you design around?
**Answer:** I'd build it as a layered script rather than one monolithic command. The bottom layer is the flash-and-reset step, driven by the J-Link command-line tooling or a Python wrapper around the J-Link API, so the same sequence works from a developer's machine and from CI. Above that, a test-runner layer that starts the target, waits for a defined handshake (a specific log line over RTT or a GPIO toggle) rather than a fixed sleep, runs the test stimulus, and then either reads a pass/fail result or detects a fault. The crash-dump layer is the interesting one: on a hard fault, the harness needs to halt the core, read out the fault status registers, the stacked PC/LR, and a region of RAM, and write that to a file with a timestamp and the firmware build ID so it's traceable. The failure modes I'd design around: the debugger failing to connect because the target is in a low-power state or the SWD pins got reconfigured by firmware — so the script needs a connect-under-reset fallback; the target hanging instead of faulting, which needs a watchdog timeout in the harness so it doesn't block forever; flash programming succeeding but verification failing silently, so I'd always verify after program; and the crash dump itself being incomplete because the fault corrupted the stack, so I'd capture a fixed RAM region rather than trusting the stack pointer. I'd also make the script idempotent and log every step with timestamps, because when it fails at 2 a.m. in CI the log is all you have.
**Possible follow-ups:** How would you make the harness distinguish a genuine test failure from a harness/infrastructure failure? What would you capture in the crash dump to make it useful to someone who wasn't there when it happened?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?
**Answer:** First I'd separate the technical question from the interpersonal one, because the engineer isn't wrong that the peaks show up — they're wrong about what that means. I'd sit down with them and explain the "why" rather than just overriding: resolution bandwidth affects the measured amplitude of narrowband versus broadband emissions, and detector mode (peak versus quasi-peak versus average) changes the number the standard actually judges you against, so a scan with the wrong settings can pass a device that would fail formal compliance, or fail one that would pass. That's a real risk to the program, not a matter of taste. Then I'd fix it practically: the settings for the target standard are documented, so we reset the analyzer to the standard's RBW and detector, re-run the scan, and compare against the quick scan to show concretely how much the numbers moved. If the formal scan is tomorrow and lab time is booked, I'd treat the re-run as mandatory before we trust any result — a scan with wrong settings isn't evidence, and submitting it would be worse than delaying. On the people side, I'd frame it as a process gap rather than a personal failing: the lab should have a written setup checklist per test standard so this doesn't depend on one person's judgment, and I'd ask the engineer to help write it, which turns the correction into ownership. I'd avoid dressing them down in front of others, but I would be unambiguous that the settings have to match the standard before results go anywhere.
**Possible follow-ups:** How would you handle it if the engineer pushed back and argued the quick scan was "close enough" to save the booked lab time? What would you put in a lab setup checklist to prevent this class of error recurring?
