# tools — Day 107

## Q1: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** I'd start by treating the decoder as a specification problem before it's a tooling problem. First I'd get the frame definition nailed down from the protocol document or, if there isn't one, by capturing a known-good transaction and reverse-engineering the bit boundaries by hand. The key insight with a non-byte-aligned header is that you can't rely on the analyzer's default bit-sampling grid — you need to define the frame in terms of a start condition (a specific edge or level transition), then a bit count to the first field boundary, then field widths in bits rather than bytes.

In most logic analyzers (Saleae, Sigrok, etc.) the practical route is a custom low-level decoder: capture the raw digital channels at a sample rate comfortably above the bus rate (at least 4–10× the fastest edge rate, more if you care about rise-time effects), then write a decoder that hunts for the start pattern, counts bits from that anchor, and slices fields at arbitrary bit offsets. I'd build it incrementally — first just detect and annotate frame boundaries, verify against a scope capture that the boundaries land where I expect, then add field decoding, then add semantic interpretation (scaling, checksums). Validating the decoder against a hand-decoded capture is essential; a decoder that "looks plausible" but is off by one bit is worse than no decoder.

I'd also make the decoder tolerant of the real-world messiness: glitches, missed frames, resync after an error. And I'd keep the decoder definition under version control alongside the firmware, because it's effectively part of the test infrastructure.

**Possible follow-ups:** How would you handle a bus where the bit clock is embedded in the data (e.g., Manchester or a self-clocking scheme) rather than a separate clock line? What would you do if the frame header length itself varied depending on a mode bit?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is reproducibility and traceability — the build that ships must be the build that was reviewed and tested, and you must be able to prove what settings produced it. I'd approach it in layers.

First, treat the project file itself as a controlled artifact: check the `.uvprojx` into version control, and review changes to it the same way you'd review source code, because a silent optimization-level change is a real defect vector. Second, pin the toolchain version explicitly — record the compiler/assembler/linker versions in the build documentation, because optimization behavior and code generation can shift between compiler releases even at the same nominal `-O` level.

For the settings themselves: set the optimization level deliberately per module or per project (often `-O0` or `-O1` for safety-critical code where debug correlation matters, with documented justification), and make the linker script and startup file explicit project members rather than IDE-generated defaults. I'd verify the scatter file / linker script is the one intended by inspecting the map file after each build — the map file is your audit trail showing where every section landed. For startup code, confirm the vector table, stack/heap sizing, and any pre-`main` initialization are all under source control and reviewed.

Finally, I'd wrap the build in a script or CI step that invokes the toolchain with the same settings and archives the map file, the ELF, and a build log with the tool versions. That way "auditable" isn't a claim about the IDE state — it's a set of artifacts you can reproduce and diff.

**Possible follow-ups:** How would you detect that someone had quietly changed the optimization level between a tested build and a release build? What's your approach if the linker script needs to differ between a debug and production image?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The tracking generator plus directional coupler gives you a reflection measurement — you're measuring return loss (S11 magnitude) by comparing incident and reflected power, and from that you can derive the input impedance magnitude and, with phase information, the complex impedance. The setup matters enormously: the directional coupler's directivity sets the floor on how small a reflection you can trust, so I'd first characterize the coupler and cables themselves — measure the open, short, and a known 50 Ω load at the reference plane to establish the system's error terms and confirm the directivity is adequate for the impedance range I care about.

Then I'd calibrate at the actual measurement plane, not at the analyzer port — de-embed the cable and any fixture, because at the frequencies where a front-end's input impedance matters, a few centimeters of coax or a probe tip can dominate the reading. I'd sweep the band of interest, look at return loss versus frequency, and sanity-check against the expected topology: a high-impedance sensor input should show a characteristic capacitive or resistive signature, and if the trace looks like a pure 50 Ω match across the band, that's a red flag that I'm measuring the fixture, not the DUT.

Deciding whether to act: I'd only trust the measurement if the calibration was done at the right plane, the coupler directivity is well above the return loss I'm trying to resolve, the sweep is repeatable (re-measure and compare), and the result is physically plausible given the circuit. If the return loss is near the system's noise/directivity floor, I'd treat it as "below resolution" rather than "good match." Cross-checking with a VNA, if available, is the cleanest confirmation.

**Possible follow-ups:** How would you extend this to get phase and thus the full complex impedance rather than just magnitude? What are the pitfalls of measuring a high-impedance input with a 50 Ω-referenced setup?

## Q4: How would you approach setting up a Segger J-Link's RTT (Real-Time Transfer) logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?

**Answer:** RTT is attractive here precisely because it uses the debug probe's background memory access rather than a peripheral, so it doesn't consume the UART and doesn't require the CPU to block on a peripheral FIFO. The setup: enable the RTT control block in the firmware (Zephyr has a logging backend for it), allocate the up-buffer and down-buffer in RAM, and point the J-Link at the control block — either by address or by having the probe search RAM for the RTT signature. I'd size the buffers deliberately: too small and you drop messages or block the producer, too large and you waste RAM that a medical device may not have to spare.

The timing-perturbation concern is the real engineering problem. RTT's fast path is a memory copy into the ring buffer, which is cheap but not free — it still costs cycles and touches cache/memory, and if the buffer fills, the default behavior can block the logging thread. To keep it non-perturbing I'd: use a lock-free single-producer/single-consumer ring buffer so the logging call never blocks; set the mode to "no-block, overwrite oldest" so a full buffer drops data rather than stalling the safety-critical path; keep the log calls off any interrupt or timing-critical thread, or gate them behind a compile-time flag that's off in the safety build; and measure the actual cost — toggle a GPIO around the log call and scope it, or use cycle counters, to confirm the added latency is within budget.

I'd also verify the probe's polling doesn't steal bus bandwidth at a rate that matters, and confirm that with the probe disconnected the firmware behaves identically (RTT should degrade gracefully to a no-op or dropped messages, never a hang).

**Possible follow-ups:** How would you confirm that log messages aren't being silently dropped under load? What's your approach if the RTT control block address moves between builds?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** First, I'd separate the technical issue from the interpersonal one and deal with the technical issue on the spot, because the scan is tomorrow. The engineer's intuition isn't wrong that peaks show up either way — but the point of a pre-compliance scan is to produce numbers you can compare against a limit line, and resolution bandwidth and detector mode directly change the measured amplitude. A wide RBW and a peak detector can make an emission look compliant or non-compliant depending on settings, so "the peaks show up" isn't the same as "the measurement is valid." I'd explain that concretely rather than just asserting authority: show the standard's required RBW and detector, re-run a quick sweep at both settings on the same emission, and let the difference speak for itself. That turns it into a learning moment instead of a correction.

Then I'd fix the setup: reconfigure to the standard's settings, re-verify the probe and cable calibration, and do a quick sanity scan to confirm the instrument is behaving before the formal run. If there's any doubt the booked lab time is enough, I'd flag it early to whoever owns the schedule rather than discover it mid-scan.

On the people side, I'd be careful not to embarrass the engineer in front of the team — pull them aside, frame it as "here's why the settings matter for a defensible measurement," and make clear the goal is a result we can stand behind, not assigning blame. I'd also follow up afterward on why the setup process didn't catch this — a checklist for pre-compliance scans, with the standard's required settings baked in, prevents the next occurrence better than any individual correction.

**Possible follow-ups:** How would you build a pre-scan checklist that catches this class of error without becoming bureaucratic? If the re-run at correct settings showed a marginal failure, how would you decide whether to escalate before the formal scan?
