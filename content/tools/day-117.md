## Q1: How would you approach setting up a Zephyr RTOS project using the west build system so that the same source tree produces both a production image and a debug image with extra logging and assertions, without maintaining two separate trees?

**Answer:** The cleanest way is to treat the difference as configuration, not as code. West already separates the application source from the build directory, so the first step is to make sure nothing environment-specific lives in the source tree — no hand-edited generated files, no per-build tweaks committed to the repo. Then I'd express the two variants as distinct build configurations: either two `west build` invocations with different `-b`/`-D` overlay arguments, or two named build directories (`build/prod`, `build/debug`) driven by a small wrapper script so nobody has to remember the flags.

The mechanism I'd lean on is Kconfig plus devicetree overlays. A production config fragment sets `CONFIG_LOG` to a minimal level or off, disables `CONFIG_ASSERT`, and picks the release optimization; a debug fragment turns logging up, enables assertions and thread analyzer, and may add a debug console. These fragments are checked in and versioned, so the difference between the two images is auditable — you can diff the fragments and see exactly what changes. For anything that genuinely needs conditional code, I'd gate it on a Kconfig symbol rather than on `#ifdef DEBUG`, so the build system owns the decision and the symbol shows up in the generated `.config`.

The part people skip is verification: after building both, I'd compare the generated `.config` and the map file to confirm the debug image really has the extra features and the production image really doesn't, and I'd make the release process build the production image from a clean tree so a stale debug artifact can't leak into a release. For a medical device this matters because the released binary has to be reproducible and traceable to a known configuration.

**Possible follow-ups:** How would you make sure a developer can't accidentally ship the debug configuration? Where would you put the board-specific devicetree overlays so they don't collide with the application overlays?

## Q2: How would you approach configuring a Keil uVision project so that the optimization level, linker script, and startup code are locked down and auditable, rather than left at whatever the IDE defaults to?

**Answer:** The risk with an IDE-managed project is that build settings live in a binary-ish project file that's easy to change by clicking, and nobody reviews the diff. So the goal is to make the important settings explicit, versioned, and hard to change silently.

Concretely: I'd keep the linker script and startup file as source-controlled files referenced by relative path, not as files the IDE generates or copies around. I'd pin the optimization level per target and document why — for a medical device, debug builds at `-O0` for traceability and release builds at a chosen level that's been validated, with the understanding that changing optimization can change timing and expose latent bugs, so it's a reviewed change, not a casual toggle. I'd also fix the compiler version and the device pack version, because "same source, different toolchain" is a classic source of non-reproducible binaries.

For auditability, I'd export the build settings into something diffable — many teams keep a build log or a settings summary in the repo, and some generate a map file and size report on every build so changes in code size or memory layout are visible in review. I'd also make sure the project builds from a script or batch file in CI, so the "official" build doesn't depend on someone's local IDE state. If the project file format makes review painful, that's a signal to keep the authoritative settings in a text file the project imports, or to drive the build from a makefile/CMake and use the IDE only as an editor and debugger.

**Possible follow-ups:** How would you catch a change in optimization level during code review if the project file diff is unreadable? What would you check in the map file to confirm the linker script is actually being applied?

## Q3: How would you approach using a spectrum analyzer with a near-field probe to determine whether a radiated emission at a specific frequency is coming from a switching regulator or from a digital clock, and how would you confirm your hypothesis?

**Answer:** The first move is arithmetic, not measurement: list the candidate sources and their harmonics. A switching regulator at, say, a few hundred kHz produces a comb of harmonics; a digital clock at some MHz produces its own comb. If the failing frequency lands on an integer multiple of one candidate and not the other, that's a strong hint — but hints aren't proof, so the measurement has to discriminate.

With a near-field probe I'd do a spatial survey: move the probe slowly over the board and find where the field at the failing frequency peaks. The probe is directional and very local, so the hotspot usually points at the culprit — the regulator's inductor/switch node loop, or the clock's trace and its return path. I'd compare the amplitude at the fundamental and at the harmonic in question: a switching regulator's harmonic amplitude typically rolls off in a characteristic way, while a clock harmonic may be stronger or show the clock's spectral signature.

To confirm, I'd perturb one source at a time. Change the regulator's switching frequency slightly (if the design allows) and see whether the emission moves with it; disable or gate the clock and see whether the emission disappears. If I can't disable a clock, I can often change its frequency or spread-spectrum setting and watch the emission shift. The confirmation is that the emission tracks the source I changed and not the other. I'd also sanity-check the measurement itself — probe orientation, cable routing, whether the analyzer's settings are appropriate for the frequency and whether I'm seeing a real peak or an artifact — before acting on it, because a near-field probe measurement is qualitative and easy to fool yourself with.

**Possible follow-ups:** What would you do if the emission frequency matches harmonics of both sources? How would you distinguish a radiated coupling path from a conducted one that's re-radiating?

## Q4: How would you approach setting up a Segger J-Link's RTT logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?

**Answer:** RTT is attractive here precisely because it doesn't consume a UART — it uses the debug probe's memory access to read a ring buffer in target RAM, so the safety-critical UART stays untouched. The setup is: enable the RTT backend in Zephyr's logging configuration, make sure the RTT control block is placed in a memory region the debugger can find (usually via the linker and the `SEGGER_RTT` section), and point the J-Link software at the control block address. On the host side, the RTT client reads the buffer continuously.

The timing concern is real and is the part I'd design around. RTT logging is not free: the target writes into the ring buffer, and if the host isn't draining it fast enough the buffer fills and the target either blocks or drops messages depending on configuration. Blocking in a safety-critical path is unacceptable, so I'd configure non-blocking/drop-on-full behavior and size the buffer deliberately. I'd also keep logging out of the tightest timing paths — log at state transitions and errors rather than every loop iteration — and use deferred logging modes where the formatting happens off the critical path. If the logging backend itself runs in a low-priority thread, that's usually the right trade.

Then I'd verify the perturbation empirically: measure a known timing-critical operation with logging on and off and compare, and watch for dropped-message counters. If enabling logging changes the behavior I'm trying to observe, the logging is part of the problem, and I'd reduce it or move it. For a medical device I'd also make sure RTT logging is compiled out or disabled in the released configuration, since it's a debug facility, not a production feature.

**Possible follow-ups:** How would you detect that RTT is silently dropping messages? What would you do if the control block address moves between builds?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** First I'd separate the technical issue from the interpersonal one, because they need different handling. Technically, the engineer isn't wrong that the peaks show up — a fast scan with a wide resolution bandwidth and a peak detector will reveal that energy exists at a frequency. What it won't do is give a measurement you can compare against a limit, because resolution bandwidth, detector type, and dwell time all affect the reported amplitude, and the standard specifies them for a reason. So the correction isn't "you're wrong," it's "this scan answers a different question than the one the formal test asks."

I'd explain that distinction concretely rather than just citing the standard — show the same emission measured with the correct settings and let the difference speak. Then I'd treat it as a process gap, not just an individual mistake: if a junior engineer can set up a compliance scan from a tutorial and nobody catches it until the day before, the setup procedure itself needs a checklist tied to the applicable standard, with the required RBW, detector, and correction factors written down and verified before the scan starts.

For the schedule: I'd check whether the correct settings can be applied and the scan re-run in the booked time — often they can, because the instrument setup is quick and the scan itself is the long part. If the booked slot genuinely can't accommodate a compliant scan, I'd rather flag that to the project lead early and rebook than produce a number that looks like a compliance result but isn't. The worst outcome is submitting a non-compliant measurement as if it were compliant. I'd deliver the feedback to the engineer privately, framed around the difference between "finding emissions" and "measuring emissions," and make clear the goal is a defensible result, not blame.

**Possible follow-ups:** How would you build the pre-scan checklist so this doesn't recur? What would you tell the project lead if the compliant scan can't happen in the booked window?
