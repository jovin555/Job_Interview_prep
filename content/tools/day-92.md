## Q1: How would you approach setting up a schematic symbol library in Altium Designer so that symbols stay consistent and traceable across a multi-year medical device program, where the same part may be reused across several board revisions?
**Answer:** I'd treat the symbol library as a controlled design asset rather than a shared folder of files. The foundation is a version-controlled library (SVN or a managed vault/Altium 365 workspace) where every symbol has a unique identifier, a revision, and a link to its datasheet and manufacturer part number. I'd standardize on a symbol convention up front — grid, pin length, pin naming, reference designator prefix, and how multi-part devices are split — and document it so contributors produce consistent output. For traceability, each symbol carries parameters that map to the BOM and to the component record, so a change to a part flows through to every board that uses it. When a part is reused across revisions, I'd avoid editing the existing symbol in place; instead I'd create a new revision and let the affected projects explicitly update, so the change is a deliberate, reviewable event rather than a silent propagation. I'd also run a library consistency check (duplicate pins, mismatched footprint links, missing parameters) before release, and keep the library under the same review discipline as the schematic itself.
**Possible follow-ups:** How would you handle a situation where a part's datasheet pinout changes between silicon revisions — do you version the symbol or add a variant? How do you prevent engineers from creating "local" symbols that bypass the library?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?
**Answer:** The goal is to make the build reproducible and to make any deviation visible. I'd start by defining the build configuration explicitly — target, optimization level, and any per-file overrides — and then treat the project file itself as a reviewed artifact under version control, so changes to optimization or linker settings show up as diffs rather than as silent IDE edits. I'd pin the linker script and startup file to specific, versioned files in the repo rather than letting them float, and I'd document why each optimization level was chosen, since optimization can change timing and expose latent undefined behavior. For auditability, I'd capture the toolchain version, the exact compiler flags, and the resulting map file with each release build, so a regulator or reviewer can reconstruct how a given binary was produced. I'd also add a build-time check or script that fails the build if the optimization level or linker script doesn't match the approved configuration, which catches accidental drift early. The key discipline is that "the code works fine" at one optimization level is not evidence it's correct at another — so the approved configuration is the one that gets tested and released, and any change to it triggers re-verification.
**Possible follow-ups:** What specific risks does changing optimization level introduce for a safety-critical firmware build? How would you verify that the released binary matches the reviewed source and settings?

## Q3: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?
**Answer:** When no built-in decoder fits, I'd first characterize the protocol from the physical layer up: capture a known-good transaction, measure the clock/data relationships, and identify the frame boundaries, header pattern, and any bit-stuffing or non-byte-aligned fields. From there I'd build a custom decoder — many logic analyzers support a scripting layer (Python or a vendor SDK) where you define states: idle, sync/header detection, field extraction, payload, and checksum. The critical design decision is how to detect frame start reliably; if the header isn't byte-aligned, I'd trigger on the specific bit pattern rather than a byte value, and I'd make the decoder tolerant of the timing jitter and idle gaps the real bus exhibits. I'd validate the decoder against captures where I already know the expected payload — for instance, a transaction I can cross-check against the sensor's documented output or a known test vector — before trusting it to interpret failures. I'd also expose intermediate fields (raw bits, computed checksum, decoded values) in the decoder output so that when something looks wrong I can see whether the issue is in the framing, the payload, or my decoder logic. Finally, I'd version the decoder script alongside the test setup so the analysis is repeatable by other engineers.
**Possible follow-ups:** How would you distinguish a genuine protocol violation from a decoder bug when the decoded output looks wrong? What would you do if the bus has variable-length frames with no explicit length field?

## Q4: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?
**Answer:** The tracking generator plus directional coupler lets me measure return loss (S11) by injecting a swept signal and observing how much reflects back, from which I can derive the input impedance across frequency. Setup discipline matters more than the math: I'd calibrate out the test setup first — cables, coupler, and any fixture — using a reference standard or a through/short/open calibration so the measurement reflects the front-end and not my bench. I'd keep the injected power low enough to stay in the front-end's linear region and avoid damaging sensitive inputs, and I'd verify the coupler's directivity is adequate for the impedance range I expect, since poor directivity limits how small a reflection I can resolve. To decide whether to trust the result, I'd check for consistency: does the measured impedance match the expected topology (e.g., a known input termination or filter) at low frequency where parasitics are minimal? Does it change sensibly with frequency rather than jumping around, which would suggest fixture resonances or grounding problems? I'd cross-check against a second method — a VNA if available, or a time-domain reflectometry view — and confirm the fixture's own impedance is characterized. If the measurement is repeatable, matches the expected circuit behavior at the frequencies that matter, and the fixture effects are accounted for, I'd act on it; otherwise I'd fix the setup before drawing conclusions.
**Possible follow-ups:** How would fixture parasitics corrupt the measurement at higher frequencies, and how would you de-embed them? What would a suspicious resonance in the return-loss trace tell you about the board or the test setup?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?
**Answer:** I'd handle it in two layers: fix tomorrow's scan, and fix the process that let it happen. First, I'd sit down with the engineer and explain concretely why the settings matter — resolution bandwidth affects the noise floor and whether closely spaced emissions are resolved, and detector mode (quasi-peak vs. peak vs. average) changes the measured amplitude against a limit line, so "the peaks show up" doesn't mean the numbers are valid against the standard. I'd frame it as a shared technical point, not a correction, and walk through the standard's required settings together so it lands as understanding rather than instruction. Then I'd verify the corrected configuration myself before the session — a quick sanity check against a known reference or a repeat of a previous scan — so we go in with confidence. On the schedule: since the lab is booked and non-refundable, I'd make sure the corrected setup is ready tonight rather than gambling on tomorrow, and if there's any doubt about the setup I'd rather use the booked time to get valid data than to discover mid-scan that the settings are still wrong. Afterward, I'd add a pre-scan checklist for standard-required instrument settings to the lab procedure so this becomes a routine gate rather than a person-dependent catch, and I'd make sure the engineer owns part of that checklist so the lesson sticks.
**Possible follow-ups:** How would you verify the corrected settings are right without consuming much of the booked lab time? How do you give this feedback so a junior engineer stays motivated rather than defensive?
