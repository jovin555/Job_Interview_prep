# tools — Day 95

## Q1: How would you approach setting up a schematic library in Altium Designer so that symbols stay consistent and traceable across a multi-year medical device program, where the same part may be reused across several board revisions?
**Answer:** The core problem is that a schematic symbol is a long-lived artifact — it will outlive individual projects, individual engineers, and possibly several PCB revisions — so the library has to be designed for change, not just for the current design. I'd start by deciding on a single source of truth: either a managed content server (Altium 365 or a Concord Pro-style vault) or a version-controlled library repository, but not a mix of local `.SchLib` files scattered across engineers' machines. If a managed server is available, I'd use its lifecycle states (draft → released → deprecated) so that a symbol can't be silently edited after it's been used on a released board; if not, I'd enforce a Git or SVN workflow with tagged releases and a rule that released symbols are immutable.

For the symbol design itself, I'd standardize on a house style: consistent pin naming and ordering, power pins grouped logically, footprint links resolved through the library rather than typed per-instance, and parameters (manufacturer part number, tolerance, temperature grade, lifecycle status) carried as symbol parameters so they propagate into the BOM and can be queried. For a medical program, I'd also add parameters that support traceability — a component risk classification, a reference to the approved-manufacturer list entry, and a revision field — because those are the fields a design history file review will ask about.

The reuse-across-revisions part is where discipline matters. When a part changes (say a package variant or a tolerance grade), I would not edit the existing symbol in place; I'd create a new revision and let the old one remain for boards already released against it. That way a schematic from two years ago still opens and resolves to exactly what was built. I'd also keep a symbol-to-footprint mapping table under review, because the most common library failure isn't a wrong symbol — it's a correct symbol pointing at the wrong footprint.

**Possible follow-ups:** How would you handle a situation where a part becomes obsolete mid-program and you need to substitute it without invalidating already-released revisions? What would you check in a library audit before a design review?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?
**Answer:** The risk with an IDE-managed project is that build settings live in a project file that's easy to change accidentally and hard to diff meaningfully, so the goal is to make the build configuration explicit, version-controlled, and reproducible. I'd start by treating the `.uvprojx` (or equivalent) as a reviewed artifact in version control, not a local file, and by pinning the toolchain version — compiler, linker, and device pack — so that a build on a colleague's machine or a CI runner produces the same output as the release build.

For the specific settings: I'd set the optimization level deliberately per build configuration rather than leaving it at whatever the IDE picked, and I'd document why that level was chosen, because optimization level can change timing behavior and expose latent undefined behavior. Debug and release configurations would differ only in ways that are explicitly listed and reviewed. The linker script and startup file would be checked into the repository as first-class source files, referenced by relative path, and reviewed like code — not regenerated by the IDE on each open. I'd also enable the linker's map file output and archive it with each release, so you can answer "what actually got linked" after the fact.

For auditability, the key is that the build should be reproducible from a clean checkout with a documented command, and the resulting binary should be hashed and recorded alongside the source revision. In a regulated context, that hash plus the toolchain version plus the source tag is what lets you demonstrate that the firmware in the device matches the firmware that was reviewed and tested.

**Possible follow-ups:** How would you catch a situation where someone changed the optimization level locally and the change never made it into version control? What's your approach to keeping debug and release configurations from drifting apart over time?

## Q3: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?
**Answer:** When the framing doesn't align to byte boundaries, the built-in decoders are useless, so the approach is to build the decoder from the physical layer upward rather than trying to bend an existing decoder. First I'd characterize the signal itself: clock or embedded clock, idle level, bit period, and where the frame actually starts. A non-byte-aligned header usually means there's a sync pattern or a start condition that the decoder has to key on, so I'd capture a known-good transaction and identify that pattern by eye before writing any decoder logic.

Then I'd decide the decoding strategy. Many logic analyzers support a scripted or high-level-language decoder (Python or a vendor scripting API), which lets me define the sync search, the bit extraction, the field boundaries, and the checksum in one place. If the tool only supports a simpler pattern-matching decoder, I'd break the problem into stages: a trigger on the sync pattern, then a bit-level extraction, then a post-processing script that reassembles fields. Either way, I'd validate the decoder against a capture where I already know the correct values — ideally by cross-checking against a firmware debug print or a second instrument — before trusting it on an intermittent failure.

The practical trap is sample rate and threshold. A decoder is only as good as the capture underneath it, so I'd confirm the sample rate is comfortably above the bit rate, set the threshold to the actual mid-rail of the logic family in use, and check that the probe loading isn't distorting the edges. For a medical device, I'd also make sure the decoder setup itself is documented and repeatable, so a colleague can reproduce the same capture rather than re-deriving it.

**Possible follow-ups:** How would you handle a protocol where the bit rate isn't constant across the frame? What would you do if the decoder works on a bench capture but produces garbage on the actual device?

## Q4: How would you approach setting up a power integrity simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?
**Answer:** The first decision is what question the simulation is actually answering, because PI simulation can mean very different things — DC IR drop, AC impedance of the PDN, or transient noise coupling — and each needs different models and different trust criteria. For a shared PDN with a switching regulator and a sensitive analog front-end, I'd typically work in this order: DC IR drop first to confirm the planes and traces can carry the current with acceptable drop, then AC impedance of the PDN across the frequency range of interest, then transient or noise coupling if the first two suggest a problem.

The trust question is the important one. A PI simulation is only as good as its inputs: the stackup and dielectric properties, the copper geometry extracted from the actual layout, the capacitor models including ESR and ESL, and the regulator's output impedance model. I'd be explicit about which of those are approximations and which are measured. Capacitor models from vendor libraries are usually decent; the regulator's output impedance is often the weakest link, and I'd rather measure it or use a vendor-provided model than guess. I'd also check that the simulation's frequency range covers the switching frequency and its harmonics, plus the bandwidth where the analog front-end is actually sensitive.

To decide what's actionable, I'd compare the simulated impedance against a target — typically a target impedance derived from the allowed ripple and the load current steps — and treat results that are within a factor of the model uncertainty as "needs measurement" rather than "needs a redesign." The output of a PI simulation should be a prioritized list of what to measure on the bench, not a verdict. If the simulation says the PDN is marginal at a particular frequency, the next step is a real measurement with a network analyzer or a scope probe at that node, not another simulation run.

**Possible follow-ups:** How would you validate a PDN impedance simulation against a real measurement on a prototype? What would you do if the simulation and the measurement disagreed significantly?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?
**Answer:** The first thing I'd do is separate the technical issue from the interpersonal one, because they need different handling and mixing them makes both worse. Technically, the engineer isn't wrong that the peaks show up — a quick scan with a wide resolution bandwidth and a peak detector will reveal that energy exists at a frequency. What it won't do is give a measurement that's comparable to the limit line, because resolution bandwidth affects the displayed amplitude of broadband versus narrowband emissions, and detector mode determines whether you're reading peak, quasi-peak, or average, which the standard specifies for a reason. So the correction isn't "you're wrong," it's "these settings answer a different question than the one the formal scan asks."

In the moment, I'd sit down with the engineer and walk through the standard's requirements together rather than just overriding the settings — pull up the relevant clause, show the specified RBW and detector, and explain what each setting does to the measurement. That does two things: it fixes tomorrow's scan, and it builds the engineer's understanding so the same issue doesn't recur. I'd frame it as a shared review of the test setup, not a correction, because the engineer's instinct to get a quick look first is actually a reasonable one — it's just not the final step.

For the schedule, I'd re-run the setup with the correct settings tonight if the lab is accessible, or first thing before the booked slot, and I'd build in a short verification step — a known reference source or a repeat of a previous scan — to confirm the instrument is configured correctly before committing the booked time. If the correct settings change the picture significantly, that's exactly the kind of thing you want to discover before the formal scan, not during it. Afterward, I'd add the required instrument settings to the test procedure document so the setup is specified rather than left to whoever configures the instrument.

**Possible follow-ups:** How would you handle it if the engineer pushed back and argued the standard's settings were overly conservative? What would you change in the team's process so that instrument setup is verified before a booked lab slot rather than discovered on the day?
