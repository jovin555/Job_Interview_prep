## Q1: How would you approach setting up a differential pair routing constraint in Cadence Allegro for a CAN-FD bus running at 5 Mbps on a mixed-signal medical device PCB, and how would you verify the constraints are actually honored in the final layout?

**Answer:** At 5 Mbps CAN-FD, the bit time is short enough that the differential pair needs controlled impedance and reasonable length matching, but the constraints are less aggressive than for something like USB 2.0 — the goal is to keep the pair's impedance consistent and avoid skew that erodes the differential signal's margin, not to chase sub-millimeter matching. I'd start in the constraint manager by defining the physical rule set: target differential impedance (typically 120 Ω for CAN, though the exact target comes from the stackup and transceiver requirements), a tolerance band, and a maximum intra-pair skew. Then I'd assign the net class and the differential pair object to that rule set so the constraints propagate to every segment of the pair rather than being applied ad-hoc.

The verification step is where a lot of people get lazy. I'd run the DRC with the differential-pair checks enabled and confirm the report actually flags violations rather than silently passing — a common failure is that the pair wasn't properly associated as a diff pair object, so the rules never applied. Beyond the automated check, I'd visually inspect the routing for the things DRC can't catch: whether the pair stays coupled through the whole run, whether there are unnecessary layer transitions, and whether the return path is continuous under the pair. For a mixed-signal board, I'd also confirm the pair doesn't run parallel to sensitive analog traces for long distances, since coupling is a two-way street.

**Possible follow-ups:** How would you decide the impedance target if the transceiver datasheet and the stackup vendor give slightly different numbers? What would you do if the DRC passes but you suspect the pair isn't actually being treated as a differential pair by the tool?

## Q2: How would you approach organizing a KiCad project for a medical device so that the schematic, PCB, footprints, and 3D models stay consistent across revisions, and how would you catch footprint-to-schematic mismatches before they reach fabrication?

**Answer:** KiCad's file-based library model is the crux of the problem — footprints and symbols live in libraries that can drift independently of the project, so consistency has to be engineered rather than assumed. I'd start by deciding whether the project uses global libraries or project-local libraries. For a medical device with regulatory traceability needs, I lean toward project-local libraries checked into version control alongside the schematic and PCB, so the exact symbol and footprint revisions travel with the design rather than depending on whatever happens to be installed on an engineer's machine.

For catching footprint-to-schematic mismatches, the first line of defense is the footprint assignment link in the schematic — every symbol should have an explicitly assigned footprint, and I'd treat any symbol with a blank or placeholder footprint field as a defect. The second line is running the footprint association check and the ERC before layout, and then re-running it after any library update. The third line, which people often skip, is a visual sanity check: cross-probing from the schematic to the PCB to confirm the pad count, pitch, and orientation match what the symbol implies, especially for parts with multiple package variants. Before fabrication, I'd also verify the 3D models load and align with the footprints, because a misaligned 3D model is often the first visible symptom of a footprint that's subtly wrong.

**Possible follow-ups:** How would you handle a situation where a footprint needs to change mid-project but the change would affect boards already in fabrication? What's your approach to versioning the project-local libraries so a reviewer can tell which revision of a footprint was used on a given board?

## Q3: How would you approach setting up a simulation workflow in LTSpice for a mixed-signal board where a switching regulator and a precision analog front-end share the same supply rail, and how would you decide which simulation results are trustworthy enough to act on?

**Answer:** The value of an LTSpice simulation here is understanding the interaction between the regulator's switching behavior and the analog front-end's sensitivity, not predicting the exact microvolts of noise you'll measure on the bench. I'd build the model in layers: first the regulator with a realistic load and a model of the output filter, then the parasitic elements that matter — the ESR and ESL of the output capacitors, the trace inductance between the regulator and the analog load, and the input impedance of the analog front-end. Without those parasitics the simulation will look unrealistically clean and give false confidence.

For the analysis itself, I'd run a transient simulation long enough to reach steady state and look at the ripple at the analog supply pin, then run an AC analysis to see how the regulator's output impedance interacts with the front-end's supply rejection across frequency. The trustworthiness question comes down to model fidelity: if I'm using ideal capacitors and a simplified regulator model, the results tell me about trends and relative sensitivities, not absolute noise levels. I'd only act on a simulation result when the model includes the dominant parasitics, when the result is stable across reasonable parameter variations, and when I can correlate the predicted behavior with at least a rough bench measurement. If the simulation and the bench disagree, the bench wins and the model gets refined.

**Possible follow-ups:** How would you model the PCB trace inductance between the regulator and the analog front-end without overcomplicating the schematic? What simulation would you run first if you suspected the problem was conducted rather than radiated coupling?

## Q4: How would you approach setting up a Gerber and drill-file verification workflow in Gerbv for a medical device PCB, so that fabrication issues are caught before the files leave for the board house?

**Answer:** Gerbv is a viewer, not a rule checker, so the workflow has to be built around what a human can reliably catch by looking — which means the process needs to be structured and checklist-driven rather than "open the files and eyeball them." I'd start by confirming the layer set is complete and correctly named: copper layers, soldermask, silkscreen, paste, drill, and any mechanical or outline layers. A missing or misnamed layer is one of the most common and most expensive release errors, and it's easy to catch if you're systematic about it.

Then I'd load all layers and step through them in a defined order. First the outline and drill against the board dimensions and mounting holes. Then each copper layer against the others to check for alignment — a layer offset by a fraction of a millimeter is subtle in isolation but obvious when overlaid. Then soldermask and paste against copper to catch mask openings that don't line up with pads. Then silkscreen against pads to catch text or outlines that overlap exposed copper, which is a manufacturing and inspection problem. I'd also check the drill file against the pad locations to confirm every through-hole has a corresponding drill hit and vice versa. The whole thing gets documented as a release checklist so the verification is repeatable and auditable, which matters for a medical device where the fabrication release is part of the design history.

**Possible follow-ups:** What would you do if you found a discrepancy between the drill file and the pad locations — how would you determine which one is wrong? How would you adapt this workflow if the board house uses a different Gerber format or has its own pre-flight checks?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the Altium Designer output job configuration for a medical device PCB release, and you discover the fabrication outputs are missing the drill table and the assembly drawings reference an outdated revision of the schematic. The board house is expecting the files tomorrow, and the engineer is confident the outputs are complete because "the Gerbers look fine." How would you handle this situation?

**Answer:** The first priority is the immediate risk: files going to a board house with missing or wrong information. I'd stop the release, tell the engineer clearly that we're not sending the files as-is, and explain specifically what's wrong — the missing drill table and the stale assembly drawing revision — so the feedback is concrete rather than "your output job is broken." The "the Gerbers look fine" comment tells me the engineer is validating one artifact in isolation rather than validating the release as a whole, so part of the conversation is about what "complete" means for a fabrication package.

Then I'd work with the engineer to fix the output job configuration, but I'd frame it as a learning opportunity rather than a correction. We'd walk through the output job together: what each output is for, why the drill table matters to the board house, and why the assembly drawing revision has to match the schematic revision that the board was designed against. I'd have the engineer regenerate the outputs and then verify them against a release checklist — the same checklist I'd want the team using going forward — so the fix reinforces the process rather than just patching this one instance. On the schedule side, I'd communicate to the board house that the files are coming a day later and why, because a short delay with a clear reason is far better than a fabrication run built on incomplete data. After the release, I'd follow up by making the release checklist a standing part of the workflow so this class of error gets caught before it reaches a lead.

**Possible follow-ups:** How would you handle it if the engineer felt singled out or defensive about the mistake? What would you change in the release process so that a missing drill table or stale assembly drawing can't slip through again?
