## Q1: How would you approach setting up a schematic library in Altium Designer so that symbols stay consistent and traceable across a multi-year medical device program, where the same part may be reused across several board revisions?

**Answer:** The core problem is that a schematic library is a living artifact, not a one-time deliverable, so the strategy has to make the "correct" symbol the path of least resistance. I'd start by deciding on a single source of truth — either a database library or a version-controlled schematic library — and forbid ad-hoc symbols created in the project. Each symbol gets a stable internal part number and a revision field, and the symbol's parameters carry the manufacturer part number, the datasheet revision it was drawn from, and a link to the approved-vendor entry. That way, when a part is reused across board revisions, the symbol itself is versioned independently of the boards that use it.

For consistency, I'd enforce a drawing standard: pin naming conventions, pin grouping (power on top, ground on bottom, functional blocks in reading order), consistent electrical types (so ERC actually means something), and a fixed set of required parameters. I'd use the library's built-in checking where possible and a scripted audit where not — for example, a script that flags symbols missing required parameters or with pins whose electrical type is "passive" when it should be "power input." For traceability, the symbol revision and the board revision have to be linked in the BOM and in the design history file, so that a reviewer can answer "which symbol revision was used on this board revision" without guesswork.

The trade-off is overhead: a strict library slows down the first use of a new part. I'd mitigate that with a fast review path for new symbols — a second pair of eyes and a checklist rather than a full committee — so the discipline doesn't become a bottleneck people route around.

**Possible follow-ups:** How would you handle a situation where a symbol needs to change because the manufacturer revised the pinout, but boards already released use the old symbol? What's your approach to migrating an existing project's loose symbols into the managed library without breaking the schematic?

## Q2: How would you approach setting up a constraint manager in Cadence Allegro for a mixed-signal PCB that has both high-speed digital interfaces and sensitive analog sensor inputs, and how would you verify the constraints are actually being honored?

**Answer:** I'd structure the constraint manager by net class first, because the physical rules follow from the electrical intent. Digital high-speed nets get their own classes with impedance targets, propagation-delay or length-matching rules, and differential-pair definitions where applicable. Analog sensor nets get a separate class with rules that are almost the inverse: no length matching, but tight rules on coupling to aggressor nets, clearance to digital, and reference-plane continuity. Power nets get their own class for width and via count. The key discipline is that every net belongs to exactly one class, and the class assignment is reviewed alongside the schematic — not left to whoever happens to route the board.

For the mixed-signal boundary, I'd use region-based rules or net-class-to-net-class spacing so that analog and digital traces are physically separated where they cross the same area, and I'd set up a keep-out or region around the analog front-end that digital routing can't enter. For differential pairs, the constraint set includes the impedance target, the gap, the max uncoupled length, and the phase tolerance.

Verification is where a lot of teams get lazy. I'd run the DRC with the full constraint set enabled, but I'd also do a visual and measurement-based check: use the constraint manager's reporting to confirm every net is in a class, run the length and impedance reports, and spot-check the actual routed geometry against the constraint rather than trusting the green checkmark alone. On a mixed-signal board I'd specifically verify reference-plane continuity under the analog traces and under the high-speed digital traces, because a constraint manager won't always catch a split plane under a signal.

**Possible follow-ups:** How would you decide the impedance target for a digital interface when the driver datasheet gives a range rather than a single number? What would you do if the constraint manager reports a violation that you believe is a false positive — how do you confirm and then handle it?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The tracking generator plus directional coupler gives me a reflection measurement — I'm measuring return loss, and from that I can infer input impedance across frequency. The setup matters more than the math: I'd calibrate the analyzer and the coupler out of the measurement first, using a short/open/load reference at the plane where the front-end connects, so that the reference plane is defined and the cable and coupler are de-embedded. Then I connect the front-end and sweep, and I convert return loss to impedance using the reflection coefficient.

The trust question is the important one. A single sweep can look clean and still be wrong, so I'd check several things: does the result change if I move the cable or touch the board (suggesting the measurement is picking up hand capacitance or a bad connection)? Does the impedance at low frequency match what I'd expect from the DC input resistance of the front-end? Does the result repeat across two different reference calibrations? Is the return loss so close to 0 dB that I'm really measuring noise floor rather than the device? And is the front-end powered in the state I'm measuring, since a biased input can look very different from an unpowered one?

I'd also sanity-check against the schematic: if the front-end has a known input filter, the impedance curve should show the expected resonance. If the measurement and the predicted behavior disagree, I trust neither until I understand why. The decision to act comes only after the measurement is repeatable, referenced to a defined plane, and consistent with the circuit's expected behavior — otherwise it's a number, not data.

**Possible follow-ups:** How would you handle a front-end that's differential rather than single-ended — what changes in the setup? What would you do if the impedance looked fine on the bench but the field behavior suggested a mismatch?

## Q4: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is that a build is reproducible and that the settings that affect behavior are explicit and reviewed, not inherited from whatever the IDE happened to default to. I'd start by treating the project file itself as a controlled artifact — version-controlled, reviewed on change, and diffed in pull requests so that a change to optimization level or linker script shows up as a visible line in review rather than a silent IDE tweak.

For optimization, I'd pin the level explicitly per build configuration (debug and release), and I'd document why each level was chosen, because optimization level can change timing and can expose or mask undefined behavior. For the linker script, I'd keep it in the repository, not in a tool-generated location, and I'd add a memory-map check — either a post-build script that parses the map file and asserts that critical regions (calibration data, bootloader, safety-critical code) land where the design intends, or a linker assertion. The startup code gets the same treatment: it's source, it's reviewed, and its vector table and stack/heap sizing are checked.

For auditability, I'd make the build emit a manifest — compiler version, optimization flags, linker script hash, source revision — so that a released binary can be traced back to exactly the settings that produced it. That's the artifact a regulatory reviewer will ask for. The trade-off is that pinning everything makes the build less flexible, so I'd keep the flexibility in separate, clearly named configurations rather than in ad-hoc edits to the default.

**Possible follow-ups:** How would you catch a situation where someone changed the optimization level locally and the change never made it into version control? What's your approach to verifying that the startup code's stack and heap sizing are actually adequate for the worst-case call depth?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** First I'd separate the technical issue from the interpersonal one, because they need different handling and conflating them makes both worse. Technically, the engineer isn't wrong that the peaks show up — the problem is that the amplitude and the comparison to the limit line are not valid with the wrong resolution bandwidth and detector, so a scan that "looks fine" can pass or fail incorrectly. I'd explain that distinction concretely rather than just asserting the settings are wrong, because the goal is for the engineer to understand why the standard specifies those settings, not just to comply.

Then I'd deal with the schedule. The right move is to fix the settings and re-run the scan tonight if the lab is accessible, or first thing before the formal slot, and to treat the formal scan as the authoritative one regardless. If the lab time is truly at risk, I'd escalate early rather than hope — a delayed scan is recoverable, a scan with invalid settings that gets used for a compliance decision is not. I'd also make sure the engineer isn't blamed in front of the team; the failure is a process gap (no pre-scan checklist, no second-person verification of instrument setup), and I'd own that gap as the lead.

The follow-through matters as much as the fix: I'd add a setup checklist for the instrument configuration that gets signed off before any formal scan, so this class of error doesn't recur, and I'd make sure the junior engineer is part of building that checklist rather than just being corrected by it.

**Possible follow-ups:** How would you handle it if the engineer pushed back in front of the rest of the team? What would you change in the lab workflow so that instrument setup is verified before every formal scan, not just this one?
