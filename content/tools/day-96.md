## Q1: How would you approach setting up a schematic library in Altium Designer so that symbols stay consistent and traceable across a multi-year medical device program, where the same part may be reused across several board revisions?

**Answer:** The core problem is that a symbol is a long-lived artifact while boards are short-lived, so the library has to be governed as a controlled document set rather than a folder of files people edit ad hoc. I'd start by deciding on a single source of truth — either a managed content server or a version-controlled library repository — and make it read-only to project engineers, with changes going through a review. Each symbol gets a stable internal part number that never changes even if the symbol graphics are revised, so the BOM and any traceability records can reference the part identity independently of the symbol revision.

For consistency, I'd enforce a symbol convention document: grid, pin length, pin naming and numbering, power pin visibility, designator placement, and how multi-part devices are split. The convention matters more than any individual choice in it, because inconsistency is what causes review errors and footprint mismatches. I'd also separate the symbol from the footprint association explicitly — the library part links symbol, footprint, and parameters, and that link is what gets reviewed, not the symbol in isolation.

For traceability, every library part carries parameters that the downstream documentation needs: manufacturer, manufacturer part number, tolerance/grade, temperature rating, and a lifecycle status. When a part is reused on a new board revision, the design references the library part, so a change to the library propagates visibly rather than silently. I'd pair that with a revision history and a rule that obsolete or "do not use" parts are flagged rather than deleted, so old board revisions remain reproducible. Finally, I'd run a periodic library audit — duplicate detection, footprint-symbol pin count checks, and orphaned parts — because libraries decay quietly otherwise.

**Possible follow-ups:** How would you handle a situation where a part needs a symbol change but two released boards already use the old symbol? What parameters would you consider mandatory versus nice-to-have for regulatory traceability?

## Q2: How would you approach setting up a constraint manager in Cadence Allegro for a mixed-signal PCB that has both high-speed digital interfaces and sensitive analog sensor inputs, and how would you verify the constraints are actually being honored?

**Answer:** I'd structure the constraint set by net class rather than by individual net, because a mixed-signal board has too many nets to manage one at a time and class-based rules are what stay maintainable as the design changes. The physical classes would separate the high-speed digital group, the analog front-end group, the power distribution group, and the low-speed housekeeping group. Then the spacing rules become meaningful: analog traces get wider clearance to digital and to switching nodes, and the high-speed group gets its own impedance and length rules.

For the high-speed interfaces, the constraints are impedance targets, differential pair coupling and gap, intra-pair skew, and inter-pair or bus-level length matching where the protocol requires it. For the analog side, the constraints are more about geometry and environment than impedance — keep analog traces short, keep them away from the switching regulator's current loops, and control the reference plane they run over. I'd also set up a region-based rule or a keepout around the analog section so the constraint engine enforces the separation automatically rather than relying on the layout engineer's memory.

Verification is the part people skip. I'd run the constraint-driven DRC and treat violations as blocking, but I'd also do a visual and measurement pass: use the constraint manager's reporting to confirm the actual routed values against targets, check that the return path under each high-speed trace is continuous, and confirm the analog section's plane splits and stitching vias are where the schematic intended. The DRC tells you the rules were met; it doesn't tell you the rules were right, so a design review against the interface specs and the analog requirements is still necessary.

**Possible follow-ups:** How would you decide the impedance target for a differential pair when the silicon vendor's recommendation and the board stackup pull in different directions? What would you do if the fab house comes back saying your stackup can't hit one of your targets?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The tracking generator plus directional coupler gives you a reflection measurement — you're injecting a swept signal and looking at what comes back — and from the reflection coefficient you can derive impedance versus frequency. The setup details dominate the result. I'd calibrate the reference plane at the end of the cable that connects to the board, using open/short/load standards, so the cable and coupler are removed from the measurement. The directional coupler's directivity sets the floor on how small a reflection you can trust, so I'd pick a coupler with directivity well above the return loss I expect to see, and I'd verify the setup by measuring a known load first.

On the device side, I'd be careful about how the front-end is powered and biased during the measurement. An unpowered front-end presents a completely different impedance than a biased one, and if the input is differential, a single-ended reflection measurement only tells you part of the story — I'd either measure each leg against ground with the other leg terminated as it would be in operation, or use a balun and account for its loss and phase. I'd also keep the injected level low enough that I'm not driving the input stage into nonlinearity, because a large-signal reflection measurement of an active input is not the same as the small-signal impedance you'd put in a simulation model.

Deciding whether to trust it: I'd look for consistency across sweeps, check that the result is stable when I wiggle the cable or re-torque the connector, and sanity-check the low-frequency end against a multimeter or LCR measurement where the parasitics are negligible. If the trace shows sharp resonances that move when I touch the probe or cable, that's the fixture talking, not the board. Only after the measurement is repeatable and physically plausible would I use it to adjust a matching network or update a simulation model.

**Possible follow-ups:** How would you separate the front-end's own impedance from the connector and trace parasitics between the calibration plane and the active circuitry? What would a Smith chart look like if the input stage were oscillating, and how would you confirm that's what you're seeing?

## Q4: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The risk with IDE-managed projects is that build settings live in a project file that anyone can change in the GUI, and the resulting binary has no obvious record of how it was produced. For a regulated device, the build configuration is part of the product definition, so I'd treat it that way. First, I'd pin the toolchain version explicitly and record it, because optimization behavior and code generation can change between compiler releases — the same source with the same flags on a different compiler version is a different binary.

Second, I'd make the critical settings explicit and reviewed rather than inherited: optimization level per translation unit or per project, the exact linker script in version control, the startup file in version control, and the memory layout (flash and RAM regions, stack and heap sizing) documented and checked. I'd add a build-time assertion or a post-build check that the map file shows the expected memory regions and that no section overflowed silently. The linker script and startup code should be treated as source, reviewed like source, and never edited only in the IDE.

Third, I'd make the build reproducible and auditable: a scripted or command-line build that produces the same artifacts as the IDE build, with the compiler version, flags, and source revision captured in a build log that gets archived alongside the binary. If the team uses the IDE day to day, that's fine, but the release build should come from the scripted path so there's no ambiguity about which settings were actually used. I'd also lock down or at least flag changes to optimization level, because dropping from a tested level to a different one late in the cycle invalidates the testing that was done.

**Possible follow-ups:** How would you handle a situation where a library vendor only ships precompiled objects built at a different optimization level than your project? What would you check in the map file to confirm the linker script is doing what you intended?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** The first thing I'd do is separate the technical issue from the interpersonal one, because they need different handling and mixing them makes both worse. Technically, the engineer isn't wrong that the peaks show up — a wide resolution bandwidth and a peak detector will find emissions. What they're missing is that the measurement isn't comparable to the limit line: resolution bandwidth affects the measured amplitude of broadband versus narrowband emissions differently, and the detector mode determines whether you're measuring peak, quasi-peak, or average, which the standard specifies for a reason. So the scan they ran is useful for locating sources but not for demonstrating compliance.

I'd explain that distinction concretely rather than just asserting the settings are wrong — show them the standard's requirement, and if there's time, re-run one band with both settings so they can see the amplitude difference themselves. That converts a correction into a learning moment and avoids the dynamic where they feel overruled on a judgment call.

Practically, I'd assess what's recoverable before the booked slot. If the correct settings can be applied and the scan re-run within the lab time, we do that — the pre-scan is fast, and the formal scan is the part that needs to be right. If the lab time genuinely can't accommodate a full re-scan, I'd prioritize: run the corrected scan on the bands most likely to fail, document what was and wasn't covered, and be explicit with the project about the gap rather than letting an incomplete scan masquerade as a complete one. I'd also make sure the engineer isn't blamed in front of the team for a setup error that a checklist should have caught — the fix is a pre-scan setup checklist signed off before lab time is consumed, not a post-mortem on one person.

**Possible follow-ups:** How would you structure that pre-scan checklist so it actually gets used under schedule pressure? If the corrected scan later shows a marginal failure that the quick scan missed, how would you communicate that to the project without undermining the engineer?
