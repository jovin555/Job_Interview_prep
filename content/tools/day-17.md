## Q1: How would you approach setting up a component library management strategy in Altium Designer for a medical device project that needs to maintain strict revision control and regulatory traceability?

**Answer:** For a medical device project, component library management is as much about traceability as it is about design efficiency. I'd start by establishing a single source of truth — a centralized, version-controlled library (whether that's an Altium 365 workspace or a managed local library with Git/SVN backing) so that every engineer on the team is pulling from the same approved components. Each component would have a complete set of parameters: manufacturer part number, datasheet revision, tolerances, ratings, and — critically for medical — a link to the component's approval status and any regulatory documentation. I'd enforce a workflow where components can only be added or modified through a review process, with the library administrator approving changes. For the schematic symbols and PCB footprints, I'd verify that each component has both, and that the pin mapping between them is checked programmatically where possible. I'd also maintain a separate "restricted" or "preferred" parts list that reflects the approved components for the project, so engineers aren't tempted to pull in unvetted parts. Finally, I'd make sure the library itself is backed up and that the revision history is preserved — in a medical device context, you may need to demonstrate years later exactly which component revision was used in a given production batch, so the library revision needs to be traceable to the BOM and the design release.

## Q2: Walk me through your approach to using a spectrum analyzer with a near-field probe to identify whether a radiated emissions failure at 80 MHz is coming from a switching regulator or a digital clock, and how you would confirm your hypothesis.

**Answer:** The first step is to establish a baseline — I'd set up the spectrum analyzer with the appropriate resolution bandwidth (typically 120 kHz for CISPR quasi-peak measurements, though for pre-compliance sniffing I might start wider to catch the signal) and use the near-field probe to scan the board systematically, mapping where the 80 MHz energy is strongest. The key differentiator between a switching regulator and a digital clock is the nature of the emission: a switching regulator will typically show a fundamental at its switching frequency with harmonics that roll off in amplitude, and the emission may be modulated by the load current. A digital clock will show a fundamental at the clock frequency with a characteristic harmonic series, and the emission will be present regardless of load. To isolate the source, I'd first identify the physical location of maximum field strength — if it's near the regulator's inductor or switching node, that's a strong hint. Then I'd use a current probe or a differential near-field probe to look at the actual signal content. A more definitive test is to temporarily disable or change the operating mode: if I can switch the regulator to a different frequency or shut it down, and the 80 MHz emission disappears, that confirms it. Similarly, if I can gate the clock or change its frequency slightly, I can see if the emission tracks. I'd also look at the spectral signature — a clock will typically have very narrow, stable peaks, while a switching regulator's emissions may be broader or have sidebands from the control loop. Once I've identified the source, I'd look at the coupling path: is it conducted through the power plane, radiated directly from a trace, or coupled onto a cable? That determines whether the fix is a layout change, a ferrite, improved filtering, or a shielding approach.

**Possible follow-ups:**
- How would you distinguish between the fundamental and a harmonic of a lower-frequency signal?
- What near-field probe types would you use for this investigation, and why?

## Q3: How would you approach setting up a Zephyr RTOS project using the west build system to support both a production build and a development build with different sensor configurations, where the development build includes additional debug logging and a mock sensor driver, without maintaining two separate codebases?

**Answer:** The key is to use Zephyr's Kconfig and devicetree overlay system to handle the differences between builds, rather than maintaining separate codebases. I'd structure the project so that the core application code is shared, and the differences are expressed through configuration. For the sensor configuration, I'd use devicetree overlays — the production build would use the real sensor node with its actual I2C or SPI address and register settings, while the development build would use an overlay that replaces the sensor node with a mock or simulated device. This could be done by having a common devicetree file for the board, and then separate overlay files for production and development. For the debug logging, I'd use Kconfig options — enabling `CONFIG_LOG` and setting the appropriate log levels for development, while keeping logging minimal or disabled in production. The mock sensor driver would be selected via Kconfig as well, so the build system picks the right driver implementation based on the configuration. In terms of west, I'd set up the `west.yml` manifest to point to the same application code, but I'd create two build configurations — either as two separate build directories with different CMake cache entries, or using a CMake preset or a custom script that sets the appropriate `-DOVERLAY_CONFIG` and `-DDTC_OVERLAY_FILE` flags. The important thing is that the production and development builds are both built from the same source tree, so there's no risk of code divergence. I'd also add a CI check that builds both configurations to ensure the shared code remains compatible with both.

**Possible follow-ups:**
- How would you ensure that the mock sensor driver doesn't accidentally get included in a production build?
- How would you handle a situation where the production and development builds need different device tree nodes for the same peripheral?

## Q4: (Behavioral) Imagine you are leading a design review for a medical device PCB, and you discover that the firmware team has been using a different version of the SPI protocol than what the hardware actually implements — the firmware is expecting a specific clock polarity and phase (CPOL=0, CPHA=0), but the hardware's SPI peripheral is configured for CPOL=1, CPHA=1. The integration testing is scheduled to start in two days, and both teams are confident their implementation is correct. How would you handle this situation?

**Answer:** The first thing I'd do is not assign blame — the goal is to get to a correct, working system, not to determine whose fault it is. I'd call a short, focused meeting with both the firmware and hardware leads, and I'd bring the actual schematic and the SPI peripheral datasheet. The key is to establish ground truth from the hardware: what does the hardware actually implement? I'd look at the SPI peripheral's configuration pins or register settings on the schematic, and I'd verify the clock polarity and phase against the sensor's datasheet requirements. If the hardware is truly configured for CPOL=1, CPHA=1, and the sensor requires that, then the firmware needs to change. If the hardware is configurable via strapping pins or firmware registers, then the question is which configuration is correct for the sensor — and that's determined by the sensor's datasheet, not by either team's preference. Once we've established the correct configuration, I'd work with the firmware team to make the change — it's a small fix, typically just a register setting, so it shouldn't take more than a few hours. I'd also have them verify the change on the actual hardware with a logic analyzer to confirm the SPI signals match the expected timing. In parallel, I'd review the hardware configuration to see if there's a way to make it match the firmware without a board change — if the SPI mode is set by a strapping resistor, for example, it might be possible to change that. The key is to make the decision based on the sensor's requirements, not on either team's confidence, and to document the resolution so it doesn't recur. I'd also use this as a learning opportunity — I'd suggest adding a pre-integration check where the firmware and hardware teams compare their interface assumptions before integration testing begins.

**Possible follow-ups:**
- How would you handle the situation if the firmware team insists that changing the SPI mode will break other functionality?
- What documentation or process changes would you propose to prevent this type of mismatch in future projects?

## Q5: How would you approach using a logic analyzer to debug a CAN-FD bus where a node intermittently enters bus-off state after several hours of operation, but only when the system is under vibration?

**Answer:** This is a classic intermittent fault that requires a systematic approach. The first thing I'd do is set up the logic analyzer to capture the CAN-FD bus continuously, with a deep buffer and triggering on the error frames or the bus-off condition. I'd configure the analyzer to decode CAN-FD frames and to capture error frames specifically — the CAN protocol has error frames that indicate what type of error occurred (bit error, stuff error, CRC error, form error, acknowledgment error). The type of error will tell me a lot about the root cause. For example, if I'm seeing bit errors, that suggests a signal integrity issue — possibly a marginal connection that's intermittent under vibration. If I'm seeing CRC errors, that could indicate corruption during transmission. I'd also capture the bus timing — the bit timing, the sample point, and whether the errors correlate with specific nodes or specific message IDs. Since the issue is vibration-related, I'd try to reproduce it in a controlled way — perhaps using a vibration table or even just tapping on the connector or harness while monitoring the bus. The goal is to capture the error frames and correlate them with the physical disturbance. Once I have the error data, I'd look at the physical layer: check the connector contacts, the termination resistors, the cable shielding, and the ground integrity. A common cause of vibration-induced CAN issues is a marginal connector or a cold solder joint on the transceiver or termination. I'd also check the CAN transceiver's common-mode voltage and the bus bias — under vibration, a marginal connection could cause the bus to drift out of spec. If the errors are bit errors at a specific node, I might suspect that node's transceiver or its connection to the bus. I'd also look at the CAN-FD bit timing — if the sample point is marginal, vibration-induced jitter could push it over the edge. The fix might be as simple as adjusting the sample point, improving the connector, or adding strain relief to the harness.

**Possible follow-ups:**
- How would you distinguish between a physical layer issue and a protocol layer issue from the logic analyzer data?
- What specific logic analyzer settings would you use to capture the error frames reliably over several hours?
