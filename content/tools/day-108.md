## Q1: How would you approach setting up a differential pair routing constraint in Cadence Allegro for a USB 2.0 interface on a mixed-signal medical device PCB, and how would you verify the constraints are actually honored in the final layout?

**Answer:** I'd start from the specification rather than from the tool defaults: USB 2.0 high-speed calls for a 90 Ω differential impedance, and the constraint set should encode that as the target, along with a tolerance band (typically ±10%) and a length-matching rule between the D+ and D− of a pair. In Allegro's constraint manager I'd create a differential pair object for the two nets, assign the impedance target and tolerance, set intra-pair skew limits, and add a max-via-count or via-proximity rule if the stackup and reference-plane transitions warrant it. I'd also constrain the pair to a single reference plane where possible, since a pair that crosses a plane split loses its return path and the impedance target becomes meaningless regardless of what the tool reports.

Verification is the part people skip. Defining a constraint doesn't mean the router honored it — I'd run the DRC with the electrical constraint checks enabled, then cross-check the actual routed geometry against the target using the impedance/etch report, and confirm the stackup used in the field solver matches the fabricated stackup (dielectric thickness, copper weight, soldermask). For a medical device I'd also capture the constraint set and the verification report as part of the design record, so the release is auditable rather than "the DRC passed on someone's machine."

**Possible follow-ups:** How would you handle a pair that has to change reference planes mid-route — what would you add to the constraint set? What would you do if the board house's stackup comes back with a different dielectric thickness than you assumed?

## Q2: How would you approach organizing a KiCad project for a medical device so that the schematic, PCB, footprints, and 3D models stay consistent across revisions, and how would you catch footprint-to-schematic mismatches before they reach fabrication?

**Answer:** KiCad's file-based library model is the crux — there's no database enforcing that a symbol and its footprint stay paired, so consistency has to come from process. I'd structure the project with project-local libraries (symbols, footprints, 3D models) checked into version control alongside the schematic and board files, rather than relying on global libraries that drift between machines. Each symbol carries its footprint assignment as a field, and each footprint carries a 3D model path relative to the project so the model travels with the repo. Naming conventions matter: a part number in the symbol, footprint, and 3D model should be traceable to the same source, so a reviewer can confirm the trio matches.

For catching mismatches before fabrication, I'd lean on the tool's own checks first — ERC for electrical issues, DRC for footprint/pad-level issues, and the "update PCB from schematic" comparison to surface any symbol-to-footprint assignment changes. Then a manual cross-check: a footprint-to-schematic audit where I compare pad counts, pin numbering, and package dimensions against the datasheet for every new or changed part, plus a 3D model overlay to catch a footprint that's the right pin count but the wrong body size. For a medical device I'd make that audit a documented step in the release checklist, not an informal glance.

**Possible follow-ups:** How would you handle a part that exists in two package variants in the same design — same symbol, different footprints? What's your approach when a footprint from a vendor library doesn't match the datasheet?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The tracking generator plus directional coupler gives you a reflection measurement — the coupler samples the reflected signal, and the analyzer displays return loss across frequency. The setup details determine whether the number means anything: I'd calibrate the reference plane at the coupler's measurement port (open/short/load, or a known standard) so the cable and connector losses are removed, set the resolution bandwidth and sweep to match the frequency range of interest, and make sure the drive level is low enough not to push the front-end's input stage into nonlinearity — a front-end characterized at a level it never sees in operation tells you little. The directional coupler's directivity sets the floor on how small a reflection you can trust; if the return loss you're measuring is near the coupler's directivity limit, the reading is suspect.

Deciding whether to act on it comes down to repeatability and sanity checks: repeat the measurement, swap in a known load to confirm the setup reads what it should, and compare against the expected impedance from the front-end's input network. If the measured return loss is poor but the circuit's topology and component values predict a good match, I'd suspect the fixture or the reference plane before I'd suspect the design. I'd also check whether the result is stable across sweeps and connector reseats — a measurement that moves when you touch the cable isn't a measurement yet.

**Possible follow-ups:** How would you extend this to a differential front-end input? What would you do if the coupler's directivity limited your ability to resolve a small reflection?

## Q4: How would you approach configuring a Segger J-Link's RTT (Real-Time Transfer) logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?

**Answer:** RTT is attractive here precisely because it doesn't consume a UART — it uses the debug probe's memory-access channel to read a ring buffer the target writes to, so the safety-critical UART stays untouched. The setup is: enable RTT support in the Zephyr configuration, allocate the RTT control block and buffers in the target's memory (with the buffer sized deliberately — too small and you drop messages, too large and you waste RAM), and point the J-Link software at the control block so the host can read it. On the host side I'd use the RTT viewer or a scripted client so the logging is captured to a file for later analysis rather than watched live.

The timing concern is real: RTT writes are fast but not free, and if the target blocks when the buffer fills, you've turned logging into a timing perturbation. I'd configure the target side to be non-blocking — drop or overwrite on overflow rather than stall the producer — and keep the log volume low enough that overflow is rare in normal operation. I'd also be careful about where logging is called from: logging inside a high-priority ISR or a tight control loop changes the timing of the very thing you're trying to observe. The test is to measure the loop's timing with logging on versus off and confirm the difference is within the budget the safety-critical path can tolerate; if it isn't, the logging moves to a lower-priority context or gets gated behind a debug build.

**Possible follow-ups:** How would you detect that the RTT buffer overflowed and you lost messages? What's your approach if the debug probe's memory access itself disturbs the target's cache or timing?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the Altium Designer output job configuration for a medical device PCB release, and you discover the fabrication outputs are missing the drill table and the assembly drawings reference an outdated revision of the schematic. The board house is expecting the files tomorrow, and the engineer is confident the outputs are complete because "the Gerbers look fine." How would you handle this situation?

**Answer:** First I'd separate the immediate problem from the process problem. The immediate problem is that the release package is incomplete and partly wrong, and the board house is expecting it tomorrow — so the priority is to regenerate a correct package, not to debate whose fault it is. I'd sit down with the engineer and walk through the output job together: confirm the drill table is included in the fabrication outputs, confirm the assembly drawings are generated from the current schematic revision rather than a cached one, and regenerate the whole package from the current design state. Then I'd verify it myself against a checklist before it goes out — Gerbers, drill files, drill table, assembly drawings, BOM, and a revision cross-check — because "the Gerbers look fine" is exactly the kind of confidence that misses the drill table.

The process problem is that the output job wasn't validated against a release checklist, and the engineer's confidence wasn't backed by a verification step. I'd address that without making it personal: the fix is a documented release checklist and a second-pair-of-eyes review before any package leaves, plus making sure the output job configuration itself is version-controlled so it can't silently drift. I'd frame it to the engineer as "the checklist catches what any of us would miss on a bad day," not as a reprimand — the goal is a repeatable release process, and one missed drill table is a cheap lesson compared to one that reaches fabrication.

**Possible follow-ups:** How would you structure the release checklist so it's fast enough that people actually use it? What would you do if the board house had already started fabrication on the incomplete package?
