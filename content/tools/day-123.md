## Q1: How would you approach setting up a Zephyr RTOS project using the west build system so that the same source tree produces both a production image and a debug image with extra logging and assertions, without maintaining two separate trees?

**Answer:** The cleanest way is to treat the difference as configuration, not code. In Zephyr, that means leaning on Kconfig and devicetree overlays rather than `#ifdef` blocks scattered through the application. I'd define a board-level or application-level Kconfig symbol — something like `CONFIG_APP_DEBUG_IMAGE` — that selects a bundle of related options: log level, assertion behavior, stack sentinel, thread analyzer, and any debug-only shell commands. The production image is built with that symbol off; the debug image turns it on.

For the build side, west makes this straightforward with build directories. Each variant gets its own build directory (`west build -d build/prod` and `west build -d build/debug`), and I'd drive the variant selection through a `-DEXTRA_CONF_FILE` pointing at a `debug.conf` overlay, or through a small wrapper script or CMake preset that pins the exact flags. The key discipline is that the *source* is identical — only the configuration inputs differ. That keeps the debug image honest: you're testing the same code paths, just with more instrumentation enabled.

I'd also make sure the debug image doesn't silently diverge in ways that mask production bugs. For example, if debug logging changes timing enough to hide a race, that's a signal the production image needs its own observability story (RTT, trace, counters). So I'd keep the debug image as a diagnostic tool, not as the thing you ship, and I'd document exactly which Kconfig symbols differ between the two so a reviewer can see the delta at a glance.

- How would you prevent someone from accidentally shipping the debug image, given that both come from the same tree?
- Where would you put the shared configuration so that a new board variant inherits the right defaults without copy-paste?

## Q2: How would you approach setting up a differential pair routing constraint in Cadence Allegro for a USB 2.0 interface on a mixed-signal medical device PCB, and how would you verify the constraints are actually honored in the final layout?

**Answer:** I'd start from the specification, not the tool. USB 2.0 full-speed/high-speed differential pairs have a target differential impedance (90 Ω nominal for the pair), plus limits on intra-pair skew and, for high-speed, inter-pair matching where it matters. Those numbers go into the constraint manager as a named electrical constraint set — differential impedance target with tolerance, max intra-pair skew, and any max uncoupled length — and then that set is assigned to the physical differential pair class. I'd also define the physical rules: trace width and gap derived from the stackup, so the impedance target and the geometry are consistent rather than guessed independently.

The important part is that the constraint set is *assigned*, not just *defined*. A common failure is having a beautiful constraint set that no net class actually references. So I'd verify by running the constraint-driven routing checks and the DRC, then cross-checking the actual routed geometry: measure the as-routed differential impedance from the stackup, confirm the pair stays coupled through the connector and any via transitions, and check that the skew report is within limits. I'd also eyeball the return path — a differential pair that's perfectly matched but crosses a plane split is still a problem.

For a mixed-signal medical board, I'd add one more layer: keep the USB pair physically separated from sensitive analog traces and make sure the pair's reference plane is continuous under it. The constraint manager can enforce spacing to other classes, but the plane continuity is a layout-review item, not something DRC will fully catch.

**Possible follow-ups:**
- How would you handle the impedance target if the board stackup changes late in the design?
- What would you check if the DRC passes but the eye diagram at the connector still looks marginal?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The tracking generator plus directional coupler gives you a reflection measurement: the coupler samples the reflected signal, and the analyzer displays return loss versus frequency. From return loss you can derive the reflection coefficient and, with a reference impedance, estimate the input impedance across the band of interest. The setup matters as much as the math — I'd calibrate out the test setup first, using a short/open/load (or the analyzer's built-in calibration routine) at the reference plane where the front-end connects, so cable and coupler losses don't masquerade as device behavior.

Trustworthiness is the real question. A few things I'd check before acting on the result: Is the calibration reference plane actually at the connector, or did I calibrate at the analyzer and then add a cable? Is the coupler's directivity adequate for the return-loss range I'm measuring — a coupler with poor directivity will floor the measurement and make a good match look bad? Is the front-end powered and biased in its normal operating state, or am I measuring an unpowered input that behaves completely differently? And is the sweep slow enough and the resolution bandwidth narrow enough that I'm not looking at noise?

I'd also sanity-check against a known reference — measure a resistor of known value or a characterized load and confirm the setup reports what it should. If the measurement disagrees with a simple DC or low-frequency check, I trust the simpler measurement and investigate the setup. The decision to act comes only after the measurement is repeatable, calibrated at the right plane, and consistent with an independent check.

**Possible follow-ups:**
- How would you interpret a return-loss plot that looks fine at low frequency but degrades sharply above a certain point?
- What would you do if the coupler you have on hand has marginal directivity for the frequency range you care about?

## Q4: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is that a build is reproducible and that the settings that affect behavior are visible and version-controlled, not buried in a project file someone edited by hand. In Keil, that means treating the project file itself as a reviewed artifact and pinning the settings explicitly: optimization level set deliberately (and documented — for a medical device, `-O0` or a specific `-O` level chosen for traceability and debug correlation, not left at whatever a template inherited), the linker script referenced by an explicit path in the project rather than a default, and the startup file and scatter file both under version control alongside the source.

I'd also make the build auditable by capturing the exact toolchain version and the full set of compiler/linker flags in the build log, and by keeping the project file in the repo so a diff shows any change to optimization or memory layout. For a regulated device, the build configuration is part of the design history — if the optimization level changes between the tested build and the shipped build, that's a finding waiting to happen. So I'd lock it: a documented build procedure, a checked-in project file, and a review step that flags any change to optimization, linker script, or startup code as a configuration change requiring justification.

One more thing: I'd verify the lock actually holds by building from a clean checkout on a different machine and comparing the output — if the binary differs, something in the environment or the project file isn't pinned.

**Possible follow-ups:**
- How would you detect that someone changed the optimization level without updating the documentation?
- What's the risk of building the tested firmware at one optimization level and the production firmware at another?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** First, I'd separate the technical issue from the interpersonal one. Technically, the engineer isn't wrong that peaks show up — the problem is that the *amplitude* and the *decision* depend on RBW and detector. A quasi-peak detector and a peak detector can give very different readings against a limit line, and an RBW that's too wide smears the spectrum and understates narrowband emissions. So "the peaks show up" isn't the criterion; "the measurement matches what the standard requires" is.

I'd sit down with the engineer and walk through *why* the settings matter, using the standard as the authority rather than my opinion — show the clause that specifies RBW and detector for the frequency range, and demonstrate the difference on a known signal if there's time. The goal is that they understand the reasoning, not just that they change the setting. That's how you build judgment rather than compliance.

On logistics: the formal scan is tomorrow and the lab is booked, so I'd treat this as a recoverable situation rather than a crisis. Re-running the scan with correct settings is the priority; if the booked time is insufficient, I'd escalate early to see whether the slot can be extended or a second slot found, and I'd be transparent with the project lead about why. I would not let a scan with wrong settings stand in for a formal result — that's a regulatory and safety issue, not a scheduling inconvenience. And afterward, I'd add a pre-scan checklist to the lab procedure so the settings are verified before anyone starts, which prevents the same conversation next time.

**Possible follow-ups:**
- How would you handle it if the engineer felt you were second-guessing them in front of the team?
- What would you put on a pre-scan checklist to catch this class of error before it costs lab time?
