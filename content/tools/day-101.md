## Q1: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** I'd start by treating the decoder as a formal specification exercise rather than a configuration exercise. First, I'd capture a long, known-good transaction and manually annotate it against the protocol document — identifying the exact bit positions of the header, the sync pattern, the payload, and the checksum. The key insight with non-byte-aligned framing is that you can't rely on the analyzer's default "start on byte boundary" assumption, so I'd look for a decoder framework that lets me define a state machine with explicit bit-level transitions: idle → hunting for sync → header → payload → CRC → idle. Many logic analyzers support a "custom" or "generic" decoder plugin (or a scripting interface like a Python/Lua extension) where you can express this as a small state machine rather than a fixed frame template.

The practical steps: (1) define the sync word and decide whether to trigger on it or hunt for it in software post-capture; (2) set the sample rate high enough that you're oversampling the fastest edge by at least 5–10×, since bit-level decoding is unforgiving of aliasing; (3) build the decoder incrementally — first just detect and highlight the sync word, verify it lands where you expect on a known capture, then add header fields, then payload, then checksum validation; (4) validate the decoder against a capture where you already know the answer from firmware-side logging or a known stimulus. A decoder that "looks plausible" but hasn't been checked against ground truth is worse than no decoder, because it creates false confidence.

For a medical device specifically, I'd also document the decoder definition and version it alongside the protocol spec, so that when the protocol revs, the decoder revs with it and there's traceability.

**Possible follow-ups:** How would you handle a protocol where the payload length is itself encoded in a variable-length header field — how does that change your state machine design? What would you do if the decoder works on bench captures but produces garbage when the bus is heavily loaded?

## Q2: How would you approach setting up a power integrity simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?

**Answer:** I'd structure this as a layered workflow, because PI simulation on a shared PDN is really two problems: the DC/IR-drop and current-density problem, and the AC impedance problem. For the DC side, I'd extract the copper geometry from the layout (stackup, plane shapes, via count) and run an IR-drop/current-density analysis to confirm the analog front-end isn't sitting at the end of a long, thin trace carrying the regulator's return current. That's usually the first thing that bites you — a shared ground return path where the switching current develops a voltage drop right under the sensitive analog section.

For the AC side, I'd build an impedance profile of the PDN as seen from the analog front-end's supply pins, from DC up to a few hundred MHz, and check it against the regulator's control loop bandwidth and the analog front-end's power-supply rejection. The goal is to make sure there's no anti-resonance peak between the bulk caps, the regulator's output cap, and the decoupling network that lands in a band where the analog front-end has poor PSRR. I'd also run a noise-coupling simulation — injecting a current step at the regulator's switching node and observing what appears at the analog supply — to see whether the decoupling and ferrite/LC filtering actually attenuate it.

On trustworthiness: I'd only act on results that (a) use a stackup and material properties I've verified against the actual fab drawing, not defaults; (b) include the real component models — capacitor ESR/ESL from the manufacturer's data, not ideal caps; and (c) show convergence when I refine the mesh or extend the frequency range. If a resonance peak moves significantly when I tighten the mesh, it's a numerical artifact, not a design problem. I'd also cross-check the simulation against a bench measurement — a VNA measurement of PDN impedance at the analog supply pins, or a scope measurement of ripple with the regulator switching — before committing to a layout change. The simulation tells you where to look; the measurement tells you whether you're right.

**Possible follow-ups:** How would you decide whether to fix a PDN resonance with layout changes versus adding a damping component, and what are the trade-offs? What's your approach when the simulation says the PDN is fine but the bench shows excessive ripple at the analog supply?

## Q3: How would you approach setting up a cross-probe workflow between OrCAD Capture and Cadence Allegro so a layout review can move efficiently between schematic and PCB, and what would you check to confirm the link actually works before relying on it in a review?

**Answer:** The cross-probe link between Capture and Allegro is one of those things that's either invisible and reliable or silently broken, so I'd treat "confirm it works" as a deliberate pre-review step rather than assuming it. The setup itself is mostly about ensuring both tools are pointed at the same design database and that the cross-probe service is enabled and communicating — typically a shared session or a running cross-probe server that both applications register with. I'd verify the netlist and design are in sync first, because cross-probing a stale netlist against a newer layout will highlight the wrong thing and erode trust in the tool during the review.

To confirm it actually works before the review, I'd do a small, unambiguous test: pick a component with a distinctive reference designator — something that appears exactly once and is easy to spot — select it in Capture, and confirm Allegro highlights the correct footprint and zooms to it. Then reverse it: select a net or component in Allegro and confirm Capture highlights the corresponding symbol and pin. I'd test both a component-level and a net-level probe, because they can fail independently. I'd also test it on a second monitor or with the review's actual display setup, since cross-probe behavior can depend on window focus and workspace configuration.

The reason I'm pedantic about this: in a live design review with several people, a broken cross-probe wastes everyone's time and, worse, can cause the team to review the wrong net. If it's not working, I'd rather know five minutes before the review and fall back to manual reference-designator lookup than discover it mid-review.

**Possible follow-ups:** What would you do if cross-probe works for components but not for nets — where would you look first? How would you handle a review where the schematic and layout are on different machines or different users' sessions?

## Q4: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The core principle is that the build configuration is a controlled artifact, not a set of IDE checkboxes that anyone can flip. I'd start by treating the project file itself as source — checked into version control, reviewed like code, and diffed on every change — and then make the critical settings explicit and documented rather than inherited from a template or a previous project.

For optimization level: I'd pin it per build target (debug vs. release) and document why. Debug builds typically use `-O0` or `-Og` for debuggability; release builds use a specific optimization level that's been validated. The trap is that optimization level can change behavior — timing, volatile access ordering, removal of "unused" code that was actually doing something — so the release optimization level needs to be the one that was actually tested, not a last-minute switch. I'd also make sure the optimization setting is visible in the build log or a generated build-info artifact, so there's no ambiguity about what was compiled.

For the linker script and startup code: these should be version-controlled files in the project, not IDE-generated defaults, and the project should reference them by relative path so the build is reproducible on another machine. I'd review the memory map explicitly — flash and RAM regions, stack and heap placement, any reserved regions for calibration data or bootloader — because a wrong memory layout can silently corrupt data. The startup code should be reviewed for the correct vector table, clock initialization, and any safety-critical early initialization.

For auditability: I'd generate a build manifest — compiler version, optimization flags, linker script hash, source revision — as part of the build, and archive it with the binary. That's what makes the build defensible later when someone asks "what exactly went into this firmware image." I'd also set up a clean-build check in CI so that the build doesn't depend on stale object files or a particular developer's local IDE state.

**Possible follow-ups:** How would you catch a situation where someone changed the optimization level locally but the committed project file still shows the old value? What's your approach to validating that the linker script's memory layout matches the actual hardware?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** First, I'd separate the technical issue from the interpersonal one, because they need different handling and conflating them makes both worse. Technically, the engineer isn't wrong that the peaks show up — the problem is that RBW and detector mode affect the *amplitude* you read, not just whether you see a peak. A wide RBW and a peak detector can overstate or understate emissions relative to what the standard's specified settings would show, so a scan done with the wrong settings isn't a conservative estimate — it's an uncalibrated one. That's the point I'd make, and I'd make it concretely: show the same emission measured with the correct RBW/detector versus the current settings, so the difference is visible rather than asserted. People change their minds faster when they can see the delta.

Interpersonally, I'd avoid framing it as "you did it wrong." The engineer set up a quick scan, which is a reasonable thing to do when you're getting oriented — the mistake is treating a quick scan as a formal one. I'd acknowledge that and redirect: "This was the right instinct for a first look; now we need to re-run with the standard's settings before we trust the numbers." That keeps the engineer engaged rather than defensive, and it's also true.

Practically, with the formal scan tomorrow and lab time booked: I'd check whether the correct settings can be applied and the scan re-run within the booked window — often a re-scan with proper settings is not much longer than the original if the setup is already in place. If the booked time genuinely isn't enough, I'd escalate early to see whether the lab slot can be extended or whether a subset of the scan (the critical frequency bands) can be re-run properly and the rest deferred. What I would not do is let the formal scan proceed with settings I know are wrong and hope the peaks "show up either way" — that's exactly the kind of shortcut that produces a result you can't defend later. I'd also use it as a coaching moment: document the required settings in the lab procedure so the next person doesn't have to rediscover them.

**Possible follow-ups:** How would you handle it if the engineer pushed back and said the standard's settings are "overly conservative" and the quick scan is more representative of real-world behavior? What would you put in place so this doesn't recur on the next pre-compliance scan?
