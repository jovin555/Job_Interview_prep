## Q1: How would you approach setting up a via structure strategy in Cadence Allegro for a mixed-signal medical device PCB that carries both high-speed digital signals and sensitive analog traces, and how would you verify that the vias don't compromise signal integrity or manufacturability?

**Answer:** I'd start by classifying the nets into tiers — high-speed digital (USB, SPI, clock lines), sensitive analog (sensor front-ends, reference voltages), power/ground, and low-speed control — because the via strategy should follow the signal class, not be applied uniformly. For high-speed digital, I'd define a preferred via geometry (drill size, pad size, antipad) that keeps the via stub short relative to the signal's rise time; on a thick board, that may mean blind or back-drilled vias for the fastest nets, though I'd weigh that against fabrication cost and whether the stackup can support it. For sensitive analog, the priority is usually continuity of the return path and avoiding via-induced discontinuities near the front-end, so I'd often keep analog routing on a single layer where possible and use ground-referenced vias with a nearby stitching via to keep the return current local. For power, I'd use multiple vias per net to reduce inductance and thermal resistance. I'd encode these as via classes in the Allegro constraint manager so the router and DRC enforce them automatically rather than relying on manual discipline. Verification is two-part: a post-route check that the constraint manager reports no via-class violations, and a signal-integrity pass — either in Allegro's SI tool or an external solver — looking at impedance discontinuity and return-path continuity on the critical nets. I'd also sanity-check the via drill-to-pad ratio and annular ring against the fab house's capability before release, since a via strategy that's electrically elegant but outside the fab's process window is useless.

**Possible follow-ups:** How would you decide when back-drilling is worth the cost versus just accepting the stub on a given net class? How would you handle a case where the analog and digital sections need to share a via field because of connector placement?

## Q2: How would you approach organizing a KiCad project for a medical device so that the schematic, PCB, footprints, and 3D models stay consistent across revisions, and how would you catch footprint-to-schematic mismatches before they reach fabrication?

**Answer:** The core problem in KiCad is that it's file-based rather than database-driven, so consistency has to be enforced by convention and tooling rather than by a central library server. I'd structure the project so that project-specific symbols and footprints live inside the project directory (or a project-local library) rather than in a shared global library, so a checkout is self-contained and a revision is reproducible. I'd keep a clear naming convention tying symbol names to footprint names, and I'd use KiCad's footprint assignment field deliberately rather than letting it drift. For 3D models, I'd store them relative to the project and verify the path references resolve on a clean checkout, since broken 3D links are a common silent failure. The real safety net is running ERC and DRC as a gate, not an afterthought — ERC catches unconnected pins, power flags, and pin-type conflicts; DRC catches clearance, courtyard, and unconnected-net issues. Beyond that, I'd do a footprint-to-schematic cross-check: generate the netlist and BOM from the schematic, then verify against the PCB's footprint assignments, and specifically check that every schematic symbol's assigned footprint actually exists in the library and matches the intended package. For a medical device, I'd also freeze a released revision as a tagged commit and archive the exact library state, because "the footprint changed in the shared library" is a classic way for a previously-verified design to silently become unverified.

**Possible follow-ups:** How would you handle a situation where a footprint in the project library was edited after a board was fabricated — how do you know which revision used which footprint? What's your approach to migrating a project from a global library to a project-local one without breaking existing references?

## Q3: How would you approach using a mixed-signal oscilloscope to measure the noise on a precision analog sensor output when a switching regulator on the same board is active, and how would you separate real sensor noise from measurement artifacts introduced by your probing?

**Answer:** The first principle is that the probe is part of the circuit, so I'd start by minimizing what the probe itself injects. That means using a short ground lead or, better, a ground spring directly at the tip, keeping the probe loop area small, and using a 1x probe only if the signal can tolerate the added capacitance — otherwise a 10x or active probe to reduce loading. I'd set the scope to AC coupling with a bandwidth limit appropriate to the noise I'm hunting, and I'd use averaging or a low-noise front end if the scope supports it, while being careful that averaging hides non-periodic noise. To separate real noise from artifacts, I'd do a controlled comparison: measure the sensor output with the regulator disabled (if the design allows it) and again with it enabled, keeping everything else identical. If the noise appears only with the regulator on, that's a strong signal it's real coupling. I'd also move the probe ground reference point around — if the measured noise changes dramatically with ground placement, I'm likely seeing a ground-loop or common-mode artifact rather than the sensor's actual output noise. Finally, I'd correlate in the frequency domain: a switching regulator's noise tends to appear at its switching frequency and harmonics, so a scope FFT or a spectrum analyzer view helps confirm the source. The discipline is to never trust a single measurement — vary the probe, the ground, and the operating condition, and only believe the noise that survives all of them.

**Possible follow-ups:** How would you distinguish conducted noise on the supply rail from radiated coupling into the sensor trace? If the noise disappears when you touch the probe ground to a different point, what does that tell you?

## Q4: How would you approach configuring a Segger J-Link for automated firmware testing on a Zephyr RTOS target, where the test harness needs to flash the device, run a test sequence, and capture a crash dump without manual intervention — and what are the failure modes you'd design around?

**Answer:** I'd build this around J-Link's command-line tooling and scripting rather than the GUI, so the whole flow is reproducible and CI-friendly. The sequence is roughly: reset and halt the target, flash the image, reset and run, then either poll for a completion signal or wait a bounded time, and on failure capture the target state. For crash capture, the key is that the debugger can read memory and registers even when the CPU is in a fault state, so I'd script a halt-on-fault or a post-mortem read of the fault status registers and the relevant RAM regions, then dump that to a file the test harness can parse. The failure modes I'd design around: the target not being detected (wrong interface speed, SWD vs JTAG mismatch, or the debug pins repurposed by firmware), the flash operation succeeding but the target not actually running (reset strategy mismatch), the test hanging so the harness waits forever (so every step needs a timeout), and the crash dump being incomplete because the fault handler overwrote the state I needed. I'd also make the harness idempotent — it should be safe to re-run after a failure without manual cleanup — and I'd log the J-Link session output so a failure can be diagnosed after the fact. For a medical device, I'd keep the automated flow strictly separate from any safety-critical release process, so a test-harness bug can't accidentally ship a non-production image.

**Possible follow-ups:** How would you capture a crash dump if the firmware's fault handler itself is what's crashing? What's your approach to making the flash-and-run step reliable when the target sometimes fails to enumerate on the debug interface?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the Altium Designer output job configuration for a medical device PCB release, and you discover the fabrication outputs are missing the drill table and the assembly drawings reference an outdated revision of the schematic. The board house is expecting the files tomorrow, and the engineer is confident the outputs are complete because "the Gerbers look fine." How would you handle this situation?

**Answer:** First, I'd separate the immediate problem from the process problem. The immediate issue is that we're about to send an incomplete release package to a board house on a deadline, so the priority is to verify exactly what's missing and whether it's fixable in time. I'd sit down with the engineer and walk through the output job together rather than just correcting it myself — partly because two sets of eyes catch more, and partly because the goal is that this doesn't happen again. I'd check the output job against a release checklist: Gerbers, drill files and drill table, assembly drawings tied to the correct schematic revision, BOM, and any fabrication notes. If the drill table is simply a missing output in the job, that's a quick fix; if the assembly drawings reference an outdated schematic, that's more serious because it suggests a revision-control gap, and I'd want to understand how the drawings were generated before trusting anything else in the package. On the people side, I'd be direct but not punitive — the engineer isn't wrong that the Gerbers look fine, they just haven't been given a clear definition of what "complete" means for a release. I'd frame it as a gap in our process, not a personal failure, and then close that gap by making the release checklist explicit and adding a second-person review step before anything goes to fabrication. If the deadline genuinely can't be met with a correct package, I'd rather tell the board house we need a short extension than ship an incomplete release — a wrong or incomplete fab package on a medical device is a much more expensive problem than a one-day delay.

**Possible follow-ups:** How would you decide whether the outdated assembly drawings indicate a deeper revision-control problem that needs a broader review? How would you structure the release checklist so it's actually used rather than ignored under deadline pressure?
