# tools — Day 111

## Q1: How would you approach setting up a Git repository for a hardware project where the PCB source files are binary and don't diff meaningfully, so that design reviews and revision history stay usable?

**Answer:** The core problem is that binary CAD files defeat Git's line-based diffing, so you have to build the review workflow around artifacts rather than around the source file itself. My approach would be layered. First, treat the native project files as the source of truth but never rely on reading a diff of them — instead, generate human-readable derivatives at each commit: a netlist export, a BOM export, a PDF of the schematic, and a PDF or image set of the layout layers. Those derivatives are text or at least viewable, so a reviewer can compare revision N against N-1 meaningfully. Second, enforce a commit discipline: one logical change per commit, with a message that states what changed and why, and tag every commit that corresponds to a fabrication release or a design review milestone. Third, use a `.gitattributes` policy to mark binary CAD files so Git doesn't attempt text merging on them, and decide explicitly whether to use file locking (Git LFS with locking, or a server-side lock) so two engineers can't silently overwrite each other's layout work — for PCB layout, concurrent editing of the same board file is almost always a corruption risk, so locking is usually the right call rather than merge. Fourth, keep the library and the project in the same repository or in a pinned submodule so a checkout reproduces the exact library state used at that revision. The test of whether the setup works is simple: can someone six months later check out a release tag and regenerate the exact fabrication outputs, and can a reviewer see what changed between two tags without opening the CAD tool? If both are yes, the workflow is sound.

**Possible follow-ups:** How would you handle a situation where two engineers genuinely need to work on different areas of the same board simultaneously — is there a partitioning strategy, or is locking the only honest answer? What would you put in the release tag annotation so it's self-describing later?

## Q2: How would you approach configuring a debug probe's scripting interface so that a test harness can flash a target, run a test, and capture a crash dump unattended — and what failure modes would you design around?

**Answer:** I'd start by separating the three phases and making each one independently verifiable, because an unattended harness fails in ways an interactive session never does. For flashing: use the probe's command-line or scripted interface to erase, program, and then verify the image by reading back a checksum or the programmed region — never trust "program succeeded" without a verify step, since a marginal connection can report success on a partial write. For the run phase: reset the target deterministically, wait for a known handshake (a GPIO toggle, a UART banner, or a debug-port memory flag) rather than a fixed sleep, because boot time varies with build configuration and temperature. For crash capture: pre-configure the debugger to halt on fault exceptions and to dump the core registers plus a defined RAM region to a file, so the dump is captured even if the harness's own communication channel is dead. The failure modes I'd design around: probe not enumerated or wrong serial number selected (enumerate and assert the expected probe ID before starting); target held in reset by a stale state (issue an explicit reset-and-halt first); flash protection or readout protection left enabled from a previous run (detect and fail loudly rather than silently); the harness hanging forever because the target never reaches the handshake (hard timeout on every wait, with the timeout itself logged as a distinct failure class, not conflated with a test failure); and power-cycle state — if the fixture controls target power, the script must guarantee a known power state at entry, because a target left powered from the last run will fail the "cold boot" assumption. Finally, every run should leave a log with the probe ID, image checksum, and timestamps, so a flaky result can be traced to a specific fixture and image rather than re-run blindly.

**Possible follow-ups:** How would you distinguish a genuine firmware crash from a harness-induced failure when the only evidence is the captured dump? What would you change if the same harness had to run against several hardware revisions with different memory maps?

## Q3: How would you approach setting up a schematic library so that symbols stay consistent and traceable across a multi-year program where the same part is reused across several board revisions?

**Answer:** The organizing principle is that the library is a controlled document, not a scratchpad, so the setup has to make the correct action the easy one. I'd start with a single authoritative library (or a small set of them, one per category) under version control, with a naming and numbering convention that encodes the part's identity and never gets reused — a retired symbol keeps its identifier forever so old schematics still resolve. Each symbol carries metadata in its parameters: manufacturer part number, a link to the datasheet revision, a lifecycle status (active, NRND, obsolete), and a note on which projects use it. That last field is what makes traceability real — when a part goes obsolete, you can find every design that depends on it. For revision control, the rule is that a released symbol is frozen: if a pin definition or footprint association must change, you create a new revision of the symbol and a new part number, and existing designs either stay on the old revision deliberately or are migrated with a documented change. Silently editing a symbol that's already in released schematics is how you get a board that doesn't match its documentation. I'd also enforce a review gate: no new symbol enters the library without a second pair of eyes checking pin numbering against the datasheet, footprint pad assignment against the package drawing, and the polarity/orientation of anything that can be installed backwards. The verification that the system is working is a periodic audit — pick a released board, walk its BOM back to library entries, and confirm every symbol still resolves and every footprint matches the physical part.

**Possible follow-ups:** How would you handle a part that's available in several package variants that share a symbol but need different footprints? What's your approach when a manufacturer changes a datasheet without changing the part number?

## Q4: How would you approach setting up a constraint manager for a mixed-signal board where high-speed digital nets and sensitive analog nets share the same design, and how would you verify the constraints are actually being honored rather than just defined?

**Answer:** The setup has to begin with a net classification scheme, because constraints are only as good as the buckets the nets are sorted into. I'd define net classes up front — high-speed differential pairs, single-ended high-speed, clock, analog signal, analog reference, power, and default — and assign every net to one deliberately, with a rule that unclassified nets are a review finding rather than a silent default. Then per class: impedance targets and tolerance for the high-speed and differential nets, length-matching rules within a group and pair-to-pair skew limits, spacing rules that keep analog nets away from switching nodes and digital edges, and a keep-out or clearance rule between analog and digital regions if the stackup uses any partitioning. For analog nets specifically, the constraints that matter most are often about what they must *not* run alongside, so I'd encode both minimum spacing to aggressor classes and, where the tool supports it, region-based rules. The verification half is where most setups fail, so I'd treat it as a separate deliverable: run the constraint checker and confirm it actually flags a deliberately introduced violation (shorten a pair, break a spacing rule) before trusting a clean report — a checker that reports zero violations because the rules never bound to any nets is worse than no checker. Then review the constraint report alongside the layout at each design review, and check that the rules are bound to the right objects, not just present in the spreadsheet. Finally, export the constraint set with the design so the rules travel with the revision and can be re-run later.

**Possible follow-ups:** How would you decide the impedance target for a differential pair when the silicon vendor's recommendation and the stackup's practical geometry disagree? What would you do if the constraint checker flags hundreds of violations late in the layout — how do you triage?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has configured the lab's spectrum analyzer for an EMI pre-compliance scan using settings from a tutorial rather than the ones the applicable test standard requires — wrong resolution bandwidth, wrong detector, and no correction for the antenna and cable losses. The engineer is confident because "the peaks show up either way," and the formal scan is booked for tomorrow. How would you handle this situation?

**Answer:** I'd handle it in two tracks at once: fix the immediate risk to tomorrow's scan, and fix the process that let it happen, without making the engineer feel personally attacked — the settings error is a training gap, not a character flaw, and the response should model that. On the immediate track, the first thing I'd do is not argue about whether the peaks show up, because they will — the question is whether the amplitudes and the frequencies are trustworthy enough to compare against a limit line, and with the wrong RBW, detector, and no loss correction, they aren't. I'd sit down with the engineer and walk through the standard's requirements together, so the correction is something we derive rather than something I dictate: here's the RBW the standard specifies and why it matters for noise floor and sweep time, here's the detector type and why peak versus quasi-peak changes the reading on impulsive emissions, here's the antenna factor and cable loss that have to be applied before the number means anything. Then we'd re-run a quick scan with corrected settings on whatever time we have today, and compare — that comparison is the teaching moment, because seeing the same emission read differently under the two setups makes the point better than any explanation. On the process track, I'd add a pre-scan checklist to the lab procedure — instrument settings, correction factors, and a sanity check against a known reference source — so the next engineer doesn't have to rediscover this. For tomorrow specifically, I'd decide whether the corrected setup can be validated in time; if not, I'd rather tell the lab and reschedule than generate data we can't defend, and I'd own that decision upward rather than letting the engineer absorb it. The follow-up conversation with the engineer afterward is about how we build the habit of checking settings against the standard rather than against a tutorial, and I'd make clear that catching this before the formal scan is a good outcome, not a failure.

**Possible follow-ups:** How would you decide whether to reschedule the lab slot versus run the scan and caveat the results? What would you change in the team's lab onboarding so a new engineer can't get this far without a settings check?
