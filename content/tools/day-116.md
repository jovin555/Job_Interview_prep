## Q1: How would you approach setting up a Gerber and drill-file verification workflow in Gerbv for a medical device PCB, so that fabrication issues are caught before the files leave for the board house?

**Answer:** I'd treat Gerbv as the last human-eye gate after the CAD tool's own checks, not as a replacement for them. The workflow starts with generating a complete, self-consistent output set from a single tagged revision — every copper layer, soldermask, silkscreen, paste, the drill file, and the fabrication drawing — so nothing is assembled from mixed revisions. In Gerbv I'd load all layers, then verify in a fixed order: first the layer stack-up and alignment, confirming each layer registers against the drill file and that the drill hits land inside their pads rather than off-center; then the drill table itself, checking tool sizes against the fab drawing and confirming plated versus non-plated holes are separated correctly; then soldermask and paste clearances, looking for mask slivers or paste apertures that don't match their pads; then silkscreen, checking for text over pads and reference designators that collide. I'd also do a visual "diff" against the previous known-good revision to spot unintended changes. For a medical device the stakes are higher, so I'd document the checklist and the revision verified, and I'd confirm the board house's own DFM rules match what I checked — a clean Gerber set against the wrong fab capabilities still fails. The key discipline is that this is a repeatable, checklist-driven review, not an ad-hoc glance.

**Possible follow-ups:** How would you catch a missing or duplicated drill hit that looks fine visually but is wrong electrically? What would you do if the fab house's DFM report flags an issue your Gerbv review missed?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is that a build is reproducible and that the settings that affect behavior are explicit and version-controlled, not inherited from whatever the IDE happened to default to. I'd start by moving the project configuration into source control alongside the code, so the optimization level, linker script path, and startup file are all tracked artifacts rather than GUI state someone can silently change. I'd pin the optimization level deliberately — for a medical device, often a lower or well-understood level during development and verification, with the exact level used for the released build recorded — because optimization can change timing and expose latent undefined behavior, and the level used for testing must match the level shipped. The linker script and startup code would be treated as first-class reviewed files: memory regions, stack and heap placement, and any reserved flash regions for calibration or bootloader must be explicit and documented, since a wrong memory map can let firmware overwrite data it shouldn't. I'd also lock the toolchain version, because a compiler upgrade can change code generation. Finally, I'd make the build emit artifacts that record these settings — a map file and a build log — so a reviewer or auditor can confirm what was actually built without opening the IDE.

**Possible follow-ups:** How would you verify that the optimization level used in the released build matches what was tested? What would you check in the map file to confirm the memory layout is what you intended?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The tracking generator plus directional coupler lets you measure return loss — how much of the incident signal reflects back from the front-end's input — and from that infer impedance match across frequency. I'd set it up carefully: the tracking generator output goes through the coupler's forward path to the device, and the reflected path goes to the analyzer input, with the coupler's directivity being the limiting factor on accuracy. Before trusting anything I'd do a full two-port calibration or at minimum a reference measurement with a known load — an open, a short, and a matched termination — to establish the baseline and confirm the setup's directivity and loss are accounted for. I'd also check the test fixture itself, since cables, connectors, and the probe introduce their own reflections that can masquerade as device behavior. The decision to act comes down to whether the measured return loss is consistent across repeated sweeps, whether it agrees with the expected impedance from the design, and whether the deviation is large enough to matter for the front-end's actual signal band. If the result is marginal or the fixture uncertainty is comparable to the effect I'm chasing, I wouldn't redesign on that basis alone — I'd cross-check with a different method, like a time-domain reflectometry measurement or a direct impedance probe, before committing to a change.

**Possible follow-ups:** How does the coupler's directivity limit what return loss you can reliably measure? When would you trust a TDR measurement over a return-loss sweep?

## Q4: How would you approach setting up a Segger J-Link's RTT (Real-Time Transfer) logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?

**Answer:** RTT is attractive here precisely because it uses the debug probe's memory-access channel rather than a peripheral, so it doesn't compete for the UART that's carrying the safety-critical protocol. The setup is to enable RTT in the Zephyr configuration, allocate the RTT control block in a known RAM region the debugger can find, and confirm the J-Link can locate that block and stream the up-channel without halting the CPU. The real engineering is in bounding the perturbation: RTT logging still costs CPU cycles to format and copy messages, and if the buffer fills because the host isn't draining it fast enough, the logging call can block or drop messages depending on configuration. So I'd size the buffer deliberately, decide the drop-versus-block policy explicitly, and keep log formatting off the timing-critical path — for instance, logging compact binary records or deferring string formatting rather than doing printf-style work inside an interrupt or a hard-real-time loop. I'd measure the impact by comparing timing of the critical path with logging enabled versus disabled, and I'd treat any measurable jitter introduced by logging as a finding to design around, not to ignore. The safety-critical protocol keeps the UART; RTT is a debug channel that must prove it isn't disturbing the system before I rely on it.

**Possible follow-ups:** What happens to your timing budget if the RTT buffer fills and the logging call blocks? How would you confirm the RTT control block is actually being found by the debugger rather than silently failing?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** I'd separate the two things going on: the technical correction, which is quick, and the coaching, which matters more long-term. Technically, the engineer is half right — the peaks do show up — but the amplitude and the pass/fail judgment depend on resolution bandwidth and detector mode matching what the standard specifies, so a "get a feel for it" scan can't be used to declare compliance. I'd explain that distinction concretely rather than just overriding them, because the lesson is about why the settings matter, not just that they were wrong. Then I'd fix the configuration, re-run the scan with the correct settings, and confirm the results are usable before the booked lab time. On the people side, I'd avoid dressing them down in front of others; I'd frame it as a shared standard we both need to meet, and I'd ask them to walk me through how they chose the settings so I understand where the gap came from — maybe the procedure wasn't clear or wasn't documented. The follow-through is to make the correct settings part of a written pre-scan checklist so this doesn't recur, and to make sure the engineer owns re-running it correctly so they build the skill rather than just watching me fix it. The formal scan still happens on schedule because the correction is fast; the real cost would have been trusting a non-compliant scan.

**Possible follow-ups:** How would you verify the re-run scan is actually configured to the standard before trusting it? What would you change in the team's process so a "quick look" scan can't be mistaken for a compliance scan again?
