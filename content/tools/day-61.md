## Q1: How would you approach setting up a symbol and footprint library in KiCad for a medical device project where the same component appears in multiple variants — different package sizes, tolerance grades, or temperature ratings — so the library stays maintainable and traceable across revisions?

**Answer:** The core problem is that a single "part" in a medical BOM often maps to several distinct orderable items that share a symbol but differ in footprint, tolerance, or temperature grade. I'd separate the two concerns rather than duplicating whole symbols. In KiCad, the symbol library holds the logical function — pins, reference designator, value field — while the footprint library holds the physical land pattern. A single symbol can carry a footprint field that points to one of several footprints, so the variant is selected at the schematic instance level, not by cloning the symbol. For tolerance and temperature grade, those are attributes, not geometry, so they belong in custom fields on the symbol (or in a database-backed library if the project warrants it) rather than in the symbol name. The naming convention matters: I'd use a consistent scheme where the base name identifies the function and a suffix identifies the variant, so a reviewer can tell at a glance which grade is placed. Traceability comes from two things — keeping the library under the same version control as the project so every revision of the schematic references a known library state, and ensuring the BOM export carries the manufacturer part number and the variant attributes so the approved-vendor list can be checked against the design. For a regulated project, I'd also want a documented rule that no symbol or footprint is edited in place once it has been used in a released design; changes create a new revision so the design history stays intact. The trade-off is between a flat file-based library, which is simple but easy to let drift, and a database-driven library, which enforces consistency but adds tooling overhead. For a small team, disciplined file-based libraries with strict naming and version control are usually enough; for a larger or multi-site team, the database approach pays for itself.

**Possible follow-ups:** How would you catch a situation where two engineers independently created footprints for the same component with slightly different pad geometry? What would you put in the library's documentation to make a regulatory auditor comfortable that the parts are controlled?

## Q2: How would you approach setting up a power integrity simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?

**Answer:** I'd start by defining what question the simulation is actually answering, because "power integrity" is too broad to simulate usefully in one pass. The two questions that matter here are: how much ripple and switching noise reaches the analog supply pins, and whether the plane impedance at the analog load is low enough across the frequencies of interest. The workflow begins with an accurate model of the power distribution network — stackup, plane shapes, via transitions, and the decoupling network with realistic parasitic values for the capacitors, not just their nominal capacitance. The switching regulator is modeled as a noise source with its switching frequency and harmonics, and the analog front-end as a load with its own current draw and sensitivity. A frequency-domain tool like SIwave or HyperLynx PI is well suited to sweeping the plane impedance and identifying resonances where the decoupling network is ineffective; a time-domain simulation is better for looking at transient droop when the analog section switches its load. The trust question is the important one. Simulation results are only as good as the models, so I'd treat the first pass as a hypothesis generator, not a verdict. I'd validate the model against measurement on a prototype — inject a known signal or measure the actual ripple at the analog supply pins with a scope and a low-inductance probe — and if the simulation and measurement disagree, I'd fix the model before trusting any further simulation. I'd only act on results that are either confirmed by measurement or that show a large margin, because a marginal simulated result is within the model's error bars. The practical output is usually a decision about decoupling: where to add bulk capacitance, where to add a ferrite or an LDO to isolate the analog rail, and where the plane split or stitching needs to change.

**Possible follow-ups:** How would you model the equivalent series inductance of a decoupling capacitor, and why does it matter more at high frequency than the capacitance value? If the simulation shows a resonance at a frequency your analog front-end is sensitive to, what are your options?

## Q3: How would you approach using a spectrum analyzer with a near-field probe to locate the source of a radiated emissions failure at a specific frequency during pre-compliance testing, and how would you confirm which component is responsible?

**Answer:** The near-field probe is a localization tool, not a compliance measurement — it tells you where the field is strongest, not whether the product passes. I'd start by confirming the failure frequency and its harmonics on a proper antenna measurement, then switch to the near-field probe to hunt. The probe is scanned slowly across the board, and I'd watch the amplitude at the failing frequency while noting where it peaks. The key discipline is to move the probe in a consistent orientation and height, because near-field coupling is highly sensitive to both; otherwise you chase artifacts. Once I have a candidate region, I confirm the source by correlation rather than assumption. If the frequency tracks a clock, I can change the clock frequency slightly and see whether the emission moves with it. If it tracks a switching regulator, I can change the load or the switching frequency and watch the emission follow. A useful cross-check is to look at the harmonic structure: a digital clock produces a comb of harmonics at multiples of its fundamental, while a switching regulator produces a fundamental plus sidebands from its modulation. If the failing frequency is a clean multiple of a known clock, that's strong evidence; if it sits near a switching harmonic with sidebands, that points elsewhere. I'd also use a current probe on the cable or a hand-held sniffer to distinguish whether the emission is radiating from the board directly or being conducted out on a cable and radiating from there, because the fix is completely different. Only after I've confirmed the source by at least two independent observations would I commit to a mitigation, and then I'd re-measure with the antenna to confirm the fix actually moved the compliance number.

**Possible follow-ups:** How would you distinguish a near-field probe reading that is a real emission from one that is an artifact of the probe's own resonance? What mitigation would you try first if the source turned out to be a clock trace running near a board edge?

## Q4: How would you approach configuring a Segger J-Link for a Zephyr RTOS target where an automated test harness needs to flash the device, run a test sequence, and capture a crash dump without manual intervention — and what failure modes would you design around?

**Answer:** The goal is a deterministic, repeatable sequence that a CI system can invoke without a human watching. I'd use the J-Link command-line tools driven by a script rather than the GUI, because the GUI is not scriptable in a reliable way. The sequence is: reset and halt the target, erase and program the image, verify the flash contents, reset and run, then let the test sequence execute while the harness monitors for a completion signal or a timeout. For crash capture, the J-Link can read the target's memory directly, so on a fault the harness can dump the relevant RAM regions and the fault status registers without needing the firmware to print anything. The failure modes I'd design around are the ones that make automated bring-up flaky. First, the debug connection itself: if the target is in a low-power state or the debug pins are repurposed, the J-Link may not connect, so the script needs a connect-under-reset option and a clear error if it fails. Second, flash programming can fail partway, leaving the target in an unknown state, so the script should verify after programming and retry or fail loudly rather than proceeding. Third, the test sequence can hang, so every step needs a timeout and a defined recovery — usually a reset and a retry, with a bounded number of retries before the harness reports a hard failure. Fourth, the crash dump itself can be ambiguous if the fault handler has already overwritten state, so I'd capture the dump as early as possible and preserve the raw memory rather than a parsed summary. Finally, I'd make the whole sequence idempotent so a re-run after a failure starts from a known state, and I'd log every step with timestamps so a failure can be diagnosed after the fact.

**Possible follow-ups:** How would you handle a target that occasionally fails to connect because it is still running the previous test? What would you capture in a crash dump to make a hard fault debuggable without a live debugger attached?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the Altium Designer output job configuration for a medical device PCB release, and you discover the fabrication outputs are missing the drill table and the assembly drawings reference an outdated revision of the schematic. The board house is expecting the files tomorrow, and the engineer is confident the outputs are complete because "the Gerbers look fine." How would you handle this situation?

**Answer:** The immediate priority is the release, and the second priority is making sure this class of error doesn't recur. I'd start by not treating it as a blame situation — the engineer's confidence is based on a real signal, that the Gerbers look correct, and the gap is that "the Gerbers look fine" is not the same as "the release package is complete." I'd sit down with them and walk through the output job against a release checklist, so the missing drill table and the stale assembly drawing are visible as checklist items rather than as my opinion. Then we fix the package together: regenerate the drill files, confirm the assembly drawing references the correct schematic revision, and verify the whole set against the checklist before it goes out. If the board house deadline is genuinely at risk, I'd communicate early rather than hope — a short delay with a correct package is better than a rushed package that causes a fabrication hold. After the release, I'd address the root cause. The output job configuration is a reusable asset, so the fix is to make the checklist part of the job itself — either by configuring the output job to always generate the drill table and to pull the assembly drawing from the current schematic revision, or by adding a documented pre-release verification step that a second person signs off on. I'd also make sure the engineer understands why the drill table and assembly revision matter in a regulated context, because the lesson lands better when it's tied to the consequence — an incomplete package can stall fabrication or, worse, produce a board that doesn't match its documentation. The tone I'd aim for is that we caught it before it left the building, which is exactly what the review process is for.

**Possible follow-ups:** How would you structure a release checklist so it catches this kind of omission without becoming a box-ticking exercise? If the same engineer made a similar omission on a later release, how would you handle it differently?
