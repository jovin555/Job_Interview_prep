## Q1: How would you approach setting up a Zephyr RTOS project using the west build system so that the same source tree produces both a production image and a debug image with extra logging and assertions, without maintaining two separate trees?

**Answer:** The cleanest way is to treat the difference as configuration, not code. In Zephyr that means leaning on Kconfig fragments and devicetree overlays rather than `#ifdef` blocks scattered through the application. I'd keep one application source tree and one `west.yml` manifest, and define two build configurations — say `prj.conf` for production and a `prj_debug.conf` fragment layered on top for the debug image — where the debug fragment enables `CONFIG_LOG`, raises the log level, turns on `CONFIG_ASSERT`, enables thread analyzer and stack sentinel, and possibly swaps in a mock sensor driver via a devicetree overlay. The build invocation then becomes `west build -b <board> -- -DEXTRA_CONF_FILE=prj_debug.conf -DDTC_OVERLAY_FILE=debug.overlay`, so the same tree yields both images and the delta between them is explicit and reviewable. The key discipline is that production defaults live in the base config and debug only *adds* — you never want a debug-only setting silently leaking into the release image. I'd also wire both configurations into CI so every commit builds both, which catches the classic failure where debug-only code paths rot because nobody compiles them. Finally, I'd document the exact west commands in the repo README so the build is reproducible by anyone, not tribal knowledge.

**Possible follow-ups:** How do you guarantee the production image can't accidentally pick up the debug fragment? / Where would you put board-specific versus application-specific configuration so the two don't get tangled?

## Q2: How would you approach configuring a Segger J-Link for a Zephyr RTOS target where an automated test harness needs to flash the device, run a test sequence, and capture a crash dump without manual intervention — and what failure modes would you design around?

**Answer:** I'd drive the J-Link through its command-line tools rather than the GUI, because a harness needs scriptable, exit-code-checked operations. The flow is roughly: `JLinkExe` (or the J-Link Commander script mode) with a script file that connects, halts, erases, programs the hex/elf, verifies, and resets — then the harness releases the target and runs the test over whatever channel the test uses (RTT, UART, or a host-side protocol). For crash capture, I'd configure the target so a hard fault lands in a known state, then have the harness re-attach with `JLinkExe`, halt, and dump the relevant memory regions (fault status registers, stacked PC/LR, the Zephyr fatal error struct) to a file for later parsing. RTT is attractive here because it gives a continuous log channel without stealing the UART. Failure modes I'd design around: the target not being detected (bad SWD wiring, target held in reset, clock too fast for the wiring — so I'd make SWD speed a tunable parameter and fall back to a slower clock); flash programming succeeding but verify failing (supply droop or a marginal part); the harness hanging because J-Link is waiting on a prompt (so every script needs timeouts and a non-interactive mode); and stale state from a previous run (so each run starts from a known erase/reset). I'd also make the harness idempotent and log the full J-Link transcript so a failure is diagnosable after the fact rather than requiring a re-run.

**Possible follow-ups:** How would you distinguish a genuine firmware crash from a debugger connection problem when the harness reports a failure? / What would you change if the target occasionally fails to enumerate on the debug probe after a power cycle?

## Q3: How would you approach setting up a constraint manager in Cadence Allegro for a mixed-signal PCB that has both high-speed digital interfaces and sensitive analog sensor inputs, and how would you verify the constraints are actually being honored rather than just defined?

**Answer:** I'd start by classifying nets before writing a single rule, because the constraint manager is only as good as the net taxonomy feeding it. High-speed digital nets (clocks, differential pairs, fast single-ended buses) get physical and spacing rules — impedance targets, differential pair gap/width, intra-pair skew, length matching within a bus, and reference-plane continuity. Sensitive analog nets get the opposite treatment: they need to be kept away from aggressors, so I'd define net classes and use spacing rules and region-based keepouts to enforce separation, plus rules preventing analog nets from crossing a split in the reference plane. The critical step people skip is *tying the constraints to the schematic* — assigning net classes and properties in OrCAD so the rules propagate to Allegro rather than being hand-applied in the layout, which is where drift creeps in. Verification is the other half: defining a rule is worthless if nobody checks it. I'd run the DRC with the constraint-driven checks enabled and treat violations as blocking, then do a targeted post-route audit — impedance and length reports for the high-speed nets, and a visual plus DRC check that analog traces respect their keepouts and reference planes. I'd also spot-check with cross-probing so I can click a schematic net and confirm the layout actually carries the class I think it does. The mindset is that the constraint manager is a contract; the DRC and the audit are how you prove the contract was met.

**Possible follow-ups:** How would you handle a case where a high-speed net and a sensitive analog net genuinely must cross? / What would you do if the DRC passes but a signal integrity simulation still shows a problem?

## Q4: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The tracking generator plus directional coupler gives you a reflection measurement — you're injecting a swept signal and looking at what comes back, then converting return loss to impedance. The setup matters more than the math: I'd calibrate the reference plane first with a short/open/load (or the analyzer's built-in calibration routine) at the point where the front-end will connect, so cable and coupler losses are removed from the measurement. Then I'd connect the front-end through the coupler, sweep the band of interest, and read return loss, converting to impedance magnitude and phase. The trust question is where most of the judgment lives. I'd want to see the calibration hold — re-check with a known load after the measurement to confirm nothing drifted. I'd sanity-check the result against the expected input impedance from the schematic (a differential front-end won't look like 50 Ω single-ended, so I'd be careful about what I'm actually measuring and whether a balun or fixture is in the path). I'd look at whether the sweep is smooth and physically plausible rather than full of sharp resonances that smell like fixture artifacts. And I'd vary the setup slightly — different cable, re-seat the connector — to see if the result is stable. If the measurement disagrees with simulation and with a simple DC/low-frequency check, I trust the simpler measurement and treat the reflection data as suspect until I understand the discrepancy. The rule I'd apply: don't act on a number you can't reproduce and can't reconcile with a second, independent method.

**Possible follow-ups:** How would you account for the fixture's own parasitics when the front-end can't be measured in isolation? / What would make you decide the return-loss data is good enough to drive a matching-network change?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** First I'd separate the technical issue from the interpersonal one, because they need different handling. Technically, the engineer isn't wrong that peaks show up — the problem is that RBW and detector choice change the *amplitude* you read and therefore whether you pass or fail against a limit line. A wide RBW and a peak detector can overstate or understate emissions depending on the signal, and the standard specifies both for a reason. So the scan as configured isn't a valid pre-compliance result; it's a survey. I'd explain that distinction concretely rather than just asserting "the settings are wrong," because the engineer's confidence comes from a reasonable observation that's being applied to the wrong question. Then the practical problem: the formal scan is tomorrow and lab time is booked. My priority is to not let an invalid scan masquerade as a valid one. I'd reconfigure the analyzer to the standard's settings and re-run — if the setup is scriptable or the sweep is fast, this may cost far less time than feared, and I'd frame it that way to reduce the sense of crisis. If there genuinely isn't time to redo the full scan properly, I'd be explicit with stakeholders that tomorrow's session is a survey, not a compliance pre-scan, and either reschedule or scope the formal run to the highest-risk bands. On the people side, I'd avoid dressing the engineer down in front of others; the lesson I want is "know why the standard specifies these settings," not "don't ask questions." I'd follow up by making the required settings part of the lab procedure so this isn't dependent on one person's memory next time.

**Possible follow-ups:** How would you decide whether to reschedule the formal scan versus run a reduced-scope one? / What would you put in place so the correct analyzer configuration is the default rather than something someone has to remember?
