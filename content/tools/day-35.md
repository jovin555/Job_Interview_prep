## Q1: How would you approach setting up a differential pair routing constraint in Cadence Allegro for a USB 2.0 interface on a mixed-signal medical device PCB, and how would you verify that the constraints are actually met in the final layout?

**Answer:** For USB 2.0, the key electrical constraints are the 90-ohm differential impedance, maximum trace length, and intra-pair skew. I'd start by defining the physical stackup in the cross-section editor — layer thickness, dielectric constant, and copper weight — because the impedance calculation is only as good as the stackup data. Then, in the constraint manager, I'd create a physical constraint set for the USB pair with the correct line width and spacing to achieve 90 ohms differential, and a spacing constraint set for the intra-pair gap and clearance to other nets. I'd also set a length matching rule for the pair, typically targeting no more than a few mils of skew. For verification, I'd run the DRC after routing and then use the constraint manager's audit report to confirm zero violations. Beyond that, I'd use the impedance calculator in Allegro to verify the actual trace geometry against the target, and if the board house provides impedance coupons, I'd review those results against the simulation. For a medical device, I'd also document the impedance requirements in the fabrication drawing so the board house knows to control the impedance during manufacturing.

## Q2: How would you approach using a Segger J-Link debugger to capture a crash dump from a Zephyr RTOS-based system that has entered a hard fault, without modifying the firmware to add debug print statements?

**Answer:** The key is to use the debugger's ability to halt the CPU and inspect the full processor state at the moment of the fault. I'd start by configuring the J-Link to halt on hard fault — this can be done by setting the appropriate debug exception mask, or by using the J-Link's flash breakpoint capability to break at the hard fault handler entry point. Once halted, I'd capture the program counter, link register, stack pointer, and the fault status registers (CFSR, HFSR, BFAR, MMFSR) to understand the fault type. The critical step is to reconstruct the call stack by reading the stack memory — the stacked registers (R0-R3, R12, LR, PC, xPSR) are pushed onto the stack when the fault occurs. I'd use the J-Link Commander script or a GDB session to dump the stack contents and then use the ELF file to resolve addresses to function names. For Zephyr specifically, I'd also look at the current thread's control block to identify which thread was running, since the thread's stack pointer is saved in the thread structure. If the fault corrupted the stack, I might need to examine the previous stack frame or use the J-Link's trace capability if available. The advantage of this approach is that it captures the exact state without altering the firmware behavior — adding debug prints can change timing and mask the fault.

**Possible follow-ups:**
- How would you distinguish between a stack overflow and a memory access violation from the fault registers?
- What would you do if the stack contents appear corrupted and you can't reconstruct the call stack?

## Q3: How would you approach setting up a component library management strategy in KiCad for a medical device project that needs to maintain strict revision control and regulatory traceability, given that KiCad's library format is file-based rather than database-driven?

**Answer:** KiCad's file-based libraries actually work well for revision control if you structure them properly. I'd organize the libraries in a dedicated repository with a clear directory structure — separate folders for schematic symbols, footprints, and 3D models, with a versioned naming convention. Each component would have a unique identifier that includes a revision suffix, and I'd maintain a changelog file documenting what changed in each revision and why. For traceability, I'd use Git tags to mark approved library states — for example, a tag for the library state at each design release. The key practice is to never modify a component in place; instead, create a new revision and update the schematic to reference it. This gives you an audit trail of which component revision was used in which design release. I'd also set up a review process where library changes require a merge request and approval before being merged into the main branch. For the schematic symbols and footprints, I'd ensure the fields include manufacturer part number, datasheet revision, and a link to the datasheet. One important detail is to use the same library path configuration across the team — I'd commit a `kicad_common` or project-specific library table file so everyone resolves the same library versions. Finally, I'd generate a bill of materials directly from the schematic that includes the component revision, so the design documentation ties back to the exact library versions used.

**Possible follow-ups:**
- How would you handle a situation where a component needs to be updated mid-project after the schematic has already been released?
- What metadata would you require in the component fields to support regulatory traceability?

## Q4: How would you approach using a mixed-signal oscilloscope to characterize the noise coupling between a switching regulator and a precision analog sensor on the same PCB, and how would you determine whether the coupling is conducted, radiated, or through the ground plane?

**Answer:** I'd approach this systematically, starting with time-domain measurements and then narrowing down the coupling path. First, I'd set up the oscilloscope with two channels — one probing the switching node of the regulator (or the inductor) to capture the switching waveform, and the other probing the analog sensor's output or its supply pin. I'd trigger on the switching signal and look for correlated noise on the analog channel. The key is to use proper probing techniques: a short ground spring on the analog probe to minimize the probe loop inductance, and a differential probe if the sensor output is referenced to a different point than the scope's ground. Once I confirm correlation, I'd determine the coupling path. For conducted coupling, I'd check the power supply rails — probe the regulator output and the sensor supply pin simultaneously to see if the noise is present on the supply line. For ground plane coupling, I'd probe between two points on the ground plane — if there's a significant voltage difference between the regulator's ground and the sensor's ground at the switching frequency, that indicates ground bounce. For radiated coupling, I'd use a near-field probe connected to the scope's input while the sensor is operating — if the noise appears when the probe is near the inductor or switching traces but not when probing the supply lines, that suggests radiated coupling. I'd also vary the load on the regulator to see how the noise changes. To further distinguish, I could temporarily lift the sensor's ground connection (if safe) or add a ferrite bead to the supply line to see if the noise changes. The measurement setup itself is critical — I'd make sure the scope's ground lead isn't creating a ground loop that masks the real coupling.

**Possible follow-ups:**
- How would you use the oscilloscope's FFT function to help identify the coupling mechanism?
- What would you do if the noise only appears when both the regulator and the sensor are active, but you can't see it on either the supply rail or the ground plane?

## Q5: (Behavioral) Imagine you are leading a design review for a medical device PCB, and you discover that the firmware team has been using a different version of the I2C protocol than what the hardware actually implements — the firmware is expecting 7-bit addressing with a specific register map, but the hardware uses 10-bit addressing with a different register layout. The integration testing is scheduled to start in two days, and both teams are confident their implementation is correct. How would you handle this situation?

**Answer:** The first priority is to get the facts on the table without letting either team feel blamed. I'd call a joint meeting with both teams and start by asking each to walk through their implementation — the hardware team would show the schematic and the actual I2C address configuration, and the firmware team would show their driver code and the register map they're using. The goal is to identify the discrepancy together, not to assign fault. Once we confirm the mismatch, I'd assess the options: the hardware is already fabricated, so changing the address strapping on the PCB isn't possible without a re-spin. The firmware change is likely the faster path — modifying the driver to use 10-bit addressing and the correct register map. I'd ask the firmware team to estimate the effort and risk of the change, and I'd ask the hardware team to confirm the exact register map from the sensor datasheet so we have a single source of truth. I'd also check whether the sensor has a 7-bit addressing mode that could be enabled via a register write — sometimes the address mode is configurable in software. If the firmware change is feasible within two days, I'd have the firmware team make the change and then run a focused integration test on the specific I2C transactions before the full test suite. If it's not feasible, I'd need to discuss schedule impact with management. Throughout this, I'd document everything — the discrepancy, the decision, and the resolution — because this is exactly the kind of issue that needs to be captured for the design history file. After the immediate issue is resolved, I'd look at how to prevent this in the future — for example, a protocol specification document that both teams sign off on before hardware fabrication, or a pre-integration checklist that includes verifying address and register maps against the datasheet.

**Possible follow-ups:**
- How would you handle the situation if the firmware team insists their implementation is correct because it works on the evaluation board?
- What process changes would you propose to prevent this type of hardware-firmware mismatch in future projects?
