## Q1: How would you approach setting up a spectrum analyzer for a conducted emissions pre-compliance scan on a medical device's AC input, and what would you check before trusting the first measurement?

**Answer:** Conducted emissions on the AC mains input is one of the areas where it's easy to produce a beautiful plot that means nothing, so I'd treat setup verification as part of the measurement rather than a formality. The scan itself is conceptually simple — you're measuring the RF current or voltage that the device pushes back onto the mains — but the measurement chain has several places to go wrong.

Start with the transducer. For mains conducted emissions you're typically using a LISN (line impedance stabilization network), and the whole point of the LISN is to present a defined, repeatable RF impedance to the device under test while isolating the measurement receiver from the actual mains supply. So the first checks are: is the LISN rated for the current the device draws, is it bonded to the reference ground plane with a short, low-inductance connection, and is the device plugged into the LISN's DUT port rather than straight into the wall? If the device has a switching supply with a Y-capacitor to chassis, the LISN's ground reference and the device's chassis reference need to be consistent, or you'll measure a common-mode path that doesn't exist in the real installation.

Then the receiver settings. Conducted emissions standards define the frequency range, the resolution bandwidth, and the detector — quasi-peak and average are the usual pair, and the limits differ between them. If you scan with peak detection and a wide RBW you'll get a fast overview, but you cannot compare those numbers to a quasi-peak limit. So I'd do a peak pre-scan to find the offenders, then re-measure each significant peak with the correct RBW and detector. The dwell time matters too: quasi-peak measurement of a signal with a low repetition rate needs enough time for the detector to settle, and if you rush it you'll under-read.

Before trusting anything, I'd verify the whole chain with a known source — a signal generator injecting a defined level through a calibration fixture, or at minimum a comb generator — and confirm the analyzer reads what it should. I'd also check the noise floor with the device off but the LISN powered, so I know which peaks are the device and which are ambient. Ambient is a real problem in a non-shielded lab: broadcast AM, switching supplies in other benches, even fluorescent ballasts. If a peak doesn't move when I change the device's operating mode, it's probably not the device.

Finally, I'd think about the device's operating state. A medical device may have multiple modes — charging, idle, full-load, wireless transmitting — and the worst case for emissions is often not the mode you'd guess. I'd document which mode each scan was taken in, because a pre-compliance result without the operating condition attached is not reproducible.

**Possible follow-ups:**
- How would you distinguish a genuine device emission from ambient noise if you can't get into a shielded room?
- What would you do if a peak sits right at the limit and you need to decide whether to redesign or re-measure?

## Q2: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** When the framing doesn't map onto any stock decoder, the productive move is to stop thinking of it as "decoding" and start thinking of it as "building a state machine that happens to run on captured samples." The logic analyzer is just giving me timestamped edges; everything above that is my model of the protocol.

First I'd characterize the physical layer independently of the framing. What's the idle level, what's the bit period, is the clock explicit or recovered from the data, is it NRZ or Manchester or something with a start-bit convention? I'd capture a known-good transaction — ideally triggered by the device itself doing something I can observe, like a sensor read I can correlate with a display update — and measure the timing by hand on a few edges. That gives me the nominal bit rate and confirms whether the transmitter is consistent or has jitter that will break a naive sampler.

Then I'd define the frame structure explicitly before writing any decoder: sync/header pattern, length field if any, payload, checksum or CRC, inter-frame gap. The non-byte-aligned header is the interesting part — it means I can't just slice the capture into bytes from an arbitrary origin. The usual approach is to search for the sync pattern as a bit sequence, then treat everything after it as offset from that anchor. If the header is, say, a 12-bit preamble, I find those 12 bits, and the payload starts at bit 12, not bit 8 or 16. Most logic analyzer software lets you define a decoder in terms of bit offsets from a trigger or from a pattern match, so the sync pattern becomes the trigger and the rest is relative.

For the decoder itself, I'd write it in whatever scripting the tool supports — many support Python or a custom decoder SDK — and structure it as: find sync, extract length, extract payload, verify checksum, emit a decoded frame or an error. The checksum is my validation: if my bit alignment is wrong, the checksum will fail almost every time, which is a much faster feedback loop than eyeballing waveforms. I'd also build in a "raw bits" output mode so that when the checksum fails I can see exactly which bits I extracted and compare against the analog waveform.

One thing I'd be careful about: a decoder that silently produces plausible-looking garbage is worse than no decoder. So I'd make it emit explicit error frames for checksum failures, framing errors, and timeouts, and I'd validate it against a capture where I already know the answer — for instance, a transaction where the sensor value is also visible on a display or in a log. If the decoder reproduces that value, I trust it; if not, I don't.

**Possible follow-ups:**
- How would you handle a protocol where the bit rate drifts slightly between transactions?
- What would you do if the bus is bidirectional and the direction changes mid-frame?

## Q3: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The core problem is that an IDE project file is a mutable artifact that a developer can change with two clicks, and for a regulated medical device that's a traceability hazard. The goal is to make the build configuration something that is reviewed, version-controlled, and reproducible — not something that lives only in a `.uvprojx` file that someone edited on their laptop.

I'd start by treating the project file itself as source. It goes into version control, changes to it go through review like any other code change, and the build that produces a released firmware image is built from a tagged commit, not from whatever is on someone's machine. That's the foundation; everything else is about making the configuration explicit and hard to change accidentally.

For the optimization level specifically: the choice between `-O0`, `-O1`, `-O2`, `-Os`, and so on is not a cosmetic setting. It affects timing, it affects whether certain volatile accesses get reordered, it affects code size, and it can expose or mask latent bugs. For a medical device I'd want the optimization level to be a deliberate, documented decision tied to the verification that was performed. If the device was verified at `-O0`, then the release build is `-O0` unless there's a documented re-verification. I'd make that explicit in the project settings and, better, in a build script or makefile that the IDE project references, so the setting isn't buried in a dialog.

The linker script and startup code are the same story. The linker script defines the memory map — where flash and RAM live, where the vector table goes, where calibration data or bootloader regions are reserved. A wrong linker script can silently place a section where it overwrites something else, and the failure may not show up until a specific code path runs. So the linker script is a reviewed artifact, and I'd want a check that the built image's memory layout matches the intended map — for example, inspecting the map file or the section addresses in the output. The startup code is where the C runtime gets initialized, where the vector table is populated, and where any early hardware setup happens; it's small but it's on the critical path for every boot, so it gets the same treatment.

Practically, I'd also want the build to be reproducible: same source, same toolchain version, same settings, same output. That means pinning the toolchain version and documenting it, and ideally having a CI build that produces the release artifact so there's no ambiguity about what was built. For auditability, the build log and the map file are part of the release record — they show what was compiled and where it landed.

**Possible follow-ups:**
- How would you detect that someone had changed the optimization level without going through review?
- What's your approach to verifying that the linker script's memory map is actually correct for a given hardware revision?

## Q4: How would you approach setting up a power integrity simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?

**Answer:** The reason to simulate power integrity here is that the interaction between a switching regulator and a precision analog front-end is exactly the kind of thing that's hard to reason about by inspection and expensive to discover on a fabricated board. But PI simulation has a reputation for producing impressive-looking plots that don't correspond to reality, so the workflow has to be built around deciding what to trust.

I'd start by defining what question I'm actually asking. "Is the PDN good?" is too vague. The useful questions are narrower: what is the impedance of the PDN from the regulator output to the analog front-end's supply pins, across the frequency range where the analog front-end is sensitive? Where are the anti-resonances between decoupling capacitors, and do any of them land in a band that matters? How much of the switching regulator's ripple and its harmonics actually reaches the analog supply, given the filtering between them? Each of these has a different modeling approach and a different level of confidence.

For the PDN impedance, the model is a network of capacitors, their ESR and ESL, the plane capacitance, the via inductance, and the regulator's output impedance. The results are only as good as the component models — a capacitor model that's just a nominal capacitance with no ESR/ESL will give you anti-resonances in the wrong places. So I'd use vendor-provided impedance models or measured data for the capacitors, and I'd be explicit about the frequency range where the model is valid. Above a few hundred MHz, the model of the board itself (plane resonances, via transitions) starts to dominate and the simple lumped model breaks down.

For the regulator-to-analog coupling, the question is really about the attenuation of the filter between them and the impedance of the return path. If the analog front-end has its own LDO or RC filter off the main rail, the simulation should include that, and the result I care about is the ripple at the analog supply pins under the regulator's actual switching waveform — not a sine wave, the real edge rates and any ringing.

The trust decision comes down to a few things. First, does the model reproduce something I can measure? If I have a prototype, I'd measure the PDN impedance with a network analyzer or the ripple with a scope and compare to the simulation. If they disagree, the model is wrong somewhere and I need to find where before I trust any prediction. Second, is the result sensitive to parameters I don't know well? If a 20% change in via inductance flips the conclusion, the result isn't robust enough to act on. Third, is the effect I'm predicting large enough to matter relative to the noise floor of the analog front-end? A simulation that predicts a 50 µV ripple on a front-end with 1 mV of intrinsic noise is not telling me anything actionable.

So the workflow is: define the question, build the model with defensible component data, run the analysis, then stress-test the conclusion against measurement and parameter uncertainty before using it to drive a design decision. If I can't get the model to agree with measurement, I'd rather fix the board empirically than trust a simulation I can't validate.

**Possible follow-ups:**
- How would you decide where to place the boundary between "the PDN I'm simulating" and "the rest of the board"?
- If the simulation says you need more decoupling but the board is already laid out, what are your options?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** The immediate practical question is whether tomorrow's scan can produce a result we can rely on, and the answer depends on what the settings actually are. So the first thing I'd do is not argue about it in the abstract — I'd sit down with the engineer and look at the current settings against the standard's requirements, side by side. That turns a disagreement about confidence into a concrete comparison: here's what the standard specifies for RBW and detector, here's what's currently set, here's the difference. If the settings are genuinely wrong, that's usually enough to make the case without it becoming about who's right.

The "peaks show up either way" reasoning is worth addressing directly, because it's a real misconception and not a stupid one. A peak scan with a wide RBW and peak detector will indeed show you where the energy is — it's a fine tool for finding candidates. What it won't do is give you a number you can compare to a quasi-peak or average limit, because the detector and RBW are part of the measurement definition. A signal that looks comfortably below the limit on a peak scan can fail a quasi-peak measurement, and vice versa. So the engineer isn't wrong that the peaks show up; the issue is that the peaks showing up isn't the same as the measurement being valid.

Then the scheduling problem. If the settings are wrong, I have two options: fix them and proceed tomorrow, or postpone. Fixing them is usually feasible — RBW and detector are settings, not hardware — so the question is whether there's time to re-scan with the correct settings in the booked slot. If the scan is a full sweep across the band with multiple detectors, that takes longer than a quick peak scan, so I'd want to know whether the slot is long enough. If it isn't, I'd rather use tomorrow's slot for a correct partial scan or a correct scan of the frequency ranges that matter most, and book additional time for the rest, than produce a full set of numbers that we can't defend.

I'd also want to understand how this happened, without making it a blame exercise. Was the setup inherited from a previous quick scan and never revisited? Was there no checklist for what "ready for a formal scan" means? If the answer is that we don't have a documented setup procedure, that's the real gap, and the fix is a checklist that gets run before any formal scan — instrument settings, probe calibration, ambient baseline, device operating mode. That's more valuable than fixing this one instance, because it prevents the next one.

Finally, I'd be clear with the engineer about why this matters in a way that's about the work, not about them. In a regulated context, a measurement that can't be tied to the correct method isn't evidence, and if it later turns out the device fails the formal test, we've lost time and credibility. The engineer's instinct to get a quick look is good; the fix is to make the boundary between "quick look" and "formal measurement" explicit so it's clear which one you're doing.

**Possible follow-ups:**
- How would you decide whether tomorrow's slot is long enough to redo the scan correctly?
- What would you put on a pre-scan checklist to prevent this from recurring?
