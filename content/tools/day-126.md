## Q1: How would you approach setting up a Gerber and drill-file verification workflow in a free viewer like Gerbv for a medical device PCB, so that fabrication issues are caught before the files leave for the board house?
**Answer:** I'd treat the free viewer as an independent second opinion, not a replacement for the CAD tool's own checks — the point is to look at the files as the board house will see them, not as the design tool renders them. The workflow starts with a checklist-driven layer-by-layer review: load every Gerber and the drill file, confirm the layer stack order matches the fabrication drawing, and verify that each layer is present, correctly named, and in the right units and format. Then I'd do a visual sanity pass — check that the soldermask openings align with pads, that silkscreen doesn't print over exposed pads, that the board outline closes cleanly, and that the drill file's tool sizes and counts match the drill table. I'd specifically look for the classic killers: missing or duplicated layers, mirrored layers, a drill file generated in the wrong units, and annular ring violations on small vias. For a medical device I'd also confirm the revision marking and any regulatory identifiers on the silkscreen match the released documentation, since a mismatch there is a documentation nonconformance even if the copper is fine. Finally, I'd record what was checked and by whom, so the verification is auditable rather than a informal glance.
**Possible follow-ups:** How would you verify the drill file's coordinate format and units before trusting the viewer's rendering? What would you do if the viewer showed a discrepancy you couldn't reproduce in the CAD tool?

## Q2: How would you approach setting up a constraint manager in Cadence Allegro for a mixed-signal PCB that has both high-speed digital interfaces and sensitive analog sensor inputs, and how would you verify the constraints are actually being honored rather than just defined?
**Answer:** The key distinction is that defining constraints and enforcing them are two different problems, and the second is where most teams get burned. I'd start by classifying nets into groups — high-speed digital (with their impedance, length-matching, and spacing rules), sensitive analog (with isolation, keepout, and reference-plane rules), and the power/ground nets that interact with both. For each group I'd set the physical and spacing constraints from the interface spec or the signal-integrity budget, not from habit, and I'd use net classes and rule precedence carefully so that a broad default doesn't silently override a specific rule. The verification step is the important one: I'd run the DRC with the full constraint set enabled and treat every waiver as a reviewed decision, not a dismissal. I'd also cross-check the actual routed geometry against the intent — for example, confirm that analog traces really are referenced to a continuous plane and that the digital return currents aren't steered under the analog section. A constraint that's defined but waived everywhere is worse than no constraint, because it creates false confidence.
**Possible follow-ups:** How would you handle a case where two constraints conflict on the same net, and how does Allegro's rule precedence resolve it? How would you audit a layout done by someone else to confirm the constraints were honored?

## Q3: How would you approach configuring a Segger J-Link's RTT logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?
**Answer:** RTT is attractive precisely because it uses the debug probe's memory-access channel rather than a peripheral, so it doesn't consume the UART — but it's not free, and the timing question is the real one. I'd set up the RTT control block in a dedicated RAM section, size the up-buffer generously so the target rarely blocks on a full buffer, and configure the host side to poll fast enough that the buffer doesn't back up. The perturbation risk comes from two places: the target blocking when the buffer fills (which stalls the logging thread and can distort timing), and the debug probe's memory accesses stealing bus cycles or causing cache effects. To manage the first, I'd use non-blocking mode where a full buffer drops messages rather than stalling, and I'd keep the logged data small and structured. To manage the second, I'd measure rather than assume — toggle a GPIO at the start and end of a timing-critical section and compare the pulse width with RTT enabled versus disabled, so any perturbation is quantified instead of hoped away. For a safety-critical system I'd also make sure RTT logging can be compiled out entirely for production builds, so the release image carries none of it.
**Possible follow-ups:** How would you decide the RTT buffer size, and what happens when the host isn't connected? How would you confirm that RTT isn't disturbing a real-time control loop?

## Q4: How would you approach using a spectrum analyzer with a near-field probe to determine whether a radiated emissions failure at a specific frequency is coming from a switching regulator's harmonic or from a digital clock harmonic, and how would you confirm your hypothesis?
**Answer:** The first step is arithmetic before measurement: list the candidate sources and their harmonics — the switching frequency and its multiples, and the clock frequencies and their multiples — and see which ones land on the failing frequency. That narrows the suspects before I touch the probe. Then I'd use the near-field probe spatially: move it over the board and find where the field at that frequency peaks, which usually points at the guilty component or trace. To confirm, I'd perturb the suspects one at a time and watch the amplitude at the failing frequency — change the switching frequency slightly (if the design allows) and see whether the emission moves with it; disable or gate a clock and see whether the emission drops. A source that tracks its presumed fundamental is confirmed; one that doesn't is a false lead. I'd also check whether the emission is broadband or narrowband, since a sharp harmonic points to a clock and a broader spread can point to a switching edge. The confirmation step matters because near-field probing is qualitative — it tells you where, not definitively what.
**Possible follow-ups:** How would you distinguish a harmonic of the switching regulator from a harmonic of a clock that happens to share the same multiple? What would you do if two candidate sources both seemed to track the emission?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the Altium Designer output job configuration for a medical device PCB release, and you discover the fabrication outputs are missing the drill table and the assembly drawings reference an outdated revision of the schematic. The board house is expecting the files tomorrow, and the engineer is confident the outputs are complete because "the Gerbers look fine." How would you handle this situation?
**Answer:** I'd separate the immediate problem from the process problem and handle them in that order. Immediately, I'd stop the release, regenerate the outputs myself or with the engineer, and verify them against the released documentation before anything goes to the board house — a missing drill table or a stale assembly drawing is exactly the kind of error that turns into scrap or a documentation nonconformance, so "the Gerbers look fine" isn't a sufficient check. I'd frame the correction to the engineer as a shared review rather than a blame exercise: walk through the output job together, show what the drill table and revision marking should contain, and make the verification checklist explicit. Then I'd address the root cause — the output job configuration should be a controlled, reviewed artifact with a defined checklist, not something one person assembles under time pressure. I'd also make sure the lesson is captured for the team, because the same gap will recur on the next release if the process doesn't change. The tone matters: the engineer's confidence was misplaced, not malicious, and the fix is a better process plus a clearer definition of "done."
**Possible follow-ups:** How would you structure the output-job review so this is caught automatically next time? How would you communicate the delay to the board house and the project stakeholders without undermining the engineer?
