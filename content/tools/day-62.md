## Q1: How would you approach setting up a schematic symbol and footprint library in KiCad for a medical device project where the same component appears in multiple variants — different package sizes, tolerance grades, or temperature ratings — so the library stays maintainable and traceable across revisions?

**Answer:** The core problem is that KiCad's library model is file-based and symbol-centric, so the natural temptation is to create a separate symbol for every variant, which quickly becomes unmaintainable and makes traceability worse rather than better. A more disciplined approach is to separate the *logical* function of a part from its *physical* realization. One symbol represents the electrical function (a resistor, a regulator, an op-amp) with generic pin names and no package-specific information baked in. The variant-specific data — package, tolerance, temperature grade, manufacturer part number — lives in the footprint assignment and in a structured BOM field set, not in duplicated symbols.

In practice this means: a single symbol library organized by function, a footprint library organized by package family, and a set of custom fields on each symbol instance (MPN, tolerance, temp grade, lifecycle status) that drive the BOM and the traceability matrix. For a medical device, those fields are not cosmetic — they are the link between the schematic and the regulatory documentation, so they need to be populated consistently and reviewed like any other design artifact. Variant selection then happens at the BOM or assembly-variant level rather than by proliferating symbols.

The traceability piece is where file-based libraries need discipline. Because KiCad libraries are just files, they should live in the same version control system as the project, with the library revision pinned to the project revision. A symbol or footprint change is a design change and should go through the same review and change-control process as a schematic edit. Where possible, a database-backed library front-end (or a script that generates the KiCad libraries from a controlled source) reduces the risk of someone editing a library file directly and silently changing a part across projects.

- How would you catch a situation where a footprint was edited in the library after a board was released, so that the released design no longer matches what's in the library today?
- If two projects share a library and one project needs a variant the other doesn't, how do you avoid forking the library?

## Q2: How would you approach setting up a power integrity simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?

**Answer:** The first step is to define what question the simulation is actually answering. "Is the PDN good?" is not a question a simulator can answer. The useful questions are narrower: what is the impedance of the PDN from the regulator output to the analog load across frequency, where are the anti-resonances between decoupling stages, and how much of the switching regulator's ripple and its harmonics actually reach the analog supply pins. Each of those maps to a specific simulation setup and a specific acceptance criterion.

For a mixed-signal board, the workflow typically starts with a DC/AC impedance sweep of the PDN — extracting the plane and trace parasitics, adding the capacitor models with their ESR and ESL, and looking at the impedance profile from the regulator's control loop bandwidth up to the frequencies where the analog front-end is sensitive. The goal is to keep the impedance below a target derived from the allowable ripple current and the analog circuit's supply rejection. Then a transient simulation with the actual switching waveform confirms whether the resonant peaks identified in the AC sweep translate into real ripple at the load.

The trustworthiness question is the important one. Simulation results are only as good as the models and the extraction. Capacitor models that ignore ESL will hide high-frequency anti-resonances. Plane extraction that doesn't include the via transitions will miss the inductance that dominates at higher frequencies. So the discipline is: identify which physical effects the model captures and which it doesn't, and treat results outside the model's valid range as indicative rather than quantitative. The results worth acting on are the ones that are consistent across two independent methods — for example, an AC impedance peak that also shows up as a transient ringing frequency in a time-domain simulation, and that is corroborated by a bench measurement on a prototype. Anything that only appears in one simulation, with no measurement to confirm it, is a hypothesis to test, not a design change to make.

**Possible follow-ups:**
- How would you decide where to place the boundary between the "digital" and "analog" portions of the PDN, and what would you do at that boundary?
- If the simulation says the PDN is fine but the bench measurement shows excessive ripple at the analog supply, how would you reconcile the two?

## Q3: How would you approach using a spectrum analyzer with a near-field probe to locate the source of a radiated emissions failure at a specific frequency during pre-compliance testing, and how would you confirm which component is responsible?

**Answer:** The near-field probe is a localization tool, not a compliance measurement — it tells you where the field is strong, not whether the product will pass. So the workflow starts by accepting that limitation and using the probe to narrow the search space, then confirming with a proper measurement.

The first step is to characterize the failing frequency itself. Is it a narrowband CW-like peak, or is it broad and modulated? A narrowband peak suggests a clock harmonic or a switching regulator fundamental; a broad or modulated emission suggests something with a spread-spectrum or data-dependent component. That distinction alone often points to a category of source before any probing happens.

Then the probe work: scan the board systematically, keeping the probe orientation and height consistent so that relative amplitudes are meaningful. The strongest field is not always at the source — it can be at a cable, a connector, or a slot in the enclosure that acts as an unintentional antenna. So the scan should cover the board, the cables, and the enclosure seams. When a hotspot is found, the confirmation step is to perturb the suspected source and watch the spectrum: change the clock frequency slightly, disable the regulator, or add a temporary ferrite or shield, and see whether the peak moves or drops. If it does, the source is confirmed. If it doesn't, the hotspot was a coupling path, not the source.

The final confirmation is a proper measurement — a calibrated antenna in a known configuration, or a pre-compliance scan in an anechoic or semi-anechoic environment — because the near-field probe's coupling is not calibrated and its absolute readings are not comparable to a limit line. The probe gets you to the right component; the calibrated measurement tells you whether you've actually fixed the problem.

**Possible follow-ups:**
- How would you distinguish between an emission that originates on the board and one that is coupled onto a cable and radiated from there?
- What would you do if the hotspot moves when you move the probe, suggesting the probe itself is loading the circuit?

## Q4: How would you approach configuring a Segger J-Link for a Zephyr RTOS target where an automated test harness needs to flash the device, run a test sequence, and capture a crash dump without manual intervention — and what failure modes would you design around?

**Answer:** The goal is a deterministic, repeatable sequence that a CI system can invoke without a human in the loop, so the design starts with the interface between the harness and the J-Link. The J-Link Commander scripting interface or the J-Link SDK gives scriptable control over connect, flash, reset, and halt, and that is what the harness should drive rather than relying on an IDE. The Zephyr side needs to expose a stable way to signal test completion and to leave a crash dump somewhere the harness can retrieve — typically a known RAM region or a flash partition that the harness reads back over the debug interface after the run.

The failure modes are where most of the engineering effort goes. The first is target state: the device may be in a low-power mode, a hard fault loop, or a state where the debug interface is disabled by firmware. The harness needs a recovery path — a connect-under-reset sequence, a mass erase fallback, or a hardware reset line under J-Link control — so that a failed run doesn't leave the target in a state that blocks the next run. The second is timing: flashing and reset take variable time, and the harness must wait on a deterministic signal (a GPIO toggle, a debug register write, or a known string on a UART) rather than a fixed sleep. The third is crash capture: if the target hard-faults, the harness needs to halt and read the fault registers and stack before anything else overwrites them, which means the crash handler and the harness have to agree on where the dump lives and how it's marked valid.

Finally, the whole sequence should be idempotent and self-checking. Each run should verify the flash image it wrote, confirm the target actually started, and record enough context (J-Link log, target reset reason, dump contents) that a failure can be diagnosed without re-running. The harness should also detect the "silent failure" case — where the target appears to run but the test never completes — with a timeout that captures the target state rather than just aborting.

**Possible follow-ups:**
- How would you handle a target that occasionally fails to connect because the firmware disables the debug pins early in boot?
- What would you log from each run so that an intermittent failure can be diagnosed after the fact?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the Altium Designer output job configuration for a medical device PCB release, and you discover the fabrication outputs are missing the drill table and the assembly drawings reference an outdated revision of the schematic. The board house is expecting the files tomorrow, and the engineer is confident the outputs are complete because "the Gerbers look fine." How would you handle this situation?

**Answer:** The immediate priority is the release, not the conversation. The outputs are wrong, the board house is waiting, and the fix is mechanical — regenerate the output job with the drill table included and the assembly drawings pointed at the current schematic revision, then verify the package against the release checklist before it goes out. That happens first, and it happens with the junior engineer involved rather than around them, because the point is to fix the process, not just the files.

The conversation comes next, and the framing matters. "The Gerbers look fine" is a reasonable statement from someone who has been taught that Gerbers are the deliverable. The gap is that a fabrication and assembly release is a package, not a single file type, and each element of the package serves a different consumer — the board house needs the drill data, the assembler needs the drawings and the BOM, and the regulatory file needs all of it to be traceable to a specific design revision. So the conversation is about what the package is for, not about who made a mistake. I'd walk through the release checklist with them, item by item, and show where each artifact goes and who uses it.

The process fix is to make the checklist the gate rather than a person's memory. An output job in Altium can be configured to produce the full package in one action, and the release should not be considered complete until someone has verified the package against the checklist — ideally with a second pair of eyes for a medical device release. I'd also make sure the engineer owns the next release end-to-end, with the checklist as their tool, so the lesson is learned by doing rather than by being told. The goal is a team that catches this before it reaches the board house, not a team that is afraid to press the release button.

**Possible follow-ups:**
- How would you structure the release checklist so that it's actually used rather than skipped under schedule pressure?
- If the board house had already started fabrication with the incomplete package, how would that change your approach?
