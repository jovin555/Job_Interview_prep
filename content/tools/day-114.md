## Q1: How would you approach setting up a Gerber and drill-file verification workflow in Gerbv for a medical device PCB, so fabrication issues are caught before the files leave for the board house?

**Answer:** I'd treat Gerbv as the independent "second set of eyes" that doesn't share the CAD tool's assumptions, and build a fixed checklist rather than an ad-hoc eyeball pass. The workflow starts with generating a complete, self-consistent output set from the CAD tool — every copper layer, soldermask, silkscreen, paste, board outline, and the drill files (both plated and non-plated, in the format the fab expects). Then in Gerbv I load all layers together and step through checks in a fixed order: first the board outline as a closed, correctly-dimensioned contour with no gaps or stray segments; then layer-to-layer registration, confirming drill hits land inside pads and vias on every copper layer and that soldermask openings align with pads; then drill verification, checking the drill table against the fab's capability and confirming no drill falls outside the board or too close to an edge; then silkscreen, looking for text over pads or off-board; then a final "what's missing" pass — is there a layer the fab needs that isn't in the set? I'd also compare against the previous revision's output set to spot unintended changes. The key discipline is that the checklist is written down and the same every time, so a tired engineer at 6 p.m. before a release doesn't skip a step. Anything ambiguous gets flagged to the fab's DFM contact rather than assumed.

**Possible follow-ups:** How would you catch a drill file that's in the wrong units or has the wrong number of decimal places? What would you do if Gerbv showed a discrepancy you couldn't explain from the CAD source?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is that the build is reproducible and that every setting that affects the binary is explicit and under version control, not buried in a GUI default. I'd start by treating the project file itself as a reviewed artifact — checked into version control and diffed like source code, so any change to optimization, defines, or include paths shows up in review. Optimization level I'd set deliberately per build configuration (a debug configuration at low or no optimization for debuggability, a release configuration at the level the team has validated), and I'd document *why* each level was chosen, because optimization can change timing and expose latent undefined behavior. The linker script and startup file I'd pull into the project as explicit, versioned files rather than accepting IDE-generated ones, and I'd verify the memory map — flash and RAM regions, stack and heap placement, any reserved regions for calibration or bootloader — against the actual part and the product requirements. I'd add a post-build step that emits the map file and size report so the build log records what was actually produced, and I'd make the build fail loudly on warnings that matter. Finally, I'd confirm the toolchain version is pinned and recorded, since a compiler upgrade can silently change code generation.

**Possible follow-ups:** How would you prove to an auditor that a released binary was built from the tagged source with the documented settings? What's your approach when a debug build behaves differently from a release build?

## Q3: How would you approach setting up a Segger J-Link's RTT (Real-Time Transfer) logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?

**Answer:** RTT is attractive here precisely because it uses the debug probe's memory-access channel rather than a peripheral, so it doesn't consume the UART and doesn't require pins that are already committed. The setup: enable the RTT backend in the logging configuration, size the up-buffer and down-buffer deliberately, and decide the RTT mode — "no block" so the target never stalls waiting for the host to drain the buffer, accepting that messages can be dropped under burst load, versus blocking mode where you get every message but risk perturbing timing. For a safety-critical system I'd default to non-blocking and treat dropped messages as a signal to increase buffer size or reduce log volume, not as acceptable data loss in a test. To avoid perturbing timing, I'd keep the logging calls off the hot path and out of interrupt context where possible, use deferred logging so formatting happens in a low-priority thread rather than inline, and measure the actual cost — toggle a GPIO around the log call and look at it on a scope, or compare cycle counts with logging on versus off. I'd also verify that the RTT control block placement in RAM doesn't collide with anything and that the buffer sizes are accounted for in the memory budget.

**Possible follow-ups:** How would you detect that RTT logging is dropping messages without adding instrumentation that itself changes behavior? What would make you decide RTT is the wrong tool and reach for something else?

## Q4: How would you approach setting up a power integrity simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?

**Answer:** I'd frame the question first: what am I actually trying to learn? Usually it's whether the impedance of the power distribution network is low enough across the frequencies the analog front-end cares about, and whether the switching regulator's ripple and its harmonics couple into the analog supply in a way that degrades performance. So the workflow starts with an accurate model of the PDN — stackup with real dielectric and copper thickness, plane shapes, via transitions, and the decoupling network with realistic component models including ESR/ESL and mounting inductance, because at high frequency the capacitor's parasitics dominate and an ideal-capacitor model will lie to you. I'd drive it with the regulator's ripple as a source and look at transfer impedance from the regulator's output to the analog load point, plus a self-impedance plot of the PDN at the analog supply pins. On trustworthiness: I'd sanity-check the model against measurement before acting on any result — measure the actual PDN impedance with a VNA or a network analyzer setup on a bare board if possible, and compare the simulated resonance peaks to measured ones. If the simulation predicts a resonance the measurement doesn't show, the model is wrong somewhere and I fix that before trusting the next simulation. I'd also check convergence and mesh sensitivity, and be explicit about what the simulation does *not* capture — radiated coupling, for instance, isn't in a PDN impedance sim.

**Possible follow-ups:** How would you decide where to place decoupling capacitors when the simulation shows a resonance in a band the analog front-end cares about? What's the risk of over-trusting a PDN simulation that was never correlated to measurement?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the Altium Designer output job configuration for a medical device PCB release, and you discover the fabrication outputs are missing the drill table and the assembly drawings reference an outdated revision of the schematic. The board house is expecting the files tomorrow, and the engineer is confident the outputs are complete because "the Gerbers look fine." How would you handle this situation?

**Answer:** First priority is the schedule: I'd separate "fix the release" from "address the process failure," and do the fix immediately so the board house isn't left waiting. I'd sit down with the engineer, not to assign blame but to walk the output job together and show concretely what's missing — the drill table absent from the set, and the assembly drawings pointing at an older schematic revision — because "the Gerbers look fine" is true and also not the whole question; the release is more than the Gerbers. We'd regenerate the outputs from the correct, tagged revision, run the full verification checklist against them, and get the corrected set to the fab with a clear note about what changed. Then, once the release is out the door, I'd address the root cause: the output job configuration should be a reviewed, version-controlled artifact with a written checklist that covers *every* deliverable, not just the copper layers, and the release should require a second pair of eyes. I'd also want to understand whether the engineer was given a checklist and skipped it, or was never given one — those are different problems with different fixes. Throughout, I'd keep the tone that this is a process gap we're closing together, because a junior engineer who feels punished for surfacing a problem will hide the next one.

**Possible follow-ups:** How would you make the release checklist something people actually use rather than rubber-stamp? What would you change so a single missing deliverable can't slip through again?
