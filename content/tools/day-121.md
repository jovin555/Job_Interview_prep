## Q1: How would you approach setting up a logic analyzer's protocol decoder for a Manchester-encoded sensor bus where the clock is embedded in the data stream, so there's no separate clock line to trigger on — and how would you verify the decoder is actually interpreting the framing correctly before trusting it?

**Answer:** Manchester encoding is the classic case where a standard SPI/I2C/UART decoder won't help because there's no separate clock — the transition in the middle of each bit period *is* the clock. The approach is to build the decode in two layers. First, get the physical layer right: set the sample rate high enough to resolve the shortest pulse (a Manchester bit period is half a full bit cell, so the sample rate needs to be at least 10–20× the bit rate to catch the mid-bit transition reliably), and set the threshold at the actual mid-rail of the signaling, not a default. Then use the analyzer's clock-recovery or "Manchester" decode mode if it has one, or build a custom decoder that detects edges, classifies each edge as rising or falling to recover the bit value, and reconstructs the bit stream from the edge timing. The key discipline is to *not* trust the decoder output until you've cross-checked it against the raw waveform: pick a known-good frame — a preamble, a sync word, or a command you can predict — and step through the decoded bits against the analog trace by eye. If the decoder shows a valid-looking frame but the bit boundaries drift relative to the actual transitions, the clock recovery is wrong. I'd also test it against a deliberately corrupted frame to confirm the decoder flags errors rather than silently producing garbage. Only after the decoder reproduces a known frame bit-for-bit do I use it to debug the unknown behavior.

**Possible follow-ups:** How would you handle a Manchester stream where the transmitter's bit rate drifts slightly over temperature — would you re-tune the decoder or build in tolerance? What would you do if the decoder works on short frames but loses sync on long ones?

## Q2: How would you approach configuring a Keil uVision project so that the optimization level, linker script, and startup code are locked down and auditable, rather than left at whatever the IDE defaults to?

**Answer:** The problem with IDE defaults is that they're invisible and they drift — a new team member opens the project, the toolchain version changes, and suddenly the optimization level or the scatter file is different from what was validated. The fix is to make every build-affecting setting explicit and version-controlled. Concretely: pin the toolchain version and record it in the project, set the optimization level explicitly per target (and document *why* — e.g., `-O0` for debug builds so variables aren't optimized away during stepping, a defined level for release), and check the linker/scatter file into the repo rather than letting the IDE generate one. The startup code should be a reviewed, versioned source file, not a regenerated stub. Then make the build reproducible: a clean checkout plus a documented build command should produce a byte-identical or at least functionally identical image, and the map file should be archived with each release so you can audit memory layout after the fact. For a regulated medical build, I'd also add a build manifest — toolchain version, optimization flags, linker script hash, git commit — so the artifact is traceable to its exact configuration. The audit test is simple: hand the project to someone else and have them reproduce the release image without asking you any questions. If they can't, the configuration isn't locked down.

**Possible follow-ups:** How would you catch a case where someone changed the optimization level locally but the committed project file still says otherwise? What's your approach when a vendor library ships with its own startup file that conflicts with yours?

## Q3: How would you approach setting up a power integrity simulation workflow for a mixed-signal PCB where a high-current switching regulator and a precision analog front-end share the same power distribution network, and how would you decide which results are trustworthy enough to act on?

**Answer:** The core risk is that the switching regulator's ripple and transient current draw couple into the analog front-end through a shared PDN, so the simulation has to model the PDN as a network — not just the regulator in isolation. I'd start by building an accurate model of the PDN: stackup and copper geometry from the layout, the regulator's output impedance and switching behavior, the decoupling network with realistic ESR/ESL (including mounting inductance, which is often the dominant term), and the analog load's current profile. Then run AC impedance analysis to find the PDN's resonant peaks and confirm the impedance at the analog supply pins is low enough across the band the front-end cares about, and transient analysis to see how a load step on the digital side propagates to the analog rail. The trust question is the important one: simulation results are only as good as the models, so I'd validate against measurement — inject a known load step and measure the actual rail with a properly probed scope (short ground lead, bandwidth-limited to avoid picking up probe artifacts), and compare the measured transient to the simulated one. If they diverge, the model is wrong somewhere — usually the decoupling parasitics or the regulator's loop response. I'd only act on simulation results that have been anchored to at least one real measurement, and I'd treat absolute numbers with suspicion while trusting relative comparisons (this decoupling change vs. that one) more readily.

**Possible follow-ups:** How would you decide where to place the boundary between "on-die/on-package" and "on-board" decoupling in the model? What would you do if the simulation says the PDN is fine but the bench measurement shows ripple on the analog rail?

## Q4: How would you approach setting up a cross-probe workflow between OrCAD Capture and Cadence Allegro so a layout review can move efficiently between schematic and PCB, and what would you check to confirm the link actually works before relying on it in a review?

**Answer:** Cross-probing is one of those features that looks trivial until it silently fails mid-review and you waste an hour hunting for a net. The setup is: both tools open on the same design database, cross-probe enabled in both, and the design synced so the netlist and component references match. But the real work is the verification *before* the review. I'd test it in both directions — select a component in the schematic and confirm it highlights the correct footprint in Allegro, then select a net in Allegro and confirm it highlights the right pins in Capture. I'd test a multi-part component (where reference designators get confusing), a net that spans several pages, and a component that was recently added or renamed, because those are the cases where the link breaks. I'd also confirm the two tools are pointed at the same revision — a stale sync is the most common cause of "it highlights the wrong thing." Only once those checks pass do I trust it in a live review. If it's flaky, I'd rather fall back to a documented net-name lookup than have the review stall on a tooling glitch.

**Possible follow-ups:** What would you do if cross-probing works for components but not for nets? How would you handle a review where the schematic and layout are on different machines?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** The first thing is to separate the person from the problem — the engineer isn't being careless, they're applying a reasonable intuition ("the peaks show up either way") that happens to be wrong for a compliance measurement, and that's a teaching moment, not a discipline moment. I'd sit down with them and explain *why* the settings matter: resolution bandwidth affects the measured amplitude of narrowband emissions and the noise floor, the detector (quasi-peak vs. peak vs. average) changes what the standard actually requires you to report, and without correcting for antenna and cable losses the absolute levels are meaningless. The "peaks show up either way" observation is true but irrelevant — a peak that reads 3 dB low because of the wrong RBW can turn a pass into a fail or vice versa. Then the practical question: can we fix it in time? Re-running the scan with correct settings is usually a matter of minutes once the setup is right, so I'd re-configure and re-scan rather than cancel the lab time. If the corrected scan reveals a marginal result, that's exactly the information we needed before the formal test, and it's better to find it now. Afterward, I'd document the correct setup — RBW, detector, correction factors, probe positioning — as a checklist so the next scan starts from a known-good configuration rather than a tutorial.

**Possible follow-ups:** How would you handle it if the engineer pushed back and said the corrected settings would take too long to re-run? What would you change in the team's process so this doesn't recur on the next pre-compliance scan?
