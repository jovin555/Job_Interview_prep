## Q1: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** The first step is to resist the temptation to start writing a decoder immediately. I'd begin by capturing raw transitions on the bus and manually annotating a few known-good transactions against the protocol specification, so I have a ground-truth reference before any automation exists. From there, I'd decide whether the protocol can be expressed as a layered decoder — a low-level layer that extracts clock/data or start/stop framing, and a higher layer that interprets the payload — because most logic analyzer frameworks (Saleae, sigrok, etc.) support decoder stacking, and separating physical framing from semantic decoding makes the decoder far easier to debug and reuse.

For a non-byte-aligned header, the key is to treat the bitstream as a continuous bit sequence and define the header as a bit-length field rather than assuming byte boundaries. I'd write the decoder to first synchronize on a known preamble or start pattern, then consume a fixed number of bits for the header, then use a length field to know how many bits to consume for the payload. I'd add explicit error states — framing error, checksum mismatch, timeout — rather than silently emitting garbage, because a decoder that fails loudly is far more useful during bring-up than one that produces plausible-looking wrong data.

I'd validate the decoder against at least three categories of capture: a clean nominal transaction, a transaction with an injected bit error, and a boundary case like a maximum-length payload. I'd also version-control the decoder alongside the firmware protocol definition so that when the protocol changes, the decoder change is reviewed in the same commit. Finally, I'd document the decoder's assumptions in a header comment — clock polarity, bit order, sync pattern — because six months later the person debugging a field issue may not be the person who wrote it.

**Possible follow-ups:**
- How would you handle a protocol where the clock is embedded in the data (e.g., Manchester or a self-clocked line) rather than a separate clock line?
- If the decoder works on your bench capture but fails on a customer's unit, what would you suspect first?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The core problem with IDE-managed build settings is that they live in a project file that's easy to change accidentally and hard to review in a diff. My approach is to treat the build configuration as a first-class artifact: the optimization level, preprocessor defines, include paths, linker script selection, and startup file should all be explicit, documented, and ideally generated or checked rather than clicked into a dialog.

Concretely, I'd start by identifying which settings are safety-relevant. Optimization level is the classic example — `-O0` versus `-O2` can change timing, stack usage, and even expose latent undefined behavior, so for a regulated medical device the optimization level used for verification must match the level used for release, and any change must trigger re-verification. I'd pin that in the project file and add a build-time check — a pre-build script or a CI step — that fails the build if the optimization level doesn't match the expected value.

For the linker script and startup code, I'd keep them under version control as separate files referenced by the project, not embedded in the project file, so their history is visible. I'd also add a post-build step that extracts and archives the actual compiler command line, the linker map file, and a hash of the source tree, so the released binary is traceable back to an exact configuration. That map file is also invaluable for verifying that critical data — calibration constants, for instance — land in the flash region you intended, rather than being silently relocated by a linker script change.

Finally, I'd make the project file itself reviewable by keeping it text-based where possible and by documenting any settings that must not be changed without a formal change request. The goal is that a new engineer can open the project, see exactly what's pinned and why, and not be able to accidentally ship a build that doesn't match what was verified.

**Possible follow-ups:**
- How would you detect at build time that a developer had changed the optimization level locally without updating the documented configuration?
- What's your approach to verifying that calibration data stored in flash is not overwritten by a firmware update, given the linker script controls the memory map?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** A tracking generator plus directional coupler gives you a scalar return-loss measurement — essentially, how much of the incident signal is reflected back — and from that you can infer impedance magnitude, though not phase. The setup matters enormously: the directional coupler's directivity sets the floor of what you can measure, so if the coupler has 20 dB directivity, you cannot trust return-loss readings better than about 20 dB regardless of what the analyzer displays. I'd calibrate the setup first with an open, a short, and a 50-ohm load at the reference plane, and I'd keep the reference plane as close to the device under test as possible, because any cable or connector between the calibration plane and the DUT adds its own impedance transformation.

For a custom analog front-end, the input impedance is often frequency-dependent and may be deliberately mismatched — a high-impedance sensor input, for example, is not a 50-ohm system, so a direct 50-ohm return-loss measurement tells you about the input network's behavior in a 50-ohm environment, not necessarily about its behavior in the actual application. I'd interpret the result with that in mind: the measurement is most useful for spotting resonances, unexpected parasitic capacitance, or a component that's the wrong value, rather than for claiming a precise impedance number.

Deciding whether to act on the result comes down to repeatability and cross-checking. I'd repeat the measurement with the DUT powered off and powered on, because an active front-end can present a different impedance depending on bias. I'd cross-check any suspicious feature against a simulation of the input network, and against a time-domain measurement — a fast step or pulse into the input, observed on a scope — to see whether the reflection behavior is consistent. If the scalar measurement and the time-domain measurement disagree, I'd trust the time-domain result more for transient behavior and treat the scalar result as a frequency-domain sanity check. Only when two independent methods agree would I consider a design change justified.

**Possible follow-ups:**
- How would you extend this to a full complex impedance measurement if you needed phase information?
- What would cause a return-loss measurement to look clean on the bench but the front-end to behave poorly in the actual system?

## Q4: How would you approach setting up a Segger J-Link's RTT (Real-Time Transfer) logging for a Zephyr RTOS target where you need continuous debug output but the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?

**Answer:** RTT is attractive here precisely because it uses the debug interface's memory access rather than a peripheral, so it doesn't consume a UART or add a physical connection. The setup is straightforward — the target firmware links an RTT control block and writes to a ring buffer, and the host-side J-Link software reads that buffer over SWD/JTAG — but the interesting part is making it safe for a system with real-time constraints.

The first concern is where the RTT buffer lives. If it's in RAM, it competes with the application for memory, and if the buffer is too small, the target either blocks when full or drops messages depending on the mode. For a safety-critical system, I'd configure RTT in non-blocking mode so the target never stalls waiting for the host to read, and I'd size the buffer generously enough that normal logging bursts don't overflow, while accepting that under extreme conditions messages may be dropped. Dropped debug messages are far preferable to a timing violation in the application.

The second concern is the cost of the logging call itself. Even a non-blocking RTT write takes some cycles — a memcpy into the ring buffer and an index update — and if that happens inside a time-critical ISR or a control loop, it can perturb timing. My approach is to keep RTT logging out of hard real-time paths entirely, or to gate it behind a compile-time flag that's off in production builds. For the paths where I do want visibility, I'd log a compact event ID and a timestamp rather than a formatted string, and do the string formatting on the host side, because formatting on the target is where most of the cycle cost and stack usage hides.

The third concern is verifying that logging isn't perturbing the system. I'd measure a known timing-critical operation — a control loop period, an ISR latency — with logging enabled and disabled, using a spare GPIO toggled at the start and end of the operation and observed on a scope. If the measured timing shifts when logging is enabled, the logging is in the wrong place. I'd also watch for the classic RTT pitfall where the host-side reader polls too aggressively and steals debug-interface bandwidth from other debug operations, which can make the system appear to behave differently under the debugger than in the field.

**Possible follow-ups:**
- How would you correlate RTT log timestamps with an external event captured on a scope, so you can align firmware events with hardware behavior?
- What would you do if RTT logging worked on your bench but the target's debug interface was unreliable in the customer's enclosure?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** The immediate priority is to separate the technical question from the interpersonal one, because they need different handling and conflating them makes both worse. Technically, the engineer is partly right — the peaks do show up either way — but the amplitude and the pass/fail verdict depend on resolution bandwidth and detector mode, so a scan with the wrong settings can either miss a marginal failure or flag a false one. That's not a matter of opinion; it's defined by the test standard, and I'd want to walk through the standard's requirements together rather than simply asserting that the settings are wrong.

I'd start by sitting down with the engineer and the relevant section of the test standard, and asking them to show me where the settings they chose are specified. If they can't find it, that's the teaching moment — not "you're wrong," but "let's find the requirement together." If they can find it and it turns out I'm the one misremembering, that's equally important to acknowledge, because credibility on the next disagreement depends on being right when it matters and honest when I'm not.

Practically, I'd assess whether the booked lab time can still be used productively. If the settings can be corrected quickly — many analyzers let you save and recall setups — then the scan can proceed tomorrow with the correct configuration, and the junior engineer can be the one to make the change, which turns the mistake into a learning experience rather than a reprimand. If the correction requires re-calibration or additional setup that won't fit the booked slot, I'd rather reschedule or use the slot for a preliminary scan clearly labeled as non-formal, than submit results that don't meet the standard. A pre-compliance scan that doesn't match the standard's methodology isn't evidence of anything, and treating it as if it were is how marginal failures slip through.

Afterward, I'd look at the process gap that allowed this to happen. If a junior engineer is setting up a formal scan, there should be a checklist or a peer review step that catches configuration errors before the lab time is spent. Adding that check is more valuable than any individual correction, because it prevents the next instance regardless of who's setting up the equipment.

**Possible follow-ups:**
- How would you handle it if the engineer became defensive and felt you were questioning their competence rather than the settings?
- What would you change in the team's process to make sure the next pre-compliance scan starts from a verified configuration?
