## Q1: How would you approach setting up a schematic symbol library in Altium Designer so that symbols stay consistent and traceable across a multi-year medical device program, where the same part may be reused across several board revisions?

**Answer:** The core problem is that a symbol library is a living artifact, not a one-time deliverable, so the strategy has to make drift visible and make the correct version the path of least resistance. I'd start by deciding on a single controlled library location — either a managed content server or a version-controlled library repository — rather than letting symbols accumulate in per-project folders. Every symbol gets a unique internal part number and a revision, and the symbol's parameters carry the manufacturer part number, the datasheet revision it was drawn from, and a link to the approved-vendor entry. The symbol graphics follow a house convention: pin grouping by function, power pins placed consistently, pin names matching the datasheet exactly, and electrical type set correctly so ERC is meaningful. For multi-year programs, the important discipline is that a released board revision references a specific library revision, not "latest" — so when a part is updated, existing designs don't silently change underneath. I'd also keep a change log per symbol and require a review before a symbol revision is promoted, because a wrong pinout caught in schematic review is cheap and caught in fabrication is not. Finally, I'd periodically audit the library against the BOMs of active projects to catch orphaned or duplicated parts before they multiply.

**Possible follow-ups:** How would you handle a situation where a manufacturer changes a part's pinout but keeps the same part number? What would you put in the symbol's parameters to make a future auditor's job easier?

## Q2: How would you approach setting up a constraint manager in Cadence Allegro for a mixed-signal PCB that has both high-speed digital interfaces and sensitive analog sensor inputs, and how would you verify the constraints are actually being honored?

**Answer:** I'd structure the constraint manager in layers, because a mixed-signal board has two very different kinds of electrical intent that shouldn't be expressed in the same way. First, the physical/electrical constraint sets: for the high-speed digital nets, impedance targets, propagation delay and length-matching windows, and differential pair rules where applicable; for the analog nets, a separate class with rules that are mostly about *isolation* — minimum spacing to aggressor nets, keepout from switching nodes, and routing-layer restrictions so analog traces don't run parallel to digital ones for long distances. I'd define net classes explicitly rather than relying on defaults, and I'd set up a region-based or room-based rule so the analog section has its own clearance and spacing regime. The verification step is the part people skip: constraints that are defined but not enforced are worse than no constraints, because they create false confidence. So I'd run the DRC with the constraint-driven rules enabled and actually read the violations rather than waiving them in bulk, and I'd do a targeted check — pick a handful of critical nets and measure the actual routed length, spacing, and impedance-relevant geometry against the rule, rather than trusting the report alone. I'd also confirm the constraint set is version-controlled alongside the design so a later revision doesn't quietly inherit stale rules.

**Possible follow-ups:** How would you decide the spacing rule between an analog sensor trace and a switching regulator's output? What would make you suspect a constraint isn't actually being applied to a net?

## Q3: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is reproducibility: a given source revision plus a given toolchain version should produce a bit-identical or at least functionally identical image, and an auditor should be able to see exactly what settings produced a released binary. I'd start by treating the project file itself as a controlled artifact — checked into version control, reviewed on change, and not edited casually in the IDE GUI without that change being visible in a diff. The optimization level, the linker script path, the startup file, and the preprocessor defines all get set explicitly and documented, with a short rationale for each (for example, why a particular optimization level was chosen and what was verified at that level). I'd pin the toolchain version and record it in the build notes, because compiler behavior changes between versions and "it built last year" is not the same as "it builds the same way." For auditability, I'd make the build emit a map file and a symbol listing, and archive those with the release so the memory layout can be reconstructed later. I'd also add a build-time check — a script or a post-build step — that fails the build if the linker script or startup file hash doesn't match the expected value, so a silent substitution gets caught rather than discovered during a regulatory review.

**Possible follow-ups:** Why does the optimization level matter for a medical device beyond performance? How would you handle a situation where a debug build and a release build behave differently?

## Q4: How would you approach using a spectrum analyzer with a near-field probe to locate the source of a radiated emissions failure at a specific frequency during pre-compliance testing, and how would you confirm which component is responsible?

**Answer:** The near-field probe is a localization tool, not a compliance measurement — its absolute amplitude means little, but its *relative* response as you move it around the board is very informative. I'd start by setting the analyzer to a span wide enough to see the failing frequency in context, with a resolution bandwidth appropriate for distinguishing the emission from nearby noise, and I'd note the exact frequency and its relationship to known clock and switching frequencies on the board. Then I'd systematically scan the board with the probe, starting coarse and narrowing down, watching for the spot where the amplitude peaks. The confirmation step is where rigor matters: a peak near a component isn't proof that component is the source. I'd test the hypothesis by perturbation — for example, temporarily changing a switching frequency or gating a clock and seeing whether the emission moves or disappears in the predicted way. I'd also check whether the emission tracks a harmonic of a candidate source across a range of frequencies, not just at the one failing point, because a single point can be coincidental. If two candidates share a harmonic at that frequency, the perturbation test is what separates them. Only after the source is confirmed would I move to mitigation, and I'd re-measure to verify the fix actually reduced the emission rather than just shifting it.

**Possible follow-ups:** Why is a near-field probe's absolute reading not trustworthy for compliance? What would you do if the emission persists even with the suspected source powered down?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** My first move is to separate the technical issue from the interpersonal one, because both need addressing and conflating them makes each worse. Technically, the engineer isn't wrong that the peaks show up — the problem is that the *amplitude* and the *decision* depend on the settings, and a scan with the wrong resolution bandwidth and detector can under- or over-report a margin, which is exactly the number the formal scan exists to produce. So I'd explain the "why" concretely rather than just asserting authority: show what changes when the settings are corrected, and let the measurement demonstrate the point. That respects the engineer's observation while correcting the conclusion. On the schedule: the lab time being booked is a real constraint, but submitting a scan with known-wrong settings to a formal record is worse than a short delay, so I'd check whether the correct settings can be applied and the scan re-run within the existing booking — often the fix is minutes, not a reschedule. If it genuinely can't be salvaged in time, I'd escalate the scheduling decision rather than quietly accepting bad data. Afterward, I'd treat it as a process gap, not just an individual mistake: a written scan-setup checklist tied to the applicable standard would have caught this before it reached me, and that's the durable fix.

**Possible follow-ups:** How would you deliver the correction so the engineer doesn't feel undermined in front of the team? What would you put on the scan-setup checklist to prevent a repeat?
