## Q1: How would you approach setting up a schematic symbol library in Altium Designer so that symbols stay consistent and traceable across a multi-year medical device program, where the same part may be reused across several board revisions?

**Answer:** I'd treat the symbol library as a controlled asset rather than a folder of files. The foundation is a single managed library — either a database library or a version-controlled schematic library under a defined folder structure — with a naming convention that encodes part family, package, and a unique internal part number, so a symbol can be found and referenced unambiguously years later. Each symbol should carry the parameters that matter for traceability: manufacturer part number, internal part number, tolerance/rating, lifecycle status, and a link to the datasheet revision that was used to create it. For a medical program, I'd also add fields for the regulatory-relevant attributes (e.g., whether the part is on a critical component list) so a BOM can be filtered for impact analysis.

The key discipline is that symbols are never edited in place once released — a change creates a new revision, and the schematic references that revision. That way, when a part is reused across several board revisions, you can always answer "which symbol revision was on which board." I'd pair this with a review step for new symbols (pin numbering, pin type, footprint mapping checked against the datasheet) and a periodic audit that flags symbols whose lifecycle status has gone obsolete. The goal is that the library becomes the single source of truth, and the schematic is just an instance of it.

**Possible follow-ups:** How would you handle a situation where a symbol needs a correction but it's already used on a released board? What's your approach to migrating an existing ad-hoc library into a managed one without breaking current projects?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The principle is that the build configuration must be an explicit, reviewed artifact — not something a developer can silently change in the IDE. I'd start by defining the target settings in the project file itself and treating that file as source-controlled, so any change to optimization level, linker script path, or startup file shows up as a diff in review. Optimization level in particular is a safety-relevant choice: it affects timing, stack usage, and whether certain code gets reordered or elided, so it should be pinned per build configuration (e.g., a debug target at low optimization for traceability, a release target at the validated level) and documented with the rationale.

For the linker script and startup code, I'd keep them in the repository alongside the project, reference them by relative path, and add a build-time check — a script or a pre-build step — that verifies the resolved paths and key settings match an expected manifest. That catches the case where someone's local IDE has drifted. I'd also make the build reproducible: same toolchain version, same flags, and ideally a CI job that builds from a clean checkout and archives the map file and the exact configuration used. For a medical device, the archived build configuration is part of the evidence that the shipped binary corresponds to the validated source.

**Possible follow-ups:** How would you detect that a developer's local build differs from the CI build? What would you do if a late-stage optimization change was needed for timing reasons after validation had started?

## Q3: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** When no built-in decoder fits, I'd first capture raw transitions and characterize the physical layer before writing any decoder logic: confirm the clock (if synchronous) or the bit period (if asynchronous), identify the idle level, and find the frame boundary by looking for the repeating pattern in the capture. The non-byte-aligned header is the tricky part — it means I can't just slice the capture into bytes at arbitrary offsets, so I need to establish the exact bit offset where the frame starts and treat the header as a bit-field rather than a byte field.

From there I'd build the decoder in layers. First, a bit-level layer that samples at the correct point in each bit cell (accounting for any clock drift over a long frame). Second, a field-extraction layer that maps bit ranges to named fields — header, address, payload, CRC — using the protocol spec as the reference. Third, a validation layer that checks the CRC or checksum and flags frames that fail, so I can distinguish "decoder is wrong" from "device sent a bad frame." I'd validate the decoder against a known-good capture first — ideally a frame I can also see on an oscilloscope and reason about by hand — before trusting it on intermittent failures. For a medical device, I'd also document the decoder configuration so the analysis is reproducible and reviewable.

**Possible follow-ups:** How would you handle a protocol where the bit rate varies slightly between devices or with temperature? What would you do if the CRC field itself is proprietary and undocumented?

## Q4: How would you approach setting up a spectrum analyzer for a conducted emissions pre-compliance scan on a medical device's AC input, and what would you check before trusting the first measurement?

**Answer:** Before trusting any reading, I'd verify the measurement chain end to end. That starts with the setup: the correct LISN (line impedance stabilization network) for the standard being targeted, the device powered through the LISN, and the analyzer connected via a properly rated cable with known loss. I'd check the LISN's own characteristics and confirm the reference ground is solid — a poor ground reference is one of the most common reasons a conducted scan looks better or worse than reality.

Then I'd validate the analyzer configuration against the test standard: frequency range, resolution bandwidth, detector mode (quasi-peak vs. average vs. peak), and sweep time. A quick "get a feel for it" scan with the wrong RBW or detector will show peaks but won't tell you whether you pass — the limits are defined at specific settings. I'd also run a noise-floor check with the device off to confirm the analyzer and cable aren't contributing, and a sanity check with a known signal or the LISN's calibration port to confirm the chain reads correctly. Only after those checks would I run the actual scan, and I'd record the full configuration so the result is reproducible and defensible.

**Possible follow-ups:** How would you distinguish a real emission from ambient noise picked up by the setup? What would you do if a peak sits right at the limit line and you need to decide whether to redesign or re-measure?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** I'd separate the technical issue from the interpersonal one and deal with the technical issue first, because the schedule is the immediate constraint. I'd sit down with the engineer and walk through why the settings matter — not as a correction, but as a shared look at the standard: the limits are defined at a specific RBW and detector, so a scan at different settings can't be compared to the limit line, and "the peaks show up either way" is exactly the trap, because the peak amplitude and even which peaks appear depend on those settings. Showing the standard's requirement side by side with the current configuration usually makes the point faster than asserting it.

Then I'd fix it pragmatically: reconfigure the analyzer to the required settings, re-run a quick verification scan to confirm the setup is sane, and preserve the original "feel for it" scan as a reference for where to look. If there's time before tomorrow, I'd have the engineer re-run the setup themselves with me reviewing, so the lesson sticks and they own the corrected configuration. I'd avoid framing it as a failure — the engineer did the right thing by getting a first look; the gap was knowing that pre-compliance settings are not interchangeable with exploratory ones. After the scan, I'd add a short checklist to the lab procedure so the next person doesn't hit the same trap.

**Possible follow-ups:** How would you handle it if the engineer pushed back and insisted the settings didn't matter? What would you change in the team's process so this kind of setup error is caught before lab time is booked?
