## Q1: How would you approach setting up differential pair routing constraints in Cadence Allegro for a USB 2.0 interface on a mixed-signal medical device PCB?

**Answer:** For USB 2.0 differential pairs, I would start by defining the physical constraints in the Allegro Constraint Manager. First, I'd set the impedance target — typically 90 ohms differential for USB, which requires calculating the appropriate trace width and spacing based on the PCB stackup (dielectric thickness, copper weight, and material properties like FR4 or a higher-performance laminate if needed). I'd create a differential pair constraint group for the D+ and D- signals, specifying the primary gap and line width, then set the maximum length mismatch (usually within 5-10 mils for USB 2.0 full/high speed) and maximum total length. For a medical device, I'd also consider adding a clearance constraint to keep the pair away from noisy switching regulators or clock traces. I'd use the interactive phase tuning tool to add serpentine delay lines where needed to match lengths, and I'd verify the impedance using the cross-section editor before routing. Finally, I'd run a DRC check specifically on the differential pair rules to catch any violations before the design review.

**Possible follow-ups:** How would you handle the transition from the connector footprint to the differential pair routing, particularly regarding anti-pad sizing on reference planes? What would you do if the stackup provided by your PCB fabricator doesn't match your impedance calculations?

## Q2: Walk me through your process for using LTSpice to simulate the power-on reset behavior of a microcontroller in a battery-powered device, and how you would verify the simulation against real measurements.

**Answer:** I'd start by modeling the power supply chain: the battery model (with appropriate internal resistance and nominal voltage), the voltage regulator (using either a vendor-supplied SPICE model or a behavioral model with the key parameters like dropout voltage, quiescent current, and transient response), and the decoupling capacitor network at the MCU power pins. I'd add a load model that represents the MCU's inrush current during startup — typically a piecewise linear current source that ramps from zero to the active current draw over a few microseconds. The key simulation would be a transient analysis spanning from power application through the reset release threshold. I'd look at the voltage ramp rate at the MCU's VDD pin, checking that it meets the device's power-on reset specifications (monotonic rise, no glitches below the minimum operating voltage). I'd also simulate worst-case scenarios: connecting the battery with a high-ESR connection, or having a partially discharged input capacitor. For verification, I'd set up an oscilloscope with a differential probe (or two single-ended probes in math mode) to capture the VDD ramp and the reset pin simultaneously during battery connection. I'd compare the measured rise time, any ringing, and the voltage level at which the reset releases against the simulation. Discrepancies often point to missing parasitic elements in the model — like trace inductance or capacitor ESR that wasn't accounted for.

**Possible follow-ups:** How would you model the effect of a long battery cable on the startup behavior? What if the simulation shows a voltage dip below the reset threshold during a transient load event after startup?

## Q3: How would you approach using a spectrum analyzer with a near-field probe to locate the source of a 200 MHz clock harmonic that is causing a radiated emissions failure during pre-compliance testing of a medical device?

**Answer:** I'd start by setting up the spectrum analyzer with the appropriate frequency span — centered around the failing harmonic, say 200 MHz, with a span wide enough to see the fundamental and adjacent harmonics (maybe 50 MHz span). I'd set the resolution bandwidth to around 1 MHz for initial scanning, then narrow it once I locate the source. Using a near-field H-field probe (loop type) connected to the analyzer, I'd first do a broad scan over the entire PCB, holding the probe about 5 mm above the board surface and moving systematically from the clock source outward. The goal is to identify hot spots where the amplitude peaks. Once I find a general area, I'd switch to a smaller-diameter probe for better spatial resolution and reduce the probe height to 1-2 mm. I'd pay particular attention to: the clock oscillator itself, the trace routing from the oscillator to the load, any vias that transition between layers, and the edges of ground pours or slots in the ground plane. If the hot spot is along a trace, I'd check whether the return path is interrupted — for example, a gap in the ground plane under the trace or a via that forces the return current to take a long detour. I'd also check connector areas where the clock signal might be coupling to an I/O cable acting as an antenna. Once I identify the physical source, I'd evaluate mitigation options: adding a series termination resistor closer to the source, slowing the edge rate with a ferrite bead, adding a local ground stitch via, or rerouting the trace on an inner layer between ground planes.

**Possible follow-ups:** How would you distinguish between radiated emissions coming from the trace itself versus emissions coupled onto an attached cable? What if the emissions are coming from a BGA package where you can't directly probe the die?

## Q4: How would you approach setting up a Git-based version control workflow for a KiCad project that includes schematic files, PCB layout, 3D models, and a Bill of Materials, ensuring that design reviews and releases are properly tracked?

**Answer:** KiCad files are text-based (the schematic and PCB files are in S-expression format), which makes them well-suited for Git version control, but there are important considerations. First, I'd establish a repository structure with a clear separation: a `hardware/` directory containing the KiCad project files (`.kicad_pro`, `.kicad_sch`, `.kicad_pcb`), a `docs/` directory for the BOM and assembly drawings, and a `mechanical/` directory for 3D models and enclosure files. I'd create a `.gitignore` that excludes auto-generated files like the cache, backup files (`.kicad_back`), and the `fp-info-cache` file, which changes frequently and adds noise to diffs. For the BOM, I'd generate it from KiCad's BOM export tool and commit the CSV or XLSX file, but I'd also maintain a separate YAML or JSON file with manually curated part numbers and sourcing information that doesn't change with every layout tweak. For 3D models, I'd use Git LFS (Large File Storage) to avoid bloating the repository with binary STEP files. The branching strategy would follow a simplified GitFlow: a `main` branch for released designs, a `develop` branch for ongoing work, and feature branches for specific changes (e.g., `fix-usb-routing`, `add-thermal-vias`). Before merging into `develop`, I'd require that the KiCad ERC and DRC pass with zero errors, and that the design has been reviewed by at least one other engineer. Releases would be tagged with version numbers (e.g., `v1.0.0`, `v1.1.0`) and accompanied by a release note summarizing changes. For design reviews, I'd use GitLab or GitHub's merge request feature, where reviewers can comment on specific lines of the schematic or PCB file diffs — though KiCad files are verbose, so I'd also export PDFs of the schematic and layout for easier visual review.

**Possible follow-ups:** How would you handle the situation where two engineers need to work on the same PCB layout simultaneously? What's your approach to resolving merge conflicts in KiCad PCB files?

## Q5: (Behavioral) Imagine you are leading a firmware bring-up for a new medical device prototype, and you discover that the Segger J-Link debugger you planned to use is not compatible with the target microcontroller because the JTAG/SWD pins were accidentally assigned to a different function in the PCB layout. The project is already behind schedule, and the junior engineer who designed the PCB layout is defensive about the error. How would you handle this situation?

**Answer:** First, I'd separate the technical problem from the interpersonal one. Technically, I need to determine if there's a workaround that doesn't require a PCB respin. I'd check if the microcontroller supports a secondary debug interface — some devices have a bootloader mode accessible via UART or USB that can re-enable the SWD pins, or a dedicated debug pin that can be jumpered. If the pins are simply shared with another function (e.g., GPIO), I might be able to hold that pin in the correct state during power-up to enter debug mode, then release it after initialization. If no workaround exists, I'd assess the fastest path to a working prototype: perhaps a small adapter board that breaks out the debug signals from an alternate pin location, or a bodge wire from the debug connector to the correct microcontroller pins. I'd document the issue and the chosen workaround clearly.

For the interpersonal aspect, I'd approach the junior engineer privately, not in a group setting. I'd frame the conversation around the system-level lesson rather than assigning blame: "We've hit a debug interface issue that's going to cost us time. Let's look at the schematic together and understand how this happened, so we can prevent it in future designs." I'd ask them to walk me through their pin assignment decisions, which helps them see the mistake themselves rather than being told. Then I'd discuss adding a checklist to the design review process: before releasing a PCB layout, verify that debug interface pins are accessible and not shared with critical functions that prevent debugging. This turns the error into a process improvement. I'd also communicate to management the technical situation and the workaround plan, without throwing the junior engineer under the bus — I'd say "we found a pin assignment conflict during bring-up" and focus on the solution timeline.

**Possible follow-ups:** What if the junior engineer continues to argue that their pin assignment was correct and the debugger should work? How would you balance mentoring the junior engineer with the project schedule pressure?
