## Q1: How would you approach setting up a spectrum analyzer for a conducted emissions pre-compliance scan on a medical device's AC input, and what would you check before trusting the first measurement?
**Answer:** Conducted emissions testing on the AC mains input is one of the more setup-sensitive measurements, because the result depends as much on the test arrangement as on the device itself. I'd start by confirming the measurement chain against the standard being targeted: the correct LISN (line impedance stabilization network) bonded to a reference ground plane, the analyzer's input attenuation and reference level set so the expected emission peaks sit comfortably inside the display without overloading the front end, and the resolution bandwidth and detector mode matching what the standard specifies for the frequency range being scanned. Before running the actual scan, I'd verify the setup with a known reference — for example, a signal generator through a calibrated attenuator, or a pre-characterized noise source — to confirm the LISN, cabling, and analyzer are all behaving as expected. I'd also check that the EUT is powered through the LISN on the correct line, that the LISN's ground return is properly bonded, and that the cable routing and EUT placement match the standard's requirements, since a few centimeters of repositioning can shift a peak by several dB. Only once the setup is verified would I trust the sweep, and even then I'd repeat it to confirm the result is stable rather than a one-off artifact.
**Possible follow-ups:** How would you distinguish a real emission from the EUT versus ambient noise picked up by the setup? What would you do if the scan showed a marginal failure right at the limit line?

## Q2: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?
**Answer:** When the framing doesn't map to a standard decoder, I'd treat the logic analyzer as a raw capture tool first and a decoder second. I'd start by capturing the raw waveform on the relevant lines and manually identifying the frame structure: where the header starts, how many bits it spans, what the clock or bit-rate relationship is, and where the payload and any checksum or CRC fall. From there, I'd write a custom decoder — most logic analyzer software supports a scripting interface for this — that parses the captured bits according to that structure and annotates them on the trace. The key discipline is to validate the decoder against a known-good transaction before relying on it: I'd capture a frame where I already know the expected payload (from a reference document or a controlled test case) and confirm the decoder produces the right output. I'd also build in error handling for partial frames, since a decoder that silently mis-parses a truncated frame is worse than one that flags it. If the protocol has a non-byte-aligned header, I'd pay particular attention to bit ordering and any bit-stuffing or escape sequences, since those are the most common sources of decoder bugs.
**Possible follow-ups:** How would you handle a protocol where the bit rate isn't fixed but negotiated at startup? What would you do if the decoder worked on one capture but failed on another with the same nominal framing?

## Q3: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?
**Answer:** The core problem is that IDE defaults are convenient during development but dangerous for a regulated build, because they can change silently between tool versions or project files. I'd approach this by treating the build configuration as a controlled artifact rather than a set of GUI settings. Concretely, I'd define the optimization level, linker script path, startup file, and any preprocessor defines explicitly in the project file and document why each was chosen — for example, a specific optimization level because it was the one validated during verification, not because it happened to be the default. I'd also check the project into version control alongside the source, so any change to the build configuration shows up as a diff that can be reviewed. For auditability, I'd generate a build log that records the compiler version, optimization flags, and linker invocation, and archive that with the released binary. Where the toolchain supports it, I'd consider driving the build from a script or makefile rather than relying on the IDE's internal state, so the build is reproducible outside the GUI. Finally, I'd verify the released binary matches the intended configuration — for example, by checking the map file or disassembly — rather than assuming the project settings were applied.
**Possible follow-ups:** How would you handle a situation where a toolchain update changes the default optimization behavior? What would you check in the map file to confirm the linker script was actually used?

## Q4: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?
**Answer:** A tracking generator plus directional coupler lets you measure return loss, which you can convert to impedance, but the measurement is only as good as the calibration and the fixture. I'd start by calibrating out the test setup itself — the cables, the coupler, and any adapter — using open, short, and load standards at the reference plane where the front-end connects, so the measurement reflects the device rather than the fixture. Then I'd sweep the frequency range of interest and look at the return loss curve, converting to impedance where needed. The trustworthiness question comes down to a few checks: does the calibration reference plane actually match where the device under test begins, or is there an unaccounted length of trace or connector? Is the coupler's directivity good enough at the frequencies of interest, or is the measurement dominated by coupler leakage? Does the result change if I repeat the calibration or reseat the connection? If the impedance curve looks plausible and stable across repeats, and the fixture effects have been accounted for, I'd act on it. If it looks noisy or inconsistent, I'd suspect the fixture or calibration before trusting the result — a bad measurement acted on is worse than no measurement.
**Possible follow-ups:** How would you handle a front-end that's only meant to operate over a narrow band — would you still sweep the full range? What would you do if the return loss looked fine but the device still behaved poorly in the actual circuit?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?
**Answer:** The first thing I'd do is separate the technical issue from the interpersonal one. Technically, the engineer isn't wrong that peaks show up either way — the problem is that the amplitude and the shape of those peaks depend on resolution bandwidth and detector mode, so a scan with the wrong settings can under- or over-report emissions relative to the limit line. That's not a cosmetic difference; it's the difference between a pass and a fail, and it's the kind of thing a reviewer or auditor would flag. So I'd explain that distinction concretely, ideally by showing the same scan with both settings side by side if there's time, rather than just asserting the settings are wrong. On the scheduling side, I'd assess whether the correct settings can be applied and the scan re-run within the booked time — often the fix is a settings change and a re-scan, not a full re-setup — and if not, I'd look at whether the scan can be extended or rebooked rather than proceeding with results I don't trust. I'd avoid framing it as the engineer having failed; the more useful message is that "the peaks show up either way" is exactly the trap, and the standard's settings exist precisely because amplitude matters. Going forward, I'd want the required settings documented as part of the test procedure so this isn't dependent on individual judgment.
**Possible follow-ups:** How would you handle it if the engineer pushed back and said the standard's settings were overly conservative? What would you put in place so the correct settings are used by default next time?
