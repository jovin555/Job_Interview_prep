## Q1: How would you approach setting up a schematic library in Altium Designer so that symbols stay consistent and traceable across a multi-year medical device program, where the same part may be reused across several board revisions?

**Answer:** The core problem is that a schematic symbol is a contract: it encodes pin numbers, pin names, electrical types, and often footprint links, and if that contract drifts between revisions you get netlist errors, wrong footprint associations, or — worst case in a medical context — a design that no longer matches its documentation. So I'd treat the library as a controlled artifact, not a scratch pad.

Practically, I'd start with a single managed library (or a version-controlled library repository) rather than letting each engineer keep a personal `.SchLib`. Every symbol gets a unique, stable identifier and a revision field, and the part number, manufacturer, and datasheet reference live in the symbol's parameters so they travel with the component into the schematic and BOM. I'd standardize the symbol grid, pin length, and naming convention up front — pin names matching the datasheet exactly, electrical types set correctly (input/output/power/passive) so ERC is meaningful — because retrofitting consistency across hundreds of symbols later is painful.

For traceability across revisions, the key discipline is: never edit a released symbol in place. If a part changes, you create a new revision of the symbol and the schematic references that revision, so an old board revision still resolves to the symbol it was designed with. In Altium that means using the vault/managed-library workflow or, if that's not available, a disciplined naming and revision scheme in a Git- or SVN-backed library folder with the library itself under version control alongside the project. I'd also add a library review step — a second pair of eyes on any new symbol — because a wrong pin number caught at library review costs minutes, while caught at bring-up it costs a board spin.

The medical-device angle is that this library becomes part of the design history file: you need to be able to show what symbol, what footprint, and what part revision were used on the board that was validated. So the library revision has to be captured at release, not just "whatever was on the server that day."

**Possible follow-ups:** How would you handle a situation where a symbol was already used on a released board and you discover a pin-name error — do you fix the symbol or fork it? And how do you keep the footprint association locked so a symbol can't silently point at the wrong land pattern?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The risk with IDE-managed build settings is that they're easy to change by accident and hard to see in a diff — someone flips optimization from `-O0` to `-O2` to "make it fit," or the linker script gets edited in the GUI and nobody notices. For a regulated device you want the build configuration to be an explicit, reviewable, reproducible artifact.

My approach: first, make the build settings visible and version-controlled. In Keil that means keeping the project file (`.uvprojx`) in source control and reviewing changes to it like code — a diff on the project file shows optimization level, defines, include paths, and linker settings. I'd pin the optimization level explicitly per target rather than leaving it at a default, and document *why* that level was chosen, because optimization level can change timing behavior and even expose latent undefined behavior. For safety-critical code I'd lean toward a conservative, well-understood optimization setting and verify the generated code behaves as tested.

Second, the linker script (scatter file) and startup code should be treated as first-class source: checked in, reviewed, and ideally generated or templated so the memory map — flash regions, RAM, any reserved calibration or bootloader sectors — is explicit and can't be silently overwritten. That's especially important if calibration data or a bootloader lives in flash; the linker script is where you guarantee the application image doesn't collide with it.

Third, reproducibility: I'd want a documented toolchain version (compiler version matters as much as the flags), a clean-build script or batch file that produces the release image from a known commit, and the resulting image plus its build log archived as the auditable artifact. The build log captures the exact flags and versions used, which is exactly what a reviewer or auditor needs. Ideally the release build is produced by a script or CI job rather than by someone clicking "Build" in the IDE, so the human step is removed.

**Possible follow-ups:** How would you detect that a released binary was built with different settings than the validated one? And what's your view on using `-O0` for debug builds versus the release build — how do you keep them from diverging in behavior?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** The tracking generator plus directional coupler gives you a scalar reflectometer: the tracking generator sweeps a known stimulus, the coupler separates the forward and reflected waves, and by measuring the reflected power relative to the incident you get return loss (S11 magnitude) versus frequency. From return loss you can derive the magnitude of the reflection coefficient and, if you assume the load is passive and you know the reference impedance, estimate the impedance — but only the magnitude, not the phase, so you can't uniquely separate resistance from reactance. That limitation is the first thing to be honest about: this tells you *how badly* you're mismatched and at what frequencies, not the full complex impedance. If I needed the complex value I'd want a VNA, or a bridge-based method.

Setup discipline matters more than the math. I'd calibrate out the test setup — cables, coupler, and fixture — with a reference measurement (open/short/load, or at minimum a through and a known load) so the response I'm seeing is the front-end and not my coax. I'd keep the coupler's directivity in mind: a cheap coupler with poor directivity puts a floor on how small a return loss I can trust, so a "great" reading near that floor is suspect. I'd also watch the stimulus level — the tracking generator output must be low enough not to overdrive or damage a sensitive analog front-end, and I'd check the front-end is powered and biased in its normal operating state, because input impedance of an active front-end depends on bias.

Deciding whether to act: I'd sanity-check the result against expectation — does the mismatch appear where the input filter or protection network would predict? Does it move when I change a component I expect to matter? I'd repeat the measurement, swap the fixture, and confirm the feature is stable and reproducible before changing a design based on it. A single sweep that shows a suspicious null near the coupler's directivity floor is not something I'd redesign around.

**Possible follow-ups:** How would you extend this to get phase information without a full VNA? And how would you separate the front-end's input impedance from the parasitic impedance of the connector and fixture you're measuring through?

## Q4: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** When there's no built-in decoder, the honest starting point is to decode by eye first: capture a known-good transaction, zoom in, and manually annotate the waveform — where's the frame start, what's the header pattern, where are the data bits, what's the clocking edge. Only once I understand the framing on paper do I try to automate it, because writing a decoder against a misunderstood protocol just produces confident-looking wrong output.

For a non-byte-aligned header, the trick is to decode at the bit level rather than assuming byte boundaries. Most logic analyzers let you define a decoder in terms of edges and bit positions — either through a scripting interface (Python or a vendor SDK) or a custom-decoder plugin. I'd define the frame as: a start condition or sync pattern (matched as a bit pattern, not a byte), a length or ID field, the payload bits, and a checksum/CRC if present. I'd make the decoder tolerant of the things that actually happen on a real bus — idle gaps, retries, error frames — and have it flag frames it can't parse rather than silently mis-decoding them.

Validation is the important part: I'd run the decoder against captures I've already hand-decoded and confirm it agrees, then against a long capture with many frames to catch edge cases. I'd also cross-check against the firmware's own view of the bus where possible — if the firmware logs what it thinks it sent and received, a mismatch between the decoder and the firmware log is a strong signal that one of them is wrong, and that's exactly the kind of bug worth finding.

The medical-device relevance is that this decoder becomes a debugging tool the whole team relies on, so it needs to be version-controlled and documented — a decoder that only one engineer understands and that lives on their laptop is a single point of failure.

**Possible follow-ups:** How would you handle a protocol where the bit rate isn't constant — say, it changes mid-frame? And how would you make the decoder robust to a bus that occasionally has noise glitches that look like edges?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** My first move is to separate the technical question from the interpersonal one, because they need different handling and mixing them makes both worse.

Technically, the engineer isn't wrong that the peaks show up — a fast scan with a wide resolution bandwidth and a peak detector will absolutely reveal *that* there's energy at a frequency. What it won't do is give a measurement you can compare against a limit line, because resolution bandwidth, detector type (peak vs. quasi-peak vs. average), and dwell time all affect the measured amplitude, and the standard specifies them for a reason. So the correction isn't "you're wrong," it's "this scan is the right tool for finding suspects and the wrong tool for the compliance number." I'd frame it that way, because it's true and it respects that the engineer did something useful.

Interpersonally, I'd avoid correcting them in front of the group. I'd pull them aside, explain the specific reason the settings matter for a limit comparison, and — importantly — have them re-run the scan with the correct settings themselves rather than doing it for them. That turns a correction into a learning moment and leaves them owning the fix. I'd also ask them to walk me through how they chose the settings, because if the root cause is "the tutorial didn't cover detector mode," that's a gap worth closing for the whole team, not just this person.

On the schedule: the lab time being booked and non-refundable is a real constraint, but a scan with the wrong settings produces data you can't submit, which is worse than a delay. So I'd prioritize getting the settings right before the session — re-run locally tonight with correct settings to confirm the setup, and if there's any doubt, use the booked session to capture properly rather than to redo a bad scan. I'd also use it as a trigger to write down the required settings as a checklist for future scans so this doesn't recur.

**Possible follow-ups:** What would you do if the engineer pushed back and argued the settings genuinely don't affect the result? And how would you build a lab checklist so that pre-compliance setups are verified before a booked session rather than discovered on the day?
