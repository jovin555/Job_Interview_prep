## Q1: How would you approach setting up a cross-probe workflow between OrCAD Capture and Cadence Allegro so that a layout review can move efficiently between schematic and PCB, and what would you check to confirm the link is actually working before relying on it in a review?

**Answer:** Cross-probing is only useful if the two tools agree on the same design database, so the first step is confirming that the Allegro board was netlisted from the exact Capture revision under review — not a copy, not a renamed variant. If the schematic and board have drifted, cross-probing will highlight the wrong reference designators and quietly undermine the whole review. Once that's confirmed, I'd verify the link in both directions with a known component: select a specific part in Capture and confirm Allegro highlights the correct footprint, then select a net in Allegro and confirm Capture highlights the corresponding net segment. I'd also test a net that spans multiple pages or a hierarchical block, since that's where cross-probe setups most often break — the tool may resolve the net name but not the sheet path. For the review itself, I'd set up a repeatable sequence: walk the schematic page by page, cross-probe each functional block to the board, and check placement, decoupling proximity, and return-path continuity as I go. The value of cross-probing is that it turns a layout review from a visual scan into a traceable, net-by-net verification, so I'd treat the link check as a prerequisite, not an afterthought.

**Possible follow-ups:**
- What would you do if cross-probing works for components but not for nets that cross hierarchical sheet boundaries?
- How would you document the cross-probe findings so they're actionable for the layout engineer rather than just a list of highlights?

## Q2: How would you approach configuring a Segger J-Link for a Zephyr RTOS target where the test harness needs to flash the device, run a test sequence, and capture a crash dump without manual intervention — and what failure modes would you design around?

**Answer:** I'd treat this as a reliability problem first and a scripting problem second. The harness needs a deterministic sequence: reset the target into a known state, flash the image, verify the flash succeeded, start the test, and then either read a pass/fail result or capture a crash dump if the target faults. J-Link's scripting interface can drive all of that, but the failure modes are what make or break it. The ones I'd design around: the debug connection dropping mid-run (so the harness needs a reconnect-and-retry path, not a hard fail), the target not resetting cleanly (so I'd assert reset explicitly rather than relying on the previous state), flash verification failing silently (so I'd read back and compare, not just trust the write), and the crash dump being lost because the target was reset before the dump was read out. For crash capture specifically, I'd configure the J-Link to halt on fault and read the relevant core registers and stack before any reset, and I'd make the harness distinguish "test failed" from "target crashed" so the results are interpretable. I'd also make the whole sequence idempotent — running it twice in a row should produce the same result — because flaky test infrastructure erodes trust in the results faster than almost anything else.

**Possible follow-ups:**
- How would you capture a crash dump if the fault occurs before the debugger has attached?
- What would you log from each run so that a failure can be diagnosed after the fact without re-running the test?

## Q3: How would you approach organizing a KiCad project for a medical device so that the schematic, PCB, footprints, and 3D models stay consistent across revisions, and how would you catch footprint-to-schematic mismatches before they reach fabrication?

**Answer:** The core problem in KiCad is that the library format is file-based rather than database-driven, so consistency depends on discipline and tooling rather than a central authority. I'd start by deciding what lives in the project versus what lives in shared libraries: project-specific symbols and footprints stay with the project, but anything reused across projects goes into a versioned library with a clear naming convention. Every symbol should carry an explicit footprint assignment — not left to be filled in at layout time — because that's where mismatches originate. For catching mismatches before fabrication, I'd lean on the tools that already exist: run ERC to catch unconnected pins and conflicting outputs, run DRC with a rule set tuned to the fabricator's capabilities, and then do a footprint-to-schematic cross-check by exporting the netlist and comparing pad counts and pin assignments against the schematic. The step people skip is the 3D model check — a footprint can be electrically correct but mechanically wrong, so I'd verify that each footprint's 3D model matches the physical part's dimensions and orientation, especially for connectors and anything with a keep-out. Finally, I'd treat the project as a Git repository with the libraries as submodules or vendored copies, so a given revision of the board is reproducible from a single commit.

**Possible follow-ups:**
- How would you handle a footprint that needs to change after the board has been fabricated — what's your process for tracking that across revisions?
- What's your approach to keeping 3D models in sync when a vendor updates a part's mechanical drawing?

## Q4: Walk me through your process for using LTSpice to simulate the noise performance of a precision analog front-end for a medical sensor, and how you would correlate those simulations with real-world measurements.

**Answer:** I'd start by being honest about what LTSpice can and can't tell me. It's excellent for verifying the transfer function, the noise gain of the topology, and the contribution of each resistor and op-amp to the total input-referred noise — assuming the models are good. It's much weaker at predicting real-world noise, because it doesn't know about PCB layout, ground return paths, or the switching regulator sitting two centimeters away. So I'd use it in two stages. First, a noise analysis with the actual component models to identify which elements dominate the noise budget — that tells me where to spend money on tighter-tolerance or lower-noise parts, and where I can relax. Second, a transient or AC analysis to check stability and bandwidth, because a front-end that's noisy but stable is a different problem from one that's quiet but oscillating. For correlation, I'd measure the real board with a low-noise measurement setup — battery-powered or linear-regulated supply, short ground leads, shielded enclosure if needed — and compare the measured noise density to the simulated one across frequency. If they diverge, the divergence itself is the diagnostic: a rise at the switching frequency points to conducted or radiated coupling, a rise at low frequency points to a model or bias issue. The simulation is a hypothesis; the measurement is the test.

**Possible follow-ups:**
- How would you separate the sensor's own noise from the front-end's noise in a real measurement?
- What would you do if the simulated noise was well within budget but the measured noise was not?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the Altium Designer output job configuration for a medical device PCB release, and you discover the fabrication outputs are missing the drill table and the assembly drawings reference an outdated revision of the schematic. The board house is expecting the files tomorrow, and the engineer is confident the outputs are complete because "the Gerbers look fine." How would you handle this situation?

**Answer:** The first thing I'd do is separate the technical problem from the interpersonal one, because they need different responses. Technically, "the Gerbers look fine" is not the same as "the release package is complete" — a fabrication package for a medical device typically needs the drill table, the stackup, the assembly drawings, and a revision that matches the schematic, and a missing drill table can stop a board house cold. So I'd pull up the output job configuration and the release checklist side by side, and walk through what's present and what's missing, using the checklist as the neutral reference rather than my own judgment. That keeps the conversation about the package, not about the engineer. On the interpersonal side, I'd avoid framing it as "you got it wrong" — the engineer is confident because the Gerbers genuinely do look fine, and that's a reasonable thing to conclude if you haven't been shown the full release checklist. I'd treat it as a gap in the process: if the checklist wasn't visible or wasn't enforced, that's a system problem, not just an individual one. Then I'd fix the immediate issue — regenerate the missing outputs, verify the assembly drawings against the current schematic revision, and get the package out — and afterward, make the release checklist a required gate so the next person doesn't hit the same wall. The deadline pressure is real, but shipping an incomplete package to a board house costs more time than fixing it now.

**Possible follow-ups:**
- How would you decide whether to delay the release to fix the package versus sending what you have and following up?
- What would you change in the release process so that a missing drill table or stale assembly drawing is caught automatically rather than by review?
