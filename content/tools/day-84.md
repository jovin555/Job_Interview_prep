## Q1: How would you approach setting up a spectrum analyzer for a conducted emissions pre-compliance scan on a medical device's AC input, and what would you check before trusting the first measurement?
**Answer:** Conducted emissions on the AC mains port is one of the first things a medical device has to clear, and the measurement is easy to get wrong in ways that either hide a real failure or invent one that isn't there. I'd start by confirming the setup matches the standard being targeted — typically CISPR 11 or the equivalent clause in IEC 60601-1-2 — because the limit line, frequency range, and quasi-peak/average detector requirements all flow from that. The device under test goes on a non-conductive table at the specified height, with the correct line impedance stabilization network (LISN) inserted between the device and the mains, and the LISN's RF output feeding the analyzer through a known attenuator. Before running anything, I'd verify the LISN is bonded to the reference ground plane, that the cable lengths and routing match the standard's setup diagram, and that the analyzer's input isn't being overdriven — a 10 dB pad is cheap insurance against front-end damage and against misleading compression artifacts.

Then I'd do a sanity check with the device powered off but the LISN and analyzer live: the noise floor should be well below the limit line, and any ambient pickup (fluorescent ballasts, nearby switching supplies, the lab's own equipment) should be identifiable and, if possible, eliminated or noted. I'd also run a known reference source or a calibration check if the lab has one. Only after that would I power the device and scan, using the correct resolution bandwidth and dwell time so that intermittent emissions aren't missed. The key discipline is treating the first sweep as a hypothesis, not a result — if a peak appears, I'd re-run with the device off to confirm it's actually coming from the DUT, and I'd check whether the peak moves when I reposition cables, since that distinguishes a real conducted emission from a setup artifact.

**Possible follow-ups:**
- How would you decide whether a marginal peak needs quasi-peak versus average measurement, and what does that choice tell you about the emission's character?
- If the device has a switching supply that only runs in a particular operating mode, how would you make sure the scan captures worst-case emissions?

## Q2: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?
**Answer:** When the framing doesn't fit a stock decoder, the first thing I'd do is resist the temptation to force it into the nearest built-in decoder and instead treat the decoder as a two-stage problem: a low-level bit/edge capture, then a custom parser layered on top. Most logic analyzer software lets you export the raw transitions with timestamps, or write a custom decoder in a scripting language (Python, or the vendor's SDK). I'd start by capturing a known-good transaction — ideally one where I can correlate the bus activity with a firmware log or a known command — and manually annotate the waveform to establish the frame structure: where the header starts, how many bits it spans, whether it's MSB- or LSB-first, what the clocking relationship is, and where the payload and checksum sit. Non-byte-aligned headers are usually the hardest part because they break the assumption that everything lines up on byte boundaries, so I'd build the parser around a bit offset rather than a byte offset.

Once I have a working parser for one frame, I'd validate it against several different transactions, including edge cases: minimum and maximum payload lengths, back-to-back frames, idle gaps, and any error or retry frames. I'd also cross-check the decoded output against an independent source — a scope capture of the same transaction, or the sensor's own status register read back over a different interface — so I'm not just confirming my parser agrees with itself. The decoder is only useful if it's trustworthy, so I'd document the frame format it assumes and version it alongside the firmware, because if the protocol changes the decoder silently producing wrong output is worse than no decoder at all.

**Possible follow-ups:**
- How would you handle a protocol where the clock is embedded in the data (e.g., Manchester or a self-clocked scheme) rather than a separate clock line?
- What would you do if the frame header length itself is variable, so the parser can't assume a fixed offset to the payload?

## Q3: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?
**Answer:** The core problem with IDE-managed build settings is that they live in a project file that's easy to change accidentally and hard to review in a diff, which is exactly the wrong property for a regulated medical device build. My approach is to treat the build configuration as a first-class artifact: the optimization level, preprocessor defines, include paths, linker script selection, and startup file should all be explicit and documented, not inherited from a template or a previous project. In Keil specifically, that means going through the target options deliberately — setting the optimization level to whatever the verification plan calls for (often `-O0` or a low level during development and formal test, with any change treated as a design change requiring re-verification), confirming the linker script matches the memory map the hardware actually has, and making sure the startup code and vector table are the ones intended for this MCU variant, not a sibling part.

The auditability piece is where a lot of teams fall down. I'd want the project file under version control with meaningful commit messages, and I'd want a build script or batch file that invokes the toolchain from the command line so the build can be reproduced outside the IDE and compared against the IDE build. If the toolchain supports it, I'd generate a map file and a build log as part of every release build and archive them with the firmware image, because that's what lets you answer "what exactly was compiled and with what settings" months later during an audit. I'd also add a pre-build check that fails the build if the optimization level or linker script doesn't match the expected values, so a stray change can't slip through silently.

**Possible follow-ups:**
- How would you handle the situation where a library or third-party object was compiled with different optimization settings than the rest of the project?
- What would you check in the map file to confirm the linker script is actually placing code and data where you expect?

## Q4: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?
**Answer:** A tracking generator plus a directional coupler lets you do a poor-man's return-loss measurement: the tracking generator sweeps a known signal into the coupler, the coupler separates forward and reflected power, and the analyzer measures the reflected component to give you return loss versus frequency, from which you can infer input impedance. The setup details matter a lot. I'd calibrate out the test fixture first — connect the coupler's measurement port to a known reference (an open, a short, and a 50-ohm load) and store the responses so the analyzer can normalize away the fixture's own parasitics. Without that, you're measuring the fixture as much as the front-end. I'd also keep the drive level low enough that the front-end stays in its linear region, because a large signal can bias active devices and give you an impedance that has nothing to do with small-signal behavior.

Deciding whether to trust the result comes down to a few checks. First, does the measurement agree with a simple independent estimate — for example, does the impedance at low frequency look like the expected bias network, and does it roll off where the input capacitance predicts? Second, is the result repeatable if I disconnect and reconnect the fixture, or does it shift with cable dressing? If it shifts, the measurement is dominated by fixture parasitics and I need to improve the setup before acting on it. Third, does the frequency range cover the band I actually care about, with enough resolution to see narrow features like a resonance? If the answer to any of these is no, I'd treat the data as indicative rather than definitive and either refine the setup or cross-check with a different method, such as a VNA if one is available.

**Possible follow-ups:**
- How would you extend this to measure output impedance rather than input impedance, and what changes in the setup?
- If the front-end is differential rather than single-ended, how would you adapt the measurement?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?
**Answer:** The first thing I'd do is separate the technical question from the interpersonal one, because they need different handling. Technically, the engineer isn't wrong that the peaks show up either way — a wide resolution bandwidth and a peak detector will absolutely reveal that emissions exist and roughly where they are. What they won't do is tell you whether those emissions pass or fail against a limit line that's defined for a specific resolution bandwidth and detector. A peak that looks fine at 120 kHz RBW with a peak detector can fail when measured at 9 kHz RBW with a quasi-peak detector, because the narrower bandwidth and the detector's charge/discharge behavior change the measured level. So the "get a feel for it" scan is a useful reconnaissance tool, but it can't be the basis for a compliance decision, and that distinction is the thing to communicate.

In the moment, I'd acknowledge the engineer's instinct — the quick scan did its job of finding candidate emissions — and then reframe the issue as one of matching the measurement to its purpose. I'd walk through the standard's requirements together rather than just asserting them, so the reasoning is visible and the engineer can apply it next time. Then I'd make a practical call: if there's time tonight, reconfigure and re-run the scan with the correct settings; if not, I'd use the booked lab time tomorrow for the compliant scan and treat the quick scan as a pre-screen that told us where to look. I'd also make sure the engineer isn't left feeling that their work was wasted — the pre-screen genuinely saved time by narrowing the frequency range — while being clear that the formal result has to come from a correctly configured measurement.

**Possible follow-ups:**
- How would you build a checklist or template so that future scans start with the correct settings by default?
- If the compliant scan tomorrow reveals a failure that the quick scan missed, how would you handle the conversation about schedule impact?
