## Q1: How would you approach setting up a multi-channel design in Altium Designer for a medical device that has four identical analog sensor front-end channels, each with its own ADC and signal conditioning, while keeping the design maintainable and the schematic readable?

**Answer:** I'd use Altium's multi-channel design feature with a single channel schematic sheet containing the complete front-end — sensor input conditioning, ADC, and any local decoupling — then instantiate it four times using the Repeat keyword in the parent sheet. The key is designing the channel sheet with consistent net naming conventions that will properly vectorize, like `SIG_IN1`, `SIG_IN2`, etc., so Altium automatically generates the channel-specific nets. I'd also make sure the channel's power and ground connections are cleanly separated at the parent level, since sharing a single noisy digital supply across all four analog channels would defeat the purpose of having separate front-ends. For the PCB layout, I'd use the channel offset feature to place the four channels in a repeating pattern, which makes the layout review much easier because you can verify one channel thoroughly and then check that the other three follow the same placement and routing. For a medical device, I'd also add a design rule that enforces the analog-to-digital keepout spacing and verify that the channel-specific component designators (like `U1A`, `U1B`, etc.) are correctly annotated before generating the BOM, since regulatory documentation requires unambiguous component identification.

## Q2: Walk me through your process for using LTSpice to simulate the common-mode rejection ratio (CMRR) of a differential amplifier front-end for a medical sensor, and how would you validate the simulation against real measurements?

**Answer:** The first step is to build the circuit in LTSpice using the actual op-amp model from the manufacturer, not an ideal model, because CMRR is highly dependent on the real device's internal matching. I'd set up the simulation with a common-mode test configuration: tie both inputs together and drive them with an AC signal source, then measure the output. The CMRR at each frequency is the ratio of the differential gain to the common-mode gain, so I'd run two AC analyses — one with a differential input and one with common-mode input — and plot the difference. I'd also include the resistor network tolerances in the simulation, because in a real differential amplifier the resistor matching often dominates the achievable CMRR, not the op-amp itself. I'd run a Monte Carlo analysis with 1% resistor tolerances to see the spread of CMRR values, which gives a realistic expectation for production. For validation, I'd build the circuit on a bench with precision resistors, measure the differential gain with a signal generator, then short the inputs together and measure the common-mode gain using the same generator. The key measurement detail is using a low-capacitance probe and keeping lead lengths short, because stray capacitance at the inputs will degrade the high-frequency CMRR and make the measurement look worse than the actual circuit performance. I'd also verify that the signal generator's own common-mode output impedance is balanced, otherwise the measurement setup itself introduces asymmetry.

**Possible follow-ups:**
- How would you account for the effect of source impedance imbalance on CMRR in your simulation?
- What CMRR value would you consider acceptable for a medical sensor measuring microvolt-level bio-signals, and why?

## Q3: How would you approach setting up a Gerber file verification workflow using Gerbv to catch common fabrication issues before sending a design to manufacturing?

**Answer:** I'd treat Gerber verification as a structured checklist rather than just a visual "does it look right" pass. First, I'd import all the Gerber files into Gerbv along with the drill file, and set up the layer stack in the correct order — copper layers, solder mask, silkscreen, and outline — so the view actually represents the physical board. The first check is the outline layer: I'd verify it's a closed contour, that there's only one outline (not multiple overlapping ones), and that the board dimensions match the mechanical drawing. Next, I'd check the solder mask layers against the copper layers, looking for pads that are missing mask openings or, conversely, mask openings that expose copper where there shouldn't be any — this is a common source of assembly issues. I'd also verify that the drill file aligns with the pad locations on the copper layers by toggling the layers and zooming into a few representative through-hole and via locations. For fine-pitch components, I'd check that the solder mask slivers between adjacent pads are within the board house's minimum capability. I'd also use Gerbv's measurement tool to spot-check critical clearances, like the spacing between a high-voltage trace and a low-voltage trace on a medical device, since that's a safety-related requirement. Finally, I'd cross-reference the Gerber file list against the fabrication drawing to confirm every layer that should be present is there, and that there are no extra or missing files.

**Possible follow-ups:**
- How would you verify that the Gerber files match the latest schematic revision, especially when multiple engineers are working on the same project?
- What specific checks would you add for a board with impedance-controlled traces?

## Q4: How would you approach using a Segger J-Link debugger to capture a real-time trace of a Zephyr RTOS-based system's thread scheduling behavior without halting the CPU or modifying the firmware?

**Answer:** The key constraint is that you want to observe the system's natural behavior without perturbing it, so I'd use the J-Link's trace capabilities rather than breakpoint-based debugging. First, I'd check whether the target microcontroller supports ETM (Embedded Trace Macrocell) or ITM (Instrumentation Trace Macrocell) — for a Cortex-M device, ITM is often sufficient for thread scheduling analysis and has lower pin requirements. I'd configure the J-Link to use the SWO pin for ITM output, and in Zephyr, I'd enable the tracing subsystem that routes thread-switch events to the ITM stimulus ports. The important part is that this is done at build time via Kconfig options, but it's not a code modification — it's using the RTOS's built-in instrumentation hooks. Then I'd use Ozone or J-Link's RTT (Real-Time Transfer) to capture the trace data while the system runs normally. For thread scheduling specifically, I'd look at the timestamps of thread-switch events to identify patterns like priority inversion, excessive context switching, or a thread that's starving others. If the target doesn't support ITM/ETM, I'd fall back to using the J-Link's sampling-based profiling via the debug interface, which periodically samples the program counter without halting — it's less precise but can still reveal which threads are consuming CPU time. One caveat: I'd verify that enabling the trace doesn't itself change timing behavior significantly, especially in a medical device where timing is safety-relevant, so I'd compare the system's behavior with and without tracing enabled.

**Possible follow-ups:**
- How would you distinguish between a thread that's blocked waiting on a semaphore versus one that's spinning in a tight loop using the trace data?
- What would you do if the target microcontroller doesn't have trace pins routed on the PCB?

## Q5: (Behavioral) Imagine you are leading a design review for a medical device PCB, and you discover that the Cadence Allegro constraint manager has been set up with incorrect differential pair impedance targets for a USB 2.0 interface — the targets are set for 85 ohms instead of the 90 ohms required by the USB specification. The PCB has already been sent to fabrication, and the project is on a tight schedule. The junior engineer who set up the constraints is confident that 85 ohms is correct based on a forum post they read. How would you handle this situation?

**Answer:** The first priority is to determine whether this is actually a problem or a non-issue, so I'd verify the facts before escalating. I'd pull up the USB 2.0 specification and confirm the 90-ohm differential impedance requirement, then check the PCB stack-up and the actual trace geometry that was routed to see what impedance the fabricated board will actually have. The 85-ohm target in the constraint manager doesn't necessarily mean the routed traces are 85 ohms — the engineer might have routed them correctly by coincidence, or the stack-up might produce 90 ohms even with the wrong target. I'd also check whether the board house has already started fabrication and whether they can hold the order. If the traces are actually routed to 85 ohms, I'd assess the impact: for USB 2.0 at 480 Mbps, a 5-ohm impedance mismatch will cause some signal reflection, but it might still pass eye-diagram testing depending on the trace length and the receiver's tolerance. I'd work with the junior engineer to calculate the actual impedance from the routed geometry using the field solver in Allegro, rather than relying on the constraint target. If the impedance is genuinely wrong and the board can't be stopped, I'd plan for a respin while simultaneously preparing a mitigation strategy — for example, checking if the USB PHY has enough drive strength adjustment to compensate, or if the trace length is short enough that the reflection is within the receiver's budget. In parallel, I'd use this as a coaching opportunity: I'd walk the junior engineer through the USB specification's impedance requirements, show them how to verify the stack-up calculations, and emphasize the importance of cross-checking constraint targets against the actual specification rather than relying on forum posts. I'd also review whether there's a gap in our design review process that allowed this to slip through — for example, whether the constraint manager setup should have been reviewed before layout began.

**Possible follow-ups:**
- How would you communicate this issue to management, especially if the schedule impact is significant?
- What process changes would you propose to prevent this type of error from happening again in future projects?
