# tools — Day 118

## Q1: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** I'd start by treating the decoder as a specification problem before it's a tooling problem. First I'd get the frame definition written down unambiguously — bit-level field map, header pattern, length encoding, CRC or checksum placement, and the clocking assumptions (is the bit clock embedded, or is it a separate strobe?). The non-byte-aligned header is the crux: most built-in decoders assume byte boundaries, so I'd build the decoder in stages. Stage one is a raw bit-level capture with a sample rate high enough to resolve the fastest edge with margin — typically 10x the bit rate or better — and I'd verify the capture is trustworthy by checking that a known-good transaction decodes cleanly by eye before writing any decoder logic. Stage two is a pattern-matching layer: rather than assuming byte alignment, I'd search the bitstream for the header pattern at any bit offset, then lock the frame boundary from that match. Stage three is field extraction driven by the written spec, with the decoder emitting raw field values plus a validity flag rather than silently misparsing. I'd validate the decoder against a deliberately corrupted frame and against a frame with a known payload so I can confirm it fails where it should and passes where it should. If the analyzer's scripting environment supports it, I'd keep the decoder in version control alongside the protocol spec so the two can't drift apart.

**Possible follow-ups:** How would you handle a protocol where the bit clock is recovered from the data itself rather than being a separate line? What would you do if the header pattern can legitimately appear inside the payload?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is that a build is reproducible from source control alone, with no dependence on whatever state the IDE happens to be in on a given engineer's machine. I'd start by moving every build-affecting setting out of the GUI and into a form that's diffable and reviewable — the project file itself under version control, plus a documented build configuration that states the optimization level, the exact linker script path, the startup file, and the preprocessor defines, each with a rationale. Optimization level in particular deserves an explicit decision and a comment: for a medical device, the level used during verification must be the level used in production, and any deviation is a change that needs review, not a local convenience. The linker script and startup code should be treated as first-class source artifacts — checked in, versioned, and reviewed like any other code, with memory region definitions and section placement visible rather than buried in IDE defaults. I'd add a build-time check that fails loudly if the active configuration doesn't match the expected one, so a stray local change can't slip into a release. Finally, I'd make the build runnable from a script or CI so the artifact can be regenerated identically later, which is what makes the whole thing auditable rather than just tidy.

**Possible follow-ups:** How would you catch a case where someone changed the optimization level locally but the checked-in project file still looks correct? What's your approach to verifying that the linker script actually placed code and data where you intended?

## Q3: How would you approach setting up a differential pair routing constraint in Cadence Allegro for a CAN-FD bus running at 5 Mbps on a mixed-signal medical device PCB, and how would you verify the constraints are actually honored in the final layout?

**Answer:** I'd begin by deriving the constraint from the interface requirements rather than picking a number — the differential impedance target comes from the transceiver and the bus specification, and the length-matching tolerance comes from the skew the receiver can tolerate at the given bit rate, with margin. In Allegro I'd set up the physical constraint set for the pair: target impedance, a tolerance band, maximum uncoupled length, gap, and the intra-pair skew limit, then assign the net class and pair to that set through the constraint manager so it's applied by rule rather than by hand. The critical part is verification, because a constraint that's defined but not enforced is worse than no constraint — it creates false confidence. I'd run the interactive and batch DRC with the electrical and physical rules enabled, then independently check the actual routed geometry: measure the achieved impedance from the stackup and trace geometry, confirm the intra-pair skew from the report, and inspect the pair visually for places where it's forced to uncouple — around vias, connectors, and any region where the pair has to separate. I'd also check the return path, since a perfectly matched pair over a split in the reference plane is still a problem. Anything the DRC can't see, I'd verify by inspection and record it in the review notes.

**Possible follow-ups:** What would you do if the layout can't meet the uncoupled-length limit because of a connector pinout you can't change? How do you decide whether a reported skew violation is actually a risk at 5 Mbps?

## Q4: How would you approach using a spectrum analyzer with a near-field probe to locate the source of a radiated emissions failure at a specific frequency during pre-compliance testing, and how would you confirm which component is responsible?

**Answer:** I'd treat the near-field probe as a localization tool, not a compliance measurement — it tells you where energy is coming from, not whether you'll pass. The workflow is: first establish that the failure is real and reproducible in the setup, with the device in the same state and orientation as the failing scan. Then, with the probe, I'd map the board systematically — a grid over the board area at the failing frequency, with the probe held at a consistent height and orientation, recording amplitude at each point. The hot spot narrows the candidate set, but a hot spot isn't proof of source; it could be a coupling path or a cable acting as an antenna. To confirm the source, I'd change one variable at a time and watch whether the emission moves with it: change the switching frequency of a suspect regulator and see if the emission shifts correspondingly; halt or gate a suspect clock and see if it disappears; add a temporary snubber or ferrite and see if it drops. If the emission tracks the change, that's strong evidence. I'd also check whether the frequency is an integer multiple of a known clock or switching frequency, which is often the fastest way to form a hypothesis worth testing. Only after the source is confirmed would I move to a fix, and I'd re-verify with the same probe setup before going back to the formal scan.

**Possible follow-ups:** How would you distinguish a near-field hot spot caused by the source from one caused by a coupling path? What would make you distrust a probe measurement enough to redo it?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** My first move is to separate the technical question from the interpersonal one, because conflating them makes both worse. Technically, the engineer isn't wrong that peaks show up — the issue is that the amplitude and the pass/fail conclusion depend on settings, so a scan with the wrong resolution bandwidth and detector can under-report or over-report margin, and either way the result isn't defensible. I'd explain that concretely rather than asserting it: show what changes when the settings are corrected, so the point lands as a measurement fact rather than a hierarchy call. Then I'd deal with the schedule. The right answer is usually not "cancel tomorrow" but "fix the settings and re-run the critical bands first" — a corrected scan of the frequencies that matter most is far more valuable than a full scan with settings that can't be trusted. I'd take responsibility for the decision and communicate it upward myself, so the junior engineer isn't left holding a schedule slip they didn't cause. And I'd treat the underlying cause as a process gap, not a personal failing: if the lab doesn't have a documented, standard-specific setup procedure that anyone can follow, this will happen again, so that's the follow-up action.

**Possible follow-ups:** How would you decide which bands to prioritize if you can only re-scan part of the range before the booked slot? What would you change in the lab's process so this doesn't recur?
