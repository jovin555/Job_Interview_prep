## Q1: How would you approach setting up a Segger J-Link's RTT (Real-Time Transfer) logging on a Zephyr RTOS target where the UART is already committed to a safety-critical protocol, and how would you avoid the logging itself perturbing the system's timing?

**Answer:** RTT is attractive here precisely because it sidesteps the UART entirely — it uses the debug probe's memory-access channel to read a ring buffer out of target RAM, so the application's serial port stays dedicated to the safety-critical protocol. The setup has two halves. On the target side, I'd enable the Zephyr RTT console/backend (or the Segger RTT library) and configure the up-buffer so the application writes into a lock-free ring buffer rather than blocking on a peripheral. On the host side, J-Link RTT Viewer or the RTT client reads that buffer over SWD/JTAG without halting the CPU.

The timing-perturbation concern is the real engineering problem. RTT writes are fast but not free: each log call costs a few hundred nanoseconds to a few microseconds depending on formatting, and if the buffer fills because the host isn't draining it, the default behavior can block or drop. For a safety-critical system I'd treat logging as a non-blocking, best-effort path: size the buffer generously, use a "drop on full" policy rather than blocking, and keep formatting out of the hot path where possible (log raw values and format host-side). I'd also isolate logging to lower-priority threads or a dedicated logging thread fed by a queue, so a burst of logs can't preempt a control loop. Finally, I'd measure the actual jitter introduced — toggle a GPIO at the start and end of the critical section with logging on and off, and compare on a scope — rather than assuming it's negligible.

**Possible follow-ups:**
- How would you decide between RTT, SWO/ITM, and a memory-backed log buffer for a given target?
- What would you do if the RTT buffer kept overflowing during the worst-case logging burst?

## Q2: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The core principle is that the build configuration is a controlled artifact, not a set of GUI checkboxes someone happened to click. In Keil uVision, that means the project file (`.uvprojx`) and any scatter file are treated as version-controlled source, reviewed like code, and diffed in pull requests. I'd pin the optimization level explicitly per target — typically `-O0` or `-O1` for debug and a validated level for release — and document *why* that level was chosen, because optimization can change timing and expose latent undefined behavior. The scatter/linker file defines memory layout (flash regions, RAM, any reserved calibration or bootloader areas), so it needs the same rigor: it should be reviewed against the memory map and checked that no region overlaps a reserved area.

For auditability, I'd make the build reproducible: fixed toolchain version (recorded, ideally with the installer hash), fixed device pack version, and a build script or batch file that invokes the toolchain from the command line so the output doesn't depend on IDE state. The startup code and any `__attribute__`-driven sections should be reviewed once and then left stable. I'd also add a post-build step that emits a map file and a checksum, and archive those alongside the binary so a released image can be tied back to an exact configuration. The goal is that anyone can rebuild the released binary from a tagged commit and get a byte-identical (or at least functionally identical, with a documented diff) result.

**Possible follow-ups:**
- How would you verify that the release optimization level hasn't introduced a timing regression?
- What would you check in the map file to confirm the linker script is doing what you expect?

## Q3: How would you approach using a spectrum analyzer's tracking generator and a directional coupler to characterize the input impedance of a custom analog front-end, and how would you decide whether the measurement is trustworthy enough to act on?

**Answer:** A tracking generator plus directional coupler lets you measure return loss (S11 magnitude) across frequency: the tracking generator sweeps a known stimulus, the directional coupler separates the forward and reflected waves, and the analyzer displays reflected power relative to forward power. From return loss you can infer the magnitude of the input impedance mismatch, and with a bit more care (phase information, or a VNA rather than a scalar analyzer) you can get closer to the complex impedance. For a custom analog front-end, the interesting range is usually the signal band plus some margin, and you're looking for whether the input looks like the intended impedance (often 50 Ω, or a high-impedance sensor interface) and where it deviates.

The trustworthiness question is where most of the work is. A scalar measurement gives you magnitude only, so you can't distinguish "too inductive" from "too capacitive" without additional info — that's a real limitation to state up front. Calibration matters enormously: you need to calibrate out the coupler's directivity, the cable losses, and the connector interface, ideally with a SOL (short-open-load) calibration at the reference plane. Directivity of the coupler sets the floor on how small a return loss you can resolve; if the coupler's directivity is poor, a "good" match can look bad. I'd also check that the front-end is powered and biased as it would be in operation, since an unpowered active front-end presents a completely different impedance. Before acting on the result, I'd cross-check with a known load (a 50 Ω terminator should read as a deep null) and, if the decision is important, confirm with a VNA that gives phase.

**Possible follow-ups:**
- How would you separate the front-end's impedance from the test fixture's parasitics?
- What would you do if the return loss looked acceptable but the front-end still misbehaved in-system?

## Q4: How would you approach setting up a logic analyzer's protocol decoder for a custom, non-standard serial protocol on a medical device, where the framing doesn't match any built-in decoder — for example, a proprietary sensor bus with a non-byte-aligned frame header?

**Answer:** When no built-in decoder fits, I'd build the decode in layers rather than trying to write one monolithic decoder. First, capture the raw waveform and get the physical layer right: confirm the clock/data relationship, idle levels, and where a frame actually starts. For a non-byte-aligned header, the trick is usually to decode at the bit level first — a simple "clocked data" or "async serial" decoder that produces a bit stream — and then apply a custom transform that searches for the header pattern at arbitrary bit offsets. Many logic analyzer tools (Saleae, sigrok, etc.) support a high-level analyzer API where you can write a small script that consumes the bit stream and emits frames once it sees the header, then slices out the payload fields by bit position.

The practical steps: define the frame format precisely on paper first (header pattern, length field, payload layout, checksum/CRC, inter-frame gap), because the decoder is only as good as that spec. Then implement the decoder to be tolerant of the real-world cases — resynchronization after a glitch, handling back-to-back frames, and flagging CRC failures rather than silently dropping them. I'd validate the decoder against a known-good capture where I can hand-decode a few frames and confirm the tool agrees. For a medical device, I'd also keep the decoder script under version control alongside the protocol spec, so when the protocol changes the decoder changes with it and the two stay in sync.

**Possible follow-ups:**
- How would you handle a protocol where the bit rate isn't constant across the frame?
- What would you log or export from the decoder to make a firmware-versus-hardware disagreement easy to settle?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** First, I'd separate the technical issue from the interpersonal one. Technically, the engineer isn't entirely wrong that peaks show up either way — but resolution bandwidth affects the measured amplitude of broadband versus narrowband emissions, and detector mode (peak vs. quasi-peak vs. average) changes whether a result is comparable to the limit line at all. A scan with the wrong settings can under- or over-report by many dB, so it's not a cosmetic difference; it's the difference between a result that means something and one that doesn't. I'd explain that concretely rather than just asserting "the standard says so," because the goal is for the engineer to internalize *why* the settings matter, not just to comply.

Then the logistics. The formal scan is tomorrow and the lab is booked, so I'd check whether the correct settings can be applied and the scan re-run within the available time — often the fix is a settings change and a re-scan, not a reschedule. If there's genuinely not enough time, I'd rather delay or rebook than submit a scan that can't be defended, because a pre-compliance result that later fails formal testing costs far more than a rescheduled lab slot. I'd frame the decision to the engineer and to management in those terms: the cost of a bad scan is a false pass or a false fail, both of which waste more time downstream. And I'd use it as a coaching moment — walk through the standard's requirements together, and set up a checklist for the next scan so the settings are verified before the session starts rather than discovered during it.

**Possible follow-ups:**
- How would you build a pre-scan checklist that catches this kind of setup error before lab time is spent?
- If the engineer felt undermined by the correction, how would you rebuild trust while still holding the technical line?
