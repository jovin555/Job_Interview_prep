## Q1: How would you approach setting up a repeatable firmware build and release process for a medical device that uses Zephyr RTOS, where you need to produce auditable artifacts for regulatory purposes?
**Answer:** For a medical device, the build process itself becomes part of the design history file, so reproducibility and traceability are the primary drivers. I'd start by establishing a single source of truth for the toolchain — pinning the Zephyr SDK version, the west version, and all module revisions using a manifest file, so that a build performed six months later produces byte-identical output. The build should be scripted end-to-end, typically through a CI pipeline, with each build tagged to the exact source commit hash. For auditable artifacts, I'd capture more than just the final binary: the build log, the manifest lock file, compiler version output, and a checksum manifest should all be archived alongside the firmware image. I'd also configure the build to embed build metadata — such as a version string, build date, and Git hash — into the firmware itself, so the running device can be traced back to its exact source. For regulatory traceability, each release candidate should go through a formal release process where the artifacts are reviewed, signed, and stored in a controlled location with access logging, rather than being built ad hoc on a developer's machine.

**Possible follow-ups:** How would you handle reproducibility when Zephyr's upstream dependencies change between releases? What build metadata would you consider essential to embed in the firmware image?

## Q2: How would you approach using a logic analyzer to debug a USB 2.0 device that enumerates correctly on some hosts but fails on others, where the failure is intermittent and appears to be timing-related?
**Answer:** USB enumeration timing failures that are host-dependent often point to subtle timing margin issues rather than protocol violations. I'd start by capturing a full enumeration sequence on both a host that works and one that fails, using a logic analyzer with USB decoding capability and sufficient sampling rate — at least 4x the USB bit rate for reliable edge detection. I'd compare the two captures systematically, looking at several specific areas: the timing of the device's response to the SETUP packet (the device has a limited window to respond), the stability of the chirp sequence during reset, and the timing of the device descriptor read — particularly whether the device is sending data too quickly after the host's IN token. A common issue is that the device firmware begins transmitting before its internal clock has fully stabilized, or the response time varies depending on what else the firmware is doing. I'd also check for frame timing issues: whether the device is holding the bus at the wrong time or if its SOF tracking is drifting. If the timing looks marginal on the failing host, I'd look at the device's clock source — is it using an internal oscillator with wider tolerance, or an external crystal? I'd also examine whether the device's D+ pull-up resistor value is within spec, since that affects how the host detects the device attach. The key is to capture enough enumeration attempts on the failing host to catch the actual failure event, which may require triggering on a specific packet type or using the analyzer's deep memory to record a long window.

**Possible follow-ups:** What specific timing parameters would you measure from the captured waveforms to quantify the margin? How would you distinguish between a firmware timing issue and a hardware signal-integrity issue from the logic analyzer capture alone?

## Q3: How would you approach setting up a component library management strategy in KiCad for a medical device project that needs to maintain strict revision control and regulatory traceability, given that KiCad's library format is file-based rather than database-driven?
**Answer:** KiCad's file-based libraries actually lend themselves well to version control, which is the backbone of regulatory traceability. I'd structure the libraries as a separate repository — or a clearly isolated directory within the project repo — containing three parallel library types: schematic symbols, footprints, and 3D models. Each component would have a consistent naming convention that includes a revision or date code, such as `SENSOR-PRESSURE-ABC123-R1`, so that the schematic and BOM can be traced to a specific library version. The key practice is treating library changes with the same rigor as source code changes: every modification goes through a review process, is committed with a descriptive message referencing the change reason, and is tagged at release points. For regulatory traceability, I'd maintain a component metadata file — either as a custom field in the symbol or as a separate CSV — that records the manufacturer part number, datasheet revision, and the date the component was approved for use. When a component changes, I'd use KiCad's ERC to flag any schematic that references the old version, forcing a review of whether the change affects existing designs. I'd also avoid the common pitfall of letting developers modify libraries in-place on their local machines; instead, the library repo is the single source of truth, and local changes are either pushed for review or done in a branch. For release traceability, the BOM generated from the schematic should include the library revision or component revision field, so you can always reconstruct exactly what was approved.

**Possible follow-ups:** How would you handle a component that needs a footprint change after the PCB has already been released to manufacturing? What fields would you consider essential to track for regulatory compliance in the component metadata?

## Q4: Walk me through your process for using LTSpice to simulate the effect of power supply ripple on a precision analog sensor front-end, and how you would correlate those simulations with real oscilloscope measurements.
**Answer:** The goal here is to understand how noise on the supply rail couples into the measurement path, so the simulation needs to model both the supply source and the analog front-end's sensitivity to supply variations. I'd start by building the analog front-end circuit in LTSpice, including the sensor model, the amplifier, and any filtering. For the power supply, I'd create a model that represents the actual ripple characteristics — this could be a switching regulator model if I have one, or a simplified equivalent: a DC source with a superimposed AC signal at the switching frequency and its harmonics. The key is to include the supply rejection characteristics of the amplifier, which means using a realistic SPICE model from the manufacturer rather than an idealized op-amp. I'd run an AC analysis sweeping the ripple frequency to see how much of the supply noise appears at the output, and then a transient analysis with the actual ripple waveform to see the time-domain effect. I'd also simulate the effect of decoupling capacitors and any supply filtering between the regulator and the analog section. For correlating with real measurements, I'd set up the actual hardware with a clean supply first, measure the output noise floor, then introduce controlled ripple using a function generator injected through a summing node or by loading the supply. Using an oscilloscope, I'd measure the ripple at the supply pin of the amplifier and simultaneously measure the amplifier output, using FFT on both channels to compare the frequency content. The correlation step is comparing the transfer function — the ratio of output noise to input ripple at each frequency — between simulation and measurement. If they diverge, common causes are missing parasitic elements in the simulation (like trace inductance or capacitor ESR) or the amplifier model not accurately representing the real device's PSRR at higher frequencies.

**Possible follow-ups:** How would you model the decoupling capacitor's non-ideal behavior in the simulation? What would you do if the measured noise at the amplifier output was significantly higher than the simulation predicted?

## Q5: (Behavioral) Imagine you are leading a design review for a medical device PCB, and you discover that the firmware team has been using a different version of the I2C protocol than what the hardware actually implements — the firmware is expecting 7-bit addressing with a specific register map, but the hardware uses 10-bit addressing with a different register layout. The integration testing is scheduled to start in two days, and both teams are confident their implementation is correct. How would you handle this situation?
**Answer:** The first priority is to establish ground truth rather than getting into a debate about who is right. I'd call a short, focused meeting with both teams and ask them to bring their source of truth: the firmware team brings the sensor datasheet section they based their register map on, and the hardware team brings the schematic and the actual sensor part number and its datasheet. The goal is to determine which implementation actually matches the physical hardware — not which team is more convincing. If the hardware is correct, then the firmware needs to change, and vice versa. Given the two-day timeline, I'd also assess the scope of the change: if the firmware needs to switch to 10-bit addressing, that might be a small change in the I2C driver configuration, but if the register map is also different, it could be more substantial. I'd ask the firmware team to estimate the effort honestly, and I'd verify their estimate rather than taking it at face value. I'd also check whether the sensor on the actual PCB is the same variant as what the firmware team tested on their evaluation board — sometimes the eval board has a different sensor revision. Once the correct implementation is identified, I'd have the responsible team make the change immediately, with the other team reviewing the diff. I'd also update the interface documentation to prevent this from recurring. If the change can't be fully verified before integration testing, I'd be transparent with management about the risk and propose a mitigation — perhaps starting integration testing with a subset of tests that don't exercise the sensor, while the fix is being validated. The key is to treat this as a process failure, not a blame exercise, and to focus everyone on the shared goal of a correct, safe device.

**Possible follow-ups:** How would you prevent this type of interface mismatch from happening on future projects? What documentation or review checkpoints would you put in place to catch protocol discrepancies before integration testing?
