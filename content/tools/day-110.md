## Q1: How would you approach setting up a simulation workflow in LTSpice for a mixed-signal board where a switching regulator and a precision analog front-end share the same supply rail, and how would you decide which simulation results are trustworthy enough to act on?

**Answer:** The core challenge is that a single SPICE deck has to capture two very different regimes at once: the switching regulator's large-signal, high-di/dt behavior and the analog front-end's small-signal sensitivity. I'd structure it in layers rather than trying to simulate the whole board in one monolithic run.

First, I'd build the switching regulator stage on its own with a realistic load model — including the actual output capacitor ESR/ESL and the parasitic inductance of the trace between the regulator and the analog section — and run a transient simulation long enough to reach steady state, capturing the ripple waveform at the analog load point rather than just at the regulator output. That ripple waveform, plus any switching-node ringing, is the "disturbance" I care about.

Second, I'd build the analog front-end separately and inject that captured ripple as a source at its supply pin, then run an AC or transient analysis to see how much of it couples into the signal path — through the amplifier's finite PSRR, through the reference, through any shared ground impedance. This two-stage approach keeps each simulation tractable and makes the coupling mechanism explicit rather than buried in one giant netlist.

On trustworthiness: I'd only act on results that (a) converge cleanly with a tightened timestep and reasonable tolerances, (b) are checked against a hand calculation or a simplified analytical model for the dominant effect, and (c) reproduce when I perturb component values within their tolerance bands — if a 20% change in an output cap ESR flips the conclusion, the result isn't robust enough to drive a design decision. I'd also sanity-check against a bench measurement of ripple on a real board before trusting any coupling prediction, because SPICE won't model PCB parasitics or radiated coupling unless I explicitly put them in.

**Possible follow-ups:** How would you model the PCB trace inductance between the regulator and the analog load in LTSpice, and where would you get that number? What would make you decide a full-board transient simulation is worth the runtime versus the two-stage approach?

## Q2: How would you approach setting up a cross-probe workflow between OrCAD Capture and Cadence Allegro so a layout review can move efficiently between schematic and PCB, and what would you check to confirm the link actually works before relying on it in a review?

**Answer:** Cross-probing depends on the two tools sharing a consistent design database and a live communication channel, so I'd verify the foundation before touching the review itself.

First, confirm the schematic and layout are the same revision — the netlist in Allegro must have been imported from the Capture design you're actually reviewing, not an earlier export. A stale netlist is the most common reason cross-probe "works" but highlights the wrong thing. I'd check the design revision or a timestamp/hash on both sides.

Second, confirm the cross-probe session is actually established: in Capture, the cross-probe command should target the running Allegro session, and both tools need to be pointed at the same design. I'd test it deliberately with a known, unambiguous object — pick a specific component reference designator in the schematic and confirm Allegro highlights exactly that footprint, then reverse it: select a net in Allegro and confirm Capture highlights the correct net and its pins. Testing both directions matters because one direction can silently fail while the other works.

Third, I'd test a net-level probe, not just a component-level one, since nets are where most review findings live — confirm that probing a named net in the schematic highlights the full routed net in the layout, including any branches.

For the review itself, I'd keep a short checklist: same revision, both directions verified, net-level probe verified, and a fallback plan (search by reference designator or net name) in case the live link drops mid-review. I'd also make sure the reviewer knows the cross-probe is a navigation aid, not a verification tool — it tells you where to look, not whether the layout is correct.

**Possible follow-ups:** What would you do if cross-probe highlights the right component but the wrong net? How would you handle a review where the layout was done by a different team and the netlist provenance is unclear?

## Q3: How would you approach configuring a Keil uVision project for a medical device firmware build so that the optimization level, linker script, and startup code are locked down and auditable, rather than relying on whatever the IDE defaults to?

**Answer:** The goal is that a build is reproducible and that every setting that affects the binary is explicit, version-controlled, and reviewable — not hidden in a project file that someone can silently change in the IDE.

I'd start by treating the project file itself as a controlled artifact: it goes into version control, and changes to it go through review like code. Then I'd make the critical settings explicit rather than inherited. Optimization level: set it deliberately per build configuration (debug vs release) and document why — for a medical device, the release optimization level should be the one that was actually tested, and the debug build should match it closely enough that behavior doesn't diverge. Linker script: point to a specific, version-controlled scatter file rather than a default, and make sure the memory regions (flash, RAM, any reserved calibration or bootloader areas) are defined explicitly so nothing overlaps. Startup code: use a known, reviewed startup file, and confirm the vector table and stack/heap sizing are set intentionally.

For auditability, I'd add a post-build step that emits a build manifest — compiler version, optimization flags, linker script hash, git commit — so a given binary can be traced back to its exact inputs. I'd also verify the settings actually took effect by inspecting the map file and the disassembly at a few key functions, rather than trusting the dialog boxes.

The key discipline is: if a setting affects the output binary, it must be visible in the project file, justified, and reproducible from a clean checkout.

**Possible follow-ups:** How would you catch a situation where someone changed the optimization level locally but the committed project file still shows the old value? What would you check in the map file to confirm the linker script's memory layout is being honored?

## Q4: How would you approach setting up a test and measurement bench for bring-up of a new mixed-signal medical device prototype, deciding which instruments to dedicate versus share, and how would you keep the setup repeatable across multiple engineers?

**Answer:** I'd start from the bring-up task list and work backward to instruments, rather than starting from what's in the lab.

The dedicated-versus-shared decision comes down to contention and calibration. Instruments that are used continuously during bring-up and are cheap enough to duplicate — a bench DMM, a basic scope channel, a bench supply per rail — I'd dedicate, because waiting for a shared instrument kills momentum and encourages people to "make do" with the wrong tool. Expensive or calibration-critical instruments — a high-bandwidth mixed-signal scope, a spectrum analyzer, a precision source — I'd share, but with a booking discipline and a documented default setup so each user starts from a known state rather than whatever the last person left.

For repeatability across engineers, the biggest lever is standardizing the setup, not the hardware. I'd define a bench configuration sheet: which instrument, which probe, which attenuation, which default settings, and where the grounds connect. I'd label the bench and the cables so a probe's attenuation is unambiguous. For anything where setup drift would invalidate a measurement — probe compensation, scope bandwidth limit, spectrum analyzer RBW — I'd write a short pre-measurement check that each engineer runs before trusting a reading.

I'd also keep a shared measurement log: what was measured, with what setup, and what the result was, so a second engineer can reproduce or challenge a finding rather than re-deriving it from scratch. And I'd make sure the bench has a known-good reference — a signal generator or a reference board — so anyone can sanity-check the setup before chasing a "problem" that's actually an instrument misconfiguration.

**Possible follow-ups:** How would you handle a situation where two engineers need the same shared instrument at the same time during a critical bring-up? What would you put on the bench configuration sheet to prevent the most common probing mistakes?

## Q5: (Behavioral) Imagine you're leading a project where a junior engineer has set up the lab's spectrum analyzer and near-field probe for an EMI pre-compliance scan, and you discover the resolution bandwidth and detector mode are set for a quick "get a feel for it" scan rather than the settings the test standard requires. The engineer is confident the settings are fine because "the peaks show up either way." The formal scan is scheduled for tomorrow, and the lab time is booked. How would you handle this situation?

**Answer:** The immediate priority is to separate the two issues: the scan settings are wrong, and the engineer believes they're fine. I'd address the technical problem first because the schedule is real, but I wouldn't let the misconception stand, because it'll resurface.

On the technical side, I'd explain concretely why the settings matter rather than just asserting it. Resolution bandwidth affects the noise floor and how a broadband versus narrowband emission is displayed — a wide RBW can hide a narrow emission below the limit or make a broadband one look worse than it is. Detector mode changes what value gets reported: peak versus quasi-peak versus average can move a reading by several dB, and the standard specifies which detector applies. "The peaks show up either way" is true and irrelevant — the question is whether the *reported level* is the one the standard defines. I'd demonstrate this if I can: re-scan one offending frequency with the correct settings and show the number move. A concrete delta is more persuasive than an argument.

On the schedule: I'd check whether the correct settings can be applied and the scan re-run within the booked time — often the fix is a settings change and a re-scan, not a re-booking. If the full formal scan genuinely can't be completed in the window, I'd use the time to run the scan correctly on the highest-risk frequencies and flag the rest for a follow-up session, rather than producing a full set of numbers that aren't defensible.

On the engineer: I'd frame it as "the standard defines these settings, and our job is to match them" rather than "you got it wrong," and I'd make the standard's requirements the shared reference so it's not my opinion versus theirs. I'd also ask them to walk me through how they chose the settings, because if the root cause is "I followed a tutorial," that's a gap worth closing for the next scan.

**Possible follow-ups:** How would you decide which frequencies to prioritize if you can only complete part of the scan in the booked window? What would you change in the team's process so the next pre-compliance scan starts from the correct settings by default?
