# debugging-failure-analysis — Day 104

## Q1: How would you approach a failure investigation where a device's firmware occasionally enters a hard fault handler, and the stack trace consistently points to a memory copy operation — but the source and destination addresses are always valid, and the memory regions being copied are within their allocated bounds?

**Answer:** A hard fault landing in a memcpy with valid-looking pointers is a classic case of the fault being a *symptom* rather than the cause. The first thing I'd do is stop trusting the stack trace as a pointer to the bug — the fault handler captures the state at the moment of the exception, but the corruption that caused it may have happened much earlier. I'd work through it in layers:

First, decode the fault status registers (CFSR/HFSR/MMFAR/BFAR on Cortex-M class parts) rather than just the PC. The sub-fault type tells you a lot: an imprecise bus fault, a stacking error, an unaligned access, or an escalation from a configurable fault all point in different directions. If it's an imprecise bus fault, the reported PC is essentially meaningless and I'd look at what was in flight before the copy.

Second, check the *alignment* and *size* arguments, not just the pointer values. A memcpy that walks off the end of a buffer because the length argument was corrupted, or that does a word access on an unaligned address, will fault even though both base pointers look sane in the debugger. I'd also check whether the copy is running from an ISR and whether the source or destination overlaps a region another context is writing — a re-entrancy or DMA-coherency problem can corrupt the length or the data mid-copy.

Third, I'd look at stack depth and interrupt nesting. A memcpy in a deeply nested ISR can overflow the stack and clobber the return path or the arguments, which then manifests as a fault inside the copy. Checking the stack canary / high-water mark and the MSP/PSP values at fault time is cheap and often decisive.

Finally, I'd try to make it deterministic: enable the MPU to guard the buffers involved, add a canary around the destination region, and run under a stress load that increases interrupt frequency. If the fault rate scales with interrupt load or with a particular peripheral being active, that points to a concurrency or DMA issue rather than a logic bug in the copy itself. The corrective action has to address the *corruption source*, not the memcpy — patching the copy would just move the fault somewhere else.

**Possible follow-ups:** How would you tell the difference between a stack overflow and a DMA writing past its buffer as the underlying cause? What would you change in the firmware architecture to make this class of bug easier to catch in the future?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** This is a load-transient and loop-stability problem, so I'd separate "the regulator can't keep up" from "the measurement is lying to me" before changing anything.

First, verify the measurement itself. Where am I probing? Ripple measured at the wrong point — long ground lead, probe tip and barrel not used, probing across a via rather than at the decoupling capacitor pads — will show artifacts that aren't really on the rail. I'd re-probe directly across the output capacitor with a short ground spring, AC-coupled, bandwidth-limited to a sensible range, and confirm the ripple is genuinely on the rail and not pickup on the probe.

Second, characterize the transient properly. I'd capture the switching subsystem's current waveform (current probe or a sense resistor) alongside the rail voltage, triggered on the load step. That tells me whether the dip is a *response* to a fast edge the regulator loop can't slew, or a sustained oscillation. If it's a fast-edge response, the fix is usually more bulk/local capacitance and better decoupling placement at the load, plus checking the load's own slew rate. If it's a sustained oscillation, I'd look at loop stability — output capacitor ESR and value versus the regulator's compensation, and whether the layout added parasitic inductance between the regulator and its output cap.

Third, I'd check the obvious coupling paths: is the high-current subsystem's return current sharing the same ground path as the analog/regulator reference, causing ground bounce that shows up as apparent ripple? A star or partitioned ground, or moving the high-current return, often cleans this up. I'd also check whether the switching subsystem's own supply is drooping and feeding back through a shared upstream rail.

Only after I understand whether it's transient response, loop stability, or ground coupling would I change components — and I'd change one thing at a time and re-measure at the same probe point so the comparison is valid.

**Possible follow-ups:** How would you determine whether the output capacitor ESR is the limiting factor versus insufficient bulk capacitance? What layout changes would you prioritize if the ripple is caused by shared return impedance?

## Q3: A medical device passes all functional and safety tests at design verification, but during a 30-unit pilot production run, three units fail a 72-hour burn-in test with the same symptom: the device stops communicating after roughly 48 hours and requires a power cycle to recover. How would you approach this?

**Answer:** The fact that it's a *pilot* run and a *time-dependent* failure is the key signal — this smells like a latent defect or a marginal design that only shows up under sustained thermal or timing stress, not a gross functional bug. I'd treat it as a structured 8D-style investigation.

First, contain and characterize. I'd pull the three failed units and the passing units and compare them: same component lots? Same assembly line/station? Same firmware build? Same environmental position in the burn-in rack? If all three failures cluster on one lot or one station, that redirects the investigation toward manufacturing. If they're spread randomly, it points to design margin.

Second, reproduce and instrument. A "stops communicating after ~48 hours, recovers on power cycle" symptom is consistent with a few families: a watchdog or bus-recovery state that latches, a thermal drift pushing a timing margin out of spec, a memory/stack leak that eventually corrupts a comms buffer, or a connector/solder joint that opens with thermal cycling. I'd put a unit back on burn-in with logging enabled — comms error counters, temperature, supply rails, watchdog resets, heap/stack high-water marks — so the failure is captured with data rather than just the symptom.

Third, use the passing units as controls. If I can make a passing unit fail faster by raising ambient temperature or adding margin stress, I've found a design-margin issue and can quantify it. If only the original three fail, I'd do failure analysis on the returned units — X-ray or cross-section on suspect joints, check for component lot differences, look for contamination or flux residue.

Fourth, trace to root cause and corrective action. The output of the investigation has to be a verified root cause with a corrective action that's validated by re-running the burn-in on a larger sample, plus a containment action for any units already built. I would not close it on "reseat and it works" — that's a symptom fix.

**Possible follow-ups:** How would you decide whether to halt the pilot run or continue while investigating? What would you add to the burn-in test to catch this class of failure earlier in future builds?

## Q4: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** The bench-to-installed delta is the whole story here — something about the mechanical/electrical environment changes when the unit is assembled and mounted, and I'd treat the enclosure and mounting as part of the circuit rather than as an afterthought.

First, I'd reproduce it deliberately and quantify it. Measure the offset with the harness, then with the board in the enclosure but not mounted, then mounted in the final position. That three-point comparison isolates whether it's the enclosure (shielding, grounding, cable routing) or the mounting (mechanical stress, chassis ground, proximity to a metal surface) that introduces the offset.

Second, I'd look at the likely mechanisms. A consistent offset — not noise — usually points to a DC path change: a ground reference shifting because the enclosure or mounting screw creates a new ground return path or a ground loop; a shield or chassis connection changing the reference potential of the analog front-end; mechanical stress on a component (a flexure-induced change in a resistor or a solder joint) altering a divider; or a cable/connector in the final assembly adding series resistance or a thermocouple effect at a dissimilar-metal junction.

Third, I'd probe the reference and the signal path in the installed state. If the offset appears at the ADC input but not at the sensor output, it's in the front-end or the reference; if it appears at the sensor output, it's the sensor or its wiring. Checking the analog ground potential relative to the digital/chassis ground in the installed state is often the fastest discriminator.

Fourth, I'd confirm with a controlled change: temporarily isolate the enclosure ground, or mount on an insulating fixture, and see if the offset disappears. That confirms the mechanism before I commit to a design change — which might be a grounding/stitching change, a shield connection revision, a mechanical decoupling of the stressed component, or a calibration step in production.

**Possible follow-ups:** How would you distinguish a ground-reference shift from a mechanical stress effect on a component? What would you change in the design review process to catch enclosure-induced offsets before pilot production?

## Q5: You're leading a cross-functional failure investigation where the firmware and hardware teams each believe the other side owns an intermittent communication failure, and neither has conclusive evidence. How would you structure the investigation to break the deadlock?

**Answer:** When two teams are each convinced the other owns the bug, the deadlock is usually a *measurement* problem, not a technical one — nobody has data that discriminates between the hypotheses. My job as lead is to convert the argument into a set of falsifiable tests and get both teams to agree on what evidence would change their mind.

First, I'd reframe the problem jointly. Get both teams in one room and write down the two hypotheses explicitly, plus what each would predict. "Hardware timing margin" predicts the failure rate scales with temperature, supply voltage, or cable length. "Firmware race condition" predicts it scales with interrupt load, task scheduling, or specific code paths. Those predictions are testable and different, which is exactly what we need.

Second, I'd design discriminating experiments rather than asking each team to defend its position. Examples: run the same firmware on a known-good hardware variant and vice versa; instrument the bus with a logic analyzer or scope to capture the actual timing at the failure, independent of either team's interpretation; add firmware counters that log the state at the moment of failure so we can see whether the hardware was late or the firmware missed the window. The goal is to produce evidence that one hypothesis explains and the other doesn't.

Third, I'd assign ownership of the *experiment*, not the *conclusion*. Each team runs the tests the other team proposes — that removes the incentive to design tests that confirm their own view and builds mutual credibility.

Fourth, I'd set a decision point. If the evidence is still ambiguous after the discriminating tests, I'd escalate to a joint review with a defined tie-breaker — often a fault-injection test that forces each failure mode and shows which one matches the field signature. Throughout, I'd keep the tone collaborative: the shared goal is a verified root cause, and the corrective action has to be validated against the same evidence standard regardless of which team "wins."

**Possible follow-ups:** What would you do if the discriminating test is inconclusive and the schedule forces a decision? How would you make sure the corrective action is validated by both teams rather than just the one that proposed it?
