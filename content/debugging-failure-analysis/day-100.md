# debugging-failure-analysis — Day 100

## Q1: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** The key observation is that the offset appears only when two variables change at once — mechanical assembly and final mounting — so the first job is to separate them. I'd build a test matrix: open bench with harness, open bench with the actual patient cable, board inside the enclosure but not mounted, and fully assembled and mounted. That isolates whether the enclosure itself, the mounting position, or the combination is responsible.

The most common mechanisms for a position-dependent offset are mechanical stress on the sensing element or its solder joints, a changed ground reference (mounting to a chassis or grounded fixture can shift the analog ground potential), and parasitic coupling that changes when the board sits close to metal or a power source. I'd measure the offset at the ADC input with a precision DMM and scope in each configuration, and also measure the analog ground relative to chassis ground — a few millivolts of ground shift across a shared return can look exactly like a sensor offset. If the offset tracks mechanical stress, I'd look at flexure of the board or the sensor package; if it tracks grounding, I'd look at the return path and any chassis-bonding points.

Once I have a candidate mechanism, I confirm it by controlled perturbation — for example, temporarily isolating the board from the chassis with insulating standoffs, or reversing the mounting orientation — and see whether the offset follows. Only then do I decide whether the fix is mechanical (strain relief, mounting tolerance), electrical (grounding/bonding scheme, input filtering), or calibration-related.

**Possible follow-ups:** How would you distinguish a genuine sensor offset from an amplifier input-offset shift caused by common-mode voltage change? What would you do if the offset were within the sensor's specified accuracy but still tripped the system's fault threshold?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** This is a load-transient and power-distribution problem, so I'd start by characterizing it properly rather than guessing at components. First, measure the ripple at the load — right at the decoupling capacitors of the aggressor subsystem and at the input of the sensitive circuitry — not just at the regulator output. Ripple that looks fine at the regulator but is large at the load points to the distribution network: trace inductance, insufficient or poorly placed decoupling, or a shared return path carrying the switching current.

Next I'd look at the transient itself: what is the di/dt, what is the repetition rate, and does the dip correlate with a specific switching edge? A scope with a proper ground-spring probe tip (not a long ground lead) is essential here, because a long ground lead will manufacture ringing that isn't real. I'd also check whether the ripple is differential (across the rail and its return) or common-mode (appearing on both), since the fixes differ — more/better-placed bulk and high-frequency decoupling and a tighter return path for differential; grounding and shielding review for common-mode.

Then I'd verify the regulator's loop stability and transient response under the actual load step, and check whether the aggressor's current return shares impedance with the sensitive load's return. The fix is usually a combination of local decoupling at the load, separating or star-pointing returns, and possibly adding a small series ferrite or LC filter — but I'd confirm with measurement after each change rather than stacking fixes.

**Possible follow-ups:** How would you decide between adding bulk capacitance versus improving the return path? What measurement would tell you the regulator's loop is marginally stable?

## Q3: A device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline. How would you approach this investigation?

**Answer:** The hard part here is that nothing in the system flags the error, so the investigation has to start from the data itself. I'd first characterize the errors statistically: are they single-bit flips, small offsets, stuck values, or values from a neighboring channel? That pattern immediately narrows the candidate mechanisms — bit flips suggest memory or bus integrity, small offsets suggest analog or calibration, stuck or swapped values suggest a firmware indexing or buffer-management bug.

Then I'd work backward along the signal chain and add instrumentation at each stage: log the raw ADC counts alongside the processed value, timestamp each sample, and check whether the bad value correlates with a specific event — a communication transaction, a DMA transfer, a context switch, a temperature threshold. If the raw ADC value is correct but the stored/transmitted value is wrong, the problem is in the digital path (buffer handling, shared memory, DMA descriptor reuse, a race between the sampling ISR and the consumer). If the raw value is already wrong, it's analog or timing — settling time, multiplexer crosstalk, reference drift.

I'd also try to reproduce it under accelerated conditions: increase sample rate, add bus traffic, raise temperature, run longer. A bug that only shows up in offline review is often a low-probability race or a marginal timing condition, so making it more frequent is the fastest route to a confirmed root cause. Throughout, I'd keep the "plausible but wrong" nature in mind — the fix may need a plausibility check or cross-channel consistency check in firmware as a defense in depth, even after the root cause is found.

**Possible follow-ups:** How would you design a self-test that could catch this class of error in the field? If the error only appears after long runtimes, how would you structure an accelerated test to reproduce it?

## Q4: You're leading a failure investigation and you've reached a point where two plausible root causes remain, both supported by partial evidence, and the team is split on which to pursue. How would you handle this and drive the investigation to a conclusion?

**Answer:** When two hypotheses both have partial support, the trap is letting the team argue about which is "more likely" instead of designing a test that discriminates between them. My first move is to reframe: for each hypothesis, what observation would be true if it were the cause and false if it weren't? Then I look for the cheapest, fastest experiment that produces a different predicted outcome for the two — a targeted measurement, a controlled perturbation, or a swap of a single variable.

I'd also make the decision criteria explicit and agreed in advance, so the result isn't argued after the fact. If a discriminating test isn't feasible in the time available, I'd consider whether both causes could be addressed with independent, low-risk mitigations and whether the evidence supports treating them as contributing factors rather than competing ones — sometimes the honest conclusion is "both contribute, and here's the evidence for each."

On the team side, I'd keep it structured and depersonalized: the hypotheses are on the whiteboard, not attached to whoever proposed them, and the plan is driven by the discriminating tests. I'd set a checkpoint — if the test is inconclusive by a certain point, we escalate to a broader diagnostic (e.g., fault injection or a design-of-experiments approach) rather than continuing to debate. Documenting the reasoning and the decision in the investigation record matters too, especially in a regulated context, because the corrective action has to be traceable to evidence.

**Possible follow-ups:** What would you do if the discriminating test is destructive or risks damaging a limited sample? How do you keep a split team engaged when their preferred hypothesis is ruled out?

## Q5: How would you approach a failure investigation where a device's power rail collapses only during a specific operating mode, but the regulator and its passives all measure within specification when the board is powered in isolation?

**Answer:** The fact that everything measures fine in isolation tells me the failure is an interaction, not a component defect — so I'd stop testing the regulator alone and start testing it in the exact conditions where it fails. First, reproduce the collapse with the scope on the rail and on the regulator's enable, feedback, and input pins simultaneously, triggered on the collapse, so I can see the sequence of events: does the rail fall because the load current spikes, because the enable or feedback signal glitches, or because the input rail sags?

Then I'd characterize the load in that operating mode: inrush or transient current, whether a high-current subsystem or a motor/actuator is switching, and whether the collapse correlates with a specific event in the mode sequence. A rail that collapses only in one mode often means the mode enables a load the regulator wasn't dimensioned for transiently, or a sequencing issue where one rail comes up before another and the regulator enters an unintended state.

I'd also check for protection-circuit interaction — overcurrent or thermal shutdown latching, or a power-good signal dropping and causing a downstream reset — and verify the regulator's stability margin under the actual load and temperature, since a marginally stable loop can look perfect on a bench supply and collapse under a real transient. The fix depends on which mechanism the measurements confirm: input/output capacitance and transient headroom, sequencing and enable logic, or a load-profile change in that mode.

**Possible follow-ups:** How would you capture a collapse that happens too fast for a standard trigger? What would you check first if the collapse only occurs at elevated temperature in that mode?
