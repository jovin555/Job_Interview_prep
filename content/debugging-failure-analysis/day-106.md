# debugging-failure-analysis — Day 106

## Q1: How would you approach a failure investigation where a device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and the error is only caught later when the data is reviewed offline?

**Answer:** The defining difficulty here is that no guardrail fires: the value is in range, the self-test passes, and the error surfaces only in retrospective review. That means the investigation has to start by turning an invisible failure into a measurable one. First I'd characterize the error from the offline data: is it a fixed offset, a gain error, a single-bit flip, a stale sample, or a value from the wrong channel? The statistical signature usually narrows the suspect list before any bench work. A fixed offset points at calibration or a reference; a single-bit flip points at memory or bus integrity; a stale value points at a timing or handshake problem; a wrong-channel value points at multiplexer or configuration sequencing.

Next I'd build a reproduction harness that logs the raw ADC output, the firmware's post-processed value, and the transmitted value simultaneously, timestamped, so I can see exactly where the corruption is introduced — at conversion, in processing, in storage, or on the wire. If the raw ADC and the processed value agree but the transmitted value differs, the problem is downstream of the conversion. If they diverge at processing, I'd look at the math path: fixed-point scaling, saturation, type conversions, buffer reuse. If the raw value itself is wrong, I'd correlate with operating state — what else was running at that moment, was a conversion triggered during a switching event, was the channel reconfigured mid-conversion.

I'd also add a lightweight runtime invariant checker — for example, a plausibility cross-check against a redundant or slower reference measurement — so the failure gets caught in the act rather than weeks later. The key discipline is to keep the investigation evidence-driven: don't accept "the firmware is correct" or "the hardware is fine" as a starting assumption, because the whole point of this class of bug is that both look correct in isolation.

**Possible follow-ups:** How would you decide whether to add a permanent runtime cross-check versus fixing the underlying cause? What would you do if the error only reproduces in the field and never on the bench?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** This is a load-transient and power-distribution problem, so I'd work it from the source outward. First I'd measure properly: ripple must be probed at the point of load with a short ground lead — a long ground clip picks up loop inductance and gives you a lying measurement. I'd capture the transient with enough bandwidth and look at both the amplitude and the shape: a fast spike suggests loop inductance or insufficient decoupling at the load, a slower droop suggests the regulator's transient response or bulk capacitance is inadequate, and ringing suggests a stability or ESR issue in the control loop.

Then I'd divide the problem: is the disturbance conducted through the shared rail, or is it coupled — radiated or via a shared ground return? I'd check whether the ripple appears on the input side of the regulator as well as the output; if it's on both, the source is upstream or the loop is common. I'd also look at the return path: a high-current switching subsystem returning through a shared ground plane segment creates ground bounce that shows up as apparent ripple everywhere.

For fixes I'd consider them in order of root cause rather than convenience: improve local decoupling at the load with the right capacitor mix and placement, tighten the high-current loop area, separate the return paths so the switching current doesn't share copper with sensitive analog returns, and only then look at regulator compensation or added bulk capacitance. I'd verify each change with the same measurement setup so I'm comparing like with like, and I'd check the fix across load steps and temperature, not just the one condition that reproduced it.

**Possible follow-ups:** How would you distinguish ground bounce from genuine rail ripple in your measurement? What role does capacitor placement play versus capacitor value?

## Q3: A medical device passes all functional and safety tests at design verification, but during a 30-unit pilot production run, three units fail a 72-hour burn-in test with the same symptom: the device stops communicating after roughly 48 hours and requires a power cycle to recover. How would you approach this?

**Answer:** Three identical failures out of thirty with a consistent time-to-failure is a strong signal — it suggests a systematic, time-dependent mechanism rather than random component failure. The first thing I'd do is resist the temptation to treat the three units as three separate problems; they're almost certainly one problem with a common cause.

I'd start by preserving evidence: capture the state of a failed unit before power-cycling it — current draw, rail voltages, any debug port access, whether the processor is running or hung, whether the communication peripheral is alive but the protocol layer is stuck. That single observation splits the problem space enormously. If the processor is hung, I'm looking at firmware, memory, or a hardware fault. If the processor is running but the link is dead, I'm looking at the communication stack, the PHY, or a state machine that never recovers.

Then I'd look for the time-dependent variable. Forty-eight hours is long enough that thermal cycling, drift, leakage, counter rollover, memory fragmentation, or a slow accumulation effect (log buffer filling, watchdog interaction, connection table exhaustion) are all candidates. I'd instrument a fresh unit to log the relevant internal state over the full burn-in window so I can see the trajectory approaching failure rather than only the endpoint. I'd also compare a passing unit against a failing one on the same instrumentation — the difference between them is often more informative than the failure itself.

Finally, I'd check whether the three failures correlate with anything in production: build date, component lot, test fixture, or operator. If they cluster, that's a manufacturing signal; if they're spread evenly, it's more likely a design margin issue that pilot volume simply exposed. Either way, the corrective action has to be verified by reproducing the failure and then demonstrating it no longer occurs under the same burn-in conditions.

**Possible follow-ups:** What would you check first if you could only make one measurement on a failed unit? How would you decide whether this is a design escape or a manufacturing escape?

## Q4: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** The bench-to-installed delta is the whole clue: something about the assembled and mounted configuration changes a physical variable that the test harness doesn't reproduce. I'd enumerate what changes between the two states — mechanical stress on the PCB, grounding and shielding topology, cable routing and length, proximity to metal structures, thermal environment, and the reference or return path. A small consistent offset usually points at a reference or bias issue rather than noise, so I'd focus there first.

I'd measure the offset's behavior: does it appear the moment the enclosure is closed, or only after mounting? Does it change with mounting torque or position? Does it persist if I mount the unit on a non-conductive fixture? That last test separates electrical coupling from mechanical stress. I'd also probe the reference voltage and the input bias at the front-end in both states — if the reference shifts when the board is fastened down, I'm looking at mechanical stress on a component or a solder joint, or a ground return that changes impedance when the chassis connection is made.

If the offset correlates with the enclosure, I'd check the shield and chassis grounding: a floating or poorly bonded shield can shift the local reference. If it correlates with mounting position, I'd suspect cable dressing, proximity to a grounded surface, or a connector that seats differently under mechanical load. The fix depends on which of these it is — a grounding change, a mechanical relief, a layout revision, or a calibration that accounts for the installed configuration — but the investigation has to identify the mechanism before choosing among them, because a calibration patch that masks a grounding problem will fail again in a different installation.

**Possible follow-ups:** How would you distinguish a mechanical stress effect from an electrical coupling effect? What would you do if the offset varied between installation sites rather than being consistent?

## Q5: You're leading a cross-functional failure investigation where the firmware and hardware teams each believe the other side owns an intermittent communication failure, and neither has conclusive evidence. How would you structure the investigation to break the deadlock?

**Answer:** Deadlocks like this usually come from each team having run tests that confirm their own side is fine, without a shared experiment that can discriminate between the two hypotheses. My first job is to reframe the question from "whose fault is it" to "what observation would distinguish these two explanations," and then design that observation as a joint experiment both teams agree to in advance.

Concretely, I'd get both teams in a room and have each state their hypothesis as a falsifiable prediction: if it's a hardware timing margin issue, what should we see on the bus when it fails? If it's a firmware race, what internal state should be captured at the moment of failure? Then I'd instrument for both simultaneously — bus analyzer or scope capture synchronized with firmware event logging and timestamps — so a single failure event produces evidence that speaks to both hypotheses at once. The key is that the experiment is designed before the failure occurs, not interpreted after, which removes the temptation to fit the data to a preferred theory.

I'd also set ground rules: no fix is implemented until the discriminating evidence is in, and both teams review the same data together rather than in separate rooms. If the evidence is genuinely ambiguous after the joint experiment, I'd escalate to fault injection — deliberately push the timing margin or deliberately perturb the firmware state — to see which perturbation reproduces the failure. That converts an argument into a controlled test. Throughout, I'd keep the tone collaborative: the goal is a shared model of the failure, not a verdict on a team, because the same people have to implement and verify the fix afterward.

**Possible follow-ups:** What would you do if the joint experiment still produced ambiguous evidence? How do you keep a cross-functional investigation from becoming adversarial when the schedule is tight?
