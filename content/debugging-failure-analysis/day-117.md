# debugging-failure-analysis — Day 117

## Q1: How would you approach a failure investigation where a device's firmware occasionally enters a hard fault handler, and the stack trace consistently points to a memory copy operation — but the source and destination addresses are always valid, and the memory regions being copied are within their allocated bounds?

**Answer:** A hard fault that lands in a memcpy with valid-looking pointers is almost never a memcpy bug — it's usually a symptom of something upstream corrupting state the copy operation depends on. My first move is to stop treating the fault location as the root cause and start treating it as the last place the damage became visible. I'd capture the full fault context: the fault status registers (bus fault, usage fault, memory management fault flags), the stacked PC/LR, and the actual register values at the time of the fault — not just the symbolic stack trace. The distinction matters: a bus fault on a load/store inside memcpy suggests the destination or source region isn't actually mapped or is write-protected at the moment of access, even though the pointer value looks in-bounds. A usage fault or an unaligned access fault points somewhere different. Next I'd check whether the copy length is what the code thinks it is — a corrupted length field can walk the copy off the end of a valid buffer into unmapped memory while both base pointers remain valid. That's the classic case where "the addresses are valid" is true and misleading at the same time. I'd also look at stack depth and interrupt nesting: if the fault only occurs under a particular interrupt load, the copy may be running on a stack that has overflowed into another region, so the "valid" destination is actually the corrupted stack of another context. Instrumentation strategy: enable the MPU or a memory-protection region around the buffers if the MCU supports it, so the fault fires at the first out-of-bounds access rather than later; add a canary pattern around the buffers and check it after each copy; and log the copy length and both pointers to a RAM buffer that survives reset so I can see the values at fault time rather than reconstructing them. If the fault is intermittent and hard to catch live, I'd run the same workload under a debugger with a data watchpoint on the buffer boundaries, or use a hardware trace unit if available. The key discipline is one variable at a time: first prove whether the copy itself is out of bounds (length or pointer corruption), then prove whether the buffers are being corrupted by another writer, then prove whether the stack or heap is the actual victim. Only after I can reproduce the fault deterministically would I consider a fix — and the fix is usually at the corruption source, not at the memcpy.

**Possible follow-ups:** If the fault only reproduces under a specific interrupt load, how would you determine whether the copy is running on a corrupted stack versus reading a corrupted length? And how would you decide whether to add MPU protection permanently versus only during investigation?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** This is a load-transient and loop-stability problem, not a steady-state regulation problem, so I'd start by separating the two. First I'd characterize the transient itself: what's the load step amplitude and slew rate when the subsystem switches, and what does the rail do in response — how far does it deviate, how fast does it recover, and is there ringing? I'd measure at the decoupling capacitors closest to the load, not at the regulator output, because the ripple the load actually sees is set by the impedance between the regulator and the load at the switching frequency and its harmonics. Probe technique matters here: a long ground lead on the scope probe will pick up loop inductance and show ripple that isn't really on the rail, so I'd use a short ground spring or a differential probe, and I'd confirm the measurement with the probe tip and ground both at the same capacitor. Next I'd look at the frequency content of the ripple. If it's at the subsystem's switching frequency, the question is whether the bulk and decoupling network has a resonance there — I'd estimate the impedance of the cap network at that frequency and check whether the regulator's control loop has adequate phase margin at the load-step frequency. If the ripple is at the regulator's own switching frequency but only appears under load, that points to the regulator running out of loop gain or hitting a current-limit or minimum-off-time condition during the transient. I'd also check the load's return path: a high-di/dt subsystem with a poorly placed return can inject ground bounce that shows up as apparent rail ripple. Practical steps: add local bulk capacitance at the load to slow the transient the regulator sees, verify the regulator's compensation network against the actual output capacitance (including derating and DC bias effects, which can cut effective capacitance substantially), and check whether the transient response improves with a deliberate load step applied from an electronic load at the same point. If the ripple persists with a clean resistive load step, it's the regulator or the distribution network; if it only appears with the real subsystem, it's the load's current profile or return path. I'd change one thing at a time — capacitance, then compensation, then layout/return — and re-measure at the same probe point each time.

**Possible follow-ups:** How would you distinguish a loop-stability problem from a decoupling-network resonance using only scope measurements? And if adding bulk capacitance fixes the symptom but the root cause is the load's di/dt, how would you decide whether to fix the load or the supply?

## Q3: A medical device passes all functional and safety tests at design verification, but during a 30-unit pilot production run, three units fail a 72-hour burn-in test with the same symptom: the device stops communicating after roughly 48 hours and requires a power cycle to recover. How would you approach this?

**Answer:** The pattern — passes DV, fails only in a longer burn-in, same symptom, requires power cycle — tells me this is a time-dependent or cumulative-stress failure, not a functional design error. The first thing I'd do is resist the temptation to treat the three failures as one problem until I've confirmed they share a mechanism. I'd pull the failed units and the passing units from the same run and compare: same component lots, same assembly line, same firmware build, same test fixture? If the three failures cluster on a lot or a fixture, that's a strong lead. Then I'd characterize the failure mode precisely: is the device truly dead, or is the communication peripheral hung while the rest of the system runs? Does the power cycle reset a specific IC, or does it reset the whole board? That distinction separates a firmware state-machine hang from a hardware latch-up or a brownout event. Next, I'd instrument a fresh pilot unit to run the same 72-hour profile with logging that survives the failure: rail voltages, reset cause register, watchdog status, communication error counters, and temperature. If the device stops communicating but the MCU is still running, the log will show whether the comms peripheral stopped, whether the bus is stuck, or whether the peer device stopped responding. I'd also look at the burn-in environment itself — temperature, humidity, supply quality — because a 48-hour failure is suspiciously close to a thermal soak or a cumulative drift. If the failure correlates with temperature, I'd run a thermal chamber sweep to find the band. If it correlates with time at temperature, I'd suspect a component parameter drift, a solder joint, or a firmware counter/timer overflow. The corrective-action path depends on which: a firmware hang gets a watchdog and a recovery routine plus a root-cause fix; a hardware drift gets a component or derating change; a lot issue gets a supplier and incoming-inspection action. Throughout, I'd keep the three failed units quarantined and documented so the investigation is traceable, and I'd expand the burn-in sample before concluding anything — three out of thirty is a real signal but a small denominator.

**Possible follow-ups:** How would you decide whether to ship with a watchdog-based recovery as an interim measure while the root cause is still open? And what would you do if the failure doesn't reproduce on the instrumented unit?

## Q4: You're leading a cross-functional failure investigation where the firmware and hardware teams each believe the other side owns an intermittent communication failure, and neither has conclusive evidence. How would you structure the investigation to break the deadlock?

**Answer:** The deadlock usually isn't a technical disagreement — it's that each team is testing its own layer in isolation and neither has a shared, falsifiable model of the failure. My first move is to reframe the question from "whose fault is it" to "what single experiment would distinguish the two hypotheses," and then get both teams to agree on that experiment before anyone runs it. Concretely, I'd build a shared failure model: what are the candidate mechanisms (marginal timing, bus contention, a race condition, a physical-layer issue), and for each, what observable would be different if that mechanism were true? Then I'd design a test that captures the observable at the boundary between the two domains — for example, a logic analyzer or scope capture on the bus lines synchronized with firmware timestamps, so the same event is seen from both sides. That single capture usually settles whether the bus is being driven correctly at the electrical level and whether the firmware is responding in time. I'd also insist on a common reproduction: if the failure is intermittent, we need a stress profile that makes it occur at a useful rate, and both teams should run the same profile. I'd assign ownership of the investigation, not of the blame — one engineer accountable for the shared test plan, with both teams contributing instrumentation. I'd set a decision rule up front: if the capture shows the bus is clean and the firmware misses the window, it's firmware; if the bus shows violations, it's hardware; if it's ambiguous, we escalate to a joint design review with the data. And I'd keep a written log of hypotheses tested and ruled out, so the team can see progress even when the answer isn't in yet. The behavioral piece is important: I'd explicitly separate "the design has a weakness" from "a person made a mistake," because the moment it becomes personal, people stop sharing data. The goal is to make the evidence do the arguing.

**Possible follow-ups:** What would you do if the shared experiment is inconclusive and the schedule forces a decision? And how would you keep both teams engaged if the evidence ultimately points to one side?

## Q5: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** The fact that it's consistent and only appears in the assembled, installed state tells me the offset is being introduced by something the bench harness doesn't reproduce — mechanical stress, a changed ground or shield path, a thermal gradient, or a different cable/connector configuration. I'd start by making the transition from bench to assembly incremental rather than jumping straight to the installed unit. First, assemble the enclosure but leave it on the bench: does the offset appear? If yes, it's mechanical or shielding-related, not installation-related. If no, add the final mounting and cabling one step at a time. That divide-and-conquer narrows the variable fast. If the offset appears at enclosure assembly, I'd suspect mechanical stress on the sensor or on the PCB — a flexed board can shift a bridge sensor's output or change a resistor's value slightly, and a changed shield or ground path can shift the front-end's reference. I'd measure the front-end's reference and ground at the ADC with the enclosure on, and compare to the bench case; a shifted ground reference shows up as a common-mode offset. If it appears only at final installation, I'd look at the mounting position: is the unit near a magnetic or conductive surface, is the cable routed differently, is there a ground loop through the mounting hardware? For a bridge-type sensor front-end, a small offset that's stable and repeatable is often a bridge imbalance or an excitation/reference mismatch, so I'd check whether the offset tracks the excitation supply and whether it changes when I swap the sensor with a known-good one in the same assembly. I'd also verify the offset is truly in the analog domain and not a firmware calibration that was performed on the bench and not re-run after assembly — a stored offset calibrated in one mechanical state can be wrong in another. The measurement discipline is to keep the same probe points and the same reference throughout, and to change one assembly variable at a time. The fix depends on the mechanism: mechanical relief or a stiffer mount, a shield/ground change, a re-calibration step in the production flow, or a front-end topology change if the offset is inherent to the installed configuration.

**Possible follow-ups:** How would you determine whether the offset is mechanical stress on the sensor versus a ground-reference shift in the front-end? And if the offset is small but within the sensor's datasheet accuracy, how would you decide whether it's a defect or an acceptable variation that the system algorithm should tolerate?
