# debugging-failure-analysis — Day 116

## Q1: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** The key insight is that the offset appears only when two variables change together — mechanical assembly and final mounting — so the first job is to separate them. I'd build a test matrix that varies one factor at a time: open bench with harness, board in enclosure but not mounted, board in enclosure and mounted in the final position, and ideally the enclosure alone (no board) placed in the mounting position to see if the environment itself is the variable. That isolates whether the cause is mechanical stress on the board, a grounding/shielding change introduced by the enclosure, or an environmental factor at the install location.

From there I'd instrument the analog front-end directly rather than trusting the reported value — probe the ADC input, the reference, and the analog ground at the point of measurement, and compare against the bench baseline. A consistent offset that appears with assembly often points to mechanical stress on a precision component (a flexed board changing a resistor or reference behavior), a changed ground return path through the enclosure or mounting hardware, or a thermal shift from reduced airflow once enclosed. I'd also check whether the offset tracks the mounting position specifically — for example, a chassis that becomes part of the ground path, or a cable routing change that couples noise differently. The goal is to reproduce the offset reliably in a controlled configuration, then remove one contributor at a time until the offset disappears.

**Possible follow-ups:** How would you distinguish a mechanical-stress-induced offset from a thermal one if both are plausible? What would you do if the offset only appears at the customer's site and not in your own mounting fixture?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** This is a load-transient and power-distribution problem, so I'd start by characterizing the ripple properly rather than just observing it. I'd measure at the point of load — right at the decoupling capacitors of the affected IC — not at the regulator output, because the ripple that matters is what the load actually sees. I'd use a short-ground-spring probe or a coaxial connection to avoid picking up radiated noise on the probe itself, and I'd trigger the scope on the switching event so I can see the transient response synchronized to the load step.

Then I'd separate the two mechanisms that produce this symptom: the regulator's transient response (loop bandwidth, output capacitance, ESR) versus the impedance of the power distribution network between the regulator and the load (trace inductance, via count, plane integrity, decoupling placement). A useful test is to add bulk capacitance right at the load and see if the ripple collapses — if it does, the PDN impedance is the issue; if it doesn't, the regulator's transient response is the issue. I'd also check whether the ripple is differential (real rail collapse) or common-mode (measurement artifact from ground bounce), by probing ground-to-ground with the same setup. Finally, I'd look at the switching subsystem itself — inrush, di/dt, and whether its return current is sharing a path with the sensitive rail.

**Possible follow-ups:** How would you quantify the PDN impedance to confirm the diagnosis? What layout changes would you prioritize if the problem is trace inductance between regulator and load?

## Q3: A device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline. How would you approach this investigation?

**Answer:** The hardest part here is that the failure is silent — no fault flag, no out-of-range value — so the investigation has to start with making the failure observable. I'd first add instrumentation that captures the raw data path: log the ADC raw counts alongside the processed value, timestamp each sample, and record the sensor's status/configuration registers at the time of the read. If the wrong value is plausible, the corruption is likely happening somewhere between the physical measurement and the stored/transmitted value, so I want visibility at each stage.

Then I'd look for patterns in the offline data — does the error correlate with a particular operating mode, temperature, time since power-on, or a specific sequence of events? A plausible-but-wrong value often comes from a stale sample (reading the previous conversion because the data-ready flag was missed), a race between the read and an update, a scaling/calibration path applied inconsistently, or a single-bit corruption in the data path. I'd try to reproduce it under accelerated conditions — rapid mode changes, temperature cycling, high bus traffic — and use fault injection (deliberately delaying reads, forcing bus contention) to see if I can trigger the same signature. The corrective action depends on which stage the corruption enters, so I'd resist fixing anything until I can show the value going wrong at a specific point in the chain.

**Possible follow-ups:** How would you design the logging so it doesn't itself perturb the timing you're trying to observe? If the corruption turns out to be a single-bit flip, what would that point you toward?

## Q4: You're leading a cross-functional investigation where the firmware and hardware teams each believe the other side owns an intermittent communication failure, and neither has conclusive evidence. How would you structure the investigation to break the deadlock?

**Answer:** The deadlock usually comes from each team testing in isolation and finding their own domain "clean," so the first move is to replace opinion with a shared, observable experiment. I'd define the failure precisely — what counts as a failure, how it's detected, and what evidence would distinguish a hardware cause from a firmware cause — and get both teams to agree on that definition before anyone runs another test. Then I'd design a test that captures both domains simultaneously: a logic analyzer or scope on the bus lines, synchronized with firmware instrumentation that timestamps when the firmware initiates a transaction and when it observes completion. That single synchronized capture usually shows whether the physical signal was present and correct while the firmware failed to act on it, or whether the signal itself was marginal.

I'd also set up a "swap" experiment to isolate the variable: run the same firmware on known-good hardware and the suspect hardware on a known-good firmware build, ideally across multiple units. That breaks the symmetry of "it works on my bench." Throughout, I'd keep the tone collaborative rather than adjudicating blame — frame it as "we don't yet have the measurement that tells us which side to look at, so let's get that measurement." If the evidence still splits, I'd bring in a neutral third party to review the capture and the test design, and I'd document the decision criteria up front so the conclusion is defensible regardless of which team it points toward.

**Possible follow-ups:** What would you do if the synchronized capture shows the failure is genuinely at the boundary — for example, a marginal timing that's legal for both sides individually? How do you keep the losing team engaged once the root cause is assigned?

## Q5: How would you approach a failure investigation where a device's power rail collapses only during a specific operating mode, but the regulator and its passives all measure within specification when the board is powered in isolation?

**Answer:** The fact that everything measures fine in isolation tells me the failure is an interaction, not a component defect — so I need to reproduce the operating mode and capture the rail behavior in situ rather than testing the regulator on its own. I'd start by characterizing the load during that specific mode: what current profile does the mode demand, what's the di/dt, and is there an inrush or a transient that the regulator wasn't designed for? A rail that collapses only in one mode usually means the load transient exceeds the regulator's transient response or the PDN's ability to supply it, even though steady-state measurements look fine.

I'd instrument the rail at the load with a scope triggered on the mode entry, capturing the collapse and the recovery, and simultaneously measure the regulator's input rail, the enable/feedback pins, and the load current. That distinguishes a few mechanisms: the regulator hitting current limit or thermal foldback, a droop from insufficient output capacitance for the transient, a feedback node disturbed by noise coupled from the mode's switching activity, or a sequencing/enable glitch that momentarily disables the regulator. I'd also check whether the collapse is a true rail collapse or a measurement artifact from ground bounce during the high-current event. Once I can see the collapse synchronized to the mode transition, I can test hypotheses one at a time — add local bulk capacitance, adjust soft-start, check the enable pin — and confirm which one removes it.

**Possible follow-ups:** How would you tell the difference between the regulator entering current limit and a PDN droop, from the scope capture alone? If adding capacitance fixes it on the bench, what would you still want to verify before calling it the corrective action?
