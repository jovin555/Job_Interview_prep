# debugging-failure-analysis — Day 79

## Q1: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** This is a classic case where the difference between bench and installed conditions is the variable, so the first step is to enumerate what actually changes between those two states rather than re-testing the same setup harder. The bench harness typically provides short, well-routed connections, a stable ground reference, and no mechanical stress; the assembled unit introduces a different ground return path, possible mechanical strain on the sensor or its connector, a changed thermal environment, and often a different cable or mounting geometry. I'd start by reproducing the offset with the unit assembled but still accessible — enclosure closed, unit in its mounting position, but with test points broken out so I can measure at the same nodes I measured on the bench. If the offset appears, I bisect: open the enclosure but keep the unit in its mounting position; then close the enclosure but keep it on the bench; then mount it without the enclosure. That isolates whether the cause is mechanical (mounting stress, connector seating), electrical (ground loop, shield termination, cable routing), or thermal (self-heating in the closed enclosure). For a bridge-type sensor front-end, a consistent offset that appears only when assembled often points to a ground reference shift — the instrumentation amplifier's reference pin or the ADC's ground is now sitting at a slightly different potential because the return current path changed. I'd measure the actual differential voltage at the amplifier inputs and the reference pin relative to the ADC ground, not just the final reading, so I can tell whether the offset is introduced before or after the amplifier. If it's mechanical, I'd look at whether the sensor is being preloaded or twisted by the mounting, which can shift a bridge output. The key discipline is to change one variable at a time and confirm the offset tracks that variable, rather than assuming it's "noise" or "just the enclosure."

**Possible follow-ups:**
- If the offset only appears after the unit has been powered for a while in the enclosure, how would you separate a thermal effect from a mechanical one?
- How would you decide whether the fix belongs in the hardware design, the assembly process, or the calibration routine?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** The fact that ripple appears only under a specific load condition tells me this is a load-transient or impedance problem, not a steady-state regulator problem, so I'd resist the temptation to swap the regulator. First I'd characterize the ripple properly: where am I measuring it? Probing at the load with a long ground lead will pick up loop inductance and give a misleading picture, so I'd use a short ground spring or a proper tip-and-barrel probe right at the decoupling capacitors, and I'd measure both at the regulator output and at the load to see how much the rail degrades between them. Then I'd look at the transient itself — its amplitude, duration, and repetition rate — and correlate it with the switching event. A few hundred millivolts lasting tens of microseconds at a regular interval is consistent with a load step that the regulator's control loop can't fully absorb before the bulk capacitance discharges. I'd check the bulk and decoupling capacitance against the actual transient current: if the subsystem draws a large step current, the local capacitors have to supply it until the regulator responds, and if they're undersized or too far away, the rail dips. I'd also check the loop stability — a regulator that's marginally stable can ring or overshoot under a fast load step even if it looks fine at steady state. Beyond the regulator, I'd look at the return path: a high di/dt load sharing a ground return with sensitive circuitry can couple noise through the ground, which looks like rail ripple at the measurement point. I'd separate the load's return path and see if the ripple changes. The approach is to measure at the right place, quantify the transient, then work backward from the load to the source, changing one thing at a time — capacitance, layout, return path, compensation — and confirming the ripple responds.

**Possible follow-ups:**
- How would you distinguish a regulator loop-stability problem from a bulk-capacitance problem using only scope measurements?
- If adding capacitance reduces the ripple but doesn't eliminate it, what would that tell you about the root cause?

## Q3: A device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline. How would you approach this investigation?

**Answer:** This is one of the harder classes of bug because there's no fault flag to anchor on, and the value passes every sanity check the system has. The first thing I'd do is make the failure observable: if the system doesn't already log raw sensor data alongside the processed value, I'd add temporary instrumentation to capture the raw reading, the timestamp, the conversion result, and the state of the bus at the moment of the read. Without that, I'm guessing. Then I'd try to reproduce it under controlled conditions — run the device through the same operating sequence, temperature, and timing that preceded the bad readings, and see whether the error correlates with anything: a particular sensor, a particular time since power-up, a particular concurrent activity, a particular temperature. A plausible-but-wrong value often comes from a read that completed but returned stale or partially updated data — for example, a multi-byte register read where the sensor updated between the two bytes, or a conversion that was read before it finished. That's a timing or synchronization issue, not a sensor failure, which is why the self-test passes. I'd look at the read sequence: is there a handshake or a "data ready" signal, or is the firmware polling on a fixed schedule? If it's polling, a marginal timing relationship between the conversion and the read can produce exactly this symptom. I'd also check for buffer or indexing errors — a value written to the wrong slot, an off-by-one in a ring buffer, a unit conversion applied twice. The discipline is to capture the raw data, reproduce under controlled conditions, and correlate the error with a specific event rather than assuming the sensor is at fault.

**Possible follow-ups:**
- If the error only appears in the field and never on the bench, how would you instrument the device to capture enough context without changing its behavior?
- How would you decide whether this is a firmware bug, a sensor timing issue, or a hardware marginality?

## Q4: You're leading a failure investigation and you've reached a point where two plausible root causes remain, both supported by partial evidence, and the team is split on which to pursue. How would you handle this and drive the investigation to a conclusion?

**Answer:** When two hypotheses both have partial support, the worst thing to do is let the team split into camps and argue — that burns time and turns a technical question into a personal one. I'd reframe the situation: instead of asking "which one is right," I'd ask "what test would distinguish between them?" If both hypotheses predict the same observable behavior, then neither is testable yet and we need a better experiment, not more debate. So I'd work with the team to define, for each hypothesis, a specific prediction that the other hypothesis does not make — a condition under which one would fail and the other wouldn't. Then we design the cheapest, fastest test that separates them. Often that means reproducing the failure with one variable forced: if hypothesis A is a timing issue, we can stress the timing and see if the failure rate changes; if hypothesis B is a marginal component, we can swap or screen that component and see if the failure follows. I'd also look at whether the two hypotheses are actually mutually exclusive — sometimes the real answer is that both contribute, and the investigation should be about the interaction rather than picking a winner. Throughout, I'd keep the team focused on evidence rather than seniority or intuition, and I'd be explicit that a hypothesis being wrong is a useful result, not a failure. If the schedule is tight, I'd time-box the discriminating test and agree in advance what result would let us commit to a fix, so the decision doesn't drag. The goal is to convert an open disagreement into a closed experiment.

**Possible follow-ups:**
- What would you do if the discriminating test is inconclusive and the schedule won't allow another round?
- How would you keep a senior engineer who's attached to one hypothesis engaged rather than defensive?

## Q5: A junior engineer has been debugging an intermittent failure for several days without progress — they've been testing components in isolation and everything passes, but the system-level failure persists. They're frustrated and the schedule is tight. How would you approach this?

**Answer:** The pattern here — components pass in isolation, the system fails — is a strong signal that the bug lives in the interaction between components, not in any one component, so the junior engineer's approach isn't wrong so much as aimed at the wrong level. I'd start by acknowledging that the isolation testing was worth doing and has actually narrowed things down: it's ruled out a lot of possibilities, which is progress even if it doesn't feel like it. Then I'd help them shift from component-level testing to system-level observation. The key question is: what is different about the system context that the isolated test doesn't reproduce? Power sequencing, shared ground returns, concurrent activity, timing relationships, thermal environment, cable and connector behavior. I'd sit with them and look at what the failure actually looks like when it happens — is there a log, a scope capture, a reproducible trigger — and if not, the first task is to make the failure observable and reproducible, because debugging an intermittent you can't see is mostly guesswork. I'd encourage a divide-and-conquer approach at the system level: can we make the failure more frequent by stressing a particular condition, and does that point at a subsystem? I'd also model the behavior I want — asking questions rather than handing over the answer, so they build the skill — while being willing to get hands-on if the schedule genuinely demands it. And I'd check in on the frustration directly: several days on an intermittent is demoralizing, and naming that, plus giving them a concrete next step, usually does more for momentum than any technical hint.

**Possible follow-ups:**
- How would you decide when to step in and solve it yourself versus letting the engineer work through it?
- What would you do if the failure turns out to be in a subsystem the junior engineer has never worked with before?
