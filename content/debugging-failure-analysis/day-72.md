# debugging-failure-analysis — Day 72

## Q1: How would you approach debugging a device whose failure only reproduces when it is tested on the production test fixture, but never on the bench with a lab supply and jumper wires?

**Answer:** The fixture and the bench differ in ways that are easy to overlook, so the first step is to enumerate those differences rather than assume the fixture is "just a power supply and a few probes." Typical differences: the fixture may power the board through a different connector or cable length, may share a single supply across multiple boards or test points, may have long unshielded probe leads, may sequence power differently (e.g., all rails up simultaneously vs. a controlled ramp), may load the outputs differently, or may run the board in a test mode the bench setup never enters. I'd start by instrumenting the fixture itself — scope the rails at the board's decoupling caps, not at the fixture's supply terminals, and compare rise times, overshoot, and ripple against the bench. Then I'd bisect: move the board from the fixture to the bench while keeping one fixture element at a time (same cable, same connector, same supply, same probe arrangement) until the failure follows a specific element. If the failure tracks the fixture's grounding or cable, that points to a ground-return or common-impedance issue; if it tracks power sequencing, that points to a reset or brownout interaction. The key discipline is changing one variable at a time and reproducing consistently before drawing conclusions — a failure that only appears on the fixture is still a real failure mode, and it often predicts a field issue that the bench simply can't excite.

**Possible follow-ups:**
- If the failure disappears when you add a ferrite bead to the fixture cable, how do you decide whether that's a legitimate fix or just masking a board-level design weakness?
- How would you modify the bench setup so it can reproduce fixture-like conditions for future regression testing?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** This is a load-transient and impedance problem, not a steady-state regulation problem, so I'd measure it as such. First, I'd characterize the transient itself: what is the load step amplitude and slew rate, and how does the rail respond? I'd probe at the load's decoupling capacitors with a short ground lead (or a proper tip-and-barrel probe) rather than at the regulator output, because the ripple the load actually sees is set by the impedance between the regulator and the load, not by the regulator alone. Then I'd separate the contributors: is the dip dominated by the regulator's loop response (recovery time too slow), by bulk capacitance (insufficient charge reservoir for the step), by high-frequency decoupling (ESL/ESR of the caps), or by PCB impedance (trace inductance, via inductance, plane splits)? A useful test is to add temporary bulk and high-frequency capacitance right at the load and see which one moves the needle — if bulk helps, it's a charge-storage problem; if a small ceramic helps, it's a high-frequency impedance problem. I'd also check whether the switching subsystem shares a ground return path with the sensitive rail, since common-impedance coupling through ground can look like rail ripple. Finally, I'd verify the regulator's compensation and current-limit behavior are appropriate for the transient, and confirm the measurement isn't an artifact of probe placement or loop area.

**Possible follow-ups:**
- How would you distinguish a genuine rail droop from a measurement artifact caused by your probe's ground loop?
- If adding capacitance fixes the symptom but the root cause is a layout issue, how would you decide whether to respin or to accept the fix?

## Q3: A device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline. How would you approach this investigation?

**Answer:** The hardest part of this class of bug is that nothing in the system flags it, so the investigation has to start by making the invisible visible. I'd first build a way to detect the error in real time: compare the sensor reading against an independent reference (a second sensor, a redundant channel, or a plausibility model based on correlated parameters), and log both the raw value and the context — timestamp, operating mode, temperature, supply voltage, recent commands — whenever they diverge. Without that, you're chasing a ghost. Then I'd look for patterns in the divergence: does it correlate with a specific operating mode, a temperature, a recent write to a shared buffer, a DMA transfer, or a particular sensor command sequence? A plausible-but-wrong value often comes from a stale sample (the firmware read the register before the conversion completed), a byte-order or scaling error in one code path, a race between an ISR updating the value and the main loop reading it, or a shared buffer being overwritten by another task. I'd check the read sequence against the sensor's timing requirements, verify the data path from ADC register to application variable with a known input, and use a logic analyzer or trace to confirm the actual bus traffic matches what the firmware believes it read. The goal is to find the specific condition under which the value is wrong, then reproduce it deterministically.

**Possible follow-ups:**
- How would you design the plausibility check so it doesn't itself generate false positives that erode trust in the system?
- If the error only appears after long runtimes, how would you instrument the system without perturbing the timing that may be causing it?

## Q4: You're leading a failure investigation and you've reached a point where two plausible root causes remain, both supported by partial evidence, and the team is split on which to pursue. How would you handle this and drive the investigation to a conclusion?

**Answer:** When two hypotheses both have partial support, the temptation is to argue about which is more likely — but that's not a productive use of the team's time. I'd reframe the question as: what is the cheapest, fastest test that would clearly distinguish between them? That usually means designing a discriminating experiment rather than gathering more of the same evidence. I'd write down, for each hypothesis, what prediction it makes that the other does not — if both predict the same observation, that observation can't discriminate and we should stop collecting it. Then I'd prioritize the test that is fastest to run and most decisive, even if it's less convenient. In parallel, I'd keep both hypotheses alive in the documentation rather than letting the team coalesce around one prematurely, because premature convergence is how you miss the real cause. If the discriminating test is expensive or slow, I'd look for a way to force the condition artificially — fault injection, a modified build, a bench setup that exaggerates the suspected mechanism — so we can get a signal quickly. Throughout, I'd keep the team aligned on the decision criteria: we will conclude when we have a test that one hypothesis passes and the other fails, and we can reproduce it.

**Possible follow-ups:**
- What if the discriminating test is inconclusive — both hypotheses partially survive? How do you avoid an endless investigation?
- How do you keep a split team motivated when the answer isn't obvious and the schedule is tight?

## Q5: A junior engineer has been debugging an intermittent failure for several days without progress — they've been testing components in isolation and everything passes, but the system-level failure persists. They're frustrated and the schedule is tight. How would you approach this?

**Answer:** The pattern here — components pass in isolation, system fails — usually means the bug lives in an interaction, not in a component, so the debugging strategy needs to shift from "verify each part" to "find the condition that makes the system fail." I'd start by sitting with the engineer and asking them to walk me through what they've tried and what they've observed, not to audit their work but to understand the shape of the problem. Often the missing piece is that they haven't found a reliable reproduction, so every test is a coin flip. I'd help them focus on reproducing the failure consistently first — even if that means running the system in a loop, adding logging, or stressing it in a specific way — because without reproduction, you can't tell whether a change fixed anything. Then I'd introduce a divide-and-conquer approach at the system level: bisect the system by disabling or stubbing subsystems, or by swapping known-good assemblies, until the failure follows a specific interaction. I'd also normalize the emotional side: intermittent bugs are genuinely hard, several days without progress is normal, and the frustration is a signal to change approach, not evidence of failure. I'd set a short, concrete next milestone — e.g., "by end of day, we have a reproduction we can trigger on demand" — so progress is visible again, and I'd check in regularly rather than taking over.

**Possible follow-ups:**
- How would you decide when to step in and debug it yourself versus continuing to coach?
- If the engineer is reluctant to ask for help, how would you address that without making them feel judged?
