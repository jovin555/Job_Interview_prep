# debugging-failure-analysis — Day 122

## Q1: How would you approach a failure investigation where a device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline?

**Answer:** The defining challenge here is that every automated check passes, so the fault is invisible to the system's own defenses. I'd start by treating this as a data-integrity problem rather than a sensor problem, and build a way to observe the value at multiple points in the chain: at the ADC output, immediately after the driver reads it, after any scaling/filtering, and at the point it's stored or transmitted. If I can capture the same event at each stage, I can localize where the plausible-but-wrong value first appears — that's the "divide and conquer" step, and it's what turns a vague symptom into a bounded search.

A key hypothesis to test early is whether the error is a single-bit flip or a small arithmetic corruption. A single-bit flip points toward memory integrity — a buffer overwrite, a DMA race, an uninitialized variable, or a stack/pointer issue — while a small consistent offset points toward a scaling, calibration, or timing problem (e.g., reading a register mid-update). I'd add lightweight instrumentation: a rolling log of raw and processed values with a checksum or redundancy check, and if the platform allows, a shadow copy compared against the primary to catch divergence. I'd also look hard at concurrency — is the value being written by an ISR while the main loop reads it? A torn read of a multi-byte value across an interrupt boundary is a classic source of plausible-but-wrong data.

Because the error is only caught offline, I'd also improve the offline review itself: add plausibility heuristics (rate-of-change limits, cross-channel consistency) so the system flags suspicious values in real time rather than weeks later. That both narrows the investigation and becomes a lasting detection improvement. Throughout, I'd keep the reproduction disciplined — one change at a time, and a fault-injection harness to confirm I can actually trigger the corruption on demand before claiming a root cause.

**Possible follow-ups:** How would you distinguish a torn multi-byte read from a genuine single-bit memory flip using only firmware-visible evidence? What would you change in the data path to make this class of error detectable at runtime rather than offline?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** The correlation with switching tells me this is a load-transient and power-distribution problem, not a steady-state regulator problem — so I'd resist the urge to swap the regulator and instead characterize the disturbance. First, I'd measure properly: ripple at the load's supply pins, not just at the regulator output, using a short-ground-tip probe and AC coupling so I'm not measuring probe loop inductance. The difference between ripple at the regulator and ripple at the load tells me how much is the regulator's transient response versus how much is the impedance of the intervening PCB trace, vias, and decoupling.

Then I'd look at the transient itself: what's the di/dt, how fast is the edge, and does the dip recover within the regulator's loop bandwidth? If the regulator responds well but the local rail still sags, the problem is the PDN impedance between the bulk cap and the load — too much inductance, decoupling placed too far, or a shared return path causing ground bounce. I'd check the return path specifically, because a high-current switching subsystem sharing a ground return with sensitive analog can inject noise that looks like ripple but is really common-impedance coupling.

I'd also verify the measurement isn't lying to me: is the "ripple" actually switching noise coupled into the probe, or real? A near-field probe sweep and a look at whether the ripple frequency matches the subsystem's switching frequency versus the regulator's helps separate the two. Only after I understand whether it's regulator transient response, PDN impedance, or return-path coupling would I propose a fix — more/better-placed decoupling, a bulk cap closer to the load, a layout change to the return path, or a regulator compensation tweak. Each fix targets a different root cause, so measuring first avoids shotgunning parts.

**Possible follow-ups:** How would you measure PDN impedance to confirm a decoupling problem before changing the layout? If the ripple is within the regulator's spec but still corrupts a downstream analog measurement, where do you draw the line between "fix the supply" and "fix the victim"?

## Q3: How would you approach a failure investigation where a device's analog front-end is accurate at room temperature but shows a growing offset error as the device warms up during continuous operation — and the offset returns to zero after the device cools down?

**Answer:** A reversible, temperature-correlated offset is a strong signal that I'm looking at a thermal coefficient mismatch or a thermal gradient across the signal chain, not a permanent degradation. The reversibility is important: it argues against a damaged component and toward something parametric — resistor TCR mismatch, an op-amp or reference with drift that isn't being compensated, a solder joint or connector whose resistance changes with temperature, or a thermocouple effect at a dissimilar-metal junction in the signal path.

I'd start by mapping the thermal profile: thermal camera or thermocouples to find where the heat is generated and how it spreads, and critically whether the offset tracks the temperature of a specific component or the gradient between two points. If the offset correlates with the difference in temperature between, say, the input connector and the ADC, that points to a thermoelectric or TCR-mismatch mechanism rather than absolute temperature. I'd then isolate: inject a known stable reference signal and watch the offset as the board heats, and if possible heat individual components with a localized source (hot air, freeze spray) to see which one moves the offset.

On the design side, I'd review the front-end for known thermal sensitivities — input bias current drift in the amplifier, reference voltage tempco, resistor divider TCR tracking (matched vs unmatched), and whether the layout puts a heat source asymmetrically near one leg of a differential pair. The fix is usually a combination of component selection (matched/low-TCR parts, lower-drift reference), layout (thermal symmetry, keep heat sources away from the front-end), and possibly a temperature-compensation term in firmware if the residual drift is predictable. I'd verify the fix by repeating the warm-up profile and confirming the offset stays within the error budget across the full operating temperature range, not just at the endpoints.

**Possible follow-ups:** How would you tell a TCR-mismatch offset apart from a thermoelectric (Seebeck) effect at a connector? If the drift is predictable, when is firmware compensation acceptable versus when must you fix it in hardware?

## Q4: How would you approach a failure investigation where a device's firmware occasionally enters a hard fault handler, and the stack trace consistently points to a memory copy operation — but the source and destination addresses are always valid, and the memory regions being copied are within their allocated bounds?

**Answer:** When the faulting instruction is a memory copy but the addresses and bounds all check out, the copy itself is probably the victim, not the cause — something upstream has corrupted state that only manifests when the copy touches it. I'd shift the investigation from "why did the copy fault" to "what made the memory or the CPU state invalid before the copy ran." The first things I'd examine are the fault status registers: the fault type (bus fault, memory management fault, usage fault) and the stacked PC/LR tell me whether it's an access violation, an alignment issue, an MPU violation, or an imprecise bus error. An imprecise bus fault is especially telling — it means the actual bad access happened earlier and the fault surfaced later, which would explain why the copy looks innocent.

Next I'd look for the classic upstream culprits: a buffer overrun from a different task corrupting the heap or stack, a DMA transfer writing past its buffer or racing with CPU access, a stack overflow in an ISR, or a use-after-free where the "valid" address is actually stale. I'd enable stack canaries and MPU regions around critical buffers to catch the corruption at the moment it happens rather than at the copy. If the platform supports it, I'd turn on a hardware watchpoint on the destination region to trap the first unexpected write. I'd also scrutinize concurrency: is the copy running while an ISR or DMA modifies the same region? A copy that's correct in isolation can fault if the source is being freed or remapped concurrently.

Finally, I'd try to make it reproducible under instrumentation — fault injection, stress the allocator, run longer — because an intermittent fault that only appears every few hours needs a way to accelerate occurrence before I can confirm a fix. The corrective action has to address the true corruptor, not add a guard around the copy.

**Possible follow-ups:** How would you use the fault status and stacked registers to distinguish a precise from an imprecise bus fault, and why does that distinction matter here? What's your approach to catching a heap corruption at the moment it happens rather than when it later crashes a copy?

## Q5: You're leading a failure investigation and you've reached a point where two plausible root causes remain, both supported by partial evidence, and the team is split on which to pursue. How would you handle this and drive the investigation to a conclusion?

**Answer:** When the team is split, the instinct is to debate harder, but that usually just entrenches positions. I'd reframe it as a decision problem: for each hypothesis, what evidence would confirm it, and what evidence would falsify it? Then I'd look for the discriminating test — the single experiment or measurement whose outcome differs depending on which hypothesis is true. That's the highest-value next step, because it collapses the ambiguity instead of accumulating more supporting evidence for both sides.

I'd make the hypotheses explicit and falsifiable, write them down where the whole team can see them, and assign each a confidence level and the specific test that would move it. If a discriminating test isn't feasible, I'd design one that's as close as possible — a controlled fault injection, a bench reproduction with one variable changed, or a targeted measurement — and be honest that we may need to run both branches in parallel if resources allow. Running two short, well-scoped experiments in parallel is often cheaper than a week of argument.

I'd also manage the human side deliberately: make clear that the goal is to find the truth, not to win, and that a hypothesis being wrong is a useful result, not a failure. I'd give each camp a fair hearing and make sure the quieter evidence gets weighed, since the loudest voice isn't always right. If the split persists after the discriminating test, I'd escalate to a decision on risk: which hypothesis, if wrong, causes the most harm, and can we mitigate both cheaply while we gather more data? Then I'd set a deadline for the decision and commit, documenting the reasoning so the choice is traceable. The investigation concludes when we have a confirmed root cause backed by a test that would have failed under the alternative — not when the debate runs out of energy.

**Possible follow-ups:** How would you design a discriminating test when neither hypothesis can be directly reproduced on the bench? If you must commit to one branch due to schedule pressure, how do you document and communicate the residual risk of the path not taken?
