# debugging-failure-analysis — Day 56

## Q1: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?
**Answer:** The key observation is that the offset appears only after two changes happen together — the enclosure is closed and the unit is mounted. That points away from the analog signal chain itself and toward something mechanical, thermal, or grounding-related that changes with assembly. I'd start by reproducing the offset with the board in the enclosure but not yet mounted, then with the enclosure open but the unit in its final position, to separate "enclosure effect" from "mounting effect." If the offset only appears when both are true, I'd look at mechanical stress on the PCB (board flex changing strain on a sense resistor or a bridge sensor's mounting), thermal gradients from nearby power components now trapped by the closed enclosure, and grounding — mounting screws or brackets can introduce a new ground path or a ground loop that shifts the reference. I'd measure the analog front-end's reference and ground at the ADC pins with a high-impedance probe in each configuration, and compare against the bench harness case. If the offset tracks temperature, I'd log it over time with the enclosure closed. If it tracks mechanical stress, I'd try loosening or isolating the mounting points. The fix usually comes down to either compensating in firmware after characterizing the shift, or changing the mechanical/thermal design so the front-end sees the same conditions in the enclosure as on the bench.

**Possible follow-ups:** How would you distinguish a thermal offset from a mechanical-stress offset if both are plausible? If the offset turns out to be inherent to the enclosure design, how would you decide between a hardware fix and a firmware calibration?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?
**Answer:** This is a classic load-transient and power-integrity problem, so I'd approach it in layers. First, I'd characterize the ripple properly — probe directly across the decoupling capacitors at the load, not at the regulator output, using a short ground lead or a proper probe tip to avoid picking up radiated noise. I'd capture the ripple's frequency content and correlate it with the subsystem's switching frequency and its harmonics. Then I'd separate two possibilities: is the regulator failing to respond fast enough to the load transient (a control-loop or output-capacitance issue), or is the ripple being coupled in from the switching subsystem through a shared impedance (a layout or grounding issue)? I'd check the regulator's load-transient response in isolation with an electronic load that mimics the subsystem's current profile, and compare that to what's seen on the board. If the regulator responds well in isolation but poorly on the board, the issue is likely the impedance between the regulator and the load — trace inductance, insufficient bulk capacitance, or a ground return that's shared with the switching subsystem. I'd also check whether the subsystem's return current is flowing through the analog ground, which would inject the ripple directly. Fixes range from adding or relocating bulk and high-frequency decoupling, tightening the ground return path, or adding local regulation at the load.

**Possible follow-ups:** How would you measure the regulator's loop stability without a dedicated network analyzer? What's the difference between ripple caused by the regulator's own switching and ripple coupled from another subsystem, and how would you tell them apart on a scope?

## Q3: A device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline. How would you approach this investigation?
**Answer:** The hardest part here is that nothing in the system flags the error, so the investigation has to start by making the failure observable. I'd first try to reproduce it in a controlled way — run the device under conditions that stress the sensor path (temperature, supply variation, timing load) and log raw sensor data alongside the processed value, so I can see whether the corruption happens at the sensor, in the communication link, or in the firmware's processing. If the raw data is correct but the reported value is wrong, the issue is in firmware — a race condition, a buffer being overwritten, a stale value being used, or a scaling/calibration step applied incorrectly. If the raw data is already wrong, the issue is in the sensor, its supply, or the communication link. I'd add a lightweight integrity check — a checksum or a plausibility cross-check against a second sensor or a redundant read — to catch the error in the field and give more data. I'd also look at whether the error correlates with specific events: a particular operating mode, a firmware task switch, a communication retry, or a power event. The goal is to turn an invisible, intermittent error into a reproducible one, then trace it to its source.

**Possible follow-ups:** How would you design a plausibility check that catches this kind of error without generating false positives? If the error only happens once every few thousand readings, how would you structure the test to get enough data to be confident in a root cause?

## Q4: You're leading a failure investigation and you've reached a point where two plausible root causes remain, both supported by partial evidence, and the team is split on which to pursue. How would you handle this and drive the investigation to a conclusion?
**Answer:** When two hypotheses both have partial support, the temptation is to pick the one that feels more likely and move on — but that's how you end up fixing the wrong thing. I'd first make sure both hypotheses are stated clearly and falsifiably, so we know what evidence would confirm or rule out each one. Then I'd design a test or experiment that distinguishes between them — ideally one where the two hypotheses predict different outcomes. If no single test can separate them, I'd run the cheapest, fastest discriminating test first, and use the result to either eliminate one hypothesis or narrow the remaining one. I'd also look for evidence that's already been collected but not fully analyzed — sometimes the answer is in the data already on hand. Throughout, I'd keep the team aligned by making the decision criteria explicit: we're not voting on which cause is more likely, we're running the test that tells us which one is real. If the schedule is tight, I'd time-box the discriminating test and agree in advance what result would let us proceed with a fix and what result would send us back to the drawing board.

**Possible follow-ups:** What would you do if the discriminating test is inconclusive? How would you handle a situation where the team's split is driven more by seniority or personality than by evidence?

## Q5: A junior engineer has been debugging an intermittent failure for several days without progress — they've been testing components in isolation and everything passes, but the system-level failure persists. They're frustrated and the schedule is tight. How would you approach this?
**Answer:** The first thing I'd do is acknowledge that the approach they've been taking — testing components in isolation — is a reasonable starting point, but it has a built-in limitation: it can't catch failures that only exist when the components are interacting. That's not a failure of effort, it's a mismatch between the method and the problem. I'd sit down with them and reframe the investigation around the system-level conditions that are present when the failure occurs but absent when it doesn't — power state, temperature, timing, load, adjacent activity, cable or accessory configuration. Then I'd help them design a test that reproduces the failure at the system level, even if it's not fully controlled yet, because a reproducible failure is worth more than a dozen passing component tests. I'd also suggest they instrument the system to capture what's happening at the moment of failure — logs, scope captures, state dumps — rather than continuing to test components that already pass. Throughout, I'd keep the tone collaborative rather than corrective, because the goal is to get them unstuck and build their debugging instincts, not to make them feel like they wasted three days. If the schedule pressure is real, I'd help them time-box the next step and check in frequently so they're not alone with it.

**Possible follow-ups:** How would you help them decide when to escalate versus when to keep digging? What would you do if they resist changing their approach because they're convinced the component-level testing will eventually find it?
