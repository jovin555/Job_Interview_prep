# debugging-failure-analysis — Day 115

## Q1: How would you approach a failure investigation where a device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline?

**Answer:** The defining characteristic here is that the error is silent — it passes every guardrail the system has, so the investigation has to start by making the invisible visible. First I'd establish whether the wrong value is wrong at the source or wrong after the fact. That means instrumenting the acquisition path at multiple points: capture the raw ADC conversion result, then the post-processing value, then the value as stored, then the value as transmitted. If the raw conversion is already wrong, the problem is upstream in the analog domain or the sampling timing. If the raw value is correct but the stored or transmitted value is wrong, the problem is in the digital pipeline — scaling, filtering, buffer handling, or a race between the acquisition and the consumer.

Because the error is intermittent and only caught offline, I'd build a targeted logger that records not just the value but the context around it: timestamp, channel, gain/range setting if it's configurable, the state of any multiplexer, and a checksum or duplicate read of the same sample. A very common cause of "plausible but wrong" is a stale or misaligned sample — the firmware reads a buffer that hasn't been refreshed, or reads channel N's result while the ADC has already moved on to channel N+1. Logging the sequence and the mux state at the moment of conversion usually exposes that.

I'd also look hard at the boundary conditions: does the error correlate with a particular operating mode, a particular sensor range, temperature, or a specific timing relationship with another task? Since it's plausible rather than out of range, I'd suspect a small systematic corruption — a single-bit flip, an off-by-one in a scaling table, a rounding path that only misbehaves at certain input codes, or a filter state that gets corrupted and then slowly recovers. Comparing the offline-caught bad values against the raw logs for the same timestamps is the key step: it tells you whether the value was wrong when captured or wrong when consumed.

Finally, I'd try to reproduce it deterministically. If I can inject the suspected condition — force the mux to switch mid-conversion, or delay the consumer task — and get the same wrong value, I've converted an intermittent field symptom into a repeatable bench test, which is what makes the eventual fix verifiable.

**Possible follow-ups:** If the raw ADC value is correct but the stored value is wrong, how would you narrow down where in the digital pipeline the corruption happens? How would you distinguish a genuine sensor fault from a firmware data-handling bug when both produce plausible values?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** The fact that the ripple appears only under switching load tells me this is a load-transient and loop-response problem, not a steady-state regulation problem — so I'd stop measuring the rail in isolation and start measuring it in the time and frequency domain where the disturbance actually lives.

First, I'd characterize the disturbance properly. I'd probe at the point of load, not at the regulator output, using a short ground lead or a proper coax/pigtail probe — a long ground clip will pick up radiated switching noise and give a misleading picture. I'd capture the ripple synchronized to the switching event with a scope triggered on the subsystem's enable or PWM signal, so I can see the phase relationship between the load step and the rail deviation. That tells me whether the dip is the regulator's transient response (loop bandwidth too slow, insufficient output capacitance, high ESR) or whether it's ground bounce and common-impedance coupling from the high-current return path.

Second, I'd separate the two mechanisms. If the ripple is measured between the rail and a local ground right at the load and it's still there, it's a real rail disturbance. If it only appears when I probe with a distant ground reference, it's likely ground bounce — the switching return current is sharing impedance with my reference. I'd check the return path layout: is the high-current subsystem's ground return kept separate and star-pointed, or does it run under sensitive analog circuitry?

Third, I'd look at the decoupling network. Under a fast load step, the bulk and local decoupling have to supply the transient before the regulator loop responds. If the local capacitance is inadequate or the ESR/ESL is too high, the rail will dip regardless of the regulator. I'd measure the load transient response directly — apply a known step and watch the recovery — and compare against the regulator's datasheet transient spec. If the observed dip exceeds what the loop should produce, the problem is the passive network or the layout's parasitic inductance, not the regulator IC.

Finally, I'd verify the fix at the worst case: maximum load step, maximum switching frequency, and over temperature, since capacitor ESR and regulator loop behavior both shift with temperature. A fix that only works at room temperature on the bench isn't a fix.

**Possible follow-ups:** How would you distinguish a regulator loop-stability problem from a decoupling problem when both produce a similar-looking dip? What role does the physical placement of the bulk capacitor play, and how would you verify it's actually effective?

## Q3: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** The bench-to-installed delta is the whole story here — the electronics haven't changed, so something about the mechanical, thermal, or electrical environment of the assembled and installed unit has. I'd treat the enclosure and mounting as part of the circuit and investigate what they introduce.

First, I'd reproduce the offset in a controlled way and quantify it: is it a fixed offset, does it scale with the input, and does it depend on the mounting orientation or the surface the unit sits on? A consistent offset that appears only when installed points toward a changed ground reference, a changed thermal environment, or a mechanical stress effect on a component.

The most common mechanism is a ground-reference shift. When the unit is assembled and mounted, the analog front-end's ground reference may now be tied to the chassis or to the mounting surface, and any current flowing through that shared path — from the digital section, the power supply, or an external connection — develops a small voltage that appears as an offset. I'd measure the potential difference between the analog ground and the chassis/mounting point with a sensitive probe, both on the bench harness and in the installed configuration, and see if the offset tracks that difference.

The second candidate is thermal. A fully assembled unit in its final mounting position may run warmer or have a different thermal gradient than an open board on a bench. A small, consistent offset that appears only when assembled could be a thermocouple effect at a connector or a component whose offset voltage drifts with temperature. I'd use a thermal camera or thermocouples to compare the temperature of the front-end components between the two configurations, and check whether the offset correlates with warm-up.

The third is mechanical stress: mounting can flex the PCB or stress a connector, changing a solder joint's resistance or a sensor's mechanical zero. I'd compare the offset with the unit mounted loosely versus torqued to spec, and inspect the mounting and connector areas.

The key discipline is to change one variable at a time — harness vs. assembled, then assembled vs. installed, then installed at different orientations — so I can attribute the offset to a specific environmental change rather than guessing.

**Possible follow-ups:** If the offset tracks the ground potential difference between analog ground and chassis, what would that tell you about the return-path design? How would you determine whether the offset originates in the sensor, the amplifier, or the ADC reference?

## Q4: A medical device passes all functional and safety tests at design verification, but during a 30-unit pilot production run, three units fail a 72-hour burn-in test with the same symptom: the device stops communicating after roughly 48 hours and requires a power cycle to recover. How would you approach this?

**Answer:** The pattern — passes design verification, fails only in a pilot build, fails at a consistent elapsed time, and recovers on power cycle — points to something that accumulates over time and is sensitive to unit-to-unit variation, not a design flaw that would fail every unit. I'd structure this as a classic 8D-style investigation, starting with containment and then moving to root cause.

First, containment: I'd quarantine the failing units and the batch, and check whether the three failures share anything — same assembly line, same component lot, same operator, same time of build. In a 30-unit pilot, three failures is a 10% rate, which is high enough that lot or process correlation is a strong lead. I'd pull the build records and compare the failing units against the passing ones.

Second, I'd characterize the failure precisely. "Stops communicating" is a symptom, not a cause. I'd instrument a failing unit to capture what's actually happening at the moment communication stops: is the processor hung, is it in a fault handler, is the communication peripheral in an error state, is the watchdog firing, is a power rail drooping? The fact that a power cycle recovers it suggests a latched state — a peripheral stuck in an error condition, a buffer that filled and never drained, a counter that overflowed, or a thermal/leakage effect that resets when power is removed.

Third, the ~48-hour consistency is a strong clue. That's long enough to suggest an accumulation mechanism: a memory leak or buffer overrun that eventually corrupts state, a thermal soak that reaches a steady-state temperature only after many hours, a counter or timestamp rollover, or a slow drift in an analog parameter (a reference voltage, an oscillator frequency) that eventually crosses a threshold. I'd run the failing units under continuous monitoring with logging of memory usage, temperature, supply voltages, and communication error counters, and look for the trend that precedes the failure.

Fourth, I'd try to accelerate the failure. If it's thermal, raising the ambient temperature should shorten the time-to-failure. If it's a counter rollover, I can force the counter near its limit. If it's a leak, I can stress the allocation path. Accelerated reproduction turns a 48-hour test into a bench experiment.

Finally, once I have a candidate root cause, I'd verify it by fault injection — deliberately induce the suspected condition on a known-good unit and confirm it produces the same symptom — and then confirm the corrective action on a fresh pilot build before closing the investigation.

**Possible follow-ups:** If the three failures don't correlate with any build record, how would you narrow down whether it's a component lot issue or a design margin issue? How would you decide whether to fix the root cause or add a recovery mechanism (like a watchdog-triggered reset) as an interim containment?

## Q5: You're leading a cross-functional failure investigation where the firmware and hardware teams each believe the other side owns an intermittent communication failure, and neither has conclusive evidence. How would you structure the investigation to break the deadlock?

**Answer:** The deadlock usually isn't a disagreement about facts — it's that each team is looking at the problem through its own lens and neither has data that spans the boundary. My job as lead is to reframe the question from "whose fault is it" to "what single experiment would tell us where the failure originates," and then get both teams to agree on that experiment before anyone runs it.

First, I'd get both teams to write down their hypotheses explicitly, with the specific evidence each would predict. If the firmware team believes it's a hardware timing issue, what would they expect to see on a scope? If the hardware team believes it's a firmware race, what would they expect in the logs? Writing these down often reveals that the two hypotheses make different, testable predictions — and that's the wedge.

Second, I'd design a boundary experiment that both teams accept as fair. The classic approach is to instrument the interface itself: capture the actual signals on the bus (with a logic analyzer or scope) synchronized with firmware-side timestamps, so we can see whether the failure occurs at the physical layer before the firmware ever sees it, or whether the physical layer is clean and the firmware mishandles a valid event. That single synchronized capture usually settles the question, because it shows the failure in both domains at once.

Third, I'd make sure the experiment is run on a unit that actually fails. Intermittent failures are notorious for disappearing under observation, so I'd want a unit with a known failure history, and I'd run the experiment long enough to capture the event rather than declaring "no fault found" after a short run.

Fourth, I'd manage the human side deliberately. The goal is not to prove one team wrong — it's to find the root cause, and the team that turns out to be wrong still contributed a valid hypothesis that got eliminated. I'd frame the investigation that way from the start, and I'd make sure both teams are in the room when the boundary data is reviewed, so the conclusion is shared rather than imposed.

Finally, if the boundary experiment is inconclusive, I'd escalate to a fault-injection approach: deliberately induce the suspected hardware condition and see if firmware fails to handle it, and vice versa. That converts a passive disagreement into an active test, and it usually produces a definitive answer.

**Possible follow-ups:** What would you do if the boundary experiment shows the failure occurs at the physical layer, but the firmware team argues the hardware should have been designed to tolerate it? How would you keep the investigation moving if one team disengages because they feel the process is biased against them?
