# debugging-failure-analysis — Day 114

## Q1: How would you approach a failure investigation where a device's firmware occasionally enters a hard fault handler, and the stack trace consistently points to a memory copy operation — but the source and destination addresses are always valid, and the memory regions being copied are within their allocated bounds?

**Answer:** When the faulting instruction is a memory copy and the addresses look valid, the first instinct is to trust the stack trace too literally. The fault may not be *caused* by the copy — it may be the first instruction that touches a resource that was already compromised. I'd treat this as a "fault site vs. root cause" separation problem.

My approach would be:

1. **Capture the full fault context, not just the PC.** On Cortex-M-class parts, that means the stacked registers (R0–R3, R12, LR, PC, xPSR), the fault status registers (CFSR/MMFSR/BFSR/UFSR), and the fault address register (MMFAR/BFAR) if the fault is a bus fault or memory management fault. The CFSR bits tell you *why* the access faulted — imprecise bus error, alignment, permission, etc. — which is often more diagnostic than the PC itself.

2. **Check whether the fault is precise or imprecise.** An imprecise bus fault means the write buffer or a peripheral returned an error asynchronously; the PC at fault time is not the instruction that caused it. That single distinction reframes the whole investigation.

3. **Look for the copy being a victim, not a culprit.** Common mechanisms: a buffer that was freed or reallocated by another context (ISR vs. main loop) between the pointer check and the copy; a DMA engine still writing into the destination region; a stack overflow that corrupted the destination pointer's *contents* even though the pointer value itself looks fine; or a peripheral that has been powered down or clock-gated, so the destination is a valid address but not a valid *target*.

4. **Instrument rather than guess.** Add a canary pattern around the destination buffer and check it before and after the copy. Enable the MPU to make the region read-only or no-access and see whether the fault moves. Add a lightweight trace (ITM/SWO or a ring buffer in RAM) that logs the pointer values and a timestamp at entry and exit of the copy.

5. **Reproduce under controlled stress.** If it only happens occasionally, I'd try to increase the fault rate deliberately — run the copy in a tight loop, add background DMA traffic, toggle the peripheral clocks — so I can observe the failure with a logic analyzer or debugger attached rather than waiting hours.

The key discipline is: don't "fix" the copy. Prove what state was wrong *before* the copy executed, then trace backward to who put it in that state.

**Possible follow-ups:**
- How would you distinguish a stack overflow from a heap corruption as the underlying cause, given only the fault registers and a memory dump?
- If the fault only reproduces with the debugger detached, what does that tell you, and how would you proceed?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** This is a classic load-transient and power-distribution problem, and the first job is to localize *where* the ripple originates and *how* it propagates, rather than assuming the regulator is at fault.

My approach:

1. **Measure at the right place, with the right probe.** Ripple measured at the bulk input capacitor looks very different from ripple at the load's decoupling capacitors. I'd probe at the IC's supply pins with a short-ground-spring tip (not a long ground lead — that turns the probe into an antenna and invents ripple that isn't there), and I'd measure differentially where possible. I'd also confirm the scope bandwidth limit and probe attenuation are set correctly so I'm not measuring my own instrumentation.

2. **Characterize the transient.** Is the ripple synchronous with the switching edges of the high-current subsystem, or is it a lower-frequency envelope? Synchronous-with-edges points to di/dt through parasitic inductance; a slower envelope points to control-loop response or bulk-capacitor ESR. I'd capture the load current with a current probe simultaneously with the rail voltage so I can correlate cause and effect.

3. **Separate the three contributors:** (a) regulator control-loop response to the transient, (b) IR/ESL drop across the PDN between the regulator and the load, and (c) ground bounce — the "ground" at the load is not the same potential as the "ground" at the regulator. Probing ground-to-ground between those two points with a differential probe is often the most revealing measurement.

4. **Check decoupling effectiveness.** Are the high-frequency decoupling caps placed close to the load pins with short, wide return paths? Is there a via-stitching or plane-split issue that forces return current through a long path? A quick test is to add a temporary bulk cap right at the load and see whether the ripple changes — if it does, the PDN impedance is the issue, not the regulator.

5. **Only then consider the regulator.** Check its loop stability (compensation network, output capacitor ESR within the stable range), its current-limit behavior during the transient, and whether the transient is exceeding its rated di/dt.

The discipline is: measure the transient at the source and at the load, and let the difference tell you whether this is a source problem, a distribution problem, or a return-path problem.

**Possible follow-ups:**
- How would you use a network analyzer or a PDN impedance measurement to confirm the diagnosis before changing components?
- If adding bulk capacitance fixes the symptom but the root cause is a plane split, what would you do differently in the next board revision?

## Q3: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** The bench-to-installed delta is one of the most common and most misleading failure patterns, because it usually means the *electrical* design is fine and the *mechanical/thermal/EMI environment* is what changed. I'd resist the temptation to re-tune the analog chain until I've proven what actually changed between the two configurations.

My approach:

1. **Enumerate what changes when the enclosure goes on and the unit is mounted.** Mechanical stress on the PCB (flexure near mounting screws, connector strain), thermal environment (self-heating trapped inside a sealed enclosure, or a nearby heat source), grounding topology (chassis ground now bonded, or a mounting bracket creating a new return path), and EMI (the enclosure may be a shield, or it may be a resonant cavity). Each of these produces a *consistent* offset, which matches the symptom.

2. **Reproduce the delta in a controlled way.** Rather than chasing the fully assembled unit, I'd try to isolate which of the above is responsible: run the unit open on the bench but with the enclosure placed over it (no screws) to test EMI/shielding; run it with the enclosure fully assembled but on an insulating stand to test grounding; run it with the enclosure assembled but with a thermocouple on the AFE to test thermal. Each test removes one variable.

3. **Check the reference and the return path first.** A consistent offset with assembly often traces to a ground-reference shift — the analog ground and the chassis ground are now connected through the mounting hardware, or the return current path has changed. Measuring the potential difference between the AFE's local ground and the system ground in both configurations is a fast, high-value test.

4. **Check mechanical stress on the sensor or its connections.** A bridge sensor or its connector can shift its zero point under mechanical preload from the enclosure. If the offset correlates with mounting torque, that's the answer.

5. **Check thermal.** A small, consistent offset that appears only when the unit is sealed is often a temperature-coefficient effect in the reference or the instrumentation amplifier. A thermal camera or a thermocouple on the AFE, compared between open and sealed configurations, will confirm or rule this out.

The key is to treat "assembled and installed" as a *set of independent environmental changes*, not a single condition, and to peel them apart one at a time.

**Possible follow-ups:**
- If the offset turns out to be a ground-reference shift caused by the chassis bonding, how would you fix it without compromising EMC?
- How would you decide whether to compensate the offset in firmware versus fix it in hardware?

## Q4: A medical device passes all functional and safety tests at design verification, but during a 30-unit pilot production run, three units fail a 72-hour burn-in test with the same symptom: the device stops communicating after roughly 48 hours and requires a power cycle to recover. How would you approach this?

**Answer:** This is a pilot-production failure with a consistent symptom and a consistent time-to-failure, which is actually a gift — the reproducibility and the timing are strong clues. I'd treat it as a combined manufacturing-variation and time-dependent-failure investigation, and I'd resist the urge to declare it a "firmware bug" or a "component problem" before the evidence says so.

My approach:

1. **Preserve the failing units and their state.** Before power-cycling anything, capture whatever diagnostic state exists — logs, memory dumps if accessible, the state of any status LEDs, the current draw, the temperature. The fact that a power cycle recovers it means the failure is a *state* the device gets stuck in, not a destroyed component. That state is the evidence.

2. **Look at the time-to-failure distribution.** Three units failing at roughly 48 hours out of 72 is suspiciously tight. That points to something that accumulates or saturates — a counter overflow, a memory leak, a thermal soak reaching steady state, a log buffer filling, a watchdog or keep-alive timer wrapping, or a communication retry counter exhausting. I'd instrument a fresh unit to log the relevant counters and see which one is approaching a limit at the 48-hour mark.

3. **Separate "manufacturing variation" from "design margin."** The design verification units passed; the pilot units didn't. What's different? Component lot, assembly process, firmware version, test fixture, ambient conditions during burn-in. I'd compare the failing units against passing units from the same run — same lot, same line, same burn-in rack — to see whether the difference is unit-to-unit or rack-to-rack.

4. **Check the burn-in environment itself.** Is the failure correlated with a particular slot in the burn-in rack, a particular power supply, a particular ambient temperature? A rack-level correlation would point to a test-environment cause rather than a product cause, and that changes the corrective action entirely.

5. **Reproduce with fault injection.** If I suspect a specific mechanism (e.g., a communication retry counter), I'd inject the condition deliberately on a bench unit — force the retries, shorten the timeout — and confirm the failure mode matches. That converts a 48-hour wait into a minutes-long test.

6. **Trace to corrective action.** Once the mechanism is confirmed, the corrective action needs to address both the *trigger* (why did the state occur) and the *recovery* (why didn't the device self-recover). A device that requires a power cycle to recover from a recoverable condition is itself a design gap, regardless of the trigger.

**Possible follow-ups:**
- If the failure turns out to be a firmware counter overflow that only manifests after 48 hours, how would you decide between a firmware fix and a design change to the recovery mechanism?
- How would you structure the 8D to distinguish between an escape (why didn't test catch it) and a root cause (why did it happen)?

## Q5: You're leading a cross-functional failure investigation where the firmware and hardware teams each believe the other side owns an intermittent communication failure, and neither has conclusive evidence. How would you structure the investigation to break the deadlock?

**Answer:** Cross-team deadlocks on intermittent failures are almost always a *framing* problem, not a technical one. Each team is looking at the same failure through a different lens and each has partial evidence that supports its own hypothesis. My job as lead is not to adjudicate between the two hypotheses but to design an investigation that produces evidence that discriminates between them.

My approach:

1. **Reframe the question.** Instead of "is it hardware or firmware?", the question becomes "what observable, measurable event precedes the failure, and which side of the interface does it live on?" That's a question both teams can contribute to without conceding their position.

2. **Define the interface contract explicitly.** Write down what the firmware *expects* from the hardware (timing, signal levels, handshake sequence) and what the hardware *provides* (measured, not assumed). The gap between expectation and reality is where the bug lives, and it's usually visible once it's written down.

3. **Instrument the boundary, not the interiors.** Put a logic analyzer or a protocol analyzer on the physical interface and capture the failure in the act. This produces evidence that neither team can dismiss as "your code" or "your board" — it's the actual traffic. Correlate the capture with firmware-side timestamps and hardware-side scope triggers so both teams are looking at the same event.

4. **Design discriminating experiments.** For each hypothesis, ask: "what would we see if this were true, and what would we see if it were false?" Then run the experiment that produces different observations under the two hypotheses. For example, if firmware suspects a marginal pull-up, swapping the pull-up value should change the failure rate; if hardware suspects a firmware race, adding a deliberate delay in the firmware should change the failure rate. Run both, and let the results speak.

5. **Assign ownership of the *investigation*, not the *blame*.** Give each team a specific experiment to run and a specific piece of evidence to produce, with a deadline. This converts a positional argument into a shared work plan, and it gives both teams a way to contribute without losing face.

6. **Escalate on evidence, not opinion.** If after the experiments the evidence still doesn't discriminate, that itself is a finding — it means the failure is genuinely at the boundary and the fix needs to be a joint one (e.g., a more robust handshake that tolerates the marginal condition regardless of which side is "at fault").

The leadership discipline is to keep the conversation on *what we can measure* rather than *who is right*, and to make it safe for either team to be wrong.

**Possible follow-ups:**
- What would you do if the discriminating experiment is inconclusive because the failure rate is too low to observe in a reasonable time?
- How would you handle it if one team's manager starts escalating the disagreement to your leadership before the investigation concludes?
