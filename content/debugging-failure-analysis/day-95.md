# debugging-failure-analysis — Day 95

## Q1: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** The key insight is that the offset appears only after two changes happen together — the enclosure is closed and the unit is mounted — so I'd treat those as separate variables and isolate them rather than assuming they're one condition. First, I'd reproduce the offset with the enclosure closed but the unit still on the bench, then with the enclosure open but the unit in its mounting position. That split tells me whether the mechanism is mechanical (flex, fastener torque, cable routing, pressure on a connector or board), environmental (thermal, airflow blocked by the enclosure), or electrical (grounding path changes, shield contact, antenna proximity, capacitive coupling to the mounting surface).

If it's mechanical, I'd look at board flex from mounting screws, connector seating that changes when the harness is dressed a certain way, or a sensor port that sees different mechanical loading once installed. If it's electrical, I'd measure the analog front-end's reference and ground at the ADC pins in both states — a consistent offset with a stable input usually points to a reference or ground shift, not noise. I'd also check whether the offset tracks a specific unit or is common across units; unit-specific points to tolerance stack-up or assembly variation, common across units points to a design-level coupling path. Throughout, I'd keep the measurement point fixed (same probe location, same input source) so the only variable changing is the assembly state.

**Possible follow-ups:** How would you distinguish a ground-shift offset from a genuine sensor offset without removing the sensor? What would you do if the offset only appeared after several hours installed, not immediately?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** Ripple that appears only under a switching load is a load-transient and loop-response problem, so I'd start by characterizing it properly rather than just observing it. I'd measure at the decoupling capacitors with a short-ground-tip probe — not a long ground lead, which turns the probe into an antenna and invents ripple that isn't there — and capture the transient with enough bandwidth to see both the high-frequency switching residue and the lower-frequency recovery. I'd compare the ripple at the regulator output, at the load's supply pins, and at the bulk cap to see where the disturbance is actually being generated versus where it's being amplified.

Then I'd separate the possible mechanisms: is it the regulator's transient response (loop bandwidth, output capacitance, ESR), is it ground bounce between the load's return path and the regulator's reference, or is it coupling from the switching subsystem's own current loop into the rail? A useful test is to slow the load's edge rate or add local bulk capacitance right at the load — if the ripple collapses, it's a local decoupling and transient-response issue; if it persists, I'd look at the return path and layout. I'd also check whether the "excessive" ripple is actually a measurement artifact from probing across a shared ground return. The fix should follow the mechanism: more local capacitance and better return path for transient response, layout and grounding changes for ground bounce, and filtering or snubbing at the source if it's coupling.

**Possible follow-ups:** How would you tell whether the regulator is oscillating versus just responding slowly to a load step? What role does the probe's ground connection play in whether you trust the ripple number?

## Q3: A device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline. How would you approach this investigation?

**Answer:** This is one of the harder classes of failure because there's no fault flag to anchor on, so the first job is to make the wrong value observable in real time rather than weeks later. I'd add instrumentation that captures the raw ADC samples alongside the processed value and a timestamp, so I can tell whether the error originates in the analog domain, the conversion, the processing, or the transport. If the raw samples are correct but the reported value is wrong, the problem is in firmware processing or a data-handling path — a scaling error, a stale buffer, a race between the sampling task and the reporting task, or a shared variable updated without proper synchronization. If the raw samples themselves are wrong, it's an analog or timing problem upstream.

I'd also look for correlation with operating state: does the wrong value cluster around a particular mode, temperature, or event like a wireless transmission or a motor actuation? A plausible-but-wrong value that appears intermittently often comes from reading a buffer while it's being updated, or from a conversion that was triggered before the input settled. I'd add a checksum or sequence counter to the data path so a corrupted or stale sample is detectable, and I'd try to reproduce it under accelerated conditions — higher sampling rate, more concurrent activity — to raise the failure rate enough to study. The corrective action has to address the mechanism, not just add a plausibility check that masks it.

**Possible follow-ups:** How would you design the instrumentation so it doesn't change the timing behavior you're trying to observe? If the raw samples are correct, what are the most likely firmware mechanisms for a plausible-but-wrong output?

## Q4: You're leading a failure investigation and you've reached a point where two plausible root causes remain, both supported by partial evidence, and the team is split on which to pursue. How would you handle this and drive the investigation to a conclusion?

**Answer:** When two hypotheses both have partial support, the trap is letting the team argue about which is more likely instead of designing a test that discriminates between them. My first move is to reframe the question: not "which cause is right" but "what observation would be true under one hypothesis and false under the other?" Then I'd design the cheapest, fastest experiment that produces that discriminating observation — a targeted measurement, a controlled fault injection, a swap of one variable — and assign it clearly so it actually gets done.

I'd also make the evidence explicit: write down what each hypothesis predicts, what's been observed, and where each is weak. Often that exercise reveals that one hypothesis is doing more explanatory work, or that the two aren't mutually exclusive — sometimes both are contributing and the real question is which dominates. I'd set a decision point: if the discriminating test is inconclusive, we escalate to a more invasive test or bring in an outside perspective rather than continuing to accumulate ambiguous data. Throughout, I'd keep the team focused on the shared goal and make sure the person advocating the losing hypothesis isn't sidelined — their reasoning often sharpens the test design. The investigation concludes when we have a mechanism that explains the evidence and a corrective action we can verify, not when the loudest voice wins.

**Possible follow-ups:** What would you do if the discriminating test is expensive and the schedule is tight? How do you keep a split team productive without suppressing the minority view?

## Q5: A junior engineer has been debugging an intermittent failure for several days without progress — they've been testing components in isolation and everything passes, but the system-level failure persists. They're frustrated and the schedule is tight. How would you approach this?

**Answer:** The pattern here — components pass in isolation, the system fails — usually means the failure depends on an interaction the isolation testing has removed, so the first thing I'd do is help them reframe from "find the bad component" to "find the condition that only exists at the system level." I'd sit with them and ask what they've actually observed versus assumed, and specifically what's different between their isolated test setup and the real system: power source, grounding, cable lengths, load, timing, temperature, concurrent activity. The failure often lives in exactly those differences.

I'd then help them build a reproduction that keeps the system intact but lets them control one variable at a time — rather than pulling components out, keep the system assembled and perturb it. I'd also introduce structure: a written log of what's been tried and ruled out, so the effort compounds instead of looping, and so they can see progress even when the failure hasn't reproduced. On the human side, I'd acknowledge that several days without progress is genuinely frustrating and normalize it, then give them a concrete next step rather than a vague "keep at it." If the schedule is tight, I'd help them time-box the current approach and define an escalation point — bring in a second pair of eyes or a different measurement technique — so the investigation doesn't stall indefinitely. The goal is to restore their sense of forward motion and give them a method that generalizes.

**Possible follow-ups:** How would you decide when to step in directly versus coach them through it? What would you do if the failure simply won't reproduce on demand?
