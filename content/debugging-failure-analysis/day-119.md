# debugging-failure-analysis — Day 119

## Q1: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** The key insight is that the offset is a function of the mechanical/electrical environment, not the circuit itself — so I'd treat the enclosure and mounting as part of the measurement system and isolate which physical variable changed. I'd start by reproducing the offset reliably and quantifying it: is it constant, does it scale with the input, and does it appear the moment the enclosure is closed or only after the unit is bolted into its mounting position? That distinction separates an enclosure-induced effect (shielding, capacitance, thermal) from a mounting-induced one (grounding path, mechanical stress on the PCB, chassis coupling).

Next I'd divide the variables. I'd run the unit open on the bench, then close the enclosure without mounting, then mount it without the enclosure if mechanically possible, and compare the offset at each stage. In parallel I'd probe the analog front-end in situ — measuring at the ADC input and at the amplifier output with a differential probe, not a ground-referenced one, because the offset may be a ground-reference shift rather than a true signal error. If the offset tracks the enclosure, I'd suspect changed parasitic capacitance on a high-impedance node, a shield now tied to a different ground point, or a thermal gradient from the sealed enclosure. If it tracks the mounting, I'd look at chassis ground bonding, mounting-screw ground paths, and mechanical stress on the board near the front-end.

I'd also check whether the offset is stable or drifts after assembly, since a thermal component would show a time constant. Throughout, I'd keep one change at a time and log the offset value at each configuration so the evidence points to a single variable rather than a guess.

**Possible follow-ups:** If the offset disappears when you probe with a differential probe but is present in the firmware reading, what does that tell you? How would you confirm a ground-reference shift versus a true amplifier offset?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** This is a load-transient and power-distribution problem, so I'd first characterize the ripple properly rather than trusting a single probe point. I'd measure at the decoupling capacitors closest to the load, using a short ground lead or a coaxial probe tip to avoid picking up radiated switching noise as "ripple," and I'd capture the transient synchronously with the subsystem's switching event so I can see whether the disturbance is a fast edge (inductive) or a slower droop (insufficient bulk capacitance or regulator loop response).

Then I'd separate the mechanisms. A high-frequency spike at the switching instant usually points to parasitic inductance in the power path — trace length, via count, missing or ineffective decoupling — while a longer droop points to the regulator's transient response or bulk capacitance being inadequate for the step load. I'd check the regulator's datasheet transient response against the measured load step, and I'd look at whether the ripple is differential (across the rail and its return) or common-mode (appearing on both), because that changes whether the fix is layout, decoupling, or grounding.

I'd also verify the load itself: is the subsystem drawing a clean step, or is it drawing a burst of current with fast edges that the supply was never designed for? Sometimes the fix is on the load side — slowing edges, adding local bulk capacitance at the subsystem — rather than the regulator. I'd confirm any change with the same synchronized measurement so I know I've addressed the actual mechanism, not just moved the ripple.

**Possible follow-ups:** How would you distinguish insufficient bulk capacitance from a regulator loop-stability problem using the transient waveform? If adding a ferrite bead reduced the measured ripple but the device still reset, what would you check next?

## Q3: A device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline. How would you approach this investigation?

**Answer:** The hard part here is that the failure is silent — no fault flag, no out-of-range value — so the investigation has to start by making the invisible visible. I'd first establish whether the wrong value originates at the sensor, at the conversion, or in the data path afterward, because "plausible but wrong" could be a real physical reading of a disturbed signal, a corrupted conversion, or a value that was correct when sampled but got mis-associated with a timestamp or channel later.

I'd add instrumentation that captures the raw ADC output alongside the processed value and a timestamp, so I can compare what the converter saw against what the firmware reported. If the raw value is also wrong, the problem is upstream — sensor, front-end, or sampling timing — and I'd look at whether the errors correlate with other activity (a switching event, a communication burst, a temperature change). If the raw value is correct but the reported value is wrong, the problem is in the firmware data path: a buffer overwrite, a race between the sampling task and the reporting task, a scaling or calibration error applied inconsistently, or a stale value being sent.

I'd also look at the error's statistics — is it a single-bit flip, a fixed offset, a value from a different channel, or a repeat of a previous sample? Each pattern points to a different mechanism. Throughout, I'd try to reproduce it under controlled conditions (fault injection, stressing the bus, varying temperature) so I can confirm a root cause rather than just observe the symptom.

**Possible follow-ups:** If the wrong values always occur shortly after a wireless transmission, how would that change your hypothesis? How would you design a self-test that could catch this class of error in the field without false positives?

## Q4: How would you approach a failure investigation where a device's power rail collapses only during a specific operating mode, but the regulator and its passives all measure within specification when the board is powered in isolation?

**Answer:** The fact that the regulator passes in isolation tells me the fault is in the interaction between the regulator and the rest of the system during that operating mode, not in the regulator's own components. So I'd stop testing the regulator alone and start testing it in the exact conditions where it fails — same load, same mode, same sequencing — while measuring the rail, the regulator's feedback and enable pins, and the input supply simultaneously.

I'd first characterize the collapse: how deep, how fast, and is it a hard drop or a gradual sag? A fast collapse suggests a transient load the regulator can't supply or a protection event (overcurrent, thermal, UVLO) tripping; a gradual sag suggests the input supply drooping, a thermal issue, or the regulator losing regulation because its feedback is disturbed. I'd check the regulator's fault and status pins if it has them, and I'd look at whether the collapse is preceded by a current spike, a temperature rise, or a control signal change.

Then I'd look at what the operating mode actually changes: additional loads switching on, a different clock or communication rate, a GPIO that reconfigures a pin the regulator depends on, or a sequencing issue where the mode enables a load before the rail is ready. I'd also verify the input supply and the ground return under that mode, since a shared ground path can make the regulator "see" a collapse that's really a reference shift. The goal is to find the specific interaction — load, sequencing, or reference — rather than re-qualifying components that already pass.

**Possible follow-ups:** If the regulator's enable pin shows a brief glitch at the moment of collapse, where would you look next? How would you distinguish a genuine overcurrent protection trip from a UVLO event using only the rail and input waveforms?

## Q5: You're leading a failure investigation and you've reached a point where two plausible root causes remain, both supported by partial evidence, and the team is split on which to pursue. How would you handle this and drive the investigation to a conclusion?

**Answer:** When two hypotheses both have partial support, the trap is to let the team argue about which is "more likely" — that's a debate about opinion, not evidence. I'd reframe the problem around discriminating tests: for each hypothesis, what observation would be true if it were the cause and false if it weren't? Then I'd prioritize the test that most cleanly separates the two, ideally one that's fast and non-destructive, and assign it explicitly rather than letting people keep gathering supporting evidence for their preferred theory.

I'd also make the decision criteria explicit up front — what result would let us close each hypothesis, and what would keep it open — so the conclusion isn't a matter of who argues hardest. If the discriminating test isn't feasible with the units on hand, I'd consider whether a controlled reproduction or fault injection can create the condition, and I'd be honest about the residual uncertainty if we have to proceed without full confirmation.

On the team side, I'd acknowledge that both hypotheses are legitimate and that the split is a sign people are engaged, then redirect the energy into designing the test rather than defending a position. I'd keep the investigation log showing what's been ruled out and why, so the team can see progress even before the answer lands. If a decision has to be made under schedule pressure before full confirmation, I'd document the leading hypothesis, the evidence for and against, and the residual risk, so the corrective action is traceable and revisitable.

**Possible follow-ups:** What would you do if the discriminating test is inconclusive and the schedule won't allow another round? How do you keep a senior engineer who backed the losing hypothesis engaged and productive afterward?
