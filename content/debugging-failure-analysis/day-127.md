# debugging-failure-analysis — Day 127

## Q1: How would you approach a failure investigation where a device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline?

**Answer:** The defining difficulty here is that nothing in the system's own health checks is failing, so the investigation has to start by making the invisible visible. My first step is to establish whether the wrong value is wrong at the source or wrong after the fact: I'd add instrumentation that captures the raw ADC counts, the timestamp, and the conversion path state at the moment of sampling, so I can compare what the converter produced against what the firmware ultimately reported. If the raw counts are correct and the reported value is wrong, the defect is in the processing chain — scaling, filtering, buffer handling, or a shared variable being written from two contexts. If the raw counts are already wrong, the problem is upstream in the analog domain or in the sampling timing.

Because the error is plausible rather than out of range, I'd suspect the mechanisms that produce small, systematic-looking errors: a stale buffer being read because a conversion-complete flag was consumed by the wrong consumer, a race between an ISR writing a sample and the main loop reading it without proper synchronization, a filter state that gets corrupted by an occasional out-of-sequence sample, or an index that wraps under a specific timing condition. I'd also check whether the wrong values cluster around specific events — mode changes, communication bursts, or low-power transitions — because that would point to a timing or state-machine interaction rather than a component defect.

To reproduce it, I'd build a test harness that drives the device through long-duration operation with a known reference input and logs every sample with its provenance, so the failure can be caught in the act rather than inferred from offline review. Once caught, I'd narrow with one change at a time — disabling the filter, then the DMA, then the interrupt path — to isolate which stage introduces the error. The corrective action has to be verified against the same long-duration harness, because a fix that only passes a short bench test hasn't proven anything for an intermittent, plausible-looking error.

**Possible follow-ups:** How would you distinguish a data race from a stale-buffer bug if both produce the same symptom? What would you log to make the failure diagnosable in the field without adding significant overhead?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** The correlation with the high-current subsystem tells me the ripple is almost certainly load-transient-driven rather than a steady-state regulator problem, so I'd start by characterizing the disturbance rather than the symptom. I'd measure the rail at the load's decoupling capacitors with a short-ground-tip probe — not a long ground lead, which will pick up loop inductance and show ringing that isn't really there — and capture the transient with enough bandwidth to see the edge. I'd simultaneously measure the subsystem's current with a current probe or a shunt so I can correlate the ripple event with the exact current step.

From there the question is whether the regulator is responding too slowly, the decoupling network is inadequate, or the disturbance is coupling in through a shared impedance. I'd check the regulator's loop response and its output capacitance against the transient magnitude and slew rate: if the rail dips and recovers over a time consistent with the regulator's bandwidth, the loop is the limit; if it dips instantly and recovers slowly, the bulk capacitance is insufficient. I'd also probe the ground return path — a high-current switching subsystem can develop ground bounce across a shared return, which shows up as ripple on other rails even when the regulator is behaving perfectly. That's where probing at the decoupling cap's ground side, and comparing against a quiet reference point, separates a real rail disturbance from a measurement artifact.

If the ripple is coupling rather than loading, I'd look at layout: shared vias, return paths that force the switching current through sensitive areas, or insufficient decoupling at the point of load. The fix candidates — more bulk or local decoupling, a snubber, layout revision, or sequencing the subsystem's enable to reduce the step — each address a different mechanism, so I'd confirm the mechanism before choosing. And I'd verify the fix at the worst-case load step, not just nominal, since the failure only appears under switching.

**Possible follow-ups:** How would you tell the difference between ground bounce and genuine rail ripple on your scope trace? What would you check first if adding decoupling didn't reduce the ripple?

## Q3: A medical device passes all functional and safety tests at design verification, but during a 30-unit pilot production run, three units fail a 72-hour burn-in test with the same symptom: the device stops communicating after roughly 48 hours and requires a power cycle to recover. How would you approach this?

**Answer:** Three out of thirty failing with an identical symptom and a consistent time-to-failure is a strong signal — it's not random component fallout, it's a systematic mechanism that design verification didn't exercise. The first thing I'd do is treat the 48-hour figure as data, not coincidence: something in the device accumulates, drifts, or wraps over that timescale. Candidates include a counter or timestamp overflow, a memory leak or buffer that fills slowly, a thermal accumulation that stabilizes at a temperature the DV chamber didn't hold long enough, a watchdog or communication timeout that only trips after a specific number of transactions, or a power component whose behavior shifts as it heats.

I'd start by capturing state at the moment of failure rather than after the power cycle — if the firmware has any logging or can be instrumented to dump its state on a communication timeout, that's the highest-value evidence. I'd also run the failing units with the enclosure open and thermocouples or a thermal camera on the communication transceiver and the main processor, because a 48-hour failure that requires a power cycle is consistent with a thermal or latch-up condition that only clears on full power removal. In parallel, I'd review the firmware for anything that increments without bound — retry counters, sequence numbers, buffer indices — and for any resource that's allocated but not freed on an error path.

The key discipline is to reproduce the failure under controlled conditions before theorizing too far: run a small batch in a chamber at the burn-in temperature for longer than 48 hours with instrumentation attached, and see whether the failure follows time, temperature, or transaction count. That distinguishes an accumulation mechanism from a thermal one. Once I have a candidate, I'd confirm it by fault injection — forcing the suspected condition and verifying the symptom appears — and then verify the corrective action against the full 72-hour burn-in, not a shortened version, since the whole point is that the failure only shows up over time.

**Possible follow-ups:** How would you decide whether to investigate the three failed units destructively or preserve them for comparison testing? What would you change in the design verification plan so this class of failure is caught before pilot production?

## Q4: You're leading a cross-functional investigation where the firmware and hardware teams each believe the other side owns an intermittent communication failure, and neither has conclusive evidence. How would you structure the investigation to break the deadlock?

**Answer:** The deadlock usually isn't a disagreement about facts — it's that each team is reasoning from evidence gathered in its own domain, and neither set of evidence is decisive at the boundary where the failure actually lives. My first move is to reframe the question from "whose fault is it" to "what single measurement would discriminate between the two hypotheses," and then get that measurement made jointly. For an intermittent communication failure, that's typically a simultaneous capture: bus traffic on a logic analyzer or scope alongside the firmware's own state and timing, so both teams are looking at the same event at the same instant rather than at separate test results.

I'd set up a joint reproduction session where hardware and firmware engineers are in the same room with the same unit, and I'd define in advance what each hypothesis predicts. If the hardware hypothesis is a marginal pull-up or excessive capacitance, the bus waveform should show slow edges or a degraded high level under worst-case conditions. If the firmware hypothesis is a timing or recovery-routine bug, the waveform should look clean but the firmware should be observed entering its recovery path at the wrong moment or missing a status flag. Those predictions are testable, and the test either supports one or forces a third hypothesis — which is itself progress.

Structurally, I'd assign a single owner for the investigation with authority to request tests from both teams, keep a shared evidence log so findings aren't disputed after the fact, and timebox each hypothesis: if a hypothesis can't be supported within its window, it gets deprioritized rather than defended. I'd also make sure the teams aren't testing in isolation — the failure is intermittent and system-level, so component-level tests that pass prove little. The goal is to converge on a mechanism both teams accept, even if the fix ultimately spans both domains.

**Possible follow-ups:** What would you do if the discriminating measurement is inconclusive and both hypotheses remain partially supported? How would you keep the teams collaborative rather than defensive when one side's hypothesis is eliminated?

## Q5: A junior engineer on your team has been debugging an intermittent failure for several days without progress — they've been testing components in isolation and everything passes, but the system-level failure persists. They're frustrated and the schedule is tight. How would you approach this?

**Answer:** The pattern here — components pass in isolation, the system fails — is itself the most useful clue, and the first thing I'd do is help the engineer see that rather than treat it as a dead end. Testing components in isolation assumes the failure lives inside a component; if every component passes, the failure lives in an interaction, and the debugging strategy has to change to match. I'd sit down with them, not to take over, but to walk through what they've ruled out and reframe the problem: what conditions exist at the system level that don't exist in isolation — power sequencing, shared grounds, thermal coupling, firmware state, timing between subsystems — and which of those could produce the symptom.

I'd then help them build a reproduction that preserves the system context, because an intermittent failure that can't be reproduced can't be debugged efficiently. That might mean instrumenting the full system to log state continuously until the failure occurs, rather than testing subassemblies on the bench. I'd also introduce the discipline of one variable at a time: change a single condition — disable one subsystem, freeze the temperature, fix the supply — and see whether the failure rate changes, which converts a vague intermittent into a measurable signal.

On the human side, frustration after several days is normal and usually comes from effort not producing information, not from lack of skill. I'd acknowledge that the isolation testing wasn't wasted — it genuinely narrowed the space — and give them a concrete next step with a short feedback loop so they can see progress again. I'd check in frequently but let them own the investigation, and I'd pair them with someone experienced in system-level debugging if that's available. The schedule pressure is real, but the fastest path out is usually a better strategy, not more hours on the same one.

**Possible follow-ups:** How would you handle it if the engineer resisted changing approach because they were confident the isolation testing would eventually find it? What would you do if the reframed investigation still hadn't produced a root cause when the schedule deadline arrived?
