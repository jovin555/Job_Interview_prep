# debugging-failure-analysis — Day 88

## Q1: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** The key observation is that the offset appears only when two variables change together — mechanical assembly and installed orientation — so the first job is to separate them. I'd build a test matrix: open bench with harness, board in enclosure but not installed, board in enclosure and installed in the final mounting position, and ideally the installed unit with the enclosure temporarily opened. If the offset follows the enclosure, I'm looking at mechanical stress on the PCB (board flex altering a strain-sensitive component or a solder joint), changed thermal environment, or a grounding/shielding path that only completes when the housing is fastened. If it follows the installed position, I'm looking at orientation-dependent effects — gravity on a sensor diaphragm, cable routing, or proximity to the mounting surface changing parasitic capacitance or coupling.

From there, measurement beats speculation. I'd measure the analog front-end at the ADC input with a high-impedance probe in each configuration, and compare against the firmware-reported value to confirm the offset is truly in the analog domain and not introduced downstream. A useful trick is to substitute a fixed reference source at the sensor connector so the sensor itself is removed from the equation — if the offset persists with a known-good source, it's the electronics or the assembly; if it disappears, it's the sensor or its interface. I'd also check whether the offset is stable and repeatable or varies with torque on the fasteners, which would point strongly at mechanical stress. Throughout, I'd keep one change at a time so I can attribute the effect cleanly, and I'd document the configuration for every measurement because "installed" is easy to reproduce inconsistently.

**Possible follow-ups:** How would you determine whether the offset originates in the sensor, the front-end electronics, or the ADC? What would you do if the offset only appeared after the unit had been installed for several hours?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** This is a load-transient and power-distribution problem, so I'd start by characterizing it properly rather than just observing that ripple is "bad." First, measure at the right place: probe directly across the decoupling capacitors at the load, not at the regulator output or at the end of a long ground lead. A probe with a long ground clip will pick up loop inductance and show ripple that isn't really there — I'd use a short ground spring or a coaxial probe tip, and confirm the measurement setup by checking a known-clean rail first. Then I'd capture the ripple synchronized to the switching event, using the subsystem's enable or a current probe on its supply as the trigger, so I can see whether the disturbance is a transient dip at the moment of switching, a sustained oscillation, or high-frequency noise coupled onto the rail.

Next I'd separate the mechanisms. A dip at load-step is the regulator's transient response — loop bandwidth, output capacitance, and ESR determine how far it sags and how fast it recovers. Ringing after the step suggests insufficient damping or a resonance between the output capacitor and the parasitic inductance of the layout. High-frequency content synchronized to the switching edges suggests the current loop area is too large or the return path is broken, so the switching current is flowing through a shared impedance. I'd check the return path first, because a split or narrow ground return under a high-di/dt load is a very common cause. I'd also verify the subsystem's own input decoupling is adequate and close to its pins, and check whether the bulk capacitance is actually where the current is drawn. Only after I understand which mechanism dominates would I consider changes — more or better-placed decoupling, a damping network, layout revision, or a different regulator compensation — and I'd verify each change with the same synchronized measurement so I can attribute the improvement.

**Possible follow-ups:** How would you distinguish regulator loop instability from a layout-related ground bounce problem? What measurement would you make to confirm the return path is the culprit?

## Q3: A device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline. How would you approach this investigation?

**Answer:** The hardest part here is that the failure is silent — no fault flag, no out-of-range value — so the investigation has to start with making the failure observable before it can be explained. I'd first establish whether the wrong value is wrong at the source or corrupted in transit. That means adding instrumentation: log the raw ADC counts alongside the converted value, timestamp each sample, and record the sensor's status register and any communication error counters at the same instant. If the raw counts are already wrong, the problem is upstream in the analog domain or the sensor itself; if the raw counts are correct but the reported value is wrong, the corruption is in the conversion, storage, or transmission path. A single-bit-flip signature would push me toward memory or bus integrity; a smoothly drifting but plausible value would push me toward the analog front-end or the sensor.

I'd also look hard at the conditions under which bad samples occur — time since power-on, temperature, which other subsystems were active, whether the sample coincided with a communication transaction or a memory write. If the error is rare, I'd try to increase the observation rate with a targeted stress test rather than waiting for it in the field: run the device through the suspected conditions in a loop and log continuously. Throughout, I'd keep the raw data and the derived data separate in the logs so I never lose the ability to re-analyze. The corrective action depends entirely on which stage the corruption enters, so I would resist the temptation to "fix" it with a plausibility check in firmware until I know the mechanism — a plausibility filter would mask the symptom and leave the root cause in the field.

**Possible follow-ups:** How would you design the logging so it doesn't itself perturb the timing you're trying to observe? If the corruption turned out to be a single-bit flip in RAM, what would your next steps be?

## Q4: You're leading a failure investigation and you've reached a point where two plausible root causes remain, both supported by partial evidence, and the team is split on which to pursue. How would you handle this and drive the investigation to a conclusion?

**Answer:** When two hypotheses both have partial support, the trap is to let the team argue about which is more likely — that's a debate about priors, not evidence. I'd reframe the question: for each hypothesis, what observation would be true if it were correct and false if it weren't? That turns the disagreement into a set of discriminating tests. I'd list the predictions each hypothesis makes, look for the test that most cleanly separates them, and prioritize by cost and speed — a bench experiment that takes an afternoon beats a field data pull that takes a month, if it discriminates.

I'd also be explicit about what "partial evidence" means for each side, because often one hypothesis explains more of the observations than the other, and that asymmetry is itself informative. If the discriminating test isn't feasible, I'd consider whether both causes could be real and interacting — sometimes the split in the team is a false dichotomy. On process, I'd assign owners to each hypothesis so both get a fair, rigorous test rather than one being quietly abandoned, and I'd set a decision point: by a certain date, we run the discriminating test and let the result decide. That keeps the investigation moving without steamrolling the minority view, and it gives the team a shared basis for the conclusion rather than a vote. Whatever the outcome, I'd document the reasoning and the evidence for the rejected hypothesis, because in a regulated context the traceability of why a cause was ruled out matters as much as why one was accepted.

**Possible follow-ups:** What would you do if the discriminating test was inconclusive? How would you keep the team aligned if the evidence ended up favoring the hypothesis held by the less senior engineer?

## Q5: A junior engineer has been debugging an intermittent failure for several days without progress — they've been testing components in isolation and everything passes, but the system-level failure persists. They're frustrated and the schedule is tight. How would you approach this?

**Answer:** The first thing I'd do is acknowledge the frustration honestly — several days on an intermittent fault with no progress is genuinely demoralizing, and pretending otherwise doesn't help. Then I'd reframe what's happening: testing components in isolation and finding them all good isn't failure, it's useful negative evidence. It tells us the fault is in an interaction, not a part, and that's a real narrowing of the search space. I'd say that explicitly so the engineer sees their work as progress rather than a dead end.

On method, I'd help them shift from "test components" to "reproduce the failure reliably." An intermittent fault that can't be reproduced on demand can't be debugged efficiently — every test is a coin flip. So the priority becomes finding the conditions that raise the failure rate: temperature, timing, load, specific sequences of operation, particular units. I'd work with them to build a stress harness or a scripted sequence that runs the suspect scenario in a loop and logs everything, so the failure surfaces on our schedule rather than the device's. I'd also introduce the divide-and-conquer discipline: change one variable at a time, and instrument the boundary between subsystems rather than the subsystems themselves, because the fault lives at the interface. And I'd pair with them for a session — not to take over, but to ask the questions that break tunnel vision, like "what's the smallest configuration in which this still fails?" Finally, I'd check the schedule pressure separately: if the timeline is genuinely at risk, that's a conversation to have with the project lead early, not something to solve by pushing the engineer harder.

**Possible follow-ups:** How would you decide when to escalate the schedule risk versus when to give the engineer more time? What would you do if the failure rate was so low that even a stress harness couldn't reproduce it reliably?
