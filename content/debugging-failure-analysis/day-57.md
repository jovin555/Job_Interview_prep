# debugging-failure-analysis — Day 57

## Q1: How would you approach debugging a device whose failure only reproduces when it is tested with the production test fixture, but never on the bench with a lab supply and jumper wires?

**Answer:** This is a classic case of the test setup itself being part of the system under test, so the first move is to treat the fixture as a variable rather than a fixed reference. I'd start by enumerating every way the fixture differs from the bench setup: supply source and cable length, grounding scheme, load conditions, signal routing, connector mating, and any automated sequencing the fixture applies (power-up order, stimulus timing, relay switching). Then I'd change one of those at a time toward the bench configuration — for example, power the board from the fixture's connector but from a lab supply, or run the fixture's sequence manually — to find which single difference flips the behavior. A common culprit is that the fixture introduces a different ground reference or a longer return path, so return currents that are harmless on the bench create a ground offset that violates a logic threshold or a reference input. Another is that the fixture's automated sequencing powers or stimulates rails in an order the firmware doesn't expect, exposing an initialization-order dependency. I'd also check whether the fixture's relay or solenoid switching injects a transient the bench never produces. The discipline is the same as any debug: reproduce reliably, then bisect the difference between "fails" and "passes" until one variable remains.

**Possible follow-ups:**
- If the fixture uses a switching supply and the bench uses a linear one, how would you determine whether supply noise or supply sequencing is the actual trigger?
- How would you decide whether the right fix is in the product or in the fixture?

## Q2: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** When a measurement is correct on an open bench but shifts once the unit is assembled and mounted, I treat it as a mechanical-to-electrical coupling problem and work through the physical changes systematically. Assembly changes several things at once: cable routing and length, connector seating, board flex and mounting torque, proximity to metal chassis or mounting hardware, and the thermal environment. I'd first confirm the offset is stable and repeatable, then re-open the unit and see whether the offset disappears — that alone tells me it's mechanical or environmental rather than a component tolerance. From there I'd isolate: flex the board by hand or with a controlled fixture to see if strain on a specific area (often a solder joint, a connector, or a strain-sensitive package) changes the reading; re-route the sensor cable to see if coupling to a nearby conductor is responsible; and check whether the mounting position places the front-end near a magnetic or electric field source. A consistent offset rather than noise usually points to a reference or bias shift — a ground reference moving because of a changed return path, or a bridge excitation changing because of cable resistance — rather than to random interference. I'd measure the reference and excitation nodes in both states to confirm which one moved.

**Possible follow-ups:**
- How would you distinguish a genuine offset caused by board strain from one caused by a changed ground reference?
- If the offset only appears at the final mounting position and not in the enclosure alone, what would that tell you?

## Q3: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** This is a load-transient and power-distribution problem, so I'd approach it in the frequency and time domains together. First I'd characterize the ripple properly: probe at the load's supply pins with a short ground lead or a proper probe tip, not at the regulator output, because the ripple that matters is what the load actually sees. I'd capture the switching event and look at the transient response — how far the rail deviates, how fast it recovers, and whether it rings. That tells me whether the issue is insufficient bulk or decoupling capacitance, excessive equivalent series inductance in the path, a control-loop bandwidth that's too slow to respond, or a ground-return problem where the switching current shares an impedance with the sensitive load. I'd then separate the two mechanisms: is the ripple conducted from the regulator's inability to respond, or is it coupled through a shared ground or a nearby trace? A useful test is to add temporary bulk capacitance right at the load and see if the deviation shrinks — if it does, the distribution impedance is the problem; if it doesn't, the regulator's transient response or the switching loop is. I'd also check the switching subsystem's own loop area and whether its return current is forced through the sensitive ground.

**Possible follow-ups:**
- How would you tell the difference between ripple caused by the regulator's loop response and ripple coupled in from a shared ground return?
- What measurements would you take to decide whether the fix belongs in the regulator, the decoupling network, or the layout?

## Q4: A device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline. How would you approach this investigation?

**Answer:** The hard part here is that the failure is silent and the evidence is stale by the time it's noticed, so the first objective is to make the failure observable in real time rather than reconstructing it after the fact. I'd start by defining what "plausible but wrong" means physically — is it a value that could come from a stale sample, a misaligned buffer, a scaling or unit error, a byte-order swap, or a value read from the wrong channel? That classification narrows the search enormously. Then I'd add instrumentation that captures the raw data path end to end: the sensor's raw output, the value at the ADC, the value after any conversion or filtering, and the value as transmitted, all timestamped, so I can see exactly where the corruption enters. If the error is intermittent, I'd set up a long-duration capture with a trigger on the anomaly rather than trying to catch it by eye. I'd also look for correlations — does it happen after a specific event, at a particular temperature, after a certain number of samples, or when another subsystem is active? A value that is plausible but wrong often points to a data-integrity issue (a race between a read and an update, a buffer that isn't double-buffered, or a conversion applied twice) rather than a sensor fault, so I'd pay close attention to concurrency and to any shared state between the acquisition path and the reporting path.

**Possible follow-ups:**
- How would you design the instrumentation so it doesn't itself perturb the timing you're trying to observe?
- If the anomaly only appears in field data and never on the bench, how would you make it reproducible?

## Q5: You're leading a failure investigation and you've reached a point where two plausible root causes remain, both supported by partial evidence, and the team is split on which to pursue. How would you handle this and drive the investigation to a conclusion?

**Answer:** When two hypotheses both fit the partial evidence, the goal isn't to argue them down but to design a test that discriminates between them — ideally one where the two hypotheses predict different, observable outcomes. I'd start by writing down, for each hypothesis, what it predicts that the other does not: a specific measurement, a specific condition under which the failure should or shouldn't occur, or a specific part of the system that should be implicated. Then I'd look for the cheapest, fastest test that separates them, and if no single test does, I'd sequence tests so each one eliminates at least one branch. I'd also be explicit with the team that we're not voting on the answer — we're letting the evidence decide — which lowers the temperature and keeps people contributing. If the two causes could both be real and interacting, I'd say so and test whether fixing one changes the other's signature. Throughout, I'd keep a written record of what each test showed and what it ruled out, so the conclusion is traceable and defensible, and I'd set a checkpoint: if the discriminating test is inconclusive, we escalate to a more direct method (fault injection, a controlled teardown, or a targeted experiment) rather than continuing to debate.

**Possible follow-ups:**
- How would you handle it if the discriminating test is expensive or would take weeks, and the schedule is tight?
- How would you keep a senior team member who strongly favors one hypothesis engaged rather than defensive?
