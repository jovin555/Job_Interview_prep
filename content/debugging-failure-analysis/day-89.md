# debugging-failure-analysis — Day 89

## Q1: How would you approach a failure investigation where a device's analog front-end is accurate on the bench with a test harness, but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** The key insight is that the offset appears only after two changes happen together — enclosure assembly and final mounting — so I'd treat those as the variables to isolate rather than re-testing the electronics, which already pass on the bench. First I'd reproduce the condition deliberately: measure the front-end output with the board on the bench, then with the enclosure fitted but the unit still on the bench, then with the unit in its final mounting position. That three-step progression tells me whether the offset is driven by the enclosure (mechanical stress, grounding, shielding, cable routing) or by the installation (mounting torque, chassis grounding, proximity to a metal surface, changed thermal environment).

A consistent offset rather than noise points toward a DC-level mechanism: mechanical stress on a sensor or on a flex, a changed ground reference, a shield or chassis connection that shifts the reference potential, or a thermal gradient that appears once the unit is enclosed and self-heating is trapped. I'd measure the actual reference node and the amplifier's input common-mode at each stage, not just the output, so I can see where the shift is introduced. I'd also check whether the offset is stable and repeatable or drifts with warm-up — that distinguishes a mechanical/grounding cause from a thermal one. Once I've localized the stage, I'd confirm by controlled intervention: re-seat the enclosure, change mounting torque, temporarily bond or lift a ground point, and see which change makes the offset appear or disappear. Only then would I decide whether the fix is a design change (grounding scheme, strain relief, thermal path) or a build/installation control.

**Possible follow-ups:**
- If the offset tracks mounting torque, how would you separate a mechanical stress effect on the sensor from a grounding effect through the chassis?
- How would you verify the fix across units rather than just the one you debugged?

## Q2: You're debugging a power rail that shows excessive ripple only when a high-current subsystem is switching, but the ripple is within specification when that subsystem is idle. How would you approach this?

**Answer:** This is a load-transient and power-distribution problem, so I'd start by characterizing it properly rather than trusting a single ripple number. I'd measure at the point of load — right at the decoupling capacitors of the affected device — not at the regulator output, because the ripple that matters is what the load actually sees. I'd use a short-ground-tip probe or a coaxial connection to avoid picking up radiated switching noise in the probe loop, and I'd trigger the scope on the subsystem's switching event so I can see the transient response synchronized to the load step.

Then I'd separate the mechanisms. Is the ripple the regulator's transient response (loop bandwidth too slow, insufficient output capacitance, ESR too high)? Is it ground bounce from the high-current return path sharing impedance with the sensitive rail? Is it conducted or radiated coupling from the switching subsystem into the rail? I'd check the return path first — where does the high current actually flow, and does the sensitive load's ground reference sit on that path? I'd also look at the input side of the regulator: a load step can pull the input down and modulate the output through the regulator's own supply. Comparing ripple at the regulator output, at the load, and across the ground plane between them usually localizes it. The fix depends on the mechanism — more bulk or better-placed decoupling, a layout change to separate return currents, a snubber or ferrite, or slowing the switching edge — so I'd confirm the mechanism before changing anything.

**Possible follow-ups:**
- How would you tell the difference between insufficient decoupling and a shared-impedance ground return?
- What would you check first if adding capacitance made the ripple worse rather than better?

## Q3: A device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline. How would you approach this investigation?

**Answer:** The hard part here is that nothing in the system flags the error, so the investigation has to start with making the failure observable. I'd first define what "wrong" means precisely — is it a fixed offset, a scaling error, a stale value, a bit flip, or a value from the wrong channel or wrong timestamp? The pattern in the offline data is the strongest clue, so I'd mine it: does the error correlate with a particular operating mode, a temperature, a time since power-on, a specific unit, or a particular sequence of events? That correlation narrows the suspect stage before I touch hardware.

Then I'd instrument the path end to end. The value travels from the sensor through the analog front-end, the ADC, the firmware acquisition, the storage/transmission buffer, and out. I'd add a way to capture the raw ADC counts alongside the processed value and a timestamp, so I can tell whether the corruption happens before the ADC (analog), at the conversion (timing, reference, settling), or in firmware (buffer handling, type conversion, shared-variable race, DMA vs CPU access). A plausible-but-wrong value often points to a data-handling bug — a race between an ISR and main-loop read, a stale buffer, a scaling constant applied twice, or a DMA transfer that completes after the value is read. I'd try to reproduce it under accelerated conditions (stress the timing, sweep temperature, run the acquisition at the edge of its timing budget) and use fault injection to confirm the mechanism. The corrective action has to include a self-check that would have caught it — a plausibility or cross-check in firmware — so the same class of error can't pass silently again.

**Possible follow-ups:**
- How would you distinguish a firmware data-handling bug from an ADC settling or reference issue using only the captured raw counts?
- What kind of runtime self-check would you add so a plausible-but-wrong value gets flagged in the field?

## Q4: You're leading a failure investigation and you've reached a point where two plausible root causes remain, both supported by partial evidence, and the team is split on which to pursue. How would you handle this and drive the investigation to a conclusion?

**Answer:** When two hypotheses both have partial support, the trap is letting the team argue about which is more likely instead of designing a test that separates them. My first move is to reframe the question: what observation would be true under one hypothesis and false under the other? If I can define that discriminating test, the disagreement resolves on evidence rather than opinion. I'd write both hypotheses down explicitly with their predicted signatures, then look for the cheapest, fastest experiment that distinguishes them — sometimes that's a targeted measurement, sometimes a controlled perturbation, sometimes going back to the field-return data with a specific question in mind.

I'd also make sure we're not treating them as mutually exclusive when they might be a chain — one cause triggering the other. I'd assign owners and a time box to each line of inquiry so the split doesn't stall progress, and I'd keep the team aligned on the decision criteria up front so the outcome isn't contested after the fact. If the discriminating test is inconclusive, I'd escalate to a more definitive method — fault injection, a teardown, or a designed experiment varying one factor at a time — rather than picking the more popular hypothesis. Throughout, I'd document the reasoning and the evidence for both paths, because in a regulated medical-device context the investigation record has to show why the conclusion was reached, not just what it was. The goal is a defensible root cause backed by a test that could have failed, not a consensus.

**Possible follow-ups:**
- How would you handle it if the discriminating test is expensive or would take weeks, and the schedule is pressing?
- What would you do if, after the test, the evidence still doesn't cleanly favor one hypothesis?

## Q5: A junior engineer has been debugging an intermittent failure for several days without progress — they've been testing components in isolation and everything passes, but the system-level failure persists. They're frustrated and the schedule is tight. How would you approach this?

**Answer:** The pattern here — components pass in isolation, the system fails — usually means the bug lives in an interaction or a condition that isolation testing removes, so the first thing I'd do is help the engineer step back from the component-by-component approach and reframe around reproduction and observation. I'd sit down with them, not to take over, but to ask what they've established and what they've assumed. Often the real gap is that they haven't found a reliable way to reproduce the failure, so every test is a coin flip and progress feels random. I'd work with them on making the failure reproducible or at least observable — better instrumentation, logging, triggering on the symptom — because a reproducible failure is debuggable and an unreproducible one isn't.

Then I'd help them build a hypothesis tree and a bisection strategy: instead of testing parts, change one system-level variable at a time (power source, load, timing, temperature, cable, firmware build) and see which one moves the failure rate. I'd also watch for the common traps — changing several things at once, trusting a passing test as proof of correctness, or assuming the failure is where the symptom appears rather than upstream. On the human side, frustration is real and it degrades debugging judgment, so I'd acknowledge the effort, give them a concrete next step rather than a vague "keep at it," and pair with them for a session so they're not alone in it. The schedule pressure is a reason to be more systematic, not less — random testing under time pressure is how days get lost. My aim is to leave them with a method they can reuse, not just a fix for this one bug.

**Possible follow-ups:**
- How would you decide when to step in and debug it yourself versus continuing to coach them?
- What would you do if the failure genuinely can't be reproduced on the bench and only shows up in the field?
