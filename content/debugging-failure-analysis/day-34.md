# debugging-failure-analysis — Day 34

## Q1: How would you approach a failure investigation where a medical device's firmware and hardware teams disagree on whether an intermittent communication failure is caused by a marginal pull-up resistor value on an I2C bus or by a firmware timing issue in the bus recovery routine?

**Answer:** The first step is to reframe this from a hardware-versus-software debate into a shared investigation with objective data collection. I'd start by defining what we actually know: the failure mode, the conditions under which it occurs, and what the bus looks like at the moment of failure. I'd want to capture the bus signals during an actual failure event — using a logic analyzer or oscilloscope with deep memory — to see whether the failure manifests as a stuck-low condition, corrupted data, or a missing clock edge. That single measurement often resolves the debate: if the bus is stuck low with the master releasing SCL, that points to a slave holding the line or a pull-up strength issue; if the clock is present but data is corrupted, that suggests a timing or protocol handling problem. In parallel, I'd review the firmware's bus recovery routine against the I2C specification — specifically whether it generates the required nine clock pulses with the bus released, and whether the timing matches the slave's requirements. I'd also check the actual pull-up values against the total bus capacitance and the slave's minimum rise-time requirements, accounting for temperature and voltage extremes. The key is to avoid implementing a fix until we have a confirmed mechanism. If the evidence is genuinely ambiguous, I'd design a controlled experiment: temporarily strengthen the pull-ups on a test unit while keeping the firmware unchanged, and separately modify the recovery routine while keeping the hardware unchanged, then compare failure rates under accelerated testing. This isolates the variables and gives both teams objective data.

**Possible follow-ups:** How would you determine the actual bus capacitance to verify the pull-up calculation? What if the failure only occurs once every several days — how would you accelerate the testing?

## Q2: How would you approach debugging a medical device where a specific analog input channel reads correctly when measured directly at the ADC input with an oscilloscope, but the firmware consistently reports a value that is offset by a fixed amount — and the offset is different on different units of the same device?

**Answer:** This is a classic case where the measurement point and the measurement method matter. If the oscilloscope probe at the ADC pin shows the correct voltage but the firmware reports an offset, I'd first question whether the scope reading is actually representative. A high-impedance scope probe can load the node differently than the ADC's sample-and-hold circuit, especially if the source impedance is high. I'd check the source impedance driving the ADC input — if there's a high-value series resistor or a filter network, the ADC's sampling capacitor can cause a voltage drop during acquisition that the scope doesn't see. The fact that the offset varies between units suggests a component tolerance issue — perhaps the series resistance or the ADC's internal sampling capacitance varies. I'd also verify the ADC reference voltage on each unit, since a reference tolerance would produce a gain error that manifests as a fixed offset at a given input level. I'd measure the actual reference voltage on the failing units and compare it to the expected value. Another angle: check whether the firmware is configuring the ADC correctly — wrong channel selection, incorrect sampling time, or a mismatch between the ADC resolution and the firmware's scaling factor. I'd also look at the PCB layout around the ADC input for leakage paths or guard ring issues that could vary with board fabrication. The systematic approach is to measure the actual voltage at the ADC input pin during acquisition, not just with a static probe, and to compare the ADC's raw conversion result against a known reference voltage injected at the input connector.

**Possible follow-ups:** How would you determine whether the issue is a sampling time problem versus a reference voltage problem? What test fixtures would you build to characterize this across multiple units?

## Q3: You're leading a failure investigation where a medical device's firmware occasionally enters a hard fault handler, and the stack trace consistently points to a memory copy operation — but the source and destination addresses are always valid, and the memory being copied is within bounds. How would you approach this?

**Answer:** When the stack trace points to a memory copy but the addresses and lengths are valid, the fault is likely not in the copy logic itself but in something the copy operation triggers — or in the state of the system at the time of the copy. I'd start by examining what the memory copy is actually accessing: is it copying from or to memory-mapped peripheral registers, or is it copying between RAM regions? If it's a peripheral register access, the fault could be a bus error caused by the peripheral being clocked down or in reset. If it's a RAM-to-RAM copy, I'd look at whether the memory regions are properly initialized and whether there's a DMA controller involved that could be conflicting with the CPU's access. I'd also check the alignment of the source and destination addresses — an unaligned access on a Cortex-M processor can cause a hard fault depending on the configuration. Another important angle: the stack trace might be misleading if the stack has been corrupted. I'd examine the stack contents around the fault to see if the return address and frame are actually consistent with the reported function. I'd also check whether the memory copy is happening in an interrupt context or a task context — if it's in an interrupt, a priority inversion or a nested interrupt could be corrupting state. I'd enable the fault status registers to capture the exact fault type (bus fault, usage fault, or mem manage fault) and the address that caused the fault. That information narrows the investigation significantly. I'd also review whether the memory copy function is being called with a length that's calculated at runtime — even if the current values are valid, a race condition could cause a different length to be passed under specific timing conditions.

**Possible follow-ups:** How would you use the fault status registers to distinguish between a bus fault and a usage fault? What if the fault only occurs when a specific peripheral interrupt fires during the copy?

## Q4: How would you approach a failure investigation where a medical device's battery charging circuit draws excessive current from the wall adapter only when the device is connected to a specific model of USB charger, but charges normally with the charger that ships with the device?

**Answer:** This points to a compatibility issue between the device's charging circuit and the specific charger's electrical characteristics. I'd start by characterizing both chargers — measuring their output voltage under load, their current capability, and their transient response. The key parameters to compare are the no-load voltage, the voltage drop under load, and any negotiation protocol behavior. Many USB chargers use different methods to indicate their current capability — resistor dividers on the data lines, or more complex protocols like USB BC 1.2 or USB-PD. If the device's charging circuit is misinterpreting the charger's capability advertisement, it could be drawing more current than the charger can supply, causing the charger's output to sag and the device to compensate by drawing even more current. I'd measure the actual current draw with each charger and look at the voltage waveforms during charging. Another possibility is that the specific charger has a different ground reference or leakage path that causes a ground loop through the device. I'd also check whether the charger's output has excessive ripple or noise that could confuse the charging IC's current sense circuitry. The investigation would involve measuring the charger's output impedance, the device's input current profile during charging, and the behavior of the charging IC's control loop. I'd also test with a range of chargers to understand whether this is a single-charger anomaly or a broader compatibility issue. The fix might involve adjusting the charging IC's input current limit setting, adding input protection circuitry, or implementing a more robust charger detection method in firmware.

**Possible follow-ups:** How would you determine whether the issue is the charger's current capability advertisement versus a ground loop problem? What changes would you consider to the charging circuit to improve compatibility?

## Q5: How would you handle a situation where you're leading a failure investigation, and a junior engineer on your team has been debugging an issue for several days without progress — they've been testing components in isolation and everything passes, but the system-level failure persists. The engineer is becoming frustrated, and the project schedule is tight. How would you approach this?

**Answer:** The first thing I'd do is acknowledge the engineer's effort and the difficulty of the problem — frustration is natural when you've been working hard without results, and it's important to separate the person from the problem. Then I'd shift the approach from component-level testing to system-level analysis. The fact that components pass in isolation but the system fails suggests the issue is in the interaction between components — power sequencing, signal integrity, timing, or resource contention. I'd ask the engineer to walk me through their debugging process so far, not to critique it, but to understand what they've already ruled out and where the gaps might be. I'd then suggest a different strategy: instead of testing components individually, we should reproduce the failure at the system level and observe it with the right tools — a logic analyzer, oscilloscope, or protocol analyzer — to see what's actually happening at the interfaces between components. I'd also suggest they consider what's different between the isolated test environment and the full system: different power supply, different ground plane, different firmware configuration, or additional loads on shared buses. I'd offer to pair with them for a debugging session — sometimes a fresh perspective helps, and it also gives me direct visibility into the problem. I'd also make sure they're taking breaks and not falling into the trap of making random changes without a hypothesis. The goal is to redirect their energy from isolated testing to system-level observation, and to provide support without taking over the investigation entirely.

**Possible follow-ups:** How would you balance giving the engineer ownership of the investigation with the need to make progress on the schedule? What specific questions would you ask to understand what they've already tried?
