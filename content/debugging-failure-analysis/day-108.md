# debugging-failure-analysis — Day 108

## Q1: How would you approach a failure investigation where a device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and it's only caught later when the data is reviewed offline?

**Answer:** The defining difficulty here is that nothing in the system considers this a failure, so there's no fault flag to chase. I'd start by treating it as a data-integrity problem and building a way to catch it in the act rather than waiting for offline review. First, I'd characterize the error from the offline data: is the wrong value a single-bit flip, a stale sample (previous reading repeated), a scaling/offset error, or a plausible-but-shifted value consistent with a wrong channel or a partially completed conversion? That classification narrows the suspect list enormously — a bit flip points at memory or bus integrity, a stale sample points at a handshake or buffer-management bug, a scaling error points at calibration or fixed-point handling.

Next I'd instrument the path: log the raw ADC/conversion result, the value after any filtering or scaling, and the value at the point of transmission, all with a common timestamp and sequence number. If the corruption appears between two of those stages, I've localized it. If the raw value is already wrong, I'd look at the acquisition side — conversion timing, reference stability, channel multiplexing settling time, and whether the read can race with a conversion. If the raw value is right but the stored/transmitted value is wrong, I'd suspect buffer aliasing, a shared variable written from an ISR without proper protection, or a DMA/ring-buffer indexing bug.

I'd also try to make it reproducible: run at temperature extremes, vary supply, exercise concurrent tasks, and stress the bus, because "plausible but wrong" often correlates with a marginal timing or concurrency window. Throughout, I'd keep a written hypothesis log and change one variable at a time so I don't lose the thread.

**Possible follow-ups:** How would you distinguish a single-bit flip caused by a bus integrity problem from one caused by a software race on a shared buffer? What would you add to the production test or field diagnostics to catch this class of error earlier?

## Q2: How would you approach a failure investigation where a device's power rail collapses only during a specific operating mode, but the regulator and its passives all measure within specification when the board is powered in isolation?

**Answer:** This is a classic case where component-level "passes" tells you almost nothing, because the failure is a system interaction, not a component defect. I'd reframe the question from "is the regulator good?" to "what is different about the load, the source, or the environment in that operating mode?" The regulator measuring fine in isolation means the fault is in how it's being driven or loaded during that mode.

First I'd capture the rail behavior in situ during the failing mode with a scope, probing at the regulator output and at the load's decoupling, using a short ground lead to avoid measurement artifacts. I'd look at whether the collapse is a slow droop (suggesting sustained overcurrent or a current-limit foldback), a fast transient (suggesting a load step the loop can't respond to), or a hard drop (suggesting a protection trip, enable glitch, or a thermal/OCP event). Each shape points somewhere different.

Then I'd examine the specific mode: what turns on, what current it draws, whether there's an inrush or a sequencing issue, whether the mode changes the regulator's feedback or enable path, and whether the mode introduces a transient the output capacitance can't absorb. I'd also check the input side — a collapsing input rail, a shared supply being loaded by another subsystem, or a ground-return path that shifts under the mode's current. And I'd verify the regulator's stability margin under the actual load, since a part that's stable on the bench can oscillate with a different load impedance. The key discipline is to reproduce the failure with the real load and real sequencing, then bisect which element of the mode triggers it.

**Possible follow-ups:** How would you tell a load-transient problem apart from a protection-trip problem from the scope signature alone? If the collapse only happens with the enclosure closed, how would that change your approach?

## Q3: How would you approach a failure investigation where a device's analog front-end is accurate at room temperature but shows a growing offset error as the device warms up during continuous operation — and the offset returns to zero after the device cools down?

**Answer:** A reversible, temperature-correlated offset is a strong signal that I'm looking at a thermal coefficient issue somewhere in the signal chain, not a permanent damage mechanism. The fact that it returns to zero on cooldown tells me the hardware isn't degraded — something's parameter is drifting with temperature and recovering.

I'd start by mapping the error against temperature rather than time: log the offset alongside board temperature at several points (ideally multiple thermocouples — at the sensor, at the amplifier, at the reference, and near any heat-dissipating component) so I can see which location's temperature best correlates with the drift. That correlation often points straight at the culprit. Then I'd work through the chain: the sensor itself (bridge or element TC), the instrumentation amplifier (offset drift, gain drift, and input bias current drift interacting with source impedance), the voltage reference (reference drift propagates directly into the measurement), and any passive components in the signal path whose TC matters — resistor matching in a differential stage is a common offender because mismatched TCs create a differential offset from a common-mode temperature change.

I'd also consider thermal gradients rather than absolute temperature: a gradient across a matched pair or between the sensor and the reference creates exactly this kind of reversible offset. I'd verify by controlled heating — a heat gun or chamber with the board instrumented — and by swapping or reflowing suspect components to see if the drift changes. If the drift is within each component's datasheet but the system error is still unacceptable, the fix may be at the architecture level: ratiometric referencing, chopping/auto-zeroing, or a temperature-compensation calibration in firmware.

**Possible follow-ups:** How would you separate a genuine sensor TC from an amplifier or reference TC when they're all on the same board? When would you solve this in hardware versus compensating in firmware?

## Q4: You're leading a cross-functional investigation where the firmware and hardware teams each believe the other side owns an intermittent communication failure, and neither has conclusive evidence. How would you structure the investigation to break the deadlock?

**Answer:** The deadlock usually isn't a technical problem so much as an evidence problem — each team is reasoning from its own domain and neither has data that can adjudicate. My job as lead is to convert the argument into a testable question and get evidence that both sides accept as neutral.

First I'd get the teams to agree on a precise, shared description of the failure: exact symptom, timing, conditions, and what "communication failure" means at the signal level. Ambiguity here is often why the two sides talk past each other. Then I'd define what evidence would distinguish the hypotheses — for example, if the hardware hypothesis is a marginal bus or timing issue, then scoping the physical lines during a failure should show it; if the firmware hypothesis is a race or recovery bug, then correlated software traces should show it. I'd design a capture that records both simultaneously: a logic analyzer or scope on the bus alongside firmware instrumentation with timestamps, so a single failure event yields both views.

I'd also set up fault injection to force the failure deterministically — deliberately marginalize the suspected hardware parameter or inject the suspected software condition — because a reproducible failure is far more persuasive than argument. And I'd keep the process blameless: frame it as "the system has a gap, let's find where the evidence points," not "who's at fault." If the evidence still splits, I'd assign each team a bounded, time-boxed experiment to prove or disprove its own hypothesis, with a shared review of results. The goal is to let data, not seniority or domain loyalty, decide.

**Possible follow-ups:** What would you do if the simultaneous capture shows the failure but neither hypothesis fully explains it? How do you keep a cross-team investigation from stalling when one side is more senior or more vocal?

## Q5: How would you approach a failure investigation where a device's firmware occasionally enters a hard fault handler, and the stack trace consistently points to a memory copy operation — but the source and destination addresses are always valid, and the memory regions being copied are within their allocated bounds?

**Answer:** When the fault lands on a memcpy but the addresses and bounds all check out, I'd treat the memcpy as the victim rather than the cause. A copy operation is often just where a latent corruption finally manifests — it's the first place the bad data or bad state gets touched. So I'd widen the investigation to "what corrupted the system state before the copy ran?"

I'd start by capturing the full fault context, not just the PC: the fault status registers (which fault — bus fault, memory management, usage fault, hard fault escalated from a configurable fault), the stacked registers, and the state of the memory being copied. The fault type is highly informative — a bus fault on a valid address can indicate a peripheral or memory region that's inaccessible at that moment, an alignment or unaligned-access issue, or a cache/MPU configuration problem, while an escalated usage fault points at something like an invalid state or stack issue. I'd check whether the copy is running from an interrupt context and whether stack depth or nesting is a factor.

Then I'd look upstream for the corruption: buffer overruns that write past a boundary into adjacent memory, a DMA transfer that runs concurrently with the copy and changes the source mid-flight, a shared buffer written by an ISR without protection, or a stack overflow that silently corrupts the frame. I'd add guard patterns around buffers and stack canaries, enable the MPU to trap out-of-bounds access, and use the fault registers plus a memory watchpoint to catch the first bad write rather than the eventual crash. The discipline is to find the earliest corruption event, not the last one.

**Possible follow-ups:** How would you use the MPU or a debug watchpoint to catch the corrupting write rather than the crashing read? What fault-status clues would make you suspect a concurrent DMA transfer versus a software overrun?
