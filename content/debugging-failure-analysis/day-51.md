# debugging-failure-analysis — Day 51

## Q1: How would you approach a failure investigation where a device's power rail collapses only during a specific operating mode, but the regulator and its passives all measure within specification when the board is powered in isolation?

**Answer:** This is a classic case of a load-dependent failure that only appears when the full system is exercising the rail, so the first principle is to reproduce the failure with the actual load present rather than testing the regulator standalone. I'd start by capturing the rail with an oscilloscope in the failing mode, using a short-ground-spring probe tip at the regulator output and at the farthest decoupling capacitor, so I can see both the source behavior and what the load actually sees. A rail that "collapses" only under a specific mode usually points to one of a few mechanisms: a transient load step that exceeds the regulator's transient response, a current limit or foldback being tripped by an inrush or surge event, a thermal or dropout condition that only occurs under sustained load, or a control-loop instability triggered by a specific load impedance. I'd measure the load transient response — how far the rail dips and how quickly it recovers — and compare that against the regulator's datasheet transient spec. I'd also profile the current draw in that mode with a current probe or a shunt, looking for a spike or a sustained increase that correlates with the collapse. If the regulator is fine in isolation, the problem is almost always in the interaction: insufficient bulk capacitance for the load step, a decoupling network with a resonance that the load excites, a feedback trace routed near a noise source, or a sequencing issue where the rail is being loaded before it has stabilized. I'd divide and conquer by progressively removing or disabling subsystems in that mode to see which one triggers the collapse, then narrow to the specific load. One change at a time, and I'd verify each hypothesis with a measurement rather than assuming.

**Possible follow-ups:**
- How would you distinguish between a regulator transient-response limitation and a control-loop instability from the scope capture alone?
- If the collapse is a current-limit trip, how would you determine whether the fix belongs in the regulator configuration or in the load's inrush behavior?

## Q2: How would you approach debugging a failure where a device's analog front-end is accurate on the bench but shows a small, consistent offset only when the enclosure is fully assembled and the unit is installed in its final mounting position?

**Answer:** A failure that appears only after final assembly and mounting strongly suggests a mechanical or environmental coupling path that doesn't exist on the open bench — something about the enclosure, the mounting, or the installation is changing the electrical environment. I'd start by reproducing the failure in the assembled state and then systematically opening up the assembly one step at a time: remove the enclosure lid, then the mounting, then any internal shielding or cable routing, measuring the offset at each step. If the offset disappears when the lid comes off, the enclosure is part of the coupling path — either it's changing a ground reference, adding capacitance to a sensitive node, or creating a thermal gradient. If it disappears when the unit is unmounted, the mounting hardware or the surface it's mounted to is the variable — a grounded metal surface can introduce a ground loop or a return path that wasn't present on the bench. I'd also check whether the offset correlates with temperature: a fully assembled unit in its final position may run warmer or cooler than an open board, and a small thermal EMF at a connector or a solder joint, or a temperature coefficient in a resistor divider, can produce a consistent offset. I'd measure the actual node voltages at the front-end input with a high-impedance probe in both states and compare, and I'd use a thermal camera or thermocouples to see if the assembled state changes the thermal profile. The key is to treat assembly and mounting as variables in the experiment, not as fixed conditions, and to isolate which one introduces the offset before theorizing about the mechanism.

**Possible follow-ups:**
- How would you determine whether the offset is a ground-reference shift versus a true differential input error?
- If the offset tracks temperature, how would you separate a thermal EMF at a connector from a component temperature coefficient?

## Q3: How would you approach a failure investigation where a device's firmware occasionally reports a sensor value that is plausible but wrong — not out of range, not flagged by any self-test, just incorrect — and the error is only caught later when the data is reviewed offline?

**Answer:** A plausible-but-wrong value is one of the harder failure classes because it defeats the usual range checks and self-tests — the system has no way to know it's wrong in real time. The first thing I'd do is establish whether the error is in the acquisition, the processing, or the reporting path. I'd add instrumentation to log the raw ADC value, the post-processing value, and the transmitted value together, so I can see exactly where the corruption is introduced. If the raw value is already wrong, the problem is in the analog front-end or the sampling timing — possibly a settling-time violation, a multiplexer channel-bleed issue, or a sampling instant that coincides with a switching event. If the raw value is correct but the processed value is wrong, it's a firmware issue — a race condition, a stale buffer, a scaling or calibration constant applied incorrectly, or a variable that's being read while it's being updated. If the processed value is correct but the transmitted value is wrong, it's a communication or memory issue. I'd also look at the timing: does the error correlate with a specific event, a specific operating mode, or a specific sequence of operations? Since the error is only caught offline, I'd build a targeted logging or fault-injection setup that can reproduce the condition and capture the full data path. I'd be careful not to assume the sensor is at fault just because the value is a sensor reading — the corruption could be anywhere downstream. The goal is to localize the error to a single stage before proposing a fix, because a fix applied to the wrong stage will mask the symptom without addressing the cause.

**Possible follow-ups:**
- How would you design a logging scheme that captures the full data path without perturbing the timing of the system you're trying to observe?
- If the error is a race condition in the processing path, how would you make it reproducible enough to confirm the fix?

## Q4: How would you approach a failure investigation where a device passes all functional tests at the module level and at the system level, but fails intermittently only after a firmware update that changed the order of peripheral initialization?

**Answer:** A failure that appears only after an initialization-order change is a strong signal that the system has a hidden dependency between peripherals — something that worked before because the old order happened to satisfy an implicit requirement, and the new order doesn't. The first step is to treat the firmware change as the primary variable: I'd confirm the failure is genuinely absent on the previous firmware by running the same test sequence on both versions, ideally with the same hardware, so I'm not chasing a hardware difference. Then I'd look at what the reordering actually changed — which peripheral is now initialized earlier or later, and what shared resources those peripherals touch. Common culprits are shared buses (I2C, SPI) where one device needs to be in a known state before another is addressed, shared GPIO pins that are multiplexed between functions, shared clock or power domains, and interrupt priorities or enable order. I'd also check for a peripheral that requires a settling time or a calibration step before it can be used, and whether the new order violates that. Since the failure is intermittent, I'd add instrumentation to log the initialization sequence and the state of each peripheral at key points, and I'd try to reproduce the failure by deliberately varying the order in a controlled way — if I can make it fail reliably by changing the order, I've confirmed the dependency. The fix is usually to make the dependency explicit rather than relying on ordering — for example, by adding a handshake or a status check before using a peripheral, rather than assuming it's ready because it was initialized earlier. I'd also review whether the reordering exposed a latent bug that was always there, because that changes the corrective action.

**Possible follow-ups:**
- How would you make an implicit initialization dependency explicit in the firmware without over-constraining the order?
- If the failure only reproduces on some units, how would you determine whether it's a timing margin issue versus a true logic dependency?

## Q5: You're leading a failure investigation and you've reached a point where two plausible root causes remain, both supported by partial evidence, and the team is split on which to pursue. How would you handle this situation and drive the investigation to a conclusion?

**Answer:** When two hypotheses remain and the evidence doesn't clearly favor one, the worst thing to do is let the team split into camps and pursue both in parallel without a plan — that burns time and often produces two half-finished investigations. I'd first make sure both hypotheses are stated clearly and falsifiably, so we agree on what evidence would confirm or rule out each one. Then I'd design a discriminating test — a single experiment or measurement whose outcome differs depending on which hypothesis is true. That's the most efficient way to break the tie: instead of trying to prove one hypothesis, find the observation that can only be explained by one of them. If no single discriminating test exists, I'd look at which hypothesis is cheaper or faster to test, and sequence the work so the cheaper test runs first, with a clear decision point: if it confirms, we act; if it rules out, we move to the other. I'd also make sure the team understands that ruling out a hypothesis is progress, not failure — it narrows the search space. Throughout, I'd keep the investigation grounded in measurements rather than opinions, and I'd document the reasoning so that if we later find the answer was the other hypothesis, we understand why the evidence pointed the way it did. If the schedule is tight, I'd be explicit about the trade-off between speed and certainty, and I'd avoid implementing a fix for a hypothesis that hasn't been confirmed unless the fix is low-risk and reversible. The goal is to converge on a defensible root cause, not to win the argument.

**Possible follow-ups:**
- How would you handle a situation where the discriminating test is expensive or slow, and the schedule doesn't allow it?
- If you implement a fix for the more likely hypothesis and the failure recurs, how would you structure the follow-up investigation so you don't lose the work already done?
