# firmware — Day 52

## Q1: How would you approach deciding whether a given piece of firmware logic belongs in an interrupt service routine versus a deferred context (thread, work queue, or bottom-half), and what criteria would drive that split?

**Answer:** The core principle is that an ISR should do the minimum work required to acknowledge the hardware and hand off data or an event to a deferred context — because ISRs run with interrupts masked (at least at their priority level), they add to interrupt latency for everything else, and they can't block on mutexes, sleep, or allocate from a general-purpose heap safely. So the decision criteria are roughly: (1) Does the hardware require an action within a hard deadline that only the ISR can meet — clearing a status flag, reading a FIFO before it overflows, latching a timestamp? That part stays in the ISR. (2) Is the remaining work unbounded in time, dependent on other resources, or able to block? That part gets deferred. (3) What is the worst-case execution time of the ISR, and does it fit within the latency budget of the highest-priority real-time task in the system?

Concretely, for something like a sensor data-ready interrupt, the ISR might just read the status register, capture a timestamp, and push a small fixed-size item into a lock-free ring buffer or post to a semaphore/message queue. The actual parsing, validation, filtering, and logging happen in a thread. For a UART, the ISR moves a byte between the peripheral and a ring buffer; framing and protocol parsing happen in a task. The trade-off is that deferring adds latency and requires a thread-safe handoff mechanism (ring buffer with atomic head/tail, Zephyr `k_msgq`, `k_fifo`, or a `k_work` item), but it keeps interrupt-off time bounded and makes the system analyzable.

A useful heuristic: if you can't state the ISR's worst-case execution time in microseconds and justify it against your latency budget, it's doing too much. Also worth remembering that on Cortex-M, an ISR at a given priority can be preempted by a higher-priority interrupt but not by a lower one, so a long ISR at a high priority effectively stalls everything below it — which is often the real problem, not the ISR itself.

**Possible follow-ups:**
- How would you measure or bound the worst-case execution time of an ISR in practice, and what tools would you use?
- If the deferred context is a low-priority thread and events arrive faster than it can process them, how would you handle the backlog without dropping data?

## Q2: You're designing a bootloader for a device that must support field updates over an unreliable link, and the device has no physical recovery mechanism (no button, no exposed debug header). How would you structure the update and recovery logic so that a failed or interrupted transfer can never leave the device unbootable?

**Answer:** The guiding principle is that the bootloader itself must be the one piece of code that is never overwritten by an update, and it must be small, simple, and independently verifiable. Everything else — application, update staging area, configuration — lives in regions the bootloader can validate and, if necessary, reject.

A workable structure: a protected bootloader region at the start of flash, a primary application slot, a secondary (staging) slot, and a small metadata region holding the state of the update (which slot is active, which is pending, a CRC/hash of each image, and a monotonically increasing version or sequence number). The update process writes the new image into the staging slot, verifies it (CRC or hash over the whole image, plus a signature if secure boot is required), and only then marks it as "pending." On the next reset, the bootloader sees the pending flag, re-verifies the staged image, and if valid, swaps or switches the active slot. If verification fails at any point — truncated transfer, corrupted block, power loss mid-write — the bootloader falls back to the last known-good image.

The critical details are: (1) the metadata write that commits the switch must be atomic or journaled, so a power loss during that write can't leave an ambiguous state; (2) the bootloader must have a bounded retry/rollback policy — if the new image fails to boot or fails a self-test within a timeout, it reverts; (3) the update protocol should be resumable or at least restartable from scratch without bricking, since an unreliable link means partial transfers are normal, not exceptional; (4) the bootloader should never erase the last known-good image until the new one is confirmed bootable. If the device truly has no recovery path, the bootloader region itself should be write-protected at the hardware level (option bytes, MPU, or a locked flash sector) so even a buggy update routine can't touch it.

**Possible follow-ups:**
- How would you design the "confirmed bootable" check so that a new image which boots but then crashes in a loop still triggers rollback?
- What would change in this design if the device also had to support secure boot with a hardware root of trust?

## Q3: How would you approach profiling and reducing RAM usage in a MicroPython application running on a microcontroller with limited RAM, and when would you decide to move a particular function down to C?

**Answer:** I'd start by measuring rather than guessing. MicroPython exposes `gc.mem_alloc()` and `gc.mem_free()`, and you can force a collection with `gc.collect()` to see the steady-state heap. The first thing to check is whether the problem is genuine exhaustion (the working set simply doesn't fit) or fragmentation (there's enough total free memory but not in contiguous-enough chunks for the next allocation). Fragmentation is common when the application creates and discards many small, differently-sized objects — strings, lists, temporary buffers — because the heap becomes a patchwork of free blocks that can't satisfy a larger request.

For reducing usage: avoid dynamic allocation in hot paths; preallocate buffers once and reuse them; prefer `bytearray` over `bytes` when you need a mutable buffer; avoid string concatenation in loops (each `+` creates a new object) and use `b"".join()` or a preallocated buffer instead; use `memoryview` to slice without copying; and consider `micropython`-specific options like frozen modules (compiled into firmware, stored in flash rather than RAM) and `__slots__` on classes to avoid per-instance dicts. If the application is doing a lot of small-object churn, restructuring to a fixed set of long-lived objects can eliminate most fragmentation.

The decision to drop to C is driven by three things: (1) timing — MicroPython's interpreter overhead and garbage collector pauses make it unsuitable for hard real-time paths, so anything with a tight deadline (a control loop, an ISR-adjacent handler, a bit-banged protocol) belongs in C; (2) memory — if a function inherently needs large or many temporary allocations, C lets you use static buffers and avoid the GC entirely; (3) correctness — if the Python-level code is fighting the GC or hitting `MemoryError` under load, that's a signal the abstraction is costing more than it's worth. The usual pattern is to keep the high-level logic, configuration, and glue in MicroPython and push the performance- or memory-critical inner loops into a C module exposed via the native module interface.

**Possible follow-ups:**
- How would you distinguish fragmentation from genuine exhaustion experimentally, without just adding more RAM?
- What are the risks of calling into C from MicroPython in terms of blocking the interpreter or interacting with the GC?

## Q4: A junior engineer has written a peripheral driver that works reliably on the bench but uses busy-wait loops to poll a status register until a peripheral is ready. They argue it's simpler and more deterministic than interrupt-driven code. How would you guide them toward a better approach without dismissing their concern about determinism?

**Answer:** I'd start by acknowledging that their instinct isn't wrong — polling *is* simpler to reason about, and in some cases it's the right choice. The problem isn't polling per se; it's *unbounded* polling in a context where it blocks other work. So the conversation should be about where the busy-wait sits in the system, not about "polling bad, interrupts good."

The first question I'd ask is: what's the worst-case time this loop can spin? If the peripheral always responds within a few microseconds and the loop is in a context where that's acceptable, it may be fine. But if the wait can be milliseconds, or if it's inside a high-priority thread or an ISR, then it's stealing time from everything else and the "determinism" argument actually cuts the other way — the rest of the system now has unpredictable latency because of this loop.

I'd walk them through the alternatives in order of increasing complexity: (1) if the wait is short and bounded, keep polling but add a timeout so a stuck peripheral doesn't hang the system forever, and make the bound explicit in a comment; (2) if the wait is longer, use a blocking API that yields — in Zephyr, `k_sem_take` with a timeout, or a driver that returns `-EAGAIN` and lets the caller retry, so the CPU can run other threads; (3) if the peripheral supports it, use an interrupt or DMA completion callback so the wait disappears entirely. The key teaching point is that "deterministic" should mean "bounded and analyzable," not "no other code runs while I wait."

I'd also point out that a busy-wait in a low-priority thread is much less harmful than one in a high-priority thread or ISR, so the fix depends on context. And I'd encourage them to add a timeout to every polling loop as a matter of habit — an infinite `while (!(reg & READY))` is a latent hang, and in a medical or safety-relevant device that's a real defect, not a style preference.

**Possible follow-ups:**
- How would you decide between a blocking API with a timeout and an asynchronous callback-based API for a given peripheral?
- If the peripheral's ready time is genuinely variable and sometimes long, how would you structure the driver so the caller isn't forced to block at all?

## Q5: How would you approach a situation where a firmware feature you own is blocked because a hardware change you depend on keeps slipping, and the schedule pressure is to ship the firmware anyway?

**Answer:** The first move is to separate what's actually blocked from what isn't. Often a hardware dependency gates only part of a feature — the final integration and validation — while a large fraction of the firmware work (protocol logic, state machines, error handling, unit tests against a simulated or mocked interface) can proceed independently. So I'd map the dependency precisely: which specific interfaces, registers, or behaviors are still in flux, and which parts of the firmware can be developed and tested against a stub, a previous revision, or a software model. That usually recovers a meaningful chunk of schedule without pretending the hardware is ready.

The second move is to make the risk visible rather than absorbing it silently. If the schedule says "ship," the honest question is: ship *what*, validated *how*? Firmware that has never run against the real hardware cannot be claimed as validated, and in a regulated context (medical, safety) that's not a schedule opinion — it's a compliance fact. So I'd bring the dependency and its consequences to the people who own the schedule, with a clear statement of what can be delivered (feature-complete against a stub, ready for integration) versus what cannot (validated against production hardware), and let them make an informed call. Escalating isn't going around anyone; it's making sure the decision is made with the real constraints on the table.

The third move is to reduce the cost of the eventual integration. If the hardware will arrive late, I'd invest in the things that make late integration cheaper: a hardware abstraction layer so the board-specific code is isolated and swappable, a test harness that can run the firmware against a simulated peripheral, and early access to whatever hardware *is* available (an early revision, a dev board with the same silicon) to shake out the parts that don't depend on the final change. I'd also push for a clear integration window and freeze point, because "we'll integrate when it's ready" without a date tends to mean the firmware absorbs all the slip.

Throughout, I'd keep the tone collaborative rather than adversarial — the hardware team is usually slipping for reasons outside their control, and the goal is a working product, not a blameless post-mortem. But I wouldn't let "the firmware can just adapt" become the default assumption, because that's how unvalidated code ends up in the field.

**Possible follow-ups:**
- How would you structure the firmware so that the eventual hardware integration is a small, well-contained change rather than a rewrite?
- If the decision is made to ship before hardware validation is complete, what would you document or flag so the risk is traceable?
