# firmware — Day 112

## Q1: How would you approach implementing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the ISR entry/exit overhead, the per-interrupt service time, and the interrupt frequency, then compute the fraction of CPU time the ISR consumes. If that fraction is unacceptable, the standard remedy is to reduce the number of interrupts serviced rather than to make each one faster. For a data-producing peripheral, the usual approach is to switch from per-sample interrupts to block-oriented transfers — configure the peripheral's FIFO or DMA to buffer a batch of samples and interrupt only when the batch is complete or the FIFO crosses a threshold. This amortizes the ISR overhead across many samples. The ISR itself should do the minimum: acknowledge the source, move the batch into a queue or ring buffer, and return. Any processing (filtering, scaling, protocol framing) is deferred to a thread or work queue so the ISR stays short and the system remains responsive. If DMA is unavailable, a FIFO threshold interrupt achieves a similar effect at coarser granularity. The trade-off to watch is latency: batching introduces a delay between sample acquisition and processing, so the batch size must be chosen so the deferred processing still meets the system's real-time deadline. I'd also verify the design under worst-case load, not just nominal, because interrupt storms often only manifest when other subsystems are also busy.

**Possible follow-ups:** How would you size the DMA buffer if the consumer thread occasionally runs long? What would you do if the peripheral's FIFO depth is too shallow to batch meaningfully?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the debugger's presence changes timing, power state, and memory layout, so the first job is to figure out which of those is masking the fault. I'd start by characterizing what "misbehaves" means precisely — a hang, a wrong value, a reset — because that narrows the suspect list. Then I'd systematically remove the debugger's side effects: run standalone but with logging over a UART or a RAM buffer that can be dumped afterward, so I get visibility without halting the CPU. Timing is the most common culprit: the debugger slows execution and adds latency, which can hide a race condition, a missing synchronization primitive, or a peripheral that needs a settling delay the code doesn't actually provide. I'd look for unsynchronized shared state, ISR/main-loop interactions, and any place where the code assumes a peripheral is ready without checking. Power is the second suspect: with a debugger attached the target may be powered from the debug probe rather than its own supply, masking brownout or regulator issues. I'd test on battery or an isolated supply. Memory layout is the third: the debugger can change where variables land, which can hide an uninitialized-variable or stack-overflow bug. I'd enable stack canaries, fill patterns, and watchdogs to catch those. The general principle is to reproduce the fault with instrumentation that doesn't perturb timing — trace buffers, GPIO toggles on a scope, or a logic analyzer — rather than relying on breakpoints.

**Possible follow-ups:** How would you use a GPIO toggle and a scope to localize a timing-sensitive fault? What would make you suspect the power supply rather than the code?

## Q3: How would you approach designing a firmware module that must survive a brownout — where the supply voltage sags briefly but doesn't fully drop — without corrupting persistent state or producing a spurious reset?

**Answer:** A brownout is dangerous because the MCU may keep executing while its supply is below the specified operating range, so behavior becomes undefined — flash writes can corrupt, and the core can execute garbage. The design has to handle it at three levels. First, detection: use the MCU's brownout detector or a comparator on the supply rail, configured to assert before the core's operating voltage is violated, and make sure the threshold accounts for the regulator's dropout and the worst-case slew rate of the sag. Second, response: the brownout handler should put the system into a safe state as fast as possible — stop flash writes, park actuators, and avoid starting any multi-step operation that can't complete. If the sag is brief, the goal may be to ride through it; if it's deep, the goal is an orderly reset rather than a corrupted one. Third, persistence: any state that must survive must be written atomically — write to a scratch area with a CRC and a commit marker, so a partially written record is detectable and discardable on the next boot. Never write persistent state in a way that assumes the write completes. On the reset side, distinguish a genuine brownout reset from a spurious one by reading the reset-cause register and logging it, so field failures can be diagnosed. I'd also validate the whole scheme by injecting controlled sags at various depths and durations on the bench, because the failure modes only show up under real supply behavior.

**Possible follow-ups:** How would you decide the brownout threshold relative to the MCU's minimum operating voltage? What would you do if the sag is long enough that the MCU resets mid-flash-write?

## Q4: How would you approach sizing thread stacks in a Zephyr RTOS application, and what would you do to verify that your sizing is actually correct rather than just "probably enough"?

**Answer:** Stack sizing is a worst-case analysis problem, not a guess. I'd start by enumerating what each thread actually does: its call depth, the largest local buffers it allocates on the stack, the deepest library call chain it can reach (including things like printf, floating-point formatting, or crypto routines that have surprisingly deep stacks), and the interrupt nesting that can occur on top of it. Zephyr gives you tools to measure rather than guess: enable stack sentinel / stack overflow detection during development, and use the high-water-mark reporting to see how close each thread actually came to its limit under realistic and stress workloads. The key is to exercise the worst-case path, not the happy path — error handlers, retry loops, and rare branches often have the deepest stacks. I'd add margin on top of the measured high-water mark, sized to the consequence of overflow: a medical device thread that can corrupt memory needs more headroom than a cosmetic one. I'd also account for the fact that measurement under one compiler/optimization level may not hold under another, so the margin should cover that variability. Finally, I'd keep the sentinel and overflow checks enabled in at least a debug build that runs in CI, so a future change that blows a stack is caught before release rather than in the field.

**Possible follow-ups:** What's the risk of relying only on high-water-mark measurement? How would you handle a thread whose worst-case path is hard to exercise in testing?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd reframe the disagreement from "which is better" to "which meets the requirements with acceptable risk," because both engineers are right about different things. The first step is to make the requirements explicit: what's the maximum acceptable latency for a message, what's the worst-case CPU budget, what's the message rate and burst behavior, and what happens if a message is missed. With those numbers on the table, the debate becomes testable. Polling's real advantage is determinism and simplicity — no ISR/main-loop interaction, no concurrency hazards, easier to reason about worst-case timing — but it costs CPU when idle and can miss events if the poll interval is too coarse. Interrupts win on responsiveness and CPU efficiency but introduce concurrency, latency jitter from other ISRs, and the need for careful synchronization. I'd ask each engineer to sketch the design and estimate worst-case latency and CPU load for the actual message profile, then compare against the requirements. Often the answer is a hybrid: interrupt-driven reception into a buffer, with the protocol state machine processed in a thread or work queue, which gets responsiveness without putting parsing in the ISR. I'd also weigh maintainability and the team's collective experience, since a design the team can't debug confidently is a liability. The decision should be documented with the reasoning, so it's revisitable if requirements change. The goal is to make the team own the decision rather than have me impose one.

**Possible follow-ups:** How would you structure the comparison so it's evidence-based rather than opinion? What would you do if the requirements genuinely don't favor either approach clearly?
