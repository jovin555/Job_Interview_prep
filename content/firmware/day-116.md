# firmware — Day 116

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual interrupt rate, the per-ISR cost (entry/exit overhead plus register access), and the resulting CPU budget consumed. If servicing every interrupt individually is genuinely too expensive, the standard remedy is to decouple the "event" from the "work" — the ISR should do the minimum needed to acknowledge the peripheral and move data out of the way, and defer the expensive processing to a lower-priority context.

Concretely, there are a few patterns worth considering. The first is batching: if the peripheral has a FIFO or a burst mode, configure it to raise an interrupt only when a threshold is reached (or on a timeout), so one ISR services many samples. The second is DMA: let the peripheral write directly into a ring buffer in memory and interrupt only on half-transfer or full-transfer events, so the CPU is involved at a fraction of the sample rate. The third is a "top half / bottom half" split — a very short ISR that timestamps or enqueues, and a work queue or thread that does the parsing, filtering, or protocol handling.

The trade-off to be explicit about is latency versus throughput. Batching and DMA reduce CPU load but add latency and require a buffer sized to absorb bursts. If the consumer can't keep up, the buffer overruns, so the design must include an overflow policy (drop oldest, drop newest, or backpressure) and a way to detect and report overruns. I'd also check that the deferred context has a priority high enough to drain the buffer before it overflows, but not so high that it starves other work. Finally, I'd verify the design under worst-case load — not just nominal — because interrupt storms often only show up when the system is busy.

**Possible follow-ups:** How would you decide the buffer depth for the DMA ring, and what would you do if the consumer occasionally stalls for longer than the buffer can absorb? How would you measure whether the deferred processing is actually keeping up in the field, without a debugger attached?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first instinct should be to treat the debugger's presence as a clue rather than an inconvenience. Attaching a debugger changes several things at once: it halts the CPU (so timing changes), it may disable or slow low-power modes, it can mask certain fault conditions, and it often changes the state of peripherals or clock configuration. So the question becomes: which of those differences is masking the bug?

I'd start by narrowing the observation method. Instead of a debugger, use non-intrusive instrumentation — a GPIO toggled at key points and captured on a scope or logic analyzer, a ring buffer in RAM that logs events and can be dumped after the fact, or a UART trace at low volume. This lets me see the sequence of events without perturbing timing the way a breakpoint does. If the bug disappears when I add logging, that itself is informative — it suggests a timing-sensitive race or a power-state issue.

Next, I'd look at the usual suspects for "works with debugger, fails standalone": uninitialized variables that happen to be zeroed by the debugger's memory initialization; a race condition whose window is widened or narrowed by halt timing; a low-power mode that the debugger prevents from being entered; a watchdog that the debugger services or disables; or a fault handler that the debugger catches before the device resets. I'd also check whether the debugger's presence changes the clock tree or disables a peripheral that the standalone build relies on.

The systematic approach is to bisect the difference: reproduce standalone with logging, then progressively remove the debugger's side effects one at a time (disable low-power modes in software, freeze the watchdog, etc.) to see which one makes the bug appear or disappear. Once I have a hypothesis, I'd try to make the failure deterministic — for example, by adding a deliberate delay or stress condition that widens the race window — so I can confirm the root cause rather than just observe that it went away.

**Possible follow-ups:** If the bug turns out to be a race condition, how would you go about proving it rather than just suspecting it? What would you do if the misbehavior only reproduces once every few hours and you can't afford to leave instrumentation running that long?

## Q3: How would you approach sizing thread stacks in a Zephyr RTOS application, and what would you do to verify that your sizing is actually correct rather than just "probably enough"?

**Answer:** Stack sizing is one of those areas where "it works in testing" is not evidence of correctness, because stack overflows often manifest as corruption elsewhere rather than an obvious crash. I'd approach it in layers.

First, establish a baseline analytically: estimate the worst-case call depth for each thread, including interrupt nesting if the thread can be preempted by ISRs that use the same stack (on many architectures, ISRs use the current thread's stack, which is a common source of surprise). Add the largest local buffers, the context-save frame, and a margin for the deepest library call (printf-style formatting is a notorious stack hog). This gives a starting number, not a final one.

Second, measure rather than guess. Zephyr provides stack usage instrumentation — `CONFIG_THREAD_ANALYZER`, `k_thread_stack_space_get()`, and the `CONFIG_INIT_STACKS` option that fills stacks with a known pattern so you can see the high-water mark. I'd run the system through its worst-case paths — not just nominal operation — and read the high-water mark for each thread. The gap between the high-water mark and the allocated size is the real safety margin.

Third, decide what margin is appropriate. For a medical device, I'd want a meaningful margin (not a few bytes) because the worst case in the field may exceed what I exercised in the lab. I'd also enable stack sentinel checking (`CONFIG_STACK_SENTINEL`) or MPU-based stack protection during development so an overflow faults immediately rather than silently corrupting memory. And I'd re-measure after any significant change to call paths, because stack usage creeps up over time.

The verification step is the key: the number isn't "correct" because it compiled and ran; it's correct because I measured the high-water mark under worst-case conditions and left a defensible margin, with a runtime check to catch the case where my worst-case assumption was wrong.

**Possible follow-ups:** How would you handle a thread whose worst-case stack usage is hard to bound because it calls into a library you don't control? What's the risk of sizing stacks too generously, and how would you balance that against safety margin?

## Q4: A junior engineer on your team has implemented a firmware module that uses a global flag to signal between an ISR and a main-loop task. The code works in testing, but you're concerned about correctness and maintainability. How would you guide them toward a better design?

**Answer:** I'd start by acknowledging that the code works and that the instinct — a simple flag to signal between contexts — is a reasonable first attempt. The goal isn't to make them feel wrong; it's to help them see why "works in testing" and "correct" aren't the same thing, and to give them a better tool.

The technical issue is that a plain global flag shared between an ISR and a thread has two problems. First, the compiler and CPU can reorder or cache accesses unless the variable is declared `volatile` (to prevent the compiler from optimizing away the read) and, more importantly, unless there's a memory barrier or proper synchronization primitive to guarantee ordering and visibility. `volatile` alone is not a synchronization mechanism — it doesn't provide atomicity or ordering guarantees across cores or against reordering. Second, a single flag can't carry information: if the ISR sets the flag twice before the task clears it, one event is lost. That's a correctness bug that may never show up in testing but will show up in the field under load.

The better design depends on what the flag is actually doing. If it's signaling "data is ready," a proper synchronization primitive is the right answer — a semaphore, an event, or a message queue in Zephyr, or a `k_sem_give`/`k_sem_take` pair. If it's a single boolean state that genuinely only needs to be set and cleared, an atomic type (`atomic_t` with `atomic_set`/`atomic_clear`) plus a clear memory-ordering story is the minimum. If events can be missed, a counting semaphore or a small queue is the correct structure because it preserves the count.

I'd walk them through the failure mode concretely — "what happens if the ISR fires twice before the task runs?" — because that's usually the moment it clicks. Then I'd pair with them on the refactor, have them write a test that exercises the double-fire case, and review the result together. The maintainability win is a bonus: a named synchronization primitive documents the intent, whereas a bare global flag requires the reader to reverse-engineer the protocol.

**Possible follow-ups:** How would you explain the difference between `volatile` and a memory barrier to someone who's only used `volatile`? If the flag is used in a context where a full semaphore feels like overkill, what's the lightest-weight correct alternative?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd resist the temptation to pick a side based on seniority or preference, and instead reframe the disagreement as a set of requirements the design has to satisfy. Both engineers are making valid points, and the right answer usually depends on specifics that neither has articulated yet.

First, I'd get the requirements on the table: what's the maximum acceptable latency for a message? What's the message rate and burst behavior? What's the CPU budget, and what else is running? Is the protocol half-duplex with tight turnaround timing, or is it tolerant of jitter? What are the consequences of a missed message — is it a retry, or a safety event? These questions usually narrow the space considerably.

Second, I'd separate the concerns. "Polling vs interrupt" is really two decisions: how the CPU learns that data is available, and how the protocol state machine advances. A hybrid is often the right answer — interrupt-driven reception into a buffer, with the protocol state machine running in a thread or work queue, and polling used only where the timing is tight and bounded. The polling engineer's concern about predictability is legitimate for hard real-time turnaround; the interrupt engineer's concern about responsiveness is legitimate for bursty or low-rate traffic where polling wastes cycles. A design that uses interrupts for the event and a deterministic state machine for the response can satisfy both.

Third, I'd make the decision empirical rather than rhetorical. Propose a small prototype or a timing analysis of both approaches against the actual requirements, and let the data decide. If the two engineers still disagree after that, I'd make the call and document the reasoning — including the conditions under which we'd revisit it — so the decision is owned by the team rather than won by one person.

Throughout, I'd keep the tone collaborative: the goal is a better design, not a verdict on who was right. Disagreements between strong engineers are usually a sign that the requirements aren't sharp enough yet, and sharpening them is the leader's job.

**Possible follow-ups:** If the prototype shows both approaches meet the requirements, how would you choose between them? How would you handle it if the engineer whose approach wasn't chosen disengages from the implementation?
