# firmware — Day 117

## Q1: How would you approach configuring the Zephyr RTOS power management subsystem for a device that must enter deep sleep between sensor reads, where the wake-up latency of the SoC is comparable to the sensor's own stabilization time — so that "wake, read, sleep" naively ends up spending more time waking than sleeping?

**Answer:** The core issue is that the total per-cycle cost is wake-latency + stabilization + acquisition + processing + sleep-entry-latency, and if the sleep interval is short relative to that overhead, deep sleep is a net loss. I'd approach it in stages.

First, quantify the budget. Measure actual wake-up latency from the SoC datasheet and, better, on hardware — the datasheet number is often a best case. Measure sensor stabilization time separately. Then compute the break-even sleep duration: below that, staying in a lighter sleep state (or running a low-power loop) is cheaper than cycling through deep sleep.

Second, decouple the two latencies. The SoC wake latency and the sensor stabilization time are independent, so if the sensor needs 50 ms to stabilize, the SoC can begin waking *before* the sample is needed and the sensor can be powered up first, then the SoC finishes waking while the sensor settles. Sequencing the power-up of the sensor ahead of the SoC wake — or using a hardware timer/GPIO to trigger sensor power independently of the CPU — overlaps the two latencies rather than serializing them.

Third, in Zephyr terms, I'd use the power management framework's device-level PM (`pm_device_action`) rather than blanket system suspend, so I can keep the sensor rail sequenced correctly and let the PM policy decide per-device whether to suspend. I'd set the residency/ latency constraints so the policy doesn't pick a state whose exit latency exceeds the remaining time budget. `pm_state_force` or a custom policy hook lets me override the default heuristic when I know the upcoming workload.

Fourth, verify empirically: instrument the actual current draw over a full cycle and confirm the average is what the model predicted. If it isn't, the model is wrong somewhere — usually an unaccounted peripheral left powered or a wake source firing more often than intended.

**Possible follow-ups:** How would you handle the case where the sensor's stabilization time varies with temperature, so a fixed wake-ahead offset is sometimes too short? What Zephyr mechanisms would you use to keep a peripheral powered across a system suspend when its state must be retained?

## Q2: You're reviewing a driver where the author has used a `union` to reinterpret a received byte buffer as a struct with multi-byte fields, relying on the struct layout matching the wire format. The code works on the current target. How would you approach this?

**Answer:** This is a portability and correctness landmine, even though it happens to work today. The problems are: struct padding and alignment are compiler- and ABI-dependent, so the in-memory layout of the struct is not guaranteed to match the packed wire format; endianness of multi-byte fields is not addressed; and type-punning through a union to read a different type than was written is, strictly, undefined behavior in C (though widely tolerated). It also silently breaks the moment someone adds a field, changes optimization level, or ports to a different core.

I'd steer toward explicit serialization/deserialization rather than memory reinterpretation. Concretely: parse the buffer field-by-field with explicit byte-order conversion (`be16toh`/`le16toh` or manual shifts), building a native-endian struct from the wire bytes. This makes the wire format explicit and independent of compiler layout. If the struct must be used directly, `__attribute__((packed))` plus static assertions on `sizeof` and `offsetof` of each field catches layout drift at compile time — but packed access can generate unaligned accesses that fault on some architectures, so that's a trade-off, not a free fix.

I'd also add a compile-time check that the struct size matches the expected wire length, and unit tests that feed known byte patterns and assert the parsed field values — including a byte pattern that would expose an endianness mistake.

The teaching point for the author: "it works on this target" is exactly the class of reasoning that produces field failures after a toolchain upgrade. The fix is cheap now and expensive later.

**Possible follow-ups:** How would you handle a wire format that includes a variable-length field in the middle of the message? What static-assertion facilities would you use in a C99 codebase versus C11?

## Q3: How would you approach designing a firmware module that must arbitrate access to a shared SPI bus between a high-priority sensor read and a lower-priority flash write, where the flash write is a long multi-byte transaction and the sensor read has a hard deadline?

**Answer:** The fundamental problem is that SPI is a single physical resource, so the two transactions cannot overlap — the question is purely about who gets the bus and for how long, and whether the long transaction can be broken up so it doesn't monopolize the bus past the sensor's deadline.

First, I'd characterize the transactions. How long is the flash write in wall-clock time at the bus clock? If it's shorter than the sensor's deadline slack, a simple mutex with priority inheritance may be sufficient — the sensor task blocks briefly, then proceeds. If the flash write is longer than the slack, no locking scheme alone saves you; the transaction itself must be chunked.

Second, chunk the long transaction. Many flash devices support page-program in bounded chunks; issuing the write as a sequence of smaller bus transactions, releasing the bus between chunks, lets the sensor read interleave. The trade-off is that chunking adds per-chunk overhead and the flash write takes longer overall — acceptable if the flash write has no hard deadline.

Third, use the RTOS primitives correctly. In Zephyr, a `k_mutex` gives priority inheritance so the high-priority sensor task isn't blocked indefinitely by a low-priority holder being preempted. But priority inheritance only helps if the holder can be preempted *between* chunks — a single long transaction holding the mutex is still a priority inversion. So the mutex protects each chunk, not the whole write.

Fourth, consider whether the sensor read can be made deadline-tolerant: if the sensor buffers its own samples, the read can be deferred slightly without data loss, which relaxes the constraint. If it can't, the deadline is real and drives the chunking requirement.

I'd document the bus-access policy explicitly — max transaction length, who may hold the bus and for how long — because this is exactly the kind of constraint that gets violated by a future contributor who doesn't know it exists.

**Possible follow-ups:** How would you detect at runtime that a bus transaction is overrunning its expected duration? What would you do if the flash device did not support chunked writes?

## Q4: A junior engineer has implemented a state machine for a device's operating modes as a large `switch` inside a single function, with transitions triggered by setting a global `next_state` variable from several different modules. It works, but you're concerned about safety and testability. How would you guide them toward a better design?

**Answer:** I'd start by naming the specific risks rather than just saying "this is bad style," because the engineer needs to see *why* it matters — especially in a medical context where an illegal transition could put the device in a state that misrepresents its condition.

The concrete problems: transitions are scattered, so no single place shows the legal state graph; a module can set `next_state` to anything, including an illegal transition, with no validation; the global is shared mutable state across modules, which makes the machine untestable in isolation and racy if any of those modules run in different threads; and the 200-line switch mixes transition logic with action logic, so neither is easy to reason about.

I'd propose a refactor in small, safe steps rather than a rewrite. First, centralize the transition table: define states and events as enums, and make a single function the only place that decides "given current state and event, what's the next state, and is it legal?" Illegal transitions get rejected and logged rather than silently applied. Second, replace the global `next_state` with an event-passing API — modules post events, they don't set state directly. Third, separate the transition decision (pure, table- or switch-driven, easily unit-tested) from the entry/exit actions (side effects). Once the decision logic is pure, you can write table-driven tests that enumerate every state/event pair and assert the outcome — including that illegal pairs are rejected.

I'd be careful about scope: if the module is fragile and untested, I'd add characterization tests around the current behavior first, so the refactor has a safety net, and do it incrementally with the engineer rather than handing down a rewrite. The goal is for them to internalize the pattern, not just accept a patch.

**Possible follow-ups:** How would you handle a transition that must be deferred until the current action completes? What would you do if two modules post conflicting events in the same tick?

## Q5: How would you approach a situation where you're asked to add a feature to a firmware module that has no tests, no documentation, and a reputation for being fragile — and the change needs to ship on a tight schedule?

**Answer:** The tension is real: the schedule says "change it fast," and the module's reputation says "change it carefully." I'd try to satisfy both by front-loading a small amount of safety work rather than either skipping it or demanding a full rewrite.

First, understand the blast radius before touching anything. Read the module, trace its callers, and identify what it actually does versus what people *think* it does — the reputation for fragility often comes from undocumented behavior that callers depend on accidentally. I'd talk to whoever has the most history with it, if they're available.

Second, build a minimal safety net targeted at the change, not the whole module. I don't need full coverage; I need characterization tests around the specific behavior my feature touches and the interfaces it crosses. Even a handful of tests that pin current behavior on the paths I'll modify turns "fragile and unknown" into "fragile but observed." If the module is hard to test in place, I'd look for a seam — a function boundary I can wrap — to test through.

Third, make the change as additive and isolated as possible. New code paths behind a flag or in a new function, rather than editing the fragile core in place, limits what can break and makes rollback trivial. If the feature genuinely requires modifying the fragile core, I'd do it in the smallest possible diff and lean on the characterization tests.

Fourth, be explicit with stakeholders about the risk and the trade-off: "I can ship this on schedule with a targeted test net and an isolated change; I cannot responsibly ship it as a blind edit to untested code." That's a schedule conversation, not a refusal — it gives them a real option.

Finally, I'd leave the module better than I found it in proportion to the time available: at minimum, document what I learned about its behavior so the next person isn't starting from zero.

**Possible follow-ups:** How would you decide how much test coverage is "enough" given a fixed schedule? What would you do if the only person with knowledge of the module had already left the company?
