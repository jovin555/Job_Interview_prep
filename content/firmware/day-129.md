# firmware — Day 129

## Q1: How would you approach implementing a state machine for a device's operational modes where the same event can arrive from multiple sources — a user interface, a communication interface, and an internal timer — and the correct transition depends on which source sent it?

**Answer:** The key insight is that the state machine should not consume raw events directly; it should consume *normalized* events that carry their source as part of the event identity. I'd structure this in three layers. First, a thin per-source adapter layer that translates each source's native signal into a common event structure — an event ID plus a source tag plus a small payload. Second, a single event queue that all sources feed into, so the state machine sees a serialized stream and doesn't need to worry about concurrency or reentrancy. Third, the state machine itself, implemented as a table or switch keyed on `(current_state, event_id, source)`. The reason source must be part of the key rather than folded into the event ID is that the same physical action — say, "start" — can mean different things depending on whether it came from a physical button, a remote command, or an internal timeout, and the transition rules differ. I'd make the transition table explicit and data-driven so it can be reviewed and tested exhaustively, and I'd add a guard/action pair per transition so side effects (enabling a peripheral, logging, arming a timer) live in one place rather than being scattered. For safety-critical modes I'd also add an explicit "rejected event" path so an illegal transition is logged and handled rather than silently ignored. Finally, I'd unit-test the table by driving synthetic events from each source and asserting the resulting state, which is far easier than trying to exercise the real UI and comms paths.

**Possible follow-ups:** How would you handle an event that arrives while a transition's action is still executing — queue it, drop it, or defer it? How would you keep the transition table from becoming unmaintainable as the number of states and sources grows?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first thing I'd do is resist the temptation to "fix" it by leaving the debugger attached. The debugger changes timing, halts the core, may disable certain low-power modes, and can mask race conditions — so the difference between attached and standalone is itself the most valuable clue. I'd start by characterizing what "misbehaves" actually means: is it a crash, a wrong value, a missed deadline, a hang? That determines which class of cause to chase. Common culprits are uninitialized variables that happen to be zero under the debugger's memory state, race conditions whose window the debugger's halts widen or narrow, timing-sensitive code that relies on a delay being "long enough," and low-power or clock-gating behavior that the debugger prevents. I'd instrument rather than halt: add GPIO toggles or a lightweight trace buffer so I can see execution order and timing without stopping the core, and use a logic analyzer or scope to correlate. I'd also check whether the debugger is masking a fault — for example, a watchdog that's being serviced by the halt, or a brownout that doesn't occur when the board is powered through the debug probe. If I suspect a race, I'd add assertions and stress the timing (vary clock, add load) to widen the window. The goal is to make the failure reproducible without the debugger, then bisect from there.

**Possible follow-ups:** What specific things does a debugger change that could mask a bug, and how would you neutralize each? How would you use a trace buffer or GPIO toggles to observe timing without perturbing it?

## Q3: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first move is to quantify the problem rather than assume it: measure the actual interrupt rate, the per-ISR cost, and the resulting CPU percentage. If servicing every interrupt truly costs too much, there are several levers, and I'd pick based on what the peripheral and SoC support. The cleanest is DMA: let the peripheral move data into a buffer without CPU involvement and interrupt only on a half-buffer or full-buffer boundary, so the ISR fires at a fraction of the sample rate. If DMA isn't available or suitable, I'd look at reducing the work per interrupt — a minimal ISR that just reads the data register into a ring buffer and defers all processing to a thread or work queue, so the ISR itself is only a few instructions. If the rate is still too high, I'd consider coalescing: if the peripheral has a FIFO or a "data available" level threshold, configure it to interrupt only when N samples have accumulated. Another option is to move to a polling or timer-driven sampling scheme if the data is periodic and the peripheral allows it — sometimes a fixed-rate timer reading a FIFO beats an interrupt per sample. The trade-off to watch is latency: batching and DMA add delay between sample and processing, which matters if there's a hard real-time consumer. I'd document the chosen trade-off explicitly and verify with measurement that CPU load dropped and latency stayed within budget.

**Possible follow-ups:** How would you decide between DMA and a FIFO-threshold interrupt for a given peripheral? What would you do if the peripheral has no FIFO and no DMA, and the interrupt rate is still too high?

## Q4: A junior engineer has written a driver that works reliably on the bench but uses a fixed `k_sleep` delay to wait for a peripheral to become ready after each command, rather than checking a status register or using an interrupt. How would you guide them?

**Answer:** I'd start by acknowledging why the approach is attractive — it's simple, it's deterministic on the bench, and it works. Then I'd walk them through why it's fragile: the delay is a guess that has to cover the worst case across temperature, voltage, and part-to-part variation, and if it's too short it fails intermittently in the field, while if it's too long it wastes time and can blow latency budgets. I'd frame it as "the delay encodes an assumption that isn't guaranteed by the datasheet." The better pattern depends on the peripheral: if it has a status/ready bit, poll it with a bounded timeout so a stuck peripheral is detected rather than hanging forever; if it has an interrupt, use it and block the calling thread on a semaphore or event with a timeout. I'd show them how to structure the wait so it's testable — a helper that waits on a condition with a timeout, returning an error on timeout — and explain that this also gives you fault detection for free. I'd be careful not to just say "don't use delays"; there are legitimate uses (power-on sequencing, some datasheet-mandated minimums), so I'd distinguish "wait for a condition" from "wait for a guaranteed minimum time." Finally, I'd pair with them on converting one instance and let them see the timeout path exercised by deliberately breaking the peripheral, so they internalize the failure mode.

**Possible follow-ups:** When is a fixed delay actually the right choice? How would you test the timeout path without physically breaking the hardware?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd resist picking a side on principle and instead reframe the disagreement around requirements and evidence. Both engineers are making valid points, and the right answer depends on the protocol's timing budget, the CPU load, and the consequences of a missed message. I'd facilitate a short structured comparison: what's the worst-case latency each approach can guarantee, what's the CPU cost of each, how does each behave under load, and how testable and debuggable is each. I'd ask each engineer to bring data rather than assertions — a quick prototype or a measurement of the actual message rate and the CPU headroom. Often the disagreement dissolves once the numbers are on the table: if the message rate is low and the CPU is busy, polling may be fine; if latency matters or the CPU has other work, interrupts win. I'd also point out that these aren't always mutually exclusive — a hybrid (interrupt to wake, then poll a FIFO) is common. The goal is a decision the team owns, not a decision I impose, so I'd make sure both engineers feel their concern was heard and captured in the decision record. I'd document the rationale and the assumptions, and set a checkpoint to revisit if the assumptions change.

**Possible follow-ups:** How would you handle it if the data still doesn't settle the disagreement? What would you put in a decision record so the choice is defensible later?
