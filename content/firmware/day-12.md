# firmware — Day 12

## Q1: How would you approach designing a firmware architecture for a device that needs to maintain a precise 1 kHz control loop while also handling slower tasks like configuration updates and data logging, without the slower tasks ever causing jitter in the control loop?

**Answer:** The fundamental principle is strict separation of time-critical and non-time-critical paths. I would structure this as a priority-based preemptive RTOS system where the control loop runs in the highest-priority task, and everything else runs at lower priorities. The control task should be the only task allowed to touch the control actuators and time-critical sensor inputs. It should communicate with lower-priority tasks only through lock-free mechanisms like a single-writer/single-reader ring buffer or a mailbox with non-blocking send/receive operations. The control task should never call blocking APIs, never perform flash writes, never wait on mutexes held by lower-priority tasks, and should avoid dynamic memory allocation entirely. For configuration updates, the lower-priority task would parse and validate the data, then publish the new parameters through a mechanism that the control task can pick up atomically — for example, a double-buffered parameter block where the control task checks a "new data available" flag at the start of each cycle and swaps pointers. For logging, the control task would write samples into a DMA-driven buffer or a ring buffer that a lower-priority task drains asynchronously. The key is to make the control task's execution time deterministic and bounded — every operation it performs must have a known worst-case execution time that fits comfortably within the 1 ms period.

**Possible follow-ups:** How would you handle a situation where a lower-priority task holds a resource that the control task needs? What if the control loop itself occasionally needs to perform a longer operation, like a sensor re-calibration?

## Q2: You're debugging a firmware issue where a device communicates with a sensor over SPI, and the sensor occasionally returns corrupted data — but only when the device is running on battery power, not when connected to a bench supply. How would you approach this?

**Answer:** This is a classic symptom that points toward a power integrity issue manifesting as a signal integrity problem, rather than a pure firmware logic bug. My first step would be to verify the hypothesis by reproducing the issue while monitoring the SPI lines with an oscilloscope or logic analyzer, paying particular attention to signal levels during the corrupted transactions. I'd look for ringing, slow rise/fall times, or voltage droop on the SPI lines or the sensor's power rail during active communication. The battery scenario suggests that the power source has higher internal impedance than the bench supply, so current spikes during SPI transitions could cause the supply voltage to sag below the sensor's minimum operating threshold. I'd check the decoupling capacitance near the sensor and the MCU's SPI pins — insufficient bypass capacitance is a common culprit. I'd also examine the SPI clock speed; if it's near the maximum rated speed, reducing it slightly might resolve marginal timing. On the firmware side, I'd add CRC or checksum validation on all sensor transactions so that corrupted data is detected and retried rather than silently accepted. I'd also verify that the SPI peripheral's configuration is correct — for example, that the clock polarity and phase match the sensor's requirements, and that the chip-select timing meets the sensor's setup and hold specifications. If the issue persists, I'd use an oscilloscope to characterize the actual signal integrity at the sensor's pins under battery power, which would tell me whether this is a board-level issue (trace impedance, grounding, decoupling) or a firmware timing issue.

**Possible follow-ups:** What if the corruption only happens at specific temperatures? How would you decide whether to fix this in hardware or firmware?

## Q3: How would you approach implementing a firmware module that must handle graceful degradation — for example, a medical monitoring device where a secondary sensor fails, and the device must continue operating with reduced functionality while clearly indicating the degraded state to the user?

**Answer:** Graceful degradation requires designing for failure modes from the start, not as an afterthought. I'd begin by defining a clear operational state model for the device — for example: fully operational, degraded (one or more non-critical functions unavailable), and critical failure (device cannot safely continue). Each state would have defined behaviors, user indications, and allowed transitions. For the sensor failure scenario, I'd implement a health-monitoring layer that periodically validates each sensor's communication, data plausibility, and calibration status. When a sensor fails, the system would transition to the degraded state, stop using that sensor's data, and clearly indicate the situation — for a medical device, this would typically mean both visual indication and an audible alarm, plus logging the event for later review. The key design decision is what happens to the data flow: the firmware should continue acquiring and processing data from the remaining healthy sensors, but the application logic must be aware that certain parameters are unavailable. I'd use a data-availability flag or a status field in the data structure so that downstream processing can adapt. For example, if the device normally displays three parameters and one is unavailable, the display would show "—" or "sensor fault" for that parameter rather than stale or incorrect data. I'd also implement automatic recovery — periodically retrying the failed sensor to see if it has recovered, with a defined retry interval to avoid excessive power consumption or bus traffic. Critically, for a medical device, the degraded mode must be designed in consultation with the risk management process — the failure modes, their likelihood, and the mitigations need to be documented and traced to requirements.

**Possible follow-ups:** How would you handle the case where the degraded mode itself affects patient safety? How would you test the degradation logic to ensure it behaves correctly under all failure scenarios?

## Q4: You're implementing a firmware module that needs to store configuration data in flash memory. The device uses a NOR flash with a limited write endurance, and the configuration may be updated frequently during development but rarely in production. How would you design the storage scheme?

**Answer:** The design needs to balance write endurance, data integrity, and atomicity of updates. I'd use a double-buffer or ping-pong scheme with two (or more) configuration slots in flash, plus a header in each slot containing a magic number, version, CRC, and a status field indicating whether the slot is valid, being written, or invalid. When updating the configuration, the firmware would write the new data to the inactive slot, verify the write by reading it back and checking the CRC, then mark the new slot as active and the old slot as invalid. This provides atomicity — if power is lost mid-write, the device boots using the last known-good slot. To handle write endurance, I'd add wear leveling by rotating through multiple slots rather than always using the same two — for example, four slots with a sequence number in each header, where the active slot is the one with the highest valid sequence number. This spreads the erase/write cycles across more flash sectors. I'd also consider whether all configuration parameters need to be stored together — if some parameters change frequently and others rarely, separating them into different regions can reduce wear on the rarely-changed data. For the development-versus-production concern, I'd add a mechanism to reduce write frequency in production — for example, only writing when parameters actually change, and adding a debounce or minimum-interval requirement between writes. I'd also ensure that the flash driver handles the erase-before-write requirement correctly and that the write routine is resilient to power loss at any point in the sequence.

**Possible follow-ups:** How would you handle the case where both slots are corrupted? How would you design the boot-time validation to distinguish between "no configuration ever written" and "configuration corrupted"?

## Q5: A junior engineer on your team has implemented a firmware module that communicates with a sensor over I2C. The module works correctly in normal operation, but you notice that the engineer's error handling simply logs an error and retries indefinitely when the sensor doesn't respond. The device is a medical monitor that must continue operating even if a sensor is temporarily unavailable. How would you guide them?

**Answer:** I'd start by acknowledging that the engineer's instinct to retry is reasonable — transient I2C errors do happen, and retrying can recover from them. But an indefinite retry loop is problematic for several reasons: it can block the calling task indefinitely, it can mask a genuine hardware failure, and it doesn't provide a path for the system to continue operating in a degraded state. I'd guide them toward a structured approach: first, define a bounded retry policy — for example, a maximum number of retries with a defined delay between attempts, after which the module reports a failure to the higher-level application. Second, the error handling should distinguish between transient errors (e.g., a NACK due to bus contention) and persistent failures (e.g., the sensor not responding at all). For transient errors, a few immediate retries make sense. For persistent failures, the module should report the failure and let the application decide what to do — for example, enter a degraded mode, alert the user, or schedule a periodic re-initialization attempt. Third, the retry logic should be non-blocking or use a timeout so that the calling task isn't stuck indefinitely — in an RTOS context, this might mean using a semaphore with a timeout or a state machine that retries in the background. I'd also emphasize that for a medical device, the error handling behavior needs to be documented and traced to requirements — the system must know what to do when a sensor fails, and that behavior should be intentional, not an accident of an infinite loop. Finally, I'd suggest adding diagnostics — logging the error type, the number of retries, and the eventual outcome — so that field failures can be analyzed and the retry policy can be tuned based on real data.

**Possible follow-ups:** How would you decide on the right number of retries and the delay between them? What if the sensor failure is intermittent — how would you distinguish between a flaky connection and a sensor that needs to be replaced?
