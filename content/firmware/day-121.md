# firmware — Day 121

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual interrupt rate, the per-ISR cost (entry/exit overhead plus register access), and the resulting CPU utilization. If servicing every interrupt would consume, say, 40% of the CPU, the goal is to amortize that cost rather than eliminate the work.

The standard techniques, roughly in order of preference:

1. **Move the data, not the interrupts, with DMA.** If the peripheral supports it, configure DMA to transfer samples into a ring buffer and have the peripheral assert an interrupt only on a half-transfer or full-transfer boundary. The CPU then services one interrupt per N samples instead of N interrupts, and the per-sample cost collapses to a memory write the DMA engine performs autonomously. This is usually the cleanest answer when the peripheral and DMA controller support it.

2. **Coalesce in the ISR.** If DMA isn't available, keep the ISR minimal — read the data register, push into a ring buffer, increment a counter — and only signal a thread or work item when a threshold number of samples has accumulated or a watermark is crossed. The ISR does the minimum hardware interaction; the expensive processing happens in deferred context.

3. **Reduce the interrupt rate at the source.** Many peripherals let you configure a FIFO watermark or an interrupt-on-threshold rather than interrupt-per-sample. Setting the watermark as high as the latency budget allows directly cuts the interrupt rate.

4. **Batch processing in a thread.** Have a consumer thread drain the ring buffer in bursts rather than waking per sample. This also improves cache behavior and lets the scheduler batch the work.

The key trade-off is latency versus overhead: coalescing adds a bounded delay between the event and its processing, so you must confirm that delay fits the system's real-time requirements. For a control loop with a hard deadline, you size the watermark so the worst-case latency (watermark × sample period + scheduling jitter) still meets the deadline. For logging or telemetry, you can be far more aggressive.

I'd also instrument the result: measure CPU utilization before and after, and verify the ring buffer never overflows under worst-case load. The design isn't done until you've shown the headroom.

**Possible follow-ups:**
- How would you size the ring buffer and the watermark if the consumer thread's scheduling latency is variable?
- What happens if the DMA half-transfer interrupt and the consumer thread's processing overlap — how do you prevent the consumer from reading a partially written buffer?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first principle is to resist the temptation to "fix" it by changing timing blindly. The debugger changes several things simultaneously: it halts the CPU (altering timing), it may disable or slow low-power modes, it can mask certain faults, and it changes the memory and peripheral access patterns. So the first job is to figure out *which* of those differences is masking the bug.

My approach:

1. **Characterize the failure precisely.** What exactly misbehaves — a wrong value, a missed deadline, a reset, a hang? When does it happen — after a fixed time, under load, at a particular temperature? Reproducibility is the foundation; if it's intermittent, I'd add non-intrusive instrumentation (a GPIO toggle, a ring-buffer log in RAM, a spare UART) to capture state without halting the CPU.

2. **Test the timing hypothesis first.** If the bug disappears when the CPU is slowed by the debugger, it's likely a race condition or a timing violation. I'd try to reproduce it standalone by deliberately perturbing timing: adding small delays in suspect paths, changing compiler optimization levels, running at different clock speeds. If a delay makes it appear or disappear, that narrows the race.

3. **Check the debugger's side effects.** Debuggers often keep the core clock running, disable sleep, or hold certain peripherals out of reset. If the device misbehaves only in low-power modes, the debugger may be preventing the very state that triggers the bug. I'd test with the debugger attached but the device actually entering its normal power states, or use a debugger that supports low-power debugging.

4. **Look for uninitialized state and memory.** The debugger can zero or preserve memory differently. Running standalone from a cold boot versus a warm reset can expose uninitialized variables, missing peripheral initialization, or reliance on power-on defaults. I'd compare behavior across cold boot, warm reset, and debugger-attached runs.

5. **Check for debugger-masked faults.** Some faults (e.g., certain bus errors, watchdog resets) may be caught or delayed by the debugger. I'd enable fault logging and a persistent crash record so the standalone failure leaves evidence.

The disciplined version of this is bisection: change one variable at a time (clock speed, optimization level, sleep enable, debugger attach) and see which one flips the behavior. That converts a vague "it works with the debugger" into a specific root cause.

**Possible follow-ups:**
- How would you capture evidence of a crash on a device with no debugger attached and limited persistent storage?
- If the bug only appears at cold boot, what classes of firmware defects would you suspect first?

## Q3: How would you approach deciding whether a piece of firmware logic belongs in an interrupt service routine versus a deferred context such as a work queue or a thread?

**Answer:** The decision comes down to a few concrete criteria, and I'd apply them in order.

**First, what is the hard deadline?** If the logic must complete within a few microseconds of the event — reading a data register before the next sample overwrites it, acknowledging a hardware condition before it re-triggers, capturing a timestamp with minimal jitter — it belongs in the ISR. Anything with a deadline measured in milliseconds can almost always be deferred.

**Second, how long does the work take?** ISRs should be short: read the hardware, clear the flag, push data to a buffer, signal a consumer. If the work involves loops over many bytes, floating-point math, flash access, blocking calls, or anything that scales with data size, it belongs in deferred context. A useful rule of thumb is that an ISR should be measured in microseconds, not tens of microseconds, unless you've proven the latency budget allows more.

**Third, what can it safely call?** ISRs run in a restricted context: they can't block, can't take mutexes, can't sleep, and can only use ISR-safe kernel APIs. If the logic needs to allocate memory, wait on a semaphore, or call into a driver that might block, it must be deferred. This alone rules out a lot of candidate work.

**Fourth, what's the priority relationship?** Deferring to a thread lets you assign a priority and let the scheduler arbitrate against other work. If the logic must preempt everything else immediately, an ISR (or a high-priority thread woken by the ISR) is appropriate. If it can tolerate being scheduled alongside other tasks, a work queue or lower-priority thread is fine.

**Fifth, what's the cost of the deferral mechanism itself?** Waking a thread or queuing a work item has overhead. For very high event rates, the deferral cost can exceed the work itself, which pushes you toward coalescing (see the high-interrupt-rate question) rather than per-event deferral.

The pattern I'd default to: ISR does the minimum hardware interaction and signals; a thread or work queue does the processing. Then I'd only move logic *into* the ISR if measurement shows the deferral latency violates a real deadline. The burden of proof is on putting work in the ISR, not on keeping it out.

**Possible follow-ups:**
- How would you decide between a work queue and a dedicated thread for the deferred processing?
- What would you do if the deferred processing occasionally needs to run at a priority higher than any thread in the system?

## Q4: A junior engineer has implemented a circular buffer shared between an ISR that writes samples and a task that reads them. It works in testing, but you notice the writer doesn't check for a full buffer and simply overwrites the oldest data. How would you guide them?

**Answer:** I'd start by making sure we agree on what the buffer is *for*, because "overwrite oldest" is a legitimate policy in some systems and a serious defect in others. For a telemetry stream where the latest data matters most, overwriting oldest is a reasonable design choice — but it must be a *deliberate, documented* choice, not an accident. For a medical monitor where every sample must be accounted for, silently dropping data is unacceptable. So the first conversation is about requirements, not code.

Assuming the policy needs to change, I'd walk through the concrete problems with the current implementation:

1. **The reader can be corrupted mid-read.** If the writer overwrites the slot the reader is currently copying from, the reader gets a torn value — half old, half new. On a 32-bit MCU reading a multi-byte sample, this is a real race even if the index arithmetic is "atomic." The fix is either a lock-free scheme with proper memory ordering (single-producer/single-consumer ring with head/tail indices and acquire/release semantics, or a seqlock), or a critical section around the read, or double-buffering.

2. **The reader can't tell data was lost.** If the writer silently overwrites, the reader has no way to know its stream has gaps. At minimum, the writer should increment an overflow counter that the reader can check, so the loss is observable and can be logged or flagged.

3. **The full condition needs a defined behavior.** The writer should check `(head + 1) % size == tail` (or the equivalent count-based check) before writing. What it does when full is a policy decision: drop the new sample, overwrite the oldest (with the overflow counter), block (not possible in an ISR), or signal an error. Each has different consequences for the system.

I'd guide them toward a design where the buffer's contract is explicit: who writes, who reads, what happens when full, how loss is reported, and what synchronization guarantees the reader has. Then I'd suggest a test that deliberately overruns the buffer and verifies the reader sees the expected behavior — because "it works in testing" usually means the test never stressed the full condition.

The teaching point I'd emphasize: a shared buffer between an ISR and a thread is a concurrency contract, and the contract has to be written down and tested, not inferred from the fact that it happens to work at low load.

**Possible follow-ups:**
- How would you implement a single-producer/single-consumer ring buffer without locks, and what memory-ordering guarantees would you need?
- If the reader occasionally falls behind and the buffer overflows, how would you decide whether to drop samples or block the writer?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd treat this as a decision to be made on evidence and explicit criteria, not on seniority or preference. Both engineers are making valid points, and the right answer depends on the system's actual requirements — so my job is to structure the decision, not to pick a side.

First, I'd get the requirements on the table: what's the worst-case latency the protocol must meet? What's the message rate? What's the CPU budget? Is the protocol's timing driven by the device (we control when we poll) or by the peer (messages can arrive at any time)? Is there a hard real-time deadline, or is "responsive enough" the actual bar? These questions usually narrow the space considerably.

Then I'd frame the trade-offs explicitly:

- **Polling** gives deterministic, bounded latency *if* the poll rate is fast enough to meet the deadline, and it's simpler to reason about because there are no asynchronous preemptions. But it burns CPU even when there's nothing to do, and its latency is bounded by the poll interval — if the peer sends a message just after a poll, you wait a full interval to see it. It also scales poorly if the protocol has many states or the CPU has other work.
- **Interrupts** give low latency and free the CPU when idle, but introduce concurrency: shared state, priority interactions, and the risk of an ISR starving other work or being starved by higher-priority interrupts. The "predictability" concern is real — interrupt latency depends on what else is running and how long other ISRs disable interrupts.

The synthesis is often a hybrid: interrupt-driven reception (so incoming messages aren't missed) with a deferred processing context, and polling or timer-driven transmission where the timing is under our control. That gets responsiveness on the receive path without the complexity of interrupt-driven transmit.

To break the tie, I'd propose a small experiment: prototype both approaches on the actual hardware with the actual message load, measure worst-case latency and CPU utilization, and let the data decide. If the polling approach meets the deadline with margin, its simplicity is a real advantage. If it doesn't, the interrupt approach is justified. Either way, the team converges on evidence rather than argument.

I'd also make sure the decision is documented — the criteria, the measurements, and the rationale — so that when someone revisits it later, they understand *why*, not just *what*.

**Possible follow-ups:**
- How would you structure the prototype so the comparison is fair and the measurements are meaningful?
- If the hybrid approach is chosen, how would you divide responsibilities between the interrupt path and the polling path to avoid duplicated logic?
