## Q1: How would you approach implementing a firmware module that must handle a sensor which occasionally returns invalid data (e.g., out-of-range values or CRC failures), where the device is a medical monitor that must never display a false reading to the clinician?

**Answer:** The core principle here is that invalid data must never propagate to the clinical display, but the device must also continue operating and alert appropriately. I'd structure this in layers. First, at the driver level, I'd validate every read: check CRC or checksum where the protocol supports it, verify the data length, and confirm the sensor is in the expected operational state. Second, at the data-processing layer, I'd apply plausibility checks — is the value within the physiological range the sensor is designed to measure? Does it change at a rate consistent with the measured parameter? A sudden jump from 70 to 180 bpm in one sample might be real, but it warrants scrutiny. Third, I'd implement a validation policy: a single bad sample might be discarded and retried, but repeated failures should trigger a degraded-mode state rather than continued retries. The key design decision is what the device displays during invalid periods. The safest approach is to display "no data" or a "signal lost" indicator rather than the last valid reading, because a stale reading can be clinically misleading. I'd also log the invalid-data events with timestamps for later analysis, since frequent CRC failures might indicate a hardware issue developing. Finally, I'd ensure the module has a clearly defined interface that returns data quality status alongside the value, so higher layers never have to guess whether a reading is trustworthy.

**Possible follow-ups:** How would you distinguish between a transient sensor glitch and a persistent sensor failure in your validation logic? What would you do if the sensor returns values that pass plausibility checks but are later determined to be inaccurate?

## Q2: You're debugging a firmware issue where a device's flash write operations occasionally corrupt data in an unrelated memory region. The corruption is intermittent and only occurs when the device is under heavy load. How would you approach this?

**Answer:** Flash corruption affecting unrelated memory regions under heavy load points to a few classic root causes, and I'd investigate systematically. First, I'd check whether the corruption is in RAM or in flash — if it's RAM, the flash write itself isn't the direct cause; something else is happening concurrently. I'd start by examining the flash driver's implementation for buffer overruns or incorrect address calculations, especially if the driver uses DMA. A DMA descriptor pointing to the wrong location, or a buffer that's smaller than the programmed transfer size, could write past the intended region. Under heavy load, timing changes could expose race conditions — for example, if a buffer is being modified by another task while the DMA engine is reading it. I'd also check the linker script and memory map: is the flash write buffer placed adjacent to critical data structures? Could a stack overflow from a deeply nested call path under load be spilling into the flash buffer or the flash controller's registers? I'd look at interrupt priorities too — if a higher-priority interrupt fires during the flash write sequence and the ISR itself writes to flash or modifies shared state, that could corrupt the operation. To isolate the issue, I'd add instrumentation: log the flash operation parameters (address, length, source buffer pointer), capture the corrupted region's contents before and after, and try to correlate the corruption with specific system states. I'd also review whether the flash driver properly handles the case where the CPU cache needs invalidation or flushing around DMA operations — stale cache lines can cause subtle corruption that only appears under specific access patterns.

**Possible follow-ups:** How would you determine whether the corruption is caused by a software bug versus a hardware issue like marginal timing on the flash interface? What role would a memory protection unit (MPU) play in preventing or detecting this class of problem?

## Q3: How would you approach designing a firmware architecture for a device that must support both a hard real-time control loop (e.g., 1 kHz motor control) and a non-real-time subsystem like a wireless stack, where the wireless stack has its own timing requirements and can consume significant CPU time?

**Answer:** The fundamental requirement is that the control loop must never be delayed by the wireless stack, regardless of what the wireless stack is doing. I'd start by establishing the timing budget: measure or estimate the worst-case execution time of the control loop, including all interrupt handling it requires, and verify that the CPU has sufficient headroom even when the wireless stack is at peak activity. The architecture would separate these concerns at the task level. The control loop runs as the highest-priority task, or ideally, is driven by a timer interrupt that triggers the control calculation directly — this gives the most deterministic behavior. The wireless stack runs as a lower-priority task, and its interrupts are assigned lower priority than the control loop's timer interrupt. The critical design point is that the wireless stack must never disable interrupts for longer than the control loop's tolerance allows. Many wireless stacks have sections where they disable interrupts to protect internal state — I'd need to verify those critical sections are bounded and acceptable. If they're not, I'd need to either use a wireless stack that supports preemption better, or offload the wireless processing to a separate MCU or radio co-processor. I'd also use a message queue or shared memory with careful synchronization for data passing between the control loop and the wireless stack — the control loop writes telemetry data, and the wireless stack reads and transmits it. The control loop should never block on the wireless stack; if the queue is full, it drops the oldest data or marks it as stale rather than waiting. Finally, I'd instrument both subsystems to measure worst-case latencies and verify the architecture meets its real-time guarantees under stress testing.

**Possible follow-ups:** How would you handle the case where the wireless stack's interrupt latency requirements conflict with the control loop's timing needs? What metrics would you collect to verify that the control loop never misses its deadline?

## Q4: You're reviewing a colleague's firmware code that uses a watchdog timer that kicks in the main loop. The device occasionally resets during a lengthy calibration routine that takes 3 seconds. The colleague proposes increasing the watchdog timeout to 5 seconds. How would you guide them?

**Answer:** Increasing the timeout to 5 seconds might mask the symptom, but it doesn't address the underlying design issue — and in a medical device, it could actually reduce safety. The watchdog's purpose is to detect that the system is still functioning correctly, not just that it hasn't hung. If the calibration routine legitimately takes 3 seconds, the watchdog should be designed to accommodate that without being disabled or extended to the point where it can no longer catch real faults. The standard approach is to kick the watchdog at multiple points throughout the calibration routine — after each major step or at regular intervals — rather than only in the main loop. This way, if the calibration routine hangs partway through, the watchdog still fires because the kicks stop. I'd also ask the colleague to examine why the calibration routine is taking 3 seconds in the first place. Is it waiting on a sensor to stabilize? Is it performing a long computation? Could it be restructured into smaller steps with the watchdog kicked between them? If the routine genuinely needs 3 seconds of uninterrupted processing, I'd consider whether the watchdog timeout needs to be longer than the main-loop period but still shorter than the calibration routine's total duration — the key is that the watchdog should be kicked at intervals that are short relative to the timeout, and the timeout should be short enough to catch a fault quickly. I'd also check whether the watchdog is being kicked in interrupt context or from a high-priority task, which could mask a hung main loop. The right answer is usually to restructure the code so the watchdog is kicked at meaningful progress points, not to simply extend the timeout.

**Possible follow-ups:** How would you determine the appropriate watchdog timeout for a system with both fast and slow operations? What are the trade-offs between a shorter and longer watchdog timeout in a medical device?

## Q5: You're leading a firmware team that is transitioning from a bare-metal approach to using Zephyr RTOS for a new medical device. Two senior engineers disagree: one wants to port the existing bare-metal drivers directly into Zephyr as custom drivers, while the other wants to rewrite them using Zephyr's native driver model. How would you guide the team to a decision?

**Answer:** This is a common tension when adopting an RTOS, and the right answer usually depends on the specific drivers and the project's constraints. I'd frame the discussion around three factors: risk, long-term maintainability, and the driver's interaction with RTOS services. Porting existing drivers as custom Zephyr drivers is faster and preserves validated code — which matters in a medical device where the drivers may have already undergone verification testing. However, custom drivers that bypass Zephyr's driver model won't integrate with Zephyr's power management, clock control, or device tree abstractions. If the device needs sophisticated low-power modes or multiple board variants, that integration becomes important. Rewriting drivers using Zephyr's native model gives better long-term maintainability and access to Zephyr's testing and abstraction layers, but it introduces risk — new code needs re-verification, and subtle timing differences between the bare-metal and RTOS environments can surface. I'd guide the team to evaluate each driver individually rather than making a blanket decision. For simple peripherals like GPIO or basic UART, rewriting to the native model is low-risk and high-value. For complex, well-tested drivers — perhaps a custom sensor interface with intricate timing — porting as a custom driver might be pragmatic initially, with a plan to migrate later if needed. I'd also consider the team's Zephyr experience: if they're new to the RTOS, rewriting everything at once increases the learning curve and risk. A hybrid approach — port critical, complex drivers initially while rewriting simpler ones — lets the team build Zephyr expertise incrementally. The decision should be documented with clear rationale, and I'd ensure that whatever approach is chosen, the drivers are tested against the same verification criteria as the original bare-metal code.

**Possible follow-ups:** How would you handle the situation where a driver ported as a custom Zephyr driver needs to interact with Zephyr's power management subsystem? What criteria would you use to decide which drivers to rewrite versus port?
