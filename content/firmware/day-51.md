## Q1: How would you approach sizing thread stacks in a Zephyr RTOS application, and what would you do to verify that your sizing is actually correct rather than just "probably enough"?

**Answer:** Stack sizing in Zephyr is a combination of static analysis, measurement, and margin — not a one-time guess. I'd start by enumerating what actually consumes stack in each thread: local variables (especially large buffers or structs passed by value), the call depth of the deepest path through that thread's functions, and the context-save overhead the architecture imposes on every function call and every interrupt that can preempt the thread. Zephyr's `CONFIG_THREAD_STACK_INFO` and the `k_thread_stack_space_get()` API let you query high-water marks at runtime, which is the only reliable way to know how close a thread actually came to overflow. I'd instrument the system to log the worst-case stack usage per thread over a representative run — including the paths that only execute on error handling or rare events, since those are often the deepest and least exercised. Then I'd apply a margin on top, sized to the risk: a thread that runs a fixed control loop can tolerate a modest margin, but a thread that calls into a library or a protocol stack with variable call depth needs more headroom, because a future code change can silently deepen the call chain. I'd also enable `CONFIG_STACK_SENTINEL` or the MPU-based stack protection so that an overflow faults deterministically instead of corrupting an adjacent thread's stack — silent corruption is far worse than a clean fault. The key discipline is treating stack sizing as something to re-verify whenever a thread's code path changes, not something you set once and forget.

## Q2: You're implementing a state machine for a device's operational modes, and a colleague argues that a table-driven approach is more maintainable than a switch-case. How would you decide which to use, and what factors would drive that decision?

**Answer:** Both are legitimate, and the right choice depends on the shape of the state machine rather than a blanket preference. A switch-case implementation is usually clearer when the number of states is small, the transitions are few, and each state's behavior is genuinely different — the code reads top-to-bottom and a debugger steps through it naturally. A table-driven approach wins when the state machine is large or regular: many states, many events, and transitions that follow a pattern, because then the table becomes a single source of truth that's easy to review, diff, and extend without touching control flow. The decision factors I'd weigh are: how many states and events there are, whether transitions are sparse or dense, whether the same event means different things in different states, and how often the machine is expected to change over the product's life. I'd also consider testability — a table can be validated exhaustively by iterating over state/event pairs, which is harder to do with scattered switch cases. One thing I'd insist on either way is that state transitions go through a single choke point rather than being scattered across modules, because scattered transitions are where state machines rot. If the team is split, I'd suggest prototyping the two or three most complex transitions in both styles and letting the code itself make the argument — that's usually more productive than debating in the abstract.

**Possible follow-ups:**
- How would you handle entry and exit actions in a table-driven state machine without making the table unreadable?
- What would you do if a state machine needs to run the same action on entry to several states — how do you avoid duplicating that logic?

## Q3: How would you approach configuring DMA for a peripheral that streams data continuously, where the data rate is high enough that per-transfer interrupts would consume too much CPU, but the buffer is too small to hold an entire acquisition?

**Answer:** The core pattern here is a circular (ring) DMA buffer with half-transfer and full-transfer interrupts, so the CPU is only woken when a meaningful chunk is ready rather than per sample. I'd size the DMA buffer as a multiple of the processing chunk — typically two or more "half-buffers" — so that while the CPU processes one half, the DMA engine is filling the other. The half-transfer and transfer-complete interrupts then act as "this half is ready to consume" signals, and the CPU's job per interrupt is small and bounded: hand off a pointer to the filled half and let a task or a lower-priority handler do the actual processing. The critical design points are: making sure the DMA buffer is in memory the DMA controller can actually reach (some controllers can't access certain RAM regions, and cache coherency matters on cores with data cache), ensuring the buffer alignment and size meet the controller's requirements, and handling the wrap-around correctly so the consumer never reads a half that's currently being overwritten. I'd also think about what happens when the consumer falls behind — if the producer outruns the consumer, you either drop samples deliberately (and flag it) or you back-pressure the source, and that decision has to be made explicitly rather than discovered in the field. For a medical or safety-relevant stream, I'd want the overflow condition to be detectable and logged, not silent.

**Possible follow-ups:**
- How would you handle cache coherency if the DMA buffer is in cached memory?
- What would you do if the consumer occasionally takes longer than one half-buffer period to process — how would you keep the system deterministic?

## Q4: How would you approach implementing a watchdog strategy for a system where several independent subsystems each need to prove they're alive, but a single missed deadline from any one of them shouldn't necessarily reset the whole device?

**Answer:** The first question is what the watchdog is actually protecting against, because that determines the architecture. A single watchdog kicked by one place in the code only proves that one place is running — it doesn't prove the sensor task, the comms task, or the control loop are healthy. A more robust pattern is a supervisory "health monitor" that each critical subsystem reports into, and the watchdog is kicked only when all the required subsystems have reported within their expected windows. That way a stuck subsystem stops the kick and the watchdog fires, but you can also distinguish "one subsystem is late" from "the whole system is wedged" and respond differently — for example, attempt a subsystem restart before resorting to a full device reset. The trade-offs are real: a health-monitor scheme adds a coordination point that itself has to be correct, and if the monitor is too strict it will reset the device for benign scheduling jitter. So I'd define per-subsystem deadlines with margin, make the monitor's own logic simple and independently testable, and make sure the monitor can't be starved by the very subsystem it's watching. I'd also want the reset reason to be captured and persisted so that a field reset is diagnosable rather than a mystery. For a medical device, the reset behavior itself has to be defined by the risk analysis — a reset during a procedure may be worse than degraded operation, so the watchdog response might be "enter a safe state and alarm" rather than "reboot."

**Possible follow-ups:**
- How would you prevent the health monitor itself from becoming a single point of failure?
- How would you test a watchdog scheme like this without waiting for real failures to occur?

## Q5: A junior engineer on your team has written a driver that works on the bench but you notice it uses blocking delays (`k_sleep` or busy-wait loops) inside a high-priority thread to wait for a peripheral to become ready. How would you guide them toward a better approach?

**Answer:** I'd start by making the problem concrete rather than abstract — show them what the blocking delay does to the rest of the system. If a high-priority thread sleeps or busy-waits for a peripheral, it either blocks lower-priority work that could have run in that window, or it burns CPU that could have been used elsewhere, and in a real-time system it can push other deadlines. The better pattern depends on the peripheral: if it can signal readiness via an interrupt or a status flag, the driver should wait on a synchronization primitive — a semaphore or a completion — that the interrupt or a polling task signals, so the waiting thread yields the CPU instead of holding it. If the peripheral genuinely has no interrupt and must be polled, the polling should be time-bounded and should yield between polls rather than spin, and the timeout should be a real error path, not an infinite loop. I'd also point out that a busy-wait inside a high-priority thread is especially dangerous because it can starve the very interrupt that would have made the peripheral ready — a classic deadlock-by-priority-inversion. Rather than just telling them the answer, I'd ask them to trace what happens to the other threads' timing when the delay executes, and let them see the cost. Then I'd pair with them on converting one wait to an interrupt-driven or semaphore-based wait, so they internalize the pattern rather than just applying a fix.

**Possible follow-ups:**
- What would you do if the peripheral has no interrupt line available and polling is the only option?
- How would you decide between a semaphore, a completion, and an event flag for signaling peripheral readiness?
