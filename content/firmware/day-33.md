## Q1: You're designing a Zephyr RTOS-based system where a high-priority sensor task must read data every 1 ms, but a lower-priority task occasionally needs to perform a flash erase that blocks for up to 100 ms. How would you approach this scheduling conflict?
**Answer:** The fundamental issue is that a blocking flash operation in any task will stall the scheduler if it disables interrupts or occupies the CPU. My first step would be to check whether the flash controller supports asynchronous or interrupt-driven erase operations — many modern MCUs do, and Zephyr's flash API has an asynchronous page erase variant that returns immediately and signals completion via a callback or semaphore. If the hardware supports this, I'd restructure the lower-priority task to initiate the erase, then block on a semaphore that the flash interrupt gives when done. That way the 1 ms sensor task continues to run while the erase proceeds in the background.

If the flash controller only supports blocking operations, the next option is to move the flash write to a dedicated lower-priority thread and accept that the sensor task will be delayed during the erase. In that case, I'd need to verify whether the sensor data can tolerate a 100 ms gap. If it can't, I'd look at buffering sensor samples in RAM during the erase window and processing them once the erase completes — but this only works if the buffer can hold the data and the system can tolerate the latency. Another approach is to break the flash operation into smaller chunks (e.g., page-by-page rather than a full sector erase) and yield between chunks, though this isn't always possible depending on the flash geometry.

I'd also consider whether the sensor task really needs to run during the erase. If the data is being collected for logging rather than real-time control, a brief gap might be acceptable with proper buffering. The key is to quantify the worst-case timing impact, document it, and verify it against the system requirements rather than assuming the conflict can be fully eliminated.

**Possible follow-ups:** How would you determine whether the sensor task can tolerate a 100 ms gap? What if the flash erase is a full-sector erase that can't be interrupted?

## Q2: You're reviewing a colleague's firmware code that implements a communication protocol using a single large interrupt service routine that handles both byte-level reception and complete message parsing. The ISR disables interrupts for the entire duration, which can be up to 300 µs for a long message. The system also has a 1 kHz control loop that must meet strict timing. How would you approach this situation?
**Answer:** This is a classic case of doing too much work in interrupt context. The ISR should handle only the time-critical part — moving bytes from the peripheral into a buffer — and defer all message parsing to a lower-priority context. I'd start by quantifying the actual interrupt latency impact: 300 µs of interrupt-disabled time on a 1 kHz control loop means the loop could miss its deadline by up to 30% of its period, which is almost certainly unacceptable.

The refactoring approach would be to split the work into two layers. The ISR's only job is to receive each byte (or DMA block) and place it into a ring buffer, then signal a worker task or set a flag. The message parsing logic moves to a normal-priority task that reads from the ring buffer, validates framing, checks CRCs, and dispatches the message to the appropriate handler. This way, the ISR stays short — typically a few microseconds — and the control loop is only delayed by that short amount.

I'd also look at whether DMA could be used for reception, which would eliminate per-byte interrupts entirely. The DMA controller can move a complete message into memory and interrupt only once when the transfer completes or when a timeout occurs. This reduces interrupt overhead even further. The trade-off is that DMA requires careful buffer management and handling of partial messages, but for a well-defined protocol with known maximum message lengths, it's often the better solution.

Finally, I'd want to understand why the original engineer put parsing in the ISR. If it was for simplicity, the refactor is worth the effort. If there was a mistaken belief that parsing must happen at interrupt priority, I'd clarify that the protocol's timing requirements are about when bytes are received, not when messages are processed — as long as the receive buffer doesn't overflow, deferred parsing is perfectly valid.

**Possible follow-ups:** How would you handle a message that arrives in fragments? What if the protocol requires a response within a tight deadline after receiving a complete message?

## Q3: How would you approach implementing a firmware module that must handle a sensor which occasionally returns invalid data (e.g., out-of-range values or CRC failures), where the device is a medical monitor that must never display a false reading to the clinician?
**Answer:** The core principle is that invalid data must never be presented as valid — the system must either show nothing, show a clearly marked invalid state, or use the last known good value with an explicit staleness indicator. I'd start by defining what "invalid" means for each sensor: out-of-range values, CRC failures, missing responses, or values that violate rate-of-change limits (e.g., a heart rate that jumps from 70 to 200 in one sample). These criteria should come from the sensor's datasheet and clinical requirements, not be invented ad hoc.

The firmware architecture would have a validation layer between the raw sensor driver and the application logic. This layer performs the checks, applies any filtering or plausibility rules, and outputs a data structure that includes both the value and a status flag (valid, invalid, stale, or degraded). The application logic then decides how to use that status. For a medical display, the rule would be: if the status isn't valid, don't display the value as if it were real. Instead, show a placeholder like "—" or "signal lost," and possibly trigger an alarm if the condition persists.

For transient errors — say, one CRC failure in a stream of good readings — I'd typically retry the read once or twice before declaring the data invalid. The retry logic needs a timeout so it doesn't block the main loop indefinitely. If the sensor consistently returns bad data, the module should transition to a degraded state, log the condition, and notify the user interface. The system should also track the duration of invalid data so that a clinician can see whether the reading is current or stale.

I'd also think about the distinction between "no data" and "bad data." A sensor that doesn't respond at all is a different failure mode than one that returns out-of-range values. Both need handling, but the user-facing indication might differ — one might say "sensor disconnected" while the other says "reading unreliable." The key is that the firmware never fabricates a plausible-looking value from invalid data, because in a medical context that could lead to a wrong clinical decision.

**Possible follow-ups:** How would you handle a sensor that returns a value that's within range but clearly wrong (e.g., a temperature of 25°C from a body sensor)? How would you test this module to ensure it never displays a false reading?

## Q4: You're leading a firmware team where two senior engineers disagree on whether to use a state machine pattern or a table-driven approach for implementing a complex device protocol. One argues that a state machine is more readable and easier to debug, while the other argues that a table-driven approach is more maintainable and easier to extend. How would you guide the team to a decision?
**Answer:** I'd frame this as a design decision that should be driven by the specific characteristics of the protocol and the team's long-term maintenance constraints, not by personal preference. The first step is to analyze the protocol itself: How many states does it have? Are transitions mostly linear or are there many conditional paths? How likely is the protocol to change in the future — are new states or events expected? How critical is it that the implementation be verifiable against the specification?

For a protocol with a small number of states (say, fewer than 10) and relatively straightforward transitions, a switch-case state machine is often the right choice. It's easy to read, easy to trace during debugging, and the control flow is explicit. For a protocol with many states, numerous events, and complex transition conditions, a table-driven approach can be more maintainable because the transition logic is data rather than code — adding a new state or transition means adding a table entry rather than modifying control flow.

I'd also consider the team's testing and verification needs. In a medical device context, the protocol implementation will need to be verified against the specification. A table-driven approach can make this easier if the table is structured to mirror the specification's state transition table — you can literally trace each row of the spec to a row in the table. On the other hand, a state machine with well-named states and clear transition functions can be easier to unit test because each transition is a discrete code path.

Rather than letting the team argue abstractly, I'd suggest they prototype a small portion of the protocol both ways and evaluate the results against concrete criteria: readability for a new engineer joining the team, ease of adding a hypothetical new state, and debuggability when a transition fails. I'd also ask them to consider the team's familiarity with each pattern — a table-driven approach is only maintainable if the team understands it well. The decision should be made collaboratively, with the understanding that either approach can work if implemented cleanly, and the real risk is an inconsistent hybrid that's neither fully one nor the other.

**Possible follow-ups:** How would you handle a situation where the protocol is likely to grow significantly in the future? What if the team has strong experience with one pattern but not the other?

## Q5: A junior engineer on your team has implemented a low-power mode for a medical monitoring device that enters deep sleep between sensor readings. The device wakes on a timer interrupt, takes a reading, then goes back to sleep. However, the device occasionally misses readings because the sensor itself requires a 50 ms stabilization time after power-up before it produces valid data. The engineer proposes keeping the sensor powered on continuously to avoid the stabilization delay. How would you guide them?
**Answer:** I'd start by acknowledging that the engineer has identified a real problem — the sensor's stabilization time is a genuine constraint that needs to be handled. But keeping the sensor powered continuously defeats the purpose of the low-power mode, since the sensor is likely one of the largest power consumers in the system. The goal should be to find a solution that meets both requirements: low power consumption and no missed readings.

The first thing I'd ask is whether the sensor truly needs to be powered down between readings, or whether it can be placed in a lower-power idle state that still maintains its internal reference and reduces stabilization time on wake. Many sensors have multiple power modes — full off, standby, and idle — with different wake-up latencies. If the sensor has a standby mode that wakes in a few milliseconds, that might be the sweet spot: lower power than full operation but fast enough to meet the sampling schedule.

If the sensor must be fully powered down, the next option is to adjust the wake-up timing. Instead of waking the MCU and immediately reading the sensor, the firmware could wake the MCU, power up the sensor, and then wait the 50 ms stabilization period before taking the reading. The question is whether the MCU needs to stay awake during that wait, or whether it can go back to sleep and wake again when the sensor is ready. If the MCU can sleep during the stabilization period, the power cost is minimal — the sensor is the only thing drawing power during that time.

Another approach is to overlap the stabilization period with other work. If the device has multiple sensors or other tasks that need attention, the firmware could power up the sensor, then handle other tasks while waiting for stabilization, then return to read the sensor. This requires careful scheduling but can eliminate the wasted time entirely.

I'd also ask the engineer to quantify the actual power impact of each option. How much current does the sensor draw in each mode? How long is the stabilization period relative to the sleep interval? If the device sleeps for 10 seconds between readings, a 50 ms stabilization period is only 0.5% of the cycle — the power cost of keeping the sensor ready might be negligible compared to the cost of the reading itself. The right answer depends on the specific numbers, and the engineer should calculate them rather than guess.

Finally, I'd emphasize that this is a systems-level trade-off, not just a firmware problem. The sensor choice, the power supply design, and the clinical sampling requirements all factor into the decision. The engineer should document the trade-offs and present a recommendation with data, rather than making a unilateral choice that might compromise the device's battery life.

**Possible follow-ups:** How would you measure the actual power consumption of each approach? What if the sensor's stabilization time varies with temperature or aging?
