# firmware — Day 128

## Q1: How would you approach implementing a state machine for a device's operational modes where the same event can arrive from multiple sources — a user interface, a communication interface, and an internal timer — and the correct transition depends on which source sent it?

**Answer:** The key insight is that the event itself is not enough information — the transition table has to be keyed on the pair (current state, event, source), not just (current state, event). I'd start by making the source an explicit part of the event type rather than something inferred from context. A common failure mode is a single `EVENT_START` enum value that gets posted from three different places, and then the state machine has no way to distinguish "user pressed start" from "remote command said start" from "timer expired and we auto-started." So the event struct should carry both an event ID and an origin tag, and the dispatch logic should look up the transition using all three fields.

Structurally, I'd keep the state machine as a pure function — `next_state(current, event) -> new_state` plus a list of side effects to perform — with no direct hardware or global access inside it. That makes it trivially testable: you can enumerate every (state, event, source) combination in a table-driven test and assert the expected transition, including the "no transition" cases. The side effects (turning on an LED, sending a response, arming a timer) get executed by the caller after the transition is computed, which keeps the logic deterministic and the I/O isolated.

For the multi-source problem specifically, I'd also think about precedence and queuing. If a UI event and a comms event can arrive nearly simultaneously, you need a defined ordering — either a single event queue that serializes everything, or explicit priority rules. I'd lean toward a single queue drained by one task, so the state machine is never re-entered concurrently. And I'd want the transition table to make "this source is not allowed to trigger this event in this state" an explicit, logged rejection rather than a silent no-op, because silent rejections are exactly the kind of thing that turns into a field bug six months later.

**Possible follow-ups:** How would you handle an event that arrives while a transition's side effects are still executing — do you queue it, drop it, or block? And how would you represent the transition table so that adding a new source later doesn't require touching every state?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is almost always a timing or observability artifact, and the first job is to figure out which. Attaching a debugger changes several things at once: it halts the core at breakpoints, it may slow down or serialize memory accesses, it can disable certain low-power modes, and it often changes the reset behavior of watchdogs. So I'd start by narrowing down *which* of those differences matters, rather than guessing at the bug directly.

A good first step is to reproduce the failure without a debugger but with instrumentation that doesn't halt the core — a GPIO toggled at key points, a ring buffer in RAM that gets dumped after the fact, or a serial log at low priority. If the bug disappears when I add logging, that itself is a clue: it means the timing shifted, which points at a race condition or a marginal timing margin rather than a logic error. If it persists with logging but vanishes with the debugger, I'd suspect something the debugger specifically masks — a watchdog that's being serviced by the halt, a low-power mode that the debugger prevents, or an uninitialized-memory read that happens to be benign when the debugger's presence changes the memory contents.

I'd also check the obvious candidates early: is the watchdog being disabled or kicked by the debugger? Is the device entering a sleep mode that the debugger blocks? Are there reads of uninitialized RAM or peripheral registers whose reset values differ after a debugger-driven reset versus a power-on reset? And is the optimizer behaving differently — sometimes the debug build is `-O0` and the release build is `-O2`, and the bug only exists in one of them, which is a code-generation or undefined-behavior issue rather than a debugger artifact at all.

The systematic approach is to bisect the differences: run the release binary standalone with a watchdog disabled, then with sleep disabled, then with logging added, and see which change makes the bug appear or disappear. Each of those isolates one variable. Once I know which variable matters, the root cause usually becomes obvious.

**Possible follow-ups:** If adding a GPIO toggle makes the bug disappear, what does that tell you, and how would you instrument without perturbing timing? How would you distinguish a genuine race condition from a compiler optimization difference between debug and release builds?

## Q3: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first thing I'd do is quantify the problem rather than assume it. If the interrupt fires at, say, 100 kHz and each ISR entry/exit plus minimal work costs a couple of microseconds, that's already 20% of the CPU just in overhead — and that's before any real work. So the design question becomes: how do we reduce the *number* of interrupts, not just make each one cheaper?

There are a few standard levers, and which one applies depends on what the peripheral supports. The best case is that the peripheral has a FIFO or a threshold interrupt — you let it buffer N samples and only interrupt when the FIFO crosses a watermark or fills. That converts N interrupts into one. The next lever is DMA: if the peripheral can stream into a circular buffer autonomously, the CPU only gets involved on half-transfer and full-transfer events, or even less if you use a larger buffer and a lower-priority "buffer is getting full" interrupt. That's usually the right answer for continuous high-rate data acquisition.

If neither FIFO nor DMA is available, then the fallback is to make the ISR do the absolute minimum — read the data register, push it into a lock-free ring buffer, clear the flag, return — and defer all processing to a thread that drains the buffer in batches. That doesn't reduce the interrupt count, but it does reduce the per-interrupt cost to the floor, and it moves the expensive work out of interrupt context where it can be preempted and batched. I'd also look at whether the interrupt can be coalesced in hardware — some peripherals let you mask the interrupt and poll a status bit at a fixed rate, which trades latency for CPU.

The trade-off to be explicit about is latency versus throughput. Batching and DMA add latency between the event and the software seeing it, which is fine for a data logger but not for a control loop. So the design has to start from the latency requirement, and the batching strategy follows from that.

**Possible follow-ups:** How would you size the DMA circular buffer given a known sample rate and a known worst-case thread scheduling delay? What happens if the consumer thread falls behind and the DMA buffer wraps — how do you detect and handle the overrun?

## Q4: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I'd start by acknowledging the part they got right — `volatile` does prevent the compiler from caching the value in a register or eliminating the access, and for a single flag that's genuinely all you need from the compiler's perspective. The problem is that `volatile` says nothing about *atomicity* or *ordering*, and those are the two things that actually bite you in an ISR/thread handoff.

The concrete failure modes I'd walk them through: first, if the shared variable is wider than the machine's natural word size — a 32-bit counter on a 16-bit MCU, or a struct — the ISR can preempt the thread mid-write and the thread reads a torn value. `volatile` doesn't prevent that. Second, even for a single-byte flag, the compiler and the CPU are both free to reorder *other* memory accesses around the volatile access. So the classic pattern of "write data buffer, then set flag" can be reordered such that the flag is visible before the data is, and the reader sees a flag set with stale data behind it. That's a memory-ordering problem, and `volatile` doesn't fix it — you need an explicit barrier or an atomic with acquire/release semantics.

The fix depends on what the variable is doing. If it's a simple "data ready" flag, I'd replace it with a proper synchronization primitive — in Zephyr, a `k_sem`, `k_event`, or an atomic flag with the right memory ordering. If it's a data handoff, a lock-free single-producer/single-consumer ring buffer with atomic head/tail indices is the standard pattern, and it's worth showing them why the indices need to be atomic and why the ordering matters. If it's genuinely just a one-way signal and they want to keep it lightweight, `atomic_set`/`atomic_get` with explicit memory barriers is the minimum bar.

I'd frame it not as "your code is wrong" but as "here's the class of bug this can produce, and here's how to prove your version is safe." A short exercise — have them write a test that hammers the ISR and thread and see if they can produce a torn read — is often more convincing than an argument. And I'd point out that the maintainability cost matters too: the next engineer reading `volatile` has to reason about whether it's sufficient, whereas a `k_sem` or an atomic makes the intent unambiguous.

**Possible follow-ups:** On a single-core Cortex-M, is a plain `volatile` flag actually sufficient for a one-way ISR-to-thread signal, and what would change on a dual-core part? How would you demonstrate a torn read or a reordering bug in a test?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd resist the urge to pick a side and instead reframe the question around the actual requirements, because "polling versus interrupts" is usually a false dichotomy — the real answer is often a hybrid, and the right choice depends on numbers neither engineer has stated yet.

The first thing I'd do is get the requirements on the table explicitly: what's the maximum acceptable latency from a byte arriving to the protocol layer seeing it? What's the worst-case CPU budget for this protocol? What's the message rate and message size distribution? Is there a hard real-time deadline, and if so, what's the margin? Once those are written down, the debate usually resolves itself — either the latency requirement is loose enough that a well-designed polling loop at a fixed rate is perfectly adequate, or it's tight enough that interrupts (or DMA) are clearly necessary.

I'd also separate two concerns that often get conflated: *detecting* that data is available, and *processing* it. You can use an interrupt purely to wake a thread or post a semaphore, and do all the actual protocol work in thread context — which gives you the responsiveness of interrupts without the "everything happens in the ISR" complexity that the polling advocate is rightly worried about. Conversely, a polling loop that runs at a high enough rate and does minimal work per iteration can be extremely predictable, and on a system with a tight, well-characterized loop it's a legitimate design. The "simpler and more predictable" argument has real merit when the loop timing is bounded and the protocol is low-rate.

My role as lead would be to make the decision criteria explicit and get both engineers to agree on them *before* evaluating the options — latency budget, CPU budget, complexity/maintainability, testability, and risk. Then I'd ask each of them to sketch their approach against those criteria, ideally with a rough measurement or a prototype on real hardware rather than an argument from principle. A short experiment — measure the actual latency and CPU load of each approach on the target — settles these debates faster than any amount of discussion. And I'd make sure the decision is documented with its rationale, so that when someone revisits it in a year they understand what was traded away.

The meta-point I'd want the team to internalize: on a medical device, "predictable" and "responsive" are both proxies for "we can demonstrate it meets its timing requirements under worst-case conditions." The decision should be driven by which approach gives us the strongest evidence of that, not by which one is more elegant.

**Possible follow-ups:** If you go with interrupts, how do you bound the worst-case interrupt latency and prove it to a reviewer? If you go with polling, how do you guarantee the loop rate under all operating conditions, including when other tasks are running?

**Possible follow-ups (Q5 continued):** How would you structure a short bake-off so the team gets real data without burning a week? And how would you handle it if the losing engineer remains unconvinced after the data comes in?
