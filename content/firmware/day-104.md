# firmware — Day 104

## Q1: How would you approach implementing a state machine for a device's operational modes where the same event can arrive from multiple sources — a user interface, a communication interface, and an internal timer — and the correct transition depends on which source sent it?

**Answer:** The key insight is that the state machine shouldn't care *where* an event came from — it should care *what* the event means. So the first design move is to normalize: each source has a thin adapter layer that translates its raw input into a canonical event type, and the event carries a source tag only as metadata, not as part of the transition logic. That keeps the state table from exploding combinatorially as sources are added.

Concretely, I'd define an event enum (e.g., `START_REQUEST`, `STOP_REQUEST`, `TIMEOUT`, `FAULT`) and a transition table indexed by `(current_state, event)`. If a given event is only legal from certain sources — say, a `STOP_REQUEST` from the UI is always honored but one from the comms interface is only honored in a remote-control mode — that's a *guard condition* on the transition, not a separate event type. Guards are small predicates evaluated before the transition fires, which keeps the table readable and the source-specific policy explicit and testable in isolation.

The adapters matter for correctness too. The timer source is usually an ISR or a kernel timer callback, the comms source is a protocol parser running in a thread, and the UI source might be a debounced GPIO or a display task. Rather than letting each of them poke the state machine directly, I'd funnel all events through a single queue (a `k_msgq` in Zephyr, or a small ring buffer bare-metal) so transitions are serialized in one context. That eliminates a whole class of races where two sources try to transition simultaneously. The state machine then runs as a single consumer of that queue — one thread of control, no locking needed inside the transition logic.

For debuggability, I'd log every event with its source tag and the resulting state, so when something behaves unexpectedly you can reconstruct the exact sequence. And I'd keep the transition function pure — state in, event in, new state and side-effect actions out — so it can be unit-tested on a host without any hardware.

**Possible follow-ups:** How would you handle an event that arrives while a transition's entry action is still running — queue it, drop it, or reject it? And how do you keep the transition table from becoming a maintenance burden as the number of states and events grows?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first thing to recognize is that attaching a debugger changes several things at once: it halts the core at breakpoints, it may slow execution enough to mask timing races, it can change the state of low-power modes (many debuggers keep clocks running), and it can alter memory layout or initialization. So the goal is to figure out *which* of those differences is masking the bug.

I'd start by narrowing the observation method rather than the hypothesis. Instead of a breakpoint debugger, I'd switch to non-intrusive instrumentation: a GPIO toggled at key points viewed on a scope, or a ring-buffer trace in RAM that I can dump after the fact. If the bug disappears with a scope attached but reappears with nothing attached, that points to timing. If it persists with tracing but vanishes with a breakpoint debugger, that points to the debugger halting the core at a critical moment.

The most common root causes fall into a few buckets. Timing races — an ISR and a thread touching shared state without proper synchronization, where the debugger's slowdown happens to widen or close the window. Low-power interactions — the debugger prevents the device from entering deep sleep, so a wake-up bug never manifests. Uninitialized memory — the debugger or its startup scripts may zero or pre-fill RAM differently. And optimization-sensitive code — `volatile` missing on a variable the compiler caches in a register, which behaves differently under debug builds.

I'd also compare the exact build: is the standalone build the same optimization level and the same linker script? A release build with `-O2` and a debug build with `-O0` are effectively two different programs, and the bug may simply live in the optimized one. Reproducing with the release binary under a debugger is a useful control.

Once I have a hypothesis, I'd try to make the bug *more* reproducible rather than less — stress the suspected path (raise the interrupt rate, add deliberate delays, run at temperature extremes) so I can iterate quickly, then confirm the fix by running the standalone build for an extended period.

**Possible follow-ups:** How would you use a logic analyzer or trace buffer to distinguish a timing race from a power-management issue? And what would you do if the bug only reproduces in the field and never on your bench?

## Q3: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it. If the peripheral fires at, say, 100 kHz and each ISR costs a few microseconds of entry, exit, and bookkeeping, the CPU is spending a large fraction of its time just getting in and out of the handler — the actual work may be trivial. So I'd measure the ISR duration and the interrupt rate, compute the duty cycle, and confirm that interrupt overhead (not the work itself) is the bottleneck.

There are several standard mitigations, and the right one depends on what the peripheral supports. The cleanest is DMA: if the peripheral can stream into a buffer without CPU involvement, you replace N interrupts with one "buffer half-full / full" interrupt, and the CPU only wakes when there's a meaningful chunk to process. That's the go-to for continuous data streams like ADC or SPI captures.

If DMA isn't available or doesn't fit, the next lever is to reduce the *number* of interrupts without losing data. Many peripherals have FIFOs — enable them and set the interrupt threshold so you service a batch rather than a byte. For a level-triggered interrupt, you can also switch to a "drain the FIFO in the ISR, then re-enable" pattern so a burst produces one interrupt instead of many.

If the interrupt source is genuinely edge-per-event and can't be batched in hardware, I'd look at whether the ISR can be made minimal — just timestamp or push a token into a lock-free ring buffer and defer all real work to a thread — so the per-interrupt cost drops to the floor. And as a last resort, if the event rate exceeds what the CPU can service at all, that's a signal the design needs to change: either the peripheral configuration is wrong (over-sampling), or the data needs to be aggregated in hardware.

Throughout, I'd keep an eye on latency for the *other* interrupts in the system — batching one source must not starve a higher-priority one, so priority assignment and the maximum time spent in any handler matter as much as the average.

**Possible follow-ups:** How would you size the DMA buffer and choose the half/full thresholds so you don't drop data during a processing burst? And how would you verify, on real hardware, that the CPU load actually dropped rather than just moved?

## Q4: A junior engineer has written a driver that works reliably on the bench but uses a fixed `k_sleep` delay to wait for a peripheral to become ready after each command, rather than checking a status register or using an interrupt. How would you guide them?

**Answer:** I'd start by acknowledging why the approach feels reasonable — it works, it's simple, and on the bench with a known part and a stable supply it's genuinely reliable. Dismissing it outright would put the engineer on the defensive and miss the teaching moment. The goal is to get them to see *why* it's fragile, not just to hear that it is.

The core argument is that a fixed delay encodes an assumption about the worst-case ready time, and that assumption is only valid under the conditions you tested. Over temperature, across part-to-part variation, at end-of-life supply margins, or when the peripheral is busy with a prior operation, the ready time can exceed the delay — and then the driver reads garbage or issues the next command too early. The delay is also pure waste in the common case: if the part is typically ready in a fraction of the specified time, you're burning CPU (or, worse, blocking a thread) on every single transaction.

I'd walk them through the alternatives in order of increasing complexity. First, poll the status register with a *timeout* — a bounded loop that exits as soon as the ready bit sets, with a deadline so a dead peripheral doesn't hang the system. That alone fixes both the correctness and the wasted-time problems for most parts. Second, if the peripheral has a ready interrupt, use it and block on a semaphore or completion with a timeout — that frees the CPU entirely while waiting. Third, if the wait is short and the driver runs in a context where blocking is acceptable, a short `k_sleep` *combined with* a status check is a reasonable compromise, but never a bare delay.

I'd frame it as "the delay is a guess; the status register is the truth." And I'd point out the maintainability angle: a driver that polls a documented status bit is self-documenting about the contract with the part, whereas a magic `k_sleep(5)` invites the next person to tweak the number without understanding it.

**Possible follow-ups:** How would you choose a sensible timeout value for the polling loop, and what should the driver do when the timeout expires? And how would you structure the driver so the same code works whether the wait is satisfied by polling or by an interrupt?

## Q5: How would you approach deciding whether a piece of firmware logic belongs in an interrupt service routine versus a deferred context such as a work queue or a thread?

**Answer:** The default should be "as little as possible in the ISR," and the decision comes down to a few concrete criteria: how much latency the work can tolerate, how long it takes, and whether it can block.

The ISR is the right home for work that is (a) short and bounded, (b) must happen immediately to avoid losing data or missing a deadline, and (c) cannot block. Typical examples: reading a data register to clear the interrupt source, capturing a timestamp, pushing a value into a lock-free ring buffer, or kicking a hardware handshake. Anything that involves waiting, allocating, taking a mutex, or doing significant computation should be deferred.

The reason is that an ISR runs at higher priority than any thread and typically with interrupts masked (or at least at a priority that preempts everything below it). Every microsecond spent in the ISR is a microsecond of added latency for every other interrupt and for the scheduler. So a long ISR doesn't just cost its own time — it degrades the timing of the whole system. That's the argument I'd make to someone tempted to "just do it in the ISR because it's simpler."

The deferred context choice then depends on the work. A work queue is good for short, non-blocking follow-up that can run in the kernel's workqueue thread — it's lightweight and doesn't need its own stack. A dedicated thread is better when the work can block (e.g., needs a mutex, does I/O, or waits on another event) or when it needs its own priority relative to other tasks. For a data pipeline, the common pattern is: ISR pushes to a ring buffer and signals a semaphore; a consumer thread drains the buffer and does the processing.

I'd also flag the boundary cases. If the "deferred" work is actually tiny and the deferral overhead (semaphore give/take, context switch) exceeds the work itself, keeping it in the ISR may be justified — but that's a measured decision, not a default. And if the ISR is firing so fast that even the minimal handler is a bottleneck, that's a signal to look at DMA or hardware batching rather than shuffling work between contexts.

**Possible follow-ups:** How would you measure whether a given ISR is "too long," and what would you do if profiling showed it was? And how do you handle the case where the deferred work must complete before the next interrupt arrives, or data will be lost?
