# firmware — Day 100

## Q1: How would you approach designing a watchdog strategy for a device that must distinguish between a genuine firmware hang and a legitimate but slow operation, without simply extending the timeout until the watchdog becomes meaningless?

**Answer:** The core problem is that a single fixed timeout conflates "the system is stuck" with "the system is busy doing something that legitimately takes a while." The way out is to make the watchdog's notion of liveness depend on *progress*, not on wall-clock time. I'd start by separating the watchdog hardware from the policy that feeds it: the hardware watchdog gets kicked from a single, well-defined place — typically a dedicated supervisory task or the scheduler idle hook — and that kick is gated on evidence that every monitored subsystem has reported in within its own expected window. Each subsystem registers a deadline or a "last seen" timestamp, and the supervisor only kicks if all of them are current. A slow calibration routine then doesn't need a longer timeout; it needs to *report progress* during the operation — for example, the calibration routine posts a heartbeat or advances a stage counter at each phase boundary, so the supervisor sees forward motion even though the whole routine takes seconds. If a stage genuinely can't report progress (a single blocking flash erase, say), the routine explicitly enters a "long operation" state that the supervisor understands, with its own bounded deadline — so the watchdog still catches a hang *inside* that operation, just with a different threshold. The key discipline is that every extension of the effective timeout is scoped, explicit, and bounded, rather than a global increase. I'd also make sure the watchdog is windowed if the hardware supports it, so that a runaway loop that kicks too *often* is also caught — a task stuck in a tight loop that happens to hit the kick call is just as broken as one that never reaches it. Finally, I'd want the reset path to leave a diagnostic breadcrumb (which subsystem was stale, what state the supervisor was in) so that a field reset is actionable rather than mysterious.

**Possible follow-ups:** How would you handle a subsystem whose heartbeat is itself unreliable — for example, one that can only report from a low-priority thread that might be starved? What would you do if the watchdog hardware only supports a single fixed timeout and no windowing?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** The debugger changes the system in several ways at once, so the first job is to figure out *which* change is masking the bug. The usual suspects are timing, memory layout, and power state. Attaching a debugger typically slows execution, adds latency to interrupt entry, and can keep certain clocks or peripherals alive that would otherwise be gated — so a race condition, a marginal setup/hold timing on an external bus, or a low-power transition that isn't quite clean can all disappear under the debugger. It also changes where code and data land in memory, which can hide a stack overflow or an out-of-bounds write that only corrupts something when the layout shifts. My approach would be to first reproduce the failure reliably without the debugger, then reintroduce observability in ways that don't perturb timing as much: GPIO toggles around suspect code paths captured on a scope or logic analyzer, a ring buffer in RAM that the firmware writes to and that I can dump after the fact, or a serial log at low priority. If the bug is timing-sensitive, I'd deliberately vary the timing — add small delays in different places, change interrupt priorities, run at different clock speeds — and see which perturbation makes it appear or vanish; that narrows down which timing relationship is marginal. If it smells like memory, I'd check stack high-water marks, enable any MPU/stack-guard facilities the MCU offers, and look at whether the failure correlates with a particular allocation or call depth. The debugger-attached case is a clue, not a nuisance: the fact that it changes behavior tells me the bug is sensitive to something the debugger perturbs, and I'd treat that perturbation as a diagnostic lever rather than trying to debug *through* the debugger.

**Possible follow-ups:** How would you use a logic analyzer to narrow down a timing-sensitive bug without changing the firmware's timing behavior? What would you do if the failure only reproduces in the field and never on your bench, debugger or not?

## Q3: How would you approach implementing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** When the interrupt rate itself is the problem, the fix is almost always to reduce the *number* of interrupts rather than to make each one faster. The first lever is the peripheral's own capabilities: many peripherals can be configured to interrupt on a FIFO threshold or a watermark rather than per-sample, or to coalesce events, so the CPU is woken once per batch instead of once per item. If the peripheral supports DMA, that's usually the right answer — let DMA move data into a buffer and interrupt only on half-transfer and transfer-complete, so the ISR runs at the buffer's cadence rather than the sample's. If neither is available, I'd look at whether the interrupt can be disabled for a window and the peripheral polled in a tight, bounded loop — essentially batching in software — as long as the peripheral's internal buffering can absorb the data during the poll gap without overflow. The design constraint I'd keep front of mind is that the ISR must stay short and bounded: capture the minimum state needed (a count, a pointer, a timestamp), defer the actual processing to a thread or work queue, and never do anything in the ISR whose duration depends on data content. I'd also budget explicitly: measure the ISR entry/exit cost and the per-event work, multiply by the event rate, and compare against the CPU budget — if the number is uncomfortable, that's the signal to move to DMA or batching rather than to micro-optimize the ISR. Finally, I'd watch for the failure mode where the ISR is fast enough on average but the *burst* rate overwhelms it; the design needs headroom for the worst-case burst, not just the mean rate.

**Possible follow-ups:** How would you decide between a FIFO-threshold interrupt and DMA for a given peripheral, if both are available? What would you do if the peripheral has no FIFO and no DMA, and the interrupt rate is still too high?

## Q4: A junior engineer has written a driver that works reliably on the bench but uses a fixed `k_sleep` delay to wait for a peripheral to become ready after each command, rather than checking a status register or using an interrupt. How would you guide them?

**Answer:** I'd start by acknowledging that the code works and that the instinct behind it — "wait long enough and it'll be ready" — isn't crazy; it's just fragile in ways that don't show up on a bench. The conversation I'd want to have is about *what the delay is actually standing in for*. A fixed delay encodes an assumption about the worst-case readiness time, and that assumption is only valid at the temperature, voltage, and part-to-part variation the engineer happened to test at. On a cold board, a marginal supply, or a different batch of the peripheral, the delay can be too short and the driver reads garbage; on a fast board it's wasted time that adds up across every command. I'd walk through the datasheet together to find the actual readiness signal — a status bit, a busy line, a data-ready interrupt — and show that the hardware already tells us when it's ready, so the delay is throwing away information we have. Then I'd help them restructure: poll the status bit with a *bounded* timeout (so a genuinely dead peripheral produces an error rather than an infinite loop), or better, use the interrupt if one exists and let the driver block on a semaphore or completion with a timeout. The bounded-timeout point matters — replacing a fixed delay with an unbounded poll is a different bug, not a fix. I'd also point out the testability angle: a status-based driver can be tested against a simulated peripheral that reports ready at different times, whereas a delay-based driver can only be tested at one timing. The framing I'd use is that the delay is a *guess* and the status register is *ground truth*; we want the driver to depend on ground truth. I'd pair with them on converting one command path first so they see the pattern, then let them carry it through the rest.

**Possible follow-ups:** How would you handle a peripheral whose datasheet gives a maximum readiness time but no status bit at all? What's the risk of replacing a fixed delay with a poll that has no timeout, and how would you catch that in review?

## Q5: How would you approach a situation where you discover, late in a project, that a firmware design decision you made early on is now causing significant problems, and changing it would require rework across several modules?

**Answer:** The first thing I'd do is resist the urge to either quietly patch around it or immediately propose a rewrite — both are ways of avoiding the actual decision. I'd start by making the problem concrete and quantified: what exactly is failing, how often, what's the cost of *not* fixing it (field failures, test escapes, schedule risk downstream), and what's the true scope of the rework if we change the decision now. "Several modules" needs to become a list with effort estimates, because the honest comparison is between the cost of rework now and the cost of carrying the problem forward. Then I'd bring it to the people who need to know — the project lead, the affected module owners, and whoever owns the schedule — early, with the facts and a recommendation rather than a confession. The framing matters: this is a design decision that was reasonable given what we knew at the time and is now demonstrably wrong given what we've learned, which is a normal engineering event, not a personal failure. I'd lay out the options honestly: fix it properly now, contain it with a documented workaround and a plan to fix later, or accept the risk and document it — and be clear about which I'd recommend and why. If the rework is genuinely too large for the remaining schedule, the containment option is legitimate *provided* it's explicit, bounded, and tracked, not silently absorbed. I'd also look for a way to stage the fix so the highest-risk modules get corrected first and the rest can follow, rather than treating it as all-or-nothing. The thing I'd want to avoid is letting the sunk cost of the early decision bias me toward defending it; the question is what's true now, not who was right then. And afterward, I'd want a short retrospective on why the decision wasn't caught earlier — was there a missing review, a missing test, an assumption nobody validated? — so the same class of decision gets caught sooner next time.

**Possible follow-ups:** How would you decide between a full fix and a documented workaround when the schedule is tight? What would you do if the affected module owners disagree with your assessment of the scope?
