# firmware — Day 102

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it — measure the actual interrupt rate, the per-ISR cost (entry/exit overhead plus the work done), and the resulting CPU utilization. If servicing every interrupt would consume, say, more than a small fraction of the budget, the fix is almost always to reduce the *number* of interrupts rather than to make each one faster.

The standard techniques, roughly in order of preference:

- **DMA with transfer-complete or half-transfer interrupts.** For a streaming peripheral (ADC, SPI, UART), let the DMA engine move data into a buffer and only interrupt on a half-buffer or full-buffer boundary. The CPU then services one interrupt per N samples instead of N interrupts. This is usually the biggest win and the cleanest.
- **FIFO / watermark thresholds.** Many peripherals have a hardware FIFO with a programmable threshold. Set the interrupt to fire only when the FIFO reaches a level that gives you enough headroom to drain it before it overflows. This trades a small amount of latency for a large reduction in interrupt count.
- **Interrupt coalescing / batching in the ISR.** If the hardware can't reduce the rate, the ISR itself can drain multiple pending events per invocation — read the status register, loop while the source is still asserted, and process a batch. This amortizes entry/exit overhead.
- **Moving work out of the ISR.** Keep the ISR to the minimum (acknowledge, move a pointer, signal a thread) and let a deferred context do the heavy processing. This doesn't reduce interrupt count but reduces per-interrupt cost and, more importantly, keeps the system responsive.

The trade-offs matter. DMA adds buffer management complexity and a latency floor (you don't see data until a transfer completes). FIFO thresholds add latency and require careful sizing against the worst-case service time. Batching in the ISR can increase worst-case interrupt latency, which is dangerous if there's a hard real-time loop elsewhere. So the choice depends on the system's latency requirements: a control loop that needs sub-millisecond response may not tolerate a large DMA buffer, while a data-logging path will.

I'd also verify the fix empirically — measure CPU utilization and worst-case interrupt latency before and after, and stress-test at the maximum data rate, not the nominal one.

**Possible follow-ups:**
- How would you size the DMA buffer if the consumer thread can occasionally be delayed by a higher-priority task?
- What happens to your scheme if the peripheral's data rate is bursty rather than constant?

## Q2: You're implementing a bootloader for a device that must support field updates over an unreliable link, and the device has no physical recovery mechanism (no button, no exposed debug header). How would you structure the update and recovery logic so that a failed or interrupted transfer can never leave the device unbootable?

**Answer:** The core principle is that the bootloader must always have a known-good image to fall back to, and the decision of what to boot must be made by logic that cannot itself be corrupted by a failed update. With no physical recovery, the bootloader becomes the last line of defense, so it has to be small, simple, and effectively immutable.

Structure:

- **Two application banks plus a bootloader region.** The bootloader lives in a protected region that is never erased or written during a normal field update. The two application banks alternate: the running image is in one, the incoming image is written to the other. The currently-running image is never touched until the new one is validated.
- **A separate, minimally-written metadata region.** This holds the state: which bank is active, which is pending, a validity flag, a sequence counter, and a CRC or hash of each bank. It must be written in a way that survives a power loss mid-write — typically two copies with a sequence number and a checksum, so the bootloader can pick the most recent valid copy. Never rely on a single write being atomic.
- **Validation before commit.** The incoming image is written to the inactive bank, then read back and verified (CRC/hash over the whole image, plus a header check for a magic number, version, and length). Only after verification does the bootloader mark the new bank as "pending" and set a boot-attempt counter.
- **Boot-attempt counter / trial boot.** The bootloader boots the pending image but increments a counter each time. The application, once it has reached a defined "healthy" point (e.g., completed self-test and initialized its watchdog), clears the counter and marks the bank as confirmed. If the counter exceeds a threshold before confirmation — meaning the new image booted but never became healthy — the bootloader reverts to the previous bank.
- **Interrupted transfer handling.** Because the inactive bank is only marked valid after full verification, an interrupted transfer simply leaves the inactive bank invalid; the bootloader keeps booting the old image. The transfer can be resumed or restarted from the host. The key is that "partially written" and "valid" are distinguishable states, and the bootloader never treats a partially written bank as bootable.

The subtle failure modes to design against: a power loss during the metadata write (solved by redundant metadata with sequence numbers), a new image that passes CRC but crashes on boot (solved by the trial-boot counter), and a bootloader bug that bricks the device (mitigated by keeping the bootloader minimal and thoroughly tested, and by never allowing field updates to touch it).

**Possible follow-ups:**
- How would you handle the case where the new image boots and runs but is functionally wrong in a way the self-test doesn't catch?
- What would you put in the bootloader versus the application to keep the bootloader small enough to trust?

## Q3: A junior engineer has written a driver that works reliably on the bench but uses a fixed `k_sleep` delay to wait for a peripheral to become ready after each command, rather than checking a status register or using an interrupt. How would you guide them?

**Answer:** I'd start by acknowledging why the approach is attractive — it's simple, it's easy to read, and on the bench with a known part it works. Then I'd walk through the specific ways it fails, because the goal is for them to see the problem themselves rather than just being told "don't do that."

The failure modes:

- **It's not guaranteed to be long enough.** The datasheet's "typical" ready time is not the worst case. Across temperature, supply voltage, and part-to-part variation, the real ready time can exceed the fixed delay, and the driver then reads garbage intermittently — the worst kind of bug, because it passes on the bench and fails in the field.
- **It's almost always too long.** A fixed delay sized for the worst case wastes CPU time on every command. In a system with a real-time loop or a power budget, that's a real cost.
- **It hides the actual handshake.** The status register or ready signal is the peripheral telling you it's done. Ignoring it means you're not actually synchronizing with the hardware, you're guessing.

The better pattern depends on context. If the peripheral has a status register, poll it with a bounded timeout — not an infinite loop, and not a fixed sleep, but a loop that checks the register and gives up after a defined maximum, returning an error. If the peripheral has an interrupt line, use it and block the calling thread on a semaphore or event with a timeout. In Zephyr, that's typically a `k_sem_take` with a timeout, signaled from the ISR. If the operation is short and the thread is high-priority, a bounded busy-poll on the status register can be acceptable, but only with a timeout and only when the wait is genuinely short.

I'd also point out that the timeout path matters: what does the driver do if the peripheral never becomes ready? Returning an error and letting the caller decide is far better than hanging or silently proceeding.

The way I'd frame it for a junior engineer: the fixed delay is a guess about hardware timing, and firmware shouldn't guess about hardware timing when the hardware provides a way to know. Then I'd pair with them to convert one driver as an example, so they see the pattern rather than just the principle.

**Possible follow-ups:**
- How would you choose the timeout value for the bounded poll, and what would you do if the datasheet doesn't specify a worst case?
- What's the difference between polling a status register in a thread versus in an ISR, and when would each be appropriate?

## Q4: How would you approach designing a watchdog strategy for a device with multiple independent subsystems, each of which needs to prove it's alive, but where a single missed deadline from any one subsystem shouldn't necessarily reset the whole device?

**Answer:** The naive approach — one watchdog, kicked from the main loop — conflates "the main loop is running" with "every subsystem is healthy," and it gives you no information about *which* subsystem failed. The goal is a strategy that detects a hung subsystem, degrades gracefully where possible, and only resets the whole device when the failure is severe enough to warrant it.

The structure I'd use:

- **Per-subsystem liveness tracking.** Each subsystem (sensor task, comms task, control loop, logging) has a way to report that it completed its work — a counter it increments, a timestamp it updates, or a flag it sets. This is the raw evidence of liveness.
- **A supervisor that aggregates.** A dedicated supervisor task (or a low-priority monitor) periodically checks each subsystem's liveness against its expected deadline. It knows the *policy*: which subsystems are critical (a missed deadline means the device is unsafe and must reset or enter a safe state) and which are non-critical (a missed deadline means degrade — disable the feature, flag it to the user, attempt a restart of just that subsystem).
- **A single hardware watchdog kicked by the supervisor, not by the subsystems.** The supervisor kicks the watchdog only if all *critical* subsystems are alive. Non-critical subsystem failures don't prevent the kick; they trigger degradation instead. This decouples "the device is fundamentally healthy" from "every feature is working."
- **Windowed watchdog where available.** A windowed watchdog catches both "too late" and "too early" kicks, which detects a runaway supervisor that's kicking in a tight loop without actually checking anything.

The key design decision is the policy table: for each subsystem, what's the deadline, what's the consequence of missing it, and what's the recovery action. That table is where the engineering judgment lives, and it should be reviewed against the risk analysis — a critical monitoring function missing its deadline is a different event from a logging function missing its deadline.

The trade-off is complexity: a supervisor adds a task and a policy layer, and it can itself become a single point of failure. So the supervisor must be simple, its own liveness must be covered by the hardware watchdog, and the policy must be conservative — when in doubt, a missed critical deadline should reset rather than silently continue.

**Possible follow-ups:**
- How would you prevent the supervisor from being starved by a higher-priority task that's spinning?
- What would you log when a subsystem misses its deadline, and how would you make sure that log survives the reset?

## Q5: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first thing to recognize is that "attaching the debugger" changes several things at once: it halts and single-steps the CPU, it changes timing, it may disable or slow low-power modes, it can mask certain faults, and it often changes the memory layout or the contents of uninitialized RAM. So the debugging strategy is to figure out *which* of those differences is masking the bug.

My approach, roughly in order:

- **Characterize the difference.** Does the bug disappear with the debugger merely *connected* but not halted, or only when single-stepping? If merely connecting fixes it, the cause is likely electrical or timing (the debug probe holds a line, changes a clock, or prevents a sleep mode). If only single-stepping fixes it, it's a timing or race condition.
- **Look at low-power and clock behavior first.** Debuggers frequently prevent the core from entering deep sleep, or keep a clock running that would otherwise be gated. A bug that only appears standalone is very often a sleep/wake or clock-gating issue — a peripheral that isn't ready after wake, a register that loses state in a low-power mode, or a timing assumption that holds only when the clock is stable.
- **Look at timing-sensitive code.** Race conditions, missing synchronization, and marginal setup/hold timing all behave differently when the CPU is slowed by debugger overhead. If the bug is a race, adding instrumentation (a GPIO toggle, a counter, a timestamp) rather than a debugger is the way to see it — the instrumentation changes timing less than a debugger does, and it works standalone.
- **Check uninitialized memory and stack.** A debugger can zero or leave different contents in RAM. A bug that depends on an uninitialized variable or a stack that happens to be clean under the debugger will misbehave standalone. Compiler warnings, static analysis, and initializing RAM to a known pattern can expose this.
- **Use persistent logging and fault capture.** Since the bug won't reproduce under the debugger, capture evidence in the field: a ring buffer in RAM that survives reset (or is written to flash), fault handlers that record the fault status registers and stack, and a way to retrieve that log after the fact. This turns an unreproducible bug into a post-mortem.
- **Reproduce with the debugger's effects removed one at a time.** If you suspect the debugger is masking a sleep issue, disable sleep in firmware and see if the bug disappears — that confirms the hypothesis without needing the debugger.

The discipline is to change one variable at a time and to prefer instrumentation that works standalone over the debugger, because the debugger is precisely the thing that's hiding the bug.

**Possible follow-ups:**
- How would you design a fault-logging mechanism that survives a reset and can be retrieved without a debugger?
- If you suspect the bug is a race condition, how would you go about proving it rather than just suspecting it?
