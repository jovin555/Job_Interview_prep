## Q1: You're designing a Zephyr RTOS-based system where a high-priority sensor task must read data every 1 ms, but a lower-priority task occasionally needs to perform a flash erase that blocks for up to 100 ms. How would you approach this scheduling conflict?

**Answer:** The core issue is that a blocking flash operation in a lower-priority thread can stall the scheduler, preventing the 1 ms sensor task from running on time. I'd approach this in layers. First, I'd check whether the flash erase can be performed by the flash controller's hardware directly, with the CPU free to continue executing — many modern MCUs support this, and Zephyr's flash API can be used in an asynchronous or non-blocking manner. If the hardware doesn't support that, I'd look at whether the erase can be broken into smaller chunks (e.g., page-by-page rather than sector-by-sector) so the blocking interval is reduced to something the sensor task can tolerate. If neither is possible, I'd consider moving the flash operation to a dedicated lower-priority thread and using Zephyr's preemptive scheduling with priority inheritance or a mutex to ensure the sensor thread isn't starved. Another option is to use a DMA-based flash write if the controller supports it. Finally, I'd measure the actual worst-case blocking time and verify against the sensor task's deadline — if the 100 ms blocking is unavoidable, the architecture may need to change, such as buffering sensor data in RAM and writing to flash less frequently, or using a dual-bank approach where one bank is erased while the other is active.

**Possible follow-ups:** How would you verify that the sensor task actually meets its 1 ms deadline in practice? What Zephyr kernel configuration options would you check to ensure the scheduler behaves as expected?

## Q2: How would you approach implementing a firmware module that must handle a sensor which occasionally returns invalid data (e.g., out-of-range values or CRC failures), where the device is a medical monitor that must never display a false reading to the clinician?

**Answer:** The fundamental principle is that invalid data must never be presented as valid — the system must fail safe. I'd structure the handling in three layers. First, at the driver level, I'd validate every reading: check the CRC, verify the value is within the sensor's specified operating range, and confirm the reading was acquired within the expected timing window. Any failure here marks the sample as invalid. Second, at the application level, I'd implement a validation policy — for example, a single invalid sample might be discarded and the previous valid sample retained, but consecutive invalid samples would trigger a degraded-state indication. The policy would depend on the clinical context: for a parameter where a single bad reading could mislead, even one invalid sample should flag the display as stale or unreliable. Third, I'd implement a clear user-visible indication of data validity — the display should show something like "signal lost" or "sensor error" rather than a stale or extrapolated value. I'd also log the invalid readings with timestamps for later analysis. The key is that the system must distinguish between "no data" and "bad data" and communicate both clearly, rather than silently substituting values.

**Possible follow-ups:** How would you decide between discarding a single invalid sample versus flagging the display as unreliable? What if the sensor returns a value that is within range but clearly implausible given the recent history?

## Q3: You're reviewing a colleague's firmware code that implements a state machine for a medical device's operational modes (idle, calibration, active monitoring, error). The state machine is implemented as a single switch-case inside a 200-line function, with state transitions scattered across multiple modules via global state variables. How would you approach refactoring this for maintainability and safety?

**Answer:** I'd approach this as a safety-critical refactoring, meaning the first priority is not breaking existing behavior. I'd start by documenting the current state machine — mapping out all states, events, transitions, and the conditions that trigger them — so we have a clear specification to preserve. Then I'd propose a structured refactoring: encapsulate the state variable so it's only accessible through a defined interface, and move the state transition logic into a single module. For the implementation pattern, I'd consider a table-driven approach where transitions are defined in a table (current state, event, guard condition, next state, action), which makes the behavior explicit and auditable. Alternatively, a state machine pattern with separate functions per state can be more readable for complex states. The key is that all transitions must go through one place, and the state variable must not be directly writable from other modules. I'd also add assertions or validation to catch illegal transitions in development. For a medical device, I'd want the state machine to be formally reviewed and tested — ideally with a test matrix that covers every state-event combination, including invalid ones. I'd also make sure that error states are handled explicitly and that the device can never enter an undefined state.

**Possible follow-ups:** How would you handle the case where a transition is triggered from an ISR? Would you use a table-driven approach or a state pattern, and why?

## Q4: You're debugging a firmware issue where a device's ADC readings are correct when the device is first powered on, but drift and become noisy after about 30 minutes of operation. The device is battery-powered and uses a switching regulator. How would you approach this?

**Answer:** This pattern — correct at power-on, then drifting after a warm-up period — suggests a thermal or power-related issue rather than a software logic bug. I'd start by gathering data: log the ADC readings over time, along with the battery voltage, regulator output, and die temperature if available. I'd also check whether the drift correlates with the battery discharging — a switching regulator's output ripple can increase as the input voltage drops, which could couple into the ADC reference or signal path. I'd look at the ADC reference: if it's derived from the battery or an unregulated supply, drift in the supply directly affects readings. I'd also check for thermal effects — the regulator heating up could change component characteristics, or the ADC's internal reference could be temperature-sensitive. On the hardware side, I'd review the PCB layout for the ADC input and reference traces — are they routed near the switching regulator's inductor or switching node? Is the ground plane solid? I'd also check the decoupling on the ADC power pin and whether the reference has adequate filtering. In firmware, I'd verify that the ADC is configured to use the correct reference and that the sampling time is adequate for the source impedance. I'd also consider whether the ADC's internal temperature sensor could be used to compensate if thermal drift is confirmed. The key is to isolate whether this is a reference drift, a signal path issue, or a power integrity problem — each has a different fix.

**Possible follow-ups:** How would you distinguish between a reference voltage drift and noise coupling into the signal path? What measurements would you take to confirm your hypothesis?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd guide the team by reframing the discussion away from personal preference and toward the system's actual requirements. First, I'd ask what the protocol's timing requirements are — what's the worst-case latency for receiving a message, and what's the consequence of missing a byte? For a critical protocol, I'd want to know the maximum allowed response time and the data rate. Then I'd ask both engineers to quantify their approaches: what's the worst-case CPU load for polling at the required rate, and what's the worst-case interrupt latency and ISR execution time for the interrupt-driven approach? I'd also consider the broader system context — are there other time-critical tasks that could be affected by a long ISR, or is the CPU mostly idle? In many cases, the right answer is a hybrid: use interrupts to signal that data is available, but do the processing in a thread or task rather than in the ISR. I'd also consider DMA if the peripheral supports it, which offloads the CPU entirely. I'd encourage the team to prototype both approaches and measure the actual timing — speculation is less useful than data. Finally, I'd make sure the decision is documented with the rationale, so future maintainers understand why the choice was made. The goal is to make the decision based on measured requirements, not on which engineer argues more persuasively.

**Possible follow-ups:** How would you handle the situation if one engineer refuses to accept the measured results? What if the two approaches have similar performance, but one is significantly more complex to maintain?
