# firmware — Day 107

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual interrupt rate, the per-ISR cost (entry/exit overhead plus the work done inside), and the resulting CPU utilization. If servicing every interrupt would consume, say, 30–40% of the CPU, that's a design smell worth addressing. The core techniques are: (1) **Reduce the number of interrupts** by switching the peripheral to a burst or FIFO mode where one interrupt covers many samples, or by using DMA so the CPU is interrupted once per block rather than once per byte/sample. (2) **Make each ISR cheaper** by moving all non-essential work out of the ISR into a deferred context — the ISR should do the minimum (acknowledge the source, move data into a buffer, signal a thread/work queue) and return. (3) **Coalesce or batch** — if the peripheral supports a threshold or watermark interrupt, raise it so you service N items per interrupt. (4) **Consider polling under a timer** if the rate is high but bounded and the latency requirement is loose — sometimes a periodic DMA-driven drain is simpler and cheaper than an interrupt storm. The trade-off is always latency vs. CPU load vs. complexity: DMA plus a deferred consumer gives the best CPU efficiency but adds buffer management and latency; watermark interrupts are a middle ground. I'd also make sure the ISR is marked appropriately and that interrupt priority is set so it doesn't starve critical real-time work, and I'd verify the result with a CPU-load measurement and a latency trace rather than assuming the fix worked.

**Possible follow-ups:** How would you size the DMA buffer or FIFO watermark, and what happens if the consumer thread falls behind? How would you detect at runtime that the ISR is becoming a bottleneck before it causes a missed deadline?

## Q2: You're implementing a bootloader for a device that must support field updates over an unreliable link, and the device has no physical recovery mechanism (no button, no exposed debug header). How would you structure the update and recovery logic so that a failed or interrupted transfer can never leave the device unbootable?

**Answer:** The guiding principle is that the bootloader itself must never be overwritten by a field update, and the application image must never be the only copy of valid code. Concretely: (1) **Keep the bootloader in a protected region** — write-protected via option bytes/fuses or a memory protection unit — so a failed or malicious update can't corrupt it. (2) **Use a dual-bank or A/B scheme** where the new image is written to the inactive bank while the active bank continues to run; the bootloader only switches the boot pointer after the new image passes validation. (3) **Validate before committing** — CRC or cryptographic hash over the whole image, plus a magic/version header, checked by the bootloader before it hands control to the new bank. If validation fails, the bootloader falls back to the known-good bank. (4) **Make the update transactional** — write a "pending" flag and only clear it after the new image has booted and self-tested successfully (a "trial boot" with a watchdog-backed confirmation). If the device resets before confirmation, the bootloader reverts. (5) **Handle partial transfers** — the receiver must be able to resume or restart a transfer without leaving a half-written image marked valid; the validation step naturally rejects an incomplete image. (6) **Provide a last-resort recovery path** — even with no button, a bootloader that always listens on the update interface for a short window at startup, or that enters recovery mode after N failed boots, gives you a way back in. The key insight is that "unbootable" only happens if you allow the only valid image to be destroyed; the A/B plus validation plus trial-boot pattern makes that structurally impossible.

**Possible follow-ups:** How would you decide how many failed boot attempts trigger a rollback, and where would you store that counter safely? What would you do if the bootloader itself needed a field update?

## Q3: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I'd start by acknowledging the part they got right — `volatile` does prevent the compiler from caching the variable in a register or eliminating the access, which is necessary for the ISR and thread to see each other's writes. But I'd explain that `volatile` is not a synchronization primitive: it provides no atomicity (a multi-byte or read-modify-write access can be interrupted mid-way), no memory ordering guarantees (the compiler and CPU can still reorder non-volatile accesses around it), and no mutual exclusion (two writers can still race). On a single-core MCU with a simple flag, it often *appears* to work, which is exactly why it's a dangerous pattern — it fails intermittently under optimization changes, compiler upgrades, or when the data grows beyond a single word. I'd walk them through a concrete failure: a 32-bit counter incremented in the ISR and read in the thread is not atomic, and a struct shared this way can be observed half-updated. Then I'd steer them to the right tools: for a simple flag, an atomic type or a `k_sem`/`k_event`; for data transfer, a proper lock-free ring buffer with acquire/release semantics, or a mutex if the ISR can't block (in which case a semaphore signaled from the ISR and a critical section on the shared data). I'd frame it as "the compiler is only one of the things that can reorder or tear your access — the hardware and the scheduler are the others," and suggest they add a test or a static-analysis rule (e.g., a MISRA or custom check) that flags `volatile` used as the sole cross-context sync. The goal is to teach the mental model, not just patch the one instance.

**Possible follow-ups:** What's the difference between `volatile` and `_Atomic` in C11, and when would you reach for each? How would you review a codebase to find other instances of this pattern?

## Q4: How would you approach designing a firmware module that must log diagnostic events to flash, where the log must survive a power loss mid-write and the flash has limited erase cycles?

**Answer:** Two constraints drive the design: crash consistency and wear. For crash consistency, the key is that a log record must be either fully present or fully absent after a power loss — never half-written and mistaken for valid. The standard approach is a **record-oriented log with a commit marker**: write the record payload first, then write a trailing CRC or a "valid" flag as the last step; on recovery, scan for records with a valid trailer and discard any trailing partial record. Alternatively, use a sequence-numbered scheme where each record carries a monotonically increasing sequence number and a checksum, so recovery can find the last complete record and truncate anything after it. For wear, avoid rewriting the same sector: use a **circular log across multiple erase blocks**, appending records until a block is full, then erasing the oldest block and continuing — this spreads erase cycles evenly. Keep a small RAM or reserved-flash index of the current write position and the oldest valid record so recovery doesn't have to scan the whole log. If the flash is NOR with a large erase block, consider a log-structured layout where you only erase when you must, and batch small records into a block before committing. I'd also think about what "survive power loss" means for the *consumer*: the log reader must tolerate a torn final record, so the recovery scan is part of the design, not an afterthought. Finally, I'd document the endurance budget — records per day × expected lifetime vs. rated erase cycles — and consider whether some events can be aggregated or rate-limited to reduce write volume.

**Possible follow-ups:** How would you handle the case where the log fills up completely — overwrite oldest, stop logging, or something else? How would you test power-loss robustness without physically cutting power thousands of times?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd reframe the disagreement from "which is better" to "which fits the requirements," because both engineers are right in different contexts. First, I'd get the actual numbers on the table: what's the message rate, the worst-case latency budget, the CPU headroom, and the jitter tolerance? Polling gives deterministic, bounded latency *if* the poll loop runs often enough and nothing else blocks it — but it burns CPU and couples responsiveness to loop timing. Interrupts give low latency and free the CPU between events, but add ISR overhead, priority interactions, and shared-data complexity. Then I'd look at the system context: is there a real-time control loop that polling would starve? Are there other interrupt sources that could delay the ISR? Is the protocol state machine complex enough that doing it in an ISR is unwise (in which case a hybrid — ISR captures bytes into a ring buffer, a thread runs the protocol — is often the answer)? I'd ask each engineer to prototype or estimate their approach against the same latency and CPU-load targets, and to identify the failure modes of their choice. Often the decision falls out of the data, and a hybrid (interrupt-driven capture, deferred processing) satisfies both concerns. If it's still a genuine judgment call, I'd make the decision, document the rationale and the assumptions it rests on, and set a review point — "we'll revisit if the message rate exceeds X or CPU load exceeds Y." The leadership part is making sure the team argues about evidence rather than preference, and that whoever "loses" understands the reasoning and is bought into the plan.

**Possible follow-ups:** How would you structure the code so that switching between the two approaches later is not a rewrite? What would you do if the two engineers continued to disagree after the decision was made?
