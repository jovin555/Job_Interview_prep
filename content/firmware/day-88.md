# firmware — Day 88

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: estimate the interrupt rate, the worst-case ISR entry/exit overhead, and the per-interrupt work, then compare that against the CPU budget. If servicing each interrupt individually is genuinely too expensive, the standard pattern is to decouple the interrupt from the work. In the ISR, do only the minimum needed to acknowledge the interrupt and move data out of the peripheral's FIFO or data register — ideally into a ring buffer — then defer all processing to a lower-priority context (a thread, work queue, or bottom-half). This keeps ISR duration bounded and predictable.

If the rate is still too high even for that minimal ISR, the next lever is to reduce the number of interrupts rather than the cost of each one. Options include using the peripheral's FIFO threshold so an interrupt fires only when a batch of samples is available, switching to DMA so the CPU is interrupted once per buffer rather than once per byte or sample, or using a timer-driven poll of the peripheral's status at a fixed cadence when the data rate is bounded and known. Each has trade-offs: FIFO thresholds add latency and require sizing the FIFO against the worst-case burst; DMA adds configuration complexity and buffer management but is usually the right answer for continuous streams; polling trades CPU predictability for latency determinism.

The key design discipline is to keep the ISR's job narrow and measurable — acknowledge, capture, defer — and to instrument the actual ISR duration and interrupt rate on target so the decision is based on measured numbers, not estimates. I'd also make sure the deferred processing path has a bounded backlog policy, because if the producer outruns the consumer, deferring just moves the problem.

**Possible follow-ups:** How would you decide the FIFO threshold or DMA buffer size when the data rate is bursty rather than constant? What would you do if the deferred processing thread still can't keep up with the average rate?

## Q2: How would you approach designing a firmware module that must handle a peripheral whose data-ready signal is edge-triggered, but where the signal can occasionally glitch and produce a spurious edge that does not correspond to valid data?

**Answer:** The core issue is that an edge-triggered signal carries no information about whether the data behind it is valid, so the firmware must validate at the data layer rather than trusting the edge. I'd structure the handler so that an edge is treated as a *hint to check*, not a *guarantee of data*. On each edge, the ISR (or the deferred handler it wakes) reads the peripheral's status register to confirm a data-ready condition is actually asserted, and then reads the data and validates it — checking a status/valid bit if the peripheral provides one, a CRC or checksum if the protocol has one, and range/plausibility checks on the value itself.

For the glitch itself, there are two complementary defenses. First, hardware-side: if the signal is routed to a GPIO, enable the input filter or debounce if the MCU supports it, and confirm the pull resistor and trace routing are appropriate — a glitch on an edge-triggered input is often a hardware symptom (ringing, crosstalk, insufficient drive) that firmware shouldn't be papering over. Second, firmware-side: after servicing an edge, apply a short blanking window during which further edges on that line are ignored, sized to the peripheral's minimum inter-sample interval. This prevents a single physical event from being counted multiple times.

The important architectural point is that the system must remain correct if a spurious edge slips through — the validation layer is the real defense, and the blanking window is an optimization. I'd also log or count spurious edges so that if the rate is non-trivial, it gets escalated as a hardware issue rather than silently absorbed.

**Possible follow-ups:** How would you size the blanking window without risking missing a legitimate closely-spaced sample? What would you do if the peripheral provides no status or validity indication at all?

## Q3: How would you approach sizing thread stacks in a Zephyr RTOS application, and what would you do to verify that your sizing is actually correct rather than just "probably enough"?

**Answer:** I'd treat stack sizing as a measurement problem, not a guess. The starting point is to enumerate what actually consumes stack in each thread: local variables (especially large buffers and structs passed by value), the call depth of the deepest call chain, and the context-save overhead on that architecture. Zephyr's `CONFIG_THREAD_ANALYZER` and the `k_thread_stack_space_get()` API let you query high-water-mark usage at runtime, and the thread analyzer can report per-thread stack usage, which turns sizing into an empirical exercise.

The practical workflow is: start with a generous estimate, run the system through its worst-case paths — not just the happy path, but error handling, deep call chains, and any path that uses more stack than the common case — and then read the high-water marks. Size each thread with a safety margin above the observed worst case, because the observed maximum is a lower bound on the true maximum; a path not exercised in testing can still consume more. I'd also make sure the margin accounts for interrupt stack usage if interrupts run on the thread's stack on that configuration, and for any library calls (printf-family, floating point, crypto) whose stack consumption is not obvious from the source.

Verification doesn't stop at the bench. I'd enable stack sentinel / canary checking (`CONFIG_STACK_SENTINEL`) and stack overflow detection in test builds so that an overflow is caught as a fault rather than silent corruption, and I'd keep the high-water-mark instrumentation available in debug builds so that as features are added, stack growth is visible before it becomes a crash. The honest answer to "is it correct?" is "it's verified against the paths we've exercised, with a margin, and instrumented to catch the paths we haven't" — and that's a much stronger position than a number that looks plausible.

**Possible follow-ups:** How would you handle a thread whose worst-case stack usage is data-dependent and hard to bound? What's your approach when a library you depend on has undocumented stack consumption?

## Q4: A junior engineer has written a driver that works reliably on the bench but uses a fixed `k_sleep` delay to wait for a peripheral to become ready after each command, rather than checking a status register or using an interrupt. How would you guide them?

**Answer:** I'd start by acknowledging what's right about their instinct: they wanted a deterministic, simple wait, and fixed delays are easy to reason about on a bench where nothing else is competing for time. The conversation is about why that simplicity doesn't survive contact with the real system. The fixed delay is a bet that the peripheral is *always* ready within that time — but the datasheet gives a maximum, not a typical, and the maximum is specified under conditions (temperature, supply voltage, part-to-part variation) that the bench setup doesn't represent. A delay tuned to the bench part will eventually be too short on a slow part or at temperature extremes, and the failure will be intermittent and hard to attribute.

The better pattern depends on what the peripheral offers. If it has a status/ready bit, poll it with a bounded timeout — that's still simple, still deterministic in the sense that it completes as soon as the device is ready, and it fails loudly (timeout) rather than silently proceeding on stale data. If it has an interrupt, use it and block the calling thread on a semaphore or event with a timeout, which frees the CPU instead of sleeping it. Either way, the timeout is the important part: it converts "the device is slow" from a silent corruption into a diagnosable error.

I'd frame it as a correctness issue rather than a style preference, and I'd point at the specific failure mode — a delay that's correct on the bench and wrong in the field — so the lesson generalizes. Then I'd pair with them on converting one instance and let them carry the pattern through the rest of the driver, so they own the fix rather than just being told.

**Possible follow-ups:** How would you choose the timeout value for the bounded poll? What would you do if the peripheral's datasheet doesn't specify a maximum ready time?

## Q5: How would you approach a situation where you discover, late in a project, that a firmware design decision you made early on is now causing significant problems, and changing it would require rework across several modules?

**Answer:** The first thing is to separate the technical question from the schedule and relationship question, because they need different handling. Technically, I'd want to characterize the problem precisely before proposing anything: what specifically is failing or becoming unmaintainable, what the cost of *not* changing is (defects, missed requirements, future velocity), and what the realistic options are — full rework, a targeted refactor that contains the damage, or a documented workaround with a plan to address it later. Vague "this design is bad" doesn't get a decision; a concrete comparison of options with costs and risks does.

Then I'd bring it to the people who own the schedule and the risk, early and with the analysis in hand, rather than either silently absorbing the rework or silently shipping the workaround. The framing matters: this is a decision about where to spend the remaining schedule, and the people accountable for the project should make it with full information. I'd be explicit that the decision was mine and that I'm not looking to assign blame — the goal is the best outcome from here.

If the decision is to contain rather than fully rework, I'd define the containment boundary clearly: which modules get the targeted fix, which get a documented interface that isolates the bad decision, and what the trigger is for revisiting it. That way the technical debt is visible and bounded rather than diffuse. And I'd capture the lesson — what signal was available early that would have caught this — so the next design review benefits from it. The behavioral core is: own the decision, bring data not opinion, let the accountable people decide, and make whatever is chosen explicit and bounded.

**Possible follow-ups:** How would you handle it if the decision-makers choose the workaround and you believe the risk is understated? What would you do differently in the early design phase to catch this kind of issue sooner?
