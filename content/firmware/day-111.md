# firmware — Day 111

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual interrupt rate, the worst-case ISR duration, and the resulting CPU utilization. If servicing every interrupt would consume, say, more than a small fraction of the CPU budget, the design needs to change. The standard approaches, roughly in order of increasing complexity:

1. **Reduce the number of interrupts, not the work.** Many peripherals can be configured to assert an interrupt only when a FIFO reaches a threshold or a transfer completes, rather than per byte or per sample. This is usually the cheapest fix and should be checked first — the hardware may already support batching.
2. **Move work out of the ISR.** Keep the ISR minimal: acknowledge the source, move data or a pointer into a queue, and return. The heavy processing happens in a deferred context (a thread or work queue). This doesn't reduce the interrupt *count*, but it reduces the time spent with interrupts disabled, which is often the real constraint.
3. **Use DMA.** For streaming data, DMA lets the peripheral write directly to memory and interrupt only on buffer half/full/complete events. This collapses thousands of per-sample interrupts into a handful per buffer. The trade-off is buffer sizing and the need to handle the half-transfer and wrap-around cases correctly.
4. **Coalesce in hardware or with a timer.** If the peripheral can't batch, a periodic timer can drain a hardware FIFO or a small ring buffer at a fixed rate, trading latency for CPU load.
5. **Reconsider the requirement.** If the data rate genuinely requires per-event handling at a rate the CPU can't sustain, that's an architecture problem — perhaps the wrong MCU, or a design that should push processing to a co-processor or FPGA.

The key reasoning is to separate *interrupt rate* from *work per event*: batching and DMA attack the rate, deferral attacks the duration, and both should be evaluated against the latency requirements of the system before committing.

**Possible follow-ups:** How would you decide the DMA buffer size when the consumer thread runs at a much lower priority than the producer? What would you do if the peripheral's FIFO threshold is fixed and too low to help?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first instinct should be to enumerate *what the debugger changes* rather than to start guessing at the firmware. The debugger alters timing (halting the core, slowing execution), may disable or mask low-power modes, may keep certain clocks or peripherals alive, can change the state of uninitialized memory, and can affect the watchdog. Any of these can mask a real bug.

A structured approach:

1. **Characterize the difference.** Does the failure disappear with the debugger merely *attached* but not halted, or only when single-stepping? That distinction narrows whether it's timing, power state, or something the debug probe holds in reset.
2. **Reproduce without the debugger but with instrumentation.** Add GPIO toggles or a lightweight trace buffer in RAM that can be dumped after the fact. This preserves timing better than a debugger while still giving visibility.
3. **Suspect timing-dependent bugs first.** Race conditions, missing synchronization, and insufficient settling delays are the usual culprits. Check ISR/thread interactions, volatile/atomic correctness, and any place where code assumes a peripheral is ready sooner than it is.
4. **Suspect power and clock state.** If the debugger keeps a clock or regulator alive, a bug in the low-power entry/exit sequence or a peripheral that loses state in sleep will only appear standalone. Verify the wake-up path and peripheral re-initialization.
5. **Suspect the watchdog.** Debuggers often freeze or disable the watchdog; a marginal kick timing will only bite in the field.
6. **Check uninitialized memory and stack.** The debugger can zero or perturb RAM; a latent bug in an uninitialized variable may only manifest when the memory contents differ.

The discipline is to treat "works under debugger" as evidence that the bug is timing-, power-, or state-dependent, and to build instrumentation that observes the standalone case without perturbing it as much as a debugger does.

**Possible follow-ups:** How would you build a trace buffer that survives a reset so you can inspect the last events before the failure? What's the risk of using printf-style logging to debug a timing-sensitive issue?

## Q3: How would you approach sizing thread stacks in a Zephyr RTOS application, and what would you do to verify that your sizing is actually correct rather than just "probably enough"?

**Answer:** Stack sizing should be treated as an engineering estimate followed by measurement, not a guess. The approach:

1. **Estimate from the call graph.** For each thread, identify the deepest call chain, including ISR entry if the thread can be preempted, and sum the worst-case frame sizes. Add space for saved context, local buffers, and any library calls (printf-family functions are notorious stack hogs). This gives a starting number, not a final one.
2. **Add margin deliberately.** A common practice is to size to the estimate plus a safety factor, but the margin should be justified — e.g., accounting for compiler differences between debug and release builds, which can change frame sizes significantly.
3. **Measure at runtime.** Zephyr provides stack usage instrumentation: enable the stack sentinel / stack usage reporting options and use `k_thread_stack_space_get()` or the high-water-mark reporting to see how close each thread actually came to its limit. Run the measurement under worst-case load, not just nominal operation — the deepest stack usage often occurs on error paths or during initialization.
4. **Test the boundaries.** Exercise error paths, logging, and any code that runs rarely but deeply. A stack that's fine in normal operation can overflow the first time an error handler runs.
5. **Use guard mechanisms.** Stack sentinels or MPU-based stack guards turn a silent overflow into a detectable fault, which is far better than corruption that manifests elsewhere.
6. **Re-verify after changes.** Stack sizing is not a one-time task; adding a feature or a library call can invalidate it. Build the measurement into the test process.

The reasoning is that stack overflow is one of the hardest bugs to diagnose after the fact, so the investment in measurement and guards pays for itself. "Probably enough" is exactly the posture that produces intermittent corruption in the field.

**Possible follow-ups:** How would debug vs. release build differences affect your sizing, and which would you size for? What would you do if a thread's high-water mark is uncomfortably close to its limit but you can't easily reduce its stack usage?

## Q4: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I'd start by acknowledging the part they got right — `volatile` does prevent the compiler from caching the value in a register or eliminating the access, which is necessary for the ISR and thread to see each other's writes. The gap is that `volatile` provides *visibility* but not *atomicity* or *ordering*, and those are what actually make shared-state communication correct.

The concrete failure modes to walk through with them:

- **Non-atomic access.** If the shared variable is wider than the architecture's atomic word size, or if the update is a read-modify-write (e.g., a counter increment), the ISR can fire mid-update and the thread can observe a torn or lost value. `volatile` doesn't prevent this.
- **Compiler and CPU reordering.** `volatile` constrains accesses to that variable, but it doesn't prevent the compiler or CPU from reordering *other* memory operations around it. If the ISR writes a data buffer and then sets a flag, the flag can become visible before the buffer writes on a weakly-ordered core. A memory barrier or a proper synchronization primitive is needed.
- **Lost wakeups and missed events.** A flag polled in a loop can miss an event if the ISR sets it between the thread's check and its sleep. Proper synchronization (a semaphore, event, or message queue) handles this.

The better design depends on intent: if it's a single flag or counter, use the kernel's atomic operations (`atomic_set`, `atomic_inc`) which are both visible and atomic. If it's signaling an event, use a semaphore or `k_event`. If it's passing data, use a message queue or a properly synchronized ring buffer. In Zephyr, these primitives are cheap and well-tested; there's rarely a reason to hand-roll synchronization with a bare `volatile`.

I'd frame it as: "`volatile` is a tool for telling the compiler the variable can change unexpectedly — it's not a synchronization primitive. Let's look at what this variable is actually doing and pick the primitive that matches." Then I'd pair with them to refactor one instance and let them apply the pattern to the rest, so the lesson sticks.

**Possible follow-ups:** Can you give an example where `volatile` alone would pass testing but fail in the field? How would you explain the difference between visibility and atomicity to someone new to embedded concurrency?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd resist framing this as a binary vote and instead drive it toward a decision based on the system's actual requirements. Both positions have legitimate merit, and the right answer usually depends on specifics the team hasn't yet made explicit.

My approach:

1. **Surface the requirements.** What's the worst-case latency the protocol must meet? What's the message rate and burst behavior? What's the CPU budget, and what else runs on the system? Is there a hard real-time deadline, or is "responsive enough" the bar? Write these down so the discussion is about numbers, not preferences.
2. **Evaluate both against the requirements.** Polling is simple, deterministic, and easy to reason about — but it burns CPU when idle and can miss events if the poll interval is too coarse. Interrupts are responsive and efficient at low rates, but add ISR latency, concurrency complexity, and can become a bottleneck at high rates. Neither is universally better; the question is which failure mode the system can tolerate.
3. **Consider a hybrid.** Often the best answer is a mix: interrupt-driven reception with a deferred processing context, or polling at a rate derived from the protocol's timing requirements. The team may be arguing over a false dichotomy.
4. **Prototype the risky part.** If the disagreement hinges on an unmeasured assumption (e.g., "interrupts will be too slow"), a small benchmark on the target hardware settles it faster than debate.
5. **Make the decision explicit and documented.** Once decided, record the rationale and the requirements it was based on, so the decision can be revisited if requirements change — and so the engineer whose approach wasn't chosen understands it was evaluated fairly.

Throughout, I'd keep the tone collaborative: the goal is the right design, not winning the argument. I'd also make sure both engineers feel their concerns were heard, because the one whose approach isn't chosen will still need to implement and maintain it.

**Possible follow-ups:** What would you do if the benchmark results are ambiguous and the team is still split? How would you handle it if the chosen approach later turns out to be wrong — how do you revisit the decision without it becoming an "I told you so" moment?
