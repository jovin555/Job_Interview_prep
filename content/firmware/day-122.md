# firmware — Day 122

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first thing I'd do is quantify the problem rather than assume it: measure the actual ISR entry/exit overhead, the per-interrupt work, and the resulting CPU utilization at the expected event rate. If servicing every event individually is genuinely too expensive, there are several standard levers, and the right one depends on what the peripheral and the data actually require.

The most common approach is to move from per-event interrupts to block or burst transfers using DMA. Instead of interrupting on every byte or sample, configure the DMA controller to move a block of data into a buffer and interrupt only on completion (or on half-transfer, so you can process one half while the other fills). This collapses N interrupts into one or two per block, and the CPU only touches the data in bulk. The trade-off is added latency — you don't see individual samples until the block completes — so this only works if the consumer can tolerate block-granularity latency.

If DMA isn't available or the peripheral doesn't support it, the next lever is to reduce the work done per interrupt to the absolute minimum: the ISR should do nothing but acknowledge the source, grab the data word, and push it into a lock-free circular buffer, then return. All parsing, validation, and processing moves to a deferred context (a thread or work queue) that drains the buffer in batches. This doesn't reduce the interrupt *count*, but it dramatically reduces the time spent per interrupt, which is often the real bottleneck.

A third option, if the hardware supports it, is to use the peripheral's FIFO and set the interrupt threshold so it only fires when the FIFO is partially full, rather than on every single event. Many UARTs, ADCs, and SPI peripherals have this. Combined with a larger FIFO depth, this directly cuts the interrupt rate.

Finally, I'd consider whether the event rate itself can be reduced at the source — for example, decimating in hardware, lowering the sample rate if the application doesn't actually need it, or using a hardware filter/counter that only interrupts on a threshold crossing rather than every sample. The key is to pick the approach based on the latency the consumer can tolerate and the hardware capabilities, and to verify with measurement (CPU load, worst-case ISR latency, buffer high-water marks) that the chosen design actually meets the timing budget rather than just looking plausible on paper.

**Possible follow-ups:**
- How would you size the DMA buffer and choose between half-transfer and full-transfer interrupts, and what would drive that choice?
- If the deferred processing thread can't keep up with the average data rate, how would you detect that and what would you do about it?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first principle is to recognize *why* attaching a debugger changes behavior: it slows execution, it may halt the core at breakpoints, it changes timing, it can mask or expose race conditions, and it may alter power state or clock behavior. So the debugging strategy is to figure out which of those differences is masking the bug, then reproduce the bug without the debugger.

I'd start by characterizing the failure precisely: when does it happen, how often, what's the symptom, and is it correlated with anything (temperature, time since boot, a particular operation, a particular power state)? Then I'd try to reproduce it standalone with instrumentation that doesn't perturb timing as much as a debugger — for example, a GPIO toggled at key points and captured on a scope or logic analyzer, or a lightweight ring buffer in RAM that logs events and can be dumped after the fact. A UART log at low baud is often too slow and can itself change timing, so I'd be careful there.

Common root causes for "works with debugger, fails standalone" include: a race condition that the debugger's slowdown happens to serialize; a timing violation (setup/hold, or a peripheral that needs a delay the debugger inadvertently provides); an uninitialized variable that happens to be zero when the debugger's memory layout differs; a stack overflow that the debugger's extra stack usage or different memory layout masks; and power-management or clock issues where the debugger keeps a clock alive or prevents a sleep state.

I'd also check whether the debugger is holding a peripheral out of reset, keeping a clock running, or preventing a low-power mode — those are very common. And I'd look at whether the failure correlates with the device entering or leaving a sleep state, since debuggers frequently disable sleep.

The systematic approach is: narrow the timing window (does it fail more at higher clock speeds? at lower supply voltage? after a specific operation?), use non-intrusive instrumentation to capture the state at failure, and form a hypothesis about which debugger-induced difference is masking it. Then design a test that removes that difference without the debugger — for example, adding a deliberate delay in the suspect path to see if the bug disappears, which would confirm a timing/race hypothesis.

**Possible follow-ups:**
- How would you use a logic analyzer or GPIO toggling to narrow down a race condition without perturbing the timing you're trying to observe?
- What are some specific ways a debugger can mask a stack overflow, and how would you detect stack overflow in the field?

## Q3: How would you approach deciding what belongs in a bootloader versus what belongs in the application, for a device that must support field updates?

**Answer:** The guiding principle is that the bootloader should contain only what is needed to reliably get a valid application image running and to recover from a failed update — nothing more. Everything else belongs in the application, because the bootloader is the hardest thing to update and the most dangerous thing to get wrong.

Concretely, the bootloader needs: the reset vector and startup code, clock and basic peripheral initialization sufficient to access the update medium (flash, external memory, or a communication interface), the logic to decide which image to boot (bank selection, validity checks), image validation (CRC or cryptographic signature), the update/recovery state machine, and a minimal communication path for receiving updates if the update is delivered by the bootloader itself. It should be small, simple, and heavily reviewed, because a bug there can brick the device.

The application owns everything else: the full feature set, the user interface, the main communication stacks, sensor drivers, logging, and — importantly — the decision of *when* to request an update and the logic to stage the new image. A common and robust pattern is for the application to receive and stage the new image (writing it to the inactive bank, verifying it), then set a flag and reboot into the bootloader, which only has to validate and swap. This keeps the bootloader's job minimal and puts the complex, frequently-changing logic in the application where it can be updated.

Things I'd deliberately keep out of the bootloader: complex protocol stacks, large feature sets, anything that depends on configuration that might change, and anything that isn't strictly needed to boot or recover. The bootloader should be boring and stable.

The trade-off is that if the update transport itself must work when the application is corrupt (which is the whole point of a recovery path), then the bootloader does need enough of a communication path to receive a recovery image. That's the one place where the bootloader legitimately grows — but it should still be the minimal viable transport, not the full application protocol.

**Possible follow-ups:**
- How would you decide whether the bootloader or the application should perform image validation, and what are the implications of each choice?
- If the bootloader must contain a recovery communication path, how would you keep that path minimal and secure?

## Q4: How would you approach designing a firmware module that must log diagnostic events to flash, where the log must survive a power loss mid-write and the flash has limited erase cycles?

**Answer:** There are two distinct problems here — power-loss atomicity and wear — and they need to be solved together, because the naive approach to one often worsens the other.

For power-loss atomicity, the core idea is to never overwrite the only valid copy of anything. A common pattern is a log-structured or append-only scheme: write records sequentially into a region, and treat a record as valid only if it's complete and passes a checksum. On power loss mid-write, the partially written record simply fails its checksum on the next boot and is discarded — the previous records are untouched. The write pointer is recovered by scanning for the last valid record, or by storing a small, atomically-updated "commit" marker. The key is that the validity of a record is self-contained (length + payload + CRC), so a torn write is detectable.

For wear, the issue is that NOR flash has limited erase cycles per sector, and a log that keeps appending to the same sector will wear it out. The standard solution is to spread writes across the region — a circular log over multiple sectors, erasing a sector only when it's full and its oldest records are no longer needed. This gives wear-leveling across the region. If the log is small and the region is large, this is usually sufficient; if not, a more sophisticated wear-leveling scheme (or a filesystem designed for flash, like a log-structured or copy-on-write FS) may be warranted.

There's a tension: erasing a sector is a relatively slow operation, and if power is lost during an erase, that sector's contents are indeterminate. So the design must ensure that erasing a sector never destroys the only copy of data you need — which means the circular log must only erase a sector whose records are either already consumed or duplicated elsewhere, and the erase must be treated as a non-atomic operation that the recovery logic can handle (e.g., by treating an erased sector as empty and re-deriving the write pointer).

I'd also consider: record size and alignment (write in aligned chunks to avoid read-modify-write on flash that requires it), whether the log needs to be readable after a crash (so the recovery scan must be fast and bounded), and whether the log needs a sequence number to preserve ordering across resets. And I'd verify the whole thing with fault injection — cutting power at random points during writes and erases and confirming the log always recovers to a consistent state.

**Possible follow-ups:**
- How would you recover the write pointer after a power loss without scanning the entire log region on every boot?
- What would you do if the log's write rate is high enough that wear-leveling across the region still isn't enough to meet the device's lifetime requirement?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd start by reframing the disagreement away from "polling vs interrupts" as an abstract preference and toward the actual requirements of this protocol on this hardware. Both engineers are making valid points, and the right answer usually depends on specifics that neither position alone captures.

First, I'd get the requirements on the table explicitly: what's the required response latency, what's the worst-case message rate, what's the CPU budget, what other tasks share the core, and what's the consequence of a missed message? "Predictable" and "responsive" are both desirable, but they can conflict, and the requirements should tell us which matters more and by how much.

Then I'd have each engineer articulate the failure modes of their preferred approach. Polling's weakness is latency and CPU waste — if the poll interval is too long you miss or delay messages, and if it's too short you burn CPU that other tasks need. Interrupts' weakness is jitter and complexity — ISR entry/exit overhead, priority interactions, shared-data synchronization, and the risk of an ISR starving lower-priority work. A good decision process makes both engineers confront the other's concerns concretely rather than defending a position.

I'd also point out that this is often not a binary choice. A very common and often best answer is a hybrid: interrupt-driven reception into a buffer (so you don't miss events and latency is low), with the actual protocol processing deferred to a thread or work queue (so the ISR is short and the processing is predictable and testable). That gets responsiveness at the hardware boundary and predictability in the processing. Similarly, transmit-side might be polled or interrupt-driven depending on whether the protocol is latency-sensitive on transmit.

To make the decision concrete and defuse the disagreement, I'd propose a small experiment: prototype both (or the hybrid) on the actual hardware, measure worst-case latency, CPU utilization, and jitter under realistic load, and let the data decide. This turns an opinion clash into an engineering question, and it gives both engineers ownership of the outcome rather than a winner and a loser. I'd also make sure the decision and its rationale are documented, so it's not relitigated later without new information.

Finally, I'd watch for the underlying dynamic — two senior engineers disagreeing can become personal if not managed. My job is to keep it about the requirements and the data, make sure both feel heard, and be willing to make the call if the data is inconclusive, while being clear about the criteria I used.

**Possible follow-ups:**
- If the prototype measurements are ambiguous — say polling meets latency but uses more CPU, interrupts use less CPU but have worse jitter — how would you break the tie?
- How would you structure the code so that the polling-vs-interrupt decision is isolated and could be changed later without rewriting the protocol logic?
