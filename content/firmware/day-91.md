# firmware — Day 91

## Q1: How would you approach designing a firmware module that must handle a peripheral whose data-ready signal is edge-triggered, but where the signal can occasionally glitch and produce a spurious edge that does not correspond to valid data?

**Answer:** The core problem is that an edge on the data-ready line is being treated as a promise that valid data exists, when in reality the line is only a hint. I'd separate the *event* from the *validation*: the ISR should do the absolute minimum — timestamp the edge, increment a counter, and signal a deferred context (a work item or a semaphore to a thread) — and never read the data payload inside the ISR itself. That keeps ISR latency bounded and moves the decision-making to a context where I can afford to be careful.

In the deferred handler, I'd validate before consuming. That means checking the peripheral's own status register or a data-valid bit if one exists, checking a frame counter or sequence number if the protocol provides one, and verifying a CRC or checksum on the payload. If the peripheral offers no such validation, I'd add a plausibility check — range limits, expected sample interval, monotonicity — and treat anything outside those bounds as a glitch to be discarded rather than acted on. A spurious edge that produces no valid data should be a no-op, not an error path that cascades.

I'd also add debouncing at the appropriate layer. If the glitch is electrical (a slow edge, ringing, or crosstalk), a small RC filter or a Schmitt-trigger input is the right fix, not firmware. If the glitch is a genuine but meaningless pulse from the peripheral, a short blanking window after each accepted edge — implemented as a timestamp comparison, not a blocking delay — prevents counting the same event twice. The key discipline is that the firmware should be robust to the line being noisy, because the hardware may be revised later and the firmware shouldn't silently depend on a clean signal.

Finally, I'd instrument it. A counter of edges seen versus edges accepted tells you whether glitching is rare-and-benign or a symptom of a deeper problem, and that counter is exactly what you want in a diagnostic log when someone reports "the readings look wrong sometimes."

**Possible follow-ups:** How would you decide whether the glitch filtering belongs in hardware, in the ISR, or in the deferred handler? What would you do if the peripheral has no status register or CRC and the only signal you get is the edge itself?

## Q2: How would you approach sizing thread stacks in a Zephyr RTOS application, and what would you do to verify that your sizing is actually correct rather than just "probably enough"?

**Answer:** I'd start from a structural estimate and then verify empirically, because the two rarely agree and the empirical number is the one that matters. Structurally, each thread's worst-case stack is the sum of its call chain's deepest path — local variables, saved registers, and any large buffers — plus the context-save frame the kernel pushes on a switch, plus interrupt stack usage if the architecture shares the interrupt stack with thread stacks. The trap is that the deepest call chain is often not the obvious one: a logging call, a printf-family function, or a crypto routine can dwarf the "real" work. So I'd walk the call graph for each thread and find the actual worst case, not the typical case.

Then I'd verify. Zephyr gives you `CONFIG_THREAD_ANALYZER` and the `k_thread_stack_space_get()` API, and the thread analyzer can report high-water marks. I'd run the system through its worst-case scenarios — not just idle operation but the burst paths, error paths, and the startup sequence — and read the high-water mark for each thread. The margin I want is not "a few bytes free" but a deliberate headroom, because a future change to a library or a compiler upgrade can shift stack usage and you don't want the margin to be zero. I'd also enable stack sentinel checking (`CONFIG_STACK_SENTINEL`) during development so an overflow traps immediately rather than corrupting an adjacent thread's stack and producing a mystery fault hours later.

The subtlety is that high-water marks only tell you about the paths you exercised. So I'd combine the measurement with a review of the paths that are hard to exercise — the fault handlers, the rare error branches, the initialization that only runs once — and size those conservatively. And I'd document the number and the reasoning, because the next person to add a feature to that thread needs to know what margin they're spending.

**Possible follow-ups:** How would you handle a thread whose worst-case stack usage depends on data received at runtime, such as a parser with recursion? What's your approach when the measured high-water mark is uncomfortably close to the limit but you can't easily reduce the call depth?

## Q3: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** The debugger changes timing, power state, and sometimes memory contents, so the first job is to figure out *which* of those is masking the bug. The classic causes are a race condition that the debugger's slowdown happens to serialize away, a timing-sensitive peripheral interaction where the debugger's halt gives the hardware time to settle, a low-power mode that the debugger prevents the device from entering, and uninitialized memory that happens to contain different values under the debugger.

I'd start by narrowing the delta. Does the bug disappear if I attach the debugger but *don't* halt — just connect and let it run? Does it disappear if I add a delay loop instead of a breakpoint? If a simple delay masks it, that points at a race or a settling-time issue rather than at the debugger's memory effects. If it only disappears when the debugger is actually halting the core, that points at something the halt is doing — a watchdog being serviced, a low-power transition being blocked, or a peripheral that needs the core to be running to complete a handshake.

Then I'd attack the low-power angle specifically, because it's the most common culprit and the easiest to overlook. Many debug probes keep the debug clock alive and prevent deep sleep, so a bug that only manifests in a sleep state will never reproduce with the probe attached. I'd check whether the device is actually entering the sleep mode I think it is — measure current, or toggle a GPIO on entry and exit — and if the debugger is blocking it, I'd use a different observation method: a logic analyzer on the relevant pins, or a RAM-based trace buffer that survives the event and can be read out afterward.

For the race-condition case, the tool is instrumentation that doesn't perturb timing much: a GPIO toggle at the suspect points, a ring buffer of timestamps in RAM, or a hardware trace facility if the MCU has one. The goal is to observe the sequence without changing it. And I'd be systematic about reproducing it standalone — run the same scenario many times, vary temperature and supply, and log enough state to know what the device was doing when it misbehaved.

**Possible follow-ups:** How would you capture evidence of a bug that only occurs in a sleep mode the debugger prevents? What would you do if the misbehavior is a hard fault that only happens standalone — how would you get a post-mortem?

## Q4: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first question is whether the interrupt rate is genuinely irreducible or whether the peripheral is being configured to interrupt more than necessary. Many peripherals can be set to interrupt on a FIFO threshold or a watermark rather than on every byte or every sample, which cuts the interrupt count by an order of magnitude with no loss of data. So before designing around a high rate, I'd check whether the rate can be reduced at the source — that's usually the cheapest fix and it's easy to miss.

If the rate is genuinely high, the answer is to move the bulk data path off the CPU entirely. DMA is the right tool: the peripheral writes into a buffer, and the CPU is interrupted only on buffer-half or buffer-complete events rather than per sample. That converts an N-interrupts-per-second problem into a handful of interrupts per second, and the ISR's job shrinks to bookkeeping — advancing a pointer, signaling a consumer, re-arming the DMA. The buffer is typically a circular or ping-pong arrangement so the DMA never has to stop while the consumer catches up.

Where DMA isn't available or isn't sufficient, I'd look at interrupt coalescing: letting the peripheral's own FIFO accumulate and servicing it on a timer or on a threshold, accepting a small bounded latency in exchange for a large reduction in interrupt overhead. The trade-off to be explicit about is latency versus throughput — coalescing adds latency, and if the consumer has a hard deadline, that deadline sets the maximum coalescing window.

I'd also make sure the ISR itself is minimal and that the real work happens in a deferred context, so that even if interrupts do arrive faster than expected, the ISR cost per interrupt is small and bounded. And I'd measure rather than assume: profile the actual CPU time spent in the ISR at the expected rate, and confirm the headroom before committing to the design.

**Possible follow-ups:** How would you size the DMA buffer given a consumer that processes data in bursts? What would you do if the peripheral's FIFO threshold granularity is too coarse for your latency requirement?

## Q5: How would you approach a situation where you discover, late in a project, that a firmware design decision you made early on is now causing significant problems, and changing it would require rework across several modules?

**Answer:** The first thing I'd do is resist the urge to either defend the decision or panic about the rework, and instead get clear on the actual cost and the actual risk. That means quantifying three things: what breaks if we don't change it, what it costs to change it now, and what it costs to change it later. A design decision that's causing problems late in a project is usually causing them because requirements shifted or because a constraint that wasn't visible early became visible — that's normal, and the honest framing is "the decision was reasonable given what we knew, and now we know more."

Then I'd bring it to the people who need to know, early and with the analysis rather than just the problem. That means the project lead and whoever owns the schedule, plus the engineers whose modules would be touched. I'd present the options concretely: fix it properly now, apply a targeted workaround that contains the damage without the full rework, or defer it with a documented risk. Each option has a cost and a risk, and the decision is a project decision, not mine alone — but it's my job to make the trade-offs legible so the decision is informed.

If the call is to fix it, I'd sequence the rework to keep the system working throughout: introduce the new interface alongside the old one, migrate callers one at a time with tests at each step, and only remove the old path when nothing depends on it. That's slower than a big-bang rewrite but it keeps the device shippable and it means a problem in one module doesn't block the others. If the call is to work around it, I'd contain the workaround behind a clear boundary and document why it exists and what would need to change to remove it, so it doesn't quietly become permanent.

Either way I'd capture the lesson — not as blame, but as a note in the design record about what constraint was missed and how to catch it earlier next time. The behavioral point is that owning the decision means surfacing the problem rather than hoping it stays hidden, and being straightforward about the cost.

**Possible follow-ups:** How would you handle it if the project lead decides to defer the fix and you believe the risk is significant? How would you keep the team's confidence in the design process intact after a decision like this turns out to be wrong?
