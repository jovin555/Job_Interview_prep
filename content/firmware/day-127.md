# firmware — Day 127

## Q1: How would you approach implementing a state machine for a device's operational modes where the same event can arrive from multiple sources — a user interface, a communication interface, and an internal timer — and the correct transition depends on which source sent it?

**Answer:** The key insight is that "the same event" from different sources is not actually the same event — it's a distinct event with a source qualifier, and the state machine should model it that way rather than collapsing sources into a single event type and then trying to disambiguate inside the transition logic. I'd define the event as a struct or tagged type carrying both an event ID and a source ID, and make the transition table keyed on the pair (current state, event ID, source). That keeps the decision logic declarative and inspectable instead of buried in nested conditionals.

The second concern is arbitration when two sources produce events close together. A UI button press and a comms command arriving in the same tick both want to drive a transition; the state machine needs a defined ordering. I'd funnel all events through a single queue so there's one serialization point, and assign priority at enqueue time based on source — typically safety-critical internal timer events first, then comms, then UI, since a human can tolerate a few milliseconds of latency but a timer-driven transition usually can't. The queue also gives you a natural place to log every event with its source, which is invaluable when someone later asks "why did the device go into error mode at 3 a.m.?"

I'd also guard against re-entrancy: a transition handler that itself generates an event (say, entering a state triggers a timer) must not recurse into the state machine synchronously. Either defer the generated event back onto the queue, or use an explicit "pending event" slot processed on the next dispatch cycle. And every transition should be validated — an event from a source that isn't legal in the current state should be logged and dropped, not silently ignored, because silent drops are exactly the kind of thing that turns into an unreproducible field bug.

**Possible follow-ups:** How would you test a state machine with this many source/event combinations without an explosion of test cases? What would you do if a source starts flooding the queue with events faster than the machine can dispatch them?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** The debugger's presence changes timing, power state, and sometimes the memory map, so the first job is to figure out which of those is the actual variable. Attaching a debugger typically halts the core at breakpoints, slows execution, keeps certain clocks or peripherals alive, and may disable low-power modes — so a bug that vanishes under debug is very often a timing or power-state bug rather than a logic bug.

My first move is to stop relying on the debugger for observation and switch to non-intrusive instrumentation: a GPIO toggled at key points and captured on a scope or logic analyzer, or a ring buffer in RAM that the firmware writes to and that I dump after the fact via a serial or comms interface. That preserves the real timing while still giving me visibility. If the device has an SWO or trace capability, that's even better because it's far less intrusive than breakpoints.

Next I'd systematically eliminate the debugger's side effects. Does the failure correlate with entering a low-power mode? I'd force the device to stay awake and see if the bug disappears — if it does, the issue is in the sleep/wake path, not the logic. Does it correlate with a watchdog? Debuggers often freeze or service the watchdog; I'd check whether the standalone failure is actually a reset by reading reset-cause registers on the next boot. Does it correlate with clock frequency or supply voltage? I'd sweep those.

I'd also look hard at anything that depends on uninitialized memory or on precise interleaving — those are the classic "works under debugger" bugs, because the debugger's slower execution and memory writes perturb the exact conditions. Running the same firmware with optimization levels varied, and with a memory-fill pattern on startup to expose uninitialized reads, often flushes them out. The discipline is: don't chase the symptom, chase the difference the debugger introduces, and remove each difference one at a time.

**Possible follow-ups:** How would you capture a trace of what happened before a reset if the device has no external debug header in the field? What reset-cause or fault-status registers would you check first, and what would each tell you?

## Q3: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first question is whether the interrupt is telling me something I actually need per-event, or whether it's just a "data is available" notification where the useful unit is a batch. If it's the latter, the right answer is almost always to move the data with DMA and let the interrupt fire per half-buffer or per full-buffer rather than per sample — that collapses thousands of interrupts into a handful and lets the CPU do real work in between. The DMA controller does the byte-shuffling; the ISR just signals a consumer that a block is ready.

If DMA isn't available or the peripheral doesn't support it cleanly, the next lever is interrupt coalescing in the peripheral itself: many peripherals have a FIFO with a programmable watermark, so you set the interrupt to fire only when N samples have accumulated. That's a one-register change that can cut interrupt load by an order of magnitude. Where the hardware offers neither, I'd look at whether the ISR can be made trivially short — read the status, drain the FIFO into a ring buffer, clear the flag, return — and push all processing to a deferred context. The ISR cost then becomes dominated by entry/exit overhead rather than work, and you can measure whether that's still too much.

The measurement matters: I'd instrument actual ISR entry count and time-in-ISR before and after, because "high interrupt rate" is a hypothesis until you've counted. If after all of this the ISR is still the bottleneck, the honest answer may be that the CPU can't keep up and the design needs a different peripheral mode, a faster part, or a hardware change — and it's better to surface that early than to keep shaving microseconds.

**Possible follow-ups:** How would you size the DMA buffer given that the consumer task runs at a lower priority than the ISR? What happens if the consumer falls behind and the DMA wraps — how do you detect and handle the overrun?

## Q4: A junior engineer has written a driver that works reliably on the bench but uses a fixed `k_sleep` delay to wait for a peripheral to become ready after each command, rather than checking a status register or using an interrupt. How would you guide them?

**Answer:** I'd start by acknowledging why the approach feels reasonable — it works, it's simple, and it's easy to read — and then walk through the specific ways it fails, because the goal is for them to see the problem themselves rather than just being told "don't do that." The fixed delay is a bet that the peripheral is always ready within that window. That bet holds on the bench at room temperature with a good supply, and it fails on a cold board, a marginal supply, a different silicon revision, or when the peripheral is busy with something else. The delay is also pure wasted time — if the peripheral is ready in 200 µs and the delay is 5 ms, you've burned 4.8 ms of CPU or sleep budget on every command, which matters enormously in a low-power device.

Then I'd show them the better pattern concretely: poll the status register with a bounded timeout, so you proceed as soon as the peripheral is ready and you fail loudly if it never becomes ready. That's strictly better than a fixed delay on both correctness and latency, and it's barely more code. For cases where the wait is long enough that polling wastes power, the interrupt-driven version is the next step, but I'd introduce that as an evolution rather than insisting on it immediately — the bounded-poll version is a genuine improvement they can adopt today.

I'd also make the failure mode visible: with a fixed delay, a too-slow peripheral produces silent corruption downstream, which is the worst kind of bug. With a bounded poll, you get a clean timeout error at the point of failure, which is exactly where you want it. Framing it as "this change makes your driver's failures diagnosable" tends to land better than framing it as a style preference. And I'd ask them to add a test or a bench check that deliberately slows the peripheral down, so they can see the fixed-delay version break and the polling version hold.

**Possible follow-ups:** What timeout value would you choose for the bounded poll, and how would you justify it? How would you handle the case where the peripheral is ready but returns a status that indicates an error rather than success?

## Q5: How would you approach designing a firmware module that must log diagnostic events to flash, where the log must survive a power loss mid-write and the flash has limited erase cycles?

**Answer:** There are two independent problems here — crash consistency and wear — and they need separate solutions that compose. For crash consistency, the core principle is that a log record is only valid once a commit marker says so. I'd structure each record with a header containing a sequence number, a length, and a CRC over the payload, and write the record body first, then the header/commit field last. On boot, the logger scans forward from the last known-good record; the first record with a bad CRC or an incomplete header is treated as torn and discarded, and the write pointer is reset to that point. That way a power loss mid-write costs you at most the in-flight record, never the log.

For wear, the enemy is erasing the same sector repeatedly. The standard approach is a circular log across multiple sectors: append records sequentially until a sector is full, then erase the oldest sector and continue. That spreads erase cycles across the whole log region, so endurance is multiplied by the number of sectors. If the log region is small relative to the write rate, I'd also consider whether every event genuinely needs to be persisted — many diagnostic events can be aggregated or rate-limited, and dropping the log level in production is often the single biggest endurance win.

There's a subtlety at the wrap point: erasing the oldest sector destroys the oldest records, so if the log is full and you need the history, you have to decide whether to stop logging, overwrite oldest, or escalate. I'd make that policy explicit and configurable rather than implicit. I'd also keep a small separate "boot counter" or "last known good" field in its own sector so that a torn write in the main log can never corrupt the metadata needed to recover — separating metadata from bulk data is cheap insurance.

**Possible follow-ups:** How would you handle the case where the log is being written from an ISR or a high-priority thread and a flash erase blocks for tens of milliseconds? What would you do if the CRC check on boot finds a record that is valid but out of sequence — how do you distinguish corruption from a legitimate gap?
