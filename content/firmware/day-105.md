# firmware — Day 105

## Q1: How would you approach implementing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual interrupt rate, the per-ISR cost (entry/exit overhead plus the work done), and the resulting CPU utilization. If servicing every interrupt would consume, say, 30–40% of the CPU, that's the number that justifies the redesign — and it also tells you how much headroom you need to recover.

The standard techniques, in rough order of preference:

1. **Reduce the number of interrupts, not the work.** Most peripherals that generate high interrupt rates do so because they signal per-sample or per-byte. Configure the peripheral to signal per-block instead — FIFO thresholds, DMA half-transfer/complete interrupts, or a "watermark" level. This is usually the biggest win and requires no change to the data path.
2. **Move the data with DMA.** Let the peripheral write directly to a ring buffer in memory and interrupt only on block completion or on a threshold. The ISR then just advances a producer index and signals a consumer — a few instructions instead of a full transfer.
3. **Defer the real work.** Keep the ISR minimal: capture the timestamp/index, clear the flag, and hand off to a work queue or a lower-priority thread. The ISR cost becomes bounded and predictable even if the total work is unchanged.
4. **Coalesce in the ISR.** If DMA isn't available, have the ISR drain the peripheral's FIFO in a loop rather than returning after one item — trading a slightly longer ISR for far fewer of them.

The trade-off to be explicit about is latency: batching and DMA introduce a delay between the event and the software seeing it. For a control loop that's usually fine if the block size is chosen so the worst-case latency stays within the loop's deadline. I'd size the buffer and threshold from the deadline, not from convenience, and verify with a scope or a GPIO toggle that the worst-case latency is actually met under load — not just on average.

**Possible follow-ups:**
- How would you decide between a FIFO-threshold interrupt and full DMA for a given peripheral?
- What would you do if the peripheral has no FIFO and no DMA support at all?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the debugger's presence changes several things at once, so the first job is to figure out *which* change is masking the fault. The usual suspects:

- **Timing.** The debugger slows execution and adds delays between instructions. A race condition, a missing settle delay, or a peripheral that needs time after a register write will "fix itself" when you single-step. Attaching a scope or toggling a GPIO at the suspect points, without halting the CPU, preserves timing.
- **Optimization and code generation.** Debug builds are often `-O0`; release builds are `-O2` or `-Os`. Different optimization can expose uninitialized variables, missing `volatile`, or undefined behavior that the debug build happens to paper over. Reproduce with the release binary and the debugger attached, and compare.
- **Debug peripheral state.** Some debuggers halt timers, watchdogs, or the core clock; some leave the watchdog serviced by the debug probe. A watchdog that would fire standalone may never fire under the debugger.
- **Power and clock state.** Debug probes can hold the part out of low-power modes, changing supply behavior and clock stability.
- **Memory layout.** Debug builds may place variables differently, changing which uninitialized or overrun memory gets clobbered.

My approach: reproduce with the release binary first, then bisect the difference — run standalone with logging over a UART or a RAM buffer that survives reset, and compare the trace against the debugger run. If the fault disappears only when the CPU is halted, it's timing; if it disappears only with the debug build, it's code generation or memory layout. Instrument with GPIO toggles and a logic analyzer to get timing-accurate evidence without perturbing the run.

**Possible follow-ups:**
- How would you capture a trace from a device that resets, so the evidence survives the reset?
- What specific classes of bug are most likely to be masked by `-O0` versus `-O2`?

## Q3: How would you approach designing a firmware module that must log diagnostic events to flash, where the log must survive a power loss mid-write and the flash has limited erase cycles?

**Answer:** Two constraints drive the design: atomicity across power loss, and wear. They're related but solved differently.

**Atomicity.** A single flash write can be interrupted by power loss, leaving a partially written record. The standard approach is to make each record self-validating and to write in an order that lets recovery distinguish complete from incomplete records:

- Append-only log with a per-record header containing a sequence number and a CRC over the payload. On boot, scan from the last known-good record forward; the first record with a bad CRC or an implausible sequence number marks the end of valid data, and the log resumes from there.
- Write the payload first, then the header/commit marker last, so a torn write leaves an uncommitted record that recovery can discard. Alternatively, write a "valid" flag as a separate word after the payload and CRC.
- Never overwrite a record in place. Append until the region is full, then erase the oldest sector and continue — a circular log across sectors.

**Wear.** Flash endurance is per-sector, so the design should spread erases evenly:

- Use a circular buffer of sectors so erases rotate across the whole log region rather than hammering one sector.
- Keep records small and batch them; erasing a sector per record would burn endurance fast.
- If the log is high-volume, consider a RAM buffer that flushes on threshold or on a timer, trading some loss window for far fewer erases — but be explicit about what's acceptable to lose on power loss.
- Track erase counts per sector in a small metadata area if the device needs to report or bound wear.

The recovery path is the part that gets under-tested. I'd deliberately corrupt records at every byte offset and verify the boot-time scan always lands on a consistent state, and I'd test power loss at each step of the write sequence, not just at the end.

**Possible follow-ups:**
- How would you handle a log region that fills up completely while the device is running unattended?
- What would change if the flash were external and shared with other data?

## Q4: A junior engineer on your team has implemented a firmware module that uses a global flag to signal between an ISR and a main-loop task. The code works in testing, but you're concerned about correctness and maintainability. How would you guide them toward a better design?

**Answer:** I'd start by understanding why they chose it — often it's the simplest thing that worked, and the concern is legitimate but the fix needs to be motivated, not imposed. Then I'd walk through the specific failure modes rather than arguing in the abstract:

- **The flag alone doesn't carry data.** If the ISR also writes a value the task reads, the flag doesn't guarantee the value is visible or consistent — the compiler and CPU can reorder, and on a multi-core or cached part the task may see a stale value. `volatile` on the flag doesn't fix that; it only prevents the compiler from eliding the access.
- **Lost events.** If the ISR sets the flag again before the task clears it, the second event is silently dropped. Whether that matters depends on the semantics — a "data ready" flag that's level-like is fine; an "event occurred" flag that's edge-like is not.
- **Maintainability.** A bare global flag has no owner, no documented protocol, and no place to enforce the ordering rules. The next person to touch it has to reverse-engineer the contract.

The better designs depend on what's actually needed:

- If it's a single producer/single consumer handoff of data, a **ring buffer** with proper memory barriers (or a Zephyr `k_fifo`/`k_msgq`) gives correctness and a clear contract.
- If it's a simple "something happened" notification, a **semaphore** or **event object** expresses the intent and handles the lost-event case correctly.
- If it's genuinely just a flag with no data, at minimum document the access rules and use the platform's atomic or barrier primitives rather than relying on `volatile`.

I'd frame it as: the current code works because the timing happens to be favorable in testing; the redesign makes it work by construction. I'd pair with them on the first conversion so they see the pattern, and let them apply it to the rest.

**Possible follow-ups:**
- How would you decide between a ring buffer and a message queue for the ISR-to-task handoff?
- What would you do if the junior engineer pushed back that the change is unnecessary churn?

## Q5: How would you approach designing a watchdog strategy for a device that has a legitimate long-running operation (e.g., a flash erase or calibration routine) that can take several seconds, while still ensuring the watchdog provides meaningful fault detection?

**Answer:** The core principle is that the watchdog should verify *liveness and progress*, not just "the main loop ran." A long operation is not a hang, so the strategy has to distinguish the two without simply widening the timeout until the watchdog stops catching anything.

The approaches, roughly in order of preference:

1. **Kick from the operation itself, on progress.** If the long routine can report incremental progress — erase block N of M, calibration step N — have it service the watchdog at each step, with a timeout sized to the longest single step rather than the whole operation. A hang inside a step still trips the watchdog; a slow-but-progressing operation doesn't. This is the cleanest answer when the routine can be instrumented.
2. **Windowed watchdog.** A windowed watchdog requires the kick to arrive within a time window, not just before a deadline. That catches both "too late" (hang) and "too early" (a runaway loop kicking in a tight cycle), which is a stronger guarantee than a plain timeout. It also makes the "kick from the main loop" pattern much harder to abuse.
3. **Dedicated supervisor task.** A high-priority task checks that each subsystem has checked in within its own deadline, and only then kicks the watchdog. The long operation checks in with the supervisor at each step, so the supervisor's logic — not the operation's — owns the policy. This scales to multiple subsystems and keeps the policy in one place.
4. **Explicit "long operation" mode.** As a last resort, the firmware can enter a mode where the watchdog timeout is extended for the duration of a known operation, then restored. This is the weakest option because it's easy to leave the device in the extended state on an error path, and it doesn't catch a hang *within* the operation. If used, it should be time-bounded and automatically revert.

The design decision I'd insist on is that the timeout is derived from the worst-case per-step time plus margin, measured, not guessed — and that the error paths are tested by deliberately hanging the operation at each step and confirming the watchdog fires. A watchdog strategy that's never been made to fire on purpose is a watchdog strategy you don't know works.

**Possible follow-ups:**
- How would you handle a long operation that genuinely cannot report progress, such as a single blocking erase?
- What are the risks of kicking the watchdog from an interrupt handler, and when would it be acceptable?
