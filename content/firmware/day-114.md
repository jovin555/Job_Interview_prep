# firmware — Day 114

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual interrupt rate, the per-ISR cost (entry/exit overhead plus register access), and the resulting CPU utilization. If servicing every interrupt would consume, say, more than a small fraction of the CPU budget, the design needs to change. The standard approaches, in rough order of preference:

1. **DMA with a large buffer.** Let the peripheral write directly to memory and interrupt only on a half-transfer or full-transfer boundary. This converts N per-sample interrupts into a handful of per-buffer interrupts. The ISR then just signals a consumer (semaphore, message queue) and the actual processing happens in a thread. This is usually the cleanest answer when the peripheral supports it.

2. **Interrupt coalescing / FIFO watermark.** Many peripherals have a hardware FIFO with a programmable "interrupt when N entries are pending" threshold. Raise the threshold so the ISR fires once per burst rather than once per sample, then drain the FIFO in a loop inside the ISR. This trades latency for CPU load and is a good middle ground when DMA isn't available.

3. **Deferred processing with a ring buffer.** Keep the ISR minimal — copy the sample into a lock-free ring buffer and return — and let a worker thread do the heavy lifting. This doesn't reduce the interrupt count, but it does reduce the time spent at interrupt priority, which matters if the real problem is latency for other interrupts rather than raw CPU.

4. **Polling in a dedicated high-priority thread.** If the rate is high enough that interrupt overhead dominates, sometimes polling a status register in a tight loop is actually cheaper than taking an interrupt per event — the crossover point is worth measuring, not guessing.

The key trade-off is latency versus throughput versus CPU headroom. I'd document the chosen approach and the reasoning, because "why didn't you just use DMA" is a question that will come up in review.

**Possible follow-ups:**
- How would you decide between a half-transfer and full-transfer DMA interrupt for a streaming sensor?
- What happens to your design if the consumer thread occasionally falls behind the producer?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the debugger's presence changes several things at once, so the first job is to figure out *which* change is masking the fault. The usual suspects:

- **Timing.** The debugger slows execution and adds latency between events. If the bug is a race condition, a too-tight deadline, or a peripheral that needs settling time, halting at a breakpoint can hide it. I'd look for shared state without proper synchronization, and for code that assumes a peripheral responds within a fixed number of cycles.
- **Optimization.** Debug builds are often `-O0`; release builds are `-O2` or higher. Optimization can expose missing `volatile`, missing memory barriers, or undefined behavior that happens to work at `-O0`. I'd try to reproduce with the release build under the debugger, and separately with the debug build standalone, to isolate which variable matters.
- **Debug peripheral state.** Some debuggers leave peripherals (watchdogs, timers, low-power modes) in a different state, or disable them. A watchdog that's silently kicking in standalone but paused under the debugger is a common one.
- **Power and clock behavior.** The debugger can hold the core awake or change clock gating. If the bug only appears when the device actually enters low-power modes, that points at the sleep/wake path.

My approach: first, try to reproduce standalone with instrumentation that doesn't halt the core — GPIO toggles, a RAM-based trace buffer, or a serial log at low priority. Second, bisect the difference: run the release build under the debugger, run the debug build standalone, and see which combination reproduces. Third, once I have a hypothesis, add targeted assertions or a canary to confirm it rather than guessing. The goal is to turn an intermittent standalone failure into a deterministic one I can actually reason about.

**Possible follow-ups:**
- How would you use a RAM trace buffer to capture state around the failure without perturbing timing?
- What kinds of bugs are specifically exposed by compiler optimization rather than hidden by it?

## Q3: How would you approach deciding what belongs in a bootloader versus what belongs in the application, for a device that must support field updates?

**Answer:** The guiding principle is that the bootloader should be as small, simple, and rarely-changed as possible, because it's the one piece of code that must work even when everything else is broken. Anything that could brick the device if it fails belongs in the bootloader only if it's essential to recovery; everything else belongs in the application.

Concretely, I'd put in the bootloader:

- **The update mechanism itself** — receiving or reading the new image, verifying it (CRC, signature), and writing it to the inactive bank. If the application handled this, a failed update could leave no working code to retry from.
- **Bank selection and rollback logic** — deciding which bank to boot, checking a validity flag or boot-attempt counter, and falling back to the known-good bank if the new image fails to validate or fails to "confirm" itself within a timeout.
- **Minimal recovery path** — a way to enter update mode even if the application is corrupt (a magic value in a retained register, a GPIO strap, or a timeout with no valid application).
- **Clock and memory initialization** needed to run that logic, and nothing more.

I'd keep in the application:

- **The decision of *when* to update** — user commands, schedule, policy. The bootloader shouldn't know about product features.
- **The transport stack** (wireless, USB) if it's large or complex. The bootloader can expose a simple, stable update protocol and let the application handle the fancy transport, handing off to the bootloader only for the actual flash write.
- **Anything that changes frequently.** Every line in the bootloader is a line that can't be fixed by an OTA update to the application.

The trade-off is bootloader size and attack surface versus recovery robustness. A bootloader that's too clever is a liability; one that's too dumb may not be able to recover from a bad application image. I'd document the boundary explicitly and treat the bootloader as frozen after validation.

**Possible follow-ups:**
- How would you handle a bootloader bug that's discovered after deployment, given that the bootloader itself can't be updated by the normal OTA path?
- Where would you store the "boot attempt counter" and why does its storage medium matter?

## Q4: A junior engineer has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I'd start by acknowledging the part they got right: `volatile` does prevent the compiler from caching the variable in a register or eliminating the access, which is necessary for the ISR and thread to see each other's writes at all. The gap is that `volatile` says nothing about *atomicity* or *ordering* relative to other memory operations, and on a multicore or pipelined part it says nothing about memory barriers.

I'd walk through the specific failure modes:

- **Non-atomic access.** If the shared variable is wider than the native word size, or if the ISR and thread both do read-modify-write (e.g., `counter++`), the operations can interleave and lose updates. `volatile` doesn't make `++` atomic.
- **Compiler and CPU reordering.** The compiler may reorder a non-volatile access across a volatile one, and the CPU may do the same. If the ISR writes data and then sets a `volatile` flag, the thread can observe the flag before the data is visible unless there's a barrier or the data is also handled correctly.
- **Lost wakeups and busy-waiting.** A `volatile` flag polled in a loop burns CPU and can still miss transitions if the flag is cleared and re-set between polls.

The fix depends on intent. If it's a simple "ISR sets a flag, thread checks it" pattern, the right tool is usually a kernel primitive — a semaphore, event, or message queue — which gives both atomicity and a proper blocking wait. If it's genuinely a single-word flag with no other shared state, `atomic_t` or the kernel's atomic operations give the needed guarantees without the overhead of a full semaphore. For data buffers, a lock-free ring buffer with proper acquire/release semantics (or the kernel's `k_fifo`/`k_msgq`) is the standard answer.

I'd frame it as "the code works today, but it works by luck of the compiler and the timing; here's how we make it work by construction." Then I'd pair with them on converting one instance and let them see the diff and the reasoning, rather than just handing them a corrected file.

**Possible follow-ups:**
- When *is* a bare `volatile` flag actually sufficient, and what conditions have to hold?
- How would you explain the difference between `volatile` and `atomic` to someone who's only worked on single-core bare-metal?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd resist the urge to pick a side and instead reframe the disagreement as a set of measurable requirements. Both engineers are right about something: polling *is* simpler and more deterministic in the sense that the timing is bounded by the loop period, and interrupts *are* necessary when the event rate or latency requirement exceeds what a poll loop can guarantee. The question is which set of constraints this protocol actually has.

I'd structure the discussion around:

- **Latency requirement.** What's the maximum acceptable delay between a byte arriving and the firmware responding? If it's tens of milliseconds, a poll loop at a known period may be fine. If it's microseconds, polling has to run fast enough to guarantee it, which may not be feasible alongside other work.
- **Event rate and burstiness.** A protocol that's mostly idle with occasional bursts is a poor fit for tight polling (wasted CPU) and a good fit for interrupts. A protocol with a steady, predictable rate can be polled cheaply.
- **CPU budget.** Polling consumes CPU whether or not there's data; interrupts consume CPU only on events but add per-event overhead and latency jitter. Which resource is scarcer on this device?
- **Determinism.** Interrupts introduce jitter from other interrupts and from critical sections. If the protocol has hard real-time deadlines, that jitter has to be budgeted, not ignored.
- **Complexity and testability.** Polling is easier to reason about and to test deterministically. Interrupt-driven code needs careful attention to shared state, reentrancy, and priority inversion.

Then I'd ask both engineers to bring evidence: a rough timing budget, a measurement of the actual event rate, or a prototype. Often the disagreement dissolves once someone measures the real numbers. If it doesn't, I'd propose a hybrid — interrupt-driven reception into a ring buffer, with the protocol state machine running in a thread — which captures most of the responsiveness benefit while keeping the complex logic out of interrupt context. I'd make the decision explicit, document the reasoning and the assumptions, and set a review point so we can revisit if the assumptions turn out wrong. The goal is a decision the team can commit to, not a victory for one engineer.

**Possible follow-ups:**
- How would you structure a prototype to settle the question empirically without committing to either design?
- If the hybrid approach is chosen, where exactly does the boundary between ISR and thread fall, and why?
