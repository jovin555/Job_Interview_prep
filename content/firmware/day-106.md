# firmware — Day 106

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual ISR entry/exit cost, the interrupt frequency, and the resulting CPU utilization. If servicing every interrupt would consume, say, 40% of the CPU, that's a design constraint to solve, not a tuning problem.

The core techniques, roughly in order of preference:

1. **Move data with DMA instead of per-sample interrupts.** For a streaming peripheral (ADC, SPI, UART), configure DMA to transfer a block of samples into a buffer and generate a single interrupt per block rather than per sample. This reduces interrupt count by the block size and is usually the biggest win.

2. **Coalesce interrupts in the ISR itself.** If DMA isn't available or appropriate, the ISR should do the absolute minimum — read the data register, push to a ring buffer, clear the flag — and defer all processing to a thread or work queue. The ISR must not do floating-point math, logging, or protocol parsing.

3. **Use a "read until empty" loop in the ISR.** For peripherals with a FIFO, drain the FIFO in the ISR rather than returning after one byte. This amortizes the interrupt overhead across multiple samples.

4. **Reduce the interrupt rate at the source if the hardware allows it** — e.g., configure the peripheral's FIFO threshold to fire when it's half-full rather than on every byte.

5. **Consider a timer-driven poll at a fixed rate** if the data rate is modest and deterministic latency matters more than minimum CPU. This trades interrupt overhead for predictable, bounded polling cost.

The trade-off to articulate: DMA adds complexity and buffer management (and cache coherency concerns on some MCUs), but it's usually the right answer for high-rate streaming. The key principle is that the ISR should be a data mover, not a data processor — the less time spent with interrupts disabled, the better for the rest of the system's latency.

**Possible follow-ups:**
- How would you size the DMA buffer, and what happens if the consumer thread falls behind?
- What are the cache coherency implications of DMA on an MCU with a data cache, and how would you handle them?

## Q2: How would you approach deciding whether a piece of firmware logic belongs in an interrupt service routine versus a deferred context such as a work queue or a thread?

**Answer:** The decision comes down to a few concrete criteria, and I'd frame it as a set of questions rather than a rule of thumb.

**Keep it in the ISR if:**
- It's a hardware-mandated action with a hard deadline — reading a data register before the next sample overwrites it, clearing a flag that would otherwise re-trigger, or acknowledging a peripheral.
- It's O(1) and bounded — a few register reads/writes, a push to a lock-free ring buffer, setting a flag.
- It must happen before the interrupt is re-enabled, or the hardware state would be lost.

**Defer it if:**
- It involves blocking calls (mutexes, `k_sleep`, memory allocation) — these are illegal or dangerous in ISR context.
- It's unbounded or data-dependent in duration — parsing a variable-length message, running a state machine with many branches, computing a checksum over a large buffer.
- It touches shared state that other threads also touch, requiring synchronization that would mean disabling interrupts for too long.
- It does anything that could take more than a small, measured fraction of the interrupt budget — logging, flash writes, floating-point math.

The practical rule I use: the ISR should do the minimum to get the hardware into a safe state and hand off a token (a buffer pointer, an event, a semaphore give) to a deferred context. Everything else — protocol parsing, filtering, state transitions, persistence — belongs in a thread or work queue where it can be preempted and where blocking is legal.

The cost of deferring is latency and context-switch overhead; the cost of doing too much in the ISR is jitter imposed on every other interrupt in the system, which is usually the more dangerous failure mode. For a medical device with a real-time control loop, an overlong ISR is a latent timing bug that may only show up under load.

**Possible follow-ups:**
- How would you measure whether an ISR is "too long," and what budget would you set?
- What's the difference between a work queue and a dedicated thread for deferred processing, and when would you choose one over the other?

## Q3: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the debugger's presence changes timing, memory layout, and sometimes power state — so the first job is to figure out *which* of those is masking the bug.

**Likely causes, roughly in order of frequency:**

1. **Timing/race conditions.** The debugger slows execution and adds delays that hide a race between an ISR and a thread, or between two threads. Attaching a debugger can also mask a missing memory barrier or a missing `volatile`.

2. **Uninitialized memory.** The debugger may zero memory or leave it in a different state than a cold boot. Standalone, the bug manifests as garbage in a variable that was never initialized.

3. **Optimization differences.** Debug builds are often `-O0`; release builds are `-O2`. A bug that only appears at `-O2` often points to undefined behavior — a missing `volatile`, a strict-aliasing violation, or reliance on evaluation order.

4. **Watchdog or low-power behavior.** The debugger can hold the core in a state that prevents sleep or resets the watchdog, masking a power-management or watchdog bug.

5. **Flash/RAM layout.** The debugger may change where code and data land, hiding a stack overflow or a buffer overrun that corrupts adjacent memory.

**Approach:**
- First, reproduce the failure without the debugger but with instrumentation that doesn't perturb timing much — GPIO toggles on a scope/logic analyzer, a ring-buffer trace in RAM dumped after the fact, or a UART log at low baud with timestamps.
- Compare behavior between `-O0` and the release optimization level. If it only fails at `-O2`, suspect UB and audit `volatile`/barriers.
- Check for uninitialized variables and stack usage — enable stack canaries or high-water-mark reporting if the RTOS supports it.
- If it's timing-related, add deliberate delays or stress the timing (e.g., inject load) to make the race more likely rather than less.
- Use the debugger *strategically*: attach only to inspect state after a fault, or use hardware breakpoints that don't halt the whole system, rather than running under the debugger continuously.

The key discipline is to treat "works with debugger" as a clue about *what the debugger changes*, not as evidence the code is correct.

**Possible follow-ups:**
- How would you capture a trace of what happened before a fault without a debugger attached?
- If you suspect a race, how would you go about proving it rather than just fixing the symptom?

## Q4: You're implementing a bootloader for a device that must support field updates over an unreliable link, and the device has no physical recovery mechanism (no button, no exposed debug header). How would you structure the update and recovery logic so that a failed or interrupted transfer can never leave the device unbootable?

**Answer:** The guiding principle is that the bootloader must always have a known-good image to fall back to, and the decision of what to boot must be made by logic that cannot itself be corrupted by a failed update.

**Structure:**

1. **Dual-bank (A/B) layout.** Two application slots plus a small, immutable bootloader region. The bootloader is never overwritten by a field update — it's either write-protected or updated only through a separate, more carefully controlled path. The active bank is tracked in a metadata region.

2. **Metadata with redundancy and integrity.** The "which bank is valid, which is being updated, which has been validated" state lives in a small metadata block with a CRC and, ideally, two copies (ping-pong) so a power loss mid-write to metadata doesn't destroy the record. A common pattern is a sequence number plus CRC so the bootloader can pick the newest valid record.

3. **Update flow:**
   - Bootloader receives the new image into the *inactive* bank. It never touches the active bank during transfer.
   - Each chunk is written and, at the end, the whole image is verified (CRC or hash) before the metadata is updated to mark the new bank as "candidate."
   - Only after verification does the bootloader mark the new bank bootable and set a "trial boot" flag.

4. **Trial boot and rollback.** On the next reset, the bootloader boots the candidate bank but with a flag indicating it's on trial. The application must "confirm" itself within some window (e.g., after passing self-tests and establishing communication). If it doesn't confirm — because it crashes, hangs, or fails validation — the bootloader on the next reset sees the unconfirmed trial flag and reverts to the previous known-good bank.

5. **Watchdog-assisted recovery.** The bootloader arms a watchdog before jumping to the application. If the application hangs before confirming, the watchdog resets the device, and the bootloader's trial logic handles the rollback.

6. **Never erase the last known-good image** until a new image has been confirmed. This is the single most important invariant.

The "no physical recovery" constraint means the bootloader itself must be treated as the root of trust and must be as simple and well-tested as possible — every line of bootloader code is a line that, if buggy, bricks the device. I'd keep it minimal: verify, select bank, jump, handle rollback. No complex protocol parsing in the bootloader if it can be avoided; the application can handle the download and hand off a verified image.

**Possible follow-ups:**
- How would you handle the case where the metadata region itself is corrupted — what's the safe default?
- What validation checks would you run before confirming a trial boot, and how long should the confirmation window be?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd steer the discussion away from "which is better in general" — because both engineers are right in different contexts — and toward the specific requirements of *this* protocol and *this* system.

**Step 1: Make the requirements explicit.** What's the maximum acceptable latency from a message arriving to the application seeing it? What's the message rate and burst behavior? What's the CPU budget? Is there a hard real-time loop elsewhere in the system that the protocol must not disturb? What's the cost of a dropped or delayed message? Writing these down often resolves the disagreement, because the two engineers are implicitly optimizing for different requirements.

**Step 2: Evaluate both against the requirements.**
- Polling is predictable and simple, but its latency is bounded by the poll period, and it wastes CPU when idle. It's a good fit when the message rate is low, latency tolerance is loose, or the system is already tightly scheduled and you want to avoid interrupt jitter.
- Interrupt-driven is responsive and efficient when idle, but adds ISR latency, potential priority inversion with other interrupts, and complexity around shared state. It's a good fit when messages are infrequent but must be handled promptly, or when the CPU is otherwise busy.

**Step 3: Consider hybrids.** A common resolution is a hybrid: the interrupt fires on the first byte (or a FIFO threshold), and the ISR hands off to a deferred context that drains the rest. Or a timer-driven poll at a rate derived from the required latency. These often satisfy both engineers' concerns.

**Step 4: Prototype if the disagreement persists.** If the requirements genuinely don't settle it, a small benchmark — measure latency and CPU under realistic load for both approaches — turns an opinion into data. This is usually faster than continued debate.

**Step 5: Decide and document the rationale.** Once decided, record *why* — the requirements that drove it — so the decision isn't relitigated later and so future engineers understand the constraint. If the requirements change, the decision can be revisited on its merits.

The leadership point: I'd frame this as a technical trade-off to be resolved by requirements and evidence, not a contest of seniority. Both engineers should feel their concern was heard and incorporated into the criteria.

**Possible follow-ups:**
- What would you do if the prototype showed the two approaches were roughly equivalent on the measured metrics?
- How would you handle it if the losing engineer remained unconvinced after the decision was made?
