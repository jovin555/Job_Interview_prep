# firmware — Day 77

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt can fire faster than the CPU can service it, so that the ISR itself becomes the bottleneck?
**Answer:** The first step is to quantify the problem rather than assume it: measure the actual interrupt rate, the worst-case ISR execution time, and the CPU headroom left for everything else. If the ISR is genuinely saturating the core, no amount of clever ISR code will fix it — the architecture has to change. The standard approach is to make the ISR do the absolute minimum: acknowledge the source, move the data (or a pointer to it) into a buffer, and return. Everything else — parsing, filtering, state updates, logging — gets deferred to a thread or work queue. If even the minimal ISR is too slow, the next lever is DMA: let the peripheral write directly into memory and have the ISR fire only on a half-buffer or full-buffer boundary, which collapses the interrupt rate by the buffer size factor. Where the peripheral supports it, a FIFO or watermark threshold can do the same job. If the rate is still too high, the honest answer is that the hardware or the sampling strategy needs to change — for example, reducing the sample rate, using a hardware filter or decimation stage, or offloading to a second core or a small FPGA. The key reasoning is to separate "how do I make the ISR faster" from "how do I make the ISR fire less often," because the second question usually has more headroom.
**Possible follow-ups:** How would you decide between a work queue and a dedicated thread for the deferred processing? What would you do if the deferred processing itself can't keep up with the incoming rate?

## Q2: How would you approach sizing thread stacks in a Zephyr RTOS application, and what would you do to verify that your sizing is actually correct rather than just "probably enough"?
**Answer:** I'd start by understanding what actually consumes stack in each thread: local variables, function call depth, any library calls that have their own stack usage (printf-style formatting, floating point, cryptographic routines), and interrupt context if the thread can be preempted by an ISR that shares its stack. A rough first estimate is fine, but the important part is verification. Zephyr gives you several tools for this: the `CONFIG_THREAD_ANALYZER` and `CONFIG_THREAD_STACK_INFO` options let you query unused stack at runtime, and you can paint the stack with a known pattern and check how much of it was overwritten. The most reliable method is to run the worst-case path — the deepest call chain, the largest local buffers, the most nested library call — and then measure the high-water mark. I'd add a safety margin on top, typically 25–50% depending on how confident I am in the worst-case analysis, and I'd keep that margin visible in the configuration rather than buried. For threads that call into third-party or vendor code, I'd treat the stack estimate as a hypothesis to be tested, not a fact. The other consideration is that stack sizing is not static: as the code evolves, the worst case can grow, so I'd want a CI check or a periodic measurement rather than a one-time decision.
**Possible follow-ups:** How would you handle a thread whose stack usage is highly variable depending on input? What's your view on using a single shared stack for multiple threads versus per-thread stacks?

## Q3: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?
**Answer:** This is a classic heisenbug, and the first thing to recognize is that attaching a debugger changes several things at once: it halts the CPU at breakpoints, it may slow down or alter timing, it can change the state of certain peripherals, and it often disables or changes the behavior of low-power modes and watchdogs. So the debugging strategy is to isolate which of those differences is masking the bug. I'd start by asking what the debugger is doing that the standalone run isn't: is it holding the CPU in a state that prevents a race from occurring? Is it keeping a clock or peripheral alive that would otherwise be gated? Is it preventing a watchdog from firing? A useful technique is to reproduce the standalone behavior while still having observability — for example, using a GPIO toggle or a spare UART as a poor man's trace, or using a RAM buffer that survives reset and can be read out afterward. If the bug is timing-related, I'd look at whether the debugger's halt is effectively adding delay that hides a race, and then try to reproduce that delay in firmware (a deliberate short delay) to see if the bug appears. If the bug is power-related, I'd check whether the debugger's connection is back-powering a rail or holding a reset line in a way that changes the power sequence. The general principle is to change one variable at a time — remove the debugger but add a different form of observability — rather than trying to reason about the bug while the debugger is still attached.
**Possible follow-ups:** How would you capture evidence of a bug that only occurs when no debugger is attached? What role does the watchdog play in this kind of scenario?

## Q4: How would you approach designing a firmware module that must survive a brownout — where the supply voltage sags briefly but doesn't fully drop — without corrupting persistent state or producing a spurious reset?
**Answer:** A brownout is a particularly nasty failure mode because the MCU may continue executing while its supply is below the specified operating range, which means the behavior is undefined: flash writes may partially complete, RAM contents may become unreliable, and the core may execute garbage. The first line of defense is hardware: a brownout detector or supervisory IC that holds the MCU in reset until the supply is stable, and a supply design with enough bulk capacitance to ride through the expected sag duration. But firmware has to assume the hardware protection isn't perfect. The key design principles are: (1) never write persistent state in a way that can be interrupted mid-write without a recovery mechanism — use a journal or a double-buffered scheme with a commit marker, so that a partially written record is detectable and discardable on the next boot; (2) keep the amount of state that must be consistent small, and make the commit operation atomic from the perspective of the recovery logic; (3) on boot, always validate persistent state before trusting it, and have a known-good fallback (defaults or the previous committed version); (4) if the MCU has a brownout reset flag, read it early and use it to distinguish a brownout from a power-on reset, which can inform recovery behavior. The other consideration is timing: if the firmware can detect the sag early (via an ADC monitoring the supply, or a brownout interrupt), it can abort any in-progress flash operation and put the system into a safe state before the supply drops further. That's not always possible, which is why the journaling approach matters — it makes the system recoverable even when the firmware has no warning.
**Possible follow-ups:** How would you test a brownout recovery scheme without damaging hardware? What's the difference between a brownout and a power-on reset from the firmware's perspective?

## Q5: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?
**Answer:** I'd start by acknowledging the part they got right: `volatile` does tell the compiler not to cache the value in a register or reorder accesses to that variable relative to other volatile accesses, which is necessary for the ISR and thread to see each other's writes. But it's not sufficient, and the gap is important. `volatile` says nothing about atomicity — if the variable is wider than the machine's natural word size, or if the thread reads it while the ISR is mid-write, the thread can observe a torn value. It also says nothing about ordering relative to non-volatile memory: the compiler and the CPU can reorder a non-volatile write past a volatile one, which means a flag can appear set before the data it's supposed to protect is actually visible. And on a multicore system, `volatile` provides no memory barrier at all. The correct tool depends on what's being shared. For a simple flag or counter, an atomic type with the appropriate memory ordering is usually the right answer. For a buffer of data with a flag, the pattern is to publish the data first, then use a release barrier (or an atomic store with release semantics) to set the flag, and on the reader side use an acquire barrier before reading the data. In Zephyr, that might mean `atomic_t` for the flag, or a `k_sem`/`k_fifo` if the data is larger. I'd walk them through a concrete example where the volatile-only version fails — for instance, a 32-bit value on a 16-bit MCU, or a struct with a flag — and then show the corrected version. The goal isn't to make them feel wrong; it's to give them a mental model of what `volatile` does and doesn't guarantee, so they reach for the right tool next time.
**Possible follow-ups:** How would you explain the difference between `volatile` and `atomic` to someone who's only worked on single-core systems? What's the smallest change you'd make to their code to make it correct without a full rewrite?
