# firmware — Day 115

## Q1: You're debugging a firmware issue where a device's SPI flash driver works correctly for reads but occasionally returns corrupted data on writes — and the corruption only appears when the device is also running a high-rate ADC sampling task. How would you approach this?

**Answer:** The correlation with the ADC task is the strongest clue, so I'd start by treating this as a resource-contention or timing problem rather than a flash-driver logic bug. My first step would be to characterize the failure precisely: is the corruption in the data payload, the address, or the command phase? Reading back the flash contents after a write and comparing against the intended buffer tells me whether the write itself failed or whether the data was already wrong when it reached the driver. I'd also check whether the corruption is deterministic (same bytes every time) or random — deterministic points to a logic or ordering bug, random points to timing, electrical, or concurrency.

The most likely culprits given the ADC task are: (1) a shared bus or DMA channel where the ADC and flash transactions collide, (2) an ISR from the ADC preempting the flash driver mid-transaction and violating a timing constraint (e.g., the flash's write-enable window or a chip-select hold time), or (3) a shared buffer that the ADC task overwrites while the flash driver is still reading from it. I'd instrument the driver to log the exact sequence of bus transactions and timestamps around a failing write, and I'd try to reproduce the failure with the ADC task artificially slowed down or stopped — if the corruption disappears, that confirms contention.

For the fix, the general principle is to make the flash transaction atomic with respect to anything that could disturb it: either take a mutex around the whole write sequence, or disable the ADC's DMA/interrupt for the duration of the critical phase if the timing budget allows. If the flash driver uses DMA, I'd verify the DMA channel isn't shared with the ADC and that the transfer-complete interrupt isn't being starved. I'd also add a CRC or checksum verification on the written data as a defensive measure — not as a substitute for fixing the root cause, but because flash corruption in a medical device is a safety issue and silent corruption is worse than a detected failure.

**Possible follow-ups:** How would you decide whether to serialize the two tasks with a mutex versus restructuring the flash driver to be non-blocking? And how would you verify the fix is robust rather than just "the corruption stopped happening in my test"?

## Q2: How would you approach implementing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first thing I'd do is quantify the problem rather than assume it — measure the actual interrupt rate, the per-ISR cost, and the resulting CPU utilization. If servicing every interrupt really does consume an unreasonable share, the standard approaches are: batching, DMA, or a hybrid.

Batching means the ISR does the minimum possible work — typically just acknowledging the interrupt and moving data into a buffer — and defers the real processing to a work queue or thread that drains the buffer in bulk. This reduces per-interrupt overhead but doesn't reduce the interrupt count itself, so it only helps if the ISR cost is dominated by processing rather than entry/exit.

DMA is usually the better answer when the peripheral supports it: configure the peripheral to transfer directly to memory and generate an interrupt only on a half-buffer or full-buffer boundary, or on a watermark. That collapses many per-sample interrupts into a handful of per-block interrupts. The trade-off is latency — you only learn about data at block granularity — and buffer sizing: the buffer must be large enough to absorb the burst between DMA interrupts but small enough that the processing thread keeps up.

A hybrid is often the practical choice: DMA for the bulk transfer, with a small number of interrupts per buffer, and a thread that processes each completed block. I'd also consider whether the peripheral has a FIFO with a programmable watermark — setting the watermark to a larger value reduces interrupt frequency without needing DMA at all.

The key design questions are: what's the maximum latency the consumer can tolerate, what's the worst-case burst size, and what happens if the consumer falls behind (drop oldest, drop newest, or backpressure)? For a medical device, dropping data silently is usually unacceptable, so I'd want an explicit overflow policy and a way to detect and report it.

**Possible follow-ups:** How would you size the DMA buffer if the processing thread's worst-case execution time is variable? And what would you do if the peripheral doesn't support DMA at all?

## Q3: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I'd start by acknowledging what they got right — `volatile` does prevent the compiler from caching the variable in a register or eliminating the access, which is necessary for the ISR and thread to see each other's writes. But I'd explain that `volatile` is not a synchronization primitive: it provides no atomicity, no memory ordering, and no mutual exclusion. On a multi-core system or with a compiler that reorders non-volatile accesses around a volatile one, the thread can still observe a torn or stale value, and a read-modify-write on a volatile variable is not atomic.

The concrete failure modes I'd walk them through: a 32-bit variable written by the ISR and read by the thread is fine on most 32-bit MCUs, but a multi-byte structure or a counter incremented with `++` is not. And even for a single word, if the thread does "check flag, then read data," the compiler or CPU can reorder the data read before the flag check unless there's a barrier.

The fix depends on what the variable is doing. If it's a simple flag or a single-word value, an atomic type or a `k_*` primitive (e.g., `atomic_t` in Zephyr) is the right tool. If it's a data buffer with a flag, the standard pattern is a lock-free single-producer/single-consumer ring buffer with proper memory barriers, or a mutex if the ISR can tolerate the (usually unacceptable) blocking — which it can't, so the ring buffer is the usual answer. For a "signal" from ISR to thread, a `k_sem` given from the ISR and taken by the thread is the idiomatic Zephyr approach.

I'd frame it as: `volatile` is a compiler directive, not a concurrency contract. The right question isn't "will the compiler optimize this away?" but "what guarantees do I need about ordering and atomicity, and which primitive provides them?" I'd pair the explanation with a concrete example of the bug — ideally one I can demonstrate with a small test — because seeing the failure is more convincing than being told about it.

**Possible follow-ups:** How would you review the rest of the codebase for the same pattern without it feeling like a personal criticism? And what would you do if the junior engineer pushed back and said the code has "worked for months"?

## Q4: How would you approach designing a watchdog strategy for a device where the main loop's timing varies significantly with workload — for example, a device that idles for long periods but occasionally runs a burst of computation that takes much longer than the idle period?

**Answer:** The core problem is that a single fixed timeout either trips during the legitimate long burst or is so long that it provides no meaningful fault detection during the idle period. The answer is to decouple "the system is alive" from "the main loop completed an iteration."

The cleanest approach is a windowed watchdog combined with a heartbeat from multiple independent checkpoints. Instead of kicking the watchdog once per main-loop iteration, I'd have each major subsystem (sensor acquisition, communication, control loop, housekeeping) set a "alive" flag or increment a counter at its own cadence. A dedicated watchdog-feeding task — running at a fixed, known period — checks that all the expected heartbeats have arrived since the last check, and only then kicks the watchdog. If any subsystem misses its deadline, the feeder stops kicking and the watchdog resets the device. This way the watchdog timeout is tied to the feeder's fixed period, not to the variable main-loop timing, and the long burst doesn't trip it as long as the subsystems that matter are still making progress.

For the burst specifically, I'd make sure the burst doesn't starve the feeder task — either the feeder runs at a higher priority, or the burst is broken into chunks that yield. If the burst genuinely must run to completion without yielding, then the feeder needs to know that a burst is in progress and extend its tolerance accordingly — but that's a deliberate, bounded exception, not a blanket timeout increase.

I'd also consider a windowed watchdog (where kicking too early is also a fault) if the concern is a runaway loop that kicks the watchdog in a tight cycle without doing real work. And I'd make sure the watchdog is not disabled in production builds — a common mistake is to leave the debug-mode bypass enabled.

**Possible follow-ups:** How would you test that the watchdog actually fires when a subsystem hangs, without waiting for a real failure? And what would you do if the burst is a flash erase that can't be interrupted?

## Q5: You're leading a firmware team that is transitioning from a bare-metal super-loop to Zephyr RTOS for a new medical device. Two senior engineers disagree: one wants to port the existing bare-metal drivers directly into Zephyr as custom drivers, while the other wants to rewrite them using Zephyr's native driver model. How would you guide the team to a decision?

**Answer:** I'd frame this as a decision to be made on evidence and risk, not on preference, and I'd structure the discussion around a few concrete criteria: schedule, maintainability, testability, and regulatory risk.

First, I'd ask both engineers to articulate the specific risks of their approach. The "port directly" camp's concern is usually schedule and the risk of introducing bugs in a rewrite of code that's already validated. The "rewrite natively" camp's concern is usually long-term maintainability and the cost of fighting the RTOS's device model. Both are legitimate, and the answer often depends on how much of the existing driver code is actually reusable.

I'd propose a middle path: categorize the drivers. For simple, well-understood peripherals (GPIO, UART, basic I2C), rewriting against Zephyr's native API is usually low-risk and pays off in maintainability. For complex, timing-critical, or heavily validated drivers (e.g., a sensor with a delicate initialization sequence that's been through regulatory testing), porting the logic into a Zephyr driver shell — keeping the proven sequence intact but wrapping it in the native device model — is often the pragmatic choice. The key is that "native driver model" and "reuse the proven logic" aren't mutually exclusive; you can have a native-model driver whose internals are the validated code.

I'd also want a decision record: document the criteria, the decision, and the rationale, so that when someone asks in six months why a particular driver is a custom port, there's an answer. And I'd set a review checkpoint — e.g., after the first two drivers are done, evaluate whether the chosen approach is working and adjust if not.

The leadership piece is making sure both engineers feel heard and that the decision is made on shared criteria rather than seniority. I'd explicitly separate "which approach for which driver" from "which approach wins" — the framing of a binary choice is often the real problem.

**Possible follow-ups:** How would you handle it if the engineer whose approach wasn't chosen disengages from the work? And how would you validate that a ported driver behaves identically to the original before trusting it in a medical device?
