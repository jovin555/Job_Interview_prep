# firmware — Day 101

## Q1: How would you approach implementing a firmware module that must handle a peripheral whose data-ready signal is edge-triggered, but where the signal can occasionally glitch and produce a spurious edge that does not correspond to valid data?

**Answer:** The core problem is that an edge on a GPIO line is not the same thing as valid data being present — the edge is only a hint, and the firmware must treat it as such rather than as a guarantee. I'd separate the two concerns: the ISR's only job is to record that an edge occurred (timestamp it, increment a counter, and signal a deferred context), and the actual data validation happens in the thread or work-queue handler where I can afford to do more work.

For the glitch itself, I'd think about it at three layers. First, hardware/electrical: is there a debounce or RC filter, or can the pin be configured with an input filter or hysteresis? Many MCUs have a digital glitch filter on certain pins, and using it is far cheaper than handling glitches in software. Second, at the ISR level, I'd capture the timestamp of each edge and compare against a minimum expected inter-edge interval derived from the peripheral's actual data rate — an edge arriving far sooner than physically possible is almost certainly spurious, so I'd drop it. Third, at the data level, the handler should validate the payload itself: check a status register, a CRC, a range check, or a "data ready" bit that the peripheral sets only when the sample is genuinely new. If the peripheral offers any way to confirm validity in-band, that's the authoritative check and the edge is just a wake-up hint.

The important design principle is that the system must be correct even if every edge is spurious and even if an edge is missed entirely. So I'd also add a periodic poll as a safety net — if no edge arrives within some multiple of the expected interval, the handler polls the peripheral directly. That way a missed edge degrades latency rather than losing data, and a spurious edge costs one wasted read rather than a corrupted sample.

**Possible follow-ups:** How would you choose the minimum inter-edge interval without hard-coding a value that breaks when the sample rate is reconfigured? What would you log to distinguish "spurious edge" from "real edge but invalid payload" when diagnosing in the field?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** The debugger being attached changes the system in several ways at once, so the first job is to figure out which of those differences is masking the bug rather than guessing. The usual suspects: the debugger halts the core and therefore changes timing; it may disable or slow low-power modes; it can change how the watchdog behaves (many debuggers freeze it); it may alter flash wait states or clock configuration; and attaching over SWD/JTAG can affect pin states and power draw.

I'd start by characterizing the failure more precisely — is it timing-dependent, power-state-dependent, or something else? A cheap experiment is to run standalone but add instrumentation that doesn't require a debugger: a GPIO toggled at key points viewed on a scope or logic analyzer, a ring buffer in RAM dumped on the next boot, or event counters written to a reserved flash region. That tells me whether the code path even reaches the point I expect. If the misbehavior correlates with entering a low-power mode, I'd suspect the debugger was preventing sleep and the bug lives in the sleep/wake path. If it correlates with watchdog resets, I'd check whether the debugger was freezing the watchdog and the standalone build is actually resetting.

I'd also deliberately reproduce the debugger's side effects without the debugger — for example, disable low-power modes in a test build, or freeze the watchdog in software — and see whether the failure disappears. If it does, I've narrowed the cause to that specific difference. And I'd check the obvious build-related traps: is the standalone image actually the same build, same optimization level, same linker script? Optimization differences alone can expose uninitialized variables or missing `volatile` that the debug build hides.

**Possible follow-ups:** How would you capture evidence of a failure that only happens when no debugger is connected and the device may reset before you can read anything out? What role does optimization level play in bugs that vanish under a debugger?

## Q3: How would you approach sizing thread stacks in a Zephyr RTOS application, and what would you do to verify that your sizing is actually correct rather than just "probably enough"?

**Answer:** I'd treat stack sizing as a measurement problem, not an estimation problem. The starting point is a static analysis of worst-case stack depth per thread: the call graph from the thread entry point, the deepest chain of function calls, plus the largest local frame along that chain, plus context-save overhead and any ISR nesting that can occur on that thread's stack. That gives a floor, but static analysis is easy to get wrong — indirect calls, library functions, and printf-style formatting can blow up frames in ways that are hard to see by inspection.

So the real answer is instrumentation. Zephyr gives you several tools: `CONFIG_THREAD_ANALYZER` and the thread analyzer shell command report per-thread stack usage; `k_thread_stack_space_get()` lets you query unused stack at runtime; and you can paint the stack with a known pattern at thread start and scan for the high-water mark. I'd run the system through its worst-case scenarios — not just nominal operation — and record the high-water mark for each thread. The scenarios that matter are the ones that stress deep call chains: error paths, logging, formatting, and any path that runs during a burst of interrupts.

Then I'd apply margin deliberately. A common rule is to size to the observed worst case plus a percentage for future code growth, but the margin should reflect risk: a thread that runs rarely and only in a fault path deserves more headroom than one exercised constantly in testing. I'd also enable stack overflow detection (`CONFIG_HW_STACK_PROTECTION` or the sentinel-based check) so that if my sizing is wrong in the field, I get a clean fault rather than silent corruption. And I'd re-measure after any significant change to the call graph — stack sizing is not a one-time decision.

**Possible follow-ups:** How would you handle a thread whose worst-case stack usage only occurs in an error path that's hard to trigger in testing? What's the trade-off between per-thread stack size and total RAM when you have many threads?

## Q4: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I'd start by acknowledging the part they got right — `volatile` does prevent the compiler from caching the value in a register or eliminating the access, and that's genuinely necessary for a variable shared with an ISR. The gap is that `volatile` is a compiler directive, not a memory-ordering or atomicity guarantee. It says nothing about the CPU or memory system reordering accesses, nothing about the read-modify-write sequence being atomic, and nothing about protecting a multi-byte or multi-field data structure from being observed half-updated.

I'd walk through concrete failure modes with them rather than just asserting the rule. If the shared data is more than one word — a struct with a timestamp and a value, say — the reader can observe the new value with the old timestamp even with both fields `volatile`, because there's no ordering between the writes as seen by the other context. If the variable is a counter incremented in both contexts, `volatile` doesn't make `++` atomic; the read-modify-write can interleave and lose an update. And on cores with weak memory ordering, `volatile` doesn't insert the barriers needed to make the ISR's writes visible to the thread in the intended order.

Then I'd move to what "safe" actually looks like for their case. For a single-word flag used purely as a signal, the right primitive is an atomic type (`atomic_t` in Zephyr) with the appropriate memory ordering, or a proper synchronization object. For anything larger, the pattern is to keep the shared data behind a lock-free single-producer/single-consumer structure — a ring buffer with atomic head/tail indices — or to use a `k_sem`/`k_mutex` if blocking is acceptable in the thread context. The ISR side should do the minimum: write the data, then publish it with a release-store on the index or flag; the thread does an acquire-load before reading.

I'd frame it as "the code works today because the compiler and CPU happen to behave a certain way on this build — the goal is code that's correct by construction, not correct by luck." And I'd suggest we add a comment documenting the synchronization contract, because the next person to touch the module needs to know which accesses are protected and how.

**Possible follow-ups:** When is a single `volatile` flag actually sufficient, and what has to be true about the data it guards? How would you review a module to find places where `volatile` is being used as a substitute for real synchronization?

## Q5: How would you approach designing a firmware module that must survive a brownout — where the supply voltage sags briefly but doesn't fully drop — without corrupting persistent state or producing a spurious reset?

**Answer:** A brownout is dangerous precisely because it's ambiguous: the MCU may keep running while its peripherals, its flash, and its analog front end are all operating outside spec, so the firmware can do real damage — a half-written flash page, a corrupted configuration record, a spurious sensor reading acted on — before any reset happens. I'd design for it at three levels: detect it, protect persistent state, and recover cleanly.

Detection first. Most modern MCUs have a brownout detector or programmable voltage-level monitor that can generate an interrupt before the core becomes unreliable. I'd enable it and set the threshold with margin above the minimum operating voltage of the whole system — not just the MCU, but the flash and any external parts that matter. If the part lacks a hardware detector, an ADC channel on the supply rail sampled periodically can serve as a slower backstop. The detector interrupt should be treated as an emergency: its handler does the absolute minimum to put the system into a safe state and must not itself depend on anything that could be unreliable at low voltage.

Protection of persistent state is where the real design work is. The rule is that any flash write must be atomic from the perspective of a reader after an arbitrary power interruption. That means never overwriting live data in place: write the new record to a fresh location, then commit it with a single small write — a sequence number, a CRC, or a valid flag — that a reader checks before trusting the record. On boot, scan for the most recent valid record and discard anything incomplete. For configuration, a double-buffered or log-structured scheme with a CRC per record handles this cleanly. I'd also make sure the flash driver itself doesn't start a write it can't finish: check the supply state before initiating a write, and if the voltage monitor fires mid-write, let the write complete if the hardware can, or accept that the record is lost but the previous one is intact.

Recovery: on the next boot, the firmware should be able to tell "I reset because of a brownout" from "I reset because of a watchdog or a software fault," because the response differs. A brownout reset should trigger a validation pass over persistent state and a re-initialization of peripherals that may have been left in an undefined state. And I'd make sure the reset itself is clean — a spurious reset caused by the brownout detector firing on a legitimate transient is its own bug, so the threshold and any filtering need to be tuned against the actual supply behavior, not just the datasheet minimum.

**Possible follow-ups:** How would you test brownout behavior without a programmable supply, and what would you look for in the results? What's the difference between a brownout detector and a power-on reset, and why does the firmware need to distinguish them?
