# firmware — Day 120

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual ISR entry/exit overhead, the per-interrupt work, and the resulting CPU utilization at the expected event rate. If servicing every event individually is genuinely too expensive, there are several standard patterns to consider, and the right choice depends on what the data actually needs.

The most common approach is to move from per-event interrupts to **DMA-driven transfers with completion or half-transfer interrupts**. Instead of interrupting on every byte or sample, the DMA engine fills a buffer in the background and only interrupts when a block is complete (or when the buffer is half full, so the CPU can process one half while the other fills). This amortizes interrupt overhead across many events and is the natural fit for streaming data from SPI, I2C, ADC, or UART peripherals.

If DMA isn't available or appropriate, the next option is to **coalesce interrupts in the peripheral itself** — many peripherals have FIFOs or watermark thresholds that let you interrupt only when N samples are available, rather than on every one. Configuring the FIFO threshold correctly is often the single highest-leverage change.

A third pattern is **interrupt mitigation at the controller level**: some interrupt controllers support rate limiting or "interrupt after quiet period" behavior, though this is less portable and should be used carefully because it can mask real events.

Regardless of mechanism, the ISR itself should do the minimum possible work — capture the data or advance a pointer, then defer processing to a work queue or thread. The key discipline is to keep the ISR bounded and predictable, and to make the deferred context do the heavy lifting. I'd also instrument the system to confirm the fix actually reduced CPU load, because it's easy to move the bottleneck rather than eliminate it.

**Possible follow-ups:** How would you size the DMA buffer, and what happens if the consumer thread falls behind? How would you verify that no events are being dropped after the change?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first instinct should be to suspect that attaching the debugger changes timing, power state, or memory layout — any of which can mask the real fault. I'd approach it systematically rather than by trial and error.

First, I'd characterize what "misbehaves" means precisely: is it a hang, a wrong value, a reset, a communication error? The symptom narrows the suspect list enormously. Then I'd look for the ways a debugger perturbs the system: it halts the core (changing timing), it may keep certain clocks or peripherals alive, it can disable low-power modes, and it changes flash/RAM access patterns. Any of these can hide a race condition, a timing violation, or a power-management bug.

The most productive technique is usually to **replace the debugger with non-intrusive instrumentation**: GPIO toggles around suspect code paths viewed on a scope or logic analyzer, a ring buffer in RAM that logs events and can be dumped after the fact, or a UART trace at low baud. This preserves real timing while still giving visibility. I'd also enable fault handlers that capture the stacked registers and fault status on any exception, so a crash leaves evidence.

I'd then form hypotheses and test them: is it a race between an ISR and a thread? A peripheral that needs a delay the debugger was inadvertently providing? A low-power transition that only happens standalone? A stack or heap issue that the debugger's memory layout happens to avoid? Each hypothesis suggests a specific experiment — adding a barrier, checking a status flag, disabling a sleep mode temporarily, or enabling stack painting and canaries.

The discipline is to change one variable at a time and confirm the fix under conditions as close to production as possible, including temperature, supply, and load.

**Possible follow-ups:** How would you capture evidence from a device that has already crashed in the field with no debugger attached? What role does compiler optimization level play in this kind of bug?

## Q3: How would you approach deciding whether a given piece of firmware logic belongs in an interrupt service routine, a deferred context like a work queue or thread, or a low-priority background task?

**Answer:** The decision comes down to a few concrete criteria: how latency-critical the work is, how long it takes, whether it can block, and what it shares with other code.

The ISR is the right home only for work that must happen within microseconds of the event and is short and bounded — capturing a timestamp, reading a data register before it's overwritten, clearing the interrupt source, and signaling a deferred context. Anything that can block (waiting on a mutex, a bus transaction, a sleep) must never run in an ISR. Anything with unbounded or long execution time — parsing a message, writing to flash, running a filter over a buffer — belongs in a deferred context, because holding off interrupts for that long harms the whole system's responsiveness.

Between a work queue/thread and a low-priority background task, the distinction is about scheduling semantics. A work queue or a dedicated thread with a defined priority gives you deterministic response relative to other threads and integrates with the RTOS scheduler; it's the right choice when the deferred work has a real deadline or ordering requirement. A low-priority background task is appropriate for genuinely best-effort work — housekeeping, logging flush, statistics — that should yield to everything else and can tolerate latency.

I'd also consider the data-sharing implications: moving work out of the ISR usually means the ISR and the deferred context share a buffer, so the design must include a correct synchronization mechanism (a lock-free ring buffer, a message queue, or a semaphore) rather than a bare global. The split should be documented so future maintainers understand why each piece lives where it does.

**Possible follow-ups:** How would you handle a case where the deferred context can't keep up with the ISR's event rate? What's the risk of doing too much deferral, and how would you detect it?

## Q4: You're implementing a firmware module that must log diagnostic events to flash, where the log must survive a power loss mid-write and the flash has limited erase cycles. How would you approach designing the storage scheme?

**Answer:** There are two independent problems here — crash consistency and wear — and the design needs to address both.

For crash consistency, the core principle is that a log entry must never be considered valid until it's fully written and committed. A common approach is a **record-based log with a commit marker**: write the payload first, then write a small header or trailer containing a sequence number and a CRC (or equivalent integrity check) as the final step. On startup, the logger scans for the last record with a valid CRC and treats anything after it as incomplete and discardable. This means a power loss mid-write leaves at worst a torn record that's ignored, never a corrupted log. Some flash parts support programming in small units where the commit byte can be written last within the same page, which makes the atomicity cleaner.

For wear, the key is to avoid rewriting the same physical location repeatedly. A **circular log across a dedicated flash region** spreads writes evenly: entries append sequentially, and when the region fills, the oldest sector is erased and reused. Erase happens per sector, not per entry, so the erase count per sector is roughly proportional to how often the whole region cycles — far better than erasing on every write. If the flash supports it, wear leveling at the block level (rotating which sector is "next") further evens out the load. I'd also size the region against the expected event rate and the flash's rated endurance to confirm the design meets the product's lifetime, and consider whether some events can be aggregated or filtered to reduce write volume.

Finally, I'd make the log format versioned and self-describing, so a firmware update can still read old entries, and I'd test the design by deliberately cutting power at random points during writes and verifying recovery.

**Possible follow-ups:** How would you handle the case where the log region is completely full and a new critical event arrives? What would you do if the flash's erase granularity is much larger than a single record?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd start by reframing the disagreement away from "which is better in general" toward "which meets this system's actual requirements," because both engineers are describing real trade-offs and the right answer depends on the specifics.

First, I'd get the requirements on the table explicitly: what's the worst-case latency the protocol must meet, what's the expected and peak message rate, how much CPU headroom exists, and what other tasks share the processor. Polling gives deterministic, bounded behavior and avoids ISR/thread synchronization complexity, but it wastes CPU when idle and can miss events if the poll interval is too coarse. Interrupts give low latency and free the CPU when idle, but add ISR overhead, concurrency hazards, and less predictable timing under load. Neither is universally correct.

Then I'd ask both engineers to make their case against those numbers rather than against intuition — for example, what worst-case latency does each approach actually deliver at peak load, and what's the CPU cost of each? Often this reveals that one approach clearly wins for the given constraints, or that a hybrid is best: interrupt-driven reception with a deferred processing context, which gets responsiveness without doing heavy work in the ISR.

If the data doesn't settle it, I'd propose a small, time-boxed prototype or benchmark of the critical path in each style, measured against the same criteria. That converts an opinion debate into an evidence-based decision and gives both engineers ownership of the outcome. I'd document the decision and the reasoning so it doesn't get relitigated, and I'd make clear that the goal is the right system, not winning the argument.

**Possible follow-ups:** How would you handle it if the benchmark is inconclusive and a decision still has to be made? How would you keep the losing engineer engaged and bought into the chosen approach?
