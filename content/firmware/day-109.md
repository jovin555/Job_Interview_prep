# firmware — Day 109

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual interrupt rate, the per-ISR cost (entry/exit overhead plus register access), and the resulting CPU utilization. If servicing every interrupt would consume, say, 40% of the CPU, that's a design constraint to be solved, not a nuisance to be tolerated.

The core techniques, roughly in order of preference:

1. **Reduce the number of interrupts, not the work.** Most peripherals that generate high interrupt rates do so because they're configured to interrupt per-sample or per-byte. Reconfigure to interrupt on a threshold, a FIFO watermark, or a burst-complete condition. A UART that interrupts per byte becomes a UART that interrupts per FIFO-half-full; an ADC that interrupts per conversion becomes one that interrupts per DMA half-buffer. This is usually the single biggest win and requires no architectural change.

2. **Move the data with DMA.** If the peripheral supports it, let DMA move samples into a ring buffer and interrupt only on half-transfer and transfer-complete. The ISR then does almost nothing — it signals a consumer and returns. This decouples the CPU from the data rate entirely.

3. **Coalesce in the ISR.** If DMA isn't available, the ISR should do the absolute minimum (read the data register, push to a buffer, increment a counter) and defer all processing to a thread or work queue. The ISR cost then becomes dominated by entry/exit overhead, which you can further amortize by handling multiple pending events per invocation where the hardware allows it.

4. **Use a deferred/bottom-half context.** A work queue or a dedicated thread drains the buffer. This keeps interrupt-disabled time short and lets the scheduler make trade-offs between this consumer and other work.

5. **Consider polling as a deliberate choice.** If the rate is high enough and the data is latency-tolerant, a tight polling loop in a high-priority thread can actually be cheaper than interrupt overhead — but only if you can afford the CPU and the thread is genuinely the highest priority. This is a trade-off to be made with measurements, not dogma.

Throughout, the design should be driven by a latency budget: what is the maximum acceptable delay between data arriving and the consumer seeing it? That number determines whether DMA + ring buffer is sufficient or whether you need a more aggressive scheme. And the ISR must remain short and bounded — never do floating-point math, logging, or blocking calls in it.

**Possible follow-ups:**
- How would you verify that your ISR is actually as short as you think it is, and what tooling would you use to measure worst-case interrupt latency?
- What happens to your design if the consumer thread occasionally falls behind — how does the ring buffer behave, and how do you detect and handle overflow?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first instinct should be to enumerate *why* attaching a debugger changes behavior, because each cause points to a different investigation:

1. **Timing.** The debugger slows execution, changes instruction timing, and can mask race conditions. A bug that disappears under the debugger is often a race — between an ISR and a thread, between two threads, or between firmware and a peripheral. The fix is to reason about the race explicitly: identify shared state, check whether access is properly synchronized (atomics, mutexes, critical sections, memory barriers), and consider whether the compiler is reordering accesses the hardware cares about.

2. **Halt-on-breakpoint side effects.** Many debuggers halt peripherals, watchdogs, and DMA when the core is stopped. A watchdog that would fire in standalone operation may never fire under the debugger; a DMA transfer that would overrun may complete cleanly. So the debugger can *hide* the very failure you're chasing.

3. **Debug peripheral state.** Some MCUs change clock configuration, disable low-power modes, or alter flash wait states when a debugger is attached. If the bug only appears in a low-power mode or at a particular clock speed, the debugger's presence may be preventing the condition from occurring.

4. **Optimization and code layout.** Debug builds are often unoptimized and laid out differently. A bug that only appears in the release build may be a compiler optimization issue (missing `volatile`, missing barrier, undefined behavior) or a timing-sensitive issue that the slower debug build masks.

My approach: first, reproduce the failure without the debugger using instrumentation that doesn't perturb timing much — GPIO toggles, a RAM-based trace buffer, or a logic analyzer on a spare pin. Capture the state at the moment of failure. Then compare the standalone and debugger-attached execution paths: same clock config? same power mode? same optimization level? If the bug is timing-related, add deliberate delays or stress the timing (run at temperature extremes, vary supply voltage, add CPU load) to make it reproducible. If it's a memory issue, enable stack canaries, MPU guards, or a heap checker. The goal is to convert an intermittent, debugger-sensitive failure into a deterministic one you can actually analyze.

**Possible follow-ups:**
- How would you use a logic analyzer or GPIO toggles to instrument a timing-sensitive bug without changing the timing you're trying to observe?
- If you suspect a missing memory barrier or a `volatile` issue, how would you confirm that hypothesis without simply adding `volatile` everywhere?

## Q3: How would you approach deciding whether a piece of firmware logic belongs in an interrupt service routine versus a deferred context such as a work queue or a thread?

**Answer:** The decision comes down to a few concrete criteria, and I'd evaluate them in roughly this order:

1. **Latency requirement.** What is the maximum acceptable delay between the event and the response? If the hardware requires an action within microseconds — clearing a flag before the next event, reading a data register before it's overwritten, toggling a line within a tight window — that action must be in the ISR. Everything else can be deferred.

2. **Duration and blocking behavior.** The ISR must be short and must never block. If the logic involves waiting for a peripheral, taking a mutex, allocating memory, doing floating-point math, or logging, it does not belong in the ISR. Those operations belong in a thread or work queue where the scheduler can preempt them and where blocking is legal.

3. **Interrupt-disabled time.** Even a short ISR disables interrupts (or at least masks lower-priority ones) for its duration. If the logic would hold interrupts off for longer than the system's worst-case latency budget allows, it must be split: a minimal ISR that acknowledges the hardware and signals a deferred context, and the bulk of the work in that context.

4. **Concurrency and shared state.** Deferred contexts can use proper synchronization primitives (mutexes, semaphores, message queues) and can be reasoned about with the scheduler's priority model. ISRs can only use ISR-safe primitives. If the logic needs to interact with other threads or shared data structures in non-trivial ways, deferring it makes the concurrency model far simpler and safer.

5. **Determinism vs. throughput.** ISR execution is deterministic in the sense that it runs immediately, but it competes with all other interrupts. A work queue or thread gives you scheduling control and priority-based preemption, which is often what you actually want for anything that isn't a hard real-time hardware handshake.

The practical pattern is almost always: **ISR does the minimum hardware interaction, then signals a deferred context.** The ISR reads the data, clears the flag, and posts to a queue or gives a semaphore. The thread or work queue does the processing. The only question is whether the "minimum" is small enough — and if it isn't, the answer is to push more of it out of the ISR, not to make the ISR longer.

**Possible follow-ups:**
- How would you decide between a work queue and a dedicated thread for the deferred context, and what are the trade-offs in terms of stack usage and scheduling?
- What ISR-safe synchronization primitives would you use to signal a thread from an ISR, and why can't you use a mutex there?

## Q4: How would you approach designing a firmware module that must handle a peripheral whose data-ready signal is edge-triggered, but where the signal can occasionally glitch and produce a spurious edge that does not correspond to valid data?

**Answer:** The core problem is that an edge-triggered signal carries no information about *why* the edge occurred, so a glitch is indistinguishable from a real event at the interrupt-controller level. The design has to add validation on top of the edge detection.

My approach, in layers:

1. **Hardware filtering first.** Before touching firmware, check what the hardware offers: input debounce filters, Schmitt-trigger inputs, or a simple RC filter on the board. If the glitch is a genuine electrical artifact, filtering it at the source is far more robust than handling it in software. This is a conversation to have with the hardware team, and it's worth having early.

2. **Validate in the ISR.** When the ISR fires, don't assume the data is valid. Read the peripheral's status register and confirm that a real data-ready condition is actually asserted. Many peripherals have a status bit that reflects the true state; if the edge was spurious, the status bit will be clear and the ISR can simply return. This is the cheapest and most direct defense.

3. **Validate the data itself.** Even if the status bit says data is ready, apply the module's normal data validation: range checks, CRC or checksum where available, sequence-number continuity, or a plausibility check against the previous sample. A spurious edge that produces a garbage read will usually fail one of these.

4. **Debounce in time.** If glitches occur in bursts, require that the signal be stable for a minimum interval before accepting the event — either by re-reading the pin after a short delay, or by counting edges within a window and rejecting implausible rates. This must be done carefully so it doesn't add latency to legitimate events.

5. **Recover gracefully.** If a spurious edge is detected, the module should discard the event, log it (rate-limited, so a glitch storm doesn't flood the log), and continue. It should not enter an error state or reset the device for a single glitch — but a sustained rate of glitches should be surfaced as a diagnostic condition, because it may indicate a hardware problem.

6. **Test it deliberately.** Inject glitches — via a signal generator, a GPIO toggle in a test harness, or a fault-injection build — and verify that the module rejects them without dropping legitimate events. The test should cover both isolated glitches and bursts.

The key principle is defense in depth: hardware filtering where possible, status-register validation in the ISR, data validation in the consumer, and graceful recovery with diagnostics. No single layer is trusted to be perfect.

**Possible follow-ups:**
- How would you distinguish a glitch from a genuine high-rate event if the peripheral legitimately produces edges faster than your debounce window?
- What would you log, and at what rate, to make a glitch problem diagnosable in the field without the log itself becoming a problem?

## Q5: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I'd start by acknowledging the part they've got right — `volatile` *does* prevent the compiler from caching the variable in a register or eliminating accesses to it, which is necessary for the ISR and thread to see each other's writes. The gap is that `volatile` provides only that: it does not provide atomicity, and it does not provide ordering with respect to other memory accesses. Those are the two things that make the pattern unsafe.

Concretely, I'd walk through the failure modes:

1. **Atomicity.** A `volatile` flag is fine if it's a single byte or word that's read and written atomically by the hardware. But if the shared data is larger than the native word size — a 32-bit counter on an 8-bit MCU, a struct, a buffer — a `volatile` qualifier does nothing to prevent the reader from seeing a torn value mid-update. The flag being volatile doesn't make the data it guards atomic.

2. **Ordering.** The compiler and the CPU can reorder accesses. A thread might write the data, then set the flag — but without a barrier, the compiler could reorder those, or the CPU could commit them out of order, so the ISR sees the flag set before the data is actually visible. `volatile` does not prevent this reordering. You need a memory barrier or an atomic operation with the right ordering semantics.

3. **Lost updates and races.** If both sides do read-modify-write on the variable, `volatile` doesn't make that atomic. Two contexts can interleave and lose an update.

The fix depends on what the variable is actually doing:

- If it's a **single flag** signaling "data ready," the right primitive is an atomic flag or a semaphore/event object — something with defined memory-ordering semantics. In Zephyr, a `k_sem`, `k_event`, or `atomic_t` with the appropriate memory barrier is the idiomatic choice.
- If it's a **shared buffer**, the pattern is a proper producer-consumer structure: a ring buffer with atomic head/tail indices, or a message queue, or a mutex-protected structure if the ISR side can be deferred. The ISR should never take a mutex, so the design usually becomes "ISR posts to a queue, thread consumes."
- If it's a **counter or status word**, use `atomic_t` operations or a critical section.

I'd frame the guidance around the question "what guarantee do you need?" — visibility, atomicity, or ordering — and show that `volatile` only gives the first, partially. Then I'd pair with them to refactor one instance, write a test that stresses the ISR/thread interaction (high interrupt rate, tight loop on the consumer), and let the test demonstrate the difference. The goal is for them to internalize that `volatile` is a compiler directive, not a concurrency primitive, and that the correct primitive is chosen based on the guarantee required.

**Possible follow-ups:**
- How would you explain the difference between a compiler barrier and a hardware memory barrier, and when would you need each?
- If the shared variable is a single `bool` flag and the platform guarantees atomic byte access, is `volatile` alone ever acceptable — and what would still be missing?
