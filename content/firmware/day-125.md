# firmware — Day 125

## Q1: How would you approach implementing a state machine for a device's operational modes where the same event can arrive from multiple sources — a user interface, a communication interface, and an internal timer — and the correct transition depends on which source sent it?

**Answer:** The key insight is that the event itself is not the transition trigger — the pair of (current state, event, source) is. So I'd model the event as a small struct or tagged value that carries both an event ID and a source ID, rather than a bare enum. The transition table then keys on all three: a "START" event from the UI might be legal in Idle but rejected in Calibration, while the same "START" from the internal timer might be a no-op or a fault depending on state.

I'd centralize the transition logic in one place — a table of `{state, event, source} -> {next_state, action}` entries, or an explicit switch that dispatches on state and then on source. Scattering the source checks across the modules that generate events is what makes these systems unmaintainable; the generator should just post the event with its source tag and let the state machine decide.

Two practical concerns: first, events from different sources may arrive concurrently (UI task, comms task, timer ISR), so the state machine needs a single serialization point — a queue drained by one task, or a mutex around the transition function — otherwise two events can race and produce an illegal state. Second, I'd make illegal transitions explicit: log them with state, event, and source, and either ignore or fault depending on how safety-critical the mode is. Silent acceptance of an unexpected transition is how devices end up in states nobody designed.

For testability, the transition table is data, so I can unit-test every (state, event, source) combination exhaustively without hardware — which matters a lot when the same event means different things depending on origin.

**Possible follow-ups:** How would you handle an event that arrives while a transition action is still executing — queue it, drop it, or block the source? And how would you represent the source tag so that adding a new source later doesn't require touching every transition entry?

## Q2: You're debugging a firmware issue where a device's behavior is correct on the first power-up after flashing, but after a warm reset (without power cycling) a peripheral initializes incorrectly. How would you approach this?

**Answer:** The first thing I'd suspect is that the peripheral — or something feeding it — is not actually returning to its power-on default state on a warm reset. A warm reset resets the CPU and its peripherals, but external chips, regulators, and analog front-ends may still be powered and holding whatever state the previous firmware run left them in. So the firmware's init sequence, which was written assuming a cold-boot peripheral, is now running against a peripheral that's already configured, mid-transaction, or holding a bus line.

I'd start by comparing the two cases directly: instrument the init sequence to dump the peripheral's key registers (or the bus state) at the top of init, once after cold boot and once after warm reset, and diff them. If the peripheral's registers differ, that confirms it. I'd also check the bus itself — a warm reset can leave an I2C slave holding SDA low mid-transfer, so the master sees a stuck bus and every transaction fails until it's cleared.

The fix is usually one of: a hardware reset line to the peripheral that firmware asserts at the top of init (so warm and cold boot converge), a software reset command to the peripheral if it has one, or explicit bus-recovery logic (clock out extra pulses to free a stuck slave) before the first transaction. I'd also make the init sequence idempotent — it should bring the peripheral to a known state regardless of what state it was in — rather than assuming defaults.

The broader lesson I'd carry: any init sequence that only works from a known-cold starting point is fragile. I'd want to verify it against a warm reset, a watchdog reset, and a brownout recovery, because those are the resets that actually happen in the field.

**Possible follow-ups:** How would you distinguish a stuck bus from a peripheral that's simply in the wrong configuration? And if the peripheral has no reset line and no software reset, what's your fallback?

## Q3: How would you approach configuring DMA for a peripheral that streams data continuously, where the data rate is high enough that per-transfer interrupts would consume too much CPU, but the buffer is too small to hold an entire acquisition?

**Answer:** This is the classic circular-buffer-plus-DMA pattern, and the design hinges on decoupling "DMA moves bytes" from "CPU consumes them" so the CPU is interrupted at a rate it can afford, not at the data rate.

I'd set up the DMA in circular mode over a buffer sized to hold several multiples of the consumer's worst-case service interval — enough that the consumer can be delayed by other work without the DMA lapping it. The DMA writes continuously and wraps; the CPU doesn't touch the buffer until it's told there's data. The notification mechanism is the interesting choice: rather than an interrupt per transfer, I'd use half-transfer and full-transfer interrupts (most DMA controllers support these), so the CPU wakes twice per buffer revolution — once when the first half fills, once when the second half fills. That gives the consumer a full half-buffer of slack to process the previous half before the DMA overwrites it.

The critical correctness concern is the race at the wrap boundary: the consumer must never read a region the DMA is actively writing. With half/full interrupts, the contract is that when the half-transfer interrupt fires, the first half is complete and stable while the DMA works on the second half — so the consumer processes the first half and vice versa. I'd document that contract explicitly and, in debug builds, add a watermark check that the consumer hasn't fallen behind (e.g., the DMA's current position has passed the region being read).

If the consumer can't keep up even at half-buffer granularity, that's a throughput problem, not a DMA-configuration problem — the answer is a bigger buffer, a faster consumer, or dropping data deliberately with a counter, not more interrupts.

**Possible follow-ups:** How would you size the buffer if the consumer's service time is variable — say, it occasionally blocks on a flash write? And how would you detect and report an overrun where the DMA lapped the consumer?

## Q4: A junior engineer has implemented a firmware module that works correctly in testing, but you notice it relies on a global variable to communicate between two threads without any synchronization. They argue that the variable is just a flag and "it's only one byte, so it's atomic." How would you guide them?

**Answer:** I'd start by acknowledging the part they're right about — a single-byte aligned store is typically atomic at the hardware level on most MCUs, so a torn read isn't the failure mode here. Then I'd walk them through the failure modes that *are* real, because "atomic" and "correctly synchronized" are different guarantees.

The first is compiler and CPU reordering: without a barrier or an atomic type, the compiler is free to reorder the flag access relative to the data it's supposed to protect, and the CPU may too. So the reader can see the flag set before the data it guards is visible — the classic broken double-checked pattern. The second is that a plain flag gives no memory-ordering guarantee between the writer's data stores and the flag store, so even if the byte itself is atomic, the *sequence* isn't. The third is that "it's only one byte" stops being true the moment someone adds a second flag or a counter next to it, and the code silently becomes wrong.

The fix depends on intent. If it's genuinely a one-way signal, I'd use the RTOS's primitives — a `k_sem`, an `atomic_t` with the appropriate memory order, or a `k_event` — which encode the ordering and make the intent legible. If it's protecting shared data, a mutex or a proper lock-free structure with documented memory ordering. The point I'd make to them is that the primitive isn't overhead, it's the specification of what the code guarantees; a bare flag specifies nothing, so every future reader has to guess.

I'd frame it as a maintainability issue as much as a correctness one: the next engineer can't tell from `flag = 1` whether ordering matters, so they'll either over-engineer around it or break it. Naming the synchronization intent in the type is how the codebase stays correct as it grows.

**Possible follow-ups:** How would you demonstrate the reordering failure concretely — what would you show them on a scope or in a disassembly? And when *is* a bare `volatile` flag actually sufficient, if ever?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd resist settling it as a matter of preference and instead turn it into a question about the actual requirements — because both of them are right about different systems, and the disagreement usually dissolves once the numbers are on the table.

First I'd get the concrete constraints: what's the message rate and worst-case latency budget, what's the CPU headroom, what else is running, and what's the cost of a missed message? Polling is genuinely simpler and more deterministic *if* the poll loop can run often enough to meet the latency budget without starving other work — that's a real property, not a rationalization. Interrupts win when the event rate is low but the latency requirement is tight, or when the CPU needs to sleep between events, because polling forces the CPU awake. So the decision criteria are latency budget, event rate, CPU budget, and power — not "which is more modern."

Then I'd have them each prototype the critical path — not the whole protocol, just the receive-and-dispatch path — and measure worst-case latency and CPU load under realistic conditions. A day of measurement beats a week of debate, and it forces both of them to confront the same numbers. I'd specifically want to see the interrupt version's worst-case latency under heavy interrupt load (interrupt latency isn't constant) and the polling version's jitter when other tasks run long.

If the measurements don't clearly favor one, I'd lean toward the simpler design — polling — because simplicity is a real asset in safety-critical firmware, and add interrupts only where the measurements show polling can't meet the budget. I'd also make clear this is a decision we're making together with shared data, not one engineer overruling the other, so whoever "loses" is bought in.

**Possible follow-ups:** What would you do if the prototype shows polling meets the latency budget but only at 90% CPU utilization — is that acceptable? And how would you structure the code so the decision can be revisited later without a rewrite?
