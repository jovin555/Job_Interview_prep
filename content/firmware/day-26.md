## Q1: You're debugging a firmware issue where a device's ADC readings are correct when the device is first powered on, but drift and become noisy after about 30 minutes of operation. The device is battery-powered and uses a switching regulator. How would you approach this?

**Answer:** I'd approach this systematically, recognizing that a time-dependent thermal drift pattern points to a few likely culprits. First, I'd verify whether the drift correlates with temperature by measuring the board temperature at failure time — if the regulator or ADC reference is heating up, that's a strong signal. I'd check the ADC reference voltage stability, since many internal references drift significantly with temperature; if the design uses an internal reference, I'd compare against an external precision reference. I'd also examine the switching regulator's output ripple under load — as components heat up, ESR of capacitors increases, which can degrade ripple performance and couple noise into the analog supply. I'd use a scope to measure the regulator output and ADC supply pins at both cold and warm states, looking for increased ripple or droop. I'd also check if the battery voltage itself is sagging over time, which could push the regulator out of its optimal operating range. Finally, I'd review the firmware's ADC configuration — is the sampling timing or averaging being affected by other system activity that changes over time? I'd instrument the firmware to log raw ADC values, temperature readings if available, and battery voltage over the failure period to correlate the onset of noise with other system parameters.

**Possible follow-ups:** How would you distinguish between a thermal issue and a firmware issue if the data doesn't clearly point to one? What design changes would you consider to make the ADC measurement more robust against regulator noise?

## Q2: You're designing a Zephyr RTOS-based system where multiple sensor threads need to share a pool of fixed-size data buffers. How would you choose between using a memory pool versus memory slabs, and what configuration considerations would you need to account for?

**Answer:** In Zephyr, memory slabs and memory pools both provide fixed-size block allocation, but they differ in flexibility and overhead. Memory slabs allocate fixed-size blocks — all blocks are the same size — which is ideal when all sensor data buffers are identical. Memory pools support multiple block sizes, which adds flexibility but also complexity and overhead in the allocator. For a sensor system where each sensor produces similarly sized data chunks, I'd lean toward memory slabs for their simplicity, determinism, and lower fragmentation risk. However, if sensors produce significantly different data sizes — say one produces 64-byte samples and another produces 512-byte samples — a memory pool with multiple block sizes would be more memory-efficient than allocating the largest size for everything. Key configuration considerations include: ensuring the total memory allocated is sufficient for worst-case concurrent usage across all threads; setting the block size to accommodate the largest data payload plus any header overhead; and configuring the number of blocks to handle peak demand without exhausting the pool. I'd also consider whether blocking allocation is acceptable — if a thread can block waiting for a buffer, that's fine for lower-priority tasks, but a high-priority sensor thread should use non-blocking allocation with a fallback strategy (like dropping the oldest sample) to avoid priority inversion or deadlock. I'd also think about whether buffers need to be returned from ISR context, which affects which allocation API is safe to use.

**Possible follow-ups:** How would you handle the case where all buffers are exhausted and a high-priority sensor thread needs one immediately? What are the trade-offs between static per-thread buffers versus a shared pool?

## Q3: You're reviewing a colleague's firmware code that implements a communication protocol using a single large interrupt service routine that handles both byte-level reception and complete message parsing. The ISR disables interrupts for the entire duration, which can be up to 300 µs for a long message. The system also has a 1 kHz control loop that must meet strict timing. How would you approach this situation?

**Answer:** This is a classic interrupt latency problem. A 300 µs ISR is far too long for a system with a 1 kHz control loop — that's 30% of the control period spent with interrupts disabled, which will almost certainly cause jitter or missed deadlines. I'd approach this by separating the concerns: the ISR should do the minimum work necessary — moving bytes from the peripheral into a buffer — and defer all parsing and protocol handling to a lower-priority context. The standard pattern is to have the ISR fill a ring buffer (or use DMA to transfer bytes directly to memory), then signal a protocol task via a semaphore or work queue. The parsing logic then runs as a normal thread, which can be preempted by the control loop's higher-priority task. This reduces the ISR to just a few microseconds. I'd also check whether DMA could eliminate the byte-level ISR entirely — if the UART or SPI peripheral supports DMA, the data can be moved to memory without CPU intervention, with a single interrupt at the end of a transaction or when the buffer is full. I'd discuss with the colleague the principle that ISRs should be as short as possible, and that moving work to thread context makes the system more maintainable and testable. I'd also point out that the current approach makes the system fragile — any increase in message length or parsing complexity directly impacts the control loop's timing.

**Possible follow-ups:** How would you handle the case where the protocol requires real-time response to certain messages? What if the parsing logic itself has timing constraints that can't be met in thread context?

## Q4: You're implementing a firmware module that must handle a sensor which occasionally returns invalid data (e.g., out-of-range values or CRC failures), where the device is a medical monitor that must never display a false reading to the clinician. How would you approach this?

**Answer:** This is fundamentally about data integrity and fail-safe behavior in a medical context. I'd approach it in layers. First, at the driver level, I'd validate every reading before it enters the system: check CRC if the protocol supports it, verify the value is within the sensor's specified operating range, and check for consistency with recent readings (e.g., a sudden jump that's physiologically impossible). If a reading fails validation, I'd discard it and mark that sample as invalid rather than propagating a potentially false value. Second, at the application level, I'd implement a policy for how many consecutive invalid readings trigger a degraded state. A single bad sample might be retried or ignored, but a pattern of failures indicates a real problem. The device should transition to a clearly indicated degraded mode — for example, showing "sensor error" or "check sensor connection" rather than displaying stale or interpolated data. The key principle is: never display a value that hasn't been validated, and never let the system silently continue with bad data. I'd also implement a data quality indicator that accompanies each displayed value — for instance, showing a confidence level or a "signal quality" icon. In terms of architecture, I'd separate the validation logic from the sensor driver so it can be unit-tested independently, and I'd make the validation rules configurable so they can be tuned without firmware changes. I'd also consider redundancy — if the system has multiple sensors measuring related parameters, cross-checking between them can catch individual sensor failures. Finally, I'd ensure that the failure handling itself is tested — including the transition into and out of degraded mode — as part of the verification process.

**Possible follow-ups:** How would you handle the case where the sensor recovers — should the device automatically resume normal operation, or require user acknowledgment? How would you distinguish between a sensor failure and a wiring/connection issue?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to use a state machine pattern or a table-driven approach for implementing a complex device protocol. One argues that a state machine is more readable and easier to debug, while the other argues that a table-driven approach is more maintainable and easier to extend. How would you guide the team to a decision?

**Answer:** I'd guide the team by reframing the discussion away from "which is better" and toward "what fits our specific constraints." Both approaches are valid, and the right choice depends on the protocol's characteristics, the team's familiarity with each pattern, and the long-term maintenance context. I'd start by having both engineers articulate the specific requirements: How complex is the protocol — how many states and transitions? How frequently will it change? Who will maintain it — the current team or future engineers? What are the failure modes we're most concerned about? For a protocol with a small, stable set of states, a hand-coded state machine is often clearer and easier to debug with a debugger — you can see exactly where you are in the code. For a protocol with many states and transitions that will evolve over time, a table-driven approach can be more maintainable because adding a transition is a data change rather than a code change. I'd also consider hybrid approaches — for example, a table-driven transition matrix with state entry/exit functions implemented as code. I'd suggest we prototype a small portion of the protocol in both styles and evaluate them against criteria we agree on: readability, testability, ease of adding a new state, and debugging experience. I'd also emphasize that this decision shouldn't be made on personal preference alone — we should consider the team's collective experience and what will be most maintainable over the product's lifetime. Finally, I'd ensure that whichever approach we choose, we document the pattern and the rationale so future engineers understand why it was selected.

**Possible follow-ups:** How would you handle the situation where one engineer strongly prefers their approach and is resistant to compromise? What criteria would you use to evaluate the two prototypes objectively?
