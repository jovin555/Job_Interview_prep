# firmware — Day 103

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual ISR entry/exit overhead, the per-interrupt work, and the resulting CPU utilization at the expected event rate. If servicing every interrupt would consume, say, more than a small fraction of the CPU budget, the fix is to decouple "acknowledging the event" from "processing the data."

The standard pattern is to make the ISR as short as possible — acknowledge the interrupt, move whatever is cheap to move (a single sample, a status word, a DMA pointer) into a lock-free structure like a ring buffer, and return. The heavy lifting (filtering, packing, protocol handling, logging) happens in a deferred context: a work queue item, a bottom-half thread, or a task woken by a semaphore. This keeps interrupt latency bounded and lets the scheduler decide when the processing runs.

If the rate is high enough that even a minimal ISR is too expensive, the next lever is to reduce the number of interrupts rather than the cost of each one. DMA is the primary tool: configure the peripheral to transfer a block of samples into memory and interrupt only on half-transfer and full-transfer (or on a watermark), so the CPU sees a handful of interrupts per buffer instead of one per sample. Where the hardware supports it, FIFOs and watermark thresholds achieve the same effect. For truly bursty sources, a timer-driven poll of a hardware FIFO can be more predictable than interrupt-per-event.

The trade-off to articulate is latency versus throughput versus jitter. Batching via DMA or FIFO thresholds adds a small, bounded latency (you wait for the buffer to fill or the watermark to trip) in exchange for a large reduction in CPU load. For a control loop that needs the freshest sample, you size the buffer small enough that the added latency is acceptable; for a logging path, you can afford a larger buffer. Either way, the design should be validated by measuring ISR duration, interrupt frequency, and worst-case deferred-context latency, not just by observing that "it works."

**Possible follow-ups:** How would you size the ring buffer between the ISR and the deferred context, and what happens when the consumer falls behind? How would you verify that the deferred processing is actually keeping up under worst-case load?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first instinct should be to treat the debugger's presence as a clue rather than an inconvenience. Attaching a debugger changes several things at once: it halts the core at breakpoints, it may slow execution, it can change memory layout and timing, and it often disables or alters low-power modes. Any of those can mask a timing-sensitive or power-related defect.

My approach is to first characterize what "misbehaves" actually means — a hang, a wrong value, a reset, corrupted data — because the symptom narrows the hypothesis space. Then I'd try to reproduce the failure without a debugger but with instrumentation that doesn't perturb timing the way a breakpoint does: GPIO toggles on a scope or logic analyzer, a ring buffer of timestamped events in RAM that can be dumped after the fact, or a UART log at a rate that doesn't dominate the CPU. If the failure disappears when I add logging, that itself is informative — it suggests a race or a timing margin that the logging is widening.

Common root causes for "works with debugger, fails standalone" include: uninitialized variables that happen to be zero under the debugger's memory setup; a race condition whose window the debugger's slowdown opens or closes; a watchdog that the debugger's halt suppresses; low-power mode entry that the debugger prevents; and timing assumptions (a delay loop calibrated for a slower clock) that only hold when execution is slowed. I'd also check whether the debugger's presence changes the clock configuration or disables a sleep instruction.

The disciplined path is to bisect: does the failure occur with the debugger attached but no breakpoints? With breakpoints but no halts? With the debugger physically disconnected but the same firmware? That isolates whether it's the halt, the slowdown, or the debug peripheral itself. Once I have a reliable standalone reproduction, I can instrument more aggressively and use the debugger only to inspect state after the fact.

**Possible follow-ups:** How would you capture evidence of a failure that only happens when no debugger is connected? What kinds of defects are most likely to be masked by a debugger's slowdown?

## Q3: How would you approach deciding what belongs in a bootloader versus what belongs in the application, for a device that must support field updates?

**Answer:** The guiding principle is that the bootloader should be as small, simple, and rarely-changed as possible, because it's the code you can't afford to get wrong — if it's broken, the device may be unrecoverable in the field. Everything that can change over the product's life, or that isn't needed to get a valid application running, belongs in the application.

Concretely, the bootloader owns: the initial hardware bring-up needed to access the update medium (flash controller, the bus the update arrives on, basic clock setup), the logic to decide which image to boot, image validation (CRC or cryptographic signature), the update/recovery state machine, and the minimal communication path needed to receive a new image when the application isn't running. It should not own application-level protocol parsing, user interface, sensor drivers, or anything that would need to change when features are added.

The application owns everything else, including the "normal" update client that downloads or receives the image and hands it to the bootloader — the application can be updated, so putting update logic there keeps the bootloader stable. The boundary is enforced by a well-defined interface: a shared memory region or flash metadata block describing the pending update, its validation status, and the boot decision, plus a documented handoff protocol (e.g., "application sets a flag and resets; bootloader reads the flag, validates, and either boots the new image or rolls back").

The trade-offs to discuss: putting more in the bootloader makes recovery more robust but increases the attack surface and the cost of fixing bootloader bugs (which may require a special recovery path). Putting more in the application keeps the bootloader small but means a corrupted application must still be recoverable by the bootloader alone. For a device with no physical recovery mechanism, I'd lean toward a bootloader that can always fall back to a known-good image and accept a new image over a minimal, well-tested transport, even if that transport is slower or less feature-rich than the application's.

**Possible follow-ups:** How would you handle a bootloader bug that's discovered after deployment, given that the bootloader itself can't be updated the normal way? What metadata would you store to let the bootloader make a safe boot decision after an interrupted update?

## Q4: How would you approach implementing a firmware module that must timestamp events with millisecond resolution across a device that sleeps for long periods, where the timestamp must remain monotonic and must not be corrupted by the sleep/wake transition?

**Answer:** The core problem is that the timebase you use while awake (a high-resolution timer or the system tick) may not be the same one that keeps counting while the device is in deep sleep, and the transition between them is where monotonicity breaks. The design should separate "what time is it" from "how do I measure short intervals."

The usual architecture is a hardware real-time counter (RTC) or a low-power timer that continues running in the deepest sleep mode the device supports, used as the persistent timebase, plus a higher-resolution timer for fine-grained intervals while awake. On wake, the firmware reads the RTC, compares it to the last recorded value, and advances a software monotonic counter by the delta — never by overwriting it with the raw RTC value, which could go backwards if the RTC was reset or if there's a wrap. The software counter is the single source of truth for event timestamps.

The subtle parts are the edges: the RTC may have a limited width and wrap, so the delta computation must handle wrap correctly (typically by treating the difference as unsigned and checking it's within a plausible range). If the RTC is battery-backed and survives a full power loss, the delta across a reset is still valid; if it isn't, the firmware must detect the reset (a magic value in retained memory, or a boot counter) and treat the timebase as discontinuous rather than silently producing a wrong delta. The sleep/wake transition itself should be atomic with respect to timestamping: capture the RTC reading and the wake reason together, so an event that arrives right at the boundary is attributed to the correct side.

For millisecond resolution specifically, I'd verify that the RTC's tick rate and the wake-up latency don't introduce more than the allowed error, and I'd document the resolution and the worst-case error rather than claiming exact milliseconds. If the application needs to correlate timestamps across resets, I'd persist the last known time and a boot identifier so the log can be reconstructed.

**Possible follow-ups:** How would you detect and handle an RTC that silently stops counting during sleep on some hardware? What would you do if the RTC resolution were coarser than the required timestamp resolution?

## Q5: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I'd start by acknowledging the part they got right: `volatile` does tell the compiler that the variable can change outside the current flow of control, so it won't cache the value in a register or eliminate the access. That's necessary for an ISR-shared variable, but it's not sufficient for correctness, and the gap is worth walking through concretely rather than just asserting "use atomics."

The key points to explain: `volatile` says nothing about atomicity — a multi-byte variable can be read while the ISR is writing it, producing a torn value — and nothing about ordering relative to other memory accesses, so the compiler and CPU can reorder a `volatile` access with respect to non-volatile data it's supposed to protect. It also doesn't provide mutual exclusion: if the thread does a read-modify-write, the ISR can interleave between the read and the write. So a `volatile` flag can work for a single-byte "data ready" signal in some cases, but it's fragile and doesn't generalize, and it gives no protection to the data the flag is guarding.

The better patterns depend on what's being shared. For a single flag or counter, use the platform's atomic operations or a proper synchronization primitive. For a data buffer, use a lock-free single-producer/single-consumer ring buffer with explicit memory barriers (or the RTOS's message queue / FIFO / mailbox, which encapsulate the barriers correctly). For a larger shared structure, a mutex or a critical section is appropriate, with the caveat that an ISR can't block on a mutex, so the ISR side uses a different mechanism (e.g., deferring to a work item). In Zephyr specifically, `k_sem`, `k_msgq`, `k_fifo`, and the atomic APIs are the idiomatic tools, and the memory model is documented.

I'd frame the guidance around consequences, not style: the failure mode of a `volatile`-only design is a rare, hard-to-reproduce corruption that shows up under load or on a different compiler optimization level, and those are expensive to debug later. I'd suggest they write a small test that exercises the ISR/thread interaction under stress and with optimization enabled, and I'd pair with them to refactor one module as a worked example so the pattern is concrete. The goal is for them to internalize "volatile is about compiler visibility, not synchronization" rather than to just follow a rule.

**Possible follow-ups:** Can you describe a specific scenario where a `volatile` flag would still be correct, and why? How would you explain memory barriers to someone who hasn't encountered them before?
