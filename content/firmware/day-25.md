## Q1: How would you approach implementing a firmware module that must handle a sensor which occasionally returns invalid data (e.g., out-of-range values or CRC failures), where the device is a medical monitor that must never display a false reading to the clinician?
**Answer:** The core principle is that invalid data must never propagate to the display or alarm logic. I'd structure the data path in layers: first, the driver layer validates raw data integrity (CRC, framing, bus-level errors) and discards or flags corrupt frames. Second, a validation layer applies plausibility checks — range limits, rate-of-change limits, and cross-channel consistency (e.g., if two sensors measure related parameters, a sudden change in one without the other is suspicious). Third, a decision layer determines the device state: if a single reading is invalid, I'd hold the last valid reading and mark it as "stale" rather than displaying a new value; if multiple consecutive readings fail, I'd transition to a degraded mode with a clear visual/audio alert. The key design choice is that the display always shows either a validated current reading or an explicit "data unavailable" state — never an unvalidated value. I'd also implement a configurable threshold for how many consecutive failures trigger a formal alarm, and ensure that the validation logic itself is testable with simulated invalid data injected at the driver level.

**Possible follow-ups:** How would you handle a sensor that returns valid-looking but systematically biased data (e.g., a slow drift)? How would you design the validation thresholds to avoid false alarms while still catching real problems?

## Q2: You're designing a Zephyr RTOS-based system where a high-priority sensor task must read data every 1 ms, but a lower-priority task occasionally needs to perform a flash erase that can block for up to 100 ms. How would you approach this scheduling conflict?
**Answer:** The fundamental issue is that a blocking flash operation in a lower-priority task can starve the high-priority sensor task if the RTOS scheduler can't preempt the blocking operation. In Zephyr, I'd first check whether the flash driver supports asynchronous or non-blocking operations — many flash controllers have a "busy" status that can be polled without blocking the CPU, or support interrupt-driven completion. If the hardware supports it, I'd use the flash driver's asynchronous API and have the lower-priority task yield while waiting. If the flash operation must be blocking, I'd consider moving the flash write to a dedicated lower-priority thread and using a message queue to pass data to it, but that doesn't solve the blocking problem by itself. The more robust approach is to use Zephyr's thread preemption: ensure the sensor task runs at a higher priority and that the flash task's blocking call is interruptible. In practice, this often means using a flash driver that supports yielding during the erase wait, or using DMA for the data transfer portion. If the hardware truly blocks the CPU during erase (some internal flash does), then I'd need to either buffer sensor data during the erase window (a 100 ms gap at 1 ms period means 100 samples of buffering, which may be acceptable depending on the sensor and memory), or restructure the system so the sensor task runs from a timer ISR rather than a thread, with data buffered in a ring buffer that the lower-priority task drains. The ISR approach guarantees the 1 ms sampling regardless of what other threads are doing.

**Possible follow-ups:** How would you size the ring buffer for the sensor data during the erase window? What if the sensor data rate is too high to buffer for the full 100 ms?

## Q3: How would you approach designing a low-power firmware architecture for a device that must wake periodically to sample a sensor, process the data, and transmit results wirelessly, while maximizing battery life?
**Answer:** I'd start by building a power budget from the datasheets: the sensor's active and sleep currents, the radio's TX current and duration, the MCU's active and sleep currents, and the time each component spends in each state. The architecture would use a state machine with explicit power states: deep sleep (MCU in the lowest sleep mode, sensors powered off, radio off), sample (wake sensor, allow stabilization time, take reading), process (MCU active, sensor can be powered down), and transmit (radio on, send data, then immediately return to deep sleep). Key design decisions include: using a low-power timer or RTC as the wake source rather than a high-frequency timer; sequencing power to peripherals so they're only powered during their specific phase; and minimizing the time spent in active states by doing processing in the shortest possible window. In Zephyr, I'd use the power management subsystem with PM states configured for the specific hardware, and I'd carefully manage the transition between states — particularly the sensor stabilization time, which is often overlooked. I'd also consider whether the radio can be turned off between transmissions and whether the sensor has a fast wake-up mode that avoids a long stabilization delay. The critical firmware aspect is that every wake cycle has a deterministic, minimal duration, and that the device spends the vast majority of time in the deepest sleep state.

**Possible follow-ups:** How would you handle a sensor that requires a long stabilization time after power-up? How would you measure and verify the actual power consumption in each state?

## Q4: You're reviewing a colleague's firmware code that uses a large number of global variables to share state between modules. The code works correctly in testing but is difficult to maintain and test. How would you approach refactoring this without introducing regressions?
**Answer:** I'd approach this as an incremental refactoring with a strong safety net. First, I'd establish a baseline: ensure there's adequate test coverage of the current behavior before changing anything — even if that means writing characterization tests that capture current outputs for given inputs, even if those outputs aren't ideal. Then I'd identify the data flow: which globals are written by which modules and read by which modules, and whether there are any implicit dependencies (e.g., module A writes a global that module B reads in a different order than expected). The refactoring strategy would be to group related globals into a single context struct that's passed explicitly to functions, starting with the most tightly coupled cluster. I'd do this one cluster at a time, running the test suite after each change. For globals that represent shared state between ISRs and main-loop code, I'd need to be careful about atomicity and use proper synchronization (critical sections or atomic operations) during the transition. I'd also look for opportunities to encapsulate the state behind accessor functions rather than exposing the variables directly, which gives a place to add validation or logging later. The goal isn't to eliminate all globals — some are legitimate for hardware registers or very low-level state — but to make the dependencies explicit and testable.

**Possible follow-ups:** How would you handle a global that's written from an ISR and read from multiple threads? How would you prioritize which globals to refactor first?

## Q5: A junior engineer on your team has implemented a low-power mode for a medical monitoring device that enters deep sleep between sensor readings. The device wakes on a timer interrupt, takes a reading, then goes back to sleep. However, the device occasionally misses readings because the sensor itself requires a 50 ms stabilization time after power-up before it produces valid data. The engineer proposes keeping the sensor powered on continuously to avoid the stabilization delay. How would you guide them?
**Answer:** I'd first acknowledge that the engineer has identified a real problem — the stabilization delay is causing missed readings — but I'd push back on the proposed solution because keeping the sensor powered continuously defeats the purpose of the low-power mode and could significantly reduce battery life. Instead, I'd guide them through the alternatives. The first option is to change the wake-up sequence: wake the MCU, power up the sensor, and then enter a short idle or low-power wait state for the stabilization period before sampling. This keeps the sensor off for the majority of the sleep cycle and only extends the active window by the stabilization time. The second option is to check whether the sensor has a "standby" or "fast wake" mode that reduces the stabilization time — many sensors have a trade-off between sleep current and wake-up time. The third option is to overlap the stabilization with other work: if there are multiple sensors or other tasks, power up the sensor first, then do other processing while it stabilizes. I'd also ask the engineer to quantify the actual power impact: how much current does the sensor draw during stabilization, and how does that compare to the current draw of keeping it powered continuously? If the sensor's sleep current is very low and the stabilization time is short, the difference might be small — but the principle of minimizing active time still matters for battery life. I'd frame this as a design trade-off to be analyzed with data, not a binary choice, and encourage them to measure the actual current draw in both scenarios.

**Possible follow-ups:** How would you calculate the break-even point where keeping the sensor powered is actually more efficient? What other design changes could reduce the impact of the stabilization delay?
