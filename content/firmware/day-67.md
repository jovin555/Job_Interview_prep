# firmware — Day 67

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt can fire faster than the CPU can service it, so that the ISR itself becomes the bottleneck?

**Answer:** The first step is to quantify the actual event rate versus the worst-case service time, because "faster than the CPU can service it" is a claim that needs numbers behind it — if the ISR takes 5 µs and events arrive every 8 µs, you have headroom; if they arrive every 3 µs, you have a hard problem. Once confirmed, the goal is to reduce per-event work in the ISR to the absolute minimum: capture the essential datum (a register read, a timestamp, a status flag) into a lock-free ring buffer or a hardware FIFO, clear the interrupt source, and return. Everything else — parsing, filtering, logging, state transitions — moves to a deferred context (a work queue item, a thread signaled by a semaphore, or a bottom-half handler). If the hardware supports DMA or a peripheral FIFO, use it so the CPU only wakes on a watermark or buffer-half interrupt rather than per byte or per sample. If the event rate genuinely exceeds what the CPU can handle even with a minimal ISR, that's a signal that either the hardware needs a different topology (a dedicated co-processor, a faster part, or a peripheral that does more in hardware) or the firmware requirement itself is unrealistic. I would also consider interrupt coalescing — deliberately batching events and servicing them at a fixed cadence — but only if the application can tolerate the added latency, which for a control loop it often cannot.

**Possible follow-ups:**
- How would you measure the actual ISR execution time and worst-case latency on a target without a cycle-accurate profiler?
- If the deferred context itself can't keep up with the ISR's production rate, what happens next, and how would you detect it?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first instinct should be to treat the debugger as a perturbation rather than a neutral observer. Attaching a debugger changes several things: it may halt the core at breakpoints, it slows execution, it can mask timing-sensitive races, it may disable certain low-power modes, and it can change the state of peripherals or clocks. So the first question is: what does the debugger change that the bug depends on? I would start by reproducing the failure without a debugger and capturing as much evidence as possible through non-intrusive means — a UART log, an on-chip trace buffer, a GPIO toggled at key points, or a RAM-based event log that survives until the next reset. If the failure is timing-related, I would look for races between ISRs and threads, missing memory barriers, or assumptions about peripheral readiness that only hold when execution is slowed. If the failure is power-related, I would check whether the debugger's presence keeps a regulator or clock alive that would otherwise be gated. A useful technique is to introduce deliberate, controlled perturbations — a small delay in a suspect path, or a dummy read — and see whether the failure appears or disappears; that narrows down which timing assumption is load-bearing. I would also check whether the debugger disables the watchdog or changes the reset behavior, since a bug that only manifests when the watchdog is active is a common variant of this.

**Possible follow-ups:**
- How would you capture a useful trace of a failure that only happens once every few hours, without a debugger attached?
- What kinds of compiler optimizations or memory-ordering issues can produce behavior that changes when a debugger is attached?

## Q3: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I would start by acknowledging what they got right: `volatile` does prevent the compiler from caching the variable in a register or eliminating an access it considers redundant, and for a single flag written by an ISR and read by a thread, that's a real and necessary property. The gap is that `volatile` says nothing about atomicity or ordering. If the shared data is wider than the machine's natural word size, or if the ISR writes multiple fields that the thread reads as a group, the thread can observe a torn or inconsistent view. `volatile` also doesn't create a memory barrier, so on a core with a weak memory model or with a compiler that reorders non-volatile accesses around a volatile one, the thread can see stale or reordered data. And it doesn't provide mutual exclusion — if both sides ever write, you have a race regardless of `volatile`. The right guidance is to separate the two concerns: use a proper synchronization primitive for the data (a `k_sem`, a `k_mutex` if the ISR can't be used, an atomic type, or a lock-free single-producer/single-consumer ring buffer with explicit acquire/release semantics), and reserve `volatile` for what it's actually for — memory-mapped registers and variables that can change outside the compiler's view. I would walk them through a concrete failure mode: a 32-bit struct written by the ISR and read by the thread, where the thread occasionally sees a half-updated value. Then I'd pair with them to refactor the module, and add a test or a static-analysis rule that flags `volatile` used as synchronization so the pattern doesn't creep back in.

**Possible follow-ups:**
- When is `volatile` genuinely the right tool, and when is it a code smell?
- How would you design a single-producer/single-consumer ring buffer between an ISR and a thread without a lock, and what memory-ordering guarantees would you need?

## Q4: How would you approach implementing a firmware module that must handle a peripheral whose data-ready signal is edge-triggered, but where the signal can occasionally glitch and produce a spurious edge that does not correspond to valid data?

**Answer:** The first thing to establish is whether the glitch is a hardware problem or a firmware problem. If the signal is genuinely noisy at the pin, no amount of firmware cleverness fully fixes it — the right answer may be a hardware debounce (an RC filter, a Schmitt trigger, or a dedicated debounce IC), and I would raise that with the hardware team rather than trying to paper over it in software. Assuming the hardware is acceptable and the glitch is a rare, bounded event, the firmware strategy is to treat every edge as a hypothesis rather than a fact. On each edge, the ISR records the event and defers the actual read to a context where it can validate: check the peripheral's own status register or data-ready bit, verify the data against a checksum or range check, and confirm that the timing since the last valid read is plausible. If the validation fails, discard the sample and increment a diagnostic counter rather than propagating bad data. For a medical device, the counter matters — it's evidence that the signal path is degrading, and it can feed a self-test or a maintenance indicator. I would also consider whether the edge can be masked or filtered at the peripheral level (some peripherals have a digital filter or a minimum pulse-width setting), which is cheaper than doing it in software. Finally, I would make sure the ISR is robust to a burst of spurious edges — a tight loop that reads and discards is fine, but it must not starve other interrupts or overflow a queue.

**Possible follow-ups:**
- How would you distinguish a genuine data-ready edge from a glitch if the peripheral has no status register to confirm readiness?
- What would you log or count to give the field service team a way to tell whether this is happening in a deployed unit?

## Q5: You're leading a firmware team that is transitioning from a bare-metal approach to using Zephyr RTOS for a new medical device. Two senior engineers disagree: one wants to port the existing bare-metal drivers directly into Zephyr as custom drivers, while the other wants to rewrite them using Zephyr's native driver model. How would you guide the team to a decision?

**Answer:** I would frame this as a decision about where the team wants to spend its maintenance budget over the life of the product, not as a binary "port versus rewrite" argument. The first step is to inventory the existing drivers and classify them: which ones are simple enough that the port is trivial, which ones have subtle timing or hardware-specific behavior that the native model might not express cleanly, and which ones are already close to what Zephyr expects. Then I would look at the cost of each path honestly — a direct port is faster to first light but tends to accumulate a parallel set of abstractions that diverge from the rest of the system, which makes onboarding, debugging, and upstreaming harder later. A native rewrite is more work up front but pays off in consistency, in access to Zephyr's power management, device tree, and driver lifecycle, and in the ability to lean on the community for bug fixes. For a medical device, I would weight the regulatory side heavily: a native driver model with clear device-tree bindings and a documented lifecycle is easier to trace through a design history file than a bespoke port that only the original author understands. My recommendation would usually be a hybrid — rewrite the drivers that are central to the product's safety and long-term maintenance, and port the peripheral or one-off drivers where the native model adds little. I would make the decision explicit, document the rationale, and set a review point where we check whether the hybrid is actually holding or whether we should converge. The goal is to get the team aligned on the criteria, not to win the argument.

**Possible follow-ups:**
- How would you handle a driver that has a hard real-time requirement that the native Zephyr model doesn't obviously support?
- What would you do if, six months in, the hybrid approach turns out to be causing more confusion than either pure path would have?
