# firmware — Day 79

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt can fire faster than the CPU can service it, so that the ISR itself becomes the bottleneck?
**Answer:** The first step is to quantify the actual event rate versus the worst-case ISR service time — if the interrupt period is shorter than the ISR's execution time, no amount of clever coding inside the ISR will keep up, so the fix has to reduce work per interrupt or reduce the number of interrupts. The standard pattern is to make the ISR do the absolute minimum: capture the data or status into a small, pre-allocated slot (or a hardware FIFO if the peripheral has one) and defer everything else — parsing, filtering, logging, protocol handling — to a lower-priority thread or work queue. If the peripheral supports DMA or a hardware FIFO, enabling it lets the hardware absorb bursts and lets the ISR fire per-block instead of per-byte or per-sample, which changes the math entirely. Where the event rate is genuinely higher than the CPU can handle even with a minimal ISR, the honest answer is that the design needs to change: reduce the sample rate, aggregate events in hardware, or move the function to a faster core or a dedicated peripheral. I'd also instrument the system to measure ISR entry-to-exit time and interrupt-to-thread latency, because "the ISR is too slow" is a hypothesis that needs data before committing to a redesign. A useful sanity check is to compute the CPU utilization implied by (event rate × ISR cost) — if that number is already near or above 100%, the architecture is wrong, not the code.
**Possible follow-ups:** How would you decide between a work queue and a dedicated high-priority thread for the deferred processing? What would you do if the deferred processing itself can't keep up with the event rate?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?
**Answer:** This is a classic heisenbug, and the debugger's presence changes timing, power state, and sometimes the memory map, so the first move is to figure out which of those is the culprit. Attaching a debugger typically slows execution, adds a small amount of current draw, may halt the core at breakpoints, and can disable certain low-power modes — any of which can mask a race condition, a marginal timing violation, or a power-related issue. I'd start by reproducing the failure without a debugger but with instrumentation that doesn't perturb timing much: a GPIO toggled at key points and captured on a scope or logic analyzer, a ring buffer in RAM that survives the failure and can be dumped afterward, or a UART log at low baud. If the failure only appears when the debugger is absent, I'd specifically look at things the debugger changes: whether the debugger keeps a clock or peripheral powered that the standalone build gates off, whether breakpoint halts are hiding a watchdog or a race, and whether the debug build's optimization level or memory layout differs from the release build. I'd also check whether the debugger's presence affects the reset sequence or the boot timing, since some peripherals need a settling time that a halted core inadvertently provides. The goal is to find the timing or power dependency the debugger is accidentally satisfying, then reproduce it deterministically with a controlled stimulus rather than chasing the symptom.
**Possible follow-ups:** How would you capture evidence of a failure that only happens when no debugger is attached? What role does optimization level play in bugs that disappear under a debugger?

## Q3: How would you approach sizing thread stacks in a Zephyr RTOS application, and what would you do to verify that your sizing is actually correct rather than just "probably enough"?
**Answer:** Stack sizing starts with an estimate and ends with measurement — the estimate alone is never trustworthy. I'd begin by accounting for the known consumers: the thread's own local variables and call depth, the worst-case call chain through any library or driver it invokes, interrupt stack usage if the architecture shares the stack or if nested interrupts push onto it, and any context-save overhead the RTOS adds on entry. Zephyr provides tooling for this: the thread analyzer can report high-water marks, and `k_thread_stack_space_get` or the stack sentinel feature can catch overflows at runtime. The verification step is what separates a guess from a number: run the system through its worst-case paths — deepest call chains, error-handling branches, the paths taken during a fault or a retry — and read the high-water mark, then add a safety margin for the paths you didn't exercise. I'd also enable stack sentinels or canaries in test builds so an overflow is caught immediately rather than corrupting an adjacent thread's stack silently. For threads that call into third-party or vendor code, I'd treat the estimate as a lower bound and measure, because those call chains are often deeper than they look. The final sizing should be documented with the reasoning, so a future change that adds a call doesn't quietly invalidate it.
**Possible follow-ups:** How would you handle a thread whose worst-case stack usage is data-dependent and hard to bound? What's the risk of sizing stacks generously "just in case"?

## Q4: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?
**Answer:** I'd start by acknowledging the part they got right — `volatile` does prevent the compiler from caching the variable in a register or eliminating an access it thinks is dead, which is why it's necessary for a variable shared with an ISR. Then I'd explain what `volatile` does not do: it doesn't make the access atomic, it doesn't order the access relative to other memory operations, and it doesn't provide any mutual exclusion. On a 32-bit MCU a single aligned word read or write is usually atomic, but a multi-byte structure, a read-modify-write, or a check-then-act sequence is not, and the compiler or CPU can reorder non-volatile accesses around a volatile one. So a flag that looks like "just one byte" can still be the wrong tool if the data it guards is larger than a word, or if the thread reads the flag and then reads associated data that the ISR could update in between. The better patterns depend on the situation: for a simple one-way signal, an atomic flag or a `k_sem`/`k_event` is clearer and gives the scheduler something to block on; for shared data, a proper critical section, a lock-free single-producer/single-consumer ring buffer with correct memory barriers, or an RTOS primitive. I'd walk through a concrete failure mode with them — a torn read of a multi-byte value, or a missed update because the compiler hoisted a load — so the lesson lands as a real bug rather than a style preference. The goal isn't to make them afraid of `volatile`; it's to make them reach for the right primitive for the job.
**Possible follow-ups:** When is a plain `volatile` flag actually sufficient between an ISR and a thread? How would you explain memory barriers to someone who hasn't encountered reordering bugs before?

## Q5: How would you approach a situation where you discover, late in a project, that a firmware design decision you made early on is now causing significant problems, and changing it would require rework across several modules?
**Answer:** The first thing I'd do is resist the urge to either quietly patch around it or immediately announce a rewrite — both are reactions, not decisions. I'd quantify the problem: what specifically is failing or becoming unmaintainable, how much of the codebase actually depends on the decision, and what the cost of change looks like in terms of modules touched, test coverage needed, and schedule impact. That analysis usually reveals one of three situations: the decision is genuinely wrong and the rework is unavoidable, the decision is fine but a specific implementation detail needs to change, or the pain is real but tolerable and the right move is to contain it and revisit later. I'd bring that analysis to the people affected — the team, the project lead, whoever owns the schedule — rather than deciding unilaterally, because a late change has ripple effects beyond the code. If the change is warranted, I'd look for a way to stage it: introduce an abstraction or a compatibility layer so modules can migrate incrementally rather than in one risky cut, keep the old path working until the new one is proven, and make sure the change is covered by tests before and after. If the change isn't warranted yet, I'd document the trade-off and the trigger that would force a revisit, so the decision is deliberate rather than forgotten. The honest framing is that early design decisions are made with incomplete information, and the professional response is to recognize when new information changes the calculus — not to defend the original choice or to panic.
**Possible follow-ups:** How would you decide whether to fix the design now versus ship and address it in the next revision? How would you communicate the rework cost to a stakeholder who is focused on the schedule?
