# firmware — Day 110

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual interrupt rate, the per-ISR cost (entry/exit overhead plus register access plus any deferred work), and the resulting CPU utilization. If servicing every interrupt would consume, say, more than a small fraction of the CPU budget, the design needs to change.

The standard approaches, roughly in order of preference:

1. **DMA with batched completion interrupts.** If the peripheral supports it, let DMA move the data into a buffer and only interrupt on a half-transfer or full-transfer boundary. This converts N per-sample interrupts into a small number of per-buffer interrupts. It's usually the cleanest solution because the CPU is entirely out of the data path.

2. **Interrupt coalescing / rate limiting.** If DMA isn't available, the ISR can be made minimal — read the data register, push to a ring buffer, increment a counter — and the peripheral's interrupt can be temporarily masked once a threshold of pending events is reached, then re-enabled after the deferred context has drained the buffer. This bounds the ISR frequency at the cost of some latency.

3. **FIFO exploitation.** Many peripherals have hardware FIFOs. Setting the FIFO trigger level so the interrupt fires only when the FIFO is half-full or full dramatically reduces the interrupt count, at the cost of added latency per sample.

4. **Polling in a dedicated high-priority thread**, if the rate is high enough that interrupts are pure overhead and the timing is predictable. This is a legitimate choice when the data rate is steady and the thread can be scheduled deterministically.

The key trade-off is latency versus CPU load. Batching always adds latency, so the design must confirm that the added latency is acceptable for the consumer of the data. For a control loop, that might be unacceptable; for a logging path, it's usually fine. I'd also make sure the ISR itself does the absolute minimum — no floating point, no logging, no allocation — and defer everything else to a work queue or thread.

**Possible follow-ups:**
- How would you decide between DMA and interrupt coalescing if the peripheral supports both?
- What would you do if the consumer of the data can't tolerate the latency that batching introduces?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first instinct should be to suspect that attaching the debugger changes timing, power state, or memory layout — any of which can mask the real defect. I'd approach it systematically:

1. **Characterize the difference.** What exactly does the debugger change? It halts the core on breakpoints, it may keep certain clocks running, it may disable low-power modes, it may change the flash/RAM layout or add a debug monitor. I'd try to isolate which of these is masking the bug — for example, running standalone but with low-power modes disabled, or with the same optimization level and linker script as the debug build.

2. **Look for timing-sensitive defects first.** Race conditions, missing synchronization, and insufficient delays are the most common culprits. If the bug disappears when execution is slowed down, that's a strong hint that a race or a setup/hold timing issue is involved. I'd add instrumentation — GPIO toggles, a logic analyzer, a ring buffer of timestamps in RAM — that doesn't halt the core, so I can observe the standalone behavior without perturbing it the way a debugger does.

3. **Check for uninitialized memory or stack issues.** Debug builds often zero memory or have different stack usage; a standalone build might expose an uninitialized variable or a stack overflow that the debug build hides. Tools like stack painting, MPU-based stack guards, or a canary value can help.

4. **Check for optimization-related issues.** If the debug build is -O0 and the release build is -O2, the compiler may reorder or eliminate accesses that the code incorrectly assumed were ordered. Missing `volatile`, missing memory barriers, or reliance on undefined behavior can all manifest this way.

5. **Reproduce with minimal perturbation.** Once I have a hypothesis, I'd try to reproduce it standalone with the smallest possible change — a single GPIO toggle, a counter in RAM — to confirm the hypothesis without the debugger's side effects.

The general principle is: don't trust the debugger build as representative, and use non-intrusive instrumentation to observe the real behavior.

**Possible follow-ups:**
- What kinds of instrumentation would you add that don't perturb timing the way a debugger does?
- How would you distinguish a race condition from an uninitialized-memory bug in this scenario?

## Q3: How would you approach deciding whether a piece of firmware logic belongs in an interrupt service routine versus a deferred context such as a work queue or a thread?

**Answer:** The default should be: keep the ISR as short as physically possible, and defer anything that isn't strictly required for hardware handshaking. The criteria I'd use to decide:

**Belongs in the ISR:**
- Reading a data register before the next sample overwrites it (hardware-imposed deadline).
- Clearing the interrupt source — mandatory, or the ISR will re-enter.
- Acknowledging a hardware event that must be acknowledged within a tight window.
- Pushing a value into a lock-free ring buffer or setting a flag for the deferred context.
- Anything with a hard deadline measured in microseconds that a thread can't reliably meet.

**Belongs in a deferred context (work queue, thread, bottom half):**
- Anything that can block: mutex acquisition, memory allocation, flash writes, bus transactions that may wait.
- Anything with variable or long execution time: parsing, protocol handling, logging, state machine transitions with side effects.
- Anything that calls into other subsystems or takes locks that could be held by a thread.
- Anything that would disable interrupts for a meaningful duration.

The reasoning is about worst-case latency, not average. An ISR that usually takes 5 µs but occasionally takes 500 µs because of a slow path is a latent real-time bug — the worst case is what matters for the rest of the system. I'd also consider priority inversion: if the ISR needs a resource that a lower-priority thread holds, deferring is the only safe option.

In Zephyr specifically, `k_work` / `k_work_delayable` submitted from the ISR is the idiomatic mechanism for the deferred half, and it keeps the ISR to a few instructions. The trade-off is added latency between the event and the deferred processing, so I'd confirm that latency is acceptable for the specific event.

**Possible follow-ups:**
- How would you bound the worst-case latency of the deferred context so you can prove the design meets its deadlines?
- What would you do if the deferred context itself can't keep up with the event rate?

## Q4: How would you approach designing a firmware module that must survive a brownout — where the supply voltage sags briefly but doesn't fully drop — without corrupting persistent state or producing a spurious reset?

**Answer:** A brownout is a nasty case because the MCU may keep running while its behavior becomes unreliable — flash writes can fail partway, ADC readings become garbage, and the brownout detector may or may not trip depending on how the supply sags. The design has to assume that at any moment the supply could dip below the safe operating threshold, and the firmware must not corrupt persistent state when that happens.

Key elements:

1. **Use the hardware brownout detector (BOD) properly.** Configure it to assert reset (or an interrupt) at a threshold safely above the MCU's minimum operating voltage, with hysteresis to avoid chatter. If the BOD can generate an interrupt before reset, use it to enter a safe state quickly — but don't rely on having enough time to do much.

2. **Make persistent-state updates atomic and power-fail-safe.** The classic pattern is a two-phase commit with a validity marker: write the new data to a scratch area, then write a checksum/marker, then invalidate the old copy. On boot, validate the marker and checksum; if the new copy is incomplete, fall back to the old one. Never overwrite the only copy of critical state in place.

3. **Avoid flash writes when the supply is marginal.** If the firmware can measure the supply voltage (via ADC or a comparator), gate flash writes on a minimum threshold with margin. A flash write that starts at 3.0 V and finishes at 2.4 V is exactly the scenario that corrupts data.

4. **Detect and recover from spurious resets.** If the BOD reset the device, the reset-cause register will tell you. On boot, check the cause and log it; if the persistent state is invalid, fall back to a known-good default rather than trusting corrupted data.

5. **Test it deliberately.** A programmable supply that ramps the voltage down slowly, or injects short sags at random times during flash writes, is the only way to gain confidence. Repeat the test many times to catch the rare timing window.

The overarching principle is: treat every persistent write as if power could be lost mid-write, and design the storage format so that any partial write is detectable and recoverable.

**Possible follow-ups:**
- How would you structure the on-flash format so that a partial write is always detectable?
- What would you do if the BOD threshold has to be set below the flash write minimum voltage because of other constraints?

## Q5: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I'd start by acknowledging the part they got right — `volatile` does prevent the compiler from caching the value in a register or eliminating the access, which is necessary for the ISR and thread to see each other's writes. But I'd walk them through why it's not sufficient, using concrete failure modes rather than just asserting it:

1. **`volatile` says nothing about atomicity.** A multi-byte variable (a 32-bit counter on an 8- or 16-bit MCU, or a struct) can be read by the thread while the ISR is halfway through writing it, producing a torn value. `volatile` doesn't prevent that.

2. **`volatile` says nothing about ordering.** The compiler and CPU can reorder non-volatile accesses around volatile ones. If the ISR writes data and then sets a volatile flag, the thread can observe the flag set before the data is visible — a classic publication race. A memory barrier or a proper synchronization primitive is required.

3. **`volatile` doesn't provide mutual exclusion.** If both contexts do read-modify-write on the same variable, updates can be lost.

The fix depends on what the variable is doing. If it's a single-byte flag, `volatile` plus a clear protocol (write data, then barrier, then set flag) may be adequate, but I'd still prefer an atomic type. If it's a counter or a multi-byte value, use C11 atomics (`atomic_t` in Zephyr) or protect it with a lock. If it's a data buffer, use a proper lock-free ring buffer with acquire/release semantics, or a mutex if the thread context can block.

I'd frame the guidance around the question "what is this variable protecting, and what's the worst-case interleaving?" — because that's the reasoning that generalizes. I'd also point them at the language and RTOS primitives that express the intent directly, so the code documents its own synchronization contract. And I'd suggest a code review checklist item: any shared variable between contexts should have a comment stating its synchronization discipline.

**Possible follow-ups:**
- How would you demonstrate the publication race concretely, so the lesson sticks?
- When is a single `volatile` flag genuinely sufficient, and what conditions have to hold?
