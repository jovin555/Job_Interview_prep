## Q1: How would you approach implementing a firmware module that must handle a sensor which occasionally returns invalid data (e.g., out-of-range values or CRC failures), where the device is a medical monitor that must never display a false reading to the clinician?
**Answer:** The core principle here is that invalid data must never propagate to the clinical display — the system must fail safe. I'd structure this in layers. First, at the driver level, I'd validate every read: check CRC or checksum, verify the data is within the sensor's specified operating range, and confirm the read completed without bus errors. Any failure gets flagged rather than silently accepted. Second, at the application level, I'd implement a validation policy that considers both the current sample and recent history. For example, a single out-of-range reading might be treated as suspect and retried, while a physiological parameter that jumps by an implausible amount between consecutive samples could indicate a real event or a sensor fault — so I'd apply rate-of-change limits based on clinical knowledge of what's physiologically possible. Third, I'd define explicit degraded states: if a sensor fails validation repeatedly, the device should transition to a clearly indicated "sensor fault" or "data unavailable" state rather than continuing to display stale or interpolated values. The display should show the last valid reading with a timestamp and an alert, or show "no data" — never a fabricated value. This aligns with IEC 60601 requirements around alarm systems and the principle that the device must not present misleading information. I'd also ensure that any retry logic has a bounded duration so the system doesn't hang in a retry loop while the clinician needs to make decisions. Finally, all invalid-data events should be logged with timestamps for post-event analysis, which supports both debugging and regulatory traceability.

**Possible follow-ups:** How would you distinguish between a transient sensor glitch and a genuine clinical event that produces an extreme reading? How would you handle the case where the sensor recovers after a period of invalid data — what state transitions would you define?

## Q2: You're debugging a firmware issue where a device's flash write operations occasionally corrupt data in an unrelated memory region. The corruption is intermittent and only occurs when the device is under heavy load. How would you approach this?
**Answer:** This pattern — corruption in an unrelated region under heavy load — points me toward a few classic root causes. The first thing I'd suspect is a stack overflow or stack collision, where a deeply nested call stack or a large stack frame grows into an adjacent memory region. Heavy load often means deeper call paths or more interrupt nesting, which can push the stack past its allocated boundary. I'd start by checking stack usage: enable stack canaries or watermark monitoring, and look at the maximum stack depth recorded before the corruption occurs. The second suspect would be a buffer overflow or out-of-bounds write somewhere in the code path that's active under heavy load — for example, a DMA buffer that's not properly sized, or a memcpy where the length is calculated incorrectly under certain conditions. I'd review the code paths that execute during heavy load, particularly any that involve copying data to or from flash buffers. Third, I'd consider whether the flash write itself is the problem — for instance, if the flash controller requires interrupts to be disabled during programming and something in the interrupt path is writing to memory, or if there's a race between the flash write completing and another task accessing the buffer being programmed. I'd also check the linker script and memory map to confirm that the corrupted region isn't overlapping with a stack or heap region. To isolate this, I'd add memory protection if the MCU supports it — using the MPU to mark regions as read-only or no-access and catching the fault at the point of corruption. I'd also instrument the system to log which tasks are running and what interrupts are active when corruption occurs. If I can capture the faulting address with the MPU, that tells me exactly which code is writing where it shouldn't.

**Possible follow-ups:** What specific instrumentation would you add to catch the corruption at the moment it happens? How would you rule out a hardware issue like marginal timing on the flash interface?

## Q3: How would you approach designing a power management subsystem in Zephyr RTOS for a battery-powered medical device that must wake periodically to sample a sensor, process the data, and transmit results wirelessly, while ensuring no sensor readings are missed during the transition between sleep and active states?
**Answer:** The key challenge is that the transition between sleep and active states has latency — the MCU needs time to wake, clocks need to stabilize, and the sensor itself may need time to power up and produce valid data. If the wake-up is triggered by a timer, the actual sampling moment could be missed if the system isn't ready in time. I'd approach this by separating the wake-up trigger from the sampling moment. The timer interrupt should fire early enough to allow the full wake sequence — clock stabilization, regulator settling, sensor power-up and stabilization — before the actual sampling deadline. This means the wake-up lead time must account for the worst-case transition latency, which I'd characterize empirically rather than trusting datasheet values alone. In Zephyr, I'd use the power management subsystem with a custom policy that defines which sleep state to enter based on the time until the next scheduled wake. For the sensor, I'd consider whether it needs to stay powered during sleep or be power-cycled each cycle. If power-cycling, the sensor's stabilization time must be factored into the wake lead time — for example, if the sensor needs 50 ms to stabilize, the MCU must wake at least that early. I'd also think about whether the sensor can be put into a low-power mode rather than fully powered off, which might reduce the stabilization time. For the wireless transmission, I'd structure the sequence as: wake, sample, process, transmit, then return to sleep — with the transmit happening as quickly as possible to minimize active time. I'd use Zephyr's tickless kernel so that the system isn't waking for timer ticks during deep sleep, and I'd verify that all peripherals are properly shut down in the sleep state to avoid excess current draw. To ensure no readings are missed, I'd add a monitoring mechanism — for example, a counter that tracks expected wake-ups versus actual samples taken, and an alert if they diverge. This also helps during development to validate that the timing budget is correct.

**Possible follow-ups:** How would you handle the case where the wireless transmission fails and needs retry — would you stay awake or go back to sleep and retry on the next cycle? How would you verify that the sleep current and wake-up timing meet the battery life requirements?

## Q4: You're reviewing a colleague's firmware code that uses a watchdog timer that kicks in the main loop. The device occasionally resets during a lengthy calibration routine that takes 3 seconds. The colleague proposes increasing the watchdog timeout to 5 seconds. How would you guide them?
**Answer:** Increasing the timeout to 5 seconds would likely fix the symptom, but it's the wrong solution because it weakens the watchdog's ability to detect genuine faults. A watchdog that fires after 5 seconds means the system could be hung for 5 seconds before recovery — which may be unacceptable for a medical device where a fault should be detected and handled quickly. The real issue is that the main loop is blocked for 3 seconds during calibration, which means the watchdog can't be kicked during that time. This is a design problem, not a timeout configuration problem. The better approach is to restructure the calibration routine so it doesn't block the main loop for the entire duration. Calibration routines often have natural break points — between steps, during settling delays, or between measurement points — where control can return to the main loop briefly to kick the watchdog. If the calibration is truly monolithic and can't be broken up, then the watchdog should be kicked from a timer interrupt or from a dedicated low-priority task that runs periodically, rather than from the main loop. This way, the watchdog monitors whether the system is genuinely alive (interrupts are firing, the scheduler is running) rather than whether the main loop happens to be executing. I'd also question whether the calibration routine itself should be blocking at all — in a well-structured system, calibration could be a state machine that runs incrementally, allowing other tasks to execute between steps. This is particularly important in a medical device where the system needs to remain responsive to safety-critical functions even during calibration. If we do need to extend the timeout, that decision should be based on a proper analysis of the maximum legitimate time between kicks, with margin, and documented as part of the system design — not just to make the current code work.

**Possible follow-ups:** How would you decide where to place the watchdog kicks if you restructure the calibration routine? What are the trade-offs between kicking the watchdog from the main loop versus from an interrupt context?

## Q5: You're leading a firmware team that is transitioning from a bare-metal approach to using Zephyr RTOS for a new medical device. Two senior engineers disagree: one wants to port the existing bare-metal drivers directly into Zephyr as custom drivers, while the other wants to rewrite them using Zephyr's native driver model. How would you guide the team to a decision?
**Answer:** This is a common tension when adopting an RTOS, and there's no single right answer — it depends on the specific drivers, the team's timeline, and the long-term maintenance strategy. I'd guide the team by first establishing the decision criteria rather than letting the debate be about preferences. The key factors are: how well the existing drivers map to Zephyr's driver model, how much Zephyr-specific functionality the device needs (like power management integration, DMA support, or interrupt handling that ties into the kernel), and the risk profile of rewriting versus porting. For drivers that are simple, well-tested, and don't need deep integration with Zephyr's subsystems — like a basic GPIO expander or a simple temperature sensor — porting them as custom drivers with minimal wrapping is pragmatic. The risk of rewriting is introducing bugs in code that already works. However, for drivers that need to interact with Zephyr's power management, use DMA in a way that should integrate with the kernel's PM subsystem, or need to support multiple instances, rewriting using the native driver model is likely worth it. The native model gives you things like automatic integration with Zephyr's device tree, power management hooks, and consistent APIs — but it comes with a learning curve and the risk of subtle behavioral differences. I'd suggest a hybrid approach: identify which drivers are critical and complex, and prioritize rewriting those using the native model, while porting the simpler ones initially. I'd also consider the team's familiarity with Zephyr — if they're new to it, starting with ports of simple drivers lets them learn the system before tackling a full rewrite. The decision should also factor in the device's regulatory requirements — any change to a driver, whether a port or a rewrite, needs to be validated, so the testing burden should be part of the decision. I'd ask the team to produce a short analysis for each driver: complexity, integration needs, testing requirements, and risk — and then make the decision based on that data rather than on architectural purity.

**Possible follow-ups:** How would you handle the validation and testing burden for drivers that are ported versus rewritten? What criteria would you use to decide that a specific driver must be rewritten rather than ported?
