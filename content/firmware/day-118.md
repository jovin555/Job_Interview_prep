# firmware — Day 118

## Q1: How would you approach designing a firmware module that must handle a peripheral whose data-ready signal is level-based rather than edge-based, where the signal can stay asserted for a variable amount of time and the CPU may be busy servicing other interrupts when it first asserts?

**Answer:** The core issue with a level-based data-ready line is that it's a state, not an event — so the correct handling depends on whether the peripheral holds data until it's read or overwrites it. I'd start by characterizing that from the datasheet: if the peripheral latches data until read, then a level-triggered interrupt is actually the safer choice, because the line stays asserted until the ISR services it, and there's no risk of missing a pulse that arrives while interrupts are masked. If the peripheral overwrites on each new sample, I'd need to know the worst-case rate versus the worst-case interrupt latency to decide whether a missed sample is even possible.

For the level-triggered case, the standard pitfall is an interrupt storm: if the ISR doesn't fully clear the condition before returning, the interrupt re-fires immediately. So the ISR must read the data and confirm the ready line has deasserted — or explicitly clear the peripheral's status flag — before returning. I'd also consider whether to disable the interrupt source in the ISR and re-enable it after the deferred processing completes, so a slow consumer doesn't cause re-entry. That's a common pattern: the ISR does the minimum (read the data register, push to a queue, disable the line), and a thread re-enables it once it's ready for more.

A second consideration is the interaction with other interrupts. If a higher-priority ISR can run long enough that the data-ready line asserts and the peripheral overwrites before we get to it, the level-based design won't save us — we'd need to either raise the priority of the data-ready ISR or use DMA to capture samples into a buffer independent of CPU scheduling. I'd want to measure the actual worst-case latency of the higher-priority ISRs and compare against the peripheral's overwrite window before deciding.

**Possible follow-ups:**
- If the peripheral overwrites data and you can't guarantee latency, what are your options short of redesigning the hardware?
- How would you verify in testing that the ISR is actually clearing the condition correctly, rather than just appearing to work?

## Q2: How would you approach deciding whether to use a hardware timer peripheral versus the RTOS tick for a periodic firmware task, and what factors would drive that choice?

**Answer:** The RTOS tick is convenient but it's the wrong tool for anything with real timing requirements, for a few reasons. First, tick resolution is coarse — a 1 ms tick means a task that needs to run every 500 µs simply can't be scheduled accurately from it. Second, tick-based timing is subject to jitter from whatever else is running: if a higher-priority task holds the CPU across a tick boundary, the "periodic" task drifts. Third, the tick is a shared resource — changing its rate to get finer resolution affects every timing calculation in the system, including timeouts and sleeps, and increases interrupt load.

A dedicated hardware timer gives you an independent time base with resolution set by the timer's clock, not the RTOS configuration. For a control loop or a sampling task with a hard period, I'd use a hardware timer to trigger the work — either directly driving the peripheral (for example, a timer-triggered ADC conversion) or generating an interrupt that releases a high-priority thread. The key advantage is that the timing is decoupled from software scheduling: the hardware fires on schedule regardless of what the CPU is doing, and the jitter is bounded by interrupt latency rather than by the scheduler.

The trade-off is complexity and resource usage. Hardware timers are a finite resource, and using one per periodic task doesn't scale. So for soft timing — a housekeeping task that runs "about every second" — the RTOS tick or a software timer built on it is perfectly adequate and simpler. I'd reserve hardware timers for the tasks where the period is a real requirement, and be explicit in the design about which is which. I'd also check whether the SoC has a timer that can drive peripherals directly without CPU involvement, because that's often the cleanest answer for sampling.

**Possible follow-ups:**
- How would you handle a system that needs several independent periodic tasks but has only two hardware timers available?
- What would you measure to confirm that a hardware-timer-driven task is actually meeting its period in the presence of other load?

## Q3: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** The debugger-attached-versus-standalone discrepancy is a classic, and the first thing I'd do is resist the temptation to treat it as a single bug — it's usually one of a small set of causes, and I'd work through them systematically rather than guessing.

The most common cause is timing. Attaching a debugger slows execution, adds latency to interrupt entry, and can change the order in which events occur. So a race condition, a missed deadline, or a setup/hold violation on a peripheral interface can all disappear under the debugger. I'd start by asking what's timing-sensitive in the failing path: is there a delay that's "long enough" only because the debugger stretches it? Is there a shared resource accessed from two contexts without proper synchronization? I'd look for busy-wait loops, fixed delays, and any place where the code assumes a peripheral responds within some window.

The second common cause is that the debugger changes the state of the hardware itself — it may halt peripherals, hold certain pins, or leave debug-related clocks running. So I'd check whether the failure correlates with a specific peripheral or power state that the debugger perturbs. A useful technique is to reproduce the failure without a debugger but with instrumentation: toggle a GPIO at key points and capture it on a scope or logic analyzer, or use a RAM-based trace buffer that survives the failure and can be read out afterward. That gives visibility without the debugger's side effects.

Third, I'd consider whether the debugger is masking an initialization or power-up issue — for example, the debugger's connection may hold the device in reset longer or provide a more stable supply. I'd try to reproduce on battery versus bench supply, and at temperature extremes if relevant, to see whether the failure is really about the debugger or about the operating conditions the debugger happens to impose.

The overall approach is: characterize the failure precisely (when, how often, under what conditions), then use instrumentation that doesn't perturb timing to narrow it down, and treat "works with debugger" as a strong hint that the root cause is timing or hardware-state-related rather than a logic error.

**Possible follow-ups:**
- What instrumentation would you add to a device with no spare pins and limited RAM for trace buffers?
- If the failure only reproduces once every several hours, how would you structure your debugging effort so you're not just waiting?

## Q4: A junior engineer has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I'd start by acknowledging the part they got right: `volatile` does tell the compiler that the variable can change outside the current flow of control, so it won't cache it in a register or eliminate the access. That's necessary for an ISR-shared variable. But it's not sufficient, and the gap is important enough to walk through concretely rather than just asserting "volatile isn't synchronization."

The first issue is atomicity. `volatile` says nothing about whether a read or write is atomic. On a 32-bit MCU, a 32-bit aligned access is typically atomic, but a 64-bit value, a struct, or a multi-field update is not — the ISR can fire mid-update and the thread can observe a torn value. Even for a single word, if the "flag" is really a multi-step protocol (set flag, then write data, then clear flag), `volatile` doesn't order those operations relative to each other from the other context's point of view.

The second issue is memory ordering and compiler reordering. `volatile` constrains accesses to that specific variable, but the compiler and CPU are still free to reorder other memory operations around it. So a pattern like "write data buffer, then set volatile flag" can, in principle, have the flag write become visible before the data writes on a weakly-ordered core. That's exactly the kind of bug that works in testing and fails in the field.

The fix depends on the pattern. For a simple flag, I'd use the RTOS's synchronization primitives — a semaphore, an event, or an atomic — which give both atomicity and the necessary memory barriers. For a data-passing pattern, I'd use a proper queue or a lock-free ring buffer with explicit memory barriers. I'd explain that the RTOS primitives aren't just "heavier" — they encode the ordering guarantees the hardware and compiler need, and they make the intent legible to the next person.

I'd frame the guidance around the question "what is this variable actually protecting?" — because once they articulate that, the right primitive usually becomes obvious, and they can see for themselves why `volatile` alone doesn't answer it.

**Possible follow-ups:**
- How would you demonstrate the failure mode to them concretely, rather than just describing it?
- Are there cases where `volatile` alone is genuinely sufficient, and how would you recognize them?

## Q5: How would you approach a situation where you discover, late in a project, that a firmware design decision you made early on is now causing significant problems, and changing it would require rework across several modules?

**Answer:** The first thing I'd do is resist the instinct to either defend the original decision or immediately commit to a rewrite. Late-project discoveries like this are usually a signal that the original decision was reasonable given what was known then, but the requirements or the understanding of the system have shifted. I'd want to separate "this decision was wrong" from "this decision no longer fits," because the second framing makes it much easier to have a constructive conversation with the team and with stakeholders.

Next I'd quantify the problem honestly. What specifically is failing or becoming unmaintainable? How often does it bite? What's the cost of working around it versus fixing it? I'd want concrete evidence — defect rates, time spent on workarounds, the specific scenarios that break — rather than a general sense that it's bad. That evidence is what lets me make a credible case for rework, and it also protects against the opposite failure mode of rewriting something that's actually fine.

Then I'd lay out the options with their costs. There's usually a spectrum: a full refactor, a targeted fix that addresses the worst symptoms, a shim or adapter layer that isolates the problem so new code doesn't inherit it, or accepting the issue and documenting it. Each has a different schedule and risk profile. I'd present these to whoever owns the schedule — not as "I want to rewrite everything," but as "here's the problem, here's the evidence, here's what each option costs and buys us."

If the decision is to do the rework, I'd sequence it to minimize risk: introduce the new approach alongside the old one, migrate module by module, and keep the system shippable throughout rather than doing a big-bang change late in the project. If the decision is to defer, I'd make sure the problem is documented and that new code doesn't make it worse — often an adapter layer is the right compromise.

Throughout, I'd own the original decision rather than deflecting it. The point isn't to relitigate who chose what; it's to get the best outcome for the project with the information now available.

**Possible follow-ups:**
- How would you handle it if the schedule owner rejects the rework and insists on shipping with the problem in place?
- What would you do differently in the original decision, in hindsight, to have made it more reversible?
