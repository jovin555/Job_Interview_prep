# firmware — Day 126

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual ISR entry/exit overhead, the per-interrupt work, and the resulting CPU utilization at the expected event rate. If servicing every event individually would consume, say, more than a small fraction of the CPU budget, the design needs to change — but the fix depends on what the peripheral actually needs.

The general strategies, roughly in order of preference:

1. **Reduce the number of interrupts, not the work.** Most peripherals that generate high event rates have a way to batch: a FIFO or watermark threshold, a "number of samples available" register, or a DMA transfer-complete/ half-complete interrupt. Configure the peripheral to interrupt only when a meaningful batch is ready, then drain the batch in one ISR. This is usually the cleanest fix because it keeps the interrupt model but amortizes the overhead over many events.

2. **Move the data with DMA.** If the peripheral streams data, DMA can move it to a buffer with zero CPU involvement per sample, and the CPU only takes an interrupt per buffer half or per buffer full. This is the standard answer for ADC, SPI, UART, and similar streaming peripherals. The ISR then just signals a consumer task and re-arms the DMA.

3. **Defer the work.** If the ISR must still run per event but the work per event is heavy, split it: the ISR does the minimum (read the data register, push to a ring buffer, clear the flag) and a deferred context — a work queue item, a thread, or a bottom-half — does the processing. This doesn't reduce interrupt count, but it reduces the time spent with interrupts disabled and keeps latency bounded.

4. **Coalesce in software.** If the peripheral can't batch and DMA isn't available, the ISR can accumulate events into a small buffer and only wake the consumer when the buffer crosses a threshold or a timer expires. This trades latency for throughput and must be evaluated against the system's real-time requirements.

The key judgment call is latency: batching and DMA both add latency between the event and the software seeing it. For a control loop with a hard deadline, that latency budget drives how aggressively you can batch. For a logging or telemetry path, you can batch much more aggressively. I'd also make sure the ISR itself is measured — sometimes the "interrupt rate is too high" diagnosis is really "the ISR is doing too much work," and the fix is to shrink the ISR rather than change the interrupt strategy.

**Possible follow-ups:**
- How would you decide between a watermark interrupt and DMA for a given peripheral, and what would make you choose one over the other?
- If you batch events in the ISR, how do you ensure the consumer task doesn't miss the last partial batch when the event rate drops?

## Q2: You're bringing up a new peripheral driver and the datasheet's initialization sequence has several steps with "wait at least X µs" and "wait no more than Y ms" constraints. How would you implement and verify that sequence so it's correct on the first hardware revision and stays correct through later ones?

**Answer:** The core problem is that datasheet timing constraints are a contract, and firmware that satisfies them by accident — because the code happened to be slow enough — is fragile. I'd approach it in layers.

**Implementation:** Encode the sequence as an explicit, linear function with named constants for each timing value, and use a delay primitive whose resolution is appropriate to the constraint. For "wait at least X µs" where X is small, a calibrated busy-wait or a hardware timer-based delay is more appropriate than a scheduler sleep, because `k_sleep`/`k_msleep` has tick granularity and may overshoot by a full tick. For "wait no more than Y ms," the concern is the opposite — you need an upper bound, so you must account for the worst-case execution time of everything between the trigger and the check, including any preemption. If the upper bound is tight, disable preemption around the critical window or use a hardware timer to measure elapsed time and fail loudly if the bound is exceeded.

**Verification:** The sequence should be instrumented so the actual elapsed times are observable — toggle a GPIO at each step and capture on a logic analyzer, or read a free-running timer before and after each wait. Compare measured against the datasheet's min/max. This is the only way to know the sequence is correct on the first hardware revision rather than "it seems to work." I'd also add a compile-time or runtime assertion that the configured delays satisfy the datasheet bounds, so a later change to a clock frequency or a scheduler tick rate that invalidates the timing fails visibly rather than silently.

**Staying correct through revisions:** The timing constants should live in one place with a comment citing the datasheet section and revision. When the datasheet or the hardware changes, there's one place to update. If the sequence is long enough, a small state machine with explicit states and timeouts is more maintainable than a straight-line function, because each step's timing constraint is local to its state and the failure mode (timeout) is explicit.

**Possible follow-ups:**
- How would you handle a "wait at least X µs" constraint where X is shorter than the time it takes to call your delay function?
- What would you do if the datasheet's timing constraints conflict with the system's interrupt latency budget?

## Q3: You're reviewing a colleague's firmware code that uses a large number of global variables to share state between modules. The code works correctly in testing but is difficult to maintain and test. How would you approach refactoring this without introducing regressions?

**Answer:** The instinct to refactor is right, but the risk is real: global-variable-heavy code often works because of implicit ordering and timing assumptions that aren't written down anywhere, and a naive refactor can break those assumptions silently. I'd approach it as a staged, behavior-preserving transformation with a safety net.

**First, build the safety net.** Before touching anything, I'd want a way to detect regressions. If there are no tests, the first investment is characterization tests — tests that capture the current behavior, even if that behavior is ugly, so that any change that alters it is caught. For firmware, this often means host-based unit tests around the modules that can be compiled off-target, plus a hardware-in-the-loop smoke test that exercises the main paths. If the code is too entangled to test at all, that itself is the finding to communicate: the refactor has to start with making the code testable, which may mean extracting one module at a time.

**Second, map the globals.** For each global, identify every reader and writer, and — critically — the ordering assumptions between them. Which module must run before which? Which globals are written in an ISR and read in a task? Which are effectively constants after init? This map is the refactor plan. Globals that are only written at init can become `const` or be passed in at construction. Globals shared between an ISR and a task need proper synchronization, not just encapsulation. Globals that are genuinely shared mutable state across modules are the hard ones and may need an owning module with an accessor API.

**Third, refactor incrementally, one global or one module at a time**, with the safety net run after each step. The typical progression is: encapsulate behind accessors first (mechanical, low risk), then move ownership into a module with a clear interface, then — if warranted — introduce a context/instance struct so the module can be tested in isolation. Each step is small enough to review and to bisect if something breaks.

**Fourth, communicate.** A refactor of this kind touches code other people own or depend on. I'd socialize the plan, keep the changes reviewable in size, and make sure the team understands the interface changes so they don't add new globals while the old ones are being removed.

The judgment call is scope: a full architectural cleanup is rarely justified under schedule pressure, but leaving the code untouched means the next feature is harder and the next bug is harder to find. I'd aim for the smallest refactor that makes the next change safe, and be explicit about what's deliberately left for later.

**Possible follow-ups:**
- How would you decide which globals to tackle first, and which to leave alone?
- What would you do if a characterization test reveals that the current behavior is actually buggy — do you preserve the bug or fix it during the refactor?

## Q4: How would you approach configuring DMA for a peripheral that streams data continuously, where the data rate is high enough that per-transfer interrupts would consume too much CPU, but the buffer is too small to hold an entire acquisition?

**Answer:** This is the classic continuous-streaming DMA problem, and the standard solution is a circular (ring) buffer with half-transfer and transfer-complete interrupts — often called "double buffering" or "ping-pong" — so the CPU is interrupted twice per buffer revolution rather than once per transfer.

**Configuration:** Set up the DMA in circular mode with the destination buffer sized to hold a comfortable chunk of samples — large enough that the per-half-buffer interrupt rate is well within budget, small enough that the latency between a sample arriving and the consumer seeing it is acceptable. Enable both the half-transfer and transfer-complete interrupts. When the half-transfer interrupt fires, the first half of the buffer is full and the DMA is writing into the second half; the consumer can process the first half while the DMA continues. When transfer-complete fires, the roles swap. This gives the consumer a full half-buffer of time to process the previous half before the DMA wraps around and overwrites it.

**The critical constraint** is that the consumer must finish processing a half-buffer before the DMA completes the other half. If the consumer is slower than the DMA, you get overrun — the DMA overwrites data the consumer hasn't read. So the sizing of the half-buffer is a trade-off between interrupt rate (bigger is better) and latency plus processing deadline (smaller is better). I'd size it from the measured worst-case consumer processing time with margin, not from a guess.

**Handling overrun:** The design must detect overrun explicitly — a counter incremented when the consumer falls behind, or a check that the DMA's current position hasn't passed the region being processed. Silent overrun is the failure mode that produces subtly wrong data, which is worse than a visible error. For a medical or safety-relevant stream, overrun should be a logged, reported event, not just a dropped sample.

**Alternatives and trade-offs:** If the consumer can't keep up even with a large half-buffer, the options are to reduce the data rate (decimate in the DMA or a hardware filter), add a second buffer stage (DMA into a small ring, ISR drains into a larger software ring), or move processing closer to the hardware. If the peripheral supports it, a FIFO watermark interrupt combined with DMA can further reduce interrupt load. The choice depends on whether the bottleneck is interrupt overhead, consumer processing time, or memory.

**Possible follow-ups:**
- How would you verify that the half-buffer size is actually sufficient under worst-case load, rather than just under nominal conditions?
- What would you do if the consumer occasionally takes longer than a half-buffer period — how would you degrade gracefully rather than corrupt data?

## Q5: You're leading a firmware team that is transitioning from a bare-metal super-loop to Zephyr RTOS for a new medical device. Two senior engineers disagree: one wants to port the existing bare-metal drivers directly into Zephyr as custom drivers, while the other wants to rewrite them using Zephyr's native driver model. How would you guide the team to a decision?

**Answer:** This is a decision that has real long-term consequences and reasonable arguments on both sides, so I'd resist picking a side in the abstract and instead structure the decision around the project's actual constraints.

**Frame the trade-off honestly.** Porting bare-metal drivers directly is faster in the short term and preserves code the team already trusts, but it tends to produce drivers that fight the RTOS: they may busy-wait, disable interrupts for long stretches, or assume exclusive access to hardware in ways that break under preemption. Rewriting to the native driver model is more work up front and requires the team to learn the model, but it gets device tree integration, power management hooks, and a consistent API — which matters a lot for a medical device that will be maintained and audited over years.

**Ask the questions that actually decide it:**
- *How many drivers are we talking about, and how complex are they?* A handful of simple drivers may not justify a full rewrite; a dozen complex ones almost certainly do.
- *What's the regulatory and maintenance horizon?* A Class II device with a multi-year lifecycle benefits disproportionately from the native model's structure and from being able to lean on upstream Zephyr drivers where they exist.
- *Do upstream Zephyr drivers already exist for these peripherals?* If so, the "rewrite" may be mostly configuration and device tree work, which changes the cost calculus significantly.
- *What's the team's Zephyr experience?* A team new to Zephyr will produce worse native drivers than experienced bare-metal drivers ported carefully — the learning curve is real and shouldn't be hand-waved.
- *What's the schedule?* If there's a hard milestone, a hybrid may be the pragmatic answer.

**Propose a hybrid where it fits.** A common resolution is: use native Zephyr drivers where upstream support exists or where the peripheral is simple and well-understood; port bare-metal drivers as custom drivers behind the Zephyr driver API for peripherals where the existing code is mature and the rewrite risk is high; and set a review gate so ported drivers are checked for RTOS-hostile patterns (busy-waits, long interrupt-disabled sections, missing synchronization). This gets most of the native model's benefits without betting the schedule on a full rewrite.

**Make the decision explicit and documented.** Whatever the team chooses, I'd want the rationale written down — the criteria, the trade-offs accepted, and the conditions under which the decision would be revisited. That way the decision is a team decision, not one engineer's preference, and it's defensible later when someone asks why a driver looks the way it does. I'd also make sure both engineers feel heard: the disagreement is a signal that both approaches have real merits, and the goal is a decision the team can commit to, not a winner and a loser.

**Possible follow-ups:**
- How would you handle it if the engineer who favored the direct-port approach is visibly unhappy with the decision and disengaged?
- What review criteria would you put in place to catch RTOS-hostile patterns in ported drivers before they reach the main branch?
