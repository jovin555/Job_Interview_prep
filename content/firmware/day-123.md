# firmware — Day 123

## Q1: How would you approach verifying that a firmware image is safe to boot after an OTA update, beyond simply checking that the transfer completed without errors?

**Answer:** Transfer completion only proves the bytes arrived, not that they form a valid, runnable image, so I'd layer several independent checks. First, an integrity check over the whole image — a CRC or cryptographic hash computed by the bootloader and compared against a value delivered alongside the image (ideally signed, so the hash itself can't be tampered with). Second, a structural sanity check: a valid vector table, a plausible stack pointer and reset vector, and a magic/version header that matches the expected image format. Third, a compatibility check against the hardware revision and the bootloader's own minimum version, so a mismatched image is rejected before it ever runs. The key design principle is that the bootloader — not the application — owns the decision, and it makes that decision from data it can verify independently. I'd also make the "image is valid" verdict a one-way ratchet: once the bootloader has committed to booting a new bank, it records that commitment in a way that survives a reset mid-boot, so a power loss during first boot doesn't leave the device oscillating between banks. Finally, I'd want the validation path itself to be testable — feeding it deliberately corrupted, truncated, and wrong-version images in a lab harness — because a validation routine that's never seen a bad image is just an assumption.

**Possible follow-ups:** How would you handle the case where the new image passes validation but crashes immediately on first boot — what does the rollback trigger look like? Where would you store the "commit" flag so that it survives a reset at any point during the boot sequence?

## Q2: You're debugging a firmware issue where a device's SPI flash driver works correctly for reads but occasionally returns corrupted data on writes, and the corruption only appears when a high-rate ADC sampling task is also running. How would you approach this?

**Answer:** The correlation with the ADC task is the strongest clue, so I'd start by asking what the two share. Most likely candidates: a shared bus (if the ADC and flash are on the same SPI peripheral), shared DMA channels, shared interrupt priority levels, or shared power rails where the ADC's switching activity couples noise into the flash supply. I'd first confirm whether the corruption is in the data as written or in the data as read back — writing a known pattern and reading it back with the ADC task stopped versus running would separate a write-path problem from a read-path problem. If it's the write path, I'd check whether the flash write is being preempted mid-transaction by the ADC's ISR in a way that violates the flash's timing requirements (many flash parts have tight timing windows during page program), and whether the SPI bus is being arbitrated correctly if shared. I'd also scope the supply rails during a write with the ADC running, since a marginal decoupling issue can corrupt flash writes in a way that reads never expose. The fix depends on the root cause — bus arbitration, DMA channel conflict, interrupt priority, or hardware decoupling — but the diagnostic path is the same: isolate the shared resource, then prove which one is the culprit by removing it from the equation one at a time.

**Possible follow-ups:** If the ADC and flash share a DMA controller, how would you structure the channel allocation and priority to prevent one from starving the other? How would you design the driver so that a mid-transaction preemption by a higher-priority ISR can't corrupt the flash write?

## Q3: How would you approach deciding whether a piece of firmware logic belongs in an interrupt service routine versus a deferred context such as a work queue or a thread?

**Answer:** The decision comes down to three questions: how much time does the work take, how hard is the deadline, and what does it need to touch. An ISR should do the minimum that absolutely must happen before the interrupt condition is lost — latch the data, clear the flag, timestamp the event — and nothing that blocks, allocates, or takes a lock that a thread might hold. Anything that can tolerate a few microseconds of deferral belongs in a work queue or thread, because that's where you get the ability to block, to use RTOS primitives safely, and to be preempted by something more urgent. The hard deadline is the discriminator: if missing the deadline by even a small margin causes data loss or a safety violation, the critical part stays in the ISR; if the deadline is measured in milliseconds, defer it. I'd also weigh the cost of the deferral mechanism itself — a work queue item has its own latency and memory cost, and on a very constrained part that overhead can be the deciding factor. The failure mode I watch for is the "everything in the ISR" pattern, where the ISR grows to include parsing, logging, and state updates because it was convenient, and suddenly the system's worst-case interrupt latency is set by the least important thing in the ISR. The rule I'd apply: the ISR's job is to get the data out of the peripheral and hand it off; the deferred context's job is to decide what it means.

**Possible follow-ups:** How would you measure the actual interrupt latency your design achieves, rather than assuming it's within budget? What would you do if the deferred context itself can't keep up with the ISR's event rate?

## Q4: You're bringing up a new peripheral driver and the datasheet's initialization sequence has several steps with "wait at least X µs" and "wait no more than Y ms" constraints. How would you implement and verify that sequence so it's correct on the first hardware revision and stays correct through later ones?

**Answer:** I'd treat the timing constraints as a specification to be encoded, not as comments to be trusted. Each step becomes an explicit wait with a named constant tied to the datasheet value, and where the constraint is a window (at least X, no more than Y), I'd implement it as a bounded wait that fails loudly if the window is missed rather than silently proceeding. For the "at least" constraints, a busy-wait or a hardware timer delay is usually appropriate because the durations are short; for the "no more than" constraints, I'd want a timeout that surfaces a diagnostic if the peripheral doesn't respond in time, so a marginal part or a wrong clock configuration shows up as a clear error instead of an intermittent failure. Verification is where most of the value is: I'd instrument the sequence to log actual elapsed times per step on the bench, compare them against the datasheet windows with margin, and run it across temperature and voltage corners if the hardware allows. To keep it correct through later revisions, I'd put the timing constants and the sequence itself behind a versioned interface, and add a bring-up self-test that exercises the sequence and checks the observed timings against the expected windows — so a future hardware revision that changes the clock tree or the part number trips the self-test rather than producing a subtle field failure.

**Possible follow-ups:** How would you implement the "at least X µs" wait so that it's accurate without depending on the RTOS tick? What would you do if a later hardware revision tightened one of the windows and the existing sequence no longer met it?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd try to reframe the disagreement, because both positions are usually right about different things and the argument is often really about unstated assumptions. The first step is to get the actual requirements on the table: what's the worst-case latency the protocol must meet, what's the CPU budget, what's the message rate, and what happens if a message is late or dropped. Then I'd ask each engineer to state the conditions under which their approach fails — polling fails when the message rate is high enough that the poll loop starves other work or misses a deadline; interrupts fail when the ISR load or the latency jitter becomes unpredictable. Often the honest answer is a hybrid: interrupt-driven reception into a buffer, with the protocol state machine and message handling deferred to a thread, which gets the responsiveness of interrupts without the ISR doing the parsing. I'd frame the decision as a design review with explicit criteria rather than a vote, and I'd want a small prototype or a timing analysis to settle the empirical questions rather than arguing from principle. The leadership part is making sure the losing engineer understands the decision was made on criteria, not on seniority, and that their concern was genuinely heard — because the worst outcome is a decision that gets relitigated every sprint.

**Possible follow-ups:** How would you structure the prototype or measurement so that it actually settles the question rather than just producing data both sides interpret differently? If the hybrid approach is chosen, how would you divide ownership between the two engineers so the design doesn't become a compromise neither of them owns?
