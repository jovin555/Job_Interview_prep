# firmware — Day 89

## Q1: How would you approach designing a watchdog strategy for a device that has multiple independent subsystems, each of which needs to prove it's alive, but where a single missed deadline from any one subsystem shouldn't necessarily reset the whole device?

**Answer:** The key insight is to separate "liveness proof" from "reset authority." A naive design has every subsystem kick the same hardware watchdog directly, which means any one subsystem's hiccup resets everything — including subsystems that were perfectly healthy. A better structure is a two-layer scheme.

At the bottom layer, each subsystem reports its liveness to a central watchdog supervisor — a small, high-priority task or a dedicated timer-driven check — rather than touching the hardware watchdog itself. Each subsystem has its own deadline and its own notion of what "alive" means: a sensor task might post a heartbeat every acquisition cycle, a comms task might post one per successful transaction or per idle period, and a control loop might post one per iteration. The supervisor tracks the last-seen timestamp per subsystem against per-subsystem deadlines.

At the top layer, the supervisor decides what action to take. The important design decision is that the response should be graduated: a single missed deadline from a non-critical subsystem might trigger a recovery action (restart that task, reinitialize that peripheral, log an event) without resetting the device; a missed deadline from a safety-critical subsystem, or multiple subsystems failing simultaneously, escalates to a full reset. This maps naturally onto a fault-containment philosophy — contain the fault where possible, escalate only when containment fails.

Practical details matter here. The supervisor itself must be simple enough to be trustworthy — if the supervisor hangs, nothing gets kicked and the hardware watchdog fires, which is the correct fail-safe. The hardware watchdog should be windowed if available, so that a supervisor that kicks too *early* (a sign of a runaway loop or corrupted timing) is also caught, not just one that kicks too late. And the whole scheme needs a debug-mode bypass so that a developer stopped at a breakpoint doesn't get reset out from under them — but that bypass must be compiled out or locked out in production, never a runtime flag an attacker or a stray write could flip.

**Possible follow-ups:** How would you decide the deadline for a subsystem whose work is naturally bursty — sometimes idle for a second, sometimes busy for a second? And how would you test that the graduated response actually works, rather than only testing the happy path?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first move is to resist the temptation to "fix" it by changing timing randomly. The debugger changes several things at once: it halts the CPU (so timing stretches), it may disable or mask certain low-power modes, it can change the state of debug-related clock and power domains, and it often perturbs the flash/RAM access pattern. So the question is which of those differences is masking the bug.

I'd start by characterizing the failure precisely without the debugger: what's the symptom, how often, and does it correlate with anything observable — temperature, time since boot, a particular operation, a particular power state? Then I'd try to reproduce it standalone with instrumentation that doesn't halt the CPU: GPIO toggles on a scope or logic analyzer, a ring buffer in RAM that survives until the next reset and gets dumped on reboot, or a serial log at low priority. The goal is to get a trace of what the firmware was doing in the moments before the misbehavior, without the debugger's timing distortion.

A few specific hypotheses I'd test early. First, low-power modes: many debuggers keep the core clocked or prevent deep sleep, so a bug in the sleep/wake path or in a peripheral's behavior across a power transition will simply not appear under debug. Second, race conditions: the debugger's halts can serialize accesses that would otherwise interleave, hiding a missing barrier or a non-atomic read-modify-write. Third, uninitialized memory or stack usage: the debugger may zero or pre-fill memory differently, or the extra stack frames change what garbage gets read. Fourth, watchdog and timing: the debugger may pause the watchdog, so a marginal kick-timing bug only shows standalone.

Once I have a hypothesis, I'd try to make the bug *more* reproducible rather than less — tighten the timing, add deliberate stress, run at temperature extremes, or instrument the suspect path with a counter that I can read back. A bug you can reproduce on demand is a bug you can fix with confidence; a bug you "fixed" by changing something and hoping is a bug that will come back.

**Possible follow-ups:** How would you capture a trace of the last few hundred milliseconds before a crash if the device resets and loses RAM contents? And what would you do if the bug only reproduces in the field, on units you can't attach a debugger to?

## Q3: How would you approach implementing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it. If the peripheral can fire, say, tens of thousands of interrupts per second, each ISR entry/exit plus the minimal work might be a few microseconds, and the arithmetic quickly shows whether you're spending a meaningful fraction of the CPU on interrupt overhead alone. That number drives the choice of mitigation.

The most common and usually best answer is DMA: let the peripheral move data to or from a buffer without CPU involvement per element, and interrupt only on a half-transfer or full-transfer boundary, or on an error. That collapses thousands of interrupts into a handful. The trade-off is buffer sizing and latency: you need enough buffer depth to cover the worst-case time between DMA interrupts, and you need to think about what happens if the consumer falls behind — do you drop, overwrite, or back-pressure? For a streaming sensor, a double-buffered or circular DMA scheme with the consumer reading the "completed" half while DMA fills the other half is a well-worn pattern.

If DMA isn't available or isn't appropriate, the next lever is to reduce the interrupt rate at the source: many peripherals have FIFOs or watermark levels that let you interrupt only when N samples are available, or a "coalescing" timer that batches events. Failing that, you can move work out of the ISR into a deferred context — the ISR does the absolute minimum (grab the data, clear the flag, signal a task) and a high-priority thread does the processing — which doesn't reduce interrupt *count* but does reduce per-interrupt cost and keeps the system responsive.

There's also a design question underneath: does every event actually need individual handling, or can the firmware treat a burst as a batch? If the data is being logged or filtered, processing it in blocks is often cheaper than per-sample processing, and the ISR can simply note "data available" while a task drains the buffer. The anti-pattern to avoid is an ISR that does substantial work per interrupt and then wonders why the CPU is saturated — the ISR should be a notification, not a worker.

**Possible follow-ups:** How would you size the DMA buffer if the consumer's worst-case latency is unknown at design time? And how would you detect and recover if the DMA transfer itself stalls mid-stream?

## Q4: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I'd start by acknowledging the part they got right — `volatile` does prevent the compiler from caching the value in a register or eliminating the access, and that's genuinely necessary for a variable shared with an ISR. The teaching moment is that it's necessary but not sufficient, and the gap is exactly where the dangerous bugs live.

The core point: `volatile` says "this memory can change outside the compiler's view, so re-read it every time." It says nothing about atomicity or ordering. If the shared variable is wider than the machine's natural word size, or if the thread does a read-modify-write (increment, set-a-bit, check-then-act), the operation can be interrupted mid-way and the ISR can observe or produce a torn value. And even for a single-byte flag, `volatile` doesn't create a memory barrier — on a multicore part or with a weakly-ordered memory model, the compiler and CPU are both free to reorder other accesses around the volatile one, so the flag can appear set before the data it's supposed to protect is actually visible.

Rather than lecture, I'd walk through a concrete failure: a `volatile uint32_t` counter incremented in a thread and read in an ISR on a 16-bit MCU, or a `volatile` "data ready" flag where the ISR sets the flag before writing the payload and the compiler reorders the payload write after the flag store. Once they see the failure mode, the fix is usually obvious: use the RTOS's synchronization primitives — a `k_sem`, `k_mutex`, or an atomic type — which provide both atomicity and the ordering guarantees. For a simple flag, an atomic set/clear with appropriate memory ordering is often enough and cheaper than a mutex. For a data buffer, a proper producer-consumer structure (a `k_fifo`, a `k_msgq`, or a lock-free ring with atomics) is the right tool.

I'd frame it as a rule of thumb they can carry: `volatile` is for memory-mapped hardware registers and for variables the compiler must not cache; it is *not* a synchronization primitive. If two contexts share data and one of them is an ISR, reach for the RTOS primitive or an atomic, not `volatile`. And I'd point them at the code review checklist so the next instance gets caught earlier.

**Possible follow-ups:** Can you give an example where `volatile` is exactly the right tool and adding a mutex would be wrong? And how would you audit an existing codebase for this pattern without reading every file?

## Q5: How would you approach a situation where you discover, late in a project, that a firmware design decision you made early on is now causing significant problems, and changing it would require rework across several modules?

**Answer:** The first thing I'd do is resist the instinct to either quietly patch around it or immediately announce a rewrite. Both are failure modes. Instead I'd spend a short, bounded amount of time turning "this is a problem" into a decision the team can actually make: what exactly is the decision, what's the cost of leaving it, what's the cost of changing it, and what's the cost of each option under the project's real constraints — schedule, regulatory, and risk.

Concretely, I'd write down the problem in terms the whole team can evaluate: which modules are affected, what the failure modes are if we leave it (does it get worse over time, does it create a safety or compliance risk, or is it just ugly?), and what the change would touch. I'd estimate the rework honestly, including test and verification time, not just code changes — in a regulated context, a design change late in the project can mean re-running verification and updating the DHF, and that cost has to be on the table. Then I'd lay out the realistic options: fix it now, fix it incrementally (contain the problem behind an interface and migrate module by module), mitigate it without changing the design, or accept it with a documented rationale and a plan to address it in the next revision.

The judgment call is usually about *containment* versus *correction*. If the design decision is causing active defects or safety risk, it has to be corrected, and the honest conversation is about what slips to make room. If it's causing maintainability pain but not defects, an incremental path — introduce an abstraction at the boundary, migrate the highest-risk call sites first, leave the rest for later — often gets most of the benefit at a fraction of the cost. What I'd avoid is a big-bang rewrite under schedule pressure, because that's how you turn one late problem into several.

I'd also own the decision rather than framing it as something that "emerged." If I made the early call, I'd say so, explain what I knew at the time and what changed, and focus the discussion on the path forward. Teams handle bad news much better when it comes with a clear analysis and a recommendation than when it comes with blame or spin. And I'd make sure the decision and its rationale get recorded, so that six months later nobody re-litigates it or, worse, re-introduces the same problem.

**Possible follow-ups:** How would you decide whether to contain the problem behind an interface versus fix it at the source? And how would you communicate the schedule impact to a project manager who is under pressure to hit a date?
