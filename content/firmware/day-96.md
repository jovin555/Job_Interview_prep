# firmware — Day 96

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the ISR entry/exit overhead, the per-interrupt work, and the worst-case interrupt rate, then compute the fraction of CPU time the ISR would consume. If that fraction is unacceptable, there are several standard mitigations, and the right one depends on the peripheral's behavior.

The most common approach is to reduce the number of interrupts rather than the work per interrupt. If the peripheral supports FIFO or burst modes, configure it to assert the interrupt only when a threshold is reached or a transfer completes, so the ISR fires once per batch instead of once per byte or sample. If the peripheral supports DMA, move the data movement entirely out of the CPU path: the DMA controller fills a buffer and raises a single interrupt per buffer-half or per buffer-complete, and the ISR does nothing but advance a pointer and signal a consumer. This is usually the cleanest answer for continuous streams.

Where DMA isn't available, a hybrid works well: keep the ISR minimal — read the data register, push into a ring buffer, clear the flag — and defer all processing to a thread or work queue. The ISR cost then becomes bounded and small, and the "unreasonable share" is really the processing cost, which now runs at thread priority where it can be scheduled and preempted. If even the minimal ISR is too frequent, consider coalescing in hardware (timer-gated sampling, FIFO watermark) or reducing the sample rate if the application can tolerate it.

The key design principle is that the ISR should do the minimum the hardware requires and no more; anything that can be deferred should be. I'd also make sure the design has headroom — measure at worst-case rate, not nominal, and leave margin for the interrupt arriving back-to-back with others.

**Possible follow-ups:** How would you decide between a FIFO-watermark approach and DMA if both are available? What would you do if the peripheral's FIFO depth is smaller than the burst size you need to move?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first instinct should be to enumerate *what the debugger changes* rather than to guess at the firmware logic. The debugger affects at least four things: timing (halts, single-steps, and slower execution stretch out every operation), the state of debug-related peripherals and pins, power state (a debugger can prevent some low-power modes or hold a clock on), and memory contents (breakpoints, watchpoints, and the debugger's own use of RAM). Any of these can mask a bug.

My approach is to first characterize the failure precisely: how often does it occur standalone, what is the symptom, and does it correlate with anything — time since boot, temperature, a particular operation, a communication event? Then I'd try to reproduce it standalone with instrumentation that doesn't require a live debugger: GPIO toggles around suspect code paths, a ring buffer or flash log of events, and a UART trace if available. If the bug disappears when I add logging, that itself is a clue — it points to a timing-sensitive race or a marginal condition.

Next I'd look for the usual suspects that a debugger masks: uninitialized variables (the debugger may zero or leave RAM in a different state), race conditions between ISRs and threads (halting changes the interleaving), stack overflow (the debugger's own stack usage or a different stack layout changes the margin), and low-power or clock issues (the debugger may keep a clock running that the standalone device gates off). I'd also check whether the debugger holds a reset line or peripheral in a different state, and whether the standalone build differs at all — optimization level, linker script, or a debug-only define.

A useful technique is to run standalone but capture a crash dump: on a fault, save the fault status registers, stacked PC/LR, and a snapshot of key state to non-volatile memory, then analyze offline. That gives the observability of a debugger without its side effects. If the bug only appears with optimization on, I'd also suspect code that relies on undefined behavior — missing `volatile`, aliasing, or uninitialized reads — which the optimizer is free to transform differently.

**Possible follow-ups:** How would you distinguish a timing-sensitive race from an uninitialized-memory problem using only standalone instrumentation? What would you check first if the misbehavior only appears at a particular temperature?

## Q3: How would you approach sizing thread stacks in a Zephyr RTOS application, and what would you do to verify that your sizing is actually correct rather than just "probably enough"?

**Answer:** Stack sizing should be treated as a measurement problem, not a guess. The starting point is to understand what consumes stack in each thread: local variables (especially large buffers and structs passed by value), the call depth of the deepest call chain, and the context-save frame on each interrupt or context switch that can land on that thread's stack. ISRs on many architectures use the current thread's stack, so the worst-case ISR nesting depth has to be added to the thread's own usage — that's a common source of underestimation.

For a first estimate, I'd sum the known large locals and add a generous allowance for call depth, then measure. Zephyr provides stack usage instrumentation — `CONFIG_THREAD_STACK_INFO` and the `k_thread_stack_space_get()` API, plus the `CONFIG_INIT_STACKS` option that fills stacks with a known pattern so high-water marks are visible. I'd run the system through its worst-case paths — all features active, deepest call chains, highest interrupt load, error paths — and read the high-water mark for each thread. The margin between the high-water mark and the stack size is the real safety number.

The verification step is what separates "probably enough" from "correct": exercise the worst case deliberately, not just the happy path, and confirm the high-water mark with margin left over. I'd also add a canary or stack-sentinel check in development builds, and consider enabling Zephyr's stack overflow detection (`CONFIG_HW_STACK_PROTECTION` or `CONFIG_STACK_SENTINEL`) so an overflow faults deterministically instead of silently corrupting adjacent memory. For a medical device, I'd want the margin documented and re-checked whenever a new feature adds call depth or a new ISR is added, because stack usage creeps.

**Possible follow-ups:** How would you account for ISR stack usage if your architecture shares the thread stack? What would you do if a thread's high-water mark is uncomfortably close to its limit but you can't easily reduce its call depth?

## Q4: How would you approach designing a firmware module that must survive a brownout — where the supply voltage sags briefly but doesn't fully drop — without corrupting persistent state or producing a spurious reset?

**Answer:** Brownout is fundamentally a power-integrity and state-integrity problem, and the design has to address both. On the hardware side, the first line of defense is a brownout detector or supply supervisor that holds the MCU in reset below a defined threshold, so the device never executes with a supply too low for reliable operation. The threshold has to be chosen with margin above the MCU's minimum operating voltage and below the nominal supply, accounting for the supervisor's own tolerance and the sag's depth and duration. Bulk and decoupling capacitance buy ride-through time for short sags, and the firmware should understand how long the supply can sag before the supervisor trips.

On the firmware side, the goal is that a brownout at any instant leaves persistent state either fully committed or fully recoverable. That means any write to non-volatile memory must be atomic from the perspective of a reset: use a commit pattern — write data, then a checksum or sequence number, then a valid flag last — so a partially written record is detectable and discarded on the next boot. Wear-leveling or a log-structured scheme helps here too, since it avoids in-place updates that can leave a record half-written. For configuration, keeping a known-good copy and a working copy, with a validity marker, lets the device fall back cleanly.

I'd also make the boot path defensive: on reset, check why the device reset (power-on, brownout, watchdog, software) and validate persistent state before trusting it. If the state is invalid, fall back to defaults or the last known-good copy and log the event. The spurious-reset concern is handled by the supervisor's hysteresis and by ensuring the reset is released only when the supply is stably above threshold, so the device doesn't oscillate in and out of reset during a slow ramp.

Finally, I'd test it: deliberately sag the supply at many points in the write cycle and confirm the device always comes back to a consistent state. That's the only way to know the design actually holds.

**Possible follow-ups:** How would you choose the brownout threshold relative to the MCU's minimum operating voltage and the regulator's dropout? What would you do if the supervisor trips during a flash erase that can't be interrupted?

## Q5: You discover, late in a project, that a firmware design decision you made early on is now causing significant problems, and changing it would require rework across several modules. How would you approach this situation?

**Answer:** The first thing I'd do is resist the urge to either defend the decision or panic — the goal is to make a clear-eyed assessment and then communicate it honestly. I'd start by characterizing the problem precisely: what specifically is failing or becoming unmaintainable, how often it bites, what the workaround cost is if we don't change it, and what the rework actually involves. That means scoping the change — which modules, how many interfaces, what testing is affected, what the risk of regression is — rather than estimating from memory.

Then I'd lay out the options with their trade-offs: fix it now (cost, schedule impact, risk), work around it (cost, technical debt, how long it can be sustained), or defer with a documented plan (what triggers the fix, what the interim mitigation is). For each, I'd be explicit about the risk to the product — for a medical device, a design flaw that affects safety or regulatory compliance changes the calculus entirely and may not be deferrable. I'd bring this to the relevant stakeholders — project lead, systems, QA, and anyone whose work is affected — with the facts and a recommendation, not just the problem. Owning the decision means owning its consequences and being the one to propose the path forward.

If the decision is to fix it, I'd sequence the rework to reduce risk: introduce the new design behind an interface or adapter so modules can migrate incrementally, keep the old path working until the new one is validated, and lean on tests to catch regressions. If the decision is to defer, I'd make sure the debt is visible and tracked, with a concrete trigger for revisiting it, so it doesn't quietly become permanent.

The behavioral core is transparency and ownership: surface the issue early, present options with data, recommend a path, and follow through. Hiding a known design problem to protect a past decision is the one thing that turns a technical issue into a trust issue.

**Possible follow-ups:** How would you decide whether to fix now versus defer when the schedule is already tight? How would you keep the team's confidence in the design process after admitting an early decision was wrong?
