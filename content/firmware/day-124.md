# firmware — Day 124

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt can fire faster than the CPU can service it, so that the ISR itself becomes the bottleneck?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual interrupt rate, the ISR entry/exit overhead, and the worst-case service time per event, then compare that against the CPU budget. If servicing every event individually exceeds the available cycles, the fix is to stop treating each event as a discrete unit of work and instead move to a batched or DMA-assisted model.

Concretely, I'd look at three levers. First, reduce the number of interrupts: configure the peripheral to assert its interrupt on a FIFO threshold or a watermark rather than per-sample, so one ISR drains many events. Second, use DMA to move data out of the peripheral without CPU involvement at all, and only interrupt on a half-buffer or full-buffer boundary — the ISR then just hands off a completed block to a deferred context. Third, if the peripheral supports it, coalesce events in hardware (e.g., a sample counter or timestamp) so the ISR can reconstruct what happened without seeing every edge.

The ISR itself should do the absolute minimum: capture the status, clear the source, and either push a pointer or a count into a lock-free queue for a worker thread to process. All parsing, filtering, and logging happens in the deferred context. I'd also verify the interrupt priority relative to other critical interrupts so that a high-rate peripheral doesn't starve something with a tighter deadline, and check that the ISR isn't accidentally re-entering or missing edges because it's still running when the next one arrives.

The key discipline is to keep the ISR's worst-case execution time bounded and measurable, and to make the deferred path's queue depth explicit so that overflow is a designed, observable condition rather than silent data loss.

**Possible follow-ups:** How would you detect and handle the case where the deferred queue overflows because the worker thread can't keep up? What trade-offs would you weigh between increasing the FIFO threshold and adding DMA?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the first instinct should be to enumerate *why* attaching a debugger changes behavior, because that list is essentially the suspect list. The debugger halts the core, which changes timing; it may disable or mask certain low-power modes; it can affect the watchdog (many debuggers freeze it); it changes flash wait states or clock configuration in some setups; and it may alter the contents of RAM or the state of peripherals on connect. Any of these can mask a real bug.

My approach is to first characterize the failure precisely: when does it happen, what's the symptom, and is it correlated with a particular operation (sleep entry, flash write, radio transmit, watchdog kick)? Then I'd try to reproduce it standalone with instrumentation that doesn't halt the core — a GPIO toggled at key points, a ring buffer in RAM that I can dump after the fact, or a serial log with timestamps. If the device resets, I'd check reset-cause registers and any fault status registers to see whether it was a watchdog, a hard fault, a brownout, or a software reset.

A common root cause is timing: the debugger slows execution enough that a race condition or a marginal setup/hold timing on an external bus no longer manifests. Another is that the debugger keeps a clock or peripheral alive that would otherwise be gated in low-power mode. I'd specifically test with the debugger attached but *not* halted (running free), and compare against standalone with the same instrumentation, to isolate whether it's the halt itself or the debug connection.

Once I have a hypothesis, I'd try to make the failure deterministic — add a delay, change a clock, or stress the suspect path — so I can confirm the fix rather than just observe that the symptom disappeared.

**Possible follow-ups:** How would you use the reset-cause and fault status registers to distinguish a watchdog reset from a hard fault? What would you do if the bug only reproduces in the field and never on the bench?

## Q3: How would you approach deciding whether a piece of firmware logic belongs in an interrupt service routine versus a deferred context such as a work queue or a thread?

**Answer:** The decision comes down to a few concrete criteria: how long the work takes, whether it can block, whether it needs to touch shared state that other contexts also use, and how tight its deadline really is.

The ISR should do only what *must* happen before the interrupt source is cleared or before the next event can arrive: read the status register, clear the source, capture the data or a pointer to it, and signal the deferred context. Anything that can wait — parsing, filtering, logging, state machine transitions, communication protocol handling — belongs in a deferred context where it can be preempted, can block on a mutex or a queue, and can be debugged without worrying about interrupt latency.

The hard constraints that force work into the ISR are: the peripheral will lose data or re-trigger if the source isn't cleared quickly, or the deadline is shorter than the scheduling latency of the deferred context. If neither applies, defer it. A useful rule of thumb is to keep ISRs in the low microseconds and to make their worst-case execution time a number you can state and defend.

I'd also consider the interaction with the scheduler: a work queue runs in a thread context at a configurable priority, so it can be preempted by higher-priority threads, which is usually what you want. A thread gives more control over priority and stack but costs more RAM. For very short, latency-critical handoffs, a lock-free single-producer/single-consumer queue between the ISR and a thread is often the cleanest pattern.

The failure mode to avoid is an ISR that grows over time as features are added — each addition seems small, but the cumulative latency eventually breaks something else. Making the boundary explicit and documented prevents that drift.

**Possible follow-ups:** How would you measure the actual worst-case ISR execution time on target? What would you do if a deferred context's queue fills because the consumer is starved?

## Q4: A junior engineer has written a driver that works reliably on the bench but uses a fixed `k_sleep` delay to wait for a peripheral to become ready after each command, rather than checking a status register or using an interrupt. How would you guide them?

**Answer:** I'd start by acknowledging that the code works and that fixed delays are a legitimate first step when bringing up a peripheral — they're simple and they get you to a known-good state. The concern isn't that the approach is wrong in principle; it's that it's fragile in ways that won't show up on the bench.

I'd walk through the specific failure modes with them. A fixed delay is a guess about the *worst case* on *this* silicon at *this* temperature and voltage; a faster part, a slower clock, a different batch, or a cold start can all violate it. Conversely, if the delay is much longer than needed, it wastes CPU time and, in a battery-powered device, wastes energy — and if it's inside a high-priority thread, it delays everything else. And a fixed delay gives no signal when the peripheral actually fails to become ready; the code just proceeds and reads garbage.

Then I'd show the better pattern: poll the status register with a bounded timeout, so the code proceeds as soon as the peripheral is ready and fails cleanly if it never is. If the peripheral has an interrupt, use it and block on a semaphore or event with a timeout, which is both more efficient and more robust. The timeout value should be derived from the datasheet's maximum, with margin, and the failure path should be handled — return an error, log it, and let the caller decide whether to retry or degrade.

I'd frame it as "make the wait observable and bounded" rather than "don't use delays," because that keeps the conversation constructive and gives them a principle they can apply elsewhere. I'd also suggest they add a test or a debug hook that exercises the slow path so the timeout behavior is actually verified, not just assumed.

**Possible follow-ups:** How would you choose a timeout value that's safe across the full operating range without being so long it masks a real failure? What would you do if the peripheral's status register itself is unreliable?

## Q5: You're leading a firmware team where two senior engineers disagree on whether to implement a critical communication protocol using a polling approach or an interrupt-driven approach. One argues that polling is simpler and more predictable for real-time constraints, while the other insists that interrupts are necessary for responsiveness. How would you guide the team to a decision?

**Answer:** I'd reframe the disagreement from "which is better" to "which meets the requirements with acceptable risk," because both engineers are describing real trade-offs and the right answer depends on the specifics of this protocol and this system.

First, I'd get the requirements on the table explicitly: what's the maximum acceptable latency for a message, what's the worst-case message rate, what else is running on the CPU, and what are the power constraints? Polling gives deterministic, bounded latency *if* the poll loop runs often enough, but it burns CPU and power continuously and its latency degrades as other work is added. Interrupts give low latency and free the CPU between events, but introduce concurrency, priority interactions, and the risk of an ISR that grows over time.

Then I'd ask each engineer to make their case against those requirements rather than against each other — what's the worst-case latency of your approach under the stated load, and what happens when the system is busy? That usually surfaces the real constraint: if the protocol has a hard deadline that polling can't meet without starving other work, interrupts win; if the message rate is low and the CPU is already heavily loaded with deterministic work, a well-structured poll may be simpler and safer.

I'd also point out that the dichotomy is often false: a hybrid — interrupt-driven reception into a buffer, with a deferred context doing the protocol state machine — gets the responsiveness of interrupts without putting the protocol logic in the ISR. That's frequently the answer both engineers can live with.

Finally, I'd make the decision explicit and documented, with the criteria and the assumptions recorded, so that if the requirements change the team knows what to revisit. The goal isn't to pick a winner; it's to make a defensible decision the whole team can commit to.

**Possible follow-ups:** How would you structure a prototype or benchmark to settle the question with data rather than opinion? What would you do if the decision turns out to be wrong after the code is written?
