# firmware — Day 108

## Q1: How would you approach designing a firmware module that must handle a peripheral whose interrupt rate is high enough that servicing every interrupt individually would consume an unreasonable share of CPU time?

**Answer:** The first step is to quantify the problem rather than assume it: measure the actual ISR entry/exit overhead, the worst-case service time, and the resulting CPU utilization at the expected event rate. If per-event servicing is genuinely eating an unreasonable share of the budget, the standard remedies are, in rough order of preference:

1. **Reduce the number of interrupts, not the work.** Many peripherals can be configured to assert an interrupt only when a FIFO crosses a threshold, or to batch events. Using the peripheral's own buffering to convert "one interrupt per byte/sample" into "one interrupt per burst" is usually the cheapest win and requires no architectural change.
2. **Move bulk data with DMA.** For streaming data, DMA lets the CPU be interrupted once per buffer-half or per transfer-complete rather than per element. The ISR then only handles bookkeeping (buffer swap, counter update), not data movement.
3. **Make the ISR minimal and defer the rest.** The ISR should do the absolute minimum — capture a timestamp, push an index or pointer, clear the flag — and hand off processing to a work queue or thread. This doesn't reduce interrupt *count*, but it reduces the time interrupts are masked and keeps latency bounded.
4. **Coalesce in software if hardware can't.** If the source truly fires faster than can be individually serviced, a "read all pending, process in one pass" loop inside the ISR (drain the status register until empty) converts N interrupts into one that does N units of work — trading latency for throughput.
5. **Reconsider the requirement.** Sometimes the event rate is higher than the application actually needs; decimating or filtering at the source may be legitimate.

The key judgment is distinguishing *interrupt rate* problems from *ISR duration* problems — they have different fixes, and conflating them leads to premature DMA or unnecessary buffering.

**Possible follow-ups:**
- How would you decide between a threshold-triggered FIFO interrupt and DMA for a given peripheral, when both are available?
- What would you measure to confirm the fix actually reduced CPU load rather than just moving it elsewhere?

## Q2: You're debugging a firmware issue where a device's behavior is correct when the debugger is attached, but the device occasionally misbehaves when running standalone. How would you approach this?

**Answer:** This is a classic heisenbug, and the debugger's presence changes timing, power state, and sometimes memory contents — so the first move is to figure out *which* of those is masking the fault.

My approach:

1. **Characterize the difference.** Does the fault disappear with the debugger merely *connected* (even halted at a breakpoint), or only when single-stepping? Connection alone can change clock configuration, disable low-power modes, or hold a peripheral in reset — those are strong clues.
2. **Suspect timing first.** Debugger attachment slows execution and adds latency between events. If the bug is a race, a missed deadline, or an ISR that occasionally overruns, the debugger can hide it. Look for shared state without proper synchronization, tight timing assumptions, and code that depends on relative speeds of two tasks.
3. **Suspect power and clock state.** Many debug probes keep the core clocked and prevent deep sleep. If the fault only appears standalone, low-power transitions, clock switching, or peripheral shutdown sequencing become prime suspects.
4. **Suspect uninitialized memory.** Debuggers sometimes zero RAM or leave different residual values. Run standalone with a memory pattern (fill RAM with a known value at startup) to expose reads of uninitialized data.
5. **Instrument without the debugger.** Add GPIO toggles, a ring buffer of event timestamps in RAM, or a lightweight trace over UART. Reproduce standalone with instrumentation, then read the trace afterward. This preserves the standalone conditions while giving visibility.
6. **Bisect the difference.** If disabling a specific low-power mode or fixing the clock makes the bug vanish standalone, you've localized it.

The discipline is to treat "works with debugger" as *data*, not as an obstacle — it narrows the search space considerably.

**Possible follow-ups:**
- How would you build a lightweight in-RAM trace that survives to be read after a fault, without a debugger?
- If the fault turns out to be a race, what's your process for proving the fix actually closed it rather than just shifting the timing?

## Q3: How would you approach deciding what belongs in a bootloader versus what belongs in the application, for a device that must support field updates?

**Answer:** The guiding principle is that the bootloader should be as small, simple, and rarely-changed as possible, because it's the one piece of code you can't afford to brick. Everything that might need to change in the field — and everything that isn't strictly required to *get the application running or recover it* — belongs in the application.

Concretely, I'd put in the **bootloader**:
- The minimal code to initialize the clock and the storage medium (flash, external memory) needed to read an image.
- Image validation: CRC or cryptographic signature check, version/rollback metadata, and the decision logic for which bank to boot.
- The update-receive path if updates arrive via a link the bootloader must service directly (e.g., a recovery channel), or the handoff to the application's update agent if the application handles reception.
- Recovery logic: the ability to fall back to a known-good image or enter a recovery mode if no valid image exists.
- Watchdog setup and a safe default state.

In the **application**:
- Everything user-facing, all protocol stacks beyond the recovery channel, logging, calibration, and any feature likely to change.
- The update *client* (downloading, staging, verifying) if the bootloader only needs to validate and swap.

The trade-off is real: pushing update reception into the bootloader makes recovery more robust but bloats the immutable code; pushing it into the application keeps the bootloader tiny but means a corrupted application must still be able to receive an update. For a device with no physical recovery mechanism, I'd lean toward a bootloader that can at least enter a minimal recovery mode, even if the full update path lives in the application.

**Possible follow-ups:**
- How would you handle the case where the application is corrupted but the bootloader's recovery channel depends on a driver that lives in the application?
- What metadata would the bootloader need to make a safe boot decision, and where would you store it so a mid-update power loss can't corrupt it?

## Q4: A junior engineer on your team has implemented a firmware module that works correctly in testing, but you notice it uses a `volatile` global variable as the sole synchronization mechanism between an ISR and a thread. They argue that `volatile` guarantees the compiler won't optimize the access away, so it's safe. How would you guide them?

**Answer:** I'd start by acknowledging the part they got right — `volatile` does prevent the compiler from caching the variable in a register or eliminating the access, which is necessary for the ISR and thread to see each other's writes at all. Then I'd explain why it's not *sufficient*:

- **`volatile` says nothing about atomicity.** If the shared data is wider than the architecture's atomic access size, or if the thread reads a multi-field structure while the ISR updates it, a torn read is possible. `volatile` doesn't prevent that.
- **`volatile` says nothing about ordering.** The compiler and CPU may reorder other memory accesses around the volatile one. If the ISR writes data and then sets a flag, the thread could observe the flag before the data — a classic bug that `volatile` alone doesn't fix.
- **It doesn't provide mutual exclusion.** If both sides do read-modify-write on the variable, updates can be lost.

The right tool depends on the intent: for a single flag or index where atomicity is guaranteed by the access width, an atomic type or a memory barrier plus `volatile` may be adequate; for anything more complex, a proper synchronization primitive (a semaphore, a mutex if the ISR can't block, or a lock-free ring buffer with correct memory ordering) is the correct answer. In Zephyr specifically, `k_sem`, `k_fifo`, or `atomic_t` with the appropriate memory semantics are the idiomatic choices.

I'd frame it as "`volatile` is a compiler directive, not a concurrency primitive" and walk through a concrete interleaving that breaks their code, so the lesson lands as reasoning rather than a rule.

**Possible follow-ups:**
- Can you describe a specific interleaving where `volatile` alone produces a wrong result?
- When *is* a single `volatile` flag actually sufficient, and what has to be true about the data and the architecture for that to hold?

## Q5: How would you approach a situation where you discover, late in a project, that a firmware design decision you made early on is now causing significant problems, and changing it would require rework across several modules?

**Answer:** The instinct to hide it or quietly patch around it is the wrong one — the earlier the problem is surfaced, the more options exist. My approach:

1. **Quantify the cost and the risk.** What exactly breaks, how often, and what's the blast radius if it ships as-is? What does the rework actually touch — how many modules, how many interfaces, how much test coverage needs to be redone? A concrete estimate turns a vague worry into a decision the team can make.
2. **Surface it immediately to the people who own the schedule and the risk.** Not as an apology, but as a decision request: "Here's the problem, here are the options, here's my recommendation." Late discovery is a schedule problem, and the people accountable for the schedule need to know before they commit further.
3. **Lay out the options honestly.** (a) Fix it properly now — highest cost, lowest long-term risk. (b) Contain it with a well-documented workaround and schedule the real fix — acceptable if the workaround is safe and the debt is tracked. (c) Ship as-is — only defensible if the impact is genuinely cosmetic, which for a medical device it rarely is.
4. **If fixing now, sequence the rework to keep the system working throughout.** Introduce the new abstraction alongside the old, migrate call sites incrementally, keep tests green at each step, and avoid a big-bang rewrite that stalls everything else.
5. **Do the retrospective honestly.** Why wasn't this caught earlier — missing tests, missing review, a requirement that changed? The fix is the immediate problem; the process gap is the recurring one.

The behavioral core is owning the decision without being defensive, and making the trade-off visible rather than deciding unilaterally to absorb the cost.

**Possible follow-ups:**
- How would you decide between fixing now versus containing with a tracked workaround, when the schedule is already tight?
- What would you change in your process to catch this class of decision earlier next time?
