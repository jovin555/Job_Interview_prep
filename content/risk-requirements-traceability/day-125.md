# risk-requirements-traceability — Day 125

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement is functionally correct but safety-anonymous — it describes *what* the firmware does without recording *why* it must do it, so the link from hazard to requirement is implicit and will not survive a change, a refactor, or a personnel turnover. I would fix this at the requirement level first: rewrite or annotate the firmware requirement so it carries an explicit safety rationale and a reference to the risk control ID it implements, and add a measurable acceptance criterion (maximum rate of change, tolerance, and the fault condition under which the limiter must act) rather than a purely descriptive statement. Then I would establish the trace as a three-way link — hazard → risk control measure → firmware requirement → verification — and make the risk control measure the anchor, so that if the requirement is ever reworded or split, the risk file still points at the intent. I would also check whether the limiter is the *only* control against overspeed or one of several; if it is credited alongside a hardware limit, the traceability should show both and make clear which hazard contribution each is credited with, otherwise the matrix implies a single point of control that doesn't exist. Finally, I would verify that the verification activity actually stresses the failure condition — commanding a step change that would exceed the limit and confirming the clamp engages within the specified tolerance — rather than just confirming nominal ramping behavior.

**Possible follow-ups:** If the firmware requirement is rewritten to reference the hazard, how do you handle the fact that the same firmware module may be reused across products where the hazard analysis differs? And how would you detect that this implicit link had been lost if you inherited the project mid-development?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** A distributed control is the classic case where a single risk control ID hides three or four separate implementation elements, each owned by a different discipline, and the traceability breaks down because no single requirement or test covers the whole. I would decompose the risk control measure into its constituent *control contributions* — sensor accuracy and response, firmware algorithm behavior and limits, actuator/power-switch behavior and failure mode — and trace each contribution to its own requirement and verification, while keeping a parent link back to the single risk control ID so the risk file still reads as one control. The key discipline is to define, at the system level, what "the loop keeps the element within a safe range" means in measurable terms — setpoint tolerance, overshoot limit, response time, and behavior under sensor failure — and then allocate that budget across the elements. That allocation is what makes the trace meaningful: each element's requirement carries a share of the system-level acceptance criterion, and each verification demonstrates its share. I would also explicitly trace the *failure modes* of each element, because a distributed loop's safety argument usually depends on what happens when one element fails (sensor stuck, firmware hung, switch welded), and those failure-mode behaviors need their own requirements and tests even though the risk analysis treats the loop as one control.

**Possible follow-ups:** How would you handle the case where the system-level acceptance criterion can only be demonstrated by an integrated test, but each element is verified separately by its owning team? And where would you record the latency budget allocation so it stays visible when one element's design changes?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review is *capable* of detecting the failure the control is meant to prevent — and a generic checklist usually isn't, because it asks general questions rather than the specific one. My first step would be to make the gap explicit: take the risk control's failure condition and ask, of the existing checklist items, which one would cause a reviewer to conclude "this control does not work." If the answer is "none," the review is not valid evidence for that control, regardless of the trace link. The fix is usually to add a control-specific review criterion — a targeted question or a dedicated review item that forces the reviewer to assess the specific failure condition and record a conclusion — and to re-run or supplement the review against that criterion. I would also consider whether the control is better verified by analysis or test, since some controls (derating, creepage, thermal margin) are genuinely review-or-analysis-verified, but the criterion still has to be specific. The traceability lesson is that "verification activity" is not a homogeneous category: a review, an analysis, an inspection, and a test each provide different kinds of evidence, and the matrix should record the method and the specific acceptance criterion, not just a link to a document.

**Possible follow-ups:** How would you word a review criterion so it is specific enough to be objective evidence without turning the review into a test? And how would you handle the situation where the review has already been signed off and the project is past that gate?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control is not a behavior but a *value plus the process that sets and preserves it*, so the traceability has to cover three things: the parameter's allowed range and rationale, the manufacturing process that programs and verifies it, and the runtime behavior that enforces it. I would create a requirement for the parameter itself — its permitted range, its tolerance, and the consequence of an out-of-range value — traced to the risk control, and then a separate requirement or process control for the programming and verification step at manufacturing, traced to the production test or calibration procedure rather than to a design verification test. The verification chain then has two distinct links: design verification that the firmware/hardware correctly enforces whatever limit is programmed (tested with representative values, including boundary values), and production verification that each unit is programmed within the allowed range and that the value is read back and confirmed. I would also trace the *integrity* aspects — checksum or CRC on the stored value, behavior on corruption or blank memory, and whether the value can be changed post-production through a service interface — because those determine whether the control survives in the field. The traceability matrix should make clear that the control is only effective when both the design link and the production link hold, so an auditor can see the full chain rather than assuming the design test covers the manufacturing step.

**Possible follow-ups:** How would you verify the firmware's behavior when the stored parameter is corrupted or out of range, and where would that verification sit in the trace? And if the parameter can be changed in the field by a service tool, how does that affect the risk analysis and the traceability?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I would treat this as a substantive quality issue rather than a documentation dispute, and I would be careful not to frame it as an accusation of the test engineer or the systems engineer — the matrix being complete and the tests passing are both true, and the disagreement is about what those facts demonstrate. My first move would be to make the concern concrete and evidence-based: pick two or three of the flagged tests and walk through them against the risk analysis entry, asking the specific question "if this control were disabled, would this test fail?" That converts a private concern into a shared technical finding, and it either confirms the gap or shows the tests are adequate — both outcomes are useful. If the gap is real, I would treat it as a verification gap to be closed, not a compliance failure to be hidden: re-derive the test from the failure condition, add a negative test (control disabled or fault injected) where feasible, and record the rationale. I would also address the process cause, because copied tests usually indicate that the test author didn't have access to the risk analysis or wasn't asked to read it — so I would build a step into the verification planning process that requires the test author to state, in the test record, which failure condition the test exercises and how. On the disagreement itself, I would avoid letting it become "matrix vs. reality" and reframe it as "what evidence do we actually have," which is a question both engineers can answer together.

**Possible follow-ups:** How would you handle it if the systems engineer's position is backed by the quality manager, who considers the audit pass sufficient? And how would you prevent this from recurring on the next project without adding a heavy review burden?
