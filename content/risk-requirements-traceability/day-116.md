# risk-requirements-traceability — Day 116

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the requirement is functionally correct but safety-anonymous — it describes *what* the firmware does without recording *why*, so the traceability link from hazard to requirement is broken at the point where it matters most. I would start by treating the risk analysis as the authoritative source: the risk control measure entry in the risk management file should carry a unique identifier, and that identifier needs to appear as an explicit attribute on the firmware requirement, not just as an implicit understanding held by the engineer who wrote it. Concretely, I would revise the firmware requirement to state the safety intent alongside the functional behavior — something like "the commanded rate of change shall be clamped to a maximum value, mitigating the hazardous overspeed condition identified in risk control RC-xxx" — and add a bidirectional link in the traceability matrix from the risk control to that requirement.

The second half of the problem is verification. A rate limiter can be tested purely functionally (does the output ramp at or below the limit?) and pass without ever demonstrating that it prevents the hazardous condition. So I would ensure the verification activity is written against the *hazard*, not just the function: the test should drive the system toward the overspeed condition — a step command, a fault-injected command, a command from a source that bypasses the normal ramp — and demonstrate that the limiter holds the rate within the specified bound under those conditions, with a measurable acceptance criterion tied to the hazard's severity threshold. I would also check whether the rate limit value itself is a safety-related parameter that needs its own justification and configuration control, since changing it silently would invalidate the risk analysis.

**Possible follow-ups:** If the rate limiter is one of several controls mitigating the same hazard, how do you decide whether each control needs its own independent verification, or whether verifying the combined effect is sufficient? And how would you handle the case where the firmware team argues the clamping behavior is a general performance feature that happens to also serve as a safety control?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** A distributed control loop is one of the harder traceability cases because the risk analysis credits a single control, but the implementation is spread across three elements owned by different disciplines, and no single element is sufficient on its own. I would resist the temptation to trace the risk control to just one of the three — that would create a matrix that looks complete but doesn't actually demonstrate the control works. Instead, I would decompose the risk control into its constituent *control functions*: sensing (the sensor must report temperature within a defined accuracy and update rate), decision (the PID loop must compute an output that keeps the element within the safe band given the sensor input), and actuation (the power switch must be able to remove power when commanded, within a defined response time). Each of those becomes a derived requirement with its own measurable acceptance criteria, and each traces back to the parent risk control.

The traceability matrix then shows the risk control as a parent node with three child requirements, each linked to its own verification activity, plus a system-level integration test that verifies the loop as a whole — because the individual pieces passing doesn't prove the loop holds the element within the safe range under realistic conditions. I would also capture the *interfaces* between the three elements explicitly, since the most likely failure mode in a distributed loop is a mismatch at a boundary (sensor latency the PID loop doesn't account for, a power switch that can't respond as fast as the loop assumes). Those interface assumptions belong in the requirements, not just in the designers' heads.

**Possible follow-ups:** How would you handle the case where the PID loop's tuning parameters are safety-relevant but are set at commissioning time rather than fixed in firmware? And if the sensor fails silently — reads a plausible but wrong value — does the risk analysis credit the loop as still effective, and how does that change the traceability?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — a general "power supply design review" checklist, for example — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** This is a case where the traceability link exists on paper but the verification activity isn't actually capable of detecting the failure the control is meant to prevent — the review could pass without anyone ever asking the question the risk analysis cares about. I would treat it as a gap in the verification activity, not in the traceability link itself. The fix is to make the review criteria explicit about the risk control: the review checklist should contain a line item that names the specific failure condition and asks the reviewers to assess whether the design mitigates it, with a recorded conclusion. That converts a generic review into a targeted one and produces objective evidence that the control was actually assessed.

I would also think about whether a design review is the *right* verification method for this control at all. Reviews are appropriate for things that can't be tested directly — layout rules, derating margins, component selection — but if the control has a testable failure condition, a review may be a weak substitute. I would want the risk management file to state the verification method and the rationale for choosing it, so that a reviewer or auditor can see the reasoning rather than just a link. Where the review is genuinely the right method, I would make sure the reviewers include someone with the domain knowledge to assess the specific failure condition, not just a generalist sign-off.

**Possible follow-ups:** How would you retrofit this into a review that has already been conducted and signed off — do you re-run the review, or add a supplementary assessment? And how do you prevent the checklist from becoming a rubber-stamp over time, where reviewers tick the box without genuinely assessing the condition?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a piece of firmware logic — it's a *value*, and the traceability has to cover not just the requirement but the process that establishes and preserves that value. I would structure it in three layers. First, the risk control traces to a requirement that defines the parameter's permissible range and the rationale for that range — the requirement is about the *bound*, not a single number, because the value can legitimately differ between units. Second, the parameter's derivation and programming at manufacturing time is itself a controlled process: there needs to be a specification for how the value is computed or selected, how it's written to non-volatile memory, and how it's read back and confirmed. That manufacturing step is a verification activity in its own right, and it should be traced from the risk control just like a bench test would be.

Third, because the value can differ between units, I would want per-unit evidence — a record that the parameter was programmed and verified for each device, tied to the device serial number — rather than a single type-test result that only proves the mechanism works. I would also think about what happens if the parameter is corrupted or reset: is there a safe default, and is that default itself a risk control that needs its own traceability? The traceability matrix should show the risk control linking to the requirement, the manufacturing process specification, the per-unit verification record, and any firmware behavior that handles an out-of-range or missing value.

**Possible follow-ups:** How would you handle a field service action that changes the parameter value — does that re-open the risk analysis, and how do you trace the change? And if the parameter range is wide enough that some units are effectively less protected than others, how do you justify that in the residual risk evaluation?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The systems engineer is technically correct that the matrix is compliant and the tests pass, but that's exactly the problem — the matrix is measuring the existence of links, not the validity of the evidence behind them, and a matrix that passes audit while the underlying tests don't exercise the failure conditions is worse than an incomplete one because it creates false confidence. I would treat the test engineer's disclosure as a serious signal and not dismiss it. My first step would be to verify the concern rather than act on hearsay: pick a sample of the flagged tests, read them against the risk analysis entries they're supposed to verify, and determine concretely whether they exercise the failure condition or not. That gives me facts rather than a disagreement between two engineers.

If the concern is confirmed, I would frame the conversation around the purpose of the traceability rather than around blame. The matrix exists to demonstrate that each risk control actually works, and a copied test that passes without stressing the failure condition doesn't demonstrate that — it demonstrates that a similar system passed a similar test. I would propose a targeted re-verification of the affected controls, prioritized by the severity of the hazard they mitigate, and I would involve the systems engineer in defining what "actually exercises the failure condition" means for each one so the fix is jointly owned rather than imposed. I would also want to understand *why* the tests were copied — schedule pressure, unclear requirements, lack of test equipment — because if the root cause isn't addressed, the same thing will happen on the next project. Finally, I would record the finding and the corrective action, because if this surfaces in an audit later, a documented, reasoned response is far better than an undocumented gap.

**Possible follow-ups:** How would you handle it if the systems engineer continues to insist there's no problem and escalates to the program manager? And what process change would you put in place to catch this kind of "link exists but evidence is hollow" gap before an audit does?
