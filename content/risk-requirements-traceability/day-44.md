# risk-requirements-traceability — Day 44

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a combination of hardware and firmware, where the hardware team documents the control in their design specification and the firmware team documents their portion in a software requirements document — but neither document references the other, and the risk management file treats the control as a single integrated measure?

**Answer:** The core problem here is that the risk management file treats the control as one logical measure, but the implementation artifacts are split across two engineering domains with no cross-references. I'd start by creating a single "risk control implementation record" — a small document or a section in the risk management file that explicitly decomposes the integrated control into its hardware and firmware contributions, and states how they interact. For example, if the control is "detect over-temperature and shut down the motor," the record would specify: the hardware sensor and comparator detect the condition and assert an interrupt; the firmware receives that interrupt and disables the motor driver within a specified time; and the control only works if both halves function correctly.

Once that decomposition exists, I'd establish bidirectional links: the hardware design specification should reference the risk control ID and state which portion it implements; the software requirements document should do the same for its portion. Each document should also reference the other — for instance, the firmware requirement might state "upon receiving the over-temperature interrupt from the hardware comparator (see HW spec section X), disable the motor output within Y ms." This cross-reference is essential because neither document alone tells a reviewer whether the integrated control is complete.

For verification, I'd argue that while unit-level tests are valuable for each half, the integrated control ultimately needs a system-level verification that exercises the full chain — sensor stimulus through to motor shutdown — because the interface between hardware and firmware (interrupt latency, signal integrity, firmware polling vs. interrupt-driven handling) is where integration failures typically hide. The traceability matrix should show the risk control ID linking to both the hardware and firmware requirements, and then to both the unit-level and system-level verification activities.

**Possible follow-ups:** How would you handle the case where the hardware and firmware teams use different requirement numbering schemes? What level of detail should the decomposition record contain — enough for a reviewer to assess completeness without constraining design freedom?

## Q2: How would you approach determining whether a risk control measure that is implemented as a firmware-based plausibility check on a sensor reading — for example, rejecting readings that change by more than a specified rate between consecutive samples — needs to be verified on the actual production hardware, or whether testing on a development board with the same microcontroller is sufficient?

**Answer:** The key question is whether the risk control's effectiveness depends on characteristics that differ between the development board and production hardware. For a plausibility check on sensor readings, I'd consider several factors. First, does the check depend on timing that could be affected by the hardware? If the plausibility window is specified in terms of sample intervals or real-time deadlines, then interrupt latency, clock accuracy, and bus timing on the actual hardware matter. A development board with the same microcontroller might have different oscillator configurations, different interrupt priorities, or different bus loading than the production board.

Second, does the check depend on the actual sensor interface? If the plausibility check operates on digital values that have already been converted by the sensor's ADC, then testing on a development board with a simulated sensor input might be sufficient — the firmware logic itself is hardware-independent. But if the check involves raw analog signal characteristics, or if the failure mode being mitigated involves a sensor that fails in a particular way (e.g., stuck high, drifting slowly), then you need to verify that the firmware correctly handles the actual signal path from the production sensor.

Third, what does the risk analysis say about the failure mode? If the hazard is "sensor reading is erroneously high, causing the device to deliver excessive therapy," and the control is "reject readings that change faster than physically possible," then the critical question is whether the firmware can detect the fault quickly enough given the actual sampling rate and processing time on production hardware. That timing argument often requires testing on the target hardware.

My general approach would be: start with a risk-based assessment of which hardware-dependent parameters could affect the control's effectiveness. If the control's logic is purely computational and the timing margins are generous relative to worst-case hardware behavior, development-board testing with a documented analysis of hardware equivalence might suffice. If the control's effectiveness depends on timing margins, interrupt behavior, or analog signal characteristics that could vary between boards, then production-hardware testing is warranted. In either case, I'd document the rationale — the decision itself needs to be traceable, showing why the chosen verification environment is adequate for the specific risk control.

**Possible follow-ups:** What if the plausibility check involves a timing threshold that is close to the worst-case interrupt latency — how would you determine whether the margin is adequate? How would you document the equivalence argument between development board and production hardware?

## Q3: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system has a distributed architecture — multiple microcontrollers, each running separate firmware, communicating over a shared bus — and a single hazard is mitigated by coordinated actions across multiple nodes?

**Answer:** Distributed architectures are where traceability schemes most often break down, because the hazard is mitigated by the *interaction* between nodes, not by any single node's behavior. I'd approach this in three layers.

First, at the system level, I'd define the integrated risk control as a distinct entity in the risk management file — something like "coordinated motor shutdown across Node A and Node B upon fault detection." This system-level control would specify the end-to-end behavior: which node detects the fault, what message is sent, what each receiving node must do, and the overall time budget from fault detection to safe state.

Second, I'd decompose this integrated control into per-node responsibilities, each captured in that node's requirements document. For example, Node A might have the requirement "detect over-current condition and broadcast a fault message on the bus within X ms," while Node B has "upon receiving a fault message, disable the motor driver within Y ms." Each per-node requirement should reference the system-level risk control ID, so a reviewer can trace from the hazard down through the system control to each node's contribution.

Third — and this is often the missing piece — I'd add explicit requirements for the *interaction* itself: the communication protocol, message timing, and failure behavior if the bus is unavailable. The hazard might not be mitigated if Node B never receives the fault message because the bus is congested or a node has failed. So the traceability scheme needs to capture not just "Node A sends" and "Node B receives," but also the bus-level requirements that make the coordinated action reliable — for example, message priority, retry behavior, and a watchdog or heartbeat mechanism that detects node failure.

For verification, I'd insist on system-level testing that exercises the full chain across the bus, not just per-node unit tests. A unit test on Node B that injects a fault message and checks the motor disables is valuable, but it doesn't verify that Node A actually detects the fault and sends the message under real conditions, or that the bus delivers it within the timing budget. The traceability matrix should show the system-level risk control linking to the per-node requirements, the bus/communication requirements, and then to both unit-level and system-level verification activities.

**Possible follow-ups:** How would you handle the case where different nodes are developed by different teams with different requirement numbering schemes? What if the bus communication itself introduces a new hazard — for example, a corrupted fault message — how would you trace that?

## Q4: How would you approach handling a situation where a risk control measure is traced to a verification test, but the test was written to verify a *different* requirement and only incidentally exercises the risk control under nominal conditions — so it passes, but it never actually stresses the failure condition the control is meant to mitigate?

**Answer:** This is a common and dangerous gap — the traceability matrix looks complete because there's a link between the risk control and a test, but the test doesn't actually demonstrate that the control works when it needs to. I'd start by examining the test procedure against the risk control's failure condition. The question to ask is: does the test create the conditions that the risk control is designed to detect and respond to? If the test exercises the system under nominal conditions and the risk control happens to be active (for example, the over-temperature shutdown is "tested" by running the device at normal temperature and observing that it doesn't shut down), then the test provides no evidence that the control would work when the temperature actually exceeds the threshold.

My approach would be to first document the discrepancy clearly — noting that the traced test does not exercise the risk control's failure condition, and therefore does not provide objective evidence of the control's effectiveness. Then I'd work with the verification engineer to design a test that actually stresses the failure condition: injecting a fault signal, simulating a sensor failure, or otherwise creating the conditions the control is meant to detect. The new test should verify both that the control activates when it should (fault present → safe state achieved) and, where appropriate, that it doesn't activate falsely under nominal conditions.

I'd also use this as an opportunity to review other risk-control-to-test links in the matrix with the same scrutiny. If one link is superficial, others might be too. The root cause is often that the traceability matrix was populated based on requirement numbers rather than on an analysis of whether the test method actually exercises the risk control's failure condition. I'd recommend adding a step to the verification planning process where each risk control is reviewed against its assigned test to confirm the test method is capable of detecting failure of the control — essentially a test-sensitivity check before the test is executed.

**Possible follow-ups:** How would you handle the situation where the test engineer argues that the nominal-condition test is still valuable as a "doesn't false-trip" check, even if it doesn't stress the failure condition? What if designing a test that actually stresses the failure condition is difficult or risky — for example, creating a real over-temperature condition could damage the device?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has created a traceability matrix that links every risk control measure to a verification activity, but during a review, you discover that several of the verification activities are actually "verification by similarity" — meaning the team is relying on test results from a previous product that used a similar component or design. The quality manager argues that similarity is not acceptable evidence for risk controls, because the previous product wasn't tested under the same conditions. The systems engineer argues that the components are identical, the design is nearly the same, and re-running the tests would waste time and money. How would you resolve this disagreement?

**Answer:** I'd start by acknowledging that both sides have legitimate points. The systems engineer is right that re-running identical tests on an identical component in a nearly identical design can be low-value — and regulatory frameworks do allow for "verification by similarity" when properly justified. The quality manager is right that similarity arguments are often used loosely, and that risk controls need objective evidence that they actually work in *this* product, under *this* product's conditions.

The resolution isn't to pick a side but to establish criteria for when similarity is acceptable. I'd propose a structured assessment: first, document precisely what is identical — the component part number, the application circuit, the operating conditions, the stress levels the risk control is designed to handle. Second, identify what has changed between the previous product and this one — different PCB layout, different adjacent components, different firmware, different environmental requirements, different power supply characteristics. Third, assess whether any of the changes could affect the risk control's effectiveness. For example, if the over-temperature shutdown circuit is identical, but the new product has a different thermal environment because of a different enclosure or a higher-power component nearby, then similarity might not hold for the thermal-related risk control — even though the circuit is identical.

If the assessment shows that the changes are genuinely irrelevant to the risk control's function, then I'd document a formal similarity rationale — stating what was tested before, what's the same, what's different, and why the differences don't affect the risk control. That rationale becomes part of the verification evidence. If the assessment shows that any change could plausibly affect the control, then the test needs to be re-run on the new product.

I'd also suggest a middle path: run a reduced set of confirmation tests on the new product — perhaps a subset of the original test cases that are most sensitive to the changes — rather than the full suite. This gives objective evidence that the risk control works in the new context while acknowledging that the full characterization from the previous product is still relevant. The key is that the decision is based on a documented technical assessment, not on schedule pressure or blanket assertions about what "should" be acceptable.

**Possible follow-ups:** What specific criteria would you use to determine whether a design change is "relevant" to a risk control's effectiveness? How would you handle the situation where the previous product's test data is incomplete or was collected under poorly documented conditions?
