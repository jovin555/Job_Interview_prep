# risk-requirements-traceability — Day 53

## Q1: How would you approach tracing a risk control measure that is implemented as a "safe state" defined by a combination of hardware and firmware — for example, a system that must enter a low-power, outputs-disabled state within a bounded time after a fault is detected — when the safe state itself is not a single component but an emergent system behavior?
**Answer:** The key insight is that a "safe state" is a system-level property, so it should be captured as a system-level requirement first, with the hazard it mitigates and the bounded transition time stated as measurable acceptance criteria. From there, decompose it into the contributing elements: the fault-detection path (which may be hardware, firmware, or both), the decision logic, and the actuation path that actually removes or disables the hazardous output. Each contributing element gets its own derived requirement, and each derived requirement traces back up to the system-level safe-state requirement, which in turn traces to the hazard and the risk control measure in the risk management file. The verification then has two layers: element-level verification that each contributor meets its allocated portion of the budget (detection latency, decision latency, actuation latency), and an integrated system-level test that demonstrates the end-to-end transition into the safe state within the bounded time under the fault conditions identified in the risk analysis. The integrated test is essential because the safe state is emergent — passing each element in isolation does not prove the composition works, especially where timing budgets interact or where a fault could be masked by another subsystem. I would also make sure the traceability matrix shows the safe-state requirement as the parent of the decomposed requirements, so a reviewer can see the complete path from hazard to the integrated verification without having to reconstruct it.
**Possible follow-ups:** How would you allocate a total transition-time budget across detection, decision, and actuation when the risk analysis only specifies the end-to-end bound? If the integrated test passes but one element-level test is marginal, how would you decide whether the safe state is adequately verified?

## Q2: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity's test procedure was written against an earlier revision of the requirement, so the test still passes but no longer exercises the current acceptance criteria?
**Answer:** This is a configuration-control problem as much as a traceability problem, and the first step is to confirm the mismatch objectively: compare the requirement revision referenced in the traceability matrix against the revision the test procedure was actually written to, and check whether the acceptance criteria changed in a way that affects what the test exercises. If the criteria changed materially, the test is no longer valid evidence for the current requirement, regardless of whether it passes — a passing test against a superseded criterion is a false sense of coverage. The corrective action is to revise the test procedure to the current acceptance criteria, re-run it, and update the traceability link so it points to the correct requirement revision and the correct test revision. I would also look at why the drift happened: if requirements and test procedures are maintained in separate documents without a revision-linking mechanism, this will recur. The systemic fix is to make the traceability matrix revision-aware — each link records the specific revisions it connects — and to include a traceability audit step in the change-control process so that when a requirement changes, the downstream test procedures are flagged for review. In a regulated context, this also matters for the design history file, because the evidence of verification must correspond to the requirement as it stood at the time of verification, and any later change needs its own verification.
**Possible follow-ups:** If the requirement change was editorial and doesn't affect the acceptance criteria, would you still re-run the test, and how would you document that decision? How would you audit a large traceability matrix to find other links that may have drifted the same way?

## Q3: How would you approach establishing traceability for a risk control measure that is implemented as a redundant channel — for example, a primary sensor path and an independent secondary path whose agreement is checked — where the control's effectiveness depends on the independence of the two channels rather than on either channel alone?
**Answer:** The control here is not either channel; it is the combination plus the independence property, so the traceability has to capture both the functional behavior and the independence claim. Functionally, I would create a system-level requirement for the cross-check behavior — what happens when the channels disagree, within what time, and what the system does as a result — and trace that to the hazard and risk control measure. Then each channel gets its own derived requirements, and the cross-check logic gets its own requirement, all tracing up to the system-level control. The independence property is the harder part: it is a design constraint rather than a functional behavior, so it needs its own requirement and its own verification approach. Independence is typically argued through analysis — separate power domains, separate signal paths, no shared failure modes, no common-cause susceptibility — and that analysis is the verification evidence, not a functional test. I would trace the independence requirement to that analysis and make sure the analysis explicitly addresses common-cause failures, because two channels that share a regulator or a clock are not truly independent. The integrated verification then has to demonstrate the cross-check actually detects a disagreement and drives the safe response, including the case where one channel fails in a way that produces a plausible but wrong reading. The traceability matrix should make it visible that the control depends on both the functional cross-check and the independence argument, so a reviewer can see that verifying the cross-check alone is not sufficient.
**Possible follow-ups:** How would you verify independence when the two channels share a common enclosure or connector, and what evidence would you accept? If a common-cause failure analysis identifies a shared component, how would you decide whether to redesign or to add a compensating control?

## Q4: How would you approach deciding whether a risk control measure should be traced to a design requirement, a design element, or both — and what practical difference does that distinction make in a traceability matrix?
**Answer:** The distinction matters because it determines what kind of evidence you can produce and what a gap in the matrix actually means. A design requirement is a statement of what the system or subsystem must do or must be — it is verifiable in principle and it is what the verification activity is written against. A design element is the physical or logical thing that implements it — a circuit block, a firmware module, a mechanical feature. Tracing a risk control measure to a requirement answers "what must be true for this control to work," and tracing it to a design element answers "where is this control actually implemented." In practice you usually need both, because they serve different audit questions: the requirement link lets you confirm the control is specified and verified, and the element link lets you confirm the control is actually realized in the design and can be located when the design changes. The practical difference shows up in gap analysis. If a control traces to a requirement but not to a design element, you may have a specified control that nobody has confirmed is implemented. If it traces to a design element but not to a requirement, you may have an implementation that was never formally specified or verified — which is a common finding when a control was added informally during debugging. I would set the convention explicitly in the traceability scheme: every risk control measure traces to at least one requirement, and every requirement that implements a control traces to at least one design element, so the matrix supports both "is it specified and verified" and "is it built" questions.
**Possible follow-ups:** For a control implemented purely through component selection and derating, what would the design element be, and how would you represent it? How would you handle a control that is implemented across several design elements with no single owning requirement?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has built a traceability matrix that links every risk control measure to a verification activity, and the matrix is complete and passes audit. However, a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and that nobody has confirmed the tests actually exercise the failure conditions in this project's risk analysis. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?
**Answer:** The matrix being complete is not the same as the verification being valid, and the private concern is exactly the kind of thing that should be surfaced rather than suppressed. My first move would be to separate the two issues: the traceability matrix's structural completeness, which may well be fine, and the validity of the verification evidence, which is what the test engineer is actually questioning. I would not treat this as an accusation against the systems engineer — copied-and-adapted tests are a normal starting point, and the problem is only that the adaptation step was skipped. I would propose a focused review: take the flagged tests and, for each, walk through the risk analysis failure condition and confirm whether the test actually stresses it, using the test procedure and the risk analysis side by side. Where a test does not exercise the failure condition, it is not valid evidence for that control, and it needs to be rewritten or supplemented regardless of the fact that it passes. I would frame this as strengthening the evidence base rather than as finding fault, because the goal is that the verification actually demonstrates the controls work, not that the paperwork is complete. I would also look at the root cause: if tests are being adapted from previous projects without a review step that checks them against the current risk analysis, that is a process gap, and the fix is to add that check to the test-development workflow. Finally, I would make sure the test engineer's concern is credited, because the alternative is that the next person with a similar concern stays quiet, and that is a much worse outcome for a safety-critical project.
**Possible follow-ups:** How would you handle it if the systems engineer continues to insist the matrix is sufficient and resists re-opening the tests? If the review finds that most of the flagged tests are actually valid, how would you avoid the review being seen as wasted effort?
