# risk-requirements-traceability — Day 108

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is a broken semantic link: the requirement exists and is testable, but it has lost its safety rationale, so anyone reading the SRS in isolation would see a performance-tuning constraint rather than a hazard mitigation. I'd start by treating the risk analysis as the authoritative source of intent and repairing the link in both directions. First, I'd create an explicit risk control measure entry in the risk management file that names the limiter, states the hazardous situation it addresses (commanded overspeed), and defines the control's effectiveness criteria — what maximum rate of change is acceptable, under what operating conditions, and what the consequence of exceeding it would be. Then I'd rewrite or annotate the firmware requirement so it carries a traceable reference back to that risk control ID, and — critically — so its acceptance criteria are expressed in terms the hazard cares about, not just "the firmware shall clamp the rate of change." That means specifying the numeric limit, the tolerance, the conditions under which the clamp must hold (all modes, including fault and degraded modes), and the behavior at the boundary. From there I'd add the forward links: requirement to design element (the specific function/module that implements the clamp) and requirement to verification activity. The verification test needs to be designed against the hazard, not the function — it should drive the commanded value with a step or ramp that would produce overspeed absent the clamp, confirm the output rate never exceeds the limit, and confirm the clamp still holds when the command source is misbehaving. I'd also check whether the limiter is the sole control or one of several; if it's credited as an independent layer, the traceability should show that independence explicitly. Finally, I'd add a review gate: any requirement tagged as implementing a risk control must carry the risk control ID, and the traceability tooling should flag orphaned risk controls (controls with no requirement) and orphaned safety requirements (requirements claiming a risk link that doesn't exist).

**Possible follow-ups:** If the firmware team argues the numeric limit is a tunable parameter that may change during development, how do you keep the traceability valid as the value changes? How would you handle the case where the same limiter also serves a non-safety purpose, such as mechanical wear reduction, so it has two justifications?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap with a distributed control is that the risk analysis credits a single control, but the implementation is spread across three owners, so a naive traceability matrix either links the control to one requirement (and silently drops the other two contributions) or links it to three unrelated requirements with no statement of how they combine. I'd decompose the control into its constituent functions and make the *composition* itself a traceable artifact. Concretely: define the risk control measure at the system level with a clear effectiveness criterion — for example, the heating element is de-energized before the sensed temperature exceeds a safe threshold, accounting for sensor accuracy, loop latency, and switch response time. Then allocate that criterion into sub-requirements, one per element: the sensor's accuracy and response time, the firmware loop's update rate and the specific safe-state action it commands, and the power switch's response time and failure behavior. Each sub-requirement traces up to the parent risk control and down to its own design element and verification. The key addition is a system-level verification that exercises the *whole chain* — injecting a temperature stimulus and measuring when power is actually removed — because individually passing sub-requirements don't prove the composed loop meets the hazard-driven criterion. I'd also document the interfaces between the elements (the sensor-to-firmware signal, the firmware-to-switch command) in the ICD so the timing budget is explicit and each element's latency allocation is visible. The traceability matrix should show the parent control, the allocation to sub-requirements, and both the per-element verifications and the integrated system verification, so an auditor can see that the control is covered end to end rather than piecemeal.

**Possible follow-ups:** How would you handle the case where the firmware PID loop is also used for normal temperature regulation, so the same code path serves both a performance function and a safety function? If one element in the chain has a failure mode that the others can't detect, how does that affect how you trace and verify the control?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence for certain kinds of controls — layout rules, derating, creepage, component selection — but only if the review actually examines the specific failure condition the control addresses. A generic checklist that happens to touch the same subsystem is not evidence; it's coincidence. My approach would be to make the review *fit for purpose* rather than to discard it. First, I'd extract from the risk analysis the precise failure condition and the control's effectiveness criteria, and write a review checklist item (or a small set of items) that directly asks the reviewers to confirm that condition is addressed — with a place to record the specific evidence they examined, not just a checkbox. Second, I'd add the risk control ID to the review record so the link is explicit and auditable. Third, I'd consider whether the review alone is sufficient evidence or whether it needs to be paired with analysis or test; for a control whose effectiveness depends on a quantitative margin, a review that confirms the calculation exists and was done correctly may be adequate, but a review that merely asserts "looks fine" is not. I'd also check whether the reviewers have the right competence for that specific control — a general power supply reviewer may not be the right person to assess a thermal cutoff's failure behavior. Finally, I'd feed this back into the process: review checklists should be derived from the risk analysis for the project, not reused wholesale from a template, and the traceability matrix should record not just "design review" but which review, which checklist item, and what evidence was captured.

**Possible follow-ups:** How would you distinguish a design review that is acceptable verification evidence from one that is effectively "verification by assertion"? If the review has already been completed and signed off without assessing the failure condition, what's your remediation path — re-review, supplemental analysis, or test?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a line of code but a *value*, and the traceability has to cover the value's derivation, its programming, and its verification — not just the firmware that reads it. I'd structure it in three linked layers. First, the risk control measure in the risk management file defines the safety intent: the output current must never exceed a level that could cause the identified hazard, and the parameter is the mechanism that enforces it. Second, a requirement captures how the limit is determined — the calculation or characterization that maps the hazard threshold to a per-unit value, including tolerances and the margin between the limit and the hazardous level — and a second requirement captures how the value is programmed and stored (the production programming step, the non-volatile memory location, any integrity check such as a checksum or redundant copy). Third, verification splits into two distinct activities: a design verification that confirms the firmware correctly reads and enforces the stored value (testable on representative hardware with known values), and a *production* verification that confirms each unit is programmed with a value within the allowed range and that the stored value is readable and correct. The production test is part of the traceability chain even though it's not a design verification — the risk file should reference it, and the manufacturing procedure should reference the requirement. I'd also address what happens if the parameter is corrupted or out of range at runtime: the firmware should have a defined safe behavior, and that behavior is itself a requirement traced to the same hazard. The traceability matrix should make clear that the control's effectiveness depends on three things — correct value derivation, correct programming, correct enforcement — and that each has its own evidence.

**Possible follow-ups:** If the parameter can be changed in the field via a service port, how does that affect the traceability and the risk analysis? How would you handle a unit where the production test shows the programmed value is out of range — what does the traceability say about disposition?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The systems engineer is describing compliance of the artifact, and the test engineer is describing a defect in the evidence — those are different claims, and the matrix passing audit doesn't resolve the second one. I'd treat the private disclosure as a serious signal and act on it without turning it into a blame exercise, because the test engineer did the right thing by raising it. First, I'd verify the concern rather than accept or dismiss it: pick a sample of the flagged tests, pull the risk analysis entry each is supposed to verify, and compare the test's stimulus and acceptance criteria against the failure condition. If the test never drives the system into the condition the control is meant to mitigate, the link is nominal — it's a paper trace, not evidence. Second, I'd widen the check: if a few tests were copied, the pattern likely extends further, so I'd do a targeted review of all tests linked to risk controls, prioritized by severity of the hazard. Third, I'd remediate: rewrite or supplement the inadequate tests so they actually exercise the failure condition, and where a test genuinely can't be made to do so, escalate to analysis or inspection with proper justification rather than leaving a false test link. Fourth, I'd address the process gap that allowed this — copied tests with relabeled links suggest the traceability was built after the fact to satisfy the matrix rather than driving the verification plan. I'd want the risk control ID to be the *starting point* for test design, and I'd add a review step where someone with risk-analysis knowledge signs off that each linked test is capable of detecting the failure. On the disagreement itself, I'd frame it to the systems engineer not as "the matrix is wrong" but as "the matrix is right and the evidence behind it is thin — an auditor who looks past the links will find the gap, and more importantly a real hazard could ship unverified." That reframes the conversation from compliance to patient safety, which is where it belongs.

**Possible follow-ups:** How would you handle the situation if the schedule doesn't allow re-running the inadequate tests before a milestone? What would you change in the verification planning process so that tests are designed from the risk analysis rather than adapted from prior projects?
