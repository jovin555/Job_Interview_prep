# risk-requirements-traceability — Day 100

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement exists and is testable, but the *safety intent* has been stripped out — a reader of the SRS alone would see a performance constraint, not a risk control. I'd fix this at the requirement level rather than trying to patch it in the traceability matrix. First, I'd add an explicit safety-derived requirement (or a safety annotation on the existing one) that states the hazard it mitigates, the failure condition it guards against, and a measurable acceptance criterion tied to the risk analysis — for example, a bounded rate of change with a tolerance and the fault condition under which it must hold. Second, I'd link that requirement bidirectionally: upward to the specific risk control measure and hazard in the risk management file, and downward to the verification activity. Third, I'd make sure the verification test actually stresses the failure condition — commanding a step change large enough that the limiter must engage — rather than just confirming nominal ramping. The traceability matrix then carries a link that is *meaningful*, not just a number match, because the requirement text itself carries the safety rationale. I'd also add a review check: any requirement traced to a risk control should name the hazard, so this gap can't silently recur.

**Possible follow-ups:** If the firmware team resists adding safety language to a requirement they see as purely functional, how would you frame the benefit to them? And how would you handle the case where the same rate limiter also serves a non-safety performance purpose — would you split it into two requirements or keep one with dual rationale?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** When the control is an emergent property of a loop rather than a single element, tracing it to one requirement or one test is a category error. I'd decompose it explicitly: create a top-level safety requirement that captures the loop's *safe behavior* (e.g., the heating element stays within a bounded temperature band under defined conditions), then allocate sub-requirements to each contributor — sensor accuracy and range, firmware loop behavior and fault response, power switch response time and failure mode — with each sub-requirement traced back to the parent safety requirement and forward to its own verification. The parent requirement gets an *integration* verification that exercises the whole loop, including fault injection at each element (sensor drift, firmware stall, switch failure), because individually-passing sub-tests don't prove the loop is safe. In the matrix I'd represent this as a hierarchy: hazard → risk control measure → parent safety requirement → allocated sub-requirements → per-element verification plus loop-level integration verification. The key discipline is that the parent requirement is never considered verified by the sum of its children alone — it needs its own end-to-end evidence.

**Possible follow-ups:** How would you decide how much of the loop's behavior belongs in the parent requirement versus the allocated sub-requirements? And if the loop-level integration test is expensive to run repeatedly, how would you keep it current as individual elements change?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review's criteria actually address the control's failure condition — otherwise the link is a false positive that will not survive scrutiny. I'd first confirm what the review actually assessed: if the checklist covers the relevant design aspects incidentally, I'd add explicit, control-specific review criteria — a line item stating the failure condition to be assessed, the design evidence to be examined, and a pass/fail judgment recorded against it. That converts a generic review into targeted verification evidence with objective output. If the control genuinely can't be assessed by review (e.g., it depends on dynamic behavior), I'd reclassify the verification method to test or analysis and update the matrix accordingly. The broader fix is a rule: every verification activity linked to a risk control must have acceptance criteria that name the failure condition being mitigated, regardless of method — review, analysis, inspection, or test. That keeps the matrix honest and makes audits straightforward.

**Possible follow-ups:** How would you retrofit control-specific criteria into a review that's already been conducted and signed off? And how would you distinguish a review that genuinely verifies a control from one that merely touches on it?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** Here the control isn't a circuit or a line of code — it's a *value plus the process that guarantees the value*. So the traceability scheme has to cover three things: the parameter's specification (what value, what tolerance, derived from what analysis), the manufacturing process that programs and verifies it, and the runtime behavior that enforces it. I'd create a safety requirement for the parameter itself with a measurable acceptance range and its hazard linkage, then trace it to two verification activities: a design-level verification that the enforcement logic correctly applies the limit (tested with boundary values), and a production verification that each unit's programmed value is within tolerance (with the test method and sampling or 100% coverage defined). The matrix needs a column or link type for "production verification" distinct from design verification, because these are different evidence streams and auditors will ask for both. I'd also trace the parameter to its configuration-control record so that any change to the value or its limits triggers a risk re-assessment. The trap to avoid is treating the parameter as a software constant and losing the manufacturing and configuration-control links entirely.

**Possible follow-ups:** How would you handle a unit that fails the production parameter check — is that a nonconformance under the quality system, and how does it feed back into the risk file? And if the parameter can be changed in the field via a service port, how does that affect the traceability scheme?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd treat this as a substantive quality issue, not a documentation dispute — a matrix that links to tests which don't exercise the failure condition is worse than an incomplete one, because it creates false confidence. My first step would be to verify the concern rather than act on hearsay: pick a sample of the flagged tests, read each against its linked risk control's failure condition, and determine concretely whether the test would fail if the control were defeated. That gives me evidence to work with. Then I'd bring the systems engineer and test lead together around that evidence, framing it not as "the matrix is wrong" but as "the evidence behind these links doesn't demonstrate what the link claims" — which is a shared risk to the project, since it's exactly what a regulator or auditor would probe. The resolution would be to re-derive the affected tests from the failure conditions (or add fault-injection steps so each test demonstrably fails when the control is disabled), update the matrix to reflect the corrected evidence, and add a review gate so that copied-and-relabeled tests can't pass as verification without someone confirming the failure condition is exercised. I'd also want to understand *why* it happened — schedule pressure, unclear test-writing guidance — because fixing the process prevents recurrence better than fixing the individual tests.

**Possible follow-ups:** How would you demonstrate to the systems engineer that a passing test can still be inadequate evidence, without it becoming a personal conflict? And if re-deriving the tests threatens the schedule, how would you prioritize which ones to fix first?
