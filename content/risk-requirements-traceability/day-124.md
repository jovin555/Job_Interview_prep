# risk-requirements-traceability — Day 124

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the requirement captures *what* the firmware does but not *why* it matters, so the safety intent is invisible to anyone reading the SRS in isolation. I'd start by treating the risk analysis entry as the authoritative source of intent and making the requirement explicitly derived from it: the requirement should carry a reference to the risk control ID and a short statement of the hazard it mitigates, not just the clamping behavior. Then I'd make the verification activity prove the *hazard-relevant* property, not merely that the clamp exists. A test that ramps the command and observes that the output rate is limited is necessary but not sufficient — it must also demonstrate that under the fault condition the risk analysis describes (e.g., a runaway command source, a corrupted setpoint, a step input far beyond normal operating range), the limiter actually prevents the hazardous overspeed. I'd also check the boundary conditions the requirement omits: what is the maximum rate, what is the tolerance, what happens at the clamp boundary, and is the limiter's behavior defined when the command source is invalid. Finally, I'd close the loop by adding a bidirectional link so that from the risk control you can navigate to the requirement and the test, and from the test you can navigate back to the hazard — otherwise the matrix is one-directional and the intent is still lost.

**Possible follow-ups:** If the firmware team argues that referencing the hazard in the requirement is "cluttering" the SRS with risk-management content, how would you frame the benefit in terms they care about? And how would you handle the case where the rate limiter is one of several controls mitigating the same overspeed hazard — how do you avoid double-counting the risk reduction?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap here is that the risk analysis credits one control, but the implementation is spread across three elements owned by different disciplines, so a single traceability link from the risk control to "the loop" hides the fact that no one element is sufficient on its own. I'd decompose the control into its constituent functions and make the traceability reflect the *chain*: the sensor's accuracy and failure behavior, the firmware's control law and its response to a sensor fault, and the power switch's ability to actually interrupt the heater. Each of those becomes a design requirement or design element with its own verification, and the risk control links to the set of them rather than to a single node. Crucially, I'd add an integration-level verification that exercises the loop as a whole under the fault conditions the risk analysis cares about — because individually correct elements can still fail to keep the heater safe if, say, the firmware's fault response assumes a sensor reading that the sensor can't provide when it fails. I'd also document the assumptions the risk analysis makes about each element (e.g., "sensor is independent of the heater drive") as explicit traceable items, because those assumptions are what make the single-control credit valid, and if an assumption is violated the control credit collapses.

**Possible follow-ups:** How would you detect that one of the elements in the chain has been changed in a way that invalidates the risk analysis's assumption about the loop? And if the firmware PID loop is later retuned for performance reasons, what traceability mechanism would flag that the safety-relevant behavior needs re-verification?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review actually examines the property the risk control depends on. A generic power-supply checklist will cover topology, decoupling, thermal margins, and so on, but it won't necessarily ask "does this supply hold its output within the safe range under the specific fault the risk analysis identified?" So the link is technically present but evidentially empty. My approach would be to keep the design review as the verification method — because for some controls, review genuinely is the right method — but add a control-specific review criterion to the checklist or to a review record that explicitly states the failure condition and the acceptance question the reviewers must answer. That converts the review from a generic pass into targeted objective evidence. I'd also make sure the review record captures the reviewers' names, the specific criterion assessed, and the conclusion, so an auditor can see that the risk control was actually examined rather than just that a review happened. If the failure condition is one that review genuinely cannot assess (e.g., it depends on dynamic behavior), then the method is wrong and it needs a test or analysis instead — the method has to match the nature of the claim.

**Possible follow-ups:** How would you retrofit this onto a review that has already been completed and signed off without the control-specific criterion? And how do you prevent the checklist from bloating into an unmanageable document as more risk controls get added over time?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a line of code — it's a *value*, and the traceability has to cover the value's entire lifecycle, not just its use. I'd break it into four traceable claims: the parameter has a defined valid range and a rationale for that range (traceable to the risk analysis); the value is written by a controlled manufacturing process with a defined method and tolerance (traceable to a manufacturing instruction); the value is read and enforced correctly by firmware at runtime (traceable to a firmware requirement and a test); and the value is protected against corruption or unauthorized change after it's set (traceable to a requirement about integrity, e.g., checksum or write-protection). Each of those is a separate link, because a unit can have a correctly computed limit that is written incorrectly, or written correctly but not enforced, or enforced but later corrupted. The verification then has to sample across the allowed range, not just at a nominal value, and the manufacturing record becomes part of the evidence chain — the traceability matrix should point to the process spec and the per-unit record, not just to a bench test. I'd also flag the units where the value is at the extreme of the allowed range as the worst-case verification samples.

**Possible follow-ups:** If the parameter can be changed in the field via a service port, how does that change the traceability and verification scheme? And how would you demonstrate to an auditor that the manufacturing-set value is actually the value the risk analysis assumed, for a specific unit in the field?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The matrix being complete and the tests passing are both true and both insufficient — the question is whether the evidence actually supports the claim, and a copied test with relabeled labels is a claim without evidence. I'd treat this as a quality-of-evidence problem rather than a compliance problem, and I'd avoid framing it as "the systems engineer is wrong," because that turns it into a territorial argument. Instead I'd ask for a focused review: take the specific linked tests the engineer flagged and walk through each one against the risk analysis entry — does the test setup reproduce the failure condition, does the stimulus reach the fault, does the acceptance criterion measure the control's effect? Where the answer is no, that's a concrete gap we can all agree on, independent of whose document is "correct." I'd then decide per test whether to rewrite it, add a supplementary test, or (if the copied test genuinely does exercise the condition) document why it's adequate. I'd also want to understand *why* the copying happened — schedule pressure, unclear test-writing guidance, no review of test intent — because fixing the individual tests without fixing the cause just moves the problem to the next project. And I'd make the review of test intent against risk analysis a standing step, so this doesn't depend on someone privately flagging it next time.

**Possible follow-ups:** How would you handle it if the systems engineer escalates and argues you're second-guessing a matrix that already passed audit? And what would you change in the test-development process so that "does this test actually exercise the failure condition?" is asked at authoring time rather than discovered later?
