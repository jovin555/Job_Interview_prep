# risk-requirements-traceability — Day 89

## Q1: How would you approach tracing a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the safety intent lives only in the risk file while the implementation lives only in the firmware requirements, so the traceability chain is broken at the most important link — the one that explains *why* the behavior matters. I'd start by making the risk file the anchor: the risk control measure entry should state the hazard, the hazardous situation, and the specific failure condition the limiter is meant to prevent (e.g., a step change in command causing mechanical overspeed). From there I'd create an explicit derived requirement in the SRS that carries the safety intent forward — something like "the system shall limit the rate of change of the motor speed command such that [measurable bound] is never exceeded, mitigating the overspeed hazard" — with a cross-reference back to the risk control ID. The firmware requirement then traces up to that SRS requirement rather than standing alone. The key discipline is that the SRS requirement must have a *measurable acceptance criterion* tied to the failure condition, not just "the firmware shall clamp the command." Finally, the verification activity must be designed to stress the failure condition — inject a step command that would cause overspeed if unclamped, and confirm the limiter holds the bound — rather than merely confirming the clamp exists under nominal ramping. I'd also add a bidirectional check: from the risk control, you can walk down to the SRS requirement, the firmware requirement, the design element, and the test; and from the test, you can walk back up to the hazard. If either direction breaks, the trace is incomplete.

**Possible follow-ups:** If the firmware team argues that adding the safety rationale to the SRS "clutters" it with risk-management language, how would you keep the SRS readable while preserving the trace? And how would you handle the case where the rate limiter is later tuned during development — what keeps the trace valid when the numeric bound changes?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap here is treating the loop as a single atomic control when it's actually a chain of elements, each with its own failure modes and its own requirements owner. I'd decompose the control into its constituent elements and make the *chain* the traceable object, not just the endpoints. Concretely: the risk control measure in the risk file stays as the top-level entry (the hazard it mitigates, the safe range it maintains), but I'd add a decomposition layer — a set of derived requirements, one per element, that together constitute the control. The sensor requirement covers accuracy, range, and failure detection; the firmware requirement covers the control law, the safe-state behavior on sensor fault, and the output bounds; the power switch requirement covers the ability to actually remove energy and the response time. Each derived requirement traces up to the parent risk control and down to its own design element and verification. The critical piece is the *interface* between elements: the sensor-to-firmware interface and the firmware-to-switch interface each need an ICD or interface requirement that captures the timing and signal-integrity assumptions the control depends on — because the control fails if any interface assumption breaks, even if each element passes in isolation. I'd also make sure the verification plan includes an end-to-end test of the loop under fault conditions (sensor dropout, sensor drift, switch failure to open) in addition to the per-element tests, because per-element verification can't catch a control that's correct in every part but wrong as a whole.

**Possible follow-ups:** If the end-to-end test is expensive or slow to run, how would you decide how much of the loop verification can rely on per-element tests plus analysis versus needing full-system testing? And how would you trace a *timing budget* — say, the total loop latency — when it's allocated across three elements owned by different teams?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review's criteria are specific enough that a reviewer could actually fail the design against the risk control. A generic checklist that happens to touch the same subsystem is not evidence that the control works — it's evidence that someone looked at the subsystem. My approach would be to make the review criteria traceable to the risk control: add an explicit review item that states the failure condition the control is meant to prevent and asks the reviewer to confirm, with a recorded rationale, that the design addresses it. That converts the review from incidental coverage into a targeted verification activity with objective evidence — the reviewer's recorded finding against a specific criterion. I'd also check whether a design review is genuinely the *right* method for this control or whether it's being used as a shortcut. Reviews are appropriate for controls that are inherently design-rule-based or that can't be exercised on a bench (creepage distances, derating margins, worst-case tolerance stack-ups), but if the control is functional and testable, a review is weak evidence and I'd push for a test. The decision rule I'd apply: does the review criterion name the failure condition, and would a competent reviewer be able to reject the design if the control were absent or inadequate? If yes, it's valid verification; if no, it needs to be rewritten or replaced.

**Possible follow-ups:** How would you record the review evidence so an auditor can see that the specific failure condition was assessed, rather than just that a review meeting occurred? And if the reviewer signs off but you suspect they didn't really evaluate the control, what would you do?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a behavior in the firmware or a component on the board — it's a *value*, and the traceability has to cover the value's specification, its programming, and its verification at the unit level. I'd structure it in three layers. First, the risk file defines the control: the hazard, the required limit range, and the rationale for why that range is safe. Second, the SRS carries a derived requirement that specifies the limit's allowable range and the conditions it must hold under (temperature, supply variation, load), with a measurable acceptance criterion. Third, and this is the part that's easy to miss, there's a *manufacturing* requirement and a *verification* requirement: the production process must program the parameter within the specified range, and there must be a per-unit or sampled verification that reads back the programmed value and confirms it's in range. The traceability matrix needs to show the path from the risk control through the SRS requirement to the manufacturing instruction and to the production test — because for a parameter-set control, the "verification activity" is partly a production test, not just a design verification test. I'd also address change control: if the allowable range is ever revised, the trace must show that the manufacturing programming limits and the production test limits were updated together, otherwise you can ship units programmed to a value the risk analysis no longer considers safe. The key insight is that for parameter-based controls, traceability extends into the manufacturing and service lifecycle, not just the design phase.

**Possible follow-ups:** How would you handle the case where the parameter can be changed in the field via a service port — does that create a new hazard that needs its own risk control and trace? And how would you decide whether per-unit readback verification is necessary or whether sampled verification is defensible?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The matrix being complete and the tests passing are both necessary but neither is sufficient — the question is whether the tests actually demonstrate the control works against *this* project's failure conditions, and the test engineer is telling me they may not. I'd treat this as a substantive quality issue, not a documentation issue, and I'd handle it in stages. First, I'd verify the concern rather than take it at face value or dismiss it: pick two or three of the flagged tests and walk through them against the risk analysis entry — does the test setup reproduce the failure condition, does the stimulus actually drive the system into the hazardous state, and would the test fail if the control were removed? That last check is the decisive one, and it's cheap to run as a thought experiment or a quick bench trial. Second, I'd bring the systems engineer and test engineer together with the specific findings rather than in the abstract — the conversation changes completely when you can show a test that passes with the control disabled. Third, if the concern holds, I'd scope the remediation: not necessarily re-writing every test, but re-validating the ones where the failure condition isn't clearly exercised, prioritizing by severity of the hazard. I'd also address the root cause — tests being copied and relabeled without review is a process gap, so I'd add a review step where the test author confirms in writing that the test exercises the specific failure condition from the risk file, and I'd make that confirmation part of the traceability record. The framing I'd use with the systems engineer is that the matrix is a map, and a map that shows a road where there's actually a cliff is worse than no map — the goal isn't audit compliance, it's confidence that the controls work.

**Possible follow-ups:** How would you prioritize which tests to re-validate first if you can't re-run everything before the next milestone? And how would you handle the situation if the systems engineer continues to resist, given that the matrix technically passes audit?
