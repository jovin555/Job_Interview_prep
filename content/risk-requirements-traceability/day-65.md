# risk-requirements-traceability — Day 65

## Q1: How would you approach tracing a risk control measure that is implemented as a combination of a hardware interlock and a firmware acknowledgment — for example, a relay that physically removes power from a heater unless firmware continuously asserts an enable signal — when the hardware and firmware teams each own half of the control and neither team's requirements document references the other?

**Answer:** The key insight is that this is a single risk control measure with two *necessary* halves — neither the relay alone nor the enable signal alone mitigates the hazard, so the traceability has to represent the control as one logical entity even though two teams implement it. I'd start by giving the control a single risk-management identifier in the risk file (something like RC-xxx) and treating that as the anchor. Then, rather than forcing one team to own the whole thing, I'd create a system-level requirement that states the *integrated* behavior — "power to the heater shall be removed unless a valid enable signal is continuously present" — with measurable acceptance criteria (e.g., maximum time from loss of enable to de-energized relay). That system requirement is what traces up to the hazard and down to verification. Below it, the hardware design spec documents the relay's fail-safe (de-energized) state and its response time, and the firmware spec documents the enable-assertion logic and its timing. Both of those lower-level items carry a cross-reference back to the same RC-xxx and to the system requirement, so the matrix shows two implementation branches converging on one control. The verification activity then has to be an *integrated* test — you can't verify the relay in isolation and the firmware in isolation and claim the control is verified, because the hazard depends on the coupling. I'd also make sure the interface between them (the enable signal's electrical definition, polarity, and timing) lives in an ICD so there's a single authoritative description both teams point to. The practical rule I'd apply: if disabling either half would defeat the control, the traceability must show them joined at the system level, not left as two orphaned links.

**Possible follow-ups:** If the firmware team changes the enable timing later, what in the traceability structure would force a re-review of the hardware verification? How would you handle it if the two teams used different requirement numbering schemes and you couldn't renumber either?

## Q2: How would you approach deciding whether a risk control measure should be traced to a design requirement, a design element, or both — and what practical difference does that distinction make in a traceability matrix?

**Answer:** The distinction matters because requirements and design elements answer different questions and fail in different ways. A *requirement* is a statement of what the system must do or be, with measurable acceptance criteria — it's the thing you can verify against. A *design element* is the specific implementation that satisfies the requirement — a circuit block, a firmware module, a mechanical feature. A risk control measure usually needs to trace to both, but for different purposes. Tracing to a requirement gives you verification coverage: you can point to a test that demonstrates the control works. Tracing to a design element gives you change-impact coverage: if someone modifies that circuit or module, you can see that a risk control depends on it and trigger a re-assessment. If you trace only to a requirement, a design change might silently invalidate the control without anyone noticing the requirement was affected. If you trace only to a design element, you have no objective acceptance criterion to verify against — you've documented *where* the control lives but not *what it must achieve*. So my default is: every risk control measure traces to at least one requirement (for verification) and to the design element(s) that implement it (for change control). The practical difference in the matrix is that the requirement link drives the verification column, while the design-element link drives the impact-analysis column — they're separate relationships, not redundant ones. Where it gets subtle is controls that are purely design-rule-based, like creepage distance or component derating: there may be no functional requirement in the usual sense, so the "requirement" is really a design constraint, and the verification is inspection or analysis rather than test. In that case I'd still create a traceable constraint item so the matrix has something to hang the verification on, rather than leaving the control linked only to a drawing.

**Possible follow-ups:** How would you represent a design constraint like creepage distance in a requirements management tool so it's still auditable? If a design element implements three different risk controls, how do you keep the impact analysis from becoming unmanageable?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity's acceptance criterion is stated as "the control functions as designed" rather than as a measurable pass/fail threshold?

**Answer:** "Functions as designed" is not an acceptance criterion — it's a placeholder that defers the real question, and it's a common finding in audits because it gives no objective evidence that the control actually mitigates the hazard. The first thing I'd do is go back to the risk analysis and ask what the control is *for*: what failure condition does it detect or prevent, and what does "working" look like in measurable terms? That usually yields a threshold, a timing bound, or a state transition that can be turned into a pass/fail. For example, if the control is a plausibility check that rejects out-of-range sensor readings, the criterion isn't "the check functions" — it's "a reading deviating by more than X from the previous sample is rejected within N samples, and the system enters the defined safe state." I'd rewrite the acceptance criterion to state the input condition, the expected observable response, and the tolerance. Then I'd check whether the existing test procedure actually *creates* that input condition — often a vague criterion is a symptom of a test that only exercises nominal behavior, so fixing the criterion may force the test to be redesigned. I'd also want to distinguish between the criterion and the method: the criterion is the measurable outcome, the method is how you induce it. Both need to be specific enough that a different engineer running the test would reach the same verdict. Finally, I'd treat this as a systemic issue, not a one-off — if one verification activity has a vague criterion, I'd sweep the matrix for others phrased the same way, because they tend to cluster where the risk analysis itself was thin. The root cause is usually that the hazard and its failure condition were never stated precisely enough to derive a threshold from.

**Possible follow-ups:** What would you do if the risk analysis genuinely can't produce a numeric threshold — for example, a control whose effectiveness is qualitative? How would you handle a test engineer who argues the vague criterion is fine because "everyone knows what it means"?

## Q4: How would you approach establishing traceability for a risk control measure that is implemented as a redundant channel — a primary sensor path and an independent secondary path whose agreement is checked — where the control's effectiveness depends on the *independence* of the two channels rather than on either channel alone?

**Answer:** This is a case where the control's *property* is the thing being verified, not just its function, and that changes how I'd structure the traceability. The hazard mitigation depends on two claims: first, that each channel can detect the fault on its own, and second, that the two channels are genuinely independent — no shared power rail, no shared clock, no shared firmware routine, no common connector that a single failure could take out. So I'd trace the control to *two* categories of requirement. The first is a functional requirement for the agreement check itself: "the system shall compare primary and secondary readings and enter the safe state when they diverge by more than X." That traces to a functional test. The second is a set of *independence* requirements — separate supplies, separate signal paths, no shared single points of failure — which are verified differently: by design analysis, by FMEA review of common-cause failures, and by inspection of the schematic and layout. The traceability matrix has to show both branches, because a functional test that proves the agreement check works tells you nothing about whether a single fault could disable both channels simultaneously. I'd also make sure the risk file explicitly names the common-cause failure modes considered, so the independence claim is auditable rather than assumed. The verification activity for independence is often analysis plus a design review with a checklist of shared-resource questions, and I'd want that review to have explicit criteria — "are the two channels powered from separate regulators?" — rather than a general "review the design." The trap here is treating the redundant channel as one control with one verification link; it's really a control whose effectiveness rests on a structural property that needs its own traceable evidence.

**Possible follow-ups:** How would you verify independence if the two channels share a common microcontroller but use separate ADC inputs? What evidence would convince you that a common-cause failure analysis was thorough enough?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has built a traceability matrix that links every risk control measure to a verification activity, and the matrix is complete and passes audit. However, a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and that nobody has confirmed the tests actually exercise the failure conditions in this project's risk analysis. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The systems engineer is right that the matrix is compliant and the tests pass, and wrong that there's no problem — because the matrix is asserting a relationship that may not be true. A traceability link is a *claim* that this test verifies this control, and if the test was copied without confirming it exercises the failure condition, the claim is unverified. That's worse than a gap, because a gap is visible and a false link is not. I'd handle it in stages. First, I'd thank the test engineer for raising it and make clear I'm treating it as a process issue, not a personal failing — copied-and-relabeled tests are usually a symptom of schedule pressure, not laziness. Second, I'd do a focused spot-check: pick the flagged tests and, for each, walk through the risk analysis's failure condition and ask "does this test actually induce that condition, and would it fail if the control were disabled?" That's the same negative-test logic you'd apply to any risk control verification. Third, based on what I find, I'd either rework the tests or, if some genuinely do exercise the right condition, document that finding so the link is defensible. Fourth, and most importantly, I'd address the root cause: the matrix was built as a linking exercise rather than as a verification-planning exercise, so the links were made on the basis of "we have a test for this area" rather than "this test stresses this failure condition." I'd want the review process to include a check that each risk control's verification activity names the failure condition it induces — that single field would have caught the copied tests. I'd also be careful not to let this become a blame exercise between the systems engineer and the test engineer; the fix is a shared review step, not a verdict on who was wrong.

**Possible follow-ups:** How would you decide how deep to re-verify — do you re-test everything, or sample? If the schedule can't absorb re-testing before a milestone, how would you handle the risk of shipping with unverified links?
