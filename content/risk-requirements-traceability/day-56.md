# risk-requirements-traceability — Day 56

## Q1: How would you approach tracing a risk control measure that is implemented as a "safe state" defined by a combination of hardware and firmware — for example, a system that must enter a low-power, outputs-disabled state within a bounded time after a fault is detected — when the safe state itself is not a single component but an emergent system behavior?
**Answer:** The key insight is that an emergent safe state cannot be traced as if it were a single design element, because no single requirement, component, or test fully owns it. I would treat the safe state as a system-level requirement in its own right, with a measurable acceptance criterion — for example, "outputs shall be de-energized within the specified bounded time after fault assertion, and the system shall remain in that state until an explicit reset." That requirement then becomes the anchor for traceability, and the hardware and firmware contributions are traced as *allocated* sub-requirements beneath it rather than as the control itself.

Concretely, I would decompose the safe state into its constituent conditions: fault detection (often hardware — a comparator, a watchdog, a supervisor), fault propagation (the signal path from detection to the firmware or to a hardware gate), the firmware decision and actuation (disabling outputs, entering low-power mode), and the timing budget across all of those. Each of those gets its own requirement and its own verification, but the *system-level* safe-state requirement is verified by an end-to-end test that injects a fault and measures the actual time to outputs-disabled and the resulting state. The traceability matrix then shows a fan-out from the single system requirement to the allocated sub-requirements, and a fan-in from the sub-verifications plus the end-to-end test back to that requirement.

The subtlety is that passing all the sub-verifications does not prove the emergent behavior, because the timing and sequencing are properties of the integration, not of any one piece. So I would insist that the end-to-end verification is mandatory and is not satisfied by "the hardware test passed and the firmware test passed." I would also capture the assumptions that make the safe state valid — for example, that the fault signal is not masked during any operating mode, and that the low-power transition does not itself create a new hazard — as explicit notes or derived requirements, because those assumptions are exactly where emergent behaviors tend to fail.

**Possible follow-ups:**
- How would you handle the case where the fault-detection hardware and the firmware actuation are verified separately but the end-to-end timing test is impractical to run on every unit?
- If the safe state depends on a bounded time, how would you decide whether that bound is a safety requirement, a performance requirement, or both?

## Q2: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity's test procedure was written against an earlier revision of the requirement, so the test still passes but no longer exercises the current acceptance criteria?
**Answer:** This is a configuration-control failure as much as a traceability failure, and I would treat it as such. The first step is to confirm the discrepancy objectively: compare the current requirement revision, its acceptance criteria, and the test procedure revision, and document exactly what changed and whether the change is material to the risk control. A wording clarification that does not alter the pass/fail threshold is a different problem from a changed threshold, a changed fault condition, or a changed operating mode.

If the change is material, the test is no longer valid evidence for that requirement, and the traceability link is misleading — it points to a test that does not verify the current requirement. I would flag the link as broken, not delete it, so the history is preserved, and raise a change request to update the test procedure to the current acceptance criteria. Until the updated test is run and passes, the requirement should be considered unverified, and that status should be visible in the coverage report rather than hidden behind a green checkmark.

The deeper fix is process: requirements and their verification activities need to be under the same change-control and review discipline, so that when a requirement revision is approved, the linked test procedures are flagged for impact assessment automatically. In practice I would want the traceability tool to support a "suspect link" state — when either end of a link changes revision, the link is marked suspect until someone reviews it. That converts a silent staleness problem into a visible action item, which is the only way it gets caught before an audit or, worse, before a device ships with a control that was never actually verified against its current specification.

**Possible follow-ups:**
- How would you decide whether a requirement change is material enough to invalidate the existing test evidence, versus a clarification that can be handled by a documented rationale?
- Who should own the decision to re-run a test after a requirement revision — the test engineer, the systems engineer, or the quality function?

## Q3: How would you approach establishing traceability for a risk control measure that is implemented as a redundant channel — for example, a primary sensor path and an independent secondary path whose agreement is checked — where the control's effectiveness depends on the independence of the two channels rather than on either channel alone?
**Answer:** Redundancy is a case where the traceability has to capture a property — independence — that is not a component and not a functional requirement in the usual sense. I would start by making the independence claim explicit as a requirement or design constraint: the two channels must not share a common failure mode that could cause both to fail or both to agree incorrectly. That claim is what the risk control actually depends on, so it needs to be traceable and verifiable in its own right.

From there, the traceability fans out in two directions. Functionally, each channel gets its own requirements and verification — the primary path must produce a valid reading, the secondary path must produce a valid reading, and the comparison logic must detect disagreement and respond. But separately, the independence claim needs its own verification, which is typically a combination of analysis and inspection rather than a functional test: shared power rails, shared clock sources, shared connectors, shared firmware routines, shared memory, and shared communication buses are all potential common-cause failure paths. I would trace the independence requirement to a design analysis (for example, a common-cause failure analysis or a dependency review) and to inspection of the schematic and the firmware architecture, and I would record the specific shared resources that were examined and the rationale for concluding they do not defeat independence.

The comparison logic itself also needs care, because it is a single point of failure: if the comparator that checks agreement fails, both channels can be present and the control still does not work. So the traceability should show that the comparison function is itself covered by a risk control or is designed to fail safe. The verification for the overall control is then an end-to-end test that injects a fault into one channel and confirms the system detects the disagreement and responds — plus the independence analysis, which is what makes the end-to-end test meaningful rather than just a demonstration that two working channels agree.

**Possible follow-ups:**
- How would you verify independence when the two channels share a microcontroller but use different sensor front-ends?
- If the independence analysis identifies a shared resource that cannot be eliminated, how would you decide whether the control is still adequate or whether a different control is needed?

## Q4: How would you approach deciding whether a risk control measure should be traced to a design requirement, a design element, or both — and what practical difference does that distinction make in a traceability matrix?
**Answer:** The distinction matters because requirements and design elements answer different questions, and conflating them is a common source of traceability gaps. A requirement states *what must be true* — a behavior, a limit, a condition — and is verified by a verification activity. A design element states *how it is realized* — a circuit block, a firmware module, a mechanical feature — and is verified by inspection, analysis, or test of that element. A risk control measure usually needs both links, but for different purposes.

Tracing a control to a design requirement is what makes it verifiable: the requirement carries the measurable acceptance criterion, and the verification activity attaches to the requirement. Tracing the same control to a design element is what makes it auditable and maintainable: it shows where in the design the control lives, so that when the design changes, the impact on the risk control is visible. If a control is traced only to a requirement, a design change can silently invalidate the control without anyone noticing the requirement is affected. If it is traced only to a design element, there may be no measurable acceptance criterion and no verification activity, so the control is effectively unverified.

In practice, I would use the requirement as the primary traceability anchor — hazard to risk control to requirement to verification — and use the design element link as a secondary, impact-analysis link. The matrix then supports two queries: "is every risk control verified?" (follow the requirement links) and "if this design element changes, which risk controls are affected?" (follow the design element links). The practical difference is that the requirement link is mandatory for every control, while the design element link is mandatory wherever the control is realized in a specific, identifiable piece of the design — which is most of the time, but not always, for example for procedural controls that live in a work instruction rather than in the product.

**Possible follow-ups:**
- How would you handle a risk control that is realized across several design elements, such as a control split between a power supply block and a firmware module?
- Would you ever accept a risk control traced only to a design element with no requirement, and if so, under what conditions?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has built a traceability matrix that links every risk control measure to a verification activity, and the matrix is complete and passes audit. However, a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and that nobody has confirmed the tests actually exercise the failure conditions in this project's risk analysis. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?
**Answer:** I would treat this as a serious issue rather than a process nitpick, because the matrix is asserting something that may not be true: that each risk control has been verified against *this* project's failure conditions. A matrix that passes audit but links to tests that do not exercise the right failure conditions is worse than an incomplete matrix, because it creates false confidence and would be very hard to defend if the device ever failed in the field in a way the control was supposed to prevent.

My first step would be to protect the test engineer who raised it — they did the right thing by surfacing it, and if the response is punitive or dismissive, the next person will stay quiet. I would thank them privately and make clear that raising it was correct. Then I would verify the concern myself on a small sample: pick two or three of the flagged tests, read the test procedure against the risk analysis failure condition, and confirm whether the test actually injects or simulates that condition. That gives me facts rather than hearsay before I talk to the systems engineer.

With the systems engineer, I would avoid framing it as "you cheated" and instead frame it as a shared risk: the matrix is structurally complete, but the *evidence* behind several links may not support the claim, and that is a gap we need to close before the next design review or audit. I would propose a targeted re-verification of the flagged tests — not a blanket re-run of everything, which would be disproportionate — and a review of the test-writing process to understand how copied tests entered the project without an independence check. I would also want to know whether the same pattern exists in other projects, because if it does, it is a process problem, not an individual one.

The systems engineer's argument that "the matrix is compliant and the tests pass" is technically true but misses the point: compliance is about the evidence supporting the claim, not about the existence of a link. I would make that explicit and, if needed, escalate to the quality function, because the decision to accept or reject the evidence is ultimately a quality call, not a schedule call. The goal is not to assign blame but to make sure that when we say a risk control is verified, we can show what failure condition was exercised and why the test is adequate for it.

**Possible follow-ups:**
- How would you decide how many of the flagged tests to re-verify, given schedule pressure and the cost of re-running tests?
- What process change would you put in place to prevent copied tests from being accepted as verification evidence in the future?
