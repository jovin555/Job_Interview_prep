# risk-requirements-traceability — Day 92

## Q1: How would you approach tracing a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is a broken semantic link: the requirement exists and the code exists, but nothing in the requirement states *why* it exists, so a future maintainer could tune the rate limit for performance reasons and silently degrade a safety control. I'd approach it in three steps.

First, I'd establish the missing upward link. The firmware requirement needs an explicit trace to the risk control measure ID in the risk management file, and the requirement text itself should carry the safety intent — not just "the commanded speed shall not change by more than X units per second" but a statement that this bound exists to prevent the actuator from reaching a hazardous rate under a runaway command. The numeric bound should be justified by the risk analysis (what rate is hazardous, what margin the control provides), so the requirement's acceptance criterion is anchored to the hazard rather than to a convenient round number.

Second, I'd make the downward link explicit and testable. The verification activity must exercise the *failure condition*, not just confirm the clamp exists. That means a test that commands a step change well beyond the limit and measures the actual output rate against the specified bound — and ideally a test that confirms the limiter holds under worst-case conditions (maximum commanded step, minimum loop period, interrupt latency at its worst). A test that only checks "output stays below max speed" doesn't prove the rate limiter works; it proves the speed cap works, which may be a different control.

Third, I'd address the systemic cause: a requirement template or review checklist item that flags any requirement derived from a risk control and requires the hazard reference and the risk-analysis justification to be present. The rate limiter case is a symptom of requirements being written from a functional mindset without a safety-intent field.

**Possible follow-ups:** If the rate limit value was chosen by the firmware team for smoothness rather than derived from the hazard analysis, how would you reconcile the two? And how would you verify the limiter behaves correctly when the actuator is already at the limit and a new command arrives mid-ramp?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** This is the classic "emergent control" problem: the risk analysis credits a single control, but the control has no single owner and no single requirement. If you trace only at the loop level, you can't verify the parts; if you trace only at the part level, you can't demonstrate the loop as a whole meets the safety intent.

My approach is to decompose the control into an allocated architecture while keeping the loop-level trace intact. At the top, the risk control measure stays as a single entry in the risk file with a stated safety intent — "keep the heating element within a safe temperature band under all operating conditions." Below it, I'd create an allocated set of sub-requirements, one per element: the sensor's accuracy and response time, the firmware loop's update rate and control law behavior (including what it does on sensor fault or saturation), and the power switch's ability to interrupt the element independent of firmware. Each sub-requirement traces up to the parent control and down to its own verification. The parent control then has a *system-level* verification — a test that exercises the loop end-to-end under fault injection (sensor drift, sensor dropout, stuck power switch) — in addition to the element-level verifications.

The key discipline is that the allocation must be justified: the risk analysis should state what each element contributes and what happens if it fails. If the loop's safety depends on the power switch being able to cut power even when firmware is hung, that's a separate risk control (an independent shutdown path) and should be traced as such, not buried inside the loop. I'd also make sure the interface between elements — the sensor-to-firmware signal, the firmware-to-switch command — is captured in an ICD so the timing and signal-level assumptions are documented and verifiable.

**Possible follow-ups:** How would you verify the loop's behavior when one element degrades slowly rather than failing hard — for example, a sensor that drifts out of calibration over months? And if the PID gains are tuned during development, how do you keep the safety-relevant bounds (e.g., maximum output, integral windup limits) under configuration control?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence for certain kinds of controls — layout rules, derating, creepage, thermal margin — but only if the review actually assesses the specific failure condition the control is meant to mitigate. A generic checklist that happens to touch the power supply is not evidence that the control works; it's evidence that someone looked at the power supply.

I'd handle it by making the review criteria explicit and traceable. First, I'd extract from the risk analysis the specific failure condition and the control's intended effect — for example, "the control must ensure the bulk capacitor's voltage rating exceeds the worst-case transient by a defined margin." Then I'd add a review checklist item that states that criterion in measurable terms, with a place to record the reviewer's finding and the evidence (the calculation, the datasheet reference, the measurement). The review record then becomes objective evidence tied to the control, not a generic sign-off.

Second, I'd distinguish between controls that can *only* be verified by review (derating, layout) and controls that could be verified by test but were assigned to review for convenience. The latter should be moved to test or analysis with a defensible rationale; the former should have review criteria written specifically for them. A useful test is: could a reviewer who had never seen the design before, armed only with the checklist, determine whether the control is satisfied? If not, the checklist is inadequate.

Third, I'd close the loop in the traceability matrix so the link points to the *specific* review record and checklist item, not just "design review DR-14." That way an auditor can see exactly what was assessed.

**Possible follow-ups:** How would you handle a review where the reviewer signed off but the recorded evidence is just "reviewed, OK" with no calculation or measurement attached? And how do you keep review checklists from becoming stale as the design evolves?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control is not a circuit or a line of code but a *value*, and the traceability has to cover three things: the requirement that defines the value and its bounds, the manufacturing process that programs it, and the verification that confirms each unit carries a correct value.

I'd structure it as follows. The risk control measure in the risk file states the safety intent — "output current shall not exceed the level that could cause harm under the worst-case fault." The SRS carries a requirement that the parameter exists, its permitted range, and the rule for how the value is determined (e.g., derived from the transducer's rated current with a defined margin). That requirement traces down to two things: the firmware/hardware design element that reads and enforces the parameter, and the manufacturing specification that programs it. The manufacturing spec is itself a controlled document with its own verification — an end-of-line test that reads back the programmed value and confirms it's within the permitted range and matches the unit's configuration.

The traceability matrix then has a branch that most matrices miss: a link from the risk control to the *production test* and to the *configuration record* for each unit. For a parameter that can differ between units, the verification isn't a single design-verification test — it's a combination of a design verification that proves the enforcement mechanism works across the permitted range, plus a per-unit production verification that the programmed value is correct. I'd also trace the change-control path: if the permitted range or the derivation rule changes, what triggers re-verification, and how do already-shipped units get assessed?

The subtle risk is that the parameter becomes a "tunable" that someone adjusts in the field or during service without re-running the safety analysis. So I'd want the requirement to state explicitly whether the value is fixed at manufacture or service-adjustable, and if adjustable, what constrains the adjustment and how it's verified.

**Possible follow-ups:** How would you verify the enforcement mechanism across the full permitted range without testing every possible value? And if a service procedure allows the parameter to be changed, how does that interact with the per-unit verification evidence?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The matrix being complete and the tests passing is exactly the condition under which this kind of problem hides — the paperwork looks right, so nobody looks deeper. I'd treat the test engineer's disclosure as a serious signal and handle it in a way that protects the person who raised it while fixing the substance.

First, I'd thank the engineer and keep the conversation confidential, then verify the claim myself on a sample — pick two or three of the flagged tests, read the test procedure against the risk analysis entry, and check whether the test actually drives the system into the failure condition or just exercises nominal behavior. If the claim holds, I'd frame the issue to the team not as "the tests are wrong" but as "the traceability is structurally sound but the verification evidence doesn't demonstrate the controls work" — which is a quality and regulatory exposure, not a paperwork dispute.

Second, I'd address the systems engineer's position directly. A matrix that links to a test that doesn't stress the failure condition is traceability in form only; the link is only meaningful if the verification activity actually verifies the control. I'd propose a targeted re-verification: for each flagged control, confirm whether the existing test genuinely covers the failure condition, and where it doesn't, write a test that does — including fault injection or worst-case conditions as the risk analysis specifies. I'd prioritize by severity, so the highest-risk controls get re-verified first.

Third, I'd look at the root cause. Copying a test from a previous project and relabeling it is a symptom of schedule pressure and of a process where test authors aren't required to read the risk analysis entry before writing the test. I'd add a step to the verification planning process: the test author signs off that they've read the risk control's failure condition and that the test exercises it, and the reviewer checks that specifically. I'd also make the risk analysis entry visible in the test procedure template so the intent travels with the test.

Finally, I'd be transparent with quality and regulatory affairs about what was found and what was re-verified, because if this surfaces in an audit later, a documented, self-corrected finding is far better than an undiscovered one.

**Possible follow-ups:** How would you decide how much re-verification is enough before you can credibly say the matrix reflects reality? And how would you handle the situation if the systems engineer continued to argue that the existing tests are adequate?
