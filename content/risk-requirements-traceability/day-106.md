# risk-requirements-traceability — Day 106

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement captures the *mechanism* but not the *safety intent*, so the link from hazard to requirement is implicit and fragile — anyone reading the firmware requirement in isolation would see a performance behavior, not a safety control, and a future change to the clamp rate could be approved without anyone realizing it weakens a risk control. I'd fix this at the requirement level rather than trying to patch it in the matrix. First, I'd add an explicit safety-derived requirement (or annotate the existing one) that states the hazard it mitigates, the failure condition it guards against, and the measurable limit — for example, a maximum commanded rate of change with a tolerance and the rationale tied to the overspeed hazard. That gives the traceability matrix a real anchor: hazard → risk control measure → safety requirement → design element (the firmware module implementing the clamp) → verification activity. Second, I'd make sure the verification test actually stresses the failure condition — commanding a step change larger than the limit and confirming the output ramps rather than jumps — not just confirming the clamp exists under nominal commands. Third, I'd add a change-control note so that any modification to the clamp rate triggers a review against the risk analysis. The general principle: a risk control implemented in firmware needs its safety intent written into the requirement, otherwise the traceability link is nominal only.

**Possible follow-ups:** If the clamp rate is a tunable parameter, how do you keep the traceability valid when the value changes between builds? / How would you handle the case where the same clamp behavior also serves a purely functional purpose (smooth motion), so the requirement has two justifications?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The difficulty is that the risk analysis credits an emergent, whole-loop property, but traceability naturally wants to decompose into per-element requirements — and if you only trace to the individual elements, you can have every element "pass" while the loop as a whole fails to hold the safe range. I'd handle this with a two-level structure. At the top, I'd create a single system-level safety requirement that expresses the loop's safe-range guarantee as a measurable, end-to-end property — for example, the heating element stays below a maximum temperature under defined load and ambient conditions, with a stated response time. That requirement is the traceability anchor for the risk control measure, and it gets verified by a system-level test that exercises the whole loop, including sensor, control law, and actuator. Below it, I'd trace the contributing elements — sensor accuracy and range, PID update rate and saturation/clamp behavior, power switch response and fail-safe state — as *allocated* sub-requirements, each with its own verification, so you can show the budget is met element by element. The key discipline is that the system-level test is not optional: element-level verification alone doesn't demonstrate the control works, because the control is the loop. I'd also document the assumptions the loop depends on (sensor placement, thermal time constants, sample timing) so a change to any of them is recognized as a change to the control.

**Possible follow-ups:** How would you allocate a timing or accuracy budget across the three elements and prove the allocation is adequate? / If the PID loop is later retuned, what in your traceability scheme tells you to re-verify the system-level control?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence for certain kinds of controls — layout rules, derating, creepage, things that can't be exercised by a functional test — but only if the review actually assesses the specific failure condition the control addresses. A generic checklist that never mentions that condition doesn't demonstrate anything about the control; it just demonstrates the power supply was reviewed. So I'd treat this as a gap, not a pass. My approach: first, confirm whether the control is genuinely review-verifiable or whether it needs a test or analysis instead — if it's a physical/design-rule control, review is appropriate; if it's a functional behavior, review alone is probably insufficient. Second, if review is the right method, I'd create a control-specific review criterion — an explicit checklist line or review record entry that states the failure condition, the acceptance criterion, and the reviewer's objective finding — and re-run or extend the review against it, capturing evidence. Third, I'd update the traceability matrix so the link points to that specific review record, not to the generic review. The broader fix is to make the review checklist derive from the risk controls it's meant to verify, so this doesn't recur. The principle: "verification by review" is only valid when the review criteria are traceable to the control's failure condition.

**Possible follow-ups:** How would you decide, for a given control, whether review, analysis, or test is the appropriate verification method? / What objective evidence would you expect a design review to produce so it stands up as verification?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a fixed design feature but a *value*, and the value can vary per unit, so the traceability has to cover not just "the parameter exists" but "the correct value is set and verified for each unit." I'd structure it in three layers. First, a requirement that defines the parameter, its permissible range, how the correct value is determined (the rule or calculation that maps unit characteristics to the limit), and the acceptance criterion — this is the traceability anchor to the risk control measure. Second, a manufacturing/production requirement or work instruction that specifies how the value is programmed and how it's verified on the line, with the verification method and pass/fail threshold — because the control is only effective if the value is correctly set, the production verification is part of the control's evidence, not a separate manufacturing concern. Third, a design-verification activity that confirms the *mechanism* works — that the firmware/hardware actually enforces the stored limit — independent of any particular unit's value. In the matrix, I'd link the risk control measure to all three: the parameter requirement, the production verification record, and the design verification of the enforcement mechanism. I'd also address change control and traceability of the value itself — how it's recorded against the unit serial number — so you can demonstrate, for any shipped unit, that its limit was set and verified within the specified range.

**Possible follow-ups:** How would you handle a unit whose computed value falls outside the permissible range — what does the traceability scheme require? / If the enforcement mechanism is verified once at design level, what convinces you each production unit actually enforces its own stored value?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd treat this as a substantive quality issue rather than a documentation dispute, and I'd be careful not to frame it as an accusation of the test engineer — they did the right thing by raising it. The systems engineer's position conflates *link completeness* with *link validity*: a matrix can be structurally complete and still be misleading if the linked evidence doesn't demonstrate the control. My approach would be to gather facts first — pick the flagged tests and actually walk each one against the risk analysis entry it's supposed to verify, checking whether the test setup, stimulus, and acceptance criteria exercise the failure condition. That turns a he-said/she-said into concrete findings. Then I'd bring the systems engineer, test lead, and quality together around those findings, not around opinions, and agree on a disposition: for each flagged test, either confirm it's adequate (and document why), or re-scope/re-write it to actually stress the failure condition, or replace it with a more appropriate method. I'd also want to understand the root cause — was it schedule pressure, a template-reuse habit, or unclear requirements? — because the fix is process, not just re-testing. Finally, I'd add a lightweight check so this doesn't recur: verification activities reviewed against the risk analysis entry, not just against the requirement number. The message I'd set is that "the matrix passes audit" is the floor, not the goal — the goal is that the evidence actually demonstrates the control works.

**Possible follow-ups:** How would you handle it if the re-scoped tests reveal a control that doesn't actually work as the risk analysis assumed? / What would you change in the review process so copied-and-relabeled tests get caught earlier, without adding heavy overhead?
