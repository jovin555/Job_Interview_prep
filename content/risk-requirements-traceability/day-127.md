# risk-requirements-traceability — Day 127

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is a broken semantic link: the requirement exists and is testable, but it doesn't carry the *safety intent* that justifies its existence, so anyone reading the SRS in isolation would see a performance nicety rather than a risk control. I'd fix this at the requirement level first. The firmware requirement should be rewritten or annotated so it explicitly states the hazard it mitigates and the risk control ID it implements — something like "the firmware shall limit the commanded actuator rate of change to X units/s to mitigate hazardous overspeed (RC-0xx)." That gives the traceability matrix a meaningful edge rather than a bare number-to-number link.

From there I'd make sure the trace is bidirectional and complete: hazard → risk control measure → firmware requirement → design element (the specific module/function that implements the clamp) → verification activity. The verification activity is the part people get wrong. A test that confirms "the clamp works under nominal command inputs" is necessary but not sufficient — the test should also demonstrate that *without* the clamp the hazardous condition is reachable, or at minimum that the clamp holds under worst-case command transients and at the boundary of the rate limit. Otherwise you can't show the control is actually doing safety work.

I'd also add a note in the risk management file pointing to the requirement ID and the verification record, so the link is navigable from both directions. The practical test I apply: if a new engineer picked up either document cold, could they find the other end of the link and understand *why* the control exists? If not, the traceability is cosmetic.

**Possible follow-ups:**
- If the firmware requirement is rewritten to reference the hazard, how do you handle the fact that the same clamping function might also serve a purely performance purpose (e.g., mechanical wear reduction) — does it get two traceability parents?
- How would you verify the rate limiter's behavior at the exact boundary of the limit, and what acceptance criterion would you write so the test is objectively pass/fail rather than "looks about right"?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap with a distributed control is that the risk analysis credits one control, but the implementation is spread across three owners, and if you trace the single control to a single requirement you lose the fact that its effectiveness depends on all three elements behaving correctly *together*. I'd decompose the control into its constituent parts for traceability purposes while keeping the risk analysis entry as the single parent.

Concretely: the risk control measure (RC-0xx) stays one entry in the risk file, but it gets child links to each contributing element — a hardware requirement for the sensor's accuracy and response time, a firmware requirement for the PID behavior and its output limits, a hardware requirement for the power switch's ability to actually interrupt the heater. Each of those has its own verification. Then, critically, there's an *integration* verification at the system level that exercises the whole loop under a fault or over-temperature condition, because the individual verifications can all pass while the loop as a whole fails to hold the safe range — for example, if the sensor is accurate but the PID output saturates, or the switch works but the firmware never commands it off.

I'd also document the assumptions the risk analysis makes about each element — independence, response time budget, failure modes — because those assumptions are what make the single-control credit valid. If the sensor and the switch share a power rail, for instance, that's a common-cause consideration the traceability should surface, not hide.

**Possible follow-ups:**
- How would you allocate a timing budget (e.g., "heater de-energized within 500 ms of over-temperature") across the sensor, the firmware loop period, and the switch response, and where would you document that allocation?
- If the integration test passes but one of the constituent element tests is later found to be inadequate, how does your traceability scheme let you find every other control that depends on that element?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can absolutely be legitimate verification evidence for certain kinds of controls — layout rules, derating, creepage, things that aren't practically testable — but only if the review actually examines the specific failure condition the control addresses. A generic checklist that happens to touch the same subsystem is not evidence; it's a coincidence of scheduling. So the first thing I'd do is check whether the review, as conducted, produced any objective record that the control's failure condition was assessed. Usually it didn't, which means the trace is formally present but evidentially empty.

The fix is to make the review criteria control-specific. I'd add explicit review items derived from the risk control — "confirm the power supply's overvoltage clamp trips below the downstream component's absolute maximum, including tolerance and temperature drift" — so the reviewer has a concrete question to answer and the record shows it was answered. That converts the review from a general design sanity check into targeted verification of the control. If the control genuinely can't be assessed by review (because it needs to be exercised), then the trace is pointing at the wrong verification method and needs to be re-linked to a test or analysis.

I'd also make the acceptance criterion for the review item measurable where possible — a specific margin, a specific calculation to be checked — rather than "reviewed and found acceptable," which is the phrase that makes auditors and good reviewers both uneasy.

**Possible follow-ups:**
- How would you distinguish, in the traceability matrix, between a review that *verifies* a control and a review that merely *informs* the design, so the two aren't conflated?
- If the review has already been completed and signed off with the generic checklist, what's your path to closing the gap without invalidating the existing record?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a piece of design at all — it's a *value*, and the traceability has to cover not just the requirement but the production process that sets and confirms the value. I'd structure it in three layers. First, a design requirement that defines the parameter, its permissible range, its resolution, and how the firmware uses it — that's the design-side trace. Second, a manufacturing/production requirement that specifies how the value is programmed, how it's verified after programming, and what the acceptance tolerance is — because a correct design with a mis-programmed value is an uncontrolled hazard. Third, a verification activity that confirms both: that the firmware correctly enforces the limit at the programmed value, and that the production test actually catches an out-of-range or missing value.

The per-unit variability is the interesting part. The traceability has to make clear that the control's effectiveness is unit-specific, so the evidence is per-unit production records rather than a single design verification. I'd link the risk control to the production test specification and to a sample of unit records, and I'd make sure the design verification includes testing at the extremes of the permissible parameter range — not just a nominal value — because the control has to hold across every value that can legitimately be programmed.

I'd also want a defined behavior for the failure case: what does the firmware do if the parameter is absent, corrupt, or out of range? That's a risk control in its own right and needs its own trace.

**Possible follow-ups:**
- How would you handle a service port that allows the parameter to be changed in the field — does that create a new hazard that needs its own risk control and trace?
- What evidence would you present to an auditor to show that the manufacturing-set parameter is actually controlled, as opposed to just documented?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file, the SRS, and the verification plan are each internally consistent and each passes its own review — but when you trace across all three, you find that a risk control measure is linked to a requirement that is linked to a test, and the test passes, yet the *combination* doesn't actually demonstrate the control works, because the requirement was written at a level of abstraction the test can satisfy without exercising the control's failure condition. The three document owners each argue their document is correct. How would you handle this?

**Answer:** The first thing I'd do is reframe the disagreement, because all three owners are actually right about their own documents — the problem is at the seams, and none of them owns the seam. So I wouldn't try to win an argument about whose document is wrong; I'd get the three of them in a room with the specific trace in front of them and walk the chain end to end: here's the hazard, here's the control, here's the requirement that's supposed to implement it, here's the test that's supposed to verify it. Then I'd ask one question: *if the control were removed or broken, would this test fail?* If the answer is no, the chain is broken regardless of what any individual document says, and that's a shared problem to solve rather than a blame allocation.

From there the fix is usually at the requirement — it's too abstract, so the test can pass without touching the failure condition. I'd have the requirement rewritten with a measurable acceptance criterion tied to the control's actual failure mode, then have the test re-derived from that criterion rather than patched. I'd also want to understand *how* the seam got missed, because it's usually a process gap: requirements written without the risk analyst in the loop, tests written from requirements without the risk file in view. A lightweight fix is to require that any requirement tagged as a risk control gets a second review by someone who has read the risk analysis entry — that closes the loop without adding heavy process.

Throughout, I'd keep it non-adversarial. The goal is a chain that actually demonstrates the control works, and framing it as "we all own this gap together" gets there faster than adjudicating whose document is at fault.

**Possible follow-ups:**
- How would you prevent this class of seam failure from recurring on the next project without adding so much process that people route around it?
- If the test can't be made to fail when the control is disabled — because the failure condition is hard to induce on the bench — what alternative evidence would you accept, and how would you document that decision?
