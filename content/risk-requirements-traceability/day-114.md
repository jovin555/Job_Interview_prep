# risk-requirements-traceability — Day 114

## Q1: How would you approach establishing traceability between a risk control measure and its verification activity when the control is implemented as a *firmware-based timeout* — for example, firmware that disables a motor output if no valid sensor reading arrives within a bounded window — and the firmware requirement only states the timeout value and the disable action, without referencing the hazard it mitigates?

**Answer:** The gap here is that the firmware requirement is written purely functionally — it describes *what* the code does but not *why it exists as a safety measure*. The first step is to make the safety intent explicit at the requirement level: either amend the firmware requirement to carry a reference to the risk control ID it implements, or add a derived safety requirement that states the hazard (e.g., "loss of valid sensor data shall not result in continued motor actuation") and links down to the functional timeout requirement. That gives a clean two-level chain: hazard → risk control measure → safety requirement → functional firmware requirement → verification test.

For the verification activity, the key question is whether the test actually exercises the *failure condition* the control is meant to mitigate — i.e., does it simulate the absence of valid sensor readings and confirm the motor is disabled within the specified window, including the worst-case timing? A test that merely confirms the timeout constant is set correctly in code is not sufficient evidence. I'd want the test to inject the fault (stop the sensor data stream, or feed invalid frames) and measure the actual disable latency against the requirement's acceptance criterion, on production-representative hardware where the timing depends on interrupt latency and scheduler behavior.

Finally, I'd make sure the traceability matrix shows the full bidirectional path: the risk control measure links to the safety requirement, which links to the functional requirement, which links to the test, and the test's acceptance criterion is traceable back to the timing budget in the risk analysis. That way an auditor can walk from hazard to evidence without guessing.

**Possible follow-ups:**
- If the timeout value itself was chosen based on a timing analysis rather than a test, how would you trace that analysis as part of the verification evidence?
- What would you do if the firmware requirement had already been baselined and changing it would trigger a re-review of the whole SRS?

## Q2: How would you approach creating a traceability scheme when a single risk control measure is implemented as a *distributed control loop* — a hardware sensor, a firmware control algorithm, and a hardware power switch each contributing to keeping an actuator within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The core problem is that the risk analysis credits a single control, but the control has no single owner and no single requirement — it's an emergent property of three subsystems working together. If you trace the risk control measure to only one of the three elements, you lose the others; if you trace it to all three without structure, the matrix becomes ambiguous about what "verified" means.

My approach is to decompose the control into its constituent functions while preserving the top-level link. I'd create a system-level safety requirement that describes the *integrated* behavior — e.g., "the actuator shall remain within the safe operating range under all specified conditions" — and trace the risk control measure to that. Then I'd derive sub-requirements for each element: the sensor's accuracy and response time, the control algorithm's stability and saturation behavior, and the power switch's ability to interrupt the actuator independently. Each sub-requirement traces to its own verification activity, and the system-level requirement traces to an integration test that exercises the loop as a whole.

The critical point is that the integration test must be more than the sum of the subsystem tests — it has to demonstrate the loop behaves safely when the elements interact, including at the boundaries where one element's behavior affects another's (sensor lag feeding into the control algorithm, for instance). I'd also explicitly capture the *assumptions* the risk analysis makes about each element — e.g., "the power switch can interrupt the actuator independent of firmware state" — as requirements in their own right, because if an assumption fails, the whole control fails even though every individual test passed.

**Possible follow-ups:**
- How would you handle the case where the integration test passes but a subsystem test fails — does the control count as verified?
- If the three elements are owned by three different teams, how would you keep the traceability links coherent as each team revises its own requirements?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — a general "power supply design review" checklist, for example — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** This is a common failure mode: the traceability link exists on paper, but the verification activity isn't actually capable of detecting whether the control works. A design review is legitimate verification evidence for some kinds of controls — particularly those that are design-rule-based or that can't be practically tested — but only if the review criteria explicitly address the control's failure condition.

My first step would be to examine the review checklist against the risk control measure and identify the specific gap: what failure condition is the control meant to mitigate, and does any checklist item require the reviewer to assess whether that condition is addressed? If not, the review as conducted is not adequate evidence, regardless of the traceability link.

The remedy is to either amend the checklist to include a targeted item for that control — phrased in terms of the failure condition, not the general design area — or to add a supplementary verification activity that does address it. If the control is genuinely review-verifiable (e.g., a creepage distance or a derating margin), a focused review with explicit criteria is appropriate and efficient. If it's not — if the failure condition is behavioral and only manifests under fault conditions — then a review was the wrong verification method to begin with, and a test or analysis should be added.

I'd also want to understand *why* the link was made to a generic review in the first place. Often it's because the review was already scheduled and someone needed to close a traceability gap quickly. That's a process signal worth addressing: verification method selection should be driven by the nature of the control, not by what's already on the calendar.

**Possible follow-ups:**
- How would you distinguish between a control that is genuinely review-verifiable and one where a review is being used as a shortcut?
- If the review has already been completed and signed off, what's the minimum you'd need to do to close the gap without invalidating the existing record?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a piece of code — it's a *value*, and the traceability has to cover not just the design but the manufacturing and service lifecycle. The risk analysis credits the parameter as the control, so the traceability scheme needs to demonstrate that the parameter is correctly determined, correctly programmed, and correctly verified on every unit.

I'd structure it in three layers. First, a design-level requirement that defines the parameter's valid range and the rationale for the limit — this traces to the risk control measure and to the analysis that established the safe value. Second, a manufacturing requirement that specifies how the value is computed or selected for each unit, how it's written to non-volatile memory, and how it's read back and verified — this traces to the production test procedure. Third, a verification activity that confirms the programmed value is within the valid range and that the unit actually enforces the limit — ideally a functional test at end-of-line that drives the output to the limit and confirms the clamp engages.

The tricky part is unit-to-unit variation: if the value can differ between units, the traceability has to show that the *range* is controlled, not just a single nominal value. I'd want the manufacturing record for each unit to capture the programmed value, and the traceability matrix to link the parameter's valid range to the risk analysis, the programming procedure, and the end-of-line verification. I'd also consider what happens if the parameter is later changed in the field — is there a service procedure, and does it have its own verification? If so, that's a fourth traceability path that needs to be captured.

**Possible follow-ups:**
- How would you handle a unit that fails the end-of-line limit test — is that a manufacturing nonconformance, a design issue, or both, and how does the traceability scheme reflect that?
- If the parameter can be reprogrammed in the field, how would you keep the traceability evidence current for units already in service?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file, the SRS, and the verification plan are each internally consistent and each passes its own review — but when you trace across all three, you find that a risk control measure is linked to a requirement that is linked to a test, and the test passes, yet the *combination* doesn't actually demonstrate the control works, because the requirement was written at a level of abstraction the test can satisfy without exercising the control's failure condition. The three document owners each argue their document is correct. How would you handle this?

**Answer:** The first thing I'd do is reframe the disagreement so it isn't about whose document is wrong. Each owner is technically correct — their document is internally consistent — and that's exactly the problem: the defect lives in the *links between* the documents, which no single owner is responsible for. I'd make that explicit up front, because otherwise the conversation becomes defensive and nobody wants to own the gap.

Then I'd walk the chain concretely with all three owners in the room: start at the risk control measure, read its stated intent and the failure condition it's meant to mitigate, then read the requirement aloud, then read the test procedure and its acceptance criterion. The question I'd put to the group is simple: "If the control were absent or broken, would this test fail?" If the answer is no — or if nobody can say with confidence — the chain is broken regardless of what the matrix shows. Making that concrete, with the actual documents in front of everyone, usually dissolves the "my document is correct" position because the gap becomes visible rather than abstract.

For the fix, I'd treat it as a requirement-quality issue first: the requirement needs to be rewritten so its acceptance criterion is tied to the failure condition, not to a nominal behavior the test can satisfy trivially. Then the test gets revised to actually stress that condition — including a negative check where the control is disabled or the fault is injected, to prove the test is capable of detecting the failure. I'd re-run the trace and confirm the chain now holds end to end.

Process-wise, I'd add a cross-document trace review to the design review cycle — a session specifically for walking hazard-to-test chains, owned jointly rather than by any single document owner — so this class of gap gets caught before it reaches an audit. And I'd be careful not to frame it as anyone's failure: the structure allowed the gap, and the fix is structural as much as technical.

**Possible follow-ups:**
- How would you handle it if the requirement owner agrees to rewrite the requirement but the test owner says re-running the test would blow the verification schedule?
- What would you do if this same pattern turned up on several other controls — is it a one-off or a systemic issue, and how would you tell the difference?
