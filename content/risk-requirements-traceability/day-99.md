# risk-requirements-traceability — Day 99

## Q1: How would you approach tracing a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement exists and is testable, but the *safety intent* has been stripped out — the requirement reads like a performance feature ("the commanded rate of change shall not exceed X units/s") rather than a risk control. That's a traceability defect even though every link technically resolves, because a future engineer reading the SRS has no way to know that loosening the clamp, or refactoring the code path that applies it, could remove a credited control.

My approach would be to fix the linkage at the requirement level rather than papering over it in the matrix. First, I'd add an explicit safety-annotation to the firmware requirement — either a derived-requirement flag with a reference to the risk control ID, or a companion "safety requirement" entry that states the hazard it mitigates and the failure condition it guards against. The functional requirement can stay as-is for implementation purposes, but it must carry a pointer to the risk control so the two are bidirectionally linked. Second, I'd make sure the risk management file's entry for the control references the specific firmware requirement ID, so the path is complete in both directions: hazard → risk control → firmware requirement → design element (the clamp function) → verification test.

The verification side needs scrutiny too. A test that confirms "the clamp limits rate of change to X under nominal command inputs" is necessary but not sufficient — the risk analysis credits this control against overspeed, so the test should also demonstrate the clamp holds under the conditions that could produce overspeed: a step command, a corrupted command stream, a command that arrives faster than the control loop can process. I'd want the acceptance criterion expressed as a measurable bound (maximum rate observed over the test, with margin to the hazardous threshold) rather than "clamp functions correctly."

Finally, I'd check whether the clamp is the *only* control against overspeed or one of several. If it's the sole credited control, the traceability needs to be airtight and the verification rigorous; if there's a redundant hardware limit, the traceability can note the redundancy and the verification burden can be shared. Either way, the fix is the same: restore the safety intent to the requirement text and make the matrix reflect it.

**Possible follow-ups:**
- If the firmware team argues that adding safety annotations to every requirement clutters the SRS, how would you decide which requirements get them?
- How would you verify the clamp actually holds when the command source is a communication bus that could deliver malformed or out-of-order messages?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The difficulty with a distributed control loop is that the risk analysis credits an *emergent* property — the loop keeps temperature within a safe band — but no single element owns that property. The sensor can be accurate and the PID can be well-tuned and the switch can be functional, and the loop can still fail to hold the band if, say, the sensor's response time is too slow for the loop's gain, or the switch's switching latency eats into the control margin. So tracing the control to any one component's requirement is misleading.

I'd handle this by decomposing the loop into an allocated set of sub-requirements, each owned by one element, with the *allocation rationale* documented. The risk control entry in the risk management file stays as the single top-level control, but it traces down to a small set of allocated requirements: sensor accuracy and response time, PID loop update rate and output limits, switch response time and failure mode. Each allocated requirement traces to its design element and its verification activity. The key discipline is that the allocation must be justified — there should be a short analysis (a budget, a timing calculation, a control-loop stability argument) showing that if each element meets its allocated requirement, the loop as a whole meets the safe-band requirement. That analysis is itself a verification artifact, and it's what makes the decomposition legitimate rather than arbitrary.

Then there's an integration-level verification: a test of the loop as a whole, under conditions that stress the interaction — sensor drift, a step change in load, a switch that's slower than nominal. This is where you catch the failure modes that no single-element test can see. The traceability matrix should show the top-level control linking both to the allocated requirements *and* to the integration test, so an auditor can see that the emergent property was verified, not just assumed from the parts.

The failure mode I'd watch for is the team verifying each element in isolation, declaring each "pass," and never testing the loop. That's a classic gap in distributed-control traceability, and it's exactly the kind of thing a good design review should catch.

**Possible follow-ups:**
- How would you document the allocation rationale so it survives a design change to one element — say, swapping the sensor for a slower one?
- If the integration test fails but every element passes its own requirement, how would you diagnose which allocation was wrong?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** This is a subtle but common traceability failure: the link exists, the review happened, the box is checked, but the review was never *about* the risk control. A general power-supply checklist might cover topology, derating, thermal margin, and EMI — none of which necessarily probe the specific failure condition the risk control is meant to mitigate. So the traceability is formally complete and substantively empty.

My first move would be to make the gap visible: pull the risk control's failure condition out of the risk analysis and ask, concretely, "did this review assess whether the design prevents/mitigates *this*?" If the answer is no, the review is not adequate evidence, regardless of what the matrix says. I'd rather surface that in a design review than have it found in an audit.

The fix has two parts. First, the review itself needs a risk-control-specific criterion. That doesn't mean rewriting the whole checklist — it means adding a targeted review item, or a short dedicated review, that states the failure condition and asks the reviewers to assess the design against it. The review record should capture the specific question asked and the specific answer, not just "reviewed, no issues." Second, the traceability matrix should distinguish between a review that *incidentally* touches the control and a review that *explicitly* assesses it — I'd want the link to point to the review record that contains the explicit assessment, so the evidence is unambiguous.

There's a broader lesson here about review-based verification generally: a design review is legitimate verification evidence only when its criteria are specific enough that a reviewer could fail the design against them. A checklist item like "power supply is adequately designed" is not a criterion; "the supply maintains output within tolerance under the worst-case load transient defined in the risk analysis" is. I'd push for that level of specificity wherever a review is the credited verification method.

**Possible follow-ups:**
- How would you retrofit risk-control-specific criteria into an existing review process without making every review enormous?
- If the review already happened and the gap is discovered afterward, is a supplementary review acceptable evidence, or does the original review need to be redone?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the "control" isn't a circuit or a piece of code — it's a *value*, and the value is established by a manufacturing process rather than by design. That breaks the usual assumption that a risk control traces to a design element and a design verification test. The control has three distinct things that need tracing: the parameter's *definition and allowable range* (a design concern), the *process that sets it correctly* (a manufacturing concern), and the *mechanism that enforces it at runtime* (a firmware/hardware concern). Each needs its own requirement and its own verification.

I'd structure it as follows. In the risk management file, the control is stated as "output current is limited to a value within the safe range defined by [analysis]." That traces to a design requirement specifying the parameter, its allowable range, its storage location, and the firmware behavior that reads and enforces it. It also traces to a *manufacturing requirement* — the process spec that defines how the value is programmed, the acceptable tolerance, and the verification step at end-of-line. And it traces to a runtime requirement — the firmware must read the parameter and enforce it, and must behave safely if the parameter is missing, out of range, or corrupted.

Verification then splits accordingly: design verification confirms the firmware enforces a given parameter value correctly (test with a range of programmed values, including boundary and out-of-range); manufacturing verification confirms each unit is programmed within tolerance (an end-of-line test, with records); and there's a system-level check that the enforced limit matches the programmed value on production-representative units. The traceability matrix needs to show all three paths, because an auditor will ask "how do you know unit #4,732 has the right limit?" and the answer has to be a manufacturing record, not a design test.

The failure mode I'd guard against is treating the parameter as a design detail and forgetting the manufacturing link entirely — the design is correct, the firmware is correct, but a programming error or a drifted calibration at the factory silently defeats the control on some units. That's why the manufacturing requirement and its end-of-line verification have to be first-class citizens in the traceability scheme, not an afterthought.

**Possible follow-ups:**
- How would you handle a parameter that can be changed in the field via a service port — does that change the traceability or the verification approach?
- If the parameter is stored in non-volatile memory, how would you verify the control still holds after a memory corruption event?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The systems engineer is technically right that the matrix is compliant and the tests pass, and that's exactly what makes this dangerous — the artifacts look complete, so the gap won't be caught by an audit or a document review. It'll be caught by a patient, or by a field failure, or by a regulator who asks a pointed question. My job is to treat the test engineer's disclosure as credible and act on it before it becomes someone else's problem.

First, I'd thank the test engineer and make clear that raising this was the right thing to do — the instinct to protect the schedule by not asking hard questions is the real risk here, and I don't want to punish the person who broke that silence. Then I'd verify the claim rather than take it on faith: pick two or three of the flagged tests and walk through them against the risk analysis entry they're supposed to verify. Does the test setup reproduce the failure condition? Does the stimulus actually drive the system into the state the control is meant to guard against? Does the acceptance criterion distinguish "control worked" from "control was never exercised"? In most copied-test cases, the tell is that the test passes trivially because the failure condition is never reached.

With evidence in hand, I'd sit down with the systems engineer and the test lead together — not to assign blame, but to reframe the question. The matrix being compliant isn't the goal; the goal is that the evidence actually supports the claim that the control works. A test that passes without exercising the failure condition is not evidence, it's a placeholder. I'd propose a targeted re-verification: identify the affected tests, rewrite them against this project's actual failure conditions, and re-run. If the schedule is tight, I'd prioritize by risk — the controls guarding the highest-severity hazards get re-verified first, and I'd document the prioritization and the plan so the decision is transparent rather than silent.

I'd also want to understand *why* it happened, because copied tests are usually a symptom of schedule pressure or a test process that rewards coverage counts over evidence quality. If the team was under pressure to close out verification, fixing three tests won't fix the next three. That's a conversation with the program manager about how verification is planned and resourced, and it's worth having even if it's uncomfortable.

Finally, I'd make sure the correction is reflected in the traceability records — the re-verified tests link to the same risk controls, with the new test IDs and the rationale for the change documented, so the audit trail shows what happened and why. The matrix ends up not just compliant but honest, which is the point.

**Possible follow-ups:**
- How would you handle it if the systems engineer escalates and argues you're creating unnecessary rework based on one engineer's informal claim?
- What would you change in the verification planning process to make copied-and-relabeled tests less likely in the first place?
