# risk-requirements-traceability — Day 4

## Q1: How would you approach determining whether a risk control measure should be documented as a separate requirement in the SRS versus being captured only in the risk management file?

**Answer:** This is a common tension point in medical device development, and the answer depends on whether the risk control measure imposes a design constraint that must be verifiable independently. My general framework is: if the risk control measure results in a specific design feature, parameter, or behavior that can be objectively verified (e.g., "the device shall shut down within 100ms of detecting over-temperature"), it should be a requirement in the SRS with bidirectional traceability to the hazard it mitigates. If the risk control is implemented through a design practice or standard that is inherently verified by compliance to that standard (e.g., "all PCB creepage distances shall comply with IEC 60601-1 Table 15"), it can remain in the risk management file with a reference to the applicable standard, and verification occurs through the design review process or compliance checklist rather than a functional test. The key is that every risk control measure must have some form of verification — the question is where that verification lives. I would document the rationale for this decision in the risk management file so that auditors can see the traceability logic.

**Possible follow-ups:** How would you handle a risk control measure that is partially implemented by a design rule and partially by a functional requirement? What if a design-rule-based risk control is later challenged by a regulatory auditor who expects a functional test?

## Q2: During a design verification campaign, you find that a requirement derived from a risk control measure passes testing, but the test method does not actually stress the system under the fault conditions identified in the DFMEA. How would you address this gap?

**Answer:** This is a serious traceability failure because the verification activity doesn't match the risk scenario it's supposed to cover. I would immediately flag this as a non-conformance and initiate a formal investigation. First, I'd review the DFMEA to confirm the specific fault condition, its severity, and the intended risk control mechanism. Then I'd examine the test specification to understand why the test method diverged — was it an oversight in the traceability matrix, a misinterpretation of the requirement, or a practical limitation of the test lab? If the test method can be corrected (e.g., by adding a fault injection step), I'd update the test protocol and re-run. If the fault condition cannot be safely or practically reproduced in a test environment (e.g., a catastrophic failure mode that would destroy the device), I would document the rationale and seek alternative verification methods, such as analysis (FEA, simulation) or inspection of design documents. Crucially, I would update the traceability matrix to reflect the actual verification method used and ensure the risk management file acknowledges any residual uncertainty. This situation also warrants a review of other risk-related test cases to catch similar gaps before they reach regulatory submission.

**Possible follow-ups:** Who would you involve in the decision to accept an analysis-based verification instead of a physical test? How would you document this change for a regulatory auditor?

## Q3: How would you design a traceability scheme that connects a single system-level hazard to multiple risk control measures distributed across hardware, firmware, and mechanical subsystems, and then traces each control measure to its verification activity?

**Answer:** I would structure this as a hierarchical traceability model starting from the hazard analysis. Each identified hazard gets a unique ID in the risk management file. For that hazard, I list all risk control measures — these might include hardware-based controls (e.g., a hardware watchdog timer), firmware-based controls (e.g., a software timeout), and mechanical controls (e.g., a physical barrier). Each control measure gets its own ID and is linked back to the hazard. Then, each control measure is translated into one or more requirements in the SRS, with the requirement ID explicitly referencing the control measure ID. For example, "REQ-123 (derived from RCM-045): The firmware shall assert the watchdog timer within 50ms of any communication timeout." These requirements then trace forward to verification activities — a hardware control might be verified by a test case, a firmware control by a unit test or integration test, and a mechanical control by a dimensional inspection. The traceability matrix would capture these multi-level relationships: Hazard → Risk Control Measure → SRS Requirement → Verification Activity. I would also include a column for the verification method type (test, analysis, inspection, demonstration) so that reviewers can quickly assess whether the verification approach is appropriate for the risk severity.

**Possible follow-ups:** How would you handle a situation where a single verification activity covers multiple risk control measures from different subsystems? What if a risk control measure is implemented redundantly across hardware and firmware — how would you trace both paths?

## Q4: (Behavioral) Imagine you're leading a project where the hardware team has completed a DFMEA and identified several risk control measures, but the firmware team has not yet started their own DFMEA. The project schedule is tight, and the program manager wants to proceed with design verification based only on the hardware DFMEA, arguing that firmware failures are "just software bugs" and don't need formal risk analysis. How would you handle this?

**Answer:** I would respectfully but firmly push back on this approach, because firmware failures in a medical device can absolutely create hazardous situations — a software timing error, a stack overflow, or a corrupted sensor reading can all lead to patient harm. I would first acknowledge the schedule pressure and the program manager's desire to move quickly, then explain that proceeding without a firmware DFMEA creates a significant regulatory risk: an IEC 60601 or ISO 14971 auditor will expect to see that all potential failure modes — including software-related ones — were systematically analyzed and mitigated. I would propose a pragmatic compromise: rather than waiting for a full, formal firmware DFMEA, we could run a rapid, focused firmware hazard analysis workshop (2-3 half-day sessions) that identifies the highest-risk firmware failure modes and their controls. This would give us enough traceability to proceed with verification planning for the critical paths, while the full firmware DFMEA could be completed in parallel. I would also offer to facilitate the workshop myself, drawing on my experience with firmware-hardware interactions from previous projects. The key is to show that I'm not blocking progress — I'm protecting the project from a costly rework or submission rejection later.

**Possible follow-ups:** How would you convince a firmware engineer who has never done a DFMEA to participate meaningfully? What if the program manager insists on a cost-benefit analysis showing the risk of delaying versus the risk of skipping the firmware DFMEA?

## Q5: How would you approach verifying that a risk control measure implemented in firmware (e.g., a software-based timeout that disables a motor if no valid sensor reading is received within 200ms) is correctly traced through to the system-level hazard it mitigates, and that the verification test adequately covers the failure scenario?

**Answer:** I would start by confirming the traceability chain: the hazard (e.g., "uncontrolled motor operation could cause patient injury") should be linked to the risk control measure in the risk management file, and that control measure should be reflected as a verifiable requirement in the SRS (e.g., "the firmware shall de-energize the motor within 200ms of losing valid sensor data"). The verification test must then reproduce the exact fault scenario described in the DFMEA — in this case, a loss of valid sensor data. I would design the test to inject the fault at the sensor interface level, not just simulate it in software. For example, physically disconnecting the sensor or corrupting the communication bus, rather than simply calling a function that returns an error code. The test should also verify timing: the motor must be de-energized within the specified 200ms, measured from the moment the fault occurs. I would also consider edge cases: what happens if the sensor data becomes intermittent (valid, then invalid, then valid again)? Does the timeout reset appropriately? What if the fault occurs during startup or a low-power state? The test protocol should document the pass/fail criteria clearly and include a reference back to the DFMEA failure mode ID. Finally, I would ensure the traceability matrix captures this test case as the verification activity for that specific risk control requirement, and I would review the test results with both the firmware engineer and the systems engineer to confirm the test adequately represents the real-world hazard scenario.

**Possible follow-ups:** How would you handle a situation where the only practical way to inject the fault is through a software simulation, not a physical fault? What if the firmware team argues that the 200ms timeout is already covered by a unit test, but the unit test doesn't test the actual hardware interface?
