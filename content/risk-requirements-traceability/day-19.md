# risk-requirements-traceability — Day 19

## Q1: How would you approach establishing traceability for risk control measures that are implemented through a combination of hardware and firmware, where the hardware team documents the control in their design specification and the firmware team documents their portion in a software requirements document — but neither document references the other, and the risk management file treats the control as a single integrated measure?

**Answer:** The core problem here is that the risk management file treats the control as one integrated measure, but the engineering artifacts treat it as two separate pieces with no link between them. I would start by creating a single "integrated risk control" record in the risk management file that explicitly identifies all contributing elements — the hardware sensor, the firmware decision logic, and the actuator — and assigns each element an identifier that can be referenced from the respective engineering documents. Then I would add cross-references in both directions: the hardware design specification would note that the sensor's output feeds a firmware-based decision (referencing the software requirements document), and the software requirements document would note that its decision logic consumes a hardware-generated signal (referencing the hardware design specification). For verification, I would establish a two-tier approach: each element gets verified at its own level (the hardware sensor's output characteristics, the firmware logic's decision behavior), and then the integrated control gets verified at the system level to demonstrate that the combination actually mitigates the hazard. The key insight is that the traceability doesn't have to live in a single document — it can be distributed across documents, as long as the links are explicit and bidirectional, and the risk management file serves as the index that ties everything together.

**Possible follow-ups:** How would you handle the situation where the hardware and firmware teams use different numbering schemes for their documents? What level of detail would you require in the cross-references — just document names, or specific section/requirement numbers?

## Q2: How would you approach determining whether a risk control measure that is implemented as a firmware-based plausibility check on a sensor reading — for example, rejecting readings that change by more than a specified rate between consecutive samples — needs to be verified on the actual production hardware, or whether testing on a development board with the same microcontroller is sufficient?

**Answer:** The key question is whether the plausibility check's behavior depends on anything that differs between the development board and the production hardware. For a pure firmware algorithm that operates on digital values, the microcontroller is the only hardware dependency, so a development board with the same MCU at the same clock speed might be sufficient — but I would be cautious. The plausibility check's behavior depends on the timing of sensor readings, which is influenced by the sensor interface, the ADC or communication peripheral configuration, and the interrupt timing — all of which could differ between the development board and the production hardware. For example, if the production hardware uses a different sensor with different noise characteristics, or a different ADC reference voltage, the rate-of-change threshold might behave differently. I would approach this by first doing a dependency analysis: identify every hardware element that could influence the plausibility check's behavior — the sensor, the interface, the clock source, the power supply — and then assess whether the development board is representative for each element. If any element differs, I would require verification on production-representative hardware. Even if the development board is representative, I would document the rationale for why it's sufficient, including a comparison of the relevant characteristics, and have that rationale reviewed. For a medical device, the regulatory expectation is that verification evidence reflects the production design, so the default should be production hardware unless there's a well-documented justification for a representative substitute.

**Possible follow-ups:** What specific characteristics would you compare between the development board and production hardware to justify using the development board? How would you handle the situation where the production hardware isn't available yet, but the verification schedule requires testing to start?

## Q3: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system has a distributed architecture — multiple microcontrollers, each running separate firmware, communicating over a shared bus — and a single hazard is mitigated by coordinated actions across multiple nodes?

**Answer:** This is a scenario where the traceability must capture not just the individual actions on each node, but the coordination between them. I would structure the traceability in layers. At the top, the hazard links to the integrated risk control measure, which is defined at the system level — for example, "the system shall shut down the motor within 200ms of detecting an over-temperature condition." This system-level control then decomposes into node-specific responsibilities: Node A detects the condition and broadcasts a shutdown command; Node B receives the command and de-energizes the motor driver; Node C logs the event and alerts the operator. Each node's responsibility becomes a requirement in that node's firmware requirements document, and each requirement traces to the system-level control. The critical piece is the coordination requirement — the bus protocol, the message format, the timing budget, and the failure behavior if a node doesn't respond. I would create an interface control document that specifies the coordination mechanism, and I would trace the coordination requirement to that ICD. For verification, I would test each node's individual responsibility at the node level, but I would also require a system-level integration test that exercises the full chain — Node A detecting the condition, broadcasting, Node B receiving and acting, within the specified timing. The traceability matrix would show the hazard → system-level control → node-specific requirements → verification activities, with the coordination requirement traced to the integration test. The key is that the coordination itself is a requirement, not just an implementation detail, because it's essential to the risk control's effectiveness.

**Possible follow-ups:** How would you handle the situation where one node's firmware is updated and the timing of its response changes, potentially affecting the coordination? How would you trace the bus communication protocol itself — is it a risk control, a requirement, or both?

## Q4: How would you approach handling a situation where a risk control measure is traced to a verification test, but the test was written to verify a *different* requirement and only incidentally exercises the risk control under nominal conditions — so it passes, but it never actually stresses the failure condition the control is meant to mitigate?

**Answer:** This is a common and dangerous gap — the traceability matrix shows a link, but the link is superficial. I would start by reviewing the test procedure against the risk control's failure condition to confirm the gap: does the test actually create the fault condition, or does it just exercise the system under normal operation? If the test doesn't stress the failure condition, the traceability link is invalid, and I would flag it as a verification gap. The fix is to either modify the existing test to include the fault injection, or create a new test specifically for the risk control. I would also look at why this happened — was the traceability link created by matching requirement numbers without reviewing test content? If so, I would implement a review step where each risk control's verification test is reviewed against the failure condition it's meant to mitigate, not just against the requirement text. This review would be part of the test plan approval process, and it would involve both the test engineer and someone familiar with the risk analysis. The deeper issue is that traceability is not just about links — it's about demonstrating that the verification activity provides objective evidence that the control actually mitigates the hazard. A link without meaningful evidence is worse than no link, because it creates a false sense of coverage.

**Possible follow-ups:** How would you handle the situation where the test engineer argues that the existing test is "close enough" and creating a new test would delay the schedule? What documentation would you require to close the gap — a new test procedure, a deviation, or a risk assessment?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has created a traceability matrix that links every risk control measure to a verification activity, but during a review, you discover that several of the verification activities are actually "verification by similarity" — meaning the team is relying on test results from a previous product that used a similar component or design. The quality manager argues that similarity is not acceptable evidence for risk controls, because the previous product wasn't tested under the same conditions. The systems engineer argues that the components are identical, the design is nearly the same, and re-running the tests would waste time and money. How would you resolve this disagreement?

**Answer:** I would start by acknowledging that both sides have valid points. The systems engineer is right that re-running tests for identical components in identical configurations can be wasteful, and the quality manager is right that similarity is often used as a shortcut without proper justification. The resolution is to establish clear criteria for when verification by similarity is acceptable, and then apply those criteria to each specific case. The criteria would include: the components are identical (same manufacturer, part number, and revision); the operating conditions are the same or less stressful (same voltage, temperature, current, and environmental conditions); the surrounding circuitry is the same or the differences don't affect the risk control's behavior; and the previous test results are documented, traceable, and still valid (the previous product wasn't modified in a way that affects the control). For each risk control where similarity is claimed, I would require a written justification that addresses these criteria, and I would have the quality manager review and approve it. If the criteria aren't met, the test must be re-run. I would also distinguish between different types of risk controls — for example, a passive component's derating might be verifiable by similarity if the component and conditions are identical, but an active control that involves firmware behavior would almost certainly require testing on the actual hardware. The key is to move from a binary argument — "similarity is always acceptable" versus "similarity is never acceptable" — to a structured decision process that evaluates each case on its merits.

**Possible follow-ups:** What would you do if the previous product's test results exist but the test conditions weren't fully documented? How would you handle the situation where the quality manager rejects the similarity justification even when the criteria are met — what escalation path would you use?
