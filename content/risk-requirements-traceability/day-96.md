# risk-requirements-traceability — Day 96

## Q1: How would you approach tracing a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the requirement captures the *behavior* but not the *safety intent*, so the traceability link is semantically broken even if a link exists on paper. I'd start by making the safety intent explicit: either amend the firmware requirement to state that the rate limit exists to mitigate a specific hazardous condition (referencing the hazard ID from the risk analysis), or add a derived safety requirement that sits above the functional one and carries the hazard reference. The functional requirement can then trace up to the safety requirement, which traces to the risk control measure, which traces to the hazard. That preserves the clean separation between "what the code does" and "why it must do it," while keeping the chain auditable.

Next, I'd check that the verification activity actually stresses the failure condition — not just that the clamp exists, but that commanding a step change larger than the limit produces a bounded rate of change under worst-case conditions (max load, max command delta, timing at the edge of the control loop period). A test that only confirms "the motor doesn't jump to full speed" under nominal conditions doesn't demonstrate the control works when it matters. I'd also want the acceptance criterion expressed numerically (maximum rate of change in units per second, with tolerance), so the test has an objective pass/fail rather than "behaves as designed."

Finally, I'd add a review gate: any firmware requirement that implements a risk control should be flagged in the SRS with a safety tag, so that future changes to the clamping logic trigger a risk re-assessment rather than being treated as an ordinary performance tweak.

**Possible follow-ups:** If the rate limiter is later tuned for performance reasons (e.g., a less aggressive clamp to improve responsiveness), how would your traceability scheme ensure that change gets routed back through risk management? And how would you handle the case where the same clamping code is reused across two products with different hazard analyses?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** When the risk analysis credits an emergent, loop-level behavior as the control, the traceability scheme has to represent that emergent behavior as a first-class entity rather than pretending one component owns it. I'd introduce a system-level safety requirement that describes the loop's required behavior in measurable terms — for example, "the heating element shall be maintained below temperature T under all specified load and ambient conditions, with the loop responding to a fault within a bounded time" — and trace the risk control measure to that requirement. Then the system requirement decomposes into subsystem requirements: a sensor accuracy and response-time requirement, a firmware control-law and fault-response requirement, and a power-switch de-energization requirement. Each of those traces to its own design element and verification activity, and each also traces back up to the system safety requirement.

The verification strategy then has two layers. At the subsystem level, each element is verified against its allocated portion (sensor accuracy over temperature, firmware response latency, switch drop-out time). At the system level, an integrated test verifies the loop behavior under fault injection — sensor drift, sensor dropout, stuck switch — because the loop-level control can only be demonstrated end-to-end. The traceability matrix needs to show both: the vertical decomposition from the single risk control down to the three elements, and the horizontal links from each element to its verification, plus the integrated system test that closes the loop back to the hazard.

The subtle risk here is that each team verifies its slice and everyone declares victory while the integrated behavior is never tested. I'd make the system-level verification a mandatory, explicitly-owned activity in the verification plan, not an assumed consequence of the subsystem tests.

**Possible follow-ups:** How would you allocate the timing budget across the three elements so that the system-level response-time requirement is provably met? And if the firmware PID loop is later replaced with a different control law, what in your traceability scheme tells you which verification activities must be re-run?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review's criteria are specific enough that a competent reviewer could fail the design on the basis of the risk control's failure condition. A generic checklist doesn't meet that bar — it verifies general design quality, not the specific control. So the first step is to make the gap visible: document that the existing review does not assess the failure condition, and treat the trace as a coverage gap rather than accepting it because "a review happened."

The fix is to either extend the review with explicit, control-specific review criteria — stated as questions a reviewer must answer with evidence, e.g., "confirm the derating margin on component X exceeds the maximum stress defined in the risk analysis, with calculation attached" — or to add a separate focused review or analysis activity dedicated to that control. The acceptance criteria for the review should be written in terms of the failure condition the control mitigates, not in terms of general design practice. The review record then needs to capture the specific evidence (calculation, measurement, or inspection result) rather than a checkbox.

I'd also look at whether the review is the *right* method at all. Some controls genuinely can only be assessed by review or analysis (derating, creepage distances, worst-case timing), and that's fine — but the review must be purpose-built for the control. Others might be better served by a test. The decision should be driven by which method produces objective evidence that the failure condition is actually mitigated.

**Possible follow-ups:** How would you word review criteria so they're auditable — what does "objective evidence" look like in a design review record? And if the review is extended, how do you ensure the reviewer has the competence to assess that specific failure condition?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a line of code — it's a *value*, and the traceability has to cover the value's definition, its programming, and its verification on the unit. I'd model it with three linked artifacts. First, a safety requirement that defines the parameter's permitted range and the rationale (derived from the risk analysis: the current limit exists to prevent a hazardous condition, and the range is bounded by the worst-case load and the component ratings). Second, a manufacturing specification that defines how the value is computed or selected, how it's written to non-volatile memory, and how it's read back and confirmed. Third, a verification activity — which in this case is a production test, not a design verification test — that confirms each unit's programmed value falls within the permitted range and that the readback matches what was written.

The traceability matrix then has an unusual shape: the risk control traces to the safety requirement, which traces to the manufacturing spec and to the production test procedure, and the production records become the objective evidence per unit. I'd also want a design-level verification that the *mechanism* works — that the firmware actually enforces the stored limit, that the memory can't be corrupted or bypassed, and that an out-of-range value is rejected at boot — because the per-unit production test only confirms the value was programmed, not that the enforcement path is sound.

The key discipline is distinguishing design verification (does the parameter mechanism work?) from production verification (was this unit programmed correctly?), and making sure both appear in the traceability scheme with the right evidence type. A common failure is to trace the control only to the production test and never verify the enforcement logic.

**Possible follow-ups:** How would you handle a unit that fails the production readback check — what does the disposition path look like, and how is it captured in traceability? And if the permitted range is later widened, what triggers re-verification of the design-level enforcement mechanism versus just updating the production limit?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The matrix being complete and the tests passing is exactly the failure mode traceability is supposed to prevent — links that exist structurally but don't carry meaning. I'd treat the test engineer's disclosure as a serious quality signal and act on it rather than letting it sit. First, I'd verify the claim myself on a sample: pick two or three of the flagged tests, read the test procedure against the risk analysis entry, and check whether the test setup, stimulus, and acceptance criteria actually correspond to the failure condition. That gives me evidence rather than hearsay before I raise it.

Then I'd frame the conversation with the systems engineer around *intent*, not compliance. The matrix is a map; if the tests don't exercise the failure conditions, the map is wrong regardless of what the audit sees. I'd propose a focused review: for each risk control, the test owner walks through how the test stresses the specific failure condition, and where it doesn't, the test gets rewritten or a new one added. I'd also want to understand *why* it happened — copied tests usually mean schedule pressure, unclear test-writing ownership, or acceptance criteria that were too vague to write a real test against — because fixing the individual tests without fixing the cause just moves the problem to the next project.

On the disagreement itself, I'd avoid framing it as "the systems engineer is wrong." I'd frame it as a shared risk: if a notified body or auditor probes one of these tests and finds it doesn't exercise the failure condition, the whole verification package loses credibility. That reframes the conversation from compliance-box-ticking versus rigor into a shared interest in defensible evidence. If the systems engineer still resists, I'd escalate with the evidence in hand — but the goal is to get the tests fixed, not to win the argument.

**Possible follow-ups:** How would you prevent copied tests from entering the verification package in the first place — what gate would you add to the test review process? And if the schedule doesn't allow rewriting all the flagged tests before a milestone, how would you prioritize which ones must be fixed first?
