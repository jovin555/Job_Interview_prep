# risk-requirements-traceability — Day 122

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the requirement captures *what the code does* but not *why it exists*, so the safety intent is invisible to anyone reading the SRS in isolation. I'd start by treating the risk analysis entry as the anchor and working outward in both directions. First, I'd add an explicit safety-derived requirement — or amend the existing one — so it states the hazard it mitigates, the failure condition it guards against, and a measurable acceptance criterion (maximum rate of change, tolerance, and the response behavior when the limit is hit). The functional clamping requirement can remain as a design-level requirement, but it should be linked *upward* to the safety requirement rather than standing alone. Second, I'd establish the trace chain: hazard → risk control measure → safety requirement → design element (the specific firmware module and the parameter that sets the limit) → verification activity. The verification needs to actually stress the failure condition — commanding a step change that would exceed the limit and confirming the output ramps rather than jumps — not just confirm the clamp exists in code review. Third, I'd make the linkage bidirectional so that if the rate-limit parameter is ever changed, the trace back to the hazard is visible and triggers a risk re-evaluation. The practical discipline here is a rule that any requirement implementing a credited risk control must carry a reference to the risk ID; that single convention closes most of this gap.

**Possible follow-ups:** If the rate limiter is one of several controls against the same hazard, how do you decide whether the verification must demonstrate the limiter alone is sufficient, or only that it contributes? And how would you handle the case where the rate limit is a tunable parameter that can be changed post-market?

## Q2: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a line of code but a *value*, so the traceability has to cover three distinct things: the parameter's definition and allowable range, the process that programs it, and the verification that the programmed value is correct on each unit. I'd structure it so the risk analysis credits a control like "output current shall not exceed the configured limit," and that maps to a requirement specifying the parameter, its permitted range, its resolution, and the consequence of an out-of-range value. From there the trace branches: one path goes to the *design element* (the firmware that reads the parameter and enforces it, plus the non-volatile storage), and another goes to the *manufacturing/production control* — the programming step, the guardrails that prevent an out-of-range value being written, and the per-unit or sample-based verification that reads back the value. The key insight is that the verification activity for a manufacturing-set parameter is usually a production test, not a design verification test, so the traceability matrix needs a column or link type that distinguishes design verification from production verification. I'd also capture the linkage between the parameter range and the risk analysis so that widening the range is visibly a risk-relevant change. Finally, I'd make sure the trace records that units can legitimately differ, so an auditor doesn't flag unit-to-unit variation as nonconformity — the control is the *range and the enforcement*, not a single fixed number.

**Possible follow-ups:** How would you handle a parameter that is set at manufacturing but can later be adjusted in the field by service personnel? And what evidence would you expect the production test to retain to close the trace?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** The trace link exists, but it's a false link — the review happened, but nothing in it demonstrates the control works against its specific failure condition. I'd treat this as a coverage gap rather than a documentation cleanup. First, I'd confirm the diagnosis by reading the review record against the risk control's failure condition and showing concretely that the checklist items don't address it. Then I'd decide the remedy based on what kind of control it is: if the control is genuinely review-verifiable (a creepage distance, a derating margin, a layout rule), the right fix is to add a *specific* checklist line item that names the failure condition and the acceptance criterion, and re-run that portion of the review with the risk entry in hand. If the control is functional and the review was never an adequate verification method in the first place, the fix is to add a proper test or analysis and re-point the trace. Either way, I'd update the traceability matrix so the link points to the *specific* review item or test, not to the review as a whole — a link to "Design Review DR-14" is too coarse to be auditable. The systemic fix is to require that any verification activity credited against a risk control state the failure condition it exercises and the pass/fail criterion, so a generic checklist can't silently absorb a safety link.

**Possible follow-ups:** How would you decide whether a design review is an acceptable verification method for a given control at all? And if the review already closed and the design is frozen, what's your path to closing the gap without reopening the whole phase?

## Q4: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The mismatch is one risk control measure against three implementation elements owned by different disciplines, so a one-to-one link will either lose information or become unmanageable. I'd decompose the single credited control into its constituent *control contributions* without splitting the risk analysis entry itself — the risk file keeps one control, but the traceability scheme records that the control is realized by a set of elements, each with its own requirement and verification. Concretely: the sensor path gets a requirement for accuracy, range, and response time; the firmware loop gets requirements for the control law, update rate, and behavior on sensor fault; the power switch gets requirements for its ability to interrupt the load and its failure mode. Each of those traces to its own verification, and then a *system-level* verification exercises the loop as an integrated whole under a fault condition — because individually-correct elements don't prove the loop keeps the element in range. The traceability matrix needs a link type that expresses "contributes to" versus "implements," so the auditor can see the whole control is covered without pretending any single element is the control. I'd also make sure the risk analysis notes the dependency on all three elements, since the control's effectiveness depends on the weakest link — if the sensor drifts, the loop is compromised even though the firmware and switch are fine.

**Possible follow-ups:** How would you allocate the safe-range budget across the three elements so each has a defensible requirement? And if one element is later changed, how does the trace tell you which system-level verification must be repeated?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file lists a risk control measure, the SRS contains a requirement that implements it, and the verification plan contains a test that verifies the requirement — but when you trace the links, you find that the requirement was written by the systems engineer, the test was written by the test engineer, and neither of them has ever read the risk analysis entry that justifies the control. The links exist on paper, but the *intent* of the control has been lost between the documents. How would you handle this?

**Answer:** The links are structurally complete but semantically empty, which is the most dangerous kind of traceability gap because it passes audit while providing no real assurance. I'd resist the temptation to just tell people to read the risk file and move on — the root cause is a process where each document is authored in isolation and the trace is assembled afterward by matching IDs. My approach would be, first, to pick a handful of these controls and walk them end to end with the systems engineer and test engineer in the same room, reading the risk entry aloud and asking each person to explain how their requirement or test addresses the specific failure condition. That usually surfaces the gap quickly and makes it concrete rather than abstract. Second, I'd fix the process so the risk entry is an *input* to requirement authoring and test design, not a downstream reference — for example, requiring that a requirement implementing a risk control quote or summarize the hazard, and that the test procedure state the failure condition it exercises. Third, I'd add a review gate where someone explicitly checks semantic alignment on safety-linked items, not just that the IDs match. I'd frame it to the team as protecting them: if a control fails in the field, the first question will be whether the test actually tested the control, and "the IDs matched" won't be a satisfying answer. I'd keep the tone collaborative — the engineers didn't do anything wrong, the process let them work in silos.

**Possible follow-ups:** How would you prioritize which controls to walk through first if there are hundreds of them? And how would you measure whether the process fix is actually working over the next few months?
