# risk-requirements-traceability — Day 98

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is a semantic gap: the requirement exists and is verifiable, but the *safety intent* behind it has been stripped out, so anyone reading the SRS in isolation would see a performance/behavior requirement rather than a risk control. I'd fix this at three levels. First, in the risk management file, I'd make the control entry explicit about the implementation: name the firmware function/module, state the hazard it mitigates (hazardous overspeed), and record the risk control option category (inherent safety by design vs. protective measure). Second, in the SRS, I'd either (a) add a dedicated safety requirement that states the hazard context and the measurable acceptance criterion — e.g., "the commanded motor speed shall not change by more than X units per second, to prevent hazardous overspeed" — or (b) if the functional requirement must stay generic, add a traceability annotation linking it to the risk control ID and a note describing the safety intent. Third, in the traceability matrix, I'd create a bidirectional link: risk control → SRS requirement → design element (the rate-limiter module) → verification test. The verification test itself must be written to stress the *failure condition* — i.e., command a step change larger than the limit and confirm the output is clamped — not just confirm nominal ramping. A useful discipline is a "safety intent" field on every requirement that traces to a risk control, so the hazard is never more than one click away from the requirement text. I'd also flag this pattern in design review: any requirement that traces to a risk control but whose text doesn't mention the hazard is a candidate for rewording.

**Possible follow-ups:** If the firmware team argues that adding hazard language to the SRS "clutters" it, how would you respond? / How would you verify that the rate limiter actually engages under the fault condition rather than only under normal commanded ramps?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** When the risk analysis credits an emergent, loop-level behavior as a single control, the traceability scheme has to bridge from that single control down to multiple contributing elements without losing the "whole is greater than the sum of parts" property. My approach: (1) In the risk file, keep the control as a single entry but decompose it into *control contributions* — sensor accuracy/response, firmware loop behavior (setpoint, integral windup limits, output clamping), and actuator switching behavior — each with its own acceptance criterion that is necessary (though maybe not sufficient) for the loop to work. (2) In the SRS, create a parent safety requirement for the loop-level behavior (e.g., "heating element temperature shall not exceed T_max under any single-fault condition") and child requirements for each contribution, with explicit parent-child links. (3) In the traceability matrix, show the parent requirement traced to an *integration-level* verification (the whole loop tested under fault conditions), and each child requirement traced to its own unit/module-level verification. The key insight is that verifying each contribution in isolation does not verify the loop — so the matrix must include a distinct integration verification node that exercises the assembled loop, including the fault conditions the risk analysis cares about (e.g., sensor stuck-high, sensor drift, PID output saturation). (4) I'd also document the *assumptions* the risk analysis makes about each contribution — e.g., "sensor response time ≤ X ms" — as derived requirements, because if any assumption is violated the loop-level control may no longer be adequate. Finally, I'd make sure the loop-level verification is owned by someone (systems/test) rather than falling between the hardware and firmware teams, which is the classic failure mode for distributed controls.

**Possible follow-ups:** How would you handle a situation where the loop-level integration test passes but one contribution's unit test fails intermittently? / If the PID gains are tuned at integration time, how do you trace the tuned values back to the risk control?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** This is a "traceability exists on paper but the evidence is hollow" problem. The link is technically present, but the review's checklist doesn't ask the question the risk control needs answered, so passing the review tells you nothing about whether the control works. I'd handle it in three steps. First, I'd audit the review record against the risk control's failure condition: read the control's description and the hazard it mitigates, then read the review checklist and minutes, and ask "could this review have passed while the control was broken?" If yes, the evidence is inadequate regardless of the traceability link. Second, I'd either (a) add a control-specific line item to the review checklist — e.g., "confirm the power supply's overvoltage clamp engages before downstream components' absolute maximum ratings are exceeded" — and re-run the review with that item in scope, or (b) if the review is genuinely the wrong verification method for this control, replace the link with a more appropriate verification (test, analysis, or inspection) that actually exercises the failure condition. Third, I'd fix the process so this doesn't recur: when a risk control is traced to a design review, the review's entry/exit criteria should explicitly include the control's failure condition, and the review record should capture the specific evidence (calculations, measurements, or inspection results) that demonstrates the control is effective. A useful rule: a design review is only valid verification evidence for a risk control if the review's scope explicitly names the control and its failure condition — otherwise it's a general design review that happens to touch the same subsystem.

**Possible follow-ups:** How would you decide whether to re-run the review versus replace it with a test? / What would you put in the review record to make it defensible as objective evidence?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is tricky because the "control" isn't a fixed design element — it's a *value* written into each unit, and the risk analysis credits the value as the mitigation. The traceability scheme has to capture three things: the parameter's definition and allowed range, the manufacturing process that sets it, and the per-unit verification that confirms it was set correctly. My approach: (1) In the risk file, document the control as "output current limited to I_max, where I_max is set at manufacturing to a value within [I_min, I_max_allowed] such that the downstream components' ratings are never exceeded." The control's effectiveness depends on the *range*, not a single value. (2) In the SRS, create a requirement for the parameter: its name, units, allowed range, resolution, storage location, and the consequence of an out-of-range value. Also create a requirement for the manufacturing process: how the value is computed (e.g., from a calibration measurement), how it's written, and how it's read back and verified. (3) In the traceability matrix, link the risk control to both the parameter requirement and the manufacturing-process requirement, and link the manufacturing-process requirement to a *per-unit* production test that reads back the stored value and confirms it's within range — this is the verification activity, and it must run on every unit, not a sample, because the control is unit-specific. (4) I'd also add a design requirement that the firmware *enforces* the limit at runtime (e.g., clamps the output command to the stored value) and a verification test that confirms the enforcement works even if the stored value is at the edge of its allowed range. The subtle risk here is that the parameter could be corrupted or mis-set after manufacturing (e.g., via a service port), so I'd trace a separate control for write-protection or checksum validation of the stored value. Finally, I'd make sure the manufacturing test record is retained as part of the device history record, because that's the objective evidence that the control was correctly applied to each unit.

**Possible follow-ups:** How would you handle a unit that fails the read-back test — is it reworked, scrapped, or does the parameter get re-set? / If the parameter can be changed in the field via a service port, how does that affect the traceability and the risk analysis?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The systems engineer is technically correct that the matrix is compliant, but compliance isn't the goal — the goal is that the controls actually work, and a copied test that passes without exercising this project's failure conditions is false assurance. I'd treat this as a quality-of-evidence problem, not a paperwork problem, and handle it in stages. First, I'd thank the test engineer for raising it and ask them to identify specifically which tests are suspect and why — I want concrete examples, not a general impression, so I can assess scope. Second, I'd independently review a sample of the flagged tests against the risk analysis: for each, read the control's failure condition, read the test procedure, and ask "if this control were disabled, would this test fail?" If the answer is no, the test is not valid evidence for that control regardless of what the matrix says. Third, I'd bring the systems engineer and test lead together with that evidence and reframe the conversation: this isn't about whether the matrix is compliant, it's about whether we can defend the verification evidence to a regulator or a notified body — and a copied test that doesn't stress the failure condition won't survive that scrutiny. I'd propose a targeted re-verification of the affected controls, prioritized by severity in the risk analysis, rather than re-running everything. Fourth, I'd fix the root cause: add a review step where each verification test is checked against the risk control's failure condition before it's accepted into the matrix, and make "does this test fail when the control is disabled?" a standard question in test review. Finally, I'd be transparent with the quality manager about what was found and what's being done — hiding it would be far worse than the finding itself. The behavioral lesson I'd emphasize is that a complete matrix is necessary but not sufficient; the evidence behind each link has to be real.

**Possible follow-ups:** How would you prioritize which suspect tests to re-verify first if you can't re-run all of them before a deadline? / What would you say to the systems engineer to get them from "compliant" to "defensible" without making them feel blamed?
