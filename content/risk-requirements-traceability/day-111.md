# risk-requirements-traceability — Day 111

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *hardware current-limit circuit* — for example, a series sense resistor feeding a comparator that gates a MOSFET — where the risk analysis credits the limit against a hazardous overcurrent condition, but the requirement only states "the output shall not exceed the maximum rated current" without specifying the trip threshold, tolerance, or response time?

**Answer:** The gap here is that the requirement is written at a level of abstraction that a test can satisfy without actually exercising the control's failure condition — "shall not exceed maximum rated current" could be verified by a nominal-load test that never approaches the limit. The first step is to decompose the risk analysis entry into the specific characteristics that make the control effective: the trip threshold (with tolerance), the response time from overcurrent to MOSFET gate-off, and the behavior under the worst-case combination of component tolerances (sense resistor tolerance, comparator offset, reference drift). Those become measurable sub-requirements derived from the risk control, each with an explicit acceptance criterion and a stated test condition. The traceability link then runs from the hazard → risk control measure → the derived requirement(s) → the design element (sense resistor, comparator, gate driver) → the verification test that stresses the trip point, not just nominal operation. I'd also add a note in the risk file cross-referencing the derived requirement IDs so a future reviewer can see the intent, and flag the original vague requirement for revision rather than leaving both versions in the SRS. The practical test is: could someone read the requirement and the test procedure alone, without the risk file, and know they had to drive the circuit into overcurrent and measure the trip point and response time? If not, the traceability is nominal only.

**Possible follow-ups:** How would you handle the case where the comparator's response time is dominated by the MOSFET gate capacitance and gate driver strength, so the "response time" requirement spans two design elements? Would you verify the trip threshold by test on every unit or by analysis plus sample testing, and how would you justify that choice in the risk file?

## Q2: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *calibration procedure performed at the customer site* — for example, a zeroing step the service technician must perform before the device is used — rather than a design verification test performed by your team?

**Answer:** This is a case where the "verification" of the control is really a verification that the *procedure* is adequate and that the device enforces it, not a verification that a design element works. I'd split it into two traceable pieces. First, the procedural control itself needs to be verified as a usability/labeling activity: does the procedure, as written, actually cause a competent technician to perform the zeroing correctly, and does the device detect and refuse to operate if zeroing hasn't been done? That second part is a design requirement — an interlock or state-machine guard — and it should be traced and tested like any other firmware control. Second, the calibration procedure's *effectiveness* (does zeroing actually bring the reading within tolerance) is verified by a combination of the procedure validation and the device's own self-check. In the traceability matrix I'd represent the procedural control as a distinct control type with its own verification method (procedure validation, usability study, or label comprehension testing), not force it into the "test" column where it doesn't belong. The risk file should state explicitly that the control depends on the procedure being followed, and that the device's enforcement mechanism is the design-side backstop — because if the procedure is the only barrier, the residual risk assessment has to account for human error.

**Possible follow-ups:** How would you trace the case where the procedure is revised after the device is released — does the risk file need re-evaluation, and how do you keep the traceability current? If the device cannot detect that zeroing was skipped, what does that do to the residual risk evaluation, and how would you document that?

## Q3: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system has a *safety-related parameter that is derived from a lookup table indexed by a sensor reading at runtime* — for example, a maximum allowable motor current computed from a temperature measurement and a table in firmware — rather than being a fixed constant or a manufacturing-set value?

**Answer:** The control here is really the *function* that maps temperature to current limit, plus the table data, plus the sensor path that feeds it — so the traceability has to cover all three, and the requirement has to be written as a verifiable relationship rather than a single number. I'd derive requirements at three levels: the table itself (the current limit at each temperature breakpoint, with tolerance, verified by inspection of the table against the thermal analysis), the interpolation/derivation logic (verified by test at and between breakpoints, including boundary conditions like sensor fault or out-of-range temperature), and the sensor path (verified as part of the temperature measurement chain, with its own accuracy and fault-detection requirements). The risk file entry should reference the derived requirement IDs and state the assumption that the table is correct — because the table is effectively a design input that comes from thermal analysis, and if the analysis changes, the table and the requirements change together. I'd also make sure the verification test exercises the *worst-case* corner: the temperature at which the current limit is lowest, and the sensor fault condition, because a lookup-table control can pass a nominal test at room temperature while failing to protect at the hot corner. The traceability matrix entry for this control will have multiple requirement rows and multiple test rows, and that's correct — a single "control → one test" link would be misleading here.

**Possible follow-ups:** How would you verify the table data itself — is that a test, an analysis, or an inspection, and how do you record that in the traceability matrix? If the temperature sensor fails open, what does the derivation function do, and how is that failure mode traced back to the hazard?

## Q4: How would you approach deciding whether a risk control measure should be traced to a *design requirement*, a *design element*, or *both* — and what practical difference does that distinction make in a traceability matrix?

**Answer:** The distinction matters because they answer different questions and fail in different ways. A design requirement is a statement of *what the system must do or be* — it's the thing you can write an acceptance criterion against and verify. A design element is the *implementation* — the specific component, circuit, or code module that realizes the requirement. Tracing a control to a requirement only tells you the control is specified; tracing it to a design element only tells you something in the design is intended to implement it. For a risk control measure, you generally want both, because the audit question is "show me the control is specified, implemented, and verified" — and a break anywhere in that chain is a finding. The practical difference shows up in gap analysis: if a control traces to a requirement but not to a design element, the requirement may be unimplemented or implemented somewhere undocumented; if it traces to a design element but not a requirement, the implementation exists but has no acceptance criterion, so verification has nothing to test against. In the matrix I'd use separate columns or link types for requirement and design element, so coverage reports can flag either gap independently. The exception is controls that are inherently design-rule-based — creepage distance, component derating — where the "requirement" may be a design standard and the "element" is the layout or the BOM; those still need both links, but the verification method is inspection or analysis rather than test.

**Possible follow-ups:** How would you represent a control that is implemented by a *combination* of design elements — say, a hardware comparator plus a firmware response — in this scheme, and where does the requirement sit? If a control traces to a design element but the requirement was written after the design was frozen, what does that tell you about the process, and how would you handle it?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file, the SRS, and the verification plan are each internally consistent and each passes its own review — but when you trace across all three, you find that a risk control measure is linked to a requirement that is linked to a test, and the test passes, yet the *combination* doesn't actually demonstrate the control works, because the requirement was written at a level of abstraction the test can satisfy without exercising the control's failure condition. The three document owners each argue their document is correct. How would you handle this?

**Answer:** The first thing I'd do is reframe the disagreement so it isn't about whose document is wrong — because in a narrow sense, all three owners are right: each document is internally consistent. The problem is at the *seams* between documents, and none of the three owners owns the seams. I'd set up a short working session with the three owners plus whoever wrote the risk analysis entry, and walk the specific control end to end: read the hazard, read the risk control measure, read the requirement, read the test procedure, and ask the group one question — "if this control failed, would this test detect it?" That question is usually enough to make the gap visible without anyone having to concede their document was defective. Then I'd fix it at the requirement level, because that's where the abstraction gap lives: rewrite the requirement to state the failure condition and a measurable acceptance criterion, and revise the test to stress that condition. I'd also add a lightweight cross-document review step — a traceability walkthrough at each design review milestone where a sample of controls is traced end to end by people from different disciplines — so this class of gap gets caught before audit rather than after. The tone matters: I'd frame it as a process gap, not an individual error, because blaming the requirement author or the test author just makes people defensive and the next gap goes unreported.

**Possible follow-ups:** How would you decide how many controls to sample in that cross-document walkthrough, and how would you prioritize which ones? If the requirement revision invalidates test results that were already recorded as passing, how would you handle the rework and the schedule impact with the program manager?
