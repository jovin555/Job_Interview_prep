# risk-requirements-traceability — Day 115

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement captures the *mechanism* but not the *intent*, so the link from hazard to requirement is implicit and fragile — anyone reading the firmware requirement in isolation would see a performance behavior, not a safety control, and a future change to the clamp rate could be approved as a routine tuning change without anyone realizing it weakens a risk control.

My approach would be to fix this at the requirement level rather than trying to paper over it in the matrix. First, I'd add an explicit safety-derived requirement that states the hazard context and the safety-relevant bound — something like "the commanded actuator rate shall not exceed X units/s, to prevent hazardous overspeed" — with a measurable acceptance criterion and a reference back to the risk analysis entry. The existing functional requirement can remain as the implementation-level description, but it should be traced *up* to the safety requirement so the two are visibly related. That gives a clean chain: hazard → risk control measure → safety requirement → functional/derived requirement → design element (the clamp logic) → verification.

Second, I'd make the traceability bidirectional and enforce it: the risk management file entry for the control should point forward to the safety requirement, and the safety requirement should point back to the hazard. This matters because it's the backward link that lets you answer "why does this requirement exist?" during a change impact assessment.

Third, on verification: the test needs to demonstrate the *hazard-relevant* behavior, not just that the clamp exists. That means driving the command input with a step or ramp that would produce an unsafe rate if unclamped, and confirming the output rate stays within the bound — ideally at the boundary and just past it, and across the operating range where the limiter is active. A test that only confirms "output changes smoothly under normal commands" doesn't exercise the failure condition.

Finally, I'd flag the requirement for change control: any modification to the clamp rate or the conditions under which it applies should trigger a risk re-assessment, because the parameter *is* the control.

**Possible follow-ups:** If the clamp rate is a tunable constant, how do you keep the requirement, the code constant, and the risk analysis from drifting apart over time? / How would you verify the limiter behaves correctly when the actuator is already at its maximum and a new command arrives?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The difficulty is that the risk analysis credits one control, but the control has no single owner and no single requirement — it's an emergent property of three elements in series, each with its own failure modes and its own latency. If you trace the risk control measure to only one of the three, you've created a false sense of coverage.

I'd decompose the control into its constituent *safety functions* while keeping the risk analysis entry as the single top-level control. Concretely: the risk management file keeps one control measure ("maintain heating element temperature below the safe limit"), and beneath it I'd create derived safety requirements for each contributing element — sensor accuracy and range, the control algorithm's response to out-of-range or invalid readings, and the power switch's ability to interrupt the element independent of the firmware. Each derived requirement gets its own verification, and each is traced back up to the single risk control measure. That way the matrix shows one control with three supporting requirements, not three unrelated requirements that happen to exist.

The critical part is the *integration* verification: because the control is emergent, you also need a system-level test that exercises the loop as a whole — for example, injecting a temperature rise and confirming the element is de-energized within the required time — because passing the three element-level tests individually doesn't prove the loop works. I'd explicitly document that the system-level test is the verification of the risk control measure, and the element-level tests are verification of the derived requirements.

I'd also pay attention to the *independence* assumption. If the risk analysis assumes the power switch can cut the element regardless of firmware state, that independence needs to be a stated requirement and verified — otherwise the "distributed" control collapses to a single point of failure and the risk estimate is wrong.

**Possible follow-ups:** How would you allocate a single response-time budget across the sensor, the firmware loop, and the switch, and trace that allocation? / If the firmware PID loop is later replaced with a different algorithm, what in your traceability scheme tells you which risk entries need re-review?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** This is a case where the traceability link exists on paper but the verification doesn't actually verify anything about the control. A general checklist review can pass while the specific failure condition the control addresses is never examined, so the "verification" is really just evidence that *a* review happened.

My first step would be to confirm the gap concretely: read the checklist against the risk control's failure condition and show that no checklist item requires the reviewer to assess it. That turns a vague concern into a specific finding.

Then I'd decide between two remedies. The cleaner one is to add a dedicated review criterion — a checklist item or a focused review record — that explicitly asks the reviewer to assess the control's failure condition and record the evidence and conclusion. That converts the review into a genuine verification activity with objective evidence, which is what the risk file needs. The alternative, if the control is testable, is to add a test and re-point the traceability link to it, keeping the review as supplementary. Which one is appropriate depends on the nature of the control: a layout-driven or derating-driven control may genuinely only be verifiable by review, whereas a functional control usually should be tested.

I'd also fix the root cause: review checklists should be derived from the requirements and risk controls they're meant to cover, not reused wholesale from a template. A short mapping from each risk control to the specific review criterion that assesses it prevents this from recurring.

Finally, I'd record the disposition — whether the original review is accepted as-is with a documented rationale, or whether re-verification is required — so the risk file reflects what was actually done rather than what was assumed.

**Possible follow-ups:** What objective evidence would you expect a design review to produce to count as verification of a risk control? / How would you handle a control where review is the only practical verification method, and the auditor questions whether review is acceptable evidence?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is tricky because the control isn't a piece of logic or a circuit — it's a *value*, and the value varies per unit. A traceability scheme built only around requirements and tests will miss it unless you deliberately account for the parameter as a first-class artifact.

I'd structure it in three layers. First, a requirement that defines the parameter: its allowed range, how it's determined, and the safety rationale — "the output current limit shall be set within [range] such that the maximum output current does not exceed the safe limit." That requirement is the traceable anchor and it references the hazard. Second, the *setting mechanism*: the production procedure or calibration step that writes the value, which needs to be a controlled, verified activity — traced as the implementation of the requirement. Third, the *verification*: both a per-unit check (the value was written and read back correctly, and falls within the allowed range) and a design-level verification that the range itself is safe across worst-case tolerances.

The per-unit aspect is what makes this different from a normal requirement. The traceability scheme needs to acknowledge that verification happens at two levels: design verification proves the *range* is safe, and production verification proves each *unit's value* is within that range and was correctly applied. I'd capture both in the matrix, with the production record (serialized) as the objective evidence for the per-unit link.

I'd also make sure the parameter is protected against unauthorized change — if it can be modified via a service port, that's a new hazard and needs its own control and traceability. And the risk analysis should state explicitly that the control depends on the parameter being correctly set and protected, so that a future change to the setting procedure triggers a risk review.

**Possible follow-ups:** How would you handle a unit that comes back from service with a parameter value outside the allowed range — what does your traceability scheme tell you about which risk entries are affected? / If the parameter range is later widened, what has to be re-verified and re-traced?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd treat this as a substantive quality issue rather than a documentation dispute, but I'd handle it carefully because the systems engineer isn't entirely wrong — the matrix *is* compliant on its face, and the tests *do* pass. The problem is that compliance and passing tests aren't the same as evidence that the controls work, and the risk file is only as good as the verification behind it.

My first move would be to verify the concern rather than act on hearsay. I'd pick a couple of the flagged tests and walk through them against the risk analysis entry: does the test setup reproduce the failure condition the control is meant to mitigate? Does the acceptance criterion actually distinguish "control working" from "control absent"? If the test would pass with the control disabled, that's a concrete, demonstrable gap — and a demonstration is far more persuasive than an argument.

With that evidence in hand, I'd bring the systems engineer and test engineer together and reframe the question away from "is the matrix compliant?" to "can we show, for each of these controls, that the test would fail if the control were removed?" That's a shared, objective standard, and it usually resolves the disagreement because it's no longer about whose document is right. Where the answer is no, the test needs to be revised or a new one added, and the traceability link updated to point at the revised test.

I'd also address the process root cause: a review step where someone other than the test author confirms each risk-control test actually exercises the failure condition, and a periodic "negative check" — deliberately disabling a control in a bench setup to confirm the test detects it — as a sanity check on the verification suite. And I'd be careful not to make it personal: copied-and-relabeled tests are usually a symptom of schedule pressure, not negligence, so the fix is process and time, not blame.

**Possible follow-ups:** How would you prioritize which of the flagged tests to re-examine first, given limited time before the audit? / If re-testing reveals a genuine gap in a control that's already been shipped, how would you handle the escalation?
