# risk-requirements-traceability — Day 91

## Q1: How would you approach tracing a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is a broken chain of *intent*: the risk analysis says "this control exists to prevent overspeed," but the firmware requirement says only "the commanded speed shall not change by more than X units per control cycle." A reader of the firmware spec alone cannot tell whether that clamp is a safety control or a performance nicety, and a reader of the risk file alone cannot tell where in the code it lives. I would repair the chain in three steps.

First, I would make the safety intent explicit at the requirement level. The cleanest approach is to add a derived safety requirement in the SRS — something like "the firmware shall limit the rate of change of the motor speed command to no more than X per cycle to prevent hazardous overspeed" — and then let the firmware requirement be a child of it, or annotate the existing firmware requirement with an explicit reference to the risk control ID it implements. The key principle is that the requirement should carry a pointer to the hazard/risk-control entry, not just describe behavior. That way the traceability link is bidirectional: risk control → requirement → design element → verification.

Second, I would check that the verification activity actually stresses the failure condition. A test that commands a step change and observes the output ramp is necessary but not sufficient — it verifies the clamp works under nominal conditions. The risk analysis is concerned with overspeed, so the test should also demonstrate that the limiter holds under worst-case inputs: maximum commanded step, minimum control-loop period, and any fault condition that could otherwise produce a large command jump. If the existing test doesn't do that, I'd flag it as a gap and either extend it or add a dedicated safety test.

Third, I would address the root cause so it doesn't recur: a rule in the requirements review checklist that any requirement implementing a risk control must carry the risk control ID, and a periodic traceability audit that samples risk controls and confirms the linked requirement text actually conveys the safety intent. The rate limiter is a good example of why "functional description only" requirements are dangerous — they can be silently weakened or removed during a refactor because nothing in the requirement signals that it's load-bearing for safety.

**Possible follow-ups:** If the firmware team argues that adding safety language to the requirement over-constrains their implementation freedom, how would you respond? And how would you handle the case where the same rate limiter also serves a purely performance purpose, so it has two justifications?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** This is the classic "emergent behavior" traceability problem: the control is not any one component, it's the closed-loop behavior of the whole chain, and no single subsystem owns it. If you try to trace it as three separate controls you lose the safety argument; if you try to trace it as one control you can't point to where it's implemented. I would handle it by decomposing the control into an *allocated* set of sub-requirements while keeping a single parent risk control entry.

Concretely: the risk management file keeps one risk control measure ("the heating element shall be maintained within a safe temperature range under all operating conditions"), and that entry is decomposed into allocated requirements across the three elements — a sensor accuracy/response-time requirement, a firmware control-law requirement including the safe-state behavior on sensor fault, and a power-switch requirement covering the ability to interrupt the element and its failure mode. Each allocated requirement traces up to the parent risk control and down to its own design element and verification. The traceability matrix then shows a fan-out from one risk control to three requirement branches, and the coverage report confirms every branch has a verification.

The subtlety is that verifying each branch in isolation does not verify the loop. So I would add an *integration* verification activity at the loop level — a test that exercises the closed loop under fault injection (sensor drift, sensor dropout, stuck power switch) and confirms the safe range is maintained or the system enters a defined safe state. That integration test traces to the parent risk control, while the branch tests trace to the allocated requirements. This gives you both the decomposition (so each team knows what they own) and the system-level evidence (so the safety argument is complete).

I would also make sure the interface between the elements is captured — the sensor-to-firmware signal range and timing, the firmware-to-switch command semantics — because distributed controls usually fail at the seams, not in the middle of a component. An ICD or interface requirement at each seam, traced to the parent control, closes that gap.

**Possible follow-ups:** How would you decide how much of the loop-level verification can be credited to analysis (e.g., a control-loop stability analysis) versus physical test? And if the PID gains are tuned at manufacturing or in the field, how does that affect the traceability of the control?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** The traceability link exists on paper but the verification is not actually verifying the control — it's a general review that happens to touch the same area. The risk is that the review passes, the matrix shows coverage, and nobody has ever asked "does this control actually mitigate the failure condition it was credited for?" I would treat this as a verification-method mismatch and fix it at the review-criteria level rather than by adding a redundant test.

First, I would confirm the mismatch by reading the review checklist against the risk control's failure condition. If the checklist has no line item that asks the reviewer to assess that specific failure mode — for example, "confirm the supply cannot deliver reverse polarity to the load under connector mis-mate" — then the review cannot be credited as verification of that control, regardless of what the matrix says.

Second, I would either extend the review checklist with an explicit, control-specific line item (with a measurable pass criterion and a recorded reviewer sign-off) or, if the control genuinely needs test evidence, reclassify the verification method. The choice depends on the nature of the control: a layout-related control like creepage distance is legitimately verified by inspection against a rule, but a functional control like "the supply shuts down on overvoltage" needs a test. The mistake is letting a general review stand in for a specific functional verification.

Third, I would update the traceability matrix to record the verification *method* and the specific acceptance criterion, not just the activity ID. A matrix that says "verified by DR-014" is weak; one that says "verified by DR-014, line item 7, criterion: no reverse current > X mA under mis-mate" is auditable. I would also add a review of the review checklists themselves as part of the verification planning phase, so this is caught before the campaign rather than during an audit.

**Possible follow-ups:** How would you handle the case where the reviewer who signed off is no longer available and you need to re-verify? And what's your view on whether a design review can ever be acceptable objective evidence for a risk control, or should it always be paired with a test?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control is not a circuit or a line of code but a *value*, and the traceability has to cover three things that are easy to miss: the parameter's definition and allowed range, the manufacturing process that programs it, and the per-unit verification that the programmed value is correct. If any of those three is untraced, the control can silently fail — a unit ships with the wrong limit and nothing in the traceability matrix catches it.

I would structure it as follows. The risk control measure in the risk file states the hazard and the required limit (e.g., "output current shall not exceed Y under any load condition"). That decomposes into: a *design* requirement defining the parameter, its units, its allowed range, and its default/safe value; a *manufacturing* requirement specifying how the value is computed or selected and how it is programmed (with the programming procedure and any checksum/readback as part of the control); and a *verification* requirement covering both the design-time validation of the range and the per-unit production test that reads back the programmed value and confirms it is within the allowed range and matches the unit's configuration.

The traceability matrix then has a branch that goes risk control → design requirement → firmware/parameter definition, and a parallel branch risk control → manufacturing requirement → production test procedure. The per-unit production record (the readback value and pass/fail) becomes the objective evidence, and it should be retained per serial number, because the control is unit-specific — a single type test on one unit does not verify the control on all units.

Two practical points: first, the allowed range and the safe default must themselves be justified against the hazard — if the range is too wide, the control is weak; if the default is unsafe on a programming failure, that's a separate hazard to analyze. Second, I would make sure the parameter is protected against unauthorized or accidental change after programming (write-protect, checksum, service-port authentication), and trace that protection as part of the control, because a limit that can be changed in the field is not a reliable control.

**Possible follow-ups:** How would you handle a unit that fails the readback check at end-of-line — is that a nonconforming product or a rework candidate, and how does that decision get traced? And if the parameter can be updated in the field via a service tool, how does that change the verification and traceability approach?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The matrix being complete and the tests passing is exactly the situation that should make a lead suspicious, because it tells you nothing about whether the tests are *capable of detecting the failure*. A copied test that passes is weak evidence — it may be exercising a different failure mode entirely, or exercising the right one only incidentally. I would treat the test engineer's report as a credible signal and act on it rather than defend the matrix.

My first step would be to verify the concern on a small sample rather than argue about it in the abstract. I would pick two or three of the flagged tests, read the test procedure against the risk control's failure condition, and ask a concrete question: if I disabled or defeated this control, would this test fail? If the answer is no, the test is not verifying the control, regardless of what the matrix says. That gives me objective evidence to bring to the systems engineer and the quality function, which is far more persuasive than a process argument.

Assuming the concern is confirmed, I would frame the fix as a *test adequacy* issue, not a traceability-compliance issue — because that's what it is, and it lets the systems engineer save face while still getting the right outcome. The remediation is to re-derive the acceptance criteria for the affected tests from the risk analysis (not from the previous project's test), add a negative check where feasible (defeat the control, confirm the test fails), and re-run. I would also add a lightweight review gate: before a test is credited to a risk control, someone other than the test author confirms the test's pass/fail criterion maps to the control's failure condition.

On the process side, I would want to understand *why* the tests were copied — usually it's schedule pressure or a lack of clear acceptance criteria in the requirements — and fix that root cause, because blaming the test engineer for a systemic gap doesn't prevent recurrence. And I would be careful not to over-correct into requiring every test to be rewritten from scratch; the goal is adequate evidence, not maximal effort.

**Possible follow-ups:** How would you handle the situation if the systems engineer escalates and the program manager backs them because the schedule is tight? And how would you document this finding so it's visible to an auditor without turning it into a formal nonconformance if it can be resolved before release?
