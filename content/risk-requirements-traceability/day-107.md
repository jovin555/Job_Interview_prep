# risk-requirements-traceability — Day 107

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement is technically correct but semantically orphaned — it describes *what* the firmware does without capturing *why it matters*, so the safety intent lives only in the risk file and can be lost the moment someone refactors the code or rewrites the requirement. I'd approach it in three steps. First, I'd establish the missing link explicitly: create a trace from the risk control measure in the risk management file to the existing firmware requirement, and annotate that requirement with a reference to the hazard and the risk control ID — not by rewriting the functional behavior, but by adding the safety rationale as a linked attribute or a companion "safety requirement" that states the hazard it mitigates and the failure condition it guards against. Second, I'd make sure the verification activity actually stresses the failure condition — a test that commands a step change in speed and confirms the output ramps within the specified rate, not just a test that confirms the motor spins. Third, I'd check that the rate limit value itself is justified against the hazard analysis (is the clamp rate derived from a safe deceleration/acceleration envelope?) and that the requirement's acceptance criterion is measurable, so the test can objectively pass or fail. The principle is that a risk control requirement should carry its hazard linkage as a first-class attribute, so traceability is bidirectional and the safety intent survives design changes.

**Possible follow-ups:** If the rate limiter is later tuned for performance reasons, how would your traceability scheme ensure the change is re-evaluated against the hazard? Would you duplicate the safety intent into the firmware requirement text, or keep it as a linked reference only — and what are the trade-offs?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** When a control is an emergent property of several elements rather than a single component, tracing it to any one requirement or design element is misleading — you'd get a matrix that looks complete but doesn't actually demonstrate the control works. I'd handle this by decomposing the control into its constituent contributions while preserving the whole. Concretely: keep the risk control measure as a single entry in the risk file, then create derived sub-requirements for each element — the sensor's accuracy and response time, the PID loop's output limits and update rate, the power switch's ability to interrupt current — each with its own measurable acceptance criterion and each traced back to the parent control. The verification then has two layers: element-level verification (does the sensor meet its accuracy spec, does the switch actually open under load) and an integrated system-level test that exercises the loop end-to-end under the fault condition the control is meant to mitigate. The traceability matrix should show the parent control fanning out to the sub-requirements and then converging back to the integrated verification, so a reviewer can see both the decomposition and the recombination. The key discipline is that the integrated test is not optional — element-level passes don't prove the loop works, because the failure mode may be in the interaction (e.g., sensor lag combined with PID windup).

**Possible follow-ups:** How would you allocate the timing budget across the sensor, loop, and switch so the integrated test has a clear pass/fail threshold? If one element is later swapped for a different part, what re-verification would your scheme require?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** This is a case where the traceability link exists on paper but the verification is not actually capable of detecting the failure the control is meant to prevent — the review could pass without anyone ever asking the safety question. I'd treat it as a gap rather than accept the link. First, I'd confirm what the risk control actually requires: what specific failure condition must be shown to be mitigated, and what evidence would demonstrate that. Then I'd either extend the existing review checklist with explicit line items tied to that failure condition — so the reviewer is forced to assess it and record a finding — or, if the control can't be meaningfully assessed by inspection, replace or supplement the review with a test or analysis that can. The traceability matrix should then point to the *specific* review criterion or test, not just to "design review" as a generic activity. I'd also make the linkage bidirectional: from the risk control to the verification evidence, and from the review record back to the risk control ID, so an auditor can see exactly where in the review the control was assessed. The underlying principle is that a verification activity is only valid evidence if it is *capable of failing* when the control is absent or broken — a generic checklist that never mentions the failure condition isn't.

**Possible follow-ups:** How would you handle a reviewer who argues that adding safety-specific line items to every review checklist creates too much overhead? What objective evidence would you expect the review record to contain to prove the control was actually assessed?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is tricky because the control isn't a fixed design feature — it's a value written into each unit, so traceability has to cover not just the requirement and the design but the *production process* that sets and verifies the value. I'd structure it in layers. At the requirements level, capture the control as a requirement on the parameter: its allowed range, its units, its resolution, and the rationale tying the range to the hazard analysis — so the safe envelope is documented, not just "the value is set in production." At the design level, trace to the firmware/hardware element that reads and enforces the parameter, and to the mechanism that stores it (non-volatile memory, its integrity checks, and what happens if the value is corrupt or out of range). At the production level, trace to the manufacturing procedure and the test that verifies each unit's stored value is within the allowed range before release — this is the verification activity for the control, and it must be per-unit, not sample-based, because the value can differ between units. I'd also address change control: if the allowed range is ever revised, the traceability must show which units were built under which revision, which usually means tying the parameter range to a build record or lot. The traceability matrix therefore has an extra column or link type for "production verification" that most functional requirements don't need.

**Possible follow-ups:** How would you handle a unit whose stored value is found to be outside the allowed range after release — what does your traceability scheme need to support for a field corrective action? Would you treat the parameter range as a design requirement, a manufacturing requirement, or both?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd take the report seriously and treat it as a potential systemic gap rather than a personnel issue — the fact that the matrix passes audit while the tests may not exercise the failure conditions is exactly the kind of false confidence a traceability scheme is supposed to prevent. My first step would be to verify the concern quietly and objectively: pick a few of the flagged tests and walk through them against the risk analysis entry they're linked to, asking "if this control were removed or broken, would this test fail?" If the answer is no, the link is invalid regardless of what the matrix says. I'd then bring the systems engineer and test lead together with that concrete evidence rather than an accusation — framing it as "the matrix is structurally correct but the evidence behind some links doesn't demonstrate the control, and here's an example" — because the systems engineer's position ("it's compliant and passing") isn't unreasonable on its face; it just misses that compliance requires the evidence to be *capable* of detecting the failure. From there I'd propose a targeted re-review of the suspect tests, prioritized by the severity of the hazard each control mitigates, and add a lightweight check to the verification review process: for each risk control test, a reviewer confirms the test would fail if the control were disabled. I'd also want to understand *why* the tests were copied — schedule pressure, unclear requirements, lack of test design guidance — because fixing the process is more durable than fixing the individual tests. The goal is to correct the record honestly before an auditor or a real failure finds it, and to make the matrix mean what it claims.

**Possible follow-ups:** How would you handle the situation if the re-review confirms that several high-severity controls have inadequate test evidence close to a regulatory submission? How would you prevent copied-and-relabeled tests from entering the matrix in the first place without adding heavy process overhead?
