# risk-requirements-traceability — Day 121

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the requirement is technically correct but semantically orphaned — it describes *what* the firmware does without recording *why*, so the traceability link from hazard to requirement is implicit and fragile. I'd fix this at the requirement level rather than trying to patch it in the matrix. First, I'd add an explicit safety-derived requirement (or a safety annotation on the existing one) that states the hazard context: the limiter exists to prevent commanded acceleration from exceeding a rate that could drive the actuator into an unsafe overspeed condition, and it must hold under the full range of commanded inputs, including step changes and fault-induced command spikes. That gives the matrix a real anchor to trace from the hazard. Second, I'd make the acceptance criteria measurable and fault-relevant — the maximum rate of change, the tolerance, and the behavior when the command source misbehaves — because a requirement that only says "clamp the rate" can be satisfied by a test that never stresses the limiter. Third, I'd verify the link bidirectionally: from the hazard down to the requirement and the test, and from the test back up to confirm the test actually exercises the clamping under conditions that would otherwise produce overspeed. Finally, I'd check whether the limiter is the sole control or one of several — if the risk analysis credits it alone, the verification needs to demonstrate it works with the command path at its worst, not just at nominal.

**Possible follow-ups:** If the firmware team resists adding hazard language to their requirements because it "belongs in the risk file," how would you reconcile that without duplicating content? And how would you confirm the verification test genuinely stresses the limiter rather than passing on a command profile that never approaches the rate limit?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap here is that the risk analysis credits one control, but the implementation is spread across three elements owned by different disciplines, so a naive matrix either links the control to one requirement (losing the others) or to none (because no single requirement describes the loop). I'd decompose the control into its constituent functions and trace each: the sensor's accuracy and failure behavior, the firmware loop's setpoint and clamping logic, and the power switch's ability to actually interrupt the heater. Each gets its own requirement with measurable criteria, and each traces back to the same risk control entry. Then I'd add an integration-level requirement and verification that exercises the loop as a whole — because the control's effectiveness depends on the *combination*, and individually-correct elements can still fail together (a sensor that reads low, a loop that trusts it, a switch that never trips). The matrix should show the risk control as a parent with three child requirements plus one integration requirement, so a reviewer can see both the decomposition and the emergent behavior. I'd also make sure the verification plan includes a fault-injection test at the loop level — for example, a stuck sensor reading — because that's the failure condition the control exists to mitigate, and no single-element test will catch it.

**Possible follow-ups:** How would you decide which element owns the integration-level requirement when the loop spans hardware and firmware teams? And if the risk analysis later splits the single control into three separate controls, how would you restructure the traceability without losing the history?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review criteria actually address the control's failure condition — otherwise the link is nominal, not substantive. I'd start by reading the checklist against the risk control entry and identifying the gap: the review covers general power supply practice but never asks whether this specific control trips at the right point, resets correctly, or behaves under the fault the risk analysis describes. Then I'd either extend the checklist with control-specific review questions and re-run that portion of the review with the right reviewers present, or add a supplementary verification activity — a targeted analysis or a bench test — if the failure condition can't be assessed by inspection. The key principle is that the verification method must be *capable* of detecting the failure the control mitigates; a review that would pass whether or not the control works is not evidence. I'd document the gap and the corrective action in the traceability record so the audit trail shows the reasoning, not just the final link. I'd also look for sibling cases — if one control was traced to a generic review, others probably were too — and fix the pattern rather than the instance.

**Possible follow-ups:** How would you decide whether extending the checklist is sufficient versus requiring a physical test? And what would you record in the traceability matrix to show that the review now genuinely covers the failure condition?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a line of code but a *value*, so the traceability has to cover three things: the parameter's definition and allowable range, the process that sets it correctly per unit, and the verification that the value actually in the unit is the right one. I'd create a requirement for the parameter itself — its range, its units, and the consequence of it being out of range — traced to the risk control. Then a separate requirement for the manufacturing/programming process: how the value is derived, how it's written, and how it's read back and confirmed. The verification activity splits accordingly: a design verification that the firmware/hardware honors the parameter correctly across its range (tested with representative values, including the extremes), and a production verification that each unit's stored value matches its specification. The traceability matrix should show both links, because a design that honors the parameter perfectly is useless if the wrong value gets programmed. I'd also address change control: if the allowable range or the derivation method changes, both the risk analysis and the production process need to be re-examined, and the matrix should make that dependency visible so a change to one doesn't silently invalidate the other.

**Possible follow-ups:** How would you verify the parameter's effect at the extremes of its range without destructive testing on every unit? And if a unit is later reworked and the parameter re-programmed, how should the traceability record reflect that?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd treat this as a substantive quality issue rather than a documentation dispute, and I'd be careful not to frame it as an accusation of the test engineer — they raised it, which is exactly the behavior I want to reinforce. First, I'd verify the concern myself on a sample: pick two or three of the flagged tests, read them against the risk analysis entries they're linked to, and check whether the test conditions actually reproduce the failure the control mitigates. If they don't, the matrix is compliant on paper but the evidence is hollow, and that's a finding I need to act on regardless of what the systems engineer argues. I'd bring the systems engineer and test lead together with the specific examples rather than the general claim, because "the matrix is compliant" and "the tests don't exercise the failure condition" can both be true, and the conversation needs to be about the second point. The resolution is to re-examine the flagged tests against their risk entries, rewrite or replace the ones that don't stress the failure condition, and add a review step where the person who wrote the risk control entry confirms the test actually targets it. I'd also look at *why* the tests were copied — schedule pressure, unclear risk entries, no review gate — because fixing the individual tests without fixing the cause just moves the problem to the next project. Throughout, I'd keep the tone on the shared goal: the matrix exists to give confidence the controls work, and a matrix that passes audit while the evidence is weak defeats its own purpose.

**Possible follow-ups:** How would you handle it if the systems engineer continues to insist the matrix is fine and escalates? And what process change would you put in place so copied-and-relabeled tests get caught before they reach the matrix, rather than after?
