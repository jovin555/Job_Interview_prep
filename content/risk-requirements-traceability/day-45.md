# risk-requirements-traceability — Day 45

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a hardware watchdog timer monitoring a firmware heartbeat, when the hardware and firmware teams each document their portions in separate specifications with no cross-references?

**Answer:** The fundamental issue here is that the risk management file treats the watchdog as a single integrated control, but the engineering artifacts treat it as two independent pieces. I'd start by creating a single "risk control implementation description" in the risk management file that explicitly names both the hardware element (the watchdog timer circuit) and the firmware element (the heartbeat generation), and assigns each a unique identifier within the risk control's implementation breakdown. This becomes the bridge document.

From there, I'd add cross-references in both directions: the hardware specification would note that the watchdog's purpose is to detect firmware heartbeat failure per risk control RC-XX, and the firmware specification would note that the heartbeat exists to keep the watchdog satisfied per the same risk control. Each team then traces their portion to the shared risk control ID rather than to each other's documents.

For verification, I'd argue that this control needs three levels of evidence: hardware-level verification that the watchdog timer actually resets the system when its timeout expires (which can be tested by simply not feeding it), firmware-level verification that the heartbeat is generated at the correct interval under normal operation, and system-level verification that the complete chain works — firmware heartbeat stops, watchdog times out, system resets. The system-level test is essential because it catches integration issues like the heartbeat being generated in an interrupt context that continues running even when the main application has hung.

**Possible follow-ups:** How would you handle the case where the firmware heartbeat is generated by a timer interrupt, so the main application loop can hang while the watchdog remains satisfied? What level of documentation detail would you require in each team's specification to ensure the cross-reference is meaningful?

## Q2: How would you approach determining whether a risk control measure that is implemented as a firmware-based plausibility check on a sensor reading needs to be verified on the actual production hardware, or whether testing on a development board with the same microcontroller is sufficient?

**Answer:** The key question is whether the risk control's behavior depends on anything that differs between the development board and production hardware. For a pure algorithmic plausibility check — say, rejecting readings that change faster than a specified rate — the logic itself is microcontroller-independent, and a host-PC unit test could theoretically verify the algorithm. However, the risk control's *effectiveness* depends on the timing and sequencing of real sensor data, which involves the actual sensor interface, interrupt timing, and the interaction between the plausibility check and other firmware tasks.

I'd approach this by analyzing what failure modes the plausibility check is meant to mitigate. If it's protecting against a sensor that fails by producing erratic readings, then the check needs to be tested with realistic sensor failure modes — which means exercising the actual sensor interface. If it's protecting against a sensor that drifts slowly out of range, the check might need to be tested with simulated sensor data injected at the driver level, which could be done on a development board.

My general rule would be: the verification environment must be representative of anything that could affect the control's behavior. For a plausibility check, that means the same microcontroller (for timing behavior), the same sensor interface (for signal characteristics), and the same firmware scheduling context (for task timing). A development board with the same MCU and the actual sensor connected would likely be sufficient for most cases. But I'd document the rationale for why the development board is representative, and I'd flag any differences — like different decoupling, different PCB layout affecting analog signal integrity — that could plausibly affect the sensor readings the check operates on.

**Possible follow-ups:** What specific differences between a development board and production hardware would cause you to insist on production-hardware testing? How would you document the rationale for using a development board in the verification report?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification test, but the test was written to verify a different requirement and only incidentally exercises the risk control under nominal conditions — so it passes, but it never actually stresses the failure condition the control is meant to mitigate?

**Answer:** This is a traceability integrity problem — the link exists on paper, but the verification evidence doesn't actually demonstrate the control works. The first step is to recognize that a passing test under nominal conditions provides no evidence that a risk control works under the fault conditions it's designed to address. A risk control that only needs to work under nominal conditions isn't a risk control at all.

I'd approach this by going back to the risk analysis to identify the specific failure condition the control mitigates, then asking: does the test actually create that failure condition? If not, the test is inadequate for verifying the risk control, regardless of whether it adequately verifies the other requirement it was written for.

The fix is to either modify the existing test to include the fault injection, or create a separate test specifically for the risk control. I'd also review other risk controls to check whether the same pattern exists elsewhere — a test that passes under nominal conditions but doesn't stress the failure mode is a systemic issue, not an isolated one. This might indicate that the verification planning process didn't explicitly map each risk control to a test that creates the relevant fault condition.

I'd also update the traceability matrix to distinguish between "incidentally exercised" and "specifically verified" — the matrix should show that the risk control has its own dedicated verification activity, not just that it happens to be active during another test.

**Possible follow-ups:** How would you determine whether a test that exercises the control under nominal conditions provides *any* useful evidence, even if it's not sufficient on its own? What would you do if the dedicated fault-injection test is significantly more complex or expensive than the nominal test?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system has a safety mechanism that can be bypassed or overridden by a clinician — for example, a "disable alarm" button on a patient monitoring device — and the override itself introduces a new hazard?

**Answer:** This is a case where the risk control creates a secondary risk, which ISO 14971 explicitly requires you to analyze. The traceability scheme needs to capture both the original hazard-control relationship and the new hazard introduced by the override mechanism itself.

I'd structure this as a chain: the original hazard (e.g., undetected patient deterioration) is mitigated by the alarm system. The alarm system includes a clinician override, which introduces a new hazard (e.g., alarm disabled while patient condition worsens). That new hazard needs its own risk control measures — perhaps a visual indicator that the alarm is disabled, an automatic re-enable after a timeout, or an audible reminder at intervals.

For traceability, I'd create explicit links showing: Hazard 1 → Risk Control 1 (alarm system) → Requirement for alarm functionality → Verification of alarm functionality. Then separately: Risk Control 1 introduces Hazard 2 (override leaves patient unprotected) → Risk Control 2 (override timeout and visual indicator) → Requirements for the timeout and indicator → Verification of those requirements.

The critical traceability point is that the override mechanism must trace to *both* the original hazard (as part of the control) and the new hazard (as a hazard source). I'd make this explicit in the risk management file and in the traceability matrix, so reviewers can see that the override was analyzed for its own risks, not just treated as a feature.

I'd also ensure that verification covers both the intended function of the override (alarm actually disables) and the risk controls on the override (alarm re-enables after timeout, indicator is visible). The override's failure modes need their own fault-injection testing — for example, what happens if the override button sticks, or if the timeout mechanism fails?

**Possible follow-ups:** How would you determine whether the override should be a one-time temporary action or a sustained mode change, from a risk perspective? How would you handle the case where the clinician override is necessary for patient care but conflicts with the risk control's intent?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has created a traceability matrix that links every risk control measure to a verification activity, but during a review, you discover that several of the verification activities are scheduled for the very end of the project, after all design work is complete. The program manager argues this is efficient because it avoids rework — the design is finalized before testing begins. The quality manager argues that late verification means design errors are discovered too late, causing expensive rework and schedule delays. How would you resolve this disagreement?

**Answer:** I'd start by acknowledging that both perspectives have merit — the program manager is right that testing a moving target wastes effort, and the quality manager is right that finding a design flaw in final verification is the most expensive possible outcome. The disagreement isn't really about whether to verify, but about when and how to stage verification activities.

I'd propose a middle path: not all verification needs to happen at the end. I'd work with the team to categorize risk control measures by how mature the design needs to be before meaningful verification can occur. Some controls can be verified early — for example, a hardware comparator's trip point can be tested on a breadboard or early prototype. Others genuinely need the final design — like EMC testing or full system integration.

The key insight I'd bring to the discussion is that early verification of risk controls isn't about testing the final design — it's about testing the *concept* and the *implementation approach*. If a risk control's fundamental approach is flawed, you want to know that before you've committed to the full design. If the approach is sound, early verification can be repeated or supplemented later on production-representative hardware.

I'd propose a staged verification plan: concept-level verification during design (to validate the approach), design-level verification on engineering prototypes (to validate the implementation), and final verification on production-representative units (to validate the actual product). Each stage answers different questions, and each stage catches different classes of errors. This gives the program manager early confidence that the design is on track, and gives the quality manager assurance that problems won't be discovered only at the very end.

I'd also suggest that the team identify which risk controls are highest-risk or most likely to have design issues, and prioritize those for earlier verification. This isn't about doing all verification early — it's about doing the *right* verification at the *right* time.

**Possible follow-ups:** How would you handle the program manager's concern that early verification results might become invalid if the design changes later? What criteria would you use to decide which risk controls should be verified early versus which can wait until final verification?
