# risk-requirements-traceability — Day 109

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement exists but has lost its safety intent — it reads like a performance feature rather than a risk control, so nothing downstream forces anyone to verify it against the hazard. I'd start by treating the risk analysis entry as the authoritative source and working forward from it: the hazard (overspeed), the hazardous situation, and the specific control (rate limiting) should each be given a stable identifier in the risk management file. Then I'd create an explicit link from that risk control identifier to the firmware requirement, and — critically — amend the requirement text so it carries the safety rationale, something like a "derived from risk control RC-xx, mitigates hazardous overspeed" annotation. That annotation is what makes the link survive future edits, because a requirement that only says "clamp rate of change" can be quietly relaxed by someone who doesn't know why it's there.

The second half is verification. The rate limiter needs a test whose acceptance criteria are expressed against the hazard, not just against the nominal function — i.e., the test must demonstrate that under a command step large enough to cause overspeed, the output rate of change stays within the limit, and that the limit is the one the risk analysis assumed. I'd also want the parameter (the maximum rate) to be traceable as a safety-related constant, so that if it's changed the risk file is flagged. Finally, I'd add a bidirectional check: from the hazard down to the requirement and test, and from the requirement back up to the hazard, so a gap analysis catches either a control with no requirement or a requirement with no hazard justification.

**Possible follow-ups:** If the rate limiter is one of several controls against the same overspeed hazard, how do you avoid double-counting its risk reduction in the risk estimation? And how would you handle it if the firmware team argues the clamping is "obviously" safe and resists adding the hazard reference to the requirement?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap with a distributed control loop is that the risk analysis credits one control, but the implementation is spread across three elements owned by different people, so no single requirement or test actually demonstrates the control works. I'd resist the temptation to just link the one risk control to one system-level requirement and call it done — that produces a matrix that looks complete but has no teeth. Instead I'd decompose the loop into its constituent functions and make each one a traceable element: the sensor's accuracy and response time, the PID loop's behavior including saturation and anti-windup, and the power switch's ability to actually interrupt the heater. Each of those gets its own requirement with measurable acceptance criteria, and each traces back to the same parent risk control.

Then the verification strategy has two layers. At the element level, each requirement is verified in isolation — sensor characterization, loop response under step and fault inputs, switch timing. At the integrated level, the whole loop is verified against the hazard: does the heating element stay within the safe range under the worst-case combination the risk analysis assumed, including a sensor that's drifting and a loop that's saturated? The integrated test is the one that actually demonstrates the control, but the element-level tests are what let you diagnose a failure and what let you argue the control is robust rather than lucky. I'd also make the interface between the elements explicit — the sensor-to-firmware signal and the firmware-to-switch command — so that a change to any one element triggers a review of the loop-level verification.

**Possible follow-ups:** If the loop is credited as a single control, how do you handle the risk estimation when one element (say the sensor) is far less reliable than the others? And how would you structure the traceability so that a firmware change to the PID gains automatically flags the loop-level test for re-run?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review actually assesses the thing the control is supposed to do. A generic power supply checklist will cover topology, derating, and layout, but it won't necessarily ask "does this supply hold its output within the range the risk analysis assumed when the input browns out" — so the link exists on paper but the evidence doesn't support the claim. My first move would be to look at what the review actually recorded and decide whether it genuinely covers the failure condition. If it does, even incidentally, I'd document that explicitly rather than leave it implicit. If it doesn't, the link is invalid and I'd treat it as a gap.

The fix is to make the review criteria traceable to the risk control. I'd add a review checklist item that states the specific failure condition and the acceptance question the reviewer must answer, and record the reviewer's conclusion against that item. That converts a vague "reviewed and acceptable" into objective evidence tied to the control. Where the failure condition is better assessed by test or analysis than by review, I'd reclassify the verification method rather than force it into a review. The principle is that the verification method should match the nature of the claim: a review is good for "is this designed correctly," a test is good for "does it behave correctly under this condition," and analysis is good for "does the margin hold across the range." Mismatching them is how you get a matrix that passes audit but doesn't actually demonstrate safety.

**Possible follow-ups:** How would you handle a reviewer who says the checklist item is redundant because "the design review already covers the whole supply"? And if you reclassify the verification from review to test, how do you manage the schedule impact late in the project?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a piece of code — it's a value, and the value varies per unit, so the traceability has to cover three things: the parameter's definition and allowed range, the process that sets it, and the verification that each unit's value is correct. I'd start by making the parameter a first-class requirement with a specified range and tolerance, derived from the risk analysis, and give it an identifier that the risk control links to. The requirement should state not just the nominal value but the acceptable window and what happens if a unit falls outside it.

Then I'd trace the manufacturing process itself as part of the control's implementation. The programming step, the calibration procedure, and the end-of-line check are all part of how the control is realized, so they need to be documented and linked — the control isn't "the parameter exists," it's "the parameter is set correctly on every unit and verified before shipment." The end-of-line test becomes the per-unit verification activity, and its acceptance criteria come straight from the requirement's tolerance window. I'd also want a way to detect drift or tampering after shipment if the parameter is accessible via a service port, which means the risk analysis should consider whether the parameter can be changed in the field and whether that change reintroduces the hazard. Finally, I'd keep a record linking each unit's serial number to its programmed value, so that if a problem is found later you can bound the affected population rather than recalling everything.

**Possible follow-ups:** If the parameter can be reprogrammed in the field, how does that change the traceability and the risk analysis? And how would you handle a manufacturing deviation where a batch was programmed to a value just inside the tolerance but not the nominal?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd take the test engineer's concern seriously and treat it as a signal that the matrix is structurally complete but substantively unverified — which is the more dangerous failure mode, because it looks fine to an auditor. My first step would be to gather evidence rather than argue: pick the specific tests in question and compare what each test actually does against the failure condition in the risk analysis. If the test exercises the failure condition, the copied origin doesn't matter and I'd document that conclusion. If it doesn't, that's a real gap regardless of what the matrix says, and I'd bring that evidence to the systems engineer rather than debating the principle.

I'd frame the conversation around the shared goal — demonstrating the control works — rather than around compliance. The systems engineer is right that the matrix is compliant; the point is that compliance isn't the same as evidence. I'd propose a targeted review of the suspect tests against their risk control entries, prioritized by severity, and re-run or rewrite only the ones that don't actually stress the failure condition. I'd also want to understand why the tests were copied — usually it's schedule pressure or a template that made copying easier than thinking — and fix the root cause, for example by requiring each test to cite the specific failure condition it exercises. Finally, I'd make sure the finding and the corrective action are recorded, because quietly fixing it without a record leaves the same weakness in the process for the next project.

**Possible follow-ups:** How would you handle it if the systems engineer escalates and the program manager sides with "the matrix is compliant, ship it"? And how would you prevent test-copying from recurring without adding so much process that the team routes around it?
