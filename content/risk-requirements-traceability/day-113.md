# risk-requirements-traceability — Day 113

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement captures the *mechanism* but not the *intent*, so the traceability link from hazard to requirement is broken at the semantic level even if a link exists on paper. I'd start by making the safety intent explicit in the requirement itself — rewriting it so it states both the functional behavior and the hazard it mitigates, or adding a derived safety requirement that references the risk control ID. From there, the traceability chain becomes: hazard → risk control measure → safety requirement (with the clamping behavior as its acceptance criterion) → firmware design element (the rate-limiter module) → verification test. The verification test is where this really matters: it must demonstrate that the limiter actually prevents the hazardous overspeed condition, not just that the clamp function returns the expected value in a unit test. That means a test that commands a step change large enough to produce hazardous overspeed if unclamped, and confirms the output rate stays within the limit under worst-case conditions (max command delta, worst-case loop timing, boundary values of the rate constant). I'd also check that the rate constant itself is treated as a safety-related parameter — its value, its units, and its tolerance should be justified against the hazard analysis, not just picked for smooth motion. Finally, I'd add a bidirectional check: from the hazard entry, can I walk down to the specific firmware requirement and test? If the firmware requirement doesn't mention the hazard, that walk fails and I fix the requirement, not the matrix.

**Possible follow-ups:** If the rate limiter is one of several controls mitigating the same overspeed hazard, how do you avoid double-counting its risk reduction credit? And how would you handle the case where the rate constant is configurable at runtime — does the verification then need to cover the range of configurable values?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap with a distributed control is that the risk analysis credits a single control, but the implementation is spread across three elements owned by different disciplines, so a naive matrix either links the control to one requirement (losing the others) or links it to three unrelated requirements (losing the fact that they must work *together*). I'd decompose the control into its constituent safety functions and make each one a traceable requirement with its own acceptance criterion: the sensor path must report temperature within a stated accuracy and latency; the PID loop must compute and command an output that keeps the element within the safe band under defined load and ambient conditions; the power switch must be capable of removing power within a stated time and must fail safe on loss of control signal. Then I'd add an *integration* requirement and verification that exercises the loop as a whole — because the individual pieces can each pass while the combination fails (e.g., sensor latency plus loop period exceeds the thermal time constant). The traceability structure I'd use is a parent risk control measure with child requirements per element plus one system-level integration requirement, all linked back to the same hazard. The verification plan then has module-level tests for each element and a system-level test for the integrated loop, and the risk file references both. The key discipline is that the integration test must be traceable to the *control*, not just to the integration requirement, so an auditor can see the whole path from hazard to the test that proves the loop holds the element safe.

**Possible follow-ups:** How do you allocate the safe-band budget across sensor accuracy, loop timing, and switch response so each element's requirement is individually verifiable? And if the PID loop is later retuned, which traceability links need to be re-examined?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence for some controls — particularly ones that are inherently design-rule-based, like creepage distances or derating — but only if the review actually assesses the specific failure condition the control addresses. A generic power-supply checklist that never asks "does this design prevent the hazardous condition the risk analysis credits it for?" is not evidence for that control, even if the review happened and passed. My approach would be to make the review criteria traceable: add explicit review checklist items derived from the risk control measures, each phrased as a question about the specific failure mode and its mitigation, with a recorded disposition. That converts the review from a general quality gate into a targeted verification activity with objective evidence — reviewer, date, the specific item, the finding, and the closure. I'd also make sure the review record captures *what was examined* (schematic reference, calculation, simulation) so the evidence is auditable, not just a sign-off. If the existing review has already happened without those items, I'd either re-run a focused review against the risk-derived checklist or supplement with analysis or test, depending on what the control needs. The principle is that the verification method (review, analysis, test, inspection) is fine, but the *content* of the method must be derived from the risk control, not borrowed from a generic template.

**Possible follow-ups:** How would you decide whether a focused re-review is sufficient versus needing a physical test? And how do you keep risk-derived review checklist items from becoming so numerous that reviewers rubber-stamp them?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a line of code — it's a *value*, and the traceability has to cover the value's derivation, its programming, and its per-unit verification. I'd structure it in three layers. First, a requirement that defines the parameter: its meaning, units, valid range, the method by which the correct value is determined for a given unit (e.g., derived from a calibration measurement or a component tolerance stack), and the tolerance on the value itself. Second, a manufacturing/production requirement and procedure that programs the value and verifies it was programmed correctly — this is where per-unit traceability lives, tied to the serial number and the production record. Third, a design verification that the *mechanism* works: that the firmware reads the parameter correctly, that out-of-range or corrupted values are handled safely (default to a safe limit, refuse to operate, etc.), and that the limit actually constrains the output as intended. The risk file links the hazard to the parameter requirement, and the parameter requirement links to both the design verification (mechanism) and the production verification (per-unit value). The subtle point is that design verification proves the *system* enforces whatever limit is programmed, while production verification proves *this unit* has the right limit programmed — you need both, and they trace to different evidence. I'd also make sure the parameter's valid range and the safe default are themselves justified in the risk analysis, because a unit with a missing or corrupted value is a foreseeable condition.

**Possible follow-ups:** How would you verify that a corrupted or out-of-range stored value fails safe rather than disabling the protection? And how do you keep the production record traceable to the risk control when the value is unit-specific?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd treat this as a substantive quality issue rather than a documentation dispute, and I'd be careful not to frame it as an accusation of the test engineer — they did the right thing by raising it. The matrix being complete and the tests passing tells me the *form* of traceability is intact, but the question is whether the evidence is *valid* — whether each test actually exercises the failure condition the risk control addresses. My first step would be to sample a few of the flagged tests and walk them against the risk analysis entry: does the test setup create the fault condition, does the acceptance criterion map to the control's intended effect, and would the test fail if the control were disabled? That last question — the negative test — is the quickest way to distinguish a real verification from a copied one. If the sample confirms the concern, I'd scope the remediation: re-derive test requirements from the risk controls for the affected items, rewrite or add tests where the failure condition isn't exercised, and re-run. I'd bring the systems engineer along by reframing the goal — the matrix exists to demonstrate the controls work, and a test that can't fail when the control is removed doesn't demonstrate that, so the matrix isn't actually doing its job even though it's compliant on paper. I'd also look at the root cause: if tests are being copied because of schedule pressure or because the risk analysis isn't easily readable by the test team, that's a process fix — making risk control intent visible in the test requirements, and building in a review step where the test author confirms the failure condition is exercised. The outcome I'd want is a matrix that's both compliant and *true*, with the audit trail showing the re-verification.

**Possible follow-ups:** How would you prioritize which tests to re-examine first if you can't re-verify everything before the next milestone? And how would you prevent copied tests from creeping back in on the next project — what process change would you put in place?
