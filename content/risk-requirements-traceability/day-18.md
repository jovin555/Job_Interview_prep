# risk-requirements-traceability — Day 18

## Q1: How would you approach establishing traceability for risk control measures that are implemented purely through software configuration parameters — for example, a maximum motor speed limit stored in non-volatile memory that can be changed via a service port — when the risk analysis treats the parameter value itself as the control?

**Answer:** This is a genuinely tricky case because the risk control isn't a piece of code logic or a hardware circuit — it's a *value* that lives in configuration data. The first thing I'd do is clarify what the actual risk control is: is it the parameter itself, or is it the combination of the parameter plus the firmware mechanism that enforces it? In practice, the enforceable control is the firmware that reads the parameter and limits motor speed accordingly — the parameter is just the setpoint. So I'd trace the control to the firmware requirement that specifies the enforcement behavior (e.g., "the system shall limit motor speed to the value stored in configuration memory"), and I'd treat the parameter value as an input to that requirement rather than a separate control.

For traceability, I'd create a link from the hazard → risk control measure → firmware requirement → verification activity. The verification would need two parts: first, a test that demonstrates the enforcement mechanism actually limits speed when the parameter is set to a given value; second, a test or inspection that verifies the specific parameter value stored in the production configuration is the one specified in the risk analysis. The second part is often overlooked — you can have a perfectly functioning enforcement mechanism with the wrong setpoint programmed in. I'd also consider whether the service port itself introduces new risks: if the parameter can be changed in the field, the risk analysis needs to address what happens if someone sets it to an unsafe value. That might require a range-checking control in firmware, which would be a separate risk control measure with its own traceability path.

**Possible follow-ups:** How would you handle the case where the parameter value is derived from a calibration procedure rather than being a fixed constant? What if the same parameter is used for both safety and performance purposes — how would you separate those concerns in the traceability scheme?

## Q2: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system uses a hardware-only control in one product variant and a firmware-only control in another variant to mitigate the same hazard, and the two variants share a common SRS?

**Answer:** The key challenge here is that you have one hazard, one risk control measure at the system level, but two different implementations. The common SRS should state the system-level requirement — for example, "the system shall prevent motor operation when the lid is open" — without prescribing the implementation. That requirement traces up to the hazard and down to variant-specific design elements. Below that, the traceability branches: for the hardware variant, the requirement traces to the hardware design specification (e.g., a physical interlock switch in series with the motor supply); for the firmware variant, it traces to the software requirements specification (e.g., a firmware routine that reads the lid sensor and disables the motor driver).

I'd structure the traceability matrix with the variant as an explicit column or attribute, so each link is tagged with which variant it applies to. The verification activities would also be variant-specific: the hardware variant might use a continuity test to verify the interlock physically breaks the circuit, while the firmware variant might use a dynamic test that opens the lid during operation and observes the motor stopping. The risk management file should document both implementations and note that the risk control is achieved through different means in each variant. One important detail: if the variants share a common SRS, the requirement text must be implementation-neutral, or you'll end up with a requirement that only makes sense for one variant. If the SRS requirement is written as "the system shall have a hardware interlock," then the firmware variant can't trace to it cleanly.

**Possible follow-ups:** How would you handle a mid-project decision to switch one variant from hardware to firmware implementation — what traceability artifacts would need to change? How would you ensure the residual risk evaluation considers both implementations equally?

## Q3: During a design verification campaign, you discover that a risk control requirement was verified using a test that exercises the control in isolation (e.g., applying a test signal directly to the comparator input), but the risk analysis specifies that the control must be verified in the context of the full system, including the sensor that generates the signal. How would you address this discrepancy?

**Answer:** This is a common and important gap. The isolated test proves the comparator works when given a known input, but it doesn't prove the *system* works — the sensor, its interface circuitry, the PCB routing, and the comparator all have to function together for the risk control to actually mitigate the hazard. The discrepancy suggests the verification plan and the risk analysis weren't reconciled during test planning.

My approach would be to first assess whether the isolated test is still valuable — it is, as a module-level verification that isolates the comparator's behavior from other system variables. But it's not sufficient on its own. I'd then determine what system-level test is needed: one that stimulates the actual sensor (or a representative stimulus that exercises the full signal chain) and observes the system response. The key is that the system-level test must stress the *failure condition* — for example, if the hazard is over-temperature, the test should drive the actual temperature sensor past the trip point, not inject a signal directly at the comparator input.

I'd document the discrepancy in the verification gap analysis, add the system-level test to the verification plan, and update the traceability matrix to show both the module-level and system-level tests as complementary evidence. I'd also review whether other risk controls have the same issue — if one test was written at the wrong level, others might be too. Finally, I'd check whether the risk analysis itself needs clarification: if it says "verify in system context," the verification plan should have captured that explicitly. If the risk analysis is ambiguous about the verification level, that's a documentation gap to fix.

**Possible follow-ups:** What if the system-level test is impractical because the sensor can't be safely stimulated to the fault condition — how would you justify an alternative approach? How would you handle the situation where the isolated test passes but the system-level test fails?

## Q4: How would you approach determining whether a risk control measure that is implemented as a combination of hardware and firmware — for example, a hardware sensor detecting an over-temperature condition and firmware deciding to shut down a motor — should be verified as a complete system, or whether separate hardware and firmware verification is sufficient?

**Answer:** The short answer is that you need both levels, but they serve different purposes. Separate hardware and firmware verification is necessary to isolate each element's contribution — you want to verify the sensor and its interface circuitry produce the correct signal, and you want to verify the firmware correctly interprets that signal and commands the motor shutdown. But separate verification is not sufficient, because the risk control only works when the two elements function together correctly. The interface between them — the electrical characteristics of the sensor signal, the firmware's interpretation of that signal, timing, noise, and edge cases — can only be verified at the system level.

My approach would be to define a verification hierarchy. At the module level: hardware tests verify the sensor produces the expected output across its operating range and that the interface circuitry conditions the signal correctly; firmware tests verify the decision logic — given a simulated sensor input, does the firmware command the shutdown within the required time? At the system level: a test with the actual sensor and actual firmware verifies the end-to-end behavior — when the temperature crosses the threshold, the motor actually stops. The system-level test is where you catch integration issues: a sensor that's slow to respond, a firmware filter that delays the response, or a noise issue on the signal line that causes false trips.

I'd also consider the failure modes that span the boundary. For example, what happens if the sensor fails open versus shorted? The hardware might detect one failure mode but not the other, and the firmware might need to handle both. These cross-boundary failure modes are exactly what separate hardware and firmware testing will miss. The traceability matrix should show the risk control tracing to both the module-level and system-level verification activities, with the system-level test being the primary evidence that the integrated control works.

**Possible follow-ups:** How would you decide what constitutes an acceptable system-level test when the fault condition is difficult or dangerous to reproduce? How would you handle the case where the hardware and firmware teams have different verification schedules, and the system-level test can't happen until both are complete?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has created a traceability matrix that links every risk control measure to a verification activity, but during a review, you discover that several of the verification activities are actually "verification by similarity" — meaning the team is relying on test results from a previous product that used a similar component or design. The quality manager argues that similarity is not acceptable evidence for risk controls, because the previous product wasn't tested under the same conditions. The systems engineer argues that the components are identical, the design is nearly the same, and re-running the tests would waste time and money. How would you resolve this disagreement?

**Answer:** I'd start by acknowledging that both sides have legitimate points. The systems engineer is right that re-running identical tests on an identical component in a nearly identical design can be low-value — the results are likely to be the same, and the cost is real. The quality manager is right that "similar" is a slippery slope: if you accept similarity for one control, where do you draw the line? And the previous product may not have been tested under the same conditions, which means the evidence may not actually cover the risk control's failure modes.

My approach would be to establish objective criteria for when similarity is acceptable, rather than arguing about this specific case in the abstract. I'd propose a structured assessment: first, document the specific differences between the previous product and the current one — component revision, PCB layout, operating environment, interface circuitry, firmware version. Second, assess whether any of those differences could plausibly affect the risk control's behavior. If the component is identical, the layout is the same, and the operating conditions are within the tested range, similarity might be defensible. If there's any meaningful difference — a different PCB stack-up, a different firmware version that interacts with the component, a different thermal environment — then similarity is not sufficient.

I'd also distinguish between different types of risk controls. For a passive component like a resistor used for current limiting, similarity might be perfectly acceptable — the physics haven't changed. For an active component like a sensor with a firmware interface, similarity is much harder to justify because the interaction between hardware and firmware is design-specific. I'd propose that similarity can be used as supporting evidence, but not as the sole evidence, for risk controls that involve active components or firmware interaction. For those, I'd require at least a targeted test that exercises the specific failure condition.

Finally, I'd make sure the decision is documented in the risk management file with clear justification. If we accept similarity for some controls, the rationale needs to be recorded — not just "the components are the same," but a systematic analysis of why the previous test results remain valid for this design. This turns the disagreement into a process improvement rather than a one-off argument.

**Possible follow-ups:** How would you handle a situation where the previous product's test data is incomplete — for example, the test was performed but the conditions weren't fully documented? What criteria would you use to determine whether a "minor" design change invalidates similarity evidence?
