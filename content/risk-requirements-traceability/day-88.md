# risk-requirements-traceability — Day 88

## Q1: How would you approach tracing a risk control measure that is implemented as a *combination of a hardware interlock and a firmware acknowledgment* — for example, a relay that physically removes power from a heater unless firmware continuously asserts an enable signal — when the hardware and firmware teams each own half of the control and neither team's requirements document references the other?

**Answer:** The core problem is that the control is a *contract* between two subsystems, and a contract that neither party has written down is not traceable. I'd start by treating the combined control as a single risk control measure in the risk management file, with an explicit statement of the safety intent — what hazard it mitigates, what the safe state is, and what the failure condition looks like. From there I'd decompose it into two halves that are each independently verifiable but jointly necessary: a hardware requirement (the relay must de-energize the heater when the enable signal is absent or invalid) and a firmware requirement (the firmware must assert the enable signal only while all preconditions are satisfied, and must de-assert it on any detected fault). The key is to make the *interface* between them a first-class requirement — the enable signal's polarity, timing, and failure mode (what happens on an open circuit, a stuck-at fault, a floating input) — and to put that interface requirement in both documents with a shared identifier, or better, in an interface control document that both teams reference. Then the traceability matrix shows the risk control measure fanning out to the hardware requirement, the firmware requirement, and the ICD entry, and each of those traces to its own verification activity, plus a system-level integration test that exercises the combined behavior. Without that integration test, you can have both halves pass in isolation and still have a control that doesn't work — for example, firmware that asserts enable correctly but hardware whose relay driver fails open.

**Possible follow-ups:** How would you decide whether the interface requirement belongs in the SRS, the ICD, or both? What would you do if the hardware team's relay driver has a failure mode that the firmware team's enable logic can't detect?

## Q2: How would you approach establishing traceability for a risk control measure that is implemented as a *timing requirement* — for example, "the system shall remove power from the heating element within 500 ms of detecting an over-temperature condition" — when the timing depends on a chain of hardware and firmware elements, each with its own latency, and the 500 ms budget is allocated across them?

**Answer:** A timing requirement that spans a chain is really a *budget*, and the traceability has to follow the budget down to each contributor. I'd start by decomposing the 500 ms into an allocation: sensor response time, analog front-end settling, ADC conversion and interrupt latency, firmware detection and decision time, and the actuator/relay drop-out time. Each allocation becomes a derived requirement owned by a specific element, and each traces back up to the parent timing requirement and the risk control measure it implements. The traceability matrix then shows the parent requirement, the allocation table, and the individual derived requirements with their verification activities — bench measurement of the sensor path, timing analysis or measurement of the firmware loop, and measurement of the relay drop-out. The subtle part is that no single test verifies the 500 ms; you need a system-level test that measures end-to-end from a physical over-temperature stimulus to power removal, and you need the allocation to have margin so that worst-case stack-up of each element's latency still fits inside the budget. I'd also make sure the allocation is documented with the assumptions behind it — clock tolerance, interrupt priority, worst-case execution path — because those assumptions are what the verification is actually confirming. If any element's measured latency exceeds its allocation, the traceability tells you exactly which requirement and which verification activity needs to be revisited.

**Possible follow-ups:** How would you verify the end-to-end timing without a test fixture that can inject a real over-temperature condition fast enough? What happens to the traceability if one element's latency is later found to be worse than allocated — how do you propagate that change?

## Q3: How would you approach creating a traceability scheme that connects risk control measures to requirements when a single risk control measure is implemented *redundantly* — the same hazard is mitigated by two independent controls, and the risk analysis credits both — but the two controls are owned by different teams and were added at different times in the project?

**Answer:** Redundancy is where traceability most often quietly breaks, because each team traces its own control and nobody traces the *pairing*. I'd start by making the risk management file explicit that this hazard has two credited controls and what the credit assumption is — specifically, that the controls are independent, meaning a single failure mode can't disable both. That independence claim is itself a requirement, and it needs its own verification: a common-cause failure analysis, and ideally a test that confirms each control works with the other disabled. Then each control gets its own requirement and its own verification activity, traced normally, but I'd add a cross-reference between the two so the matrix shows they're a redundant pair mitigating the same hazard. The "added at different times" problem is the real risk — the second control may have been added later without revisiting the first control's assumptions, or the two may share a hidden dependency (same power rail, same sensor, same firmware task) that undermines the independence credit. So I'd do a deliberate independence review of the pair, document the shared elements and whether they're acceptable, and record that review as part of the risk management file. The traceability scheme should make it impossible to look at either control in isolation and miss that it's half of a redundant pair.

**Possible follow-ups:** If the independence review finds the two controls share a power rail, how would you handle the risk analysis credit — reduce it, add a third control, or something else? How would you structure the matrix so an auditor can see at a glance that both controls are credited to the same hazard?

## Q4: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *manual* test with no automated logging — the operator toggles a signal and observes an LED — and the risk file treats it as objective evidence?

**Answer:** The question is whether the evidence is *objective* and *reproducible*, not whether it's automated. A manual test can be perfectly valid objective evidence if the procedure is written precisely enough that a different operator would reach the same conclusion, and if the record captures what was actually observed rather than just a checkbox. So I'd first look at the test procedure: does it specify the exact stimulus, the exact expected response, the acceptance criterion in measurable terms, and the pass/fail decision rule? "Toggle signal, observe LED" is not that — it's underspecified, because "observed LED" doesn't say whether the LED was on, off, blinking, or the wrong color, and it doesn't say what the operator should do if the response is ambiguous. I'd rewrite the procedure to be unambiguous, add a record sheet that captures the actual observation (with a photo or a signed witness where appropriate), and require the operator to record the specific value or state observed, not just "pass." Where the risk control is safety-critical and the manual test is the only verification, I'd push to add instrumentation — a scope capture, a data logger, a firmware debug output — so the evidence is a measurement rather than a human judgment. The risk file should then reference the procedure and the record as the evidence, and the traceability link should point to the controlled procedure document, not to a vague "test performed" note.

**Possible follow-ups:** How would you handle a manual test where the acceptance criterion is inherently subjective, like "the alarm is audible in a noisy environment"? What would you do if the operator who performed the test is no longer available and the record is ambiguous?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file lists a risk control measure, the SRS contains a requirement that implements it, and the verification plan contains a test that verifies the requirement — but when you trace the links, you find that the requirement was written by the systems engineer, the test was written by the test engineer, and neither of them has ever read the risk analysis entry that justifies the control. The links exist on paper, but the *intent* of the control has been lost between the documents. How would you handle this?

**Answer:** This is the classic failure mode of traceability done as a paperwork exercise rather than as a communication tool — the links are structurally correct but semantically empty, and that's more dangerous than a missing link because it looks compliant. My first move would be to stop treating it as a documentation problem and treat it as a shared-understanding problem. I'd get the systems engineer, the test engineer, and whoever owns the risk analysis entry into a room with the three artifacts and walk the chain backwards: start from the hazard, read the risk control measure aloud, then ask "does this requirement actually implement this control, and does this test actually demonstrate the control works under the failure condition the risk analysis describes?" Very often the answer is "the requirement captures the function but not the safety intent" — for example, the requirement says "disable the motor output within 100 ms of a fault signal" but doesn't say the control exists to prevent a hazardous over-speed, so the test engineer wrote a test that checks the 100 ms timing under nominal conditions and never exercises the fault path. The fix is to make the safety intent explicit in the requirement itself — a rationale field or a linked hazard ID — so anyone reading the requirement downstream knows *why* it exists and what failure it's guarding against. Then I'd re-review the test against that intent and add the fault-condition coverage that's missing. Longer term, I'd change the process so that the risk analysis entry is a required input to both requirement authoring and test authoring, and so that design reviews check semantic traceability, not just link existence.

**Possible follow-ups:** How would you make semantic traceability reviewable at scale, when you have hundreds of requirements and can't walk every chain in a meeting? If the test engineer pushes back and says the test is adequate because it passes, how do you make the case that passing isn't the same as verifying the control?
