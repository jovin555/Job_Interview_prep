# risk-requirements-traceability — Day 73

## Q1: How would you approach tracing a risk control measure whose effectiveness depends on a *sequence* of events rather than a single action — for example, a control that requires the system to detect a fault, log it, notify the user, and then enter a safe state, where each step is owned by a different subsystem?

**Answer:** The key insight is that the risk control is not any one of those steps — it is the *ordered, bounded completion* of the whole sequence. So the traceability artifact has to represent the control as a single logical entity with a defined sequence, and then decompose that entity into per-step requirements that each carry a reference back to the parent control ID. In practice I'd create a control-level identifier in the risk management file, then derive a small set of child requirements — one per step — each tagged with that parent ID, plus an explicit requirement for the sequencing and timing constraints between steps (ordering, maximum latency from detection to safe state, what happens if a step fails). Verification then has two layers: per-step verification that each subsystem does its part, and an integration-level verification that the sequence completes within its bounded time under the fault condition. The failure mode people miss is verifying each step in isolation and declaring the control verified, when the actual hazard arises from the sequence stalling or reordering. So the traceability matrix needs a row for the integrated sequence test, not just the per-step tests.

**Possible follow-ups:**
- If the notification step is a user-facing alert and the safe-state step is automatic, how would you decide whether they can be verified by the same test or need separate evidence?
- What would you do if one subsystem team argues their step is "not a safety requirement" because it's just logging?

## Q2: How would you approach deciding whether a risk control measure should be traced to a *design requirement*, a *design element*, or *both* — and what practical difference does that distinction make in a traceability matrix?

**Answer:** The distinction matters because requirements and design elements answer different questions. A requirement states *what must be true* — a measurable, verifiable obligation. A design element is *how it is realized* — a circuit block, a firmware module, a mechanical feature. A risk control measure usually needs to be traced to a requirement first, because that's what gives you something verifiable with an acceptance criterion. Tracing to a design element is useful when the control is realized through a specific implementation whose properties matter — for example, a creepage distance on a PCB, a particular component's derating margin, or a specific state machine. In those cases the design element *is* the control, and the "requirement" may be a design constraint rather than a functional behavior. Practically, I'd trace the control to a requirement wherever a measurable acceptance criterion can be written, and additionally to the design element where the control's correctness depends on implementation-specific properties that a functional test can't fully capture. The matrix then shows both links, and the verification activity is chosen to match — a test for the requirement, an inspection or analysis for the design element. The failure mode is tracing only to the design element and then having no verifiable requirement, which makes the control hard to audit.

**Possible follow-ups:**
- If a control is traced to a design element but not to a requirement, how would you justify that in a design review?
- How would you handle a control that is realized by a design element but whose requirement is expressed only as a design constraint rather than a functional behavior?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity's test procedure was written against an earlier revision of the requirement, so the test still passes but no longer exercises the current acceptance criteria?

**Answer:** This is a configuration-control problem as much as a traceability problem. The first step is to confirm the drift: compare the requirement revision referenced by the test procedure against the current requirement revision, and identify what changed — a threshold, a timing bound, a condition, a tolerance. If the change is material to the control's effectiveness, the test is no longer valid evidence and needs to be re-baselined. If the change is editorial or non-material, that still needs to be documented, because an auditor will ask why the test references an obsolete revision. The fix is procedural: test procedures should reference the requirement by ID *and* revision, and any change to a requirement that has a linked verification activity should trigger a review of that activity. In a mature process this is a change-impact step in the requirements management workflow — when a requirement is modified, the tool flags linked tests for re-review. The deeper issue is that if this happened once, it probably happened elsewhere, so I'd run a coverage check across the matrix for revision mismatches rather than fixing only the one that was found.

**Possible follow-ups:**
- If the requirement change was a tightening of a threshold, but the old test still passes at the new threshold by coincidence, is the test valid?
- How would you prevent this class of drift in a tool that doesn't natively support revision-aware links?

## Q4: (Behavioral) Imagine you're leading a project where the risk management file lists a risk control measure, the SRS contains a requirement that implements it, and the verification plan contains a test that verifies the requirement — but when you trace the links, you find that the requirement was written by the systems engineer, the test was written by the test engineer, and neither of them has ever read the risk analysis entry that justifies the control. The links exist on paper, but the *intent* of the control has been lost between the documents. How would you handle this?

**Answer:** The links are structurally correct but semantically empty, which is the most dangerous kind of traceability gap because it passes a mechanical audit. My first move is not to blame anyone — it's to recognize that the process allowed this to happen, because the risk analysis, the SRS, and the verification plan were authored in separate workflows with no shared review of the control's intent. I'd fix the immediate instance by pulling the three artifacts together for the affected controls and having the systems engineer, test engineer, and whoever owns the risk analysis walk through each one: what hazard does this control mitigate, what failure condition must it detect, what does "working" look like, and does the test actually exercise that condition. Where the test doesn't, it gets rewritten. Then I'd fix the process so this doesn't recur — the most effective lever is to make the risk analysis entry visible at the point where the requirement and the test are written, for example by carrying a short "safety intent" statement alongside the requirement ID, and by including the risk owner in the review of any requirement derived from a risk control. The goal is that the person writing the test understands *why* the control exists, not just which requirement number it maps to.

**Possible follow-ups:**
- How would you scale that review if there are dozens of controls and the schedule is tight?
- What artifact would you point to as evidence that the intent is now captured, if an auditor asked?

## Q5: How would you approach establishing traceability for a risk control measure that is implemented as a *timing requirement* — for example, "the system shall remove power from the heating element within a bounded time after an over-temperature condition is detected" — when the timing depends on a chain of hardware and firmware elements, each with its own latency, and the total budget is allocated across them?

**Answer:** The control is the end-to-end latency, so the traceability artifact has to represent the budget as a single requirement with a single acceptance criterion, and then decompose it into allocated sub-budgets per element in the chain — sensor response, signal conditioning, ADC conversion, firmware detection and decision, output driver turn-off, and any communication delay if the decision is made on a different node. Each sub-budget becomes a derived requirement owned by the relevant subsystem, each traced back to the parent timing requirement. Verification then has two levels: per-element verification that each stays within its allocated sub-budget, and an end-to-end verification that the total is met under the worst-case combination — because the worst case is not the sum of typical latencies, it's the sum of worst-case latencies, and that's the number the hazard analysis cares about. The subtlety is that the budget allocation itself is a design decision that should be justified in the risk analysis, and any change to one element's latency has to be checked against the total. So the traceability matrix needs to show the parent-child relationship between the total requirement and the sub-budgets, and the verification plan needs both the per-element tests and the integrated timing test. Without the integrated test, you can have every element passing its own budget and still miss the total.

**Possible follow-ups:**
- If the end-to-end test is difficult to instrument because the fault condition is hard to induce, how would you get objective evidence?
- How would you handle a situation where one element's worst-case latency is only known from a datasheet maximum rather than measured?
