# risk-requirements-traceability — Day 105

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *hysteresis-based thermal cutoff* — a hardware comparator with a fixed trip point and a deliberate reset band — where the risk analysis credits the control against overheating, but the requirement only states "the system shall disable heating above the maximum safe temperature" without specifying the reset behavior or the hysteresis band?
**Answer:** The gap here is that the requirement captures only half of the control's actual behavior. A hysteresis-based cutoff has two distinct thresholds — the trip point and the reset point — and the reset band is not incidental: it prevents the heater from chattering on and off around a single threshold, which is itself a hazard contributor (contact wear, thermal cycling, and in the worst case a stuck-on heater if the comparator oscillates). So the first step is to treat the requirement as incomplete rather than the traceability as complete. I'd go back to the risk analysis entry and ask what failure condition the control is actually mitigating: is it "temperature exceeds safe limit" alone, or is it "temperature exceeds safe limit and the system must not re-enable heating until it has cooled to a safe margin"? If the latter, the requirement needs to be rewritten to capture both thresholds and the band, with measurable acceptance criteria — trip point, reset point, and tolerance on each. Then the verification activity must demonstrate both edges, not just the trip. On the traceability side, I'd link the single risk control measure to two derived requirements (trip and reset) rather than forcing one requirement to carry both, because a test that only exercises the trip edge will pass while leaving the reset behavior unverified. The practical rule I'd apply: if a control has more than one observable threshold or state transition, it needs more than one requirement, and the traceability matrix should show the one-to-many relationship explicitly so a reviewer can see that both edges are covered.
**Possible follow-ups:** If the risk analysis genuinely only credits the trip point and treats the reset band as a design convenience, how would you decide whether the reset behavior needs its own requirement at all? And how would you handle the case where the hysteresis band is set by component tolerances rather than by a firmware or trim adjustment — does that change how you write the acceptance criterion?

## Q2: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *field service procedure* — for example, a maintenance step that requires the technician to verify a ground connection before returning the device to service — rather than a design verification test?
**Answer:** This is a case where the "verification" is really a process control, not a design verification, and the traceability scheme needs to distinguish the two. A field service procedure verifies that a *particular unit* is in a safe state at a *particular time*; it does not verify that the *design* reliably achieves the control across the population and across the life of the device. So the first question I'd ask is: what is the risk control actually credited against? If the hazard is "device returned to service with a compromised ground connection," then the service procedure is a legitimate risk control — but it's a *procedural* control, and its verification is not a bench test but evidence that the procedure is correctly written, that technicians are trained to it, and that the procedure is actually followed (audit records, training records, maybe a usability or human-factors validation). If the hazard is "ground connection can fail in the field," then the service procedure is not a control at all — it's a detection mechanism at best, and the real control has to be a design feature (redundant grounding, a ground-fault monitor, a connector that can't be partially mated). The traceability mistake I'd want to avoid is letting a procedural control get traced to a design verification test that doesn't exist, which creates the appearance of coverage. In the matrix I'd want a column or tag that identifies the control type — design, protective, or information-for-safety — because the verification evidence for each is fundamentally different, and mixing them in one matrix without that distinction is how gaps hide.
**Possible follow-ups:** If the procedural control is the only mitigation for a hazard and the design cannot practically eliminate it, how would you argue that the residual risk is acceptable in the risk management report? And how would you trace the training and audit records into the traceability matrix without turning it into a document that tries to cover everything and ends up covering nothing well?

## Q3: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system has a *safety-related parameter that is derived at runtime* — for example, a maximum allowable motor current that is computed from a temperature reading and a lookup table at startup — rather than being a fixed constant or a manufacturing-set value?
**Answer:** The interesting problem here is that the control's *value* is not fixed at design time, so neither a single requirement nor a single test can pin it down. What's fixed is the *function* that computes the limit and the *bounds* on that function — the lookup table, the temperature range over which it's valid, the clamping behavior outside that range, and the failure behavior if the temperature reading is invalid. So I'd decompose the control into a set of requirements that are each individually verifiable: the lookup table itself (verified by inspection or by a table-driven test against the specified breakpoints), the interpolation or clamping behavior (verified by boundary tests at and beyond the table edges), the handling of an invalid or out-of-range temperature input (verified by fault injection), and the enforcement of the resulting limit on the actuator command (verified by a command-path test). The traceability link then goes from the single risk control measure to this *family* of requirements, and each requirement to its own verification. The key discipline is that the risk analysis entry should state the *envelope* — the range of current limits the control can produce and the conditions under which each applies — because that envelope is what the residual risk evaluation is actually based on. If the risk analysis says "current limited to X" but the runtime function can produce 1.5X at low temperature, the traceability is formally complete and substantively wrong. I'd also want the runtime-computed value to be observable in the logs or service interface, so that verification and post-market surveillance can confirm the function is producing values inside the envelope on real units, not just on the bench.
**Possible follow-ups:** How would you verify a lookup-table-based limit without exhaustively testing every temperature point, and what would you put in the verification record to justify the sampling? And if the lookup table is updated in a firmware revision, what does that do to the traceability links and the prior verification evidence?

## Q4: How would you approach deciding whether a risk control measure should be traced to a *design requirement*, a *design element*, or *both* — and what practical difference does that distinction make in a traceability matrix?
**Answer:** The distinction matters because the two links answer different questions and fail in different ways. A link to a *design requirement* answers "is the intended behavior specified and verifiable?" — it's the link that lets you confirm the control is testable and that a verification activity exists. A link to a *design element* answers "is the thing that implements the control actually present in the design, and can I point to it?" — it's the link that lets you confirm the control wasn't specified but never built, or was built in a way that doesn't match the requirement. In practice I'd want both for any control that is implemented in a concrete artifact, because each catches a different class of gap: a requirement with no design element is a spec that was never implemented; a design element with no requirement is an implementation nobody specified or verified. The practical difference in the matrix is that the design-element link is often where the *cross-team* handoffs live — the hardware schematic page, the firmware module, the mechanical drawing — and those are exactly the places where a control can silently fall between teams. So I'd structure the matrix with separate columns for requirement link and design-element link, and I'd treat a control that has one but not the other as an open item rather than a complete row. The exception is controls that are purely procedural or purely analytical (a derating calculation, a label), where there may be no design element in the schematic sense — for those, the "design element" is the analysis document or the label artwork, and I'd still want a link, just to a different kind of artifact.
**Possible follow-ups:** In a matrix with thousands of rows, how would you keep the design-element links maintainable as the design changes, without the matrix going stale every time a schematic page is renumbered? And would you ever accept a control traced only to a design element with no requirement, on the grounds that the requirement would be redundant with the design documentation?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file, the SRS, and the verification plan are each internally consistent and each passes its own review — but when you trace across all three, you find that a risk control measure is linked to a requirement that is linked to a test, and the test passes, yet the *combination* doesn't actually demonstrate the control works, because the requirement was written at a level of abstraction the test can satisfy without exercising the control's failure condition. The three document owners each argue their document is correct. How would you handle this?
**Answer:** I'd start by reframing the disagreement so it isn't about whose document is wrong — because in a narrow sense, none of them are. Each document is internally consistent; the failure is in the *seams* between them, and seams don't belong to any single owner. The way I'd make that concrete is to walk the chain backwards from the hazard: take the risk analysis entry, read the failure condition it's mitigating, and ask "if I only had this test result, could I conclude the failure condition is mitigated?" If the answer is no — and in this scenario it's no — then the gap is visible to everyone in the room without anyone having to concede their document is defective. From there the fix is usually at the requirement level: the requirement is too abstract to force a test that stresses the failure condition, so it needs to be rewritten with a measurable acceptance criterion tied to the failure condition, and the test rewritten against that criterion. I'd assign that as a joint action between the requirements owner and the test owner, with the risk owner confirming the rewritten requirement still reflects the intended control. The process fix I'd put in place afterward is a cross-document trace review — not three separate document reviews, but one review that walks hazard → control → requirement → test as a single chain — because that's the only review that can catch a seam failure. I'd also want the traceability matrix to carry the failure condition (or a reference to it) alongside the requirement ID, so that a reviewer comparing requirement to test can see what the test is supposed to stress, not just which requirement number it points at.
**Possible follow-ups:** How would you get the three document owners to accept a joint review without it feeling like a blame exercise, especially if the project is already under schedule pressure? And if the rewritten requirement changes the acceptance criterion, what happens to the verification evidence that was already collected against the old criterion — is it invalidated, or can any of it be reused?
