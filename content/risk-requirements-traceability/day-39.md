# risk-requirements-traceability — Day 39

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a combination of hardware and firmware, where the hardware team documents the control in their design specification and the firmware team documents their portion in a software requirements document — but neither document references the other, and the risk management file treats the control as a single integrated measure?

**Answer:** This is a common challenge when a single risk control spans multiple engineering disciplines. The core problem is that the risk management file treats the control as one integrated measure, but the implementation artifacts are fragmented across two separate document trees with no cross-references. My approach would be to create a "control implementation record" — a single artifact that lives in the risk management file and serves as the bridge between the hazard analysis and the engineering documents. This record would define the control at the system level, describe the complete implementation chain (sensor → signal conditioning → firmware decision → actuator), and then explicitly reference the specific hardware design specification section and the specific software requirements document section that implement each portion. The key is that this record becomes the single point of truth for the control's implementation, and both engineering documents would need to reference it back. I would also establish a naming convention — for example, each risk control gets a unique identifier (like RC-014) that appears in both the hardware and firmware documents, so a reviewer can immediately see that a given hardware circuit and a given firmware function are both part of the same control. This creates bidirectional traceability: from the hazard to the control, from the control to each implementation element, and from each implementation element back to the control. Without this bridging artifact, you end up with two partial traceability chains that don't connect, and a reviewer cannot verify that the complete control is actually implemented.

**Possible follow-ups:**
- How would you handle the situation where the hardware and firmware teams use different numbering schemes for their documents, and neither wants to adopt the other's scheme?
- What would you do if the risk management file already exists and was created before the hardware and firmware documents were written — how would you retrofit the traceability?

## Q2: How would you approach determining whether a risk control measure that is implemented as a firmware-based plausibility check on a sensor reading — for example, rejecting readings that change by more than a specified rate between consecutive samples — needs to be verified on the actual production hardware, or whether testing on a development board with the same microcontroller is sufficient?

**Answer:** The key question here is whether the plausibility check's behavior depends on characteristics that differ between the development board and the production hardware. For a rate-of-change check on a sensor reading, I would consider several factors. First, does the check depend on timing? If the plausibility window is defined in terms of real time (e.g., "reject readings that change by more than X% within 100ms"), then the verification must account for the actual clock speed, interrupt latency, and scheduling behavior of the production firmware running on the target hardware. A development board with the same microcontroller might have different peripheral configurations, different interrupt priorities, or different bus speeds that could affect timing. Second, does the check depend on the actual sensor interface? If the plausibility check is validating readings from a specific sensor over a specific bus (e.g., I2C or SPI), then the verification should exercise the real sensor interface, including realistic noise, timing variations, and fault conditions. A development board might use a different sensor or a simulated input. Third, does the check interact with other firmware modules? If the plausibility check runs in the context of a larger firmware architecture — with other tasks, interrupts, and shared resources — then the verification should reflect that context. My general approach would be to start with a risk-based assessment: what is the consequence if the plausibility check fails to detect an invalid reading? For a medical device, the consequence could be patient harm, so the verification evidence needs to be strong. I would likely require verification on production-representative hardware for the final qualification, but I would also use development board testing earlier in the cycle for iterative debugging and initial validation of the algorithm. The development board testing can catch logic errors and algorithm issues, but the production hardware verification is necessary to confirm that the check works correctly in the actual system context — with real timing, real sensor behavior, and real firmware integration.

**Possible follow-ups:**
- What specific test cases would you design to verify the plausibility check on production hardware?
- How would you handle the situation where the production hardware is not available until late in the project, but the firmware team wants to proceed with verification on the development board to save time?

## Q3: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system has a distributed architecture — multiple microcontrollers, each running separate firmware, communicating over a shared bus — and a single hazard is mitigated by coordinated actions across multiple nodes?

**Answer:** This is a challenging scenario because the hazard is mitigated by a coordinated sequence of actions across multiple nodes, and the traceability needs to capture not just the individual actions but the coordination itself. My approach would be to model the control as a system-level behavior rather than as separate node-level functions. I would start by defining the control at the system level in the risk management file — for example, "the system shall detect an over-temperature condition and shut down the motor within 500ms." Then I would decompose this into node-level responsibilities: Node A detects the temperature and broadcasts a shutdown command; Node B receives the command and de-energizes the motor driver; Node C logs the event and alerts the operator. Each of these node-level responsibilities becomes a requirement in the respective node's requirements document. The critical part is the coordination — the timing requirement (500ms) spans multiple nodes, and the traceability must capture the end-to-end timing budget. I would create a system-level interface control document that defines the message format, the timing requirements, and the expected behavior of each node in the sequence. This ICD becomes a traceability artifact in its own right — it links the system-level control to the node-level requirements. For the traceability matrix, I would have a row for the system-level control, and then columns for each node's requirement, with the ICD reference capturing the coordination. The verification strategy would also need to be system-level: you can verify each node's individual behavior in isolation, but you also need an integration test that exercises the full sequence across the bus, including timing measurements. The key insight is that the coordination itself is a risk control element, and it needs its own traceability and verification — you can't just trace the individual node actions and assume the coordination works.

**Possible follow-ups:**
- How would you handle the situation where the bus communication itself introduces a failure mode — for example, a message being corrupted or delayed — and the risk control depends on the message arriving within a specific time window?
- How would you allocate the end-to-end timing budget across the nodes, and how would you verify that each node meets its portion of the budget?

## Q4: How would you approach handling a situation where a risk control measure is traced to a verification test, but the test was written to verify a *different* requirement and only incidentally exercises the risk control under nominal conditions — so it passes, but it never actually stresses the failure condition the control is meant to mitigate?

**Answer:** This is a traceability integrity problem — the link exists on paper, but the verification evidence doesn't actually demonstrate that the control works. My first step would be to flag the discrepancy and initiate a gap analysis. I would review the risk control's failure condition as defined in the risk management file, and then compare it against the test procedure to identify exactly what conditions the test exercises. The key question is: does the test apply the specific stimulus or fault condition that the control is designed to detect and respond to? If the test only exercises nominal conditions, then it provides no evidence that the control actually works when it needs to. I would document this gap formally — in a design verification gap report or a non-conformance report — and then work with the test engineer to design a new test or modify the existing test to include the failure condition. The new test would need to: (1) inject the specific fault or abnormal condition that the control is designed to detect, (2) verify that the control responds correctly (e.g., the alarm triggers, the motor shuts down, the system enters safe state), and (3) verify that the response happens within the required time or with the required behavior. I would also review other traceability links to check for similar issues — if one test was incorrectly linked, others might be too. This is a systemic issue, not just a single test problem. I would also revisit the test design process to understand how this happened — was the test written without reference to the risk control's failure condition? Was the traceability link created after the fact without reviewing the test content? The corrective action would include updating the test design process to require that each risk control verification test explicitly state which failure condition it exercises and how.

**Possible follow-ups:**
- How would you handle the situation where the test engineer argues that the existing test is "good enough" because it exercises the system under normal conditions and the risk control is "just a safety net"?
- What would you do if the corrected test reveals that the risk control actually doesn't work under the failure condition — how would you manage the impact on the design and the project schedule?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has created a traceability matrix that links every risk control measure to a verification activity, but during a review, you discover that several of the verification activities are actually "verification by similarity" — meaning the team is relying on test results from a previous product that used a similar component or design. The quality manager argues that similarity is not acceptable evidence for risk controls, because the previous product wasn't tested under the same conditions. The systems engineer argues that the components are identical, the design is nearly the same, and re-running the tests would waste time and money. How would you resolve this disagreement?

**Answer:** I would start by acknowledging that both sides have valid points. The systems engineer is right that re-running tests on identical components in nearly identical designs can feel wasteful, and there are legitimate cases where similarity arguments are accepted — for example, when a component is used in exactly the same way with the same operating conditions and the same surrounding circuitry. The quality manager is also right that risk controls need objective evidence, and similarity arguments can be weak if the conditions differ in ways that matter. My approach would be to move from a binary "similarity is acceptable" versus "similarity is not acceptable" debate to a structured assessment of what the similarity claim actually covers. I would ask the systems engineer to document, for each "verification by similarity" item: (1) exactly which component or design element is claimed to be similar, (2) what the previous test actually verified, (3) what conditions the previous test was run under, and (4) how the current product's conditions compare — same operating voltage, same temperature range, same surrounding circuitry, same firmware interaction, same mechanical mounting, etc. Then I would convene a review with the quality manager, the systems engineer, and the relevant technical experts to assess each item. For some items, the similarity argument might hold — for example, if the component is identical, the operating conditions are within the same range, and the previous test was run under conditions that encompass the current product's requirements. For other items, the similarity argument might fail — for example, if the previous product used the component in a different circuit configuration, or the previous test didn't exercise the specific failure mode that the risk control is meant to mitigate. For items where similarity is accepted, I would document the rationale in the verification record — not just "similarity" but a detailed justification of why the previous evidence is applicable. For items where similarity is rejected, I would work with the team to plan the necessary testing. I would also establish a general principle: similarity can be used as supporting evidence, but it should not be the sole evidence for a risk control that mitigates a high-severity hazard. The higher the risk, the stronger the evidence needs to be.

**Possible follow-ups:**
- How would you handle the situation where the previous product's test data is incomplete — for example, the test was run but the records don't clearly document the test conditions?
- What criteria would you use to decide whether a similarity argument is strong enough to accept, versus when you would require new testing?
