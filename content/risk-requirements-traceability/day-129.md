# risk-requirements-traceability — Day 129

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement is technically correct but semantically orphaned — it describes *what* the firmware does without recording *why*, so the link from hazard to control exists only in the risk analyst's head. I'd fix this at the requirement level rather than trying to patch it in the matrix. First, I'd add an explicit safety-intent annotation to the firmware requirement — either a dedicated field or a linked note — that names the hazard, the risk control measure ID, and the failure condition the limiter is meant to prevent (commanded acceleration exceeding the safe envelope). That gives the matrix a real anchor to trace from, rather than a functional requirement that happens to be credited as a control. Second, I'd check that the requirement is actually *sufficient* as a control: a rate limiter credited against overspeed needs a measurable acceptance criterion — maximum rate of change, tolerance, and the conditions under which it must hold — not just "the firmware shall clamp the commanded rate." If the requirement is underspecified, the verification test can pass without exercising the failure condition. Third, I'd make sure the verification activity deliberately drives the input past the limit and confirms the clamp holds, including at the boundary and under worst-case command transients, rather than just confirming nominal behavior. Finally, I'd add a bidirectional check: from the hazard, confirm the control traces down to this requirement and test; from the requirement, confirm it traces back up to a hazard or is justified as a purely functional requirement. That bidirectional pass is what catches orphaned safety requirements.

**Possible follow-ups:** If the firmware team resists adding safety-intent annotations because it "clutters" the requirements document, how would you make the case? And how would you handle the situation where the same rate limiter is also a performance feature, so it has both a functional and a safety justification?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap with a distributed control is that the risk analysis credits one control, but no single requirement, design element, or test owns the whole thing — so the traceability matrix can look complete while the *integration* is untested. I'd start by decomposing the single risk control measure into its constituent elements at the architecture level: the sensing path, the control algorithm, and the actuation path, each with its own requirement and its own verification, but all parented to the same risk control ID. That gives you a tree rather than a single link. Then I'd add an explicit *integration* requirement and verification at the loop level — a test that exercises the whole loop end-to-end under the fault condition the control is meant to mitigate, because passing the three component tests individually does not demonstrate the loop works as a control. I'd also want the loop's timing and stability characteristics captured somewhere, since a distributed control's effectiveness often depends on latency and loop behavior that no single component requirement describes. In the matrix, I'd represent this as one risk control measure with multiple child requirements and a top-level integration verification, and I'd flag it so reviewers understand the control is emergent rather than localized. The key discipline is: never let a single matrix link stand in for a control that is actually distributed across subsystems.

**Possible follow-ups:** How would you decide where the boundary of the "loop" is for verification purposes — is testing the sensor, the algorithm, and the switch separately plus one integration test enough, or do you need fault injection at each element? And how would you handle the case where the PID loop is tuned at runtime and the tuning itself affects whether the control meets its safety intent?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review actually assesses the specific failure condition the control is meant to mitigate — a generic checklist that happens to touch the same subsystem is not evidence that the control works. I'd treat this as a gap in the verification activity rather than a gap in the traceability link. First, I'd add a review criterion specific to the risk control: an explicit question in the review checklist that asks the reviewers to confirm the control's failure condition is addressed, with a recorded conclusion. Second, I'd make sure the review record captures *who* assessed it and *what* they concluded, so the evidence is objective rather than implied by the review having happened. Third, I'd consider whether a design review is genuinely the right verification method for this control — for some controls (layout rules, derating, creepage) review or inspection is the appropriate method, but for a control whose effectiveness depends on behavior under a fault, a review alone is usually insufficient and a test or analysis should supplement it. The distinction I'd draw is between "verification by inspection/review" as a legitimate method for design-rule-type controls, and using a review as a substitute for behavioral verification of a control that has a dynamic failure mode. In the matrix, I'd want the verification method to be explicit and the acceptance criterion to be specific to the control, not inherited from a generic checklist.

**Possible follow-ups:** How would you retrofit a specific risk-control criterion into a review that's already been conducted and signed off? And how would you handle the case where the reviewer who assessed the control is the same engineer who designed it?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control is not a behavior but a *value*, and the traceability has to cover the value's derivation, its programming, and its verification on the unit — not just a functional requirement. I'd structure it in three layers. First, a requirement that defines the parameter's allowable range and the rule by which the value is determined for a given unit (the derivation, whether from a calibration measurement, a component tolerance, or a fixed table). Second, a manufacturing/programming requirement that specifies how the value is written, read back, and protected — because a control that depends on a stored value is only as good as the integrity of that storage and the readback check. Third, a verification activity that confirms, on the unit, that the programmed value is within the allowed range and that the system actually enforces the limit at that value — not just that the value was written. The traceability matrix needs to link the risk control measure to all three, and I'd want the manufacturing record to be part of the objective evidence, since the value differs per unit and a single design-verification test on one unit doesn't demonstrate the control holds across the population. I'd also flag the population aspect: if the value varies per unit, the verification strategy has to address the range of values, not just a nominal one, and there should be a process control that prevents an out-of-range value from being programmed and shipped.

**Possible follow-ups:** How would you verify that the enforcement actually tracks the programmed value rather than a hard-coded default that happens to be close? And how would you handle a service scenario where the parameter can be changed in the field — does that change the traceability and verification approach?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file, the SRS, and the verification plan are each internally consistent and each passes its own review — but when you trace across all three, you find that a risk control measure is linked to a requirement that is linked to a test, and the test passes, yet the *combination* doesn't actually demonstrate the control works, because the requirement was written at a level of abstraction the test can satisfy without exercising the control's failure condition. The three document owners each argue their document is correct. How would you handle this?

**Answer:** The first thing I'd do is reframe the disagreement so it isn't about whose document is wrong — because in a narrow sense, all three owners are right: each document is internally consistent. The problem is at the *seams* between documents, and that's a shared ownership problem, not an individual one. I'd bring the three owners together with the specific trace in front of them and walk the chain end to end: here is the hazard, here is the control, here is the requirement that implements it, here is the test that verifies it — and then ask the concrete question: if we disabled this control, would this test fail? If the answer is no, the chain doesn't demonstrate the control, regardless of the links being present. That single question usually dissolves the "my document is correct" framing because it's an empirical test of the chain, not a judgment about any one document. From there, I'd drive a fix at the weakest link — usually the requirement's abstraction level, which needs a measurable acceptance criterion tied to the failure condition — and then re-derive the test from that criterion. I'd also add a cross-document trace review as a standing gate, because this class of defect is invisible to document-level reviews by design. The leadership point I'd emphasize is that traceability is only meaningful if it's verified *across* documents, and that means the owners have to review the seams together, not just their own pages.

**Possible follow-ups:** How would you structure that cross-document review so it becomes a routine gate rather than a one-off rescue? And if the test owner pushes back that rewriting the test is out of scope for the current phase, how would you prioritize the fix against schedule pressure?
