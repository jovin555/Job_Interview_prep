# risk-requirements-traceability — Day 103

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the link exists in the risk file but the *intent* is missing from the requirement, so anyone reading the firmware spec in isolation would see a performance behavior rather than a safety control. I'd start by treating the risk analysis entry as the authoritative source and working outward from it: the hazard, the hazardous situation, and the credited control become the anchor, and the firmware requirement must be reworded (or supplemented) so it explicitly states that the clamping behavior is a risk control for the overspeed hazard, not merely a smoothness feature. That gives the requirement a safety classification, which in turn drives the verification rigor — the test must demonstrate that the clamp actually prevents the hazardous condition, not just that the output changes gradually.

Practically, I'd add a bidirectional link: from the risk control measure to the firmware requirement ID, and from the requirement back to the hazard ID. I'd also make sure the acceptance criterion is measurable in hazard terms — for example, a maximum rate of change expressed as a value the test can measure, plus a demonstration that the actuator cannot reach the hazardous speed under the fault condition the limiter is meant to cover. The subtle trap here is that a rate limiter can be defeated by a fault it doesn't cover (e.g., a stuck command that ramps slowly but still reaches a dangerous value), so the verification should confirm the limiter is effective against the specific failure mode credited in the risk analysis, not just against nominal step inputs.

**Possible follow-ups:** If the firmware team argues the requirement is "just a performance spec" and resists reclassifying it as a safety requirement, how would you make the case? / How would you verify the limiter under a fault condition where the command source itself is misbehaving?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The difficulty is that the risk analysis credits an emergent property — the loop keeps temperature safe — but no single element owns that property, so a naive traceability matrix either links the control to one arbitrary element or to nothing at all. I'd decompose the control into its constituent functions and allocate sub-requirements to each element, each with its own measurable acceptance criterion, while keeping a single parent risk control ID that all of them trace back to. The sensor path gets a requirement about accuracy, range, and response time; the firmware gets a requirement about the control law, update rate, and behavior on sensor fault; the power switch gets a requirement about switching authority, fail-safe state, and independence from the firmware. Each sub-requirement then traces to its own verification, and the parent control traces to an integrated system-level test that demonstrates the loop as a whole holds temperature within the safe band under the fault conditions in the risk analysis.

The key discipline is that the integrated test is not optional — passing the three element-level tests does not prove the loop works, because the failure modes that matter (sensor drift, firmware saturation, switch welding) are interactions. I'd also document the assumed independence between elements explicitly, because if the sensor and the switch share a power rail, the "distributed" control may not be as robust as the risk analysis assumes, and that assumption needs to be visible in the traceability so it can be challenged.

**Possible follow-ups:** How would you handle the case where the integrated test is expensive or slow to run, and the team wants to rely on element-level tests plus analysis? / What would you do if the risk analysis credits the loop as a single control but the loop has no single owner in the org chart?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review actually assesses the thing the control is supposed to do. A generic checklist that happens to touch the same subsystem is not evidence that the specific failure condition was evaluated — it's evidence that the subsystem was reviewed for general quality. So the first step is to read the checklist against the risk control's failure condition and ask: is there a line item that would fail if the control were absent or ineffective? If not, the traceability link is nominal only.

I'd fix it by adding a targeted review criterion — a specific question the reviewers must answer, with a recorded conclusion — and re-running that portion of the review with the risk analysis entry in front of the reviewers. The output should be objective evidence: a signed record that the specific failure condition was considered, what the reviewers concluded, and any actions raised. I'd also consider whether a review is the right verification method at all for this control; if the control's effectiveness is behavioral or timing-dependent, a review may be insufficient and a test or analysis may be needed. The general principle is that the verification method must be capable of detecting the failure the control prevents, and the traceability link should record *why* that method was judged adequate.

**Possible follow-ups:** How would you decide between adding a review criterion versus replacing the review with a test? / If the review already happened and the project is late, how would you handle the rework without derailing the schedule?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control is not a behavior in the design but a *value* in a unit, so the traceability has to cover three distinct things: the requirement that defines the parameter and its allowable range, the manufacturing process that programs the value, and the per-unit verification that confirms the programmed value is correct. I'd create a requirement for the parameter itself — its name, units, allowable range, and the rationale tied to the hazard — and then trace it forward to two verification activities: a design-level verification that the firmware/hardware correctly enforces the limit when programmed, and a production test that confirms each unit's stored value is within the allowed range and that the limit is actually active.

The tricky part is that the risk analysis credits the parameter value as the control, but the value varies per unit, so the risk file can't cite a single number. I'd handle that by having the risk analysis reference the *range* and the *enforcement mechanism*, and by making the production record part of the objective evidence — the device history record shows what was programmed, and the production test shows it was verified. I'd also want a control on how the parameter can be changed after manufacturing (service port, firmware update), because if it's changeable in the field, the control's integrity depends on access control and change logging, and that needs its own requirement and verification.

**Possible follow-ups:** How would you verify that the limit is enforced, not just stored — i.e., that the firmware actually reads and applies the value? / What would you do if the production test only checks the stored value but never exercises the limit?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd treat this as a substantive quality issue rather than a documentation issue, and I'd be careful not to frame it as an accusation of the test engineer — they did the right thing by raising it. The matrix being complete on paper is not the same as the controls being verified; if the tests don't exercise this project's failure conditions, the traceability is nominal and the risk file's claim of verification is unsupported. The systems engineer's position — "it passes, so there's no problem" — conflates passing with being meaningful, and that's exactly the gap I'd want to close.

My approach would be to sample a few of the flagged tests and walk through them against the risk analysis entry with the test engineer and systems engineer in the room: what failure condition is this control supposed to mitigate, what does the test actually do, and would the test fail if the control were disabled? That last question is the decisive one — a test that passes with the control disabled is not verifying the control. Where the sample shows a real gap, I'd scope the rework: rewrite the affected tests to stress the actual failure condition, re-run them, and update the traceability records to reflect the new evidence. I'd also want to understand *why* the copy-and-relabel happened — schedule pressure, unclear requirements, no review of test adequacy — because fixing the tests without fixing the cause just moves the problem to the next project. And I'd communicate it upward as a finding with a remediation plan rather than letting it sit, since an auditor asking the same question later would be a much worse outcome.

**Possible follow-ups:** How would you handle the conversation with the systems engineer who believes the matrix is fine? / If the rework is significant and the schedule is tight, how would you prioritize which tests to fix first?
