# risk-requirements-traceability — Day 29

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a combination of hardware and firmware, where the hardware team documents the control in their design specification and the firmware team documents their portion in a software requirements document — but neither document references the other, and the risk management file treats the control as a single integrated measure?

**Answer:** The core problem here is that the risk management file treats the control as one logical measure, but the implementation artifacts are split across two engineering disciplines with independent documentation. I'd start by creating a single "risk control implementation" record in the risk management file that explicitly lists every implementation element — the hardware sensor, the firmware decision logic, the actuator — as separate traceable items under one control ID. Each element would then link to its respective design document. The key is establishing a cross-reference convention: the hardware design specification should contain a note like "this circuit implements risk control RC-014, see firmware requirement FW-221 for the response logic," and the firmware document should carry the reciprocal reference. In practice, I'd add a dedicated traceability section to both documents rather than trying to force a single numbering scheme across disciplines. For verification, I'd require three levels of evidence: hardware-level tests for the sensor/condition detection, firmware-level tests for the decision logic, and a system-level test that exercises the complete chain end-to-end. The system-level test is essential because it proves the integration — that the hardware actually triggers the firmware response as intended. Without that cross-referencing, you risk having a hardware team verify their comparator trips correctly and a firmware team verify their shutdown routine works, but nobody proves the interrupt actually reaches the firmware and triggers the shutdown in the real system.

**Possible follow-ups:**
- How would you handle the situation where the hardware and firmware teams use different requirement management tools that don't integrate with each other?
- What level of detail would you require in the cross-references — just document IDs, or also specific signal names, pin assignments, and timing parameters?

## Q2: How would you approach determining whether a risk control measure that is implemented as a firmware-based plausibility check on a sensor reading — for example, rejecting readings that change by more than a specified rate between consecutive samples — needs to be verified on the actual production hardware, or whether testing on a development board with the same microcontroller is sufficient?

**Answer:** The decision hinges on what aspects of the risk control's behavior could differ between the development board and production hardware. For a plausibility check, I'd analyze the failure modes the control is meant to mitigate and ask: does the check depend on timing characteristics, interrupt latency, ADC behavior, or interaction with other peripherals that might differ? If the check is purely algorithmic — comparing two consecutive values and rejecting if the delta exceeds a threshold — and the microcontroller is identical, a development board might be sufficient for the logic itself. However, the risk control's effectiveness often depends on the sensor interface: the ADC reference voltage, the sensor's analog output characteristics, noise on the power supply, and the actual signal conditioning circuitry. Those are production-hardware-specific. My approach would be to decompose the verification into layers: unit-level testing of the algorithm on the development board (or even host PC), integration testing of the sensor-to-firmware path on production-representative hardware, and system-level testing that exercises the complete hazard scenario. The critical question is whether the plausibility check's timing budget — how quickly it must detect and respond to a fault — is affected by the hardware. If the check must respond within a hard real-time deadline, you need to verify on the actual production hardware because interrupt latency, bus contention, and clock behavior can vary. I'd also consider whether the production hardware has additional features that could interfere — a watchdog timer, other interrupts at higher priority, or power management states that could delay the check. If any of those exist, development-board testing alone is insufficient.

**Possible follow-ups:**
- What specific information would you look for in the risk analysis to determine whether the timing of the plausibility check is safety-critical?
- How would you document the rationale for choosing development-board testing versus production-hardware testing in the verification plan?

## Q3: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system has a distributed architecture — multiple microcontrollers, each running separate firmware, communicating over a shared bus — and a single hazard is mitigated by coordinated actions across multiple nodes?

**Answer:** This is one of the more challenging traceability scenarios because the risk control doesn't live in any single subsystem — it's emergent from the coordinated behavior of multiple nodes. I'd approach this by first defining the hazard and the overall risk control at the system level, then decomposing it into node-specific responsibilities. Each node's contribution becomes a separate requirement in that node's firmware requirements document, but crucially, each of those requirements must carry a reference back to the same system-level risk control ID. The traceability scheme would have a hub-and-spoke structure: the risk control ID at the center, with spokes to each node's requirement, and then from each requirement to that node's verification activity. But the critical piece is the system-level integration test that proves the coordinated behavior — that when node A detects the fault and broadcasts the message, node B receives it within the required latency and takes the required action. That integration test traces to the risk control ID directly, not to any single node's requirement. I'd also need to address the communication protocol itself as a risk-relevant element: the message format, the timing requirements, and the failure behavior (what happens if the message is corrupted or lost). Those protocol requirements need their own traceability, typically in an interface control document, and they trace to the same risk control. One practical technique is to create a "risk control coordination matrix" that shows, for each hazard, which nodes participate, what each node does, what messages flow between them, and what timing constraints apply. This matrix becomes the bridge between the risk management file and the individual subsystem documents.

**Possible follow-ups:**
- How would you handle the situation where one node's contribution to the risk control is verified at the node level, but the coordination timing can only be verified at the system level?
- What happens if the communication bus itself is a potential failure point — how would you trace the bus failure modes and their mitigations?

## Q4: How would you approach handling a situation where a risk control measure is traced to a verification test, but the test was written to verify a *different* requirement and only incidentally exercises the risk control under nominal conditions — so it passes, but it never actually stresses the failure condition the control is meant to mitigate?

**Answer:** This is a classic traceability gap that looks fine on paper but fails in practice. The first step is to recognize that a traceability link is only meaningful if the verification activity actually exercises the risk control's failure condition — not just its nominal behavior. I'd start by reviewing the test procedure against the risk control's intended function, specifically looking at whether the test injects the fault or stress condition that the control is designed to detect and respond to. If the test only runs under nominal conditions, it's providing false confidence. My approach would be to flag this as a verification adequacy issue, not just a documentation issue. I'd work with the test engineer to either modify the existing test to include the fault injection, or create a new test specifically for the risk control. The key is to define what "stressing the failure condition" means for this particular control — for an overcurrent protection, it means actually driving the current above the threshold; for a plausibility check, it means feeding the sensor an implausible reading; for a watchdog, it means stopping the heartbeat. I'd also review the test's pass/fail criteria to ensure they're tied to the risk control's required behavior, not just to the nominal requirement. In terms of process, I'd document this as a verification gap in the traceability matrix, with a clear action item to either revise the test or add a new one. The traceability matrix should include a column for "failure condition exercised" or "fault injection method" so that reviewers can quickly identify which tests actually stress the risk control versus which merely exercise the system under normal conditions.

**Possible follow-ups:**
- How would you determine whether the existing test can be modified or whether a completely new test is needed?
- What would you do if the test engineer argues that adding fault injection to the test would make it too complex or time-consuming?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has created a traceability matrix that links every risk control measure to a verification activity, but during a review, you discover that several of the verification activities are actually "verification by analysis" — for example, a worst-case timing analysis or a thermal derating calculation — rather than physical tests. The quality manager argues that analysis is not objective evidence and demands physical testing for all risk controls. The systems engineer argues that some controls, like timing margins or thermal derating, can only be practically verified by analysis, and that physical testing would be impractical or impossible. How would you resolve this disagreement?

**Answer:** I'd start by acknowledging that both parties have legitimate concerns. The quality manager is right that analysis can be misused — it's easy to create a simulation that confirms your assumptions rather than challenging them. But the systems engineer is also right that some risk controls are inherently analytical in nature. A worst-case timing analysis, for example, often can't be fully verified by physical testing because you can't easily create the exact worst-case conditions — you'd need to manipulate clock skew, temperature, and voltage simultaneously in ways that may not be achievable on a test bench. My approach would be to establish criteria for when analysis is acceptable as verification evidence. First, the analysis must be based on validated models — the simulation or calculation tool must have been previously correlated against physical measurements. Second, the analysis must include conservative assumptions and clearly document them. Third, the analysis must be independently reviewed — ideally by someone who wasn't involved in creating it. Fourth, and most importantly, I'd require a physical test that provides partial confirmation of the analysis. For a timing analysis, that might be a test that measures actual interrupt latency under representative conditions, even if it can't hit the absolute worst case. For thermal derating, it might be a thermal imaging test at nominal load that confirms the thermal model's predictions. This gives you a "bracketed" verification approach: analysis covers the full range, physical testing validates the model at achievable points. I'd also ask the quality manager to identify which specific risk controls they're most concerned about, and work through those individually rather than making a blanket policy decision. Some controls genuinely need physical testing — a hardware fuse, for example, either blows or it doesn't. Others, like timing margins, may be better served by analysis plus targeted physical confirmation.

**Possible follow-ups:**
- How would you decide which specific risk controls require physical testing versus which can be verified by analysis?
- What would you do if the physical test results don't match the analysis predictions — how would you handle that discrepancy?
