# risk-requirements-traceability — Day 120

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the requirement captures *what the code does* but not *why it exists*, so the traceability link from hazard to requirement is implicit and fragile — anyone reading the SRS in isolation would see a performance behavior, not a safety control, and could reasonably deprioritize or "optimize" it later. I'd fix this at three levels. First, in the risk management file, make the control entry explicit and specific: name the hazardous situation (commanded rate of change exceeding a safe value), the control's intended effect (clamp the rate so the actuator cannot accelerate faster than the hazard analysis assumes), and the parameters that matter for safety (maximum rate, the time window over which it's computed, behavior at saturation). Second, in the SRS, either amend the existing functional requirement to carry a safety rationale and a reference back to the risk control ID, or add a derived safety requirement that states the safety-relevant performance envelope — the maximum permitted rate, the tolerance, and the required response — with a bidirectional link to the risk control. The functional description stays; what's added is the hazard reference and the measurable safety envelope. Third, in the verification plan, the test must not merely confirm "the output ramps smoothly" — it must drive the commanded input with a step or a rate that would violate the limit and demonstrate that the actual output is clamped within the specified tolerance, including at the boundary and under worst-case timing. I'd also check that the requirement's acceptance criterion is measurable (a numeric rate limit with tolerance), because a vague "shall limit the rate of change" cannot be objectively verified. The general principle: a risk control implemented in firmware needs its safety intent carried in the requirement text and its hazard link carried in the matrix — the code alone doesn't preserve intent.

**Possible follow-ups:** If the rate limiter is later tuned for performance reasons, what process would prevent that change from silently eroding the safety margin? How would you verify the limiter's behavior when the actuator is already at its mechanical limit and the command keeps increasing?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap here is that the risk analysis credits one control, but the implementation is spread across three elements owned by different people, so a single "control → requirement → test" link is misleading — it implies one owner and one verification, when in reality the control's effectiveness depends on all three elements working together and on the interfaces between them. I'd decompose the control into its constituent functions and allocate sub-requirements: the sensor path must deliver a reading with a defined accuracy and update rate; the firmware loop must compute and command an output with a defined response and must fail in a defined direction (e.g., command off) if the sensor reading is invalid or stale; the power switch must be capable of removing energy within a bounded time and must default to the safe state on loss of control signal. Each sub-requirement gets its own verification, but — and this is the key point — the *integrated* control also needs an end-to-end verification that exercises the whole loop under the fault conditions the risk analysis cares about: sensor drift or failure, loop saturation, switch failure to open. So the traceability structure has one risk control linked to a set of allocated requirements across hardware and firmware, plus a system-level verification that demonstrates the composite behavior. I'd also capture the interfaces explicitly — the sensor-to-firmware signal definition and the firmware-to-switch command definition — because those interfaces are where distributed controls most often fail silently. The matrix should make clear that passing the individual sub-verifications is necessary but not sufficient; the integrated test is what actually closes the control.

**Possible follow-ups:** How would you decide which fault conditions must be covered by the integrated test versus which can be argued by analysis? If the firmware loop is later replaced with a different control algorithm, which verification evidence would you consider invalidated?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — a general "power supply design review" checklist, for example — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review is actually capable of detecting the failure the control is meant to prevent — and a generic checklist usually isn't, because it asks broad questions ("are decoupling capacitors placed correctly?") rather than the specific one the risk analysis requires ("does the circuit still hold the output within the safe range when the feedback path opens?"). My approach would be to make the review fit for purpose rather than to discard it. First, extract from the risk analysis the precise failure condition the control addresses and the design property that makes the control effective. Second, add review checklist items that directly interrogate that property — specific, answerable questions with a defined acceptance judgment, not "review the power supply." Third, define the review's entry criteria (which schematics, calculations, and worst-case analyses must be available) and its exit criteria (what must be demonstrated for the review to count as verification of this control). Fourth, record the outcome against the risk control ID, not just as "review completed" but as an explicit statement of what was assessed and the conclusion. If the review genuinely cannot assess the property — for example, the failure mode is timing-dependent and only a test can reveal it — then the review is the wrong verification method and I'd reallocate the control to a test or an analysis. The principle is that the verification method must match the nature of the failure condition; a review is acceptable when the failure is a design omission or a calculable margin, not when it's a dynamic behavior.

**Possible follow-ups:** How would you handle a review where the checklist item is answered "yes" but the reviewer's rationale is thin — what evidence standard would you require? If the review has already been completed and signed off before you added the specific checklist items, what would you do?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a line of code but a *value*, and the traceability has to cover the value's entire lifecycle: how it's determined, how it's written, how it's read back, and how it's protected from corruption or unauthorized change. I'd structure it in layers. First, a requirement that defines the parameter's permitted range and the rule for deriving the per-unit value (from calibration, from a component tolerance, from a configuration table) — the requirement must state the safety-relevant bound, not just "the limit shall be programmed." Second, a requirement on the programming process itself: the value must be written and then read back and verified against the intended value, with a defined tolerance, and the unit must not be releasable if the readback fails. Third, a requirement on the runtime behavior: firmware must validate the stored value at startup against the permitted range and enter a safe state if it's missing, out of range, or fails a checksum — because a corrupted limit is a failed control. Fourth, verification: the manufacturing procedure is verified as a process (does the readback catch a mis-programmed unit?), and the runtime validation is verified by test (inject an out-of-range value and confirm the safe state). The traceability matrix then links the risk control to the parameter requirement, the programming-process requirement, and the runtime-validation requirement, each with its own verification. I'd also make sure the parameter's identity, range, and checksum scheme are captured in the interface control documentation, since the programming fixture and the firmware both depend on that definition. The general point: when the control is a value, traceability must follow the value from derivation through programming to runtime use, and the verification must include the failure modes of the value itself.

**Possible follow-ups:** How would you handle a service replacement board that is programmed in the field rather than at the factory — what additional traceability would that require? If two units with different programmed limits are compared in a post-market investigation, how would your scheme let you reconstruct which limit each unit should have had?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd treat this as a substantive quality issue rather than a documentation dispute, and I'd be careful not to frame it as an accusation of the test engineer — they did the right thing by raising it. The matrix being complete and the tests passing tells me the *form* of traceability is satisfied, but the whole point of the link is that the verification actually demonstrates the control works, and a copied test that passes without exercising the failure condition provides no such evidence. My first step would be to gather facts rather than argue: pick a small sample of the flagged tests and walk through each one against the risk analysis entry — what failure condition is the control meant to address, and does the test procedure actually create that condition and observe the control's response? That gives me concrete examples instead of a general claim. Then I'd bring the systems engineer, test lead, and quality together with those examples and reframe the question away from "is the matrix compliant?" toward "does this test, if it passed, give us confidence the control works?" — because that's the question an auditor or a regulator is ultimately asking, and it's the question that matters for patient safety. On the disagreement itself, I'd acknowledge the systems engineer's point that the matrix meets its formal requirement, but explain that traceability exists to preserve the *intent* of the control across documents, and a copied test breaks that chain even though the link exists. The resolution I'd propose is a targeted re-review of the flagged tests: for each, either confirm it exercises the failure condition (and document that confirmation), or rewrite it so it does, or reallocate the control to a verification method that can. I'd also look at *why* the tests were copied — schedule pressure, unclear requirements, a template that encouraged reuse — because fixing the individual tests without fixing the cause just moves the problem to the next project. Finally, I'd want the outcome recorded in the verification documentation so the evidence trail reflects what was actually assessed, not just that a test with a matching ID exists.

**Possible follow-ups:** How would you prevent this from recurring on the next project without adding so much review overhead that the team routes around it? If the re-review finds that one of the copied tests genuinely does exercise the failure condition, how do you close that out without implying the original concern was unfounded?
