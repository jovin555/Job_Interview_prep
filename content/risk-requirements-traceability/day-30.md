# risk-requirements-traceability — Day 30

## Q1: How would you approach establishing traceability for a risk control measure that is implemented through a combination of hardware and firmware, where the hardware team documents the control in their design specification and the firmware team documents their portion in a software requirements document — but neither document references the other, and the risk management file treats the control as a single integrated measure?

**Answer:** The core issue here is that the risk management file treats the control as one integrated measure, but the engineering artifacts treat it as two separate pieces. I'd start by creating a single "risk control implementation" record in the risk management file that explicitly decomposes the control into its hardware and firmware contributions, with each contribution linked to the relevant design document. For the hardware portion, I'd reference the specific circuit or component in the hardware design specification; for the firmware portion, I'd reference the specific software requirement. Then I'd add cross-references in both directions — the hardware design spec should note that this circuit's function is only complete when the firmware response is implemented, and the software requirements document should note the hardware dependency. The verification strategy would then have three levels: hardware-level verification (does the sensor/comparator detect the condition correctly?), firmware-level verification (does the software respond correctly when given the appropriate input?), and system-level verification (does the complete chain work end-to-end?). The system-level test is essential because it proves the integration, not just the individual pieces. I'd also ensure the traceability matrix captures the control as a single row at the hazard level, with sub-rows for each implementation element.

**Possible follow-ups:** How would you handle the situation where the hardware and firmware teams use different numbering schemes for their documents? What if the hardware portion is verified by analysis (e.g., worst-case tolerance analysis) rather than test?

## Q2: How would you approach determining whether a risk control measure that is implemented as a firmware-based plausibility check on a sensor reading — for example, rejecting readings that change by more than a specified rate between consecutive samples — needs to be verified on the actual production hardware, or whether testing on a development board with the same microcontroller is sufficient?

**Answer:** The key question is whether the risk control's effectiveness depends on characteristics that differ between the development board and production hardware. For a plausibility check on sensor readings, I'd consider three factors. First, timing: does the check depend on interrupt latency, clock speed, or scheduling behavior that might differ between boards? If the check has a hard real-time deadline, production hardware verification is likely necessary. Second, the sensor interface: if the plausibility check processes raw analog signals through an ADC, the production board's analog front-end, PCB layout, and noise characteristics could affect behavior — a development board with the same microcontroller but different analog circuitry wouldn't be representative. Third, the failure modes the control mitigates: if the hazard involves a sensor failing in a specific way (e.g., shorted output, open connection), the test needs to inject those faults at the actual sensor interface on production-representative hardware. If the plausibility check operates purely on digital values after the ADC and the timing behavior is identical, development board testing might be sufficient for the firmware logic itself — but I'd still want at least a subset of tests on production hardware to confirm the integration. The risk management file should document the rationale for whichever approach is chosen, including an analysis of why the chosen test environment is representative for the specific failure conditions being mitigated.

**Possible follow-ups:** What if the plausibility check involves timing that depends on the RTOS scheduler — how would you verify that on a development board? How would you document the justification for using a development board in the verification evidence?

## Q3: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system has a distributed architecture — multiple microcontrollers, each running separate firmware, communicating over a shared bus — and a single hazard is mitigated by coordinated actions across multiple nodes?

**Answer:** This is a situation where the traceability scheme needs to reflect the distributed nature of the control without losing sight of the integrated hazard mitigation. I'd structure it in layers. At the top, the hazard and its risk control measure are defined in the risk management file as a single integrated control. Below that, I'd decompose the control into node-specific responsibilities: what each microcontroller must detect, decide, and communicate, and what coordinated action results. Each node's responsibility becomes a requirement in that node's firmware requirements document, with a cross-reference to the integrated risk control. The communication protocol requirements — message formats, timing, acknowledgment mechanisms — would be captured in the interface control document, and these protocol requirements also trace back to the risk control. The verification strategy would include node-level tests (does each node correctly execute its portion?), bus-level tests (does the communication correctly convey the necessary information within the required timing?), and system-level tests (does the coordinated action actually mitigate the hazard?). The traceability matrix would show the hazard → integrated control → node-specific requirements → verification activities, with the bus/protocol requirements appearing as an intermediate layer. One important consideration is failure of the communication itself — if the hazard mitigation depends on nodes coordinating over a bus, the risk analysis should also consider what happens if the bus fails, and that failure scenario needs its own traceability path.

**Possible follow-ups:** How would you handle the situation where one node's firmware is updated independently of the others, potentially changing the coordination behavior? How would you verify the timing of the coordinated response across the bus?

## Q4: How would you approach handling a situation where a risk control measure is traced to a verification test, but the test was written to verify a *different* requirement and only incidentally exercises the risk control under nominal conditions — so it passes, but it never actually stresses the failure condition the control is meant to mitigate?

**Answer:** This is a common and dangerous gap — the traceability matrix looks complete because there's a link, but the link is meaningless because the test doesn't exercise the failure condition. I'd start by reviewing the test procedure against the risk control's intended function and the specific failure modes identified in the risk analysis. For each risk control, I'd ask: what specific fault condition must be injected, and does the test actually inject it? If the test only exercises nominal conditions, it's not providing evidence that the control works when it needs to. I'd then work with the verification engineer to either modify the existing test to include fault injection, or create a new test specifically for the risk control. The key is to define the test's pass/fail criteria in terms of the risk control's behavior under the fault condition, not just its normal operation. I'd also update the traceability matrix to distinguish between "incidental exercise" and "targeted verification" — perhaps with a note field indicating whether the test actually stresses the failure condition. If the test can't be modified (e.g., it's a regulatory submission test that's already been run), I'd create a supplemental test and document why the original test was insufficient. The risk management file should record this as a finding — the original verification evidence was inadequate, and the supplemental test provides the necessary objective evidence.

**Possible follow-ups:** How would you prevent this situation from recurring in future projects? What if the test engineer argues that the nominal-condition test is sufficient because the risk control is "designed to work across the full range"?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has created a traceability matrix that links every risk control measure to a verification activity, but during a review, you discover that several of the verification activities are actually "verification by similarity" — meaning the team is relying on test results from a previous product that used a similar component or design. The quality manager argues that similarity is not acceptable evidence for risk controls, because the previous product wasn't tested under the same conditions. The systems engineer argues that the components are identical, the design is nearly the same, and re-running the tests would waste time and money. How would you resolve this disagreement?

**Answer:** I'd approach this by first acknowledging that both sides have valid points. The systems engineer is right that re-running identical tests on identical components can be wasteful, and the quality manager is right that similarity arguments can be overused and may not account for meaningful differences. Rather than taking sides, I'd facilitate a structured assessment of each "verification by similarity" claim. For each one, I'd ask three questions: First, is the component or design truly identical, or just similar? I'd want to see a side-by-side comparison of the specifications, operating conditions, and interface requirements. Second, were the original test conditions representative of the current product's use conditions — including worst-case scenarios, environmental extremes, and fault conditions? Third, is there documented evidence from the previous test that's actually accessible and reviewable, not just a verbal claim that "it was tested before"? Based on this assessment, I'd categorize each similarity claim: some might be genuinely acceptable with proper documentation and rationale; others might require targeted supplemental testing to cover differences in conditions or interfaces. I'd also consider a hybrid approach — for example, running a reduced set of confirmation tests on the current hardware to verify that the similarity argument holds, rather than either accepting the claim wholesale or requiring a full re-test. The key is to move the discussion from a binary "similarity is acceptable/unacceptable" to a risk-based assessment of what evidence is actually needed for each specific control. I'd document the rationale for each decision in the risk management file so the reasoning is transparent to auditors and future reviewers.

**Possible follow-ups:** How would you handle a situation where the previous product's test data exists but was collected under different regulatory standards? What criteria would you use to determine when similarity is acceptable versus when re-testing is required?
