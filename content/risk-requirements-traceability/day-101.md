# risk-requirements-traceability — Day 101

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement captures the *behavior* but not the *safety intent*, so the traceability link from hazard to requirement is broken at the point where it matters most. I'd approach it in three steps.

First, I'd close the semantic gap by making the safety intent explicit. The functional requirement ("the firmware shall clamp the commanded motor speed to a maximum rate of change of X units per second") is necessary but not sufficient — I'd add a derived safety requirement or an explicit annotation that ties this behavior to the hazard it mitigates (hazardous overspeed). The cleanest approach is a bidirectional link in the traceability matrix: hazard → risk control measure → safety requirement → functional requirement → verification. The functional requirement stays as-is for the firmware team's purposes, but the safety requirement carries the "why" and the hazard reference.

Second, I'd make sure the verification actually stresses the failure condition, not just the nominal clamping. A test that commands a step change and observes the output ramp is a good functional test, but the safety verification needs to demonstrate that under the worst-case conditions the risk analysis assumes — maximum commanded step, worst-case timing, fault conditions that could bypass the limiter — the rate of change never exceeds the safe bound. That may mean a separate safety test case with its own acceptance criterion derived from the risk analysis, not just the functional test.

Third, I'd address the process gap that allowed this to happen: the firmware requirements were written from a functional decomposition without a check against the risk management file. I'd add a review gate where every risk control measure is confirmed to have a corresponding requirement that references the hazard, and every safety-relevant requirement is confirmed to trace back to a risk control. That prevents the same drift on the next control.

**Possible follow-ups:**
- If the firmware team argues that adding hazard references to their requirements "clutters" the document, how would you keep the safety intent visible without duplicating the risk analysis into the SRS?
- How would you verify the rate limiter under fault conditions where the commanded speed signal itself is corrupted — does that change what the verification needs to cover?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** This is a case where the risk analysis is correct to treat the loop as one control — the safety property is emergent from the whole loop, not from any single element — but the traceability has to decompose it without losing that emergent property. I'd handle it with a two-level structure.

At the top level, I'd create a single system-level safety requirement that expresses the loop's safety intent: "the system shall maintain the heating element temperature below T_max under all specified operating conditions." That requirement is the traceable anchor for the risk control measure, and it's what the system-level verification tests against.

Below that, I'd decompose into the contributing elements: a sensor requirement (accuracy, range, response time), a firmware requirement (PID behavior, output limits, fault response), and a hardware requirement (power switch response time, fail-safe state on loss of control signal). Each of these is a *derived* requirement that contributes to the top-level safety property, and each traces up to the system-level safety requirement. Crucially, each derived requirement needs its own verification — sensor accuracy test, firmware loop response test, switch timing test — but those verifications are necessary, not sufficient. The system-level verification (does the whole loop hold temperature under worst-case conditions, including sensor drift, load changes, and fault injection) is what actually verifies the risk control.

The key discipline is to make the decomposition explicit in the traceability matrix: the risk control measure links to the system-level safety requirement, which links down to the derived requirements, which link to their element-level verifications, and the system-level verification links back up to the risk control. That way an auditor can see both the whole and the parts, and no one mistakes an element-level test for verification of the whole control.

**Possible follow-ups:**
- If the system-level test is expensive or slow to run, how would you decide how much of the loop's behavior can be verified by element-level tests plus analysis versus needing full system testing?
- How would you handle the case where the PID loop's behavior is tuned during development — does the traceability need to capture the tuning parameters as part of the control?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** The traceability link exists on paper, but the verification activity isn't actually capable of detecting the failure the control is meant to prevent — so the link is misleading. I'd treat this as a verification-adequacy problem, not just a documentation problem.

First, I'd confirm the gap by walking through the review checklist against the risk control's failure condition. If the checklist has no line item that asks "does this design prevent [specific failure condition]?", then the review cannot have verified the control, regardless of whether the review passed.

Second, I'd decide how to close the gap. There are two legitimate options: extend the design review with a control-specific checklist item that explicitly assesses the failure condition, or add a separate verification activity (a test, an analysis, or a focused review) that does. Which one is appropriate depends on the nature of the control — a PCB creepage-distance control is naturally verified by inspection against a checklist item, while a thermal shutdown control probably needs a test. The point is that the verification method must be *capable* of detecting the failure, and the acceptance criterion must be stated in terms of the failure condition, not just "design looks acceptable."

Third, I'd fix the process so this doesn't recur: when a risk control is linked to a design review as its verification method, the review checklist should be derived from (or explicitly reference) the risk control's failure condition. I'd add a review step where the person maintaining the traceability matrix confirms that each review-based verification has a checklist item that addresses the specific failure mode — otherwise the link gets flagged as a gap.

**Possible follow-ups:**
- How would you handle the situation where the design review has already been completed and signed off before you discover the gap — do you re-run the review, or add a supplementary verification?
- If the risk control is one where inspection is the only practical verification method, how do you make the inspection objective enough to satisfy a quality auditor?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a behavior in the firmware or a component in the hardware — it's a *value* that's programmed at manufacturing, and the traceability has to cover the value's specification, its programming, and its verification, not just the code path that reads it.

I'd structure the traceability around three linked artifacts. First, a requirement that specifies the parameter: what it is, its allowable range, how it's determined for a given unit (fixed value, calibrated, derived from a test), and the safety rationale for the limit. That requirement traces up to the risk control measure and the hazard it mitigates. Second, a manufacturing specification that defines how the value is programmed and what the acceptance criteria are — this is the "implementation" of the control at the manufacturing level, and it needs to be traceable to the requirement. Third, a verification activity that confirms the programmed value is within the specified range and that the system behaves correctly at that value — which may be a per-unit production test, a sample-based audit, or both, depending on the criticality and the risk analysis.

The tricky part is that the value can differ between units, so the traceability can't just say "the parameter is set to X." It has to say "the parameter is set to a value within range R, determined by method M, verified by test T, with records retained per unit." I'd also make sure the risk analysis accounts for the range — if the control is effective only when the value is within a certain band, the risk analysis needs to state that, and the manufacturing acceptance criteria need to enforce it. And I'd link the production records to the device serial number so that if a unit is ever investigated, you can trace back to what value was actually programmed.

**Possible follow-ups:**
- If the parameter is calibrated per-unit based on a measurement, how would you verify that the calibration itself is correct — is that a separate control with its own traceability?
- How would you handle a field service scenario where the parameter can be changed after manufacturing — does the traceability scheme need to cover the service action as well?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The matrix is structurally complete but substantively hollow — the links exist, but the verification activities may not actually verify the controls. I'd treat the test engineer's disclosure as a serious signal and handle it in a way that protects the person who raised it while getting to the truth.

First, I'd thank the test engineer and make clear that raising this was the right thing to do, and that I'll handle it in a way that doesn't single them out. Then I'd do my own quiet assessment before convening anyone: pick a sample of the flagged tests, read the test procedure against the risk control's failure condition, and determine for myself whether the test actually stresses that condition. That gives me evidence rather than hearsay when I talk to the systems engineer.

Second, I'd sit down with the systems engineer and the test lead together, framed not as an accusation but as a verification-adequacy review: "The matrix is compliant, and I want to confirm the tests are capable of detecting the failure conditions, not just that they pass." I'd walk through the specific examples — a test labeled as verifying a control that actually exercises nominal conditions — and ask the systems engineer to explain how that test would fail if the control were disabled. If the answer is "it wouldn't," then the link is not adequate regardless of what the matrix says.

Third, I'd drive a remediation: re-examine every test linked to a risk control against the criterion "would this test fail if the control were removed or defeated?" Tests that don't meet that criterion get rewritten or supplemented. I'd also fix the process that allowed copied tests to be linked without review — a verification-adequacy check as part of the traceability review, and a rule that a test linked to a risk control must state the failure condition it's designed to detect.

The framing I'd use with the team is that a compliant matrix that doesn't actually verify the controls is worse than an incomplete one, because it creates false confidence. The goal isn't to assign blame for the copied tests — it's to make sure the safety case is real.

**Possible follow-ups:**
- How would you handle the situation if the systems engineer continues to insist the matrix is compliant and resists re-opening the tests, especially if the project is near a regulatory submission?
- What would you do if your sample review finds that most of the flagged tests are actually adequate, and only a few are not — how does that change your approach?
