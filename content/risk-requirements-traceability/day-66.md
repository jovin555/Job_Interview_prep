# risk-requirements-traceability — Day 66

## Q1: How would you approach tracing a risk control measure that is implemented as a two-channel architecture where the channels are functionally identical but share a common element — for example, two independent sensor paths that both rely on the same power rail — when the risk analysis assumes the channels are fully independent?

**Answer:** This is fundamentally a common-cause failure problem, and the traceability scheme has to make the shared dependency visible rather than hiding it behind two parallel branches. The first step is to represent the control not as "Channel A + Channel B" but as a small dependency graph: each channel traces to its own design elements and verification activities, and both channels trace to the shared element (the power rail) as a common node. That common node needs its own risk analysis entry — because if the risk file claims independence as the basis for the risk reduction, the shared rail is exactly the assumption that has to be validated or the claimed reduction is overstated.

Practically, I would add a "common cause" or "shared dependency" column to the traceability matrix so that any control whose effectiveness depends on independence is flagged, and then require that each flagged control has a verification activity specifically targeting the shared element — for example, a fault-injection test that pulls the shared rail out of spec and confirms the system detects the loss of both channels rather than silently continuing. If the shared dependency cannot be eliminated, the honest move is to revise the risk analysis: either downgrade the claimed risk reduction, or add a diverse backup (different power domain, different sensing principle) so the independence assumption becomes true. The traceability matrix should never show two clean independent branches when the schematic shows a shared node — that's a documentation artifact that gives false confidence.

**Possible follow-ups:**
- How would you decide whether a shared dependency is acceptable versus requiring a design change, and who should be involved in that decision?
- If the shared element is a commercial off-the-shelf component with its own reliability data, how would you incorporate that into the independence argument?

## Q2: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a "test" that was actually performed by manually toggling a signal and observing an LED, with no automated logging or measurement instrument, and the risk file treats it as objective evidence?

**Answer:** The core issue is whether the evidence is objective and reproducible, not whether it was automated. A manual toggle-and-observe test can be legitimate evidence if it is controlled: the procedure specifies the exact stimulus, the exact expected response, the acceptance criterion is measurable, and the result is recorded with enough detail that an independent person could repeat it and reach the same conclusion. What makes this case weak is usually not the manual nature but the missing rigor — no defined stimulus level, no measurement instrument, no record of the actual observed value, just "LED came on."

So my approach would be to first classify the control by what it actually needs to demonstrate. If the control is a binary logic function (interlock prevents state transition), a well-documented manual test with a defined pass/fail and a recorded result may be sufficient. If the control involves a threshold, a timing bound, or an analog quantity, then an LED is not a measurement and the test needs an instrument — oscilloscope, DMM, logic analyzer, or logged firmware output — with the actual value recorded against the acceptance criterion. I would work with the test author to upgrade the procedure: define the stimulus precisely, specify the measurement method and instrument, state the acceptance criterion numerically, and require the raw result to be attached to the test record. If the control is safety-critical and the manual method is inherently subjective, I would push for an automated or instrumented version so the evidence is repeatable across units and operators.

The traceability link itself is fine — the problem is the quality of the evidence at the end of the link. A traceability matrix that points to weak evidence is worse than one that flags the gap, because it looks complete while providing no real assurance.

**Possible follow-ups:**
- How would you decide which risk controls can be verified by manual observation and which require instrumented measurement?
- If the test was already executed and signed off with weak evidence, what would your remediation path look like?

## Q3: How would you approach establishing traceability for a risk control measure that is implemented as a timing requirement — for example, "the system shall remove power from the heating element within 500 ms of detecting an over-temperature condition" — when the timing depends on a chain of hardware and firmware elements, each with its own latency, and the 500 ms budget is allocated across them?

**Answer:** Timing controls are a good example of a risk control that cannot be traced to a single design element, because the control is the *end-to-end latency* of a chain. The traceability scheme needs to decompose the budget explicitly: the risk file states the 500 ms requirement, and the SRS or architecture document breaks it into allocated latencies — sensor response time, analog signal conditioning delay, ADC conversion and interrupt latency, firmware detection and decision time, and the actuator/relay drop-out time. Each allocation traces to the specific design element responsible for it, and each gets its own verification activity (component datasheet analysis, bench measurement, firmware timing test), while the end-to-end 500 ms is verified by a system-level test that measures the total from fault injection to power removal.

The critical discipline is that the sum of the allocated budgets must be less than the total with margin, and the traceability matrix must show both the allocations and the roll-up. If any single allocation changes — say the firmware detection window is widened — the matrix should make it obvious that the end-to-end verification needs to be re-examined, because the system-level test is the only place the total is actually proven. I would also require that the system-level test measure the worst case, not the typical case: slowest sensor response, lowest clock frequency within tolerance, maximum relay drop-out. A timing control verified only at nominal conditions doesn't demonstrate the 500 ms bound holds across the operating envelope.

**Possible follow-ups:**
- How would you handle a situation where the allocated budgets sum to more than the total requirement, but each individual allocation passes its own test?
- If the end-to-end timing test is destructive or expensive to run repeatedly, how would you structure the verification to balance coverage against practicality?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when a single risk control measure is implemented redundantly — the same hazard is mitigated by two independent controls, and the risk analysis credits both — but the two controls are owned by different teams and were added at different times in the project?

**Answer:** The key insight is that redundant controls are not two separate traceability chains that happen to point at the same hazard — they are a single risk reduction argument that depends on both being present and independent. The traceability scheme should represent this as a control group: the hazard traces to a risk reduction claim, the claim traces to both controls, and each control traces to its own requirements, design elements, and verification activities. The matrix needs a way to express "AND" relationships (both controls required) versus "OR" relationships (either control sufficient), because the risk math is completely different.

When the controls were added at different times by different teams, the practical risk is that neither team knows the other control exists, or that one team assumes the other is the primary and treats its own as a backup. I would start by creating a single "risk control group" entry in the risk management file that names both controls and states the independence assumption explicitly, then link both teams' requirements documents to that group entry. Each team's verification activity should include a test that confirms the control works *in the presence of the other control* — not just in isolation — because redundant controls can interact (shared power, shared bus, shared firmware task) in ways that break the independence the risk analysis assumes. Finally, I would add a periodic review checkpoint: whenever either control's requirements change, the group entry is flagged for re-evaluation, because a change to one control can invalidate the independence argument for the pair.

**Possible follow-ups:**
- How would you determine whether two redundant controls are truly independent, and what evidence would you require to support that claim?
- If one of the redundant controls is later removed for cost reasons, how should the traceability matrix and risk file be updated?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file lists a risk control measure, the SRS contains a requirement that implements it, and the verification plan contains a test that verifies the requirement — but when you trace the links, you find that the requirement was written by the systems engineer, the test was written by the test engineer, and neither of them has ever read the risk analysis entry that justifies the control. The links exist on paper, but the *intent* of the control has been lost between the documents. How would you handle this?

**Answer:** This is the classic failure mode of traceability done as a documentation exercise rather than as a communication tool — the links are technically present, but the safety intent has been diluted at each handoff. The first thing I would do is not treat it as a compliance problem to be patched, but as a process problem to be understood. I would pick two or three of the affected controls and walk the chain backwards with the people involved: show the test engineer the hazard the control mitigates, show the systems engineer the failure condition the control is meant to address, and ask each of them whether the requirement and test they wrote would actually catch that failure. In most cases, the answer is "not quite" — the requirement captures the function but not the failure mode, or the test exercises the function under nominal conditions but never induces the fault.

From there, the fix has two parts. The immediate part is to strengthen the artifacts: rewrite the affected requirements so they state the safety intent (not just the functional behavior), and revise the tests so they explicitly exercise the failure condition from the risk analysis. The systemic part is to change how the documents are authored so the intent can't get lost again — for example, require that every safety-related requirement carries a reference to the risk control it implements and a one-line statement of the hazard, and require that test authors review the risk analysis entry before writing the test. I would also add a design review checkpoint where the risk analyst, systems engineer, and test engineer sit down together and walk the chain for the highest-severity controls, so the intent is transmitted in person rather than only through document links.

The behavioral dimension is that this is not anyone's fault individually — it's a handoff problem — so the conversation has to be framed as "how do we make the intent survive the handoff" rather than "who wrote the wrong requirement." Blame makes people defensive and hides the real gaps.

**Possible follow-ups:**
- How would you prioritize which controls to review first if there are too many to walk through all of them?
- What would you put in place to detect this kind of intent-loss earlier in future projects, before the verification phase?
