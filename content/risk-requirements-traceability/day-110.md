# risk-requirements-traceability — Day 110

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the requirement captures *what the code does* but not *why it exists*, so the safety intent is invisible to anyone reading the SRS in isolation. I'd start by treating the risk analysis entry as the anchor and working outward in both directions. First, I'd create an explicit link from the hazard/risk control entry to the existing functional requirement — even if that means adding a "derived from" or "risk control reference" attribute to the requirement rather than rewriting it. Second, I'd add a companion requirement or a requirement annotation that states the safety intent explicitly: not just "the firmware shall clamp commanded speed change to X units per second," but a statement that this clamping exists to prevent the actuator from reaching a hazardous rate under any commanded input, including fault or corrupted commands. That second statement is what makes the requirement verifiable *as a control* rather than just as a behavior.

The reason this matters is that a purely functional requirement can be satisfied by a test that never approaches the hazard. If the requirement only says "clamp the rate," a test that ramps a command slowly and observes smooth output passes — but it never demonstrates that a step command or a runaway command gets clamped. So I'd also make sure the verification activity is derived from the hazard, not just from the functional wording: the test must inject the failure condition the limiter is meant to catch (an abrupt or out-of-range command) and confirm the output rate stays bounded. Finally, I'd check the reverse direction — does the risk analysis entry point back to the requirement and the test? — so the trace is bidirectional and an auditor can walk from hazard to evidence without guessing.

**Possible follow-ups:**
- If the firmware team resists adding safety-intent language to their requirements because it "duplicates the risk file," how would you frame the argument?
- How would you handle the case where the same rate limiter is reused across several products with different maximum rates — where does the traceability live?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap here is that the risk file credits one control, but the control has no single owner and no single requirement — it's an emergent property of three subsystems. If you trace naively, you either link the risk entry to one arbitrary requirement (usually the firmware PID, because it's the most visible) and lose the other two contributors, or you link it to nothing because no single document describes "the loop." I'd decompose the control into its constituent functions and make the decomposition explicit in the traceability structure. That means creating a control-level node — sometimes called a risk control measure identifier — that sits above the subsystem requirements, with the hardware sensor requirement, the firmware control requirement, and the power-switch requirement each traced up to it. The risk analysis entry links to that control node, and the control node links down to all three subsystem requirements and to the integrated verification.

The critical part is the *integrated* verification. Each subsystem can pass its own test — sensor accuracy, PID response, switch actuation — and the loop can still fail to hold temperature, because the failure mode lives in the interaction: sensor lag combined with PID tuning combined with switch latency. So I'd require a system-level test that exercises the loop as a loop, under conditions the individual tests don't cover (e.g., a step disturbance, a sensor that reads slightly low, a switch that's slow to open). I'd also document the *assumed independence or contribution* of each element in the control description, so that if one element changes later, you can see which part of the control is affected. The traceability matrix then shows hazard → control node → three subsystem requirements → three unit verifications plus one integrated verification, and a reviewer can see at a glance that the control is only as good as its weakest link.

**Possible follow-ups:**
- If the integrated test is expensive or slow to run, how would you decide how much of it can be replaced by analysis of the individual element margins?
- How would you keep the control node from becoming a "dumping ground" that links to everything and therefore proves nothing?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review is actually capable of detecting the failure the control is meant to prevent. A generic power-supply checklist reviews things like margin, thermal derating, and layout — it may never ask "does this supply hold its output within the safe range when the load transient the hazard describes occurs?" So the trace exists on paper but the evidence is hollow. I'd treat this as a verification-method mismatch and fix it at the review-criteria level rather than by swapping in a test reflexively. First, I'd extract the specific failure condition from the risk analysis — what exactly must the review confirm? — and add a review item that asks that question explicitly, with a defined acceptance criterion and a named reviewer competent to judge it. That converts the generic review into a targeted one for this control.

If the failure condition genuinely can't be assessed by inspection — for example, it depends on dynamic behavior — then the review isn't the right method and I'd move the control to a test or analysis. The decision rule I'd apply is: does the chosen method have a realistic chance of catching the failure if it's present? If not, the method is wrong regardless of how the traceability matrix looks. I'd also record in the verification record *which review item* satisfied the control, not just "design review held," so the evidence is specific and auditable. And I'd check whether other controls are traced to the same generic review — if several are, that's a systemic gap worth fixing once rather than control by control.

**Possible follow-ups:**
- How would you handle a reviewer who argues that adding control-specific items to every review makes the checklist unmanageably long?
- What's the difference between a design review that *verifies* a control and one that merely *confirms the design intent* — and does that distinction change the evidence you'd accept?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a line of code — it's a *value*, and the value is only correct if three things hold: the parameter is defined correctly, it's programmed correctly at manufacturing, and it's not corrupted or changed afterward. So the traceability has to cover all three, not just the design. I'd start by tracing the risk control to a requirement that specifies the parameter's *permissible range and its safety significance* — not a single number, but the envelope within which the control remains valid, plus the rule for how the per-unit value is determined. That requirement then traces to the manufacturing specification or work instruction that programs the value, and to the production test that reads it back and confirms it's within the permitted envelope for that unit.

The subtle part is that a design-verification test on a prototype proves the *mechanism* works, but it doesn't prove that every shipped unit has a correct value — that's a production control, and it needs its own verification evidence, typically a 100% readback check or a statistically justified sampling plan depending on the criticality. I'd also trace the *change* path: if the parameter can be modified in the field via a service port, that's a new hazard (an incorrect value could disable the control), so the traceability should include the access control and the re-verification step after any change. In the matrix, I'd represent this as hazard → control → parameter requirement → {design verification of mechanism, manufacturing programming spec, production readback test, field-change procedure}, so it's clear the control depends on a chain of activities, not a single artifact. The failure mode I'd watch for is the matrix showing "verified" because the prototype test passed, while the production and field paths are untraced.

**Possible follow-ups:**
- How would you decide whether 100% production readback is required versus sampling, for a parameter like this?
- If the parameter value is derived from a calibration that varies unit to unit, how does that change what "the requirement" even is?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The systems engineer is right that the matrix is compliant and the tests pass — and that's exactly the problem, because compliance and passing tests are not the same as evidence. A copied test can pass while never touching the failure condition this project's risk analysis describes, which means the control is effectively unverified even though every box is ticked. I'd treat the test engineer's disclosure as a serious finding and handle it in a way that protects them — they came forward privately, and if that turns into blame, no one will raise the next one. My first step is to verify the concern rather than accept or dismiss it: pick two or three of the flagged tests, pull the risk analysis entry each is supposed to verify, and compare the failure condition against what the test actually does. That gives me facts instead of a he-said-she-said.

If the gap is real, I'd frame it to the systems engineer not as "the matrix is wrong" but as "the matrix is right and the evidence behind it is weak — which is a bigger risk than a missing link, because it looks complete." I'd propose a targeted re-verification: for each flagged control, either confirm the existing test genuinely exercises the failure condition (and document that confirmation) or rewrite the test around the failure condition. I'd also look at *why* the tests were copied — usually it's schedule pressure or a template that made copying the path of least resistance — and fix that root cause, for example by requiring that each verification test trace to the specific failure condition in the risk entry, not just to a requirement ID. Finally, I'd record the finding and the corrective action in the risk management file, because an auditor finding this later without a record of how it was handled is far worse than finding it with one.

**Possible follow-ups:**
- How would you handle the situation if the re-verification reveals that a control genuinely doesn't work as the risk analysis assumed?
- What would you change in the process so that copied tests get caught earlier, before an audit or a private disclosure surfaces them?
