# risk-requirements-traceability — Day 128

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the requirement captures *behavior* but not *intent*, so the link from hazard to requirement is implicit and fragile — anyone reading the firmware spec in isolation would see a performance feature, not a safety control, and could reasonably relax or remove it during a refactor. I'd fix this at the requirement level first: either amend the existing firmware requirement to explicitly state that it implements a risk control for the overspeed hazard (referencing the risk analysis entry ID), or add a derived safety requirement that sits above it and traces down to the functional clamping requirement. The traceability matrix then carries hazard → risk control → safety requirement → functional requirement → verification test, so the safety intent is visible at every hop. I'd also make sure the verification test actually demonstrates the failure condition — commanding a step change in speed and confirming the output rate never exceeds the clamp — rather than just checking that the motor runs. Finally, I'd add a code-level comment or tag linking the limiter implementation to the requirement ID, so the intent survives into the source tree, not just the documents.

**Possible follow-ups:** If the firmware team pushes back that adding safety language to a functional requirement "clutters" the spec, how would you frame the trade-off? How would you handle this if the same limiter code is shared across two products, only one of which credits it as a risk control?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** A distributed control is the classic case where a single risk-analysis line item doesn't map cleanly to a single requirement, and trying to force a one-to-one link will either lose information or produce a matrix that's technically complete but misleading. I'd decompose the control into its constituent elements — sensing, decision, actuation — and create a requirement for each element that states its contribution to the loop's safe behavior, plus a system-level requirement that captures the emergent property (the heating element stays within the safe range under defined conditions). The risk control then traces to the system-level requirement, which traces down to the element requirements, each of which traces to its own verification. Critically, I'd also define an *integration* verification that exercises the whole loop — because individually correct elements can still fail to keep the element in range if, say, the sensor's response time and the PID's tuning interact badly. The matrix needs to show both the decomposition and the integration test, otherwise you've verified the parts and never the whole.

**Possible follow-ups:** How would you allocate the safe-range budget across the three elements so each element requirement has a measurable acceptance criterion? If the integration test fails but every element test passes, how would you use the traceability structure to localize the problem?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** The traceability link exists but it's not *meaningful* — the review will pass without anyone ever asking whether the control works, which is worse than no link at all because it creates false confidence. I'd treat this as a gap and close it in one of two ways depending on what the control actually is. If the control is genuinely reviewable — a creepage distance, a derating margin, a worst-case tolerance stack — I'd add a control-specific line item to the review checklist that states the failure condition and the acceptance criterion, so the reviewer has an explicit question to answer and the review record becomes objective evidence. If the control can't be meaningfully assessed by review, I'd replace the link with a test or analysis that can. Either way, I'd update the traceability matrix to point at the *specific* review criterion or test, not at the review as a whole, so an auditor can see exactly what evidence demonstrates the control. I'd also check whether other controls are linked to the same generic review and fix them in the same pass.

**Possible follow-ups:** How would you make the case to a reviewer that "the review passed" is not sufficient evidence without a control-specific criterion? What would you do if the design review has already been signed off and the project is past that gate?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a behavior in the design, it's a *value* written into each unit, so the traceability has to cover the value's derivation, its programming, and its verification per unit — not just a design requirement. I'd structure it in three layers. First, a requirement that defines the allowable range for the parameter and how the correct value is determined for a given unit (the calculation or the source data), traced to the risk analysis entry that credits the limit as a control. Second, a manufacturing-process requirement that specifies how the value is programmed and how it's read back and confirmed — because a correct value that isn't actually written, or is written to the wrong location, provides no protection. Third, a per-unit verification record: the readback value, compared against the allowable range, retained as device history. The traceability matrix links hazard → risk control → parameter requirement → programming procedure → per-unit verification record. I'd also think about what happens if the parameter is corrupted or reset in the field — if the control depends on a stored value, the risk analysis should address the failure mode where that value is lost or altered, and that failure mode needs its own control and verification.

**Possible follow-ups:** How would you handle a unit that fails the readback check on the production line — is that a nonconformance, and how does it feed back into the risk file? If the parameter can be changed later via a service port, how does that affect the traceability and the risk analysis?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file, the SRS, and the verification plan are each internally consistent and each passes its own review — but when you trace across all three, you find that a risk control measure is linked to a requirement that is linked to a test, and the test passes, yet the *combination* doesn't actually demonstrate the control works, because the requirement was written at a level of abstraction the test can satisfy without exercising the control's failure condition. The three document owners each argue their document is correct. How would you handle this?

**Answer:** The instinct in this situation is to find who's wrong, but the honest answer is that all three documents can be individually correct and the *system* of documents can still be wrong — the defect is in the links, not the nodes, and no single owner can see it from inside their own document. So I'd reframe the conversation away from blame and toward the cross-document path: put the hazard, the requirement, and the test side by side on one page and ask the group a single question — "if the control were removed or broken, would this test fail?" If the answer is no, the path is broken regardless of whose document is at fault, and that's a shared problem to fix. Then I'd work the fix from the hazard end: restate what failure condition the control must mitigate, check whether the requirement is specific enough to be falsifiable against that condition, and if not, tighten the requirement's acceptance criteria so the test has something concrete to fail against. I'd also use it as a process signal — if the three documents were written independently with links added afterward, this will keep happening, so I'd push for the requirement author and test author to review the risk analysis entry together at the point of writing, not at audit time. The goal is to leave with a corrected path and a process change, not a verdict on who was right.

**Possible follow-ups:** How would you prevent this class of defect from recurring across the rest of the matrix without re-reviewing every link manually? If the schedule is tight and the fix requires rewriting requirements and tests, how would you prioritize which broken paths to fix first?
