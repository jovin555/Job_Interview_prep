# risk-requirements-traceability — Day 118

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement captures the *what* (clamp the rate of change) but not the *why* (mitigate overspeed), so the link between the requirement and the hazard exists only in someone's head. The first step is to make the safety intent explicit: either amend the firmware requirement to carry a reference to the risk control ID it implements, or add a derived safety requirement that states the hazard being mitigated and the rationale. In practice I'd prefer the second — keep the functional requirement clean and add a traceable safety requirement that points back to the risk analysis entry, so the functional behavior and the safety justification are both visible without overloading one statement.

Then I'd close the loop on verification. The verification activity must not just confirm "the clamp works at nominal conditions" — it has to demonstrate that the limiter actually prevents the hazardous overspeed condition under the fault scenario the risk analysis describes (e.g., a runaway command from a stuck input, or a step change in the setpoint). That means the test needs a stimulus that would produce overspeed *absent* the limiter, and an acceptance criterion tied to the hazard threshold, not just to the clamp rate. I'd also check that the risk analysis credits the limiter with a specific risk reduction — if the residual risk estimate depends on the limiter, the verification evidence has to be strong enough to support that credit.

Finally, I'd add a bidirectional check: from the hazard, can I walk down to the requirement and the test? And from the requirement, can I walk up to the hazard? If either direction breaks, the traceability is incomplete regardless of what the matrix says.

**Possible follow-ups:** If the firmware team argues that adding a hazard reference to the requirement "pollutes" the functional spec, how would you structure the documents so both audiences are served? And how would you handle the case where the same rate limiter is reused across several products with different hazard thresholds?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap with a distributed control is that the risk analysis credits it as a single measure, but no single requirement, design element, or test owns the whole thing — so the traceability matrix can look complete while each contributor only covers its slice. I'd start by decomposing the control into its constituent functions and allocating a requirement to each: the sensor's accuracy and response time, the firmware loop's behavior and limits, the power switch's ability to interrupt. Each of those gets its own requirement, its own design element, and its own verification. That gives me the bottom-up coverage.

But decomposition alone isn't enough, because the control's *effectiveness* is an emergent property of the loop — the individual pieces can each pass while the combination fails (e.g., sensor lag plus loop tuning produces overshoot beyond the safe range). So I'd add an explicit system-level requirement and a system-level verification that exercises the whole loop against the hazard condition, with the acceptance criterion stated in terms of the safe range, not the individual component specs. The traceability then has two layers: the risk control maps to the system-level requirement and test, and also to the allocated sub-requirements and their tests. The matrix should show both, so an auditor can see that the integrated behavior was verified, not just the parts.

I'd also make sure the interface between the pieces is captured — the sensor-to-firmware signal, the firmware-to-switch command — because that's where distributed controls usually break down in traceability. An ICD or interface requirement that both teams trace to closes that gap.

**Possible follow-ups:** How would you decide how much of the loop's behavior to verify at the system level versus relying on component-level verification? And if the loop is tuned at manufacturing or in the field, how does that affect what you can claim in the traceability?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review actually assesses the thing the control is supposed to do. A generic checklist that happens to touch the same subsystem is not evidence that the control's failure condition was evaluated — it's evidence that the subsystem was reviewed for general quality. The traceability link is technically present but evidentially empty.

My approach would be to make the review criteria control-specific. I'd add explicit review items derived from the risk analysis: for each risk control verified by review, the checklist should contain a question that directly addresses the failure condition and the design features that mitigate it, with a place to record the reviewer's judgment and any findings. That converts the review from a general pass into objective evidence tied to the specific control. If the existing review has already happened, I'd either re-run the relevant portion with the augmented checklist or supplement it with a focused review of just that control.

I'd also think about whether review is the *right* method for this control at all. Review is appropriate for things that can't be practically tested — derating margins, creepage distances, layout rules — but if the control's effectiveness is behavioral and testable, a test is stronger evidence. So part of the fix is a method-selection sanity check: is review being used because it's appropriate, or because it was convenient?

**Possible follow-ups:** How would you record the outcome of a control-specific design review so it stands up as objective evidence? And how would you handle a reviewer who argues that adding control-specific checklist items duplicates what the general review already covers?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a piece of code — it's a *value*, and the traceability has to cover not just the design but the production process that sets and confirms that value. I'd structure it in three parts. First, a design requirement that defines the parameter, its permissible range, and the rationale (the hazard it mitigates) — so the safety intent is captured even though the specific value varies. Second, a production requirement or work instruction that specifies how the value is determined, written, and read back, with the acceptance criteria for each unit. Third, a verification activity that confirms the value was correctly set on the actual unit — typically a production test that reads back the stored value and, where feasible, confirms the resulting behavior (e.g., that the current limit actually trips at the configured value).

The traceability matrix then has to show the risk control mapping to the design requirement, the production control, and the per-unit verification record. The per-unit records are what make this auditable — a sample-based check isn't enough if the control is unit-specific, because a single mis-programmed unit is a hazard on its own. I'd also want a change-control path: if the permissible range or the programming method changes, the risk analysis and the production instructions both need to be revisited, and the traceability should show that linkage.

One subtlety: if the parameter can be changed in the field via a service port, the control's integrity depends on access control and on re-verification after any change. That's a separate risk control (or a constraint on this one) and should be traced as well.

**Possible follow-ups:** How would you handle the case where the manufacturing test only reads back the stored value but doesn't confirm the behavior? And how would you trace the control if the parameter range is later widened for a product variant?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file, the SRS, and the verification plan are each internally consistent and each passes its own review — but when you trace across all three, you find that a risk control measure is linked to a requirement that is linked to a test, and the test passes, yet the *combination* doesn't actually demonstrate the control works, because the requirement was written at a level of abstraction the test can satisfy without exercising the control's failure condition. The three document owners each argue their document is correct. How would you handle this?

**Answer:** The first thing I'd do is reframe the disagreement so it isn't about whose document is wrong — because in a narrow sense, all three owners are right: each document is internally consistent. The problem is at the *seams* between them, and no single owner is responsible for the seams. So I'd convene the three owners together and walk the trace end to end, from the hazard through the requirement to the test, asking one question at each link: does this artifact actually address the failure condition the previous one describes? That usually makes the gap visible to everyone at once, rather than one person asserting it against the others.

Once the gap is acknowledged, the fix is usually at the requirement level: the requirement is too abstract, so the test can pass without stressing the control. I'd work with the requirement owner to sharpen the acceptance criteria so they're stated in terms of the failure condition and a measurable threshold, then have the test owner confirm the test can actually demonstrate that. If the test can't, it needs to be redesigned — and that's a real finding, not a paperwork exercise.

I'd also treat this as a process signal, not just a one-off. If the seams between the three documents aren't anyone's explicit responsibility, this will recur. I'd propose a cross-document traceability review as a standing gate — before verification starts, someone walks the hazard-to-test path for each safety-related control and confirms the chain actually demonstrates the control. That gives the team a shared ownership point for the seams.

**Possible follow-ups:** How would you handle it if the requirement owner insists the abstraction is deliberate — that the requirement is meant to be implementation-independent? And how would you prevent this kind of gap from being introduced in the first place during requirements authoring?
