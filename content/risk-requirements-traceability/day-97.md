# risk-requirements-traceability — Day 97

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the requirement as written is functionally correct but safety-anonymous — nothing in the SRS tells a reader *why* the clamp exists or what happens if it's removed. I'd start by making the safety intent explicit at the requirement level: either amend the existing requirement to carry a reference to the risk control ID and the hazard it mitigates, or (better, where the tooling supports it) create a derived safety requirement that states the clamp rate, the tolerance, and the failure condition it guards against, and link the functional requirement to it. Then I'd build the trace chain in both directions: hazard → risk control measure → safety requirement → firmware design element (the specific module/function implementing the clamp) → verification activity. The verification activity needs to be written against the *failure condition*, not just nominal behavior — so the test must command a step change larger than the clamp rate and confirm the output rate of change stays within the specified bound, and ideally also confirm behavior at the boundary and under fault conditions (e.g., sensor dropout mid-ramp). Finally, I'd add a review checkpoint: any requirement that traces to a risk control must name the control, so the intent survives future edits. The practical test of whether the traceability is real is whether someone reading only the SRS could tell that removing that clamp would be a safety regression.

**Possible follow-ups:** If the clamp rate is a tunable constant, how do you trace the *value* as well as the behavior? / How would you handle the case where the same clamp is also credited as a performance control (e.g., mechanical wear reduction), so it has two justifications?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** When the risk analysis credits an emergent property of a loop rather than a single element, the traceability has to be decomposed without losing the whole. I'd keep the risk control measure as a single parent entity in the risk management file, then create a set of *allocated* sub-requirements — one per contributing element — that together define the loop's safe behavior: sensor accuracy and response time, firmware loop bounds and saturation behavior, power switch response and fail-safe state, and the overall loop settling/overshoot requirement that ties them together. Each sub-requirement traces up to the parent control and down to its own design element and verification. Critically, I'd add an *integration-level* verification that exercises the loop as a whole under fault conditions — sensor drift, sensor stuck-at, firmware saturation, switch failure — because element-level tests can all pass while the loop as a system still violates the safe-range requirement. The traceability matrix then shows a fan-out from one control to several requirements and a fan-in from those requirements to both element tests and the integration test. The thing I'd guard against is treating the integration test as redundant once the element tests pass; it's the only evidence that the *emergent* behavior the risk analysis actually credits is present.

**Possible follow-ups:** How do you allocate a single numeric safe-range requirement across elements without over-constraining one of them? / If the PID loop is later retuned, which traceability links tell you what verification must be re-run?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review criteria actually address the failure condition the control mitigates — otherwise the link is nominal, not substantive. My first step would be to read the review checklist against the risk control's failure condition and document the gap explicitly: which specific question in the checklist would have caught a failure of this control? If the answer is "none," the link is invalid regardless of the review having been completed. The fix is to add a control-specific review criterion — a line item that states the failure condition and asks the reviewer to confirm the design addresses it, with a place to record the evidence (schematic reference, calculation, simulation result). I'd also make sure the reviewer has the risk analysis entry in front of them, not just the schematic, because a reviewer who doesn't know the control exists can't assess it. Where the review is the *only* verification for a control, I'd push to add at least one objective check — a calculation, an analysis, or a targeted test — because a review is a judgment activity and its strength depends entirely on the criteria being specific. The general principle: verification method (test, analysis, inspection, review) is less important than whether the method can actually detect the failure mode.

**Possible follow-ups:** How would you retrofit control-specific criteria into a review process that's already underway? / When is a design review genuinely sufficient as the sole verification for a risk control?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control lives in *data*, not in a circuit or a line of code, so the traceability has to cover three things: the parameter's definition and allowed range, the process that sets it, and the verification that the set value is correct on each unit. I'd start by making the parameter a first-class requirement: a requirement that states the parameter, its permitted range, its units, and the hazard it mitigates, traced up to the risk control measure. Then I'd trace down to two distinct design elements — the firmware that reads and enforces the limit, and the manufacturing/programming process that writes it — because a correct value written by a broken process, or a correct process writing to firmware that ignores the value, are different failure modes. Verification splits accordingly: a design verification test that confirms the firmware enforces whatever value is programmed (test with several values across the range, including boundary values), and a production verification that confirms each unit's programmed value is within the permitted range and matches its record. The per-unit nature matters — this is where sample-based verification may not be enough, because the control's effectiveness depends on the value actually stored in *that* unit. I'd also trace the parameter's change control: if the permitted range is revised, the traceability must show which units were built under which revision, otherwise fielded units may be outside the currently-credited range.

**Possible follow-ups:** How would you handle a unit whose stored value is found out of range during service? / What's the traceability link between the manufacturing test record and the device's risk management file?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd treat this as a substantive quality issue rather than a documentation dispute, and I'd be careful not to frame it as an accusation of the systems engineer — the matrix *is* structurally compliant, and that's a real achievement; the problem is that structural compliance isn't the same as evidence. My approach would be: first, verify the claim myself on a small sample — pick two or three of the flagged tests, read the test procedure against the risk analysis failure condition, and see whether the test would actually fail if the control were disabled. That gives me facts rather than hearsay. Second, if confirmed, I'd raise it as a finding with a clear framing: the risk isn't audit failure, it's that we may be shipping with controls whose effectiveness we haven't actually demonstrated, and the cost of finding that out in the field is far higher than re-running a handful of tests. Third, I'd propose a targeted remediation rather than a blanket re-test of everything: a focused review of every test linked to a risk control, checking that each one stresses the failure condition, with re-writes only where the gap is real. Fourth, I'd fix the process cause — a review step where the test author and the person who wrote the risk control sit down together before the test is baselined, so tests are written against the failure condition rather than adapted from a template. I'd also want to understand *why* the copy-and-relabel happened: if it's schedule pressure, the fix is different from if it's a missing template or unclear ownership. Throughout, I'd keep the tone collaborative — the goal is a defensible verification package, not blame.

**Possible follow-ups:** How would you prioritize which linked tests to re-examine first if you can't review them all? / What would you do if the systems engineer continued to insist the matrix was sufficient and escalated the disagreement?
