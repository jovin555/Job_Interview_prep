# risk-requirements-traceability — Day 104

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the requirement captures the *behavior* but not the *safety intent*, so the link between the hazard and the requirement is implicit and fragile — anyone reading the requirement in isolation would see a performance constraint, not a risk control. I'd start by making the safety intent explicit rather than relying on tribal knowledge. Concretely: (1) In the risk management file, record the control with a unique identifier and state the hazard it mitigates, the failure condition it guards against, and the assumed effectiveness (e.g., the limiter bounds the rate of change such that the actuator cannot reach the hazardous state within the system's response time). (2) Add a derived requirement in the firmware SRS that references the risk control ID and states the safety intent alongside the functional behavior — something like "the firmware shall clamp the commanded actuator rate of change to no more than X units/s, implementing risk control RC-xxx against hazardous overspeed." The functional clause stays; the traceability clause is added. (3) Trace that requirement to the verification activity, and make sure the verification actually stresses the failure condition — commanding a step change far larger than the limit and confirming the output ramps rather than steps, and doing so at the worst-case operating point (max load, max supply, worst-case timing). (4) Close the loop back to the risk file so the residual risk evaluation can cite the verification evidence. The key discipline is that the requirement must be *derived from* the risk control, not merely *coincidentally identical to* it — otherwise a future engineer can "optimize" the clamp rate for performance and silently weaken a safety control.

**Possible follow-ups:** If the firmware team pushes back that referencing the hazard in the SRS "clutters" the requirement, how would you frame the argument? And how would you handle the case where the same rate limiter serves both a safety function and a performance function — do you write one requirement or two?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap here is treating the loop as a single atomic control in the traceability matrix, which hides the fact that its effectiveness depends on three independently-owned elements all working. I'd decompose without losing the whole. First, in the risk file, keep the control as one entry but explicitly enumerate its constituent elements and the *assumptions* each makes about the others — the sensor's accuracy and response time, the PID loop's update rate and saturation behavior, the power switch's drop-out time and failure mode. Those assumptions are the real interface between the elements, and they need to become requirements in their own right. Second, in the traceability matrix, model the control as a parent node with child links to each element's requirement(s) and each element's verification, plus a system-level verification that exercises the loop end-to-end under fault conditions (sensor drift, sensor stuck, PID windup, switch failure). Third, make the independence or non-independence explicit: if the sensor and the switch share a power rail, the "loop" isn't as robust as the risk analysis assumes, and that shared dependency belongs in the risk file as a common-cause consideration. The matrix should show, for each element, hazard → control → element requirement → element verification, and then a separate top-level row for the integrated loop verification. That way an auditor can see both the decomposition and the integration, and a change to any one element's requirement is visibly a change to a risk control.

**Possible follow-ups:** How would you verify the loop's behavior when one element fails silently — say the sensor reads plausibly but is drifting — without building a full fault-injection rig? And where would you document the element-to-element assumptions so they don't get lost between the hardware and firmware specs?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review's criteria actually address the control's failure condition — a generic checklist that happens to be applied to the right board is not evidence that the specific hazard was assessed. I'd treat this as a verification-method mismatch, not a paperwork gap. First, confirm what the risk control actually requires: what failure condition must be shown to be mitigated, and what would count as objective evidence that the design addresses it. Second, either (a) extend the review with control-specific review criteria — explicit questions, a dedicated checklist section, and named reviewers with the relevant expertise — and record the outcome against the risk control ID, or (b) if the control is better verified by analysis or test, reclassify the verification method and add the appropriate activity. The decision between these depends on the nature of the control: a creepage/clearance or derating control is genuinely review-and-analysis territory; a functional response to a fault is test territory. Third, update the traceability matrix so the link points to the *specific* review criteria or test, not to the generic review. The principle I'd apply is that the verification activity must be *capable of failing* if the control is inadequate — a review whose checklist can't distinguish a good design from a bad one on this specific point provides no assurance, regardless of how it's labeled in the matrix.

**Possible follow-ups:** How would you handle the reviewer-expertise question — does the review need someone who understands the hazard, or is a generalist reviewer sufficient if the checklist is good? And if you extend the checklist, how do you keep the review from ballooning into a re-design session?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a behavior in the firmware or a component on the board — it's a *value*, and the traceability has to cover how that value is derived, how it's programmed, and how it's confirmed on each unit. I'd structure it in three layers. First, the *derivation*: the risk analysis establishes the maximum allowable current limit from the hazard analysis, and that becomes a requirement with a stated range and rationale — the value isn't arbitrary, it's bounded by the risk control. Second, the *programming*: a manufacturing requirement and procedure that specifies how the parameter is written (what tool, what verification of the write, what read-back), traced to the production process documentation rather than to a design verification test. Third, the *per-unit confirmation*: a production test that reads back the programmed value and confirms it's within the risk-derived range, with the result recorded against the unit's serial number. In the traceability matrix, I'd show hazard → risk control → parameter requirement (with range) → manufacturing procedure → per-unit production test, and separately note that the design verification covers the *mechanism* (that the firmware honors the parameter and that out-of-range values are rejected or clamped) while the production test covers the *instance* (that this unit's value is correct). The distinction matters because a design verification on a golden unit says nothing about whether unit 4,000 got the right value burned in, and a production read-back says nothing about whether the firmware actually enforces the limit. You need both links.

**Possible follow-ups:** What would you do if the parameter can be changed in the field via a service port — does that change the traceability, and how? And how would you handle a unit that comes back from service with a parameter value outside the risk-derived range?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd treat this as a substantive quality issue rather than a documentation dispute, and I'd be careful not to let the "it passes audit" framing shut down the conversation. The matrix being complete is a necessary condition, not a sufficient one — the question is whether the evidence behind each link is valid for *this* system's failure conditions. My approach would be: first, thank the test engineer and protect the disclosure — the worst outcome is that the next person who spots something stays quiet. Second, do a focused sample audit: pick a handful of the flagged tests and walk each one against the risk analysis entry it's supposed to verify, asking "if this control were removed or degraded, would this test fail?" If the answer is no, the link is nominal and needs rework. Third, bring the systems engineer into that audit rather than arguing abstractly — once they see a test that passes with the control disabled, the conversation changes from "is the matrix compliant" to "what do we need to fix." Fourth, scope the remediation: re-derive the affected tests from the failure conditions, re-run them, and update the matrix to reflect the corrected evidence. Fifth, look at the root cause — copied tests usually mean schedule pressure, unclear test-derivation guidance, or a matrix process that rewards link count over link validity — and address that so it doesn't recur. Throughout, I'd keep the tone factual and non-blaming: the goal is valid evidence, not finding a culprit. If the systems engineer continues to resist, I'd escalate on the basis of risk, not process — an unverified risk control is a patient-safety exposure, and that's the frame that matters.

**Possible follow-ups:** How would you decide how many tests to sample before you're confident the problem is contained? And if the rework threatens the verification schedule, how would you prioritize which tests to fix first?
