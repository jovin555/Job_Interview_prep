# risk-requirements-traceability — Day 58

## Q1: How would you approach tracing a risk control measure that is implemented as a firmware-based watchdog kick — where the firmware must periodically write to a hardware register to prove liveness — when the firmware team owns the kick logic and the hardware team owns the watchdog peripheral, and neither team's requirements document references the other?

**Answer:** The core problem is that the control is a *contract* between two subsystems, and a contract needs a single owner who defines the interface and both parties who implement against it. I'd start by recognizing that the risk control is not "the firmware kicks the watchdog" or "the watchdog resets the MCU" — it's the *pairing*: a bounded liveness guarantee. So the first artifact I'd create is a system-level safety requirement that states the emergent behavior in measurable terms — for example, "if the firmware fails to execute its main loop within the specified period, the system shall be reset and enter a safe state within a bounded time." That requirement lives in the SRS, not in either team's document, and it becomes the anchor that both the hardware and firmware requirements trace *up* to.

From there, I'd decompose it into two interface-level requirements: one on the hardware side (the watchdog peripheral shall assert a reset if no valid kick is received within the configured window, with the window value specified) and one on the firmware side (the firmware shall issue a valid kick only from the main loop, not from an interrupt or a timer ISR, so that a hung main loop actually triggers the reset). Both of these trace up to the system safety requirement, and both trace down to their respective design elements and verification activities. The key discipline is that the *interface* — the register address, the kick pattern, the window value, the reset behavior — is captured in an ICD that both teams reference by the same identifier. That ICD is what makes the two separate requirements documents linkable without forcing one team to adopt the other's numbering scheme.

For verification, I'd want at least three activities: a hardware-level test that the watchdog peripheral resets when kicks stop (verified on the peripheral in isolation), a firmware-level test that the kick is issued from the correct context (verified by inspection or by a fault-injection test that hangs the main loop), and a system-level test that the *combination* produces the safe state within the bounded time. The system-level test is the one that actually verifies the risk control, because it's the only one that exercises the emergent behavior. The lower-level tests are necessary but not sufficient — they verify the pieces, not the contract.

**Possible follow-ups:**
- If the firmware team later changes the kick period to a different value, how would your traceability scheme catch the fact that the hardware watchdog window is now mismatched, before it reaches verification?
- How would you handle the case where the watchdog reset itself is a hazard — for example, if resetting mid-procedure could leave a device in an unsafe state — and the risk control now needs a second control to manage the reset behavior?

## Q2: How would you approach deciding whether a risk control measure should be traced to a design requirement, a design element, or both — and what practical difference does that distinction make in a traceability matrix?

**Answer:** The distinction matters because requirements and design elements answer different questions, and a traceability matrix that conflates them becomes either unreadable or un-auditable. A *requirement* is a statement of what the system must do or be — it's testable, it has an acceptance criterion, and it's the thing verification activities are written against. A *design element* is a specific implementation choice — a component, a circuit block, a firmware module, a mechanical feature — that satisfies one or more requirements. A single requirement can be satisfied by multiple design elements, and a single design element can satisfy multiple requirements, so the mapping is many-to-many and needs to be captured explicitly rather than assumed.

For a risk control measure, I'd trace it to a *requirement* whenever the control has a measurable behavior that needs to be verified — which is almost always. The requirement is what the verification activity tests against, and it's what gives the control an objective acceptance criterion. I'd trace it to a *design element* when the control's effectiveness depends on a specific implementation choice that isn't fully captured by the requirement — for example, a control that relies on physical separation between two traces, or on a particular component's failure mode, or on the independence of two firmware tasks. In those cases, the design element is where the *rationale* lives, and the requirement alone doesn't tell a reviewer why the control works.

The practical difference in the matrix is that requirement links drive verification coverage, while design element links drive design review coverage. If a risk control is traced only to a design element and not to a requirement, it will likely be missed by the verification plan — the test engineer has nothing to test against. If it's traced only to a requirement and not to a design element, a design reviewer may not realize that the control depends on a specific implementation choice that could be changed without anyone noticing. So I'd want both links for any control whose effectiveness depends on implementation, and at minimum a requirement link for every control.

**Possible follow-ups:**
- If a design element is changed — say a component is substituted — how would your traceability scheme flag which risk controls need to be re-verified?
- How would you handle a risk control that is implemented entirely through a design rule (e.g., a creepage distance) where there is no functional requirement to trace to?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity's acceptance criterion is stated as "the control functions as designed" rather than as a measurable pass/fail threshold?

**Answer:** "Functions as designed" is not an acceptance criterion — it's a placeholder that defers the actual judgment to whoever runs the test, which means the test is not repeatable and the result is not objective evidence. The first thing I'd do is treat this as a requirements defect, not a test defect, because the test can only be as precise as the requirement it verifies. If the requirement itself doesn't have a measurable threshold, the test author had nothing to write against. So I'd trace back up from the test to the requirement and check whether the requirement is measurable. If it isn't, the fix starts there.

For a risk control, the requirement should state the failure condition it mitigates and the measurable behavior that demonstrates the control is working. For example, instead of "the over-temperature control shall function as designed," the requirement should say something like "when the sensed temperature exceeds the threshold, the system shall disable the heater output within the specified response time, and shall not re-enable it until the temperature falls below the reset threshold." That gives the test author three measurable things: the trip point, the response time, and the reset behavior. The acceptance criterion then becomes a set of pass/fail thresholds against those three, with tolerances specified.

If the requirement is already measurable but the test's acceptance criterion is vague, then the fix is at the test level — rewrite the acceptance criterion to match the requirement's thresholds, and add the specific test conditions (nominal, worst-case, fault-injected) that the risk analysis says the control must handle. I'd also check whether the test actually stresses the failure condition or just exercises the control under nominal conditions, because a vague acceptance criterion often hides a test that never triggers the control at all.

The broader point is that "functions as designed" is a symptom of a missing measurable requirement, and the fix is to close that gap at the source rather than patching the test. If the requirement can't be made measurable, that's a signal that the risk control itself may not be well-defined enough to verify, which is a risk management issue, not just a documentation issue.

**Possible follow-ups:**
- If the requirement is measurable but the test engineer argues that the threshold is "obvious" and doesn't need to be written down, how would you handle that?
- How would you handle a risk control whose correct behavior is genuinely difficult to express as a single threshold — for example, a control that depends on the *rate* of change of a signal rather than its absolute value?

## Q4: (Behavioral) Imagine you're leading a project where the systems engineer has built a traceability matrix that links every risk control measure to a verification activity, and the matrix is complete and passes audit. However, a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and that nobody has confirmed the tests actually exercise the failure conditions in this project's risk analysis. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The matrix being complete and the tests passing are both necessary but neither is sufficient — the question is whether the tests actually verify the controls they're linked to, and a copied test with adjusted labels is a classic case where the link exists on paper but the verification is hollow. I'd treat the test engineer's disclosure as a serious signal and handle it carefully, because the person who raised it took a risk to do so, and how I respond will determine whether future problems get surfaced or buried.

My first step would be to verify the concern rather than act on it immediately — I'd pick two or three of the flagged tests and walk through them against the risk analysis myself, checking whether the test conditions actually reproduce the failure mode the control is meant to mitigate. If the test exercises the control under nominal conditions but the risk analysis specifies a fault condition, that's a concrete gap I can point to, not an accusation. I'd want to be able to say "this test applies a nominal input, but the risk analysis says the control must respond to a sensor fault — the test doesn't create that fault, so it can't demonstrate the control works."

Once I have concrete examples, I'd bring it to the systems engineer and the test lead together, framed as a coverage gap rather than a compliance failure. The systems engineer's position — that the matrix is compliant — is technically true but misses the point: compliance is about the *evidence* being valid, not just the links existing. I'd propose a targeted review of the flagged tests against their linked risk controls, with the test engineer and the systems engineer both present, and a clear criterion: for each test, can we point to the specific step that reproduces the failure condition, and does the acceptance criterion match the requirement? Tests that fail that check get rewritten or replaced.

I'd also want to understand *why* the tests were copied — was it schedule pressure, a lack of clarity about what the tests needed to exercise, or a process that rewarded matrix completeness over verification quality? If it's systemic, fixing three tests doesn't fix the problem. I'd look at whether the test plan review process has a step that checks test-to-risk-control alignment, and if not, add one. And I'd make sure the test engineer who raised the concern isn't penalized for it — if anything, that's exactly the behavior the process should encourage.

**Possible follow-ups:**
- If the systems engineer pushes back and says the tests are fine because they pass, how would you move the conversation forward without turning it into a personal conflict?
- How would you handle the situation if the copied tests had already been submitted as part of a regulatory submission, and the gap was discovered afterward?

## Q5: How would you approach establishing traceability for a risk control measure that is implemented as a redundant channel — for example, a primary sensor path and an independent secondary path whose agreement is checked — where the control's effectiveness depends on the *independence* of the two channels rather than on either channel alone?

**Answer:** Redundancy is a case where the risk control is not located in either channel — it's located in the *relationship* between them, and specifically in the property of independence. That makes it one of the harder controls to trace, because the thing being verified is a negative property: the absence of a common cause that could fail both channels simultaneously. A traceability scheme that only links each channel to its own requirements and tests will miss the control entirely, because neither channel's test demonstrates independence.

I'd start by writing a system-level safety requirement that states the control in terms of the emergent behavior: for example, "if the primary and secondary sensor paths disagree beyond a specified tolerance, the system shall detect the disagreement and enter a safe state within a bounded time." That requirement traces down to three things: the primary path's requirement, the secondary path's requirement, and a *comparison* requirement that defines the tolerance, the detection time, and the safe-state behavior. The comparison requirement is the one that actually implements the risk control, and it's the one that needs its own verification activity.

For independence, I'd treat it as a separate design constraint that needs its own analysis and its own verification. The analysis would be a common-cause failure analysis — looking at shared power rails, shared clocks, shared communication buses, shared firmware tasks, shared PCB regions, shared environmental exposure — and identifying any path by which a single fault could affect both channels. Each identified common-cause path becomes either a design requirement (e.g., "the two channels shall be powered from independent regulators") or a documented residual risk. The verification of independence is typically a mix of analysis (for shared resources) and test (for fault injection — deliberately failing one channel and confirming the other still functions and the disagreement is detected).

In the traceability matrix, I'd want the redundancy control to appear as a single row with links to: the system safety requirement, the comparison requirement, the independence requirements, the design elements for both channels, the common-cause analysis, and the verification activities for both the comparison logic and the independence property. The key discipline is that the matrix must show the *control* as a single entity even though it's implemented across multiple components — otherwise a reviewer will see two channel tests and conclude the control is verified, when in fact the independence property was never checked.

**Possible follow-ups:**
- If the two channels share a common power supply but the design includes a filter on each channel's supply, how would you decide whether that's sufficient independence or whether a common-cause failure still exists?
- How would you handle the case where the redundancy control is implemented in firmware (the comparison logic) but the independence property depends on hardware (separate sensor front-ends), so the control spans both domains?
