# risk-requirements-traceability — Day 94

## Q1: How would you approach tracing a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the requirement and the risk analysis describe the same behavior in two different languages — one functional, one safety-intent — and nothing formally connects them. I'd start by treating the risk analysis entry as the authoritative statement of *why* the limiter exists, and the firmware requirement as the statement of *what* it does. The traceability link should run from the hazard, through the risk control measure, to the firmware requirement, and then to verification. If the firmware requirement doesn't reference the hazard, the link is broken at the requirement level even though the behavior is implemented.

Practically, I'd do three things. First, add an explicit safety-intent annotation to the firmware requirement — not necessarily rewriting it, but attaching a reference to the risk control ID and the hazard it mitigates, so anyone reading the requirement sees why the clamp value and rate limit are what they are. Second, verify that the requirement is actually *measurable* in a way that reflects the hazard: "clamps commanded speed to a maximum rate of change" needs a numeric rate, a tolerance, and a defined behavior at the boundary (does it clamp, reject, or saturate?). If the requirement is vague, the verification can't demonstrate the control works. Third, check that the verification test stresses the failure condition — commanding a step change large enough that an unclamped system would overspeed — rather than just confirming the motor reaches a setpoint smoothly.

The deeper point is that a rate limiter credited as a risk control is a *safety function*, and safety functions deserve requirements that state the safety intent, not just the functional behavior. If the firmware team resists adding safety language to their SRS, I'd propose a lightweight cross-reference field rather than a rewrite — the goal is that a reviewer can follow the chain from hazard to code to test without needing tribal knowledge.

**Possible follow-ups:** If the clamp value is a tunable parameter, how do you trace the parameter value itself as part of the control? And how would you verify the limiter behaves correctly when the actuator is already at its maximum and a new command arrives?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** This is the classic case where the risk analysis reasons at the level of *emergent system behavior* while the requirements and design artifacts are organized by component. The control isn't any one element — it's the loop. So the traceability scheme has to represent the loop as a first-class entity, not try to force it into a single component's requirements.

I'd create a system-level safety requirement that describes the loop's behavior as a whole: the safe range, the response time to bring the element back within range after a disturbance, and the behavior on sensor fault or actuator failure. That requirement is the anchor. Then I'd decompose it into allocated requirements for each contributor — the sensor's accuracy and response time, the PID loop's update rate and output limits, the power switch's switching behavior and failure modes — and trace each allocated requirement back up to the system-level safety requirement. The risk control measure in the risk file links to the system-level requirement, and the system-level requirement links down to the three allocated requirements, each of which links to its own verification.

The important discipline is that the *integration* verification — the test that demonstrates the loop as a whole keeps the element in range under realistic disturbances — must exist and must be traced to the system-level requirement. Component-level tests alone don't prove the loop works, because the loop's safety depends on the interaction: a perfectly accurate sensor and a perfectly functional switch can still produce a hazardous overshoot if the PID tuning or the update rate is wrong. I'd also make sure the risk analysis's assumptions about the loop — sampling rate, sensor placement, thermal time constant — are captured somewhere traceable, because those assumptions are effectively part of the control.

**Possible follow-ups:** How would you handle a change to the PID tuning after verification — does that invalidate the loop's verification? And how do you trace the failure modes of each element (sensor stuck, switch welded closed) when the risk analysis treats the loop as one control?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review actually assesses the thing the control is supposed to do. A general checklist that happens to touch the same subsystem is not evidence that the specific failure condition was evaluated — it's evidence that *something* was reviewed. The traceability link exists, but it's a false link: it points to an activity that doesn't exercise the control's intent.

My approach would be to first confirm what the review actually covered by looking at the review record — the checklist items, the attendees, the findings. If the risk control's failure condition isn't in there, the link is not valid and I'd treat it as a gap. Then I'd decide how to close it: either extend the review with a focused set of review criteria specific to the control (for example, "confirm the bulk capacitor voltage rating exceeds the worst-case transient by the specified margin, and confirm the derating calculation is documented"), or replace the review with a test or analysis that directly addresses the failure condition, whichever is more appropriate for the control type.

The fix isn't just to add a line to the checklist — it's to make the review criteria *derived from* the risk control's failure condition, so that a reviewer who doesn't know the risk analysis can still assess the control by following the criteria. I'd also add a review-record field that captures the specific control ID being assessed and the reviewer's conclusion, so the evidence is auditable. If the same general checklist is used across many reviews, I'd propose a control-specific addendum rather than rewriting the whole checklist, to keep the change manageable.

**Possible follow-ups:** How would you handle a review that already happened and passed, but you now believe didn't assess the control — do you re-review or supplement with a test? And how do you prevent this pattern from recurring across a large review program?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** When the parameter value *is* the control, the traceability has to cover three distinct things: the parameter's definition and allowed range, the manufacturing process that sets it, and the per-unit verification that confirms it was set correctly. A traceability scheme that only links the risk control to a firmware requirement saying "the current limit shall be configurable" misses the point — the control isn't the configurability, it's the specific value and the assurance that it's correct on each unit.

I'd structure it as follows. The risk analysis credits the current limit as a control and states the required limit and tolerance. That maps to a system requirement that defines the parameter, its allowed range, its default, and the consequence of an out-of-range value. The manufacturing process — the programming step, the calibration procedure, the fixture — becomes a *process requirement* or work instruction that's traceable to the same control, because the process is what actually realizes the control on each unit. And the per-unit verification — the production test that reads back the parameter and confirms it's within tolerance — is the verification activity, with the test record (serialized to the unit) as the objective evidence.

The tricky part is that this is a *per-unit* control, not a design-level one, so the verification evidence is a population of production records rather than a single design verification test. I'd make sure the traceability matrix distinguishes design verification (does the mechanism work?) from production verification (was it set correctly on this unit?), and that the risk file references both. I'd also want a change-control path: if the allowed range changes, the risk analysis, the requirement, the manufacturing instruction, and the production test all need to move together, and the traceability links are what make that visible.

**Possible follow-ups:** How would you handle a unit that fails the production parameter check — is that a nonconformance, and how does it feed back into the risk file? And how do you verify the parameter can't be changed in the field outside the allowed range?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The matrix being complete and the tests passing are both true and both insufficient — the question is whether the evidence actually demonstrates the controls work, and a copied test with adjusted labels is a hypothesis, not evidence. I'd treat the test engineer's disclosure as a serious quality signal and handle it carefully: protect the source, because the person who raised it did the right thing and shouldn't be exposed, and don't turn it into a blame exercise against whoever copied the tests, because copying a similar test is a rational response to schedule pressure and the process allowed it.

My first step would be to verify the concern rather than accept or dismiss it — pick a sample of the flagged tests and walk through each one against the risk analysis entry it's supposed to verify. Does the test setup reproduce the failure condition? Does the stimulus actually drive the system into the hazardous state? Does the acceptance criterion map to the risk control's required behavior? In many cases the copied test will be *partially* valid — it exercises the right subsystem but not the right fault condition — and the fix is to extend it rather than discard it. In some cases it'll be genuinely wrong and need to be rewritten.

Then I'd address the systemic issue. The systems engineer's position — "the matrix is compliant and the tests pass" — reflects a process that measures traceability by link count rather than by evidence quality. I'd propose adding an evidence-quality check to the verification review: for each risk control, a reviewer confirms the test actually stresses the failure condition, not just that a test exists. That's a review criterion, not a new document, so it's cheap to adopt. I'd also want to understand *why* the tests were copied — if it's schedule pressure, the fix is to build test-development time into the plan for risk-control verification specifically, because those tests are the ones that can't be templated safely.

Finally, I'd be transparent with the quality function about what was found and what's being done, because discovering this internally and fixing it is far better than having an auditor or a regulator discover it later. The goal isn't to protect the matrix's appearance — it's to make sure the controls actually work.

**Possible follow-ups:** How would you prioritize which flagged tests to re-examine first, given limited time? And how would you change the test-development process so that risk-control tests are treated differently from functional tests?
