# risk-requirements-traceability — Day 62

## Q1: How would you approach tracing a risk control measure that is implemented as a "safe state" defined by a combination of hardware and firmware — for example, a system that must enter a low-power, outputs-disabled state within a bounded time after a fault is detected — when the safe state itself is not a single component but an emergent system behavior?

**Answer:** The core difficulty here is that the risk control isn't a component or a line of code — it's a *behavior* that only exists when several subsystems act in concert, so a traceability scheme that only links requirements to design elements will miss it entirely. I'd start by decomposing the emergent behavior into its constituent, individually traceable pieces while keeping a single top-level entry that represents the whole. Concretely: create one risk control measure in the risk management file for "system enters safe state within bounded time T after fault detection," then derive from it a small set of *allocated* requirements — a fault-detection requirement (hardware or firmware), a fault-propagation/response requirement (firmware decision logic), an actuation requirement (hardware output disable path), and a timing requirement (the bounded time T) that spans the boundary. Each allocated requirement traces to a design element and a verification activity, but the top-level control also traces to an *integration* verification that exercises the whole chain end-to-end under a fault injection. That integration test is the one that actually proves the emergent behavior; the per-subsystem tests only prove the pieces. The key discipline is that the timing budget must be decomposed and allocated across the chain (detection latency + decision latency + actuation latency ≤ T), with margin, and each allocation verified — otherwise you can pass every subsystem test and still miss the system-level bound. I'd also make sure the safe-state definition itself (what "outputs-disabled" and "low-power" mean, measurably) is captured as acceptance criteria, not left as prose, because "safe state" is exactly the kind of term that different teams interpret differently.

**Possible follow-ups:**
- How would you verify the timing budget when the detection, decision, and actuation latencies are measured by different teams on different benches?
- If a subsystem test passes but the end-to-end integration test fails the timing bound, how would you localize which allocation is at fault?

## Q2: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity's test procedure was written against an earlier revision of the requirement, so the test still passes but no longer exercises the current acceptance criteria?

**Answer:** This is a configuration-control failure as much as a traceability failure, and the fact that the test still passes is the dangerous part — it gives false confidence. The first thing I'd do is establish the actual delta: diff the requirement revision the test was written against versus the current revision, and identify precisely what changed — a threshold, a timing bound, a condition, a mode. Then I'd assess whether the change is material to the risk control: if the acceptance criterion moved (say, a response time tightened, or a fault condition was added), the existing test is no longer valid evidence and must be revised and re-run. If the change was purely editorial, the test may still stand, but that determination needs to be documented, not assumed. The systemic fix is to make the linkage revision-aware: the traceability record should capture not just "requirement X → test Y" but the *version* of the requirement the test was validated against, so that any requirement change automatically flags linked verification activities for review. In practice this means either a requirements management tool with suspect-link detection, or a disciplined review step in the change-control process where a requirement change triggers a check of every downstream test. I'd also treat this as a signal to audit whether other tests have the same staleness problem, because if one drifted, others likely did too.

**Possible follow-ups:**
- How would you decide whether a requirement change is "material" enough to invalidate a test, without re-running every test on every editorial change?
- What would you put in the change-control process to prevent a test from silently going stale again?

## Q3: How would you approach establishing traceability for a risk control measure that is implemented as a redundant channel — for example, a primary sensor path and an independent secondary path whose agreement is checked — where the control's effectiveness depends on the *independence* of the two channels rather than on either channel alone?

**Answer:** The subtlety is that the risk control's value comes from a property — independence — that isn't located in either channel, so tracing each channel separately and declaring victory would miss the point entirely. I'd structure it in layers. First, each channel gets its own requirements and verification: the primary path must produce a valid reading, the secondary path must produce a valid reading, and the comparison logic must detect disagreement and respond. Those are traceable in the normal way. But then there's a separate, explicit requirement for *independence* itself, and that's the one people forget. Independence has to be defined measurably — what does it mean for these two channels to be independent? It typically means no shared failure mode: separate sensors, separate signal conditioning, separate power domains, separate ADC channels or even separate microcontrollers, no shared clock, no shared communication bus that a single fault could take down. So I'd derive requirements that capture those constraints (e.g., "the two channels shall not share a power rail," "a single point fault shall not disable both channels") and verify them by analysis — a common-cause failure analysis or a fault tree — rather than by a functional test, because you can't test independence by running the system normally. The verification of independence is fundamentally an analysis activity, and the traceability matrix needs to reflect that: the independence requirement traces to a common-cause analysis, not to a bench test. Finally, the comparison-and-response logic gets its own functional verification, including the case where one channel drifts out of agreement with the other.

**Possible follow-ups:**
- How would you verify independence when the two channels share a PCB and therefore share some environmental and mechanical failure modes?
- If a common-cause analysis reveals a shared failure mode you can't eliminate, how does that change the risk control's claimed effectiveness?

## Q4: How would you approach deciding whether a risk control measure should be traced to a design requirement, a design element, or both — and what practical difference does that distinction make in a traceability matrix?

**Answer:** The distinction matters because a requirement and a design element answer different questions, and conflating them is a common source of traceability gaps. A *design requirement* states what the system must do or must be — it's a specification statement with measurable acceptance criteria ("the firmware shall disable the motor output within 100 ms of a valid over-temperature assertion"). A *design element* is the thing that implements it — a specific comparator circuit, a firmware module, a state machine, a mechanical interlock. The practical difference: requirements are what you verify against, and design elements are what you inspect, review, or test. If a risk control is traced only to a design element, you have no acceptance criterion to verify against — you can point at the circuit but not state what "working" means. If it's traced only to a requirement, you may have a specification with no identified implementation, which is a gap you can't close during verification. So for a well-formed control I'd want both: the risk control measure traces to one or more design requirements (the "what"), each of which traces to one or more design elements (the "how"), and each requirement traces to a verification activity. The matrix then supports two different audits: "is every requirement implemented?" (requirement → element) and "is every requirement verified?" (requirement → verification). Some controls genuinely only need one link — a purely procedural control might have a requirement but no design element, and a derating rule might be a design element with the requirement implicit in a design standard — and in those cases the matrix should say so explicitly rather than leave a blank cell that looks like an oversight.

**Possible follow-ups:**
- How would you handle a design element that implements several requirements at once — for example, a single microcontroller that runs multiple risk-control functions?
- When a risk control is captured only as a design element with no explicit requirement, how would you decide whether to promote it to a requirement?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has built a traceability matrix that links every risk control measure to a verification activity, and the matrix is complete and passes audit. However, a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and that nobody has confirmed the tests actually exercise the failure conditions in this project's risk analysis. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The matrix being complete and the tests passing are both true and both beside the point — the question is whether the evidence actually demonstrates the controls work, and a copied test with relabeled labels is exactly the kind of thing that passes audit while providing no real assurance. I'd treat the private report as a serious signal and act on it without putting the test engineer in an awkward position: I wouldn't name them as the source, I'd frame it as a routine review of verification adequacy. Concretely, I'd take a sample of the flagged tests and walk each one against its risk control: does the test setup reproduce the failure condition the control is meant to mitigate? Does it inject the fault, or does it just run the system under nominal conditions and observe a pass? Does the acceptance criterion match the requirement? For any test that doesn't actually stress the failure condition, the evidence is invalid regardless of the pass result, and it needs to be rewritten and re-run. I'd then widen the review — if several tests were copied, the whole verification set deserves a coverage check, not just the ones reported. On the disagreement with the systems engineer: I'd reframe it away from "is the matrix compliant?" (it is) to "does the matrix link to evidence that demonstrates the control?" (it may not). Compliance is a floor, not a ceiling. I'd also want to understand *why* the tests were copied — schedule pressure, unclear risk analysis, lack of test-development time — because that root cause will produce the same problem again on the next project unless it's addressed.

**Possible follow-ups:**
- How would you protect the test engineer who raised the concern, given that the review will inevitably touch the tests they flagged?
- If the schedule can't absorb re-running all the affected tests, how would you prioritize which ones must be redone first?
