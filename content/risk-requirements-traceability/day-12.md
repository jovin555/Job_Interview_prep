# risk-requirements-traceability — Day 12

## Q1: How would you approach establishing bidirectional traceability between risk control measures and verification activities when the verification plan uses a mix of test methods — automated tests, manual test procedures, design reviews, and analysis — rather than just pass/fail tests?

**Answer:** The first principle is that traceability doesn't require every verification activity to be a pass/fail test — it requires that each risk control measure has *objective evidence* of verification, and that the evidence is appropriate to the nature of the control. I'd start by categorizing each risk control measure by its implementation type: hardware (e.g., a comparator circuit), firmware (e.g., a timeout), or a combination. For hardware controls, automated or manual functional tests are usually appropriate, but some controls — like component derating or creepage distances — are better verified by design review or analysis. For firmware controls, code review combined with targeted dynamic testing is often the right mix. The key is that the traceability matrix should capture not just "requirement X → test Y" but also the *verification method* (test, analysis, inspection, demonstration) and the *rationale* for why that method is sufficient. For example, if a risk control is a hardware watchdog timer, a functional test that asserts a reset when the heartbeat stops is appropriate. But if the control is a firmware plausibility check on a sensor reading, you might need both a code review (to confirm the logic is correct) and a dynamic test (to confirm it behaves correctly under fault injection). I'd also ensure that the traceability matrix records the verification artifact identifier (test procedure number, analysis report number, review minutes) so an auditor can find the evidence. One important nuance: for analysis-based verification, the analysis itself must be documented with its assumptions, inputs, and results — and the traceability link should point to that document, not just to a checkbox in a spreadsheet.

## Q2: How would you approach handling a situation where a risk control measure is traced to a verification test, but the test was written to verify a *different* requirement — and the test happens to exercise the risk control as a side effect, so it passes, but it doesn't actually stress the failure condition the risk control is meant to mitigate?

**Answer:** This is a classic traceability trap — the test passes, the requirement number matches, but the test doesn't actually verify the risk control. The first step is to recognize that a test that exercises a control as a side effect is not the same as a test that verifies the control. I'd start by reviewing the test procedure against the risk control's intended function and the failure scenario it mitigates. The question to ask is: does the test create the *fault condition* identified in the risk analysis, or does it just observe the control operating under nominal conditions? If the test doesn't stress the fault condition, it's not adequate verification, regardless of whether it passes. I'd then work with the test engineer to either modify the existing test to include fault injection, or create a new test specifically for the risk control. The traceability matrix should be updated to reflect the corrected link — and importantly, the discrepancy should be documented. In a regulated environment, this kind of finding during design verification would typically be logged as a non-conformance or at least a documented deviation, because it indicates the verification plan had a gap. I'd also review other traceability links to see if the same pattern exists elsewhere — if one test was incorrectly linked, there may be others. Finally, I'd update the verification planning process to include a step where each test is reviewed not just for "does it map to a requirement?" but "does it actually exercise the requirement's acceptance criteria, including fault conditions where applicable?"

**Possible follow-ups:**
- How would you distinguish between a test that "exercises the control as a side effect" versus one that genuinely verifies it, in a way you could explain to a test engineer who disagrees?
- Would you require the original test to be re-run, or would you only run the new, corrected test?

## Q3: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system uses a combination of hardware and firmware to implement a single control, and the hardware and firmware teams maintain separate requirements documents with different numbering schemes?

**Answer:** The core challenge here is that a single risk control measure spans two engineering domains, each with its own document structure. I'd approach this by introducing a system-level traceability layer that sits above the individual team documents. The risk control measure would be defined at the system level — for example, "the system shall shut down the motor within 200ms of detecting an over-temperature condition" — and then decomposed into hardware and firmware contributions. The hardware contribution might be "the temperature sensor shall provide a valid reading within ±2°C across the operating range," and the firmware contribution might be "the firmware shall initiate motor shutdown within 50ms of receiving an over-temperature signal." Each of these becomes a requirement in the respective team's document, with its own identifier. The traceability matrix then links: system-level risk control → hardware requirement (with its HW-xxx identifier) → hardware verification test (with its HW-TEST-xxx identifier), and similarly for firmware. The key is that the system-level traceability matrix is the single source of truth for the *control* — it shows the decomposition and the verification evidence for each part. I'd also ensure that the risk management file references the system-level control definition, not the individual hardware or firmware requirements, so that if the design changes, the risk analysis stays stable. One practical detail: I'd use a naming convention that makes the decomposition explicit — for example, appending "-HW" and "-FW" suffixes to the control identifier in the traceability matrix, so it's immediately clear which parts are hardware and which are firmware.

## Q4: How would you approach determining whether a risk control measure that is implemented as a combination of hardware and firmware — for example, a hardware sensor detecting a fault and firmware deciding to take action — should be verified as a complete system, or whether separate hardware and firmware verification is sufficient?

**Answer:** The answer depends on the nature of the interaction between the hardware and firmware. If the hardware and firmware each have well-defined interfaces and the risk control's behavior is fully determined by the sum of the parts, then separate verification may be sufficient — but only if the interface between them is also verified. For example, if the hardware sensor produces a digital signal that the firmware reads, you need to verify: (1) the sensor produces the correct signal under fault conditions (hardware test), (2) the firmware correctly interprets that signal and takes the right action (firmware test), and (3) the interface between them — the electrical connection, the signal timing, the protocol — is correct. The third item is often the gap. I'd approach this by first defining the interface between hardware and firmware in an interface control document (ICD) — signal levels, timing, protocol, and the meaning of each signal state. Then I'd determine whether the risk control can be adequately verified by testing each side against the ICD, or whether a system-level test is needed. In practice, for safety-critical controls, I'd typically recommend at least one system-level test that exercises the complete chain — sensor, interface, firmware decision, and actuator action — because it catches integration issues that component-level tests miss. For example, a hardware test might verify the sensor outputs the correct voltage, and a firmware test might verify the firmware responds correctly to a simulated input, but only a system-level test verifies that the actual sensor's output is correctly interpreted by the actual firmware running on the actual processor. The traceability matrix should show both levels: component-level tests for each part, and a system-level test for the integrated behavior.

- What would you do if a system-level test fails, but both the hardware and firmware component tests pass?

## Q5: (Behavioral) Imagine you're leading a project where the verification engineer has created a test that exercises a risk control measure, but the test is designed to run in a "best-case" configuration — for example, using a fresh battery, nominal temperature, and a known-good sensor. The test passes, but you know from the risk analysis that the control must also work under worst-case conditions, such as low battery, high temperature, and a sensor that is drifting out of specification. The verification engineer argues that the test is sufficient because the risk control is "designed to work across the full range" and the worst-case conditions are covered by design margin, not by testing. The quality manager insists that the test must include worst-case conditions. How would you resolve this disagreement?

**Answer:** I'd start by acknowledging that both perspectives have merit — the verification engineer is right that design margin is a legitimate risk control strategy, and the quality manager is right that verification should demonstrate the control works under the conditions it's designed for. The resolution lies in the risk analysis itself. I'd go back to the risk management file and look at the hazard analysis: what fault conditions and operating conditions were identified as relevant to this risk control? If the risk analysis specifies that the control must operate under low battery and high temperature, then verification must demonstrate that — either by testing at those conditions, or by a documented analysis that shows the design margin is sufficient. The key is that the verification method must match the risk analysis. If the risk analysis says "the control shall operate at 3.0V to 4.2V battery voltage," then testing at nominal voltage alone is insufficient. I'd facilitate a discussion where the verification engineer and quality manager review the risk analysis together, and I'd ask: "What does the risk analysis require the control to do, and under what conditions?" If the risk analysis is clear, the answer is clear. If the risk analysis is ambiguous, then the gap is in the risk analysis, not the test — and we need to clarify the risk analysis first. In practice, I'd likely end up with a compromise: run the test at nominal conditions as a baseline, and then either run additional tests at worst-case conditions or produce a documented analysis (e.g., a worst-case circuit analysis) that demonstrates the control will work at the extremes. The analysis would need to be rigorous enough to satisfy the quality manager — including component tolerances, temperature effects, and aging. The important thing is that the decision is driven by the risk analysis, not by either person's preference, and that the outcome is documented in the verification plan with a clear rationale.

**Possible follow-ups:**
- How would you handle a situation where the risk analysis specifies worst-case conditions, but the test equipment cannot simulate those conditions (e.g., extreme temperature)?
- What would you do if the verification engineer produces a worst-case analysis, but the quality manager argues that analysis is not sufficient and only physical testing is acceptable?
