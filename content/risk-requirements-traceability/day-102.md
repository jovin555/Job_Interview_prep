# risk-requirements-traceability — Day 102

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement captures the *mechanism* but not the *safety intent*, so the traceability link from hazard to requirement is broken at the semantic level even if it exists on paper. I would start by treating the risk analysis entry as the authoritative source of intent: the hazard is overspeed, the control is a rate limiter, and the requirement must be reworded or annotated so that it explicitly states the safety purpose — something like "the firmware shall clamp the commanded motor speed to a maximum rate of change of X per unit time, to prevent hazardous overspeed conditions." That gives the requirement a hazard reference (the risk control ID) in addition to its functional description.

From there I would build the traceability chain in both directions: hazard → risk control measure → firmware requirement → design element (the specific module/function implementing the clamp) → verification activity. The verification activity is where I'd be most careful, because a test that only confirms "the clamp works under nominal command inputs" does not demonstrate the control mitigates the hazard. The test needs to drive the system into the failure condition the limiter is meant to guard against — a command step or ramp that would produce overspeed if unclamped — and confirm the output stays within the safe envelope. I'd also want a negative test: disable or bypass the limiter and confirm the test fails, which proves the test is actually sensitive to the control.

Finally, I'd add a review checkpoint so that any firmware requirement derived from a risk control carries an explicit reference to the risk management file entry, and I'd flag this as a systemic gap to fix across the requirement set, not just this one item.

**Possible follow-ups:** If the rate limiter is one of several layered controls against overspeed, how do you avoid double-counting it in the risk analysis while still tracing it correctly? / How would you handle the case where the rate limit value is configurable at runtime rather than fixed in firmware?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap with a distributed control loop is that the risk analysis credits a single control, but the implementation is spread across three elements owned by different disciplines, so no single requirements document owns the whole thing. I would decompose the control into its constituent parts while preserving the top-level identity: keep one risk control measure ID in the risk management file, then create sub-requirements or design elements for each contributor — sensor accuracy and response time, PID loop behavior and saturation limits, power switch response and fail-safe state — each traced back to the parent control ID. That way the matrix shows one control with multiple implementing elements, rather than three orphan requirements.

The critical piece is the *interface* between the elements, because the loop only works if the handoffs are correct: the sensor's output range and update rate must match what the PID loop expects, and the PID output must map correctly onto the power switch's control input. I'd capture those in an interface control document or equivalent, and trace the ICD to the risk control as well, since a broken interface is a plausible failure mode that the risk analysis should account for.

For verification, I would not accept three independent element-level tests as sufficient evidence that the loop mitigates the hazard. Each element test is necessary but not sufficient — the control's effectiveness is an emergent property of the loop, so there needs to be an integrated test that drives the full loop into the hazardous condition (e.g., a thermal load that would overshoot if the loop failed) and confirms the safe range is maintained. I'd also want to think about single-point failures within the loop: if the sensor fails high or low, does the loop fail safe? That's a risk-analysis question that should feed back into the requirements.

**Possible follow-ups:** How would you allocate the timing budget across the sensor, PID loop, and power switch if the risk analysis specifies a maximum time to reach a safe temperature? / If the PID loop is later retuned during development, what does that do to your traceability and verification evidence?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence, but only if the review criteria actually address the failure condition the control is meant to mitigate. A generic power supply checklist might cover topology, derating, and layout, but if the risk control is, say, "the supply shall not produce an output overvoltage under a load-dump condition," and the checklist never asks about load-dump behavior, then the review passing tells you nothing about that control. The traceability link exists but the evidence is hollow.

My approach would be to make the review criteria control-specific. I'd add explicit review questions or checklist items derived from the risk analysis — for each risk control verified by review, the checklist should contain a line item that states the failure condition and asks the reviewer to confirm the design addresses it, with a place to record the rationale. That converts a generic review into targeted evidence and gives the auditor something concrete to trace. Where the existing review has already happened without those criteria, I'd either re-run a focused review on that specific control or supplement it with analysis or test, depending on what's practical and what the risk file requires.

I'd also step back and look at the pattern: if several controls are traced to reviews whose criteria don't match, that's a process gap in how verification activities are selected, not just a one-off. I'd want the verification planning step to explicitly map each risk control to a verification method and confirm the method's criteria address the failure condition before the activity is scheduled.

**Possible follow-ups:** How would you decide whether a focused re-review is sufficient evidence or whether a test is required? / What would you record in the traceability matrix to show that the review criteria were derived from the risk analysis?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a piece of code — it's a *value*, and the traceability has to cover the value's derivation, its programming, and its verification, not just the existence of a parameter. I'd structure it in three layers. First, the risk analysis defines the control: the output current must not exceed a safe limit, and the limit is enforced by a stored parameter. Second, a requirement specifies how the limit is determined — the calculation or derating basis that produces the value, and the acceptable range — and a design element identifies where the parameter lives (the non-volatile memory location, the firmware that reads it, the hardware that enforces it). Third, verification covers both that the correct value was computed and that the value actually programmed into each unit produces the intended behavior.

The per-unit variability is the interesting part. If the value can differ between units — because it's calibrated to the specific hardware, for example — then the traceability scheme needs to account for the production programming step as part of the control's implementation. That means the manufacturing procedure and its records become verification evidence: you need to show that each unit was programmed with a value within the validated range, and that out-of-range or missing values are detected and rejected. I'd trace the manufacturing test or programming record to the risk control, and I'd want a requirement that the firmware validates the stored parameter at startup and fails safe if it's absent or out of bounds — because a unit with a corrupted or unprogrammed parameter is a failure mode the risk analysis should consider.

I'd also make sure the validated range is documented and that any change to the allowed range triggers a re-review of the risk analysis, since widening the range could undermine the control.

**Possible follow-ups:** How would you verify that the parameter validation at startup actually fails safe, rather than just defaulting to some value? / If the parameter is serviceable in the field, how does that change your traceability and risk picture?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd take the test engineer's concern seriously and treat it as a quality signal, not a compliance nuisance — a matrix that's structurally complete but evidentially hollow is exactly the kind of thing that passes audit and fails in the field. My first step would be to verify the concern rather than act on hearsay: pick a sample of the flagged tests, read each one against the risk analysis entry it's supposed to verify, and check whether the test setup actually drives the failure condition. If the test only exercises nominal behavior, that's a concrete finding I can show people, which is far more persuasive than an argument about process.

With evidence in hand, I'd bring the systems engineer and test lead together and reframe the conversation away from "is the matrix compliant" toward "does the evidence demonstrate the control works." The matrix is a map, not the territory — its purpose is to let someone confirm that each control is actually verified, and a copied test with relabeled steps doesn't do that. I'd propose a targeted re-verification of the affected tests: for each, either confirm it genuinely stresses the failure condition or rewrite it so it does, and record the rationale. I'd also want a negative check where feasible — disable the control and confirm the test fails — because that's the cheapest way to prove a test is sensitive to what it claims to verify.

Systemically, I'd look at why this happened: copied tests usually come from schedule pressure and a verification plan that didn't specify the failure condition precisely enough. I'd tighten the verification planning step so each test's acceptance criteria and fault conditions are derived explicitly from the risk analysis, and I'd add a peer review of test procedures against risk entries before the campaign starts. I'd communicate all of this as strengthening the evidence base, not as assigning blame, because the goal is a defensible verification package.

**Possible follow-ups:** How would you handle it if the re-verification finds that a control genuinely doesn't work as the risk analysis assumed? / What would you tell the quality manager and auditor about the gap, and on what timeline?
