# risk-requirements-traceability — Day 9

## Q1: How would you approach verifying that a risk control measure implemented as a hardware-based analog comparator (e.g., monitoring a voltage rail and asserting a reset if it drops below a threshold) is adequately traced through requirements, and that the verification test actually stresses the fault condition rather than just testing nominal behavior?

**Answer:** I'd start by confirming the traceability chain is complete: the system-level hazard (e.g., "uncontrolled motor operation due to undervoltage") links to a risk control measure in the risk management file, which maps to a specific requirement in the SRS (e.g., "the device shall assert a system reset when the 3.3V rail drops below 3.0V for more than 10ms"), and that requirement traces to a verification test case. The critical gap I'd check is whether the verification test actually recreates the fault condition. A common mistake is testing the comparator's behavior under nominal conditions—applying a voltage just above the threshold and confirming no reset occurs—without ever driving the rail below the threshold. For an analog comparator, I'd want the test to include: (1) ramping the monitored voltage slowly through the threshold to measure the exact trip point and hysteresis, (2) applying a step change below threshold to measure response time, and (3) introducing noise on the rail to ensure the comparator doesn't falsely trigger on transients. I'd also verify that the test setup uses a controllable power supply or signal generator to simulate the undervoltage condition, rather than relying on the actual system power rail which may never naturally droop during benchtop testing. Finally, I'd check that the test limits (trip voltage, response time, hysteresis) are explicitly stated in the requirement and that the test method measures against those limits, not just a pass/fail based on whether a reset occurred.

**Possible follow-ups:** What would you do if the comparator's trip point has a ±5% tolerance and the requirement specifies a single threshold value? How would you handle a scenario where the comparator is integrated into a PMIC that also performs other functions, making it difficult to isolate the comparator behavior in testing?

## Q2: How would you approach establishing traceability between risk control measures and requirements when the same risk control measure is implemented differently across multiple product variants or hardware revisions?

**Answer:** This is a common challenge in medical device families where a base platform is adapted for different markets or feature sets. I'd approach it by first identifying whether the risk control measure's *intent* is identical across variants, even if the implementation differs. For example, "overcurrent protection on the motor driver" might be implemented via a resettable fuse in one variant and a current-sense resistor with firmware monitoring in another. The system-level hazard and the risk control objective are the same, so I'd keep a single entry in the risk management file for that control measure. However, the SRS requirements and verification tests would be variant-specific because the implementation differs. I'd structure the traceability matrix with a "variant" column or use separate requirement IDs per variant (e.g., REQ-MOTOR-OC-A and REQ-MOTOR-OC-B), each tracing to the same risk control measure ID. The key is maintaining a clear mapping so that if the risk control measure changes (e.g., a new hazard analysis identifies a different failure mode), you can quickly identify which variants' requirements and tests need updating. I'd also include a rationale field in the traceability matrix explaining why the implementation differs—for example, "Variant B uses firmware-based monitoring because the hardware fuse variant could not meet the response time requirement for the higher-current motor used in that configuration." This prevents future reviewers from questioning whether the difference is intentional or an oversight.

**Possible follow-ups:** How would you handle a scenario where a hardware revision changes a risk control measure's implementation but the requirement text remains the same—would you create a new requirement or revise the existing one? How would you ensure that the traceability matrix doesn't become unwieldy when you have 10+ variants?

## Q3: How would you approach determining whether a requirement in the SRS is truly a "safety requirement" derived from risk management, versus a "performance requirement" that exists for functional reasons, and how would you decide which traceability links are necessary for each type?

**Answer:** I'd start by asking a simple question: "If this requirement were not met, could it directly cause or contribute to a hazardous situation?" If the answer is yes, it's a safety requirement and must trace to a risk control measure. If the answer is no—the device would still function safely but might not meet performance expectations—it's a performance requirement. However, there's a gray area where performance requirements indirectly affect safety. For example, "the device shall measure pressure with ±2% accuracy" might seem like a performance requirement, but if inaccurate pressure readings could cause the device to deliver incorrect therapy, it becomes safety-related. In that case, the accuracy requirement should trace to the risk control measure that mitigates the hazard of "incorrect therapy delivery due to sensor error." For pure performance requirements—like "the device shall have a battery life of 8 hours"—I'd still include them in the traceability matrix, but they would trace to design verification tests and possibly to user needs, not to risk control measures. The traceability matrix should distinguish between these types, perhaps with a column indicating "safety-critical" vs "performance" vs "regulatory" so reviewers can quickly assess coverage. I'd also ensure that safety requirements have additional traceability links: to the hazard they mitigate, to the risk control measure, and to the verification test that proves the control is effective. Performance requirements typically only need forward traceability (to design elements and tests) and backward traceability (to user needs or system requirements).

**Possible follow-ups:** How would you handle a requirement that is partly safety-related and partly performance-related—for example, a motor speed requirement that affects both therapy efficacy and patient safety? What criteria would you use to decide whether to split it into two requirements or keep it as one with dual traceability?

## Q4: How would you approach creating a traceability scheme that captures the evolution of risk control measures and their associated requirements across multiple design iterations, given that both the risk analysis and the requirements specification are living documents?

**Answer:** I'd treat traceability as a version-controlled artifact, not a static spreadsheet. The key is maintaining a history of changes so that reviewers can understand why a risk control measure or requirement changed, and whether the change introduced new hazards or invalidated existing controls. I'd use a tool that supports versioning (like a requirements management database or a Git-tracked document) and include a change log or revision history for each traceability link. For each change, I'd capture: (1) what changed, (2) why it changed (e.g., "design review found that the original 200ms timeout was insufficient for the worst-case sensor settling time"), (3) who approved the change, and (4) what impact analysis was performed (e.g., "verified that the new 500ms timeout still meets the response time requirement from the risk analysis"). I'd also maintain a "superseded links" table that shows previous versions of the traceability chain, so if someone asks "was this requirement ever traced to that risk control measure?" the answer is clear. For the traceability matrix itself, I'd include effective dates or version numbers for each link, and I'd run periodic gap analyses comparing the current risk analysis against the current SRS to identify any risk control measures that have no corresponding requirement, or requirements that have no risk justification. When a design iteration introduces a new risk control measure, I'd create the traceability link immediately—even if the requirement is still draft—rather than waiting until the design is finalized. This prevents the common problem of discovering at verification time that a risk control measure was never translated into a verifiable requirement.

**Possible follow-ups:** How would you handle a situation where a risk control measure is removed in a later design iteration because the hazard was re-evaluated and found to be acceptable without the control—would you delete the traceability link or mark it as superseded? How would you ensure that the traceability history doesn't become so complex that it's unusable for day-to-day design decisions?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has created a comprehensive requirements traceability matrix linking every requirement to a risk control measure and a verification test. However, during a design review, the test lead points out that several verification tests are testing the wrong thing — for example, a test labeled "verifies overcurrent protection" is actually testing nominal current draw. The systems engineer insists the traceability matrix is correct because the requirement numbers match. How would you resolve this disagreement?

**Answer:** I'd first acknowledge that both parties have valid concerns. The systems engineer is correct that the traceability matrix is structurally consistent—the requirement numbers link correctly to test case numbers. But the test lead is also correct that the *content* of the test doesn't match the *intent* of the requirement. The traceability matrix is only as good as the accuracy of the links, and a link that connects a requirement to a test that doesn't actually verify that requirement is a false positive—it gives the appearance of coverage without the substance. I'd call a brief meeting with both individuals and walk through the specific example together. I'd start by reading the requirement aloud: "The device shall limit motor current to 2A under stall conditions." Then I'd read the test procedure: "Apply nominal load, measure current draw, confirm it is below 2A." The test lead's point is clear—this test never creates a stall condition, so it doesn't verify the requirement. The systems engineer's matrix is correct in terms of IDs, but the test procedure itself is wrong. I'd propose that we update the test procedure to include a stall condition, and I'd ask the systems engineer to add a note in the traceability matrix indicating that the test was revised to properly verify the requirement. I'd also suggest that we add a "verification method" column to the matrix that briefly describes *how* the test verifies the requirement (e.g., "stall motor by locking rotor, measure current, confirm <2A"), so that future reviewers can quickly assess whether the test method is appropriate without reading the full test procedure. Finally, I'd use this as a learning opportunity: I'd propose that future design reviews include a "traceability sanity check" where a sample of traceability links are examined for content accuracy, not just ID matching. This prevents the matrix from becoming a bureaucratic exercise where people focus on filling in cells rather than ensuring the links are meaningful.

**Possible follow-ups:** How would you handle a situation where the test lead and systems engineer continue to disagree after your intervention—for example, the systems engineer argues that the test is "close enough" because nominal current is always below the limit? What would you do if you discovered that this was a systemic issue affecting dozens of traceability links, not just one or two?
