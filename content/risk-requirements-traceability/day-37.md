# risk-requirements-traceability — Day 37

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a combination of hardware and firmware, where the hardware team documents the control in their design specification and the firmware team documents their portion in a software requirements document — but neither document references the other, and the risk management file treats the control as a single integrated measure?

**Answer:** The core problem here is that the risk management file treats the control as one logical measure, but the implementation is split across two engineering disciplines that maintain separate documentation silos. I would start by creating a single "control owner" artifact — a risk control implementation sheet or a dedicated section in the risk management file — that explicitly decomposes the integrated control into its hardware and firmware contributions. This sheet would define the interface between the two parts: what signal the hardware produces (e.g., an asserted interrupt line), what timing or electrical characteristics are guaranteed, and what behavior the firmware must exhibit in response (e.g., the maximum latency to disable the output, the state transition required). Each subsystem's document would then reference this sheet by ID, and the sheet would reference both the hardware design specification and the software requirements document. This creates a hub-and-spoke model where the risk management file is the authoritative integration point, and each engineering team only needs to maintain traceability to that hub rather than directly to each other's documents. For verification, I would require three levels of evidence: hardware-level tests proving the sensor/comparator produces the correct signal under fault conditions, firmware-level tests proving the response logic behaves correctly given the expected input, and a system-level test proving the integrated behavior — because neither subsystem test alone can demonstrate that the interface between them works as specified (e.g., the firmware might respond correctly to a clean digital signal, but the hardware's signal might have noise, glitches, or marginal timing that the firmware doesn't handle).

**Possible follow-ups:**
- How would you handle the situation where the hardware and firmware teams use different numbering schemes for their requirements, and neither wants to adopt the other's scheme?
- What level of detail would you require in the interface definition between the hardware and firmware portions of the control?

## Q2: How would you approach determining whether a risk control measure that is implemented as a firmware-based plausibility check on a sensor reading — for example, rejecting readings that change by more than a specified rate between consecutive samples — needs to be verified on the actual production hardware, or whether testing on a development board with the same microcontroller is sufficient?

**Answer:** The key question is whether the risk control's behavior depends on characteristics that differ between the development board and production hardware. For a plausibility check on sensor readings, I would analyze the failure modes the control is meant to mitigate. If the hazard is that a sensor fails in a way that produces implausible readings, the control's effectiveness depends on the sensor's actual output characteristics, the analog front-end that conditions the sensor signal, and the ADC's behavior — none of which are exercised meaningfully on a development board with a different sensor or front-end. The plausibility check logic itself might be identical, but the verification needs to demonstrate that the control works in the context of the actual signal chain. However, there's a legitimate role for development-board testing: unit-level testing of the algorithm logic, boundary conditions (e.g., exactly at the rate threshold, slightly above, slightly below), and code coverage can all be done efficiently on the development board. The production-hardware testing would then focus on the integration aspects: injecting realistic fault signals through the actual sensor interface, verifying the timing behavior with the production clock configuration and interrupt priorities, and confirming that the firmware's response (e.g., entering a safe state, generating an alarm) works with the production hardware's peripheral configuration. I would also consider whether the plausibility check's timing parameters are sensitive to interrupt latency, ADC conversion time, or bus arbitration — if so, those dependencies argue strongly for production-hardware verification. The decision ultimately comes down to a risk-based analysis: what could differ between the two platforms that would affect the control's ability to mitigate the hazard, and is that difference covered by the verification approach?

**Possible follow-ups:**
- What specific test cases would you design for the development-board testing versus the production-hardware testing?
- How would you document the rationale for why development-board testing is sufficient for certain aspects of the verification?

## Q3: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system has a distributed architecture — multiple microcontrollers, each running separate firmware, communicating over a shared bus — and a single hazard is mitigated by coordinated actions across multiple nodes?

**Answer:** This is one of the more challenging traceability scenarios because the hazard mitigation is emergent — it only exists when multiple nodes behave in a coordinated way, and no single node's requirement set fully captures the control. I would approach this by introducing a layer of "system-level risk control requirements" that sit above the individual node-level requirements. These system-level requirements would describe the coordinated behavior in terms of the observable system response: for example, "the system shall transition to a safe state within X milliseconds of any node detecting a fault condition, regardless of which node initiates the response." Each node's firmware requirements would then trace up to these system-level requirements, with the specific contribution of that node clearly identified (e.g., Node A detects the fault and broadcasts a shutdown command; Node B receives the command and disables its motor output; Node C logs the event and alerts the operator). The traceability matrix would capture three types of links: hazard-to-system-requirement, system-requirement-to-node-requirement, and node-requirement-to-verification. For verification, I would require both node-level tests (each node responds correctly to the fault condition and to the bus messages) and a system-level integration test that exercises the full coordinated response — because the failure modes in distributed systems often live in the interfaces: message timing, bus contention, partial message delivery, node startup/shutdown sequences, and clock synchronization. The system-level test would need to inject faults at various points in the network and verify the coordinated response under realistic bus loading conditions. I would also pay particular attention to the failure modes where one node fails to receive or act on the message — the traceability needs to capture not just the happy path but also the degraded modes.

**Possible follow-ups:**
- How would you handle the situation where different nodes are developed by different teams with different documentation standards and requirement numbering schemes?
- What system-level verification approach would you use to prove the coordinated response works under worst-case bus loading or partial node failure?

## Q4: How would you approach handling a situation where a risk control measure is traced to a verification test, but the test was written to verify a *different* requirement and only incidentally exercises the risk control under nominal conditions — so it passes, but it never actually stresses the failure condition the control is meant to mitigate?

**Answer:** This is a common and dangerous gap because the traceability matrix looks complete — there's a link from the risk control to a test, and the test passes — but the evidence is meaningless for demonstrating the control's effectiveness. My first step would be to analyze the test procedure against the failure condition identified in the risk analysis. I would ask: does the test create the specific fault or abnormal condition that the control is designed to detect and respond to? If not, the test is not providing verification evidence for that control, regardless of whether it's linked in the matrix. I would document this gap explicitly — a traceability gap analysis that identifies the control, the linked test, and the specific reason the test doesn't exercise the failure condition. Then I would work with the verification engineer to design a new test or modify the existing one to actually stress the failure condition. The new test would need to inject the fault (e.g., simulate a sensor failure, apply an over-voltage condition, interrupt a communication stream) and verify that the control responds as specified. I would also review the traceability matrix to understand how this happened — was it a deliberate shortcut, an error in the matrix, or a misunderstanding of what the test actually does? This review might reveal systemic issues: perhaps the matrix was populated by matching requirement numbers without reviewing test content, or perhaps there's pressure to show complete coverage. I would also flag this as a finding in the design verification report, because it indicates that the verification evidence for that hazard is incomplete, which has regulatory implications. The key principle is that traceability is not just about having links — it's about having links that represent meaningful evidence, and the verification activity must be designed to exercise the failure condition, not just to pass under nominal conditions.

**Possible follow-ups:**
- How would you prioritize which risk controls need new verification tests versus which can be addressed through analysis or other methods?
- What would you do if the schedule doesn't allow time to design and execute new verification tests before the regulatory submission deadline?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has created a traceability matrix that links every risk control measure to a verification activity, but during a review, you discover that several of the verification activities are actually "verification by similarity" — meaning the team is relying on test results from a previous product that used a similar component or design. The quality manager argues that similarity is not acceptable evidence for risk controls, because the previous product wasn't tested under the same conditions. The systems engineer argues that the components are identical, the design is nearly the same, and re-running the tests would waste time and money. How would you resolve this disagreement?

**Answer:** I would start by acknowledging that both sides have legitimate concerns. The quality manager is right that similarity arguments can be overused and that risk controls need objective evidence — but the systems engineer is also right that re-running identical tests on an identical component in an identical configuration can be wasteful. The resolution lies in establishing clear criteria for when similarity is acceptable, and then applying those criteria rigorously to each specific case. I would convene a meeting with both parties and propose a structured assessment framework. For each "verification by similarity" item, we would evaluate: (1) Is the component or design element truly identical, or just similar? (2) Are the operating conditions — voltage, temperature, loading, environmental stress — the same between the previous product and the current one? (3) Is the risk control's function dependent on the component's behavior in a way that could be affected by differences in the surrounding circuit or system? (4) Was the previous test actually designed to stress the failure condition, or did it just exercise the component under nominal conditions? (5) Is there documented evidence from the previous test that we can review, including the test procedure, raw data, and pass/fail criteria? Based on this assessment, each item would fall into one of three categories: acceptable similarity (with documented rationale and reference to the previous test evidence), needs limited re-testing (e.g., re-run only the specific test that stresses the failure condition, perhaps on a sample basis), or needs full re-testing (because the conditions or configuration differ materially). I would document this assessment in the verification plan so the rationale is transparent and auditable. I would also note that for medical devices, the regulatory expectation is that verification evidence is specific to the product being submitted — similarity arguments need to be well-justified and documented, not just asserted. The goal is to find the middle ground: rigorous evidence where it matters, and efficiency where the evidence genuinely already exists.

**Possible follow-ups:**
- What specific criteria would you use to determine whether the previous test conditions are "close enough" to the current product's conditions?
- How would you handle a situation where the previous test data exists but is incomplete — for example, the test procedure is documented but the raw data has been lost?
