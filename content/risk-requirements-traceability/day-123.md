# risk-requirements-traceability — Day 123

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement is *functionally complete but safety-anonymous* — it describes what the code does but not why it matters, so the traceability link from hazard to requirement is missing at the requirement level even though it exists conceptually in the risk analyst's head. My approach would be to fix the requirement itself rather than paper over the gap in the matrix. First, I'd add an explicit safety-intent statement to the firmware requirement — something like "the commanded rate of change shall be clamped to X units/s to mitigate the hazardous condition of uncontrolled actuator acceleration" — so the requirement carries its own justification and a reviewer reading only the SRS understands why the clamp exists and what failure it guards against. Second, I'd make sure the requirement specifies measurable acceptance criteria: the maximum permitted rate of change, the tolerance, the behavior at the boundary, and what happens when a command exceeds the limit (clamp vs reject vs fault). Third, I'd link the risk control measure in the risk file bidirectionally to that requirement ID, and from the requirement to the verification activity. The verification itself needs to stress the failure condition — commanding a step change far larger than the limit and confirming the output ramps rather than jumps — not just confirm the clamp exists under nominal commands. Finally, I'd check whether the rate limiter interacts with other controls (for example, an independent overspeed cutoff) so the traceability reflects whether this is a sole control or one layer of defense, because that affects how rigorously it must be verified.

**Possible follow-ups:** If the rate limiter is one of two independent controls against the same hazard, does that change how much verification rigor you'd demand for each? And how would you catch this class of "functionally described but safety-anonymous" requirement systematically rather than one at a time?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap with a distributed control is that the risk file credits "the loop" as a single control, but no single requirement, design element, or test owns the loop end-to-end — so the traceability matrix can look complete at the control level while the actual safety property (the element stays within a safe range) is never verified as an integrated behavior. I'd handle this by decomposing the control into its constituent elements for traceability purposes while keeping the integrated behavior as a separate, explicitly verified item. Concretely: allocate the safety property across the chain — sensor accuracy and range, firmware loop response and saturation behavior, power switch response time and failure mode — and write a requirement for each element that states its contribution and its budget (for example, the sensor must be accurate to within a stated tolerance across the operating range, the firmware must command the switch off within a stated latency when the loop saturates). Then, critically, add a *system-level* requirement and verification for the emergent property: apply a fault or disturbance that drives the loop toward the unsafe region and confirm the element stays within the safe range. The element-level tests verify the pieces; the system-level test verifies the loop actually works as a loop. I'd also document the loop's failure modes explicitly — sensor stuck, firmware hung, switch welded closed — because a distributed control's safety argument depends on which single-point failures it tolerates, and that reasoning needs to live somewhere traceable, not just in the analyst's head.

**Possible follow-ups:** How would you decide how to allocate the timing budget across the sensor, firmware, and switch so each element's requirement is individually verifiable? And if the firmware PID loop is later retuned, what in your traceability scheme tells you which verifications must be re-run?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — a general "power supply design review" checklist, for example — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence for certain kinds of controls — layout rules, derating, creepage, component selection — but only if the review actually examines the specific failure condition the control addresses. A generic checklist that happens to touch the same subsystem is not evidence that anyone assessed *this* control. My approach would be to make the review criteria control-specific rather than subsystem-generic. I'd add an explicit review item derived from the risk control: state the failure condition, state what the reviewer must confirm in the design to show the control addresses it, and require a recorded conclusion with the reviewer's name and the artifact examined. That converts a passive checklist item into an auditable assessment. If the existing review has already happened without that item, I'd either re-run a focused review scoped to the control or supplement it with a different verification method (analysis, inspection with recorded criteria, or test) — whichever is proportionate to the control's risk. I'd also fix the root cause: review checklists should be generated or at least cross-checked against the risk controls that map to the subsystem being reviewed, so this gap doesn't recur on the next design. The key principle is that "verification by review" is only objective evidence if the review criteria are traceable to the control's failure condition and the outcome is recorded against measurable or at least clearly stated criteria.

**Possible follow-ups:** How would you word a review checklist item so it's specific enough to be meaningful evidence without being so prescriptive that reviewers just tick the box? And how would you handle a reviewer who signs off without genuinely assessing the item?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a circuit or a line of code — it's a *value plus the process that puts it there plus the process that keeps it there*. So the traceability has to cover three things that are easy to miss if you only think in terms of design requirements. First, the parameter's *definition*: a requirement stating the permitted range, the resolution, the default, and the consequence of an out-of-range value — this is a design requirement on the firmware that reads and enforces the parameter. Second, the *programming process*: the manufacturing step that writes the value is itself part of the control, so it needs a documented procedure, a verification step (read-back and compare, or a functional check at the specified limit), and a record tied to the unit's serial number. That manufacturing verification is the objective evidence that the control is present on each unit, and it belongs in the traceability chain alongside the design verification. Third, the *integrity of the stored value in the field*: if the parameter can be corrupted, changed via a service port, or lost on a memory fault, the control's effectiveness depends on protections (checksums, write protection, range validation on read) that themselves need requirements and verification. I'd also make sure the risk file states clearly that the control is unit-specific, so the verification strategy is per-unit or sample-based by deliberate decision rather than by accident, and that the traceability matrix distinguishes "verified by design" from "verified per unit at manufacturing."

**Possible follow-ups:** How would you decide whether per-unit read-back verification is sufficient or whether you need a functional test at the limit on every unit? And if a unit is later serviced and the parameter is rewritten, what in your scheme ensures the control is re-verified before the device returns to service?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd treat this as a substantive quality problem, not a documentation problem, and I'd be careful not to let the "it passes audit" framing shut down the conversation — a matrix that links to tests which don't exercise the failure condition is traceability in form only. My first step would be to gather facts rather than adjudicate: take the specific tests the engineer flagged and, with the test engineer and the systems engineer in the room, walk each one against its risk control's failure condition and ask a simple question — "if this control were removed or broken, would this test fail?" That's a concrete, non-accusatory way to make the gap visible, and it usually settles the disagreement on evidence rather than opinion. Where the answer is no, those tests need to be rewritten or supplemented so they actually stress the failure condition, and I'd prioritize by the severity of the hazard each control mitigates. I'd also address the systemic cause: copied-and-relabeled tests are a symptom of test development being disconnected from the risk analysis, so I'd want the person writing each test to have read the risk control entry, and I'd add a review step where the link between test and failure condition is explicitly confirmed — not just the requirement ID match. On the people side, I'd frame this to the systems engineer not as "your matrix is wrong" but as "the matrix is doing its job by surfacing this — now let's make the evidence match the links," because the goal is a defensible safety argument, not winning the argument.

**Possible follow-ups:** How would you handle it if re-running the corrected tests late in the schedule threatens the verification timeline? And how would you prevent copied-and-relabeled tests from creeping back in on the next project without adding so much process that test development slows to a crawl?
