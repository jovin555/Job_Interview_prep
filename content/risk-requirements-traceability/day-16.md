# risk-requirements-traceability — Day 16

## Q1: How would you approach establishing traceability between risk control measures and requirements when the system uses a hardware-only control in one product variant and a firmware-only control in another variant to mitigate the same hazard?

**Answer:** The key challenge here is that the traceability structure needs to be stable at the hazard level while accommodating different implementation paths. I'd start by defining the traceability at the hazard level first — the hazard, the risk control measure as a *function* (e.g., "prevent motor operation when over-temperature condition is detected"), and the verification objective (e.g., "demonstrate motor is disabled when over-temperature is detected"). This functional-level traceability stays constant across variants.

Below that, I'd create variant-specific traceability branches. For the hardware variant, the functional control traces to a hardware requirement (e.g., "analog comparator shall assert reset when temperature exceeds threshold") and then to a hardware verification test. For the firmware variant, it traces to a firmware requirement (e.g., "firmware shall disable motor driver output when temperature sensor reading exceeds threshold") and then to a firmware verification test.

The critical piece is maintaining a clear mapping between the variant-specific requirements and the shared functional control. I'd use a traceability matrix that has the hazard and functional control at the top level, with columns for each variant showing the implementation-specific requirement and verification. This way, a reviewer can see at a glance that both variants trace back to the same hazard, even though the implementation differs. I'd also flag in the risk management file that the control is variant-dependent, so that if one variant changes its implementation, the traceability impact is immediately visible.

**Possible follow-ups:** How would you handle a situation where one variant's verification test is more rigorous than the other's — for example, the hardware variant is tested under fault injection but the firmware variant is only tested under nominal conditions? What if a third variant uses a combination of hardware and firmware — how would you integrate that into the same scheme?

## Q2: How would you approach determining whether a risk control measure that is implemented as a firmware-based state machine guard — for example, preventing transition from "standby" to "active" unless a self-test passes — needs to be verified on the actual production hardware, or whether testing on a development board with the same microcontroller is sufficient?

**Answer:** The first question I'd ask is: what is the risk control actually relying on? If the control is purely logical — the state machine logic, the self-test algorithm, the decision to block the transition — then a development board with the same microcontroller and the same firmware binary could be sufficient, because the logic is deterministic and doesn't depend on the specific PCB layout or analog characteristics. The verification would demonstrate that the firmware correctly evaluates the self-test result and blocks the transition when the test fails.

However, I'd look carefully at what the self-test actually exercises. If the self-test checks an analog sensor reading — for example, verifying that a temperature sensor is within a plausible range — then the verification needs to confirm that the firmware correctly interprets the sensor signal in the context of the actual hardware. A development board might have different pull-up resistors, different decoupling, or a different sensor interface, which could affect the signal levels the firmware sees. In that case, I'd want at least a subset of verification on production-representative hardware to confirm the interface behaves as expected.

I'd also consider whether the risk control interacts with other hardware — for example, if the state machine guard controls a motor driver enable line, the verification needs to confirm that the firmware actually drives the correct pin on the production hardware, and that the pin is connected to the right component. A development board might have the same microcontroller but different pin routing or different peripheral connections.

My approach would be to do a risk-based assessment: identify what the control depends on, and verify each dependency on the appropriate platform. Pure logic can be verified on a development board; anything that touches analog interfaces, pin assignments, or hardware-specific behavior needs production-representative hardware. I'd document this rationale in the verification plan so the decision is transparent and defensible.

**Possible follow-ups:** How would you handle a situation where the self-test itself is designed to detect a hardware fault — for example, a stuck sensor or a shorted trace — and the development board doesn't have the ability to inject those faults? How would you decide whether a test on production hardware is required for the self-test's fault detection capability, or whether the self-test logic can be verified independently?

## Q3: (Behavioral) Imagine you're leading a project where the systems engineer has created a traceability matrix that links every risk control measure to a verification activity, but during a review, you discover that several of the verification activities are actually "verification by similarity" — meaning the team is relying on test results from a previous product that used a similar component or design. The quality manager argues that similarity is not acceptable evidence for risk controls, because the previous product wasn't tested under the same conditions. The systems engineer argues that the components are identical, the design is nearly the same, and re-running the tests would waste time and money. How would you resolve this disagreement?

**Answer:** I'd start by acknowledging that both sides have legitimate concerns. The systems engineer is right that re-testing identical components under identical conditions can be wasteful, and the quality manager is right that similarity arguments can be stretched too far. The resolution is to define clear criteria for when similarity is acceptable, and then apply those criteria to each specific case.

First, I'd ask the systems engineer to document, for each similarity-based verification, exactly what is being claimed: what component or design element is the same, what conditions were tested in the previous product, and what conditions apply in the current product. Then I'd compare those conditions against the risk control's failure condition. If the previous test actually stressed the same failure mode under the same or more severe conditions, and the component is truly identical (same part number, same manufacturer, same revision), then similarity might be defensible.

But I'd also look at the context. For example, if the previous product used the same over-temperature comparator but a different power supply design, the comparator's behavior under a brown-out condition might be different. If the previous product used the same firmware watchdog but a different clock source, the timing margins might differ. These are the kinds of differences that can invalidate a similarity argument.

My approach would be to create a formal similarity assessment process: for each verification activity that relies on similarity, the team must document (1) the exact component/design element being claimed as similar, (2) the test conditions from the previous product, (3) the test conditions required for the current product, and (4) an analysis of why the differences (if any) don't affect the risk control's effectiveness. The quality manager reviews these assessments and can accept or reject each one. If the quality manager rejects a similarity claim, the team runs the test. If the quality manager accepts it, the similarity assessment becomes part of the verification evidence.

This approach respects both concerns: it avoids unnecessary re-testing where similarity is genuinely justified, but it also ensures that similarity is never assumed — it's demonstrated with objective evidence.

**Possible follow-ups:** How would you handle a situation where the previous product's test data exists but was collected under a different standard or with different measurement equipment? What if the previous product's test data is incomplete — for example, the test was run but the pass/fail criteria weren't documented?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system has a distributed architecture — multiple microcontrollers, each running separate firmware, communicating over a shared bus — and a single hazard is mitigated by coordinated actions across multiple nodes?

**Answer:** The fundamental challenge here is that the hazard is mitigated by a *system-level behavior* — the coordinated action of multiple nodes — but the implementation is spread across multiple firmware and hardware components, each with its own requirements and verification. The traceability scheme needs to bridge that gap.

I'd start by defining the risk control at the system level as a functional requirement: for example, "the system shall shut down the motor within 100ms of detecting an over-temperature condition on any node." This system-level requirement captures the hazard mitigation without prescribing how the coordination happens.

Then I'd decompose that system-level requirement into node-level requirements. Each node's requirement would be defined in terms of its role in the coordination: for example, "Node A shall broadcast an over-temperature alert on the bus within 10ms of detecting the condition," and "Node B shall disable the motor driver within 50ms of receiving an over-temperature alert." These node-level requirements are traceable to the system-level requirement, and each node's firmware can be verified against its own requirement.

The tricky part is verifying the *coordination* — the timing, the message format, the failure modes of the bus itself. I'd add a system-level verification activity that exercises the full chain: inject an over-temperature condition on Node A, and verify that Node B disables the motor within the required time. This system-level test is the ultimate evidence that the risk control works, and it's traced directly to the system-level requirement.

I'd also think about bus failure modes. If the bus is the communication path for the alert, then a bus failure could defeat the risk control. I'd add a risk control measure for the bus itself — for example, a watchdog timeout on Node B that disables the motor if no heartbeat is received from Node A within a specified interval. This would be a separate risk control with its own traceability.

The traceability matrix would have three levels: system-level hazard → system-level risk control requirement → node-level requirements (one per node) → node-level verification → system-level integration verification. The key is that the system-level verification is the final proof that the coordinated behavior works, and the node-level verifications provide diagnostic evidence if the system-level test fails.

**Possible follow-ups:** How would you handle a situation where the bus protocol itself is a risk control — for example, a checksum that detects corrupted messages — and the checksum is implemented in the bus driver layer shared by all nodes? How would you trace that single implementation across multiple nodes? What if the coordination involves a handshake — for example, Node A sends an alert and waits for an acknowledgment from Node B before proceeding — how would you verify the timeout and retry behavior?

## Q5: How would you approach establishing traceability between risk control measures and requirements when the risk analysis identifies a control that is implemented as a combination of a hardware analog comparator and a firmware-based response — for example, the comparator detects an over-voltage condition and asserts an interrupt, and the firmware responds by disabling a power output — but the hardware and firmware teams maintain separate requirements documents with different numbering schemes?

**Answer:** The first step is to recognize that the risk control is a single logical entity, even though it's implemented across two disciplines. I'd define the risk control at the system level in the risk management file — for example, "over-voltage protection: disable power output within 50ms of detecting voltage exceeding 5.5V" — and give it a stable identifier that doesn't depend on either team's numbering scheme.

Then I'd create a mapping document that connects this system-level risk control to the specific requirements in each team's document. The hardware requirement might be "U3 comparator shall assert INT_L when VIN exceeds 5.5V ± 2%," and the firmware requirement might be "FW shall disable PWR_EN output within 10ms of INT_L assertion." Each team's requirement gets its own identifier in their own document, but the mapping document links both back to the system-level risk control.

The critical piece is the interface between the two. The hardware requirement specifies the comparator's behavior — the threshold, the tolerance, the output signal. The firmware requirement specifies the response — the timing, the action. But the *interface* — the INT_L signal itself, its electrical characteristics, its timing relative to the comparator's assertion — needs to be defined somewhere. I'd put that in an interface control document (ICD) that both teams reference, and the ICD would be traced to the system-level risk control as well.

For verification, I'd have three levels: hardware verification (does the comparator assert INT_L when VIN exceeds the threshold?), firmware verification (does the firmware disable PWR_EN when INT_L is asserted?), and system-level verification (does the power output actually disable within 50ms when VIN exceeds 5.5V?). The system-level test is the ultimate proof, but the hardware and firmware tests provide diagnostic evidence.

The traceability matrix would show: system-level risk control → hardware requirement (with its ID) → hardware verification; system-level risk control → firmware requirement (with its ID) → firmware verification; system-level risk control → ICD → system-level verification. The numbering schemes are different, but the mapping document makes the relationships explicit, and the system-level risk control ID is the anchor that ties everything together.

**Possible follow-ups:** How would you handle a situation where the hardware team changes the comparator threshold during development, and the firmware team's timing requirement is affected? How would you ensure the traceability matrix is updated to reflect the change? What if the ICD is not maintained — for example, the INT_L signal's electrical characteristics are only documented in the hardware schematic, not in a formal ICD — how would you handle that gap?
