# risk-requirements-traceability — Day 60

## Q1: How would you approach tracing a risk control measure that is implemented as a firmware-based watchdog kick — where the firmware must periodically write to a hardware register to prove liveness — when the firmware team owns the kick logic and the hardware team owns the watchdog peripheral, and neither team's requirements document references the other?

**Answer:** This is a classic split-ownership traceability gap, and the root problem is that the risk control is a *contract* between two subsystems, not a property of either one alone. The watchdog only mitigates the hazard if both halves hold up their end: the hardware must reset the system within a bounded time when the kick stops, and the firmware must actually kick within the required window under all operating conditions (including worst-case interrupt latency and task starvation). Neither document alone captures that contract, so the first step is to create a single system-level requirement that expresses the integrated behavior — something like "the system shall reset within T ms of the firmware failing to service the watchdog" — and make that the traceable anchor for the risk control. From there, decompose it into a hardware requirement (reset assertion timing, watchdog timeout range, reset behavior) and a firmware requirement (kick period, kick placement relative to the main control loop, behavior under fault), and cross-reference each to the parent. The traceability matrix then shows the risk control → system requirement → hardware requirement + firmware requirement → verification activities, with the verification covering both the individual halves and the integrated behavior. The integrated test is the one that matters most: you need to demonstrate that if you stop the kicks (or delay them beyond the window), the system actually resets. That test can't be owned by either team in isolation — it needs a joint owner or a systems engineer.

**Possible follow-ups:**
- How would you decide the timeout value, and how would you trace the justification for that value back to the hazard analysis?
- If the firmware team later changes the kick period, what process would ensure the hardware team and the risk file are updated?

## Q2: How would you approach establishing traceability for a risk control measure that is implemented as a redundant channel — for example, a primary sensor path and an independent secondary path whose agreement is checked — where the control's effectiveness depends on the *independence* of the two channels rather than on either channel alone?

**Answer:** The key insight is that the risk control here is not "sensor A works" or "sensor B works" — it's "the two channels fail independently, and disagreement between them is detected and acted upon." That means the traceability has to capture three distinct things: the detection logic (the comparison and the threshold for declaring disagreement), the response (what the system does when disagreement is detected — alarm, safe state, fallback), and the independence claim itself. The first two map cleanly to functional requirements and verification tests. The third is the hard one, because independence is a property of the *design*, not a behavior you can test directly. You verify it through analysis and design review: shared power rails, shared clock sources, shared communication buses, shared firmware, common-mode environmental effects (temperature, EMI), and common-cause failures like a single connector or a shared ADC. Each of those is a potential coupling path that breaks independence, and each should be captured as a design constraint or a derived requirement with its own verification activity — often inspection or analysis rather than test. In the traceability matrix, I'd link the risk control to the detection requirement, the response requirement, and a set of independence constraints, then trace each to its verification method. The independence constraints are the ones most likely to be missed, because they don't look like "requirements" in the usual sense — they look like design rules — but they're the ones that actually make the control work.

**Possible follow-ups:**
- How would you verify independence if the two channels share a common power supply but have separate regulators?
- If a design review finds that both channels use the same sensor part number from the same manufacturer, does that break independence, and how would you assess it?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity's test procedure was written against an earlier revision of the requirement, so the test still passes but no longer exercises the current acceptance criteria?

**Answer:** This is a configuration-management failure as much as a traceability failure, and it's dangerous precisely because everything *looks* fine — the matrix is complete, the test passes, and the link exists. The first step is to confirm the discrepancy: pull the requirement revision history, the test procedure revision history, and the verification record, and identify exactly what changed and when. Usually the requirement was tightened or a parameter was added, and the test procedure was never updated to match. Once confirmed, the test is effectively invalid for the current requirement, so the verification record needs to be flagged — not deleted, but marked as not covering the current revision — and the test procedure needs to be revised and re-run. The deeper fix is process: the traceability matrix should link to *revision-controlled* requirement IDs and test procedure IDs, not just to titles or numbers, so that a change to either side triggers a review of the link. Many requirements management tools support this natively; if you're working in spreadsheets, you need a change-control step that explicitly checks downstream links whenever a requirement or test is revised. I'd also add a periodic audit — before each design review or verification milestone — that samples links and confirms the test procedure revision matches the requirement revision. It's tedious but it catches exactly this class of silent drift.

**Possible follow-ups:**
- How would you decide whether the old test results can be partially credited, or whether the test must be fully re-run?
- What would you put in the traceability matrix to make this kind of drift visible at a glance?

## Q4: How would you approach deciding whether a risk control measure should be traced to a design requirement, a design element, or both — and what practical difference does that distinction make in a traceability matrix?

**Answer:** The distinction matters because requirements and design elements answer different questions and support different kinds of verification. A *requirement* states what the system must do or be — "the enclosure shall prevent user contact with voltages above the safety threshold." A *design element* is the specific thing that implements it — a particular shield geometry, a specific material, a creepage distance on the PCB. Tracing a risk control to a requirement gives you a verifiable statement with acceptance criteria; tracing it to a design element gives you the physical or logical artifact that carries the control. In practice, most risk controls need both: the requirement is what you verify against, and the design element is what you inspect, analyze, or test. If you trace only to a requirement, you can end up with a verified requirement and no clear picture of *how* it's implemented, which makes change impact analysis hard — if the design element changes, you don't know which risk controls are affected. If you trace only to a design element, you have no acceptance criteria, so verification becomes subjective ("does this look safe enough?"). The practical difference in the matrix is that you get two columns instead of one: requirement ID and design element ID, both linked to the risk control, and both linked forward to verification. That lets you answer both "is this control verified?" and "if I change this component, which controls are at risk?" — which are the two questions that come up most often during audits and design changes.

**Possible follow-ups:**
- For a purely procedural control — like a label warning — what would the "design element" be, and does the distinction still apply?
- How would you handle a case where one design element implements multiple risk controls, or one risk control is spread across multiple design elements?

## Q5: (Behavioral) Imagine you're leading a project where the systems engineer has built a traceability matrix that links every risk control measure to a verification activity, and the matrix is complete and passes audit. However, a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and that nobody has confirmed the tests actually exercise the failure conditions in this project's risk analysis. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The systems engineer is technically correct that the matrix is compliant, but compliance isn't the goal — the goal is that the risk controls actually work, and a copied test that doesn't exercise the failure condition gives false confidence. The first thing I'd do is thank the test engineer for raising it and make clear that surfacing this is the right behavior, because the instinct in a lot of organizations is to stay quiet when the paperwork looks fine. Then I'd verify the concern directly: pick two or three of the flagged tests, pull the risk analysis failure condition, and walk through the test procedure step by step to see whether it actually drives the system into that condition. If it doesn't, that's not a paperwork problem — it's a verification gap, and it needs to be treated as such. I'd bring the systems engineer and the test engineer together, not to assign blame but to look at the evidence side by side, because the systems engineer may genuinely believe the tests are adequate and needs to see the specific mismatch. Once the gap is confirmed, the fix is to revise the affected test procedures to explicitly exercise the failure conditions from the risk analysis, re-run them, and update the verification records. The broader fix is to change how tests are written: every verification test for a risk control should start from the failure condition in the risk analysis and work backward to the test setup, rather than starting from a similar test and adjusting labels. I'd also add a review step where the test engineer and the person who wrote the risk analysis sign off that the test actually stresses the failure condition — that's the check that would have caught this earlier.

**Possible follow-ups:**
- How would you handle the situation if the systems engineer pushes back and insists the matrix is sufficient because it passes audit?
- What would you change in the test development process to prevent copied tests from being reused without validation?
