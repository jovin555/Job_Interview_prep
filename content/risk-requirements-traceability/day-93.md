# risk-requirements-traceability — Day 93

## Q1: How would you approach tracing a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the traceability link exists structurally but not semantically — the requirement describes *what* the firmware does, not *why* it matters, so anyone reading the SRS in isolation would have no way to know this is a safety-relevant behavior. I'd address it in two directions. First, I'd add an explicit safety annotation to the firmware requirement — not necessarily rewriting it as a "safety requirement" in a separate document, but adding a traceability tag or attribute that links it back to the specific risk control measure ID in the risk management file. That preserves the functional phrasing the firmware team finds natural while making the safety intent machine-traceable. Second, I'd check whether the acceptance criterion in the requirement is actually measurable in a way that stresses the failure condition: "clamps the commanded speed to a maximum rate of change" needs a numeric rate, a tolerance, and a test condition that drives the command faster than the limit — otherwise the requirement can pass a nominal test without ever exercising the limiter. I'd also verify that the verification activity explicitly cites the risk control, so the test isn't just "does the motor respond to commands" but "does the limiter prevent a step command from producing a hazardous rate of acceleration." The general principle is that a risk control implemented in firmware needs three things linked: the hazard it mitigates, a requirement with a measurable acceptance criterion tied to that hazard, and a verification that drives the failure condition — not just nominal behavior.

**Possible follow-ups:** If the firmware team resists adding safety annotations because they see it as documentation overhead, how would you make the case? And how would you handle the situation where the rate limiter is one of several controls mitigating the same overspeed hazard, so the test can't isolate its contribution?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** This is a case where the risk analysis is correct to treat the loop as one control — the hazard is only mitigated if all three elements work together — but the traceability scheme has to decompose it without losing the integration. I'd start by defining the risk control measure at the system level with a single ID and a clear statement of the safe condition it maintains (e.g., "heating element surface temperature shall not exceed X under any single-fault condition"). Then I'd create derived requirements at each subsystem level: a sensor requirement (accuracy, range, response time), a firmware requirement (PID behavior, output limits, fault response), and a power-switch requirement (switching behavior, fail-safe state on loss of drive). Each derived requirement traces *up* to the system-level control and *down* to its own verification. The critical piece is an integration verification that exercises the loop as a whole — because each subsystem can pass its own test while the loop as a whole fails, for example if the sensor's response time and the PID's update rate interact badly. I'd also make sure the risk analysis documents the assumed independence or interaction between the elements, because if the loop's effectiveness depends on the sensor being accurate, then a sensor failure mode needs its own analysis. The traceability matrix should show the system-level control as a parent node with three children and one integration test, so an auditor can see both the decomposition and the recombination.

**Possible follow-ups:** How would you allocate the safe-range budget across the three elements — for example, how much of the total temperature tolerance belongs to sensor error versus control overshoot? And if the integration test fails, how would you use the traceability structure to isolate which element is responsible?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence for certain kinds of controls — layout rules, derating, creepage distances — but only if the review actually assesses the specific failure condition the control addresses. A generic power supply checklist that never mentions the risk control's failure mode is not evidence that the control works; it's evidence that the power supply was reviewed for general quality. I'd handle this by first confirming what the risk control actually requires: if it's a design-rule-based control, a review is appropriate, but the review criteria need to be augmented with explicit questions tied to the control. I'd add a review item that states the failure condition and asks the reviewer to confirm the design addresses it, with a recorded disposition — not just a checkbox. If the control requires functional behavior that a review can't assess (e.g., "the supply shall recover within X ms after a transient"), then the review is the wrong verification method entirely and a test is needed. The general fix is to make the verification activity's acceptance criteria derive from the risk control's failure condition, not from the document's original purpose. I'd also flag this pattern in the traceability matrix — a column or attribute indicating whether the verification method is capable of detecting the failure — so this kind of mismatch surfaces in review rather than at audit.

**Possible follow-ups:** How would you retrofit explicit risk-control criteria into an existing review checklist without invalidating reviews that have already been completed? And how would you distinguish a review that genuinely verifies a design-rule control from one that's just a paper exercise?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is tricky because the control isn't a circuit or a line of code — it's a *value*, and the traceability has to cover the value's specification, its programming process, and its verification on the unit. I'd structure it in three layers. First, a requirement that defines the parameter: its name, its permitted range, its units, and the rationale tied to the risk control (e.g., "output current shall be limited to a value not exceeding X, programmed at manufacturing"). Second, a manufacturing process requirement or work instruction that defines how the value is computed or selected, how it's written to non-volatile memory, and how it's read back and confirmed — because the control is only effective if the programming step is correct and verified. Third, a verification activity: for a parameter that can vary per unit, verification by test on a sample may be acceptable for the design, but 100% read-back verification at end-of-line is the practical control that every unit actually has a value in range. The traceability matrix should link the risk control to the parameter requirement, the manufacturing instruction, and both the design verification (does the limit actually protect against the hazard?) and the production verification (is the value correctly programmed on each unit?). I'd also make sure the parameter's range is justified by analysis — the risk analysis should state why values within the range are safe, so that a unit at the edge of the range is still covered.

**Possible follow-ups:** How would you handle a parameter whose safe range depends on other unit-specific calibration values, so the limit isn't a single number but a computed value? And what evidence would you need to show that the manufacturing programming step itself can't silently fail?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The systems engineer is describing compliance, and the test engineer is describing whether the evidence is *valid* — those are different questions, and the second one is the one that matters for patient safety and for a regulator who looks past the matrix. I'd treat the private disclosure seriously and not dismiss it, but I'd also avoid turning it into an accusation. My approach would be to run a focused validity check: pick the flagged tests and, for each, compare the test procedure against the risk control's failure condition — does the test drive the system into the failure state the control is meant to mitigate, and does it have a measurable pass/fail criterion tied to the control? If the test only exercises nominal behavior, it's not valid evidence regardless of whether it passes. I'd do this as a joint exercise with the systems engineer and test engineer present, so the finding is shared rather than relayed. If the check confirms the concern, the fix is to rewrite or supplement the affected tests, re-run them, and update the traceability links — and I'd extend the check to the rest of the matrix on a sampling basis, because if this happened once it likely happened elsewhere. I'd also address the process gap: tests should be reviewed against the risk control's failure condition at the time they're written, not just linked by requirement number. The conversation with the systems engineer would frame it as strengthening the evidence base, not as a compliance failure — the matrix is a map, and a map that points to the wrong place is worse than no map.

**Possible follow-ups:** How would you handle it if the systems engineer continues to argue that passing tests are sufficient evidence and refuses to authorize re-testing? And what would you change in the test-development process so that copied-and-relabeled tests get caught before they enter the matrix?
