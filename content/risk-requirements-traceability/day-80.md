# risk-requirements-traceability — Day 80

## Q1: How would you approach tracing a risk control measure that is implemented as a *combination of a hardware interlock and a firmware acknowledgment* — for example, a relay that physically removes power from a heater unless firmware continuously asserts an enable signal — when the hardware and firmware teams each own half of the control and neither team's requirements document references the other?

**Answer:** The core problem is that the control is a *contract* between two subsystems, and the contract itself has no owner. My approach would be to first make the contract explicit as a system-level requirement before worrying about which document it lives in. The control's effectiveness depends on two properties that neither team can verify alone: (1) the relay de-energizes when the enable signal is absent, and (2) the firmware asserts the enable signal only under conditions that are safe. Neither property is meaningful in isolation — a relay that works perfectly is useless if the firmware asserts enable unconditionally, and firmware that correctly gates the enable is useless if the relay welds closed.

Practically, I'd create a single system-level requirement that states the *integrated* behavior and the failure condition it mitigates, then derive two sub-requirements — one allocated to hardware, one to firmware — that each carry an explicit cross-reference to the parent. The hardware requirement would specify the de-energize behavior and the signal's electrical characteristics (polarity, voltage threshold, default state on loss of signal). The firmware requirement would specify the conditions under which the enable is asserted and the timing of the assertion relative to the heater's power-up. Both sub-requirements would reference the same risk control ID, so the traceability matrix shows a single control fanning out to two implementation requirements and then re-converging at a system-level integration test.

The verification strategy matters as much as the traceability. Each half can be verified in isolation — the relay by a bench test that removes the enable signal and confirms de-energization, the firmware by a test that confirms the enable is not asserted under fault conditions. But the *control* is only verified by an integration test that exercises the failure condition end-to-end: inject a fault that should cause the firmware to drop the enable, and confirm the heater actually loses power within the specified time. Without that integration test, you have two passing tests and an unverified control.

**Possible follow-ups:**
- If the hardware team's relay has a default state that is "energized" on loss of the enable signal (fail-safe vs fail-active), how does that change the traceability and verification approach?
- How would you handle the case where the firmware's enable assertion is itself a risk control for a *different* hazard, so the same signal is now traced to two risk controls?

## Q2: How would you approach establishing traceability for a risk control measure that is implemented as a *timing requirement* — for example, "the system shall remove power from the heating element within 500 ms of detecting an over-temperature condition" — when the timing depends on a chain of hardware and firmware elements, each with its own latency, and the 500 ms budget is allocated across them?

**Answer:** A timing requirement that spans a chain of elements is really a *budget*, and the traceability problem is that no single element owns the whole requirement. The first step is to decompose the budget explicitly: sensor response time, analog signal conditioning and filter delay, ADC conversion time, firmware detection and decision latency, output driver response, and relay or switch actuation time. Each of these becomes a derived requirement allocated to a specific element, and each carries a cross-reference to the parent timing requirement and the risk control it implements. The sum of the allocated latencies, plus a margin for the worst case, must be less than the total budget — and that sum should be documented as an analysis artifact, not just assumed.

The subtlety is that the worst case is not the sum of the *typical* latencies. It's the sum of the *worst-case* latencies, and those worst cases may not occur simultaneously in a way that is easy to reason about. For example, the firmware detection latency might depend on where in its execution cycle the fault occurs, and the ADC conversion might be delayed by a higher-priority interrupt. So the derived requirements need to specify worst-case values, not typical ones, and the analysis needs to justify that the worst cases are additive or that a more sophisticated method (e.g., a timing analysis that accounts for scheduling) was used.

For verification, I'd want both element-level tests (does the sensor respond within its allocated time? does the firmware detect within its allocated time?) and an end-to-end test that measures the total from fault injection to power removal. The end-to-end test is the one that actually verifies the risk control, because it captures interactions the element-level tests miss — for example, a filter that was characterized in isolation but behaves differently when the sensor is noisy. The element-level tests are useful for diagnosing *where* a budget overrun occurs, but they don't substitute for the integrated measurement.

**Possible follow-ups:**
- If the end-to-end test passes but one element is over its allocated budget while another is under, is the control verified? How would you handle that?
- How would you trace a timing requirement when the firmware latency is not deterministic — for example, because it depends on task scheduling in an RTOS?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *manual* test with no automated logging — the operator toggles a signal and observes an LED — and the risk file treats it as objective evidence?

**Answer:** The issue here is not that manual tests are inherently invalid — many legitimate verification activities are manual, especially for controls that involve human interaction or physical state changes. The issue is whether the test produces *objective evidence* that the control works, and whether that evidence is *reproducible* and *auditable*. A test where an operator toggles a signal and observes an LED can be objective if the procedure specifies exactly what to toggle, exactly what to observe, and what constitutes pass versus fail — and if the result is recorded in a way that a third party could review. It becomes weak evidence when the procedure says "verify the LED illuminates" without specifying timing, brightness, or what happens if it flickers, and when the record is a checkbox with no measurement.

My approach would be to first assess whether the manual test is *adequate* for the control in question. If the control's failure condition is subtle — for example, the LED illuminates but the actual power removal is delayed — then observing the LED is not sufficient evidence, because the LED is a proxy for the control, not the control itself. In that case, the test needs to be strengthened: add an instrument (a scope, a data logger, a multimeter) that captures the actual behavior, or add a step that confirms the downstream effect. If the control is genuinely binary and the LED is a faithful indicator, the manual test may be acceptable, but the procedure still needs to specify the acceptance criterion precisely and the record needs to capture enough detail to be auditable.

The traceability angle is that the verification activity should be linked to the *failure condition* it is meant to exercise, not just to the requirement. A manual test that toggles a signal and observes an LED is only valid evidence if the toggling actually reproduces the fault condition the risk control is designed to mitigate. If the test exercises the control under nominal conditions and the risk analysis specifies a fault condition, the test is not verifying the control — it's verifying that the control doesn't interfere with normal operation. That distinction needs to be visible in the traceability matrix, ideally by linking the verification activity to the specific failure mode or fault condition it addresses.

**Possible follow-ups:**
- If the manual test is the only practical way to verify the control — for example, because the control involves a physical action that can't be automated — how would you strengthen the evidence without redesigning the test?
- How would you handle a situation where the manual test was performed correctly but the record is a single checkbox with no date, operator name, or measured value?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when a single risk control measure is implemented *redundantly* — the same hazard is mitigated by two independent controls, and the risk analysis credits both — but the two controls are owned by different teams and were added at different times in the project?

**Answer:** Redundant controls are a common source of traceability confusion because the risk analysis treats them as a *pair*, but the requirements and verification artifacts treat them as two separate things. The first step is to make the redundancy explicit in the risk management file: the hazard is mitigated by control A *and* control B, and the risk analysis credits both because they are independent. That independence claim is itself a requirement — it needs to be stated, justified, and verified. If the two controls share a power supply, a microcontroller, or a communication bus, they are not fully independent, and the risk analysis's credit for both may be overstated.

For traceability, I'd create a single risk control entry that references both implementations, then derive two requirements — one per control — each carrying a cross-reference to the shared risk control ID. The traceability matrix would show the risk control fanning out to two requirements, each with its own verification activity, and then a *combined* verification activity that confirms the redundancy claim: with one control disabled, the other still mitigates the hazard. That combined test is the one that actually verifies the risk analysis's assumption, and it's the one most likely to be missing when the two controls were added at different times by different teams.

The "added at different times" aspect is a real risk. If control A was added early and control B was added later as a belt-and-suspenders measure, the later team may not have known that the risk analysis was crediting both, or may have assumed the earlier control was the primary one. The traceability scheme needs to make the redundancy visible so that anyone reviewing the risk file can see that two controls are credited and that both are verified. I'd also want a periodic review — perhaps at design review milestones — that checks whether the independence claim still holds after design changes, because redundancy is easy to lose inadvertently when a shared component is introduced later.

**Possible follow-ups:**
- If the two controls are credited as redundant but one is significantly more reliable than the other, how does that affect the risk analysis and the traceability?
- How would you verify the *independence* of two controls, as opposed to verifying each control individually?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file lists a risk control measure, the SRS contains a requirement that implements it, and the verification plan contains a test that verifies the requirement — but when you trace the links, you find that the requirement was written by the systems engineer, the test was written by the test engineer, and neither of them has ever read the risk analysis entry that justifies the control. The links exist on paper, but the *intent* of the control has been lost between the documents. How would you handle this?

**Answer:** This is a traceability failure that is invisible to a matrix audit, because the links are all present — the problem is that the links are *semantic* rather than *syntactic*. The requirement and the test may be technically correct, but if neither author understood *why* the control exists, the requirement may be under-specified (missing the failure condition it must handle) and the test may be under-stressing (exercising nominal behavior rather than the fault). The first thing I'd do is not blame the individuals — this is a process gap, not a competence gap. The systems engineer and test engineer were each doing their job; the process didn't require them to engage with the risk analysis.

My approach would be to close the loop in three steps. First, I'd bring the systems engineer, the test engineer, and the person who authored the risk analysis entry into the same conversation, and walk through the control together: what hazard does it mitigate, what failure condition must it handle, what does the requirement actually say, and what does the test actually exercise. That conversation usually surfaces the gaps quickly — the requirement may be missing a fault condition, or the test may be running under nominal conditions. Second, I'd fix the artifacts: update the requirement to explicitly reference the risk control and the failure condition, and update the test to exercise that condition. Third, and most importantly, I'd change the process so that this doesn't recur — for example, by requiring that any requirement derived from a risk control be reviewed by someone who has read the risk analysis entry, or by adding a "risk intent" field to the requirement template that forces the author to state the hazard and failure condition.

The deeper issue is that traceability is often treated as a documentation exercise — create the links, pass the audit — when it's really a *communication* mechanism. The links are only valuable if they carry intent from the risk analysis through to the verification. A matrix that shows "RC-001 → SRS-042 → TEST-017" is not traceability if the people who wrote SRS-042 and TEST-017 never understood RC-001. So I'd frame the fix not as "add more links" but as "make the links meaningful" — and that means involving the authors in the risk analysis, not just handing them a requirement number.

**Possible follow-ups:**
- How would you detect this kind of semantic traceability gap *before* a design review, rather than discovering it during one?
- If the systems engineer and test engineer are resistant to engaging with the risk analysis — for example, because they see it as the quality team's job — how would you bring them in?
