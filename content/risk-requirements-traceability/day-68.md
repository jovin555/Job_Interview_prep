# risk-requirements-traceability — Day 68

## Q1: How would you approach tracing a risk control measure that is implemented as a *latency budget* distributed across a chain of hardware and firmware elements — for example, "the system shall de-energize the output within a bounded time after a fault is detected" — when no single element owns the whole timing requirement?

**Answer:** The key insight is that the system-level timing requirement is a *composite* of per-element latencies, and traceability has to make that decomposition explicit rather than hiding it behind a single link. I'd start by treating the system-level timing requirement as the parent, then allocate a budget across each stage in the detection-to-actuation chain: sensor response time, signal conditioning/sampling, firmware detection and decision logic, actuation driver, and the physical switching element. Each allocation becomes a derived requirement owned by the responsible discipline, with its own acceptance criterion and its own verification activity. The traceability matrix then shows the parent requirement decomposed into child requirements, each child traced to a design element and a verification method, and the parent traced to an integration test that measures end-to-end latency under worst-case conditions. The critical discipline is that the *sum* of the allocated budgets must be less than the parent requirement with margin, and that margin itself should be documented — otherwise you can pass every child test and still fail the parent. I'd also make sure the integration test exercises the worst-case combination (slowest sensor, highest firmware load, lowest supply voltage within spec) rather than nominal, because timing margins often erode under corner conditions. Finally, I'd flag any element whose latency is not directly measurable in isolation — for example, interrupt latency that depends on the RTOS scheduler — and require either a measured bound or a documented analysis with justification.

**Possible follow-ups:**
- If one element in the chain has a latency that varies with operating conditions, how would you represent that variability in the traceability matrix without making it unreadable?
- How would you handle a situation where the integration test passes but one of the child allocations was never independently verified?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented *redundantly* — the same hazard is mitigated by two independent controls, and the risk analysis credits both — but the two controls were added at different times by different teams?

**Answer:** The first thing I'd do is make the redundancy explicit in the risk management file: the hazard, the two control measures, and the claim that they are independent. That independence claim is itself a safety argument that needs to be verified, not assumed — if both controls share a common element (same power rail, same sensor, same firmware module), they aren't truly independent and the risk credit may be overstated. So the traceability scheme needs to capture not just "hazard → control A → verification" and "hazard → control B → verification," but also "control A and control B → independence claim → verification of independence." On the practical side, when controls were added at different times by different teams, the numbering schemes and document structures often diverge, so I'd introduce a cross-reference at the hazard level: a single hazard ID that both controls trace back to, with each control's requirements, design elements, and verification activities linked underneath. I'd also check whether the risk analysis credits both controls fully or partially — if it credits both, then *both* must be verified, and the failure of either must be shown not to defeat the mitigation. A common gap is that each team verifies its own control in isolation, but nobody verifies that the two together actually achieve the claimed risk reduction, or that a single fault can't take out both.

**Possible follow-ups:**
- How would you verify the independence claim if the two controls share a common power supply but are otherwise separate?
- If the risk analysis credits both controls but one was added late in the project and has weaker verification evidence, how would you handle the gap?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *manual* test with no automated logging — the operator toggles a signal and observes an LED — and the risk file treats it as objective evidence?

**Answer:** Manual observation can be legitimate objective evidence, but only if the test is structured so that the result is unambiguous and recorded in a way that a third party could audit. The problem with "toggle a signal and observe an LED" is that it's vulnerable to observer error, timing ambiguity, and lack of a permanent record. I'd first ask what the acceptance criterion actually is: if the requirement is "the LED illuminates within X ms of the fault," then human observation is almost certainly inadequate because reaction time and perception introduce error far larger than the tolerance. If the requirement is qualitative — "the LED illuminates" — manual observation may be acceptable, but I'd still want a documented procedure with a defined pass/fail criterion, a record of the unit under test, the operator, the date, and the observed result. Where the risk control's effectiveness depends on timing, magnitude, or repeatability, I'd push to instrument the test: a scope, a data logger, or a firmware counter that captures the event with a timestamp. That converts a subjective observation into a measurement. If instrumentation genuinely isn't feasible, I'd document *why* manual observation is sufficient — for example, because the failure mode is gross and binary — and have that justification reviewed and approved, rather than leaving it implicit. The traceability link should point to the test procedure and the recorded result, not just to a test name.

**Possible follow-ups:**
- If the test was already performed manually and the risk file has been submitted, how would you remediate without invalidating the whole verification campaign?
- How would you decide which risk controls genuinely require instrumented measurement versus which can be verified by documented observation?

## Q4: How would you approach deciding whether a risk control measure should be traced to a *design requirement*, a *design element*, or *both* — and what practical difference does that distinction make in a traceability matrix?

**Answer:** The distinction matters because requirements and design elements answer different questions and fail in different ways. A design requirement is a statement of *what the system shall do* — it's the contract, and it's what verification is written against. A design element is *how* that contract is realized — a circuit block, a firmware module, a mechanical feature. Tracing a risk control to a requirement ensures the control is specified and verifiable; tracing it to a design element ensures the control is actually implemented somewhere and can be located, reviewed, and changed under configuration control. In practice, most risk controls need both links: the requirement captures the intent and the acceptance criterion, and the design element captures the physical or logical realization. The practical difference shows up when something changes. If you only trace to the requirement and the design element is later refactored — say, a discrete comparator is replaced by an ADC input to the microcontroller — the requirement may still be satisfied on paper, but the verification method may no longer be valid, and nobody notices because the design link was missing. Conversely, if you only trace to the design element and the requirement is never written, you have no measurable acceptance criterion and verification becomes subjective. So my rule of thumb: trace to the requirement for verifiability, trace to the design element for change impact and review coverage, and make sure the two links are consistent — if the design element changes, the requirement and its verification should be re-examined.

**Possible follow-ups:**
- For a risk control implemented purely through component derating, is there a meaningful "design requirement," or is the design element the only sensible anchor?
- How would you handle a case where one requirement is implemented by multiple design elements, or one design element implements multiple requirements?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file lists a risk control measure, the SRS contains a requirement that implements it, and the verification plan contains a test that verifies the requirement — but when you trace the links, you find that the requirement was written by the systems engineer, the test was written by the test engineer, and neither has ever read the risk analysis entry that justifies the control. The links exist on paper, but the *intent* of the control has been lost between the documents. How would you handle this?

**Answer:** This is a classic case of traceability that is structurally complete but semantically empty — the links exist, but the *reason* for the control has been lost. The first thing I'd do is not treat it as a documentation problem but as a communication problem: the people writing requirements and tests need to understand *why* the control exists, not just *what* it does. I'd start by pulling the three artifacts together — the risk analysis entry, the requirement, and the test — and walking through them with the systems engineer and test engineer to confirm whether the test actually exercises the failure condition the risk analysis describes. Often it won't, because the test was written against the literal wording of the requirement, which may have been paraphrased away from the original hazard. Where the test is inadequate, I'd revise it to explicitly reference the hazard and the failure condition, and add a note in the test procedure explaining what the test is proving. Where the requirement is ambiguous, I'd tighten it so the safety intent is visible — for example, adding a rationale field or a reference to the risk control ID. Longer term, I'd change the process so that risk control measures are reviewed jointly by the systems engineer, the test engineer, and whoever owns the risk analysis, at the point the requirement is written, not after the fact. The goal is that anyone reading the requirement or the test can see the hazard it addresses without having to go hunting through the risk file. I'd also add a periodic traceability audit that checks not just that links exist, but that the linked artifacts are consistent in intent — a "does this test actually prove this control works?" review, not just a "does this link exist?" check.

**Possible follow-ups:**
- How would you scale that kind of intent-level review across a project with hundreds of risk controls, without it becoming a bottleneck?
- If the risk analysis entry itself is vague about the failure condition, how would you go about tightening it without reopening the whole hazard analysis?
