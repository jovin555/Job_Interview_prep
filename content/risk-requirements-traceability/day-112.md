# risk-requirements-traceability — Day 112

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement is technically correct but semantically orphaned — it describes *what* the firmware does without capturing *why*, so the safety intent lives only in the risk file and can be lost the moment someone refactors the code or rewrites the requirement. I'd fix this at three levels. First, I'd rewrite the firmware requirement so it carries the safety intent explicitly: not just "the firmware shall clamp commanded motor speed to a maximum rate of change of X units/s," but a requirement that states the hazard it mitigates, the failure condition it guards against, and a measurable acceptance criterion tied to the overspeed threshold from the risk analysis. Second, I'd add a bidirectional link in the traceability matrix from the risk control measure (in the risk management file) to that requirement, and from the requirement to the verification activity — so the chain hazard → control → requirement → test is explicit and auditable. Third, I'd make the verification test actually stress the failure condition: drive a command step that would produce an unsafe rate of change if unclamped, and confirm the output rate stays within the limit — not just confirm the clamp function exists. The key principle is that a risk control measure implemented in firmware is still a risk control measure, and the requirement that implements it must be traceable to the hazard, not merely to a functional behavior. I'd also flag this pattern to the team as a general rule: any firmware requirement that implements a risk control should reference the risk ID, so the intent survives future edits.

**Possible follow-ups:** If the firmware requirement is rewritten to reference the hazard, how do you keep the risk file and the SRS from drifting out of sync as both evolve? / How would you verify the rate limiter under conditions where the command source itself is faulty — for example, a sensor feeding a wildly oscillating setpoint?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap with a distributed control loop is that the risk analysis credits one control, but the implementation is spread across three owners, and no single requirements document describes the whole thing — so the traceability matrix either links the control to one arbitrary element or to nothing meaningful. I'd approach it by decomposing the single risk control measure into its constituent *control elements* while keeping the parent control intact. In the risk file, I'd keep the control as one entry (because that's how the hazard is mitigated), but I'd add a decomposition note that identifies the sensor path, the control law, and the actuator path as the elements whose combined behavior achieves the control. Then in the traceability matrix, I'd create a parent-child structure: the risk control measure links to a system-level requirement that describes the loop's overall safe behavior (e.g., "the heating element shall be maintained below the maximum safe temperature under all operating conditions"), and that system requirement decomposes into subsystem requirements — a sensor accuracy/response requirement, a firmware control-law requirement, and a power-switch response requirement. Each subsystem requirement then traces to its own verification activity, and the system-level requirement traces to an integrated test that exercises the whole loop. The critical point is that the integrated test must exist — verifying each element in isolation doesn't prove the loop works, because the failure modes are often at the interfaces (sensor latency, control-law saturation, switch response time). I'd also make sure the timing budget across the loop is captured as an explicit allocation, since "keeps it within a safe range" is really a timing and gain-margin claim that no single element owns.

**Possible follow-ups:** How would you allocate the timing budget across the sensor, firmware, and switch, and who owns the integrated verification? / If the firmware PID loop is later retuned, what in the traceability scheme tells you that the integrated verification needs to be re-run?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** This is a classic case of a traceability link that is formally complete but evidentially hollow — the matrix shows a link, but the linked activity doesn't actually assess the control's failure condition, so the review can pass without anyone confirming the control works. I'd treat it as a gap, not a valid link. My approach: first, confirm the gap by reading the review checklist against the risk control's failure condition — if the checklist has no line item that asks the reviewer to assess that specific failure mode, the link is invalid. Second, either amend the review checklist to add an explicit assessment item for that risk control (with a measurable criterion — what the reviewer must confirm and what evidence they must record), or replace the review with a more appropriate verification method (a test, an analysis, or a targeted inspection) if the control can't be meaningfully assessed by review. Third, update the traceability matrix so the link points to the amended activity, and record the rationale for the change. The broader principle is that a verification activity is only valid evidence if it is *capable of detecting the failure* the control is meant to prevent — a design review can be perfectly valid evidence for some controls (creepage distances, derating, layout rules), but only if the review criteria explicitly target the failure condition. I'd also add a review of the whole matrix for this pattern, because checklists written for one purpose tend to get reused across controls, and the same hollow-link problem often appears in clusters.

**Possible follow-ups:** How would you decide whether a control is better verified by an amended design review versus a functional test? / What objective evidence would you require a design review to record so that it counts as verification rather than opinion?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is tricky because the control isn't a circuit or a piece of firmware logic — it's a *value*, and the value can vary unit to unit, so the traceability scheme has to capture not just "the parameter exists" but "the parameter was set correctly on this unit and the setting is protected." I'd structure it in layers. First, a design requirement that defines the parameter: its name, its valid range, its units, its default, and the rationale (the hazard it mitigates). Second, a manufacturing requirement or work instruction that defines how the value is determined and written — the calibration or programming step — and the acceptance criteria for the written value. Third, a verification activity at two levels: a design verification that confirms the parameter is actually used by the firmware/hardware to enforce the limit (i.e., the control is effective when the parameter is set to a worst-case value), and a production verification that confirms each unit's stored value is within the valid range and was written correctly. The traceability matrix then links the risk control measure to the design requirement, the design requirement to the manufacturing instruction, and both to their respective verification activities. I'd also make sure the parameter is protected against corruption or unauthorized change — checksum, write-protection, or a service-port access control — and that this protection is itself a requirement with its own verification, because a safety parameter that can be silently changed is not a reliable control. The key insight is that for manufacturing-set parameters, traceability has to span design *and* production, and the verification evidence has to include per-unit records, not just a one-time design test.

**Possible follow-ups:** How would you handle a unit that comes back from the field with a parameter value outside the valid range — what does your traceability scheme tell you about how it got there? / If the parameter can be changed via a service port, how do you trace the change control back to the risk analysis?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** I'd take the test engineer's concern seriously and treat it as a potential systemic gap rather than a paperwork issue, because a matrix that passes audit while the underlying evidence is hollow is worse than an incomplete matrix — it creates false confidence. My first step would be to verify the concern directly: pick a sample of the flagged tests, read each against the risk control's failure condition, and check whether the test actually drives the system into that condition and would fail if the control were disabled. That gives me objective evidence rather than a he-said-she-said. If the concern is confirmed, I'd frame the conversation with the systems engineer around *evidence capability*, not compliance: the question isn't whether the matrix is complete, it's whether each linked test is capable of detecting the failure it's credited with mitigating — a test that passes whether or not the control works provides no evidence. I'd propose a targeted remediation: for each flagged test, either rewrite it to exercise the actual failure condition (including a negative check — disable the control and confirm the test fails), or re-link the control to a test that does. I'd also want to understand *why* it happened — copied tests usually mean schedule pressure or a template-driven process — and address that root cause, for example by adding a review step where the test author must state which failure condition the test exercises and how. Throughout, I'd keep the tone collaborative: the systems engineer isn't wrong that the matrix is compliant, but compliance without evidence capability doesn't survive a real audit or a real field failure, and the goal is a matrix we can actually defend.

**Possible follow-ups:** How would you prioritize which flagged tests to remediate first if you can't re-run all of them before the next milestone? / What process change would you put in place to prevent copied-and-relabeled tests from entering the matrix in the first place?
