# risk-requirements-traceability — Day 90

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement exists and is testable, but the *safety intent* is invisible in the SRS — so anyone reading the firmware spec in isolation would see a performance feature, not a risk control. I'd fix this at three levels. First, in the risk management file, I'd make the control entry explicit about the implementation: name the firmware function or module, state the hazard it mitigates, and record the assumed rate limit and the rationale for that value (derived from the hazard analysis, not chosen arbitrarily). Second, in the SRS, I'd either add a safety-annotated requirement or attach a safety classification attribute to the existing functional requirement — something like a "safety-relevant" flag plus a cross-reference to the risk control ID — so the link is machine-traceable rather than living in someone's head. Third, in the verification plan, the test must be written against the *failure condition*, not just the clamping behavior: drive the actuator command with a step input that would produce overspeed if unclamped, and confirm the output rate of change stays within the limit and that the hazard state is never reached. The key discipline is that the traceability link should carry the *reason*, not just the ID — a bare "RC-014 → SRS-221 → TP-088" chain is auditable but not reviewable. I'd also check whether the rate limit value itself is a configurable parameter, because if it is, the parameter becomes part of the control and needs its own protection and verification.

**Possible follow-ups:** If the rate limit is a compile-time constant, does that change how you'd verify it versus a runtime-configurable parameter? And how would you handle the case where the firmware team later refactors the limiter into a shared library used by non-safety features — how do you keep the traceability intact?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** This is the classic "emergent control" problem: the risk analysis credits a single control, but no single artifact implements it, so a naive traceability matrix either links the control to three unrelated requirements (losing the sense that they must work *together*) or links it to nothing concrete (losing auditability). I'd handle it by introducing an explicit intermediate node in the traceability structure — a "control realization" or "control allocation" record that sits between the risk control measure and the subsystem requirements. That record states the control's safety intent, decomposes it into the contributions each element must make (sensor accuracy and response time, PID loop stability and saturation behavior, switch response and failure mode), and allocates a portion of the overall performance budget to each. Then each subsystem requirement traces up to that allocation record, and the record traces up to the risk control. Verification is the harder half: because the control is emergent, element-level tests are necessary but not sufficient — you need an integrated test that exercises the loop under the fault conditions the risk analysis cares about (sensor drift, sensor stuck-at, switch failure to open) and confirms the *system* stays in a safe range. I'd also make sure the interface assumptions between the elements are documented — the PID loop's behavior depends on the sensor's sample rate and noise characteristics, and if those change, the control's effectiveness changes even though no single requirement was violated.

**Possible follow-ups:** How would you allocate the performance budget across the three elements — top-down from the hazard, or bottom-up from what the components can achieve? And if the integrated test is expensive to run, how would you decide how much of the fault space to cover?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence for certain kinds of controls — layout rules, derating, creepage, thermal margin — but only if the review actually examines the thing the control is supposed to achieve. A generic checklist that happens to touch the same subsystem is not evidence; it's coincidence. My approach would be to treat this as a traceability defect rather than a documentation nicety: the link exists, but the *acceptance criterion* of the verification activity doesn't match the risk control's failure condition, so the coverage is illusory. Concretely, I'd go back to the risk control entry, extract the specific failure condition it mitigates, and check whether the review record contains an explicit assessment of that condition with a stated conclusion. If it doesn't, I'd either (a) extend the review checklist with a risk-control-specific line item and re-run that portion of the review with the right reviewers present, or (b) reclassify the verification method — if the control genuinely can't be assessed by review, it needs a test or an analysis instead. I'd also look at whether this is a one-off or a pattern: if several controls are traced to generic reviews, the review templates themselves need a "risk control verification" section that forces the reviewer to state which control they're assessing and what they concluded. The output of the review should be objective evidence — a signed record naming the control, the condition assessed, and the result — not just a checked box.

**Possible follow-ups:** How would you decide whether a given control is legitimately review-verifiable versus needing a test? And if the review has already been signed off and the design is frozen, what's the least disruptive way to close the gap without invalidating the whole review?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** When the parameter value is the control, the traceability has to cover three distinct things that are easy to conflate: the *requirement* that defines the allowable range and the rationale for it, the *manufacturing process* that programs and verifies the value, and the *runtime behavior* that enforces it. I'd structure it as follows. In the risk management file, the control entry states the hazard, the parameter, the safe range, and the basis for the range — derived from the hazard analysis, not from what the hardware happens to tolerate. In the SRS, there's a requirement specifying the parameter's allowed range and the behavior if the stored value is out of range or corrupted (this is important — a unit with a corrupted parameter must fail safe, not run unconstrained). In the manufacturing/test documentation, there's a procedure that programs the value and verifies it against the range, with the record retained per unit — that's the verification evidence for the *as-built* control. And in the design, there's a runtime check that validates the parameter at startup and enforces it during operation, traced to its own requirement. The traceability matrix then shows the risk control branching to three verification activities: a design verification of the runtime enforcement, a process validation of the programming step, and a per-unit production test record. The subtle point is that unit-to-unit variation means the control's effectiveness is only as good as the production verification — so I'd want the production test to be a real measurement against limits, not just a "programmed OK" flag, and I'd want the traceability to make clear that the per-unit record is part of the evidence package.

**Possible follow-ups:** How would you handle a field service scenario where the parameter can be re-programmed after shipment — does that change the traceability model? And what would you do if the production test only samples units rather than testing every one?

## Q5: (Behavioral) Imagine you're leading a project where the traceability matrix is complete and passes audit — every risk control measure links to a requirement and a verification activity — but a test engineer privately tells you that several of the linked tests were written by copying a similar test from a previous project and adjusting the labels, and nobody has confirmed the tests actually exercise this project's failure conditions. The systems engineer argues the matrix is compliant and the tests pass, so there's no problem. How would you handle this?

**Answer:** The systems engineer is technically correct that the matrix is compliant and the tests pass, but that's exactly the failure mode I'd be worried about: traceability that satisfies the auditor while the underlying evidence is hollow. A copied test that passes tells you the DUT behaves like the previous project's DUT under the previous project's stimulus — it tells you nothing about whether this project's failure condition is exercised. I'd handle it in stages. First, I'd verify the concern myself rather than acting on hearsay — pick two or three of the flagged tests, read the test procedure against the risk control's failure condition, and check whether the stimulus actually drives the system into the hazardous state or just near it. That gives me facts to work with. Second, I'd frame the conversation with the systems engineer around *evidence adequacy*, not compliance: the question isn't whether the link exists, but whether the linked activity demonstrates the control works under the conditions the risk analysis says matter. I'd propose a targeted review — not a re-run of everything, but a focused gap assessment of the flagged tests against their risk control entries, with the test engineer, systems engineer, and quality representative in the room. Third, depending on what the review finds, the remedy is either re-writing the affected tests to stress the actual failure condition, or documenting a justified rationale for why the existing test is adequate (sometimes it genuinely is, and that should be written down). I'd also want to understand *why* it happened — copying tests is usually a symptom of schedule pressure or unclear test-writing guidance — and fix the process so the next project doesn't repeat it. The tone matters: I'd avoid turning it into a blame exercise, because the test engineer did the right thing by raising it, and I want that channel to stay open.

**Possible follow-ups:** If the gap assessment finds that a control was never actually verified, how would you handle the schedule and cost conversation with the program manager? And how would you prevent "copy-paste test" from becoming the path of least resistance on the next project?
