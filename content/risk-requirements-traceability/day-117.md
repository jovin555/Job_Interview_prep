# risk-requirements-traceability — Day 117

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — for example, firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem here is that the requirement is functionally correct but safety-anonymous — it describes *what* the firmware does without recording *why* it exists. That breaks the audit chain: an auditor or a future maintainer can read the requirement, see the code, see a passing test, and still have no way to know that removing or loosening the limiter would reintroduce a hazardous overspeed condition. My approach would be to repair the link at the requirement level rather than paper over it in the matrix.

First, I'd add an explicit safety-intent annotation to the firmware requirement — not necessarily a new requirement, but a traceable reference back to the specific risk control measure ID and the hazard it mitigates. Something like a "derived from" or "safety rationale" attribute on the requirement record. This keeps the functional statement intact (the clamping behavior) while making the safety lineage explicit and machine-traceable.

Second, I'd check whether the requirement is actually *complete* as a safety requirement. A functional statement like "clamp commanded speed to a maximum rate of change" often omits the parameters that make the control effective: the actual rate limit value, its tolerance, the behavior at the boundary, and what happens if the limiter itself is bypassed or the parameter is corrupted. If those are missing, the requirement is under-specified for its safety role, and I'd work with the firmware lead to tighten it — with measurable acceptance criteria so the verification test has something objective to check.

Third, I'd verify the trace is bidirectional: from the risk control measure down to the requirement and the test, and from the requirement back up to the hazard. The downward direction is what audits usually check; the upward direction is what catches orphaned requirements and lost intent.

Finally, I'd add a review gate: any change to a requirement tagged as safety-derived should trigger a risk file review, so the link can't silently rot when the limiter is retuned during development.

**Possible follow-ups:**
- If the rate limit value is a tunable parameter rather than a fixed constant, how does that change what the requirement needs to say and how the verification test is structured?
- How would you detect this kind of "safety-anonymous requirement" systematically across an existing SRS, rather than fixing them one at a time as you find them?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap with a distributed control is treating it as a single atomic control in the matrix. If the risk file says "control: temperature loop keeps heater in safe range" and the matrix links that one line to one test, you've lost all the internal structure — and when a subsystem changes, you have no way to know which part of the control you've affected.

My approach is to decompose the control into its constituent *elements* while preserving the top-level identity. The risk control measure stays as the parent record, but I'd create child trace links to each contributing element: the sensor's accuracy and response time, the firmware loop's algorithm and its bounds (integral windup limits, output clamping), and the power switch's ability to actually interrupt the heater — including its failure mode (does it fail open or closed?). Each element gets its own requirement with measurable criteria, and each traces back up to the parent control.

The verification strategy then has two layers. Element-level verification confirms each piece meets its allocation — sensor calibration and response, loop behavior under step and saturation inputs, switch actuation and drop-out. System-level verification confirms the *emergent* behavior: that the whole loop holds the heater in range under realistic disturbances, including the failure of any single element. That second layer is essential because the risk analysis credits the loop as a whole, and no amount of element-level testing proves the combination works.

I'd also make the interface between elements explicit — the sensor-to-firmware signal range and timing, the firmware-to-switch command semantics — because distributed controls usually fail at the seams, not inside the blocks. Those interfaces belong in an ICD, and the traceability should reference them so a change to, say, the sensor's output scaling flags the loop requirement for review.

**Possible follow-ups:**
- If the risk analysis assumes the loop tolerates the failure of any one element, how would you trace and verify that fault-tolerance claim specifically?
- How would you handle the case where the firmware PID loop is later retuned — what in the traceability structure tells you whether the retune invalidates the original verification?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** This is a case where the trace exists but the evidence is hollow. A design review can be legitimate verification for certain kinds of controls — derating, creepage, layout rules — but only if the review actually examines the specific failure condition the control addresses. A generic checklist that happens to touch the same subsystem is not evidence that anyone assessed whether the control works.

My first step would be to read the review record and check honestly: did any reviewer, at any point, evaluate the control's specific failure condition? Sometimes the answer is yes and it's just not documented — in which case the fix is to capture the evidence properly, not to redo the review. If the answer is genuinely no, the trace is invalid and I'd treat it as a gap.

The fix is to make the review criteria control-specific. I'd add explicit review items derived from the risk control measure — for example, "confirm the [component] voltage rating exceeds the worst-case stress by the specified margin, including transient conditions" — so the reviewer has a concrete question to answer and the record shows the answer. The review checklist should be generated or at least cross-referenced from the risk file, not maintained as a separate generic document.

I'd also make sure the review record captures the *evidence* — the calculation, the datasheet reference, the measured value — not just a checkbox. For a control verified by review, the review record *is* the objective evidence, so it has to stand on its own the way a test report would.

Longer term, I'd want the traceability matrix to distinguish verification method (test, analysis, inspection, review) and to flag any control whose only evidence is a review, so those get extra scrutiny at audit time.

**Possible follow-ups:**
- How would you decide whether a given risk control is legitimately verifiable by design review versus needing a physical test?
- If the review has already been signed off and the design is frozen, what's the least disruptive way to close this gap without invalidating the whole review?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is one of the harder cases because the control isn't a circuit or a piece of code — it's a *value*, and the value varies per unit. A naive traceability scheme links the risk control to a requirement ("the output current shall not exceed the maximum rated value") and to a test, and everything looks fine — but the actual control lives in the manufacturing process and the per-unit programming step, which the matrix never touches.

I'd structure this as a chain with three distinct links. First, the risk control measure traces to a *parameter specification*: the parameter's allowed range, its tolerance, and the rationale for the limit — this is the design-side requirement. Second, the parameter specification traces to the *manufacturing programming procedure*: how the value is computed or selected, how it's written to non-volatile memory, and how it's read back and verified. Third, the programming procedure traces to *production test evidence*: the per-unit record showing the value written and the readback confirmation.

The verification story then has two parts. Design verification confirms that the parameter, when set anywhere in its allowed range, actually produces the safe behavior — that's a bench test sweeping the range, not a single nominal value. Production verification confirms each unit got a value in range and that the value survived programming. Those are different activities with different evidence, and both need to be in the matrix.

I'd also address integrity: what prevents the parameter from being changed after manufacturing — a service port, a firmware update, a memory corruption? If the parameter is writable in the field, the control has a whole additional failure mode, and the traceability needs to cover the write-protection or authentication mechanism too. And I'd want the device's serial number or lot to be traceable to its programmed value, so a field issue can be correlated back to production records.

**Possible follow-ups:**
- How would you verify that the safe behavior holds at the *edges* of the allowed parameter range, not just at the nominal value?
- If the parameter can be updated in the field by service personnel, how does that change the risk analysis and the traceability?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file, the SRS, and the verification plan are each internally consistent and each passes its own review — but when you trace across all three, you find that a risk control measure is linked to a requirement that is linked to a test, and the test passes, yet the *combination* doesn't actually demonstrate the control works, because the requirement was written at a level of abstraction the test can satisfy without exercising the control's failure condition. The three document owners each argue their document is correct. How would you handle this?

**Answer:** The first thing I'd do is reframe the disagreement, because all three owners are right about their own documents — the failure is in the *seams*, and no single document owner can see it from inside their document. So I wouldn't adjudicate who's wrong; I'd put the three artifacts side by side and walk the chain together, with all three owners in the room, starting from the hazard and ending at the test evidence.

The concrete question I'd put on the table is: "If we disabled this control, would this test fail?" If the answer is no — or if nobody can say for certain — then the chain doesn't demonstrate the control works, regardless of what each document says internally. That's a shared, objective test of the linkage that doesn't require anyone to concede their document is defective.

Once we agree there's a gap, the fix is usually at the requirement, not the test. The requirement was written at an abstraction level that let the test pass without stressing the failure condition — so I'd work with the systems engineer to make the requirement's acceptance criteria specific enough that a test *could* fail it. Then the test engineer revises the test to actually exercise the failure condition, ideally including a negative check — deliberately disabling or defeating the control and confirming the test detects it. That negative check is the strongest evidence that the test is capable of detecting the failure, and it's worth building into the verification approach for safety-critical controls generally.

Process-wise, I'd add a cross-document trace review as a gate — not three separate document reviews, but one review that walks hazard → requirement → test as a single chain. That's where this class of defect gets caught, and it's cheap compared to finding it at audit or, worse, in the field.

**Possible follow-ups:**
- How would you build the "disable the control and confirm the test fails" check into the verification plan without making every test prohibitively expensive?
- If the schedule doesn't allow reworking the requirement and test before a milestone, how would you handle the risk in the interim?
