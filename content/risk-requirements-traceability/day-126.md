# risk-requirements-traceability — Day 126

## Q1: How would you approach establishing traceability for a risk control measure that is implemented as a *firmware-based rate limiter on an actuator command* — firmware that clamps the commanded speed of a motor to a maximum rate of change — when the risk analysis credits the limiter as a control against a hazardous overspeed condition, but the firmware requirements only describe the clamping behavior functionally and never reference the hazard?

**Answer:** The core problem is that the requirement captures the *mechanism* but not the *safety intent*, so the traceability link from hazard to requirement is implicit and fragile — anyone reading the requirement in isolation would treat it as a performance feature, not a risk control. I'd fix this at the requirement level rather than trying to patch the matrix. First, I'd add an explicit safety-derived requirement (or annotate the existing one) that states the hazard it mitigates, the failure condition it guards against, and the measurable acceptance criteria — maximum rate of change, tolerance, and the conditions under which the clamp must hold. That gives the verification activity something objective to test against, and it gives the traceability matrix a real anchor: hazard → risk control measure → safety requirement → design element (the clamp logic) → verification test. Second, I'd make sure the verification test actually stresses the failure condition — commanding a step change that would exceed the limit and confirming the output ramps rather than jumps — rather than just confirming nominal operation. Third, I'd check whether the rate limit interacts with other controls (e.g., a hardware overcurrent trip) so the matrix doesn't double-count or leave a gap. The general principle: a risk control that lives only in the risk file and a functional requirement is a control whose intent can be silently lost at the next requirement revision.

**Possible follow-ups:** If the firmware team argues that adding hazard references to requirements "clutters" the SRS, how would you respond? How would you handle the case where the same clamp logic is reused in a non-safety context in another product, so the requirement is shared?

## Q2: How would you approach establishing traceability when a single risk control measure is implemented as a *distributed control loop* — for example, a temperature control where a hardware sensor, a firmware PID loop, and a hardware power switch each contribute to keeping a heating element within a safe range — and the risk analysis treats the whole loop as one control?

**Answer:** The trap here is treating the loop as a single atomic control and tracing it to one requirement and one test, when in reality its effectiveness depends on three elements each doing their job and on the *interfaces* between them. I'd decompose the control into its constituent elements and trace each one, while keeping a parent link so the risk file still shows the integrated measure. Concretely: a system-level safety requirement describing the safe operating envelope (the temperature the element must never exceed, and the response time), then derived requirements for the sensor path (accuracy, range, failure detection), the firmware loop (setpoint limits, integral windup protection, behavior on sensor fault), and the power switch (ability to interrupt, response time, failure mode). Each derived requirement traces to its design element and its verification activity — sensor calibration test, firmware loop test with injected faults, switch response-time test — and the parent control traces to an integration test that exercises the whole loop under a fault condition. The key insight is that the *interfaces* need their own traceability: what happens when the sensor reads stale, when the firmware commands but the switch doesn't respond. Those are where distributed controls usually fail, and they're invisible if you only trace the loop as a black box.

**Possible follow-ups:** How would you allocate the overall response-time budget across the three elements, and how would you verify the allocation holds? If the integration test passes but a component-level test fails, how do you decide which result governs?

## Q3: How would you approach handling a situation where a risk control measure is traced to a verification activity, but the verification activity is a *design review* whose checklist was written for a different purpose — for example, a general "power supply design review" checklist — and the risk control's specific failure condition is never explicitly assessed during the review?

**Answer:** A design review can be legitimate verification evidence for certain kinds of controls — layout rules, derating, creepage — but only if the review actually examines the specific failure condition the control addresses. A generic checklist that happens to touch the same subsystem is not evidence; it's a coincidence of scope. My approach would be to make the review *fit for purpose* rather than replace it with a test. I'd add explicit review criteria derived from the risk control: the specific failure mode, the design features that mitigate it, and the acceptance criteria the reviewer must confirm. I'd also make the review record capture the reviewer's explicit statement that those criteria were assessed, so the evidence is auditable rather than implied. If the control genuinely can't be assessed by review — for example, it depends on dynamic behavior — then the traceability link is wrong and needs to point to a test or analysis instead. The general rule I'd apply: the verification method should be chosen because it can demonstrate the control works, not because it's convenient, and the acceptance criteria in the review record should be traceable back to the risk control's failure condition.

**Possible follow-ups:** How would you handle a reviewer who signs off without genuinely assessing the added criteria? What's the difference between a design review as verification and a design review as a design activity, and does that distinction matter for the traceability matrix?

## Q4: How would you approach creating a traceability scheme that connects risk control measures to requirements when the system includes a *safety-related parameter set at manufacturing time* — for example, a maximum output current limit stored in non-volatile memory during production — where the parameter value itself is the control, and the value can differ between units?

**Answer:** This is a case where the control isn't a design feature but a *value*, so the traceability has to cover the value's derivation, its programming, and its verification — three things that are easy to leave dangling. I'd structure it as: a safety requirement stating the maximum allowable output current and the rationale (derived from the hazard analysis), a specification of how the limit is computed or selected per unit (from component tolerances, calibration, or a fixed worst-case value), a manufacturing procedure requirement that defines how the value is programmed and read back, and a verification activity that confirms the programmed value is within the safe range on the actual unit. The traceability matrix then has links from hazard → risk control → safety requirement → manufacturing specification → per-unit verification record. The subtle part is that the *range* of acceptable values is itself safety-relevant: if the parameter can be set anywhere in a wide window, the upper bound of that window is the real control, and it needs its own justification and its own verification. I'd also want a link to the change-control process, because a parameter that can be reprogrammed via a service port is a control that can drift out of spec after release — so the traceability should extend to whatever governs who can change it and how changes are validated.

**Possible follow-ups:** How would you verify the parameter on a sample basis versus every unit, and what determines which is appropriate? If a service procedure can change the value in the field, how does that affect the traceability scheme?

## Q5: (Behavioral) Imagine you're leading a project where the risk management file, the SRS, and the verification plan are each internally consistent and each passes its own review — but when you trace across all three, you find that a risk control measure is linked to a requirement that is linked to a test, and the test passes, yet the *combination* doesn't actually demonstrate the control works, because the requirement was written at a level of abstraction the test can satisfy without exercising the control's failure condition. The three document owners each argue their document is correct. How would you handle this?

**Answer:** The first thing I'd do is reframe the disagreement so it isn't about whose document is wrong — because in a narrow sense, all three owners are right: each document is internally consistent. The failure is in the *seams* between them, and no single owner is accountable for the seam. So I'd convene the three owners around a single concrete question: take this specific control, describe the failure condition it's meant to mitigate, and ask what evidence would convince an auditor that the control actually works under that condition. That usually surfaces the gap quickly — the requirement is too abstract, or the test is too shallow, or both — and it moves the conversation from blame to a shared technical problem. Then I'd fix it at the requirement level first, because a requirement with measurable acceptance criteria tied to the failure condition gives the test something real to verify; patching the test alone would leave the abstraction in place for the next test. I'd also add a cross-document review step — a traceability walkthrough where someone who owns none of the three documents samples a few controls end-to-end and asks "does this chain actually prove the control works?" — because the root cause is that the documents were reviewed in isolation. And I'd be careful not to over-correct into requiring every requirement to be maximally detailed; the fix is targeted at safety-derived requirements, where the abstraction actually costs you evidence.

**Possible follow-ups:** How would you prevent this from recurring on the next project without adding so much process that reviews become rubber stamps? If the test engineer pushes back that rewriting the test is out of scope for the current phase, how would you prioritize?
