# medical-devices — Day 36

## Q1: How would you approach verifying that a medical device's firmware correctly handles a situation where the device's non-volatile memory becomes corrupted during a firmware update, given that the device must remain safe and functional if the update fails?

**Answer:** This is fundamentally a reliability and safety architecture question. The first principle is that firmware updates must never compromise the device's ability to boot into a known-good state. I'd start by designing the memory map with redundancy in mind — typically a dual-bank or A/B partition scheme where the active application runs from one bank while the update writes to the other. A bootloader with a valid-image check (CRC or cryptographic signature verification) would determine which bank to boot from, and if the newly written image fails validation, it falls back to the previous known-good image.

For the corruption scenario specifically, I'd verify the failure handling at several levels. First, the bootloader must detect corruption during the update process itself — if the write fails mid-transfer, the device should either retry or revert immediately. Second, I'd test what happens if corruption occurs after the update is marked "complete" but before the device reboots — the bootloader's integrity check on the next power-up should catch this. Third, I'd consider what happens if both banks become corrupted, which is unlikely but possible with certain failure modes — in that case, the device should enter a recovery mode that allows a forced reflash, and critically, it should fail safe from a clinical perspective (e.g., alarm, stop therapy delivery, or enter a defined safe state depending on the device function).

For test strategy, I'd use fault injection to simulate corruption at various points: partial writes, bit flips in the image, corrupted metadata, interrupted power during the update, and a reset mid-update. Each test case would verify that the device either completes the update successfully, reverts to the previous version, or enters a defined safe state — never an undefined or bricked state. I'd also verify that the device's clinical functionality is preserved during the update process itself, since many medical devices can't simply be taken offline.

**Possible follow-ups:** How would you handle the case where the device is in active patient use when an update is attempted? What metrics would you use to determine whether the update failure rate is acceptable?

## Q2: How would you approach designing a test strategy for verifying that a medical device's firmware correctly handles a situation where the device's non-volatile memory is full, given that the device must continue monitoring and displaying physiological data in real time?

**Answer:** The key design consideration here is that data logging is typically a non-critical function relative to real-time monitoring and alarm generation. The firmware architecture should decouple these concerns so that a full or failing storage medium never impacts the monitoring path. I'd approach this by first defining the expected behavior: the device should continue monitoring and displaying data without interruption, generate an alert or indicator that storage is full, and handle the logging failure gracefully — either by overwriting oldest data (circular logging), stopping logging while preserving existing data, or transitioning to a reduced logging mode.

For the test strategy, I'd start with unit-level tests that simulate the storage-full condition at the driver level — filling the storage to capacity, then verifying that write attempts return the appropriate error code and that the logging module handles that error without propagating it to the monitoring task. At the integration level, I'd verify that the monitoring and alarm functions continue to operate with correct timing and accuracy while the storage is full. I'd also test the user-visible behavior: the alert or indicator, and the options presented to the user (e.g., clear data, replace storage, or acknowledge and continue).

I'd also test edge cases around the transition point — what happens when the storage fills during an active write, whether there's a race condition between the "check if space available" and the actual write, and how the system behaves if the user clears data while logging is actively failing. Finally, I'd verify the behavior across power cycles — if the device is powered off and on while storage is full, it should still boot correctly, continue monitoring, and maintain the full-storage indicator. The clinical risk here is that a caregiver might not notice data isn't being logged, so the alerting behavior is as important to test as the technical handling.

**Possible follow-ups:** How would you decide between circular logging versus stopping logging when storage is full? What information would you preserve in the alert to the clinician?

## Q3: During IEC 60601-1 testing, your medical device fails the patient leakage current test under normal condition (NC) with a measurement of 120 µA on a BF-type applied part, where the limit is 100 µA. How would you approach diagnosing and resolving this?

**Answer:** A 20% margin over the limit suggests a systematic issue rather than a marginal component tolerance problem. I'd approach this systematically, starting with understanding the leakage current path. Patient leakage current flows from the applied part through the patient to earth, so I'd first identify all the paths that could contribute: capacitive coupling from mains through the power supply to the isolated side, coupling through the isolation barrier itself, leakage through protection components (like Y-capacitors), and any unintended paths through the PCB or cabling.

My first step would be to isolate the contribution of each path. I'd measure leakage with the applied part disconnected from the rest of the circuitry to establish the baseline contribution from the power supply and isolation barrier. Then I'd reconnect subsystems one at a time — the sensor front-end, the signal conditioning, the display, any communication interfaces — to identify which subsystem is contributing the excess. I'd also check whether the measurement is affected by the test setup itself, such as the measuring device (MD) configuration or the grounding arrangement.

Common culprits in my experience would be: excessive Y-capacitance across the isolation barrier, a ground plane or trace routing that brings mains-side noise too close to the patient side, or a component (like an optocoupler or isolated DC-DC converter) with higher than expected coupling capacitance. I'd also check whether the device's internal earth connection is properly bonded, since a poor earth bond can force more current through the patient path.

Once I identify the dominant contributor, the fix would depend on the root cause. If it's Y-capacitance, I might reduce the capacitance value (while ensuring EMC performance is maintained) or improve the isolation barrier design. If it's PCB layout, I'd look at increasing creepage and clearance, adding a shielding layer, or rerouting sensitive traces. If it's a specific component, I might need to select a component with lower coupling capacitance. I'd also verify the fix doesn't degrade other parameters — for example, reducing Y-capacitance might worsen radiated emissions, so I'd re-run EMC testing as part of the verification.

**Possible follow-ups:** How would you determine whether the excess leakage is capacitive or resistive in nature? What role does the measuring device (MD) configuration play in this measurement?

## Q4: How would you approach developing a design verification test plan for a medical device that must measure both temperature and pressure, where the two sensors share a common ADC and multiplexer, and the device must maintain specified accuracy for both parameters simultaneously?

**Answer:** The shared ADC and multiplexer introduces a specific risk: cross-talk between channels and the potential for one sensor's characteristics to affect the other's measurement accuracy. I'd structure the test plan around three layers: individual sensor accuracy, cross-channel interaction, and system-level performance under realistic operating conditions.

At the individual level, I'd verify each channel's accuracy independently — temperature accuracy against a calibrated reference thermometer, and pressure accuracy against a calibrated pressure source. This establishes the baseline performance of each sensor and its signal conditioning path. I'd test across the full specified range, including the extremes, and at multiple points within the range to characterize linearity.

For cross-channel interaction, I'd design specific tests to expose multiplexer-related issues. I'd test with one sensor at its maximum signal while the other is at minimum, and vice versa, to check for crosstalk. I'd also test with both sensors at mid-range to verify there's no systematic offset introduced by the multiplexer switching. A key test would be to vary one sensor's input rapidly while holding the other constant, to check for settling time issues — if the ADC samples too quickly after switching, the previous channel's residual charge could affect the reading. I'd also verify that the multiplexer switching doesn't introduce noise into the analog front-end.

At the system level, I'd test with both sensors operating simultaneously under conditions that represent clinical use — for example, temperature changing while pressure is held constant, and vice versa. I'd also test the timing behavior: how often each channel is sampled, whether the sampling rate is sufficient for the clinical application, and whether there's any data alignment issue between the two measurements. Finally, I'd include environmental testing — temperature and pressure accuracy across the device's specified operating temperature range, since the ADC reference and multiplexer performance can drift with temperature.

**Possible follow-ups:** How would you determine the minimum sampling rate for each channel given the clinical requirements? What would you do if you found that the multiplexer settling time was causing accuracy issues at the required sampling rate?

## Q5: You're leading a project where a field complaint reports that a medical device's patient-contacting silicone sensor pad is causing skin irritation in several patients. How would you approach the investigation and corrective action process?

**Answer:** This is a serious complaint that touches on patient safety, biocompatibility, and potentially the device's regulatory compliance. I'd approach it as a formal investigation following a structured root-cause analysis process, with patient safety as the immediate priority.

The first step is to assess the immediate risk. I'd gather all available information about the reported cases — the nature and severity of the irritation, how many patients were affected, whether there are common factors (like duration of contact, skin type, or specific device lots), and whether any patients required medical treatment. Based on this initial assessment, I'd determine whether the device needs to be recalled, whether use should be restricted, or whether the investigation can proceed while the device remains in use. This decision would involve the quality organization and potentially regulatory affairs, and would be documented in the complaint handling system.

For the technical investigation, I'd consider multiple hypotheses. The irritation could be caused by a material change — perhaps the silicone formulation changed, or a processing step (like a mold release agent or curing process) introduced a contaminant. It could be a design issue — perhaps the pad's geometry creates friction or pressure points, or the pad traps moisture against the skin. It could also be a use issue — perhaps cleaning agents or other substances interact with the silicone. I'd examine the manufacturing records for the affected lots, review the material certifications and any incoming inspection results, and test samples from the same lots for biocompatibility per ISO 10993. I'd also consider whether the issue is related to a change in the raw material supplier or a process change that wasn't properly qualified.

The corrective action would depend on the root cause. If it's a material issue, I'd work with the supplier to identify the change and either revert it or qualify a new material. If it's a design issue, I'd need to consider a design change, which would trigger a full design review and potentially regulatory notification. If it's a use issue, I'd update the instructions for use and potentially provide additional training. Throughout the process, I'd document everything in the complaint handling system and the design history file, and I'd work with regulatory affairs to determine whether a field safety corrective action (FSCA) or regulatory notification is required.

**Possible follow-ups:** How would you determine whether this requires a field safety corrective action (FSCA) versus a less urgent corrective action? What information would you need from the clinical sites to support your investigation?
