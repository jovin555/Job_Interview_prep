# medical-devices — Day 20

## Q1: How would you approach designing a test strategy for verifying that a medical device's firmware correctly handles a sensor that intermittently provides valid but erroneous readings (e.g., a pressure sensor that occasionally reports a spike that is within the valid range but physiologically impossible)?

**Answer:** I'd approach this as a combination of fault injection, data validation logic verification, and clinical relevance assessment. First, I'd work with the clinical team to define what constitutes a "physiologically plausible" reading — for example, a pressure change rate that exceeds a certain threshold per sample interval. This becomes the basis for the firmware's plausibility checks. For testing, I'd use a signal generator or a hardware-in-the-loop setup to inject realistic sensor waveforms with superimposed artifacts — spikes, dropouts, and step changes — that are within the ADC's valid range but violate physiological constraints. The test strategy would verify three things: that the firmware detects and flags the artifact, that it doesn't trigger a false alarm or inappropriate therapy action, and that it recovers gracefully once the sensor returns to normal. I'd also test edge cases like a sustained series of artifacts that might indicate a failing sensor rather than a transient event. The test plan should include both automated scripted injection for repeatability and some randomized artifact generation to probe unexpected interactions with the filtering and alarm logic. Finally, I'd review the test results with the clinical team to confirm that the firmware's response — whether it's ignoring the sample, holding the last valid value, or generating a low-priority technical alert — is clinically appropriate.

**Possible follow-ups:** How would you decide between ignoring an artifact versus generating a technical alarm? What if the artifact pattern is indistinguishable from a real physiological event?

## Q2: You're leading a project where the firmware team wants to implement an over-the-air (OTA) firmware update capability for a medical device used in home environments. The hardware team has concerns about security and the risk of bricking the device. How would you approach this?

**Answer:** I'd frame this as a risk-benefit analysis under ISO 14971, since OTA updates introduce new hazards — unauthorized access, corrupted firmware, interrupted updates — but also mitigate existing risks like devices operating with known software defects. First, I'd establish the security requirements: authenticated and encrypted update packages, signed firmware images with a verified chain of trust, and a secure boot process that refuses to run unsigned code. For the update process itself, I'd design it with a dual-bank or A/B partition scheme so the device always has a known-good firmware image to fall back to if the new image fails to validate or boot. The update would be staged: download and verify the complete image, store it in the inactive partition, then atomically switch on the next reboot. If the new image fails to start or fails its self-test, the bootloader rolls back automatically. I'd also consider the clinical context — for a home-use device, the update should only install when the device is not actively monitoring a patient, or it should be designed to resume monitoring immediately after reboot. From a regulatory perspective, I'd assess whether the update capability itself requires a new submission or a supplement, and I'd document the cybersecurity risk controls in the risk management file. The test strategy would include simulated interrupted downloads, corrupted images, power loss during the update, and rollback verification.

**Possible follow-ups:** How would you handle a situation where a field device fails to update and is stuck in a boot loop? What cybersecurity standards or frameworks would you reference for medical device software?

## Q3: How would you approach verifying that a medical device's alarm system correctly handles a situation where the device is in a "suspended" or "paused" state (e.g., during patient transport or a temporary procedure) and a critical alarm condition occurs?

**Answer:** This is fundamentally a usability and risk management question. The key is to define the intended behavior clearly in the requirements — what does "suspended" mean clinically, and what alarms should still be presented? I'd start by reviewing the alarm philosophy with the clinical team: during transport, for example, the device may be disconnected from the main display but still monitoring. The verification strategy would test each alarm priority level in each device state. For a high-priority alarm (e.g., apnea or loss of pulse), the device should probably override the suspended state and alert immediately, possibly through a local audible alarm. For a medium-priority alarm, the device might queue it and present it when monitoring resumes, but with a clear indication that an alarm condition occurred during the suspended period. I'd also test the transition edges — what happens if an alarm condition starts just before suspension, or just after resumption? The test plan would include state-machine testing where I systematically exercise all valid state transitions with alarms occurring at each transition point. I'd also verify that the suspended state itself is clearly indicated on the display and that the duration of suspension is logged. Finally, I'd review the alarm presentation against IEC 60601-1-8 requirements for alarm signal prioritization and the usability engineering file to ensure the behavior is intuitive to clinicians.

**Possible follow-ups:** How would you handle a situation where a clinician wants to silence an alarm for a specific parameter during a procedure? How would you verify that the alarm system's behavior during suspension is consistent across all physiological parameters?

## Q4: During a design review for a medical device that uses an optical sensor to measure blood oxygen saturation (SpO2), the firmware engineer proposes using an adaptive filtering algorithm to reduce motion artifacts. The algorithm is complex and difficult to verify deterministically. How would you approach evaluating this proposal?

**Answer:** I'd approach this by separating the algorithm's clinical performance from its software verification challenges. First, I'd ask the firmware engineer to clarify what the adaptive filter is adapting to — is it adapting to the motion artifact frequency, to the patient's physiology, or to signal quality? The answer determines how we can test it. For a medical device, I'd want to understand whether the algorithm's behavior is deterministic given the same input, or whether it has state that depends on prior inputs in ways that are hard to reproduce. If it's deterministic, we can build a test corpus of recorded physiological signals with known motion artifacts — ideally from clinical data or a validated simulator — and verify that the output meets accuracy specifications. If it's non-deterministic or has long-term state, I'd ask for a simplified version or a way to reset the algorithm state for testing. I'd also evaluate the algorithm's failure modes: what happens if it converges on the wrong frequency and filters out the actual pulse signal? Is there a plausibility check on the output? From a regulatory perspective, I'd consider whether the algorithm falls under IEC 62304 Class C, which would require more rigorous verification, and whether we need to characterize its performance across a patient population. I'd propose a phased approach: first, validate the algorithm offline against recorded data to demonstrate it meets accuracy requirements; second, implement it with test hooks that allow deterministic input injection; and third, run a structured test matrix covering motion frequencies, amplitudes, and patient physiologies. If the algorithm can't be verified to the required confidence level, I'd recommend a simpler, more deterministic approach, even if it means accepting some motion artifact.

**Possible follow-ups:** How would you handle a situation where the algorithm performs well on recorded data but fails during live testing? What level of documentation would you require for the algorithm's design and verification?

## Q5: You're leading a project where a field complaint reports that a medical device's battery fails prematurely in a subset of devices used in a home environment. The battery is specified for 500 charge cycles, but some users report needing to recharge after only 6 months of daily use. How would you approach the investigation and corrective action process?

**Answer:** I'd structure this as a formal complaint investigation following a root-cause analysis methodology, likely an 8D or similar process, since it involves both field performance and potential design issues. First, I'd gather data: how many complaints, what's the failure pattern, and are there common factors — specific battery lot, charging behavior, environmental conditions, or firmware version? I'd also pull the device logs if available to see charge/discharge patterns and whether the battery management system recorded any anomalies. The investigation would branch into several hypotheses: the battery cells themselves may be defective or counterfeit; the charging algorithm may be overcharging or undercharging in certain conditions; the device's power consumption may be higher than expected, causing more frequent charge cycles; or the battery management system's state-of-charge estimation may be inaccurate, causing premature "low battery" indications. I'd work with the supplier to review the battery's manufacturing records and test samples from the affected lot. I'd also compare the actual usage patterns in the field against the design assumptions — for example, if the device is used for 8 hours daily and recharged nightly, that's roughly 365 cycles per year, which exceeds the 500-cycle specification over 6 months only if the battery is also being cycled during the day. The corrective action would depend on the root cause: if it's a charging algorithm issue, a firmware update might suffice; if it's a battery cell quality issue, we'd need a supplier corrective action and possibly a recall of affected units; if it's a usage pattern mismatch, we might need to update the labeling or redesign the battery capacity. Throughout the process, I'd document everything in the complaint handling system and assess whether this constitutes a reportable event under the relevant regulations. I'd also review the risk management file to see if premature battery failure was a identified hazard and whether the existing risk controls were adequate.

**Possible follow-ups:** How would you determine whether this is a reportable event to the regulatory authority? How would you communicate with affected users while the investigation is ongoing? What if the investigation reveals that the battery failure is caused by users leaving the device plugged in continuously, which the design didn't anticipate?
