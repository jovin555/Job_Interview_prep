# medical-devices — Day 33

## Q1: How would you approach designing a test strategy for verifying that a medical device's firmware correctly handles a sensor that intermittently provides valid but erroneous readings — for example, a pressure sensor that occasionally reports a spike that is within the valid range but physiologically impossible?

**Answer:** I'd start by distinguishing between two failure modes: sensor readings that are out of the valid range (which are relatively easy to detect with bounds checking) and readings that are within range but physiologically implausible (which require more sophisticated detection). For the latter, I'd look at rate-of-change limits — a pressure reading that jumps by a physiologically impossible amount between consecutive samples is a strong indicator of an artifact. The test strategy would have several layers. First, unit-level tests that inject synthetic sensor data into the firmware's signal-processing pipeline, including pre-recorded artifact waveforms and programmatically generated spikes, to verify the detection algorithm behaves correctly. Second, integration tests that simulate the full data path from sensor driver through filtering to alarm generation, verifying that a detected artifact doesn't trigger a false alarm and that the device continues monitoring normally. Third, I'd include fault-injection tests at the driver level — for example, corrupting the communication bus between sensor and microcontroller to verify the firmware handles CRC errors or invalid frames gracefully. A key consideration is what the device should do when it detects an artifact: it shouldn't silently discard the data, because that could mask a real physiological event. Instead, it should flag the reading as suspect, log it for later review, and potentially trigger a "signal quality" indicator to the clinician. I'd also want to verify the detection algorithm's sensitivity and specificity using recorded clinical data if available, or at least a corpus of annotated artifact examples, to ensure we're not over-filtering real events.

**Possible follow-ups:** How would you determine the rate-of-change threshold for a specific physiological parameter? What would you do if the artifact detection algorithm itself introduces latency that delays detection of a real clinical event?

## Q2: During a design review for a medical device that uses a wireless link to transmit physiological data to a display unit, the firmware engineer proposes using an unacknowledged broadcast protocol to simplify the design, while the clinical team requires that data loss be detectable and that the display unit indicate when data is stale. How would you approach this trade-off?

**Answer:** The core tension here is between design simplicity and clinical safety requirements. An unacknowledged broadcast protocol is attractive because it avoids the complexity of connection management, retransmission logic, and buffering — but it means the transmitter has no way of knowing whether the display unit actually received the data. The clinical requirement isn't necessarily that no data is ever lost; it's that data loss is *detectable* and that the display indicates staleness. Those are achievable even with a broadcast protocol. I'd approach this by first clarifying the clinical use case: how critical is real-time data continuity? If the device is monitoring a patient where a gap in data could delay clinical intervention, then we need at least some form of acknowledgment or a mechanism to detect gaps. A practical middle ground is to use a broadcast protocol with sequence numbers embedded in each packet. The display unit can then detect missing sequence numbers and immediately indicate "data gap" or "signal lost" to the clinician. This gives us the simplicity of broadcast — no connection setup, no retransmission — while meeting the clinical requirement of detectable data loss. The display unit would also track the time since the last valid packet and display a staleness indicator (e.g., "data age: 5 seconds") that becomes more prominent as the gap grows. If the clinical team requires guaranteed delivery — for example, if the data is used for alarm generation — then we'd need to move to an acknowledged protocol with retransmission, accepting the added complexity. I'd also consider a hybrid approach: broadcast for continuous waveform data where occasional loss is acceptable, with a separate acknowledged channel for alarm events and critical status changes. The key is to have the clinical team explicitly define what "detectable data loss" means in terms of maximum acceptable gap duration and what the display must show during a gap.

**Possible follow-ups:** How would you verify that the staleness indicator meets the usability requirements of IEC 60601-1-6? What if the wireless link is also used for alarm delivery — would that change your approach?

## Q3: How would you approach developing a design verification test plan for a medical device that must measure both temperature and pressure, where the two sensors share a common ADC and multiplexer, and the device must maintain specified accuracy for both parameters simultaneously?

**Answer:** The shared ADC and multiplexer introduces a coupling risk: the measurement of one parameter could be affected by the other, either through settling time issues, crosstalk, or multiplexer switching transients. I'd structure the test plan around three levels. First, I'd verify each sensor channel independently — temperature accuracy with the pressure channel disconnected or held at a fixed value, and vice versa — to establish baseline accuracy for each parameter. Second, I'd test simultaneous operation, where both sensors are active and the multiplexer is switching between them, to verify that the specified accuracy is maintained for both parameters when measured in the same acquisition cycle. This is where settling time becomes critical: if the ADC samples the pressure channel immediately after switching from the temperature channel, residual charge on the sample-and-hold capacitor could cause an error. The test plan should include worst-case scenarios, such as the largest expected temperature swing combined with the smallest expected pressure change, to stress the settling behavior. Third, I'd include cross-talk testing: applying a known stimulus to one sensor (e.g., a rapid temperature change) while measuring the other sensor's output to verify there's no measurable coupling through the shared signal path. For the test equipment, I'd use calibrated reference sensors or precision sources — a temperature bath with a reference thermometer for temperature, and a pressure calibrator for pressure. The test plan should also include testing across the device's specified operating temperature range, since ADC offset and gain errors can drift with temperature, and the multiplexer's on-resistance can vary. I'd also want to verify the firmware's channel sequencing and settling delay configuration — if the firmware doesn't allow sufficient settling time between channel switches, no amount of hardware testing will pass. So the test plan should include a review of the firmware configuration and possibly a test that intentionally stresses the settling timing to confirm the margin.

**Possible follow-ups:** How would you determine the required settling time between channel switches? What failure modes would you specifically look for in the cross-talk testing?

## Q4: You're leading a project where a field complaint reports that a medical device's rechargeable battery is swelling after 6-12 months of use in a hospital setting. The device is used for continuous patient monitoring and the battery is not user-replaceable. How would you approach the investigation and corrective action process?

**Answer:** Battery swelling is a serious safety issue — it can indicate internal short circuits, overcharging, or thermal runaway risk, and in a patient-monitoring device it also means the device may fail unexpectedly. I'd structure the investigation in parallel tracks. First, safety: I'd immediately assess whether there's an imminent risk to patients or staff. If the swelling creates a risk of enclosure rupture or fire, I'd recommend a field safety notice or recall depending on the severity and the regulatory requirements. This decision would involve the quality and regulatory teams, and we'd follow the FSCA process if warranted. Second, technical investigation: I'd collect the affected devices and perform a systematic analysis. This would include visual inspection, measuring the battery voltage and internal resistance, X-ray or CT imaging to look for internal structural changes, and disassembly in a controlled environment to examine the cell construction. I'd also review the charge/discharge history if the device logs battery data — looking for patterns like over-discharge events, repeated deep discharges, or charging at elevated temperatures. Third, I'd look at the charging algorithm and power management design. Common causes of swelling include overcharging (voltage too high or charging too long), charging at temperatures outside the cell's specification, or a defective batch of cells. I'd review the charge profile against the battery manufacturer's specifications, check the firmware's charge termination logic, and verify the temperature sensing during charging. I'd also examine whether the device's continuous monitoring load creates a pattern of shallow charge/discharge cycles that could stress the cell. Fourth, I'd work with the battery supplier to determine if this is a cell manufacturing issue — reviewing their production records, lot traceability, and any known issues with that cell model. The corrective action would depend on the root cause: it could be a firmware fix to the charge algorithm, a hardware change to improve thermal management, a supplier change, or a combination. I'd also update the risk management file to reflect the newly identified hazard and ensure the post-market surveillance plan captures this failure mode going forward.

**Possible follow-ups:** How would you determine whether a field safety corrective action (FSCA) is required versus a less urgent corrective action? What battery data would you want the device to log to aid future investigations?

## Q5: How would you approach verifying that a medical device's firmware meets IEC 62304 requirements for a Class C software safety classification?

**Answer:** Class C is the highest software safety classification under IEC 62304 — it applies when a software failure could contribute to a hazardous situation that could result in death or serious injury. The verification approach needs to be comprehensive and traceable. I'd start by confirming the classification is correct through a documented rationale that ties the software's failure modes to the device's hazard analysis. If the software can cause or fail to mitigate a serious hazard, Class C is appropriate. For verification, I'd structure the effort around the standard's key requirements. First, the software development plan must be detailed and followed — it should define the development lifecycle, the verification activities, and the acceptance criteria. Second, software requirements must be traceable to design inputs and to test cases — I'd maintain a traceability matrix that links each requirement to its verification method (inspection, analysis, or test) and to the specific test case or review record. Third, the architectural design must be documented, including how safety-critical functions are isolated from non-critical functions. Verification here would include design reviews to confirm the architecture adequately partitions safety-related software. Fourth, detailed design and unit implementation must be verified — this includes code reviews, static analysis, and unit testing. For Class C, the standard requires more rigorous unit verification, including statement coverage and branch coverage, and I'd want to measure and document coverage. Fifth, integration and system testing must verify that the software meets its requirements in the context of the complete device. This includes testing under fault conditions — for example, sensor failures, communication errors, and power interruptions — to verify the software responds safely. I'd also include stress testing and boundary testing. Throughout, I'd maintain a software defect tracking system and document the resolution of all defects, with a clear rationale for any deferred fixes. Finally, the software release criteria must be defined and met — this includes confirming that all verification activities are complete, all critical defects are resolved, and the residual risk from software failures is acceptable per the risk management file. The key principle is that verification isn't just about testing — it's about demonstrating through objective evidence that the software is safe, reliable, and traceable to its requirements.

**Possible follow-ups:** How would you determine the appropriate level of unit test coverage for Class C software? What's the difference between verification and validation in the context of IEC 62304?
