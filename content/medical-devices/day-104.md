# medical-devices — Day 104

## Q1: How would you approach designing the alarm signal chain for a device that has both audible and visual alarms, so that a single component failure cannot silently disable both alarm pathways?

**Answer:** The core principle is independence of the alarm signal paths, driven by the risk analysis rather than by convenience. I'd start by treating the alarm subsystem as its own safety-related function: identify in the risk file what happens if the audible path fails, if the visual path fails, and if the shared driver between them fails, and let that drive the architecture.

Practically, I'd avoid a single microcontroller pin or a single driver stage feeding both transducers. The audible and visual alarms would be driven from separate output stages, ideally with separate enable logic, so that a shorted driver or a stuck output on one path doesn't take the other down. Where the device has a safety-critical alarm condition, I'd consider a hardware-level alarm path that can assert independently of the main firmware loop — for example, a watchdog or supervisory circuit that can force the audible alarm if the main processor stops servicing it. That gives a defense against firmware hangs, not just component failures.

I'd also think about the failure modes that are easy to miss: a piezo driver that fails open (silent but the firmware thinks it's driving), an LED that fails short (visual alarm appears permanently on, masking a new alarm). Those argue for some form of feedback or monitoring — sensing the audible driver current, or checking LED forward voltage — so the device can detect a failed alarm pathway and raise a technical alarm. The exact depth of monitoring should be proportionate to the alarm's priority and the harm if it's missed.

Finally, I'd verify the independence claim with fault injection: deliberately disable each path in turn and confirm the other still functions and that the device reports the failure appropriately. The design isn't done until the independence is demonstrated, not just asserted in a block diagram.

**Possible follow-ups:** How would you decide whether hardware-level alarm independence is warranted versus relying on firmware monitoring? What would you do if the risk analysis showed that a shared power rail to both alarm drivers was an unacceptable common-cause failure?

## Q2: How would you approach deciding whether a device's software needs to be classified as Class B or Class C under IEC 62304, and how would you handle a situation where the hardware and software leads disagree on the classification?

**Answer:** The classification follows from the risk analysis, not from how complex or how "important" the software feels. The question IEC 62304 asks is: could a software failure contribute to a hazardous situation that results in serious injury or death? If yes, Class C. If the hazardous situation is possible but the resulting harm is non-serious, Class B. If no hazardous situation can arise from software failure, Class A.

So my approach is to work backwards from the hazard analysis. For each hazardous situation in the risk file, I'd ask whether software could cause or contribute to it, and whether any risk controls that prevent that harm are implemented in software. If a software-implemented risk control is the thing standing between a failure and serious harm, that pushes toward Class C. If the harm is bounded — say, a monitoring function where loss of the display leads to a delayed response but not immediate serious injury, and there are independent hardware or clinical mitigations — Class B may be defensible. The classification should be documented with the reasoning, because auditors will ask for it.

On disagreement: this is exactly the kind of question that shouldn't be settled by seniority. I'd bring both leads back to the hazard analysis and ask each to point to the specific hazardous situations and risk controls that justify their position. Often the disagreement dissolves once you're both looking at the same hazard table — one person may be thinking of a failure mode the other hasn't considered, or one may be over-classifying out of caution without a concrete harm pathway. If it genuinely remains ambiguous, I'd err toward the higher classification, because the cost of over-classifying is documentation and process overhead, while the cost of under-classifying is a safety and regulatory exposure. I'd also loop in quality/regulatory early so the decision is owned collectively rather than imposed.

**Possible follow-ups:** How would segregation of software items affect the classification — could part of the system be Class C and part Class B? What evidence would you expect to see in the software development file to support a Class B claim?

## Q3: How would you approach designing the isolation barrier for a patient-connected front-end where the barrier must pass a low-level analog signal and a bidirectional digital control link, while keeping the analog signal clean enough to meet the accuracy specification?

**Answer:** The first decision is the barrier technology, and it's driven by the required isolation level and the signal types. For a patient-connected applied part needing two means of patient protection from mains, I'd be looking at reinforced isolation components rated for the working voltage and the transient/defibrillation withstand the standard demands. The analog and digital paths usually want different solutions: a digital isolator for the control link, and either an isolated amplifier or a modulator-based approach for the analog signal.

For the analog path, the key trade-off is where you digitize. If you can put the ADC on the patient side and send digital data across the barrier, you avoid transporting a fragile low-level analog signal across a noisy boundary — that's often the cleanest answer for accuracy. If the architecture requires the analog signal to cross, an isolated amplifier with good common-mode transient immunity is the tool, but you have to watch its gain error, offset drift, and nonlinearity against your accuracy budget, and its output still needs clean filtering and a well-referenced ADC on the isolated side.

The digital control link is more forgiving but not free: I'd choose an isolator with adequate data rate and, importantly, check its behavior under the transient conditions the standard imposes — you don't want the control link glitching during a defibrillation discharge and commanding the front-end into a bad state. I'd also think about the barrier's power: an isolated DC-DC to feed the patient-side electronics, with its own emissions and immunity characteristics, since that converter is often the dominant noise source sitting right at the barrier.

Layout matters as much as part selection. Creepage and clearance across the barrier have to be maintained physically, which means a slot or sufficient spacing under the isolators, no copper crossing the barrier, and the isolated ground plane kept genuinely separate. I'd verify the whole thing with the accuracy test at the system level and with the dielectric and leakage tests at the barrier level — the two verification streams have to both pass, and sometimes a layout tweak that helps one hurts the other.

**Possible follow-ups:** How would you handle the isolated DC-DC converter's switching noise coupling into the analog front-end? What would you do if the isolated amplifier's drift over temperature ate too much of your accuracy budget?

## Q4: How would you approach structuring the design transfer from R&D to manufacturing for a medical device, so that the production team can build and test it repeatably without the design team being in the loop for every unit?

**Answer:** Design transfer is where a lot of medical device problems surface late, so I'd treat it as a deliberate phase with its own deliverables rather than a handoff meeting. The goal is that manufacturing has everything it needs to build, test, and release the device to the same standard the design was verified against.

The core deliverables are the production documentation set: assembly drawings and work instructions, the bill of materials with approved manufacturer parts and approved alternates, the test specifications with pass/fail limits and the rationale for those limits, and the acceptance criteria for incoming inspection of critical components. For a medical device, I'd pay particular attention to the test coverage — the production test has to catch the failure modes that matter for safety and for the specified performance, not just "does it power on." That means defining what's measured, at what accuracy, with what reference equipment, and how often the test equipment itself is calibrated.

I'd also make sure the design's critical characteristics are explicitly flagged for manufacturing: the isolation spacing on the PCB, the conformal coating on high-voltage areas, the torque on patient-contact connectors, the calibration steps for sensors. Those are the things where a well-meaning process change on the floor could quietly compromise a safety margin, so they need to be called out as controlled characteristics, not buried in a drawing.

A practical step that pays off is building the first production units with the design team present, or at least reviewing the first-article inspection results together. That's where you find the ambiguities in the work instructions and the test limits that are too tight or too loose. I'd also want a feedback path so manufacturing can raise issues back to design without them getting lost — a formal deviation or change-request route, not a hallway conversation.

Finally, the transfer has to be documented as complete: the design history file should show that production-equivalent units were built and tested, and that the manufacturing process is capable of meeting the specification. That's the evidence a regulator or auditor will look for.

**Possible follow-ups:** How would you set production test limits so they're tight enough to catch real defects but not so tight they cause false failures? What would you do if first-article inspection revealed a unit that passed design verification but failed a production test?

## Q5: How would you approach a situation where, during system integration testing, a device intermittently fails in a way that could plausibly be caused by either a firmware timing issue or a hardware signal-integrity problem, and the two discipline leads are each convinced it's the other's area?

**Answer:** The first thing I'd do is resist the pull to adjudicate between the two theories on the basis of who's more senior or more persuasive. Intermittent failures that sit on a hardware/firmware boundary are almost always best resolved by narrowing the failure conditions empirically, and that work is more productive than debate.

I'd start by characterizing the failure: how often does it occur, under what conditions, and is it reproducible on demand or only statistically? If it's only statistical, the first priority is to increase the observation rate — run the test in a loop, log everything, and get enough occurrences that any change in behavior is measurable rather than anecdotal. I'd want correlated logs from both sides: firmware timestamps and state transitions alongside hardware measurements like supply rails, clock, and the relevant signal lines, captured on the same time base if possible. That correlation is usually what breaks the tie.

Then I'd design experiments that discriminate between the hypotheses rather than confirm them. If firmware timing is suspected, can we perturb the timing deliberately — add delay, change task priority, stress the scheduler — and see if the failure rate moves? If signal integrity is suspected, can we perturb the hardware — swap cables, add termination, change the grounding, vary temperature or supply voltage — and see if the rate moves? A well-chosen experiment that changes one variable and moves the failure rate is worth more than a week of argument.

I'd also set up the investigation so both leads own a piece of it rather than defending a position. Give the firmware lead the task of proving or disproving the timing hypothesis with data, and the hardware lead the same for signal integrity, and agree in advance what evidence would change each person's mind. That reframes it from "who's right" to "what does the data say," which is a much easier room to manage.

Throughout, I'd keep the risk file and the test record updated, because if the failure turns out to be safety-relevant, the investigation and its conclusion need to be traceable. And I'd be prepared for the answer to be "both" — a marginal timing margin that only fails when a signal-integrity issue eats into it. Those are the cases where the two disciplines have to fix their halves together, and framing the investigation that way from the start makes that outcome easier to reach.

**Possible follow-ups:** What specific measurements would you capture to correlate firmware state with hardware behavior on a common time base? How would you decide when you've gathered enough evidence to close the investigation and implement a fix?
