# medical-devices — Day 100

## Q1: How would you approach designing a test strategy to verify that a device's firmware correctly handles a sensor that intermittently produces readings within the valid range but physiologically implausible — for example, a pressure spike that is numerically possible but inconsistent with the patient's condition?

**Answer:** The key distinction here is between *range checking* and *plausibility checking*. A value can be inside the sensor's valid output range and still be physiologically impossible, so the test strategy has to exercise the plausibility layer specifically, not just the range layer.

I'd start by defining the plausibility model explicitly, because you can't test what you haven't specified. That usually means a combination of: rate-of-change limits (a pressure can't jump by a large amount in one sample interval given the physics of the system), cross-parameter consistency (a flow spike that isn't accompanied by any corresponding pressure change is suspect), and persistence rules (a single outlier sample versus a sustained shift should be handled differently). These rules should be written as testable requirements with explicit thresholds and time windows, derived from the physiology and the sensor's own noise characteristics — not picked arbitrarily.

Then I'd build the test strategy in layers. At unit level, feed the plausibility filter synthetic sequences: single-sample spikes, multi-sample ramps, step changes, slow drifts, and values that sit just inside and just outside each threshold. At integration level, inject these through the real sensor interface or a hardware-in-the-loop fixture so the full signal chain — analog front-end, ADC, filtering, plausibility logic, alarm logic — is exercised together. At system level, verify the *response* to a detected implausible reading: does the device flag it, suppress it, hold the last good value, or alarm? That behavior needs to be specified and verified, because silently discarding data is itself a design decision with clinical consequences.

I'd also want to verify the negative case — that legitimate fast transients (a real cough, a real patient movement) are *not* rejected. A plausibility filter that's too aggressive is a safety problem in its own right. So the test set needs physiologically realistic "true positive" signals alongside the injected artifacts, ideally drawn from recorded clinical waveforms rather than synthesized.

Finally, I'd make the injection repeatable and automated so it can run as regression on every firmware change, and I'd document the coverage — which rules were exercised, with what inputs, and what the expected versus actual response was — so it feeds directly into the verification traceability.

**Possible follow-ups:** How would you decide the thresholds for the rate-of-change rule without either missing real events or rejecting valid ones? / If the plausibility filter suppresses a reading, what should the device display, and how would you verify that behavior?

## Q2: How would you approach determining which IEC 60601-2 particular standards apply to a device that combines two clinical functions — for example, a device that both monitors a physiological parameter and delivers a therapy — and how would you resolve conflicts between the general standard and the particular standards?

**Answer:** I'd start from the device's *intended use and clinical function*, not from its marketing category or its closest competitor's classification. The particular standards in the 60601-2 series are organized around clinical function — monitoring, infusion, respiratory, therapeutic devices, and so on — so a combination device can legitimately fall under more than one. The first step is to enumerate every clinical function the device performs and map each one to a candidate particular standard, then confirm that mapping against the scope clause of each standard rather than relying on the title.

The scope clause is where the real work is. Each particular standard states what it covers and, importantly, what it excludes or defers to another standard. For a combination device, I'd build a matrix: functions down one axis, candidate standards across the other, with a note for each cell on whether the standard applies, partially applies, or is excluded. That matrix becomes the basis for a conversation with the regulatory/quality function and, if there's genuine ambiguity, a documented rationale for the interpretation chosen — because a reviewer will ask why a given standard was or wasn't applied.

On conflicts: the general standard (60601-1) sets the baseline, and a particular standard is generally allowed to *add to or modify* the general requirements for that device type — it doesn't usually override them silently. Where a particular standard explicitly replaces a clause, that replacement governs for that device. Where two particular standards both apply and appear to conflict, I'd look for whether one is more specific to the function in question, check the collateral standards (the 60601-1-x series, which cover things like EMC, usability, and alarms across device types), and treat the most specific applicable requirement as governing while documenting the reasoning. If the conflict is material to safety or to test outcomes, that's a conversation to have early with the test lab and the regulatory body rather than resolving it unilaterally late in the project.

The practical point is to do this mapping at the requirements stage, not at test time. Discovering a second applicable particular standard after the design is frozen is expensive.

**Possible follow-ups:** How would you handle a case where a particular standard's test method isn't feasible for your device's form factor? / What would you do if the test lab and your team disagreed on whether a particular standard applies?

## Q3: How would you approach structuring a risk management file so that it stays useful and auditable throughout a project, rather than becoming a document assembled at the end?

**Answer:** The failure mode I'd design against is the risk file that gets written retrospectively to match a design that's already done. That file is auditable on paper but useless as an engineering tool, and it tends to fall apart under review because the traceability is reconstructed rather than real.

The structural approach I'd take is to make the risk management file a *living* set of linked artifacts rather than a single document. At the center is the hazard analysis — a structured list of foreseeable hazards, the hazardous situations that could lead to them, and the associated harms, organized by the device's functions and by its lifecycle (use, cleaning, storage, disposal, failure modes). Each hazard links forward to risk controls, and each risk control links to the design element that implements it and the verification evidence that confirms it's effective. That linkage is what makes the file auditable: for any hazard, you can walk to the control and to the proof.

To keep it maintainable, I'd tie it to the design process rather than to a separate schedule. Risk review becomes a standing agenda item at each design review, so new hazards identified during design are captured when they're found, not reconstructed later. Changes to the design trigger a review of the affected hazard entries — a design change that removes a component, for example, may invalidate a risk control or introduce a new failure mode. The risk file and the DHF should reference each other rather than duplicate each other; the risk file owns the hazard/control/verification logic, and the DHF owns the design inputs, outputs, and verification records.

I'd also make the residual risk evaluation explicit and traceable to the risk acceptability criteria defined at the start of the project. Those criteria should be set before the analysis, not adjusted to fit the results. And I'd keep a clear record of the *decisions* — why a particular risk control was chosen over an alternative, why a residual risk was judged acceptable — because that reasoning is what a reviewer is actually assessing.

Practically, this means a tool or at least a structured spreadsheet with stable IDs and cross-references, version-controlled alongside the design. The discipline of stable IDs and forward/backward links is what makes the difference between a file that survives an audit and one that has to be rebuilt.

**Possible follow-ups:** How would you handle a hazard that's identified late, after the design is largely frozen? / What's the relationship between the risk management file and the usability engineering file, and where do they overlap?

## Q4: How would you approach selecting materials for a patient-contacting sensor housing that must meet both biocompatibility (ISO 10993) and mechanical durability requirements?

**Answer:** I'd treat this as a two-sided constraint problem from the start, because the material that's easiest to justify biologically is often not the one that survives the mechanical and cleaning environment, and vice versa.

On the biocompatibility side, the first question is the *nature and duration of patient contact* — surface contact versus mucosal versus breached surface, and the contact duration category — because that determines which ISO 10993 parts and which test endpoints are relevant. A short-term intact-skin contact housing has a very different test burden from a prolonged mucosal contact. I'd also want to know whether the housing is a single material or an assembly, because adhesives, coatings, and secondary processes (mold release agents, sterilization) can introduce leachables that the base resin doesn't have. The material selection has to account for the *finished, processed, sterilized* article, not the resin datasheet.

On the mechanical side, I'd define the durability requirements concretely: expected drop/impact, insertion and removal cycles if it's a connectorized sensor, resistance to the cleaning and disinfection agents it will actually see in use, and the temperature range over the service life. Chemical compatibility with cleaning agents is a common failure point — a material can be mechanically fine and still craze or degrade after repeated exposure to a disinfectant.

The practical approach is to shortlist candidate materials that have a documented biocompatibility history for the relevant contact category — using materials with existing ISO 10993 data and a known supply chain reduces the testing burden and the risk of a late surprise — then verify the mechanical and chemical requirements against that shortlist, and only then commit to testing. I'd also involve the contract manufacturer early, because moldability, dimensional stability, and process parameters can eliminate a material that looked good on paper.

I'd keep the material and its test evidence as a controlled item in the design history, with the specific grade and supplier identified, because a material substitution later — even a "equivalent" grade — can invalidate the biocompatibility justification.

**Possible follow-ups:** How would you handle a supplier changing the formulation or grade of a material you'd already qualified? / What would you do if the mechanically best material had no biocompatibility history for the required contact category?

## Q5: You're the lead engineer on a project where the clinical team has requested a usability change late in development that would require a hardware revision and push the regulatory submission out by several months. How would you evaluate and respond to the request?

**Answer:** The first thing I'd do is separate the *clinical need* from the *proposed solution*. The clinical team has identified a real problem — that's valuable and shouldn't be dismissed — but the specific change they've proposed may not be the only way to address it, and it may not be the highest-value use of the remaining schedule.

So I'd start by understanding the problem behind the request: what task is failing, for which users, under what conditions, and what's the clinical consequence of the current design? That reframes the conversation from "yes or no to this change" to "how do we address this need." Sometimes the underlying need can be met with a firmware change, a labeling or training change, or a smaller mechanical modification that doesn't require a full hardware revision. Sometimes it genuinely requires the hardware change, and then the question becomes one of sequencing.

I'd then assess the request against the risk and regulatory picture. Is the current design actually deficient against the usability engineering requirements, or is this an enhancement? That distinction matters enormously: a genuine usability deficiency that could contribute to use error is a safety issue and has to be addressed, whereas an enhancement is a scope decision. I'd want the human factors/usability engineering input on that, and I'd document the assessment either way.

If it's a real deficiency, the schedule impact has to be confronted honestly rather than absorbed silently. I'd bring the trade-off to the project leadership with options: delay the submission and include the change; submit as-is with the change as a planned post-market update, if the risk assessment supports that; or find a lower-cost mitigation that addresses the use error without the full hardware revision. Each option has a risk and a cost, and the decision belongs with the people who own the overall risk — not with engineering alone.

If it's an enhancement, I'd say so clearly and propose capturing it for the next revision, with the clinical rationale documented so it isn't lost. What I'd avoid is either unilaterally refusing the request or quietly accepting a schedule slip without the trade-off being visible to the people accountable for it.

**Possible follow-ups:** How would you distinguish a usability deficiency from an enhancement in a way that would hold up to a regulator? / If leadership decided to submit as-is and address the change post-market, what would you want documented to support that decision?
