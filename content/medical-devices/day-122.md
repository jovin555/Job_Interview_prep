# medical-devices — Day 122

## Q1: How would you approach designing a firmware watchdog strategy for a medical device that must detect a hung safety-critical monitoring task without causing nuisance resets during normal heavy processing?

**Answer:** The key distinction is between a simple watchdog that only proves "the CPU is executing something" and a supervisory scheme that proves "the safety-critical task is actually making progress." A plain hardware watchdog kicked from a low-priority housekeeping loop will happily stay fed while the monitoring task is starved or deadlocked, so it provides almost no real protection. I'd design a layered scheme: a hardware watchdog as the last line of defense, but fed only by a supervisory task that checks liveness of the critical task through a shared "heartbeat" or progress counter that the critical task must update at a defined cadence. The supervisory task verifies the counter advanced within a bounded window and only then kicks the watchdog. This turns the watchdog into a proof of end-to-end progress rather than mere scheduler activity.

The nuisance-reset problem is the hard part. If the critical task legitimately takes longer under some conditions — a long ADC conversion sequence, a blocking bus transaction, a burst of processing — a naive fixed timeout will trip. So I'd set the timeout from measured worst-case execution time with margin, and I'd make the progress check tolerant of bounded jitter: the critical task updates its heartbeat at multiple defined checkpoints within its cycle, not just at the end, so a slow-but-progressing task still passes. I'd also separate "task is late" from "task is stuck": a soft warning or degraded-mode flag for lateness, and a hard reset only for genuine non-progress. That distinction matters clinically — a reset during patient monitoring is itself a disruptive event, so I want to avoid it unless the alternative is worse.

Finally, I'd make the whole mechanism testable and verifiable. I'd want a way to inject a hang (halt the critical task, corrupt its state, starve it of CPU) and confirm the supervisory logic detects it and the device reaches a defined safe state — alarm, display indication, logging — before or instead of a blind reset. The safe-state behavior on reset needs to be defined too: does the device alarm on restart, does it preserve logged data, does it re-enter monitoring cleanly? The watchdog is only as good as the recovery path it triggers.

**Possible follow-ups:** How would you decide the timeout value when the critical task's timing depends on patient physiology that varies widely? And how would you prevent the supervisory task itself from being the single point of failure?

## Q2: How would you approach determining whether a device's software needs Class A, B, or C under IEC 62304, and how would you handle a case where the hardware and software leads disagree on the classification?

**Answer:** Classification flows from hazard analysis, not from intuition about how "important" the software feels. The question IEC 62304 asks is: could a software failure — including a latent bug, an unhandled input, a race — contribute to a hazardous situation that could result in harm? Class A means no injury is possible from software failure; Class B means non-serious injury is possible; Class C means death or serious injury is possible. So the correct process is to start from the ISO 14971 hazard analysis, trace each hazardous situation back to whether software could cause or contribute to it, and let that drive the class. It's an output of risk analysis, not an input chosen for convenience.

The common disagreement is usually about the boundary: one person argues "the software only displays data, the clinician decides," the other argues "if the display is wrong, the clinician acts on wrong data." That's exactly the kind of question that should be resolved by looking at the hazard analysis rather than by seniority. I'd bring both leads back to the specific hazardous situations: for each one, is software a credible contributor? If the display can show a stale or wrong value that a clinician would act on, that's a software-contributable path to harm, and the class should reflect it. The conservative reading is usually correct because the burden is on demonstrating that software cannot contribute, not on assuming it can't.

If the disagreement persists after that analysis, I'd escalate it as a documented decision with rationale rather than letting it sit unresolved — the classification drives the entire software development process rigor (documentation, unit verification, architectural design, detailed design), so an unresolved disagreement is a real project risk. I'd also note that over-classifying is sometimes the pragmatic choice: the cost of Class C process on a Class B device is effort, while the cost of under-classifying is a compliance and safety gap. But I wouldn't default to over-classifying to avoid the conversation — that hides a real analysis question. The right outcome is a defensible, documented classification traceable to the hazard analysis, agreed by both leads and reviewed by quality/regulatory.

**Possible follow-ups:** How would you handle a device where different software items within the same system legitimately fall into different classes? And what would you do if the classification changed mid-project after new hazards were identified?

## Q3: How would you approach designing the filtering strategy for a device that must pass both conducted and radiated emissions limits under IEC 60601-1-2 while also meeting its own signal integrity requirements?

**Answer:** The central tension is that emissions filtering and signal integrity pull in opposite directions: the filter components that suppress high-frequency noise on a power or signal line are the same components that can degrade the edge rates, add phase shift, or introduce resonances that hurt the signal you care about. So I'd start by separating the problem into domains — power input filtering, per-rail decoupling, and I/O/interface filtering — because each has different constraints and different failure modes.

For the mains input, the conducted emissions problem is largely about the differential and common-mode noise the switching supplies and digital loads inject back onto the line. I'd design a multi-stage filter: a common-mode choke plus X and Y capacitors sized against the relevant frequency bands, with the Y-capacitor value bounded by leakage current limits (which is a safety constraint, not just an EMC one — too much Y-capacitance and you fail patient/earth leakage). The filter's effectiveness depends heavily on layout: the filter must be at the connector, with tight return paths and no coupling from the noisy side around the filter. A textbook filter on a bad layout does nothing.

For radiated emissions, the dominant mechanisms are usually cables acting as antennas and loops on the board. I'd attack it at the source — minimize loop areas on high-di/dt and high-dv/dt nets, keep switching nodes small, use ground planes with continuous return paths, and place series termination or ferrites on fast interfaces at the source. For signal integrity, the constraint is that any series element on a high-speed line must be chosen so it doesn't corrupt the eye — a ferrite bead with the wrong impedance profile can ring or slow edges unacceptably. So I'd select filter components by their impedance-vs-frequency curve against both the emissions band and the signal's spectral content, not by a single "it's a ferrite" heuristic.

The practical approach is iterative and measurement-driven: pre-compliance scan early, identify the offending frequencies, and correlate them to specific sources (switching frequency harmonics, clock harmonics, cable resonances) before adding components. Blindly adding filters is how you end up with a design that passes emissions but fails its own accuracy or timing spec. I'd also keep the two requirements in the same verification loop — every filter change gets checked against both the EMC scan and the signal integrity/functional test, so I'm not trading one for the other unknowingly.

**Possible follow-ups:** How would you decide whether a problem is best solved with a filter component versus a layout or grounding change? And how do you handle a case where the Y-capacitor you need for emissions pushes you close to the leakage current limit?

## Q4: How would you approach investigating a field complaint where a device's patient-contacting temperature sensor reads consistently higher than a reference thermometer used by clinical staff, but the device passes its calibration check when returned to the manufacturer?

**Answer:** The fact that it passes calibration at the manufacturer but reads high in the field is the whole clue — it means the discrepancy is context-dependent, not a static offset in the electronics. So I'd resist the temptation to "recalibrate and return it" and instead treat it as a systematic investigation into what differs between the field and the bench. The 8D-style discipline applies: contain, characterize, find root cause, verify, prevent recurrence.

First I'd characterize the complaint precisely: is the offset consistent across units and sites, or clustered? Is it always the same magnitude, or does it vary with patient, ambient temperature, probe placement, or duration of use? That pattern tells me which hypothesis to pursue. Common candidates: thermal path differences (the probe's contact with the patient, insulation, or a thermal mass that changes response time and steady-state reading), self-heating from the electronics that's present in the field but not on the bench, ambient/room temperature differences between the clinical environment and the calibration lab, or a reference-thermometer measurement-site difference (measuring at a different body location than the device's sensor). A consistent positive offset that vanishes on the bench strongly suggests a thermal or placement effect rather than an electronics fault.

I'd then reproduce it: bring the device into an environment that mimics the field — same ambient, same probe placement on a calibrated thermal source or a patient simulator, same duty cycle and self-heating — and see whether the offset reappears. If it does, I can isolate whether it's the sensor, the thermal interface, or the electronics by swapping components one at a time. If it doesn't reproduce, I'd look harder at the clinical measurement method and the reference thermometer's own calibration and placement, because "device reads high" is only meaningful relative to a trusted reference.

The corrective action depends on root cause: if it's a thermal-design or self-heating issue, that's a design change and potentially a field action; if it's a use/placement issue, it's an instructions-for-use and training fix; if it's the reference method, it's a complaint-closure with evidence. Either way I'd document the investigation, verify the fix against the original complaint scenario, and feed it into post-market surveillance so I can detect whether it's an isolated report or an emerging signal.

**Possible follow-ups:** How would you distinguish self-heating from a genuine sensor error in your test setup? And what would you do if the complaint rate were low but the potential harm from a high reading were significant?

## Q5: You're the lead engineer, and during a design review the quality manager insists on adding a risk control measure for a hazard the engineering team considers negligible, while the schedule impact would be significant. How would you handle this situation?

**Answer:** I'd treat this as a disagreement about risk acceptability, not about whether the quality manager is being unreasonable — and the resolution has to be evidence-based, not a negotiation over schedule. The first step is to make sure we're actually arguing about the same thing: get the specific hazard, the estimated severity and probability, and the rationale for "negligible" onto the table in the risk management file. Often the disagreement dissolves once the assumptions are explicit — either the engineering team's probability estimate was optimistic, or the quality manager's concern is already covered by an existing control and the "new" measure is redundant.

If the disagreement survives that, I'd apply the ISO 14971 logic: risk acceptability is judged against defined criteria, and the burden is on demonstrating that the residual risk is acceptable, not on asserting it. If the engineering team believes the risk is negligible, they should be able to show the hazard analysis, the probability rationale, and why existing controls are sufficient. If they can't, the quality manager is right to push. I'd also separate two questions that often get conflated: is the control *necessary* for safety, and is it *worth the schedule cost*? Those are different decisions. A control can be genuinely optional from a safety standpoint but still worth adding if it's cheap; conversely, a control can be important but implemented in a way that's cheaper than the first proposal.

On the schedule impact, I'd look for a path that doesn't force a binary choice: can the control be implemented in a way that doesn't move the critical path — a firmware change instead of a hardware respin, a design change that fits an already-planned revision, a procedural or labeling control instead of a physical one? Risk control doesn't have to mean "add hardware." If the only viable control genuinely pushes the submission, then it becomes a management decision with the trade-off documented: safety benefit versus delay, with the residual-risk rationale recorded either way. I'd escalate that decision rather than unilaterally overruling quality — the quality function has a legitimate independent authority here, and steamrolling it is both a compliance risk and a culture problem.

Throughout, I'd keep the tone collaborative: the quality manager and I have the same goal, which is a device whose residual risk is defensible. Framing it as "help me understand the hazard you're seeing" rather than "you're blocking the schedule" usually gets to a faster, better-documented resolution.

**Possible follow-ups:** What would you do if the quality manager's concern turned out to be valid but the control they proposed was impractical, and a different control would address the same hazard? And how would you document a decision to accept a risk the quality manager still disagreed with?
