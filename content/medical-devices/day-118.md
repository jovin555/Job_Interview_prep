# medical-devices — Day 118

## Q1: How would you approach designing the patient leakage current measurement path for a device that has both BF-type and CF-type applied parts, and how would you decide which measurements are actually required?

**Answer:** The measurement path has to be built around the standard's definitions, not around convenience. Patient leakage current is the current flowing from the applied part, through the patient, to earth — so the measurement network has to represent the patient, and the standard gives you the measuring device (MD) that does that: a defined impedance that stands in for the patient's body. The first design decision is where that MD sits in the circuit for each test condition, because the answer differs depending on whether the applied part is BF or CF and whether you're testing normal condition or single-fault condition.

For a device with both BF and CF applied parts, I'd map out the measurement matrix before touching the fixture. Each applied part gets tested individually and, where the standard requires it, in combination with the other applied parts and with earth. The key distinction is that CF parts have a much tighter limit than BF parts, so the CF part drives the design — you can't share a measurement path that's adequate for BF and assume it's adequate for CF. I'd build a dedicated, low-leakage measurement jig with guarding on the high-impedance nodes, keep the cabling short and fixed, and characterize the fixture's own leakage and offset before trusting any reading. A measurement path that itself leaks a few microamps is useless when you're trying to demonstrate margin against a tight CF limit.

Deciding which measurements are actually required comes from reading the clause structure carefully: the standard specifies the applied-part configuration, the condition (normal vs. single fault, including loss of protective earth and loss of one means of protection), and the polarity of the mains connection. I'd build a traceability table that lists every required measurement, the clause it comes from, the limit, and the configuration — then execute against that table rather than improvising. Where a configuration isn't explicitly required, I'd document why it was excluded, because a reviewer will ask. And I'd measure with margin in mind: a result that passes by a hair is a design signal, not a pass.

**Possible follow-ups:** How would you verify that your measurement fixture itself isn't contributing to the reading? What would you do if a CF applied part passed in normal condition but failed under a single-fault condition involving the other applied part?

## Q2: During IEC 60601-1-2 immunity testing, a device passes radiated RF immunity at most frequencies but shows a reproducible malfunction in a narrow band around one specific frequency. How would you approach diagnosing and resolving it?

**Answer:** A narrow, reproducible band is a gift — it tells you there's a resonance or a specific coupling path, not a general shielding deficiency. The first thing I'd do is characterize the failure precisely: sweep in fine steps around the band to find the exact center frequency and the bandwidth over which it fails, and note whether the malfunction depends on the modulation applied (the standard uses amplitude modulation, and some failures only appear with the modulation envelope, not the carrier). That distinction matters because it separates a carrier-coupling problem from a demodulation problem in a semiconductor junction.

Then I'd form hypotheses about what's resonant at that frequency. Candidates are: a cable harness acting as an antenna at a length that's a quarter-wave multiple, a slot or seam in the enclosure, a ferrite or filter component whose impedance rolls off, or a specific IC input that's picking up the field and rectifying it. I'd test these one at a time — ferrites clipped onto cables, copper tape over seams, temporarily shielding a subsystem — and watch whether the failure frequency shifts or disappears. If adding a ferrite to one cable moves the failure, that cable is the antenna. If covering a seam kills it, it's an aperture.

On the fix side, I'd prefer to attack the coupling path and the victim rather than blanket-shield everything. That usually means: improve the return path so the induced current doesn't flow through a sensitive loop, add common-mode filtering at the cable entry, slow down or add hysteresis to the affected digital input so a small rectified offset doesn't cause a state change, and add firmware-level confirmation (debounce, plausibility check, re-read) so a transient upset doesn't propagate to a user-visible malfunction. Firmware mitigation is legitimate under the standard as long as the device continues to perform its intended function safely, but I'd want the hardware fix to be the primary control and the firmware to be defense in depth. Finally, I'd re-test at the exact failing frequency and at the band edges, and document the root cause and fix in the EMC test report so the next reviewer understands why the design changed.

**Possible follow-ups:** How would you tell the difference between a radiated coupling problem and a conducted one that happens to correlate with the same frequency? If the fix is a firmware plausibility check, how do you demonstrate that it doesn't mask a genuine physiological event?

## Q3: How would you approach classifying a device's software under IEC 62304, and what would you do if the hardware and software leads disagreed on the classification?

**Answer:** Classification starts from the hazard analysis, not from the software architecture. The question IEC 62304 asks is: could a software failure contribute to a hazardous situation, and if so, what's the severity of the resulting harm? Class A means no injury is possible from software failure; Class B means non-serious injury is possible; Class C means death or serious injury is possible. So the classification is a downstream consequence of the risk analysis, and the right way to do it is to walk each software function against the hazard list and ask what happens if it fails, including failures of omission, commission, and timing.

The subtlety is that "the software doesn't control therapy" doesn't automatically mean Class A or B. A monitoring function that drives an alarm can absolutely contribute to serious harm if it fails to alarm or alarms falsely in a way that leads to a delayed response — so the classification has to consider the clinical use, the alarm function, and whether there's an independent hardware or human mitigation. I'd document the reasoning per function, because a device can have mixed classification: some software items Class C, others Class A, with the segregation justified architecturally.

When the hardware and software leads disagree, I'd reframe the conversation away from opinion and toward the hazard analysis. The disagreement usually comes from one person reasoning about the code and the other about the system. I'd get both to walk the same hazard through the same questions: what's the hazardous situation, what's the severity, can software cause or contribute to it, and is there an independent control? If they still disagree, the conservative classification wins until evidence justifies lowering it — you can always argue down with a documented rationale, but arguing up after the fact is much harder. I'd also bring in quality/regulatory early, because the classification drives the whole software development and verification burden, and a late change is expensive.

**Possible follow-ups:** How would you justify a mixed-classification architecture to an auditor? What evidence would you need to downgrade a function from Class B to Class A?

## Q4: You're the lead engineer, and during a design review the quality manager insists on adding a risk control measure for a hazard that the engineering team considers negligible. The schedule impact would be significant. How would you handle this situation?

**Answer:** First, I'd resist the framing that this is engineering versus quality. Both roles are trying to get to the same place — a device that's safe and defensible — and the disagreement is usually about the risk estimate, not about whether the hazard exists. So I'd start by getting the hazard on the table in the risk management file's own terms: what's the hazardous situation, what's the severity, what's the probability of occurrence, and what's the current risk control and residual risk. If the engineering team thinks it's negligible, they should be able to point to the estimate and the rationale. If the quality manager disagrees, they should be able to say which input they think is wrong.

Often the gap is that the engineering team is estimating probability from bench experience while quality is estimating from the clinical use environment, or vice versa. I'd surface that explicitly and, where it matters, get more data rather than argue — a targeted test, a review of complaint history on a similar product, or a clinical input. That converts an opinion contest into an evidence question.

If, after that, the risk genuinely is low and the control is disproportionate, I'd document the rationale for accepting the residual risk and get it reviewed and signed off through the risk management process — that's exactly what the process is for. If the quality manager still wants the control, I'd look for the cheapest control that addresses the concern: sometimes a labeling change, a training item, or a firmware guard costs a fraction of a hardware change and satisfies the intent. And I'd be honest about schedule: I'd bring the cost into the conversation openly rather than letting it be an unspoken reason to dismiss the concern. The one thing I wouldn't do is quietly drop it, because an unresolved risk disagreement that surfaces during an audit or a field issue is far more expensive than the control would have been.

**Possible follow-ups:** What would you do if the quality manager's concern can't be resolved with data before the design freeze? How do you make sure a documented risk acceptance doesn't become a way to avoid legitimate controls?

## Q5: How would you approach verifying that a medical device's firmware correctly handles a situation where the device's non-volatile memory becomes corrupted during normal operation, given that the device must continue monitoring and displaying physiological data in real time?

**Answer:** The verification strategy has to start from the requirement, and the requirement should say what "correctly handles" means: the device must not display corrupted or stale data as if it were valid, must not lose the ability to monitor, and must recover or degrade in a defined, safe way. So I'd break the verification into three layers.

First, fault injection at the storage layer. I'd build a test harness that can corrupt specific regions of non-volatile memory — a header, a record, a checksum field, a wear-leveling table — and run the firmware against each corruption pattern. The point is to exercise every path the firmware has for detecting and responding to bad data: checksums, CRCs, redundancy, version tags, and the recovery logic. I'd include corruption that's detectable (checksum mismatch) and corruption that's silent (a bit flip that still passes a weak check), because the second is where designs fail.

Second, behavior verification during the fault. The device must keep monitoring and displaying real-time physiological data while the storage subsystem is degraded. So the test has to confirm that the monitoring path is decoupled from the storage path — that a storage fault doesn't block the acquisition loop, doesn't stall the display, and doesn't trigger a watchdog reset that takes the device offline. I'd measure timing during the fault, not just functional correctness, because a device that "handles" corruption by freezing for two seconds hasn't handled it.

Third, recovery and data integrity. After the fault, does the device recover to a known-good state, does it preserve the data it could, and does it flag the gap rather than silently filling it? For logged physiological data that may be used clinically, the requirement is usually that the device marks the affected records as invalid or missing rather than presenting them as valid. I'd verify that explicitly.

Throughout, I'd keep the tests deterministic and repeatable — scripted corruption, fixed seeds, automated pass/fail — so they can run in regression. And I'd trace each test back to the requirement and the hazard it mitigates, so the verification evidence is defensible in the DHF.

**Possible follow-ups:** How would you test corruption that occurs during a write, as opposed to between writes? What's your approach if the firmware's recovery path itself depends on reading the corrupted region?
