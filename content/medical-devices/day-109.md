# medical-devices — Day 109

## Q1: How would you approach designing the patient leakage current measurement path for a device that has both BF-type and CF-type applied parts, and how would you decide which measurements are actually required?

**Answer:** I'd start by mapping the applied parts and their classifications against the standard's measurement network definitions, because the measurement path is dictated by the classification, not the other way around. For each applied part I'd identify whether it's BF or CF, whether it's intended for direct cardiac contact, and whether it's earthed or floating in normal condition. Then I'd build the measurement network per the standard's figures — the patient leakage measurement is essentially a defined impedance (the measuring device plus the specified network) connected between the applied part(s) and earth, with the device powered in normal condition and then in each relevant single-fault condition.

The key decisions are: which applied parts get measured individually versus tied together, whether the measurement is made with mains on the applied part in the reversed-polarity case, and whether the CF part requires the tighter limit. CF parts have a much lower patient leakage limit than BF, so if a device has both, the CF part drives the design of the isolation and the measurement setup. I'd also make sure the measurement is done with the device in its worst-case operating mode — for example, with the highest supply voltage within rating and with any patient-connected circuitry active — because leakage can vary with operating state.

On deciding what's actually required: I'd work from the standard's decision tree rather than measuring everything. If two applied parts are of the same type and are connected together in normal use, they may be measured as a group. If an applied part is not accessible in normal use, that changes the measurement. And single-fault conditions only need to be applied where they're plausible and required by the standard — not every conceivable fault. I'd document the rationale for each measurement performed and each one deliberately not performed, because that rationale is what a reviewer or test lab will scrutinize.

**Possible follow-ups:** How would you set up the test to distinguish a genuine design leakage problem from a measurement artifact caused by the test network or the environment? And how would you handle a device where the BF and CF applied parts share a common reference node internally?

## Q2: During IEC 60601-1-2 immunity testing, a device passes radiated RF immunity at most frequencies but shows a reproducible malfunction in a narrow band around one specific frequency. How would you approach diagnosing and resolving it?

**Answer:** A narrow, reproducible band is a strong clue that something in the device is resonant or that a specific internal signal is being demodulated by an unintended nonlinearity. My first step is to characterize the failure precisely: sweep in fine steps around the band to find the exact center frequency and the bandwidth over which it fails, then vary the modulation (CW versus the standard's modulated test signal) and the field orientation and cable placement. If the failure only appears with modulation, that points to demodulation of the RF envelope by a semiconductor junction — often an ESD diode, an op-amp input, or a poorly bypassed reference. If it appears with CW, it's more likely a resonance in a cable, a trace, or an enclosure slot.

Next I'd localize it physically. Moving cables, adding ferrites temporarily, shielding sections with copper tape, or probing with a near-field probe while injecting a local field can tell me whether the coupling path is conducted (through cables) or radiated (through an aperture or a long trace acting as an antenna). I'd also check whether the failure frequency corresponds to a half-wave resonance of a cable or a quarter-wave of a trace, which is a common cause of narrowband susceptibility.

For resolution, the fix depends on the mechanism: if it's demodulation at an input, I'd add or improve filtering and bypassing at that node and consider the input's common-mode range and bias; if it's a cable resonance, I'd address common-mode chokes, cable routing, and shielding termination; if it's an aperture, I'd look at enclosure seams and internal layout. I'd verify the fix at the exact failing frequency and at the band edges, and re-test with margin rather than just passing at the center point, because production variation can shift the resonance.

**Possible follow-ups:** How would you decide whether to fix this in hardware versus adding firmware filtering or error recovery, and what would make you choose one over the other? And how would you confirm the fix is robust across units rather than just the unit you debugged on?

## Q3: How would you approach structuring a risk management file so that it stays useful and auditable throughout a project, rather than becoming a document assembled at the end?

**Answer:** The file stays useful if it's built as a living traceability structure rather than a report. I'd start with the intended use and the hazard identification early — before the design is frozen — because hazards identified late tend to get bolted on as afterthoughts. The core structure I'd use is: intended use and foreseeable misuse, a hazard/hazardous situation list, risk estimation per hazardous situation, risk control measures with their verification evidence, and a residual risk evaluation with an overall benefit-risk conclusion. Each risk control should link forward to the design output that implements it and the verification that proves it works, and backward to the hazard it addresses.

The practical discipline that keeps it alive is making the risk file a required input to design reviews and change control. When a design change is proposed, the first question is which hazards and risk controls it touches, and the file gets updated as part of the change, not afterward. I'd also keep a running "open risks" view so the team can see what's unresolved at any point, rather than discovering a pile of unclosed items at the end.

For auditability, I'd make sure every entry has an owner, a date, and a rationale, and that the traceability is bidirectional — from hazard to control to verification and back. I'd avoid the trap of a risk file that only lists hazards the team already solved; the valuable entries are the ones where the control was hard or where residual risk was accepted with justification. And I'd keep the file's structure stable across the project so reviewers can navigate it, rather than reorganizing it every few months.

**Possible follow-ups:** How would you handle a hazard that's identified during verification, after the design is essentially complete — where does it enter the file and how does it flow through? And how do you keep the risk file consistent with the DHF when the two are maintained by different people?

## Q4: A clinical stakeholder requests a usability change late in development that would require a hardware revision and push the regulatory submission out by several months. How would you evaluate and respond to the request?

**Answer:** I'd treat it as a structured trade-off rather than a yes/no, and I'd start by making sure I understand the actual clinical problem behind the request — often the requested change is one solution to a problem that has a cheaper solution. I'd ask the stakeholder to describe the workflow failure or use error they're trying to prevent, and whether there's evidence (usability testing, complaints, near-misses) behind it. That reframing sometimes reveals that a firmware or labeling change addresses the same risk without touching hardware.

Then I'd quantify the options honestly: the hardware revision path with its schedule, cost, and re-verification/re-validation burden; a firmware-only or labeling-only mitigation with its own limits; and deferring the change to a next revision with a documented rationale. I'd bring in regulatory and quality early, because a usability change late in development can trigger re-assessment under the usability engineering process and potentially affect the submission content, and I don't want to promise a path that regulatory then blocks.

My response to the stakeholder would be a clear recommendation with the trade-offs stated, not a flat refusal. If the change is genuinely necessary for safe use, the schedule impact is the cost of doing it right and I'd advocate for it. If it's a nice-to-have, I'd propose the cheaper mitigation and put the full change on the roadmap. Either way I'd document the decision and its rationale, because "we considered this and chose X because Y" is exactly what a design review and an auditor want to see.

**Possible follow-ups:** How would you handle it if the clinical stakeholder escalates above you because they disagree with your recommendation? And what would you do if the usability issue turns out to be a use error that could lead to harm — does that change the calculus?

## Q5: How would you approach verifying that a medical device's firmware meets IEC 62304 requirements for a Class C software safety classification?

**Answer:** Class C means the software failure could result in death or serious injury, so the verification has to demonstrate that the safety-related requirements are met with a level of rigor that matches that consequence. I'd start from the software requirements and the architecture: every safety-related requirement needs to trace to a verification method, and the architecture needs to show how the safety-critical functions are segregated or protected from non-critical ones. For Class C, the standard expects unit-level verification, integration testing, and system-level testing, plus evidence of the development process controls — the software development plan, detailed design, and the verification plan all need to be consistent with each other.

The verification itself would combine several layers. At unit level, I'd want requirements-based tests plus structural coverage appropriate to the classification — for Class C that generally means statement and branch coverage at minimum, and I'd look at whether the architecture justifies anything beyond that. At integration level, I'd test the interfaces between software items, including fault and error handling paths, because a lot of Class C failures live in the interaction between modules rather than inside one. At system level, I'd verify the safety-related requirements against the actual device, including the alarm and monitoring behavior under fault conditions.

The part people underestimate is the evidence trail: each test needs to trace to a requirement, each requirement to a design element, and any untested code or uncovered branch needs a documented justification. I'd also make sure the anomaly/problem resolution process is real — defects found during verification get logged, assessed for safety impact, fixed, and retested, with the record showing that loop closed. And I'd verify the software configuration and release criteria are met before calling it done, because "the tests passed" isn't the same as "the software is releasable."

**Possible follow-ups:** How would you decide whether a particular safety-related function needs defensive architecture (like a watchdog or redundant channel) versus just thorough testing? And how would you handle a unit that's genuinely unreachable in testing — what's an acceptable justification?
