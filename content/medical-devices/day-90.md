# medical-devices — Day 90

## Q1: How would you approach verifying that a medical device's firmware meets IEC 62304 requirements for a Class B software safety classification?

**Answer:** The starting point is confirming the classification itself is defensible, because everything downstream depends on it. Class B applies when a software failure could contribute to a hazardous situation that is non-serious — so I'd want the classification traced back to the ISO 14971 risk analysis, not decided by intuition. Once that's settled, IEC 62304 imposes a defined set of processes: software development planning, software requirements analysis, architectural design, detailed design and implementation, unit verification, integration and integration testing, system testing, and software release. For Class B, the standard permits some relaxation relative to Class C — for example, unit verification can be less rigorous, and there's no mandatory requirement for independent verification of detailed design — but the process areas themselves still apply.

In practice I'd build the verification evidence around traceability: every software requirement traces to a risk control or a functional need, every requirement traces forward to a test case, and every test result traces back. I'd want the software development plan to state up front which activities are being performed, what the acceptance criteria are, and how anomalies are handled — because a common audit finding is that the plan exists but the actual work deviated from it without a documented rationale. Unit-level verification can be a mix of code review, static analysis, and targeted testing, but the rationale for the chosen methods should be documented. Integration testing should exercise the interfaces between software items, and system testing should verify the software against the system requirements, including the risk control measures implemented in software.

The release criteria are worth defining early: all planned verification complete, all anomalies either resolved or formally accepted with a risk assessment, and the released configuration identified and archived. I'd also make sure the problem resolution process is genuinely used — defect records that show the anomaly was analyzed for safety impact, not just fixed. The evidence should live in the DHF in a form an auditor can navigate without a guide.

**Possible follow-ups:** How would you justify a Class B classification if a reviewer challenged it? What's the difference in verification rigor you'd actually apply between Class B and Class C?

## Q2: How would you approach designing the filtering strategy for a device that has to pass both conducted and radiated emissions limits while also meeting its own signal integrity requirements?

**Answer:** I'd treat this as a single problem rather than two, because the measures that fix emissions and the measures that preserve signal integrity often pull in opposite directions. The first step is understanding where the noise is coming from and how it leaves the enclosure — conducted emissions typically travel out the power and interface cables, while radiated emissions couple from cables, slots, and fast edges. So I'd start with the noise sources: switching power supplies, clock and data edges, motor drive, and any high-current loops. Then I'd map the coupling paths before choosing components, because a filter placed on the wrong path just moves the problem.

For conducted emissions, the classic approach is a two-stage filter — a common-mode choke plus X and Y capacitors — with the layout of the filter itself mattering as much as the component values. The filter has to be referenced to a clean ground, the input and output traces must not couple around the filter, and the Y-capacitor return path has to be short. For radiated emissions, the levers are edge rate control on fast digital lines, series termination, keeping high-frequency return currents close to their traces, and shielding or enclosure design to close slots and seams.

The signal integrity side is where the trade-off bites. Adding series resistance or slowing edge rates reduces emissions but can degrade timing margin; adding capacitance to ground for filtering can load a high-speed line and distort it. So I'd define the signal integrity budget first — what rise time, what eye margin, what jitter the interface can tolerate — and then choose filtering that stays inside that budget. Where a signal is genuinely sensitive, I'd rather isolate it physically (routing, shielding, separation from noisy nets) than filter it electrically. And I'd verify early with pre-compliance scans on a prototype rather than waiting for the formal test, because the fix is far cheaper before the layout is frozen.

**Possible follow-ups:** How would you decide whether a problem is conducted or radiated when you see a failure at a specific frequency? What layout mistakes most commonly undermine an otherwise well-designed input filter?

## Q3: How would you approach deciding whether a given software failure in a medical device should be classified as a safety-related failure requiring formal risk controls, versus a non-safety usability or reliability issue?

**Answer:** The decision has to come out of the risk analysis, not out of a judgment call made in isolation when the defect is found. The question I'd ask is: what is the reasonably foreseeable sequence of events that follows from this failure, and could that sequence lead to harm? A software failure that produces a wrong displayed value, a missed alarm, or a delayed response can be safety-related even if the software itself doesn't control therapy — the harm pathway runs through the clinician's or patient's response to the wrong information. Conversely, a failure that only affects convenience features, logging cosmetics, or a non-clinical display may be a reliability or usability issue.

So the process is: characterize the failure precisely, trace it to the hazardous situations in the risk file, and evaluate whether existing risk controls already mitigate it. If a control was supposed to prevent or detect that failure and it didn't, that's a signal the control is inadequate — which is itself a risk management finding, not just a bug. If the failure maps to a hazardous situation with no adequate control, it needs formal treatment: a risk control, verification of that control, and a re-evaluation of residual risk.

I'd also be careful about the "usability" label. A failure that stems from a confusing interface can still contribute to harm, and usability engineering under IEC 62304 and IEC 62366 is part of the safety story, not separate from it. The defensible position is one where the classification is documented with the reasoning, reviewed by quality, and consistent with how similar failures were treated elsewhere in the file. Inconsistency across the risk file is what auditors pick up on.

**Possible follow-ups:** What would you do if you found a failure that clearly maps to a hazardous situation but the risk file has no entry for it? How do you keep this classification consistent across a large risk file over time?

## Q4: How would you approach selecting materials for a patient-contacting sensor housing that must meet both biocompatibility (ISO 10993) and mechanical durability requirements?

**Answer:** I'd start by defining the contact category precisely, because ISO 10993 is applied by the nature and duration of contact — surface contact versus external communicating device versus implant, and the duration (limited, prolonged, or long-term). That determines which tests are actually required: cytotoxicity is essentially always in scope, but sensitization, irritation, and systemic toxicity depend on contact type and duration. Getting the category wrong either over-tests (cost and schedule) or under-tests (a regulatory problem later).

Then I'd separate the material decision into the bulk material and the patient-contacting surface. The bulk has to meet mechanical requirements — stiffness, impact resistance, resistance to cleaning agents, dimensional stability over the service life — while the surface has to be biocompatible and, importantly, has to stay biocompatible after the manufacturing process. Mold release agents, colorants, adhesives, and sterilization can all change the extractables profile, so the material selection has to be validated on the finished, processed part, not just on the resin datasheet. I'd want the supplier's ISO 10993 data as a starting point, but I'd confirm it applies to the grade and processing route actually used.

Durability and biocompatibility also interact: a material that cracks or crazes in service exposes a fresh surface, and a coating that wears through changes what the patient is contacting. So I'd include aging and cleaning-cycle testing in the material qualification, and I'd consider whether the design can avoid a coating altogether if the coating is the weak point. Where a material change is proposed later, I'd treat it as a design change requiring re-evaluation of the biocompatibility evidence, not a drop-in substitution.

**Possible follow-ups:** How would you handle a supplier who can only provide biocompatibility data for a different grade than the one you're using? What role does sterilization method play in the material selection?

## Q5: You're the lead engineer, and during a design review the quality manager insists on adding a risk control measure for a hazard that the engineering team considers negligible. The schedule impact would be significant. How would you handle this situation?

**Answer:** I'd treat the disagreement as a signal that the risk evaluation isn't shared, and resolve that before arguing about schedule. The first step is to get the hazard on the table in concrete terms: what is the hazardous situation, what's the sequence of events, what's the severity, and what's the probability estimate and its basis? If the engineering team's "negligible" judgment rests on data — occurrence rates, similar-device history, existing controls — then that data should be able to persuade the quality manager. If it doesn't, that's useful information: either the estimate is weaker than the team assumed, or the quality manager is applying a more conservative criterion than the team realized.

I'd also separate two questions that often get conflated: whether the risk is acceptable as-is, and whether a control is feasible. ISO 14971 doesn't require eliminating every risk — it requires that risks be evaluated against defined acceptability criteria and that residual risk be acceptable. So I'd ask the quality manager what criterion they're applying and whether the current residual risk fails it. If it does, the control is justified regardless of schedule, and the conversation becomes about how to implement it efficiently rather than whether to. If it doesn't, the disagreement is about the estimate, and we can resolve it with data.

On schedule, I'd be honest rather than defensive: quantify the impact, look for a control that addresses the hazard with less disruption (a detection measure rather than a design change, for example), and if the impact is genuinely significant, escalate the decision with the trade-off documented rather than letting it stall. The one thing I wouldn't do is let the disagreement sit unresolved — an open risk question at a design review is exactly the kind of thing that becomes an audit finding or, worse, a field issue.

**Possible follow-ups:** What would you do if the quality manager's criterion turned out to be stricter than the company's documented acceptability policy? How would you document a decision to accept a risk without adding the control?
