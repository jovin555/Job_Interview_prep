# medical-devices — Day 24

## Q1: How would you approach verifying that a medical device's firmware correctly handles a situation where a sensor is disconnected or shorted during patient monitoring, given that the device must continue monitoring other parameters and must not generate false alarms?

**Answer:** I'd approach this as a combination of fault injection testing and requirements-based verification. First, I'd ensure the firmware architecture explicitly separates sensor fault detection from the monitoring/alarm logic — each sensor channel should have its own fault state machine that detects open, short, and out-of-range conditions independently. The key design principle is that a fault on one channel must not affect the data path or alarm evaluation of other channels.

For the test strategy, I'd build a fault injection harness that can physically disconnect or short each sensor line (or simulate the electrical condition at the ADC input) while the device is actively monitoring. The test plan would cover: (1) fault detection latency — how quickly the device flags the condition; (2) behavior of unaffected channels — verifying they continue to report valid data with no degradation in accuracy; (3) alarm behavior — confirming that a sensor fault generates an appropriate technical alarm (not a physiological alarm) and does not suppress or delay alarms on other channels; (4) recovery — when the sensor is reconnected, the device should automatically resume normal monitoring after a defined stabilization period, without requiring a power cycle.

A critical detail is the distinction between a "valid but erroneous" reading and a hard fault. An open or short typically produces a recognizable electrical signature (rail voltage, zero-scale reading), but a partially shorted sensor might produce readings within the valid range. So the test plan should also include marginal conditions — for example, a high-impedance connection that produces intermittent readings — to verify the firmware's plausibility checks catch these cases. I'd also verify that the fault handling doesn't interfere with the watchdog timer or other safety mechanisms, since a fault condition might trigger code paths that aren't exercised during normal operation.

**Possible follow-ups:** How would you determine the appropriate alarm priority for a sensor fault versus a physiological alarm? What if the device has a single ADC with a multiplexer — how would you verify that a fault on one channel doesn't affect the other channels through the shared front-end?

## Q2: How would you approach designing a test strategy for verifying that a medical device's firmware correctly handles a situation where the device is in a "suspended" or "paused" state (e.g., during patient transport or a temporary procedure) and a critical alarm condition occurs?

**Answer:** This is fundamentally a question about state machine design and alarm management. The first step is to define the intended behavior clearly in the requirements — what does "suspended" mean for each alarm type? For a critical alarm, the device should typically still alert, but perhaps with a different presentation (e.g., a temporary audible alert that can be silenced, or a visual indicator that persists). For non-critical alarms, suspension might mean they're suppressed entirely or logged for later review.

The test strategy would be built around the state transition matrix: normal → suspended → normal, and normal → suspended → critical alarm → suspended → normal. I'd test each alarm priority level (low, medium, high) in the suspended state, verifying: (1) the alarm is detected and presented according to the suspended-state requirements; (2) the alarm is properly logged with timestamps; (3) when the device returns to normal state, the alarm state is correctly reconciled — for example, if the critical condition persists, the alarm should re-present at full priority; (4) the suspension has a maximum duration or requires explicit user confirmation to prevent indefinite suspension.

A key edge case is what happens if the device is suspended and the critical condition occurs, but then resolves before the user acknowledges the alarm. The device should still log the event and present a "missed alarm" or "alarm occurred during suspension" notification when returning to normal. I'd also test the interaction with the alarm reset/acknowledge mechanism — verifying that a suspended-state alarm can't be accidentally acknowledged without the user being aware of what they're acknowledging.

For the test execution, I'd use a combination of scripted scenarios (predefined sequences of state changes and alarm conditions) and randomized testing to catch unexpected interactions. The test harness would need to inject alarm conditions at precise times relative to state transitions, which requires careful synchronization between the test script and the device's internal clock.

**Possible follow-ups:** How would you handle the situation where the clinical staff intentionally suspends alarms during a procedure, but the device's alarm history needs to show that a critical event occurred during that window? What usability testing would you recommend for the suspension feature to ensure clinicians understand the implications?

## Q3: During a design review for a medical device that uses an optical sensor to measure blood oxygen saturation (SpO2), the firmware engineer proposes using an adaptive filtering algorithm to reduce motion artifacts. The algorithm is complex and difficult to verify deterministically. How would you approach evaluating this proposal?

**Answer:** I'd approach this by separating the technical merit of the algorithm from the verification challenge. The first question is whether the adaptive filter is actually necessary — can the requirement be met with a simpler, deterministic approach? If the device is intended for spot-check measurements in a clinic, a simpler algorithm with a "motion detected — reading unreliable" indicator might be sufficient. If it's for continuous monitoring in a home environment, adaptive filtering might be genuinely necessary.

If the adaptive algorithm is justified, I'd evaluate it against three criteria: (1) determinism — can the algorithm's behavior be characterized well enough to define testable requirements? Even adaptive filters have defined convergence behavior and bounds; (2) failure modes — what happens when the filter converges incorrectly or oscillates? The device needs a mechanism to detect when the filtered output is unreliable; (3) verification feasibility — can we generate test vectors that exercise the algorithm's full range of behavior?

For verification, I'd propose a tiered approach. First, offline validation using recorded physiological signals with known motion artifacts — this can be done in simulation with a large dataset. Second, hardware-in-the-loop testing with a programmable patient simulator that can generate controlled motion artifacts. Third, a limited set of deterministic tests that verify the algorithm's behavior at defined operating points (e.g., no motion, moderate motion, severe motion) and its convergence time after motion stops.

The key concern with adaptive algorithms in medical devices is that they can mask genuine physiological changes — for example, a real desaturation event might be filtered out as an artifact. So the test plan must include scenarios where the "artifact" is actually a true signal change, verifying that the algorithm doesn't suppress real events. I'd also require the algorithm to output a confidence or quality metric that the device can use to flag unreliable readings, rather than silently presenting potentially incorrect data.

**Possible follow-ups:** How would you handle the situation where the algorithm's performance on the test dataset is excellent, but the dataset doesn't cover a specific patient population (e.g., neonates or patients with poor perfusion)? What would you require before accepting the algorithm for clinical use?

## Q4: How would you approach investigating a field complaint where a medical device's patient-contacting temperature sensor is reading approximately 2°C higher than the reference thermometer used by clinical staff, but the device passes its calibration check when returned to the manufacturer?

**Answer:** This is a classic "cannot reproduce" field complaint, and I'd approach it systematically. The first step is to gather as much contextual information as possible from the field: which specific devices are affected, what patient populations, what environmental conditions, and whether the discrepancy is consistent or intermittent. I'd also want to understand how the clinical staff is using the reference thermometer — is it a validated reference, and is it being used correctly?

The fact that the device passes calibration in the lab suggests the issue is either environmental, usage-related, or intermittent. I'd investigate several hypotheses in parallel: (1) thermal coupling — the sensor might be reading correctly but not in good thermal contact with the patient in certain conditions (e.g., if the sensor is applied differently by different staff members); (2) environmental factors — the device might be exposed to direct sunlight, near a heat source, or in a location with poor air circulation; (3) reference thermometer error — the clinical reference might be the one that's inaccurate; (4) intermittent hardware fault — a marginal connection or component that only manifests under specific conditions (temperature, humidity, mechanical stress).

For the investigation, I'd develop a structured data collection plan for the field: ask the clinical staff to record simultaneous readings from the device and a calibrated reference thermometer across multiple patients and conditions, along with photos of the sensor placement. I'd also request that affected devices be returned with detailed usage logs if available. In parallel, I'd review the device's calibration procedure to understand what it actually verifies — a calibration check might only verify the electronics, not the complete sensor assembly including the thermistor and its housing.

If the issue persists without a clear cause, I'd consider a controlled clinical evaluation where the device is used alongside a validated reference under observation, to determine whether the discrepancy is real and under what conditions it occurs. The key principle is to avoid assuming the device is faulty or the clinical staff is wrong — the investigation needs to be hypothesis-driven and data-based.

**Possible follow-ups:** How would you handle the situation where the clinical staff is reluctant to participate in the data collection because they believe the device is simply faulty? What would you do if the investigation reveals that the discrepancy only occurs with a specific patient population (e.g., patients with poor peripheral perfusion)?

## Q5: You're leading a project where the quality manager and the firmware lead disagree on the appropriate software safety classification under IEC 62304 for a medical device that monitors patient physiology and provides alerts, but does not directly control therapy. The quality manager argues for Class B, while the firmware lead argues for Class A. How would you handle this disagreement?

**Answer:** I'd handle this by refocusing the discussion on the standard's intent rather than personal opinions. The IEC 62304 classification is based on the potential for harm to the patient if the software fails — not on whether the software directly controls therapy. The key question is: if the monitoring and alerting software fails to detect a critical condition, or generates a false alert that leads to inappropriate treatment, could that cause harm?

For a device that monitors patient physiology and provides alerts, the argument for Class B is strong: a failure to alert could result in delayed treatment, and a false alert could lead to unnecessary intervention. Both scenarios have the potential for patient harm, even though the software doesn't directly control therapy. Class A is typically reserved for software where failure poses no risk of injury — for example, software that only displays non-critical information or performs administrative functions.

I'd facilitate a structured review where both parties walk through the hazard analysis: what are the credible failure modes of the software, and what is the potential harm for each? We'd use the risk management file to identify the hazards associated with software failure and map them to the classification criteria. If the risk analysis shows that a missed alert could lead to a serious injury, then Class B is clearly appropriate. If the device has redundant safety mechanisms (e.g., a hardware alarm that operates independently of the software), that might support a lower classification — but the firmware lead would need to demonstrate that the hardware backup is truly independent and reliable.

If the disagreement persists after the structured review, I'd escalate to the regulatory affairs team or an external consultant for an independent interpretation. The key is to make the decision based on evidence and the standard's intent, not on schedule pressure or a desire to minimize documentation burden. I'd also document the rationale for the final classification decision in the design history file, including the discussion and the evidence considered.

**Possible follow-ups:** How would you handle the situation where the firmware lead's argument is based on the fact that the device has a hardware watchdog that would detect a software failure? Would that change your assessment? What if the device is intended for home use by patients rather than hospital use by trained clinicians — does that affect the classification?
