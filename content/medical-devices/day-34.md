# medical-devices — Day 34

## Q1: How would you approach designing a test strategy for verifying that a medical device's firmware correctly handles a situation where a sensor provides valid but out-of-range physiological readings (e.g., a heart rate of 240 bpm or a temperature of 42°C)?

**Answer:** I'd start by distinguishing between three cases: readings that are physiologically impossible, readings that are possible but dangerous, and readings that are valid for the sensor but indicate a fault condition. The test strategy needs to cover all three. First, I'd work with clinical input to define the alarm limits and the expected device behavior for each range — for example, a heart rate of 240 bpm might trigger a high-priority alarm and require the device to continue monitoring, while a value outside the sensor's calibrated range might indicate a hardware fault and require a different response. The test plan would include injecting known values at the boundary conditions (just below, at, and just above each threshold) and verifying that the alarm states, displayed values, and logged data all behave correctly. I'd also test the transition between states — for example, what happens when a reading moves from normal to out-of-range and back, and whether the device correctly clears the alarm. For the firmware implementation, I'd expect to see range checking at the point where the raw sensor value is converted to a physiological value, with separate handling for "physiologically plausible but alarming" versus "sensor fault" conditions. The test strategy would also include verifying that the device continues to monitor other parameters correctly while one parameter is out of range, and that the alarm system doesn't get stuck in a state that prevents new alarms from being presented.

**Possible follow-ups:**
- How would you decide whether an out-of-range reading should trigger an alarm or be treated as a sensor fault?
- How would you test the hysteresis behavior when a reading oscillates around an alarm threshold?

## Q2: During a design review for a medical device that uses a wireless link to transmit physiological data to a display unit, the firmware engineer proposes using a proprietary protocol with a simple checksum, while the clinical team requires that data loss be detectable and that the display unit indicate when data is stale. How would you approach this trade-off?

**Answer:** The core issue here is that a simple checksum detects corruption but doesn't detect loss — and for physiological data, missing data can be just as dangerous as corrupted data. I'd frame the discussion around the clinical risk: if the display unit shows data that is actually stale, a clinician might make a decision based on outdated information. The proprietary protocol with a checksum might be acceptable if it includes sequence numbers and a timeout mechanism, but the clinical requirement for staleness indication needs to be designed in from the start. I'd ask the firmware engineer to explain how the protocol handles packet loss — does it use acknowledgments, sequence numbers, or a heartbeat mechanism? If the protocol doesn't provide these, then the design needs to add them at a higher layer. I'd also ask the clinical team to define what "stale" means in practice — is it 2 seconds, 5 seconds, 10 seconds? This drives the timeout value and the display behavior. The solution would likely be a layered approach: the link layer provides error detection and sequence numbering, and the application layer tracks the time since the last valid data packet and displays a "data stale" indicator when that time exceeds the clinical threshold. I'd also consider whether the device needs to buffer data during brief link interruptions and replay it when the link recovers, or whether it's acceptable to display a gap. This is a case where the simplest protocol that meets the clinical requirements is the right choice — but the clinical requirements must be explicit about data loss detection and staleness indication.

**Possible follow-ups:**
- How would you verify that the staleness indication works correctly under real-world wireless conditions like interference or range limits?
- What if the clinical team can't agree on a specific staleness threshold?

## Q3: How would you approach developing a design verification test plan for a medical device that must measure both temperature and pressure, where the two sensors share a common ADC and multiplexer, and the device must maintain specified accuracy for both parameters simultaneously?

**Answer:** The key risk with a shared ADC and multiplexer is crosstalk and settling time — when the multiplexer switches between channels, the ADC needs sufficient settling time to acquire an accurate reading, and the two sensor signals might interact through the multiplexer's on-resistance or charge injection. I'd start by identifying the accuracy requirements for each parameter and the expected signal characteristics — for example, a temperature sensor might have a slow-changing, low-bandwidth signal, while a pressure sensor might have faster dynamics. The test plan would need to verify accuracy under worst-case conditions: when both channels are active, when one channel has a large signal and the other has a small signal, and when the multiplexer is switching at its maximum rate. I'd include tests that verify the settling time is adequate by injecting a step change on one channel and measuring the effect on the other channel's reading. I'd also test the timing of the multiplexer switching relative to the ADC conversion — if the firmware switches channels and immediately starts a conversion, the reading might be corrupted by the previous channel's residual charge. The test plan would include both static accuracy tests (known reference inputs on both channels) and dynamic tests (varying one input while holding the other constant). I'd also verify that the calibration procedure accounts for any offset or gain errors introduced by the multiplexer itself, since the multiplexer's on-resistance can vary with temperature and input voltage. Finally, I'd include a test that verifies the device meets its accuracy specification when both parameters are changing simultaneously, since this is the realistic clinical scenario.

**Possible follow-ups:**
- How would you determine the required settling time for the multiplexer and ADC combination?
- How would you verify that the calibration of one channel doesn't affect the other channel?

## Q4: You're leading a project where a field complaint reports that a medical device's rechargeable battery is swelling after 6-12 months of use in a hospital setting. The device is used for continuous patient monitoring and the battery is not user-replaceable. How would you approach the investigation and corrective action process?

**Answer:** Battery swelling is a serious safety issue — it can indicate thermal runaway risk, mechanical stress on the enclosure, or a charging circuit fault. I'd start by treating this as a potential safety signal and initiating a formal investigation following the company's complaint handling and CAPA procedures. The first step would be to gather data: how many devices are affected, what's the commonality (batch, manufacturing date, firmware version, usage patterns), and what are the clinical circumstances when the swelling was noticed. I'd want to retrieve affected devices and examine the battery, the charging circuit, and the enclosure fit. The investigation would branch into several hypotheses: overcharging due to a charging circuit fault, excessive discharge depth due to firmware behavior, thermal stress from the device's operating environment, or a battery cell defect from a specific manufacturing batch. I'd work with the battery supplier to review the cell specifications and any known failure modes. I'd also review the charge profile in the firmware — is the charging voltage within the cell's specification, and is there proper termination of charging? For the corrective action, I'd consider both immediate actions (notifying users, potentially recalling affected devices) and long-term fixes (hardware changes to the charging circuit, firmware changes to the charge algorithm, or a different battery cell). The risk assessment would need to determine whether the swelling poses an immediate safety risk — if there's any chance of rupture or fire, the field action needs to be expedited. I'd also review the design history to understand why the battery was specified as non-replaceable and whether that decision needs to be revisited given the failure mode.

**Possible follow-ups:**
- How would you prioritize the investigation steps when there are multiple potential root causes?
- How would you communicate the risk to the hospital while the investigation is ongoing?

## Q5: How would you approach verifying that a medical device's firmware meets IEC 62304 requirements for a Class C software safety classification?

**Answer:** Class C is the highest safety classification under IEC 62304, meaning the software can contribute to a hazardous situation. The verification approach needs to be comprehensive and traceable. I'd start by confirming that the software safety classification is correct — this is a documented decision based on the risk analysis, and it drives the entire development and verification effort. For Class C, the standard requires documented software development planning, requirements traceability, architecture design, detailed design, unit verification, integration testing, and system testing. The verification strategy would include static analysis, code reviews, unit testing with coverage analysis, integration testing, and system-level testing against the software requirements. I'd expect to see a requirements traceability matrix that links each software requirement to its design elements, test cases, and verification results. For unit testing, I'd use a coverage tool to measure statement, branch, and MC/DC coverage where appropriate, and I'd document any uncovered code with justification. For integration testing, I'd verify that the software components interact correctly, particularly at interfaces between safety-critical and non-safety-critical modules. At the system level, I'd verify that the software meets its requirements in the context of the complete device, including fault injection testing to verify that the software handles failures safely. I'd also ensure that the verification activities are documented with sufficient detail for a regulatory audit — test procedures, test results, defect tracking, and resolution of any discrepancies. The key is that verification isn't just about running tests — it's about demonstrating that the software development process followed the standard's requirements and that the verification evidence is complete and traceable.

**Possible follow-ups:**
- How would you determine the appropriate level of coverage for unit testing in a Class C device?
- How would you handle a situation where a software defect is found during system testing but the root cause is in a third-party library?
