# medical-devices — Day 93

## Q1: How would you approach verifying that a device's firmware correctly handles a sensor that intermittently produces readings within the valid range but physiologically implausible — for example, a pressure spike that is numerically possible but inconsistent with the patient's condition?

**Answer:** The key insight is that range checking alone is insufficient — a value can be inside the ADC's valid window and still be physiologically impossible. I'd approach this in layers. First, define plausibility criteria beyond min/max: rate-of-change limits (a pressure signal can only slew so fast given the sensor's physical response and the sampling rate), cross-parameter consistency (does a pressure spike correlate with anything else that should accompany it?), and persistence (a single-sample spike is suspect; a sustained change is more likely real). Second, decide the response policy per criterion — a single implausible sample might be flagged and held rather than acted on, while a sustained implausible trend should raise a technical alarm rather than a physiological one, so the clinician knows it's a sensor problem, not a patient problem. Third, make the test strategy explicit: inject synthetic spike sequences at varying amplitudes, widths, and intervals, including spikes that straddle the plausibility threshold, and verify the firmware's behavior at each boundary. I'd also test the interaction with filtering — a median filter may mask single-sample spikes, so the test must confirm the filter doesn't hide a real fast physiological event while suppressing artifacts. Finally, document the rationale for each plausibility limit in the risk file, because those limits are effectively risk controls and need verification evidence.

**Possible follow-ups:** How would you distinguish a genuine fast physiological event from an artifact if both produce a rapid change? Where would you draw the line between a firmware plausibility check and a hardware-level filter?

## Q2: How would you approach determining which IEC 60601-2 particular standards apply to a device that combines two clinical functions — for example, a device that both monitors a physiological parameter and delivers a therapy — and how would you resolve conflicts between the general standard and the particular standards?

**Answer:** I'd start from the device's intended use and clinical claims, not from a keyword search of standard titles — the classification drives everything. I'd map each function to its clinical domain and check the IEC 60601-2 series for a particular standard covering that function, then confirm scope by reading the standard's scope clause rather than assuming from the title. For a combined device, it's common that more than one particular standard applies, and the correct position is usually that all applicable particular standards apply, with the more stringent requirement governing where they overlap. Where two particular standards genuinely conflict — for example, different alarm or accuracy requirements — I wouldn't silently pick one; I'd document the conflict, consult the standards themselves for any stated precedence, and if unresolved, seek a formal interpretation or raise it with the test lab early, because discovering it at test time is expensive. I'd record the applicability rationale in the design history file so a reviewer can follow the reasoning. The general standard always applies as the baseline; particular standards modify or supplement it, they don't replace it.

**Possible follow-ups:** How would you handle a particular standard that applies to only one mode of a multi-mode device? What would you do if a particular standard's requirement seemed clinically inappropriate for your device's use case?

## Q3: How would you approach designing the filtering strategy for a device that has to pass both conducted and radiated emissions limits while also meeting its own signal integrity requirements?

**Answer:** The tension is that an EMI filter and a signal-integrity filter often want opposite things — the EMI filter wants to attenuate high-frequency content aggressively, while the signal path may need that bandwidth. I'd separate the problem by domain: keep the noisy switching and digital sections physically and electrically distinct from the sensitive analog front end, and apply filtering where it belongs rather than globally. For conducted emissions, the filter goes at the power entry — common-mode choke plus X and Y capacitors sized against the applicable limits, with layout of the filter itself treated as critical, since a poorly laid-out filter can couple around its own components. For radiated emissions, the levers are usually return-path integrity, clock edge rates (slow them where timing allows), and shielding/cabling — filtering alone rarely fixes radiated problems. On the signal side, I'd define the bandwidth the measurement actually needs and filter to that, not to the ADC's maximum, so the signal chain isn't carrying noise it doesn't need. Then I'd verify both requirements together, not sequentially — pre-compliance scans with the signal chain active, because a filter that passes emissions but degrades the analog accuracy has just moved the problem. If a conflict is unavoidable, I'd revisit the architecture (e.g., relocate the noise source, change the conversion topology) rather than trying to tune a filter into a corner.

**Possible follow-ups:** How would you decide whether a ferrite bead or an LC filter is appropriate at a given interface? What layout mistakes most often defeat a well-designed EMI filter?

## Q4: How would you approach structuring a risk management file so that it stays useful and auditable throughout a project, rather than becoming a document assembled at the end?

**Answer:** The failure mode I'd design against is the risk file that gets written retrospectively to match a finished design — it's neither useful during development nor credible in an audit. I'd structure it so risk management is a live thread: hazards and hazardous situations identified from intended use, use environment, and the architecture as it evolves; each risk linked to the design inputs it drives and the verification evidence that closes it. The traceability is the point — a reviewer should be able to start at a hazardous situation and walk forward to the risk control, the requirement it generated, and the test that verified it, without hunting across documents. I'd keep the file modular (hazard analysis, risk evaluation, risk control measures, residual risk evaluation, production/post-production monitoring inputs) so changes touch one section rather than forcing a rewrite. Practically, I'd tie risk review to design review gates so the file is updated at the same cadence as the design, and I'd make sure the risk controls that end up in manufacturing or labeling are flagged for design transfer. The test of a good file is whether a new engineer could pick it up mid-project and understand why the design is the way it is.

**Possible follow-ups:** How would you handle a risk that's identified late, after the design is largely frozen? What's the difference between residual risk evaluation and benefit-risk analysis, and where does each live in the file?

## Q5: You're the lead engineer, and during a design review the quality manager insists on adding a risk control measure for a hazard that the engineering team considers negligible. The schedule impact would be significant. How would you handle this situation?

**Answer:** I'd treat the disagreement as a signal that the risk evaluation isn't shared, rather than as an obstacle to route around. First, I'd get to the substance: is the quality manager working from a different severity or probability estimate, a different interpretation of the standard, or knowledge of field history the engineering team doesn't have? Often the gap is that engineering is estimating probability from bench experience while quality is reasoning from worst-case clinical consequence — and for a medical device, severity tends to dominate the calculus. I'd walk through the hazard analysis together and make the assumptions explicit, because "negligible" is a conclusion that needs to be defensible in the file, not a gut call. If the risk genuinely is low, the file should show why — and if it can't, that's useful information. On schedule, I'd separate the decision from the cost: agree on whether the control is warranted first, then work the schedule problem, which might mean a lower-cost implementation, a design change that eliminates the hazard rather than controlling it, or a phased approach. I wouldn't unilaterally overrule a quality function on a safety question — the asymmetry of consequences means the conservative position deserves a real hearing, and if we still disagree after the analysis, that's a decision to escalate with the reasoning documented rather than settle informally.

**Possible follow-ups:** How would you handle it if the analysis confirmed the risk was low but the quality manager still wanted the control? What would you document about a disagreement like this, and where?
