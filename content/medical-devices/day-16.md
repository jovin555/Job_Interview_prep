# medical-devices — Day 16

## Q1: How would you approach designing the patient monitoring algorithm for a device that must detect a critical physiological event (e.g., apnea or arrhythmia) while minimizing false alarms that could cause alarm fatigue in clinical staff?

**Answer:** I'd start by clearly defining the clinical sensitivity and specificity requirements with input from clinicians—understanding what event detection threshold is clinically meaningful versus what constitutes a nuisance alarm. The algorithm design would use a tiered approach: a sensitive detection stage that casts a wide net, followed by a confirmation stage that applies additional criteria (e.g., duration, signal quality checks, cross-parameter correlation) before declaring an alarm. Signal quality assessment is critical—artifacts from patient movement, lead disconnection, or sensor displacement should be identified and either suppress or annotate alarms rather than trigger them. I'd also implement a learning/adaptive component that tracks false alarm patterns in the specific clinical environment, though any adaptive behavior would need careful validation and would be subject to change control. The algorithm would be developed against a curated dataset of annotated physiological signals, including both real clinical events and known artifact patterns, with performance metrics tracked throughout development. Finally, I'd ensure the alarm presentation follows IEC 60601-1-8 requirements for alarm prioritization and escalation, and that the algorithm's performance is validated in a clinical setting with representative patient populations and device usage patterns.

**Possible follow-ups:** How would you handle the trade-off between sensitivity and specificity when clinical stakeholders disagree on the acceptable false alarm rate? What role would the risk management process play in determining alarm thresholds?

## Q2: How would you approach verifying that a medical device's firmware correctly handles a situation where a sensor provides valid but out-of-range physiological readings (e.g., a heart rate of 240 bpm or a temperature of 42°C)?

**Answer:** This is fundamentally a question about how the device distinguishes between a genuine physiological extreme and a sensor malfunction. I'd approach it by first establishing clear definitions in the requirements: what ranges are physiologically plausible, what ranges are physiologically impossible, and what transition rates are realistic. The firmware should implement a state machine that classifies readings as normal, alerting (out-of-range but plausible), or invalid (impossible values or implausible rates of change). For alerting values, the device should trigger appropriate clinical alarms while continuing to monitor—a heart rate of 240 bpm in a neonate might be real, while the same value in an adult warrants a different response. For invalid values, the firmware should flag the data as suspect, potentially request a re-measurement, and if the condition persists, transition to a sensor-failure state with appropriate user notification. I'd also consider redundancy: if multiple parameters are available, cross-checking (e.g., heart rate versus ECG waveform versus oxygen saturation pulse rate) can help validate whether a reading is real. The verification strategy would include fault injection testing to confirm each state transition, boundary testing at range limits, and simulation of realistic physiological scenarios to ensure the device behaves appropriately for both genuine clinical events and sensor artifacts.

**Possible follow-ups:** How would you document the clinical rationale for the alarm thresholds in the design history file? How would you test the device's behavior when the sensor drifts gradually into out-of-range territory versus an abrupt step change?

## Q3: During a design review for a medical device that uses a motor to drive a mechanical actuator, the firmware engineer proposes using a PID control loop implemented in software, while the hardware engineer recommends a dedicated motor control IC with integrated closed-loop control. How would you approach this trade-off?

**Answer:** I'd evaluate this on several dimensions: safety, determinism, development risk, and system complexity. A dedicated motor control IC typically provides hardware-based closed-loop control with guaranteed timing, built-in fault detection (overcurrent, over-temperature, stall detection), and reduced CPU load—which can be attractive for safety-critical applications where the main processor is also handling monitoring functions. However, it adds a component, increases BOM complexity, and may limit flexibility for tuning or algorithm changes. A software PID loop offers more flexibility, easier tuning during development, and potentially lower cost, but introduces concerns about timing determinism—especially if the RTOS scheduler can be delayed by other tasks—and requires careful analysis of worst-case execution time. For a medical device, I'd lean toward a hybrid approach: use the hardware IC for the safety-critical closed-loop control and fault protection, while the firmware handles higher-level functions like speed profiling, user commands, and system-level monitoring. This creates a clean separation where the safety function doesn't depend on software timing. If we went with a software PID, I'd require rigorous analysis of loop timing under all conditions, a watchdog strategy that detects control loop stalls, and hardware-level backup protection (e.g., independent over-speed detection). The decision would also consider the motor type, the consequences of control failure, and whether the actuator's position/speed directly affects patient safety or is a secondary function.

**Possible follow-ups:** How would you verify that the motor control system meets its response time requirements under worst-case conditions? What failure modes would you analyze in the risk management file for the motor control system?

## Q4: How would you approach developing a design verification test plan for a medical device that must operate correctly during brief power interruptions (e.g., when a patient or caregiver accidentally disconnects the device from mains power for 1-2 seconds)?

**Answer:** I'd start by understanding the device's power architecture and what happens during a power interruption: does the device have a battery backup, a supercapacitor, or does it rely solely on mains power? The test plan would depend on the intended behavior during and after the interruption. For a device with battery backup, the key questions are: does the switchover happen seamlessly without affecting monitoring functions, and does the device properly indicate that it's on battery power? For a device without backup, the critical concern is safe shutdown and recovery—data integrity, device state, and user notification. The test plan would include: (1) interruption at various points in the device's operational state (during monitoring, during data logging, during alarm conditions, during firmware updates if applicable); (2) interruptions of varying duration—from brief glitches (milliseconds) to longer outages (seconds); (3) repeated interruptions to test for cumulative effects; (4) interruptions at different points in the AC waveform (peak voltage, zero crossing) to stress the power supply differently; and (5) verification that the device recovers to a known safe state, that logged data is not corrupted, and that any alarms that were active before the interruption are properly restored or re-annunciated. I'd also test the device's behavior when power is restored—does it automatically resume normal operation, or does it require user intervention? The test plan would be documented with pass/fail criteria tied to the device's requirements, and I'd include testing at the extremes of the device's specified operating voltage range.

**Possible follow-ups:** How would you determine the acceptable duration of power interruption that the device must withstand? How would you verify that data logged during the interruption is not corrupted or lost?

## Q5: You're leading a project where a senior firmware engineer and a senior hardware engineer disagree on whether a device failure observed during system integration testing is caused by a firmware timing issue or a hardware signal integrity problem. The failure is intermittent and occurs only when the device is operating at elevated temperature. How would you handle this disagreement and drive the investigation forward?

**Answer:** I'd approach this by structuring the investigation to gather data rather than letting the disagreement become a matter of opinion. First, I'd ensure we have a clear, reproducible description of the failure—what exactly happens, what the device is doing at the time, and what the observable symptoms are. Then I'd work with both engineers to design experiments that can discriminate between the two hypotheses. For the firmware timing hypothesis, we might add diagnostic logging to capture task execution times, interrupt latency, and any timing violations around the failure point. For the hardware hypothesis, we might add instrumentation to monitor signal integrity—checking for glitches, ringing, or voltage droop on the relevant lines. The elevated temperature aspect is a key clue: it suggests we should characterize the failure across a temperature range to see if there's a threshold effect, which could point to a component derating issue (hardware) or a timing margin that degrades with temperature (could be either). I'd also consider whether the failure correlates with specific device states or operations, which might narrow the search. Rather than having the two engineers argue, I'd facilitate a structured root-cause analysis using a fishbone diagram or similar tool to systematically list potential causes and design experiments to eliminate them. I'd also make sure we're capturing good failure data—using a logic analyzer or oscilloscope triggered on the failure event, and ensuring the firmware logs enough context. If the investigation stalls, I might bring in a third-party expert or use simulation tools to model the suspected failure mechanisms. The key is to keep the investigation data-driven and collaborative, and to document findings as we go so the eventual root cause is well-supported.

**Possible follow-ups:** How would you handle the situation if the investigation reveals that both issues are contributing to the failure? What role would the risk management process play in deciding whether to fix the root cause or implement a mitigation?
